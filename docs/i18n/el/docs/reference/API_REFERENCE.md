## Ολοκληρώσεις Συνομιλίας

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Προσαρμοσμένες Κεφαλίδες

| Κεφαλίδα                 | Κατεύθυνση | Περιγραφή                                                                                                                                                                                                                                   |
| ------------------------ | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Αίτημα     | Ορίστε την τιμή σε `true` για παράκαμψη της κρυφής μνήμης                                                                                                                                                                                   |
| `x-omniroute-no-memory`  | Αίτημα     | Ορίστε την τιμή σε `true` για παράλειψη της εισαγωγής μνήμης και δεξιοτήτων για αυτό το αίτημα (αντιστοιχεί στη συμπεριφορά no-cache και αποφεύγει την επιβάρυνση διακριτικών/κόστους ανά κλήση)                                            |
| `X-OmniRoute-Progress`   | Αίτημα     | Ορίστε την τιμή σε `true` για συμβάντα προόδου                                                                                                                                                                                              |
| `X-Session-Id`           | Αίτημα     | Μόνιμο κλειδί συνεδρίας για συσχέτιση εξωτερικής συνεδρίας                                                                                                                                                                                  |
| `x_session_id`           | Αίτημα     | Γίνεται επίσης αποδεκτή η παραλλαγή με κάτω παύλες (απευθείας HTTP)                                                                                                                                                                         |
| `X-OmniRoute-Session-Id` | Αίτημα     | Ετικέτα συνεδρίας/συνομιλίας που παρέχεται από τον καλούντα (τροφοδοτεί επίσης τη μνήμη). Όταν υπάρχει, αποθηκεύεται αυτούσια στο `call_logs.session_tag` για απόδοση κόστους ανά συνεδρία (#8249) — δεν δημιουργείται ποτέ όταν απουσιάζει |
| `Idempotency-Key`        | Αίτημα     | Κλειδί αποδιπλοποίησης (παράθυρο 5 δευτερολέπτων)                                                                                                                                                                                           |
| `X-Request-Id`           | Αίτημα     | Εναλλακτικό κλειδί αποδιπλοποίησης                                                                                                                                                                                                          |
| `x-omniroute-connection` | Αίτημα     | Καρφιτσώστε ένα αίτημα μεμονωμένου μοντέλου σε μία σύνδεση παρόχου (λογαριασμό) βάσει του αναγνωριστικού της — δείτε [Καρφίτσωμα λογαριασμού ανά αίτημα](#account-pinning-per-request)                                                      |
| `X-OmniRoute-Cache`      | Απόκριση   | `HIT` ή `MISS` (χωρίς ροή)                                                                                                                                                                                                                  |
| `X-OmniRoute-Idempotent` | Απόκριση   | `true` εάν έγινε αποδιπλοποίηση                                                                                                                                                                                                             |
| `X-OmniRoute-Progress`   | Απόκριση   | `enabled` εάν είναι ενεργοποιημένη η παρακολούθηση προόδου                                                                                                                                                                                  |
| `X-OmniRoute-Session-Id` | Απόκριση   | Το πραγματικό αναγνωριστικό συνεδρίας που χρησιμοποιήθηκε από το OmniRoute                                                                                                                                                                  |
| `X-OmniRoute-Request-Id` | Απόκριση   | Αναγνωριστικό συσχέτισης αιτήματος (όταν είναι γνωστό)                                                                                                                                                                                      |
| `X-OmniRoute-Version`    | Απόκριση   | Έκδοση build του OmniRoute (υπάρχει πάντα)                                                                                                                                                                                                  |
| `X-OmniRoute-Cost-Saved` | Απόκριση   | Το ποσό σε USD που εξοικονομήθηκε μέσω της κρυφής μνήμης σε περίπτωση HIT (μόνο για επιτυχίες κρυφής μνήμης)                                                                                                                                |
| `X-OmniRoute-Decision`   | Απόκριση   | Ίχνος δρομολόγησης: `strategy=<name>; provider=<alias>; latency_ms=<n>` (το `<name>` είναι η στρατηγική συνδυασμού ή `single` για αίτημα που δεν αφορά συνδυασμό) — υπάρχει πάντα στις αποκρίσεις ολοκλήρωσης                               |

> Σημείωση για το Nginx: αν βασίζεστε σε κεφαλίδες με κάτω παύλες (για παράδειγμα `x_session_id`), ενεργοποιήστε το `underscores_in_headers on;`.

#### Καρφίτσωμα λογαριασμού ανά αίτημα

Όταν ένας πάροχος έχει πολλές συνδέσεις (λογαριασμούς ή κλειδιά), το OmniRoute συνήθως επιλέγει μία
μέσω της στρατηγικής επιλογής λογαριασμού του. Εναλλακτικά, ένα αίτημα μπορεί να καρφιτσώσει μία συγκεκριμένη σύνδεση
με την κεφαλίδα `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Πού θα βρείτε το αναγνωριστικό.** Ανοίξτε τη σελίδα του παρόχου στον πίνακα ελέγχου
  (**Πίνακας ελέγχου → Πάροχοι → <provider>**) και κάντε κλικ στο πλακίδιο αναγνωριστικού `xxxxxxxx…` σε μια γραμμή
  σύνδεσης — έτσι αντιγράφεται το πλήρες αναγνωριστικό σύνδεσης.
- **Ποια αιτήματα το λαμβάνουν υπόψη.** Αιτήματα ενός μοντέλου (`provider/model`) στα
  `/v1/chat/completions`, `/v1/messages` και `/v1/responses`. Οι συνδυασμοί αγνοούν την κεφαλίδα: καρφιτσώστε
  έναν λογαριασμό ανά βήμα συνδυασμού μέσω της σύνδεσης του ίδιου του βήματος.
- **Το καρφίτσωμα είναι αυστηρό, όχι προτίμηση.** Χρησιμοποιείται αποκλειστικά η καρφιτσωμένη σύνδεση. Μια
  αποτυχία εντός του αιτήματος καταγράφει την περίοδο αναμονής του λογαριασμού, αλλά **δεν** μεταβαίνει σε
  άλλον λογαριασμό του ίδιου παρόχου.
- **Η περίοδος αναμονής και το όριο χρήσης αποδεσμεύουν το καρφίτσωμα.** Όσο η καρφιτσωμένη σύνδεση βρίσκεται σε περίοδο αναμονής,
  έχει εξαντλήσει το όριο χρήσης ή αποκλείεται από μια πολιτική ορίων χρήσης, τα επόμενα αιτήματα χρησιμοποιούν εναλλακτικά τις άλλες
  συνδέσεις του παρόχου, ακριβώς όπως η μη καρφιτσωμένη κίνηση.
- **Άγνωστα ή απενεργοποιημένα αναγνωριστικά προκαλούν αποτυχία.** Ένα αναγνωριστικό που δεν βρίσκεται στην ενεργή ομάδα του παρόχου (έχει διαγραφεί,
  απενεργοποιηθεί ή ανήκει σε άλλον πάροχο) δεν αφήνει κανέναν επιλέξιμο λογαριασμό, οπότε το αίτημα
  αποτυγχάνει αντί να δρομολογείται σιωπηρά αλλού.

Το Claude Code στέλνει προσαρμοσμένες κεφαλίδες μέσω του `ANTHROPIC_CUSTOM_HEADERS`. Τοποθετήστε το στο μπλοκ `env`
του `~/.claude/settings.json` ή σε ένα `.claude/settings.json` σε επίπεδο έργου, για να καρφιτσώσετε διαφορετικό
λογαριασμό ανά έργο:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Πηγή: `src/sse/handlers/chat.ts` (ανάγνωση κεφαλίδας), `src/sse/services/auth.ts` και
`src/sse/services/sessionAffinityPin.ts` (αποδέσμευση καρφιτσώματος και έλεγχος απουσίας από την ομάδα).

> **Κεφαλίδες τηλεμετρίας κόστους:** οι επιτυχείς αποκρίσεις χωρίς ροή περιλαμβάνουν επίσης το σύνολο τηλεμετρίας κόστους `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, σταθερά 10 δεκαδικά ψηφία· `0.0000000000` για δωρεάν υπηρεσίες ή υπηρεσίες χωρίς τιμολόγηση), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` και `X-OmniRoute-Fallback-Attempts` (μόνο όταν > 0), καθώς και `X-OmniRoute-Request-Id` και `X-OmniRoute-Version`. Αυτές εκπέμπονται από τις ολοκληρώσεις συνομιλίας, τα `/v1/responses`, `/v1/messages`, **καθώς και τα τελικά σημεία πολυμέσων** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` και `/v1/moderations` (πάντα με κόστος `0`). Το κόστος πολυμέσων υπολογίζεται ανά τροπικότητα (ανά εικόνα, ανά δευτερόλεπτο, ανά χαρακτήρα, ανά μονάδα αναζήτησης), όταν υπάρχουν διαθέσιμες τιμές· διαφορετικά είναι `0` (fail-open).

> **Σημασιολογία κόστους για επιτυχία από την κρυφή μνήμη:** σε ένα HIT της σημασιολογικής κρυφής μνήμης (`X-OmniRoute-Cache-Hit: true`) δεν πραγματοποιείται κλήση προς ανάντη υπηρεσία, επομένως το `X-OmniRoute-Response-Cost` είναι `0.0000000000` (το **επαυξητικό** κόστος εξυπηρέτησης της επιτυχίας). Το αρχικό κόστος ή το κόστος που θα προέκυπτε αναφέρεται ξεχωριστά στο `X-OmniRoute-Cost-Saved`. Οι καταναλωτές δεδομένων χρέωσης θα πρέπει να αθροίζουν το `X-OmniRoute-Response-Cost` (οι επιτυχίες από την κρυφή μνήμη δεν κοστίζουν τίποτα)· τα αναλυτικά στοιχεία της κρυφής μνήμης μπορούν να συγκεντρώνουν το `X-OmniRoute-Cost-Saved`.

## Αποκλειστικές μισθώσεις διαχειριζόμενων συνεδριών

Η αποκλειστική μίσθωση διαχειριζόμενων συνεδριών είναι μια προαιρετική σύμβαση δρομολόγησης, ανεξάρτητη από τον πελάτη: ένας ενεργός κάτοχος
δεσμεύει μία επιλέξιμη σύνδεση OmniRoute. Δεν μισθώνει ένα μοντέλο, δεν απαιτεί OAuth, δεν προσδιορίζει έναν
συγκεκριμένο πελάτη και δεν απαιτεί συγκεκριμένο πάροχο.

Το κλειδί API που χρησιμοποιείται για τον έλεγχο ταυτότητας πρέπει να έχει το πεδίο εφαρμογής `lease:exclusive` και μια ρητή, μη κενή
λίστα `allowedConnections`. Το όριο μεταβολής της βάσης δεδομένων επιβάλλει και τα δύο πεδία μαζί κατά τη
δημιουργία κλειδιού και τις μερικές ενημερώσεις.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Οι επιτυχείς αποκρίσεις απόκτησης, ανανέωσης και αποδέσμευσης εκθέτουν χρονικές σημάνσεις, το `state` και την ακριβή θετική
`generation`, αλλά ποτέ την επιλεγμένη σύνδεση ή τα διαπιστευτήρια. Η ανανέωση και η αποδέσμευση παρέχουν τη
γενιά στο σώμα JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Ο κάτοχος μιας ενεργής μίσθωσης μπορεί να ζητήσει ρητά ασφαλή ως προς το απόρρητο μεταδεδομένα εμφάνισης για την τρέχουσα δέσμευσή του:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Αυτή η προαιρετική ενέργεια κατάστασης προστατεύεται από τον αδιαφανή κάτοχο, το πιστοποιημένο διαχειριζόμενο κλειδί API και την ακριβή
ενεργή γενιά, σε μία συναλλαγή βάσης δεδομένων. Το `displayName` είναι μόνο το περικομμένο ρυθμισμένο
όνομα σύνδεσης· είναι `null` όταν δεν υπάρχει ασφαλές ρυθμισμένο όνομα. Το OmniRoute δεν το αντικαθιστά ποτέ με
διεύθυνση email ή παραγόμενη ταυτότητα λογαριασμού. Η τιμή παρόχου είναι μια μη ευαίσθητη ετικέτα εμφάνισης και ποτέ
ένα παραγόμενο αναγνωριστικό συμβατού παρόχου. Εξαιρούνται τα διαπιστευτήρια, τα διακριτικά, τα cookies, τα ακατέργαστα αναγνωριστικά σύνδεσης ή κλειδιών
API, τα hash κατόχων, τα μυστικά περίφραξης και τα εσωτερικά δεδομένα δρομολόγησης.

Οι αναζητήσεις με λανθασμένο κλειδί, λανθασμένο κάτοχο, παρωχημένη γενιά, καθώς και οι αναζητήσεις που αφορούν μίσθωση που λείπει, έχει λήξει, έχει αποδεσμευτεί ή έχει ακυρωθεί,
επιστρέφουν όλες το ίδιο σφάλμα `409 LEASE_FENCE_STALE` χωρίς μεταδεδομένα σύνδεσης. Ένας πελάτης που έλαβε την απόκριση αναμονής χωρητικότητας δεν έχει ενεργή δέσμευση προς επιθεώρηση. Όταν η δρομολόγηση μεταφέρει μια ενεργή μίσθωση,
η ίδια γενιά παραμένει έγκυρη και η κατάσταση επιστρέφει ατομικά τη νέα δέσμευση, ποτέ την παλιά.
Οι υπάρχοντες πελάτες παραμένουν αμετάβλητοι, επειδή οι αποκρίσεις απόκτησης, ανανέωσης, αποδέσμευσης και αναμονής διατηρούν
τις προηγούμενες δομές τους.

Αυτή η σύμβαση διακομιστή δεν αλλάζει το τυπικό `/status` του OpenAI Codex. Το τυπικό Codex αναφέρει επί του παρόντος τον
πάροχο μοντέλου και την ενσωματωμένη κατάσταση ελέγχου ταυτότητας/λογαριασμού, αλλά δεν εμφανίζει αυθαίρετα προσαρμοσμένα
μεταδεδομένα λογαριασμού παρόχου· μια μεταγενέστερη ενσωμάτωση πελάτη πρέπει να καλεί αυτή την ενέργεια και να αποφασίζει πώς θα
εμφανίζει το `connection.displayName`.

Στη συνέχεια, κάθε διαχειριζόμενο αίτημα συμπερασμού παρέχει και τις δύο κεφαλίδες ελέγχου:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Ο ακριβής κάτοχος, η γενιά, η ενεργή σύνδεση και το πιστοποιημένο κλειδί API περιφράσσονται αμέσως
πριν από κάθε υποστηριζόμενη απόπειρα προς ανάντη υπηρεσία. Η επανάληψη του κατόχου και της γενιάς με άλλο κλειδί αποτυγχάνει ακόμη
και όταν αυτό το κλειδί επιτρέπει την ίδια σύνδεση. Οι ακατέργαστες τιμές κατόχου δεν αποθηκεύονται μόνιμα, δεν καταγράφονται, δεν διατηρούνται στο
στιγμιότυπο αιτήματος και δεν προωθούνται προς τα ανάντη.

Η προσωρινή διεκδίκηση πόρων επιστρέφει HTTP `429` με `Retry-After` και:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Αυτή η απόκριση σημαίνει μόνο ότι το συνηθισμένο σύνολο επιλέξιμων συνδέσεων δεν ήταν κενό και κάθε ελεύθερη υποψήφια σύνδεση
δεσμευόταν από μια ξένη ενεργή μίσθωση. Τα μη υποστηριζόμενα μοντέλα/οι μη υποστηριζόμενοι πάροχοι, η ασυμφωνία πολιτικής, η περίοδος αναμονής, το όριο χρήσης,
η εύρυθμη λειτουργία και άλλες συνηθισμένες αποτυχίες επιλεξιμότητας διατηρούν τις υπάρχουσες αποκρίσεις OmniRoute.

### `x-omniroute-compression`

Παράκαμψη του σχεδίου συμπίεσης ανά αίτημα. Έχει την υψηλότερη προτεραιότητα — υπερισχύει της παράκαμψης συνδυασμού δρομολόγησης,
του ενεργού προφίλ, της αυτόματης ενεργοποίησης και της προεπιλογής του πίνακα. Τιμές:

| Τιμή          | Αποτέλεσμα                                                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `off`         | Καμία συμπίεση για αυτό το αίτημα.                                                                                                      |
| `default`     | Το προφίλ Default που προκύπτει από τον πίνακα (αγνοεί το ενεργό προφίλ). Οι μηχανές με απώλειες παραμένουν απενεργοποιημένες.          |
| `safe`        | Μόνο αποδιπλοποίηση και σύμπτυξη κενών διαστημάτων.                                                                                     |
| `allow-lossy` | Διατήρηση του σχεδίου του χειριστή για αυτό το αίτημα, συμπεριλαμβανομένων των συνόψεων και των αναδιατυπώσεων ύφους.                   |
| `engine:<id>` | Μία μόνο μηχανή, όταν είναι ενεργοποιημένη, π.χ. `engine:rtk`. Προαιρετική ενεργοποίηση ανά αίτημα για αυτή τη μηχανή.                  |
| `<combo>`     | Ένας ονομασμένος συνδυασμός, που αντιστοιχίζεται πρώτα βάσει ονόματος (χωρίς διάκριση πεζών-κεφαλαίων) και έπειτα βάσει αναγνωριστικού. |

Σημειώσεις:

- Οι άγνωστες τιμές αγνοούνται (το αίτημα δεν απορρίπτεται ποτέ)· η επίλυση συνεχίζει με την κανονική σειρά προτεραιότητας του χειριστή.
- Αν πολλοί συνδυασμοί έχουν το ίδιο όνομα, περάστε το **αναγνωριστικό** του συνδυασμού για ντετερμινιστική αντιστοίχιση.
- Ένας συνδυασμός του οποίου το όνομα είναι `off` ή `default` δεν μπορεί να επιλεγεί βάσει ονόματος (αυτές οι λέξεις-κλειδιά ερμηνεύονται πρώτα)· αναφερθείτε σε έναν τέτοιο συνδυασμό μέσω του αναγνωριστικού του.
- Ο κύριος διακόπτης συμπίεσης αποτελεί απόλυτη δικλείδα: όταν η συμπίεση είναι καθολικά απενεργοποιημένη, αυτή η κεφαλίδα δεν μπορεί να την ενεργοποιήσει.

Το εφαρμοσμένο σχέδιο επιστρέφεται στην κεφαλίδα απόκρισης:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

όπου το `<source>` είναι ένα από τα `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` ή `off`.

## Ενσωματώσεις

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Διαθέσιμοι πάροχοι: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Τα αναγνωριστικά καταλόγου έχουν τη μορφή `provider/model` (παράδειγμα: `jina-ai/jina-embeddings-v5-omni-small`). Τα απλά αναγνωριστικά μοντέλων Jina που εμφανίζονται στο μητρώο (για παράδειγμα `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) επιλύονται επίσης. Οι λειτουργίες embed/rerank/classify/segment της Jina χρησιμοποιούν πρώτα τα διαπιστευτήρια `jina-ai` του πίνακα ελέγχου· το `JINA_AI_API_KEY` χρησιμοποιείται ως εφεδρική επιλογή μόνο όταν δεν υπάρχει κλειδί στον πίνακα ελέγχου. Η κάρτα `jina-reader` προορίζεται μόνο για το Reader / `r.jina.ai` (`POST /v1/web/fetch`) και δεν παρέχει ποτέ ενσωματώσεις ή ανακατάταξη.

Τα μοντέλα μητρώου που δηλώνουν υποστήριξη πολλαπλών τρόπων εισόδου δέχονται επίσης έως και 32 δομημένα στοιχεία ανεξάρτητα από πάροχο.
Οι τύποι στοιχείων πολυμέσων είναι `text`, `image`, `audio`, `video` και `document`. Το `source` των πολυμέσων
είναι είτε `{"type":"url","url":"https://..."}` είτε
`{"type":"base64","data":"...","media_type":"..."}`.

Το Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
και το ψευδώνυμο οικογένειας `jina-ai/jina-embeddings-v5-omni` → omni-small) δέχεται επίσης τα εγγενή
έγγραφα EmbeddingsV5Request της Jina και **τα προωθεί αυτούσια** στο `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Οι εγγενείς τιμές `{ image | audio | video | pdf }` μπορούν να είναι ένα δημόσιο URL HTTPS, ένα URI `data:` ή ακατέργαστα
δεδομένα base64. Το OmniRoute δεν μετατρέπει αυτά τα αντικείμενα σε συμβολοσειρές ούτε ανακτά εγγενή URL εικόνων — η Jina ανακτά
η ίδια τα δημόσια πολυμέσα. Τα πρόσθετα πεδία της Jina (`task`, `normalized`, `truncate`, `embedding_type`)
προωθούνται. Τα SKU της Jina που υποστηρίζουν μόνο κείμενο εξακολουθούν να απορρίπτουν έγγραφα που δεν είναι κείμενο.

Όρια ασφαλείας και μεταφοράς:

- Τα απομακρυσμένα URL πολυμέσων πρέπει να είναι δημόσια URL HTTPS. Τα κανονικοποιημένα στοιχεία `{type,source:url}` ανακτώνται
  από την πλευρά του διακομιστή (επανεπικύρωση ανακατευθύνσεων, χρονικό όριο, όρια μεγέθους, δημόσιο DNS, σταθερή σύνδεση) και
  ενσωματώνονται πριν από την κλήση προς τον πάροχο. Τα εγγενή στοιχεία Jina `{image:"https://..."}` προωθούνται ως έχουν
  μετά τον ίδιο έλεγχο δημόσιου HTTPS· η Jina ανακτά το URL.
- Τα ενσωματωμένα πολυμέσα base64 περιορίζονται σε 8 MiB αποκωδικοποιημένων δεδομένων ανά στοιχείο και 16 MiB αποκωδικοποιημένων δεδομένων συνολικά για το αίτημα.

Μετάφραση ανά πάροχο (τα κανονικοποιημένα στοιχεία δεν προωθούνται ποτέ χωρίς αλλαγές):

- Πολυτροπικά μοντέλα Jina: κάθε στοιχείο ανώτατου επιπέδου μετατρέπεται σε ένα αντικείμενο με κλειδί τρόπου εισόδου
  (`text` / `image` / `audio` / `video` / `pdf`), χρησιμοποιώντας URI δεδομένων για ενσωματωμένα πολυμέσα· ένα διάνυσμα ανά
  στοιχείο ανώτατου επιπέδου.
- Οικογένεια Gemini Embedding 2: ένας πίνακας ανώτατου επιπέδου μετατρέπεται σε ένα ενιαίο εγγενές
  αίτημα `models/{model}:embedContent` με `content.parts` (`text` ή `inline_data`).
- llama.cpp (`llama-cpp/<model>`, οποιοδήποτε μοντέλο έχει φορτωθεί από τον τοπικό διακομιστή): τα κανονικοποιημένα στοιχεία `text`
  μετατρέπονται σε απλές συμβολοσειρές, ενώ τα `image` / `audio` / `video` μετατρέπονται το καθένα σε ένα
  αντικείμενο `{"content": [part]}`, χρησιμοποιώντας τα τμήματα περιεχομένου συνομιλίας του llama-server (`image_url`,
  `input_audio` με μορφή `wav` / `mp3` / `flac`, `input_video`) με ενσωματωμένα δεδομένα· ένα διάνυσμα
  ανά στοιχείο ανώτατου επιπέδου. Ο διακομιστής πρέπει να εκτελείται με `--embedding --mmproj …`· χωρίς προβολέα,
  απορρίπτει ο ίδιος τα πολυμέσα. Το `document` δεν υποστηρίζεται.
- Άγνωστα/δυναμικά μοντέλα χωρίς ρητά μεταδεδομένα τρόπου εισόδου απορρίπτουν τη δομημένη είσοδο με HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Οι μη υποστηριζόμενοι συνδυασμοί μοντέλου/τρόπου εισόδου επιστρέφουν HTTP 400 αντί να εξαναγκάζουν τη μετατροπή του στοιχείου. Τα πεδία επέκτασης
που δεν αφορούν την είσοδο σε παλαιού τύπου αιτήματα συμβολοσειρών/token εξακολουθούν να προωθούνται χωρίς αλλαγές.

```bash
# Παράθεση όλων των μοντέλων ενσωματώσεων
GET /v1/embeddings
```

## Δημιουργία εικόνων

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Οι διαθέσιμοι πάροχοι περιλαμβάνουν τους OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (τοπικά), ComfyUI (τοπικά).

Το `n` επιστρέφει `n` εικόνες στο `data[]`. Για παρόχους των οποίων το upstream API επιστρέφει μία εικόνα ανά κλήση
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), πραγματοποιούνται `n` ξεχωριστές upstream κλήσεις, με έως και 4 να εκτελούνται ταυτόχρονα. Ένα
σταθερό `seed` μετατοπίζεται βάσει του δείκτη κλήσης (`seed`, `seed + 1`, …), ώστε οι εικόνες να διαφέρουν αλλά να παραμένουν
αναπαραγώγιμες. Το `n` περιορίζεται σε μέγιστη τιμή 10. Το αίτημα αποτυγχάνει συνολικά εάν αποτύχει οποιαδήποτε κλήση. Η λίστα
των μορφών fan-out βρίσκεται στο `SINGLE_IMAGE_FANOUT_FORMATS` στο
`open-sse/handlers/imageGeneration/fanOut.ts`.

Το ZenMux επαναχρησιμοποιεί την υπάρχουσα σύνδεση κλειδιού API και δέχεται τα προθέματα `zenmux/` ή `zm/`:

- Το `zenmux/openai/gpt-image-2` χρησιμοποιεί το OpenAI Images API του ZenMux. Οι επιλογές περιλαμβάνουν τα `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` και `response_format`.
- Άλλοι εκδότες, όπως το `zm/meta/muse-image-1.0`, χρησιμοποιούν το endpoint `:predict`
  του Vertex AI μέσω ZenMux. Το `n` αντιστοιχίζεται στο `sampleCount`, το `aspect_ratio` στο `aspectRatio` και το `image_size`
  (`1K`, `2K`, `4K`) στο `sampleImageSize`. Ένα `size` σε pixel παρέχει μόνο αναλογία διαστάσεων,
  όχι εγγυημένες διαστάσεις σε pixel. Οι υποστηριζόμενες αναλογίες, αναλύσεις και αριθμοί διαφέρουν ανά μοντέλο.
- Το `zm/inclusionai/ming-image-0.1-design` επιλέγει τις δικές του διαστάσεις. Παραλείψτε τα `size`,
  `aspect_ratio` και `image_size`· οι ρητές τιμές επιστρέφουν HTTP 400. Μπορείτε να ζητήσετε PNG, JPEG και WebP
  μέσω του `output_format`.

Αυτή η ενσωμάτωση υποστηρίζει δημιουργία εικόνων από κείμενο και όχι επεξεργασία εικόνων αναφοράς. Η έξοδος του Vertex
κανονικοποιείται σε `data[].b64_json`· το `response_format: "url"` επιστρέφει ένα upstream
HTTPS URL ή ένα base64 data URL όταν είναι διαθέσιμα μόνο τα byte της εικόνας. Οι κενές/φιλτραρισμένες έξοδοι
επιστρέφουν σφάλμα αντί για κενή επιτυχή απόκριση. Η πρόσβαση στα μοντέλα εξαρτάται από τον λογαριασμό ZenMux.
Δείτε το [Vertex API του ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) και το
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Παράθεση όλων των μοντέλων εικόνας
GET /v1/images/generations
```

| `mistral`                     | `mistral-ocr-latest`   | `mistral/mistral-ocr-latest` (ή σκέτο `mistral-ocr-latest`) | Σύγχρονη λειτουργία — η απόκριση επιστρέφεται απευθείας από τη μοναδική upstream κλήση.                                                |
| `azure-document-intelligence` | `prebuilt-read`        | `azure-document-intelligence/prebuilt-read`                 | Ασύγχρονη upstream λειτουργία (`analyze` + polling) — δείτε παρακάτω.                                                                  |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`    | `vertex-deepseek-ocr/deepseek-ocr-maas`                     | Σύγχρονη λειτουργία, μέσω του endpoint συνεργατών `openapi/chat/completions` του Vertex AI — δείτε παρακάτω για έλεγχο ταυτότητας/URL. |

Και οι τρεις πάροχοι αποκρίνονται με το ίδιο σώμα στη μορφή του Mistral:

```json

}
```

### Ροή polling του Azure Document Intelligence

Το API `analyze` του Azure Document Intelligence είναι ασύγχρονο: το αρχικό αίτημα επιστρέφει μια
κεφαλίδα `Operation-Location` αντί για σώμα και πρέπει να πραγματοποιείται polling για το αποτέλεσμα. Ο handler
(`open-sse/handlers/ocr.ts`) εκτελεί polling σε αυτό το URL κάθε δευτερόλεπτο για έως και 30 προσπάθειες, αποτυγχάνει άμεσα (δεν
συνεχίζει το polling) σε απόκριση polling που δεν είναι `ok` ή σε κατάσταση `"failed"` και επιστρέφει `504` εάν η
λειτουργία εξακολουθεί να εκτελείται μετά την εξάντληση του ορίου προσπαθειών. Η τελική απόκριση του Azure
κανονικοποιείται στην ίδια μορφή `pages`/`markdown` που χρησιμοποιεί το Mistral πριν επιστραφεί στον
καλούντα, ώστε ο κώδικας του client να μη χρειάζεται ειδικό χειρισμό ανά πάροχο.

### Έλεγχος ταυτότητας και επίλυση endpoint για το Vertex AI DeepSeek OCR

Το `vertex-deepseek-ocr` επαναχρησιμοποιεί τον ίδιο έλεγχο ταυτότητας Vertex AI που υποστηρίζει ήδη το OmniRoute για
κίνηση συνομιλιών/εικόνων (`open-sse/executors/vertex.ts`): το κλειδί API της σύνδεσης είναι είτε
ένα διαπιστευτήριο Service Account JSON (το οποίο ανταλλάσσεται με ένα βραχύβιο OAuth access token μέσω της ροής JWT-bearer)
είτε ένα ήδη εκδοθέν OAuth access token που χρησιμοποιείται ως έχει. Το upstream endpoint URL είναι το γενικό
endpoint συνεργατών `openapi/chat/completions` του Vertex, το οποίο δημιουργείται από το project και την
περιοχή της σύνδεσης — ένα ρητό `providerSpecificData.project`/`providerSpecificData.region` έχει πάντα προτεραιότητα·
διαφορετικά, το project προκύπτει από το `project_id` του Service Account JSON και η περιοχή
έχει ως προεπιλογή το `us-central1`. Και οι δύο επιλύσεις πραγματοποιούνται στο `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) και χρησιμοποιούνται από το
`src/app/api/v1/ocr/route.ts` πριν από την ανάθεση στο `handleOcr`.

### Προθέματα αναγνωριστικών μοντέλων (`?prefix=`)

Τα περισσότερα μοντέλα δημοσιεύονται με ένα **πρόθεμα παρόχου**. Το πρόθεμα που λαμβάνετε ελέγχεται από τη σημαία λειτουργίας
`MODELS_CATALOG_PREFIX_MODE` και μπορεί να παρακαμφθεί **ανά αίτημα** με μια
παράμετρο ερωτήματος — χρήσιμο για έναν πελάτη που θέλει μια καθαρή λίστα χωρίς να αλλάξει τη ρύθμιση
σε επίπεδο διακομιστή για όλους τους υπόλοιπους:

```bash
GET /v1/models?prefix=alias        # ένα αναγνωριστικό ανά μοντέλο — το σύντομο πρόθεμα ψευδωνύμου
GET /v1/models?prefix=dual         # και οι δύο μορφές (προεπιλογή διακομιστή)
GET /v1/models?prefix=canonical    # μόνο το πλήρες πρόθεμα αναγνωριστικού παρόχου
```

| Λειτουργία  | Παράγει                                                   | Σημειώσεις                                                                                                                                                                                                                      |
| ----------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **και** `claude/claude-sonnet-4-6` | **Προεπιλογή.** Και τα δύο αναγνωριστικά δρομολογούνται στο ίδιο μοντέλο· διατηρούνται ώστε οι ρυθμίσεις πελατών που έχουν ενσωματωμένη μία από τις δύο μορφές να συνεχίσουν να λειτουργούν. Σχεδόν διπλασιάζει τον κατάλογο.   |
| `alias`     | `cc/claude-sonnet-4-6`                                    | Μία καταχώριση ανά μοντέλο. Οι πάροχοι χωρίς διακριτό ψευδώνυμο εξακολουθούν να παράγουν την καταχώρισή τους, επομένως δεν χάνεται τίποτα.                                                                                      |
| `canonical` | `claude/claude-sonnet-4-6`                                | Μία καταχώριση ανά μοντέλο κάτω από το πλήρες πρόθεμα αναγνωριστικού παρόχου. Οι πάροχοι χωρίς διακριτό ψευδώνυμο (π.χ. `antigravity/…`, `agy/…`) παράγουν και εδώ το μοναδικό αναγνωριστικό τους, επομένως δεν χάνεται τίποτα. |

Ένα είδωλο σε λειτουργία `dual` μπορεί επίσης να αναγνωριστεί χωρίς την παράμετρο ερωτήματος: διαθέτει ένα πεδίο `parent`
που παραπέμπει στο κύριο αναγνωριστικό.

Οι πελάτες που εμφανίζουν έναν επιλογέα μοντέλων θα πρέπει να ζητούν `?prefix=alias` — αυτό κάνει η
[επέκταση OmniCopilot για το VS Code](../guides/VSCODE-COPILOT.md).

### Φίλτρα ανακάλυψης (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

Το `GET /v1/models` δέχεται προαιρετικά φίλτρα ανακάλυψης. Χωρίς κανένα από αυτά, η απόκριση
παραμένει αμετάβλητη. Περιορίζουν τον κατάλογο που ήδη βλέπει ο καλών (τα δικαιώματα κλειδιού API εφαρμόζονται πρώτα)
και εκτελούνται πριν από τη σελιδοποίηση τύπου OpenAI με `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # κάθε αναφερόμενη δυνατότητα πρέπει να είναι αληθής
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` καταλόγου· οι γραμμές χωρίς αυτό είναι `chat`
GET /v1/models?q=sonnet&limit=10                           # αντιστοίχιση χωρίς διάκριση πεζών-κεφαλαίων στο αναγνωριστικό ή το όνομα
```

| Παράμετρος    | Τιμές                                                                                               |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | μη αρνητικός ακέραιος, συγκρίνεται με το `context_length`                                           |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 χαρακτήρες                                                                                    |

Μια άγνωστη τιμή ή ένα `min_context` που δεν είναι μη αρνητικός ακέραιος (για παράδειγμα `1.5`),
επιστρέφει HTTP `400` και το μήνυμα παραθέτει τις έγκυρες τιμές. Υλοποίηση:
`src/app/api/v1/models/catalogFilters.ts`.

### Σύντομη λίστα μοντέλων (`POST /v1/models/query`)

Το `POST /v1/models/query` επιστρέφει μια σύντομη, ντετερμινιστική λίστα από τον ίδιο κατάλογο, με τον ίδιο
έλεγχο ταυτότητας και την ίδια ορατότητα ανά κλειδί όπως το `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Κάθε πεδίο είναι προαιρετικό. Τα `capabilities` και `exclude` δέχονται έναν πίνακα ή μια συμβολοσειρά διαχωρισμένη με κόμματα·
το `max_output` συγκρίνεται με το `max_output_tokens`. Τα αποτελέσματα ταξινομούνται κατά `owned_by` και έπειτα κατά `id`.
Η προεπιλεγμένη τιμή του `limit` είναι `20` και οι τιμές πάνω από `100` περιορίζονται σε `100`. Μη έγκυρο JSON, ένα άγνωστο
πεδίο ή μια μη έγκυρη τιμή επιστρέφει HTTP `400`.

### Μεμονωμένα κρυφά μοντέλα συνομιλίας

Ένα μοντέλο που έχει επισημανθεί ως **Κρυφό** στη σελίδα του παρόχου του εξαιρείται από τον κατάλογο και απορρίπτεται
με HTTP `404` / `model_not_found` όταν ζητείται ρητά. Ο έλεγχος χρησιμοποιεί τον επιλυμένο
πάροχο και μοντέλο, συμπεριλαμβανομένων των ψευδωνύμων παρόχου, των προθεμάτων κόμβων συμβατού παρόχου και των
προεπιλογών σύνδεσης. Ένας συνδυασμός παραλείπει τους κρυφούς προορισμούς και μπορεί να χρησιμοποιήσει έναν ορατό συγγενικό προορισμό· όταν δεν
απομένει κανένας εκτελέσιμος προορισμός, επιστρέφει τον ίδιο κωδικό σφάλματος. Η άρση της απόκρυψης τίθεται σε ισχύ με το επόμενο
αίτημα. Οι παρακάμψεις ορατότητας μόνο για εικόνες δεν αποκρύπτουν το μοντέλο συνομιλίας με το ίδιο αναγνωριστικό.

Αυτή η μεμονωμένη ρύθμιση μοντέλου είναι ανεξάρτητη από τις
[λίστες επιτρεπόμενων/αποκλεισμένων μοντέλων](../routing/MODEL_EXPOSURE_LIST.md), οι οποίες φιλτράρουν τη
δημοσίευση του καταλόγου και τους υποψηφίους αυτόματης δρομολόγησης, διατηρώντας παράλληλα τη ρητή αποστολή. Τα δικαιώματα μοντέλων
ανά κλειδί API συνεχίζουν να εφαρμόζονται ανεξάρτητα. Η προεπιλεγμένη λειτουργία προθέματος καταλόγου παραμένει `dual`.

### Παραλλαγές μοντέλων χωρίς συλλογισμό

Για μοντέλα Claude με δυνατότητα συλλογισμού, το `/v1/models` δημοσιεύει επίσης μια παραλλαγή **χωρίς συλλογισμό**, της οποίας το αναγνωριστικό έχει ως πρόθεμα το `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Η επιλογή αυτού του αναγνωριστικού (π.χ. σε μια διαμόρφωση του Claude Code που επισυνάπτει πάντα ένα μπλοκ `thinking`) επιλύεται ξανά στο πραγματικό `<provider>/<model>` με απενεργοποιημένο τον συλλογισμό — `thinking:{type:"disabled"}` στη διαδρομή `/v1/messages` ή με παράλειψη των πεδίων `reasoning`/`reasoning_effort` στη διαδρομή `/v1/chat/completions`. Η παραλλαγή εμφανίζεται μόνο για μοντέλα της οικογένειας Claude που υποστηρίζουν τη σκέψη **και** τηρούν την τιμή `disabled` (επομένως, π.χ. εξαιρούνται τα μοντέλα που υποστηρίζουν μόνο προσαρμοστική λειτουργία και απορρίπτουν την τιμή `disabled`). Οι διαχειριστές μπορούν να ενεργοποιήσουν ή να απενεργοποιήσουν υποχρεωτικά την παραλλαγή ανά μοντέλο μέσω του `ModelSpec.noThinkingAlias`.

## Δημιουργία ήχου ElevenLabs

Διαμορφώστε μια σύνδεση παρόχου `elevenlabs` στο OmniRoute με το κλειδί API του ElevenLabs.
Οι πελάτες πραγματοποιούν έλεγχο ταυτότητας με το κλειδί τους για το **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`)·
η πύλη παρέχει το αποθηκευμένο κλειδί παρόχου ως `xi-api-key`. Μην αποστέλλετε ποτέ ένα κλειδί ElevenLabs
ως διακριτικό bearer της πύλης.

| Μέθοδος | Διαδρομή                    | Απόκριση                                            | Κατηγορία τελικού σημείου κλειδιού API |
| ------- | --------------------------- | --------------------------------------------------- | -------------------------------------- |
| POST    | `/v1/sound-generation`      | Εγγενή byte ήχου                                    | `elevenlabs`                           |
| POST    | `/v1/music`                 | Εγγενή byte ήχου                                    | `music`                                |
| POST    | `/v1/music/stream`          | Byte ήχου συνεχούς ροής                             | `music`                                |
| POST    | `/v1/music/detailed`        | Εγγενής ήχος πολλαπλών τμημάτων και σχέδιο σύνθεσης | `music`                                |
| POST    | `/v1/music/detailed/stream` | Εγγενή μεταδεδομένα SSE και τμήματα ήχου            | `music`                                |
| POST    | `/v1/music/plan`            | Σχέδιο σύνθεσης JSON                                | `music`                                |

Αυτά τα τελικά σημεία συμπληρώνουν τις υπάρχουσες διαδρομές `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` και `/v1/speech-to-text`. Τα εγγενή πεδία JSON
και οι παράμετροι ερωτήματος, όπως `output_format` και `enable_logging`, διατηρούνται.
Οι αποκρίσεις `/v1/music/detailed` διατηρούν τα όρια πολλαπλών τμημάτων τους· αναλύστε τις ως πολλαπλών τμημάτων.
Το `/v1/music/detailed/stream` επιστρέφει `text/event-stream` με μεταδεδομένα σύνθεσης και
τμήματα ήχου base64 σε συμβάντα SSE. Και οι έξι διαδρομές υποστηρίζουν προκαταρκτικό αίτημα CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Ένα σύντομο ηχητικό εφέ. Διάρκεια: 0,5 έως 30 δευτερόλεπτα.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Η διάρκεια της μουσικής εκφράζεται σε χιλιοστά του δευτερολέπτου: 3000 έως 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Χρησιμοποιήστε το `/v1/music/stream` με το ίδιο σώμα JSON για σταδιακή παράδοση ήχου. Η σύνθεση
δέχεται ακριβώς ένα από τα `prompt` ή `composition_plan`· το `/v1/music/plan` απαιτεί `prompt`
και δέχεται προαιρετικά `source_composition_plan`. Τα εγγενή σχήματα διατηρούν πρόσθετα
πεδία παρόχου, ώστε οι εκδόσεις σχεδίων σύνθεσης και οι επιλογές λεπτομερούς ρύθμισης να φτάνουν στο ElevenLabs.

Το ενοποιημένο τελικό σημείο `/v1/music/generations` δέχεται επίσης `elevenlabs/music_v1`,
`elevenlabs/music_v2` και `elevenlabs/music_v2_5`. Με μια ενεργή σύνδεση ElevenLabs,
αυτά τα μοντέλα εμφανίζονται στον κατάλογο μουσικής. Αυτό το τελικό σημείο επιστρέφει
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Το πεδίο `duration` είναι σε
δευτερόλεπτα και αντιστοιχίζεται στο `music_length_ms`· ένα ρητά καθορισμένο `music_length_ms` υπερισχύει.
Το `instrumental` αντιστοιχίζεται στο `force_instrumental`, με το εγγενές πεδίο να υπερισχύει.
Χρησιμοποιήστε τα εγγενή τελικά σημεία συνεχούς ροής για ροή και το εγγενές τελικό σημείο σύνθεσης
για αιτήματα που καθοδηγούνται αποκλειστικά από ένα σχέδιο σύνθεσης.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Οι περιορισμοί τελικού σημείου, μοντέλου, προϋπολογισμού και σύνδεσης εφαρμόζονται πριν από μια κλήση προς τον upstream πάροχο. Οι εγγενείς
διαδρομές επιστρέφουν αμετάβλητους τους κωδικούς κατάστασης και τα σώματα σφαλμάτων του upstream παρόχου, συμπεριλαμβανομένου του `402` για περιορισμό
προγράμματος και του `429` για όριο ποσόστωσης. Οι κεφαλίδες `character-cost`, `song-id`, `request-id` και `retry-after`
διατηρούνται όταν υπάρχουν. Ένα δωρεάν υπόλοιπο πιστώσεων δεν εγγυάται πρόσβαση σε κάθε
μοντέλο μουσικής, μορφή εξόδου ή δυνατότητα API: το ElevenLabs αποφασίζει τα δικαιώματα για κάθε αίτημα.
Το ενοποιημένο τελικό σημείο διατηρεί τους κωδικούς κατάστασης σφαλμάτων στο κανονικοποιημένο περίβλημα σφάλματος του OmniRoute.

Συμβάσεις upstream παρόχου: [ηχητικά εφέ](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[σύνθεση μουσικής](https://elevenlabs.io/docs/api-reference/music/compose) και
[λεπτομέρειες μουσικής συνεχούς ροής](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

> **Κόμβοι παρόχων για rerank:** Το `POST /v1/rerank` δρομολογείται επίσης σε κόμβους παρόχων συμβατούς με το OpenAI
> (oMLX, vLLM, Infinity, TEI πίσω από μια πύλη, …), οι οποίοι προσδιορίζονται ως `<node-prefix>/<model>`. Οι κόμβοι
> loopback (`localhost`, `127.0.0.1`, `172.16.0.0/12`) είναι πάντα επιλέξιμοι, όπως και τα ονόματα κεντρικών υπολογιστών που
> παραθέτει ο διαχειριστής στο `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (π.χ. ένα όνομα υπηρεσίας Docker/Compose όπως
> `http://reranker:8080/v1`· αυτοί καλούνται απευθείας, ποτέ μέσω `HTTP(S)_PROXY` ή του
> σταθερά αντιστοιχισμένου διακομιστή μεσολάβησης μιας σύνδεσης). Οι κόμβοι σε οποιονδήποτε άλλο
> κεντρικό υπολογιστή — ένα μηχάνημα LAN ή έναν ομότιμο Tailscale — είναι επιλέξιμοι μόνο όταν ο διαχειριστής ενεργοποιήσει τη
> σημαία δυνατότητας `RERANK_REMOTE_PROVIDER_NODES` **και** το βασικό URL του κόμβου συμμορφώνεται με την πολιτική
> εξερχόμενων URL παρόχων (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Το βήμα rerank της μηχανής μνήμης καλεί αυτήν τη διαδρομή μέσω
> loopback, επομένως ο ίδιος κανόνας διέπει το `rerankProviderModel` στις ρυθμίσεις μνήμης.
>
> **Μορφές τοπικών διακομιστών:** Ο κόμβος καλείται στο `<base>/v1/rerank` και, σε περίπτωση 404, στο `<base>/rerank`
> (Infinity, TEI). Το σώμα του αιτήματος προς το upstream περιλαμβάνει τόσο την ορθογραφία Cohere/OpenAI (`documents`,
> `return_documents`) όσο και την ορθογραφία TEI (`texts`, `return_text`), ενώ η απόκριση του upstream
> κανονικοποιείται στη δομή φακέλου Cohere: το γυμνό `[{index, score, text}]` του TEI, το `{results: [{index, score}]}`
> από ελαφριές πύλες και το `{data: [...]}` τύπου Voyage επιστρέφονται όλα στον πελάτη ως
> `{results: [{index, relevance_score, document?}]}`, ταξινομημένα κατά βαθμολογία και περιορισμένα στο `top_n`.

> **Εντοπισμός κόμβων παρόχων:** Τα μοντέλα σε έναν κόμβο παρόχου συμβατό με το OpenAI εμφανίζονται στο `GET /v1/models`
> κάτω από το πρόθεμα του κόμβου. Οι εγγραφές που δεν περιέχουν μεταδεδομένα τελικού σημείου (κάτι σύνηθες για τοπικές καταχωρίσεις `/v1/models`)
> κληρονομούν το `apiType` του κόμβου, επομένως τα μοντέλα ενός κόμβου `embeddings` έχουν `type: "embedding"` και τα
> μοντέλα ενός κόμβου `rerank` έχουν `type: "rerank"` αντί να χρησιμοποιούν από προεπιλογή τον τύπο συνομιλίας· ένα ρητό
> `supportedEndpoints` σε μια συγχρονισμένη ή μη αυτόματα προστεθειμένη εγγραφή εξακολουθεί να έχει προτεραιότητα.

### `provider_options` των Exa και Tavily

Τα Exa και Tavily διαβάζουν πεδία ειδικά για τον πάροχο από έναν χώρο ονομάτων:
`provider_options.exa` (ή `provider_options["exa-search"]`) και `provider_options.tavily`
(ή `provider_options["tavily-search"]`). Προωθούνται μόνο τα παρακάτω κλειδιά. Καθένα
ελέγχεται με βάση το δικό του σχήμα Zod στο `open-sse/handlers/search/providerOptionsPassthrough.ts`,
και ένα κλειδί λανθασμένου τύπου απορρίπτεται. Οποιοδήποτε άλλο κλειδί αγνοείται, συμπεριλαμβανομένων των στοιχείων ελέγχου ταυτότητας, του βασικού URL,
των `stream` και `outputSchema`. Τα επίπεδα κλειδιά που χρησιμοποιούνται από άλλους παρόχους (`cx`, `depth`, ...) λειτουργούν
όπως προηγουμένως.

| Πάροχος | Πεδία ανώτατου επιπέδου                                                                                                                                                                                                                                                                                                                                                   | Ένθετα                                                                                                                                                                            |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa     | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (επίπεδες πρωταρχικές τιμές), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                   | Το `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` συγχωνεύεται πάνω από την προεπιλογή `{ text: true, highlights: true }` |
| Tavily  | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                                 |

Τα γενικά πεδία έχουν πάντα προτεραιότητα: `query`, `max_results`, `filters` (τομείς), `country` και το
θέμα που προκύπτει από το `search_type`. Στο Exa, το `search_type: "news"` διατηρεί το `category: "news"`.
Το Tavily δέχεται επίσης `search_type: "finance"` (`topic: "finance"`).

Το γενικό `time_range` μεταβιβάζεται πλέον και στους δύο παρόχους: το Exa λαμβάνει `startPublishedDate` (χρονοσήμανση
ISO) και το Tavily λαμβάνει `start_date` (`YYYY-MM-DD`). Μια ρητή ημερομηνία στο `provider_options`
αντικαθιστά την αντιστοιχισμένη.

Τα αποτελέσματα του Exa διατηρούν τα `id`, `highlight_scores`, `summary`, `subpages`, `entities` και `extras` στο
`provider_raw`. Τα αποτελέσματα του Tavily διατηρούν τα `images` και `favicon`.

Η κοστολόγηση εξακολουθεί να χρησιμοποιεί το επίπεδο μητρώο `costPerQuery`. Το Tavily χρεώνει
το `search_depth: "advanced"` με περισσότερες μονάδες ανά κλήση και αυτή η διαφορά δεν αντικατοπτρίζεται στο
`usage.search_cost_usd`.

## Web Fetch API

Εξαγωγή περιεχομένου από ένα URL μέσω ενός διαμορφωμένου παρόχου web-fetch (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Το Parallel Extract (`parallel-search`, ίδιο API key με το Parallel Search) επιστρέφει μόνο
Markdown — οποιοδήποτε άλλο `format` οδηγεί σε `400` — και περιορίζει το περιεχόμενο στους 100.000 χαρακτήρες. Όταν
η ίδια η σελίδα-στόχος δεν μπορεί να εξαχθεί, η upstream υπηρεσία το αναφέρει μέσα σε HTTP 200·
το OmniRoute το εμφανίζει ως `422` με σταθερό μήνυμα.

| Μέθοδος | Διαδρομή        | Περιγραφή                                                                   |
| ------- | --------------- | --------------------------------------------------------------------------- |
| POST    | `/v1/web/fetch` | Ανάκτηση/scraping ενός URL — το σώμα επικυρώνεται από το `v1WebFetchSchema` |

**Έλεγχος ταυτότητας:** Bearer API key (`extractApiKey` + `isValidApiKey`). Η πολιτική επιβάλλεται μέσω του `enforceApiKeyPolicy`.

**Εναλλακτική μετάπτωση με επίγνωση ορίων χρήσης (#8297):** όταν δεν δίνεται ρητά `provider`, γίνεται
διάσχιση του συνόλου
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) με σταθερή
σειρά προτεραιότητας (πρώτα η πλήρωση) — ένας διαμορφωμένος πάροχος που έχει περιοριστεί λόγω ορίου αιτημάτων παραλείπεται
αντί να τερματίζεται άμεσα το αίτημα, ενώ μια επαναλήψιμη αποτυχία ή αποτυχία ορίου χρήσης της upstream υπηρεσίας
(HTTP 429 πάντα· 402/403 για δωρεάν επίπεδα χρήσης τύπου ορίου των Firecrawl/Tavily/TinyFish —
όχι για το Jina Reader και ποτέ για ένα απλό εσφαλμένο αίτημα 400) οδηγεί στον
επόμενο πάροχο με διαπιστευτήρια που δεν έχει ακόμη δοκιμαστεί κατά τον χρόνο εκτέλεσης του αιτήματος. Όταν εξαντληθούν όλοι οι πάροχοι του
συνόλου, το endpoint επιστρέφει ένα μόνο `429` (με κεφαλίδα `Retry-After`)
αντί για το προηγούμενο γενικό `400`. Όταν ζητείται ρητά ένα `provider`,
δεν υπάρχει **καμία** σιωπηρή εναλλακτική μετάπτωση — ένας ρητά επιλεγμένος πάροχος που έχει περιοριστεί λόγω ορίου αιτημάτων ή αποτυγχάνει
εμφανίζει το δικό του σφάλμα (`429` αν έχει περιοριστεί λόγω ορίου αιτημάτων, διαφορετικά την κατάσταση της upstream
υπηρεσίας).

## Ροή μέσω WebSocket

```bash
GET /v1/ws?handshake=1
```

Επικυρώνει μια χειραψία αναβάθμισης WebSocket και επιστρέφει τα παραδείγματα μηνυμάτων του πρωτοκόλλου μετάδοσης (`request`, `cancel`). Τα πραγματικά πλαίσια WS διαχειρίζονται από τον ενσωματωμένο διακομιστή WS εκτός του πίνακα διαδρομών του Next.js.

**Έλεγχος ταυτότητας:** Bearer API key κατά τη χειραψία.

### Responses API μέσω WebSocket (μόνο codex)

```bash
# Ίδιο host:port με το HTTP API (προεπιλογή 20128)· αναβαθμίστε τη σύνδεση:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (ή: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Το πρώτο πλαίσιο ΠΡΕΠΕΙ να είναι response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Ένας διακομιστής μεσολάβησης Responses-API-over-WebSocket είναι συνδεδεμένος **αποκλειστικά με το `codex`** (backend του ChatGPT). Ακούει στην ίδια θύρα με το API/dashboard στις διαδρομές `/v1/responses`,
`/responses` και `/api/v1/responses`. Στο πρώτο πλαίσιο `response.create`,
πραγματοποιεί έλεγχο ταυτότητας + προετοιμασία μέσω της εσωτερικής γέφυρας `codex-responses-ws`, επιλέγει μια
σύνδεση OAuth του codex και δημιουργεί σήραγγα προς το `wss://chatgpt.com/backend-api/codex/responses`
μέσω του transport `wreq-js`. **Τα μοντέλα που δεν είναι codex απορρίπτονται** (`codex_ws_provider_required`).
Για δρομολόγηση με κοινόχρηστο όριο χρήσης, χρησιμοποιήστε `model: "qtSd/<group>/codex/<model>"`. Υλοποιείται στα
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Έλεγχος ταυτότητας:** Bearer API key κατά τη χειραψία. Ο ενσωματωμένος διακομιστής HTTP (`server-ws.mjs`)
πρέπει να είναι το ενεργό σημείο εισόδου (είναι από προεπιλογή, όταν υπάρχει το `app/server-ws.mjs`).

#### Αναγνωριστικό μοντέλου: χρησιμοποιήστε το απλό αναγνωριστικό του ChatGPT (χωρίς πρόθεμα `codex/`)

Το OpenAI **Codex CLI** επικυρώνει το όνομα μοντέλου στην πλευρά του client όταν
`supports_websockets = true` και **απορρίπτει αναγνωριστικά με πρόθεμα παρόχου** όπως
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Στείλτε το **απλό** αναγνωριστικό (π.χ. `gpt-5.5`). Η γέφυρα του OmniRoute είναι
μόνο για codex, επομένως επιλύει εκ νέου ένα απλό αναγνωριστικό ως μοντέλο codex
(`resolveCodexWsModelInfo`) πριν δημιουργήσει τη σήραγγα προς την upstream υπηρεσία — παρόλο που ένα απλό
`gpt-5.5` θα δρομολογούνταν διαφορετικά προς άλλον πάροχο μέσω HTTP.

#### Διαμόρφωση του OpenAI Codex CLI

Κατευθύνετε το Codex CLI προς το OmniRoute προσθέτοντας έναν προσαρμοσμένο πάροχο με υποστήριξη
WebSocket στο `~/.codex/config.toml` (χρησιμοποιήστε ξεχωριστό `CODEX_HOME` για να αποφύγετε την τροποποίηση
μιας υπάρχουσας διαμόρφωσης):

```toml
model = "gpt-5.5"                 # απλό αναγνωριστικό — ΟΧΙ "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # χωρίς τελική κάθετο· το URL του WS παράγεται αυτόματα (χρησιμοποιήστε https/wss σε περιβάλλον παραγωγής)
wire_api = "responses"                    # η μόνη υποστηριζόμενη τιμή από τον Φεβ 2026
supports_websockets = true                # ενεργοποιεί το transport Responses-over-WS
env_key = "OMNIROUTE_API_KEY"             # περιέχει το API key του OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # ένα API key του OmniRoute (οποιοδήποτε κλειδί αν REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

Το CLI αναβαθμίζει το `base_url + /responses` σε WebSocket και το OmniRoute δημιουργεί σήραγγα
προς την επιλεγμένη σύνδεση OAuth του codex. Έχει επικυρωθεί από άκρο σε άκρο με τον τοπικό
διακομιστή: το ChatGPT επιστρέφει `codex.rate_limits` + `response.created` και μεταδίδει τη
συμπλήρωση σε ροή.

## Αυτοεξυπηρετούμενη χρήση (`/api/usage/om-usage`)

Οποιοδήποτε κλειδί API μπορεί να διαβάσει τη **δική του** χρήση και τα δικά του όρια — χωρίς έλεγχο ταυτότητας διαχείρισης. Αυτό είναι το endpoint που χρησιμοποιεί ένας
πελάτης (CLI, ο πίνακας OmniCopilot) για να εμφανίσει σε έναν κάτοχο κλειδιού τις δαπάνες του.

```bash
# Μορφή κειμένου (η ιστορική σύμβαση — απλό κείμενο για τερματικό)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Δομημένη μορφή — αυτή που καταναλώνει ένα UI
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Το κλειδί πρέπει να έχει ενεργοποιημένο το **`allowUsageCommand`** (είναι απενεργοποιημένο από προεπιλογή — ο διαχειριστής κλειδιών API του dashboard
το ενεργοποιεί ή το απενεργοποιεί ανά κλειδί). Χωρίς αυτό, το endpoint απαντά με `403`.

Το `?format=json` επιστρέφει μια διακριτή δομή, ώστε ο καλών να μην επιχειρεί ποτέ να διαβάσει ένα πεδίο δεδομένων από μια
άρνηση. Σε περίπτωση επιτυχίας:

```jsonc
{
  "allowed": true,
  // υπάρχει μόνο όταν το κλειδί έχει επιλέξει όρια χρήσης ανά κλειδί (ημερήσια/εβδομαδιαία σε USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // το στιγμιότυπο ορίου του επιλεγμένου παρόχου ή null όταν δεν υπάρχει ακόμη τίποτα στην cache:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // το στιγμιότυπο κάθε σύνδεσης, ώστε ένα UI να μπορεί να εμφανίσει πολλούς παρόχους δίπλα-δίπλα:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Σε περίπτωση άρνησης (`401` μη έγκυρο κλειδί / `403` δεν επιτρέπεται), η ίδια διαδρομή επιστρέφει
`{ "allowed": false, "error": { "message": "…" } }` — ένα υπάρχον αλλά κενό `personal`/`provider`
(το κλειδί επιτρέπεται, αλλά δεν έχει αντληθεί ακόμη καμία πληροφορία) αποτελεί διαφορετική κατάσταση από μια άρνηση, και μόνο η μορφή JSON
τις διακρίνει.

**Έλεγχος ταυτότητας:** το κλειδί API τύπου Bearer του ίδιου του καλούντος, επικυρωμένο με `isValidApiKey` — αυτή _δεν_ είναι η
επιφάνεια διαχείρισης (`/api/keys/…`), η οποία παραμένει προστατευμένη από το `requireManagementAuth`.

### Ανεπεξέργαστα έναντι Προσαρμοσμένων στο Όριο Ποσοστών Ορίου Χρήσης

Κατά την κατανάλωση του `/api/usage/om-usage`, οι καλούντες θα πρέπει να λαμβάνουν υπόψη τη διαφορά μεταξύ των
ποσοστών που παρουσιάζονται από την **έξοδο απλού κειμένου** και τη δομημένη **έξοδο JSON**:

| Πτυχή                  | Μορφή απλού κειμένου (`/api/usage/om-usage` / `@@om-usage`)                                                      | Μορφή JSON (`?format=json`)                                                                      |
| :--------------------- | :--------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------- |
| **Πεδίο εξόδου**       | `NN% left` (π.χ. `20% left`)                                                                                     | `provider.quotas` / `providers[].quotas`                                                         |
| **Μέτρηση**            | **Χρησιμοποιήσιμο απόθεμα προσαρμοσμένο στο όριο αποκοπής**: υπολειπόμενη χωρητικότητα πάνω από το όριο αποκοπής | **Ανεπεξέργαστο όριο upstream**: μη προσαρμοσμένη μέτρηση παρόχου                                |
| **Κλιμάκωση αποκοπής** | Κλιμακώνεται μέσω του `effectiveRemainingPercent()`, ώστε το προστατευμένο απόθεμα να εμφανίζεται ως `0% left`   | Καμία (ανεπεξέργαστες τιμές στιγμιοτύπου, όπως αναφέρονται από τον πάροχο)                       |
| **Δεδομένα ορίου**     | Ενσωματώνονται στο εμφανιζόμενο ποσοστό                                                                          | Αποθηκεύονται στο `quotaWindowThresholds` ανά σύνδεση (ή στις προεπιλογές του server)            |
| **Κύριος καταναλωτής** | Διαδραστικά CLI, προτροπές τερματικού, ανθρώπινοι χειριστές                                                      | Προγραμματιστικές ενσωματώσεις, dashboard, αναλυτικά στοιχεία, συστήματα παρακολούθησης χρεώσεων |

#### Ο Τύπος Προσαρμογής Αποκοπής

Το OmniRoute υποστηρίζει προληπτικά όρια αποκοπής για την αποτροπή εξάντλησης του upstream (διαμορφώνονται μέσω του
`quotaWindowThresholds` της σύνδεσης, των προεπιλογών του παρόχου ή των καθολικών ρυθμίσεων ανθεκτικότητας). Όταν ένα όριο αποκοπής
(π.χ. `cutoff = 25%`) είναι ενεργό σε ένα παράθυρο ορίου χρήσης, ο renderer κειμένου υπολογίζει το υπολειπόμενο απόθεμα ως εξής:

- Αν `remaining <= cutoff`: επιστρέφει `0%`.
- Αν `remaining > cutoff`: επιστρέφει `((remaining - cutoff) / (100 - cutoff)) * 100`.

Η μορφοποιημένη έξοδος κειμένου στρογγυλοποιεί το αποτέλεσμα στον πλησιέστερο ακέραιο (`Math.round(...)`).

#### Επεξηγηματικό Παράδειγμα

Εξετάστε ένα παράθυρο παρόχου με **60% ανεπεξέργαστη χρήση** (άρα **40% ανεπεξέργαστο υπολειπόμενο όριο**) και ένα διαμορφωμένο
**όριο αποκοπής 25% του υπολειπόμενου ορίου**:

| Αναπαράσταση                            | Υπολογισμός                                        | Υπολειπόμενο |              Συνεπαγόμενη Χρήση               |
| :-------------------------------------- | :------------------------------------------------- | :----------: | :-------------------------------------------: |
| **Ανεπεξέργαστο JSON (`?format=json`)** | Στιγμιότυπο upstream (`quotas[window]`)            |   **40%**    |                    **60%**                    |
| **Μορφή κειμένου (`NN% left`)**         | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |   **20%**    | **80%** (αν υπολογιστεί ως `100 - remaining`) |

- **Γιατί το κείμενο εμφανίζει 20% υπολειπόμενο:** Από το 40% του φυσικού ορίου που απομένει στον λογαριασμό, το 25% δεσμεύεται από την
  πολιτική αποκοπής. Ο καλών διαθέτει μόνο 15% από το 75% του χρησιμοποιήσιμου περιθωρίου πριν ο router σταματήσει
  να δρομολογεί προς αυτήν τη σύνδεση. Η κλιμάκωση διασφαλίζει ότι η σύνδεση σηματοδοτεί εξάντληση (`0% left`) ακριβώς όταν
  θα διακοπεί η δρομολόγηση.
- **Γιατί το JSON διατηρεί τις ανεπεξέργαστες τιμές:** Το payload JSON επιστρέφει το ακριβές στιγμιότυπο του παρόχου (`UsageSnapshot`),
  ώστε τα εξωτερικά εργαλεία να έχουν πρόσβαση στην πραγματική αξιοποίηση του upstream και στο
  `quotaWindowThresholds` σε επίπεδο σύνδεσης, χωρίς απωλεστική κλιμάκωση από την πλευρά του server.

#### Οδηγίες Μετάβασης για Καταναλωτές

Αν μια εξωτερική ενσωμάτωση (όπως ένα πρόσθετο επεξεργαστή ή μια επέκταση agent) προηγουμένως αντλούσε το κείμενο από το
endpoint κειμένου (`NN% left`) και υπολόγιζε το χρησιμοποιημένο ποσοστό ως `100 - NN`, η μετάβαση στο `?format=json` σημαίνει ότι:

- Η ανάγνωση των ακατέργαστων τιμών JSON θα αντικατοπτρίζει την **πραγματική κατανάλωση upstream** (60% χρησιμοποιημένο στο παραπάνω παράδειγμα).
- Αν η ενσωμάτωση επιθυμεί να διατηρήσει τη σημασιολογία του διαθέσιμου ορίου του endpoint κειμένου, μπορεί να αξιολογήσει
  τον τύπο του πραγματικού υπολοίπου στην πλευρά του client, χρησιμοποιώντας το `quotaWindowThresholds` για παρακάμψεις σε επίπεδο σύνδεσης.

### Επίδραση στον λανθάνοντα χρόνο

Ένα HIT στη σημασιολογική κρυφή μνήμη εξυπηρετεί την απόκριση από την κρυφή μνήμη **χωρίς κλήση προς το upstream
σύστημα**, επομένως το αναφερόμενο `X-OmniRoute-Response-Latency` είναι σχεδόν μηδενικό
(ανεξάρτητα από τον αρχικό λανθάνοντα χρόνο του upstream συστήματος). Οι πελάτες που είναι ευαίσθητοι στον λανθάνοντα χρόνο
(συγκριτική αξιολόγηση, παρακολούθηση p50/p99) θα πρέπει να ελέγχουν την κεφαλίδα απόκρισης
`X-OmniRoute-Cache-Latency`:

| Τιμή        | Σημασία                                                                                      |
| ----------- | -------------------------------------------------------------------------------------------- |
| `synthetic` | Η απόκριση εξυπηρετήθηκε από την κρυφή μνήμη· ο χρόνος δεν είναι πραγματικός χρόνος upstream |
| _(απούσα)_  | Απόκριση από πραγματική κλήση προς το upstream σύστημα                                       |

### Παράκαμψη κρυφής μνήμης ανά κλειδί

Τα κλειδιά API μπορούν να εξαιρεθούν από τις αναγνώσεις της σημασιολογικής κρυφής μνήμης μέσω του `cacheDefaultMode`:

| Τιμή     | Συμπεριφορά                                                        |
| -------- | ------------------------------------------------------------------ |
| `legacy` | Κανονική συμπεριφορά κρυφής μνήμης (προεπιλογή)                    |
| `bypass` | Πλήρης παράλειψη αναζήτησης στην κρυφή μνήμη· πάντα χρήση upstream |

Ορίστε το κατά τη δημιουργία κλειδιού (`POST /api/keys`) ή την ενημέρωση (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Παράκαμψη ανά αίτημα

Οποιοδήποτε αίτημα μπορεί να παρακάμψει την κρυφή μνήμη ανεξάρτητα από τις ρυθμίσεις του κλειδιού:

```
X-OmniRoute-No-Cache: true
```

με OpenAI προσφέρει τα ίδια στοιχεία ελέγχου επεξεργασίας/εκκαθάρισης και επισημαίνει τα μοντέλα με ρητή υποστήριξη όρασης.

Οι προσαρμοσμένοι κόμβοι Chat Completions προσαρμόζουν τις ρητές εξαιρέσεις συλλογισμού στο ανάντη backend. Μια
επιτυχής δοκιμή σύνδεσης επιλέγει αυτόματα στοιχεία ελέγχου προτύπου συνομιλίας για κάθε ακριβές αναγνωριστικό μοντέλου
του οποίου η καταχώριση `/models` αποδεικνύει μια αναγνωρισμένη τιμή `owned_by`: `vllm`, `sglang` ή `llamacpp`.
Τα διαφανή wrappers που είναι συμβατά με OpenAI ενδέχεται να διατηρούν την αρχική καταχώριση μοντέλου μέσα σε ένα ένθετο
αντικείμενο `openai`· η ανίχνευση ακολουθεί έως και τρεις τέτοιους φακέλους. Τα μοντέλα με ελλιπή, άγνωστη ή
αντικρουόμενη ιδιοκτησία διατηρούν τη συνήθη συμπεριφορά OpenAI. Η ανίχνευση επαναχρησιμοποιεί το υπάρχον αίτημα καταλόγου,
δεν δημιουργεί διακριτικά ολοκλήρωσης και ακυρώνεται όταν αλλάξει το τελικό σημείο σύνδεσης.

Για να καθηλώσετε τη συμπεριφορά για ένα backend που δεν εκθέτει αυτά τα μεταδεδομένα, χρησιμοποιήστε το υπάρχον API
μερικής ενημέρωσης παρόχου:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Στείλτε αυτό το σώμα με `PUT /api/providers/<connection-id>`. Σε αυτήν τη σύνδεση, μια ρητή
προσπάθεια συλλογισμού `none` αποστέλλεται ως `chat_template_kwargs.thinking=false` και
`chat_template_kwargs.enable_thinking=false`. Οι ρητές εγγενείς τιμές προτύπου παραμένουν καθοριστικές,
εκτός εάν ένας κανόνας συλλογισμού στην πλευρά του διακομιστή επιβάλλει μια προσπάθεια. Η ρύθμιση εφαρμόζεται μόνο όταν μια προσαρμοσμένη
σύνδεση συμβατή με OpenAI αποστέλλει ένα σώμα Chat Completions· τα αιτήματα Responses και οι συνήθεις
πάροχοι διατηρούν την εγγενή μορφή αιτήματός τους. Ορίστε το `reasoningControl` σε `openai` για να επιβάλετε τη συνήθη προώθηση του
`reasoning_effort` του OpenAI ή παραλείψτε το/ορίστε το σε `null` για να χρησιμοποιήσετε την αυτόματη ανίχνευση.

Τα αιτήματα του ταξινομητή αυτόματης λειτουργίας του Claude Code ορίζουν από προεπιλογή την εγγενή σκέψη ως απενεργοποιημένη, όταν δεν
περιέχουν ρητά στοιχεία ελέγχου συλλογισμού. Η ανίχνευση χρησιμοποιεί τον δείκτη συστήματος του ταξινομητή σε αιτήματα μορφής Claude
και όχι ονόματα μοντέλων ή όρια ολοκλήρωσης. Τα ρητά στοιχεία ελέγχου σώματος, οι υποστηριζόμενες κεφαλίδες προσπάθειας/σκέψης,
οι κανόνες δρομολόγησης και η επιλυμένη προσπάθεια μοντέλου διατηρούν την υπάρχουσα προτεραιότητά τους. Και τα δύο στάδια του ταξινομητή
διατηρούν τις προτροπές, τα όρια ολοκλήρωσης, τις ακολουθίες διακοπής και τις πραγματικές αποφάσεις δικαιωμάτων από το ανάντη σύστημα·
το δεύτερο στάδιο εξακολουθεί να μπορεί να παράγει τον ζητούμενο ορατό συλλογισμό του ως απλό κείμενο.

### Έκδοση και κανάλι κυκλοφορίας

```bash
GET /api/system/version
```

Διαδρομή διαχείρισης μόνο μέσω loopback (έλεγχος ταυτότητας διαχειριστή). Επιστρέφει την έκδοση που εκτελείται, την πιο πρόσφατη δημοσιευμένη έκδοση και την κατάσταση της αυτόματης ενημέρωσης. Τα `releaseChannel` και `channels` είναι πρόσθετα πεδία (γραμμή 3.8.54)· το `channel` διατηρεί τη σημασία του — τον τρόπο ανάπτυξης που χρησιμοποιεί το πρόγραμμα ενημέρωσης του πίνακα ελέγχου (`npm`, `source` ή `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — το κανάλι npm της έκδοσης που εκτελείται: `nightly` για εκδόσεις `-nightly.*`,
  `next` για άλλες προεκδόσεις (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` για μια σταθερή έκδοση
  παλαιότερης κύριας έκδοσης από την `channels.latest`, διαφορετικά `latest`. Ισχύουν οι ίδιοι κανόνες με
  το `scripts/release/dist-tag.mjs`, το οποίο επιλέγει την ετικέτα διανομής npm κατά τη δημοσίευση.
- `channels` — η πιο πρόσφατη δημοσιευμένη έκδοση κάθε ετικέτας διανομής, από το `npm view omniroute dist-tags` (με εφεδρική
  χρήση HTTP του μητρώου), αποθηκευμένη στην κρυφή μνήμη με το ίδιο TTL 10 λεπτών όπως το `latest`. Το `latest` υπάρχει πάντα
  (χρησιμοποιεί εφεδρικά το πεδίο `latest` και έπειτα το `"unavailable"`)· τα `next`, `nightly` και `lts` εμφανίζονται
  μόνο όταν υπάρχει η αντίστοιχη ετικέτα διανομής. Ένα αίτημα `Cache-Control: no-cache` ανανεώνει και τις δύο αναζητήσεις.

Το μοντέλο καναλιών (`latest` = v3 έως τη γενική διαθεσιμότητα της 4.0, `next` = rc, `nightly` = εκδόσεις του `develop`,
`lts` = διορθωτικές εκδόσεις v3 μετά τη γενική διαθεσιμότητα της 4.0) περιγράφεται στο `docs/ops/RELEASE_STRATEGY.md`.

## Μεταγραφή ήχου

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Μεταγράψτε αρχεία ήχου χρησιμοποιώντας οποιονδήποτε διαμορφωμένο πάροχο STT. Το πρώτο τμήμα
της διαδρομής επιλέγει τον εγγενή πάροχο (`openai/…`, `deepgram/…`). Οι πύλες που
επανεξάγουν το μοντέλο άλλου προμηθευτή χρησιμοποιούν ένα προσδιορισμένο αναγνωριστικό
(`openrouter/deepgram/nova-3`).

**Αίτημα:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Απόκριση:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Παραδείγματα αναγνωριστικών μοντέλων:** `openai/whisper-1` (απαιτεί κλειδί OpenAI),
`openrouter/deepgram/nova-3` (απαιτεί κλειδί OpenRouter),
`deepgram/nova-3` (απαιτεί εγγενές κλειδί Deepgram). Ένα μη προσδιορισμένο αίτημα
`deepgram/nova-3` **δεν** χρησιμοποιεί το OpenRouter.

**Υποστηριζόμενες μορφές:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

## Ψευδώνυμα με διακριτικό για VS Code / Χωρίς κεφαλίδες

Χρησιμοποιήστε αυτά τα ψευδώνυμα όταν μια ενσωμάτωση δεν μπορεί να εισαγάγει μια κεφαλίδα `Authorization` και χρειάζεται το κλειδί API ενσωματωμένο στη βασική διεύθυνση URL.

```bash
# Ψευδώνυμο καταλόγου τύπου OpenAI
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# Ψευδώνυμα συνομιλίας τύπου OpenAI
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Ψευδώνυμα τύπου Ollama
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

Παράδειγμα:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

Σημειώσεις:

- Τα ψευδώνυμα με διακριτικό επαναχρησιμοποιούν τους ίδιους χειριστές με τα `/v1/*` και `/api/tags`· οι μορφές των αποκρίσεων παραμένουν πανομοιότυπες.
- Προτιμήστε το `Authorization: Bearer ...` όποτε το πρόγραμμα-πελάτης υποστηρίζει προσαρμοσμένες κεφαλίδες.
- Τα διακριτικά που βασίζονται σε URL ενδέχεται να εμφανίζονται σε αρχεία καταγραφής αντίστροφων διακομιστών μεσολάβησης, στο ιστορικό του προγράμματος περιήγησης και σε δεδομένα τηλεμετρίας εκτός του OmniRoute. Αντιμετωπίστε τα ως επιλογή συμβατότητας και όχι ως τον προεπιλεγμένο τρόπο ελέγχου ταυτότητας.

## Όρια Token

Προϋπολογισμοί **token** ανά κλειδί API (διακριτοί από τον παραπάνω προϋπολογισμό βάσει USD). Επιβάλλονται απευθείας κατά την επεξεργασία του αιτήματος: όταν η χρήση ενός κλειδιού στο τρέχον χρονικό παράθυρο φτάσει το όριό του, τα αιτήματα απορρίπτονται με `429 Too Many Requests`. Τα όρια μπορούν να περιορίζονται σε συγκεκριμένο `model`, σε `provider` ή να εφαρμόζονται σε επίπεδο `global` σε ολόκληρο το κλειδί· όταν αντιστοιχούν πολλά όρια σε ένα αίτημα, υπερισχύει το πιο περιοριστικό.

```bash
# Παραθέτει τα όρια token ενός κλειδιού (περιλαμβάνει την τρέχουσα χρήση του χρονικού παραθύρου)
GET /api/usage/token-limits?apiKeyId=key-123

# Δημιουργεί ή ενημερώνει ένα όριο token
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Διαγράφει ένα όριο token βάσει id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Σημειώσεις σχήματος** (`setTokenLimitSchema`): Τα `apiKeyId` και `scopeType` (`model` | `provider` | `global`) είναι υποχρεωτικά. Το `scopeValue` είναι υποχρεωτικό, εκτός εάν το `scopeType` είναι `global` (π.χ. ένα αναγνωριστικό μοντέλου για εμβέλεια `model`, ένα αναγνωριστικό παρόχου για εμβέλεια `provider`). Το `tokenLimit` πρέπει να είναι θετικός ακέραιος (μετατρέπεται από συμβολοσειρά). Προαιρετικά: `id` (παραλείψτε το για δημιουργία, συμπεριλάβετέ το για ενημέρωση), `resetInterval` (`daily` | `weekly` | `monthly`, προεπιλογή `monthly`), `resetTime` (`HH:MM`), `enabled` (προεπιλογή `true`). Οι αποκρίσεις `GET` εμπλουτίζουν κάθε όριο με τα `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` και `nextResetAt`. Πρόκειται για endpoint κατηγορίας διαχείρισης (ο έλεγχος ταυτότητας επιβάλλεται κεντρικά από τη διοχέτευση εξουσιοδότησης).

## Επεξεργασία Αιτημάτων

1. Ο πελάτης στέλνει αίτημα στο `/v1/*`
2. Ο χειριστής διαδρομής καλεί `handleChat`, `handleEmbedding`, `handleAudioTranscription` ή `handleImageGeneration`
3. Γίνεται επίλυση του μοντέλου (άμεσος πάροχος/μοντέλο ή ψευδώνυμο/συνδυασμός)
4. Επιλέγονται διαπιστευτήρια από την τοπική βάση δεδομένων, με φιλτράρισμα βάσει διαθεσιμότητας λογαριασμού
5. Για συνομιλία: το `handleChatCore` ελέγχει τη σημασιολογική cache/cache υπογραφών και επιλύει τις ρυθμίσεις συμπίεσης του συνδυασμού
6. Η προληπτική συμπίεση εκτελείται πριν από τη μετάφραση για τον πάροχο, όταν είναι ενεργοποιημένη (`lite`, Caveman, RTK ή σε στοίβα)
7. Ο εκτελεστής του παρόχου στέλνει το αίτημα προς την υπηρεσία ανάντη
8. Η απόκριση μεταφράζεται ξανά στη μορφή του πελάτη (συνομιλία) ή επιστρέφεται ως έχει (ενσωματώσεις/εικόνες/ήχος)
9. Καταγράφονται η χρήση, τα αναλυτικά στοιχεία συμπίεσης και τα αρχεία καταγραφής αιτημάτων
10. Σε περίπτωση σφαλμάτων εφαρμόζεται εναλλακτική δρομολόγηση σύμφωνα με τους κανόνες του συνδυασμού

Πλήρης αναφορά αρχιτεκτονικής: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Ανθεκτικότητα (εκτεταμένη)

Το OmniRoute παρέχει τρεις ανεξάρτητους μηχανισμούς προσωρινής αποτυχίας· τα παρακάτω endpoints διαχείρισης επιτρέπουν στους διαχειριστές να τους ελέγχουν και να παρακάμπτουν τις ρυθμίσεις τους:

| Εμβέλεια                   | Αποθήκευση κατάστασης                     | Ανάγνωση                                  | Επαναφορά / εκκαθάριση                                    |
| -------------------------- | ----------------------------------------- | ----------------------------------------- | --------------------------------------------------------- |
| Διακόπτης παρόχου          | `domain_circuit_breakers` + στη μνήμη     | `/api/monitoring/health`                  | `POST /api/resilience/reset`                              |
| Περίοδος αναμονής σύνδεσης | `rateLimitedUntil` στις συνδέσεις παρόχων | `/api/rate-limits`, `/api/providers/[id]` | (επανενεργοποιείται αδρανώς· εκκαθάριση μέσω PUT παρόχου) |
| Αποκλεισμός μοντέλου       | Μητρώο διαθεσιμότητας μοντέλων στη μνήμη  | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                  |

Το `PATCH /api/resilience` δέχεται παρακάμψεις του διακόπτη παρόχου στα `providerBreaker.oauth` και `providerBreaker.apikey`. Κάθε προφίλ υποστηρίζει τα `degradationThreshold`, `failureThreshold` και `resetTimeoutMs`· τα ίδια πεδία είναι διαθέσιμα στο Πίνακας ελέγχου → Ρυθμίσεις → Ανθεκτικότητα.

```bash
# Εκκαθάριση αποκλεισμού ενός μοντέλου
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Διαγραφή όλων των αποκλεισμών
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Για την πλήρη εννοιολογική αναφορά και τις προεπιλογές του διακόπτη, ανατρέξτε στο [`CLAUDE.md`](../../CLAUDE.md) → "Κατάσταση χρόνου εκτέλεσης ανθεκτικότητας" και στο [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Ουρά περιορισμού ρυθμού και δικλείδα ασφαλείας αυτόματης ενεργοποίησης

- **Υποστηριζόμενη διαδρομή εγγραφής**: Το `POST /api/rate-limits` με σώμα `{"connectionId": "<id>", "enabled": true|false}` είναι το υποστηριζόμενο endpoint διαχείρισης για την ενεργοποίηση ή απενεργοποίηση της προστασίας περιορισμού ρυθμού μιας σύνδεσης. Το `PUT /api/providers/[id]` σκοπίμως δεν τροποποιεί ούτε αντιστρέφει το `rateLimitProtection` (#11278).
- **Σημασιολογία του `enabled: false`**: Ο ορισμός του `enabled: false` καταργεί τη ρητή προστασία της σύνδεσης, αλλά **δεν** εξαιρεί μια ενεργή σύνδεση με κλειδί API από την καθολική δικλείδα ασφαλείας αυτόματης ενεργοποίησης (`autoEnableApiKeyProviders = true`). Στο `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`), τα `false` και `undefined` είναι ισοδύναμα· οι ενεργές συνδέσεις με κλειδί API χωρίς ρητή προστασία παραμένουν προστατευμένες από τη δικλείδα ασφαλείας αυτόματης ενεργοποίησης.
- **Καθολική απενεργοποίηση**: Για την εκτέλεση συνδέσεων με κλειδί API χωρίς ουρές περιορισμού ρυθμού, απενεργοποιήστε καθολικά τη δικλείδα ασφαλείας μέσω του `RATE_LIMIT_AUTO_ENABLE=false` (μεταβλητή περιβάλλοντος) ή του `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Ρυθμίσεις → Ανθεκτικότητα / `PATCH /api/resilience`).

## Διακομιστής MCP

Το OmniRoute διαθέτει έναν ενσωματωμένο διακομιστή Model Context Protocol με 3 μεταφορές (stdio, SSE, streamable-http) και εργαλεία με καθορισμένο πεδίο εφαρμογής. Τα παρακάτω endpoints του πίνακα ελέγχου διαβάζουν δεδομένα κατάστασης/ελέγχου και λειτουργούν ως proxy για τις μεταφορές HTTP.

| Μέθοδος | Διαδρομή | Περιγραφή |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | Σήμα ζωής, μεταφορά, κατάσταση σύνδεσης, τελευταία κλήση, κορυφαία εργαλεία, ποσοστό επιτυχίας 24 ωρών |
| GET | `/api/mcp/tools` | Λίστα εργαλείων MCP με `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` |
| GET | `/api/mcp/sse` | Άνοιγμα ροής SSE για τη μεταφορά SSE (επιστρέφει `503` εάν το MCP είναι απενεργοποιημένο ή δεν ταιριάζει η μεταφορά) |
| POST | `/api/mcp/sse` | Αποστολή πλαισίου JSON-RPC μέσω της μεταφοράς SSE |
| GET | `/api/mcp/stream` | Άνοιγμα της πλευράς SSE της μεταφοράς Streamable HTTP (μηνύματα που εκκινούν από τον διακομιστή) |
| POST | `/api/mcp/stream` | Αποστολή πλαισίου JSON-RPC μέσω της μεταφοράς Streamable HTTP |
| DELETE | `/api/mcp/stream` | Τερματισμός συνεδρίας Streamable HTTP |
| GET | `/api/mcp/audit` | Αναζήτηση στο αρχείο καταγραφής ελέγχου — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | Συγκεντρωτικά στατιστικά ελέγχου (σύνολα, ποσοστό επιτυχίας, μέση διάρκεια, κορυφαία εργαλεία) |

**Έλεγχος ταυτότητας:** οι μεταφορές `sse`/`stream` χρησιμοποιούν την ειδική επιφάνεια ελέγχου ταυτότητας του MCP (κλειδί API Bearer με πεδίο εφαρμογής `mcp`)· οι διαδρομές `status`/`tools`/`audit*` είναι προσβάσιμες για ανάγνωση από τον πίνακα ελέγχου (δεν απαιτείται πρόσθετος έλεγχος ταυτότητας πέρα από την πρόσβαση στον κεντρικό υπολογιστή του πίνακα ελέγχου).

> Και οι δύο μεταφορές HTTP ελέγχονται από τα `settings.mcpEnabled` και `settings.mcpTransport` — μια ασυμφωνία μεταφοράς επιστρέφει `400`, ενώ μια κατάσταση απενεργοποιημένου MCP επιστρέφει `503`.

## Διακομιστής A2A

Το OmniRoute παρέχει ένα τελικό σημείο A2A (Agent-to-Agent) JSON-RPC 2.0, καθώς και ένα περίβλημα REST για χρήση επιθεώρησης/πίνακα ελέγχου.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # προαιρετικό, εκτός εάν έχει οριστεί το OMNIROUTE_API_KEY
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Υποστηριζόμενες μέθοδοι (όλες ελέγχονται μέσω του `settings.a2aEnabled`):

| Μέθοδος          | Περιγραφή                                                              |
| ---------------- | ---------------------------------------------------------------------- |
| `message/send`   | Σύγχρονη εκτέλεση δεξιότητας· επιστρέφει `{task, artifacts, metadata}` |
| `message/stream` | Εκτέλεση ροής SSE του ίδιου συνόλου δεξιοτήτων                         |
| `tasks/get`      | Ανάκτηση μιας εργασίας μέσω `taskId`                                   |
| `tasks/cancel`   | Ακύρωση μιας εργασίας μέσω `taskId`                                    |

Ενσωματωμένες δεξιότητες: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Κάρτα πράκτορα

```bash
GET /.well-known/agent.json
```

Επιστρέφει τη δημόσια κάρτα πράκτορα A2A (όνομα, περιγραφή, δυνατότητες, κατάλογος δεξιοτήτων, σχήμα ελέγχου ταυτότητας) — αποθηκεύεται δημόσια στην κρυφή μνήμη για 1h. Δεν απαιτείται έλεγχος ταυτότητας.

### Βοηθητικά REST

| Μέθοδος | Διαδρομή                     | Περιγραφή                                                                                                           |
| ------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| GET     | `/api/a2a/status`            | Κατάσταση ενεργοποίησης A2A + στατιστικά εργασιών + σύνοψη της αποθηκευμένης στην κρυφή μνήμη κάρτας πράκτορα       |
| GET     | `/api/a2a/tasks`             | Λίστα εργασιών — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST    | `/api/a2a/tasks`             | (Δεν έχει υλοποιηθεί ως βοηθητικό REST — δημιουργήστε μέσω JSON-RPC `message/send`)                                 |
| GET     | `/api/a2a/tasks/[id]`        | Ανάκτηση μίας εργασίας                                                                                              |
| POST    | `/api/a2a/tasks/[id]/cancel` | Ακύρωση μιας εργασίας                                                                                               |

**Έλεγχος ταυτότητας:** τα βοηθητικά REST εκτελούνται χωρίς έλεγχο ταυτότητας διαχείρισης (αναγνώσιμα από τον πίνακα ελέγχου)· η διαδρομή JSON-RPC `/a2a` χρησιμοποιεί Bearer `OMNIROUTE_API_KEY`, εάν έχει ρυθμιστεί.

## Έλεγχος ταυτότητας

Ανατρέξτε στην ενότητα [Έλεγχος ταυτότητας διαχείρισης](../guides/MANAGEMENT-AUTH.md) για τις τέσσερις
οικογένειες διαπιστευτηρίων (συνεδρία πίνακα ελέγχου, τοπικό διακριτικό CLI, Διακριτικό
πρόσβασης `oma_live_…`, κλειδί API με εμβέλεια διαχείρισης) και για το πώς διαφέρουν από τα κλειδιά συμπερασμού.

- Οι διαδρομές του πίνακα ελέγχου (`/dashboard/*`) χρησιμοποιούν το cookie `auth_token`
- Η σύνδεση χρησιμοποιεί το αποθηκευμένο hash κωδικού πρόσβασης, με εναλλακτική χρήση του `INITIAL_PASSWORD`
- Το `requireLogin` μπορεί να ενεργοποιηθεί ή να απενεργοποιηθεί μέσω του `/api/settings/require-login`
- Οι διαδρομές `/v1/*` απαιτούν προαιρετικά κλειδί API τύπου Bearer όταν `REQUIRE_API_KEY=true`
- Οι όροι «διακριτικό διαχείρισης» / «κλειδί API με εμβέλεια διαχείρισης» σε αυτήν την αναφορά σημαίνουν μία από τις οικογένειες που περιγράφονται σε εκείνον τον οδηγό — όχι έναν απροσδιόριστο πρόσθετο τύπο μυστικού

> **Αλλαγή που διακόπτει τη συμβατότητα (v3.8.0)** — Τα `/api/v1/agents/tasks/*` και τα τελικά σημεία διαχείρισης χρόνου αναμονής απαιτούν πλέον **έλεγχο ταυτότητας διαχείρισης** (cookie `auth_token` του πίνακα ελέγχου ή κλειδί API με εμβέλεια διαχείρισης). Οι πελάτες που προηγουμένως καλούσαν αυτές τις διαδρομές χωρίς έλεγχο ταυτότητας θα λαμβάνουν `401 Unauthorized`. Ανατρέξτε στο commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
