## Chatfuldførelser

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Brugerdefinerede headere

| Header                   | Retning   | Beskrivelse                                                                                                                                                                                                             |
| ------------------------ | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Anmodning | Indstil til `true` for at omgå cachen                                                                                                                                                                                   |
| `x-omniroute-no-memory`  | Anmodning | Indstil til `true` for at springe injektion af hukommelse og færdigheder over for denne anmodning (svarer til no-cache og undgår token-/omkostningsoverhead pr. kald)                                                   |
| `X-OmniRoute-Progress`   | Anmodning | Indstil til `true` for statushændelser                                                                                                                                                                                  |
| `X-Session-Id`           | Anmodning | Fast sessionsnøgle til ekstern sessionstilknytning                                                                                                                                                                      |
| `x_session_id`           | Anmodning | Variant med understregning accepteres også (direkte HTTP)                                                                                                                                                               |
| `X-OmniRoute-Session-Id` | Anmodning | Sessions-/samtaletag leveret af kalderen (bruges også af hukommelsen). Når det findes, gemmes det ordret i `call_logs.session_tag` til omkostningsfordeling pr. session (#8249) — det genereres aldrig, når det mangler |
| `Idempotency-Key`        | Anmodning | Dedupliceringsnøgle (vindue på 5 sek.)                                                                                                                                                                                  |
| `X-Request-Id`           | Anmodning | Alternativ dedupliceringsnøgle                                                                                                                                                                                          |
| `x-omniroute-connection` | Anmodning | Fastlås en anmodning med én model til én udbyderforbindelse (konto) via dens id — se [Fastlåsning til konto pr. anmodning](#account-pinning-per-request)                                                                |
| `X-OmniRoute-Cache`      | Svar      | `HIT` eller `MISS` (uden streaming)                                                                                                                                                                                     |
| `X-OmniRoute-Idempotent` | Svar      | `true`, hvis dedupliceret                                                                                                                                                                                               |
| `X-OmniRoute-Progress`   | Svar      | `enabled`, hvis statussporing er slået til                                                                                                                                                                              |
| `X-OmniRoute-Session-Id` | Svar      | Effektivt sessions-id anvendt af OmniRoute                                                                                                                                                                              |
| `X-OmniRoute-Request-Id` | Svar      | Korrelations-id for anmodningen (når det er kendt)                                                                                                                                                                      |
| `X-OmniRoute-Version`    | Svar      | OmniRoutes buildversion (altid til stede)                                                                                                                                                                               |
| `X-OmniRoute-Cost-Saved` | Svar      | Det USD-beløb, som cachen sparede ved et HIT (kun cachehits)                                                                                                                                                            |
| `X-OmniRoute-Decision`   | Svar      | Routingsporing: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` er kombinationsstrategien eller `single` for en anmodning uden kombination) — altid til stede i fuldførelsessvar                          |

> Nginx-bemærkning: Hvis du er afhængig af headers med understregningstegn (f.eks. `x_session_id`), skal du aktivere `underscores_in_headers on;`.

#### Fastlåsning af konto pr. anmodning

Når en udbyder har flere forbindelser (konti eller nøgler), vælger OmniRoute normalt én
via sin strategi for kontovalg. En anmodning kan i stedet fastlåses til én bestemt forbindelse
med headeren `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Hvor id'et findes.** Åbn udbydersiden i dashboardet
  (**Dashboard → Udbydere → <udbyder>**), og klik på id-mærket `xxxxxxxx…` på en forbindelsesrække
  — så kopieres det fulde forbindelses-id.
- **Hvilke anmodninger der respekterer det.** Anmodninger med én model (`provider/model`) på
  `/v1/chat/completions`, `/v1/messages` og `/v1/responses`. Kombinationer ignorerer headeren: Fastlås
  i stedet en konto pr. kombinationstrin via trinnets egen forbindelse.
- **Fastlåsningen er streng, ikke en præference.** Den fastlåste forbindelse bruges udelukkende. En
  fejl i anmodningen registrerer kontoens nedkølingsperiode, men skifter **ikke** til en
  anden konto hos samme udbyder.
- **Nedkøling og kvote frigiver fastlåsningen.** Mens den fastlåste forbindelse er under nedkøling,
  har opbrugt sin kvote eller er blokeret af en kvotepolitik, falder senere anmodninger tilbage til udbyderens
  øvrige forbindelser, præcis som trafik uden fastlåsning.
- **Ukendte eller deaktiverede id'er medfører fejl.** Et id, der ikke findes i udbyderens aktive pulje (slettet,
  deaktiveret eller tilhørende en anden udbyder), efterlader ingen kvalificeret konto, så anmodningen
  mislykkes i stedet for lydløst at blive dirigeret et andet sted hen.

Claude Code sender brugerdefinerede headers via `ANTHROPIC_CUSTOM_HEADERS`. Placer den i `env`-blokken
i `~/.claude/settings.json` eller i en `.claude/settings.json` på projektniveau for at fastlåse en anden
konto pr. projekt:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Kilde: `src/sse/handlers/chat.ts` (læsning af header), `src/sse/services/auth.ts` og
`src/sse/services/sessionAffinityPin.ts` (frigivelse af fastlåsning og kontrollen for manglende tilstedeværelse i puljen).

> **Headers til omkostningstelemetri:** Vellykkede ikke-streamede svar indeholder også sættet af `X-OmniRoute-*`-headers til omkostningstelemetri — `X-OmniRoute-Response-Cost` (USD, fast 10 decimaler; `0.0000000000` for gratis/ikke-prissat), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` og `X-OmniRoute-Fallback-Attempts` (kun når > 0) samt `X-OmniRoute-Request-Id` og `X-OmniRoute-Version`. Disse udsendes af chatfuldførelser, `/v1/responses`, `/v1/messages` **og medieendepunkterne** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` og `/v1/moderations` (altid med omkostningen `0`). Medieomkostninger beregnes pr. modalitet (pr. billede, pr. sekund, pr. tegn eller pr. søgeenhed), når priser er tilgængelige, ellers `0` (fejler åbent).

> **Omkostningssemantik ved cache-hit:** Ved et HIT i den semantiske cache (`X-OmniRoute-Cache-Hit: true`) foretages der intet upstream-kald, så `X-OmniRoute-Response-Cost` er `0.0000000000` (den **inkrementelle** omkostning ved at levere cache-hittet). Den oprindelige omkostning/omkostningen, der ellers ville være påløbet, rapporteres separat i `X-OmniRoute-Cost-Saved`. Faktureringssystemer bør summere `X-OmniRoute-Response-Cost` (cache-hits koster intet); cacheanalyse kan aggregere `X-OmniRoute-Cost-Saved`.

## Eksklusive administrerede sessionslejemål

Eksklusiv administration af sessionslejemål er en valgfri, klientneutral routingkontrakt: Én aktiv ejer
besidder én kvalificeret OmniRoute-forbindelse. Den udlejer ikke en model, kræver ikke OAuth, identificerer
ikke en bestemt klient og kræver ikke en bestemt udbyder.

Den API-nøgle, der bruges til godkendelse, skal have rettigheden `lease:exclusive` og en eksplicit ikke-tom
`allowedConnections`-liste. Databasens mutationsgrænse håndhæver begge felter samlet ved oprettelse af nøgler
og delvise opdateringer.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Vellykkede svar på overtagelse, fornyelse og frigivelse viser tidsstempler, `state` og den nøjagtige positive
`generation`, men aldrig den valgte forbindelse eller legitimationsoplysninger. Ved fornyelse og frigivelse
angives generationen i JSON-brødteksten:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

En aktiv lejemålsejer kan eksplicit anmode om visningsmetadata, der beskytter privatlivets fred, for sin aktuelle binding:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Denne valgfrie statushandling afskærmes af den uigennemsigtige ejer, den godkendte administrerede API-nøgle og den nøjagtige
aktive generation i én databasetransaktion. `displayName` er kun det beskårne konfigurerede
forbindelsesnavn; det er `null`, når der ikke findes et sikkert konfigureret navn. OmniRoute erstatter det aldrig med en
e-mailadresse eller en genereret kontoidentitet. Udbyderværdien er en ikke-følsom visningsetiket og aldrig
en genereret identifikator for en kompatibel udbyder. Legitimationsoplysninger, tokens, cookies, rå forbindelses- eller API-
nøgle-id'er, ejerhashes, afskærmningshemmeligheder og interne routingdata udelades.

Opslag med forkert nøgle, forkert ejer, forældet generation, manglende, udløbne, frigivne eller ugyldiggjorte lejemål
returnerer alle den samme `409 LEASE_FENCE_STALE`-fejl uden forbindelsesmetadata. En klient, der har modtaget svaret om kapacitetsventetid, har ingen aktiv binding at inspicere. Når routing ændrer et aktivt lejemål,
forbliver den samme generation gyldig, og status returnerer atomisk den nye binding, aldrig den gamle.
Eksisterende klienter forbliver uændrede, fordi svar på overtagelse, fornyelse, frigivelse og ventetid bevarer
deres tidligere strukturer.

Denne serverkontrakt ændrer ikke standardfunktionen OpenAI Codex `/status`. Standard-Codex rapporterer i øjeblikket sin
modeludbyder og indbyggede godkendelses-/kontostatus, men viser ikke vilkårlige kontometadata for
tilpassede udbydere. En senere klientintegration skal kalde denne handling og afgøre, hvordan
`connection.displayName` skal vises.

Hver administreret inferensanmodning angiver derefter begge kontrolheadere:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Den nøjagtige ejer, generation, aktive forbindelse og godkendte API-nøgle afskærmes umiddelbart
før hvert understøttet upstream-forsøg. Genafspilning af ejer og generation med en anden nøgle mislykkes, selv
når denne nøgle tillader den samme forbindelse. Rå ejere gemmes, logges eller bevares ikke i
anmodningsøjebliksbilledet og videresendes ikke upstream.

Midlertidig kapacitetskonflikt returnerer HTTP `429` med `Retry-After` og:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Dette svar betyder kun, at det normale sæt af kvalificerede forbindelser ikke var tomt, og at alle ledige kandidater var
besat af et fremmed aktivt lejemål. Ikke-understøttede modeller/udbydere, uoverensstemmelse med politik, nedkøling, kvote,
tilstand og andre almindelige kvalifikationsfejl bevarer deres eksisterende OmniRoute-svar.

### `x-omniroute-compression`

Tilsidesættelse af komprimeringsplanen pr. anmodning. Højeste prioritet — går forud for routingkombinationens
tilsidesættelse, den aktive profil, automatiske udløsning og panelets standardindstilling. Værdier:

| Værdi         | Effekt                                                                                                            |
| ------------- | ----------------------------------------------------------------------------------------------------------------- |
| `off`         | Ingen komprimering for denne anmodning.                                                                           |
| `default`     | Panelets afledte standardprofil (ignorerer den aktive profil). Tabsbehæftede motorer forbliver deaktiverede.      |
| `safe`        | Kun deduplikering og foldning af blanktegn.                                                                       |
| `allow-lossy` | Behold operatørplanen for denne anmodning, inklusive resuméer og stilomskrivninger.                               |
| `engine:<id>` | En enkelt motor, når den er aktiveret, f.eks. `engine:rtk`. Valgfri aktivering af denne motor pr. anmodning.      |
| `<combo>`     | En navngiven kombination, først matchet efter navn (uden forskel på store og små bogstaver) og derefter efter id. |

Bemærkninger:

- Ukendte værdier ignoreres (anmodningen afvises aldrig); evalueringen fortsætter med den normale operatørprioritet.
- Hvis flere kombinationer har samme navn, skal kombinationens **id** angives for at opnå et deterministisk match.
- En kombination, hvis navn er `off` eller `default`, kan ikke vælges efter navn (disse nøgleord fortolkes først); henvis til en sådan kombination via dens id.
- Hovedkontakten for komprimering er en absolut spærring: Når komprimering er deaktiveret globalt, kan denne header ikke aktivere den.

Den anvendte plan returneres i svarheaderen:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

hvor `<source>` er én af `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` eller `off`.

## Embeddings

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Tilgængelige udbydere: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Katalog-id'er er `provider/model` (eksempel: `jina-ai/jina-embeddings-v5-omni-small`). Jina-model-id'er uden præfiks, som findes i registreringsdatabasen (f.eks. `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`), kan også slås op. Jina embed/rerank/classify/segment bruger først `jina-ai`-legitimationsoplysninger fra dashboardet; `JINA_AI_API_KEY` bruges kun som reserve, når der ikke findes en dashboardnøgle. `jina-reader`-kortet er kun til Reader / `r.jina.ai` (`POST /v1/web/fetch`) og leverer aldrig embeddings eller rerank.

Modeller i registreringsdatabasen, der angiver understøttelse af multimodalitet, accepterer også op til 32 strukturerede elementer, som er uafhængige af udbyderen. Medieelementtyperne er `text`, `image`, `audio`, `video` og `document`. Deres medie-`source` er enten `{"type":"url","url":"https://..."}` eller `{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano` og familiealiasset `jina-ai/jina-embeddings-v5-omni` → omni-small) accepterer også Jinas oprindelige EmbeddingsV5Request-dokumenter og **videresender dem intakte** til `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Oprindelige `{ image | audio | video | pdf }`-værdier kan være en offentlig HTTPS-URL, en `data:`-URI eller rå base64. OmniRoute konverterer ikke disse objekter til strenge og henter ikke oprindelige billed-URL'er — Jina henter selv offentlige medier. Ekstra Jina-felter (`task`, `normalized`, `truncate`, `embedding_type`) videresendes. Jina-SKU'er, der kun understøtter tekst, afviser fortsat dokumenter, der ikke er tekst.

Sikkerheds- og transportgrænser:

- Eksterne medie-URL'er skal være offentlige HTTPS-URL'er. Kanoniske `{type,source:url}`-elementer hentes på serversiden (fornyet validering af omdirigeringer, timeout, størrelsesgrænser, offentlig DNS, fastlåsning af forbindelser) og indlejres før kaldet til udbyderen. Jina-oprindelige `{image:"https://..."}`-elementer videresendes, som de er, efter den samme kontrol af offentlig HTTPS; Jina henter URL'en.
- Indlejrede base64-medier er begrænset til 8 MiB afkodet pr. element og 16 MiB afkodet på tværs af anmodningen.

Udbyderoversættelse (kanoniske elementer videresendes aldrig uændret):

- Jina-multimodalitetsmodeller: Hvert element på øverste niveau bliver til ét objekt med en modalitetsnøgle (`text` / `image` / `audio` / `video` / `pdf`), som bruger data-URI'er til indlejrede medier; én vektor pr. element på øverste niveau.
- Gemini Embedding 2-familien: Ét array på øverste niveau bliver til en enkelt oprindelig `models/{model}:embedContent`-anmodning med `content.parts` (`text` eller `inline_data`).
- llama.cpp (`llama-cpp/<model>`, enhver model, som den lokale server har indlæst): Kanoniske `text`-elementer bliver til almindelige strenge, og `image` / `audio` / `video` bliver hver til ét `{"content": [part]}`-objekt ved hjælp af llama-servers chatindholdsdele (`image_url`, `input_audio` med formatet `wav` / `mp3` / `flac`, `input_video`) med indlejrede data; én vektor pr. element på øverste niveau. Serveren skal køre med `--embedding --mmproj …`; uden en projektor afviser den selv medier. `document` understøttes ikke.
- Ukendte/dynamiske modeller uden eksplicitte modalitetsmetadata afviser struktureret input med HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Ikke-understøttede kombinationer af model/modalitet returnerer HTTP 400 i stedet for at konvertere elementet. Udvidelsesfelter, der ikke er inputfelter, i ældre streng-/tokenanmodninger videresendes fortsat uændret.

```bash

GET /v1/embeddings
```

## Billedgenerering

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Tilgængelige udbydere omfatter OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (lokal), ComfyUI (lokal).

`n` returnerer `n` billeder i `data[]`. Udbydere, hvis upstream-API returnerer ét billede pr. kald
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), modtager `n` separate upstream-kald med højst 4 samtidige kald. En
fast `seed` forskydes med kaldets indeks (`seed`, `seed + 1`, …), så billederne er forskellige, men stadig
reproducerbare. `n` er begrænset til 10. Anmodningen mislykkes som helhed, hvis et af kaldene mislykkes. Listen
over fan-out-formater findes i `SINGLE_IMAGE_FANOUT_FORMATS` i
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux genbruger den eksisterende API-nøgleforbindelse og accepterer præfikserne `zenmux/` eller `zm/`:

- `zenmux/openai/gpt-image-2` bruger ZenMux' OpenAI Images API. Valgmulighederne omfatter `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` og `response_format`.
- Andre udgivere, såsom `zm/meta/muse-image-1.0`, bruger ZenMux' Vertex AI-`:predict`-
  slutpunkt. `n` svarer til `sampleCount`, `aspect_ratio` til `aspectRatio` og `image_size`
  (`1K`, `2K`, `4K`) til `sampleImageSize`. En pixelbaseret `size` angiver kun et billedformat,
  ikke garanterede pixeldimensioner. Understøttede billedformater, opløsninger og antal varierer efter model.
- `zm/inclusionai/ming-image-0.1-design` vælger selv sine dimensioner. Udelad `size`,
  `aspect_ratio` og `image_size`; eksplicitte værdier returnerer HTTP 400. PNG, JPEG og WebP
  kan anmodes om med `output_format`.

Denne integration understøtter tekst-til-billede-generering, ikke redigering af referencebilleder. Vertex-
output normaliseres til `data[].b64_json`; `response_format: "url"` returnerer en upstream-
HTTPS-URL eller en base64-data-URL, når kun billedbytes er tilgængelige. Tomme/filtrerede output
returnerer en fejl i stedet for et tomt, vellykket svar. Modeladgang afhænger af ZenMux-kontoen.
Se [ZenMux' Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) og
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash

GET /v1/images/generations
```

## Dokument-OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` vælger OCR-udbyderen via et `provider/model`-præfiks; et model-id uden præfiks (f.eks.
`mistral-ocr-latest`) slås op hos den registrerede udbyder, og hvis `model` udelades, bruges
Mistral (`mistral-ocr-latest`) som standard. Registrerede udbydere (`open-sse/config/ocrRegistry.ts`):

| Udbyder-id                    | Model-id             | `model`-værdi                                                  | Bemærkninger                                                                                          |
| ----------------------------- | -------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (eller blot `mistral-ocr-latest`) | Synkron — svaret returneres direkte fra det enkelte upstream-kald.                                    |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                    | Asynkron upstream (`analyze` + polling) — se nedenfor.                                                |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                        | Synkron via Vertex AI's `openapi/chat/completions`-partnerslutpunkt — se nedenfor om godkendelse/URL. |

Alle tre udbydere svarer med den samme Mistral-formaterede struktur:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Pollingforløb for Azure Document Intelligence

Azure Document Intelligence's `analyze`-API er asynkront: Den indledende anmodning returnerer en
`Operation-Location`-header i stedet for en brødtekst, og der skal foretages polling for at hente resultatet. Handleren
(`open-sse/handlers/ocr.ts`) poller denne URL hvert sekund i op til 30 forsøg, stopper straks (fortsætter
ikke med at polle) ved et pollingsvar, der ikke er `ok`, eller en `"failed"`-status og returnerer `504`, hvis
handlingen stadig kører, efter at antallet af tilladte forsøg er opbrugt. Det endelige Azure-svar
normaliseres til det samme `pages`/`markdown`-format, som Mistral bruger, før det returneres til
kalderen, så klientkoden ikke behøver at specialbehandle udbyderen.

### Godkendelse og slutpunktsopløsning for Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` genbruger den samme Vertex AI-godkendelse, som OmniRoute allerede understøtter til
chat-/billedtrafik (`open-sse/executors/vertex.ts`): Forbindelsens API-nøgle er enten en
Service Account JSON-legitimationsoplysning (som udveksles med et kortvarigt OAuth-adgangstoken via JWT-bearer-
forløbet) eller et allerede udstedt OAuth-adgangstoken, som bruges uændret. Upstream-slutpunktets URL er Vertex'
generiske `openapi/chat/completions`-partnerslutpunkt, som bygges ud fra forbindelsens projekt og
region — en eksplicit `providerSpecificData.project`/`providerSpecificData.region` har altid forrang;
ellers udledes projektet fra Service Account JSON's `project_id`, og regionen sættes som standard
til `us-central1`. Begge opløsninger foretages i `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) og bruges af
`src/app/api/v1/ocr/route.ts`, før anmodningen videresendes til `handleOcr`.

### Præfikser for model-id'er (`?prefix=`)

De fleste modeller annonceres under et **udbyderpræfiks**. Hvilket præfiks du får, styres af
funktionsflaget `MODELS_CATALOG_PREFIX_MODE` og kan tilsidesættes **pr. anmodning** med en
forespørgselsparameter — nyttigt for en klient, der ønsker en overskuelig liste uden at ændre
indstillingen for hele serveren for alle andre:

```bash
GET /v1/models?prefix=alias        # ét id pr. model — det korte aliaspræfiks
GET /v1/models?prefix=dual         # begge former (serverens standard)
GET /v1/models?prefix=canonical    # kun det fulde udbyder-id-præfiks
```

| Tilstand    | Udsender                                                 | Bemærkninger                                                                                                                                                                       |
| ----------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **og** `claude/claude-sonnet-4-6` | **Standard.** Begge id'er dirigeres til den samme model; dette bevares, så klientkonfigurationer, der har hardkodet en af formerne, fortsat fungerer. Fordobler omtrent kataloget. |
| `alias`     | `cc/claude-sonnet-4-6`                                   | Én post pr. model. Udbydere uden et særskilt alias udsender stadig deres post, så intet går tabt.                                                                                  |
| `canonical` | `claude/claude-sonnet-4-6`                               | Én post pr. model under det fulde udbyder-id-præfiks. Udbydere uden et særskilt alias (f.eks. `antigravity/…`, `agy/…`) udsender også deres ene id her, så intet går tabt.         |

Et spejl i `dual`-tilstand kan også genkendes uden forespørgselsparameteren: Det indeholder et `parent`-felt,
der peger på det primære id.

Klienter, der viser en modelvælger, bør anmode om `?prefix=alias` — det er det, som
[OmniCopilot VS Code-udvidelsen](../guides/VSCODE-COPILOT.md) gør.

### Opdagelsesfiltre (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` accepterer valgfrie opdagelsesfiltre. Uden nogen af dem er svaret
uændret. De indsnævrer det katalog, som kalderen allerede kan se (API-nøgletilladelser anvendes først),
og de køres før OpenAI-lignende sideinddeling med `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # hver angivet funktion skal være tilgængelig
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # katalogets `type`; rækker uden en type er `chat`
GET /v1/models?q=sonnet&limit=10                           # match på id eller navn uden forskel på store og små bogstaver
```

| Parameter     | Værdier                                                                                             |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | ikke-negativt heltal, sammenlignet med `context_length`                                             |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 tegn                                                                                          |

En ukendt værdi eller en `min_context`, der ikke er et ikke-negativt heltal (f.eks. `1.5`),
returnerer HTTP `400`, og meddelelsen angiver de gyldige værdier. Implementering:
`src/app/api/v1/models/catalogFilters.ts`.

### Kortliste over modeller (`POST /v1/models/query`)

`POST /v1/models/query` returnerer en kort, deterministisk liste fra det samme katalog med den samme
godkendelse og synlighed pr. nøgle som `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Alle felter er valgfrie. `capabilities` og `exclude` accepterer en matrix eller en kommasepareret streng;
`max_output` sammenlignes med `max_output_tokens`. Resultater sorteres efter `owned_by` og derefter `id`.
Standardværdien for `limit` er `20`, og værdier over `100` begrænses til `100`. Ugyldig JSON, et ukendt
felt eller en ugyldig værdi returnerer HTTP `400`.

### Individuelt skjulte chatmodeller

En model, der er markeret som **Skjult** på sin udbyderside, udelades fra kataloget og afvises
med HTTP `404` / `model_not_found`, når der udtrykkeligt anmodes om den. Kontrollen bruger den fundne
udbyder og model, herunder udbyderaliasser, nodepræfikser for kompatible udbydere og
standardindstillinger for forbindelser. En kombination springer skjulte mål over og kan bruge en synlig søstermodel; når
der ikke er nogen eksekverbare mål tilbage, returnerer den den samme fejlkode. Ophævelse af skjulningen træder i kraft ved den næste
anmodning. Synlighedstilsidesættelser, der kun gælder billeder, skjuler ikke chatmodellen med det samme id.

Denne individuelle modelindstilling er adskilt fra
[tilladelses-/afvisningslisterne for modeleksponering](../routing/MODEL_EXPOSURE_LIST.md), som filtrerer katalogets
annoncering og kandidater til automatisk dirigering, mens eksplicit afsendelse bevares. API-nøglens
modeltilladelser gælder fortsat uafhængigt. Katalogets standardpræfikstilstand forbliver `dual`.

### Modelvarianter uden tænkning

For Claude-modeller med tænkefunktion annoncerer `/v1/models` også en **variant uden tænkning**, hvis id har præfikset `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Valg af dette id (f.eks. i en Claude Code-konfiguration, der altid vedhæfter en `thinking`-blok) fortolkes som den faktiske `<provider>/<model>` med ræsonnering deaktiveret — `thinking:{type:"disabled"}` på stien `/v1/messages`, eller med felterne `reasoning`/`reasoning_effort` udeladt på stien `/v1/chat/completions`. Varianten vises kun for modeller i Claude-familien, der understøtter tænkning **og** respekterer `disabled` (så f.eks. modeller, der kun understøtter adaptiv tænkning og afviser `disabled`, udelades). Operatører kan gennemtvinge aktivering eller deaktivering af varianten for hver model via `ModelSpec.noThinkingAlias`.

| POST   | `/v1/music/detailed/stream` | Native SSE-metadata og lydsegmenter      | `music`                        |
| POST   | `/v1/music/plan`            | JSON-kompositionsplan                    | `music`                        |

Disse endpoints supplerer de eksisterende ruter `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` og `/v1/speech-to-text`. Native JSON-felter
og query-parametre såsom `output_format` og `enable_logging` bevares.
Svar fra `/v1/music/detailed` bevarer deres multipart-grænser; fortolk dem som multipart.
`/v1/music/detailed/stream` returnerer `text/event-stream` med kompositionsmetadata og
base64-kodede lydsegmenter i SSE-hændelser. Alle seks ruter understøtter CORS-preflight.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# En kort lydeffekt. Varighed: 0,5 til 30 sekunder.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Musikvarighed angives i millisekunder: 3000 til 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Brug `/v1/music/stream` med det samme JSON-indhold til trinvis levering af lyd. Komposition
accepterer præcis én af `prompt` eller `composition_plan`; `/v1/music/plan` kræver `prompt`
og accepterer valgfrit `source_composition_plan`. De native skemaer bevarer yderligere
udbyderfelter, så versioner af kompositionsplaner og finjusteringsindstillinger når ElevenLabs.

Det samlede endpoint `/v1/music/generations` accepterer også `elevenlabs/music_v1`,
`elevenlabs/music_v2` og `elevenlabs/music_v2_5`. Med en aktiv ElevenLabs-forbindelse
vises disse modeller i musikkataloget. Dette endpoint returnerer
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Dets `duration`-felt er angivet i
sekunder og knyttes til `music_length_ms`; en eksplicit `music_length_ms` har forrang.
`instrumental` knyttes til `force_instrumental`, hvor det native felt har forrang.
Brug de native streaming-endpoints til streaming og det native kompositions-endpoint
til requests, der udelukkende styres af en kompositionsplan.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Begrænsninger for endpoint, model, budget og forbindelse anvendes før et upstream-kald. Native
ruter returnerer upstream-statuskoder og fejlindhold uændret, herunder `402` ved en
abonnementsbegrænsning og `429` ved en kvotegrænse. Headerne `character-cost`, `song-id`, `request-id` og `retry-after`
bevares, når de er til stede. En gratis kreditsaldo garanterer ikke adgang til alle
musikmodeller, outputformater eller API-funktioner: ElevenLabs afgør adgangsretten for hver request.
Det samlede endpoint bevarer fejlstatuskoder i OmniRoutes normaliserede fejlformat.

Upstream-kontrakter: [lydeffekter](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[musikkomposition](https://elevenlabs.io/docs/api-reference/music/compose) og
[detaljer om streaming af musik](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

> (oMLX, vLLM, Infinity, TEI bag en gateway, …), der adresseres som `<node-prefix>/<model>`. Loopback-
> noder (`localhost`, `127.0.0.1`, `172.16.0.0/12`) er altid kvalificerede, og det samme gælder værtsnavne, som
> operatøren angiver i `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (f.eks. et Docker/Compose-tjenestenavn som
> `http://reranker:8080/v1`; disse kaldes direkte, aldrig gennem `HTTP(S)_PROXY` eller en
> forbindelses fastlåste proxy). Noder på enhver anden
> vært — en maskine på lokalnetværket eller en Tailscale-peer — er kun kvalificerede, når operatøren aktiverer
> funktionsflaget `RERANK_REMOTE_PROVIDER_NODES` **og** nodens basis-URL overholder udbyderens
> politik for udgående URL'er (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Hukommelsesmotorens rerank-trin kalder denne rute via
> loopback, så den samme regel gælder for `rerankProviderModel` i hukommelsesindstillingerne.
>
> **Lokale serverformater:** noden kaldes på `<base>/v1/rerank` og, ved 404, på `<base>/rerank`
> (Infinity, TEI). Upstream-brødteksten indeholder både Cohere/OpenAI-stavemåden (`documents`,
> `return_documents`) og TEI-stavemåden (`texts`, `return_text`), og upstream-svaret
> normaliseres til Cohere-formatet: TEI's rene `[{index, score, text}]`, `{results: [{index, score}]}`
> fra simple gateways og Voyage-formatet `{data: [...]}` returneres alle til klienten som
> `{results: [{index, relevance_score, document?}]}`, sorteret efter score og begrænset til `top_n`.

> **Registrering af udbydernoder:** modeller på en OpenAI-kompatibel udbydernode vises i `GET /v1/models`
> under nodepræfikset. Rækker uden endpointmetadata (typisk for lokale `/v1/models`-oversigter)
> arver nodens `apiType`, så modellerne på en `embeddings`-node får `type: "embedding"`, og modellerne på en
> `rerank`-node får `type: "rerank"` i stedet for som standard at blive behandlet som chat; et eksplicit
> `supportedEndpoints` på en synkroniseret eller manuelt tilføjet række har stadig forrang.

### Exa og Tavily `provider_options`

Exa og Tavily læser udbyderspecifikke felter fra en navneområdespecifik samling:
`provider_options.exa` (eller `provider_options["exa-search"]`) og `provider_options.tavily`
(eller `provider_options["tavily-search"]`). Kun nøglerne nedenfor videresendes. Hver af dem
kontrolleres mod sit eget Zod-skema i `open-sse/handlers/search/providerOptionsPassthrough.ts`,
og en nøgle med den forkerte type udelades. Alle andre nøgler ignoreres, herunder godkendelse, basis-URL,
`stream` og `outputSchema`. De flade nøgler, der bruges af andre udbydere (`cx`, `depth`, ...), fungerer
som før.

| Udbyder | Felter på øverste niveau                                                                                                                                                                                                                                                                                                                                                  | Indlejrede                                                                                                                                                                |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa     | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (flade primitive værdier), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                      | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` flettes oven på standardværdien `{ text: true, highlights: true }` |
| Tavily  | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                         |

De generiske felter har altid forrang: `query`, `max_results`, `filters` (domæner), `country` og det
emne, der udledes af `search_type`. På Exa bevarer `search_type: "news"` værdien `category: "news"`.
Tavily accepterer også `search_type: "finance"` (`topic: "finance"`).

Det generiske `time_range` når nu begge udbydere: Exa modtager `startPublishedDate` (ISO-
tidsstempel), og Tavily modtager `start_date` (`YYYY-MM-DD`). En eksplicit dato i `provider_options`
tilsidesætter den tilknyttede dato.

Exa-resultater bevarer `id`, `highlight_scores`, `summary`, `subpages`, `entities` og `extras` i
`provider_raw`. Tavily-resultater bevarer `images` og `favicon`.

Omkostningsberegningen bruger fortsat det flade register `costPerQuery`. Tavily fakturerer
`search_depth: "advanced"` med flere kreditter pr. kald, og denne forskel afspejles ikke i
`usage.search_cost_usd`.

## Webhentnings-API

Udtræk indhold fra en URL via en konfigureret webhentningsudbyder (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, samme API-nøgle som Parallel Search) returnerer kun
Markdown — ethvert andet `format` giver en `400` — og begrænser indholdet til 100.000 tegn. Når
selve målsiden ikke kan udtrækkes, rapporterer upstreamtjenesten det i et HTTP 200-svar;
OmniRoute viser dette som en `422` med en fast meddelelse.

| Metode | Sti             | Beskrivelse                                                |
| ------ | --------------- | ---------------------------------------------------------- |
| POST   | `/v1/web/fetch` | Hent/skrabet en URL — body valideres af `v1WebFetchSchema` |

**Godkendelse:** Bearer-API-nøgle (`extractApiKey` + `isValidApiKey`). Politikken håndhæves via `enforceApiKeyPolicy`.

**Kvotebevidst fallback (#8297):** Når der ikke er angivet en eksplicit `provider`, gennemgås puljen
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) i
en fast
prioritetsrækkefølge (fyld-først) — en hastighedsbegrænset, men konfigureret udbyder springes over
i stedet for at afbryde anmodningen, og en upstreamfejl, der kan forsøges igen, eller en kvotefejl
(altid HTTP 429; 402/403 for kvotebaserede gratisniveauer hos Firecrawl/Tavily/TinyFish —
ikke for Jina Reader og aldrig for en almindelig 400-fejl ved en ugyldig anmodning) fortsætter til den
næste endnu ikke afprøvede udbyder med legitimationsoplysninger på anmodningstidspunktet. Når alle udbydere i
puljen er udtømt, returnerer endpointet en enkelt `429` (med en `Retry-After`-
header) i stedet for den tidligere generiske `400`. Når der anmodes om en eksplicit `provider`,
er der **ingen** lydløs fallback — en hastighedsbegrænset eller fejlende eksplicit
udbyder viser sin egen fejl (`429`, hvis den er hastighedsbegrænset, ellers upstreamtjenestens
status).

## WebSocket-streaming

```bash
GET /v1/ws?handshake=1
```

Validerer et WebSocket-opgraderingshandshake og returnerer eksempelmeddelelserne for wire-protokollen (`request`, `cancel`). Faktiske WS-frames håndteres af den medfølgende WS-server uden for Next.js-rutetabellen.

**Godkendelse:** Bearer-API-nøgle under handshaket.

### Responses-API via WebSocket (kun codex)

```bash
# Samme vært:port som HTTP-API'en (standard er 20128); opgrader forbindelsen:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (eller: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Første frame SKAL være response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

En Responses-API-via-WebSocket-proxy er **udelukkende forbundet med `codex`** (ChatGPT-
backend). Den lytter på samme port som API'et/dashboardet på stierne `/v1/responses`,
`/responses` og `/api/v1/responses`. Ved den første `response.create`-frame
godkender og forbereder den via den interne `codex-responses-ws`-bro, vælger en
codex OAuth-forbindelse og etablerer en tunnel til `wss://chatgpt.com/backend-api/codex/responses`
via `wreq-js`-transporten. **Modeller, der ikke er codex-modeller, afvises** (`codex_ws_provider_required`).
Brug `model: "qtSd/<group>/codex/<model>"` til kvotedelingsrouting. Implementeret i
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Godkendelse:** Bearer-API-nøgle under handshaket. Den medfølgende HTTP-server (`server-ws.mjs`)
skal være det aktive startpunkt (hvilket den som standard er, når `app/server-ws.mjs` findes).

#### Model-id: Brug det rene ChatGPT-id (uden præfikset `codex/`)

OpenAI **Codex CLI** validerer modelnavnet på klientsiden, når
`supports_websockets = true`, og **afviser id'er med udbyderpræfiks** såsom
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Send det **rene** id (f.eks. `gpt-5.5`). OmniRoutes bro er
kun til codex, så den genfortolker et rent id som en codex-model
(`resolveCodexWsModelInfo`), før der etableres en tunnel til upstreamtjenesten — selvom et rent
`gpt-5.5` ellers ville blive routet til en anden udbyder via HTTP.

#### Konfiguration af OpenAI Codex CLI

Ret Codex CLI mod OmniRoute ved at tilføje en brugerdefineret udbyder med WebSocket-
understøttelse i `~/.codex/config.toml` (brug en separat `CODEX_HOME` for at undgå at ændre
en eksisterende konfiguration):

```toml
model = "gpt-5.5"                 # rent id — IKKE "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # ingen afsluttende skråstreg; WS-URL'en afledes (brug https/wss i produktion)
wire_api = "responses"                    # den eneste understøttede værdi siden februar 2026
supports_websockets = true                # aktiverer Responses-via-WS-transporten
env_key = "OMNIROUTE_API_KEY"             # indeholder OmniRoute-API-nøglen (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # en OmniRoute-API-nøgle (en vilkårlig nøgle, hvis REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI'en opgraderer `base_url + /responses` til en WebSocket, og OmniRoute etablerer en tunnel
til den valgte codex OAuth-forbindelse. Valideret fra ende til anden mod den lokale
server: ChatGPT returnerer `codex.rate_limits` + `response.created` og streamer
fuldførelsen.

## Selvbetjent forbrug (`/api/usage/om-usage`)

Enhver API-nøgle kan læse **sit eget** forbrug og sine egne kvoter — ingen administrationsgodkendelse. Dette er det endpoint, som en
klient (CLI, OmniCopilot-panelet) bruger til at vise en nøgleindehaver vedkommendes forbrug.

```bash
# Tekstformat (den historiske kontrakt — almindelig tekst til en terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Struktureret format — det, som en brugergrænseflade anvender
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Nøglen skal have **`allowUsageCommand`** aktiveret (deaktiveret som standard — dashboardets API-nøgleadministrator
slår det til eller fra for hver nøgle). Uden denne indstilling svarer endpointet med `403`.

`?format=json` returnerer en diskrimineret struktur, så en kalder aldrig læser et datafelt fra et
afslag. Ved succes:

```jsonc
{
  "allowed": true,
  // findes kun, når nøglen har tilvalgt forbrugsgrænser pr. nøgle (dagligt/ugentligt i USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // øjebliksbilledet af den valgte udbyderkvote eller null, når intet er cachelagret endnu:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // øjebliksbilledet for hver forbindelse, så en brugergrænseflade kan vise flere udbydere side om side:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Ved afslag (`401` ugyldig nøgle / `403` ikke tilladt) returnerer den samme rute
`{ "allowed": false, "error": { "message": "…" } }` — en eksisterende, men tom `personal`/`provider`
(nøglen er tilladt, men intet er registreret endnu) er en anden tilstand end et afslag, og kun JSON-formatet
skelner mellem dem.

**Godkendelse:** kalderens egen Bearer-API-nøgle, valideret med `isValidApiKey` — dette er _ikke_
administrationsgrænsefladen (`/api/keys/…`), som fortsat er beskyttet af `requireManagementAuth`.

### Rå kontra cutoff-justerede kvoteprocenter

Ved brug af `/api/usage/om-usage` bør kaldere være opmærksomme på forskellen mellem de
procenter, der vises i **outputtet i almindelig tekst**, og det strukturerede **JSON-output**:

| Aspekt               | Almindeligt tekstformat (`/api/usage/om-usage` / `@@om-usage`)                            | JSON-format (`?format=json`)                                                        |
| :------------------- | :---------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------- |
| **Outputfelt**       | `NN% left` (f.eks. `20% left`)                                                            | `provider.quotas` / `providers[].quotas`                                            |
| **Måling**           | **Cutoff-justeret anvendelig kvote**: resterende kapacitet over cutoff-tærsklen           | **Rå opstrømskvote**: ikke-justeret måling fra udbyderen                            |
| **Cutoff-skalering** | Skaleret via `effectiveRemainingPercent()`, så den beskyttede reserve vises som `0% left` | Ingen (rå øjebliksbilledværdier som rapporteret af udbyderen)                       |
| **Tærskeldata**      | Indarbejdet i den viste procent                                                           | Gemt i `quotaWindowThresholds` pr. forbindelse (eller serverens standarder)         |
| **Primær forbruger** | Interaktive CLI'er, terminalprompter, menneskelige operatører                             | Programmatiske integrationer, dashboards, analyseværktøjer, fakturasporingssystemer |

#### Formlen for cutoff-justering

OmniRoute understøtter proaktive kvotecutoffs for at forhindre udtømning hos opstrømsudbyderen (konfigureret via forbindelsens
`quotaWindowThresholds`, udbyderens standarder eller globale robusthedsindstillinger). Når en cutoff-tærskel
(f.eks. `cutoff = 25%`) er aktiv for et kvotevindue, beregner tekst-rendereren den resterende kvote således:

- Hvis `remaining <= cutoff`: returneres `0%`.
- Hvis `remaining > cutoff`: returneres `((remaining - cutoff) / (100 - cutoff)) * 100`.

Det formaterede tekstoutput afrunder dette til nærmeste heltal (`Math.round(...)`).

#### Illustrativt eksempel

Betragt et udbydervindue med **60 % råt forbrug** (og dermed **40 % rå resterende kvote**) og en konfigureret
**cutoff-tærskel på 25 % resterende kvote**:

| Repræsentation               | Beregning                                          | Resterende |             Implicit forbrugt              |
| :--------------------------- | :------------------------------------------------- | :--------: | :----------------------------------------: |
| **Rå JSON (`?format=json`)** | Opstrømsøjebliksbillede (`quotas[window]`)         |  **40 %**  |                  **60 %**                  |
| **Tekstformat (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20 %**  | **80 %** (hvis `100 - remaining` beregnes) |

- **Hvorfor teksten viser 20 % tilbage:** Af de 40 % fysisk kvote, der er tilbage på kontoen, er 25 % reserveret af
  cutoff-politikken. Kalderen har kun 15 % ud af 75 % anvendelig margen tilbage, før routeren stopper med at
  dirigere til denne forbindelse. Skaleringen sikrer, at forbindelsen signalerer udtømning (`0% left`), præcis når
  dirigeringen ophører.
- **Hvorfor JSON bevarer rå værdier:** JSON-payloaden returnerer udbyderens præcise øjebliksbillede (`UsageSnapshot`),
  så eksterne værktøjer har adgang til de faktiske opstrømsudnyttelsesdata og forbindelsesniveauets
  `quotaWindowThresholds` uden tabsgivende skalering på serversiden.

#### Vejledning til migrering af forbrugere

Hvis en ekstern integration (f.eks. et editorplugin eller en agentudvidelse) tidligere ekstraherede data fra tekstslutpunktet
(`NN% left`) og beregnede den anvendte procentdel som `100 - NN`, betyder en migrering til `?format=json`:

- Aflæsning af rå JSON-værdier afspejler det **faktiske upstream-forbrug** (60 % anvendt i eksemplet ovenfor).
- Hvis integrationen ønsker at bevare tekstslutpunktets semantik for den anvendelige kvote, kan den evaluere
  den effektive formel for resterende kvote på klientsiden ved hjælp af `quotaWindowThresholds` til tilsidesættelser på forbindelsesniveau.

## Semantisk cache

```bash
# Hent cachestatistik
GET /api/cache/stats

# Ryd alle cacher
DELETE /api/cache/stats
```

Eksempel på svar:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Påvirkning af latenstid

Et HIT i den semantiske cache leverer svaret fra cachen **uden et upstream-
kald**, så den rapporterede `X-OmniRoute-Response-Latency` er tæt på nul
(uanset den oprindelige upstream-latenstid). Klienter, der er følsomme over for
latenstid (benchmarking, p50/p99-overvågning), bør kontrollere
`X-OmniRoute-Cache-Latency`-headeren i svaret:

| Værdi          | Betydning                                                        |
| -------------- | ---------------------------------------------------------------- |
| `synthetic`    | Svaret leveres fra cachen; latenstiden er ikke reel upstream-tid |
| _(fraværende)_ | Svar fra et reelt upstream-kald                                  |

### Cache-omgåelse pr. nøgle

API-nøgler kan fravælge læsninger fra den semantiske cache via `cacheDefaultMode`:

| Værdi    | Adfærd                                            |
| -------- | ------------------------------------------------- |
| `legacy` | Normal cacheadfærd (standard)                     |
| `bypass` | Spring cacheopslag helt over; brug altid upstream |

Angiv ved oprettelse af nøglen (`POST /api/keys`) eller ved opdatering (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Omgåelse pr. anmodning

Enhver anmodning kan omgå cachen uanset nøgleindstillingerne:

```
X-OmniRoute-No-Cache: true
```

For synkroniserede/importerede modeller accepterer `PUT /api/provider-models` `provider`, `modelId` og
`maxOutputTokenOverride`: Et positivt heltal angiver den manuelle grænse for outputtokens, og `null`
fjerner den for at gendanne standardværdien. `GET /api/provider-models?provider=<provider>` returnerer disse
værdier i `modelOutputOverrides`, herunder modeller uden en række for en brugerdefineret model. Tilsidesættelsen
bruger runtime-funktionaliteten `max_output_tokens` og bevares efter en ny modelsynkronisering. Siden for den OpenAI-kompatible
udbyder tilbyder de samme kontrolelementer til redigering/rydning og markerer modeller med eksplicit understøttelse af billedforståelse.

Brugerdefinerede Chat Completions-noder tilpasser eksplicitte fravalg af ræsonnering til upstream-backenden. En
vellykket forbindelsestest vælger automatisk chat-skabelonkontroller for hvert nøjagtigt model-id,
hvis `/models`-post dokumenterer en genkendt `owned_by`-værdi: `vllm`, `sglang` eller `llamacpp`.
Transparente OpenAI-kompatible wrappers kan bevare den oprindelige modelpost i et indlejret
`openai`-objekt; registreringen følger op til tre sådanne indkapslinger. Modeller med manglende, ukendt eller
modstridende ejerskab beholder den almindelige OpenAI-adfærd. Registreringen genbruger den eksisterende kataloganmodning,
genererer ingen completion-tokens og ugyldiggøres, når forbindelsens slutpunkt ændres.

Brug det eksisterende API til delvis opdatering af udbydere for at fastholde adfærden for en backend,
der ikke eksponerer disse metadata:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Send denne body med `PUT /api/providers/<connection-id>`. På denne forbindelse sendes en eksplicit
ræsonneringsindsats på `none` som `chat_template_kwargs.thinking=false` og
`chat_template_kwargs.enable_thinking=false`. Eksplicitte indbyggede skabelonværdier har fortsat forrang,
medmindre en ræsonneringsregel på serversiden gennemtvinger en indsats. Indstillingen anvendes kun, når en brugerdefineret
OpenAI-kompatibel forbindelse sender en Chat Completions-body; Responses-anmodninger og almindelige
udbydere beholder deres indbyggede anmodningsformat. Indstil `reasoningControl` til `openai` for at gennemtvinge almindelig OpenAI-
videresendelse af `reasoning_effort`, eller udelad den/indstil den til `null` for at bruge automatisk registrering.

Claude Code-klassifikatoranmodninger i automatisk tilstand deaktiverer som standard indbygget tænkning, når de
ikke indeholder eksplicitte ræsonneringskontroller. Registreringen bruger klassifikatorens systemmarkør i anmodninger
i Claude-format, ikke modelnavne eller completion-grænser. Eksplicitte body-kontroller, understøttede indsats-/tænknings-
headers, routingregler og den fastlagte modelindsats bevarer deres eksisterende prioritet. Begge klassifikator-
faser bevarer deres prompts, completion-grænser, stopsekvenser og reelle upstream-tilladelsesafgørelser;
anden fase kan stadig generere den ønskede synlige ræsonnering som almindelig tekst.

### Version og udgivelseskanal

```bash
GET /api/system/version
```

Administrationsrute kun til loopback (administratorgodkendelse). Returnerer den kørende version, den senest
udgivne version og status for automatisk opdatering. `releaseChannel` og `channels` er additive
felter (rail 3.8.54); `channel` beholder sin betydning — den implementeringstilstand, som dashboardets opdateringsfunktion
bruger (`npm`, `source` eller `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — npm-kanalen for den kørende build: `nightly` for `-nightly.*`-versioner,
  `next` for andre forhåndsudgivelser (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` for en stabil version af en
  ældre hovedversion end `channels.latest`, ellers `latest`. Samme regler som
  `scripts/release/dist-tag.mjs`, der vælger npm-dist-tagget på udgivelsestidspunktet.
- `channels` — det senest udgivne element for hvert dist-tag fra `npm view omniroute dist-tags` (HTTP-reserveløsning
  til registreringsdatabasen), cachelagret med samme TTL på 10 minutter som `latest`. `latest` er altid til stede
  (falder tilbage til feltet `latest` og derefter `"unavailable"`); `next`, `nightly` og `lts` vises
  kun, når det pågældende dist-tag findes. En anmodning med `Cache-Control: no-cache` opdaterer begge opslag.

Kanalmodellen (`latest` = v3 indtil den generelle udgivelse af 4.0, `next` = rc, `nightly` = builds fra `develop`,
`lts` = v3-rettelser efter den generelle udgivelse af 4.0) er beskrevet i `docs/ops/RELEASE_STRATEGY.md`.

## Tokeniserede VS Code-aliasser uden headers

Brug disse aliasser, når en integration ikke kan indsætte en `Authorization`-header og har brug for, at API-nøglen er indlejret i basis-URL'en.

```bash
# Katalogalias i OpenAI-stil
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# Chat-aliasser i OpenAI-stil
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Aliasser i Ollama-stil
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

Eksempel:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

Bemærkninger:

- De tokeniserede aliasser genbruger de samme handlers som `/v1/*` og `/api/tags`; svarstrukturerne forbliver identiske.
- Foretræk `Authorization: Bearer ...`, når klienten understøtter brugerdefinerede headers.
- URL-baserede tokens kan optræde i reverse proxy-logfiler, browserhistorik og telemetri uden for OmniRoute. Betragt dem som en kompatibilitetsmulighed, ikke som standardgodkendelsesmetoden.

## Tokenbegrænsninger

**Tokenbudgetter** pr. API-nøgle (adskilt fra det USD-baserede budget ovenfor). Håndhæves direkte i anmodningsforløbet: Når en nøgles forbrug i det aktuelle tidsvindue når grænsen, afvises anmodninger med `429 Too Many Requests`. Begrænsninger kan afgrænses til en bestemt `model` eller `provider` eller anvendes `global`t på tværs af nøglen. Når flere begrænsninger matcher en anmodning, gælder den mest restriktive.

```bash
# Vis en nøgles tokenbegrænsninger (inkluderer aktuelt forbrug i tidsvinduet)
GET /api/usage/token-limits?apiKeyId=key-123

# Opret eller opdater en tokenbegrænsning
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Slet en tokenbegrænsning efter id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Skemabemærkninger** (`setTokenLimitSchema`): `apiKeyId` og `scopeType` (`model` | `provider` | `global`) er påkrævede. `scopeValue` er påkrævet, medmindre `scopeType` er `global` (f.eks. et model-id for omfanget `model` eller et udbyder-id for omfanget `provider`). `tokenLimit` skal være et positivt heltal (konverteres fra en streng). Valgfrit: `id` (udelad for at oprette, angiv for at opdatere), `resetInterval` (`daily` | `weekly` | `monthly`, standardværdi `monthly`), `resetTime` (`HH:MM`), `enabled` (standardværdi `true`). `GET`-svar supplerer hver begrænsning med `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` og `nextResetAt`. Dette er et administrationsendpoint (godkendelse håndhæves centralt af authz-pipelinen).

## Behandling af anmodninger

1. Klienten sender en anmodning til `/v1/*`
2. Route-handleren kalder `handleChat`, `handleEmbedding`, `handleAudioTranscription` eller `handleImageGeneration`
3. Modellen slås op (direkte udbyder/model eller alias/kombination)
4. Legitimationsoplysninger vælges fra den lokale database med filtrering efter kontotilgængelighed
5. For chat kontrollerer `handleChatCore` den semantiske cache/signaturcache og slår kombinationens komprimeringsindstillinger op
6. Proaktiv komprimering køres før oversættelse til udbyderformatet, når den er aktiveret (`lite`, Caveman, RTK eller stablet)
7. Udbyder-eksekveringen sender anmodningen til upstream-tjenesten
8. Svaret oversættes tilbage til klientformatet (chat) eller returneres uændret (embeddings/billeder/lyd)
9. Forbrug, komprimeringsanalyse og anmodningslogfiler registreres
10. Fallback anvendes ved fejl i henhold til kombinationsreglerne

Komplet arkitekturreference: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Robusthed (udvidet)

OmniRoute stiller tre uafhængige mekanismer til midlertidige fejl til rådighed; nedenstående administrationsendepunkter gør det muligt for operatører at aflæse og tilsidesætte dem:

| Omfang            | Tilstandslagring                           | Aflæsning                                 | Nulstilling / rydning                           |
| ----------------- | ------------------------------------------ | ----------------------------------------- | ----------------------------------------------- |
| Udbyderafbryder   | `domain_circuit_breakers` + i hukommelsen  | `/api/monitoring/health`                  | `POST /api/resilience/reset`                    |
| Forbindelsespause | `rateLimitedUntil` på udbyderforbindelser  | `/api/rate-limits`, `/api/providers/[id]` | (genaktiveres efter behov; ryd via udbyder-PUT) |
| Modelspærring     | Modeltilgængelighedsregister i hukommelsen | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`        |

`PATCH /api/resilience` accepterer tilsidesættelser af udbyderafbrydere under `providerBreaker.oauth` og `providerBreaker.apikey`. Hver profil understøtter `degradationThreshold`, `failureThreshold` og `resetTimeoutMs`; de samme felter er tilgængelige under Kontrolpanel → Indstillinger → Robusthed.

```bash
# Ryd spærringen for en enkelt model
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Ryd alle spærringer
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

En fuldstændig begrebsmæssig reference og standardværdier for afbrydere findes i [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" og [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Kø til hastighedsbegrænsning og sikkerhedsnet til automatisk aktivering

- **Understøttet skrivevej**: `POST /api/rate-limits` med brødteksten `{"connectionId": "<id>", "enabled": true|false}` er det understøttede administrationsendepunkt til at slå beskyttelse mod hastighedsbegrænsning til eller fra for en forbindelse. `PUT /api/providers/[id]` ændrer eller skifter bevidst ikke `rateLimitProtection` (#11278).
- **Semantik for `enabled: false`**: Indstilling af `enabled: false` fjerner eksplicit beskyttelse for forbindelsen, men undtager **ikke** en aktiv API-nøgleforbindelse fra det globale sikkerhedsnet til automatisk aktivering (`autoEnableApiKeyProviders = true`). I `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) er `false` og `undefined` ækvivalente; aktive API-nøgleforbindelser uden eksplicit beskyttelse forbliver beskyttet af sikkerhedsnettet til automatisk aktivering.
- **Global deaktivering**: Hvis API-nøgleforbindelser skal køre uden køer til hastighedsbegrænsning, skal sikkerhedsnettet deaktiveres globalt via `RATE_LIMIT_AUTO_ENABLE=false` (miljøvariabel) eller `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Indstillinger → Robusthed / `PATCH /api/resilience`).

## A2A-server

OmniRoute eksponerer et A2A-slutpunkt (Agent-to-Agent) baseret på JSON-RPC 2.0 samt en REST-wrapper til inspektion og brug i dashboards.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # valgfrit, medmindre OMNIROUTE_API_KEY er angivet
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Understøttede metoder (alle styret af `settings.a2aEnabled`):

| Metode           | Beskrivelse                                                              |
| ---------------- | ------------------------------------------------------------------------ |
| `message/send`   | Synkron udførelse af færdighed; returnerer `{task, artifacts, metadata}` |
| `message/stream` | Streamet SSE-udførelse af det samme sæt færdigheder                      |
| `tasks/get`      | Hent en opgave via `taskId`                                              |
| `tasks/cancel`   | Annuller en opgave via `taskId`                                          |

Indbyggede færdigheder: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Agentkort

```bash
GET /.well-known/agent.json
```

Returnerer det offentlige A2A-agentkort (navn, beskrivelse, funktioner, færdighedskatalog og godkendelsesmetode) — cachelagres offentligt i 1 time. Kræver ingen godkendelse.

### REST-hjælpere

| Metode | Sti                          | Beskrivelse                                                                                                      |
| ------ | ---------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/a2a/status`            | A2A aktiveret + opgavestatistik + oversigt over cachelagret agentkort                                            |
| GET    | `/api/a2a/tasks`             | Vis opgaver — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (Ikke implementeret som REST-hjælper — opret via JSON-RPC `message/send`)                                        |
| GET    | `/api/a2a/tasks/[id]`        | Hent en enkelt opgave                                                                                            |
| POST   | `/api/a2a/tasks/[id]/cancel` | Annuller en opgave                                                                                               |

**Godkendelse:** REST-hjælperne kører uden administrationsgodkendelse (kan læses af dashboardet); JSON-RPC-ruten `/a2a` bruger Bearer `OMNIROUTE_API_KEY`, hvis den er konfigureret.

## Godkendelse

Se [Godkendelse til administration](../guides/MANAGEMENT-AUTH.md) for de fire
legitimationsfamilier (dashboardsession, lokalt CLI-token, `oma_live_…`-adgangstoken,
API-nøgle med administrationsomfang), og hvordan de adskiller sig fra inferensnøgler.

- Dashboardruter (`/dashboard/*`) bruger cookien `auth_token`
- Login bruger den gemte adgangskodehash med fallback til `INITIAL_PASSWORD`
- `requireLogin` kan slås til eller fra via `/api/settings/require-login`
- `/v1/*`-ruter kræver valgfrit en Bearer-API-nøgle, når `REQUIRE_API_KEY=true`
- "administrationstoken" / "API-nøgle med administrationsomfang" betyder i denne reference en af familierne i den pågældende guide — ikke en ekstra, udefineret type hemmelighed

> **Inkompatibel ændring (v3.8.0)** — `/api/v1/agents/tasks/*` og slutpunkterne til administration af nedkølingsperioder kræver nu **administrationsgodkendelse** (dashboardets `auth_token`-cookie eller en API-nøgle med administrationsomfang). Klienter, der tidligere kaldte disse ruter uden godkendelse, modtager nu `401 Unauthorized`. Se commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
