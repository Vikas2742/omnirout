## Завершення чату

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Користувацькі заголовки

| Заголовок                | Напрямок  | Опис                                                                                                                                                                                                                                      |
| ------------------------ | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Запит     | Установіть значення `true`, щоб обійти кеш                                                                                                                                                                                                |
| `x-omniroute-no-memory`  | Запит     | Установіть значення `true`, щоб пропустити додавання пам’яті та навичок для цього запиту (аналогічно до вимкнення кешу; дає змогу уникнути накладних витрат токенів і вартості для кожного виклику)                                       |
| `X-OmniRoute-Progress`   | Запит     | Установіть значення `true`, щоб отримувати події перебігу виконання                                                                                                                                                                       |
| `X-Session-Id`           | Запит     | Ключ закріпленої сесії для зовнішньої спорідненості сесій                                                                                                                                                                                 |
| `x_session_id`           | Запит     | Також приймається варіант із підкресленнями (прямий HTTP)                                                                                                                                                                                 |
| `X-OmniRoute-Session-Id` | Запит     | Надана викликачем мітка сесії/розмови (також передається до пам’яті). Якщо вона наявна, дослівно зберігається в `call_logs.session_tag` для віднесення витрат до окремих сесій (#8249) — ніколи не створюється автоматично за відсутності |
| `Idempotency-Key`        | Запит     | Ключ дедуплікації (вікно 5 с)                                                                                                                                                                                                             |
| `X-Request-Id`           | Запит     | Альтернативний ключ дедуплікації                                                                                                                                                                                                          |
| `x-omniroute-connection` | Запит     | Закріплює запит до однієї моделі за одним підключенням постачальника (обліковим записом) за його ідентифікатором — див. [Закріплення облікового запису для кожного запиту](#account-pinning-per-request)                                  |
| `X-OmniRoute-Cache`      | Відповідь | `HIT` або `MISS` (без потокового передавання)                                                                                                                                                                                             |
| `X-OmniRoute-Idempotent` | Відповідь | `true`, якщо виконано дедуплікацію                                                                                                                                                                                                        |
| `X-OmniRoute-Progress`   | Відповідь | `enabled`, якщо відстеження перебігу виконання ввімкнено                                                                                                                                                                                  |
| `X-OmniRoute-Session-Id` | Відповідь | Фактичний ідентифікатор сесії, використаний OmniRoute                                                                                                                                                                                     |
| `X-OmniRoute-Request-Id` | Відповідь | Ідентифікатор кореляції запиту (якщо відомий)                                                                                                                                                                                             |
| `X-OmniRoute-Version`    | Відповідь | Версія збірки OmniRoute (наявна завжди)                                                                                                                                                                                                   |
| `X-OmniRoute-Cost-Saved` | Відповідь | Сума в USD, яку вдалося заощадити завдяки кешу в разі `HIT` (лише для влучань у кеш)                                                                                                                                                      |
| `X-OmniRoute-Decision`   | Відповідь | Трасування маршрутизації: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` — стратегія комбінації або `single` для запиту без комбінації) — завжди наявне у відповідях після завершення                                      |

> Примітка щодо Nginx: якщо ви покладаєтеся на заголовки з підкресленнями (наприклад, `x_session_id`), увімкніть `underscores_in_headers on;`.

#### Закріплення облікового запису для окремого запиту

Якщо провайдер має кілька з’єднань (облікових записів або ключів), OmniRoute зазвичай вибирає одне з них
за допомогою своєї стратегії вибору облікового запису. Натомість запит може закріпити одне конкретне з’єднання
за допомогою заголовка `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Де знайти ідентифікатор.** Відкрийте сторінку провайдера на панелі керування
  (**Панель керування → Провайдери → <provider>**) і натисніть на мітку ідентифікатора `xxxxxxxx…` у рядку з’єднання —
  повний ідентифікатор з’єднання буде скопійовано.
- **Які запити його враховують.** Запити з однією моделлю (`provider/model`) до
  `/v1/chat/completions`, `/v1/messages` і `/v1/responses`. Комбінації ігнорують цей заголовок: натомість
  закріплюйте обліковий запис для кожного кроку комбінації через власне з’єднання цього кроку.
- **Закріплення є суворим, а не просто побажанням.** Використовується виключно закріплене з’єднання.
  Помилка під час виконання запиту активує період очікування для облікового запису, але **не** спричиняє
  перемикання на інший обліковий запис того самого провайдера.
- **Період очікування та квота скасовують закріплення.** Поки закріплене з’єднання перебуває в періоді очікування,
  вичерпало квоту або заблоковане політикою квот, наступні запити перемикаються на інші з’єднання провайдера
  так само, як і незакріплений трафік.
- **Невідомі або вимкнені ідентифікатори спричиняють помилку.** Якщо ідентифікатора немає в активному пулі провайдера (його видалено,
  деактивовано або він належить іншому провайдеру), не залишається жодного доступного облікового запису, тому запит
  завершується помилкою замість непомітного перенаправлення в інше місце.

Claude Code надсилає власні заголовки через `ANTHROPIC_CUSTOM_HEADERS`. Додайте цю змінну до блоку `env`
у `~/.claude/settings.json` або до файлу `.claude/settings.json` на рівні проєкту, щоб закріпити окремий
обліковий запис для кожного проєкту:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Джерело: `src/sse/handlers/chat.ts` (зчитування заголовка), `src/sse/services/auth.ts` і
`src/sse/services/sessionAffinityPin.ts` (скасування закріплення та перевірка відсутності в пулі).

> **Заголовки телеметрії витрат:** успішні відповіді без потокового передавання також містять набір телеметрії витрат `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, фіксовані 10 десяткових знаків; `0.0000000000` для безкоштовних варіантів або варіантів без визначеної ціни), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` і `X-OmniRoute-Fallback-Attempts` (лише коли > 0), а також `X-OmniRoute-Request-Id` і `X-OmniRoute-Version`. Їх повертають завершення чатів, `/v1/responses`, `/v1/messages`, **а також кінцеві точки для медіаданих** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` і `/v1/moderations` (вартість завжди `0`). Вартість медіаданих обчислюється окремо для кожної модальності (за зображення, секунду, символ або одиницю пошуку), коли дані про ціни доступні; інакше вона дорівнює `0` (помилка не блокує виконання).

> **Семантика вартості в разі влучання в кеш:** у разі влучання в семантичний кеш (`X-OmniRoute-Cache-Hit: true`) виклик до вищого сервісу не виконується, тому значення `X-OmniRoute-Response-Cost` дорівнює `0.0000000000` (**додаткова** вартість обслуговування влучання). Початкова/гіпотетична вартість повідомляється окремо в `X-OmniRoute-Cost-Saved`. Системи обліку оплати мають підсумовувати `X-OmniRoute-Response-Cost` (влучання нічого не коштують); системи аналітики кешу можуть агрегувати `X-OmniRoute-Cost-Saved`.

## Ексклюзивні оренди керованих сеансів

Ексклюзивна оренда керованих сеансів — це необов’язковий, незалежний від клієнта контракт маршрутизації: один активний власник
утримує одне придатне підключення OmniRoute. Він не орендує модель, не вимагає OAuth, не ідентифікує
конкретного клієнта та не вимагає конкретного провайдера.

API-ключ, що використовується для автентифікації, повинен мати область дії `lease:exclusive` і явно заданий непорожній
список `allowedConnections`. Межа операцій зміни бази даних забезпечує спільне дотримання обох вимог під час
створення ключа та часткових оновлень.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Успішні відповіді на отримання, продовження та звільнення містять часові позначки, `state` і точне додатне
значення `generation`, але ніколи не розкривають вибране підключення або облікові дані. Для продовження та звільнення
значення generation передається в тілі JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Власник активної оренди може явно запитати безпечні для конфіденційності метадані відображення для свого поточного прив’язування:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Ця необов’язкова дія перевірки статусу захищена непрозорим ідентифікатором власника, автентифікованим керованим API-ключем і точним
активним значенням generation у межах однієї транзакції бази даних. `displayName` містить лише налаштовану назву
підключення без початкових і кінцевих пробілів; якщо безпечної налаштованої назви немає, значенням є `null`. OmniRoute ніколи не підставляє
адресу електронної пошти або згенеровану ідентичність облікового запису. Значення провайдера є нечутливою міткою для відображення й ніколи
не є згенерованим ідентифікатором сумісного провайдера. Облікові дані, токени, файли cookie, необроблені ідентифікатори підключень або API-ключів,
хеші власників, секрети бар’єрного захисту та внутрішні дані маршрутизації не включаються.

Запити з неправильним ключем, неправильним власником, застарілим значенням generation, відсутньою, простроченою, звільненою або анульованою орендою
повертають ту саму помилку `409 LEASE_FENCE_STALE` без метаданих підключення. Клієнт, який отримав відповідь про очікування доступної ємності, не має активного прив’язування, яке можна перевірити. Коли маршрутизація перемикає активну оренду,
те саме значення generation залишається чинним, а статус атомарно повертає нове прив’язування, але ніколи не старе.
Наявні клієнти працюють без змін, оскільки відповіді на отримання, продовження, звільнення та очікування
зберігають свою попередню структуру.

Цей серверний контракт не змінює стандартний `/status` OpenAI Codex. Наразі стандартний Codex повідомляє про свого
провайдера моделі та вбудований стан автентифікації/облікового запису, але не відображає довільні метадані облікових записів
власних провайдерів; майбутня клієнтська інтеграція повинна викликати цю дію та вирішувати, як
відображати `connection.displayName`.

Після цього кожен керований запит на інференс передає обидва керівні заголовки:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Точний власник, значення generation, активне підключення та автентифікований API-ключ перевіряються бар’єрним механізмом безпосередньо
перед кожною підтримуваною спробою звернення до висхідного сервісу. Повторне використання власника та generation з іншим ключем завершується невдало,
навіть якщо цей ключ дозволяє те саме підключення. Необроблені значення власників не зберігаються, не журналюються, не залишаються
у знімку запиту та не передаються висхідному сервісу.

Тимчасова конкуренція за ресурс повертає HTTP `429` із `Retry-After` і:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Ця відповідь означає лише те, що стандартна множина придатних підключень була непорожньою, а кожен вільний кандидат
утримувався сторонньою активною орендою. Непідтримувані моделі/провайдери, невідповідність політиці, період відновлення, квота,
стан працездатності та інші стандартні причини непридатності й надалі повертають наявні відповіді OmniRoute.

### `x-omniroute-compression`

Перевизначення плану стиснення для окремого запиту. Має найвищий пріоритет — переважає над перевизначенням комбінації маршрутизації,
активним профілем, автоматичним тригером і профілем Default панелі. Значення:

| Значення      | Ефект                                                                                                              |
| ------------- | ------------------------------------------------------------------------------------------------------------------ |
| `off`         | Без стиснення для цього запиту.                                                                                    |
| `default`     | Отриманий із панелі профіль Default (активний профіль ігнорується). Рушії зі втратою даних залишаються вимкненими. |
| `safe`        | Лише дедуплікація та згортання пробільних символів.                                                                |
| `allow-lossy` | Зберігає операторський план для цього запиту, включно з резюме та переписуванням стилю.                            |
| `engine:<id>` | Один рушій, якщо його ввімкнено, наприклад `engine:rtk`. Увімкнення цього рушія для окремого запиту.               |
| `<combo>`     | Іменована комбінація: спочатку виконується зіставлення за назвою без урахування регістру, а потім за id.           |

Примітки:

- Невідомі значення ігноруються (запит ніколи не відхиляється); визначення продовжується відповідно до звичайного порядку пріоритетів оператора.
- Якщо кілька комбінацій мають однакову назву, передайте **id** комбінації для детермінованого зіставлення.
- Комбінацію з назвою `off` або `default` не можна вибрати за назвою (ці ключові слова інтерпретуються першими); посилайтеся на таку комбінацію за її id.
- Головний перемикач стиснення є жорстким обмеженням: коли стиснення глобально вимкнено, цей заголовок не може його ввімкнути.

Застосований план дублюється в заголовку відповіді:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

де `<source>` має одне зі значень `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` або `off`.

## Вбудовування

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Доступні постачальники: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Ідентифікатори каталогу мають формат `provider/model` (приклад: `jina-ai/jina-embeddings-v5-omni-small`). Прості ідентифікатори моделей Jina, наявні в реєстрі (наприклад, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`), також розпізнаються. Jina embed/rerank/classify/segment спочатку використовують облікові дані `jina-ai` з панелі керування; `JINA_AI_API_KEY` використовується як резервний варіант, лише якщо в панелі керування немає ключа. Картка `jina-reader` призначена лише для Reader / `r.jina.ai` (`POST /v1/web/fetch`) і ніколи не обслуговує вбудовування чи переранжування.

Моделі реєстру, для яких заявлена підтримка мультимодальності, також приймають до 32 нейтральних щодо постачальника структурованих
елементів. Типи медіаелементів: `text`, `image`, `audio`, `video` і `document`. Їхнє медіаджерело `source`
має вигляд `{"type":"url","url":"https://..."}` або
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
і псевдонім сімейства `jina-ai/jina-embeddings-v5-omni` → omni-small) також приймає нативні документи
EmbeddingsV5Request від Jina та **пересилає їх без змін** до `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Нативні значення `{ image | audio | video | pdf }` можуть бути загальнодоступною HTTPS-URL-адресою, URI `data:` або необробленими
даними base64. OmniRoute не перетворює ці об’єкти на рядки й не завантажує нативні URL-адреси зображень — Jina самостійно отримує
загальнодоступні медіадані. Додаткові поля Jina (`task`, `normalized`, `truncate`, `embedding_type`)
пересилаються. Текстові SKU Jina, як і раніше, відхиляють нетекстові документи.

Обмеження безпеки та передавання:

- URL-адреси віддалених медіаданих мають бути загальнодоступними й використовувати HTTPS. Канонічні елементи `{type,source:url}` завантажуються
  на стороні сервера (повторна перевірка перенаправлень, тайм-аут, обмеження розміру, загальнодоступний DNS, фіксація з’єднання) і
  вбудовуються перед викликом постачальника. Нативні елементи Jina `{image:"https://..."}` пересилаються без змін
  після такої самої перевірки загальнодоступності HTTPS; Jina завантажує дані за URL-адресою.
- Вбудовані медіадані base64 обмежено 8 МіБ декодованих даних на елемент і 16 МіБ декодованих даних на весь запит.

Перетворення для постачальників (канонічні елементи ніколи не пересилаються без змін):

- Мультимодальні моделі Jina: кожен елемент верхнього рівня стає одним об’єктом із ключем модальності
  (`text` / `image` / `audio` / `video` / `pdf`), що використовує URI даних для вбудованих медіаданих; один вектор на
  елемент верхнього рівня.
- Сімейство Gemini Embedding 2: один масив верхнього рівня стає єдиним нативним запитом
  `models/{model}:embedContent` із `content.parts` (`text` або `inline_data`).
- llama.cpp (`llama-cpp/<model>`, будь-яка модель, завантажена локальним сервером): канонічні елементи `text`
  стають звичайними рядками, а `image` / `audio` / `video` — по одному об’єкту
  `{"content": [part]}` кожен, використовуючи частини вмісту чату llama-server (`image_url`,
  `input_audio` з форматом `wav` / `mp3` / `flac`, `input_video`) із вбудованими даними; один вектор
  на елемент верхнього рівня. Сервер має працювати з `--embedding --mmproj …`; без проєктора він
  самостійно відхиляє медіадані. `document` не підтримується.
- Невідомі/динамічні моделі без явних метаданих модальності відхиляють структуровані вхідні дані з HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Непідтримувані комбінації моделі та модальності повертають HTTP 400 замість примусового перетворення елемента. Поля розширення,
не пов’язані з вхідними даними, у застарілих рядкових/токенних запитах і надалі передаються без змін.

```bash
# Перелічити всі моделі вбудовування
GET /v1/embeddings
```

## Генерування зображень

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Серед доступних постачальників: OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (локальний), ComfyUI (локальний).

`n` повертає `n` зображень у `data[]`. Для постачальників, API яких повертає одне зображення за виклик
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), виконується `n` окремих викликів до API постачальника, щонайбільше 4 одночасно. Фіксоване
значення `seed` зміщується на індекс виклику (`seed`, `seed + 1`, …), тому зображення відрізняються, але залишаються
відтворюваними. Значення `n` обмежено 10. Увесь запит завершується помилкою, якщо будь-який виклик зазнає невдачі. Перелік
форматів із розгалуженням міститься в `SINGLE_IMAGE_FANOUT_FORMATS` у
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux повторно використовує наявне підключення з ключем API та приймає префікси `zenmux/` або `zm/`:

- `zenmux/openai/gpt-image-2` використовує OpenAI Images API від ZenMux. Доступні параметри: `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` і `response_format`.
- Інші видавці, як-от `zm/meta/muse-image-1.0`, використовують кінцеву точку Vertex AI `:predict`
  від ZenMux. `n` зіставляється із `sampleCount`, `aspect_ratio` — із `aspectRatio`, а `image_size`
  (`1K`, `2K`, `4K`) — із `sampleImageSize`. Значення `size` у пікселях визначає лише співвідношення сторін,
  а не гарантовані розміри в пікселях. Підтримувані співвідношення сторін, роздільності та кількості залежать від моделі.
- `zm/inclusionai/ming-image-0.1-design` самостійно визначає розміри. Не вказуйте `size`,
  `aspect_ratio` та `image_size`; явне зазначення цих значень повертає HTTP 400. Формати PNG, JPEG і WebP
  можна запитати за допомогою `output_format`.

Ця інтеграція підтримує генерування зображень із тексту, але не редагування зображень за зразком. Вихідні дані Vertex
нормалізуються до `data[].b64_json`; `response_format: "url"` повертає HTTPS URL від постачальника
або URL даних base64, якщо доступні лише байти зображення. Порожні або відфільтровані вихідні дані
повертають помилку, а не порожню успішну відповідь. Доступ до моделей залежить від облікового запису ZenMux.
Див. [Vertex API від ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) та
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Перелічити всі моделі зображень
GET /v1/images/generations
```

```bash
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` вибирає постачальника OCR за допомогою префікса `provider/model`; ідентифікатор моделі без префікса (наприклад,
`mistral-ocr-latest`) зіставляється із зареєстрованим постачальником, а якщо `model` не вказано, за замовчуванням
використовується Mistral (`mistral-ocr-latest`). Зареєстровані постачальники (`open-sse/config/ocrRegistry.ts`):

| Ідентифікатор постачальника   | Ідентифікатор моделі | Значення `model`                                               | Примітки                                                                                                                               |
| ----------------------------- | -------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (або просто `mistral-ocr-latest`) | Синхронний — відповідь повертається безпосередньо з єдиного виклику до API постачальника.                                              |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                    | Асинхронний API постачальника (`analyze` + опитування) — див. нижче.                                                                   |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                        | Синхронний, через партнерську кінцеву точку Vertex AI `openapi/chat/completions` — відомості про автентифікацію та URL наведено нижче. |

Усі три постачальники повертають тіло відповіді в однаковому форматі Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Процес опитування Azure Document Intelligence

API `analyze` від Azure Document Intelligence є асинхронним: початковий запит повертає заголовок
`Operation-Location` замість тіла відповіді, після чого результат потрібно отримувати шляхом опитування. Обробник
(`open-sse/handlers/ocr.ts`) опитує цей URL щосекунди, виконуючи до 30 спроб, негайно завершується помилкою (не
продовжує опитування) у разі відповіді опитування, відмінної від `ok`, або стану `"failed"`, і повертає `504`, якщо
після вичерпання ліміту спроб операція все ще виконується. Перед поверненням викликувачу остаточна відповідь Azure
нормалізується до того самого формату `pages`/`markdown`, який використовує Mistral, тому клієнтському коду
не потрібно окремо обробляти кожного постачальника.

### Автентифікація та визначення кінцевої точки Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` повторно використовує ту саму автентифікацію Vertex AI, яку OmniRoute уже підтримує для
трафіку чатів і зображень (`open-sse/executors/vertex.ts`): ключ API підключення є або обліковими даними
Service Account JSON (які обмінюються на короткостроковий токен доступу OAuth за допомогою процесу JWT-bearer),
або вже створеним токеном доступу OAuth, що використовується без змін. URL кінцевої точки постачальника — це
універсальна партнерська кінцева точка Vertex `openapi/chat/completions`, сформована на основі проєкту та
регіону підключення: явно задані `providerSpecificData.project`/`providerSpecificData.region` завжди мають пріоритет;
інакше проєкт визначається з `project_id` у Service Account JSON, а регіон за замовчуванням має значення
`us-central1`. Обидва значення визначаються в `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) і використовуються в
`src/app/api/v1/ocr/route.ts` перед передаванням до `handleOcr`.

### Префікси ідентифікаторів моделей (`?prefix=`)

Більшість моделей публікуються з **префіксом провайдера**. Вибір префікса визначається прапорцем функції
`MODELS_CATALOG_PREFIX_MODE`, але його можна перевизначити **для кожного запиту** за допомогою
параметра запиту — це корисно для клієнта, якому потрібен чистий список без зміни загальносерверного
налаштування для всіх інших:

```bash
GET /v1/models?prefix=alias        # один ідентифікатор на модель — короткий префікс псевдоніма
GET /v1/models?prefix=dual         # обидві форми (стандартне налаштування сервера)
GET /v1/models?prefix=canonical    # лише повний префікс ідентифікатора провайдера
```

| Режим       | Виводить                                                | Примітки                                                                                                                                                                                                               |
| ----------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **і** `claude/claude-sonnet-4-6` | **За замовчуванням.** Обидва ідентифікатори спрямовуються до тієї самої моделі; збережено, щоб конфігурації клієнтів із жорстко заданою будь-якою формою продовжували працювати. Приблизно подвоює каталог.            |
| `alias`     | `cc/claude-sonnet-4-6`                                  | Один запис на модель. Провайдери без окремого псевдоніма все одно виводять свій запис, тому нічого не втрачається.                                                                                                     |
| `canonical` | `claude/claude-sonnet-4-6`                              | Один запис на модель із повним префіксом ідентифікатора провайдера. Провайдери без окремого псевдоніма (наприклад, `antigravity/…`, `agy/…`) також виводять тут свій єдиний ідентифікатор, тому нічого не втрачається. |

Дзеркальний запис у режимі `dual` також можна розпізнати без параметра запиту: він містить поле `parent`,
яке вказує на основний ідентифікатор.

Клієнти, що відображають засіб вибору моделі, мають запитувати `?prefix=alias` — саме так робить
[розширення OmniCopilot для VS Code](../guides/VSCODE-COPILOT.md).

### Фільтри виявлення (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` підтримує необов’язкові фільтри виявлення. Без жодного з них відповідь
не змінюється. Вони звужують каталог, уже доступний виклику (спочатку застосовуються дозволи ключа API),
і виконуються перед пагінацією в стилі OpenAI за допомогою `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # кожна зазначена можливість має бути доступною
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` каталогу; рядки без нього мають тип `chat`
GET /v1/models?q=sonnet&limit=10                           # пошук без урахування регістру за ідентифікатором або назвою
```

| Параметр      | Значення                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | невід’ємне ціле число, яке порівнюється з `context_length`                                          |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 символів                                                                                      |

Невідоме значення або значення `min_context`, яке не є невід’ємним цілим числом (наприклад, `1.5`),
повертає HTTP `400`, а повідомлення містить перелік допустимих значень. Реалізація:
`src/app/api/v1/models/catalogFilters.ts`.

### Короткий список моделей (`POST /v1/models/query`)

`POST /v1/models/query` повертає короткий детермінований список із того самого каталогу, з тією самою
автентифікацією та видимістю для кожного ключа, що й `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Кожне поле є необов’язковим. `capabilities` і `exclude` приймають масив або рядок зі значеннями, розділеними комами;
`max_output` порівнюється з `max_output_tokens`. Результати сортуються спочатку за `owned_by`, а потім за `id`.
Значення `limit` за замовчуванням дорівнює `20`, а значення понад `100` обмежуються до `100`. Некоректний JSON, невідоме
поле або недопустиме значення повертає HTTP `400`.

### Окремо приховані моделі чату

Модель, позначена як **Прихована** на сторінці свого провайдера, виключається з каталогу, а явний
запит до неї відхиляється з HTTP `404` / `model_not_found`. Перевірка використовує визначені
провайдера й модель, зокрема псевдоніми провайдерів, префікси вузлів сумісних провайдерів і
стандартні налаштування підключення. Комбінація пропускає приховані цілі й може використовувати видиму споріднену модель; якщо
не залишається жодної доступної для виконання цілі, повертається той самий код помилки. Скасування приховування набуває чинності під час наступного
запиту. Перевизначення видимості лише для зображень не приховують модель чату з таким самим ідентифікатором.

Це індивідуальне налаштування моделі відокремлене від
[списків дозволу/заборони доступності моделей](../routing/MODEL_EXPOSURE_LIST.md), які фільтрують
публікацію каталогу та кандидатів для автоматичної маршрутизації, водночас зберігаючи явне спрямування. Дозволи моделей
для ключів API продовжують застосовуватися незалежно. Стандартним режимом префіксів каталогу залишається `dual`.

### Варіанти моделей без мислення

Для моделей Claude із підтримкою мислення `/v1/models` також публікує варіант **без мислення**, ідентифікатор якого має префікс `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Вибір цього ідентифікатора (наприклад, у конфігурації Claude Code, яка завжди додає блок `thinking`) зіставляється зі справжнім `<provider>/<model>` із вимкненим міркуванням — `thinking:{type:"disabled"}` для шляху `/v1/messages` або з вилученими полями `reasoning`/`reasoning_effort` для шляху `/v1/chat/completions`. Варіант відображається лише для моделей сімейства Claude, які підтримують міркування **і** враховують значення `disabled` (тому, наприклад, моделі, що підтримують лише адаптивний режим і відхиляють `disabled`, не включаються). Оператори можуть примусово ввімкнути або вимкнути цей варіант для кожної моделі за допомогою `ModelSpec.noThinkingAlias`.

## Генерування аудіо ElevenLabs

Налаштуйте підключення провайдера `elevenlabs` в OmniRoute за допомогою свого API-ключа ElevenLabs.
Клієнти автентифікуються за допомогою свого ключа **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
шлюз передає збережений ключ провайдера як `xi-api-key`. Ніколи не надсилайте ключ ElevenLabs
як bearer-токен шлюзу.

| Метод | Шлях                        | Відповідь                                  | Категорія кінцевої точки API-ключа |
| ----- | --------------------------- | ------------------------------------------ | ---------------------------------- |
| POST  | `/v1/sound-generation`      | Нативні байти аудіо                        | `elevenlabs`                       |
| POST  | `/v1/music`                 | Нативні байти аудіо                        | `music`                            |
| POST  | `/v1/music/stream`          | Потокові байти аудіо                       | `music`                            |
| POST  | `/v1/music/detailed`        | Нативне multipart-аудіо та план композиції | `music`                            |
| POST  | `/v1/music/detailed/stream` | Нативні метадані SSE та фрагменти аудіо    | `music`                            |
| POST  | `/v1/music/plan`            | План композиції у форматі JSON             | `music`                            |

Ці кінцеві точки доповнюють наявні маршрути `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` і `/v1/speech-to-text`. Нативні поля JSON
і параметри запиту, як-от `output_format` та `enable_logging`, зберігаються.
Відповіді `/v1/music/detailed` зберігають свої межі multipart; обробляйте їх як multipart.
`/v1/music/detailed/stream` повертає `text/event-stream` із метаданими композиції та
фрагментами аудіо у форматі base64 в подіях SSE. Усі шість маршрутів підтримують попередні запити CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Короткий звуковий ефект. Тривалість: від 0,5 до 30 секунд.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Тривалість музики вказується в мілісекундах: від 3000 до 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Використовуйте `/v1/music/stream` із тим самим тілом JSON для поетапного передавання аудіо. Композиція
приймає лише одне з двох полів: `prompt` або `composition_plan`; `/v1/music/plan` вимагає `prompt`
і необов’язково приймає `source_composition_plan`. Нативні схеми зберігають додаткові
поля провайдера, щоб версії плану композиції та параметри тонкого налаштування передавалися до ElevenLabs.

Уніфікована кінцева точка `/v1/music/generations` також приймає `elevenlabs/music_v1`,
`elevenlabs/music_v2` і `elevenlabs/music_v2_5`. За наявності активного підключення ElevenLabs
ці моделі відображаються в каталозі музики. Ця кінцева точка повертає
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Її поле `duration` задається в
секундах і зіставляється з `music_length_ms`; явно вказане `music_length_ms` має пріоритет.
`instrumental` зіставляється з `force_instrumental`, водночас нативне поле має пріоритет.
Використовуйте нативні потокові кінцеві точки для потокового передавання, а нативну кінцеву точку композиції —
для запитів, що керуються лише планом композиції.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Обмеження кінцевої точки, моделі, бюджету та підключення застосовуються до виклику зовнішнього сервісу. Нативні
маршрути повертають коди стану та тіла помилок зовнішнього сервісу без змін, зокрема `402` для обмеження
тарифного плану та `429` для перевищення квоти. Заголовки `character-cost`, `song-id`, `request-id` і `retry-after`
зберігаються, якщо вони наявні. Безплатний кредитний баланс не гарантує доступу до кожної
музичної моделі, формату виведення або функції API: ElevenLabs визначає право доступу для кожного запиту.
Уніфікована кінцева точка зберігає коди стану помилок у нормалізованій оболонці помилок OmniRoute.

Контракти зовнішнього сервісу: [звукові ефекти](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[створення музичних композицій](https://elevenlabs.io/docs/api-reference/music/compose) і
[потокові відомості про музику](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

| GET   | `/api/v1/vscode/{token}/models`           | Псевдонім моделей OpenAI                     |
| POST  | `/api/v1/vscode/{token}/chat/completions` | Токенізований псевдонім OpenAI               |
| POST  | `/api/v1/vscode/{token}/responses`        | Токенізований псевдонім OpenAI Responses     |
| POST  | `/api/v1/vscode/{token}/api/chat`         | Токенізований псевдонім Ollama               |
| GET   | `/api/v1/vscode/{token}/api/tags`         | Токенізований псевдонім тегів Ollama         |

Усі маршрути POST мають однакову структуру: `Bearer your-api-key` + перевірене за допомогою Zod тіло JSON (`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema` тощо; див. `src/shared/validation/schemas.ts`). У разі невдалої перевірки схеми повертається 4xx.

Для клієнтів, які не можуть додати `Authorization: Bearer ...`, OmniRoute також приймає ключі API в URL — через сумісні параметри рядка запиту (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) або спеціальні кінцеві точки `/api/v1/vscode/{token}/...`, описані нижче.

```bash
# Переранжування (провайдер хмарного реєстру або вузол OpenAI-сумісного провайдера у вигляді "<prefix>/<model>")
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Класифікація Jina (облікові дані Foundation API)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Сегментатор Jina
POST /v1/segment     { "content": "...", "return_chunks": true }

# Пошук Jina (s.jina.ai; псевдоніми провайдера: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# Модерація
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — повертає тіло audio/mpeg (або запитаного формату)
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS вимагає мову та голос: `language` за замовчуванням має значення "en"; відсутній
# голос або назва стандартного голосу OpenAI (alloy, nova, …) замінюється на "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# Редагування зображення (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# Генерування відео / музики (ідентифікатор моделі з префіксом провайдера)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **Вузли провайдерів переранжування:** `POST /v1/rerank` також маршрутизує запити до сумісних з OpenAI вузлів провайдерів
> (oMLX, vLLM, Infinity, TEI за шлюзом, …), адресованих як `<node-prefix>/<model>`. Вузли зворотного зв’язку
> (`localhost`, `127.0.0.1`, `172.16.0.0/12`) завжди дозволені, як і імена хостів, які
> оператор перелічує в `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (наприклад, ім’я служби Docker/Compose,
> як-от `http://reranker:8080/v1`; до них звертаються безпосередньо, ніколи не через `HTTP(S)_PROXY` або
> закріплений проксі з’єднання). Вузли на будь-якому іншому
> хості — комп’ютері в LAN або вузлі Tailscale — дозволені лише тоді, коли оператор вмикає
> прапорець функції `RERANK_REMOTE_PROVIDER_NODES` **і** базова URL-адреса вузла відповідає політиці
> вихідних URL-адрес провайдера (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Етап переранжування рушія пам’яті викликає цей маршрут через
> зворотний зв’язок, тому те саме правило застосовується до `rerankProviderModel` у налаштуваннях Memory.
>
> **Формати локальних серверів:** вузол викликається за адресою `<base>/v1/rerank`, а в разі 404 — за адресою `<base>/rerank`
> (Infinity, TEI). Тіло запиту до сервера містить як написання Cohere/OpenAI (`documents`,
> `return_documents`), так і написання TEI (`texts`, `return_text`), а відповідь сервера
> нормалізується до оболонки Cohere: неперероблений масив TEI `[{index, score, text}]`, `{results: [{index, score}]}`
> від простих шлюзів і формат Voyage `{data: [...]}` повертаються клієнту як
> `{results: [{index, relevance_score, document?}]}`, відсортовані за оцінкою та обмежені значенням `top_n`.

> **Виявлення вузлів провайдерів:** моделі на сумісному з OpenAI вузлі провайдера відображаються в `GET /v1/models`
> під префіксом вузла. Рядки без метаданих кінцевої точки (типово для локальних списків `/v1/models`)
> успадковують `apiType` вузла, тому моделі вузла `embeddings` мають `type: "embedding"`, а моделі
> вузла `rerank` — `type: "rerank"` замість типового типу чату; явне значення
> `supportedEndpoints` у синхронізованому або доданому вручну рядку все одно має пріоритет.

### Спеціалізовані маршрути провайдерів

```bash
POST /v1/providers/{provider}/chat/completions
POST /v1/providers/{provider}/embeddings
POST /v1/providers/{provider}/images/generations
```

## API пошуку

Абстракція провайдерів вебпошуку (Tavily, Brave, Exa, Serper тощо).

| Метод | Шлях                   | Опис                                                                                                           |
| ----- | ---------------------- | -------------------------------------------------------------------------------------------------------------- |
| GET   | `/v1/search`           | Перелік налаштованих провайдерів пошуку та їхніх можливостей                                                   |
| POST  | `/v1/search`           | Виконання пошукового запиту — тіло перевіряється за допомогою `v1SearchSchema`, підтримує кешування/об’єднання |
| GET   | `/v1/search/analytics` | Статистика влучань/затримки/кешу для кожного провайдера                                                        |

**Автентифікація:** API-ключ Bearer (`extractApiKey` + `isValidApiKey`). Політика пошуку застосовується через `enforceApiKeyPolicy`.

### `provider_options` для Exa та Tavily

Exa та Tavily зчитують специфічні для провайдера поля з простору імен:
`provider_options.exa` (або `provider_options["exa-search"]`) і `provider_options.tavily`
(або `provider_options["tavily-search"]`). Передаються лише наведені нижче ключі. Кожен із них
перевіряється за власною схемою Zod у `open-sse/handlers/search/providerOptionsPassthrough.ts`,
а ключ із неправильним типом відкидається. Будь-який інший ключ ігнорується, зокрема автентифікація, базова URL-адреса,
`stream` та `outputSchema`. Плоскі ключі, які використовують інші провайдери (`cx`, `depth`, ...), працюють
як і раніше.

| Провайдер | Поля верхнього рівня                                                                                                                                                                                                                                                                                                                                                      | Вкладені                                                                                                                                                                   |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa       | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (плоскі примітиви), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                             | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` об’єднується з типовим значенням `{ text: true, highlights: true }` |
| Tavily    | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                          |

Загальні поля завжди мають пріоритет: `query`, `max_results`, `filters` (домени), `country` і
тема, отримана з `search_type`. Для Exa `search_type: "news"` зберігає `category: "news"`.
Tavily також приймає `search_type: "finance"` (`topic: "finance"`).

Загальне поле `time_range` тепер передається обом провайдерам: Exa отримує `startPublishedDate` (часова мітка ISO),
а Tavily — `start_date` (`YYYY-MM-DD`). Явно вказана дата в `provider_options`
перевизначає зіставлену дату.

Результати Exa зберігають `id`, `highlight_scores`, `summary`, `subpages`, `entities` і `extras` у
`provider_raw`. Результати Tavily зберігають `images` і `favicon`.

Облік вартості й надалі використовує плоский реєстр `costPerQuery`. Tavily нараховує
більше кредитів за виклик із `search_depth: "advanced"`, і ця різниця не відображається в
`usage.search_cost_usd`.

## API Web Fetch

Видобувайте вміст із URL через налаштованого провайдера вебзавантаження (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, той самий ключ API, що й для Parallel Search) повертає лише
Markdown — будь-який інший `format` спричиняє `400` — і обмежує вміст 100 000 символами. Якщо
саму цільову сторінку неможливо видобути, upstream-сервіс повідомляє про це всередині відповіді HTTP 200;
OmniRoute повертає це як `422` із фіксованим повідомленням.

| Метод | Шлях            | Опис                                                                            |
| ----- | --------------- | ------------------------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | Завантаження/скрейпінг URL — тіло перевіряється за допомогою `v1WebFetchSchema` |

**Автентифікація:** Bearer-ключ API (`extractApiKey` + `isValidApiKey`). Політика застосовується через `enforceApiKeyPolicy`.

**Резервне перемикання з урахуванням квот (#8297):** коли явний `provider` не вказано, пул
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) обходиться у фіксованому
порядку пріоритету (fill-first) — налаштований провайдер, для якого перевищено ліміт запитів, пропускається
замість негайного завершення запиту, а повторювана помилка upstream-сервісу або помилка квоти
(HTTP 429 завжди; 402/403 для безкоштовних рівнів Firecrawl/Tavily/TinyFish із квотами —
не для Jina Reader і ніколи для звичайного помилкового запиту 400) спричиняє перехід до
наступного ще не випробуваного провайдера з обліковими даними під час виконання запиту. Коли всі провайдери в
пулі вичерпано, кінцева точка повертає єдину відповідь `429` (із заголовком `Retry-After`)
замість попередньої загальної відповіді `400`. Коли явно запитується `provider`,
**приховане резервне перемикання не виконується** — явний провайдер, для якого перевищено ліміт запитів або який завершився помилкою,
повертає власну помилку (`429`, якщо перевищено ліміт запитів, інакше — статус
upstream-сервісу).

## Потокове передавання через WebSocket

```bash
GET /v1/ws?handshake=1
```

Перевіряє handshake для переходу на WebSocket і повертає приклади повідомлень протоколу передавання (`request`, `cancel`). Фактичні WS-фрейми обробляються вбудованим WS-сервером поза таблицею маршрутів Next.js.

**Автентифікація:** Bearer-ключ API під час handshake.

### Responses API через WebSocket (лише codex)

```bash
# Той самий хост і порт, що й у HTTP API (типово 20128); виконайте перехід з'єднання:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (або: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Перший фрейм МАЄ бути response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Проксі Responses API через WebSocket підключено **виключно до `codex`** (бекенд ChatGPT).
Він прослуховує той самий порт, що й API/панель керування, за шляхами `/v1/responses`,
`/responses` і `/api/v1/responses`. Під час першого фрейму `response.create` він
виконує автентифікацію й підготовку через внутрішній міст `codex-responses-ws`, вибирає
OAuth-з'єднання codex і тунелює запит до `wss://chatgpt.com/backend-api/codex/responses`
через транспорт `wreq-js`. **Моделі, що не належать до codex, відхиляються** (`codex_ws_provider_required`).
Для маршрутизації зі спільною квотою використовуйте `model: "qtSd/<group>/codex/<model>"`. Реалізовано у
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Автентифікація:** Bearer-ключ API під час handshake. Вбудований HTTP-сервер (`server-ws.mjs`)
має бути активною точкою входу (і є нею типово, коли існує `app/server-ws.mjs`).

#### Ідентифікатор моделі: використовуйте простий ідентифікатор ChatGPT (без префікса `codex/`)

OpenAI **Codex CLI** перевіряє назву моделі на стороні клієнта, коли
`supports_websockets = true`, і **відхиляє ідентифікатори з префіксом провайдера**, як-от
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Надсилайте **простий** ідентифікатор (наприклад, `gpt-5.5`). Міст OmniRoute
працює лише з codex, тому перед тунелюванням до upstream-сервісу він повторно визначає простий ідентифікатор як модель codex
(`resolveCodexWsModelInfo`) — навіть попри те, що простий
`gpt-5.5` інакше маршрутизувався б до іншого провайдера через HTTP.

#### Налаштування OpenAI Codex CLI

Спрямуйте Codex CLI на OmniRoute, додавши спеціального провайдера з підтримкою WebSocket
до `~/.codex/config.toml` (використовуйте окремий `CODEX_HOME`, щоб не змінювати
наявну конфігурацію):

```toml
model = "gpt-5.5"                 # простий ідентифікатор — НЕ "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # без кінцевої скісної риски; URL для WS формується автоматично (у production використовуйте https/wss)
wire_api = "responses"                    # єдине підтримуване значення з лютого 2026 року
supports_websockets = true                # вмикає транспорт Responses через WS
env_key = "OMNIROUTE_API_KEY"             # містить ключ API OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # ключ API OmniRoute (будь-який ключ, якщо REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI перетворює `base_url + /responses` на WebSocket, а OmniRoute тунелює його
до вибраного OAuth-з'єднання codex. Перевірено наскрізно з локальним
сервером: ChatGPT повертає `codex.rate_limits` + `response.created` і потоково передає
результат.

## Самообслуговування для перегляду використання (`/api/usage/om-usage`)

Будь-який API-ключ може переглядати **власні** дані про використання та квоти — без автентифікації для керування. Це кінцева точка, яку
клієнт (CLI, панель OmniCopilot) використовує, щоб показати власнику ключа його витрати.

```bash
# Текстовий формат (історичний контракт — звичайний текст для термінала)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Структурований формат — для використання інтерфейсом
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Для ключа має бути ввімкнено **`allowUsageCommand`** (типово вимкнено — менеджер API-ключів
на інформаційній панелі перемикає цей параметр окремо для кожного ключа). Без нього кінцева точка повертає `403`.

`?format=json` повертає дискриміновану структуру, тож клієнт ніколи не зчитуватиме поле даних із
відмови. У разі успіху:

```jsonc
{
  "allowed": true,
  // наявне лише тоді, коли для ключа ввімкнено окремі ліміти використання (денні/тижневі в доларах США):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // знімок квоти вибраного постачальника або null, якщо в кеші ще нічого немає:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // знімки всіх підключень, щоб інтерфейс міг відображати кількох постачальників поруч:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

У разі відмови (`401` — неправильний ключ / `403` — доступ не дозволено) той самий маршрут повертає
`{ "allowed": false, "error": { "message": "…" } }` — наявне, але порожнє значення `personal`/`provider`
(ключ дозволено, але даних ще не отримано) є станом, відмінним від відмови, і розрізнити їх можна лише
у форматі JSON.

**Автентифікація:** власний API-ключ Bearer клієнта, перевірений за допомогою `isValidApiKey` — це _не_
інтерфейс керування (`/api/keys/…`), який залишається захищеним через `requireManagementAuth`.

### Необроблені та скориговані за порогом відсікання відсотки квоти

Під час використання `/api/usage/om-usage` клієнтам слід ураховувати різницю між
відсотками, представленими у **звичайному текстовому виведенні**, і структурованим **виведенням JSON**:

| Аспект                   | Формат звичайного тексту (`/api/usage/om-usage` / `@@om-usage`)                                     | Формат JSON (`?format=json`)                                                                                  |
| :----------------------- | :-------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------ |
| **Поле виведення**       | `NN% left` (наприклад, `20% left`)                                                                  | `provider.quotas` / `providers[].quotas`                                                                      |
| **Вимірювання**          | **Скоригований за порогом відсікання доступний залишок**: доступна місткість понад поріг відсікання | **Необроблена квота постачальника**: нескориговане вимірювання постачальника                                  |
| **Масштабування порогу** | Масштабується через `effectiveRemainingPercent()`, щоб захищений резерв відображався як `0% left`   | Відсутнє (необроблені значення знімка, повідомлені постачальником)                                            |
| **Дані порога**          | Ураховуються у відображеному відсотку                                                               | Зберігаються в `quotaWindowThresholds` для кожного підключення (або використовуються типові значення сервера) |
| **Основний споживач**    | Інтерактивні CLI, запити термінала, оператори                                                       | Програмні інтеграції, інформаційні панелі, аналітика, засоби обліку витрат                                    |

#### Формула коригування за порогом відсікання

OmniRoute підтримує завчасне відсікання квоти для запобігання вичерпанню ресурсів постачальника (налаштовується через
`quotaWindowThresholds` підключення, типові значення постачальника або глобальні налаштування стійкості). Коли для вікна квоти
активний поріг відсікання (наприклад, `cutoff = 25%`), засіб текстового відтворення обчислює доступний залишок так:

- Якщо `remaining <= cutoff`: повертає `0%`.
- Якщо `remaining > cutoff`: повертає `((remaining - cutoff) / (100 - cutoff)) * 100`.

У форматованому текстовому виведенні результат округлюється до найближчого цілого числа (`Math.round(...)`).

#### Ілюстративний приклад

Розгляньмо вікно постачальника з **60% необробленого використання** (а отже, **40% необробленої квоти, що залишилася**) і налаштованим
порогом відсікання на рівні **25% залишку квоти**:

| Представлення                          | Обчислення                                         | Залишок |           Відповідне використання            |
| :------------------------------------- | :------------------------------------------------- | :-----: | :------------------------------------------: |
| **Необроблений JSON (`?format=json`)** | Знімок постачальника (`quotas[window]`)            | **40%** |                   **60%**                    |
| **Текстовий формат (`NN% left`)**      | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (якщо обчислювати `100 - remaining`) |

- **Чому текст показує 20% залишку:** Із 40% фізичної квоти, що залишилася в обліковому записі, 25% зарезервовано
  політикою відсікання. Клієнту доступно лише 15% із 75% придатного до використання запасу, перш ніж маршрутизатор припинить
  спрямовувати запити до цього підключення. Масштабування гарантує, що підключення сигналізуватиме про вичерпання (`0% left`) саме тоді, коли
  маршрутизацію буде припинено.
- **Чому JSON зберігає необроблені значення:** Корисне навантаження JSON повертає точний знімок постачальника (`UsageSnapshot`),
  щоб зовнішні інструменти мали доступ до фактичного використання ресурсів постачальника та значень
  `quotaWindowThresholds` на рівні підключення без масштабування зі втратою даних на сервері.

#### Рекомендації щодо міграції споживачів

Якщо зовнішня інтеграція (наприклад, плагін редактора або розширення агента) раніше отримувала дані з текстової
кінцевої точки (`NN% left`) і обчислювала використаний відсоток як `100 - NN`, перехід на `?format=json` означає:

- Читання необроблених значень JSON відображатиме **фактичне споживання на стороні постачальника** (60% використано в наведеному вище прикладі).
- Якщо інтеграція прагне зберегти семантику доступного залишку текстової кінцевої точки, вона може обчислювати
  ефективну формулу залишку на боці клієнта, використовуючи `quotaWindowThresholds` для перевизначень на рівні підключення.

## Семантичний кеш

```bash
# Отримати статистику кешу
GET /api/cache/stats

# Очистити всі кеші
DELETE /api/cache/stats
```

Приклад відповіді:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Вплив на затримку

У разі ВЛУЧАННЯ в семантичний кеш відповідь надсилається з кешу **без виклику
висхідного сервісу**, тому вказана затримка `X-OmniRoute-Response-Latency` є майже нульовою
(незалежно від початкової затримки висхідного сервісу). Клієнти, чутливі до затримки
(тестування продуктивності, моніторинг p50/p99), мають перевіряти заголовок відповіді
`X-OmniRoute-Cache-Latency`:

| Значення     | Пояснення                                                                |
| ------------ | ------------------------------------------------------------------------ |
| `synthetic`  | Відповідь надано з кешу; затримка не є реальним часом висхідного сервісу |
| _(відсутнє)_ | Відповідь отримано в результаті реального виклику висхідного сервісу     |

### Обхід кешу для окремого ключа

API-ключі можуть відмовитися від читання семантичного кешу за допомогою `cacheDefaultMode`:

| Значення | Поведінка                                                                 |
| -------- | ------------------------------------------------------------------------- |
| `legacy` | Звичайна поведінка кешу (за замовчуванням)                                |
| `bypass` | Повністю пропускати пошук у кеші; завжди звертатися до висхідного сервісу |

Установіть під час створення ключа (`POST /api/keys`) або оновлення (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Обхід кешу для окремого запиту

Будь-який запит може обійти кеш незалежно від налаштувань ключа:

```
X-OmniRoute-No-Cache: true
```

Для синхронізованих/імпортованих моделей `PUT /api/provider-models` приймає `provider`, `modelId` і
`maxOutputTokenOverride`: додатне ціле число встановлює задане вручну обмеження вихідних токенів, а `null`
скасовує його, відновлюючи значення за замовчуванням. `GET /api/provider-models?provider=<provider>` повертає ці
значення в `modelOutputOverrides`, зокрема для моделей без запису користувацької моделі. Перевизначення
використовує можливість середовища виконання `max_output_tokens` і зберігається після повторної синхронізації моделі. Сторінка
OpenAI-сумісного постачальника пропонує ті самі елементи керування редагуванням/скасуванням і позначає моделі з явно заявленою підтримкою зору.

Користувацькі вузли Chat Completions адаптують явну відмову від міркування до серверної частини постачальника. Успішна
перевірка підключення автоматично вибирає елементи керування шаблоном чату для кожного точного ідентифікатора моделі,
для якого запис `/models` підтверджує розпізнане значення `owned_by`: `vllm`, `sglang` або `llamacpp`.
Прозорі OpenAI-сумісні обгортки можуть зберігати початковий запис моделі у вкладеному
об’єкті `openai`; виявлення охоплює до трьох таких оболонок. Моделі з відсутньою, невідомою або
суперечливою інформацією про власника зберігають звичайну поведінку OpenAI. Виявлення повторно використовує наявний запит каталогу,
не генерує токенів завершення та анулюється, коли змінюється кінцева точка підключення.

Щоб зафіксувати поведінку для серверної частини, яка не надає ці метадані, скористайтеся наявним API
часткового оновлення постачальника:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Надішліть це тіло за допомогою `PUT /api/providers/<connection-id>`. Для цього підключення явно заданий
рівень зусиль для міркування `none` надсилається як `chat_template_kwargs.thinking=false` і
`chat_template_kwargs.enable_thinking=false`. Явні нативні значення шаблону залишаються пріоритетними,
якщо правило міркування на стороні сервера не встановлює рівень зусиль примусово. Налаштування застосовується лише тоді, коли користувацьке
OpenAI-сумісне підключення надсилає тіло Chat Completions; запити Responses і звичайні
постачальники зберігають свою нативну структуру запиту. Установіть `reasoningControl` у `openai`, щоб примусово використовувати звичайне наскрізне
передавання OpenAI `reasoning_effort`, або не вказуйте його чи встановіть у `null`, щоб використовувати автоматичне виявлення.

Запити класифікатора автоматичного режиму Claude Code за замовчуванням вимикають нативне міркування, якщо вони
не містять явних елементів керування міркуванням. Виявлення використовує системний маркер класифікатора в запитах
формату Claude, а не назви моделей чи обмеження завершення. Явні елементи керування в тілі, підтримувані заголовки
рівня зусиль/міркування, правила маршрутизації та визначений рівень зусиль моделі зберігають наявний пріоритет. Обидва етапи
класифікатора зберігають свої підказки, обмеження завершення, стоп-послідовності та фактичні вердикти постачальника
щодо дозволів; другий етап усе ще може повертати запитане видиме міркування як звичайний текст.

### Версія та канал випуску

```bash
GET /api/system/version
```

Маршрут керування лише через loopback-інтерфейс (автентифікація адміністратора). Повертає запущену версію, останню
опубліковану версію та стан автоматичного оновлення. `releaseChannel` і `channels` є додатковими
полями (гілка 3.8.54); `channel` зберігає своє значення — режим розгортання, який використовує засіб оновлення
панелі керування (`npm`, `source` або `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — npm-канал запущеної збірки: `nightly` для версій `-nightly.*`,
  `next` для інших попередніх випусків (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` для стабільної версії
  попередньої основної версії відносно `channels.latest`, інакше `latest`. Застосовуються ті самі правила, що й у
  `scripts/release/dist-tag.mjs`, який вибирає npm dist-tag під час публікації.
- `channels` — остання опублікована версія для кожного dist-tag, отримана через `npm view omniroute dist-tags` (із резервним
  використанням HTTP реєстру), кешована з тим самим 10-хвилинним TTL, що й `latest`. `latest` присутній завжди
  (резервно використовується поле `latest`, а потім `"unavailable"`); `next`, `nightly` і `lts` з’являються
  лише тоді, коли відповідний dist-tag існує. Запит із `Cache-Control: no-cache` оновлює обидва результати пошуку.

Модель каналів (`latest` = v3 до загальнодоступного випуску 4.0, `next` = rc, `nightly` = збірки `develop`,
`lts` = виправлення v3 після загальнодоступного випуску 4.0) описана в `docs/ops/RELEASE_STRATEGY.md`.

> **Примітки до схеми** (`setBudgetSchema`): `apiKeyId` є обов’язковим; принаймні одне зі значень `dailyLimitUsd`, `weeklyLimitUsd` або `monthlyLimitUsd` має бути більшим за нуль. Необов’язкові поля: `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`). Застаріла структура `{keyId, limit, period}` повертає `400 Bad Request`.

## Ліміти токенів

Бюджети **токенів** для кожного ключа API (окремо від наведеного вище бюджету на основі USD). Застосовуються безпосередньо під час обробки запиту: коли використання ключа в поточному вікні досягає ліміту, запити відхиляються з помилкою `429 Too Many Requests`. Ліміти можна встановлювати для конкретної `model`, конкретного `provider` або застосовувати глобально (`global`) до всього ключа; якщо запиту відповідає кілька лімітів, застосовується найсуворіший із них.

```bash
# Перелічити ліміти токенів ключа (включно з поточним використанням у вікні)
GET /api/usage/token-limits?apiKeyId=key-123

# Створити або оновити ліміт токенів
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Видалити ліміт токенів за ідентифікатором
DELETE /api/usage/token-limits?id=tl-abc
```

> **Примітки щодо схеми** (`setTokenLimitSchema`): `apiKeyId` і `scopeType` (`model` | `provider` | `global`) є обов’язковими. `scopeValue` є обов’язковим, якщо `scopeType` не має значення `global` (наприклад, ідентифікатор моделі для області дії `model` або ідентифікатор провайдера для області дії `provider`). `tokenLimit` має бути додатним цілим числом (перетворюється з рядка). Необов’язкові поля: `id` (не вказуйте для створення, вкажіть для оновлення), `resetInterval` (`daily` | `weekly` | `monthly`, типове значення — `monthly`), `resetTime` (`HH:MM`), `enabled` (типове значення — `true`). Відповіді `GET` доповнюють кожен ліміт полями `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` і `nextResetAt`. Це кінцева точка класу керування (автентифікація централізовано забезпечується конвеєром авторизації).

## Обробка запитів

1. Клієнт надсилає запит до `/v1/*`
2. Обробник маршруту викликає `handleChat`, `handleEmbedding`, `handleAudioTranscription` або `handleImageGeneration`
3. Визначається модель (безпосередня пара провайдер/модель або псевдонім/комбінація)
4. Облікові дані вибираються з локальної БД із фільтрацією за доступністю облікового запису
5. Для чату: `handleChatCore` перевіряє семантичний кеш/кеш сигнатур і визначає налаштування стиснення комбінації
6. Якщо ввімкнено, проактивне стиснення виконується до перетворення запиту для провайдера (`lite`, Caveman, RTK або їх поєднання)
7. Виконавець провайдера надсилає запит до зовнішнього сервісу
8. Відповідь перетворюється назад у формат клієнта (для чату) або повертається без змін (для вбудовувань, зображень і аудіо)
9. Записуються дані про використання, аналітика стиснення та журнали запитів
10. У разі помилок застосовується резервний варіант відповідно до правил комбінації

Повний опис архітектури: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Відмовостійкість (розширено)

OmniRoute надає три незалежні механізми обробки тимчасових збоїв; наведені нижче кінцеві точки керування дають операторам змогу переглядати та перевизначати їх:

| Область                     | Зберігання стану                           | Перегляд                                  | Скидання / очищення                                             |
| --------------------------- | ------------------------------------------ | ----------------------------------------- | --------------------------------------------------------------- |
| Запобіжник провайдера       | `domain_circuit_breakers` + у пам’яті      | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                    |
| Період очікування з’єднання | `rateLimitedUntil` у з’єднаннях провайдера | `/api/rate-limits`, `/api/providers/[id]` | (повторно вмикається відкладено; очищення через PUT провайдера) |
| Блокування моделі           | Реєстр доступності моделей у пам’яті       | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                        |

`PATCH /api/resilience` приймає перевизначення запобіжника провайдера в `providerBreaker.oauth` і `providerBreaker.apikey`. Кожен профіль підтримує `degradationThreshold`, `failureThreshold` і `resetTimeoutMs`; ці самі поля доступні в Панель керування → Налаштування → Відмовостійкість.

```bash
# Очистити блокування однієї моделі
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Очистити всі блокування
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Повний концептуальний довідник і значення запобіжників за замовчуванням: див. [`CLAUDE.md`](../../CLAUDE.md) → «Стан середовища виконання відмовостійкості» та [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Черга обмеження частоти запитів і механізм автоматичного ввімкнення

- **Підтримуваний шлях запису**: `POST /api/rate-limits` із тілом `{"connectionId": "<id>", "enabled": true|false}` — це підтримувана кінцева точка керування для ввімкнення або вимкнення захисту від обмеження частоти запитів для з’єднання. `PUT /api/providers/[id]` навмисно не змінює та не перемикає `rateLimitProtection` (#11278).
- **Семантика `enabled: false`**: Установлення `enabled: false` прибирає явний захист з’єднання, але **не** виключає активне з’єднання за API-ключем із глобального механізму автоматичного ввімкнення (`autoEnableApiKeyProviders = true`). У `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) значення `false` і `undefined` еквівалентні; активні з’єднання за API-ключем без явного захисту залишаються захищеними глобальним механізмом автоматичного ввімкнення.
- **Глобальне вимкнення**: Щоб використовувати з’єднання за API-ключем без черг обмеження частоти запитів, глобально вимкніть цей механізм через `RATE_LIMIT_AUTO_ENABLE=false` (змінна середовища) або `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Налаштування → Відмовостійкість / `PATCH /api/resilience`).

| Метод | Шлях | Опис |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | Сигнал активності, транспорт, стан підключення, останній виклик, найпопулярніші інструменти, показник успішності за 24 години |
| GET | `/api/mcp/tools` | Список інструментів MCP із `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` |
| GET | `/api/mcp/sse` | Відкриває потік SSE для транспорту SSE (повертає `503`, якщо MCP вимкнено або транспорт не відповідає налаштуванням) |
| POST | `/api/mcp/sse` | Надсилає фрейм JSON-RPC через транспорт SSE |
| GET | `/api/mcp/stream` | Відкриває сторону SSE транспорту Streamable HTTP (повідомлення, ініційовані сервером) |
| POST | `/api/mcp/stream` | Надсилає фрейм JSON-RPC через транспорт Streamable HTTP |
| DELETE | `/api/mcp/stream` | Завершує сеанс Streamable HTTP |
| GET | `/api/mcp/audit` | Запит до журналу аудиту — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | Агрегована статистика аудиту (загальна кількість, показник успішності, середня тривалість, найпопулярніші інструменти) |

**Автентифікація:** транспорти `sse`/`stream` використовують спеціальний механізм автентифікації MCP (ключ API типу Bearer з областю доступу `mcp`); маршрути `status`/`tools`/`audit*` доступні для читання з панелі керування (додаткова автентифікація, окрім доступу до хоста панелі керування, не потрібна).

> Обидва HTTP-транспорти обмежуються налаштуваннями `settings.mcpEnabled` і `settings.mcpTransport` — невідповідність транспорту повертає `400`, а вимкнений стан MCP повертає `503`.

## Сервер A2A

OmniRoute надає кінцеву точку A2A (Agent-to-Agent) JSON-RPC 2.0, а також REST-обгортку для перевірки та використання в панелі керування.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # необов’язково, якщо не задано OMNIROUTE_API_KEY
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Підтримувані методи (усі залежать від `settings.a2aEnabled`):

| Метод            | Опис                                                                |
| ---------------- | ------------------------------------------------------------------- |
| `message/send`   | Синхронне виконання навички; повертає `{task, artifacts, metadata}` |
| `message/stream` | Потокове виконання того самого набору навичок через SSE             |
| `tasks/get`      | Отримання завдання за `taskId`                                      |
| `tasks/cancel`   | Скасування завдання за `taskId`                                     |

Вбудовані навички: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Картка агента

```bash
GET /.well-known/agent.json
```

Повертає загальнодоступну картку агента A2A (назву, опис, можливості, каталог навичок, схему автентифікації), яка кешується загальнодоступно протягом 1 години. Автентифікація не потрібна.

### Допоміжні REST-кінцеві точки

| Метод | Шлях                         | Опис                                                                                                                |
| ----- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/a2a/status`            | Стан увімкнення A2A + статистика завдань + зведення кешованої картки агента                                         |
| GET   | `/api/a2a/tasks`             | Список завдань — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST  | `/api/a2a/tasks`             | (Не реалізовано як допоміжну REST-кінцеву точку — створюйте через JSON-RPC `message/send`)                          |
| GET   | `/api/a2a/tasks/[id]`        | Отримання одного завдання                                                                                           |
| POST  | `/api/a2a/tasks/[id]/cancel` | Скасування завдання                                                                                                 |

**Автентифікація:** допоміжні REST-кінцеві точки працюють без автентифікації керування (доступні для читання з панелі керування); маршрут JSON-RPC `/a2a` використовує Bearer `OMNIROUTE_API_KEY`, якщо його налаштовано.

## Автентифікація

Опис чотирьох типів облікових даних (сеанс панелі керування, локальний токен CLI, токен доступу `oma_live_…`, API-ключ з областю керування) та їхніх відмінностей від ключів інференсу див. у розділі [Автентифікація керування](../guides/MANAGEMENT-AUTH.md).

- Маршрути панелі керування (`/dashboard/*`) використовують файл cookie `auth_token`
- Для входу використовується збережений хеш пароля; резервний варіант — `INITIAL_PASSWORD`
- Параметр `requireLogin` можна перемикати через `/api/settings/require-login`
- Маршрути `/v1/*` за потреби вимагають API-ключ Bearer, коли `REQUIRE_API_KEY=true`
- «токен керування» / «API-ключ з областю керування» в цьому довіднику означає один із типів, описаних у зазначеному посібнику, а не невизначений додатковий тип секрету

> **Критична зміна (v3.8.0)** — `/api/v1/agents/tasks/*` та кінцеві точки керування періодом очікування тепер вимагають **автентифікації керування** (файл cookie `auth_token` панелі керування або API-ключ з областю керування). Клієнти, які раніше викликали ці маршрути без автентифікації, отримуватимуть `401 Unauthorized`. Див. коміт `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
