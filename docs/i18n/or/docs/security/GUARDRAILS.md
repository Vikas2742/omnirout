ଗାର୍ଡରେଲ୍ସ OmniRoute ଏବଂ ଅପଷ୍ଟ୍ରିମ୍ ପ୍ରୋଭାଇଡରମାନଙ୍କ ମଧ୍ୟରେ ସୀମାରେ ସୁରକ୍ଷା, ନୀତି ଏବଂ ବିଷୟବସ୍ତୁ ରୂପାନ୍ତରଣ ଲାଗୁ କରେ। ପ୍ରତ୍ୟେକ ଗାର୍ଡରେଲ୍ ଅନୁରୋଧ ପେଲୋଡ୍ (`preCall`) ଏବଂ ଅପଷ୍ଟ୍ରିମ୍ ପ୍ରତିକ୍ରିୟା (`postCall`) ଯାଞ୍ଚ କରିପାରେ (ଏବଂ ଇଚ୍ଛାଧୀନ ଭାବରେ ପ୍ରତ୍ୟାଖ୍ୟାନ, ରୂପାନ୍ତର କିମ୍ବା ଟୀକା କରିପାରେ)।

ସିଷ୍ଟମ୍ **ଫେଲ୍-ଓପେନ୍**: ଯଦି ଏକ ଗାର୍ଡରେଲ୍ ଚାଲିବା ସମୟରେ ତ୍ରୁଟି ଫିଙ୍ଗେ, ରେଜିଷ୍ଟ୍ରି ତ୍ରୁଟି ରେକର୍ଡ କରେ ଏବଂ ଅନୁରୋଧକୁ ବିଫଳ କରିବା ପରିବର୍ତ୍ତେ ପରବର୍ତ୍ତୀ ଗାର୍ଡରେଲ୍ ସହିତ ଆଗକୁ ବଢ଼େ। ବ୍ଲକିଂ ଏକ ସ୍ପଷ୍ଟ ନିଷ୍ପତ୍ତି (`block: true`), କେବେ ଆକସ୍ମିକ ନୁହେଁ। ଏକମାତ୍ର ବ୍ୟତିକ୍ରମ ହେଉଛି ଏକ ବାତିଲ୍ ଅନୁରୋଧ: ଯେତେବେଳେ କଲରଙ୍କ `signal` ବାତିଲ୍ ହୁଏ, ତ୍ରୁଟି ଫିଙ୍ଗୁଥିବା ଗାର୍ଡରେଲ୍ ଛାଡ଼ିଦିଆଯିବା ପରିବର୍ତ୍ତେ ହୁକ୍ ରନ୍କୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ।

ହୁକ୍ସଗୁଡ଼ିକ **ପ୍ରତ୍ୟେକ** ରୁଟ୍ କିମ୍ବା ପ୍ରତ୍ୟେକ ପ୍ରତିକ୍ରିୟାରେ ଚାଲନ୍ତି ନାହିଁ। ଏକ ଗାର୍ଡରେଲ୍କୁ ସୁରକ୍ଷା ନିୟନ୍ତ୍ରଣ ଭାବରେ ବିଶ୍ୱାସ କରିବା ପୂର୍ବରୁ [କଭରେଜ୍ ଏବଂ ସୀମା](#coverage-and-limits) ପଢ଼ନ୍ତୁ।

### ଭିଜନ୍ ବ୍ରିଜ୍ (`visionBridge.ts`) — ମୋଡାଲିଟି ବ୍ରିଜ୍ PR-1

GLM 5.3 ବେସ୍ ମଡେଲ୍ ଏବଂ `glm-5.3-{low,high,max}` ସ୍ପଷ୍ଟ `supportsVision:false`
ରେଜିଷ୍ଟ୍ରି/ସ୍ପେକ୍ ମେଟାଡାଟା ରଖେ। GLM 5.3 Flash ପ୍ରକାରଗୁଡ଼ିକ ନେଟିଭ୍-ଭିଜନ୍ ମଡେଲ୍
ଭାବରେ ରହିଥାନ୍ତି। Claude Codeର `/v1/messages` ରୁଟ୍ Claude-ରୁ-OpenAI
ଅନୁବାଦର **ପୂର୍ବରୁ** ସେୟାର କରାଯାଇଥିବା `handleChat` ପ୍ରି-କଲ୍ ଗାର୍ଡରେଲ୍ ଚେନ୍ରେ ପ୍ରବେଶ କରେ;
ନେଷ୍ଟେଡ୍ `Read` ଟୁଲ୍-ଫଳାଫଳ ଚିତ୍ରଗୁଡ଼ିକୁ ସେହି ଅନୁବାଦ ସେଗୁଡ଼ିକୁ OpenAI `image_url` ବିଷୟବସ୍ତୁକୁ
ଉଠାଇବା ପୂର୍ବରୁ ବର୍ଣ୍ଣନା କରାଯିବା କିମ୍ବା ପରିଚାଳନା କରାଯିବା ଆବଶ୍ୟକ (#17069)।

**ଅଣ-ଭିଜନ୍ ମଡେଲ୍** ପାଇଁ ଲକ୍ଷ୍ୟ କରାଯାଇଥିବା ଚିତ୍ର-ଧାରୀ ଅନୁରୋଧଗୁଡ଼ିକୁ ଇଣ୍ଟରସେପ୍ଟ କରେ ଏବଂ ହୁଏ ପୂରା ଅନୁରୋଧକୁ
ଭିଜନ୍-ସକ୍ଷମ ମଡେଲ୍କୁ ପୁନଃରୁଟ୍ କରେ କିମ୍ବା ଅପଷ୍ଟ୍ରିମ୍ କଲ୍ ପୂର୍ବରୁ କନଫିଗରେବଲ୍ ଭିଜନ୍ ମଡେଲ୍ ଦ୍ୱାରା ଉତ୍ପାଦିତ
ଟେକ୍ସଟ୍ ବର୍ଣ୍ଣନାରେ ଚିତ୍ର ଅଂଶଗୁଡ଼ିକୁ ବଦଳାଇଦିଏ। ଏହା ଟେକ୍ସଟ୍-ଓନ୍ଲି ପ୍ରୋଭାଇଡରମାନଙ୍କୁ ମଲ୍ଟିମୋଡାଲ୍
ପେଲୋଡ୍ଗୁଡ଼ିକୁ ସ୍ୱଚ୍ଛ ଭାବରେ ପରିଚାଳନା କରିବାକୁ ଦିଏ।

ପ୍ରବାହ:

1. ଯଦି ଟାର୍ଗେଟ୍ ମଡେଲ୍ ପୂର୍ବରୁ ଭିଜନ୍ ସମର୍ଥନ କରେ ତେବେ ଛାଡ଼ନ୍ତୁ (ଯଦି ଏହା ଫୋର୍ସଡ୍-ବ୍ରିଜ୍ ତାଲିକା
   `isVisionBridgeForcedModel` ରେ ନ ଥାଏ)।
2. `extractImageParts(messages)` (`visionBridgeHelpers.ts`) ମାଧ୍ୟମରେ ଚିତ୍ର ଅଂଶ ଏକ୍ସଟ୍ରାକ୍ଟ କରନ୍ତୁ, ଯାହା
   `open-sse/utils/mediaParts.ts` ରେ **ଏକୀକୃତ ମିଡିଆ ଡିଟେକ୍ଟର** `detectMediaParts()` କୁ
   ଡେଲିଗେଟ୍ କରେ — କମ୍ବୋ ସୁସଙ୍ଗତତା ଫିଲ୍ଟର ସହିତ ସେୟାର କରାଯାଇଥିବା ଏକକ ପ୍ରାମାଣିକ ଉତ୍ସ।
   ଏକ୍ସଟ୍ରାକ୍ସନ୍ ସେହି ଆକୃତିଗୁଡ଼ିକ ପାଇଁ ଅନୁମତିପ୍ରାପ୍ତ, ଯାହାକୁ `replaceImageParts` ପୁନଃ ସଂଯୋଗ କରିପାରେ
   (ଏକ୍ସଟ୍ରାକ୍ଟ↔ରିପ୍ଲେସ୍ ଚୁକ୍ତି): OpenAI `image_url`, Anthropic base64
   `source.type:"base64"`, Anthropic URL `source.type:"url"`, ଏବଂ Responses
   API `input_image`। Claude Code `tool_result.content` ଏବଂ Responses ଟୁଲ୍ ଆଉଟ୍ପୁଟ୍ସ
   ଭିତରେ ନେଷ୍ଟେଡ୍ ଥିବା ମେଳ ଖାଉଥିବା ଚିତ୍ରଗୁଡ଼ିକ ମଧ୍ୟ ଏକ୍ସଟ୍ରାକ୍ଟ ହୁଏ ଏବଂ ସେମାନଙ୍କ ମୂଳ ପଥରେ
   ବଦଳାଯାଏ; କେବଳ-ସୂଚକ ଆକୃତିଗୁଡ଼ିକ କମ୍ବୋ-ଫିଲ୍ଟର ସାମଗ୍ରୀ ଏବଂ ଏକ୍ସଟ୍ରାକ୍ଟ ହୁଏ ନାହିଁ।
   କିଛି ନ ମିଳିଲେ ଛାଡ଼ନ୍ତୁ।
3. `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`) ମାଧ୍ୟମରେ ରନ୍ଟାଇମ୍ କନଫିଗ୍ ନିର୍ଣ୍ଣୟ କରନ୍ତୁ: ନୂଆ
   `modalityBridge*` ସେଟିଂସ୍ କୀଗୁଡ଼ିକ ଅଗ୍ରାଧିକାର ପାଏ; ଲେଗାସି `visionBridge*` କୀଗୁଡ଼ିକ
   ଏକ **ଏକ-ଚକ୍ର ଫଲବ୍ୟାକ୍** (ରୋଲବ୍ୟାକ୍ ୱିଣ୍ଡୋ) ଭାବରେ ରହେ। ବ୍ରିଜ୍ ଅକ୍ଷମ ଥିଲେ କୌଣସି ମିଡିଆ
   ଟ୍ରାଭର୍ସାଲ୍ ପୂର୍ବରୁ ଛାଡ଼ନ୍ତୁ।
4. ମୋଡ୍ ସିଲେକ୍ଟର୍ (`modalityBridgeVisionMode`, ତଳ ତାଲିକା ଦେଖନ୍ତୁ) ପୁନଃରୁଟ୍ ବନାମ ବର୍ଣ୍ଣନା
   ନିର୍ଣ୍ଣୟ କରେ। ପୁନଃରୁଟ୍ କେବଳ `model` ବଦଳାଯାଇ `modifiedPayload` ଫେରାଏ, ସହିତ ମେଟା
   `{ rerouted, fromModel, toModel, imagesKept }`।
5. ବର୍ଣ୍ଣନା ପଥ: ଚିତ୍ରଗୁଡ଼ିକୁ `maxImages` ପର୍ଯ୍ୟନ୍ତ ସୀମିତ କରନ୍ତୁ, କାର୍ଯ୍ୟ-ସଚେତନ ପ୍ରମ୍ପ୍ଟ ରଚନା
   କରନ୍ତୁ, ବର୍ଣ୍ଣନା କ୍ୟାସ୍ ଦେଖନ୍ତୁ, ଭିଜନ୍ ମଡେଲ୍କୁ **ସମାନ୍ତରାଳ ଭାବରେ** (`Promise.allSettled`)
   କଲ୍ କରନ୍ତୁ, ଏବଂ ସେମାନଙ୍କ ସ୍ଥାନରେ `[Image N]: <description>` ଟେକ୍ସଟ୍ ଅଂଶ ଇଞ୍ଜେକ୍ଟ କରନ୍ତୁ।
   ବିଫଳ ବର୍ଣ୍ଣନା `null` ଦିଏ: ଅଜ୍ଞାତ/ଭିଜନ୍-ସକ୍ଷମ ଟାର୍ଗେଟଗୁଡ଼ିକ ପାଇଁ କଞ୍ଚା ଚିତ୍ର ସଂରକ୍ଷିତ ରହେ
   (#4012), କିନ୍ତୁ ଏକ **ନିଶ୍ଚିତ ଟେକ୍ସଟ୍-ଓନ୍ଲି ପ୍ରତ୍ୟକ୍ଷ ଟାର୍ଗେଟ୍** କିମ୍ବା ଶୂନ୍ୟ-ଭିଜନ୍ କମ୍ବୋ
   ପ୍ରତ୍ୟେକ ଅବର୍ଣ୍ଣିତ ଚିତ୍ର ପାଇଁ ଏକ ସ୍ପଷ୍ଟ
   `(unavailable — no vision-capable provider connected)` ଟେକ୍ସଟ୍ ଷ୍ଟବ୍ ପାଏ, ଯେଉଁଥିରେ
   ଆଂଶିକ ବିଫଳତା ଏବଂ ବର୍ଣ୍ଣନା-କଲ୍ ସୀମାର ଅତିରିକ୍ତ ଚିତ୍ରଗୁଡ଼ିକ ଅନ୍ତର୍ଭୁକ୍ତ (#17069)। ବିଦ୍ୟମାନ
   ସମସ୍ତ-ବିଫଳ କମ୍ବୋ ବର୍ଣ୍ଣନା ଫଲବ୍ୟାକ୍ ଯେପରି ଅଛି ସେପରି ରହେ (#8430)।
6. `modifiedPayload` + ମେଟା (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) ଫେରାନ୍ତୁ।

#### API-କୀ ସ୍କୋପ୍ (`visionBridgeKeyScope.ts`)

ଯେତେବେଳେ କଲରଙ୍କ API କୀ `allowedConnections`, କୋଟା ପୁଲ୍ (`allowedQuotas`) କିମ୍ବା ମଡେଲ (`allowedModels` / `blockedModels` / `modelAccessMode: "restricted"` / `disableNonPublicModels`) ପ୍ରତିବନ୍ଧିତ କରେ, ବ୍ରିଜ୍ କେବଳ ସେହି ରିରାଉଟ୍ ଏବଂ ବର୍ଣ୍ଣନା ମଡେଲ ବାଛେ ଯାହା କୀ ବ୍ୟବହାର କରିପାରେ, ସେହି ସଂଯୋଗଗୁଡ଼ିକରେ ଯାହା କୀ ବ୍ୟବହାର କରିପାରେ। ତା'ପରେ ବର୍ଣ୍ଣନା କଲ୍ ସର୍ବଦା `x-omniroute-self-loop-key-id` ହେଡର ସହିତ OmniRoute ଆତ୍ମ-ଲୁପ୍ ମାଧ୍ୟମରେ ଯାଏ, ତେଣୁ ଗ୍ରହଣକାରୀ ଚାଟ୍ ଅନୁରୋଧ ସେହି କୀର ସଂଯୋଗ ଏବଂ ମଡେଲ ନୀତିକୁ ପୁନର୍ବାର ଲାଗୁ କରେ। `enforceApiKeyPolicy()` ସେହି ହେଡରକୁ କେବଳ ଆତ୍ମ-ଲୁପ୍ ବିଅରର ସହିତ ସମ୍ମାନ କରେ, ତେଣୁ ଏହା କେବଳ ପ୍ରବେଶକୁ ସଙ୍କୁଚିତ କରିପାରେ, ଏବଂ ଏକ id ଯାହା ସମାଧାନ ହୁଏ ନାହିଁ ତାହା ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଏ।

ଯଦି କୀ ପାଇଁ କୌଣସି ଭିଜନ୍ ମଡେଲ ଅନୁମତିପ୍ରାପ୍ତ ନଥାଏ, ଏକ **ନିଶ୍ଚିତ କେବଳ-ଟେକ୍ସଟ୍ ଟାର୍ଗେଟ** ଅକ୍ଷମ ଅପଷ୍ଟ୍ରିମକୁ ଇମେଜ୍ ବାଇଟ୍ ଫରୱାର୍ଡ କରିବା ପରିବର୍ତ୍ତେ ସ୍ପଷ୍ଟ HTTP 400 ସହିତ ସ୍ଥାନୀୟ ଭାବରେ ଇମେଜ୍ ଅନୁରୋଧକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ (#17069)। ଅଜ୍ଞାତ କିମ୍ବା ନେଟିଭ୍ ଭିଜନ୍ ସାମର୍ଥ୍ୟ ଥିବା ଟାର୍ଗେଟଗୁଡ଼ିକ ପାଇଁ, ବର୍ଣ୍ଣନା ପଥ ଏହାର ପୂର୍ବ ଫେଲ୍-ଓପନ୍ ଆଚରଣ ବଜାୟ ରଖେ (ମେଟା `{ skipped: true, reason: "no_permitted_vision_model" }`)। କୀ ବିନା ଅନୁରୋଧ, ଏବଂ ଏହି ପ୍ରତିବନ୍ଧନ ବିନା କୀ, ପୂର୍ବ ପରି ସମାନ ଭାବରେ ଆଚରଣ କରେ।

#### ଟାସ୍କ-ସଚେତନ ବର୍ଣ୍ଣନା ପ୍ରମ୍ପ୍ଟ୍ (`modalityBridgeVisionTaskAware`)

ଡିଫଲ୍ଟ **true**। `composeVisionPrompt()` (`visionBridgeHelpers.ts`) **ଶେଷ ଉପଭୋକ୍ତା ସନ୍ଦେଶ**ର ଟେକ୍ସଟ୍ (500 ଅକ୍ଷରରେ ଛୋଟ କରାଯାଇ) ମୂଳ ବର୍ଣ୍ଣନା ପ୍ରମ୍ପ୍ଟ୍ରେ ଯୋଡ଼େ, ବର୍ଣ୍ଣନାକୁ ଉପଭୋକ୍ତା ପ୍ରକୃତରେ କଣ ପଚାରିଥିଲେ ସେଆଡ଼କୁ ନିର୍ଦ୍ଦେଶିତ କରେ (codex-vision-proxy ପ୍ୟାଟର୍ନ) ଏବଂ ଭିଜନ୍ ମଡେଲକୁ ଦୃଶ୍ୟମାନ ଟେକ୍ସଟ୍ ଟ୍ରାନ୍ସକ୍ରାଇବ୍ କରିବାକୁ କହେ। ଫ୍ଲାଗ୍ ବନ୍ଦ ଥିଲେ — କିମ୍ବା କୌଣସି ଉପଭୋକ୍ତା ଟେକ୍ସଟ୍ ନଥିଲେ — ମୂଳ ପ୍ରମ୍ପ୍ଟ୍ ଅପରିବର୍ତ୍ତିତ ଭାବରେ ବ୍ୟବହୃତ ହୁଏ।

ବର୍ଣ୍ଣନା ଆତ୍ମ-ଲୁପ୍ର ନିଜସ୍ୱ OpenAI-ସୁସଙ୍ଗତ ଅନୁରୋଧ (`visionBridgeHelpers.ts` ରେ `callVisionModelSingle()`) ସର୍ବଦା `image_url.detail: "high"` ଅନୁରୋଧ କରେ — ଅବିଚାରିତ ଭାବରେ, ପ୍ରତ୍ୟେକ କଲର/ପ୍ରୋଭାଇଡର୍ ପାଇଁ, କୌଣସି କ୍ଲାଏଣ୍ଟ ସିଗ୍ନାଲରେ ଗେଟେଡ୍ ନୁହେଁ। ନିମ୍ନ-ବିବରଣୀ ସାମ୍ପଲିଂ OCR ସଠିକତାକୁ ଅବକ୍ଷୟ କରେ ଠିକ୍ ସେହି ଟେକ୍ସଟ୍-ଟ୍ରାନ୍ସକ୍ରିପସନ୍ କାର୍ଯ୍ୟ ପାଇଁ ଯାହା ଏହି ପ୍ରମ୍ପ୍ଟ୍ ମାଗେ, ତେଣୁ ବର୍ଣ୍ଣନା କଲ୍ ନିଜେ ସର୍ବଦା ଉଚ୍ଚ ବିବରଣୀ ମାଗେ ମୂଳ ଇନବାଉଣ୍ଡ ଅନୁରୋଧ ଯେକୌଣସି ବିବରଣୀ ସ୍ତର ବ୍ୟବହାର କରିଥାଉ ନା କାହିଁକି। ଏହା କେବଳ ଆଭ୍ୟନ୍ତରୀଣ ବର୍ଣ୍ଣନା ଅନୁରୋଧ ବଡି ଉପରେ ପ୍ରଭାବ ପକାଏ; ଏହା ପରିବର୍ତ୍ତନ କରେ ନାହିଁ ଯେ OmniRoute ପ୍ରାଥମିକ ଅନୁରୋଧରେ କଲରଙ୍କ ନିଜସ୍ୱ `image_url.detail` କିପରି ଫରୱାର୍ଡ କରେ — ସେହି ଡିଫଲ୍ଟ ଅଲଗା ଭାବରେ ଲାଗୁ ହୁଏ, ଏବଂ କେବଳ ଚିହ୍ନଟ ହୋଇଥିବା OpenCode କ୍ଲାଏଣ୍ଟ ପାଇଁ, `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) ରେ। ବର୍ଣ୍ଣନା ଆତ୍ମ-ଲୁପ୍ର Anthropic ୱାୟାର୍-ଫର୍ମାଟ୍ ଶାଖାରେ `detail` ଫିଲ୍ଡ ନାହିଁ ଏବଂ ଉଭୟ ଡିଫଲ୍ଟରୁ ପ୍ରଭାବିତ ନୁହେଁ।

| `modalityBridgeVisionMaxChars` | `0`    | `0` କିମ୍ବା 100–50000 |

`0` (ଡିଫଲ୍ଟ) ଅର୍ଥ **କୌଣସି କ୍ୟାପ୍ ନାହିଁ** — `callVisionModel()` ଦ୍ୱାରା ଫେରାଇଦିଆଯାଇଥିବା ବର୍ଣ୍ଣନା ଅପରିବର୍ତ୍ତିତ ଭାବରେ ପାସ୍ ହୁଏ, ବିଦ୍ୟମାନ ଆଚରଣ ସଂରକ୍ଷଣ କରେ। 100–50000 ପରିସରରେ ଥିବା ଯେକୌଣସି ମୂଲ୍ୟ ବର୍ଣ୍ଣନାକୁ `…` ସଫିକ୍ସ ସହିତ ଛୋଟ କରେ `[Image N]: <description>` ଭାବରେ ପୁନଃ ସ୍ପ୍ଲାଇସ୍ ହେବା ପୂର୍ବରୁ (`src/lib/guardrails/visionBridge.ts` ରେ `VisionBridgeGuardrail.preCall()`)। ବିବରଣୀ-ଭାରୀ OCR କାର୍ଯ୍ୟ ପାଇଁ ଏହାକୁ ବଢ଼ାନ୍ତୁ ଯେଉଁଠାରେ ଡାଉନଷ୍ଟ୍ରିମ୍ ମଡେଲକୁ ସମ୍ପୂର୍ଣ୍ଣ ଟ୍ରାନ୍ସକ୍ରିପସନ୍ ଆବଶ୍ୟକ; ଚାଟି ଭିଜନ୍ ମଡେଲରେ ଟୋକେନ୍ ବ୍ୟବହାରକୁ ସୀମିତ କରିବାକୁ ଏହାକୁ କମାନ୍ତୁ। ଡାସବୋର୍ଡ ଫିଲ୍ଡ Vision ଟ୍ୟାବ୍ର Advanced ପ୍ୟାନେଲରେ ଅଛି (`ModalityBridgeVisionTab.tsx` ରେ `modality-bridge-max-chars`) ଏବଂ 1 ରୁ 99 ମଧ୍ୟରେ ଥିବା ଯେକୌଣସି ମୂଲ୍ୟକୁ 100 ଫ୍ଲୋରକୁ କ୍ଲାମ୍ପ୍ କରେ ଯେତେବେଳେ ଏକ ସ୍ପଷ୍ଟ `0` ଅସ୍ପୃଶ୍ୟ ରଖେ — `0` ନିଜ ଅଧିକାରରେ ଏକ ବୈଧ Zod ମୂଲ୍ୟ (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), କେବଳ "ଅନସେଟ୍" ଡିଫଲ୍ଟ ନୁହେଁ।

#### ବର୍ଣ୍ଣନା କ୍ୟାଚ୍ (`modalityBridge/bridgeCache.ts`)

ବର୍ଣ୍ଣନା ଆଉଟପୁଟ୍ ପାଇଁ ଇନ୍-ମେମୋରୀ LRU + TTL କ୍ୟାଚ୍, ପ୍ରକ୍ରିୟା-ବ୍ୟାପୀ ଅଂଶୀଦାର। କୀ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` ଲମ୍ବ-ପ୍ରିଫିକ୍ସ ଫ୍ରେମିଂ ସହିତ (କୌଣସି ଫିଲ୍ଡ-ସୀମା ଧକ୍କା ନାହିଁ)। ମଡେଲ ଉପାଦାନ ହେଉଛି **କନଫିଗର୍ ହୋଇଥିବା** ବ୍ରିଜ୍ ମଡେଲ, ପ୍ରକୃତରେ ଉତ୍ତର ଦେଇଥିବା ମଡେଲ ନୁହେଁ — `callVisionModel` ଆଭ୍ୟନ୍ତରୀଣ ଭାବରେ ଫଲବ୍ୟାକ୍ କରିପାରେ, ଏବଂ ପ୍ରତି ପ୍ରୟାସ ପାଇଁ କୀ ଦେବା କ୍ୟାଚ୍କୁ ବିଖଣ୍ଡିତ କରିବ। ବିଫଳ ବର୍ଣ୍ଣନାଗୁଡ଼ିକ କେବେ କ୍ୟାଚ୍ ହୁଏ ନାହିଁ। ସେଟିଂସ:

| କୀ                              | ଡିଫଲ୍ଟ | ପରିସର   |
| ------------------------------- | ------ | ------- |
| `modalityBridgeCacheEnabled`    | `true` | —       |
| `modalityBridgeCacheTtlMinutes` | `60`   | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`  | 10–5000 |

#### ରିମୋଟ୍ ଇମେଜ୍ ସାମାନ୍ୟୀକରଣ (ସେଲ୍ଫ-ଲୁପ୍ ଡିସ୍କ୍ରାଇବ/ବେସ୍64 ଫେଚ୍)

ଯେତେବେଳେ ବ୍ରିଜ୍ ନିଜେ ଏକ **ରିମୋଟ୍** ଇମେଜ୍ ଫେଚ୍ କରେ — Anthropic describe self-call ଏବଂ claude-wire-format base64 ରୂପାନ୍ତର (`ensureBase64ImagesForClaudeWire`), ଉଭୟ `visionBridgeHelpers.ts` ରେ `fetchRemoteImageAsDataUri()` ମାଧ୍ୟମରେ — ଫଳସ୍ୱରୂପ data URI ଭିଜନ୍-ମଡେଲ୍ ଅନୁରୋଧରେ ସନ୍ନିବେଶ ହେବା ପୂର୍ବରୁ `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) ମାଧ୍ୟମରେ ପଠାଯାଏ। ଅତି ବଡ଼ ଇମେଜଗୁଡ଼ିକ **2048px long edge** କୁ ଡାଉନସ୍କେଲ୍ କରାଯାଏ (OpenAI/Anthropic ପୂର୍ବରୁ ସର୍ଭର-ପାର୍ଶ୍ୱରେ ଲଗାଉଥିବା resize cap ସହ ମେଳ ଖାଉଥାଏ), ଯାହା ଅପଲୋଡ୍ ବାଇଟ୍/ଲେଟେନ୍ସି କମାଏ, କିନ୍ତୁ ଭିଜନ୍ ମଡେଲ୍ ଯାହା ଦେଖେ ତାହା ବଦଳାଏ ନାହିଁ। ରିସାଇଜିଂ `sharp` ବ୍ୟବହାର କରେ, ଯାହା dynamic import ମାଧ୍ୟମରେ ଲୋଡ୍ ହୁଏ: ଯେଉଁ ପ୍ଲାଟଫର୍ମରେ ଏହାର native binary ଲୋଡ୍ ହେବାରେ ବିଫଳ ହୁଏ, ସେଠାରେ `normalizeDataUri()` **କେବେ ବି throw କରେ ନାହିଁ** — ଏହା ମୂଳ ବାଇଟଗୁଡ଼ିକର passthrough କୁ ଫେରିଯାଏ, ତେଣୁ describe/base64-conversion ପଥ ସର୍ବଦା କାର୍ଯ୍ୟକ୍ଷମ ରହେ। ଅଣ-ଇମେଜ୍ ବାଇଟ୍ (ଏକ fetch ଯାହା ଡିକୋଡେବଲ୍ ଇମେଜ୍ ଫେରାଇ ନାହିଁ) ମଧ୍ୟ ଅସ୍ପୃଶିତ ଭାବରେ ପଠାଯାଏ। ଏହି ସାମାନ୍ୟୀକରଣ କେବଳ ବ୍ରିଜ୍ ନିଜର self-call ପାଇଁ ଫେଚ୍ କରୁଥିବା ଇମେଜଗୁଡ଼ିକ ପାଇଁ ସୀମିତ — ଏହା କଲରଙ୍କ raw passthrough payload ଉପରେ କେବେ ବି ପ୍ରୟୋଗ ହୁଏ ନାହିଁ, ଯାହା କେବଳ opt-in ମ୍ୟୁଟେସନ୍ ନୀତି (Hard Rule #20) ସହ ସଙ୍ଗତ।

#### ସେଟିଂସ୍ ସ୍କିମା + ମାଇଗ୍ରେସନ୍

ନୂତନ `modalityBridge*` କୀଗୁଡ଼ିକ `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`) ରେ Zod-ଦ୍ୱାରା ବୈଧତା ଯାଞ୍ଚ ହୁଏ: `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCache*` ତିନୋଟି, ଏବଂ Audio Bridge ଦ୍ୱାରା ବ୍ୟବହୃତ `modalityBridgeAudio*` ଗ୍ରୁପ୍। ମାଇଗ୍ରେସନ୍ `141_modality_bridge_settings.sql` ବିଦ୍ୟମାନ ଲିଗାସି `visionBridge*` ମୂଲ୍ୟଗୁଡ଼ିକୁ ମେଳ ଖାଉଥିବା ନୂତନ କୀଗୁଡ଼ିକୁ କପି କରେ (idempotent, ଅପରେଟର-ସେଟ୍ `modalityBridge*` ମୂଲ୍ୟକୁ କେବେ ବି ଓଭରରାଇଟ୍ କରେ ନାହିଁ); ଲିଗାସି କୀଗୁଡ଼ିକ ଏକ release cycle ପାଇଁ read fallback ଭାବରେ ଗ୍ରହଣ କରାଯାଇ ରହେ।

#### ସ୍ୱଚ୍ଛତା ହେଡର୍ + ପରିସଂଖ୍ୟାନ

Describe-ରୂପାନ୍ତରିତ ପ୍ରତିକ୍ରିୟାଗୁଡ଼ିକ `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` ବହନ କରେ (`modalityBridge/bridgeStats.ts` ରେ `buildModalityBridgeHeader()` ଦ୍ୱାରା ନିର୍ମିତ, `src/sse/handlers/chatHelpers.ts` ରେ `withModalityBridgeHeader()` ଦ୍ୱାରା ସ୍ଟାମ୍ପ୍ କରାଯାଏ)। Reroute ହୋଇଥିବା ଅନୁରୋଧଗୁଡ଼ିକୁ **କୌଣସି** ହେଡର୍ ମିଳେ ନାହିଁ — payload ଅସ୍ପୃଶିତ ଥିଲା ଏବଂ ମଡେଲ୍ ସ୍ୱାପ୍ ପ୍ରତିକ୍ରିୟା ବଡିର `model` ଫିଲ୍ଡରେ ପୂର୍ବରୁ ଦୃଶ୍ୟମାନ ଅଛି।

`GET /api/modality-bridge/stats` (ମ୍ୟାନେଜମେଣ୍ଟ auth, `GET /api/settings` ସହ ସମାନ tier) `vision`, `audio`, ଏବଂ `video` ପାଇଁ ଇନ୍-ମେମୋରୀ per-modality counters `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` ଫେରାଏ। `averageLatencyMs` ର ହରଣକାରୀ ଭାବରେ ସମସ୍ତ ପ୍ରୟାସ ନୁହେଁ, `latencySamples` ବ୍ୟବହାର କରେ; ସମୟ-ମାପ ନଥିବା କାର୍ଯ୍ୟ ଏକ zero-millisecond sample ତିଆରି କରେ ନାହିଁ। `bridged` ସଫଳ ରୂପାନ୍ତର ପାଇଁ ପଛୁଆ-ସଙ୍ଗତ alias ଭାବରେ ରହେ; ବିଫଳ ପ୍ରୟାସଗୁଡ଼ିକ ଏହାକୁ ବଢ଼ାଏ ନାହିଁ। ପ୍ରକ୍ରିୟା restart ହେଲେ counters ଡିଜାଇନ୍ ଅନୁସାରେ ରିସେଟ୍ ହୁଏ (ଟେଲିମେଟ୍ରି, ଆକାଉଣ୍ଟିଂ ନୁହେଁ)।

#### ଡ୍ୟାସବୋର୍ଡ କନଫିଗୁରେସନ୍

ସମର୍ପିତ ଡ୍ୟାସବୋର୍ଡ ପୃଷ୍ଠା ହେଉଛି `/dashboard/settings/modality-bridge`। ଏହାର URL-ଦ୍ୱାରା ଠିକଣା କରାଯାଇପାରୁଥିବା `Vision`, `Audio`, ଏବଂ `Video` ଟ୍ୟାବଗୁଡ଼ିକ `tab` ମୂଲ୍ୟ ବଦଳାଇବା ସମୟରେ query parameters ସଂରକ୍ଷିତ ରଖେ। Vision ଟ୍ୟାବ enablement, mode, model selection (ସ୍ୱଚାଳିତ default ସହିତ), task-aware prompting, ଉନ୍ନତ timeout/ଇମେଜ୍/ବର୍ଣ୍ଣନା-ଲମ୍ବା/cache ସୀମା, runtime counters, ଏବଂ ଏକ ସୁରକ୍ଷିତ sample request ପ୍ରଦର୍ଶନ କରେ। Audio ଟ୍ୟାବ ମଧ୍ୟ ସକ୍ରିୟ: ଏହା enablement, Auto ସହିତ STT-only model picker, timeout/max-clip ସୀମା, audio counters, ଏବଂ `input_audio` sample test ପ୍ରଦର୍ଶନ କରେ। Video ଟ୍ୟାବ କାର୍ଯ୍ୟକ୍ଷମ: ଏହା FFmpeg/ffprobe runtime ସ୍ଥିତି ରିପୋର୍ଟ କରେ — ଚାରିଟି ସ୍ପଷ୍ଟ UI ସ୍ଥିତି ମଧ୍ୟରୁ ଗୋଟିଏ (`unknown` ଯେତେବେଳେ probe ଚାଲୁଥାଏ କିମ୍ବା ସମ୍ପୂର୍ଣ୍ଣ ହୋଇପାରିଲା ନାହିଁ, `restricted` ଏକ non-loopback dashboard host ଉପରେ ଯେଉଁଠାରେ probe client-sideରେ skip ହୁଏ, `unavailable` ଥରେ probe ହୋଇ ନାହିଁ ବୋଲି ନିଶ୍ଚିତ ହେଲେ, କିମ୍ବା `available` FFmpeg/ffprobe ସଂସ୍କରଣ ସହିତ) — enable/model/frame/video/timeout ସୀମାଗୁଡ଼ିକୁ ସ୍ଥାୟୀ ଭାବରେ ସଂରକ୍ଷଣ କରେ, model picker କୁ vision-capable models ପାଇଁ ଫିଲ୍ଟର କରେ, ଏବଂ video counters ପ୍ରଦର୍ଶନ କରେ।

AI settings ଅଧୀନରେ ଥିବା ପୂର୍ବତନ Vision Bridge card ନୂତନ ପୃଷ୍ଠାକୁ ଏକ compatibility link; ଏହା ଆଉ ଫର୍ମର ଦ୍ୱିତୀୟ କପି ଧାରଣ କରେ ନାହିଁ। Media Providers ମଧ୍ୟ Image-to-Text ଏବଂ Speech-to-Text workflows କୁ ସମ୍ପୃକ୍ତ Modality Bridge tabs ସହିତ ଲିଙ୍କ୍ କରେ, ବିଦ୍ୟମାନ Speech-to-Text playground କୁ ହଟାଇ ନାହିଁ।

**ସେଲ୍ଫ-ଲୁପ୍ ଆଡମିଶନ୍ ବାଇପାସ୍:** ଯେତେବେଳେ describe call OmniRoute ର ନିଜ `/v1` ସେଲ୍ଫ-ଲୁପ୍ (ନନ୍-ଷ୍ଟାଣ୍ଡାର୍ଡ ପ୍ରୋଭାଇଡର୍ ମଡେଲ୍) ମାଧ୍ୟମରେ route ହୁଏ, ସେତେବେଳେ sub-request `x-omniroute-admission-bypass: internal` ପଠାଏ ଏବଂ resolved self-loop credential ସହିତ authenticate ହୁଏ — local mode ରେ local `sk_omniroute` sentinel, କିମ୍ବା ଅପରେଟର-କନଫିଗର୍ ହୋଇଥିବା `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env key (#1350), ଯାହାଫଳରେ `REQUIRE_API_KEY=true` deployments ମଧ୍ୟ describe call ଚଲାଇପାରିବେ। ବାଇପାସ୍ କେବଳ ସେହି ସଠିକ୍ credentials ପାଇଁ ମାନ୍ୟ ହୁଏ, ତେଣୁ ବାହ୍ୟ clients admission skip କରିବା ପାଇଁ header ବ୍ୟବହାର କରିପାରିବେ ନାହିଁ।

ଲିଗାସି defaults `src/shared/constants/visionBridgeDefaults.ts` ରେ ଅଛି; ନୂତନ mode/task-aware/cache defaults ଏବଂ ସେଟିଂସ୍ resolver `src/shared/constants/modalityBridgeDefaults.ts` ରେ ଅଛି। Guardrail ଏକ `deps` constructor option ପ୍ରଦାନ କରେ ଯାହାଫଳରେ tests fake `getSettings` ଏବଂ `callVisionModel` implementations inject କରିପାରିବେ।

### ଅଡିଓ ବ୍ରିଜ୍ (`audioBridge.ts`) — Modality Bridge PR-3

ଏହା audio-ଧାରଣକାରୀ chat requests କୁ ସେମାନେ audio input ଗ୍ରହଣ କରୁଥିବା ଜଣା ନଥିବା target ପାଖରେ ପହଞ୍ଚିବା ପୂର୍ବରୁ intercept କରେ। ଏହା chat request କୁ କେବେ ବି reroute କରେ ନାହିଁ: audio parts ବିଦ୍ୟମାନ OpenAI-compatible multipart endpoint ମାଧ୍ୟମରେ transcribe ହୁଏ ଏବଂ ଚୟନିତ chat model text transcripts ସହିତ ଆଗକୁ ବଢ଼େ।

ଫ୍ଲୋ:

1. `getResolvedModelCapabilities()` ମାଧ୍ୟମରେ `supportsAudio` ନିର୍ଣ୍ଣୟ କରନ୍ତୁ। ସ୍ପଷ୍ଟ ପ୍ରୋଭାଇଡର-ରେଜିଷ୍ଟ୍ରି ମେଟାଡାଟା ପ୍ରଥମେ ଜିତେ, ତାପରେ ସ୍ଥିର ମଡେଲ ମେଟାଡାଟା, ତାପରେ ସିଙ୍କ ହୋଇଥିବା `modalities_input`। `audio` ବିନା ଏକ ଘୋଷିତ ଇନପୁଟ ତାଲିକା `false`; କୌଣସି ସାମର୍ଥ୍ୟ ପ୍ରମାଣ ନଥିଲେ `null` ରହେ। `false` ଏବଂ `null` ଉଭୟ ରକ୍ଷଣଶୀଳ ବ୍ରିଜ୍ ସକ୍ରିୟ କରେ, ଯେତେବେଳେ `true` ଏହାକୁ ବାଇପାସ୍ କରେ।
2. `modalityBridgeAudio*` ସେଟିଂସମୂହ ନିର୍ଣ୍ଣୟ କରନ୍ତୁ ଏବଂ ସେୟାର୍ ହୋଇଥିବା `detectMediaParts()` ଡିଟେକ୍ଟର ମାଧ୍ୟମରେ ପ୍ରତ୍ୟେକ ମେସେଜରୁ ସ୍ପ୍ଲାଇସ୍ ଯୋଗ୍ୟ ଟପ୍-ଲେଭେଲ ଅଡିଓ ପାର୍ଟ ବାହାର କରନ୍ତୁ। ସମର୍ଥିତ ୱାୟାର ଆକୃତିଗୁଡ଼ିକ ହେଉଛି OpenAI `input_audio`, `audio_url`, ଏବଂ `source.media_type: "audio/*"`। ନେଷ୍ଟେଡ୍ ଅଡିଓ ରାଉଟିଂ ପାଇଁ ଚିହ୍ନଟ କରାଯାଏ କିନ୍ତୁ ସ୍ପ୍ଲାଇସ୍ ପାଥ୍ ଦ୍ୱାରା ଅପସାରିତ ହୁଏ ନାହିଁ। କାର୍ଯ୍ୟ `modalityBridgeAudioMaxClips` ଦ୍ୱାରା ସୀମିତ; ପରବର୍ତ୍ତୀ ପାର୍ଟଗୁଡ଼ିକ ଅସ୍ପୃଷ୍ଟ ରହେ।
3. ଏକ କନଫିଗର୍ ହୋଇଥିବା `provider/model` କୁ ସମ୍ମାନ କରନ୍ତୁ, କିମ୍ବା `selectAudioBridgeModel()` କୁ ସ୍ଥିର କାଟାଲଗ କ୍ରମରେ `AUDIO_TRANSCRIPTION_PROVIDERS` ମଧ୍ୟରେ ଗମନ କରିବାକୁ ଦିଅନ୍ତୁ ଏବଂ ବ୍ୟବହାରଯୋଗ୍ୟ ସକ୍ରିୟ ପ୍ରୋଭାଇଡର କ୍ରେଡେନସିଆଲ୍ ଥିବା ପ୍ରଥମ ମଡେଲ ଚୟନ କରନ୍ତୁ।
4. `callAudioTranscription()` base64/data-URI ଅଡିଓକୁ ଏକ ମଲ୍ଟିପାର୍ଟ `file` କୁ ରୂପାନ୍ତର କରେ, କିମ୍ବା DNS ପିନିଂ ଏବଂ 25 MB ସୀମା ସହିତ କେବଳ-ପବ୍ଲିକ୍ ଆଉଟବାଉଣ୍ଡ ଗାର୍ଡ ମାଧ୍ୟମରେ ଏକ ରିମୋଟ `audio_url` ଡାଉନଲୋଡ୍ କରେ। ଏହା ପରେ ସ୍ଥାନୀୟ `/v1/audio/transcriptions` ସେଲ୍ଫ-ଲୁପ୍କୁ ଫାଇଲ୍ ଏବଂ ଚୟନିତ ମଡେଲ POST କରେ, ଯାହା `resolveSelfLoopBearer()` ସହିତ ପ୍ରମାଣିତ ହୁଏ। ବିଦ୍ୟମାନ ଟ୍ରାନ୍ସକ୍ରିପସନ୍ ରୁଟ୍ ସ୍ୱାଭାବିକ କ୍ରେଡେନସିଆଲ୍ ଲୁକଅପ୍, କୁଲଡାଉନ୍/ରେଟ୍-ଲିମିଟ୍ ହ୍ୟାଣ୍ଡଲିଂ, ଏବଂ ପ୍ରୋଭାଇଡର ଡିସ୍ପାଚ୍ କରେ।
5. ସଫଳ କଲ୍ଗୁଡ଼ିକ ସେମାନଙ୍କ ପାର୍ଟଗୁଡ଼ିକୁ `[Audio N]: <transcript>` ସହିତ ବଦଳାଏ। କଲ୍ଗୁଡ଼ିକ `Promise.allSettled` ସହିତ ଚାଲେ: ଏକ ବ୍ୟକ୍ତିଗତ ବିଫଳତା ସେହି ମୂଳ ଅଡିଓ ପାର୍ଟକୁ ସଂରକ୍ଷିତ ରଖେ (#4012 ଚୁକ୍ତି)। ଯଦି ପ୍ରତ୍ୟେକ କଲ୍ ବିଫଳ ହୁଏ ଏବଂ ଲକ୍ଷ୍ୟ `supportsAudio === false` ପ୍ରମାଣିତ ହୁଏ, ପାର୍ଟଗୁଡ଼ିକ `[Audio N]: (unavailable — no STT provider connected)` ହୋଇଯାଏ (#8430 ଚୁକ୍ତି)। ଏକ ଅଜ୍ଞାତ ଲକ୍ଷ୍ୟ (`null`) ପାଇଁ, ସମସ୍ତ-ବିଫଳତା ଫଳାଫଳ ଅସ୍ପୃଷ୍ଟ ରହେ। ବ୍ୟବହାରଯୋଗ୍ୟ STT କ୍ରେଡେନସିଆଲ୍ ନଥିବା ଏକ ପ୍ରମାଣିତ କେବଳ-ଟେକ୍ସଟ୍ ଲକ୍ଷ୍ୟ ନେଟୱାର୍କ କଲ୍ ନକରି ସେହି ସ୍ପଷ୍ଟ ଷ୍ଟବ୍ ଗ୍ରହଣ କରେ।

ସଫଳ ଟ୍ରାନ୍ସକ୍ରିପ୍ଟଗୁଡ଼ିକ ପ୍ରୋସେସ୍-ୱାଇଡ୍ Modality Bridge LRU/TTL କ୍ୟାଚ୍ ବ୍ୟବହାର କରେ। କୀ ଅଡିଓ ରେଫରେନ୍ସ, ସ୍ଥିର `audio-transcription` ଅପରେସନ୍ ଲେବଲ୍, ଏବଂ ଚୟନିତ STT ମଡେଲକୁ ଏକତ୍ରିତ କରେ; ବିଫଳତାଗୁଡ଼ିକ କେବେ ବି କ୍ୟାଚ୍ ହୁଏ ନାହିଁ। ଅଡିଓ ପ୍ରୟାସଗୁଡ଼ିକ ସେୟାର୍ କରାଯାଇଥିବା `bridged`, `cacheHits`, `failures`, ଏବଂ `lastUsedAt` କାଉଣ୍ଟରଗୁଡ଼ିକୁ ଅପଡେଟ୍ କରେ। ରୂପାନ୍ତରିତ ପ୍ରତିକ୍ରିୟାଗୁଡ଼ିକ `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` ବହନ କରେ; ଅସ୍ପୃଷ୍ଟ ଅନୁରୋଧଗୁଡ଼ିକ ଏକ Audio Bridge ସେଗମେଣ୍ଟ ଗ୍ରହଣ କରେ ନାହିଁ।

ରନଟାଇମ୍ ସେଟିଂସମୂହ DB-ସମର୍ଥିତ ଏବଂ Zod-ଦ୍ୱାରା ବୈଧିକୃତ:

| ----------------------------- | ------- | ----------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —                 |
| `modalityBridgeAudioModel`    | `""`    | ଅଟୋ କିମ୍ବା STT ID |

ସେୟାର୍ କ୍ୟାଚ୍ `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, ଏବଂ `modalityBridgeCacheMaxEntries` ଦ୍ୱାରା ନିୟନ୍ତ୍ରିତ ରହେ।

### ଭିଡିଓ ବ୍ରିଜ୍ (`videoBridge.ts`, `videoBridgePipeline.ts`)

ଜ୍ଞାତ ନେଟିଭ୍ ଭିଡିଓ ସମର୍ଥନ ନଥିବା ଏକ ଲକ୍ଷ୍ୟ କଲ୍ ହେବା ପୂର୍ବରୁ Chat Completions `messages` ଏବଂ Responses API `input` ରେ ଟପ୍-ଲେଭେଲ ଭିଡିଓ ପାର୍ଟଗୁଡ଼ିକୁ ଇଣ୍ଟରସେପ୍ଟ କରେ। ସମର୍ଥିତ ଆକୃତିଗୁଡ଼ିକ ହେଉଛି `input_video`, `video_url`, `video_source`, HTTPS URL, ଏବଂ `data:video/*;base64,...` ଡାଟା URI। ଟେକ୍ସଟରେ ଥିବା ସାଧାରଣ ଫାଇଲନାମ ଭିଡିଓ ଭାବରେ ବିବେଚିତ ହୁଏ ନାହିଁ।

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) ଅନୁରୋଧ ଟ୍ରାଭର୍ସାଲ୍, ସାମର୍ଥ୍ୟ/ନୀତି ଯାଞ୍ଚ, ପ୍ରତି-ଅନୁରୋଧ ଏଗ୍ରିଗେସନ୍, ଏବଂ ପ୍ରତିକ୍ରିୟା ପେଲୋଡ୍ ର ମାଲିକାନା କରେ। ପ୍ରତି-ଭିଡିଓ କାର୍ଯ୍ୟ — ଅଧିଗ୍ରହଣ, ସମଗ୍ର-ଫଳାଫଳ କ୍ୟାଚ୍, ଏକ ଫ୍ରେମ୍ କ୍ରମର ବର୍ଣ୍ଣନା (ଯାହା କୌଣସି କଲର୍-ଘୋଷିତ ଅଡିଓ ଟ୍ରାନ୍ସକ୍ରିପ୍ଟକୁ ଫ୍ୟୁଜ୍ କରେ), ଏବଂ ପ୍ରତି-ପ୍ରୟାସ ମେଟ୍ରିକ୍ସ/ଆବର୍ଟ/କ୍ଲିନଅପ୍ — `videoBridgePipeline.ts` ରେ `processVideoPart` ପଛରେ ଲୁଚି ରହିଛି, ଯାହା `preCall` ର ଲୁପ୍ ଭିତରେ ପ୍ରତି ଭିଡିଓ ପାର୍ଟ ପାଇଁ ଥରେ କଲ୍ ହୁଏ। ସେହି ମଡ୍ୟୁଲ୍ ସ୍ପଷ୍ଟ ପୋର୍ଟ ସୀମାଗୁଡ଼ିକୁ ମଧ୍ୟ ପରିଭାଷିତ କରେ: `VideoMediaBrokerPort` (ବାଇଟ୍ ଅଧିଗ୍ରହଣ ଏବଂ ସାମ୍ପଲ୍ ହୋଇଥିବା ଫ୍ରେମ୍ ବାହାର କରିବା), `VideoAudioTranscriptionPort` (ଏକ କଲର୍-ଘୋଷିତ ଅଡିଓ ଟ୍ରାନ୍ସକ୍ରିପ୍ଟକୁ ସାମ୍ପଲ୍ ହୋଇଥିବା କ୍ୟାପସନ୍ ସହିତ ଫ୍ୟୁଜ୍ କରିବା), ଏବଂ `VideoDrilldownPort` (ଫ୍ରେମ୍ ଡ୍ରିଲ୍-ଡାଉନ୍ ପର୍ସିଷ୍ଟେନ୍ସ ସୀମା; ଏପର୍ଯ୍ୟନ୍ତ `processVideoPart` ରେ ୱାୟାର୍ ହୋଇନାହିଁ — ଆଜି କେବଳ ପୃଥକ `/api/modality-bridge/video/drilldown` ରୁଟ୍ ଡ୍ରିଲ୍-ଡାଉନ୍ ଏଣ୍ଟ୍ରିଗୁଡ଼ିକ ଲେଖେ)।

ପବ୍ଲିକ୍ `/v1` ଅନୁରୋଧ ପାଥ୍ କେବେ ବି ଏକ ସବ୍ପ୍ରୋସେସ୍ ଇମ୍ପୋର୍ଟ କିମ୍ବା ଇନଭୋକ୍ କରେ ନାହିଁ। ରିମୋଟ ଭିଡିଓଗୁଡ଼ିକ 50 MiB ସୀମା ଅଧୀନରେ ଡାଉନଲୋଡ୍ ହୁଏ; ଇନଲାଇନ୍ base64 ଭିଡିଓଗୁଡ଼ିକର ଏକ ରକ୍ଷଣଶୀଳ 36 MiB ଡିକୋଡେଡ୍ ପ୍ରତି-ଭିଡିଓ କ୍ୟାପ୍ ଥାଏ ଯାହା ଦ୍ୱାରା ମଡେଲ/ମେସେଜ/ଫ୍ରେମିଂ ଏନଭେଲପ୍ 50 MiB ର ପବ୍ଲିକ୍ JSON ଅନୁରୋଧ ପ୍ରବେଶ ସୀମା ଭିତରେ ରହିପାରେ। ଆଲୋକେସନ୍ ପୂର୍ବରୁ ଇନଲାଇନ୍ ଲମ୍ବ ଏବଂ ଡିକୋଡେଡ୍-ଆକାର ଆନୁମାନ ଯାଞ୍ଚ କରାଯାଏ। ପ୍ରାରମ୍ଭିକ ରିମୋଟ URL ଏବଂ ପ୍ରତ୍ୟେକ ରିଡାଇରେକ୍ଟରେ HTTPS ଆବଶ୍ୟକ, ଯାହା DNS ପିନିଂ ସହିତ ବିଦ୍ୟମାନ କେବଳ-ପବ୍ଲିକ୍ ଆଉଟବାଉଣ୍ଡ ଗାର୍ଡ ବ୍ୟବହାର କରେ। ଏହା ପରେ ବାଇଟଗୁଡ଼ିକ ସଠିକ୍ ଆଭ୍ୟନ୍ତରୀଣ `POST /api/modality-bridge/video/extract` ବ୍ରୋକର୍ ସୀମା ଅତିକ୍ରମ କରେ। ସେହି ରୁଟ୍ ଉଭୟ `LOCAL_ONLY` ଏବଂ `SPAWN_CAPABLE`, କେବଳ ଏକ ପ୍ରତି-ପ୍ରୋସେସ୍ ପ୍ରମାଣିତ, ବିଶ୍ୱସ୍ତ ଲୁପବ୍ୟାକ୍ ଅନୁରୋଧ ଗ୍ରହଣ କରେ, ଏବଂ କେବେ ବି URL, ଫାଇଲସିଷ୍ଟମ୍ ପାଥ୍, ଏକ୍ଜିକ୍ୟୁଟେବଲ୍, କିମ୍ବା ଆର୍ଗୁମେଣ୍ଟ ତାଲିକା ଗ୍ରହଣ କରେ ନାହିଁ। API ବଡି-ଆକାର ପାଇପଲାଇନ୍ ଏବଂ ହ୍ୟାଣ୍ଡଲରର ଇନକ୍ରିମେଣ୍ଟାଲ୍ ବଡି ରିଡର୍ ସ୍ୱତନ୍ତ୍ର ଭାବରେ 50 MiB ବ୍ରୋକର୍ ଇନପୁଟ୍ କ୍ୟାପ୍ ଲାଗୁ କରେ। ଏହାର ସୀମିତ କ୍ୟୁ ଏକ ସମୟରେ ଗୋଟିଏ ଏକ୍ସଟ୍ରାକସନ୍ ଚଲାଏ, ଚାରୀଟି ପେଣ୍ଡିଂ ଜବ୍ ଅନୁମତି ଦିଏ, ଏବଂ ପେଣ୍ଡିଂ ଇନପୁଟ୍କୁ 100 MiB ରେ ସୀମିତ ରଖେ।

ବ୍ରୋକର୍ ଭିତରେ, `ffprobe` ଏକ ଘରୋଇ ସ୍ଥାନୀୟ ଫାଇଲ୍ ପଢ଼େ; ସ୍ଥିର ଫର୍ମାଟ୍ ଅନୁମତି-ତାଲିକା ପ୍ଲେଲିଷ୍ଟ ଏବଂ ମେନିଫେଷ୍ଟ ଫର୍ମାଟ୍ଗୁଡ଼ିକୁ ବାଦ ଦିଏ। ଅନୁମତିପ୍ରାପ୍ତ MOV-ପରିବାର କଣ୍ଟେନର୍ଗୁଡ଼ିକ ପାଇଁ, ବାହ୍ୟ MOV ଡାଟା ରେଫରେନ୍ସଗୁଡ଼ିକ ଡିଫଲ୍ଟ ଭାବରେ ନିଷ୍କ୍ରିୟ ରହେ, ଏବଂ ସ୍ଥିର କମାଣ୍ଡ୍ ସେଗୁଡ଼ିକୁ ଅପ୍ଟ୍-ଇନ୍ କରେ ନାହିଁ। `ffprobe` ଏବଂ `ffmpeg` ଉଭୟ କେବଳ `file` ପ୍ରୋଟୋକଲ୍ ହ୍ୱାଇଟଲିଷ୍ଟ, ଗୋଟିଏ ଥ୍ରେଡ୍, ସ୍ଥିର ଆର୍ଗୁମେଣ୍ଟ୍ ଆରେ, କୌଣସି ଶେଲ୍ ନାହିଁ, ଏବଂ `PATH` ରୁ ରିଜୋଲ୍ଭ ହୋଇଥିବା ଏକ୍ଜିକ୍ୟୁଟେବ୍ଲ୍ଗୁଡ଼ିକ ବ୍ୟବହାର କରନ୍ତି। ସଂଲଗ୍ନ-ଚିତ୍ର କଭର୍ ଷ୍ଟ୍ରିମ୍ଗୁଡ଼ିକ ପ୍ଲେୟେବଲ୍ ପ୍ରାର୍ଥୀ ନୁହନ୍ତି। ସମସ୍ତ ପ୍ଲେୟେବଲ୍ ଷ୍ଟ୍ରିମ୍ ସୀମାଗୁଡ଼ିକୁ ପୂରଣ କରିବା ଆବଶ୍ୟକ, ଏବଂ ସ୍ପଷ୍ଟ ଡିଫଲ୍ଟ ଷ୍ଟ୍ରିମକୁ ନିର୍ଣ୍ଣାୟକ ସର୍ବନିମ୍ନ-ଇଣ୍ଡେକ୍ସ ଫଲବ୍ୟାକ୍ ପୂର୍ବରୁ ପ୍ରାଥମିକତା ଦିଆଯାଏ। ଭିଡିଓଗୁଡ଼ିକ 600 ସେକେଣ୍ଡ, ପ୍ରତି ଡାଇମେନ୍ସନ୍ 8,192 ପିକ୍ସେଲ୍, ଏବଂ 33,554,432 ଉତ୍ସ ପିକ୍ସେଲ୍ରେ ସୀମିତ। FFmpeg 1–16ଟି ମିଡ୍ପଏଣ୍ଟ JPEG ଫ୍ରେମ୍ ସାମ୍ପିଲ୍ କରେ, ଛୋଟ ଇନପୁଟ୍ଗୁଡ଼ିକୁ ଅପ୍ସ୍କେଲ୍ ନକରି ଲମ୍ବା ଧାରକୁ ସର୍ବାଧିକ 1,024 ପିକ୍ସେଲ୍କୁ ସ୍କେଲ୍ ଡାଉନ୍ କରେ, ଏବଂ କେବେ ବି URL ଗ୍ରହଣ କରେ ନାହିଁ। ସାମ୍ପଲିଂ ଡିଫଲ୍ଟ ଭାବରେ `uniform`। ବୈକଳ୍ପିକ `scene_aware` ଏବଂ ପରୀକ୍ଷାମୂଳକ `segment_aware` ନୀତିଗୁଡ଼ିକ ପୂର୍ବରୁ ବୈଧ ହୋଇଥିବା ସ୍ଥାନୀୟ ଷ୍ଟ୍ରିମ୍ ଉପରେ ଗୋଟିଏ ଅତିରିକ୍ତ ସ୍ଥିର FFmpeg ପାସ୍ କରନ୍ତି, ସୀମିତ `showinfo` ଦୃଶ୍ୟ ଟାଇମଷ୍ଟାମ୍ପ ଚୟନ କରନ୍ତି, ଏବଂ ଡିଟେକ୍ଟର ବିଫଳତା, ଟାଇମଆଉଟ୍, ବିକୃତ ଆଉଟ୍ପୁଟ୍, କିମ୍ବା ଖାଲି ପ୍ରାର୍ଥୀ ସେଟ୍ ଉପରେ ସେହି ସମାନ uniform ମିଡ୍ପଏଣ୍ଟ୍ଗୁଡ଼ିକୁ ନିର୍ଣ୍ଣାୟକ ଭାବରେ ଫଲବ୍ୟାକ୍ କରନ୍ତି। ସେଗମେଣ୍ଟ୍-ସଚେତନ ମୋଡ୍ ବୈଧ ହୋଇଥିବା ଦୃଶ୍ୟ ବ୍ୟବଧାନଗୁଡ଼ିକ ଅନୁପାତିକ ଭାବରେ ମିଡ୍ପଏଣ୍ଟ ନମୁନାଗୁଡ଼ିକୁ ଆବଣ୍ଟନ କରେ; ସେଗମେଣ୍ଟ୍-ସଚେତନ ପ୍ରମାଣ ଏବଂ ଫଲବ୍ୟାକ୍ ଆଚରଣ ତଳେ ବିସ୍ତୃତ ଅଛି। ପ୍ରତ୍ୟେକ ନୀତିରେ ଚୟନ ପରେ କଠିନ 16-ଫ୍ରେମ୍ ସୀମା ଲାଗୁ କରାଯାଏ। ଯେତେବେଳେ ଏକ scene-aware ଅନୁରୋଧରେ କେବଳ ଏକ-ଫ୍ରେମ୍ ବଜେଟ୍ ଥାଏ, ସେତେବେଳେ ଏହା ସକ୍ରିୟ ସମ୍ପୂର୍ଣ୍ଣ-ଭିଡିଓ କିମ୍ବା ଫୋକସ୍ ୱିଣ୍ଡୋର uniform ମିଡ୍ପଏଣ୍ଟ ବ୍ୟବହାର କରେ ଏବଂ `policyEffective: uniform` ରିପୋର୍ଟ କରେ: ଗୋଟିଏ ଚୟନିତ ଦୃଶ୍ୟ ଫ୍ରେମ୍ ଉଭୟ ସାମୟିକ ପ୍ରାନ୍ତକୁ ସଂରକ୍ଷଣ କରିପାରିବ ନାହିଁ। ଏକ କଲର୍ ବୈକଳ୍ପିକ ଭାବରେ ଏକ ସୀମିତ ଫୋକସ୍ ୱିଣ୍ଡୋ (`start`/`end` ସେକେଣ୍ଡ) ଦେଇପାରେ; ସୀମାଗୁଡ଼ିକ ମିଡିଆ ଅବଧିରେ କ୍ଲାମ୍ପ୍ ହୁଏ, ଓଲଟା କିମ୍ବା ଅସୀମିତ ୱିଣ୍ଡୋଗୁଡ଼ିକ ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଏ, ଏବଂ ସମସ୍ତ ସାମ୍ପଲିଂ ନୀତିଗୁଡ଼ିକ କେବଳ ସାମାନ୍ୟୀକୃତ ଅନ୍ତରାଳ ଭିତରେ ସମ୍ପାଦିତ ହୁଏ। ଫଳସ୍ୱରୂପ ୱିଣ୍ଡୋ ସାମ୍ପଲିଂ ମେଟାଡାଟା ଏବଂ ଅବିଶ୍ୱସ୍ତ ବର୍ଣ୍ଣନା ପ୍ରିଫିକ୍ସରେ ଅନ୍ତର୍ଭୁକ୍ତ କରାଯାଏ, ଯାହାଫଳରେ ଡାଉନ୍ଷ୍ଟ୍ରିମ୍ ମଡେଲଗୁଡ଼ିକ ଏକ ଫୋକସ୍ ଅଂଶକୁ ସମ୍ପୂର୍ଣ୍ଣ ସମୟରେଖାରୁ ପୃଥକ କରିପାରିବେ।

ସେମାଣ୍ଟିକ୍ କ୍ୟାପ୍ସନ୍ ଫୋକସ୍ ଏକ ପୃଥକ, ସ୍ପଷ୍ଟ ସେଟିଂ। ଡିଫଲ୍ଟ `full` ବିଶ୍ଳେଷଣ ମୋଡ୍ ବିଦ୍ୟମାନ ଫ୍ରେମ୍ ପ୍ରମ୍ପ୍ଟକୁ ସଂରକ୍ଷଣ କରେ ଏବଂ କେବେ ବି ଅନୁରୋଧ ପାଠ୍ୟକୁ କ୍ୟାପ୍ସନ୍ ମଡେଲକୁ ଫରୱାର୍ଡ କରେ ନାହିଁ। `focused` ମୋଡ୍ରେ, ବ୍ରିଜ୍ ସମାନ Chat କିମ୍ବା Responses କଣ୍ଟେନର୍ରୁ କେବଳ ନବୀନତମ ଅଣ-ଖାଲି ଉପଭୋକ୍ତା-ଲିଖିତ `text`/`input_text` ପଢ଼େ, ଏହାକୁ NFC କୁ ସାମାନ୍ୟୀକରଣ କରେ, ନିୟନ୍ତ୍ରଣ ଅକ୍ଷର ଏବଂ ୱାଇଟ୍ସ୍ପେସ୍ କୁ ସଂକୁଚିତ କରେ, ଏବଂ ଏହାକୁ 500 Unicode କୋଡ୍ ପଏଣ୍ଟରେ ସୀମିତ କରେ। ଏକ ଖାଲି ଫଳାଫଳ ସଠିକ୍ `full` ପ୍ରମ୍ପ୍ଟକୁ ଫଲବ୍ୟାକ୍ ହୁଏ। ଏକ ବ୍ୟବହାରଯୋଗ୍ୟ ସୂଚନା ସମର୍ପିତ ଅବିଶ୍ୱସ୍ତ-ଉପଭୋକ୍ତା-ପ୍ରସଙ୍ଗ ବ୍ଲକରେ JSON ଭାବରେ ସିରିଏଲାଇଜ୍ ହୁଏ ଏବଂ କେବଳ ପର୍ଯ୍ୟବେକ୍ଷଣଯୋଗ୍ୟ ବିବରଣୀଗୁଡ଼ିକୁ ପ୍ରାଥମିକତା ଦେଇପାରେ; ମିଡିଆରେ ଦୃଶ୍ୟମାନ କିମ୍ବା ଶ୍ରବଣଯୋଗ୍ୟ ନିର୍ଦ୍ଦେଶଗୁଡ଼ିକୁ ଅନୁସରଣ କରିବା ବିରୁଦ୍ଧରେ ଥିବା ପୃଥକ ଚେତାବନୀକୁ ଏହା ଅତିକ୍ରମ କରିପାରିବ ନାହିଁ। ପାଠ୍ୟ ଫୋକସ୍ କେବେ ବି `start`/`end` ଅନୁମାନ କରେ ନାହିଁ କିମ୍ବା ସାମୟିକ ସାମ୍ପଲର୍କୁ ପରିବର୍ତ୍ତନ କରେ ନାହିଁ।

#### FU-07 ସଂରଚନାତ୍ମକ ସେଗମେଣ୍ଟ୍ ପ୍ରମାଣ

`segment_aware` ପୂର୍ବରୁ ବୈଧ ହୋଇଥିବା ସ୍ଥାନୀୟ ଭିଡିଓ ଷ୍ଟ୍ରିମ୍ ଉପରେ ଗୋଟିଏ ସୀମିତ ପୂର୍ବ-ବିଶ୍ଳେଷଣ ପାସ୍ ବ୍ୟବହାର କରେ। ସ୍ଥିର ଫିଲ୍ଟର୍ ଚେନ୍ ପ୍ରଥମେ ସର୍ବାଧିକ 320 ପିକ୍ସେଲ୍ ଓସାରକୁ ସ୍କେଲ୍ କରେ, ଦୃଶ୍ୟ ପରିବର୍ତ୍ତନ ଏବଂ ସ୍ଥିର (frozen) ବ୍ୟବଧାନ ଚିହ୍ନଟ କରେ, ତାପରେ ବ୍ଲର୍, ହାରାହାରି ଲୁମା, ଏବଂ ସ୍ଥାନିକ/ସାମୟିକ ସୂଚନା ପାଇଁ ପ୍ରତି ସେକେଣ୍ଡକୁ 1 ଫ୍ରେମ୍ ହାରରେ ସାମ୍ପିଲ୍ କରେ। ଏହି ପାସ୍ 600 ସଂରଚନାତ୍ମକ ନମୁନା, ଗୋଟିଏ FFmpeg/ଫିଲ୍ଟର୍ ଥ୍ରେଡ୍, ସମାନ କେବଳ `file` ପ୍ରୋଟୋକଲ୍ ଏବଂ କଣ୍ଟେନର୍ ଅନୁମତି-ତାଲିକା, 1 MiB ପ୍ରୋସେସ୍-ଆଉଟ୍ପୁଟ୍ ସୀମା, ଏବଂ ବ୍ରୋକର୍ର ସାଝା abort/deadline ଭିତରେ ସର୍ବାଧିକ 30 ସେକେଣ୍ଡରେ ସୀମିତ। ଏହା ଅନୁରୋଧରୁ କମାଣ୍ଡ୍, ଫିଲ୍ଟର୍, ପାଥ୍, କିମ୍ବା URL କେବେ ବି ଗ୍ରହଣ କରେ ନାହିଁ।

ସଂରଚନାତ୍ମକ ମୂଲ୍ୟଗୁଡ଼ିକ ନିର୍ଣ୍ଣାୟକ ସାମ୍ପଲିଂ ପ୍ରମାଣ, ସେମାଣ୍ଟିକ୍ ଭିଡିଓ ବୁଝାମଣା ନୁହେଁ। ସେଗୁଡ଼ିକ ବିଷୟବସ୍ତୁ, କାର୍ଯ୍ୟ, କ୍ୟାପ୍ସନ୍, ବକ୍ତୃତା, କିମ୍ବା ଉପଭୋକ୍ତା ଉଦ୍ଦେଶ୍ୟ ଅନୁମାନ କରେ ନାହିଁ। ଦୃଶ୍ୟ ଏବଂ ଫ୍ରିଜ୍ ସୀମାଗୁଡ଼ିକ ସେଗମେଣ୍ଟ୍ ଗଠନ କରନ୍ତି; ଫ୍ରିଜ୍ କଭରେଜ୍, ବ୍ଲର୍, ଏକ୍ସପୋଜର୍, ସ୍ଥାନିକ ବିବରଣୀ, ଏବଂ ସାମୟିକ ପରିବର୍ତ୍ତନ କେବଳ ବିଦ୍ୟମାନ 1–16 ଫ୍ରେମ୍ ବଜେଟ୍ କିପରି ଆବଣ୍ଟିତ ହେବ ତାହା ପ୍ରଭାବିତ କରନ୍ତି। ସମ୍ପୂର୍ଣ୍ଣ ଫ୍ରିଜ୍ ହୋଇଥିବା ସେଗମେଣ୍ଟ୍ ଏକ ଫ୍ରେମରେ ସୀମିତ ଥାଏ, ଯେତେବେଳେ ଅଣ-ଫ୍ରିଜ୍ ସେଗମେଣ୍ଟଗୁଡ଼ିକ ଅବଶିଷ୍ଟ ବଜେଟ୍ ପାଇଁ ପ୍ରତିଦ୍ୱନ୍ଦ୍ୱିତା କରନ୍ତି। ଯେତେବେଳେ ସୀମାଗୁଡ଼ିକ ଫ୍ରେମଠାରୁ ଅଧିକ ସଂଖ୍ୟାରେ ଥାଏ, uniform ସମୟରେଖା କଭରେଜ୍ ସଂରକ୍ଷିତ ରହେ, ଯାହାଫଳରେ ପ୍ରାରମ୍ଭିକ ଦ୍ରୁତ କଟ୍ଗୁଡ଼ିକ ଏକ ଦୀର୍ଘ ଅନ୍ତିମ ସେଗମେଣ୍ଟକୁ ଲୁଚାଇପାରିବେ ନାହିଁ। ଏକ ଫ୍ରିଜ୍ ସୀମାର 1-ସେକେଣ୍ଡ ବିଶ୍ଳେଷଣ ରେଜୋଲ୍ୟୁଶନ୍ ଭିତରେ ଥିବା ଦୃଶ୍ୟ ସୀମାଗୁଡ଼ିକ ଏକତ୍ରିତ କରାଯାଏ।

ଅନୁପସ୍ଥିତ ଫିଲ୍ଟର୍, ବିକୃତ/ଖାଲି ପ୍ରମାଣ, ଡିଟେକ୍ଟର ତ୍ରୁଟି, କିମ୍ବା ସୀମିତ ପୂର୍ବ-ବିଶ୍ଳେଷଣ ଟାଇମଆଉଟ୍ ସଠିକ୍ uniform ମିଡ୍ପଏଣ୍ଟ ନୀତିକୁ ଫେଲ୍-ଓପନ୍ ହୁଏ। କଲର୍ abort କିମ୍ବା ବ୍ରୋକର୍ deadline ଫେଲ୍-ଓପନ୍ କରେ ନାହିଁ: ଏହା ଚାଲୁଥିବା ସବ୍ପ୍ରୋସେସ୍କୁ ସମାପ୍ତ କରେ, ପରବର୍ତ୍ତୀ ଫ୍ରେମ୍ ନିଷ୍କାସନକୁ ରୋକେ, ଏବଂ ବ୍ୟକ୍ତିଗତ ଅସ୍ଥାୟୀ ଟ୍ରିକୁ `finally` ରେ ଅପସାରଣ କରାଯାଏ।

ପ୍ରତ୍ୟେକ ଫ୍ରେମ୍ 4 MiB ପର୍ଯ୍ୟନ୍ତ ସୀମିତ, ସମସ୍ତ କଞ୍ଚା ଫ୍ରେମ୍ ଏକତ୍ର 23 MiB ପର୍ଯ୍ୟନ୍ତ, ଏବଂ ସିରିଆଲାଇଜ୍ ହୋଇଥିବା ବ୍ରୋକର୍ ପ୍ରତିକ୍ରିୟା 32 MiB ପର୍ଯ୍ୟନ୍ତ। ଏକ ଘରୋଇ ଅସ୍ଥାୟୀ ଡିରେକ୍ଟୋରୀ `finally` ରେ ଅପସାରିତ ହୁଏ। OmniRoute FFmpeg ବଣ୍ଡଲ୍ କରେ ନାହିଁ ଏବଂ ଏକ କଷ୍ଟମ୍ ଏକ୍ଜିକ୍ୟୁଟେବଲ୍ ପାଥ୍ ଗ୍ରହଣ କରେ ନାହିଁ। କ୍ୟାପ୍ସନିଂ ପୂର୍ବରୁ, ବ୍ରିଜ୍ ଏକ ରକ୍ଷଣଶୀଳ ଭିଜୁଆଲ୍ ଡିଡୁପ୍ଲିକେସନ୍ ପାସ୍ ଲଗାଏ: ପ୍ରତ୍ୟେକ JPEG ଏକ 16×16 ଗ୍ରେସ୍କେଲ୍ ବଫର୍କୁ ହ୍ରାସ କରାଯାଏ ଏବଂ କେବଳ ସର୍ବଶେଷରେ ଧରାଯାଇଥିବା ଫ୍ରେମ୍ ସହିତ ତୁଳନା କରାଯାଏ। ଗୋଟିଏ ଫ୍ରେମ୍ ଉପରେ ଅନୁରୋଧିତ କ୍ୟାପ୍ସନ୍ ବଜେଟ୍ ପାଇଁ, ଏକ୍ସଟ୍ରାକ୍ସନ୍ ସେହି ବଜେଟ୍ର ଦୁଇଗୁଣ ପର୍ଯ୍ୟନ୍ତ ଏବଂ 16 ଫ୍ରେମ୍ରୁ ଅଧିକ ନୁହେଁ ଏପରି ଏକ ସୀମିତ ପ୍ରାର୍ଥୀ ପୁଲ୍ ଯୋଗାଏ। ଅନୁରୋଧିତ କ୍ୟାପ୍ କେବଳ ଡିଡୁପ୍ଲିକେସନ୍ ପରେ ଲାଗୁ ହୁଏ, ଏବଂ ବଜେଟ୍ ଅନ୍ତତଃ ଦୁଇ ହେଲେ ଚୂଡ଼ାନ୍ତ ଥିନିଂ ସମୟରେ ପ୍ରଥମ ଓ ଅନ୍ତିମ ଚୟନିତ ପ୍ରାର୍ଥୀ ସଂରକ୍ଷିତ ରହନ୍ତି। ସଂସ୍କରଣଯୁକ୍ତ `grayscale-16x16-mean-cells-v2` ନୀତି ମିନ୍ ଲୁମା ଡେଲ୍ଟା ଏବଂ ଯେଉଁ ଥମ୍ବନେଲ୍ ସେଲ୍ଗୁଡ଼ିକର ସାମାନ୍ୟୀକୃତ ଡେଲ୍ଟା ଅନ୍ତତଃ 0.05 ସେମାନଙ୍କର ଅନୁପାତ ମଧ୍ୟରୁ ବଡ଼ଟି ବ୍ୟବହାର କରେ। ଡୁପ୍ଲିକେଟ୍ ଥ୍ରେସହୋଲ୍ଡ ସ୍ଥିର 0.04, ଯାହା ପୂର୍ବାନୁମାନଯୋଗ୍ୟତା ପାଇଁ ବଛାଯାଇଛି, ରନ୍ଟାଇମ୍ ସେଟିଂ ଭାବରେ ପ୍ରକାଶ କରାଯାଏ ନାହିଁ। ଏହି ଦ୍ୱିତୀୟକ ଉଚ୍ଚ-କଣ୍ଟ୍ରାସ୍ଟ ସିଗ୍ନାଲ୍ କ୍ଷୁଦ୍ର ଗତି ଏବଂ ଦୃଶ୍ୟମାନ-ପାଠ୍ୟ ପରିବର୍ତ୍ତନଗୁଡ଼ିକୁ ସଂରକ୍ଷିତ କରେ ଯାହା କେବଳ-ମିନ୍ ତୁଳନା ଲୁଚାଇପାରେ। ତୁଳନାକାରୀ କିମ୍ବା ଡିକୋଡର୍ ତ୍ରୁଟିଗୁଡ଼ିକ ଫେଲ୍ ଓପନ୍ ହୁଅନ୍ତି ଏବଂ କଭରେଜ୍ ବଜାୟ ରଖନ୍ତି। ଆଉଟପୁଟ୍ ମେଟାଡାଟା ଏକ୍ସଟ୍ରାକ୍ଟ ହୋଇଥିବା ପ୍ରାର୍ଥୀ, ସଫଳଭାବେ ବ୍ୟବହୃତ ଫ୍ରେମ୍, ଏବଂ ବାଦ ଦିଆଯାଇଥିବା ଭିଜୁଆଲ୍ ଡୁପ୍ଲିକେଟ୍ଗୁଡ଼ିକୁ ଅଲଗା କରେ।

ଏକ ସ୍ପଷ୍ଟଭାବେ ଚିହ୍ନିତ ଭିଡିଓ ଅଂଶ ଏକ ଟାଇମଷ୍ଟାମ୍ପଯୁକ୍ତ କଣ୍ଟାକ୍ଟ ସିଟ୍ ଅନୁରୋଧ କରିପାରେ। ବ୍ରିଜ୍ ସର୍ବାଧିକ 4-ସ୍ତମ୍ଭ, 16-ଫ୍ରେମ୍ JPEG ଗ୍ରିଡ୍ ତିଆରି କରେ। ପ୍ରତ୍ୟେକ 512-ପିକ୍ସେଲ୍ ସେଲ୍ ଏହାର ଉତ୍ସ ଟାଇମଷ୍ଟାମ୍ପକୁ ଉଚ୍ଚ-କଣ୍ଟ୍ରାସ୍ଟ ତଳ ବ୍ୟାଣ୍ଡରେ ଉତ୍କୀର୍ଣ୍ଣ କରେ, ଯେତେବେଳେ ସେହି ଟାଇମଷ୍ଟାମ୍ପଗୁଡ଼ିକ ଡାଉନଷ୍ଟ୍ରିମ୍ ସଂଯୋଗ ଏବଂ ଅଡିଟ୍ ପାଇଁ ପାଠ୍ୟ ମେଟାଡାଟାରେ ରହେ। ସମ୍ପୂର୍ଣ୍ଣ JPEG 32 MiB ପର୍ଯ୍ୟନ୍ତ ସୀମିତ ରହେ। ଯଦି `sharp` ଗ୍ରିଡ୍କୁ ଡିକୋଡ୍ କିମ୍ବା କମ୍ପୋଜ୍ କରିପାରେ ନାହିଁ, ବ୍ରିଜ୍ ବ୍ୟକ୍ତିଗତ JPEG ଫ୍ରେମ୍ଗୁଡ଼ିକୁ ଫେରିଆସେ; କ୍ଲାଏଣ୍ଟ ଅବର୍ଟ ତଥାପି ସିଟ୍ ଅପରେସନ୍ ମଧ୍ୟରେ ପ୍ରସାରିତ ହୁଏ।

ପ୍ରମୋଶନ୍ ପ୍ରମାଣ ଉଦ୍ଦେଶ୍ୟମୂଳକ ଭାବରେ ସିନ୍ଥେଟିକ୍ କମ୍ପୋଜିସନ୍ ମାଇକ୍ରୋବେଞ୍ଚମାର୍କରୁ ଅଲଗା। `scripts/perf/video-bridge-contact-sheet-eval.ts` ପ୍ରକୃତ OpenAI-ଅନୁକୂଳ ଭିଜନ୍ ମଡେଲ୍ ପାଇଁ ଏକ ସ୍କିମା-ସଂସ୍କରଣଯୁକ୍ତ A/B ହାର୍ନେସ୍ ନିର୍ଦ୍ଧାରଣ କରେ। ଏହା ପ୍ରଦାତା-ରିପୋର୍ଟ ଟୋକେନ୍, ଏଣ୍ଡ୍-ଟୁ-ଏଣ୍ଡ୍ ୱାଲ୍ ଲେଟେନ୍ସି (ସିଟ୍ କମ୍ପୋଜିସନ୍ ସହିତ), ମଡେଲ୍-କଲ୍ ଗଣନା, ଏବଂ ମାନିଫେଷ୍ଟ-ନିର୍ଦ୍ଧାରିତ ଫ୍ୟାକ୍ଟ ଧାରଣ ମାପେ। କଞ୍ଚା ମଡେଲ୍ ପ୍ରତିକ୍ରିୟା ରିପୋର୍ଟରେ ଲେଖାଯାଏ ନାହିଁ; କେବଳ SHA-256 ଡାଇଜେସ୍ଟ ଏବଂ ମେଳିଥିବା ଫ୍ୟାକ୍ଟ ID ସଂରକ୍ଷିତ ରହେ। `--execute-real` ପାସ୍ ହେବା ଏବଂ `--model`, `OMNIROUTE_BASE_URL`, ଓ `OMNIROUTE_API_KEY` କନଫିଗର୍ ହେବା ବିନା ହାର୍ନେସ୍ କୌଣସି ନେଟୱର୍କ କିମ୍ବା ଦେୟଯୁକ୍ତ ମଡେଲ୍ କଲ୍ କରେ ନାହିଁ। ସେହି ସ୍ପଷ୍ଟ ପ୍ରକୃତ ରନ୍ ବିନା, ଏହାର ମେସିନ୍-ପଠନୀୟ ନିର୍ଣ୍ଣୟ `HOLD` ରହେ; କେବଳ ସିନ୍ଥେଟିକ୍ ପେଲୋଡ୍/କଲ୍-ଗଣନା ମାପ ପ୍ରମୋଶନ୍ ପ୍ରମାଣ ନୁହେଁ।

କଲର୍ମାନେ ଏକ ସମର୍ଥିତ ଭିଡିଓ ଅଂଶରେ ଏକ ବୈକଳ୍ପିକ `transcript.cues` ଆରେ ଯୋଡ଼ିପାରନ୍ତି, ଯେତେବେଳେ ସେମାନଙ୍କ ପାଖରେ ପୂର୍ବରୁ ସଂରେଖିତ ପାଠ୍ୟ ରହିଥାଏ। ପ୍ରତ୍ୟେକ କ୍ୟୁରେ `text`, ପ୍ରୋବ୍ ହୋଇଥିବା ଅବଧି ଭିତରେ ଏକ ସୀମିତ `start`/`end` ଅନ୍ତରାଳ, ଏବଂ ଏକ ଅନୁମୋଦିତ-ତାଲିକାଭୁକ୍ତ `source` (`client`, `embedded`, କିମ୍ବା `audio-bridge`) ରହିବା ଆବଶ୍ୟକ; `confidence` ଡିଫଲ୍ଟ `1` ଏବଂ `0` ଏବଂ `1` ମଧ୍ୟରେ ରହିବା ଆବଶ୍ୟକ। ସଠିକ୍ ଡୁପ୍ଲିକେଟ୍ କ୍ୟୁଗୁଡ଼ିକୁ ସଂକୁଚିତ କରାଯାଏ। OmniRoute ଏହି ମେଟାଡାଟାରୁ କଦାପି ଟ୍ରାନ୍ସକ୍ରିପ୍ସନ୍ ଆରମ୍ଭ କରେ ନାହିଁ: ବୈଧତା ଯାଞ୍ଚିତ କ୍ୟୁଗୁଡ଼ିକ ଉତ୍ସ, ବିଶ୍ୱାସସ୍ତର ଏବଂ ଅନ୍ତରାଳ ସହିତ ବର୍ଣ୍ଣିତ ଫଳାଫଳକୁ କପି କରାଯାଏ, ଏବଂ ଫ୍ରେମ୍ କ୍ୟାପ୍ସନ୍ଗୁଡ଼ିକ ସହିତ ଅବିଶ୍ୱସ୍ତ ପର୍ଯ୍ୟବେକ୍ଷଣ ଭାବରେ ରେଣ୍ଡର କରାଯାଏ। ଅବୈଧ, ପରିସର-ବାହିର, କିମ୍ବା ପ୍ରୋଭେନାନ୍ସ-ବିହୀନ ପାଠ୍ୟକୁ କ୍ୟାପ୍ସନ୍ ଷ୍ଟ୍ରିମ୍ରେ ମିଶାଇବା ପରିବର୍ତ୍ତେ ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଏ। ଉଭୟ ରିକ୍ୱେଷ୍ଟ-ବଡି ଟ୍ରାନ୍ସକ୍ରିପ୍ଟ ଚ୍ୟାନେଲ୍ ଯୋଗାଇଦିଆଯାଇଥିବା ପ୍ରୋଭେନାନ୍ସକୁ `client` କୁ ସାମାନ୍ୟୀକରଣ କରେ, ଯେଉଁଥିରେ ସ୍ୱୟଂ-ଦର୍ଶିତ `embedded` କିମ୍ବା `audio-bridge` ଲେବଲ୍ ମଧ୍ୟ ଅନ୍ତର୍ଭୁକ୍ତ। କେବଳ ଏକ ସର୍ଭର-ମାଲିକାନାର ଆଡାପ୍ଟର୍ କେବଳ-କୋଡ୍ `trustedSource` ଆର୍ଗୁମେଣ୍ଟ ମାଧ୍ୟମରେ ସେହି ବିଶ୍ୱସ୍ତ ଲେବଲ୍ଗୁଡ଼ିକୁ ନ୍ୟସ୍ତ କରିପାରେ; ଏକ ରିକ୍ୱେଷ୍ଟ JSON ଫିଲ୍ଡ ସେହି ଆର୍ଗୁମେଣ୍ଟ ପର୍ଯ୍ୟନ୍ତ ପହଞ୍ଚିପାରିବ ନାହିଁ। ଟ୍ରାନ୍ସକ୍ରିପ୍ଟ ପାଠ୍ୟ ଏହାର ପ୍ରୋଭେନାନ୍ସ ନିର୍ବିଶେଷରେ ଅବିଶ୍ୱସ୍ତ ମିଡିଆ-ଉତ୍ପନ୍ନ ବିଷୟବସ୍ତୁ ରହେ, ଏବଂ କଦାପି ଅନୁମୋଦନ ନିର୍ଣ୍ଣୟ କରିବ ନାହିଁ।

ଏକ ଉନ୍ନତ କଲର୍ ସମାନ ଭିଡିଓ ପାଇଁ ଏକ `audioTranscript` ଟ୍ରାକ୍ ଯୋଗାଇପାରେ; ଏହାକୁ କ୍ଲାଏଣ୍ଟ-ଯୋଗାଇଥିବା ପାଠ୍ୟ ଭାବରେ ଗ୍ରହଣ କରାଯାଏ, ସର୍ଭର୍ ଟ୍ରାନ୍ସକ୍ରିପ୍ସନ୍ର ପ୍ରମାଣ ଭାବରେ ନୁହେଁ। ଫ୍ୟୁଜନ୍ ସିମ୍ ଏକ ସମୟସୀମା ଏବଂ ଅବର୍ଟ ସିଗ୍ନାଲ୍ ଅଧୀନରେ ଭିଜୁଆଲ୍ ଏବଂ ଅଡିଓ ପର୍ଯ୍ୟବେକ୍ଷଣ ଚଲାଏ, ସେଗୁଡ଼ିକୁ ଏକ ସାଧାରଣ ଟାଇମଲାଇନରେ ସଜାଡ଼େ, ସଠିକ୍ ଡୁପ୍ଲିକେଟ୍ଗୁଡ଼ିକୁ ଏକତ୍ରିତ କରେ, ଏବଂ କେବଳ ଗୋଟିଏ ପାର୍ଶ୍ୱ ସଫଳ ହେଲେ ଏକ ଆଂଶିକ ଫଳାଫଳ ରିପୋର୍ଟ କରେ। ଏକ ଅବୈଧ `audioTranscript` ସେହି ଆଂଶିକ ଫଳାଫଳକୁ ଅବନତ ହୁଏ — ଭିଜୁଆଲ୍ ବର୍ଣ୍ଣନା ରଖାଯାଏ ଏବଂ ଅଡିଓ ଶାଖା ଏକ ସାନିଟାଇଜ୍ ହୋଇଥିବା ବିଫଳତା କୋଡ୍ ରେକର୍ଡ କରେ — ସମଗ୍ର ଭିଡିଓ ବିଫଳ କରିବା ପରିବର୍ତ୍ତେ। ପ୍ରତି-ଶାଖା ଉପଲବ୍ଧତା, ଆଂଶିକ ଫ୍ଲାଗ୍, ଏବଂ ସାନିଟାଇଜ୍ ହୋଇଥିବା ବିଫଳତା କୋଡ୍ଗୁଡ଼ିକ ବର୍ଣ୍ଣିତ ଫଳାଫଳରେ, ଗାର୍ଡରେଲ୍ ମେଟାଡାଟାରେ (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), ରିଜଲ୍ଟ-କ୍ୟାସ୍ ମେଟାଡାଟାରେ, ଏବଂ ବ୍ରିଜ୍ ଫ୍ୟୁଜନ୍ କାଉଣ୍ଟରରେ ସଂରକ୍ଷିତ ରହେ। ଡିଫଲ୍ଟ Video Bridge ପଥ speech-to-text କୁ ଆହ୍ୱାନ କରେ ନାହିଁ କିମ୍ବା ଦ୍ୱିତୀୟ ମିଡିଆ କପି ଡାଉନଲୋଡ୍ କରେ ନାହିଁ; ସେହି ସ୍ପଷ୍ଟ ଟ୍ରାକ୍ ବିନା, ଏହା କେବଳ-ଭିଡିଓ ରହେ।

**ଟ୍ରାନ୍ସକ୍ରିପ୍ଟ ସଂରକ୍ଷଣ (#12150 P1)।** Video Bridge (ଯାହା ନିଜେ opt-in) କୌଣସି ଟ୍ରାନ୍ସକ୍ରିପ୍ଟ ସଙ୍କେତ ରେଣ୍ଡର୍ କରିବାମାତ୍ରେ ଏହା ସ୍ୱୟଂଚାଳିତ ଭାବେ ପ୍ରଯୁଜ୍ୟ ହୁଏ — ଏଥିପାଇଁ କୌଣସି ପୃଥକ ସଂରକ୍ଷଣ ଫ୍ଲାଗ୍ ନାହିଁ। ଯେତେବେଳେ କୌଣସି ଅନୁରୋଧ ଯେକୌଣସି ଟ୍ରାନ୍ସକ୍ରିପ୍ଟ ସଙ୍କେତ (କଲର୍ଙ୍କ ଦ୍ୱାରା ଘୋଷିତ `transcript` କିମ୍ବା ସଂଯୋଜିତ `audioTranscript`) ରେଣ୍ଡର୍ କରେ, guardrail ଏହାକୁ `videoBridgeObserved` ଭାବେ ଚିହ୍ନିତ କରେ ଏବଂ ଭିଡିଓ ବର୍ଣ୍ଣନାର ଏକ ସମ୍ପାଦିତ shadow ତିଆରି କରେ — ଏହା ଏକ ସମାନ ରେଣ୍ଡରିଂ, ଯେଉଁଥିରେ ପ୍ରତ୍ୟେକ ସଙ୍କେତର free-text bodyକୁ `[redacted-video-transcript]` ଦ୍ୱାରା ବଦଳାଯାଏ; string ଏକତ୍ରିତ ହେବା ପୂର୍ବରୁ structured cue fieldକୁ ପ୍ରତିସ୍ଥାପନ କରି ଏହା ନିର୍ମାଣ କରାଯାଏ (flattened textକୁ କେବେବି parse କରି ନୁହେଁ, ତେଣୁ କୌଣସି cue content — ପ୍ରତିକୂଳ କିମ୍ବା ସାଧାରଣ, `[inaudible]`/`[music]` ପରି `]` ଥିବା body ସମେତ — ରହିପାରିବ ନାହିଁ)। ସଂରକ୍ଷିତ call-log request bodyରେ content equality ଦ୍ୱାରା ମେଳ କରି, ପ୍ରତ୍ୟେକ video-derived text partକୁ ସେହି ସମ୍ପାଦିତ shadow ସହିତ ବଦଳାଯାଏ; ସମାପ୍ତ pre-call guardrail payloadରୁ `fullText` anchorକୁ ପୁନର୍ବାର ପଢ଼ାଯାଏ, ତେଣୁ ପରବର୍ତ୍ତୀ chain guardrailଗୁଡ଼ିକ (PII ଏବଂ credential masker, ପ୍ରାଥମିକତା 10/95) ବର୍ଣ୍ଣନା textକୁ ସେହି ସ୍ଥାନରେ ପୁନର୍ଲିଖନ କରିବା ପରେ ଏବଂ system-prompt/handoff/memory injection message arrayକୁ ପୁନରାକାର ଦେବା ପରେ ମଧ୍ୟ ମେଳ ସଫଳ ହୁଏ। modelକୁ upstream ପଠାଯାଇଥିବା body ଅପରିବର୍ତ୍ତିତ ରହେ। ଏକ observed request କୌଣସି ସ୍ଥାୟୀ Memory ମଧ୍ୟ ପୂରଣ କରେ ନାହିଁ (request- ଏବଂ response-derived extraction ଉଭୟକୁ ଏଡ଼ାଯାଏ), ତେଣୁ modelର ନିଜସ୍ୱ reply ଟ୍ରାନ୍ସକ୍ରିପ୍ଟ textକୁ Memoryରେ ପ୍ରତିଧ୍ୱନିତ କରିପାରିବ ନାହିଁ।

**କଞ୍ଚା ଭିଡିଓ ଫିଲ୍ଡ୍ (#12430)।** bridge ସକ୍ଷମ ଥିବାବେଳେ ଏବଂ native video support ଅଜଣା କିମ୍ବା ଅନୁପସ୍ଥିତ ଥିଲେ, ପରିଭାଷିତ `transcript`/`audioTranscript` fieldଗୁଡ଼ିକ ମଧ୍ୟ `videoBridgeObserved`କୁ ସକ୍ରିୟ କରନ୍ତି, description failure କିମ୍ବା `maxVideos` ସୀମା ପରେ ମଧ୍ୟ। `null` ଏବଂ ଖାଲି stringକୁ ଗଣନା କରାଯାଏ; ଅନୁପସ୍ଥିତ field ଏବଂ non-video metadataକୁ କରାଯାଏ ନାହିଁ। ସଂରକ୍ଷିତ copyଗୁଡ଼ିକ ଏହି fieldଗୁଡ଼ିକୁ ସମ୍ପାଦନ କରନ୍ତି କିମ୍ବା requestକୁ ବାଦ ଦିଅନ୍ତି, ଏବଂ cache/Memoryକୁ bypass କରାଯାଏ।

ସେହି fallback pathଗୁଡ଼ିକରେ, ବୈଧ caller cueଗୁଡ଼ିକ nonstandard provider field ପରିବର୍ତ୍ତେ ସମର୍ଥିତ `text`/`input_text` part ହୁଅନ୍ତି। request ଦ୍ୱାରା ଯୋଗାଇ ଦିଆଯାଇଥିବା ଉଭୟ track ଅବିଶ୍ୱସନୀୟ `client` observation ଭାବେ ରହେ, ଏବଂ ଭିଡିଓଟି ବର୍ଣ୍ଣନା କରାଯାଇ ନଥିଲା ଓ timestampଗୁଡ଼ିକୁ media ସହିତ ଯାଞ୍ଚ କରାଯାଇ ନଥିଲା ବୋଲି ଏକ ସ୍ପଷ୍ଟ ଚେତାବନୀ ଥାଏ। ବିଦ୍ୟମାନ 256-cue/64-KiB ସମୁଦାୟ ଏବଂ ପ୍ରତି-cue budget ଦୁଇଟି track ଉପରେ ମିଳିତ ଭାବେ ପ୍ରଯୁଜ୍ୟ ହୁଏ; timestampଗୁଡ଼ିକ brokerର 600-second ceiling ଏବଂ ଯୋଗାଇ ଦିଆଯାଇଥିବା ଯେକୌଣସି focus window ମଧ୍ୟରେ ରହିବା ଆବଶ୍ୟକ। ଅବୈଧ trackଗୁଡ଼ିକୁ ବର୍ଜନ କରାଯାଏ, arbitrary text ଭାବେ forward କରାଯାଏ ନାହିଁ; ସେମାନଙ୍କର ମିଳିତ budget ଅତିକ୍ରମ ନହେଲେ ଏକ ବୈଧ siblingକୁ ତଥାପି ବ୍ୟବହାର କରାଯାଇପାରେ। Null/empty field କୌଣସି text ଯୋଡ଼େ ନାହିଁ। ଏହି fallback ଦ୍ୱାରା କୌଣସି media fetch କିମ୍ବା transcription ଯୋଡ଼ାଯାଏ ନାହିଁ। Transcript extension fieldଗୁଡ଼ିକୁ fallback video carrier ଏବଂ ଏହାର `video_url`/`source` objectଗୁଡ଼ିକରୁ ଅପସାରଣ କରାଯାଏ। OpenAI wire allowlist କଠୋର ରହେ; unknown-native video carrierଗୁଡ଼ିକ ଉପଲବ୍ଧ ରହନ୍ତି ଏବଂ ଜଣାଶୁଣା text-only targetଗୁଡ଼ିକ ସୁରକ୍ଷିତ marker ରଖନ୍ତି। Structured redaction shadowଗୁଡ଼ିକ ଯୋଡ଼ାଯାଇଥିବା transcript textକୁ ସୁରକ୍ଷା କରନ୍ତି, ଯେତେବେଳେ ମୂଳ caller-owned request ଅପରିବର୍ତ୍ତିତ ରହେ। Native-supported target ଏବଂ ଅକ୍ଷମ bridgeଗୁଡ଼ିକ ସେମାନଙ୍କର ବିଦ୍ୟମାନ bypass ଆଚରଣ ବଜାୟ ରଖନ୍ତି।

### PII ମାସ୍କର୍ (`piiMasker.ts`)

**ଉଭୟ** ପର୍ଯ୍ୟାୟରେ ଚାଲେ।

- **`preCall`** ପେଲୋଡ୍କୁ କ୍ଲୋନ୍ କରେ, `system`, `messages`, `input`, ଏବଂ `prompt` (ସାଧାରଣ ଷ୍ଟ୍ରିଙ୍ଗ୍ ଆଇଟମ୍ଗୁଡ଼ିକ ସହିତ) ପରିଦର୍ଶନ କରେ, ଏବଂ ଷ୍ଟ୍ରିଙ୍ଗ୍ `content`/`text` ଫିଲ୍ଡଗୁଡ଼ିକ ଉପରେ `processPII()` (`@/shared/utils/inputSanitizer` ରୁ) ପ୍ରୟୋଗ କରେ. ଯେତେବେଳେ `PII_REDACTION_ENABLED=true`, ଚିହ୍ନଟ ହୋଇଥିବା PII ଆଉଟବାଉଣ୍ଡ ପେଲୋଡ୍ରେ ରେଡାକ୍ଟ୍ କରାଯାଏ. ଏହା `INPUT_SANITIZER_MODE` ଠାରୁ ସ୍ୱାଧୀନ (ଯାହା କେବଳ ପ୍ରମ୍ପ୍ଟ-ଇଞ୍ଜେକ୍ସନ ନୀତିକୁ ନିୟନ୍ତ୍ରଣ କରେ). ରେଡାକ୍ସନ୍ ବନ୍ଦ ଥିଲେ, କଲ୍ ବିଷୟବସ୍ତୁ ପୁନଃଲେଖନ ନକରି ଚିହ୍ନଟ ଗଣନା ରେକର୍ଡ କରେ.
- **`postCall`** ପ୍ରତିକ୍ରିୟାକୁ ଗଭୀର-କ୍ଲୋନ୍ କରେ, `sanitizePIIResponse()` ସହିତ Responses-API-ଆକୃତି ମାସ୍କର୍ (`maskResponsesOutput` — `output_text` ଏବଂ `output[].content[].text` ଅନ୍ତର୍ଭୁକ୍ତ କରେ) ଚଲାଏ. ଯଦି କୌଣସି ରେଡାକ୍ସନ୍ ଘଟେ, ପରିବର୍ତ୍ତିତ ପ୍ରତିକ୍ରିୟା ମୂଳଟିକୁ ବଦଳାଇଥାଏ.

ଗାର୍ଡରେଲ୍ କେବେ ବ୍ଲକ୍ କରେ ନାହିଁ; ଏହା କେବଳ ଆନୋଟେଟ୍ କରେ (`meta.detections`, `meta.redacted`) କିମ୍ବା ପୁନଃଲେଖନ କରେ.

#### ପ୍ରକାର-ଅନୁଯାୟୀ ଚୟନ, କଷ୍ଟମ୍ ପ୍ୟାଟର୍ନ ଏବଂ ଚିହ୍ନଟ କାଉଣ୍ଟରଗୁଡ଼ିକ

**ଡ୍ୟାସବୋର୍ଡ → ସେଟିଂସ → ସିକ୍ୟୁରିଟି → PII ମାସ୍କିଂ** _କଣ_ ମାସ୍କ୍ ହେବ ତାହା ବାଛେ. ଏହା ମାସ୍କିଂ ଚାଲୁ କରେ ନାହିଁ: ତାହା ଏବେ ମଧ୍ୟ `PII_REDACTION_ENABLED` (ରିକ୍ୱେଷ୍ଟ) ଏବଂ `PII_RESPONSE_SANITIZATION` (ପ୍ରତିକ୍ରିୟା + SSE) ଅଟେ, ଉଭୟ ଡିଫଲ୍ଟରେ ବନ୍ଦ.

- **ପ୍ରକାର-ଅନୁଯାୟୀ ଚୟନ** — ଅନ୍ତର୍ନିହିତ IDଗୁଡ଼ିକ `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`) ରେ ତାଲିକାଭୁକ୍ତ ଅଛି. ଅନସେଟ୍ ରହିଲେ ଅର୍ଥ ସମସ୍ତ ପ୍ରକାର (ଏହି ସେଟିଂ ଉପସ୍ଥିତ ହେବା ପୂର୍ବର ଆଚରଣ). ରିକ୍ୱେଷ୍ଟ ଇଞ୍ଜିନର `ssn_us` ପ୍ୟାଟର୍ନ `ssn` ସହିତ ମ୍ୟାପ୍ ହୁଏ. ଟେମ୍ପଲେଟଗୁଡ଼ିକ (Minimal, Standard, Financial, Brazilian, USA, Full) କେବଳ UIରେ ଚେକବକ୍ସଗୁଡ଼ିକ ପୂରଣ କରେ.
- **କଷ୍ଟମ୍ ପ୍ୟାଟର୍ନଗୁଡ଼ିକ** — 20 ପର୍ଯ୍ୟନ୍ତ regex କିମ୍ବା ୱାଇଲ୍ଡକାର୍ଡ ପ୍ୟାଟର୍ନ (`*` = 64 ପର୍ଯ୍ୟନ୍ତ ଅଣ-ୱ୍ହାଇଟସ୍ପେସ୍ ଅକ୍ଷର, `?` = ଗୋଟିଏ). ମ୍ୟାଚ୍ଗୁଡ଼ିକ `[CUSTOM_REDACTED]` ହୋଇଯାଏ. ପ୍ରତ୍ୟେକ ପ୍ୟାଟର୍ନ `compilePiiCustomPattern()` (`src/shared/utils/piiCustomPatterns.ts`) ମଧ୍ୟ ଦେଇ ଯାଏ: ସର୍ବାଧିକ 500 ଅକ୍ଷର, ଫ୍ଲାଗଗୁଡ଼ିକ `g i m s u` ମଧ୍ୟରେ ସୀମିତ, କମ୍ପାଇଲ୍ ହେବା ଆବଶ୍ୟକ, `safe-regex` (ବିପର୍ଯ୍ୟୟ ବ୍ୟାକଟ୍ରାକିଂ) ପାସ୍ କରିବା ଆବଶ୍ୟକ, ଏବଂ ଏକ ଖାଲି ଷ୍ଟ୍ରିଙ୍ଗ୍ କିମ୍ବା ରେଡାକ୍ସନ୍ ପ୍ଲେସହୋଲ୍ଡର ସହିତ ମେଳ ଖାଇବା ଉଚିତ ନୁହେଁ. ବିଫଳ ହେଉଥିବା ପ୍ୟାଟର୍ନ ସେଭ୍ ଏବଂ ପରୀକ୍ଷା ସମୟରେ ଅଗ୍ରାହ୍ୟ କରାଯାଏ, ଏବଂ ବିଫଳ ହେଉଥିବା ସଂରକ୍ଷିତ ଧାଡ଼ି କମ୍ପାଇଲ୍ ହେବା ପରିବର୍ତ୍ତେ ରନ୍ଟାଇମରେ ଛାଡ଼ିଦିଆଯାଏ. କଷ୍ଟମ୍ ପ୍ୟାଟର୍ନଗୁଡ଼ିକ କେବଳ ମାସ୍କିଂ ଚାଲୁ ଥିବା ସମୟରେ ଚାଲେ.
- **ଚିହ୍ନଟ କାଉଣ୍ଟରଗୁଡ଼ିକ** — ପ୍ରକାର-ଅନୁଯାୟୀ ଗଣନା (କେବେ ମ୍ୟାଚ୍ ହୋଇଥିବା ମୂଲ୍ୟ ନୁହେଁ), ମେମୋରୀରେ ରଖାଯାଏ ଏବଂ ପୁନଃଆରମ୍ଭରେ ରିସେଟ୍ ହୁଏ (`src/lib/pii/piiDetectionStats.ts`). ମାସ୍କିଂ ଚାଲୁ ଥିବା ସମୟରେ ସେଗୁଡ଼ିକ କେବଳ ବଢ଼େ.

ସେଟିଂସଗୁଡ଼ିକ `key_value` ଟେବୁଲରେ ରହେ (ନେମସ୍ପେସ୍ `pii_settings`, `src/lib/db/piiSettings.ts`) ଏବଂ 1 s କ୍ୟାଚ୍ ମାଧ୍ୟମରେ ପଢ଼ାଯାଏ. API:

| Method | Path                     | Purpose                                                                                |
| ------ | ------------------------ | -------------------------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | ଫ୍ଲାଗ ସ୍ଥିତି, `enabledTypes`, `customPatterns`, ଚିହ୍ନଟ କାଉଣ୍ଟର                         |
| `PUT`  | `/api/settings/pii`      | `enabledTypes` (`null` = ସମସ୍ତ) ଏବଂ/କିମ୍ବା `customPatterns` ବଦଳାନ୍ତୁ                   |
| `POST` | `/api/settings/pii/test` | ସର୍ବାଧିକ 8 KB ର ନମୁନା ବିରୁଦ୍ଧରେ ଗୋଟିଏ ପ୍ୟାଟର୍ନ Dry-run କରନ୍ତୁ; କିଛି ସଂରକ୍ଷିତ ହୁଏ ନାହିଁ |

ତିନୋଟି ମଧ୍ୟରୁ ସମସ୍ତେ ମେନେଜମେଣ୍ଟ ଅଥେନ୍ଟିକେସନ୍ ଆବଶ୍ୟକ କରେ ଏବଂ Zod (`src/shared/validation/schemas/piiSettings.ts`) ସହିତ ବଡି ଭାଲିଡେଟ୍ କରେ.

### ପ୍ରମ୍ପ୍ଟ ଇଞ୍ଜେକ୍ସନ (`promptInjection.ts`)

ଉପଭୋକ୍ତା-ପ୍ରଦତ୍ତ ବିଷୟବସ୍ତୁରେ ବିରୋଧୀ ଗଠନଗୁଡ଼ିକୁ ଚିହ୍ନଟ କରେ ଏବଂ ବିନ୍ୟାସିତ ନୀତି ଲାଗୁ କରେ. ଆଚରଣ ପରିବେଶ ଭେରିଏବଲ୍ ଏବଂ କନଷ୍ଟ୍ରକ୍ଟର ଅପ୍ସନ୍ସ ଦ୍ୱାରା ପରିଚାଳିତ ହୁଏ:

| Setting          | Env var                                                                                                | Default | Effect                                                                                                                                                                                                          |
| ---------------- | ------------------------------------------------------------------------------------------------------ | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ସକ୍ଷମ            | `INPUT_SANITIZER_ENABLED`                                                                              | `true`  | ଯେତେବେଳେ `false`, ଗାର୍ଡରେଲ୍ ସର୍ଟ-ସର୍କିଟ୍ ହୁଏ.                                                                                                                                                                   |
| ମୋଡ୍             | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                        | `warn`  | ଇଞ୍ଜେକ୍ସନ ନୀତି: `block`, `warn`, କିମ୍ବା `log`. (`redact` ବ୍ୟାକ୍-କମ୍ପାଟ୍ ପାଇଁ ଗ୍ରହଣ କରାଯାଏ କିନ୍ତୁ ଇଞ୍ଜେକ୍ସନ ଟେକ୍ସଟ୍କୁ **କାଢ଼ିଦିଏ ନାହିଁ**; ରିକ୍ୱେଷ୍ଟ PII ପୁନଃଲେଖନ `PII_REDACTION_ENABLED` ଦ୍ୱାରା ନିୟନ୍ତ୍ରିତ ହୁଏ.) |
| ବ୍ଲକ୍ ଥ୍ରେସହୋଲ୍ଡ | `blockThreshold` ଅପ୍ସନ୍ / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ଅଲିଆସ୍ `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | ବ୍ଲକ୍ କରିବା ପାଇଁ ଆବଶ୍ୟକ ସର୍ବନିମ୍ନ ଗମ୍ଭୀରତା. ଡିଫଲ୍ଟରେ ମଧ୍ୟମ କେବଳ ପର୍ଯ୍ୟବେକ୍ଷଣ ଅଟେ.                                                                                                                               |

**ମୋଡ୍ ପ୍ରାଥମିକତା** (`getMode`): କଲର୍ `options.mode` → `INJECTION_GUARD_MODE` **DB ଫିଚର୍-ଫ୍ଲାଗ୍ ଓଭରରାଇଡ୍** (ଡ୍ୟାସବୋର୍ଡ → ସେଟିଂସ → ଫିଚର୍ ଫ୍ଲାଗସ୍) → `INJECTION_GUARD_MODE` ପରିବେଶ → `INPUT_SANITIZER_MODE` ପରିବେଶ → `warn`. ତେଣୁ ଏକ ଡ୍ୟାସବୋର୍ଡ ଓଭରରାଇଡ୍ ପରିବେଶ ଭେରିଏବଲ୍ ଉପରେ ଜିତେ, ଫଳରେ ଫିଚର୍ ଫ୍ଲାଗସ୍ UI ଚାଲୁଥିବା ଗାର୍ଡକୁ ଲାଇଭ୍ ନିୟନ୍ତ୍ରଣ କରେ (ପୁନଃଆରମ୍ଭ ନାହିଁ). DB ପଠନ ଫେଲ୍-ସେଫ୍: ଯଦି ଏଥିରେ ତ୍ରୁଟି ହୁଏ, ଗାର୍ଡ ପରିବେଶ-ଆଧାରିତ ଆଚରଣକୁ ଫେରିଯାଏ, ଏବଂ କୌଣସି ଓଭରରାଇଡ୍ ସେଟ୍ ହୋଇନଥିଲେ ଆଚରଣ କେବଳ-ପରିବେଶ ରିଜୋଲ୍ୟୁସନ୍ ସହିତ ସମାନ ହୁଏ.

ଚିହ୍ନଟ ଉତ୍ସଗୁଡ଼ିକ:

1. `@/shared/utils/inputSanitizer` ରୁ `sanitizeRequest()` (ପାଇପଲାଇନରେ ଅନ୍ୟତ୍ର ବ୍ୟବହୃତ ସେୟାର୍ଡ ଡିଟେକ୍ଟର ସେଟ୍).
2. ଅନ୍ତର୍ନିହିତ `DEFAULT_GUARD_PATTERNS` (ବର୍ତ୍ତମାନ `system_override_inline` ଏବଂ `markdown_system_block`, ଉଭୟ `high` ଗମ୍ଭୀରତା).
3. ବୈକଳ୍ପିକ `customPatterns` କନଷ୍ଟ୍ରକ୍ଟର ଅପ୍ସନ୍ସ ମାଧ୍ୟମରେ ପାସ୍ କରାଯାଏ (ଷ୍ଟ୍ରିଙ୍ଗ୍, regex, କିମ୍ବା `{ name, pattern, severity }` ରେକର୍ଡ).

ଯେତେବେଳେ `mode === "block"` **ଏବଂ** ଅତି କମରେ ଗୋଟିଏ ଚିହ୍ନଟକରଣ ଗୁରୁତ୍ୱ
ସୀମା ପୂରଣ କରେ, `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` ଫେରାଏ। `warn`/`log` ମୋଡ୍ଗୁଡ଼ିକରେ ଗାର୍ଡରେଲ୍ ଲଗ୍ କରେ କିନ୍ତୁ
କଲ୍କୁ ଅନୁମତି ଦିଏ। ଅଂଶୀଦାର ହେଲ୍ପର୍ `evaluatePromptInjection()` ମଧ୍ୟ ରପ୍ତାନି କରାଯାଏ,
ଯେଉଁ କଲର୍ମାନଙ୍କୁ ରେଜିଷ୍ଟ୍ରି ମାଧ୍ୟମରେ ନ ଯାଇ ପ୍ରମ୍ପ୍ଟଗୁଡ଼ିକର ମୂଲ୍ୟାୟନ କରିବାକୁ ପଡ଼େ।

**ସ୍କାନ୍ ସୀମା (v3.8.20):** ଡିଟେକ୍ଟର୍ ଯୋଡ଼ାଯାଇଥିବା ପ୍ରମ୍ପ୍ଟ ଟେକ୍ସଟ୍ର କେବଳ **ପ୍ରଥମ 16 KB** ଯାଞ୍ଚ କରେ —
`src/shared/utils/inputSanitizer.ts`ରେ `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ବାଇଟ୍)।
ପ୍ୟାଟର୍ନ ଲୁପ୍ ଚଲାଇବା ପୂର୍ବରୁ `detectInjection()` ଏବଂ
`evaluatePromptInjection()` ଉଭୟ `slice(0, MAX_INJECTION_SCAN_BYTES)` ବ୍ୟବହାର କରନ୍ତି।
ଇଞ୍ଜେକ୍ସନ୍ ନିର୍ଦ୍ଦେଶଗୁଡ଼ିକ ଇନ୍ପୁଟ୍ର ଉପର ଭାଗ ପାଖରେ ରହେ, ତେଣୁ ଏହା ଚିହ୍ନଟ କ୍ଷମତାକୁ ଦୁର୍ବଳ ନ କରି
ଏକାଧିକ-ଶହ-KB ପେଲୋଡ୍ରେ regex CPU/GCକୁ ସୀମିତ କରେ (ଦେଖନ୍ତୁ
#3932, #4041)।

### କ୍ରେଡେନ୍ସିଆଲ୍ ମାସ୍କର୍ (`credentialMasker.ts`)

**ଉଭୟ** ପର୍ଯ୍ୟାୟରେ ଚାଲେ, ଡିଫଲ୍ଟ ଶୃଙ୍ଖଳରେ ଶେଷରେ ଥାଏ (ପ୍ରାଥମିକତା `95`)। ଆଉଟ୍ବାଉଣ୍ଡ ପେଲୋଡ୍ରୁ
(ମେସେଜ୍ ବିଷୟବସ୍ତୁ, ଟୁଲ୍-କଲ୍ ଆର୍ଗୁମେଣ୍ଟ, ଟୁଲ୍ ଫଳାଫଳ) **ଏବଂ** ପ୍ରଦାତାଙ୍କ ପ୍ରତିକ୍ରିୟାରୁ
ସୁପରିଚିତ API-କି / ଗୁପ୍ତ-ଟୋକେନ୍ ପ୍ୟାଟର୍ନଗୁଡ଼ିକୁ ସମ୍ପାଦିତ କରେ, ଯାହାଦ୍ୱାରା ପ୍ରମ୍ପ୍ଟରେ ପେଷ୍ଟ କରାଯାଇଥିବା
କୌଣସି କ୍ରେଡେନ୍ସିଆଲ୍ (କିମ୍ବା ଟୁଲ୍ ଫଳାଫଳ ଦ୍ୱାରା ପୁନରୁକ୍ତ କରାଯାଇଥିବା) ଅପ୍ଷ୍ଟ୍ରିମ୍ ପ୍ରଦାତା କିମ୍ବା
କ୍ଲାଏଣ୍ଟଙ୍କ ପାଖକୁ ଲିକ୍ ନ ହୁଏ।

- **କେବଳ ଅପ୍ଟ-ଇନ୍**, PII ସମ୍ପାଦନ ଭଳି ସମାନ ପ୍ରଥା (କଠୋର ନିୟମ #20-ସଂଲଗ୍ନ):
  `settings.credentialRedactionEnabled === true` **କିମ୍ବା**
  `CREDENTIAL_REDACTION_ENABLED=true` ନ ଥିଲେ ଏହା ଅକ୍ଷମ ରହେ। ଏହା ବନ୍ଦ ଥିବାବେଳେ ଗାର୍ଡରେଲ୍ କୌଣସି କାର୍ଯ୍ୟ କରେନାହିଁ —
  ଏହା କେବେ ଅବରୋଧ କରେନାହିଁ କିମ୍ବା ପୁନର୍ଲିଖନ କରେନାହିଁ।
- `redactCredentials()` ସମ୍ପୂର୍ଣ୍ଣ ପେଲୋଡ୍/ପ୍ରତିକ୍ରିୟା ଟ୍ରିକୁ ପରିକ୍ରମା କରେ (`walkValue()`,
  ପ୍ରୋଟୋଟାଇପ୍-ପଲ୍ୟୁସନ୍ରୁ ସୁରକ୍ଷିତ, `WeakSet` ମାଧ୍ୟମରେ ସାଇକେଲ୍ରୁ ସୁରକ୍ଷିତ) ଏବଂ ମେଳଗୁଡ଼ିକୁ
  ଏକ `[REDACTED:<type>]` ପ୍ଲେସ୍ହୋଲ୍ଡର୍ରେ ବଦଳାଏ, କେବଳ ପ୍ରକୃତରେ ପରିବର୍ତ୍ତିତ ହୋଇଥିବା
  ଶାଖାଗୁଡ଼ିକୁ କ୍ଲୋନ୍ କରେ।
- `CREDENTIAL_PATTERNS` LLM ପ୍ରଦାତା କିଗୁଡ଼ିକୁ (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ଟୋକେନ୍ଗୁଡ଼ିକୁ (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), ପେମେଣ୍ଟ କିଗୁଡ଼ିକୁ (Stripe, Square), କ୍ଲାଉଡ୍
  କିଗୁଡ଼ିକୁ (AWS ଆକ୍ସେସ୍ କି, Twilio, SendGrid, Mailgun), ପ୍ରାଇଭେଟ୍ କି / JWT,
  କ୍ରେଡେନ୍ସିଆଲ୍-ଯୁକ୍ତ କନେକ୍ସନ୍ ଷ୍ଟ୍ରିଙ୍ଗ୍ଗୁଡ଼ିକୁ (`mongodb://user:pass@...`, ଇତ୍ୟାଦି), ଏବଂ
  ଏକ ସାଧାରଣ `Authorization`/`x-api-key`/`api-key`/`apikey` ହେଡର୍-ମୂଲ୍ୟ
  ପ୍ୟାଟର୍ନକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରେ। ହେଡର୍-ଆକୃତିର କିଗୁଡ଼ିକ (`authorization`, `x-api-key`, `api-key`,
  `apikey`) ସାଧାରଣ ଟେକ୍ସଟ୍ regex ମାଧ୍ୟମରେ ନୁହେଁ, ବରଂ ଗଠନାତ୍ମକ ଭାବରେ (କେବଳ ମୂଲ୍ୟ,
  `Bearer `/`Basic ` ପରି ସ୍କିମ୍ ପ୍ରିଫିକ୍ସ ସଂରକ୍ଷିତ ରଖି) ସମ୍ପାଦିତ ହୁଏ।
- ଗାର୍ଡରେଲ୍ କେବେ ଅବରୋଧ କରେନାହିଁ; ଏହା କେବଳ ପୁନର୍ଲିଖନ (`modifiedPayload` /
  `modifiedResponse`) ଏବଂ ଟୀକାକରଣ (`meta.credentialsRedacted`, `meta.count`) କରେ।

ରିଗ୍ରେସନ୍ ଗାର୍ଡ: `tests/unit/credential-masker-guardrail.test.ts`।

## ମୂଳ କଣ୍ଟ୍ରାକ୍ଟ (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ଚେନ୍କୁ ସ୍ୱଳ୍ପପଥରେ ସମାପ୍ତ କରେ
  message?: string; // ବ୍ଲକ୍ କରିବା ସମୟରେ ପ୍ରଦର୍ଶିତ ହୁଏ
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // ଅନୁରୋଧକୁ ପୁନର୍ଲେଖନ କରିବା ପାଇଁ preCall ଦ୍ୱାରା ଫେରାଯାଏ
  modifiedResponse?: TValue; // ପ୍ରତିକ୍ରିୟାକୁ ପୁନର୍ଲେଖନ କରିବା ପାଇଁ postCall ଦ୍ୱାରା ଫେରାଯାଏ
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ଏକ ଗାର୍ଡରେଲ୍ `void`, `{}`, କିମ୍ବା `{ block: false }` ମଧ୍ୟରୁ ଯେକୌଣସିଟି ଫେରାଇ “କୌଣସି ପରିବର୍ତ୍ତନ ନାହିଁ” ବୋଲି ସୂଚାଏ। ଏକ `modifiedPayload`/`modifiedResponse` ଫେରାଇବା ଦ୍ୱାରା ଚେନ୍ରେ ପରବର୍ତ୍ତୀ ଗାର୍ଡରେଲ୍ଗୁଡ଼ିକ ପାଖକୁ ପ୍ରବାହିତ ହେଉଥିବା ମୂଲ୍ୟଟି ପ୍ରତିସ୍ଥାପିତ ହୁଏ।
`signal?: AbortSignal` କଲର୍ର ଜୀବନଚକ୍ରକୁ ଗାର୍ଡରେଲ୍ଗୁଡ଼ିକ ମଧ୍ୟକୁ ବହନ କରେ। ଅନୁରୋଧ ବାତିଲ୍ ହେବା ହେଉଛି ସୁଚିନ୍ତିତ ଫେଲ୍-ଓପେନ୍ ବ୍ୟତିକ୍ରମ: ଏହାକୁ ସମର୍ଥନ କରେନାହିଁ ବୋଲି ଜଣାଥିବା ଏକ ଲକ୍ଷ୍ୟରେ ଅପରିଷ୍କୃତ ମିଡିଆ ପୁନଃସ୍ଥାପନ ନକରି, ମିଡିଆ ବ୍ରିଜ୍ଗୁଡ଼ିକ କାର୍ଯ୍ୟ ବନ୍ଦ କରି ପରିଷ୍କାର କରନ୍ତି।

## ରେଜିଷ୍ଟ୍ରି (`registry.ts`)

ସିଙ୍ଗଲଟନ୍ `guardrailRegistry` ନିମ୍ନଲିଖିତଗୁଡ଼ିକୁ ଉନ୍ମୁକ୍ତ କରେ:

- `register(guardrail)` — ଏକ ଗାର୍ଡରେଲ୍ ଯୋଡ଼େ (କିମ୍ବା ସ୍ୱାଭାବିକୀକୃତ ନାମ ଅନୁସାରେ ପ୍ରତିସ୍ଥାପନ କରେ) ଏବଂ
  ଆରୋହୀ `priority` ଅନୁସାରେ ପୁନଃ ସଜାଏ।
- `clear()` / `list()` — ପ୍ରଶାସନିକ ସହାୟକ।
- `runPreCallHooks(payload, context)` — ସକ୍ରିୟ ଗାର୍ଡରେଲ୍ଗୁଡ଼ିକ ଉପରେ ପୁନରାବୃତ୍ତି କରେ, ପେଲୋଡ୍କୁ
  `modifiedPayload` ମାଧ୍ୟମରେ ପ୍ରବାହିତ କରେ ଏବଂ ପ୍ରଥମ `block: true` ମିଳିଲେ ବନ୍ଦ କରେ।
- `runPostCallHooks(response, context)` — ପ୍ରତିକ୍ରିୟା ପାର୍ଶ୍ୱରେ ସମାନ ପ୍ରବାହ।
- `resetGuardrailsForTests({ registerDefaults })` — ସ୍ୱଚ୍ଛ ପରୀକ୍ଷଣ ପୃଥକୀକରଣ ପାଇଁ ସ୍ଥିତି ସଫା କରେ ଏବଂ ଇଚ୍ଛାନୁସାରେ
  ଡିଫଲ୍ଟଗୁଡ଼ିକୁ ପୁନଃ ପଞ୍ଜୀକୃତ କରେ।

ଉଭୟ ରନର୍ `{ blocked, payload|response, results, guardrail?, message? }`
ଫେରାନ୍ତି, ଯେଉଁଠାରେ `results` ହେଉଛି `GuardrailExecutionResult` ରେକର୍ଡଗୁଡ଼ିକର ଏକ ଆରେ, ଯେଉଁଥିରେ
ପ୍ରତ୍ୟେକ ଗାର୍ଡରେଲ୍ ପାଇଁ `blocked`, `skipped`, `modified`, `error`, ଏବଂ `meta` ଫିଲ୍ଡ ଅନ୍ତର୍ଭୁକ୍ତ ଥାଏ,
ଯାହା ଟ୍ରେସିଂ ପାଇଁ ଉପଯୋଗୀ।

### ପ୍ରତି ଅନୁରୋଧରେ ଗାର୍ଡରେଲ୍ଗୁଡ଼ିକୁ ଅକ୍ଷମ କରିବା

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` ବର୍ତ୍ତମାନ ଅନୁରୋଧ ପାଇଁ ଏଡ଼ାଇ ଦିଆଯିବା ଉଚିତ ଗାର୍ଡରେଲ୍ ନାମଗୁଡ଼ିକର ଏକ ପୁନରାବୃତ୍ତି-ମୁକ୍ତ ତାଲିକା ସଂଗ୍ରହ କରେ। ପାଞ୍ଚଟି ଚ୍ୟାନେଲ୍ ଅଛି, ଯାହାକୁ ଏହି କ୍ରମରେ ପଢ଼ାଯାଇ ଗୋଟିଏ ତାଲିକାରେ ମିଶ୍ରଣ କରାଯାଏ
(ପୁନରାବୃତ୍ତି ହଟାଇବା ସମୟରେ ପ୍ରଥମ ଘଟଣାଟି ରହିଥାଏ):

1. `apiKeyInfo.disabledGuardrails`
2. ଅନୁରୋଧ ବଡିର `disabledGuardrails` (ଶୀର୍ଷ-ସ୍ତର)
3. ଅନୁରୋଧ ବଡିର `metadata.disabledGuardrails` (କେବଳ `metadata` ଏକ ଅବଜେକ୍ଟ ହୋଇଥିଲେ)
4. ହେଡର୍ `x-omniroute-disabled-guardrails`
5. ପୁରୁଣା ହେଡର୍ `x-disabled-guardrails`

ଦୁଇଟି ହେଡର୍ ସହିତ ସମସ୍ତ ପାଞ୍ଚଟି ଚ୍ୟାନେଲ୍କୁ ମିଶ୍ରଣ କରାଯାଏ: `x-omniroute-disabled-guardrails` ଏବଂ `x-disabled-guardrails` ଉଭୟ ପଠାଇଲେ ସେମାନଙ୍କ ତାଲିକାର ସଂଯୁକ୍ତ ସମୁଚ୍ଚୟକୁ ଏଡ଼ାଇ ଦିଆଯାଏ, ଏବଂ ଏକ ଖାଲି ଆଧୁନିକ ହେଡର୍ ଆଉ ପୁରୁଣାଟିକୁ ଲୁଚାଏ ନାହିଁ
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412),
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805)-ରେ ସମାଧାନ କରାଯାଇଛି)।

ମୂଲ୍ୟଗୁଡ଼ିକ ଷ୍ଟ୍ରିଙ୍ଗର ଆରେ କିମ୍ବା କମା ଦ୍ୱାରା ପୃଥକ ହୋଇଥିବା ଷ୍ଟ୍ରିଙ୍ଗ ହୋଇପାରେ; ନାମଗୁଡ଼ିକୁ ଟ୍ରିମ୍ କରାଯାଇ ଲୋୟରକେସ୍ କେବାବ୍-କେସ୍କୁ ସ୍ୱାଭାବିକୀକୃତ କରାଯାଏ (`pii_masker` → `pii-masker`), ଏବଂ ଖାଲି
ଏଣ୍ଟ୍ରିଗୁଡ଼ିକୁ ବାଦ ଦିଆଯାଏ। ଫଳାଫଳଟି `context.disabledGuardrails`
ମାଧ୍ୟମରେ ରେଜିଷ୍ଟ୍ରିକୁ ପଠାଯାଏ, ଯାହା ମେଳ ଖାଉଥିବା ଗାର୍ଡରେଲ୍ଗୁଡ଼ିକୁ ଏଡ଼ାଇ ଦିଏ (`results`-ରେ `skipped: true`)।

ଅକ୍ଷମ ତାଲିକା କେବଳ **ରେଜିଷ୍ଟ୍ରି**କୁ ପ୍ରଭାବିତ କରେ। ପ୍ରମ୍ପ୍ଟ-ଇଞ୍ଜେକ୍ସନ୍ `block` ମୋଡ୍
ଏକ ବାଧ୍ୟତାମୂଳକ ସୀମା: ଇଞ୍ଜେକ୍ସନ୍-ଗାର୍ଡ ମିଡଲୱେର୍
(`src/middleware/promptInjectionGuard.ts`) କଲର୍-ନିୟନ୍ତ୍ରିତ କୌଣସି ଅକ୍ଷମ ତାଲିକା ବିନା `evaluatePromptInjection()`
କୁ କଲ୍ କରେ (ଏହା ପୂର୍ବରୁ କରୁଥିବା ଅକାର୍ଯ୍ୟକର
`resolveDisabledGuardrails({ body })` କଲ୍ଟି
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934)-ରେ ହଟାଇ ଦିଆଯାଇଥିଲା), ତେଣୁ
`prompt-injection`କୁ ଅକ୍ଷମ କରୁଥିବା ଏକ ଅନୁରୋଧ ତଥାପି `block` ମୋଡ୍ରେ ପ୍ରତ୍ୟାଖ୍ୟାନ ହୁଏ। ଏହା
ଡିଜାଇନ୍ ଅନୁଯାୟୀ। ଅକ୍ଷମ ଚ୍ୟାନେଲ୍ଗୁଡ଼ିକ କଲର୍-ନିୟନ୍ତ୍ରିତ (ଅନୁରୋଧ ବଡି,
ମେଟାଡାଟା, ହେଡର୍ଗୁଡ଼ିକ), ଏବଂ ଅପରେଟର୍ ସେଟ୍ କରିଥିବା ଏକ ସୁରକ୍ଷା
ନିୟନ୍ତ୍ରଣକୁ ବନ୍ଦ କରିବାରେ କଲର୍ ସକ୍ଷମ ହେବା ଉଚିତ ନୁହେଁ
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413))। [#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412)-ର ହେଡର୍
ସଂଯୁକ୍ତ ସମୁଚ୍ଚୟ କେବଳ କେଉଁ ରେଜିଷ୍ଟ୍ରି ଗାର୍ଡରେଲ୍ଗୁଡ଼ିକୁ ଏଡ଼ାଇ ଦିଆଯାଏ ତାହା ପରିବର୍ତ୍ତନ କରେ; ଏହା କୌଣସି କ୍ଲାଏଣ୍ଟକୁ

## କାର୍ଯ୍ୟନିର୍ବାହ କ୍ରମ

`src/sse/handlers/chat.ts` ଏବଂ `open-sse/handlers/chatCore.ts` ( [କଭରେଜ ଏବଂ ସୀମା](#coverage-and-limits) ଅଧୀନରେ ତାଲିକାଭୁକ୍ତ ଚାଟ୍-ପରିବାର ରୁଟଗୁଡ଼ିକ) ମାଧ୍ୟମରେ ଯାଉଥିବା ପ୍ରତ୍ୟେକ ଅନୁରୋଧ ପାଇଁ:

1. `resolveDisabledGuardrails(...)` API କୀ, ବଡି ଏବଂ ହେଡରରୁ ସ୍କିପ୍ ତାଲିକା ତିଆରି କରେ।
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ବର୍ଦ୍ଧମାନ ପ୍ରାଥମିକତା କ୍ରମରେ ଗାର୍ଡରେଲଗୁଡ଼ିକୁ ଚଲାଏ:
   - ଅକ୍ଷମ ଗାର୍ଡରେଲଗୁଡ଼ିକ `skipped` ଭାବରେ ରେକର୍ଡ ହୁଏ।
   - ପ୍ରତ୍ୟେକ ଗାର୍ଡରେଲର `preCall` `modifiedPayload` ମାଧ୍ୟମରେ ପେଲୋଡ଼କୁ ପୁନଃଲେଖନ କରିପାରେ।
   - ପ୍ରଥମ `block: true` ଶୃଙ୍ଖଳାକୁ ସର୍ଟ-ସର୍କିଟ୍ କରେ ଏବଂ ହ୍ୟାଣ୍ଡଲର ଏକ ଗାର୍ଡରେଲ ପ୍ରତ୍ୟାଖ୍ୟାନ ପ୍ରତିକ୍ରିୟା ଫେରାଏ।
3. (ସମ୍ଭାବ୍ୟ ପୁନଃଲିଖିତ) ପେଲୋଡ଼ କମ୍ବୋ ରାଉଟିଂ ଏବଂ ଅପଷ୍ଟ୍ରିମ୍ ଡିସ୍ପ୍ୟାଚ୍ ଭିତରକୁ ଯାଏ।
4. **କେବଳ ଅଣ-ଷ୍ଟ୍ରିମିଂ:** ପ୍ରତିକ୍ରିୟା ସଂଯୋଜିତ ହେବା ପରେ, `guardrailRegistry.runPostCallHooks(...)` ପ୍ରତିକ୍ରିୟା ଉପରେ ସେହି ଶୃଙ୍ଖଳା ଚଲାଏ। ଏଠାରେ `block: true` ଅପଷ୍ଟ୍ରିମ୍ ପ୍ରତିକ୍ରିୟାକୁ ବାଦ ଦିଏ ଏବଂ HTTP 400 ଫେରାଏ। ଷ୍ଟ୍ରିମ୍ ହୋଇଥିବା ପ୍ରତିକ୍ରିୟାଗୁଡ଼ିକ ଏହି ପଦକ୍ଷେପକୁ ସମ୍ପୂର୍ଣ୍ଣ ବାଦ ଦିଏ।

ଯେଉଁ ଗାର୍ଡରେଲଗୁଡ଼ିକ ଏକ୍ସେପ୍ସନ୍ ଫିଙ୍ଗନ୍ତି ସେଗୁଡ଼ିକ `error: <message>` ସହିତ ରେକର୍ଡ ହୁଏ ଏବଂ `logger.warn` ମାଧ୍ୟମରେ ଲଗ୍ ହୁଏ, କିନ୍ତୁ ଶୃଙ୍ଖଳା ଜାରି ରହେ — ଡିଜାଇନ୍ ଅନୁସାରେ ଫେଲ୍-ଓପନ୍।

### ଯାହା କଭର ହୋଇନାହିଁ

- **ମିଡିଆ, ଏମ୍ବେଡିଂ ଏବଂ ଡାଟା ରୁଟ୍** (`/v1/images/*`, `/v1/embeddings`,
  `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`,
  `/v1/rerank`, `/v1/search`, `/v1/moderations`) କେବେ ରେଜିଷ୍ଟ୍ରିରେ ପହଞ୍ଚେ ନାହିଁ। ସେଠାରେ କୌଣସି
  PII ମାସ୍କିଂ, କ୍ରେଡେନସିଆଲ ମାସ୍କିଂ କିମ୍ବା ମୋଡାଲିଟି ବ୍ରିଜ୍ ଚାଲେ ନାହିଁ। ସେମାନଙ୍କର ଏକମାତ୍ର
  ଯାଞ୍ଚ ହେଉଛି ଲିଗାସି ଇଞ୍ଜେକ୍ସନ୍-ଗାର୍ଡ ମିଡଲୱେୟାର।
- **ଷ୍ଟ୍ରିମ୍ ହୋଇଥିବା ପ୍ରତିକ୍ରିୟା** କୌଣସି ପୋଷ୍ଟ-କଲ୍ ଗାର୍ଡରେଲ ପାଏ ନାହିଁ: `pii-masker` କିମ୍ବା
  `credential-masker` ପୋଷ୍ଟ-କଲ୍ ନାହିଁ, ଏବଂ ପୋଷ୍ଟ-କଲ୍ ବ୍ଲକ୍ ନାହିଁ। କେବଳ ଷ୍ଟ୍ରିମିଂ PII
  ଟ୍ରାନ୍ସଫର୍ମ ପ୍ରଯୁଜ୍ୟ ହୁଏ (`PII_RESPONSE_SANITIZATION` ଚାଲୁ ଥିଲେ)। ଏକ ଷ୍ଟ୍ରିମ୍ ହୋଇଥିବା
  ପ୍ରତିକ୍ରିୟାରେ ପ୍ରତିଧ୍ୱନିତ କ୍ରେଡେନସିଆଲ ରିଡାକ୍ଟ ହୁଏ ନାହିଁ।
- **ଅକ୍ଷମ ଚ୍ୟାନେଲ ବନାମ ମିଡଲୱେୟାର (ଡିଜାଇନ୍ ଅନୁସାରେ):** ମିଡଲୱେୟାର
  `evaluatePromptInjection()` ପ୍ରତି ନିଜର କଲ୍ ସହିତ ପ୍ରମ୍ପ୍ଟ ଇଞ୍ଜେକ୍ସନ୍ ମୂଲ୍ୟାଙ୍କନ କରେ, କୌଣସି
  କଲର୍-ନିୟନ୍ତ୍ରିତ ଅକ୍ଷମ ତାଲିକା ପାସ୍ ନକରି। `block` ମୋଡ୍ ଏକ ବାଧ୍ୟତାମୂଳକ ସୀମା ଯାହାକୁ
  କଲର୍-ନିୟନ୍ତ୍ରିତ ଅକ୍ଷମତାଗୁଡ଼ିକ ଅତିକ୍ରମ କରିପାରିବେ ନାହିଁ, ଚାଟ୍-ପରିବାର ରୁଟଗୁଡ଼ିକ ସହିତ
  ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413))। `prompt-injection` ଅକ୍ଷମ
  କରିବା କେବଳ ରେଜିଷ୍ଟ୍ରି ଗାର୍ଡରେଲକୁ ଛାଡ଼ିଦିଏ।

### ପୋଷ୍ଟ-କଲ୍ ପୂର୍ବରୁ ପ୍ରତିକ୍ରିୟା କଣ ଦେଖେ

ଅଣ-ଷ୍ଟ୍ରିମିଂ ପଥରେ କ୍ରମ ହେଉଛି: ମେମୋରୀ ଏକ୍ସଟ୍ରାକ୍ସନ → ବିଲ୍ଟ-ଇନ୍ ଟୁଲ୍ ଏକ୍ଜିକ୍ୟୁସନ → ପୋଷ୍ଟ-କଲ୍ ଗାର୍ଡରେଲ → ପୋଷ୍ଟ-କଲ୍ ବ୍ଲକ୍ ଏକ୍ଜିଟ → ସେମାଣ୍ଟିକ୍-କ୍ୟାଚ୍ ଷ୍ଟୋର।

- **ମେମୋରୀ ଏକ୍ସଟ୍ରାକ୍ସନ** ଏବଂ **ଟୁଲ୍ ଏକ୍ସିକ୍ୟୁସନ** ପୋଷ୍ଟ୍-କଲ୍ ଗାର୍ଡରେଲ୍ଗୁଡ଼ିକ ଏହାକୁ ପୁନଃଲେଖନ କିମ୍ବା ବ୍ଲକ୍ କରିବା ପୂର୍ବରୁ ପ୍ରତିକ୍ରିୟା ଦେଖନ୍ତି। [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401) ଠାରୁ, ଯେତେବେଳେ `PII_RESPONSE_SANITIZATION` ଚାଲୁ ଥାଏ (ଷ୍ଟ୍ରିମିଂ ଏବଂ ଅ-ଷ୍ଟ୍ରିମିଂ ଉଭୟ), ମେମୋରୀ ଏକ୍ସଟ୍ରାକ୍ସନ ଏକ୍ସଟ୍ରାକ୍ଟ କରାଯାଇଥିବା ଟେକ୍ସଟ୍କୁ `sanitizePII` ମାଧ୍ୟମରେ ଚଲାଏ, କିନ୍ତୁ ପୋଷ୍ଟ୍-କଲ୍ ପରେ ବ୍ଲକ୍ ହେଉଥିବା ଏକ ପ୍ରତିକ୍ରିୟା ତଥାପି ମେମୋରୀ ଏବଂ ଟୁଲ୍ଗୁଡ଼ିକୁ ଦିଆଯାଇଛି।
- **ସେମାଣ୍ଟିକ୍ କ୍ୟାଚ୍** ପୋଷ୍ଟ୍-କଲ୍ ପରେ ପ୍ରତିକ୍ରିୟା ସଂରକ୍ଷଣ କରେ, ତେଣୁ ଏହା ପୁନଃଲିଖିତ ପ୍ରତିକ୍ରିୟା ସଂରକ୍ଷଣ କରେ, ଏବଂ ବ୍ଲକ୍ ହୋଇଥିବା ପ୍ରତିକ୍ରିୟା କେବେ ବି କ୍ୟାଚ୍ ହୁଏ ନାହିଁ। କ୍ୟାଚ୍ ଏଣ୍ଟ୍ରିଗୁଡ଼ିକ ପ୍ରତି API କି ଅନୁସାରେ କୀ କରାଯାଇଥାଏ।

## କଷ୍ଟମ୍ ଗାର୍ଡରେଲ୍ସ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ପଦକ୍ଷେପଗୁଡ଼ିକ:

1. `src/lib/guardrails/myGuardrail.ts` ତିଆରି କରନ୍ତୁ ଯାହା `BaseGuardrail` କୁ ଏକ୍ସଟେଣ୍ଡ୍ କରେ।
2. `preCall` ଏବଂ/କିମ୍ବା `postCall` ଲାଗୁ କରନ୍ତୁ।
3. ଇମ୍ପୋର୍ଟ ସମୟରେ ପଞ୍ଜିକରଣ କରନ୍ତୁ (`registerDefaultGuardrails` ରୁ ପୁଶ୍ କରନ୍ତୁ) କିମ୍ବା
   ରନ୍ଟାଇମରେ `guardrailRegistry.register(...)` କୁ କଲ୍ କରନ୍ତୁ — ରେଜିଷ୍ଟ୍ରି ସମାନ ସାଧାରଣୀକୃତ ନାମ ଥିବା
   ପୂର୍ବ ଗାର୍ଡରେଲ୍କୁ ବଦଳାଇଦିଏ।
4. `tests/unit/` ଅଧୀନରେ ପରୀକ୍ଷଣ ଯୋଡ଼ନ୍ତୁ (ବିଦ୍ୟମାନ ଉଦାହରଣ:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)।

## ପରୀକ୍ଷଣ

ଜଣାଶୁଣା ସ୍ଥିତିରୁ ଆରମ୍ଭ କରିବା ପାଇଁ ପରୀକ୍ଷଣ ମଧ୍ୟରେ `resetGuardrailsForTests()` ବ୍ୟବହାର କରନ୍ତୁ।
ଏକ ଖାଲି ରେଜିଷ୍ଟ୍ରି ସହିତ ଆରମ୍ଭ କରିବା ଏବଂ କେବଳ ପରୀକ୍ଷାଧୀନ ଗାର୍ଡରେଲ୍ଗୁଡ଼ିକୁ ପଞ୍ଜିକରଣ କରିବା ପାଇଁ
`{ registerDefaults: false }` ପାସ୍ କରନ୍ତୁ। Vision Bridge ଡିପେଣ୍ଡେନ୍ସି
ଇଞ୍ଜେକ୍ସନ୍ (`deps.getSettings`, `deps.callVisionModel`) ଗ୍ରହଣ କରେ; Audio Bridge ସେଟିଂସ୍, କ୍ଷମତା, STT ମଡେଲ୍ ଚୟନ, କ୍ରେଡେନ୍ସିଆଲ୍
ଯାଞ୍ଚ, ଏବଂ ଟ୍ରାନ୍ସକ୍ରିପ୍ସନ୍ ପାଇଁ ସମାନ ସିମ୍ଗୁଡ଼ିକୁ ପ୍ରକାଶ କରେ। ତେଣୁ ପରୀକ୍ଷଣଗୁଡ଼ିକ DB
କିମ୍ବା ନେଟୱାର୍କ ଆକ୍ସେସ୍ ବିନା ଉଭୟ ଫ୍ଲୋକୁ ପରୀକ୍ଷା କରିପାରିବେ।

## ଇଞ୍ଜେକ୍ସନ୍-ଗାର୍ଡ ରୁଟ୍ କଭରେଜ୍ ଏବଂ ରେଡ୍-ଟିମ୍ (ଫେଜ୍ 8 · ବ୍ଲକ୍ D)

ଇଞ୍ଜେକ୍ସନ୍-ଗାର୍ଡ (`createInjectionGuard` / `withInjectionGuard`) ସମସ୍ତ ରୁଟ୍କୁ କଭର କରେ
ଯାହା ଉପଭୋକ୍ତା ପ୍ରମ୍ପ୍ଟ ଗ୍ରହଣ କରେ। ଏହା `INJECTION_GUARD_MODE` କୁ ସମ୍ମାନ କରେ (ଡିଫଲ୍ଟ `warn` = କେବଳ ଲଗ୍;
`block` = HTTP 400 `SECURITY_001` ଫେରାଏ)।

| ପ୍ରକାର             | ରୁଟ୍ଗୁଡ଼ିକ                                                                                                                                           | ଡିଫଲ୍ଟ ମୋଡ୍ |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| ଟେକ୍ସଟ୍ (ବିଦ୍ୟମାନ) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn        |
| ଜେନେରେଟିଭ୍         | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn        |
| ଡାଟା               | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn        |

ଟେକ୍ସଟ୍ ଏକ୍ସଟ୍ରାକ୍ସନ୍ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` କୁ କଭର କରେ।

**ରେଡ୍-ଟିମ୍ (ରାତ୍ରୀ, `nightly-llm-security.yml`):** promptfoo ଯାଞ୍ଚ କରେ ଯେ ପ୍ରତ୍ୟେକ ରୁଟ୍
`INJECTION_GUARD_MODE=block` ରେ OWASP-LLM କର୍ପସ୍ କୁ ବ୍ଲକ୍ କରେ; garak ପ୍ରୋବ୍ ଚଲାଏ (ସିକ୍ରେଟ୍ ବିନା ଛାଡିଦିଏ)।
`moderations` ସ୍ଥିରତା ପାଇଁ ଅନ୍ତର୍ଭୁକ୍ତ। ବ୍ଲକ୍ ମୋଡ୍ ଏକ ବାଧ୍ୟତାମୂଳକ ସୀମା: `evaluatePromptInjection()`
ମିଡଲୱେର୍ ଏହାକୁ ପାସ୍ କରୁଥିବା ପ୍ରତି-ଅନୁରୋଧ ନିଷ୍କ୍ରିୟ ତାଲିକାକୁ ଅଣଦେଖା କରେ, ତେଣୁ `disabledGuardrails`
ଏହାରୁ ଏକ ରୁଟ୍କୁ **ମୁକ୍ତ** କରେ ନାହିଁ ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413))।

ରାତ୍ରୀ ୱାର୍କଫ୍ଲୋ (`.github/workflows/nightly-llm-security.yml`, cron + ମାନୁଆଲ୍
ଡିସ୍ପାଚ୍) ରେ ଦୁଇଟି ଜବ୍ ଅଛି:

- **`promptfoo-guard` (ବ୍ଲକିଂ)** — `INJECTION_GUARD_MODE=block` ସହିତ
  `promptfoo eval -c promptfooconfig.yaml` ଚଲାଏ। ପ୍ରତ୍ୟେକ ବିରୋଧୀ କେସ୍ (ଉଦାହରଣ ସ୍ୱରୂପ "ignore all
  previous instructions…", DAN-ଶୈଳୀ ଜେଲବ୍ରେକ୍ଗୁଡ଼ିକ) ନିଶ୍ଚିତ କରେ ଯେ ପ୍ରତିକ୍ରିୟାରେ
  `error.code === "SECURITY_001"` ଅଛି, ଅର୍ଥାତ୍ ଗାର୍ଡ ପ୍ରକୃତରେ ଅନୁରୋଧକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରିଛି।
- **`garak` (ପରାମର୍ଶଦାୟକ)** — ସ୍ଥାନୀୟ OmniRoute ଇନଷ୍ଟାନ୍ସ (`http://localhost:20128/v1`)
  ବିରୁଦ୍ଧରେ garak `--probes promptinject,dan,leakreplay` ଚଲାଏ। ଏକ
  ପ୍ରୋଭାଇଡର୍ ସିକ୍ରେଟ୍ (`PROMPTFOO_PROVIDER_KEY`) ଉପରେ ନିର୍ଭରଶୀଳ; ସୁନ୍ଦର ଭାବରେ ଛାଡିଦିଏ ଏବଂ
  `|| true` ସହିତ ସଫିକ୍ସ ହୋଇଥାଏ, ତେଣୁ ଏହା CI ଫେଲ୍ ନକରି ରିପୋର୍ଟ କରେ।

ଗାର୍ଡ ହେଲ୍ପର୍ (`createInjectionGuard` / `withInjectionGuard`) ର କଭରେଜ୍
ପ୍ରତ୍ୟେକ ପ୍ରମ୍ପ୍ଟ-ଧାରୀ `/v1` ରୁଟ୍କୁ ବ୍ୟାପିଥାଏ; ପ୍ରମ୍ପ୍ଟ ଟେକ୍ସଟ୍
`src/shared/utils/inputSanitizer.ts` ରେ ଥିବା `extractMessageContents()` ଦ୍ୱାରା
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ରୁ ନିଆଯାଏ।
