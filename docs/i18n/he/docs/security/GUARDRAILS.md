> **מקור האמת:** `src/lib/guardrails/`
> **עדכון אחרון:** 2026-10-17 — v3.8.52 (נוסף הסעיף [כיסוי ומגבלות](#coverage-and-limits):
> לאילו נתיבים ומסלולי תגובה מגיעים ה-hooks, כותרות ההשבתה הממוזגות (#16412), מצב
> חסימת הזרקה כגבול חובה (#16413), ומה נחשף לתגובה לפני שלב post-call)

מנגנוני הגנה אוכפים בטיחות, מדיניות והתמרות תוכן בגבול שבין
OmniRoute לבין ספקים במעלה הזרם. כל מנגנון הגנה יכול לבדוק (ולפי הצורך
לדחות, להתמיר או להוסיף הערות אל) מטעני בקשות (`preCall`) ותגובות
במעלה הזרם (`postCall`).

המערכת פועלת בגישת **fail-open**: אם מנגנון הגנה זורק חריגה בזמן הריצה, ה-registry
מתעד את השגיאה וממשיך למנגנון ההגנה הבא במקום להכשיל את
הבקשה. חסימה היא החלטה מפורשת (`block: true`), ולעולם אינה מתרחשת בטעות.
החריג היחיד הוא בקשה שבוטלה: כאשר ה-`signal` של הקורא מבוטל,
מנגנון הגנה שזורק חריגה גורם לדחיית הרצת ה-hook במקום לדילוג עליו.

ה-hooks **אינם** פועלים בכל נתיב או בכל תגובה. קראו את
[כיסוי ומגבלות](#coverage-and-limits) לפני שתסתמכו על מנגנון הגנה כבקרת
אבטחה.

## מנגנוני הגנה מובנים

בעת הייבוא, ה-registry טוען אוטומטית שישה מנגנוני הגנה לפי סדר עדיפות
(ראו `registry.ts` ← `registerDefaultGuardrails()`):

| עדיפות | שם                  | שלב(ים)        | קובץ                  |
| ------ | ------------------- | -------------- | --------------------- |
| `5`    | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`    | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`    | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`   | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`   | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`   | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

מספרי עדיפות נמוכים יותר מופעלים **ראשונים**.

### גשר ראייה (`visionBridge.ts`) — גשר מודאליות PR-1

למודל הבסיס GLM 5.3 ול-`glm-5.3-{low,high,max}` יש מטא-נתוני
registry/spec מפורשים מסוג `supportsVision:false`. גרסאות GLM 5.3 Flash
נותרות מודלים בעלי יכולת ראייה מובנית. הנתיב `/v1/messages` של Claude Code נכנס
לשרשרת מנגנוני ההגנה המשותפת של `handleChat` בשלב pre-call **לפני** תרגום
מ-Claude ל-OpenAI; יש לתאר או לטפל בתמונות מקוננות בתוצאות הכלי `Read`
לפני שתרגום זה מעלה אותן לתוכן `image_url` של OpenAI (#17069).

מיירט בקשות המכילות תמונות ומיועדות ל**מודלים ללא יכולת ראייה**, ואז
מנתב מחדש את הבקשה כולה למודל בעל יכולת ראייה או מחליף את חלקי
התמונה בתיאורים טקסטואליים שמופקים באמצעות מודל ראייה ניתן להגדרה לפני
הקריאה במעלה הזרם. כך ספקים התומכים בטקסט בלבד יכולים לטפל
באופן שקוף במטענים מרובי-מודאליות.

זרימה:

1. דלגו אם מודל היעד כבר תומך בראייה (אלא אם הוא מופיע
   ברשימת הגישור הכפוי `isVisionBridgeForcedModel`).
2. חלצו חלקי תמונה באמצעות `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), שמעבירה את הטיפול אל **גלאי המדיה
   המאוחד** `detectMediaParts()` שב-`open-sse/utils/mediaParts.ts` — מקור
   האמת היחיד המשותף למסנן התאימות המשולב.
   החילוץ מוגבל ברשימת היתרים למבנים ש-`replaceImageParts` יכול לשלב
   בחזרה (חוזה החילוץ↔החלפה): `image_url` של OpenAI, מקור base64 של Anthropic
   מסוג `source.type:"base64"`, כתובת URL של Anthropic מסוג `source.type:"url"`, ו-`input_image`
   של Responses API. גם תמונות תואמות המקוננות בתוך
   `tool_result.content` של Claude Code ובפלטי כלים של Responses מחולצות
   ומוחלפות בנתיבים המקוריים שלהן; מבנים הכוללים מחוון בלבד מיועדים למסנן
   המשולב ואינם מחולצים.
   דלגו אם לא נמצאו תמונות.
3. קבעו את תצורת זמן הריצה באמצעות `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): למפתחות ההגדרות החדשים `modalityBridge*`
   יש קדימות; מפתחות `visionBridge*` הישנים נשארים כ**חלופה למחזור
   אחד** (חלון חזרה לאחור). דלגו לפני מעבר כלשהו על המדיה כאשר
   הגשר מושבת.
4. בורר המצבים (`modalityBridgeVisionMode`, ראו טבלה להלן) מחליט בין
   ניתוב מחדש לתיאור. ניתוב מחדש מחזיר `modifiedPayload` שבו מוחלף רק `model`,
   יחד עם מטא-נתונים `{ rerouted, fromModel, toModel, imagesKept }`.
5. נתיב התיאור: הגבילו את התמונות ל-`maxImages`, הרכיבו את ההנחיה המותאמת למשימה,
   בדקו את מטמון התיאורים, קראו למודל הראייה **במקביל**
   (`Promise.allSettled`), והזריקו במקומן חלקי טקסט מסוג `[Image N]: <description>`.
   תיאור שנכשל מחזיר `null`: התמונה הגולמית נשמרת עבור יעדים
   לא ידועים או בעלי יכולת ראייה (#4012), אך **יעד ישיר שאושר כתומך
   בטקסט בלבד** או שילוב ללא יכולת ראייה מקבל מציין טקסט מפורש
   מסוג `(unavailable — no vision-capable provider connected)` עבור
   כל תמונה שלא תוארה, לרבות כשלים חלקיים ותמונות מעבר למגבלת
   קריאות התיאור (#17069). חלופת התיאור הקיימת עבור שילוב שבו כל הניסיונות נכשלו
   נשארת במקומה (#8430).
6. החזירו `modifiedPayload` יחד עם מטא-נתונים (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### בורר מצבים (`modalityBridgeVisionMode`)

| מצב        | ברירת מחדל | התנהגות                                                                                                                                                                                                                                   |
| ---------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔          | היוריסטיקה מדור קודם, ללא שינוי (#6640/#7204): מודלים שאינם משולבים/`auto/` מנותבים מחדש למודל הראייה הטוב ביותר, אלא אם למודל המקורי כבר יש פרטי גישה שמישים (ואז מתבצע תיאור); יעדים משולבים תמיד מבצעים תיאור.                         |
| `describe` |            | תמיד מתבצע תיאור — מדלגים לחלוטין על מקטע הניתוב מחדש; המודל שבחר המשתמש תמיד משיב.                                                                                                                                                       |
| `reroute`  |            | כפיית ניתוב מחדש: מתבצע מעקף של מנגנון ההגנה המשאיר מודל בעל פרטי גישה. מנגנון ההגנה על פרטי הגישה של **יעד** הניתוב מחדש עדיין חל — כאשר אין יעד ראייה שמיש, הגשר חוסם עם שגיאה ברורה במקום לתאר או לשלוח תמונות גולמיות ליעד טקסט בלבד. |

מצבים כפויים עוצרים את התהליך **לפני** הפעלת ההיוריסטיקה האוטומטית; ההתנהגות של `auto`
זהה ברמת הבתים למנגנון ההגנה שהיה קיים לפני PR-1.

#### היקף מפתח API (`visionBridgeKeyScope.ts`)

כאשר מפתח ה-API של מבצע הקריאה מגביל את `allowedConnections`, את מאגרי המכסות
(`allowedQuotas`) או את המודלים (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), הגשר בוחר רק
מודלים לניתוב מחדש ולתיאור שבהם המפתח רשאי להשתמש, דרך חיבורים שבהם המפתח רשאי
להשתמש. לאחר מכן, קריאת התיאור תמיד עוברת דרך הלולאה העצמית של OmniRoute עם
הכותרת `x-omniroute-self-loop-key-id`, כך שבקשת הצ'אט המקבלת אוכפת שוב את
מדיניות החיבורים והמודלים של אותו מפתח. `enforceApiKeyPolicy()` מכבדת את הכותרת
הזו רק בצירוף אסימון הנושא של הלולאה העצמית, ולכן היא יכולה רק לצמצם את הגישה,
ומזהה שלא ניתן לפתור נדחה.

אם אף מודל ראייה אינו מורשה עבור המפתח, **יעד שאומת כיעד טקסט בלבד**
דוחה את בקשת התמונה מקומית עם HTTP 400 ברור, במקום להעביר בתי תמונה לשירות
במעלה הזרם שאינו מסוגל לטפל בהם (#17069). עבור יעדים שיכולת הראייה שלהם אינה
ידועה או שהיא מובנית, נתיב התיאור שומר על התנהגות הכשל-הפתוח הקודמת שלו
(מטא-נתונים `{ skipped: true, reason: "no_permitted_vision_model" }`).
בקשות ללא מפתח, ומפתחות ללא הגבלות אלה, מתנהגים בדיוק כפי שהתנהגו קודם.

#### הנחיית תיאור מודעת-משימה (`modalityBridgeVisionTaskAware`)

ברירת המחדל היא **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) מצרפת
את הטקסט של **הודעת המשתמש האחרונה** (מקוצר ל-500 תווים) להנחיית התיאור
הבסיסית, מכוונת את התיאור למה שהמשתמש ביקש בפועל
(תבנית codex-vision-proxy) ומבקשת ממודל הראייה לתמלל טקסט גלוי.
כאשר הדגל כבוי — או שאין טקסט משתמש — נעשה שימוש בהנחיה הבסיסית ללא שינוי.

הבקשה תואמת-OpenAI של לולאת התיאור העצמית (`callVisionModelSingle()`
ב-`visionBridgeHelpers.ts`) תמיד מבקשת `image_url.detail: "high"` —
ללא תנאי, עבור כל מבצע קריאה/ספק, וללא תלות באות כלשהו מהלקוח.
דגימה ברמת פירוט נמוכה פוגעת בדיוק ה-OCR בדיוק עבור משימת תמלול הטקסט
שהנחיה זו מבקשת, ולכן קריאת התיאור עצמה תמיד מבקשת רמת פירוט גבוהה, בלי קשר
לרמת הפירוט שבה השתמשה הבקשה הנכנסת המקורית. הדבר משפיע רק על גוף בקשת
התיאור הפנימית; הוא אינו משנה את האופן שבו OmniRoute מעביר את
`image_url.detail` של מבצע הקריאה בבקשה הראשית — ברירת המחדל הזו מוחלת
בנפרד, ורק עבור לקוחות OpenCode שזוהו, ב-`defaultImageDetail()`
(`open-sse/handlers/chatCore/upstreamBody.ts`). לענף פורמט התעבורה של
Anthropic בלולאת התיאור העצמית אין שדה `detail`, ואף אחת מברירות המחדל
אינה משפיעה עליו.

#### מגבלת פלט התיאור (`modalityBridgeVisionMaxChars`)

| מפתח                           | ברירת מחדל | טווח             |
| ------------------------------ | ---------- | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`        | `0` או 100–50000 |

`0` (ברירת המחדל) פירושו **ללא מגבלה** — התיאור שמוחזר על ידי
`callVisionModel()` מועבר ללא שינוי, וכך נשמרת ההתנהגות הקיימת.
כל ערך בטווח 100–50000 מקצר את התיאור ומוסיף את הסיומת
`…` לפני שהוא משולב מחדש בתור `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` ב-`src/lib/guardrails/visionBridge.ts`).
הגדילו ערך זה עבור משימות OCR עתירות פרטים שבהן המודל שבהמשך הזרם זקוק
לתמלול המלא; הקטינו אותו כדי להגביל את השימוש באסימונים במודלי ראייה
פטפטניים. שדה לוח הבקרה נמצא בחלונית Advanced של לשונית Vision
(`modality-bridge-max-chars` ב-`ModalityBridgeVisionTab.tsx`) ומעלה כל
ערך בין 1 ל-99 לרף התחתון של 100, תוך השארת `0` מפורש ללא שינוי —
`0` הוא ערך Zod תקף בפני עצמו
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), ולא רק
ברירת המחדל "לא מוגדר".

#### מטמון תיאור (`modalityBridge/bridgeCache.ts`)

מטמון LRU + TTL בזיכרון עבור פלטי תיאור, המשותף לכל התהליך.
מפתח = `sha256(imageRef + composedPrompt + configuredBridgeModel)` עם
מסגור של קידומת-אורך (ללא התנגשויות בין גבולות שדות). רכיב המודל הוא מודל
הגשר **שהוגדר**, ולא המודל שהשיב בפועל —
`callVisionModel` עשויה לבצע נסיגה פנימית, ויצירת מפתח לכל ניסיון הייתה
מפצלת את המטמון. תיאורים שנכשלו לעולם אינם נשמרים במטמון. הגדרות:

| מפתח                            | ברירת מחדל | טווח    |
| ------------------------------- | ---------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`     | —       |
| `modalityBridgeCacheTtlMinutes` | `60`       | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`      | 10–5000 |

#### נרמול תמונות מרוחקות (קריאת describe בלולאה עצמית/אחזור base64)

כאשר הגשר מאחזר בעצמו תמונה **מרוחקת** — קריאת ה-describe העצמית של Anthropic והמרת ה-base64 לפורמט claude-wire
(`ensureBase64ImagesForClaudeWire`), שתיהן באמצעות
`fetchRemoteImageAsDataUri()` בתוך `visionBridgeHelpers.ts` — ה-URI שנוצר
מועבר דרך `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) לפני הטמעתו בבקשה למודל הראייה.
תמונות גדולות מדי מוקטנות כך ש**הצלע הארוכה תהיה באורך 2048px** (בהתאם
למגבלת שינוי הגודל ש-OpenAI/Anthropic כבר מחילים בצד השרת), דבר שמפחית
את כמות הבתים המועלים ואת זמן ההשהיה מבלי לשנות את מה שמודל הראייה רואה. שינוי הגודל
משתמש ב-`sharp`, שנטען באמצעות ייבוא דינמי: בפלטפורמה שבה הטעינה של הקובץ
הבינארי המקורי שלו נכשלת, `normalizeDataUri()` **לעולם אינו זורק חריגה** — במקום זאת הוא
מעביר את הבתים המקוריים ללא שינוי, כך שמסלול ה-describe/המרת ה-base64
ממשיך לפעול תמיד. גם בתים שאינם תמונה (אחזור שלא החזיר תמונה
שניתנת לפענוח) מועברים ללא שינוי. נרמול זה מוגבל לתמונות שהגשר מאחזר
עבור הקריאה העצמית שלו — הוא לעולם אינו מוחל על מטען ההעברה הגולמי של המתקשר, בהתאם
לעקרון השינוי בהצטרפות מפורשת בלבד (כלל מחייב מס' 20).

`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,

אל המפתחות החדשים המתאימים (באופן אידמפוטנטי, ולעולם אינה דורסת ערך

#### כותרת שקיפות + סטטיסטיקות

תגובות שעברו טרנספורמציית describe כוללות
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(נבנה על ידי `buildModalityBridgeHeader()` בתוך `modalityBridge/bridgeStats.ts`,
ונחתם על ידי `withModalityBridgeHeader()` בתוך `src/sse/handlers/chatHelpers.ts`).
בקשות שנותבו מחדש **אינן** מקבלות כותרת — המטען לא השתנה והחלפת המודל
כבר גלויה בשדה `model` שבגוף התגובה.

`GET /api/modality-bridge/stats` (אימות ניהולי, באותה רמה כמו
`GET /api/settings`) מחזיר את המונים השמורים בזיכרון לכל מודאליות
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` עבור `vision`, `audio` ו-
`video`. `averageLatencyMs` משתמש ב-`latencySamples`, ולא בכל הניסיונות, בתור
המכנה; פעולה ללא מדידת זמן אינה מייצרת דגימה מלאכותית של אפס אלפיות השנייה.
`bridged` נשאר כינוי תואם לאחור להמרות מוצלחות;
ניסיונות שנכשלו אינם מגדילים אותו.
המונים מתאפסים עם הפעלת התהליך מחדש במכוון
(טלמטריה, לא הנהלת חשבונות).

#### הגדרת לוח המחוונים

העמוד הייעודי בלוח המחוונים הוא
`/dashboard/settings/modality-bridge`. הלשוניות `Vision`, `Audio`
ו-`Video`, הניתנות למיעון באמצעות URL, משמרות את פרמטרי השאילתה בעת החלפת הערך `tab`.
הלשונית Vision מציגה הפעלה, מצב, בחירת מודל (כולל ברירת המחדל
האוטומטית), ניסוח הנחיות המודע למשימה, מגבלות מתקדמות של זמן קצוב/תמונות/אורך תיאור/מטמון,
מוני זמן ריצה ובקשת דוגמה מוגנת. גם הלשונית Audio פעילה: היא מציגה
הפעלה, בורר מודלים ל-STT בלבד הכולל Auto, מגבלות זמן קצוב/אורך מרבי של קטע,
מוני אודיו ובדיקת דוגמה מסוג `input_audio`. הלשונית Video פעילה: היא מדווחת
על מצב זמן הריצה של FFmpeg/ffprobe — אחד מארבעה מצבי ממשק משתמש מפורשים (`unknown` בזמן
שהבדיקה מתבצעת או כאשר לא ניתן היה להשלים אותה, `restricted` כאשר מארח לוח המחוונים
אינו loopback ולכן הבדיקה מדולגת בצד הלקוח, `unavailable` לאחר ביצוע הבדיקה
ואישור שהכלים חסרים, או `available` יחד עם גרסאות FFmpeg/ffprobe) — שומרת
מגבלות הפעלה/מודל/פריימים/וידאו/זמן קצוב, מסננת את בורר המודלים למודלים
התומכים בראייה ומציגה מוני וידאו.

כרטיס Vision Bridge הקודם תחת הגדרות ה-AI הוא כעת קישור תאימות לעמוד
החדש; הוא כבר אינו מחזיק עותק נוסף של הטופס. Media Providers מקשר גם
תהליכי עבודה של Image-to-Text ו-Speech-to-Text ללשוניות המתאימות של Modality
Bridge, מבלי להסיר את סביבת הניסוי הקיימת של Speech-to-Text.

**עקיפת בקרת קבלה בלולאה עצמית:** כאשר קריאת ה-describe מנותבת דרך
לולאת ה-`/v1` העצמית של OmniRoute (מודל של ספק לא סטנדרטי), בקשת המשנה שולחת
`x-omniroute-admission-bypass: internal` ומאומתת באמצעות פרטי האימות שנפתרו
עבור הלולאה העצמית — ערך הסמן המקומי `sk_omniroute` במצב מקומי, או מפתח הסביבה
`OMNIROUTE_API_KEY` / `ROUTER_API_KEY` שהוגדר על ידי המפעיל (#1350), כך שגם
פריסות עם `REQUIRE_API_KEY=true` עדיין יכולות להריץ את קריאת ה-describe. העקיפה
מכובדת רק עבור פרטי האימות המדויקים האלה, ולכן לקוחות חיצוניים אינם יכולים להשתמש
בכותרת כדי לדלג על בקרת הקבלה.

ברירות המחדל הישנות נמצאות בתוך `src/shared/constants/visionBridgeDefaults.ts`;
ברירות המחדל החדשות עבור מצב/מודעות למשימה/מטמון ופותר ההגדרות נמצאים בתוך
`src/shared/constants/modalityBridgeDefaults.ts`. מנגנון ההגנה חושף אפשרות בנאי
`deps`, כך שבדיקות יכולות להזריק מימושים מדומים של `getSettings` ושל
`callVisionModel`.

### גשר אודיו (`audioBridge.ts`) — Modality Bridge PR-3

מיירט בקשות צ'אט המכילות אודיו לפני שהן מגיעות ליעד שלא ידוע כתומך
בקלט אודיו. הוא לעולם אינו מנתב מחדש את בקשת הצ'אט: חלקי האודיו מתומללים
דרך נקודת הקצה הרב-חלקית הקיימת, התואמת ל-OpenAI, ומודל הצ'אט שנבחר ממשיך
עם תמלילים טקסטואליים.

זרימה:

1. יש לקבוע את `supportsAudio` באמצעות `getResolvedModelCapabilities()`. מטא-נתונים מפורשים של מרשם הספקים מקבלים עדיפות, אחריהם מטא-נתונים סטטיים של המודל, ולבסוף `modalities_input` מסונכרן. רשימת קלט מוצהרת שאינה כוללת `audio` נותנת `false`; בהיעדר ראיות ליכולת, הערך נשאר `null`. גם `false` וגם `null` מפעילים את הגשר השמרני, בעוד `true` עוקף אותו.
2. יש לקבוע את הגדרות `modalityBridgeAudio*` ולחלץ מכל הודעה חלקי שמע ברמה העליונה שניתנים לשילוב, באמצעות המזהה המשותף `detectMediaParts()`. תצורות התעבורה הנתמכות הן `input_audio` של OpenAI,‏ `audio_url` ו-`source.media_type: "audio/*"`. שמע מקונן מזוהה לצורכי ניתוב, אך אינו מוסר בנתיב השילוב. היקף העבודה מוגבל באמצעות `modalityBridgeAudioMaxClips`; חלקים מאוחרים יותר נשארים ללא שינוי.
3. יש לכבד `provider/model` שהוגדר, או לאפשר ל-`selectAudioBridgeModel()` לעבור על `AUDIO_TRANSCRIPTION_PROVIDERS` לפי סדר קטלוג יציב ולבחור את המודל הראשון שעבורו קיים אישור גישה פעיל ושמיש של ספק.
4. `callAudioTranscription()` ממירה שמע בקידוד base64 או מסוג data URI ל-`file` רב-חלקי, או מורידה `audio_url` מרוחק דרך מנגנון ההגנה לתעבורה יוצאת ציבורית בלבד, עם קיבוע DNS ומגבלה של 25 MB. לאחר מכן היא שולחת באמצעות POST את הקובץ ואת המודל שנבחר ללולאה העצמית המקומית `/v1/audio/transcriptions`, עם אימות באמצעות `resolveSelfLoopBearer()`. נתיב התמלול הקיים מבצע חיפוש רגיל של אישורי גישה, טיפול בתקופות צינון ובמגבלות קצב, וניתוב לספק.
5. קריאות מוצלחות מחליפות את החלקים שלהן ב-`[Audio N]: <transcript>`. הקריאות רצות באמצעות `Promise.allSettled`: כשל נקודתי משמר את חלק השמע המקורי (#4012 contract). אם כל הקריאות נכשלות והוכח כי יעד החיפוש הוא `supportsAudio === false`, החלקים הופכים ל-`[Audio N]: (unavailable — no STT provider connected)` (#8430 contract). עבור יעד לא ידוע (`null`), תוצאה שבה כל הקריאות נכשלו נשארת ללא שינוי. יעד שהוכח כי הוא תומך בטקסט בלבד ושאין עבורו אישור גישה שמיש ל-STT מקבל את אותה תבנית מפורשת, ללא ביצוע קריאת רשת.

תמלולים מוצלחים משתמשים במטמון LRU/TTL הכלל-תהליכי של Modality Bridge. המפתח משלב את הפניית השמע, את תווית הפעולה היציבה `audio-transcription` ואת מודל ה-STT שנבחר; כשלים לעולם אינם נשמרים במטמון. ניסיונות שמע מעדכנים את המונים המשותפים `bridged`,‏ `cacheHits`,‏ `failures` ו-`lastUsedAt`. תגובות שעברו המרה כוללות את `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; בקשות שלא שונו אינן מקבלות מקטע Audio Bridge.

הגדרות זמן הריצה מגובות במסד נתונים ומאומתות באמצעות Zod:

| מפתח                          | ברירת מחדל | טווח                |
| ----------------------------- | ---------- | ------------------- |
| `modalityBridgeAudioEnabled`  | `true`     | —                   |
| `modalityBridgeAudioModel`    | `""`       | אוטומטי או מזהה STT |
| `modalityBridgeAudioTimeout`  | `60000`    | 1000–300000         |
| `modalityBridgeAudioMaxClips` | `3`        | 1–10                |

המטמון המשותף ממשיך להיות נשלט באמצעות `modalityBridgeCacheEnabled`,‏ `modalityBridgeCacheTtlMinutes` ו-`modalityBridgeCacheMaxEntries`.

### גשר וידאו (`videoBridge.ts`, `videoBridgePipeline.ts`)

מיירט חלקי וידאו ברמה העליונה ב-`messages` של Chat Completions וב-`input` של Responses API, לפני קריאה ליעד שלא ידוע כי קיימת בו תמיכה מובנית בווידאו. התצורות הנתמכות הן `input_video`,‏ `video_url`,‏ `video_source`, כתובות URL מסוג HTTPS וכתובות data URI מסוג `data:video/*;base64,...`. שמות קבצים רגילים בתוך טקסט אינם נחשבים לווידאו.

`VideoBridgeGuardrail.preCall`‏ (`videoBridge.ts`) אחראי על מעבר הבקשה, בדיקת היכולת והמדיניות, צבירה לכל בקשה ומטען התגובה. העבודה לכל סרטון — השגה, מטמון התוצאה המלאה, תיאור רצף פריימים (המשלב כל תמלול שמע שהוצהר בידי הקורא), ומדדים, ביטול וניקוי לכל ניסיון — מוסתרת מאחורי `processVideoPart` בתוך `videoBridgePipeline.ts`, שנקראת פעם אחת לכל חלק וידאו בתוך הלולאה של `preCall`. מודול זה גם מגדיר את גבולות היציאות המפורשים `VideoMediaBrokerPort` (השגת בתים וחילוץ פריימים שנדגמו), `VideoAudioTranscriptionPort` (שילוב תמלול שמע שהוצהר בידי הקורא עם הכתוביות של הפריימים שנדגמו) ו-`VideoDrilldownPort` (גבול השמירה של התעמקות בפריימים; טרם חובר ל-`processVideoPart` — כיום רק הנתיב הנפרד `/api/modality-bridge/video/drilldown` כותב רשומות התעמקות).

נתיב הבקשה הציבורי `/v1` לעולם אינו מייבא או מפעיל תהליך משנה. סרטונים מרוחקים מורדים תחת מגבלה של 50 MiB; לסרטוני base64 מוטבעים יש מגבלה שמרנית של 36 MiB לאחר פענוח לכל סרטון, כדי שמעטפת המודל, ההודעות והמסגור תוכל להישאר בתוך מגבלת הקבלה של בקשת JSON ציבורית, העומדת על 50 MiB. האורך המוטבע והערכות הגודל לאחר הפענוח נבדקים לפני הקצאת זיכרון. HTTPS נדרש בכתובת ה-URL המרוחקת הראשונית ובכל הפניה, באמצעות מנגנון ההגנה הקיים לתעבורה יוצאת ציבורית בלבד, עם קיבוע DNS. לאחר מכן הבתים חוצים את גבול המתווך הפנימי המדויק `POST /api/modality-bridge/video/extract`. נתיב זה הוא גם `LOCAL_ONLY` וגם `SPAWN_CAPABLE`, מקבל רק בקשה מאומתת לכל תהליך דרך loopback מהימן, ולעולם אינו מקבל כתובת URL, נתיב במערכת הקבצים, קובץ הפעלה או רשימת ארגומנטים. צינור מגבלת גודל הגוף של ה-API וקורא הגוף המצטבר של המטפל אוכפים בנפרד מגבלת קלט של 50 MiB למתווך. התור המוגבל שלו מריץ חילוץ אחד בכל פעם, מאפשר ארבע משימות ממתינות ומגביל את הקלט הממתין ל-100 MiB.

בתוך המתווך, `ffprobe` קורא קובץ מקומי פרטי; רשימת ההיתרים הקבועה של הפורמטים
אינה כוללת פורמטים של רשימות השמעה ומניפסטים. עבור מכלים מותרים ממשפחת MOV,
הפניות חיצוניות לנתוני MOV נשארות מושבתות כברירת מחדל, והפקודה
הקבועה אינה מפעילה אותן. גם `ffprobe` וגם `ffmpeg` משתמשים ברשימת היתרים
לפרוטוקול `file` בלבד, בתהליכון אחד, במערכי ארגומנטים קבועים, ללא מעטפת פקודות,
ובקובצי הפעלה שאותרו מתוך `PATH`. זרמי תמונת עטיפה מצורפת אינם
מועמדים להפעלה. כל הזרמים הניתנים להפעלה חייבים לעמוד במגבלות, וזרם ברירת מחדל
מפורש מקבל עדיפות לפני ברירת המחדל הדטרמיניסטית בעלת האינדקס הנמוך ביותר.
סרטונים מוגבלים ל-600 שניות, ל-8,192 פיקסלים בכל ממד ול-33,554,432
פיקסלים במקור. FFmpeg דוגם 1–16 מסגרות JPEG מנקודות האמצע, מקטין
את הצלע הארוכה ל-1,024 פיקסלים לכל היותר בלי להגדיל קלטים קטנים יותר,
ולעולם אינו מקבל URL. ברירת המחדל לדגימה היא `uniform`. המדיניות האופציונלית
`scene_aware` והמדיניות הניסיונית `segment_aware` מבצעות מעבר FFmpeg
קבוע נוסף אחד על הזרם המקומי שכבר אומת, בוחרות חותמות זמן מוגבלות של סצנות
מתוך `showinfo`, ובמקרה של כשל בגלאי, חריגה מהזמן הקצוב, פלט פגום או קבוצת
מועמדים ריקה, חוזרות באופן דטרמיניסטי לאותן נקודות אמצע אחידות. מצב מודע
למקטעים מקצה דגימות מנקודות אמצע באופן יחסי למרווחי הסצנות המאומתים; הראיות
והתנהגות ברירת המחדל של מצב זה מפורטות להלן. התקרה הקשיחה של 16 מסגרות
מוחלת לאחר הבחירה בכל מדיניות. כאשר לבקשה מודעת לסצנות יש תקציב של מסגרת
אחת בלבד, היא משתמשת בנקודת האמצע האחידה של הסרטון המלא הפעיל או של חלון
המיקוד ומדווחת `policyEffective: uniform`: מסגרת סצנה יחידה שנבחרה
אינה יכולה לשמר את שני הקצוות הזמניים. קורא רשאי לספק חלון מיקוד סופי
(`start`/`end` בשניות); הגבולות מוגבלים למשך המדיה, חלונות הפוכים או
לא-סופיים נדחים, וכל מדיניות הדגימה מתבצעת רק בתוך המרווח המנורמל. החלון
שמתקבל נכלל במטא-נתונים של הדגימה ובתחילית התיאור שאינה מהימנה, כדי שמודלים
בהמשך התהליך יוכלו להבחין בין קטע ממוקד לבין ציר הזמן המלא.

מיקוד סמנטי של כתוביות הוא הגדרה נפרדת ומפורשת. מצב הניתוח `full`
המוגדר כברירת מחדל משמר את הנחיית המסגרות הקיימת ולעולם אינו מעביר טקסט
מהבקשה למודל הכתוביות. במצב `focused`, הגשר קורא רק את ה-`text`/`input_text`
האחרון שאינו ריק ושנכתב בידי המשתמש, מאותו מכל Chat או Responses, מנרמל
אותו ל-NFC, מכווץ תווי בקרה ורווחים ומגביל אותו ל-500 נקודות קוד של Unicode.
תוצאה ריקה חוזרת להנחיית `full` המדויקת. רמז שמיש מסודר כ-JSON בבלוק ייעודי
של הקשר משתמש שאינו מהימן, ורשאי רק לתעדף פרטים הניתנים לצפייה; הוא אינו יכול
לעקוף את האזהרה הנפרדת מפני ציות להוראות הנראות או נשמעות במדיה. מיקוד טקסטואלי
לעולם אינו מסיק `start`/`end` ואינו משנה את הדוגם הזמני.

#### FU-07 ראיות מבניות למקטעים

`segment_aware` משתמש במעבר קדם-ניתוח מוגבל אחד על זרם הווידאו המקומי
שכבר אומת. שרשרת המסננים הקבועה מקטינה תחילה את הרוחב ל-320 פיקסלים לכל
היותר, מזהה שינויי סצנה ומרווחים קפואים, ולאחר מכן דוגמת בקצב של מסגרת אחת
לשנייה לצורך טשטוש, בהיקות ממוצעת ומידע מרחבי/זמני. המעבר מוגבל ל-600
דגימות מבניות, לתהליכון FFmpeg/מסנן אחד, לאותן רשימות היתרים של פרוטוקול
`file` בלבד ושל מכלים, למגבלת פלט תהליך של 1 MiB ול-30 שניות לכל היותר
בתוך מנגנון הביטול/המועד האחרון המשותף של המתווך. הוא לעולם אינו מקבל
פקודה, מסנן, נתיב או URL מהבקשה.

הערכים המבניים הם ראיות דגימה דטרמיניסטיות, ולא הבנה סמנטית של הווידאו.
הם אינם מסיקים נושאים, פעולות, כתוביות, דיבור או כוונת משתמש. גבולות סצנה
וקפיאה יוצרים מקטעים; כיסוי קפיאה, טשטוש, חשיפה, פירוט מרחבי ושינוי זמני
משפיעים רק על אופן הקצאת התקציב הקיים של 1–16 מסגרות. מקטע שקפוא במלואו
מוגבל למסגרת אחת, בעוד שמקטעים שאינם קפואים מתחרים על יתרת התקציב. כאשר
מספר הגבולות גדול ממספר המסגרות, נשמר כיסוי אחיד של ציר הזמן, כדי שמעברים
מהירים בתחילתו לא יוכלו להסתיר מקטע ארוך בסופו. גבולות סצנה הנמצאים בטווח
רזולוציית הניתוח של שנייה אחת מגבול קפיאה מאוחדים.

מסננים חסרים, ראיות פגומות/ריקות, שגיאת גלאי או חריגה מהזמן הקצוב של
קדם-הניתוח המוגבל חוזרים באופן מתיר למדיניות המדויקת של נקודות האמצע
האחידות. ביטול מצד הקורא או הגעה למועד האחרון של המתווך אינם חוזרים באופן
מתיר: הם מסיימים את תת-התהליך הפעיל, מונעים חילוץ מסגרות נוסף, והעץ הזמני
הפרטי מוסר בתוך `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` יוצר התקני בדיקה אמיתיים
ודטרמיניסטיים של FFmpeg לצורך חיסכון בקריאות למודל הכתוביות לאחר הסרת
כפילויות, הקצאת תקציב לתנועה צפופה, ראיות טשטוש/חשיפה/SI-TI, מעברים מהירים
עם זנב ארוך ותוצאות חיוביות שגויות בדעיכה הדרגתית. הוא מתעד את זמן השעון
של קדם-הניתוח, ובמקומות שבהם `/usr/bin/time` זמין, גם את זמן המעבד של תהליך
הבן ואת שיא ה-RSS. בדיקות האיכות שלו הן אורקלים מבניים בלבד. איכות אמיתית
של מודל הכתוביות נשארת `HOLD`, משום שלרתמה זו אין נקודת קצה מורשית או שופט
מוקפא. גם החיסכון הכספי נשאר `HOLD`, אלא אם `--caption-cost-per-call-usd`
מספק אומדן חיובי מפורש לעלות לכל קריאה; הסקריפט לעולם אינו ממציא אף אחת
מהתוצאות.

כל פריים מוגבל ל־4 MiB, כלל הפריימים הגולמיים יחד מוגבלים ל־23 MiB, ותגובת הברוקר שעברה סריאליזציה מוגבלת ל־32 MiB. ספרייה זמנית פרטית מוסרת ב־`finally`. ‏OmniRoute אינו כולל את FFmpeg ואינו מקבל נתיב מותאם אישית לקובץ הפעלה. לפני יצירת הכתוביות, הגשר מפעיל מעבר שמרני להסרת כפילויות חזותיות: כל JPEG מוקטן למאגר גוני אפור בגודל 16×16 ומושווה רק לפריים האחרון שנשמר. כאשר תקציב הכתוביות המבוקש גדול מפריים אחד, החילוץ מספק מאגר מועמדים מוגבל של עד פי שניים מאותו תקציב, ולעולם לא יותר מ־16 פריימים. המכסה המבוקשת מוחלת רק לאחר הסרת הכפילויות, והמועמד הראשון והאחרון שנבחרו נשמרים במהלך הדילול הסופי כאשר התקציב הוא שניים לפחות. המדיניות בעלת הגרסה
`grayscale-16x16-mean-cells-v2` משתמשת בערך הגדול מבין ההפרש הממוצע בבהיקות לבין היחס של תאי התמונה הממוזערת שההפרש המנורמל שלהם הוא לפחות 0.05. סף הכפילויות הוא הקבוע 0.04, שנבחר לשם יכולת חיזוי במקום לחשוף אותו כהגדרת זמן ריצה. אות משני זה, בעל ניגודיות גבוהה, משמר תנועה קטנה ושינויים בטקסט גלוי שהשוואה המבוססת על ממוצע בלבד עלולה להסתיר. שגיאות במשווה או במפענח פועלות במצב פתוח ושומרות על הכיסוי. מטא־נתוני הפלט מפרידים בין מועמדים שחולצו, פריימים שנעשה בהם שימוש בהצלחה וכפילויות חזותיות שהושמטו.

חלק וידאו שסומן במפורש עשוי לבקש גיליון תמונות ממוזערות עם חותמות זמן. הגשר בונה רשת JPEG הכוללת לכל היותר 4 עמודות ו־16 פריימים. כל תא בגודל 512 פיקסלים מטביע את חותמת הזמן של המקור שלו ברצועה תחתונה בעלת ניגודיות גבוהה, ואותן חותמות זמן נשמרות גם במטא־נתונים טקסטואליים לצורך שיוך וביקורת בהמשך העיבוד. קובץ ה־JPEG המלא נותר מוגבל ל־32 MiB. אם `sharp` אינו מצליח לפענח או להרכיב את הרשת, הגשר חוזר להשתמש בפריימי ה־JPEG הנפרדים; ביטול מצד הלקוח עדיין מועבר דרך פעולת הגיליון.

ראיות לקידום מופרדות במכוון ממבחן הביצועים הזעיר של ההרכבה הסינתטית. `scripts/perf/video-bridge-contact-sheet-eval.ts` מגדיר מסגרת A/B בעלת גרסת סכמה עבור מודלי ראייה אמיתיים התואמים ל־OpenAI. היא מודדת טוקנים שעליהם דיווח הספק, השהיה מקצה לקצה לפי שעון קיר (לרבות הרכבת הגיליון), מספר קריאות למודל ושימור עובדות שהוגדרו במניפסט. תגובות גולמיות של המודל אינן נכתבות לדוח; נשמרים רק תקצירי SHA-256 ומזהי העובדות שנמצאה להן התאמה. המסגרת אינה מבצעת קריאת רשת או קריאה בתשלום למודל אלא אם מועבר `--execute-real` ואם `--model`, ‏`OMNIROUTE_BASE_URL` ו־`OMNIROUTE_API_KEY` מוגדרים. ללא הרצה אמיתית ומפורשת זו, פסק הדין הקריא למכונה נשאר `HOLD`; מדידות סינתטיות של מטען ומספר קריאות לבדן אינן מהוות ראיות לקידום.

מתקשרים רשאים לצרף מערך `transcript.cues` אופציונלי לחלק וידאו נתמך כאשר כבר מצוי בידיהם טקסט מסונכרן. כל רמז חייב לכלול `text`, מרווח סופי של `start`/`end` בתוך משך הזמן שנבדק, וכן `source` מתוך רשימת ההיתרים (`client`, ‏`embedded` או `audio-bridge`); ערך ברירת המחדל של `confidence` הוא `1`, ועליו להישאר בין `0` ל־`1`. רמזים כפולים זהים לחלוטין מאוחדים. OmniRoute לעולם אינו מתחיל תמלול מתוך מטא־נתונים אלה: רמזים מאומתים מועתקים לתוצאה המתוארת יחד עם המקור, רמת הביטחון ומרווח הזמן, ומוצגים כתצפיות שאינן מהימנות לצד כתוביות הפריימים. טקסט לא תקין, מחוץ לטווח או חסר מקור נדחה במקום להשתלב בזרם הכתוביות. שני ערוצי התמלול בגוף הבקשה מנרמלים את המקור שסופק ל־`client`, לרבות תוויות `embedded` או `audio-bridge` שהוצהרו עצמאית. רק מתאם בבעלות השרת יכול להקצות תוויות מהימנות אלה באמצעות הארגומנט הזמין בקוד בלבד `trustedSource`; שדה JSON בבקשה אינו יכול להגיע לארגומנט זה. טקסט התמלול נשאר תוכן בלתי מהימן שנגזר ממדיה, ללא קשר למקורו, ולעולם אסור לו לקבוע הרשאה.

מתקשר מתקדם רשאי לספק רצועת `audioTranscript` עבור אותו סרטון; היא מטופלת כטקסט שסופק בידי הלקוח, ולא כהוכחה לתמלול בשרת. נקודת האיחוד מריצה תצפיות חזותיות וקוליות תחת מועד סיום ואות ביטול משותפים, מסדרת אותן על ציר זמן משותף, מאחדת כפילויות זהות לחלוטין ומדווחת על תוצאה חלקית כאשר רק צד אחד מצליח. `audioTranscript` לא תקין מוביל לתוצאה חלקית זו — התיאור החזותי נשמר והענף הקולי מתעד קוד כשל מחוטא — במקום להכשיל את הסרטון כולו. הזמינות של כל ענף, דגל התוצאה החלקית וקודי הכשל המחוטאים נשמרים בתוצאה המתוארת, במטא־נתוני מנגנוני ההגנה (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), במטא־נתוני מטמון התוצאות ובמוני האיחוד של הגשר. נתיב ברירת המחדל של Video Bridge אינו מפעיל המרת דיבור לטקסט ואינו מוריד עותק נוסף של המדיה; ללא רצועה מפורשת זו, הוא נשאר וידאו בלבד.

**שמירת תמלילים (#12150 P1).** הדבר חל אוטומטית בכל פעם ש־Video Bridge (שהפעלתו עצמה דורשת הצטרפות מפורשת) מעבד רמז תמלול — אין דגל שמירה נפרד. כאשר בקשה מעבדת רמז תמלול כלשהו (`transcript` שהוצהר על ידי המתקשר או `audioTranscript` שמוזג), מנגנון ההגנה מסמן אותה כ־`videoBridgeObserved` ומפיק עותק צל מושחר של תיאור הווידאו — עיבוד זהה שבו גוף הטקסט החופשי של כל רמז מוחלף ב־`[redacted-video-transcript]`, הנבנה באמצעות החלפת שדה הרמז המובנה לפני הרכבת המחרוזת (לעולם לא באמצעות ניתוח הטקסט המשוטח, כך ששום תוכן של רמז — עוין או רגיל, לרבות גופים המכילים `]` כגון `[inaudible]`/`[music]` — אינו יכול לשרוד). גוף הבקשה הנשמר ביומן הקריאות מחליף כל חלק טקסט שמקורו בווידאו בעותק הצל המושחר הזה, בהתאמה לפי שוויון תוכן; העוגן `fullText` נקרא מחדש ממטען מנגנון ההגנה המוגמר שלפני הקריאה, כך שההתאמה עדיין מצליחה לאחר שמנגנוני הגנה מאוחרים יותר בשרשרת (מסכות PII ופרטי הזדהות, בעדיפויות 10/95) משכתבים את טקסט התיאור במקום, ולאחר שהזרקת הנחיית מערכת/העברת הקשר/Memory מעצבת מחדש את מערך ההודעות. הגוף הנשלח במעלה הזרם למודל נותר ללא שינוי. בקשה שנצפתה גם אינה מאכלסת שום Memory מתמיד (מדלגים הן על חילוץ הנגזר מהבקשה והן על חילוץ הנגזר מהתגובה), כך שהתשובה של המודל עצמו אינה יכולה להדהד טקסט מהתמליל אל Memory.

**שדות וידאו גולמיים (#12430).** כאשר הגשר מופעל ותמיכת הווידאו המקורית אינה ידועה או אינה קיימת, שדות `transcript`/`audioTranscript` מוגדרים מפעילים גם הם את `videoBridgeObserved`, אפילו לאחר כשל בתיאור או מגבלת `maxVideos`. ערכי `null` ומחרוזות ריקות נחשבים; שדות חסרים ומטא־נתונים שאינם של וידאו אינם נחשבים. עותקים נשמרים משחירים שדות אלה או משמיטים את הבקשה, ועוקפים מטמונים/Memory.

בנתיבי נסיגה אלה, רמזים תקינים שסופקו על ידי המתקשר הופכים לחלקי `text`/`input_text` נתמכים במקום לשדות ספק לא תקניים. שתי הרצועות שסופקו בבקשה נותרות תצפיות `client` בלתי מהימנות, עם אזהרה מפורשת שהווידאו לא תואר ושחותמות הזמן לא אומתו מול המדיה. התקציבים הקיימים של 256 רמזים/64 KiB בסך הכול ולכל רמז חלים על שתי הרצועות יחד; חותמות הזמן חייבות להתאים לתקרה של 600 שניות אצל הברוקר ולכל חלון מיקוד שסופק. רצועות לא תקינות נזרקות ואינן מועברות כטקסט שרירותי; עדיין ניתן להשתמש ברצועה אחות תקינה, אלא אם חורגים מהתקציב המשולב שלהן. שדות null/ריקים אינם מוסיפים טקסט. נסיגה זו אינה מוסיפה אחזור מדיה או תמלול. שדות הרחבת התמליל מוסרים מנשא הווידאו המשמש לנסיגה ומאובייקטי `video_url`/`source` שלו. רשימת ההיתרים בתעבורת OpenAI נשארת מחמירה; נשאי וידאו שתמיכתם המקורית אינה ידועה נותרים זמינים, ויעדים ידועים התומכים בטקסט בלבד שומרים על סמנים בטוחים. עותקי צל מושחרים מובנים מגינים על טקסט התמליל שנוסף, בעוד שהבקשה המקורית שבבעלות המתקשר נותרת ללא שינוי. יעדים בעלי תמיכה מקורית וגשרים מושבתים שומרים על התנהגות העקיפה הקיימת שלהם.

עותקים שמורים נוספים משתמשים באותו אות של בקשה שנצפתה. תמונת המצב הגולמית של בקשת הלקוח מלפני מנגנון ההגנה, הבקשה הממתינה בזיכרון ויומן הבקשות שנדחו בשלב מוקדם מחליפים באופן מובנה שדות תמליל בחלקי וידאו; הנחיות מחרוזת שנוצרו על ידי שלבי צינור העיבוד והעברת ההקשר מושחרות בנקודת הקליטה של גוף הבקשה הנשמר. הסמן השמור `video_content_removed` גורם להמשך באמצעות `previous_response_id` להיכשל באופן סגור במקום לשחזר טקסט שנמחק במכוון. אם בקשה שנצפתה מאבדת את עותק הצל המושחר שלה לכל חלק לפני הרישום ביומן, או אם אפילו אחד מכמה עותקי צל של וידאו אינו מצליח להתאים לאחר שינויים מאוחרים יותר בבקשה, גוף הבקשה הנשמר מושמט לחלוטין במקום לשמור תמליל שהושחר באופן חלקי.

עבור בקשה שנצפתה, תגובת מודל עשויה לצטט כל חלק מהתמליל ללא גבול רמז מובנה. לכן `responseBody` הנשמר ביומן הקריאות מוחלף בסמן השמטה; ארטיפקט צינור העיבוד המפורט (שעשוי לכלול גופי upstream/client ומקטעי זרם) אינו נשמר. מטמוני סמנטיקה, אידמפוטנטיות ושחזור הנמקה עוקפים קריאות וכתיבות עבור בקשה זו. בקשת הספק והתגובה הגלויה ללקוח נותרות ללא שינוי. בתי keepalive מוקדמים מנוקזים מהמאגר הזמני כאשר הארטיפקט המפורט מושמט. אזהרת EventStream הפגום של Kiro מדווחת רק על מספר הבתים במטען, ולעולם לא על תוכנו או על השגיאה הגולמית של מנתח ה־JSON.
אין בכך טענה שכל אבחון לא קשור של ספק/תוסף עבר ביקורת; הסריקה הרחבה יותר של יעדי שמירה מתועדת ב־#11658.

מחזור החיים הפנימי של `/api/modality-bridge/video/drilldown` הוא תשתית מטמון נפרדת המאומתת באמצעות loopback/אסימון. כל פעולה דורשת גם מזהה principal אטום וקנוני. לפני שמתקשר בסביבת ייצור מופעל, עליו לגזור מזהה זה מהדייר המאומת ולעולם לא להעביר ערך שנבחר על ידי הלקוח. מפתחות המטמון קושרים principal זה למזהי הפעלה והפניית וידאו קנוניים, מאחסנים רק את המפתחות שלהם שנגזרו באמצעות SHA-256, ומגבילים הן קריאות והן מחיקה לאותו principal. המטמון מאחסן לכל היותר 16 מסגרות JPEG נגזרות לכל רשומה, מפוגג אותן לאחר עשר דקות ותומך בקריאות תחומות באמצעות `start`/`end` או במחיקה מפורשת של הפעלה.

כל principal מוגבל ל־16 רשומות ול־64 MiB של נתוני JPEG קנוניים. מגבלות אלה בלתי תלויות בתקרה הגלובלית של 64 רשומות/256 MiB: לחץ על מכסת principal מפנה רק את הרשומות של אותו principal שנעשה בהן שימוש לאחרונה לפני הזמן הרב ביותר, בטרם נשקל פינוי LRU גלובלי. רשומות שפג תוקפן מסולקות הן מההתחשבנות לפי principal והן מההתחשבנות הגלובלית בעת פעילות מטמון, בעוד שביטול וכשל אימות אינם מבצעים commit להחלפה חלקית.

המטמון דוחה Base64 שאינו קנוני, ריפוד עודף, מדיה שאינה JPEG, קובצי JPEG פגומים או
קטועים, וקובצי JPEG שמפיקים אזהרה במהלך פענוח מלא ומוגבל של התמונה באמצעות `sharp`.
הוא מקודד מחדש כל תמונה שהתקבלה כ-JPEG קנוני, גוזר את הרוחב והגובה
מהבתים המפוענחים במקום לתת אמון בשדות שסיפק הקורא, ומשליך בתים פוליגלוטיים
עודפים במקום לשמור אותם. רק המאגר הדחוס, הקנוני והמוגבל
נזקף לחובת שתי המכסות. מגבלת התעבורה בפורמט JSON כוללת את התקורה של Base64 עבור תקרת
הקלט המפוענח של 32 MiB. כל
נגזרת שמאוחסנת מתעדת את פורמט ה-JPEG והרזולוציה המאומתים שלה, מדיניות הדגימה,
גרסת הנגזרת, זמן היצירה, גיבוב התוכן שחושב בשרת והפניית אב
מגובבת, יחד עם גיבוב תוכן האב של הקורא המהימן. ביטול נבדק
בין שלבי הפענוח והגיבוב האסינכרוניים, לפני השמירה האטומית במטמון.

מקבץ עבודה זה עדיין אינו מחבר יצרן לשימוש בייצור אל הנתיב ואינו
מספק בחירה בין וריאנטים ברזולוציות מרובות. לכן, נתיב הבקשה השקוף של Video Bridge
אינו כרוך בעבודה נוספת, ואילו גזירת זהות ראשית התחומה לדייר
ומחזור החיים המלא של FU-08 ברזולוציות מרובות נותרים עבודות המשך מפורשות,
ולא התנהגות המתועדת כמושלמת.

הפריימים מקבלים כתוביות ברצף באמצעות מודל ה-Video שהוגדר. דריסת
Video ריקה יורשת את הגדרת Vision; אם שתיהן ריקות, הנתב האוטומטי של Vision
בוחר את המודל האפקטיבי התומך בראייה. כתוביות שנוצרו בהצלחה
מחליפות את החלק המקורי בקידומת יציבה `[Video description:`, שגם
מסמנת את הטקסט כתצפית בלתי מהימנה שמקורה במדיה ומנחה מודלים
במורד הזרם שלא לציית להוראות שנמצאו במדיה. מפתחות המטמון של כתוביות הפריימים
כוללים את בתי ה-JPEG, ההנחיה, חותמת הזמן והמודל האפקטיבי; רק כתוביות
שהופקו בהצלחה נשמרות במטמון. רשומות המטמון שומרות את מודל היצרן שהצליח בפועל,
לרבות מודל חלופי; הגשר מדווח `mixed` כאשר פריימים שונים
הופקו בידי מודלים שונים. פגיעה במטמון עושה שימוש חוזר בזהות היצרן
במקום לתייג אותה מחדש כתוכנית הניתוב המבוקשת. מטמון התוצאות של הסרטון
כולו ממופתח לפי כל קלט שמשנה את הפלט — ההנחיה, המודל
האפקטיבי, מדיניות הדגימה, מספר הפריימים, מצב הניתוח הסמנטי, טביעת האצבע SHA-256
של רמז המיקוד המנורמל, חלון המיקוד, `transcript`,
`audioTranscript` ודגל גיליון התמונות — כך ששינוי של כל אחד
מהממדים האלה גורם להחטאת מטמון, ולעולם לא לשימוש חוזר בתוצאה מיושנת. גם גרסת
מדיניות מניעת הכפילויות החזותית, הסף ומספר הפריימים המועמדים המוגבל מפורטים במפורש
במפתח ובמטא-נתונים של מטמון התוצאות; לכן שינוי מדיניות אינו יכול לעשות שימוש חוזר
בתיאור מיושן של הסרטון כולו. המטא-נתונים של מטמון התוצאות בגרסה v4 שומרים את המצב
ואת טביעת האצבע, ולעולם לא את משימת המשתמש הגולמית. המטא-נתונים של מנגנון ההגנה מדווחים הן על
מצב הניתוח המבוקש והן על המצב האפקטיבי; מצב `focused` שהתבקש ללא
טקסט משתמש שמיש מדווח כאפקטיבית `full`.

מנגנון ההגנה מחלץ כל חלק וידאו נתמך, אך מתאר לא יותר מאשר
`modalityBridgeVideoMaxVideos`. עבור יעד שהוכח כי
`supportsVideo === false`, סרטונים שכשלו או חרגו מהמגבלה הופכים לסמני טקסט בטוחים
ומפורשים, כך שלא נותר וידאו גולמי. כאשר היכולת אינה ידועה, חלקים אלה
שומרים על מעטפת הווידאו שלהם; כל תמליל חלופי עובר את המרת הטקסט המוגבלת
שתוארה לעיל. יעדים שבהם `supportsVideo === true` עוקפים את הגשר.
אות הביטול של בקשת הלקוח מועבר דרך ההורדה, תור המתווך,
תהליכי המשנה וקריאות יצירת הכתוביות; ביטולים עוצרים בין סרטונים ולעולם אינם נכשלים
בצורה שמאפשרת למדיה גולמית לעבור.

הגדרות זמן הריצה מגובות במסד הנתונים ומאומתות באמצעות Zod:

| מפתח                                | ברירת מחדל  | טווח / התנהגות                                                                     |
| ----------------------------------- | ----------- | ---------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | זמן ריצה אופציונלי, בהצטרפות מפורשת                                                |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` משמר כתוביות כלליות; `focused` משתמש בהקשר מוגבל ובלתי מהימן מהמשתמש האחרון |
| `modalityBridgeVideoModel`          | `""`        | יורש את מודל Vision Bridge                                                         |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                               |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware`, או `segment_aware` יחסי; כשל בגלאי חוזר ל-`uniform`      |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                     |

ערכי זמן קצוב ישנים של Video שנשמרו ושעולים על 120 שניות מוגבלים
למועד הסיום של המתווך; כתיבות חדשות של הגדרות מעל מגבלה זו נדחות.
`GET /api/modality-bridge/video/runtime` דורש מקומיות loopback מהימנה וחתומה
לפני אימות או בדיקת זמן הריצה, ולאחר מכן דורש אימות ניהולי.
הוא מחזיר רק את `available`, גרסאות FFmpeg/ffprobe שעברו טיהור וסיבה קבועה
כאשר זמן הריצה אינו זמין. נקודת הקצה הפנימית לחילוץ אינה
API ציבורי להעלאה: רוויית התור מחזירה `503` יחד עם `Retry-After`, ניתוק מצד הקורא
מחזיר `499`, ומועד הסיום הקבוע של המתווך מחזיר `504`. תגובות שעברו המרה מוסיפות
`video->text;model=<visionModel>;parts=<videos>` לכותרת המרכזית
`x-omniroute-modality-bridge` מבלי להסיר מקטעי Vision או Audio.

### ממסך PII (`piiMasker.ts`)

פועל ב**שני** השלבים.

- **`preCall`** משכפל את המטען, עובר על `system`,‏ `messages`,‏ `input` ו-`prompt`
  (כולל פריטי מחרוזת פשוטים), ומחיל את `processPII()` (מתוך
  `@/shared/utils/inputSanitizer`) על שדות `content`/`text` מסוג מחרוזת. כאשר
  `PII_REDACTION_ENABLED=true`, פרטי PII שזוהו מושחרים במטען היוצא.
  פעולה זו אינה תלויה ב-`INPUT_SANITIZER_MODE` (ששולט רק במדיניות של
  הזרקת הנחיות). כאשר ההשחרה כבויה, הקריאה מתעדת את מספר הזיהויים
  בלי לשכתב את התוכן.
- **`postCall`** יוצר עותק עמוק של התגובה, ומפעיל את `sanitizePIIResponse()` יחד עם
  ממסך המבנה של Responses API (`maskResponsesOutput` — המכסה את
  `output_text` ואת `output[].content[].text`). אם מתבצעת השחרה כלשהי,
  התגובה ששונתה מחליפה את התגובה המקורית.

מנגנון ההגנה לעולם אינו חוסם; הוא רק מוסיף הערות (`meta.detections`,
`meta.redacted`) או משכתב.

#### בחירה לפי סוג, תבניות מותאמות אישית ומוני זיהוי

**לוח הבקרה → הגדרות → אבטחה → מיסוך PII** קובע _מה_ ימוסך. הוא
אינו מפעיל את המיסוך: על כך עדיין שולטים `PII_REDACTION_ENABLED` (בקשה) ו-
`PII_RESPONSE_SANITIZATION` (תגובה + SSE), ושניהם כבויים כברירת מחדל.

- **בחירה לפי סוג** — המזהים המובנים מפורטים ב-
  `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`). ערך שלא הוגדר פירושו כל
  הסוגים (ההתנהגות שהייתה קיימת לפני הוספת הגדרה זו). התבנית
  `ssn_us` של מנוע הבקשות ממופה אל `ssn`. תבניות ההגדרה (מינימלית, רגילה, פיננסית,
  ברזילאית, ארה״ב, מלאה) רק מסמנות את תיבות הסימון בממשק המשתמש.
- **תבניות מותאמות אישית** — עד 20 תבניות של ביטוי רגולרי או תווים כלליים (`*` = עד 64
  תווים שאינם רווח לבן, `?` = תו אחד). התאמות הופכות ל-`[CUSTOM_REDACTED]`.
  כל תבנית עוברת דרך `compilePiiCustomPattern()`
  (`src/shared/utils/piiCustomPatterns.ts`): לכל היותר 500 תווים, דגלים מוגבלים
  ל-`g i m s u`, עליה לעבור הידור, לעבור בדיקת `safe-regex` (חזרה לאחור
  קטסטרופלית), ואסור לה להתאים למחרוזת ריקה או למציין מקום של השחרה.
  תבנית שנכשלת נדחית בעת השמירה ובעת הבדיקה, ושורה שמורה
  שנכשלת מדולגת בזמן הריצה במקום לעבור הידור. תבניות מותאמות אישית
  מופעלות רק כאשר המיסוך פעיל.
- **מוני זיהוי** — ספירות לפי סוג (לעולם לא הערכים שהותאמו), נשמרות
  בזיכרון ומתאפסות בהפעלה מחדש (`src/lib/pii/piiDetectionStats.ts`). הן
  גדלות רק כאשר המיסוך פעיל.

ההגדרות נשמרות בטבלה `key_value` (מרחב השמות `pii_settings`,
`src/lib/db/piiSettings.ts`) ונקראות דרך מטמון של שנייה אחת. API:

| שיטה   | נתיב                     | מטרה                                                             |
| ------ | ------------------------ | ---------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | מצב הדגל, `enabledTypes`,‏ `customPatterns`, מוני זיהוי          |
| `PUT`  | `/api/settings/pii`      | החלפת `enabledTypes` (`null` = הכול) ו/או `customPatterns`       |
| `POST` | `/api/settings/pii/test` | הרצה יבשה של תבנית אחת מול דגימה בגודל של עד 8 KB; דבר אינו נשמר |

שלושת הנתיבים דורשים אימות ניהולי ומאמתים את גוף הבקשה באמצעות Zod
(`src/shared/validation/schemas/piiSettings.ts`).

### הזרקת הנחיות (`promptInjection.ts`)

מזהה מבנים עוינים בתוכן שסופק על ידי המשתמש ואוכף את
המדיניות שהוגדרה. ההתנהגות נקבעת באמצעות משתני סביבה ואפשרויות
הבנאי:

| הגדרה    | משתנה סביבה                                                                                            | ברירת מחדל | השפעה                                                                                                                                                                    |
| -------- | ------------------------------------------------------------------------------------------------------ | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| מופעל    | `INPUT_SANITIZER_ENABLED`                                                                              | `true`     | כאשר הערך הוא `false`, מנגנון ההגנה מסיים את פעולתו באופן מיידי.                                                                                                         |
| מצב      | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                        | `warn`     | מדיניות הזרקה: `block`,‏ `warn` או `log`. (`redact` מתקבל לצורך תאימות לאחור, אך **אינו** מסיר טקסט של הזרקה; השכתוב של PII בבקשה נשלט באמצעות `PII_REDACTION_ENABLED`.) |
| סף חסימה | האפשרות `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (כינוי `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`     | רמת החומרה המזערית הנדרשת לחסימה. ברמת ברירת המחדל, חומרה בינונית מיועדת לתצפית בלבד.                                                                                    |

**קדימות המצבים** (`getMode`):‏ `options.mode` של הקורא →
דריסת **דגל תכונה במסד הנתונים** עבור `INJECTION_GUARD_MODE` (לוח הבקרה → הגדרות →
דגלי תכונות) → משתנה הסביבה `INJECTION_GUARD_MODE` → משתנה הסביבה `INPUT_SANITIZER_MODE` →
`warn`. לכן דריסה מלוח הבקרה גוברת על משתני הסביבה, כך שממשק המשתמש של דגלי
התכונות שולט במנגנון ההגנה הפעיל בזמן אמת (ללא הפעלה מחדש). הקריאה ממסד הנתונים פועלת באופן בטוח במקרה של כשל:
אם מתרחשת שגיאה, מנגנון ההגנה חוזר להתנהגות המבוססת על משתני הסביבה, וכאשר לא
מוגדרת דריסה, ההתנהגות זהה לחלוטין לפתרון המבוסס על משתני סביבה בלבד.

מקורות הזיהוי:

1. `sanitizeRequest()` מתוך `@/shared/utils/inputSanitizer` (קבוצת גלאים משותפת
   המשמשת במקומות אחרים בצינור העיבוד).
2. `DEFAULT_GUARD_PATTERNS` המובנות (נכון לעכשיו `system_override_inline` ו-
   `markdown_system_block`, שתיהן ברמת חומרה `high`).
3. `customPatterns` אופציונליות המועברות דרך אפשרויות הבנאי (מחרוזות, ביטויים רגולריים
   או רשומות `{ name, pattern, severity }`).

כאשר `mode === "block"` **וגם** לפחות זיהוי אחד עומד בסף החומרה,
`preCall` מחזירה `{ block: true, message: "Request rejected:
suspicious content detected" }`. במצבי `warn`/`log`, מנגנון ההגנה מתעד ביומן אך
מאפשר את הקריאה. פונקציית העזר המשותפת `evaluatePromptInjection()` מיוצאת גם היא
עבור צרכנים שצריכים להעריך הנחיות בלי לעבור דרך הרישום.

**מגבלת סריקה (v3.8.20):** הגלאי בודק רק את **16 KB הראשונים** של
טקסט ההנחיה המצורף — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` ‏(16,384 בתים) בתוך
`src/shared/utils/inputSanitizer.ts`. גם `detectInjection()` וגם
`evaluatePromptInjection()` מפעילות `slice(0, MAX_INJECTION_SCAN_BYTES)` לפני הרצת
לולאת התבניות. הנחיות הזרקה מופיעות סמוך לתחילת הקלט, ולכן הדבר מגביל את צריכת
ה-CPU/GC של הביטויים הרגולריים במטענים בגודל מאות KB מבלי להחליש את הזיהוי (ראו
#3932, #4041).

### ממסך פרטי גישה (`credentialMasker.ts`)

פועל **בשני** השלבים, אחרון בשרשרת ברירת המחדל (עדיפות `95`). משחיר תבניות
מוכרות של מפתחות API / אסימונים סודיים מהמטען היוצא (תוכן הודעות,
ארגומנטים של קריאות לכלים ותוצאות כלים) **וגם** מתגובת הספק, כך שפרטי גישה
שהודבקו להנחיה (או הוחזרו כהד על ידי תוצאת כלי) לא ידלפו לספק שבמעלה הזרם
או בחזרה ללקוח.

- **בהצטרפות מפורשת בלבד**, בהתאם לאותה מוסכמה של השחרת מידע המאפשר זיהוי אישי (בסמוך לכלל הקשיח #20):
  מושבת אלא אם `settings.credentialRedactionEnabled === true` **או**
  `CREDENTIAL_REDACTION_ENABLED=true`. כאשר הוא כבוי, מנגנון ההגנה אינו מבצע דבר —
  הוא לעולם אינו חוסם ולעולם אינו משכתב.
- `redactCredentials()` עוברת על כל עץ המטען/התגובה (`walkValue()`,
  באופן בטוח מפני זיהום אב-טיפוס ובטוח מפני מחזורים באמצעות `WeakSet`) ומחליפה התאמות
  במציין מיקום מסוג `[REDACTED:<type>]`, תוך שכפול של הענפים שהשתנו בפועל בלבד.
- `CREDENTIAL_PATTERNS` מכסה מפתחות של ספקי LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), אסימוני VCS/SaaS ‏(GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), מפתחות תשלום (Stripe, Square), מפתחות
  ענן (מפתח גישה של AWS, ‏Twilio, ‏SendGrid, ‏Mailgun), מפתחות פרטיים / JWTs,
  מחרוזות חיבור המכילות פרטי גישה (`mongodb://user:pass@...` וכו'), וכן
  תבנית כללית לערכי כותרות `Authorization`/`x-api-key`/`api-key`/`apikey`.
  מפתחות במבנה כותרת (`authorization`, `x-api-key`, `api-key`,
  `apikey`) מושחרים באופן מבני (הערך בלבד, בעוד שקידומת הסכמה כגון
  `Bearer `/`Basic ` נשמרת), ולא באמצעות הביטוי הרגולרי הכללי לטקסט.
- מנגנון ההגנה לעולם אינו חוסם; הוא רק משכתב (`modifiedPayload` /
  `modifiedResponse`) ומוסיף הערות (`meta.credentialsRedacted`, `meta.count`).

הגנת רגרסיה: `tests/unit/credential-masker-guardrail.test.ts`.

## חוזה בסיסי (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // הערך true עוצר מיד את השרשרת
  message?: string; // מוצג בעת חסימה
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // מוחזר על ידי preCall כדי לשנות את הבקשה
  modifiedResponse?: TValue; // מוחזר על ידי postCall כדי לשנות את התגובה
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

מעקה בטיחות מציין "ללא שינוי" באמצעות החזרת `void`,‏ `{}` או
`{ block: false }`. החזרת `modifiedPayload`/`modifiedResponse` מחליפה
את הערך שעובר בשרשרת עבור מעקות הבטיחות שבהמשך.
`signal?: AbortSignal` מעביר את מחזור החיים של הקורא אל מעקות הבטיחות. ביטול בקשה הוא החריג המכוון של כשל פתוח: גשרי מדיה מפסיקים את עבודתם ומבצעים ניקוי מבלי לשחזר מדיה גולמית ליעד שידוע כי אינו תומך בה.

## מרשם (`registry.ts`)

היחידון `guardrailRegistry` חושף:

- `register(guardrail)` — מוסיף מעקה בטיחות (או מחליף לפי שם מנורמל) וממיין מחדש לפי `priority` בסדר עולה.
- `clear()` / `list()` — כלי עזר ניהוליים.
- `runPreCallHooks(payload, context)` — עובר על מעקות הבטיחות הפעילים, מעביר את המטען דרך `modifiedPayload`, ועוצר ב-`block: true` הראשון.
- `runPostCallHooks(response, context)` — אותה זרימה בצד התגובה.
- `resetGuardrailsForTests({ registerDefaults })` — מנקה את המצב, ובאופן אופציונלי רושם מחדש את ברירות המחדל כדי להבטיח בידוד נקי בין בדיקות.

שני מנגנוני ההרצה מחזירים `{ blocked, payload|response, results, guardrail?, message? }`,
כאשר `results` הוא מערך של רשומות `GuardrailExecutionResult` הכוללות
את השדות `blocked`,‏ `skipped`,‏ `modified`,‏ `error` ו-`meta` לכל מעקה בטיחות,
והם שימושיים למעקב.

### השבתת מעקות בטיחות לכל בקשה

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` מאגד רשימה
ללא כפילויות של שמות מעקות הבטיחות שעליהם יש לדלג בבקשה הנוכחית.
קיימים חמישה ערוצים, הנקראים בסדר הבא וממוזגים לרשימה אחת
(בעת הסרת כפילויות, המופע הראשון גובר):

1. `apiKeyInfo.disabledGuardrails`
2. `disabledGuardrails` בגוף הבקשה (ברמה העליונה)
3. `metadata.disabledGuardrails` בגוף הבקשה (רק כאשר `metadata` הוא אובייקט)
4. הכותרת `x-omniroute-disabled-guardrails`
5. הכותרת הקודמת `x-disabled-guardrails`

כל חמשת הערוצים ממוזגים, כולל שתי הכותרות: שליחת
`x-omniroute-disabled-guardrails` וגם `x-disabled-guardrails` גורמת לדילוג על איחוד
הרשימות שלהן, וכותרת מודרנית ריקה כבר אינה מסתירה את הכותרת הקודמת
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), תוקן במסגרת
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805)).

הערכים יכולים להיות מערכים של מחרוזות או מחרוזת מופרדת בפסיקים; השמות עוברים חיתוך
ורמול לאותיות קטנות בפורמט kebab-case (`pii_masker` → `pii-masker`), ורשומות
ריקות מוסרות. התוצאה מועברת דרך `context.disabledGuardrails`
אל המרשם, שמדלג על מעקות בטיחות תואמים (`skipped: true` בתוך `results`).

רשימת ההשבתה משפיעה רק על **המרשם**. מצב `block` של הזרקת הנחיות הוא
גבול מחייב: תווכת ההגנה מפני הזרקת הנחיות
(`src/middleware/promptInjectionGuard.ts`) קוראת ל-`evaluatePromptInjection()`
ללא רשימת השבתה כלשהי שבשליטת הקורא (הקריאה המתה
`resolveDisabledGuardrails({ body })` שביצעה בעבר הוסרה במסגרת
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934)), ולכן בקשה
שמשביתה את `prompt-injection` עדיין נדחית במצב `block`. זהו
התכנון המכוון. ערוצי ההשבתה נשלטים על ידי הקורא (גוף הבקשה,
מטא-נתונים וכותרות), ואסור שלקורא תהיה אפשרות לכבות בקרת אבטחה
שהוגדרה על ידי המפעיל
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). איחוד הכותרות
מ-[#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412)
משנה רק על אילו מעקות בטיחות במרשם מדלגים; הוא אינו מאפשר ללקוח
לעקוף את התווכה. מדיניות חובה של מעקות בטיחות לכל מפתח ולכל קבוצה
נמצאת במעקב ב-RFC של v4‏ [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417).
ראו [כיסוי ומגבלות](#coverage-and-limits).

## סדר הביצוע

עבור כל בקשה שעוברת דרך `src/sse/handlers/chat.ts` ודרך
`open-sse/handlers/chatCore.ts` (נתיבי משפחת הצ'אט המפורטים תחת
[כיסוי ומגבלות](#coverage-and-limits)):

1. `resolveDisabledGuardrails(...)` בונה את רשימת הדילוג ממפתח ה-API, מגוף הבקשה
   ומהכותרות.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` מפעיל את מנגנוני ההגנה לפי סדר
   עדיפות עולה:
   - מנגנוני הגנה מושבתים מתועדים בתור `skipped`.
   - ה-`preCall` של כל מנגנון הגנה עשוי לשכתב את המטען באמצעות `modifiedPayload`.
   - ה-`block: true` הראשון עוצר מיד את השרשרת, והמטפל מחזיר
     תגובת דחייה של מנגנון ההגנה.
3. המטען (שעשוי להיות משוכתב) מועבר לניתוב משולב ולשליחה לשירות במעלה הזרם.
4. **ללא הזרמה בלבד:** לאחר הרכבת התגובה,
   `guardrailRegistry.runPostCallHooks(...)` מפעיל את אותה השרשרת על
   התגובה. `block: true` בשלב זה מבטל את תגובת השירות במעלה הזרם ומחזיר HTTP 400. תגובות מוזרמות מדלגות לחלוטין על שלב זה.

מנגנוני הגנה שזורקים חריגה מתועדים עם `error: <message>` ונרשמים ביומן באמצעות
`logger.warn`, אך השרשרת ממשיכה — בתכנון מכוון של כשל פתוח.

### היכן ה-hooks פועלים

| Hook / בקרה                       | פועל על                                                                                                                                                                                                                                                                                                                                                                                                                             |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `runPreCallHooks`                 | בקשות המטופלות באמצעות `handleChat` (`src/sse/handlers/chat.ts`): `/v1/chat/completions`, `/v1/completions`, `/v1/messages`, `/v1/responses` (וכן `/v1/responses/*`), `/v1/relay/chat/completions`, `/v1/providers/{provider}/chat/completions`, `/v1/api/chat`, `/v1/antigravity`, `/v1beta/models/*`, ופרוקסי הצ'אט של Telegram. כמו כן, נקודת הקצה לבדיקות בלוח הבקרה `/api/guardrails/test`. חסימה לפני הקריאה מחזירה HTTP 400. |
| `runPostCallHooks`                | תגובות צ'אט **ללא הזרמה** בלבד (`open-sse/handlers/chatCore/nonStreamingResponse.ts`). תגובות מוזרמות לעולם אינן מגיעות אליו.                                                                                                                                                                                                                                                                                                       |

| תווכת הגנה מפני הזרקה (מדור קודם) | כל נתיב `/v1` הנושא הנחיה, לרבות משפחת הצ'אט (ראו [כיסוי נתיבים](#injection-guard-route-coverage--red-team-phase-8--block-d)). הזרקת הנחיות בלבד.                                                                                                                                                                                                                                                                                   |

### מה אינו מכוסה

- **נתיבי מדיה, הטמעות ונתונים** (`/v1/images/*`, `/v1/embeddings`,
  `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`,
  `/v1/rerank`, `/v1/search`, `/v1/moderations`) לעולם אינם מגיעים לרישום. לא
  מתבצעים בהם מיסוך PII, מיסוך פרטי גישה או גשר בין אופני קלט. הבדיקה היחידה
  שלהם היא תווכת ההגנה מפני הזרקה מהדור הקודם.
- **תגובות מוזרמות** אינן עוברות מנגנוני הגנה לאחר הקריאה: אין הפעלה לאחר הקריאה של `pii-masker` או
  `credential-masker`, ואין חסימה לאחר הקריאה. רק התמרת PII בהזרמה
  חלה (כאשר `PII_RESPONSE_SANITIZATION` מופעל). פרטי גישה
  המוחזרים בתגובה מוזרמת אינם מצונזרים.
- **ערוצי השבתה לעומת התווכה (בתכנון מכוון):** התווכה מעריכה
  הזרקת הנחיות באמצעות קריאה עצמאית ל-`evaluatePromptInjection()`, בלי
  להעביר רשימת השבתה כלשהי שבשליטת הקורא. מצב `block` הוא גבול
  מחייב שהשבתות בשליטת הקורא אינן יכולות לעקוף, לרבות בנתיבי משפחת הצ'אט
  ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). השבתת
  `prompt-injection` מדלגת רק על מנגנון ההגנה שברישום.

### מה נחשף לתגובה לפני שלב post-call

בנתיב ללא הזרמה הסדר הוא: חילוץ זיכרון → הפעלת כלים מובנים
→ מנגנוני הגנה לאחר הקריאה → יציאה בעקבות חסימה לאחר הקריאה → אחסון במטמון סמנטי.

- **חילוץ זיכרון** ו**הפעלת כלים** נחשפים לתגובה לפני שמנגנוני ההגנה שלאחר הקריאה יכולים לשכתב או לחסום אותה. מאז
  [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401), חילוץ
  הזיכרון מעביר את הטקסט שחולץ דרך `sanitizePII` כאשר
  `PII_RESPONSE_SANITIZATION` מופעל (הן בהזרמה והן ללא הזרמה), אך תגובה
  שנחסמת מאוחר יותר לאחר הקריאה עדיין מוצעת לזיכרון ולכלים.
- **המטמון הסמנטי** מאחסן את התגובה לאחר שלב שלאחר הקריאה, ולכן הוא מאחסן את
  התגובה המשוכתבת, ותגובה חסומה לעולם אינה נשמרת במטמון. רשומות המטמון
  מקושרות לכל מפתח API בנפרד.

## תצורה

משתני סביבה הנקראים על ידי מנגנוני ההגנה המובנים:

| משתנה                                 | משמש את                   | השפעה                                                                                               |
| ------------------------------------- | ------------------------- | --------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`        | הגדירו כ־`false` כדי להשבית את הזיהוי לחלוטין.                                                      |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`        | מדיניות הזרקה: `warn`, `block` או `log`. הערך הישן `redact` אינו משכתב את טקסט ההזרקה.              |
| `INJECTION_GUARD_MODE`                | `prompt-injection`        | מצב מנגנון ההגנה מפני הזרקה; זהו גם דגל תכונה במסד הנתונים אשר **גובר** על משתני הסביבה (DB > ENV). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`        | דרגת החומרה המזערית ש־`MODE=block` דוחה: `high` (ברירת המחדל), `medium` או `low`.                   |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`        | כינוי ישן עבור `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                   |
| `PII_REDACTION_ENABLED`               | `pii-masker`              | כאשר הערך הוא `true`, מידע אישי מזהה בבקשה מושחר (ללא תלות במצב ההזרקה).                            |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (בהמשך הזרם) | שולט בהתנהגות מנגנון המיסוך בצד התגובה.                                                             |

מנגנוני ההגנה של Modality Bridge קוראים את תצורת זמן הריצה ממאגר ההגדרות
המגובה במסד הנתונים (`getSettings()`), ולא ממשתני סביבה. המפתחות הראשיים של Vision הם
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` ו־
`modalityBridgeCacheMaxEntries`. המפתחות הישנים
`visionBridge*` מתקבלים רק כמנגנון הנסיגה המתועד לקריאה במשך מחזור אחד;
כתיבות מלוח הבקרה משתמשות במפתחות הראשיים. ערכי ברירת המחדל ופותר מנגנון הנסיגה
נמצאים ב־`src/shared/constants/modalityBridgeDefaults.ts`, בעוד שהקבועים הישנים
נשמרים ב־`src/shared/constants/visionBridgeDefaults.ts`.

Audio משתמש ב־`modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` וב־`modalityBridgeAudioMaxClips`, בנוסף להגדרות
`modalityBridgeCache*` המשותפות. ל־Audio אין מנגנון נסיגה למפתחות ישנים, מפני שמפתחות
אלה הוצגו יחד עם הסכימה של Modality Bridge.

Video משתמש ב־`modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` וב־
`modalityBridgeVideoTimeout`, בנוסף להגדרות `modalityBridgeCache*` המשותפות.
הוא מושבת כברירת מחדל, מפני ש־FFmpeg/ffprobe הם תלויות תפעוליות
אופציונליות, והוספת כתוביות תיאור לפריימים מגדילה את זמן ההשהיה ואת עלות המודל.

## מנגנוני הגנה מותאמים אישית

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

שלבים:

1. צרו את `src/lib/guardrails/myGuardrail.ts` כך שירחיב את `BaseGuardrail`.
2. ממשו את `preCall` ו/או את `postCall`.
3. רשמו אותו בזמן הייבוא (באמצעות הוספה מתוך `registerDefaultGuardrails`) או
   קראו ל-`guardrailRegistry.register(...)` בזמן ריצה — המאגר מחליף
   כל מנגנון הגנה קודם בעל אותו שם מנורמל.
4. הוסיפו בדיקות תחת `tests/unit/` (דוגמאות קיימות:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## בדיקות

השתמשו ב-`resetGuardrailsForTests()` בין בדיקות כדי להתחיל ממצב ידוע.
העבירו `{ registerDefaults: false }` כדי להתחיל עם מאגר ריק ולרשום
רק את מנגנוני ההגנה הנבדקים. Vision Bridge תומך בהזרקת תלויות
(`deps.getSettings`, `deps.callVisionModel`); ‏Audio Bridge חושף את
נקודות ההרחבה המקבילות עבור הגדרות, יכולות, בחירת מודל STT, בדיקות
אישורים ותמלול. לכן, בדיקות יכולות להפעיל את שני התהליכים ללא גישה
למסד נתונים או לרשת.

## כיסוי נתיבים ובדיקות צוות אדום למנגנון ההגנה מפני הזרקה (שלב 8 · בלוק D)

מנגנון ההגנה מפני הזרקה (`createInjectionGuard` / `withInjectionGuard`) מכסה את כל הנתיבים
שמקבלים הנחיות ממשתמשים. הוא מכבד את `INJECTION_GUARD_MODE` (ברירת המחדל `warn` = רישום ביומן בלבד;
`block` = החזרת HTTP 400 עם `SECURITY_001`).

| סוג         | נתיבים                                                                                                                                               | מצב ברירת מחדל |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| טקסט (קיים) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | אזהרה          |
| גנרטיבי     | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | אזהרה          |
| נתונים      | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | אזהרה          |

חילוץ הטקסט (`extractMessageContents`) מכסה את `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**צוות אדום (מדי לילה, `nightly-llm-security.yml`):** ‏promptfoo מוודא שכל נתיב חוסם
את קורפוס OWASP-LLM כאשר `INJECTION_GUARD_MODE=block`; ‏garak מריץ בדיקות חדירה (ומדלג בהיעדר סוד).
`moderations` נכלל לשם עקביות. מצב חסימה הוא גבול מחייב: `evaluatePromptInjection()`
מתעלם מרשימת ההשבתה לכל בקשה שמעביר אליו המתווך, ולכן `disabledGuardrails`
**אינו** מחריג נתיב ממנו ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

תהליך העבודה הלילי (`.github/workflows/nightly-llm-security.yml`, תזמון cron + הפעלה
ידנית) כולל שתי משימות:

- **`promptfoo-guard` (חוסמת)** — מריצה את `promptfoo eval -c promptfooconfig.yaml`
  עם `INJECTION_GUARD_MODE=block`. כל מקרה עוין (למשל, "התעלם מכל
  ההוראות הקודמות…", פריצות בסגנון DAN) מוודא שהתגובה מכילה
  `error.code === "SECURITY_001"`, כלומר שמנגנון ההגנה אכן דחה את הבקשה.
- **`garak` (מייעצת)** — מריצה את garak עם `--probes promptinject,dan,leakreplay`
  מול מופע מקומי של OmniRoute‏ (`http://localhost:20128/v1`). היא מותנית בקיומו של
  סוד ספק (`PROMPTFOO_PROVIDER_KEY`); מדלגת באופן תקין ומסתיימת
  ב-`|| true`, כך שהיא מדווחת בלי להכשיל את ה-CI.

כיסוי מסייע מנגנון ההגנה (`createInjectionGuard` / `withInjectionGuard`)
משתרע על כל נתיב `/v1` שמכיל הנחיות; טקסט ההנחיה נשלף מתוך
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` באמצעות
`extractMessageContents()` שבקובץ `src/shared/utils/inputSanitizer.ts`.
