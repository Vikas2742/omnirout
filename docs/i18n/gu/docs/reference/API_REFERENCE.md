## ચેટ પૂર્ણતાઓ

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### કસ્ટમ હેડર્સ

| હેડર                     | દિશા     | વર્ણન                                                                                                                                                                                                                                 |
| ------------------------ | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | વિનંતી   | કૅશને બાયપાસ કરવા માટે `true` પર સેટ કરો                                                                                                                                                                                              |
| `x-omniroute-no-memory`  | વિનંતી   | આ વિનંતી માટે મેમરી + કૌશલ્યોનું ઇન્જેક્શન છોડવા `true` પર સેટ કરો (નો-કૅશ જેવું જ; દરેક કૉલનો ટોકન/ખર્ચ ઓવરહેડ ટાળે છે)                                                                                                              |
| `X-OmniRoute-Progress`   | વિનંતી   | પ્રગતિ ઇવેન્ટ્સ માટે `true` પર સેટ કરો                                                                                                                                                                                                |
| `X-Session-Id`           | વિનંતી   | બાહ્ય સેશન એફિનિટી માટે સ્ટિકી સેશન કી                                                                                                                                                                                                |
| `x_session_id`           | વિનંતી   | અન્ડરસ્કોર વેરિઅન્ટ પણ સ્વીકારવામાં આવે છે (સીધું HTTP)                                                                                                                                                                               |
| `X-OmniRoute-Session-Id` | વિનંતી   | કૉલર દ્વારા પૂરું પાડવામાં આવેલ સેશન/વાતચીત ટૅગ (મેમરીને પણ ફીડ કરે છે). હાજર હોય ત્યારે, પ્રતિ-સેશન ખર્ચ એટ્રિબ્યુશન માટે `call_logs.session_tag`માં યથાવત્ સંગ્રહિત થાય છે (#8249) — ગેરહાજર હોય ત્યારે ક્યારેય બનાવવામાં આવતું નથી |
| `Idempotency-Key`        | વિનંતી   | ડિડુપ કી (5 સેકન્ડની વિન્ડો)                                                                                                                                                                                                          |
| `X-Request-Id`           | વિનંતી   | વૈકલ્પિક ડિડુપ કી                                                                                                                                                                                                                     |
| `x-omniroute-connection` | વિનંતી   | સિંગલ-મોડેલ વિનંતીને તેના id દ્વારા એક પ્રોવાઇડર કનેક્શન (એકાઉન્ટ) સાથે પિન કરો — [વિનંતીદીઠ એકાઉન્ટ પિનિંગ](#account-pinning-per-request) જુઓ                                                                                        |
| `X-OmniRoute-Cache`      | પ્રતિસાદ | `HIT` અથવા `MISS` (નોન-સ્ટ્રીમિંગ)                                                                                                                                                                                                    |
| `X-OmniRoute-Idempotent` | પ્રતિસાદ | ડિડુપ્લિકેટ થયું હોય તો `true`                                                                                                                                                                                                        |
| `X-OmniRoute-Progress`   | પ્રતિસાદ | પ્રગતિ ટ્રૅકિંગ ચાલુ હોય તો `enabled`                                                                                                                                                                                                 |
| `X-OmniRoute-Session-Id` | પ્રતિસાદ | OmniRoute દ્વારા ઉપયોગમાં લેવાયેલ અસરકારક સેશન ID                                                                                                                                                                                     |
| `X-OmniRoute-Request-Id` | પ્રતિસાદ | વિનંતી સહસંબંધ id (જ્યારે જાણીતું હોય)                                                                                                                                                                                                |
| `X-OmniRoute-Version`    | પ્રતિસાદ | OmniRoute બિલ્ડ વર્ઝન (હંમેશાં હાજર)                                                                                                                                                                                                  |
| `X-OmniRoute-Cost-Saved` | પ્રતિસાદ | HIT પર કૅશને કારણે બચેલા USD (ફક્ત કૅશ હિટ્સ માટે)                                                                                                                                                                                    |
| `X-OmniRoute-Decision`   | પ્રતિસાદ | રાઉટિંગ ટ્રેસ: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` એ કોમ્બો સ્ટ્રેટેજી છે અથવા નોન-કોમ્બો વિનંતી માટે `single`) — પૂર્ણતા પ્રતિસાદોમાં હંમેશાં હાજર હોય છે                                                  |

> Nginx નોંધ: જો તમે અન્ડરસ્કોર ધરાવતા હેડર્સ પર આધાર રાખતા હોવ (ઉદાહરણ તરીકે `x_session_id`), તો `underscores_in_headers on;` સક્ષમ કરો.

#### દરેક વિનંતી માટે એકાઉન્ટ પિનિંગ

જ્યારે કોઈ પ્રદાતા પાસે અનેક કનેક્શન્સ (એકાઉન્ટ્સ અથવા કીઝ) હોય, ત્યારે OmniRoute સામાન્ય રીતે તેની એકાઉન્ટ-પસંદગી વ્યૂહરચના દ્વારા તેમાંથી એક પસંદ કરે છે. તેના બદલે, વિનંતી `x-omniroute-connection` હેડર વડે કોઈ એક ચોક્કસ કનેક્શનને પિન કરી શકે છે:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **id ક્યાંથી મેળવવું.** ડેશબોર્ડમાં પ્રદાતાનું પેજ ખોલો
  (**Dashboard → Providers → <provider>**) અને કનેક્શનની પંક્તિ પરના `xxxxxxxx…` id ચિપને ક્લિક કરો
  — તે સંપૂર્ણ કનેક્શન id કૉપિ કરે છે.
- **કઈ વિનંતીઓ તેનો ઉપયોગ કરે છે.** `/v1/chat/completions`, `/v1/messages` અને
  `/v1/responses` પરની સિંગલ-મોડલ વિનંતીઓ (`provider/model`). કોમ્બોઝ હેડરને અવગણે છે: તેના બદલે
  દરેક કોમ્બો સ્ટેપ માટે તે સ્ટેપના પોતાના કનેક્શન દ્વારા એકાઉન્ટ પિન કરો.
- **પિન કડક છે, માત્ર પસંદગી નથી.** ફક્ત પિન કરેલું કનેક્શન જ વપરાય છે. વિનંતીની અંદર
  નિષ્ફળતા થાય તો એકાઉન્ટનો કૂલડાઉન નોંધાય છે, પરંતુ તે સમાન પ્રદાતાના અન્ય
  એકાઉન્ટ પર **સ્વિચ થતું નથી**.
- **કૂલડાઉન અને ક્વોટા પિનને મુક્ત કરે છે.** જ્યારે પિન કરેલું કનેક્શન કૂલડાઉનમાં હોય,
  ક્વોટા સમાપ્ત થઈ ગયો હોય અથવા ક્વોટા નીતિ દ્વારા અવરોધિત હોય, ત્યારે પછીની વિનંતીઓ પ્રદાતાના
  અન્ય કનેક્શન્સનો ઉપયોગ કરે છે, બિલકુલ પિન ન કરેલા ટ્રાફિકની જેમ.
- **અજાણ્યા અથવા અક્ષમ કરેલા ids નિષ્ફળ જાય છે.** પ્રદાતાના સક્રિય પૂલમાં ન હોય તેવો id (કાઢી નાખેલો,
  નિષ્ક્રિય કરેલો અથવા અન્ય પ્રદાતાનો હોય તેવો) કોઈ પાત્ર એકાઉન્ટ છોડતો નથી, તેથી વિનંતી
  ચૂપચાપ અન્યત્ર રૂટ થવાને બદલે નિષ્ફળ જાય છે.

Claude Code `ANTHROPIC_CUSTOM_HEADERS` દ્વારા કસ્ટમ હેડર્સ મોકલે છે. તેને
`~/.claude/settings.json` ના `env` બ્લોકમાં મૂકો અથવા દરેક પ્રોજેક્ટ માટે અલગ
એકાઉન્ટ પિન કરવા પ્રોજેક્ટ-સ્તરની `.claude/settings.json` ફાઇલમાં મૂકો:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

સ્રોત: `src/sse/handlers/chat.ts` (હેડર વાંચવું), `src/sse/services/auth.ts` અને
`src/sse/services/sessionAffinityPin.ts` (પિન મુક્ત કરવું અને પૂલમાં ગેરહાજરીની ચકાસણી).

> **ખર્ચ ટેલિમેટ્રી હેડર્સ:** નોન-સ્ટ્રીમિંગ સફળતા પ્રતિસાદોમાં `X-OmniRoute-*` ખર્ચ-ટેલિમેટ્રી સમૂહ પણ હોય છે — `X-OmniRoute-Response-Cost` (USD, નિશ્ચિત 10 દશાંશ સ્થાનો; મફત/કિંમત નક્કી ન હોય તે માટે `0.0000000000`), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit`, અને `X-OmniRoute-Fallback-Attempts` (માત્ર જ્યારે > 0 હોય ત્યારે), ઉપરાંત `X-OmniRoute-Request-Id` અને `X-OmniRoute-Version`. આ chat completions, `/v1/responses`, `/v1/messages`, **તેમજ મીડિયા એન્ડપોઇન્ટ્સ** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations`, અને `/v1/moderations` (ખર્ચ હંમેશાં `0`) — દ્વારા ઉત્સર્જિત થાય છે. જ્યારે કિંમત ઉપલબ્ધ હોય ત્યારે મીડિયા ખર્ચ દરેક મોડાલિટી મુજબ (દર ઇમેજ, દર સેકન્ડ, દર અક્ષર, દર સર્ચ-યુનિટ) ગણવામાં આવે છે, અન્યથા `0` (નિષ્ફળતા છતાં આગળ વધે છે).

> **કૅશ-હિટ ખર્ચના અર્થનિર્ધારણ:** સેમેન્ટિક-કૅશ HIT (`X-OmniRoute-Cache-Hit: true`) પર કોઈ અપસ્ટ્રીમ કૉલ કરવામાં આવતો નથી, તેથી `X-OmniRoute-Response-Cost` એ `0.0000000000` હોય છે (હિટ પૂરી પાડવાનો **વધારાનો** ખર્ચ). મૂળ/થવાનો હતો તે ખર્ચ `X-OmniRoute-Cost-Saved` માં અલગથી જણાવવામાં આવે છે. બિલિંગ ઉપભોક્તાઓએ `X-OmniRoute-Response-Cost` નો સરવાળો કરવો જોઈએ (હિટ્સનો કોઈ ખર્ચ નથી); કૅશ એનાલિટિક્સ `X-OmniRoute-Cost-Saved` ને એકત્રિત કરી શકે છે.

## વિશિષ્ટ સંચાલિત સત્ર લીઝ

વિશિષ્ટ સંચાલિત સત્ર લીઝિંગ એ સ્વૈચ્છિક, ક્લાયન્ટ-નિરપેક્ષ રૂટિંગ કરાર છે: એક સક્રિય માલિક
એક પાત્ર OmniRoute કનેક્શન ધરાવે છે. તે કોઈ મોડેલને લીઝ પર આપતું નથી, OAuthની આવશ્યકતા રાખતું નથી, કોઈ
ચોક્કસ ક્લાયન્ટને ઓળખતું નથી અથવા કોઈ ચોક્કસ પ્રદાતાની આવશ્યકતા રાખતું નથી.

પ્રમાણીકરણ કરતી API કી પાસે `lease:exclusive` સ્કોપ અને સ્પષ્ટ બિન-ખાલી
`allowedConnections` સૂચિ હોવી આવશ્યક છે. ડેટાબેઝ મ્યુટેશન સીમા કી બનાવતી વખતે અને
આંશિક અપડેટ્સ વખતે બંને ફીલ્ડને એકસાથે લાગુ કરે છે.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

સફળ acquire, renew અને release પ્રતિસાદો ટાઇમસ્ટેમ્પ્સ, `state` અને ચોક્કસ ધન
`generation` દર્શાવે છે, પરંતુ પસંદ કરેલું કનેક્શન અથવા ક્રેડેન્શિયલ્સ ક્યારેય દર્શાવતા નથી. Renew અને release
JSON બોડીમાં જનરેશન આપે છે:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

સક્રિય લીઝ માલિક તેના વર્તમાન બાઇન્ડિંગ માટે ગોપનીયતા-સુરક્ષિત ડિસ્પ્લે મેટાડેટાની સ્પષ્ટ વિનંતી કરી શકે છે:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

આ સ્વૈચ્છિક status ક્રિયા એક જ ડેટાબેઝ ટ્રાન્ઝેક્શનમાં અપારદર્શક માલિક, પ્રમાણિત સંચાલિત API કી અને ચોક્કસ
સક્રિય જનરેશન દ્વારા ફેન્સ કરવામાં આવે છે. `displayName` માત્ર ટ્રિમ કરેલું રૂપરેખાંકિત
કનેક્શન નામ છે; જ્યારે કોઈ સુરક્ષિત રૂપરેખાંકિત નામ અસ્તિત્વમાં ન હોય ત્યારે તે `null` હોય છે. OmniRoute ક્યારેય
ઇમેઇલ અથવા જનરેટ કરેલી એકાઉન્ટ ઓળખને તેના સ્થાને મૂકતું નથી. પ્રદાતા મૂલ્ય બિન-સંવેદનશીલ ડિસ્પ્લે લેબલ છે અને ક્યારેય
જનરેટ કરેલું સુસંગત-પ્રદાતા ઓળખકર્તા નથી. ક્રેડેન્શિયલ્સ, ટોકન્સ, કૂકીઝ, કાચા કનેક્શન અથવા API
કી ids, માલિક હૅશ, ફેન્સિંગ સિક્રેટ્સ અને આંતરિક રૂટિંગ ડેટાને બાકાત રાખવામાં આવે છે.

ખોટી-કી, ખોટા-માલિક, જૂના-જનરેશન, ગુમ, સમાપ્ત થયેલા, રિલીઝ થયેલા અને અમાન્ય બનાવેલા લુકઅપ્સ બધા
કનેક્શન મેટાડેટા વિના સમાન `409 LEASE_FENCE_STALE` ભૂલ પરત કરે છે. ક્ષમતા-પ્રતીક્ષા પ્રતિસાદ મેળવનારા ક્લાયન્ટ પાસે તપાસવા માટે કોઈ સક્રિય બાઇન્ડિંગ હોતું નથી. જ્યારે રૂટિંગ સક્રિય લીઝને પરિવર્તિત કરે છે,
ત્યારે સમાન જનરેશન માન્ય રહે છે અને status જૂનું બાઇન્ડિંગ ક્યારેય નહીં, પરંતુ નવું બાઇન્ડિંગ એટોમિક રીતે પરત કરે છે.
હાલના ક્લાયન્ટ્સમાં કોઈ ફેરફાર થતો નથી, કારણ કે acquire, renew, release અને waiting પ્રતિસાદો
તેમના અગાઉના માળખાં જાળવી રાખે છે.

આ સર્વર કરાર માનક OpenAI Codex `/status`ને બદલતો નથી. માનક Codex હાલમાં તેનો
મોડેલ પ્રદાતા અને બિલ્ટ-ઇન પ્રમાણીકરણ/એકાઉન્ટ સ્થિતિ દર્શાવે છે, પરંતુ મનસ્વી કસ્ટમ
પ્રદાતા એકાઉન્ટ મેટાડેટા રેન્ડર કરતું નથી; ભાવિ ક્લાયન્ટ ઇન્ટિગ્રેશને આ ક્રિયાને કૉલ કરીને
`connection.displayName` કેવી રીતે દર્શાવવું તે નક્કી કરવું પડશે.

ત્યારબાદ દરેક સંચાલિત ઇન્ફરન્સ વિનંતી બંને નિયંત્રણ હેડર્સ આપે છે:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

ચોક્કસ માલિક, જનરેશન, સક્રિય કનેક્શન અને પ્રમાણિત API કીને દરેક સમર્થિત
અપસ્ટ્રીમ પ્રયાસ પહેલાં તરત જ ફેન્સ કરવામાં આવે છે. અન્ય કી સાથે માલિક અને જનરેશનને ફરી ચલાવવાનો પ્રયાસ ત્યારે પણ
નિષ્ફળ જાય છે જ્યારે તે કી સમાન કનેક્શનને મંજૂરી આપતી હોય. કાચા માલિકોને સાચવવામાં, લૉગ કરવામાં, વિનંતી
સ્નૅપશૉટમાં જાળવવામાં અથવા અપસ્ટ્રીમ પર ફોરવર્ડ કરવામાં આવતા નથી.

કામચલાઉ સંસાધન-સ્પર્ધા `Retry-After` સાથે HTTP `429` અને નીચેનો પ્રતિસાદ આપે છે:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

આ પ્રતિસાદનો અર્થ માત્ર એટલો છે કે સામાન્ય પાત્ર સેટ બિન-ખાલી હતો અને દરેક મુક્ત ઉમેદવાર
અન્ય સક્રિય લીઝ દ્વારા રોકાયેલો હતો. અસમર્થિત મોડેલ્સ/પ્રદાતાઓ, નીતિ અસંગતતા, કૂલડાઉન, ક્વોટા,
હેલ્થ અને અન્ય સામાન્ય પાત્રતા નિષ્ફળતાઓ તેમના હાલના OmniRoute પ્રતિસાદો જાળવી રાખે છે.

### `x-omniroute-compression`

કમ્પ્રેશન પ્લાનનું પ્રતિ-વિનંતી ઓવરરાઇડ. સર્વોચ્ચ અગ્રતા — રૂટિંગ-કોમ્બો
ઓવરરાઇડ, સક્રિય પ્રોફાઇલ, ઑટો-ટ્રિગર અને પેનલના ડિફૉલ્ટ કરતાં પણ પ્રબળ. મૂલ્યો:

| મૂલ્ય         | અસર                                                                                                    |
| ------------- | ------------------------------------------------------------------------------------------------------ |
| `off`         | આ વિનંતી માટે કોઈ કમ્પ્રેશન નહીં.                                                                      |
| `default`     | પેનલથી મેળવેલી ડિફૉલ્ટ પ્રોફાઇલ (સક્રિય પ્રોફાઇલને અવગણે છે). નુકસાનકારક એન્જિન્સ બંધ રાખવામાં આવે છે. |
| `safe`        | માત્ર ડિડુપ્લિકેશન અને વ્હાઇટસ્પેસ ફોલ્ડિંગ.                                                           |
| `allow-lossy` | સારાંશો અને શૈલી પુનર્લેખનો સહિત, આ વિનંતી માટે ઑપરેટર પ્લાન જાળવે છે.                                 |
| `engine:<id>` | સક્ષમ હોય ત્યારે એક જ એન્જિન, દા.ત. `engine:rtk`. તે એન્જિન માટે પ્રતિ-વિનંતી સ્વૈચ્છિક પસંદગી.        |
| `<combo>`     | નામથી ઓળખાતો કોમ્બો, પ્રથમ નામ પ્રમાણે (કેસ-ઇન્સેન્સિટિવ), ત્યારબાદ id પ્રમાણે મેળ ખવડાવવામાં આવે છે.  |

નોંધો:

- અજાણ્યા મૂલ્યો અવગણવામાં આવે છે (વિનંતી ક્યારેય નકારવામાં આવતી નથી); રિઝોલ્યુશન સામાન્ય ઑપરેટર અગ્રતા મુજબ આગળ વધે છે.
- જો એકથી વધુ કોમ્બો સમાન નામ ધરાવતા હોય, તો નિશ્ચિત મેળ માટે કોમ્બોનું **id** આપો.
- જે કોમ્બોનું નામ `off` અથવા `default` હોય તેને નામ દ્વારા પસંદ કરી શકાતું નથી (તે કીવર્ડ્સનું અર્થઘટન પહેલાં થાય છે); આવા કોમ્બોને તેના id દ્વારા સંદર્ભિત કરો.
- મુખ્ય કમ્પ્રેશન સ્વિચ કડક અવરોધ છે: જ્યારે કમ્પ્રેશન વૈશ્વિક રીતે અક્ષમ હોય, ત્યારે આ હેડર તેને સક્ષમ કરી શકતું નથી.

લાગુ કરેલો પ્લાન પ્રતિસાદ હેડરમાં પાછો દર્શાવવામાં આવે છે:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

જ્યાં `<source>` એ `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` અથવા `off`માંથી એક છે.

## એમ્બેડિંગ્સ

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

ઉપલબ્ધ પ્રદાતાઓ: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

કૅટલૉગ IDs `provider/model` સ્વરૂપે હોય છે (ઉદાહરણ: `jina-ai/jina-embeddings-v5-omni-small`). રજિસ્ટ્રીમાં દેખાતા ફક્ત Jina મૉડલ IDs (ઉદાહરણ તરીકે `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) પણ રિઝોલ્વ થાય છે. Jina embed/rerank/classify/segment પહેલાં ડૅશબોર્ડનાં `jina-ai` ક્રેડેન્શિયલ્સનો ઉપયોગ કરે છે; કોઈ ડૅશબોર્ડ કી અસ્તિત્વમાં ન હોય ત્યારે જ `JINA_AI_API_KEY` ફૉલબૅક તરીકે વપરાય છે. `jina-reader` કાર્ડ માત્ર Reader / `r.jina.ai` માટે છે (`POST /v1/web/fetch`) અને ક્યારેય એમ્બેડિંગ્સ અથવા રીરૅન્ક પ્રદાન કરતું નથી.

મલ્ટિમોડલ સપોર્ટ દર્શાવતા રજિસ્ટ્રી મૉડલ્સ વધુમાં વધુ 32 પ્રદાતા-નિરપેક્ષ સંરચિત
આઇટમ્સ પણ સ્વીકારે છે. મીડિયા આઇટમના પ્રકારો `text`, `image`, `audio`, `video`, અને `document` છે. તેમનો મીડિયા `source`
કાં તો `{"type":"url","url":"https://..."}` અથવા
`{"type":"base64","data":"...","media_type":"..."}` હોય છે.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`,
અને ફૅમિલી ઉપનામ `jina-ai/jina-embeddings-v5-omni` → omni-small) Jinaના મૂળ
EmbeddingsV5Request ડૉક્સ પણ સ્વીકારે છે અને તેમને `https://api.jina.ai/v1/embeddings` પર **કોઈ ફેરફાર કર્યા વિના ફૉરવર્ડ કરે છે**:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

મૂળ `{ image | audio | video | pdf }` મૂલ્યો સાર્વજનિક HTTPS URL, `data:` URI, અથવા કાચું
base64 હોઈ શકે છે. OmniRoute તે ઑબ્જેક્ટ્સને સ્ટ્રિંગમાં રૂપાંતરિત કરતું નથી કે મૂળ ઇમેજ URLs ફેચ કરતું નથી — Jina
સાર્વજનિક મીડિયા જાતે મેળવે છે. વધારાનાં Jina ફીલ્ડ્સ (`task`, `normalized`, `truncate`, `embedding_type`)
ફૉરવર્ડ કરવામાં આવે છે. ફક્ત-ટેક્સ્ટ Jina SKUs હજુ પણ નૉન-ટેક્સ્ટ ડૉક્સને નકારે છે.

સુરક્ષા અને ટ્રાન્સપોર્ટ મર્યાદાઓ:

- રિમોટ મીડિયા URLs સાર્વજનિક HTTPS હોવા આવશ્યક છે. કૅનોનિકલ `{type,source:url}` આઇટમ્સને
  સર્વર-સાઇડ પર ફેચ કરવામાં આવે છે (રિડાયરેક્ટનું પુનઃમાન્યકરણ, સમયસમાપ્તિ, કદ મર્યાદાઓ, સાર્વજનિક DNS, કનેક્શન પિનિંગ) અને
  પ્રદાતાને કૉલ કરતાં પહેલાં ઇનલાઇન કરવામાં આવે છે. Jinaના મૂળ `{image:"https://..."}` આઇટમ્સને
  સમાન સાર્વજનિક-HTTPS ચકાસણી બાદ યથાવત્ ફૉરવર્ડ કરવામાં આવે છે; Jina URL ફેચ કરે છે.
- ઇનલાઇન base64 મીડિયા દરેક આઇટમ દીઠ ડિકોડ કરેલા 8 MiB અને સમગ્ર રિક્વેસ્ટમાં ડિકોડ કરેલા 16 MiB સુધી મર્યાદિત છે.

પ્રદાતા રૂપાંતરણ (કૅનોનિકલ આઇટમ્સ ક્યારેય ફેરફાર વિના ફૉરવર્ડ થતા નથી):

- Jina મલ્ટિમોડલ મૉડલ્સ: દરેક ટોચના સ્તરની આઇટમ એક મોડાલિટી-કી ધરાવતું ઑબ્જેક્ટ બને છે
  (`text` / `image` / `audio` / `video` / `pdf`), જેમાં ઇનલાઇન મીડિયા માટે data URIs વપરાય છે; દરેક
  ટોચના સ્તરની આઇટમ દીઠ એક વેક્ટર.
- Gemini Embedding 2 ફૅમિલી: ટોચના સ્તરની એક ઍરે એક જ મૂળ
  `models/{model}:embedContent` રિક્વેસ્ટમાં રૂપાંતરિત થાય છે, જેમાં `content.parts` (`text` અથવા `inline_data`) હોય છે.
- llama.cpp (`llama-cpp/<model>`, સ્થાનિક સર્વરે લોડ કરેલું કોઈપણ મૉડલ): કૅનોનિકલ `text` આઇટમ્સ
  સાદી સ્ટ્રિંગ્સ બને છે, અને `image` / `audio` / `video` દરેક એક
  `{"content": [part]}` ઑબ્જેક્ટ બને છે, જેમાં ઇનલાઇન ડેટા સાથે llama-serverના ચૅટ કન્ટેન્ટ ભાગો (`image_url`,
  `input_audio`, ફૉર્મેટ `wav` / `mp3` / `flac` સાથે, `input_video`) વપરાય છે; દરેક ટોચના સ્તરની
  આઇટમ દીઠ એક વેક્ટર. સર્વર `--embedding --mmproj …` સાથે ચાલવું આવશ્યક છે; પ્રોજેક્ટર વિના તે
  મીડિયાને જાતે નકારે છે. `document` સપોર્ટેડ નથી.
- સ્પષ્ટ મોડાલિટી મેટાડેટા વિનાનાં અજ્ઞાત/ડાયનેમિક મૉડલ્સ HTTP 400 સાથે સંરચિત ઇનપુટને નકારે છે.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

અસમર્થિત મૉડલ/મોડાલિટી સંયોજનો આઇટમને બળજબરીથી રૂપાંતરિત કરવાને બદલે HTTP 400 પરત કરે છે. લેગસી સ્ટ્રિંગ/ટોકન રિક્વેસ્ટ્સ પરનાં નૉન-ઇનપુટ
એક્સ્ટેન્શન ફીલ્ડ્સ કોઈ ફેરફાર વિના યથાવત્ પસાર થતા રહે છે.

```bash
# બધા એમ્બેડિંગ મૉડલ્સની યાદી બતાવો
GET /v1/embeddings
```

## છબી જનરેશન

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

ઉપલબ્ધ પ્રદાતાઓમાં OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (લોકલ), ComfyUI (લોકલ)નો સમાવેશ થાય છે.

`n`, `data[]`માં `n` છબીઓ પરત કરે છે. જે પ્રદાતાઓની અપસ્ટ્રીમ API દરેક કૉલ દીઠ એક છબી પરત કરે છે
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), તેમના માટે `n` અલગ અપસ્ટ્રીમ કૉલ કરવામાં આવે છે, જેમાં એકસાથે વધુમાં વધુ 4 કૉલ ચાલુ હોય છે. નિશ્ચિત
`seed`ને કૉલ ઇન્ડેક્સ પ્રમાણે ઑફસેટ કરવામાં આવે છે (`seed`, `seed + 1`, …), જેથી છબીઓ અલગ હોય પરંતુ
પુનરુત્પાદિત કરી શકાય તેવી રહે. `n`ની મહત્તમ મર્યાદા 10 છે. કોઈપણ કૉલ નિષ્ફળ જાય તો સમગ્ર વિનંતી
નિષ્ફળ જાય છે. ફૅન-આઉટ ફૉર્મેટની સૂચિ
`open-sse/handlers/imageGeneration/fanOut.ts`માં `SINGLE_IMAGE_FANOUT_FORMATS` છે.

ZenMux હાલના API-key કનેક્શનનો ફરીથી ઉપયોગ કરે છે અને `zenmux/` અથવા `zm/` પ્રીફિક્સ સ્વીકારે છે:

- `zenmux/openai/gpt-image-2`, ZenMuxની OpenAI Images APIનો ઉપયોગ કરે છે. વિકલ્પોમાં `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background`, અને `response_format`નો સમાવેશ થાય છે.
- અન્ય પબ્લિશર્સ, જેમ કે `zm/meta/muse-image-1.0`, ZenMuxના Vertex AI `:predict`
  એન્ડપોઇન્ટનો ઉપયોગ કરે છે. `n`, `sampleCount` સાથે, `aspect_ratio`, `aspectRatio` સાથે અને `image_size`
  (`1K`, `2K`, `4K`), `sampleImageSize` સાથે મૅપ થાય છે. પિક્સેલ `size` માત્ર આસ્પેક્ટ રેશિયો પૂરો પાડે છે,
  બાંયધરીકૃત પિક્સેલ પરિમાણો નહીં. સમર્થિત રેશિયો, રિઝોલ્યુશન અને ગણતરીઓ મોડેલ પ્રમાણે બદલાય છે.
- `zm/inclusionai/ming-image-0.1-design` પોતાનાં પરિમાણો જાતે પસંદ કરે છે. `size`,
  `aspect_ratio`, અને `image_size`ને છોડી દો; સ્પષ્ટ મૂલ્યો આપવાથી HTTP 400 પરત થાય છે. PNG, JPEG અને WebP
  માટે `output_format` વડે વિનંતી કરી શકાય છે.

આ ઇન્ટિગ્રેશન ટેક્સ્ટ-ટુ-ઇમેજ જનરેશનને સપોર્ટ કરે છે, રેફરન્સ-ઇમેજ એડિટિંગને નહીં. Vertex
આઉટપુટને `data[].b64_json`માં નોર્મલાઇઝ કરવામાં આવે છે; `response_format: "url"` અપસ્ટ્રીમ

## દસ્તાવેજ OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model`, `provider/model` પ્રીફિક્સ દ્વારા OCR પ્રદાતા પસંદ કરે છે; માત્ર મોડેલ id (દા.ત.
`mistral-ocr-latest`) તેના નોંધાયેલા પ્રદાતા પર રિઝોલ્વ થાય છે, અને `model` આપવામાં ન આવે તો તે ડિફૉલ્ટ રૂપે
Mistral (`mistral-ocr-latest`)નો ઉપયોગ કરે છે. નોંધાયેલા પ્રદાતાઓ (`open-sse/config/ocrRegistry.ts`):

| પ્રદાતા id                    | મોડેલ id             | `model` મૂલ્ય                                                  | નોંધો                                                                                                      |
| ----------------------------- | -------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (અથવા માત્ર `mistral-ocr-latest`) | સિંક્રોનસ — એકમાત્ર અપસ્ટ્રીમ કૉલમાંથી પ્રતિસાદ સીધો પરત કરવામાં આવે છે.                                   |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                    | અસિંક્રોનસ અપસ્ટ્રીમ (`analyze` + પોલ) — નીચે જુઓ.                                                         |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                        | Vertex AIના `openapi/chat/completions` પાર્ટનર એન્ડપોઇન્ટ મારફતે સિંક્રોનસ — પ્રમાણીકરણ/URL માટે નીચે જુઓ. |

ત્રણેય પ્રદાતાઓ સમાન Mistral-આકારની બૉડીમાં પ્રતિસાદ આપે છે:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence પોલ ફ્લો

Azure Document Intelligenceની `analyze` API અસિંક્રોનસ છે: પ્રારંભિક વિનંતી બૉડીને બદલે
`Operation-Location` હેડર પરત કરે છે અને પરિણામ માટે પોલ કરવું જરૂરી છે. હેન્ડલર
(`open-sse/handlers/ocr.ts`) તે URLને દર સેકન્ડે વધુમાં વધુ 30 પ્રયાસો સુધી પોલ કરે છે, `ok` ન હોય તેવા પોલ પ્રતિસાદ અથવા `"failed"` સ્ટેટસ પર તરત નિષ્ફળ થાય છે (પોલિંગ ચાલુ
રાખતું નથી), અને પ્રયાસોની મર્યાદા પૂરી થયા પછી પણ ઑપરેશન ચાલુ હોય તો `504` પરત કરે છે.
કૉલરને પરત કરતાં પહેલાં અંતિમ Azure પ્રતિસાદને Mistral દ્વારા ઉપયોગમાં લેવાતા સમાન
`pages`/`markdown` આકારમાં નોર્મલાઇઝ કરવામાં આવે છે, જેથી ક્લાયન્ટ કોડને પ્રદાતા માટે ખાસ વ્યવસ્થા કરવાની જરૂર રહેતી નથી.

### Vertex AI DeepSeek OCR પ્રમાણીકરણ અને એન્ડપોઇન્ટ રિઝોલ્યુશન

`vertex-deepseek-ocr`, ચૅટ/ઇમેજ ટ્રાફિક માટે OmniRoute પહેલેથી સપોર્ટ કરતું હોય તે જ Vertex AI પ્રમાણીકરણનો
ફરીથી ઉપયોગ કરે છે (`open-sse/executors/vertex.ts`): કનેક્શનની API key કાં તો
Service Account JSON ક્રેડેન્શિયલ હોય છે (જે JWT-bearer ફ્લો મારફતે ટૂંકી અવધિના OAuth access token માટે એક્સચેન્જ થાય છે)
અથવા પહેલેથી બનાવેલો OAuth access token હોય છે, જે જેમ છે તેમ ઉપયોગમાં લેવાય છે. અપસ્ટ્રીમ એન્ડપોઇન્ટ URL એ Vertexનું
સામાન્ય `openapi/chat/completions` પાર્ટનર એન્ડપોઇન્ટ છે, જે કનેક્શનના પ્રોજેક્ટ અને
રિજનમાંથી બનાવવામાં આવે છે — સ્પષ્ટ `providerSpecificData.project`/`providerSpecificData.region`ને હંમેશાં પ્રાથમિકતા મળે છે;
અન્યથા પ્રોજેક્ટ Service Account JSONના `project_id`માંથી મેળવવામાં આવે છે અને રિજન
ડિફૉલ્ટ રૂપે `us-central1` હોય છે. બંને રિઝોલ્યુશન `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`)માં થાય છે, અને `handleOcr`ને ડિસ્પૅચ કરતા પહેલાં
`src/app/api/v1/ocr/route.ts` દ્વારા તેનો ઉપયોગ કરવામાં આવે છે.

### મોડલ id પ્રિફિક્સ (`?prefix=`)

મોટાભાગનાં મોડલ્સ **પ્રોવાઇડર પ્રિફિક્સ** હેઠળ દર્શાવવામાં આવે છે. તમને કયો પ્રિફિક્સ મળે છે તે
`MODELS_CATALOG_PREFIX_MODE` ફીચર ફ્લૅગ દ્વારા નિયંત્રિત થાય છે અને ક્વેરી પેરામીટર વડે
**દરેક રિક્વેસ્ટ માટે** ઓવરરાઇડ કરી શકાય છે — જે એવા ક્લાયન્ટ માટે ઉપયોગી છે જેને બીજા બધા માટે
સર્વર-વ્યાપી સેટિંગ બદલ્યા વિના સ્વચ્છ સૂચિ જોઈએ છે:

```bash
GET /v1/models?prefix=alias        # દરેક મોડલ દીઠ એક id — ટૂંકો alias પ્રિફિક્સ
GET /v1/models?prefix=dual         # બંને સ્વરૂપો (સર્વર ડિફૉલ્ટ)
GET /v1/models?prefix=canonical    # ફક્ત સંપૂર્ણ provider-id પ્રિફિક્સ
```

| મોડ         | ઉત્સર્જિત કરે છે                                          | નોંધો                                                                                                                                                                                          |
| ----------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **અને** `claude/claude-sonnet-4-6` | **ડિફૉલ્ટ.** બંને ids એક જ મોડલ તરફ રૂટ થાય છે; બંનેમાંથી કોઈપણ સ્વરૂપ હાર્ડકોડ કરેલ હોય તેવા ક્લાયન્ટ કન્ફિગ્સ કાર્યરત રહે તે માટે જાળવી રાખવામાં આવ્યા છે. કેટલૉગનું કદ લગભગ બમણું કરે છે.   |
| `alias`     | `cc/claude-sonnet-4-6`                                    | દરેક મોડલ દીઠ એક એન્ટ્રી. અલગ alias ન ધરાવતા પ્રોવાઇડર્સ પણ તેમની એન્ટ્રી ઉત્સર્જિત કરે છે, તેથી કશું ગુમાતું નથી.                                                                             |
| `canonical` | `claude/claude-sonnet-4-6`                                | સંપૂર્ણ provider-id પ્રિફિક્સ હેઠળ દરેક મોડલ દીઠ એક એન્ટ્રી. અલગ alias ન ધરાવતા પ્રોવાઇડર્સ (દા.ત. `antigravity/…`, `agy/…`) પણ અહીં તેમનો એકમાત્ર id ઉત્સર્જિત કરે છે, તેથી કશું ગુમાતું નથી. |

`dual`-મોડ મિરરને ક્વેરી પેરામીટર વિના પણ ઓળખી શકાય છે: તેમાં પ્રાથમિક id તરફ નિર્દેશ કરતું `parent`
ફીલ્ડ હોય છે.

મોડલ પિકર રેન્ડર કરતા ક્લાયન્ટ્સે `?prefix=alias` માટે રિક્વેસ્ટ કરવી જોઈએ —
[OmniCopilot VS Code extension](../guides/VSCODE-COPILOT.md) પણ આવું જ કરે છે.

### ડિસ્કવરી ફિલ્ટર્સ (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` ઑપ્ટ-ઇન ડિસ્કવરી ફિલ્ટર્સ સ્વીકારે છે. તેમાંથી કોઈપણ વિના રિસ્પોન્સ
અપરિવર્તિત રહે છે. તેઓ કૉલરને પહેલેથી દેખાતા કેટલૉગને સીમિત કરે છે (API-key પરવાનગીઓ પહેલાં લાગુ થાય છે),
અને તેઓ OpenAI-શૈલીના `limit` / `after` પેજિંગ પહેલાં ચાલે છે:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # સૂચિબદ્ધ દરેક ક્ષમતા true હોવી જરૂરી છે
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # કેટલૉગ `type`; તે વિનાની પંક્તિઓ `chat` છે
GET /v1/models?q=sonnet&limit=10                           # id અથવા નામ પર કેસ-ઇન્સેન્સિટિવ મેળ
```

| પેરામીટર      | મૂલ્યો                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | નૉન-નેગેટિવ પૂર્ણાંક, જેની સરખામણી `context_length` સાથે થાય છે                                     |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 અક્ષરો                                                                                        |

અજ્ઞાત મૂલ્ય અથવા નૉન-નેગેટિવ પૂર્ણાંક ન હોય તેવું `min_context` (ઉદાહરણ તરીકે `1.5`)
HTTP `400` પરત કરે છે અને મેસેજમાં માન્ય મૂલ્યોની સૂચિ હોય છે. અમલીકરણ:
`src/app/api/v1/models/catalogFilters.ts`.

### મોડલની ટૂંકી સૂચિ (`POST /v1/models/query`)

`POST /v1/models/query`, `GET /v1/models` જેવી જ ઑથ અને દરેક કી માટેની દૃશ્યતા સાથે, એ જ
કેટલૉગમાંથી ટૂંકી અને નિર્ધારિત સૂચિ પરત કરે છે:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

દરેક ફીલ્ડ વૈકલ્પિક છે. `capabilities` અને `exclude` ઍરે અથવા કૉમાથી અલગ કરેલી સ્ટ્રિંગ સ્વીકારે છે;
`max_output`ની સરખામણી `max_output_tokens` સાથે થાય છે. પરિણામોને પહેલાં `owned_by` અને પછી `id`
પ્રમાણે સૉર્ટ કરવામાં આવે છે. `limit`નું ડિફૉલ્ટ મૂલ્ય `20` છે અને `100` કરતાં વધુ મૂલ્યોને `100` સુધી મર્યાદિત કરવામાં આવે છે.
અમાન્ય JSON, અજ્ઞાત ફીલ્ડ અથવા અમાન્ય મૂલ્ય HTTP `400` પરત કરે છે.

### વ્યક્તિગત રીતે છુપાવેલાં ચૅટ મોડલ્સ

તેના પ્રોવાઇડર પેજ પર **છુપાવેલું** તરીકે ચિહ્નિત કરેલું મોડલ કેટલૉગમાંથી બાકાત રાખવામાં આવે છે અને
જ્યારે સ્પષ્ટપણે રિક્વેસ્ટ કરવામાં આવે ત્યારે HTTP `404` / `model_not_found` સાથે નકારવામાં આવે છે. આ તપાસ રિઝૉલ્વ કરેલા
પ્રોવાઇડર અને મોડલનો ઉપયોગ કરે છે, જેમાં પ્રોવાઇડર aliases, સુસંગત-પ્રોવાઇડર નોડ પ્રિફિક્સ અને
કનેક્શન ડિફૉલ્ટ્સનો સમાવેશ થાય છે. કોમ્બો છુપાયેલા ટાર્ગેટ્સને અવગણે છે અને દૃશ્યમાન સમકક્ષનો ઉપયોગ કરી શકે છે; જ્યારે કોઈ
એક્ઝિક્યુટ કરી શકાય એવો ટાર્ગેટ બાકી ન રહે ત્યારે તે સમાન એરર કોડ પરત કરે છે. મોડલને ફરી દૃશ્યમાન કરવું આગલી
રિક્વેસ્ટથી અમલમાં આવે છે. ફક્ત ઇમેજ માટેના દૃશ્યતા ઓવરરાઇડ્સ સમાન ID ધરાવતા ચૅટ મોડલને છુપાવતા નથી.

આ વ્યક્તિગત મોડલ સેટિંગ
[મોડલ એક્સપોઝર allow/deny સૂચિઓ](../routing/MODEL_EXPOSURE_LIST.md)થી અલગ છે, જે સ્પષ્ટ ડિસ્પૅચ જાળવી રાખીને કેટલૉગ
જાહેરાત અને ઑટો-રૂટિંગ ઉમેદવારોને ફિલ્ટર કરે છે. API-key મોડલ
પરવાનગીઓ સ્વતંત્ર રીતે લાગુ થતી રહે છે. ડિફૉલ્ટ કેટલૉગ પ્રિફિક્સ મોડ `dual` જ રહે છે.

### વિચારણા-વિનાનાં મોડલ વેરિઅન્ટ્સ

વિચારણા-સક્ષમ Claude મોડલ્સ માટે, `/v1/models` એક **વિચારણા-વિનાનું** વેરિઅન્ટ પણ દર્શાવે છે, જેનો id `claude-3-omniroute-no-thinking/`થી શરૂ થાય છે:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

આ id પસંદ કરવાથી (દા.ત. એવા Claude Code config માં જે હંમેશાં `thinking` block જોડે છે) reasoning દબાવીને વાસ્તવિક `<provider>/<model>` પર પાછું resolve થાય છે — `/v1/messages` path પર `thinking:{type:"disabled"}`, અથવા `/v1/chat/completions` path પર `reasoning`/`reasoning_effort` fields દૂર કરવામાં આવે છે. આ variant માત્ર એવા Claude-family models માટે સૂચિબદ્ધ થાય છે જે thinking ને support કરે છે **અને** `disabled` ને માન્ય રાખે છે (તેથી, દા.ત. માત્ર adaptive એવા models જે `disabled` ને reject કરે છે, તેઓ બાકાત રહે છે). Operators `ModelSpec.noThinkingAlias` દ્વારા દરેક model માટે આ variant ને બળજબરીથી ચાલુ કે બંધ કરી શકે છે.

## ElevenLabs ઑડિયો જનરેશન

તમારી ElevenLabs API કી વડે OmniRouteમાં `elevenlabs` પ્રોવાઇડર કનેક્શન કૉન્ફિગર કરો.
ક્લાયન્ટ્સ તેમની **OmniRoute** કી (`Authorization: Bearer $OMNIROUTE_API_KEY`) વડે ઑથેન્ટિકેટ કરે છે;
ગેટવે સંગ્રહિત પ્રોવાઇડર કીને `xi-api-key` તરીકે પૂરી પાડે છે. ગેટવે બેરર ટોકન તરીકે ElevenLabs કી ક્યારેય મોકલશો નહીં.

| પદ્ધતિ | પાથ                         | પ્રતિસાદ                                 | API કી એન્ડપોઇન્ટ શ્રેણી |
| ------ | --------------------------- | ---------------------------------------- | ------------------------ |
| POST   | `/v1/sound-generation`      | મૂળ ઑડિયો બાઇટ્સ                         | `elevenlabs`             |
| POST   | `/v1/music`                 | મૂળ ઑડિયો બાઇટ્સ                         | `music`                  |
| POST   | `/v1/music/stream`          | સ્ટ્રીમિંગ ઑડિયો બાઇટ્સ                  | `music`                  |
| POST   | `/v1/music/detailed`        | મૂળ મલ્ટિપાર્ટ ઑડિયો અને કમ્પોઝિશન પ્લાન | `music`                  |
| POST   | `/v1/music/detailed/stream` | મૂળ SSE મેટાડેટા અને ઑડિયો ચંક્સ         | `music`                  |
| POST   | `/v1/music/plan`            | JSON કમ્પોઝિશન પ્લાન                     | `music`                  |

આ એન્ડપોઇન્ટ્સ હાલના `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` અને `/v1/speech-to-text` રૂટ્સને પૂરક છે. `output_format` અને `enable_logging` જેવા મૂળ JSON ફીલ્ડ્સ
અને ક્વેરી પેરામીટર્સ જાળવી રાખવામાં આવે છે.
`/v1/music/detailed` પ્રતિસાદો તેમની મલ્ટિપાર્ટ બાઉન્ડરીઝ જાળવી રાખે છે; તેમને મલ્ટિપાર્ટ તરીકે પાર્સ કરો.
`/v1/music/detailed/stream` કમ્પોઝિશન મેટાડેટા અને
SSE ઇવેન્ટ્સમાં base64 ઑડિયો ચંક્સ સાથે `text/event-stream` પરત કરે છે. તમામ છ રૂટ્સ CORS પ્રીફ્લાઇટને સપોર્ટ કરે છે.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# એક ટૂંકી સાઉન્ડ ઇફેક્ટ. અવધિ: 0.5થી 30 સેકન્ડ.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# સંગીતની અવધિ મિલિસેકન્ડમાં દર્શાવવામાં આવે છે: 3000થી 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

ઇન્ક્રિમેન્ટલ ઑડિયો ડિલિવરી માટે સમાન JSON બોડી સાથે `/v1/music/stream`નો ઉપયોગ કરો. કમ્પોઝિશન
`prompt` અથવા `composition_plan`માંથી ચોક્કસપણે એકને સ્વીકારે છે; `/v1/music/plan` માટે `prompt`
જરૂરી છે અને તે વૈકલ્પિક રીતે `source_composition_plan` સ્વીકારે છે. મૂળ સ્કીમા વધારાના
પ્રોવાઇડર ફીલ્ડ્સ જાળવી રાખે છે, જેથી કમ્પોઝિશન-પ્લાન વર્ઝન્સ અને ફાઇન-ટ્યુનિંગ વિકલ્પો ElevenLabs સુધી પહોંચે.

એકીકૃત `/v1/music/generations` એન્ડપોઇન્ટ `elevenlabs/music_v1`,
`elevenlabs/music_v2` અને `elevenlabs/music_v2_5`ને પણ સ્વીકારે છે. સક્રિય ElevenLabs કનેક્શન સાથે,
આ મોડલ્સ મ્યુઝિક કૅટલૉગ દ્વારા ઉપલબ્ધ કરાવવામાં આવે છે. આ એન્ડપોઇન્ટ
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` પરત કરે છે. તેનું `duration` ફીલ્ડ
સેકન્ડમાં હોય છે અને `music_length_ms` સાથે મેપ થાય છે; સ્પષ્ટપણે આપેલ `music_length_ms`ને અગ્રતા મળે છે.
`instrumental`, `force_instrumental` સાથે મેપ થાય છે, જેમાં મૂળ ફીલ્ડને અગ્રતા મળે છે.
સ્ટ્રીમિંગ માટે મૂળ સ્ટ્રીમિંગ એન્ડપોઇન્ટ્સ અને માત્ર કમ્પોઝિશન પ્લાન દ્વારા સંચાલિત રિક્વેસ્ટ્સ માટે
મૂળ કમ્પોઝિશન એન્ડપોઇન્ટનો ઉપયોગ કરો.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

અપસ્ટ્રીમ કૉલ પહેલાં એન્ડપોઇન્ટ, મોડલ, બજેટ અને કનેક્શન પ્રતિબંધો લાગુ થાય છે. મૂળ
રૂટ્સ અપસ્ટ્રીમ સ્ટેટસ કોડ્સ અને એરર બોડીઝને કોઈ ફેરફાર વિના પરત કરે છે, જેમાં પ્લાન
પ્રતિબંધ માટે `402` અને ક્વોટા મર્યાદા માટે `429`નો સમાવેશ થાય છે. હાજર હોય ત્યારે `character-cost`, `song-id`, `request-id` અને `retry-after`
હેડર્સ જાળવી રાખવામાં આવે છે. મફત ક્રેડિટ બેલેન્સ દરેક
મ્યુઝિક મોડલ, આઉટપુટ ફોર્મેટ અથવા API સુવિધાની ઍક્સેસની ખાતરી આપતું નથી: ElevenLabs દરેક રિક્વેસ્ટ માટે હક નક્કી કરે છે.
એકીકૃત એન્ડપોઇન્ટ OmniRouteના નોર્મલાઇઝ્ડ એરર એન્વલપમાં એરર સ્ટેટસ કોડ્સ જાળવી રાખે છે.

અપસ્ટ્રીમ કોન્ટ્રાક્ટ્સ: [સાઉન્ડ ઇફેક્ટ્સ](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[મ્યુઝિક કમ્પોઝિશન](https://elevenlabs.io/docs/api-reference/music/compose) અને
[સ્ટ્રીમિંગ મ્યુઝિક વિગતો](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

| POST   | `/v1/models/query`                        | ફિલ્ટર કરેલી મોડલ શૉર્ટલિસ્ટ       |
| POST   | `/v1/messages/count_tokens`               | Anthropic                          |

બધા POST રૂટ્સ સમાન માળખું અનુસરે છે: `Bearer your-api-key` + Zod દ્વારા માન્ય કરાયેલ JSON બૉડી (`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema`, વગેરે; `src/shared/validation/schemas.ts` જુઓ). સ્કીમા નિષ્ફળ જાય ત્યારે 4xx પરત કરવામાં આવે છે.

જે ક્લાયન્ટ્સ `Authorization: Bearer ...` જોડી શકતા નથી, તેમના માટે OmniRoute ક્વેરી-સ્ટ્રિંગ સુસંગતતા (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) અથવા નીચે દસ્તાવેજીકૃત સમર્પિત `/api/v1/vscode/{token}/...` એન્ડપોઇન્ટ્સ દ્વારા URLમાં API કીઝ પણ સ્વીકારે છે.

```bash
# રીરૅન્ક (ક્લાઉડ રજિસ્ટ્રી પ્રદાતા, અથવા "<prefix>/<model>" તરીકે OpenAI-સુસંગત પ્રદાતા નોડ)
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina વર્ગીકરણ (Foundation API ઓળખપત્રો)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina સેગમેન્ટર
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina શોધ (s.jina.ai; પ્રદાતા ઉપનામો: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# મોડરેશન્સ
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — audio/mpeg (અથવા વિનંતી કરાયેલ ફોર્મેટ) બૉડી પરત કરે છે
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS માટે ભાષા અને વૉઇસ જરૂરી છે: `language`નું ડિફૉલ્ટ મૂલ્ય "en" છે; ગેરહાજર
# વૉઇસ અથવા OpenAIનું સ્ટૉક વૉઇસ નામ (alloy, nova, …) "Adrian" બની જાય છે
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# ઇમેજ સંપાદન (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# વિડિયો / સંગીત જનરેશન (પ્રદાતા-ઉપસર્ગવાળી મોડલ id)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **રિરૅન્ક પ્રોવાઇડર નોડ્સ:** `POST /v1/rerank` OpenAI-સુસંગત પ્રોવાઇડર નોડ્સ
> (oMLX, vLLM, Infinity, ગેટવેની પાછળ TEI, …) તરફ પણ રૂટ કરે છે, જેમને `<node-prefix>/<model>` તરીકે સંબોધવામાં આવે છે. લૂપબૅક
> નોડ્સ (`localhost`, `127.0.0.1`, `172.16.0.0/12`) હંમેશાં પાત્ર હોય છે, અને ઑપરેટર દ્વારા
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`માં સૂચિબદ્ધ કરાયેલા હોસ્ટનેમ પણ પાત્ર હોય છે (દા.ત. Docker/Compose સર્વિસ નામ,
> જેમ કે `http://reranker:8080/v1`; આને સીધા જ કૉલ કરવામાં આવે છે, ક્યારેય `HTTP(S)_PROXY` અથવા
> કનેક્શનના પિન કરેલા પ્રોક્સી મારફતે નહીં). અન્ય કોઈપણ
> હોસ્ટ પરના નોડ્સ — LAN બૉક્સ અથવા Tailscale પિયર — માત્ર ત્યારે જ પાત્ર હોય છે જ્યારે ઑપરેટર
> `RERANK_REMOTE_PROVIDER_NODES` ફીચર ફ્લૅગ સક્ષમ કરે **અને** નોડનું બેઝ URL પ્રોવાઇડરની
> આઉટબાઉન્ડ URL નીતિ (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`) પાસ કરે.
> મેમરી એન્જિનનું રિરૅન્ક પગલું આ રૂટને
> લૂપબૅક મારફતે કૉલ કરે છે, તેથી આ જ નિયમ મેમરી સેટિંગ્સમાં `rerankProviderModel`ને નિયંત્રિત કરે છે.
>
> **લોકલ સર્વર સ્વરૂપો:** નોડને `<base>/v1/rerank` પર અને 404 મળ્યે `<base>/rerank`
> (Infinity, TEI) પર કૉલ કરવામાં આવે છે. અપસ્ટ્રીમ બોડીમાં Cohere/OpenAI સ્પેલિંગ (`documents`,
> `return_documents`) અને TEI સ્પેલિંગ (`texts`, `return_text`) બંને હોય છે, અને અપસ્ટ્રીમ પ્રતિસાદને
> Cohere એન્વલપ મુજબ નોર્મલાઇઝ કરવામાં આવે છે: TEIનું સીધું `[{index, score, text}]`, પાતળા ગેટવેમાંથી
> મળતું `{results: [{index, score}]}`, અને Voyage-શૈલીનું `{data: [...]}`, બધું જ ક્લાયન્ટને
> `{results: [{index, relevance_score, document?}]}` તરીકે પરત મળે છે, જે સ્કોર મુજબ સૉર્ટ થયેલું અને `top_n` સુધી મર્યાદિત હોય છે.

> **પ્રોવાઇડર-નોડ શોધ:** OpenAI-સુસંગત પ્રોવાઇડર નોડ પરના મોડલ્સ `GET /v1/models`માં
> નોડ પ્રીફિક્સ હેઠળ દેખાય છે. જે પંક્તિઓમાં કોઈ એન્ડપોઇન્ટ મેટાડેટા ન હોય (સામાન્ય રીતે લોકલ `/v1/models` સૂચિઓમાં)
> તે નોડનું `apiType` વારસામાં મેળવે છે, તેથી `embeddings` નોડનાં મોડલ્સ ચૅટને ડિફૉલ્ટ થવાને બદલે
> `type: "embedding"` અને `rerank` નોડનાં મોડલ્સ `type: "rerank"` બને છે; સિંક કરેલી અથવા મેન્યુઅલી ઉમેરેલી
> પંક્તિ પર સ્પષ્ટ `supportedEndpoints`ને હજુ પણ પ્રાથમિકતા મળે છે.

### સમર્પિત પ્રોવાઇડર રૂટ્સ

```bash
POST /v1/providers/{provider}/chat/completions
POST /v1/providers/{provider}/embeddings
POST /v1/providers/{provider}/images/generations
```

પ્રોવાઇડર પ્રીફિક્સ ન હોય તો તે આપમેળે ઉમેરવામાં આવે છે. મેળ ન ખાતા મોડલ્સ `400` પરત કરે છે.

## Files API

બૅચ ઇનપુટ/આઉટપુટ અને ફાઇલ-હેતુ અપલોડ્સ માટે OpenAI-સુસંગત ફાઇલ્સ એન્ડપોઇન્ટ.

| પદ્ધતિ | પાથ                      | વર્ણન                                                                                                              |
| ------ | ------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| POST   | `/v1/files`              | ફાઇલ અપલોડ કરો (મલ્ટિપાર્ટ: `file`, `purpose`, `expires_after[anchor]`, `expires_after[seconds]`) — મહત્તમ 512 MiB |
| GET    | `/v1/files`              | પ્રમાણિત API કી માટેની ફાઇલોની સૂચિ મેળવો                                                                          |
| GET    | `/v1/files/[id]`         | ફાઇલનું મેટાડેટા મેળવો                                                                                             |
| DELETE | `/v1/files/[id]`         | ફાઇલ કાઢી નાખો                                                                                                     |
| GET    | `/v1/files/[id]/content` | કાચી ફાઇલ બૉડીને પાછી સ્ટ્રીમ કરો                                                                                  |

**પ્રમાણીકરણ:** Bearer API કી — ફાઇલો `getApiKeyRequestScope` મારફતે દરેક API કી પ્રમાણે મર્યાદિત છે. કી
ફક્ત પોતાની ફાઇલો જોઈ, ડાઉનલોડ કરી અને કાઢી શકે છે; કી વિનાનું ડૅશબોર્ડ સત્ર
સમગ્ર ઇન્સ્ટન્સ વાંચે છે; માલિક વિનાની ફાઇલ (અનામી અથવા ડૅશબોર્ડ-સત્ર અપલોડ) દરેક
બિન-સત્ર કૉલર માટે પ્રતિબંધિત છે. `GET /v1/files` અનામી કૉલરને — તેમજ પ્રસ્તુત કરેલી એવી કીને જેનું
નિરાકરણ થતું નથી — `REQUIRE_API_KEY=false` હોય ત્યારે પણ દરેક ટેનન્ટની
ફાઇલો સૂચિબદ્ધ કરવાને બદલે `401` સાથે નકારે છે (GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523).

## Batches API

OpenAI-સુસંગત બૅચ પ્રોસેસિંગ.

| પદ્ધતિ | પાથ                       | વર્ણન                                                                                                                   |
| ------ | ------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/batches`             | બૅચ બનાવો — બૉડીને `v1BatchCreateSchema` દ્વારા માન્ય કરવામાં આવે છે (`input_file_id`, `endpoint`, `completion_window`) |
| GET    | `/v1/batches`             | બૅચોની સૂચિ મેળવો                                                                                                       |
| GET    | `/v1/batches/[id]`        | બૅચની સ્થિતિ + `request_counts` મેળવો                                                                                   |
| DELETE | `/v1/batches/[id]`        | પૂર્ણ/નિષ્ફળ થયેલો બૅચ કાઢી નાખો                                                                                        |
| POST   | `/v1/batches/[id]/cancel` | પ્રગતિમાં રહેલો બૅચ રદ કરો                                                                                              |

**પ્રમાણીકરણ:** Bearer API કી. બૅચો માટે પણ ફાઇલો જેવો જ ત્રણ-માર્ગી નિયમ લાગુ કરીને દરેક API કી પ્રમાણે મર્યાદા રાખવામાં આવે છે:
ફક્ત પોતાની કી, સમગ્ર ઇન્સ્ટન્સ માટે ડૅશબોર્ડ સત્ર, અને null-owner રેકોર્ડ્સ દરેક
બિન-સત્ર કૉલર માટે પ્રતિબંધિત (મેળવવું, કાઢી નાખવું, રદ કરવું અને બનાવતી વખતે `input_file_id` તપાસ).
`GET /v1/batches`, `REQUIRE_API_KEY=false` હોય ત્યારે પણ, અનામી કૉલરને `401` સાથે નકારે છે.

## શોધ API

વેબ/શોધ પ્રદાતા એબ્સ્ટ્રેક્શન (Tavily, Brave, Exa, Serper વગેરે).

| પદ્ધતિ | પાથ                    | વર્ણન                                                                                                        |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| GET    | `/v1/search`           | ગોઠવેલા શોધ પ્રદાતાઓ અને તેમની ક્ષમતાઓની યાદી                                                                |
| POST   | `/v1/search`           | શોધ ક્વેરી ચલાવે છે — બોડી `v1SearchSchema` દ્વારા માન્ય કરવામાં આવે છે અને કૅશિંગ/કોએલેસિંગને સપોર્ટ કરે છે |
| GET    | `/v1/search/analytics` | પ્રત્યેક પ્રદાતા માટે હિટ/લેટન્સી/કૅશના આંકડા                                                                |

**પ્રમાણીકરણ:** Bearer API કી (`extractApiKey` + `isValidApiKey`). શોધ નીતિ `enforceApiKeyPolicy` દ્વારા લાગુ કરવામાં આવે છે.

### Exa અને Tavily `provider_options`

Exa અને Tavily નેમસ્પેસવાળા બૅગમાંથી પ્રદાતા-વિશિષ્ટ ફીલ્ડ વાંચે છે:
`provider_options.exa` (અથવા `provider_options["exa-search"]`) અને `provider_options.tavily`
(અથવા `provider_options["tavily-search"]`). ફક્ત નીચેની કી જ આગળ મોકલવામાં આવે છે. દરેકને
`open-sse/handlers/search/providerOptionsPassthrough.ts` માં તેના પોતાના Zod સ્કીમા સામે
ચકાસવામાં આવે છે અને ખોટા પ્રકારવાળી કી કાઢી નાખવામાં આવે છે. પ્રમાણીકરણ, બેઝ URL,
`stream` અને `outputSchema` સહિતની અન્ય કોઈપણ કીને અવગણવામાં આવે છે. અન્ય પ્રદાતાઓ દ્વારા ઉપયોગમાં લેવાતી ફ્લૅટ કી (`cx`, `depth`, ...) પહેલાંની જેમ
કાર્ય કરે છે.

| પ્રદાતા | ટોચના સ્તરનાં ફીલ્ડ                                                                                                                                                                                                                                                                                                                                                       | નેસ્ટેડ                                                                                                                                                                     |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa     | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (ફ્લૅટ પ્રિમિટિવ), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                              | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` ને ડિફૉલ્ટ `{ text: true, highlights: true }` પર મર્જ કરવામાં આવે છે |
| Tavily  | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                           |

સામાન્ય ફીલ્ડ હંમેશાં અગ્રતા મેળવે છે: `query`, `max_results`, `filters` (ડોમેન), `country` અને
`search_type` પરથી મેળવેલો વિષય. Exa પર, `search_type: "news"` દ્વારા `category: "news"` જાળવી રાખવામાં આવે છે.
Tavily `search_type: "finance"` (`topic: "finance"`) પણ સ્વીકારે છે.

સામાન્ય `time_range` હવે બંને પ્રદાતાઓ સુધી પહોંચે છે: Exa ને `startPublishedDate` (ISO
ટાઇમસ્ટૅમ્પ) અને Tavily ને `start_date` (`YYYY-MM-DD`) મળે છે. `provider_options`
માં આપેલી સ્પષ્ટ તારીખ મૅપ કરેલી તારીખને ઓવરરાઇડ કરે છે.

Exa પરિણામોમાં `provider_raw` હેઠળ `id`, `highlight_scores`, `summary`, `subpages`, `entities` અને `extras`
જાળવી રાખવામાં આવે છે. Tavily પરિણામોમાં `images` અને `favicon` જાળવી રાખવામાં આવે છે.

ખર્ચનો હિસાબ હજી પણ ફ્લૅટ રજિસ્ટ્રી `costPerQuery` દ્વારા થાય છે. Tavily માં
`search_depth: "advanced"` માટે પ્રત્યેક કૉલ દીઠ વધુ ક્રેડિટ વસૂલવામાં આવે છે અને આ તફાવત
`usage.search_cost_usd` માં પ્રતિબિંબિત થતો નથી.

## Web Fetch API

કૉન્ફિગર કરેલા web-fetch પ્રદાતા (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract) મારફતે URLમાંથી કન્ટેન્ટ મેળવો.

Parallel Extract (`parallel-search`, Parallel Search જેવી જ API કી) ફક્ત Markdown
પરત કરે છે — અન્ય કોઈપણ `format` માટે `400` મળે છે — અને કન્ટેન્ટને 100,000 અક્ષરો સુધી મર્યાદિત કરે છે. જ્યારે
લક્ષ્ય પેજને જ એક્સ્ટ્રેક્ટ કરી શકાતું નથી, ત્યારે upstream તેને HTTP 200ની અંદર દર્શાવે છે;
OmniRoute તેને નિશ્ચિત સંદેશ સાથે `422` તરીકે રજૂ કરે છે.

| પદ્ધતિ | પાથ             | વર્ણન                                                                     |
| ------ | --------------- | ------------------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | URL મેળવો/સ્ક્રેપ કરો — બોડીનું `v1WebFetchSchema` દ્વારા માન્યકરણ થાય છે |

**પ્રમાણીકરણ:** Bearer API કી (`extractApiKey` + `isValidApiKey`). નીતિ `enforceApiKeyPolicy` મારફતે લાગુ કરવામાં આવે છે.

**ક્વોટા-જાગૃત ફૉલબૅક (#8297):** જ્યારે સ્પષ્ટ `provider` આપવામાં આવ્યો ન હોય, ત્યારે પૂલમાં
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) નિશ્ચિત
પ્રાથમિકતા ક્રમમાં (પહેલાં પહેલું ભરો) આગળ વધવામાં આવે છે — રેટ-લિમિટેડ પરંતુ કૉન્ફિગર થયેલા પ્રદાતાને
વિનંતી તરત અટકાવવાને બદલે છોડી દેવામાં આવે છે, અને પુનઃપ્રયાસ કરી શકાય તેવી/ક્વોટા-સંબંધિત upstream નિષ્ફળતા
(HTTP 429 હંમેશાં; Firecrawl/Tavily/TinyFishના ક્વોટા-પ્રકારના મફત ટિયર માટે 402/403 —
Jina Reader માટે નહીં, અને સાદી 400 bad request માટે ક્યારેય નહીં) વિનંતીના સમયે
આગળના હજી અજમાવ્યા ન હોય તેવા, ક્રેડેન્શિયલ ધરાવતા પ્રદાતા પર જાય છે. જ્યારે પૂલના દરેક પ્રદાતાની
ક્ષમતા સમાપ્ત થઈ જાય, ત્યારે endpoint અગાઉના સામાન્ય `400`ને બદલે એક જ `429`
(`Retry-After` હેડર સાથે) પરત કરે છે. જ્યારે સ્પષ્ટ `provider`ની વિનંતી કરવામાં આવે છે,
ત્યારે કોઈ મૌન ફૉલબૅક **નથી** — રેટ-લિમિટેડ અથવા નિષ્ફળ થયેલો સ્પષ્ટ
પ્રદાતા પોતાની જ ભૂલ રજૂ કરે છે (રેટ-લિમિટેડ હોય તો `429`, અન્યથા upstream
સ્ટેટસ).

## WebSocket સ્ટ્રીમિંગ

```bash
GET /v1/ws?handshake=1
```

WebSocket અપગ્રેડ હેન્ડશેકનું માન્યકરણ કરે છે અને વાયર પ્રોટોકૉલના ઉદાહરણ સંદેશાઓ (`request`, `cancel`) પરત કરે છે. વાસ્તવિક WS ફ્રેમ્સને Next.js રૂટ ટેબલની બહાર આવેલા બંડલ કરેલા WS સર્વર દ્વારા સંચાલિત કરવામાં આવે છે.

**પ્રમાણીકરણ:** હેન્ડશેક દરમિયાન Bearer API કી.

### WebSocket પર Responses API (ફક્ત codex)

```bash
# HTTP API જેવો જ host:port (ડિફૉલ્ટ 20128); કનેક્શન અપગ્રેડ કરો:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (અથવા: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# પ્રથમ ફ્રેમ response.create જ હોવી આવશ્યક છે:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket પ્રૉક્સી **ફક્ત `codex` સાથે** જોડાયેલી છે (ChatGPT
બૅકએન્ડ). તે API/dashboard જેવા જ પોર્ટ પર `/v1/responses`,
`/responses` અને `/api/v1/responses` પાથ પર સાંભળે છે. પ્રથમ `response.create` ફ્રેમ પર તે
આંતરિક `codex-responses-ws` બ્રિજ મારફતે પ્રમાણીકરણ + તૈયારી કરે છે, એક
codex OAuth કનેક્શન પસંદ કરે છે અને `wreq-js` ટ્રાન્સપોર્ટ મારફતે `wss://chatgpt.com/backend-api/codex/responses`
સુધી ટનલ બનાવે છે. **codex સિવાયનાં મોડલ નકારવામાં આવે છે** (`codex_ws_provider_required`).
ક્વોટા-શેર રૂટિંગ માટે `model: "qtSd/<group>/codex/<model>"` વાપરો. તેનો અમલ
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`માં કરવામાં આવ્યો છે.

**પ્રમાણીકરણ:** હેન્ડશેક દરમિયાન Bearer API કી. બંડલ કરેલું HTTP સર્વર (`server-ws.mjs`)
સક્રિય એન્ટ્રીપૉઇન્ટ હોવું આવશ્યક છે (`app/server-ws.mjs` અસ્તિત્વમાં હોય ત્યારે ડિફૉલ્ટ રૂપે તે જ હોય છે).

#### મોડલ id: મૂળ ChatGPT id વાપરો (`codex/` પ્રિફિક્સ વગર)

જ્યારે `supports_websockets = true` હોય ત્યારે OpenAI **Codex CLI** ક્લાયન્ટ તરફથી મોડલના નામનું માન્યકરણ કરે છે અને
`codex/gpt-5.5` જેવા **પ્રદાતા-પ્રિફિક્સવાળા ids નકારે છે**
(`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). **મૂળ** id મોકલો (દા.ત. `gpt-5.5`). OmniRouteનો બ્રિજ
ફક્ત codex માટે હોવાથી, upstream પર ટનલ બનાવતાં પહેલાં તે મૂળ idને codex મોડલ તરીકે
(`resolveCodexWsModelInfo`) ફરીથી રિઝૉલ્વ કરે છે — ભલે મૂળ
`gpt-5.5` અન્યથા HTTP પર બીજા પ્રદાતા તરફ રૂટ થાય.

#### OpenAI Codex CLIને કૉન્ફિગર કરવું

`~/.codex/config.toml`માં WebSocket
સપોર્ટ ધરાવતો કસ્ટમ પ્રદાતા ઉમેરીને Codex CLIને OmniRoute તરફ નિર્દેશિત કરો (હાલના
કૉન્ફિગને સ્પર્શવાનું ટાળવા અલગ `CODEX_HOME` વાપરો):

```toml
model = "gpt-5.5"                 # મૂળ id — "codex/gpt-5.5" નહીં
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # અંતે slash નહીં; WS URL તેમાંથી મેળવવામાં આવે છે (પ્રોડક્શનમાં https/wss વાપરો)
wire_api = "responses"                    # ફેબ્રુઆરી 2026થી એકમાત્ર સપોર્ટેડ મૂલ્ય
supports_websockets = true                # Responses-over-WS ટ્રાન્સપોર્ટ સક્રિય કરે છે
env_key = "OMNIROUTE_API_KEY"             # OmniRoute API કી (Bearer) ધરાવે છે
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API કી (REQUIRE_API_KEY=false હોય તો કોઈપણ કી)
codex exec "Responda apenas: PONG"
```

CLI `base_url + /responses`ને WebSocketમાં અપગ્રેડ કરે છે અને OmniRoute તેને
પસંદ કરેલા codex OAuth કનેક્શન સુધી ટનલ કરે છે. સ્થાનિક
સર્વર સામે શરૂઆતથી અંત સુધી માન્ય કરેલું છે: ChatGPT `codex.rate_limits` + `response.created` પરત કરે છે અને
પૂર્ણતાને સ્ટ્રીમ કરે છે.

## સ્વ-સેવા વપરાશ (`/api/usage/om-usage`)

કોઈપણ API કી **પોતાનો** વપરાશ અને ક્વોટા વાંચી શકે છે — કોઈ મેનેજમેન્ટ પ્રમાણીકરણ જરૂરી નથી. આ તે એન્ડપોઇન્ટ છે જેનો
ક્લાયન્ટ (CLI, OmniCopilot પેનલ) કી ધારકને તેનો ખર્ચ બતાવવા માટે ઉપયોગ કરે છે.

```bash
# ટેક્સ્ટ સ્વરૂપ (ઐતિહાસિક કરાર — ટર્મિનલ માટે સાદો ટેક્સ્ટ)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# સંરચિત સ્વરૂપ — જેનો UI ઉપયોગ કરે છે
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

કી માટે **`allowUsageCommand`** સક્ષમ હોવું આવશ્યક છે (ડિફૉલ્ટ રૂપે બંધ — ડૅશબોર્ડનું API-કી
મેનેજર તેને દરેક કી માટે ચાલુ કે બંધ કરે છે). તેના વિના એન્ડપોઇન્ટ `403` જવાબ આપે છે.

`?format=json` એક વિભેદિત સંરચના પરત કરે છે જેથી કૉલર ક્યારેય અસ્વીકૃતિમાંથી ડેટા ફીલ્ડ ન વાંચે.
સફળતા પર:

```jsonc
{
  "allowed": true,
  // ફક્ત ત્યારે હાજર હોય છે જ્યારે કીએ પ્રતિ-કી વપરાશ મર્યાદાઓ પસંદ કરી હોય (દૈનિક/સાપ્તાહિક USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // પસંદ કરેલા પ્રોવાઇડરના ક્વોટાનો સ્નૅપશૉટ, અથવા હજી કંઈ કૅશ ન થયું હોય ત્યારે null:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // દરેક કનેક્શનનો સ્નૅપશૉટ, જેથી UI અનેક પ્રોવાઇડરોને બાજુ-બાજુ રેન્ડર કરી શકે:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

અસ્વીકૃતિ પર (`401` અમાન્ય કી / `403` મંજૂરી નથી) એ જ રૂટ
`{ "allowed": false, "error": { "message": "…" } }` પરત કરે છે — હાજર-પરંતુ-ખાલી `personal`/`provider`
(કી મંજૂર છે, હજી કંઈ જાણવા મળ્યું નથી) અસ્વીકૃતિથી અલગ સ્થિતિ છે, અને ફક્ત JSON સ્વરૂપ
તેમની વચ્ચે ભેદ કરે છે.

**પ્રમાણીકરણ:** કૉલરની પોતાની Bearer API કી, જે `isValidApiKey` વડે માન્ય કરવામાં આવે છે — આ
મેનેજમેન્ટ સપાટી (`/api/keys/…`) _નથી_, જે `requireManagementAuth` પાછળ સુરક્ષિત રહે છે.

### કાચી અને કટઓફ-સમાયોજિત ક્વોટા ટકાવારીઓ

`/api/usage/om-usage` નો ઉપયોગ કરતી વખતે, કૉલરોએ **સાદા-ટેક્સ્ટ આઉટપુટ** અને સંરચિત
**JSON આઉટપુટ** દ્વારા રજૂ થતી ટકાવારીઓ વચ્ચેનો તફાવત ધ્યાનમાં લેવો જોઈએ:

| પાસું                | સાદા-ટેક્સ્ટનું સ્વરૂપ (`/api/usage/om-usage` / `@@om-usage`)                               | JSON સ્વરૂપ (`?format=json`)                                                  |
| :------------------- | :------------------------------------------------------------------------------------------ | :---------------------------------------------------------------------------- |
| **આઉટપુટ ફીલ્ડ**     | `NN% left` (દા.ત., `20% left`)                                                              | `provider.quotas` / `providers[].quotas`                                      |
| **માપન**             | **કટઓફ-સમાયોજિત ઉપયોગી મર્યાદા**: કટઓફ થ્રેશોલ્ડથી ઉપરની બાકી ક્ષમતા                        | **કાચો અપસ્ટ્રીમ ક્વોટા**: પ્રોવાઇડરનું અસંશોધિત માપન                         |
| **કટઓફ સ્કેલિંગ**    | `effectiveRemainingPercent()` દ્વારા સ્કેલ કરેલું જેથી સુરક્ષિત અનામત `0% left` તરીકે દેખાય | કંઈ નહીં (પ્રોવાઇડરે જાણ કરેલા કાચા સ્નૅપશૉટ મૂલ્યો)                          |
| **થ્રેશોલ્ડ ડેટા**   | દર્શાવેલી ટકાવારીમાં સમાવિષ્ટ                                                               | દરેક કનેક્શન માટે `quotaWindowThresholds` માં સંગ્રહિત (અથવા સર્વર ડિફૉલ્ટ્સ) |
| **મુખ્ય વપરાશકર્તા** | ઇન્ટરૅક્ટિવ CLI, ટર્મિનલ પ્રોમ્પ્ટ, માનવીય ઑપરેટરો                                          | પ્રોગ્રામેટિક ઇન્ટિગ્રેશન, ડૅશબોર્ડ, ઍનલિટિક્સ, બિલિંગ ટ્રૅકર્સ               |

#### કટઓફ સમાયોજનનું સૂત્ર

OmniRoute અપસ્ટ્રીમ ક્ષમતા ખૂટી જતી અટકાવવા માટે સક્રિય ક્વોટા કટઓફને સપોર્ટ કરે છે (જે કનેક્શનના
`quotaWindowThresholds`, પ્રોવાઇડર ડિફૉલ્ટ્સ અથવા વૈશ્વિક સ્થિતિસ્થાપકતા સેટિંગ્સ દ્વારા ગોઠવાય છે). જ્યારે કોઈ ક્વોટા વિન્ડો પર કટઓફ થ્રેશોલ્ડ
(દા.ત., `cutoff = 25%`) સક્રિય હોય, ત્યારે ટેક્સ્ટ રેન્ડરર બાકી મર્યાદાની ગણતરી આ પ્રમાણે કરે છે:

- જો `remaining <= cutoff`: તો `0%` પરત કરે છે.
- જો `remaining > cutoff`: તો `((remaining - cutoff) / (100 - cutoff)) * 100` પરત કરે છે.

ફોર્મેટ કરેલું ટેક્સ્ટ આઉટપુટ તેને નજીકના પૂર્ણાંક સુધી રાઉન્ડ કરે છે (`Math.round(...)`).

#### ઉદાહરણાત્મક દાખલો

**60% કાચો વપરાશ** (એટલે કે **40% કાચો બાકી ક્વોટા**) અને ગોઠવેલા
**25% બાકી-ક્વોટા કટઓફ** થ્રેશોલ્ડવાળી પ્રોવાઇડર વિન્ડો ધ્યાનમાં લો:

| રજૂઆત                           | ગણતરી                                              |  બાકી   |                     સૂચિત વપરાશ                     |
| :------------------------------ | :------------------------------------------------- | :-----: | :-------------------------------------------------: |
| **કાચો JSON (`?format=json`)**  | અપસ્ટ્રીમ સ્નૅપશૉટ (`quotas[window]`)              | **40%** |                       **60%**                       |
| **ટેક્સ્ટ સ્વરૂપ (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (જો `100 - remaining` ની ગણતરી કરવામાં આવે) |

- **ટેક્સ્ટ 20% બાકી કેમ બતાવે છે:** એકાઉન્ટમાં બાકી રહેલા 40% ભૌતિક ક્વોટામાંથી 25% કટઓફ
  નીતિ દ્વારા અનામત રાખવામાં આવે છે. રાઉટર આ કનેક્શન તરફ રૂટ કરવાનું બંધ કરે તે પહેલાં કૉલર પાસે 75% ઉપયોગી ક્ષમતામાંથી
  માત્ર 15% ક્ષમતા બાકી છે. સ્કેલિંગ ખાતરી કરે છે કે જ્યારે રૂટિંગ
  બંધ થશે ત્યારે જ કનેક્શન ક્ષમતા સમાપ્ત થઈ હોવાનો સંકેત (`0% left`) આપે છે.
- **JSON કાચા મૂલ્યો શા માટે જાળવે છે:** JSON પેલોડ પ્રોવાઇડરનો ચોક્કસ સ્નૅપશૉટ (`UsageSnapshot`)
  પરત કરે છે જેથી બાહ્ય ટૂલ્સને સર્વર-સાઇડ નુકસાનકારક સ્કેલિંગ વિના વાસ્તવિક અપસ્ટ્રીમ ઉપયોગ અને કનેક્શન-સ્તરના
  `quotaWindowThresholds` ઉપલબ્ધ રહે.

#### વપરાશકર્તા માઇગ્રેશન માર્ગદર્શન

જો કોઈ બાહ્ય એકીકરણ (જેમ કે એડિટર પ્લગઇન અથવા એજન્ટ એક્સ્ટેન્શન) અગાઉ ટેક્સ્ટ
એન્ડપોઇન્ટ (`NN% left`) માંથી ડેટા મેળવીને વપરાયેલી ટકાવારીની ગણતરી `100 - NN` તરીકે કરતું હોય, તો `?format=json` પર સ્થાનાંતરિત કરવાનો અર્થ છે:

- અપરિષ્કૃત JSON મૂલ્યો વાંચવાથી **અપસ્ટ્રીમનો વાસ્તવિક વપરાશ** પ્રતિબિંબિત થશે (ઉપરના ઉદાહરણમાં 60% વપરાયેલ).
- જો એકીકરણ ટેક્સ્ટ એન્ડપોઇન્ટના ઉપયોગ કરી શકાય તેવા ભથ્થાના અર્થને જાળવી રાખવા ઇચ્છે, તો તે કનેક્શન-સ્તરના ઓવરરાઇડ માટે `quotaWindowThresholds` નો ઉપયોગ કરીને
  અસરકારક બાકી રહેલા પ્રમાણના સૂત્રનું ક્લાયન્ટ-સાઇડ મૂલ્યાંકન કરી શકે છે.

## સિમેન્ટિક કૅશ

```bash
# કૅશના આંકડા મેળવો
GET /api/cache/stats

# બધા કૅશ સાફ કરો
DELETE /api/cache/stats
```

પ્રતિસાદનું ઉદાહરણ:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### લેટન્સી પર અસર

સિમેન્ટિક કૅશ HIT પ્રતિસાદને કૅશમાંથી **અપસ્ટ્રીમ કૉલ કર્યા વિના**
પરસે છે, તેથી દર્શાવાયેલ `X-OmniRoute-Response-Latency` લગભગ શૂન્ય હોય છે
(મૂળ અપસ્ટ્રીમ લેટન્સી ગમે તેટલી હોય). લેટન્સી પ્રત્યે સંવેદનશીલ ક્લાયન્ટ્સે
(બેન્ચમાર્કિંગ, p50/p99 મોનિટરિંગ) `X-OmniRoute-Cache-Latency`
પ્રતિસાદ હેડર તપાસવું જોઈએ:

| મૂલ્ય       | અર્થ                                                                   |
| ----------- | ---------------------------------------------------------------------- |
| `synthetic` | પ્રતિસાદ કૅશમાંથી આપવામાં આવ્યો છે; લેટન્સી વાસ્તવિક અપસ્ટ્રીમ સમય નથી |
| _(ગેરહાજર)_ | વાસ્તવિક અપસ્ટ્રીમ કૉલમાંથી મળેલો પ્રતિસાદ                             |

### પ્રતિ-કી કૅશ બાયપાસ

API કીઓ `cacheDefaultMode` દ્વારા સિમેન્ટિક કૅશ રીડ્સમાંથી બહાર રહી શકે છે:

| મૂલ્ય    | વર્તણૂક                                                  |
| -------- | -------------------------------------------------------- |
| `legacy` | સામાન્ય કૅશ વર્તણૂક (ડિફૉલ્ટ)                            |
| `bypass` | કૅશ લુકઅપ સંપૂર્ણપણે છોડો; હંમેશાં અપસ્ટ્રીમનો ઉપયોગ કરો |

કી બનાવતી વખતે (`POST /api/keys`) સેટ કરો અથવા અપડેટ કરો (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### પ્રતિ-વિનંતી બાયપાસ

કી સેટિંગ્સને ધ્યાનમાં લીધા વિના કોઈપણ વિનંતી કૅશને બાયપાસ કરી શકે છે:

```
X-OmniRoute-No-Cache: true
```

સમન્વયિત/આયાત કરેલા મોડેલો માટે, `PUT /api/provider-models` દ્વારા `provider`, `modelId`, અને
`maxOutputTokenOverride` સ્વીકારવામાં આવે છે: ધન પૂર્ણાંક મેન્યુઅલ આઉટપુટ-ટોકન મર્યાદા સેટ કરે છે અને `null`
તેને સાફ કરીને ડિફૉલ્ટ પુનઃસ્થાપિત કરે છે. `GET /api/provider-models?provider=<provider>` આ
મૂલ્યોને `modelOutputOverrides`માં પરત કરે છે, જેમાં કસ્ટમ-મોડેલ પંક્તિ વિનાના મોડેલો પણ સામેલ હોય છે. આ ઓવરરાઇડ
રનટાઇમ `max_output_tokens` ક્ષમતાનો ઉપયોગ કરે છે અને મોડેલના પુનઃ-સમન્વય પછી પણ જળવાઈ રહે છે. OpenAI-સુસંગત
પ્રદાતા પૃષ્ઠ સમાન સંપાદન/સાફ કરવાનાં નિયંત્રણો આપે છે અને સ્પષ્ટ વિઝન સપોર્ટ ધરાવતા મોડેલોને ચિહ્નિત કરે છે.

કસ્ટમ Chat Completions નોડ્સ સ્પષ્ટ રીઝનિંગ ઑપ્ટ-આઉટને અપસ્ટ્રીમ બેકએન્ડ માટે અનુકૂળ બનાવે છે. સફળ
કનેક્શન પરીક્ષણ એવા દરેક ચોક્કસ મોડેલ ID માટે આપમેળે ચેટ-ટેમ્પલેટ નિયંત્રણો પસંદ કરે છે
જેની `/models` એન્ટ્રી માન્યતાપ્રાપ્ત `owned_by` મૂલ્ય સાબિત કરે છે: `vllm`, `sglang`, અથવા `llamacpp`.
પારદર્શક OpenAI-સુસંગત રૅપર્સ મૂળ મોડેલ એન્ટ્રીને નેસ્ટેડ
`openai` ઑબ્જેક્ટમાં જાળવી શકે છે; શોધ આવી વધુમાં વધુ ત્રણ આવરણોને અનુસરે છે. ગેરહાજર, અજ્ઞાત અથવા
પરસ્પર વિરોધી માલિકી ધરાવતા મોડેલો સામાન્ય OpenAI વર્તન જાળવી રાખે છે. શોધ હાલની કેટલૉગ વિનંતીનો પુનઃઉપયોગ કરે છે,
કોઈ કમ્પ્લીશન ટોકન જનરેટ કરતી નથી અને કનેક્શન એન્ડપોઇન્ટ બદલાય ત્યારે અમાન્ય થઈ જાય છે.

આ મેટાડેટા પ્રદર્શિત ન કરતા બેકએન્ડ માટે આ વર્તન નિશ્ચિત કરવા, હાલની આંશિક
પ્રદાતા અપડેટ APIનો ઉપયોગ કરો:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

તે બૉડીને `PUT /api/providers/<connection-id>` સાથે મોકલો. તે કનેક્શન પર, સ્પષ્ટ
રીઝનિંગ એફર્ટ `none`ને `chat_template_kwargs.thinking=false` અને
`chat_template_kwargs.enable_thinking=false` તરીકે મોકલવામાં આવે છે. જ્યાં સુધી સર્વર-સાઇડ રીઝનિંગ નિયમ કોઈ એફર્ટને ફરજિયાત ન કરે,
ત્યાં સુધી સ્પષ્ટ નેટિવ ટેમ્પલેટ મૂલ્યો અધિકૃત રહે છે. આ સેટિંગ ફક્ત ત્યારે લાગુ પડે છે જ્યારે કસ્ટમ
OpenAI-સુસંગત કનેક્શન Chat Completions બૉડી મોકલે છે; Responses વિનંતીઓ અને સામાન્ય
પ્રદાતાઓ તેમના નેટિવ વિનંતી સ્વરૂપને જાળવી રાખે છે. સામાન્ય OpenAI
`reasoning_effort` પાસથ્રૂ ફરજિયાત કરવા માટે `reasoningControl`ને `openai` પર સેટ કરો અથવા સ્વચાલિત શોધનો ઉપયોગ કરવા માટે તેને છોડી દો/`null` પર સેટ કરો.

Claude Code ઑટો-મોડ ક્લાસિફાયર વિનંતીઓમાં કોઈ
સ્પષ્ટ રીઝનિંગ નિયંત્રણ ન હોય ત્યારે ડિફૉલ્ટ રૂપે નેટિવ થિંકિંગ અક્ષમ રહે છે. શોધ મોડેલનાં નામો અથવા કમ્પ્લીશન મર્યાદાઓને બદલે Claude-ફોર્મેટ
વિનંતીઓમાં ક્લાસિફાયરના સિસ્ટમ માર્કરનો ઉપયોગ કરે છે. સ્પષ્ટ બૉડી નિયંત્રણો, સપોર્ટેડ એફર્ટ/થિંકિંગ
હેડર્સ, રૂટિંગ નિયમો અને ઉકેલાયેલો મોડેલ એફર્ટ તેમની હાલની અગ્રતા જાળવી રાખે છે. ક્લાસિફાયરના બંને
તબક્કાઓ તેમના પ્રોમ્પ્ટ્સ, કમ્પ્લીશન મર્યાદાઓ, સ્ટોપ સિક્વન્સ અને વાસ્તવિક અપસ્ટ્રીમ પરવાનગી
નિર્ણયો જાળવી રાખે છે; બીજો તબક્કો હજી પણ તેનું વિનંતી કરાયેલું દૃશ્યમાન રીઝનિંગ સામાન્ય ટેક્સ્ટ તરીકે આપી શકે છે.

સંગ્રહિત ઓળખપત્ર પ્રદાન કરે છે, તેથી તેમને ડૅશબોર્ડ સેશન અથવા સ્થાનિક CLI (અથવા અક્ષમ કરેલું
લૉગિન) જરૂરી છે. કોઈપણ સ્કોપની API કી અને `oma_` ઍક્સેસ ટોકનને `403` મળે છે. પુનઃસ્થાપનો પર પણ એ જ
મર્યાદા લાગુ પડે છે: `POST /api/db-backups/import` (`dryRun=true` સહિત), `POST /api/db-backups` (id
દ્વારા પુનઃસ્થાપન) અને `POST /api/settings/import-json` સક્રિય ડેટાબેઝ અથવા સેટિંગ્સને બદલે છે, તેથી મશીન
ઓળખપત્રને ત્યાં પણ `403` મળે છે; `omniroute sync import` સ્થાનિક CLI ઓળખપત્ર મોકલે છે. આ જ નિયમ
`DELETE /api/db-backups` (સંગ્રહિત બૅકઅપ કાઢવા) અને `PATCH /api/db-backups` (જાળવણી સેટિંગ્સ:
સાચવેલા મૂલ્યો દરેક બૅકઅપ પછી સ્વચાલિત રીતે બૅકઅપ કાઢવાની પ્રક્રિયાને નિયંત્રિત કરે છે) પર પણ લાગુ પડે છે. સૂચિ મેળવવા (`GET`) અને
મેન્યુઅલ બૅકઅપ બનાવવા (`PUT`) માટે સામાન્ય વ્યવસ્થાપન પ્રમાણીકરણ યથાવત્ રહે છે.

> તમામ ચાર `/api/resilience/*` રૂટ્સ માટે **મેનેજમેન્ટ પ્રમાણીકરણ** (`requireManagementAuth`) જરૂરી છે. પ્રદાતા બ્રેકર, કનેક્શન કૂલડાઉન અને મોડેલ લૉકઆઉટની સંપૂર્ણ વિગતો માટે [સ્થિતિસ્થાપકતા (વિસ્તૃત)](#resilience-extended) જુઓ.

### સંસ્કરણ અને રિલીઝ ચેનલ

```bash
GET /api/system/version
```

ફક્ત લૂપબૅક માટેનો મેનેજમેન્ટ રૂટ (એડમિન પ્રમાણીકરણ). હાલમાં ચાલી રહેલું સંસ્કરણ, નવીનતમ પ્રકાશિત સંસ્કરણ અને સ્વચાલિત અપડેટની સ્થિતિ પરત કરે છે. `releaseChannel` અને `channels` ઉમેરાત્મક ફીલ્ડ્સ છે (રેલ 3.8.54); `channel` તેનો અર્થ જાળવી રાખે છે — ડૅશબોર્ડ અપડેટર દ્વારા ઉપયોગમાં લેવાતો ડિપ્લોયમેન્ટ મોડ (`npm`, `source` અથવા `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — ચાલી રહેલા બિલ્ડની npm ચેનલ: `-nightly.*` સંસ્કરણો માટે `nightly`,
  અન્ય પૂર્વ-રિલીઝ (`-rc.*`, `-beta.*`, `-alpha.*`) માટે `next`, `channels.latest` કરતાં જૂના
  મેજરના સ્થિર સંસ્કરણ માટે `lts`, અન્યથા `latest`. આ `scripts/release/dist-tag.mjs` જેવા જ
  નિયમો છે, જે પ્રકાશન સમયે npm dist-tag પસંદ કરે છે.
- `channels` — `npm view omniroute dist-tags`માંથી દરેક dist-tagનું પ્રકાશિત હેડ (રજિસ્ટ્રી
  HTTP ફૉલબૅક), જે `latest`ની જેમ જ 10-મિનિટના TTL સાથે કૅશ થાય છે. `latest` હંમેશાં હાજર
  હોય છે (પહેલાં `latest` ફીલ્ડ અને પછી `"unavailable"` પર ફૉલબૅક કરે છે); `next`, `nightly`
  અને `lts` માત્ર ત્યારે જ દેખાય છે જ્યારે તે dist-tag અસ્તિત્વમાં હોય. `Cache-Control: no-cache`
  વિનંતી બંને લુકઅપને રિફ્રેશ કરે છે.

ચેનલ મોડેલ (`latest` = 4.0 GA સુધી v3, `next` = rc, `nightly` = `develop` બિલ્ડ્સ,
`lts` = 4.0 GA પછીના v3 પેચ)નું વર્ણન `docs/ops/RELEASE_STRATEGY.md`માં કરવામાં આવ્યું છે.

## ઑડિયો ટ્રાન્સક્રિપ્શન

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

કોઈપણ ગોઠવેલા STT પ્રદાતાનો ઉપયોગ કરીને ઑડિયો ફાઇલોનું ટ્રાન્સક્રિપ્શન કરો. પ્રથમ પાથ
સેગમેન્ટ મૂળ પ્રદાતા પસંદ કરે છે (`openai/…`, `deepgram/…`). અન્ય વિક્રેતાના
મોડેલને ફરીથી નિકાસ કરતા ગેટવે ક્વોલિફાઇડ id નો ઉપયોગ કરે છે
(`openrouter/deepgram/nova-3`).

**વિનંતી:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**પ્રતિસાદ:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**મોડેલ id ના ઉદાહરણો:** `openai/whisper-1` (OpenAI કીની જરૂર છે),
`openrouter/deepgram/nova-3` (OpenRouter કીની જરૂર છે),
`deepgram/nova-3` (મૂળ Deepgram કીની જરૂર છે). માત્ર
`deepgram/nova-3` વિનંતી OpenRouter નો ઉપયોગ **કરતી નથી**.

**સપોર્ટેડ ફોર્મેટ્સ:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

## ટોકનયુક્ત VS Code / હેડર વિનાના ઉપનામો

જ્યારે કોઈ ઇન્ટિગ્રેશન `Authorization` હેડર સામેલ કરી શકતું ન હોય અને API કીને બેઝ URL માં એમ્બેડ કરવાની જરૂર હોય, ત્યારે આ ઉપનામોનો ઉપયોગ કરો.

```bash
# OpenAI-શૈલીનું કૅટલૉગ ઉપનામ
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# OpenAI-શૈલીનાં ચેટ ઉપનામો
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Ollama-શૈલીનાં ઉપનામો
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

ઉદાહરણ:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

નોંધો:

- ટોકનયુક્ત ઉપનામો `/v1/*` અને `/api/tags` જેવા જ હેન્ડલર્સનો ફરીથી ઉપયોગ કરે છે; પ્રતિસાદની રચના સમાન રહે છે.
- જ્યારે ક્લાયન્ટ કસ્ટમ હેડર્સને સપોર્ટ કરતું હોય ત્યારે `Authorization: Bearer ...` ને પ્રાધાન્ય આપો.
- URL-આધારિત ટોકન્સ રિવર્સ-પ્રૉક્સી લૉગ્સ, બ્રાઉઝર ઇતિહાસ અને OmniRoute ની બહારની ટેલિમેટ્રીમાં દેખાઈ શકે છે. તેમને ડિફૉલ્ટ પ્રમાણીકરણ મોડ તરીકે નહીં, પરંતુ સુસંગતતા વિકલ્પ તરીકે ગણો.

## બજેટ

```bash
# બધી API કીઓ માટે બજેટની સ્થિતિ મેળવો
GET /api/usage/budget

# બજેટ સેટ અથવા અપડેટ કરો
POST /api/usage/budget
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "dailyLimitUsd": 5.00,
  "weeklyLimitUsd": 30.00,
  "monthlyLimitUsd": 100.00,
  "warningThreshold": 0.8,
  "resetInterval": "monthly"
}
```

> **સ્કીમા નોંધો** (`setBudgetSchema`): `apiKeyId` આવશ્યક છે; `dailyLimitUsd`, `weeklyLimitUsd` અથવા `monthlyLimitUsd` માંથી ઓછામાં ઓછું એક શૂન્ય કરતાં મોટું હોવું આવશ્યક છે. વૈકલ્પિક ફીલ્ડ્સ: `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`). જૂનું `{keyId, limit, period}` સ્વરૂપ `400 Bad Request` પરત કરે છે.

## ટોકન મર્યાદાઓ

પ્રતિ-API-key **ટોકન** બજેટ (ઉપરના USD-આધારિત બજેટથી અલગ). વિનંતીના પાથ પર જ લાગુ કરવામાં આવે છે: જ્યારે કોઈ keyના વર્તમાન વિન્ડોનો વપરાશ તેની મર્યાદા સુધી પહોંચે છે, ત્યારે વિનંતીઓ `429 Too Many Requests` સાથે નકારવામાં આવે છે. મર્યાદાઓને ચોક્કસ `model`, `provider` માટે વ્યાપબદ્ધ કરી શકાય છે અથવા સમગ્ર key પર `global` રીતે લાગુ કરી શકાય છે; જ્યારે એક વિનંતી સાથે અનેક મર્યાદાઓ મેળ ખાય, ત્યારે સૌથી પ્રતિબંધિત મર્યાદા લાગુ થાય છે.

```bash
# કોઈ keyની ટોકન મર્યાદાઓની યાદી આપો (લાઇવ વિન્ડો વપરાશ સહિત)
GET /api/usage/token-limits?apiKeyId=key-123

# ટોકન મર્યાદા બનાવો અથવા અપડેટ કરો
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# id દ્વારા ટોકન મર્યાદા કાઢી નાખો
DELETE /api/usage/token-limits?id=tl-abc
```

> **સ્કીમા નોંધો** (`setTokenLimitSchema`): `apiKeyId` અને `scopeType` (`model` | `provider` | `global`) આવશ્યક છે. જો `scopeType`, `global` ન હોય તો `scopeValue` આવશ્યક છે (દા.ત. `model` વ્યાપ માટે model id, `provider` વ્યાપ માટે provider id). `tokenLimit` ધન પૂર્ણાંક હોવો આવશ્યક છે (stringમાંથી રૂપાંતરિત). વૈકલ્પિક: `id` (બનાવવા માટે છોડો, અપડેટ કરવા માટે આપો), `resetInterval` (`daily` | `weekly` | `monthly`, ડિફૉલ્ટ `monthly`), `resetTime` (`HH:MM`), `enabled` (ડિફૉલ્ટ `true`). `GET` પ્રતિસાદો દરેક મર્યાદામાં `tokensUsed`, `remaining`, `windowStart`, `periodStartAt`, અને `nextResetAt` ઉમેરે છે. આ management-class endpoint છે (authz pipeline દ્વારા અધિકૃતતા કેન્દ્રીય રીતે લાગુ કરવામાં આવે છે).

## વિનંતી પ્રક્રિયા

1. ક્લાયન્ટ `/v1/*` પર વિનંતી મોકલે છે
2. રૂટ હેન્ડલર `handleChat`, `handleEmbedding`, `handleAudioTranscription`, અથવા `handleImageGeneration`ને કૉલ કરે છે
3. Model ઉકેલવામાં આવે છે (સીધો provider/model અથવા alias/combo)
4. એકાઉન્ટ ઉપલબ્ધતા ફિલ્ટરિંગ સાથે સ્થાનિક DBમાંથી credentials પસંદ કરવામાં આવે છે
5. Chat માટે: `handleChatCore` semantic/signature cache તપાસે છે અને combo compression સેટિંગ્સ ઉકેલે છે
6. સક્ષમ હોય ત્યારે provider translation પહેલાં proactive compression ચાલે છે (`lite`, Caveman, RTK, અથવા stacked)
7. Provider executor upstream વિનંતી મોકલે છે
8. પ્રતિસાદને પાછો ક્લાયન્ટ ફોર્મેટમાં રૂપાંતરિત કરવામાં આવે છે (chat) અથવા જેમનો તેમ પરત કરવામાં આવે છે (embeddings/images/audio)
9. Usage, compression analytics, અને request logs નોંધવામાં આવે છે
10. ભૂલો વખતે comboના નિયમો અનુસાર fallback લાગુ થાય છે

સંપૂર્ણ આર્કિટેક્ચર સંદર્ભ: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Combo વ્યવસ્થાપન

ઉચ્ચ-સ્તરીય routing combos (પહેલેથી `/api/combos*` હેઠળ સારાંશિત)ને model id patternમાંથી 1:1 પણ મેપ કરી શકાય છે, જે OpenAI-શૈલીના model idને combo તરફ પારદર્શક રીતે પુનઃદિશામાન કરવાની મંજૂરી આપે છે.

| પદ્ધતિ | પાથ                              | વર્ણન                                                                         |
| ------ | -------------------------------- | ----------------------------------------------------------------------------- |
| GET    | `/api/model-combo-mappings`      | તમામ model→combo mappingsની યાદી આપો                                          |
| POST   | `/api/model-combo-mappings`      | Mapping બનાવો — body: `{pattern, comboId, priority?, enabled?, description?}` |
| GET    | `/api/model-combo-mappings/[id]` | એક mapping મેળવો                                                              |
| PUT    | `/api/model-combo-mappings/[id]` | હાલની mappingનાં fields અપડેટ કરો                                             |
| DELETE | `/api/model-combo-mappings/[id]` | Mapping દૂર કરો                                                               |

**અધિકૃતતા:** management session/API key (`requireManagementAuth`).

## મેનેજમેન્ટ પ્રોક્સીઓ

આઉટબાઉન્ડ HTTP(S)/SOCKS પ્રોક્સીઓ, જે પ્રોવાઇડરો, એકાઉન્ટ્સ અથવા વૈશ્વિક સ્તરે સોંપી શકાય છે.

| પદ્ધતિ | પાથ                                          | વર્ણન                                                                                                                                                                 |
| ------ | -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/management/proxies`                 | પ્રોક્સીઓની યાદી (`?id=` સાથે એક પ્રોક્સી પરત કરે છે; `?id=&where_used=1` સાથે અસાઇનમેન્ટ ગ્રાફ પરત કરે છે)                                                           |
| POST   | `/api/v1/management/proxies`                 | પ્રોક્સી બનાવો — બોડીનું `createProxyRegistrySchema` દ્વારા માન્યીકરણ થાય છે                                                                                          |
| PATCH  | `/api/v1/management/proxies`                 | પ્રોક્સી અપડેટ કરો — બોડીનું `updateProxyRegistrySchema` દ્વારા માન્યીકરણ થાય છે (`id` આવશ્યક છે)                                                                     |
| DELETE | `/api/v1/management/proxies?id=...&force=1`  | પ્રોક્સી કાઢી નાખો (અસાઇનમેન્ટ્સને અલગ કરવા માટે `force=1` વાપરો)                                                                                                     |
| GET    | `/api/v1/management/proxies/assignments`     | અસાઇનમેન્ટ્સની યાદી — `proxy_id`, `scope`, `scope_id` દ્વારા ફિલ્ટર કરી શકાય છે; કોઈ કનેક્શન માટે સક્રિય પ્રોક્સી નિર્ધારિત કરવા `resolve_connection_id=<id>` પાસ કરો |
| PUT    | `/api/v1/management/proxies/assignments`     | અસાઇન કરો — બોડીનું `proxyAssignmentSchema` (`{scope, scopeId?, proxyId?}`) દ્વારા માન્યીકરણ થાય છે. ડિસ્પેચર કૅશ સાફ કરે છે                                          |
| PUT    | `/api/v1/management/proxies/bulk-assign`     | બલ્ક અસાઇન કરો — બોડીનું `bulkProxyAssignmentSchema` (`{scope, scopeIds[], proxyId?}`) દ્વારા માન્યીકરણ થાય છે                                                        |
| GET    | `/api/v1/management/proxies/health?hours=24` | સમયગાળા દરમિયાન પ્રોક્સીની સંકલિત હેલ્થ (સફળતા/નિષ્ફળતાની સંખ્યા, વિલંબ)                                                                                              |

**પ્રમાણીકરણ:** દરેક રૂટ પર મેનેજમેન્ટ સેશન/API કી (`requireManagementAuth`).

> કાર્યના વર્ણનમાં દર્શાવેલ `POST /api/v1/management/proxies/[id]/assignments` અને `POST /api/v1/management/proxies/[id]/health`, ઉપર બતાવેલા ફ્લેટ `/assignments` અને `/health` રૂટ્સ દ્વારા સર્વ થાય છે — કોડબેઝમાં પ્રતિ-id સબરૂટ્સ નથી.

## સ્થિતિસ્થાપકતા (વિસ્તૃત)

OmniRoute ત્રણ સ્વતંત્ર અસ્થાયી-નિષ્ફળતા મિકેનિઝમ ઉપલબ્ધ કરાવે છે; નીચેના મેનેજમેન્ટ એન્ડપોઇન્ટ્સ ઓપરેટર્સને તેમને વાંચવા અને ઓવરરાઇડ કરવાની સુવિધા આપે છે:

| વ્યાપ            | સ્થિતિ સ્ટોરેજ                            | વાંચવું                                   | રીસેટ / સાફ કરવું                                           |
| ---------------- | ----------------------------------------- | ----------------------------------------- | ----------------------------------------------------------- |
| પ્રોવાઇડર બ્રેકર | `domain_circuit_breakers` + ઇન-મેમરી      | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                |
| કનેક્શન કૂલડાઉન  | પ્રોવાઇડર કનેક્શન્સ પર `rateLimitedUntil` | `/api/rate-limits`, `/api/providers/[id]` | (જરૂર પડ્યે ફરી સક્ષમ થાય છે; પ્રોવાઇડર PUT દ્વારા સાફ કરો) |
| મોડલ લૉકઆઉટ      | ઇન-મેમરી મોડલ-ઉપલબ્ધતા રજિસ્ટ્રી          | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                    |

`PATCH /api/resilience`, `providerBreaker.oauth` અને `providerBreaker.apikey` હેઠળ પ્રોવાઇડર બ્રેકર ઓવરરાઇડ્સ સ્વીકારે છે. દરેક પ્રોફાઇલ `degradationThreshold`, `failureThreshold`, અને `resetTimeoutMs` ને સપોર્ટ કરે છે; આ જ ફીલ્ડ્સ Dashboard → Settings → Resilience માં ઉપલબ્ધ છે.

```bash
# એક મોડલ લૉકઆઉટ સાફ કરો
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# દરેક લૉકઆઉટ સાફ કરો
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

સંપૂર્ણ વૈચારિક સંદર્ભ અને બ્રેકર ડિફૉલ્ટ્સ માટે: [`CLAUDE.md`](../../CLAUDE.md) → "સ્થિતિસ્થાપકતા રનટાઇમ સ્થિતિ" અને [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) જુઓ.

### રેટ-લિમિટ કતાર અને સ્વતઃ-સક્ષમ સુરક્ષા વ્યવસ્થા

- **સમર્થિત રાઇટ પાથ**: `{"connectionId": "<id>", "enabled": true|false}` બોડી સાથેનું `POST /api/rate-limits`, કોઈ કનેક્શન માટે રેટ-લિમિટ સુરક્ષા ચાલુ અથવા બંધ કરવા માટેનું સમર્થિત મેનેજમેન્ટ એન્ડપોઇન્ટ છે. `PUT /api/providers/[id]` ઇરાદાપૂર્વક `rateLimitProtection` ને સંશોધિત કે ફ્લિપ કરતું નથી (#11278).
- **`enabled: false` નો અર્થ**: `enabled: false` સેટ કરવાથી કનેક્શન માટેની સ્પષ્ટ સુરક્ષા દૂર થાય છે, પરંતુ સક્રિય API-કી કનેક્શનને વૈશ્વિક સ્વતઃ-સક્ષમ સુરક્ષા વ્યવસ્થા (`autoEnableApiKeyProviders = true`) માંથી **બાકાત રાખવામાં આવતું નથી**. `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) માં, `false` અને `undefined` સમાન છે; સ્પષ્ટ સુરક્ષા વિનાનાં સક્રિય API-કી કનેક્શન્સ સ્વતઃ-સક્ષમ સુરક્ષા વ્યવસ્થા હેઠળ સુરક્ષિત રહે છે.
- **વૈશ્વિક અક્ષમતા**: રેટ-લિમિટ કતારો વિના API-કી કનેક્શન્સ ચલાવવા માટે, `RATE_LIMIT_AUTO_ENABLE=false` (env) અથવા `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`) દ્વારા સુરક્ષા વ્યવસ્થાને વૈશ્વિક સ્તરે અક્ષમ કરો.

## MCP સર્વર

OmniRoute 3 ટ્રાન્સપોર્ટ (stdio, SSE, streamable-http) અને મર્યાદિત ટૂલ્સ સાથે એમ્બેડેડ Model Context Protocol સર્વર પ્રદાન કરે છે. નીચેના ડેશબોર્ડ એન્ડપોઇન્ટ્સ સ્થિતિ/ઑડિટ ડેટા વાંચે છે અને HTTP ટ્રાન્સપોર્ટ્સને પ્રોક્સી કરે છે.

| પદ્ધતિ | પાથ | વર્ણન |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | હાર્ટબીટ, ટ્રાન્સપોર્ટ, ઑનલાઇન સ્થિતિ, છેલ્લો કૉલ, ટોચના ટૂલ્સ, 24 કલાકનો સફળતા દર |
| GET | `/api/mcp/tools` | `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` સાથે MCP ટૂલ્સની સૂચિ |
| GET | `/api/mcp/sse` | SSE ટ્રાન્સપોર્ટ માટે ખુલ્લો SSE સ્ટ્રીમ (MCP અક્ષમ હોય અથવા ટ્રાન્સપોર્ટ મેળ ન ખાતો હોય તો `503` પરત કરે છે) |
| POST | `/api/mcp/sse` | SSE ટ્રાન્સપોર્ટ પર JSON-RPC ફ્રેમ મોકલો |
| GET | `/api/mcp/stream` | Streamable HTTP ટ્રાન્સપોર્ટની SSE બાજુ ખોલો (સર્વર દ્વારા શરૂ કરાયેલા સંદેશાઓ) |
| POST | `/api/mcp/stream` | Streamable HTTP ટ્રાન્સપોર્ટ પર JSON-RPC ફ્રેમ મોકલો |
| DELETE | `/api/mcp/stream` | Streamable HTTP સેશન સમાપ્ત કરો |
| GET | `/api/mcp/audit` | ઑડિટ લૉગ ક્વેરી કરો — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | એકત્રિત ઑડિટ આંકડા (કુલ સંખ્યા, સફળતા દર, સરેરાશ અવધિ, ટોચના ટૂલ્સ) |

**પ્રમાણીકરણ:** `sse`/`stream` ટ્રાન્સપોર્ટ્સ MCP-વિશિષ્ટ પ્રમાણીકરણ સપાટીને અનુસરે છે (`mcp` સ્કોપ સાથેની Bearer API કી); `status`/`tools`/`audit*` રૂટ્સ ડેશબોર્ડમાંથી વાંચી શકાય છે (ડેશબોર્ડ હોસ્ટ સુધી પહોંચવા ઉપરાંત કોઈ વધારાના પ્રમાણીકરણની જરૂર નથી).

> બંને HTTP ટ્રાન્સપોર્ટ્સ `settings.mcpEnabled` અને `settings.mcpTransport` દ્વારા નિયંત્રિત થાય છે — ટ્રાન્સપોર્ટ મેળ ન ખાય તો `400` પરત મળે છે અને MCP અક્ષમ સ્થિતિમાં `503` પરત મળે છે.

## A2A સર્વર

OmniRoute નિરીક્ષણ/ડૅશબોર્ડના ઉપયોગ માટે REST રૅપરની સાથે A2A (Agent-to-Agent) JSON-RPC 2.0 એન્ડપોઇન્ટ ઉપલબ્ધ કરાવે છે.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # OMNIROUTE_API_KEY સેટ ન હોય ત્યાં સુધી વૈકલ્પિક
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

સમર્થિત મેથડ્સ (બધા `settings.a2aEnabled` દ્વારા નિયંત્રિત છે):

| મેથડ             | વર્ણન                                                                 |
| ---------------- | --------------------------------------------------------------------- |
| `message/send`   | સિંક્રોનસ સ્કિલ એક્ઝિક્યુશન; `{task, artifacts, metadata}` પરત કરે છે |
| `message/stream` | સમાન સ્કિલ સેટનું સ્ટ્રીમિંગ SSE એક્ઝિક્યુશન                          |
| `tasks/get`      | `taskId` દ્વારા કાર્ય મેળવે છે                                        |
| `tasks/cancel`   | `taskId` દ્વારા કાર્ય રદ કરે છે                                       |

બિલ્ટ-ઇન સ્કિલ્સ: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### એજન્ટ કાર્ડ

```bash
GET /.well-known/agent.json
```

સાર્વજનિક A2A એજન્ટ કાર્ડ (નામ, વર્ણન, ક્ષમતાઓ, સ્કિલ કૅટલૉગ, ઑથ સ્કીમ) પરત કરે છે — 1 કલાક માટે સાર્વજનિક રીતે કૅશ કરેલું. ઑથ જરૂરી નથી.

### REST સહાયકો

| મેથડ | પાથ                          | વર્ણન                                                                                                              |
| ---- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| GET  | `/api/a2a/status`            | A2A સક્ષમ સ્થિતિ + કાર્યના આંકડા + કૅશ કરેલા એજન્ટ કાર્ડનો સારાંશ                                                  |
| GET  | `/api/a2a/tasks`             | કાર્યોની સૂચિ — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST | `/api/a2a/tasks`             | (REST સહાયક તરીકે અમલમાં મૂકાયેલ નથી — JSON-RPC `message/send` મારફતે બનાવો)                                       |
| GET  | `/api/a2a/tasks/[id]`        | એક કાર્ય મેળવો                                                                                                     |
| POST | `/api/a2a/tasks/[id]/cancel` | કાર્ય રદ કરો                                                                                                       |

**ઑથ:** REST સહાયકો મેનેજમેન્ટ ઑથ વિના ચાલે છે (ડૅશબોર્ડ દ્વારા વાંચી શકાય તેવા); JSON-RPC `/a2a` રૂટ, જો કન્ફિગર કરેલું હોય, તો Bearer `OMNIROUTE_API_KEY` નો ઉપયોગ કરે છે.

**ઑથ:** `/api/cloud/auth` સીધી Bearer કી માન્ય કરે છે અને ફક્ત `manage` / `admin` સ્કોપ ધરાવતી કી માટે જ દરેક કનેક્શનની માસ્ક કરેલી કી અને `projectId` પરત કરે છે; અન્ય `/api/cloud/*`, `/api/evals/*`, અને `/api/assess` રૂટ્સ માટે મેનેજમેન્ટ સેશન/API કી જરૂરી છે. `/api/assess` POST ડિસ્ક્રિમિનેટેડ-યુનિયન સ્કોપ સ્કીમા સાથે `validateBody` નો ઉપયોગ કરે છે.

## ACP (Agent Client Protocol) વ્યવસ્થાપન

ચાઇલ્ડ પ્રોસેસ તરીકે. આ એન્ડપોઇન્ટ્સ ACP એજન્ટની શોધ અને કસ્ટમ એજન્ટ
નોંધણીનું વ્યવસ્થાપન કરે છે.

| પદ્ધતિ | પાથ               | વર્ણન                                                                                                                                                                 |
| ------ | ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/acp/agents` | ઇન્સ્ટોલેશન સ્થિતિ, વર્ઝન અને બાઇનરી સહિતના તમામ જાણીતા CLI એજન્ટ્સની (બિલ્ટ-ઇન + કસ્ટમ) યાદી આપે છે                                                                  |
| POST   | `/api/acp/agents` | કસ્ટમ ACP એજન્ટની નોંધણી કરે છે અથવા કૅશને રિફ્રેશ કરે છે — બોડી: `{id, name, binary, versionCommand, providerAlias, spawnArgs, protocol}` અથવા `{action: "refresh"}` |
| DELETE | `/api/acp/agents` | કસ્ટમ ACP એજન્ટને દૂર કરે છે — ક્વેરી પેરામ: `?id=<agentId>`                                                                                                          |

**પ્રતિસાદનું ઉદાહરણ** (`GET /api/acp/agents`):

```json
{
  "agents": [
    {
      "id": "claude",
      "name": "Claude Code CLI",
      "binary": "claude",
      "version": "1.0.45",
      "installed": true,
      "protocol": "stdio",
      "providerAlias": "claude",
      "isCustom": false
    },
    {
      "id": "my-custom-cli",
      "name": "My Custom CLI",
      "installed": false,
      "protocol": "stdio",
      "providerAlias": "my-provider",
      "isCustom": true
    }
  ],
  "cacheTtlMs": 60000,
  "cacheAge": 1234
}
```

**પ્રમાણીકરણ:** વ્યવસ્થાપન સત્ર (ડૅશબોર્ડ `auth_token` કૂકી) અથવા
વ્યવસ્થાપન-સ્કોપ ધરાવતી API કીની જરૂર છે.

સંપૂર્ણ વિગતો માટે [ACP ફ્રેમવર્ક](../frameworks/ACP.md) જુઓ.

| DELETE | `/api/webhooks/[id]`            | વેબહુક સબ્સ્ક્રિપ્શન કાઢી નાખો                                         |
| GET    | `/api/webhooks/[id]/deliveries` | વેબહુક માટેનો ડિલિવરી ઇતિહાસ સૂચિબદ્ધ કરો (સફળતા/નિષ્ફળતાનો લૉગ)       |

## ગાર્ડરેલ્સ

રનટાઇમ ગાર્ડરેલ્સ (PII શોધ, પ્રોમ્પ્ટ ઇન્જેક્શન શોધ, વિઝન બ્રિજિંગ)નું નિરીક્ષણ કરો. ગાર્ડરેલ્સ દરેક રિક્વેસ્ટ પર ચાલે છે; દરેક કૉલ માટે ઑપ્ટ-આઉટ `x-omniroute-disabled-guardrails` રિક્વેસ્ટ હેડર દ્વારા થાય છે — કાયમી સક્ષમ/અક્ષમ કરવાની કોઈ સરફેસ નથી.

| પદ્ધતિ | પાથ                    | વર્ણન                                                                                   |
| ------ | ---------------------- | --------------------------------------------------------------------------------------- |
| GET    | `/api/guardrails`      | રજિસ્ટર કરેલા ગાર્ડરેલ્સ અને તેમની સ્થિતિની યાદી આપો (નામ / સક્ષમ / પ્રાથમિકતા)         |
| POST   | `/api/guardrails/test` | નમૂના ઇનપુટ પર પ્રી-કૉલ પાઇપલાઇનનું ડ્રાય-રન કરો — બોડી: `{input, disabledGuardrails?}` |

**પ્રમાણીકરણ:** મેનેજમેન્ટ સેશન જરૂરી છે.

સંપૂર્ણ વિગતો માટે [સુરક્ષા > ગાર્ડરેલ્સ](../security/GUARDRAILS.md) જુઓ.

## પ્રમાણીકરણ

ચાર ક્રેડેન્શિયલ પરિવારો (ડેશબોર્ડ સત્ર, સ્થાનિક CLI ટોકન, `oma_live_…` ઍક્સેસ ટોકન, મેનેજમેન્ટ-સ્કોપ્ડ API કી) અને તેઓ ઇન્ફરન્સ કીથી કેવી રીતે અલગ પડે છે તે જાણવા માટે [મેનેજમેન્ટ પ્રમાણીકરણ](../guides/MANAGEMENT-AUTH.md) જુઓ.

- ડેશબોર્ડ રૂટ્સ (`/dashboard/*`) `auth_token` કૂકીનો ઉપયોગ કરે છે
- લૉગિન સાચવેલા પાસવર્ડ હૅશનો ઉપયોગ કરે છે; ઉપલબ્ધ ન હોય તો `INITIAL_PASSWORD`નો ઉપયોગ કરે છે
- `requireLogin`ને `/api/settings/require-login` દ્વારા ચાલુ અથવા બંધ કરી શકાય છે
- જ્યારે `REQUIRE_API_KEY=true` હોય ત્યારે `/v1/*` રૂટ્સ માટે વૈકલ્પિક રીતે Bearer API કી જરૂરી બને છે
- આ સંદર્ભમાં "મેનેજમેન્ટ ટોકન" / "મેનેજમેન્ટ-સ્કોપ્ડ API કી"નો અર્થ તે માર્ગદર્શિકામાં દર્શાવેલા પરિવારોમાંથી કોઈ એક છે — કોઈ અસ્પષ્ટ વધારાનો સિક્રેટ પ્રકાર નહીં

> **બ્રેકિંગ ફેરફાર (v3.8.0)** — `/api/v1/agents/tasks/*` અને કૂલડાઉન મેનેજમેન્ટ એન્ડપોઇન્ટ્સ માટે હવે **મેનેજમેન્ટ પ્રમાણીકરણ** (ડેશબોર્ડ `auth_token` કૂકી અથવા મેનેજમેન્ટ-સ્કોપ્ડ API કી) જરૂરી છે. જે ક્લાયન્ટ્સ અગાઉ પ્રમાણીકરણ વિના આ રૂટ્સને કૉલ કરતા હતા, તેમને `401 Unauthorized` પ્રાપ્ત થશે. કમિટ `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`) જુઓ.
