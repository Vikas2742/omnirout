> હૂક્સ કયા રૂટ્સ અને પ્રતિસાદ પાથ્સ સુધી પહોંચે છે, મર્જ કરેલા નિષ્ક્રિયકરણ હેડર્સ (#16412), ફરજિયાત સીમા તરીકે ઇન્જેક્શન
> બ્લોક મોડ (#16413), અને પોસ્ટ-કૉલ પહેલાં પ્રતિસાદને શું જોઈ શકે છે)

Guardrails, OmniRoute અને અપસ્ટ્રીમ પ્રદાતાઓ વચ્ચેની સીમા પર સલામતી, નીતિ અને સામગ્રી રૂપાંતરણો લાગુ કરે છે. દરેક guardrail વિનંતીના પેલોડ્સ (`preCall`) અને અપસ્ટ્રીમ પ્રતિસાદો (`postCall`)નું નિરીક્ષણ કરી શકે છે (અને વૈકલ્પિક રીતે તેમને નકારી, રૂપાંતરિત અથવા એનોટેટ કરી શકે છે).

સિસ્ટમ **નિષ્ફળતા વખતે ખુલ્લી રહે છે**: જો guardrail અમલ દરમિયાન અપવાદ ફેંકે, તો registry ભૂલ નોંધે છે અને વિનંતીને નિષ્ફળ બનાવવાને બદલે આગળના guardrail સાથે ચાલુ રાખે છે. બ્લોક કરવું એ સ્પષ્ટ નિર્ણય (`block: true`) છે, ક્યારેય અકસ્માત નથી.
એકમાત્ર અપવાદ રદ કરાયેલી વિનંતી છે: જ્યારે કૉલરનું `signal` રદ થાય છે, ત્યારે અપવાદ ફેંકનાર guardrailને અવગણવાને બદલે હૂક રન નકારવામાં આવે છે.

હૂક્સ દરેક રૂટ કે દરેક પ્રતિસાદ પર ચાલતા **નથી**. guardrail પર સુરક્ષા નિયંત્રણ તરીકે આધાર રાખતા પહેલાં [કવરેજ અને મર્યાદાઓ](#coverage-and-limits) વાંચો.

## બિલ્ટ-ઇન Guardrails

આયાત કરતી વખતે registry પ્રાથમિકતાના ક્રમમાં છ guardrails આપમેળે લોડ કરે છે
(`registry.ts` → `registerDefaultGuardrails()` જુઓ):

| પ્રાથમિકતા | નામ                 | તબક્કો(ઓ)      | ફાઇલ                  |
| ---------- | ------------------- | -------------- | --------------------- |
| `5`        | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`        | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`        | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`       | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`       | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`       | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

ઓછી પ્રાથમિકતા સંખ્યાઓ **પહેલાં** ચાલે છે.

### વિઝન બ્રિજ (`visionBridge.ts`) — મોડાલિટી બ્રિજ PR-1

GLM 5.3 બેઝ મોડેલ અને `glm-5.3-{low,high,max}` પાસે સ્પષ્ટ
`supportsVision:false` registry/spec મેટાડેટા છે. GLM 5.3 Flash વેરિઅન્ટ્સ
મૂળ વિઝન મોડેલ્સ તરીકે યથાવત્ રહે છે. Claude Codeનો `/v1/messages` રૂટ,
Claude-થી-OpenAI રૂપાંતરણ **પહેલાં** શેર કરેલી `handleChat` પ્રી-કૉલ guardrail ચેઇનમાં પ્રવેશે છે; રૂપાંતરણ દ્વારા નેસ્ટેડ `Read` ટૂલ-પરિણામ છબીઓને OpenAI `image_url` સામગ્રીમાં ઉઠાવવામાં આવે તે પહેલાં તેમનું વર્ણન કે સંચાલન થવું જરૂરી છે (#17069).

**વિઝન વિનાના મોડેલ્સ**ને લક્ષ્ય બનાવતી છબી ધરાવતી વિનંતીઓને ઇન્ટરસેપ્ટ કરે છે અને કાં તો આખી વિનંતીને વિઝન-સક્ષમ મોડેલ તરફ ફરી રૂટ કરે છે અથવા અપસ્ટ્રીમ કૉલ પહેલાં છબીના ભાગોને રૂપરેખાંકિત કરી શકાય તેવા વિઝન મોડેલ દ્વારા બનાવાયેલા ટેક્સ્ટ વર્ણનોથી બદલે છે. આ ટેક્સ્ટ-માત્ર પ્રદાતાઓને મલ્ટિમોડલ પેલોડ્સ પારદર્શક રીતે સંભાળવા દે છે.

પ્રવાહ:

1. જો લક્ષ્ય મોડેલ પહેલેથી જ વિઝનને સપોર્ટ કરતું હોય, તો તેને છોડી દો (સિવાય કે તે ફરજિયાત-બ્રિજ સૂચિ `isVisionBridgeForcedModel`માં દેખાતું હોય).
2. `extractImageParts(messages)` દ્વારા છબીના ભાગો કાઢો
   (`visionBridgeHelpers.ts`), જે `open-sse/utils/mediaParts.ts`માં રહેલા **એકીકૃત મીડિયા ડિટેક્ટર** `detectMediaParts()`ને કાર્ય સોંપે છે — combo સુસંગતતા ફિલ્ટર સાથે શેર કરાયેલ સત્યનો એકમાત્ર સ્રોત.
   નિષ્કર્ષણ માત્ર `replaceImageParts` ફરીથી જોડી શકે તેવા આકારો પૂરતું allowlist કરેલું છે (extract↔replace કરાર): OpenAI `image_url`, Anthropic base64
   `source.type:"base64"`, Anthropic URL `source.type:"url"`, અને Responses
   API `input_image`. Claude Codeના `tool_result.content` અને Responses ટૂલ આઉટપુટ્સની અંદર નેસ્ટેડ મેળ ખાતી છબીઓ પણ કાઢવામાં આવે છે અને તેમના મૂળ પાથ્સ પર બદલવામાં આવે છે; માત્ર-સૂચક આકારો combo-filter માટેની સામગ્રી છે અને કાઢવામાં આવતા નથી.
   જો કોઈ ન મળે તો છોડી દો.
3. `resolveVisionBridgeRuntimeSettings()` દ્વારા રનટાઇમ રૂપરેખાંકન ઉકેલો
   (`src/shared/constants/modalityBridgeDefaults.ts`): નવી `modalityBridge*`
   સેટિંગ્સ કીઝ પ્રાથમિકતા મેળવે છે; લેગસી `visionBridge*` કીઝ **એક-ચક્ર
   fallback** (રોલબૅક વિન્ડો) તરીકે યથાવત્ રહે છે. બ્રિજ નિષ્ક્રિય હોય ત્યારે કોઈપણ મીડિયા ટ્રાવર્સલ પહેલાં છોડી દો.
4. મોડ સિલેક્ટર (`modalityBridgeVisionMode`, નીચેનું કોષ્ટક જુઓ) ફરી રૂટ કરવું કે વર્ણન કરવું તે નક્કી કરે છે. ફરી રૂટ કરવાથી માત્ર `model`
   બદલાયેલું `modifiedPayload`, તેમજ મેટા `{ rerouted, fromModel, toModel, imagesKept }` પરત મળે છે.
5. વર્ણન પાથ: છબીઓને `maxImages` સુધી મર્યાદિત કરો, કાર્યને અનુરૂપ પ્રોમ્પ્ટ તૈયાર કરો, વર્ણન કૅશ તપાસો, વિઝન મોડેલને **સમાંતરમાં**
   (`Promise.allSettled`) કૉલ કરો અને તેમના સ્થાને `[Image N]: <description>` ટેક્સ્ટ ભાગો ઇન્જેક્ટ કરો. નિષ્ફળ વર્ણનથી `null` મળે છે: અજ્ઞાત/વિઝન-સક્ષમ લક્ષ્યો માટે મૂળ છબી જાળવવામાં આવે છે (#4012), પરંતુ **પુષ્ટિ થયેલા ટેક્સ્ટ-માત્ર સીધા
   લક્ષ્ય** અથવા શૂન્ય-વિઝન combo માટે વર્ણન ન થઈ શકેલી દરેક છબી માટે સ્પષ્ટ
   `(unavailable — no vision-capable provider connected)` ટેક્સ્ટ સ્ટબ મળે છે, જેમાં આંશિક નિષ્ફળતાઓ અને વર્ણન-કૉલ મર્યાદાથી આગળની છબીઓ પણ સામેલ છે (#17069). હાલનો બધા-નિષ્ફળ combo વર્ણન fallback
   યથાવત્ રહે છે (#8430).
6. `modifiedPayload` + મેટા (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) પરત કરો.

| મોડ        | ડિફૉલ્ટ | વર્તણૂક                                                                                                                                                                                                                                                                                                                |
| ---------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔       | લેગસી હ્યુરિસ્ટિક, અપરિવર્તિત (#6640/#7204): નૉન-કોમ્બો/`auto/` મોડલને શ્રેષ્ઠ વિઝન મોડલ તરફ ફરી રૂટ કરવામાં આવે છે, સિવાય કે મૂળ મોડલ પાસે પહેલેથી ઉપયોગ કરી શકાય તેવા ક્રેડેન્શિયલ્સ હોય (ત્યારે વર્ણન કરવામાં આવે છે); કોમ્બો ટાર્ગેટ હંમેશાં વર્ણન કરે છે.                                                         |
| `describe` |         | હંમેશાં વર્ણન કરો — રીરુટ બ્લૉક સંપૂર્ણપણે છોડી દેવામાં આવે છે; વપરાશકર્તાએ પસંદ કરેલું મોડલ હંમેશાં જવાબ આપે છે.                                                                                                                                                                                                      |
| `reroute`  |         | બળજબરીથી રીરુટ કરો: ક્રેડેન્શિયલ ધરાવતા મોડલને જાળવી રાખતો ગાર્ડ બાયપાસ થાય છે. રીરુટ-**ટાર્ગેટ** ક્રેડેન્શિયલ ગાર્ડ હજુ પણ લાગુ પડે છે — જ્યારે ઉપયોગ કરી શકાય તેવું કોઈ વિઝન ટાર્ગેટ અસ્તિત્વમાં ન હોય, ત્યારે બ્રિજ વર્ણન કરવાને અથવા માત્ર-ટેક્સ્ટ ટાર્ગેટને કાચી છબીઓ મોકલવાને બદલે સ્પષ્ટ ભૂલ સાથે બ્લૉક કરે છે. |

બળજબરીથી પસંદ કરેલા મોડ્સ `auto` હ્યુરિસ્ટિક ચાલે તે **પહેલાં** જ શૉર્ટ-સર્કિટ થાય છે;
`auto` ની વર્તણૂક PR-1 પહેલાંના ગાર્ડરેલ સાથે બાઇટ-દર-બાઇટ સમાન છે.

#### API-કીનો વ્યાપ (`visionBridgeKeyScope.ts`)

જ્યારે કૉલરની API કી `allowedConnections`, ક્વોટા પૂલ્સ
(`allowedQuotas`) અથવા મોડલ્સ (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`)ને પ્રતિબંધિત કરે છે, ત્યારે બ્રિજ માત્ર
એવા કનેક્શન્સ પરના રીરુટ અને વર્ણન મોડલ્સ પસંદ કરે છે, જેનો ઉપયોગ કીને કરવાની મંજૂરી હોય.
ત્યારબાદ વર્ણન કૉલ હંમેશાં `x-omniroute-self-loop-key-id` હેડર સાથે
OmniRoute સેલ્ફ-લૂપમાંથી પસાર થાય છે, જેથી તેને પ્રાપ્ત કરતી ચેટ રિક્વેસ્ટ
તે કીની કનેક્શન અને મોડલ નીતિ ફરીથી લાગુ કરે. `enforceApiKeyPolicy()`
એ હેડરને માત્ર સેલ્ફ-લૂપ બેરર સાથે જ માન્ય રાખે છે, તેથી તે ઍક્સેસને માત્ર
વધુ સીમિત કરી શકે છે, અને જે idનું નિરાકરણ ન થાય તેને નકારવામાં આવે છે.

જો કી માટે કોઈ વિઝન મોડલની મંજૂરી ન હોય, તો **પુષ્ટિ થયેલ માત્ર-ટેક્સ્ટ
ટાર્ગેટ** છબીના બાઇટ્સ અસમર્થ અપસ્ટ્રીમને ફૉરવર્ડ કરવાને બદલે
સ્પષ્ટ HTTP 400 સાથે છબી રિક્વેસ્ટને સ્થાનિક રીતે નકારે છે (#17069).
અજ્ઞાત અથવા મૂળભૂત વિઝન ક્ષમતા ધરાવતા ટાર્ગેટ્સ માટે, વર્ણન પાથ તેની અગાઉની
ફેલ-ઓપન વર્તણૂક જાળવી રાખે છે (મેટા `{ skipped: true, reason: "no_permitted_vision_model" }`).
કી વિનાની રિક્વેસ્ટ્સ અને આવા પ્રતિબંધો વિનાની કીઓ પહેલાંની જેમ જ વર્તે છે.

#### કાર્ય-જાગૃત વર્ણન પ્રૉમ્પ્ટ (`modalityBridgeVisionTaskAware`)

ડિફૉલ્ટ **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) મૂળ
વર્ણન પ્રૉમ્પ્ટ સાથે **છેલ્લા વપરાશકર્તા સંદેશા**નો ટેક્સ્ટ (500 અક્ષર સુધી સંક્ષિપ્ત કરેલો)
ઉમેરે છે, જેથી વર્ણન વપરાશકર્તાએ ખરેખર જે પૂછ્યું હોય તે તરફ દોરાય
(codex-vision-proxy પેટર્ન), અને વિઝન મોડલને દેખાતો ટેક્સ્ટ ટ્રાન્સક્રાઇબ કરવા કહે છે.
ફ્લૅગ બંધ હોય — અથવા વપરાશકર્તાનો કોઈ ટેક્સ્ટ ન હોય — ત્યારે મૂળ પ્રૉમ્પ્ટનો
કોઈ ફેરફાર વિના ઉપયોગ થાય છે.

વર્ણન સેલ્ફ-લૂપની પોતાની OpenAI-સુસંગત રિક્વેસ્ટ (`callVisionModelSingle()`
માં `visionBridgeHelpers.ts`) હંમેશાં `image_url.detail: "high"` માગે છે —
બિનશરતી રીતે, દરેક કૉલર/પ્રોવાઇડર માટે, અને કોઈપણ ક્લાયન્ટ સિગ્નલ પર નિર્ભર રહ્યા વિના.
નિમ્ન-વિગત સેમ્પલિંગ આ પ્રૉમ્પ્ટ જે ટેક્સ્ટ-ટ્રાન્સક્રિપ્શન કાર્ય માગે છે તેની OCR ચોકસાઈ
ઘટાડે છે, તેથી મૂળ ઇનબાઉન્ડ રિક્વેસ્ટમાં ગમે તે વિગત સ્તર વપરાયું હોય, વર્ણન કૉલ પોતે
હંમેશાં ઉચ્ચ વિગત માગે છે. આ માત્ર આંતરિક વર્ણન રિક્વેસ્ટ બૉડીને અસર કરે છે; OmniRoute
કૉલરની પોતાની `image_url.detail`ને પ્રાથમિક રિક્વેસ્ટમાં કેવી રીતે ફૉરવર્ડ કરે છે તે બદલતું નથી —
એ ડિફૉલ્ટ અલગથી લાગુ થાય છે, અને ફક્ત શોધાયેલા OpenCode ક્લાયન્ટ્સ માટે,
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`)માં લાગુ થાય છે.
વર્ણન સેલ્ફ-લૂપની Anthropic વાયર-ફૉર્મેટ બ્રાન્ચમાં કોઈ `detail` ફીલ્ડ નથી
અને તેથી કોઈપણ ડિફૉલ્ટથી તે પ્રભાવિત થતી નથી.

#### વર્ણન આઉટપુટ મર્યાદા (`modalityBridgeVisionMaxChars`)

| કી                             | ડિફૉલ્ટ | શ્રેણી             |
| ------------------------------ | ------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`     | `0` અથવા 100–50000 |

`0` (ડિફૉલ્ટ)નો અર્થ **કોઈ મર્યાદા નહીં** છે — `callVisionModel()` દ્વારા પરત કરાયેલું
વર્ણન કોઈ ફેરફાર વિના પસાર થાય છે, જે હાલની વર્તણૂક જાળવી રાખે છે.
100–50000 શ્રેણીનું કોઈપણ મૂલ્ય વર્ણનને ફરીથી `[Image N]: <description>` તરીકે
ઉમેરવામાં આવે તે પહેલાં `…` પ્રત્યય સાથે સંક્ષિપ્ત કરે છે
(`VisionBridgeGuardrail.preCall()` માં `src/lib/guardrails/visionBridge.ts`).
વિગત-ભારે OCR કાર્યોમાં, જ્યાં ડાઉનસ્ટ્રીમ મોડલને સંપૂર્ણ ટ્રાન્સક્રિપ્શનની જરૂર હોય,
આ મર્યાદા વધારો; વધુ બોલકાં વિઝન મોડલ્સ માટે ટોકન વપરાશ મર્યાદિત કરવા તેને ઘટાડો.
ડૅશબોર્ડ ફીલ્ડ Vision ટૅબના Advanced પૅનલમાં આવેલું છે
(`modality-bridge-max-chars` માં `ModalityBridgeVisionTab.tsx`) અને સ્પષ્ટ `0`ને
અસ્પર્શિત રાખીને 1 અને 99 વચ્ચેના કોઈપણ મૂલ્યને ઓછામાં ઓછી 100ની મર્યાદા સુધી વધારે છે —
`0` માત્ર "અસેટ ન કરેલ" ડિફૉલ્ટ નહીં, પરંતુ પોતાની રીતે એક માન્ય Zod મૂલ્ય છે
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`).

#### વર્ણન કૅશ (`modalityBridge/bridgeCache.ts`)

વર્ણન આઉટપુટ્સ માટે ઇન-મેમરી LRU + TTL કૅશ, જે સમગ્ર પ્રોસેસમાં શેર થાય છે.
કી = `sha256(imageRef + composedPrompt + configuredBridgeModel)` જેમાં
લેન્થ-પ્રીફિક્સ ફ્રેમિંગ છે (ફીલ્ડ-બાઉન્ડરી અથડામણો નથી). મોડલ ઘટક
**કૉન્ફિગર કરેલું** બ્રિજ મોડલ છે, વાસ્તવમાં જવાબ આપનાર મોડલ નહીં —
`callVisionModel` આંતરિક રીતે ફૉલબૅક કરી શકે છે, અને દરેક પ્રયાસ પ્રમાણે કી બનાવવાથી
કૅશ વિખંડિત થઈ જશે. નિષ્ફળ વર્ણનો ક્યારેય કૅશ થતા નથી. સેટિંગ્સ:

| કી                              | ડિફૉલ્ટ | શ્રેણી  |
| ------------------------------- | ------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`  | —       |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000 |

#### રિમોટ છબી નોર્મલાઇઝેશન (સેલ્ફ-લૂપ વર્ણન/base64 ફેચ)

જ્યારે બ્રિજ પોતે કોઈ **રિમોટ** છબી ફેચ કરે છે — Anthropic વર્ણન સેલ્ફ-કૉલ અને claude-wire-format base64 રૂપાંતરણ (`ensureBase64ImagesForClaudeWire`), બંને `visionBridgeHelpers.ts` માંના `fetchRemoteImageAsDataUri()` દ્વારા — ત્યારે પરિણામી ડેટા URI ને વિઝન-મોડેલ વિનંતીમાં એમ્બેડ કરતાં પહેલાં `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) મારફતે પસાર કરવામાં આવે છે. અતિમોટી છબીઓને **2048px લાંબી કિનારી** સુધી ડાઉનસ્કેલ કરવામાં આવે છે (OpenAI/Anthropic પહેલેથી સર્વર-સાઇડ પર લાગુ કરતા રિસાઇઝ મર્યાદા સાથે સુસંગત), જે વિઝન મોડેલ શું જુએ છે તે બદલ્યા વિના અપલોડ બાઇટ્સ/લેટન્સી ઘટાડે છે. રિસાઇઝિંગ `sharp` નો ઉપયોગ કરે છે, જે ડાયનેમિક ઇમ્પોર્ટ દ્વારા લોડ થાય છે: જે પ્લેટફોર્મ પર તેની નેટિવ બાઇનરી લોડ થવામાં નિષ્ફળ જાય ત્યાં `normalizeDataUri()` **ક્યારેય થ્રો કરતું નથી** — તે મૂળ બાઇટ્સને યથાવત પસાર કરવા પર પાછું ફરે છે, જેથી વર્ણન/base64-રૂપાંતરણ પાથ હંમેશાં કાર્યરત રહે. છબી ન હોય તેવા બાઇટ્સ (એવો ફેચ જેણે ડિકોડ કરી શકાય તેવી છબી પરત ન કરી હોય) પણ કોઈ ફેરફાર વિના પસાર કરવામાં આવે છે. આ નોર્મલાઇઝેશન માત્ર એવી છબીઓ સુધી મર્યાદિત છે જેને બ્રિજ પોતાના સેલ્ફ-કૉલ માટે ફેચ કરે છે — તે કૉલરના કાચા પાસથ્રૂ પેલોડ પર ક્યારેય લાગુ કરવામાં આવતું નથી, જે માત્ર ઑપ્ટ-ઇન મ્યુટેશનના સિદ્ધાંત (કડક નિયમ #20) સાથે સુસંગત છે.

#### સેટિંગ્સ સ્કીમા + માઇગ્રેશન

નવી `modalityBridge*` કીઝને `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`) માં Zod દ્વારા માન્ય કરવામાં આવે છે: `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCache*` ત્રિપુટી અને Audio Bridge દ્વારા ઉપયોગમાં લેવાતું `modalityBridgeAudio*` જૂથ. માઇગ્રેશન `141_modality_bridge_settings.sql` હાલની લેગસી `visionBridge*` વેલ્યૂઝને મેળ ખાતી નવી કીઝમાં કૉપિ કરે છે (આઇડેમ્પોટન્ટ, ઑપરેટરે સેટ કરેલી `modalityBridge*` વેલ્યૂને ક્યારેય ઓવરરાઇટ કરતું નથી); એક રિલીઝ ચક્ર માટે લેગસી કીઝને રીડ ફૉલબૅક તરીકે સ્વીકારવાનું ચાલુ રહેશે.

#### પારદર્શિતા હેડર + આંકડા

વર્ણન દ્વારા રૂપાંતરિત પ્રતિસાદોમાં `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` હોય છે (`modalityBridge/bridgeStats.ts` માંના `buildModalityBridgeHeader()` દ્વારા બનાવાયેલ અને `src/sse/handlers/chatHelpers.ts` માંના `withModalityBridgeHeader()` દ્વારા સ્ટૅમ્પ કરાયેલ). રિરાઉટ કરેલી વિનંતીઓને કોઈ હેડર મળતું **નથી** — પેલોડને સ્પર્શવામાં આવ્યો નહોતો અને મોડેલ સ્વૅપ પહેલેથી જ પ્રતિસાદ બોડીના `model` ફીલ્ડમાં દેખાય છે.

`GET /api/modality-bridge/stats` (મેનેજમેન્ટ ઑથ, `GET /api/settings` જેટલું જ સ્તર) `vision`, `audio` અને `video` માટે ઇન-મેમરી પ્રતિ-મોડેલિટી કાઉન્ટર્સ `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` પરત કરે છે. `averageLatencyMs` તેના છેદ તરીકે તમામ પ્રયાસોને બદલે `latencySamples` નો ઉપયોગ કરે છે; ટાઇમિંગ વિનાનું ઑપરેશન શૂન્ય-મિલિસેકન્ડનો નકલી નમૂનો બનાવતું નથી. `bridged` સફળ રૂપાંતરણો માટે બૅકવર્ડ-કમ્પેટિબલ ઉપનામ તરીકે યથાવત રહે છે; નિષ્ફળ પ્રયાસો તેને વધારતા નથી.
કાઉન્ટર્સ ડિઝાઇન મુજબ પ્રોસેસ રિસ્ટાર્ટ થાય ત્યારે રીસેટ થાય છે
(ટેલિમેટ્રી, હિસાબ-કિતાબ નહીં).

#### ડૅશબોર્ડ કન્ફિગરેશન

સમર્પિત ડૅશબોર્ડ પેજ `/dashboard/settings/modality-bridge` છે. તેની URL દ્વારા ઍક્સેસ કરી શકાય તેવી `Vision`, `Audio` અને `Video` ટૅબ્સ `tab` વેલ્યૂ બદલતી વખતે ક્વેરી પેરામીટર્સ જાળવી રાખે છે. Vision ટૅબ સક્ષમતા, મોડ, મોડેલ પસંદગી (ઑટોમેટિક ડિફૉલ્ટ સહિત), કાર્ય-જાગૃત પ્રૉમ્પ્ટિંગ, અદ્યતન ટાઇમઆઉટ/છબી/વર્ણન-લંબાઈ/કૅશ મર્યાદાઓ, રનટાઇમ કાઉન્ટર્સ અને સુરક્ષિત નમૂના વિનંતી પ્રદાન કરે છે. Audio ટૅબ પણ લાઇવ છે: તે સક્ષમતા, Auto સાથે માત્ર-STT મોડેલ પિકર, ટાઇમઆઉટ/મહત્તમ-ક્લિપ મર્યાદાઓ, ઑડિયો કાઉન્ટર્સ અને `input_audio` નમૂના પરીક્ષણ પ્રદાન કરે છે. Video ટૅબ કાર્યરત છે: તે FFmpeg/ffprobe રનટાઇમ સ્થિતિ દર્શાવે છે — ચાર સ્પષ્ટ UI સ્થિતિઓમાંથી એક (`unknown` જ્યારે પ્રોબ ચાલુ હોય અથવા પૂર્ણ ન થઈ શક્યો હોય, નૉન-લૂપબૅક ડૅશબોર્ડ હોસ્ટ પર જ્યાં પ્રોબ ક્લાયન્ટ-સાઇડથી સ્કિપ કરવામાં આવ્યો હોય ત્યાં `restricted`, પ્રોબ કર્યા પછી તે ઉપલબ્ધ નથી તેની પુષ્ટિ થાય ત્યારે `unavailable`, અથવા FFmpeg/ffprobe વર્ઝન સાથે `available`) — સક્ષમતા/મોડેલ/ફ્રેમ/વિડિયો/ટાઇમઆઉટ મર્યાદાઓ પર્સિસ્ટ કરે છે, મોડેલ પિકરને વિઝન-ક્ષમ મોડેલો સુધી ફિલ્ટર કરે છે અને વિડિયો કાઉન્ટર્સ પ્રદાન કરે છે.

AI સેટિંગ્સ હેઠળનું અગાઉનું Vision Bridge કાર્ડ હવે નવા પેજ માટેની કમ્પેટિબિલિટી લિંક છે; હવે તેમાં ફોર્મની બીજી નકલ રહેતી નથી. Media Providers પણ હાલનું Speech-to-Text પ્લેગ્રાઉન્ડ દૂર કર્યા વિના Image-to-Text અને Speech-to-Text વર્કફ્લોને સંબંધિત Modality Bridge ટૅબ્સ સાથે લિંક કરે છે.

**સેલ્ફ-લૂપ ઍડમિશન બાયપાસ:** જ્યારે વર્ણન કૉલ OmniRoute ના પોતાના `/v1` સેલ્ફ-લૂપ (નૉન-સ્ટાન્ડર્ડ પ્રોવાઇડર મોડેલ) મારફતે રાઉટ થાય છે, ત્યારે સબ-રિક્વેસ્ટ `x-omniroute-admission-bypass: internal` મોકલે છે અને રિઝૉલ્વ કરેલા સેલ્ફ-લૂપ ક્રેડેન્શિયલથી ઑથેન્ટિકેટ થાય છે — લોકલ મોડમાં સ્થાનિક `sk_omniroute` સેન્ટિનલ અથવા ઑપરેટર દ્વારા કન્ફિગર કરેલી `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env કી (#1350), જેથી `REQUIRE_API_KEY=true` ડિપ્લોયમેન્ટ્સમાં પણ વર્ણન કૉલ ચાલી શકે. બાયપાસ માત્ર આ ચોક્કસ ક્રેડેન્શિયલ્સ માટે જ માન્ય રાખવામાં આવે છે, જેથી બાહ્ય ક્લાયન્ટ્સ ઍડમિશન ટાળવા માટે હેડરનો ઉપયોગ ન કરી શકે.

લેગસી ડિફૉલ્ટ્સ `src/shared/constants/visionBridgeDefaults.ts` માં છે; નવા મોડ/કાર્ય-જાગૃત/કૅશ ડિફૉલ્ટ્સ અને સેટિંગ્સ રિઝૉલ્વર `src/shared/constants/modalityBridgeDefaults.ts` માં છે. ગાર્ડરેલ `deps` કન્સ્ટ્રક્ટર વિકલ્પ પ્રદાન કરે છે, જેથી પરીક્ષણો નકલી `getSettings` અને `callVisionModel` અમલીકરણો ઇન્જેક્ટ કરી શકે.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

ઑડિયો ઇનપુટ સ્વીકારતું હોવાનું જાણીતું ન હોય તેવા ટાર્ગેટ સુધી પહોંચે તે પહેલાં ઑડિયો ધરાવતી ચૅટ વિનંતીઓને ઇન્ટરસેપ્ટ કરે છે. તે ચૅટ વિનંતીને ક્યારેય રિરાઉટ કરતું નથી: હાલના OpenAI-કમ્પેટિબલ મલ્ટિપાર્ટ એન્ડપોઇન્ટ મારફતે ઑડિયો ભાગોનું ટ્રાન્સક્રિપ્શન કરવામાં આવે છે અને પસંદ કરેલું ચૅટ મોડેલ ટેક્સ્ટ ટ્રાન્સક્રિપ્ટ્સ સાથે ચાલુ રહે છે.

પ્રવાહ:

1. `getResolvedModelCapabilities()` દ્વારા `supportsAudio` ને રિઝોલ્વ કરો. સૌપ્રથમ સ્પષ્ટ
   provider-registry મેટાડેટાને પ્રાથમિકતા મળે છે, પછી સ્થિર મોડલ મેટાડેટાને, અને ત્યારબાદ સમન્વિત
   `modalities_input` ને. `audio` વિનાની જાહેર કરેલી ઇનપુટ સૂચિ `false` છે; ક્ષમતાનો
   કોઈ પુરાવો ન હોય તો `null` રહે છે. `false` અને `null` બંને રૂઢિચુસ્ત બ્રિજને
   સક્રિય કરે છે, જ્યારે `true` તેને બાયપાસ કરે છે.
2. `modalityBridgeAudio*` સેટિંગ્સને રિઝોલ્વ કરો અને શેર કરાયેલા `detectMediaParts()`
   ડિટેક્ટર દ્વારા દરેક સંદેશમાંથી સ્પ્લાઇસ કરી શકાય તેવા ટોચના-સ્તરના
   ઑડિયો ભાગો કાઢો. સપોર્ટેડ વાયર આકારો OpenAI `input_audio`, `audio_url`, અને
   `source.media_type: "audio/*"` છે. નેસ્ટેડ ઑડિયો રૂટિંગ માટે શોધાય છે પરંતુ
   સ્પ્લાઇસ પાથ દ્વારા દૂર થતો નથી. કાર્ય `modalityBridgeAudioMaxClips` દ્વારા મર્યાદિત છે;
   પછીના ભાગો અસ્પર્શિત રહે છે.
3. કન્ફિગર કરેલા `provider/model` ને માન આપો, અથવા `selectAudioBridgeModel()` ને
   સ્થિર કૅટલૉગ ક્રમમાં `AUDIO_TRANSCRIPTION_PROVIDERS` માંથી પસાર થવા દો અને ઉપયોગમાં લઈ શકાય તેવા
   સક્રિય પ્રોવાઇડર ક્રેડેન્શિયલ ધરાવતું પ્રથમ મોડલ પસંદ કરવા દો.
4. `callAudioTranscription()` base64/data-URI ઑડિયોને multipart
   `file` માં રૂપાંતરિત કરે છે, અથવા DNS પિનિંગ અને 25 MBની મર્યાદા ધરાવતા ફક્ત-જાહેર આઉટબાઉન્ડ
   ગાર્ડ દ્વારા દૂરસ્થ `audio_url` ડાઉનલોડ કરે છે. પછી તે ફાઇલ અને પસંદ કરેલું
   મોડલ સ્થાનિક `/v1/audio/transcriptions` સેલ્ફ-લૂપ પર POST કરે છે, જેને
   `resolveSelfLoopBearer()` વડે પ્રમાણિત કરવામાં આવે છે. હાલનો ટ્રાન્સક્રિપ્શન રૂટ સામાન્ય
   ક્રેડેન્શિયલ લુકઅપ, કૂલડાઉન/રેટ-લિમિટ હેન્ડલિંગ અને પ્રોવાઇડર ડિસ્પેચ કરે છે.
5. સફળ કૉલ્સ તેમના ભાગોને `[Audio N]: <transcript>` થી બદલે છે. કૉલ્સ
   `Promise.allSettled` સાથે ચાલે છે: કોઈ વ્યક્તિગત નિષ્ફળતા તે મૂળ
   ઑડિયો ભાગને જાળવી રાખે છે (#4012 કરાર). જો દરેક કૉલ નિષ્ફળ જાય અને લક્ષ્ય માટે
   `supportsAudio === false` સાબિત થયેલું હોય, તો ભાગો
   `[Audio N]: (unavailable — no STT provider connected)` બને છે (#8430 કરાર). અજ્ઞાત
   લક્ષ્ય (`null`) માટે, તમામ કૉલ નિષ્ફળ રહે તેવું પરિણામ અસ્પર્શિત રહે છે. ઉપયોગમાં લઈ શકાય તેવા
   STT ક્રેડેન્શિયલ વિનાના સાબિત ટેક્સ્ટ-માત્ર લક્ષ્યને નેટવર્ક કૉલ કર્યા વિના સમાન સ્પષ્ટ
   સ્ટબ મળે છે.

સફળ ટ્રાન્સક્રિપ્ટ્સ પ્રક્રિયા-વ્યાપી Modality Bridge LRU/TTL કૅશનો ઉપયોગ કરે છે.
કીમાં ઑડિયો સંદર્ભ, સ્થિર `audio-transcription` ઑપરેશન
લેબલ અને પસંદ કરેલું STT મોડલ સંયોજિત થાય છે; નિષ્ફળતાઓ ક્યારેય કૅશ થતી નથી. ઑડિયો પ્રયાસો
શેર કરેલા `bridged`, `cacheHits`, `failures`, અને `lastUsedAt` કાઉન્ટર્સ અપડેટ કરે છે.
રૂપાંતરિત પ્રતિસાદોમાં
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` હોય છે; અસ્પર્શિત
વિનંતીઓને Audio Bridge સેગમેન્ટ મળતું નથી.

રનટાઇમ સેટિંગ્સ DB-બૅક્ડ અને Zod-વૅલિડેટેડ છે:

| કી                            | ડિફૉલ્ટ | શ્રેણી          |
| ----------------------------- | ------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —               |
| `modalityBridgeAudioModel`    | `""`    | ઑટો અથવા STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10            |

શેર કરાયેલ કૅશ હજુ પણ `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, અને `modalityBridgeCacheMaxEntries` દ્વારા નિયંત્રિત થાય છે.

### વિડિયો બ્રિજ (`videoBridge.ts`, `videoBridgePipeline.ts`)

જાણીતા મૂળ વિડિયો સપોર્ટ વિનાના લક્ષ્યને કૉલ કરવામાં આવે તે પહેલાં Chat Completions
`messages` અને Responses API `input` માં ટોચના-સ્તરના વિડિયો ભાગોને ઇન્ટરસેપ્ટ કરે છે.
સપોર્ટેડ આકારો `input_video`, `video_url`, `video_source`, HTTPS URLs,
અને `data:video/*;base64,...` ડેટા URIs છે. ટેક્સ્ટમાં સાદા ફાઇલનામોને વિડિયો
તરીકે ગણવામાં આવતા નથી.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) વિનંતી ટ્રાવર્સલ,
ક્ષમતા/પૉલિસી તપાસ, પ્રતિ-વિનંતી એગ્રીગેશન અને પ્રતિસાદ પેલોડનું સંચાલન કરે છે.
પ્રતિ-વિડિયો કાર્ય — અધિગ્રહણ, સંપૂર્ણ-પરિણામ કૅશ, ફ્રેમ
ક્રમનું વર્ણન (જે કૉલર દ્વારા જાહેર કરાયેલ કોઈપણ ઑડિયો ટ્રાન્સક્રિપ્ટને ફ્યુઝ કરે છે), અને પ્રતિ-પ્રયાસ
મેટ્રિક્સ/અબોર્ટ/ક્લીનઅપ — `videoBridgePipeline.ts` માં
`processVideoPart` પાછળ છુપાયેલું છે, જેને `preCall` ના લૂપમાં દરેક વિડિયો ભાગ માટે એક વખત કૉલ કરવામાં આવે છે.
આ મોડ્યુલ સ્પષ્ટ પોર્ટ સીમાઓ `VideoMediaBrokerPort`
(બાઇટ્સ મેળવવા અને સૅમ્પલ કરેલી ફ્રેમ્સ કાઢવા), `VideoAudioTranscriptionPort`
(કૉલર દ્વારા જાહેર કરાયેલ ઑડિયો ટ્રાન્સક્રિપ્ટને સૅમ્પલ કરેલા કૅપ્શન્સ સાથે ફ્યુઝ કરવા), અને
`VideoDrilldownPort` (ફ્રેમ ડ્રિલ-ડાઉન પર્સિસ્ટન્સ સીમા; હજુ સુધી
`processVideoPart` સાથે વાયર કરાયેલ નથી — આજે ફક્ત અલગ `/api/modality-bridge/video/drilldown`
રૂટ ડ્રિલ-ડાઉન એન્ટ્રીઓ લખે છે) પણ વ્યાખ્યાયિત કરે છે.

જાહેર `/v1` વિનંતી પાથ ક્યારેય સબપ્રોસેસને ઇમ્પોર્ટ કરતો કે બોલાવતો નથી. દૂરસ્થ
વિડિયો 50 MiBની મર્યાદા હેઠળ ડાઉનલોડ થાય છે; ઇનલાઇન base64 વિડિયો માટે
પ્રતિ-વિડિયો રૂઢિચુસ્ત 36 MiB ડિકોડેડ મર્યાદા છે જેથી મોડલ/સંદેશા/ફ્રેમિંગ એન્વલોપ
50 MiBની જાહેર JSON વિનંતી સ્વીકૃતિ મર્યાદાની અંદર રહી શકે. ફાળવણી પહેલાં ઇનલાઇન
લંબાઈ અને ડિકોડેડ-કદના અંદાજો તપાસવામાં આવે છે. પ્રારંભિક દૂરસ્થ URL અને દરેક
રીડાયરેક્ટ પર HTTPS આવશ્યક છે, જેમાં DNS પિનિંગ સાથેના હાલના
ફક્ત-જાહેર આઉટબાઉન્ડ ગાર્ડનો ઉપયોગ થાય છે. ત્યારબાદ બાઇટ્સ ચોક્કસ આંતરિક
`POST /api/modality-bridge/video/extract` બ્રોકર સીમા પાર કરે છે. તે રૂટ
`LOCAL_ONLY` અને `SPAWN_CAPABLE` બંને છે, ફક્ત પ્રતિ-પ્રક્રિયા પ્રમાણિત,
વિશ્વસનીય-લૂપબૅક વિનંતી સ્વીકારે છે અને ક્યારેય URL, ફાઇલસિસ્ટમ પાથ, એક્ઝિક્યુટેબલ
અથવા આર્ગ્યુમેન્ટ સૂચિ સ્વીકારતો નથી. API બૉડી-કદ પાઇપલાઇન અને હૅન્ડલરનું ઇન્ક્રિમેન્ટલ બૉડી
રીડર સ્વતંત્ર રીતે 50 MiB બ્રોકર ઇનપુટ મર્યાદા લાગુ કરે છે. તેની મર્યાદિત કતાર
એક સમયે એક એક્સ્ટ્રેક્શન ચલાવે છે, ચાર પેન્ડિંગ જૉબ્સને મંજૂરી આપે છે અને પેન્ડિંગ ઇનપુટને
100 MiB સુધી મર્યાદિત કરે છે.

બ્રોકરની અંદર, `ffprobe` ખાનગી સ્થાનિક ફાઇલ વાંચે છે; નિશ્ચિત ફોર્મેટ
અનુમતિસૂચિ પ્લેલિસ્ટ અને મેનિફેસ્ટ ફોર્મેટને બાકાત રાખે છે. અનુમતિપ્રાપ્ત MOV-ફેમિલી
કન્ટેનર્સ માટે, બાહ્ય MOV ડેટા રેફરન્સ મૂળભૂત રીતે અક્ષમ રહે છે અને
નિશ્ચિત કમાન્ડ તેમને સક્રિય કરવાનું પસંદ કરતું નથી. `ffprobe` અને `ffmpeg` બંને
માત્ર-`file` પ્રોટોકોલ શ્વેતસૂચિ, એક થ્રેડ, નિશ્ચિત આર્ગ્યુમેન્ટ એરે, કોઈ શેલ નહીં,
અને `PATH`માંથી રિઝોલ્વ થયેલ એક્ઝિક્યુટેબલ્સનો ઉપયોગ કરે છે. જોડાયેલ-ચિત્ર કવર સ્ટ્રીમ્સ
પ્લે કરી શકાય તેવા ઉમેદવારો નથી. પ્લે કરી શકાય તેવી તમામ સ્ટ્રીમ્સે મર્યાદાઓ સંતોષવી
આવશ્યક છે અને નિર્ધારિત સૌથી ઓછા-ઇન્ડેક્સ ફૉલબૅક પહેલાં સ્પષ્ટ ડિફૉલ્ટ સ્ટ્રીમને
પ્રાધાન્ય આપવામાં આવે છે. વિડિયો 600 સેકન્ડ, દરેક પરિમાણમાં 8,192 પિક્સેલ અને
33,554,432 સોર્સ પિક્સેલ સુધી મર્યાદિત છે. FFmpeg મધ્યબિંદુનાં 1–16 JPEG ફ્રેમ્સના
નમૂના લે છે, નાનાં ઇનપુટ્સને અપસ્કેલ કર્યા વિના લાંબી ધારને વધુમાં વધુ 1,024
પિક્સેલ સુધી ઘટાડે છે અને ક્યારેય URL મેળવતું નથી. નમૂના લેવાની નીતિ મૂળભૂત રીતે
`uniform` છે. વૈકલ્પિક `scene_aware` અને પ્રાયોગિક `segment_aware` નીતિઓ પહેલેથી
માન્ય કરાયેલી સ્થાનિક સ્ટ્રીમ પર એક વધારાનો નિશ્ચિત FFmpeg પાસ કરે છે, મર્યાદિત
`showinfo` દૃશ્ય ટાઇમસ્ટૅમ્પ પસંદ કરે છે અને ડિટેક્ટરની નિષ્ફળતા, ટાઇમઆઉટ, વિકૃત
આઉટપુટ અથવા ખાલી ઉમેદવાર સમૂહની સ્થિતિમાં નિર્ધારિત રીતે એ જ સમાન મધ્યબિંદુઓ પર
ફૉલબૅક કરે છે. સેગમેન્ટ-અવેર મોડ માન્ય કરાયેલા દૃશ્ય અંતરાલોના પ્રમાણમાં મધ્યબિંદુ
નમૂનાઓ ફાળવે છે; સેગમેન્ટ-અવેર પુરાવા અને ફૉલબૅક વર્તનની વિગતો નીચે આપી છે.
દરેક નીતિમાં પસંદગી પછી 16-ફ્રેમની કડક મહત્તમ મર્યાદા લાગુ કરવામાં આવે છે. જ્યારે
સીન-અવેર વિનંતીમાં માત્ર એક-ફ્રેમનું બજેટ હોય, ત્યારે તે સક્રિય પૂર્ણ-વિડિયો અથવા
ફોકસ વિન્ડોના સમાન મધ્યબિંદુનો ઉપયોગ કરે છે અને `policyEffective: uniform` રિપોર્ટ
કરે છે: પસંદ કરાયેલી એક દૃશ્ય ફ્રેમ સમયરેખાના બંને છેડા જાળવી શકતી નથી. કૉલર
વૈકલ્પિક રીતે સીમિત ફોકસ વિન્ડો (`start`/`end` સેકન્ડ) આપી શકે છે; સીમાઓને મીડિયા
અવધિ સુધી ક્લૅમ્પ કરવામાં આવે છે, ઉલટી અથવા અસીમિત વિન્ડો નકારવામાં આવે છે અને
તમામ નમૂના નીતિઓ ફક્ત સામાન્યકૃત અંતરાલની અંદર જ અમલમાં મૂકવામાં આવે છે. પરિણામી
વિન્ડો નમૂના મેટાડેટા અને અવિશ્વસનીય વર્ણન પ્રીફિક્સમાં સામેલ કરવામાં આવે છે, જેથી
ડાઉનસ્ટ્રીમ મોડેલો કેન્દ્રિત અંશને સંપૂર્ણ સમયરેખાથી અલગ ઓળખી શકે.

મોડલ-કૉલની સંખ્યા અને મેનિફેસ્ટ દ્વારા વ્યાખ્યાયિત હકીકતોનું રિટેન્શન માપે છે. રૉ મોડલ પ્રતિસાદો
રિપોર્ટમાં લખવામાં આવતા નથી; ફક્ત SHA-256 ડાઇજેસ્ટ્સ અને મેળ ખાતા ફેક્ટ IDs જાળવવામાં આવે છે. આ
હાર્નેસ ત્યાં સુધી કોઈ નેટવર્ક અથવા ચૂકવણીવાળો મોડલ કૉલ કરતું નથી, જ્યાં સુધી `--execute-real` પાસ ન કરવામાં આવે અને
`--model`, `OMNIROUTE_BASE_URL` તથા `OMNIROUTE_API_KEY` કૉન્ફિગર ન કરેલા હોય. આવી
સ્પષ્ટ વાસ્તવિક રન વિના, તેનો મશીન-વાંચનીય ચુકાદો `HOLD` જ રહે છે; માત્ર સિન્થેટિક
પેલોડ/કૉલ-સંખ્યા માપન પ્રમોશન માટેના પુરાવા નથી.

જ્યારે કૉલર્સ પાસે પહેલેથી જ સંરેખિત ટેક્સ્ટ હોય, ત્યારે તેઓ સમર્થિત વિડિયો
ભાગ સાથે વૈકલ્પિક `transcript.cues` ઍરે જોડી શકે છે. દરેક ક્યૂમાં `text`,
ચકાસેલા સમયગાળાની અંદર મર્યાદિત `start`/`end` અંતરાલ અને વ્હાઇટલિસ્ટ કરેલો
`source` (`client`, `embedded`, અથવા `audio-bridge`) હોવો આવશ્યક છે; `confidence` નું ડિફૉલ્ટ મૂલ્ય
`1` છે અને તે `0` તથા `1` ની વચ્ચે જ રહેવું જોઈએ. બરાબર સમાન ડુપ્લિકેટ ક્યૂઝ સંકુચિત કરવામાં આવે છે.
OmniRoute આ મેટાડેટામાંથી ક્યારેય ટ્રાન્સક્રિપ્શન શરૂ કરતું નથી: માન્ય કરેલા ક્યૂઝને
સ્રોત, વિશ્વસનીયતા અને અંતરાલ સાથે વર્ણવેલા પરિણામમાં કૉપિ કરવામાં આવે છે અને
ફ્રેમ કૅપ્શન્સની સાથે અવિશ્વસનીય અવલોકનો તરીકે રેન્ડર કરવામાં આવે છે. અમાન્ય,
રેન્જની બહારનું અથવા પ્રોવેનન્સ વિનાનું ટેક્સ્ટ કૅપ્શન સ્ટ્રીમમાં ભેળવવાને બદલે નકારવામાં આવે છે.
બંને રિક્વેસ્ટ-બોડી ટ્રાન્સક્રિપ્ટ ચૅનલ્સ આપેલા પ્રોવેનન્સને `client` તરીકે નોર્મલાઇઝ કરે છે,
જેમાં સ્વયં-દાવો કરેલા `embedded` અથવા `audio-bridge`
લેબલ્સનો પણ સમાવેશ થાય છે. ફક્ત સર્વર-માલિકીનું ઍડેપ્ટર કોડ-માત્ર `trustedSource` આર્ગ્યુમેન્ટ દ્વારા એ વિશ્વસનીય લેબલ્સ આપી શકે છે;
રિક્વેસ્ટ JSON ફીલ્ડ એ આર્ગ્યુમેન્ટ સુધી પહોંચી શકતું નથી. ટ્રાન્સક્રિપ્ટ ટેક્સ્ટ તેના
પ્રોવેનન્સને ધ્યાનમાં લીધા વિના અવિશ્વસનીય મીડિયા-ઉત્પન્ન કન્ટેન્ટ જ રહે છે અને તેનાથી ક્યારેય અધિકૃતતા નક્કી થવી જોઈએ નહીં.

અદ્યતન કૉલર એ જ વિડિયો માટે `audioTranscript` ટ્રૅક આપી શકે છે;
તેને ક્લાયન્ટ દ્વારા આપેલા ટેક્સ્ટ તરીકે ગણવામાં આવે છે, સર્વર ટ્રાન્સક્રિપ્શનના પુરાવા તરીકે નહીં.
ફ્યુઝન સીમ વિઝ્યુઅલ અને ઑડિયો અવલોકનોને એક
ડેડલાઇન અને અબોર્ટ સિગ્નલ હેઠળ ચલાવે છે, તેમને એક સામાન્ય સમયરેખા પર ગોઠવે છે, બરાબર સમાન
ડુપ્લિકેટ્સને સંકુચિત કરે છે અને માત્ર એક બાજુ સફળ થાય ત્યારે આંશિક પરિણામની જાણ કરે છે.
અમાન્ય `audioTranscript` સંપૂર્ણ વિડિયોને નિષ્ફળ બનાવવાને બદલે તે આંશિક પરિણામ સુધી ડિગ્રેડ થાય છે —
વિઝ્યુઅલ વર્ણન જાળવી રાખવામાં આવે છે અને ઑડિયો બ્રાન્ચ સૅનિટાઇઝ કરેલો નિષ્ફળતા કોડ નોંધે છે —
દરેક બ્રાન્ચની ઉપલબ્ધતા, આંશિક ફ્લૅગ અને સૅનિટાઇઝ કરેલા નિષ્ફળતા કોડ્સ વર્ણવેલા પરિણામમાં,
ગાર્ડરેલ મેટાડેટામાં (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), રિઝલ્ટ-કૅશ મેટાડેટામાં અને બ્રિજ
ફ્યુઝન કાઉન્ટર્સમાં જાળવવામાં આવે છે. ડિફૉલ્ટ Video Bridge પાથ સ્પીચ-ટુ-ટેક્સ્ટને
કૉલ કરતો નથી અથવા મીડિયાની બીજી કૉપિ ડાઉનલોડ કરતો નથી; એ સ્પષ્ટ ટ્રૅક વિના, તે
ફક્ત વિડિયો માટે જ રહે છે.

**ટ્રાન્સક્રિપ્ટ જાળવણી (#12150 P1).** જ્યારે પણ Video Bridge (જે પોતે opt-in છે) કોઈ ટ્રાન્સક્રિપ્ટ ક્યૂ રેન્ડર કરે છે ત્યારે આ આપમેળે લાગુ પડે છે — તેના માટે કોઈ અલગ જાળવણી ફ્લૅગ નથી. જ્યારે કોઈ વિનંતી કોઈપણ ટ્રાન્સક્રિપ્ટ ક્યૂ (કૉલર દ્વારા જાહેર કરાયેલ `transcript` અથવા સંયોજિત `audioTranscript`) રેન્ડર કરે છે, ત્યારે ગાર્ડરેલ તેને `videoBridgeObserved` તરીકે ચિહ્નિત કરે છે અને વિડિયો વર્ણનની રીડેક્ટ કરેલી છાયા બનાવે છે — એવું સમાન રેન્ડરિંગ જેમાં દરેક ક્યૂનું મુક્ત-ટેક્સ્ટ બૉડી `[redacted-video-transcript]` વડે બદલાયેલું હોય છે. આ છાયા સ્ટ્રિંગ એસેમ્બલ થાય તે પહેલાં સંરચિત ક્યૂ ફીલ્ડને બદલીને બનાવવામાં આવે છે (ફ્લૅટન કરેલા ટેક્સ્ટને પાર્સ કરીને ક્યારેય નહીં, જેથી કોઈપણ ક્યૂ સામગ્રી — પ્રતિકૂળ કે સામાન્ય, જેમાં `]` ધરાવતી બૉડી જેમ કે `[inaudible]`/`[music]` પણ સામેલ છે — બચી ન શકે). જાળવી રાખવામાં આવેલી કૉલ-લૉગ વિનંતી બૉડીમાં, સામગ્રીની સમાનતા દ્વારા મેળ ખવડાવીને, વિડિયોમાંથી મેળવાયેલા દરેક ટેક્સ્ટ ભાગને તે રીડેક્ટ કરેલી છાયા વડે બદલવામાં આવે છે; પૂર્ણ થયેલા પ્રી-કૉલ ગાર્ડરેલ પેલોડમાંથી `fullText` ઍન્કરને ફરી વાંચવામાં આવે છે, જેથી પછીના ચેઇન ગાર્ડરેલ્સ (PII અને ક્રેડેન્શિયલ માસ્કર્સ, પ્રાથમિકતાઓ 10/95) વર્ણન ટેક્સ્ટને તે જ સ્થાને ફરી લખે અને સિસ્ટમ-પ્રોમ્પ્ટ/હૅન્ડઑફ/મેમરી ઇન્જેક્શન મેસેજ ઍરેને ફરી આકાર આપે તે પછી પણ મેળ સફળ રહે છે. મોડલને અપસ્ટ્રીમ મોકલાતી બૉડી બદલાતી નથી. અવલોકિત વિનંતી કોઈ ટકાઉ Memory પણ ભરતી નથી (વિનંતી અને પ્રતિસાદ, બંનેમાંથી થતું એક્સટ્રેક્શન છોડવામાં આવે છે), જેથી મોડલનો પોતાનો જવાબ ટ્રાન્સક્રિપ્ટ ટેક્સ્ટને Memoryમાં ફરી પ્રતિધ્વનિત કરી ન શકે.

**કાચા વિડિયો ફીલ્ડ્સ (#12430).** જ્યારે બ્રિજ સક્ષમ હોય અને નેટિવ વિડિયો સપોર્ટ અજ્ઞાત અથવા ગેરહાજર હોય, ત્યારે વ્યાખ્યાયિત `transcript`/`audioTranscript` ફીલ્ડ્સ પણ `videoBridgeObserved` સક્રિય કરે છે, વર્ણન નિષ્ફળ થયા પછી અથવા `maxVideos` મર્યાદા લાગુ થયા પછી પણ. `null` અને ખાલી સ્ટ્રિંગ્સ ગણાય છે; ગેરહાજર ફીલ્ડ્સ અને નોન-વિડિયો મેટાડેટા ગણાતા નથી. જાળવી રાખવામાં આવેલી નકલોમાં આ ફીલ્ડ્સને રીડેક્ટ કરવામાં આવે છે અથવા વિનંતીને છોડી દેવામાં આવે છે, અને કૅશ/Memoryને બાયપાસ કરવામાં આવે છે.

આ ફૉલબૅક પાથ્સ પર, માન્ય કૉલર ક્યૂઝ બિનપ્રમાણભૂત પ્રોવાઇડર ફીલ્ડ્સને બદલે સમર્થિત `text`/`input_text` ભાગો બને છે. વિનંતીમાં આપવામાં આવેલા બંને ટ્રૅક્સ અવિશ્વસનીય `client` અવલોકનો તરીકે જ રહે છે, સાથે સ્પષ્ટ ચેતવણી હોય છે કે વિડિયોનું વર્ણન કરવામાં આવ્યું નહોતું અને ટાઇમસ્ટૅમ્પ્સને મીડિયા સામે ચકાસવામાં આવ્યા નહોતા. હાલના 256-ક્યૂ/64-KiB કુલ અને પ્રતિ-ક્યૂ બજેટ્સ બંને ટ્રૅક્સ પર સંયુક્ત રીતે લાગુ પડે છે; ટાઇમસ્ટૅમ્પ્સ બ્રોકરની 600-સેકન્ડની મહત્તમ મર્યાદા અને આપવામાં આવેલી કોઈપણ ફોકસ વિન્ડોમાં બંધબેસતા હોવા જોઈએ. અમાન્ય ટ્રૅક્સને કાઢી નાખવામાં આવે છે, મનસ્વી ટેક્સ્ટ તરીકે ફૉર્વર્ડ કરવામાં આવતા નથી; તેમનું સંયુક્ત બજેટ વટાવાતું ન હોય તો માન્ય સહોદર ટ્રૅકનો હજુ પણ ઉપયોગ થઈ શકે છે. Null/ખાલી ફીલ્ડ્સ કોઈ ટેક્સ્ટ ઉમેરતા નથી. આ ફૉલબૅક દ્વારા કોઈ મીડિયા ફેચ અથવા ટ્રાન્સક્રિપ્શન ઉમેરાતું નથી. ટ્રાન્સક્રિપ્ટ એક્સટેન્શન ફીલ્ડ્સને ફૉલબૅક વિડિયો કૅરિયર અને તેના `video_url`/`source` ઑબ્જેક્ટ્સમાંથી દૂર કરવામાં આવે છે. OpenAI વાયર અલાઉલિસ્ટ કડક રહે છે; અજ્ઞાત-નેટિવ વિડિયો કૅરિયર્સ ઉપલબ્ધ રહે છે અને જાણીતા માત્ર-ટેક્સ્ટ લક્ષ્યો સુરક્ષિત માર્કર્સ જાળવે છે. સંરચિત રીડેક્શન છાયાઓ ઉમેરાયેલા ટ્રાન્સક્રિપ્ટ ટેક્સ્ટનું રક્ષણ કરે છે, જ્યારે કૉલરની માલિકીની મૂળ વિનંતી યથાવત રહે છે. નેટિવ સપોર્ટ ધરાવતા લક્ષ્યો અને અક્ષમ કરેલા બ્રિજ તેમનું હાલનું બાયપાસ વર્તન જાળવે છે.

વધારાની જાળવી રાખવામાં આવેલી નકલો એ જ અવલોકિત-વિનંતી સિગ્નલનો ઉપયોગ કરે છે. ગાર્ડરેલ પહેલાંનો કાચો ક્લાયન્ટ-વિનંતી સ્નૅપશૉટ, ઇન-મેમરી બાકી વિનંતી અને વહેલી તકે નકારાયેલી વિનંતીનો લૉગ વિડિયો ભાગોમાંના ટ્રાન્સક્રિપ્ટ ફીલ્ડ્સને સંરચનાત્મક રીતે બદલે છે; પાઇપલાઇન તબક્કાઓ અને કૉન્ટેક્સ્ટ હૅન્ડઑફ દ્વારા બનાવવામાં આવેલા સ્ટ્રિંગ પ્રોમ્પ્ટ્સને જાળવી રાખવામાં આવેલી વિનંતી-બૉડીના સિંક પર રીડેક્ટ કરવામાં આવે છે. જાળવી રાખવામાં આવેલ `video_content_removed` માર્કર `previous_response_id` ચાલુ રાખવાની પ્રક્રિયાને ઇરાદાપૂર્વક કાઢી નાખવામાં આવેલા ટેક્સ્ટનું પુનઃનિર્માણ કરવાને બદલે સુરક્ષિત રીતે નિષ્ફળ બનાવે છે. જો અવલોકિત વિનંતી લૉગિંગ પહેલાં તેની પ્રતિ-ભાગ રીડેક્શન છાયા ગુમાવે, અથવા પછીના વિનંતી પરિવર્તનો બાદ અનેક વિડિયો છાયાઓમાંથી એક પણ મેળ ખાવામાં નિષ્ફળ જાય, તો આંશિક રીતે રીડેક્ટ કરેલી ટ્રાન્સક્રિપ્ટ જાળવવાને બદલે જાળવી રાખવામાં આવેલી વિનંતી બૉડીને સંપૂર્ણપણે છોડી દેવામાં આવે છે.

અવલોકિત વિનંતી માટે, મોડલ પ્રતિસાદ સંરચિત ક્યૂ સીમા વિના ટ્રાન્સક્રિપ્ટના કોઈપણ ભાગને ટાંકી શકે છે. તેથી તેની જાળવી રાખવામાં આવેલી કૉલ-લૉગ `responseBody`ને ઓમિશન માર્કર વડે બદલવામાં આવે છે; વિગતવાર પાઇપલાઇન આર્ટિફૅક્ટ (જેમાં અપસ્ટ્રીમ/ક્લાયન્ટ બૉડીઝ અને સ્ટ્રીમ ચંક્સ સામેલ હોઈ શકે છે) જાળવવામાં આવતું નથી. સિમેન્ટિક, આઇડેમ્પોટન્સી અને રીઝનિંગ-રિપ્લે કૅશ તે વિનંતી માટે વાંચન અને લેખનને બાયપાસ કરે છે. પ્રોવાઇડર વિનંતી અને ક્લાયન્ટને દેખાતો પ્રતિસાદ યથાવત રહે છે. જ્યારે વિગતવાર આર્ટિફૅક્ટને છોડી દેવામાં આવે છે ત્યારે વહેલા keepalive બાઇટ્સને અસ્થાયી બફરમાંથી કાઢી નાખવામાં આવે છે. Kiroની વિકૃત EventStream ચેતવણી માત્ર પેલોડ બાઇટ ગણતરી જણાવે છે, તેની સામગ્રી અથવા JSON પાર્સરની કાચી ભૂલ ક્યારેય નહીં.
આવો દાવો કરવામાં આવતો નથી કે દરેક અસંબંધિત પ્રોવાઇડર/પ્લગઇન ડાયગ્નોસ્ટિકનું ઑડિટ કરવામાં આવ્યું છે; જાળવી રાખતા સિંક્સનું વ્યાપક સર્વેક્ષણ #11658માં ટ્રૅક કરવામાં આવે છે.

આંતરિક `/api/modality-bridge/video/drilldown` લાઇફસાઇકલ એક અલગ, લૂપબૅક/ટોકન-પ્રમાણિત કૅશ સબસ્ટ્રેટ છે. દરેક ઑપરેશન માટે એક કેનોનિકલ અપારદર્શક પ્રિન્સિપલ ID પણ જરૂરી છે. પ્રોડક્શન કૉલરને સક્ષમ કરવામાં આવે તે પહેલાં, તેણે પ્રમાણિત ટેનન્ટમાંથી તે ID મેળવવી આવશ્યક છે અને ક્લાયન્ટ દ્વારા પસંદ કરાયેલ મૂલ્યને ક્યારેય ફૉર્વર્ડ કરવું નહીં. કૅશ કીઝ તે પ્રિન્સિપલને કેનોનિકલ સેશન અને વિડિયો-રેફરન્સ IDs સાથે બાંધે છે, ફક્ત તેમની SHA-256માંથી મેળવેલી કીઝ સંગ્રહે છે અને વાંચન તથા કાઢી નાખવા બંનેને એ જ પ્રિન્સિપલ સુધી મર્યાદિત કરે છે. કૅશ દરેક એન્ટ્રીમાં વધુમાં વધુ 16 ડેરાઇવ કરેલી JPEG ફ્રેમ્સ સંગ્રહે છે, દસ મિનિટ પછી તેમને સમાપ્ત કરે છે અને મર્યાદિત `start`/`end` વાંચન અથવા સ્પષ્ટ સેશન ડિલીશનને સપોર્ટ કરે છે.

દરેક પ્રિન્સિપલ 16 એન્ટ્રીઝ અને 64 MiB કેનોનિકલ JPEG ડેટા સુધી મર્યાદિત છે. આ મર્યાદાઓ વૈશ્વિક 64-એન્ટ્રી/256 MiB મહત્તમ મર્યાદાથી સ્વતંત્ર છે: વૈશ્વિક LRU ઇવિક્શન પર વિચાર થાય તે પહેલાં પ્રિન્સિપલ ક્વોટાનું દબાણ ફક્ત તે પ્રિન્સિપલની સૌથી લાંબા સમયથી ઉપયોગમાં ન લેવાયેલી એન્ટ્રીઝને ઇવિક્ટ કરે છે. કૅશ પ્રવૃત્તિ વખતે સમાપ્ત થયેલી એન્ટ્રીઝને પ્રિન્સિપલ અને વૈશ્વિક, બંને હિસાબોમાંથી સાફ કરવામાં આવે છે, જ્યારે રદબાતલ અથવા માન્યતા નિષ્ફળતા આંશિક રિપ્લેસમેન્ટને કમિટ કરતી નથી.

Video ઓવરરાઇડ Vision સેટિંગને વારસામાં મેળવે છે; જો બંને ખાલી હોય, તો Vision
ઑટો-રાઉટર અસરકારક વિઝન-સક્ષમ મોડલ પસંદ કરે છે. સફળ કૅપ્શન્સ મૂળ ભાગને સ્થિર
`[Video description:` પ્રિફિક્સથી બદલે છે, જે ટેક્સ્ટને અવિશ્વસનીય મીડિયા-ઉદ્ભવિત
અવલોકન તરીકે પણ ચિહ્નિત કરે છે અને ડાઉનસ્ટ્રીમ મોડલ્સને મીડિયામાં મળેલી સૂચનાઓનું
પાલન ન કરવા કહે છે. ફ્રેમ-કૅપ્શન કૅશ કીમાં JPEG બાઇટ્સ, પ્રોમ્પ્ટ, ટાઇમસ્ટૅમ્પ અને
અસરકારક મોડલ સામેલ હોય છે; ફક્ત સફળ કૅપ્શન્સ જ કૅશ થાય છે. કૅશ એન્ટ્રીઓ ફૉલબૅક
મોડલ સહિત, વાસ્તવિક સફળ પ્રોડ્યુસર મોડલ જાળવી રાખે છે; અલગ-અલગ ફ્રેમ્સ અલગ
મોડલ્સ દ્વારા બનાવવામાં આવી હોય ત્યારે બ્રિજ `mixed` રિપોર્ટ કરે છે. કૅશ હિટ તેને
માગવામાં આવેલી રાઉટિંગ યોજના તરીકે ફરીથી લેબલ કરવાને બદલે તે પ્રોડ્યુસરની ઓળખનો
પુનઃઉપયોગ કરે છે. સમગ્ર-વિડિયો પરિણામ કૅશ આઉટપુટ બદલતા દરેક ઇનપુટ પર આધારિત
કી ધરાવે છે — પ્રોમ્પ્ટ, અસરકારક મોડલ, સેમ્પલિંગ નીતિ, ફ્રેમ ગણતરી, સિમેન્ટિક
વિશ્લેષણ મોડ, નોર્મલાઇઝ કરેલી ફોકસ હિન્ટની SHA-256 ફિંગરપ્રિન્ટ, ફોકસ વિન્ડો,
`transcript`, `audioTranscript` અને કૉન્ટેક્ટ-શીટ ફ્લૅગ — તેથી આમાંથી કોઈપણ
પરિમાણ બદલવાથી કૅશ મિસ થાય છે, જૂના પરિણામનો પુનઃઉપયોગ ક્યારેય થતો નથી.
વિઝ્યુઅલ ડિડુપ નીતિનું વર્ઝન, થ્રેશોલ્ડ અને સીમિત ઉમેદવાર-ફ્રેમ ગણતરી પણ
રિઝલ્ટ-કૅશ કી અને મેટાડેટામાં સ્પષ્ટ હોય છે; તેથી નીતિમાં ફેરફાર જૂના સમગ્ર-વિડિયો
વર્ણનનો પુનઃઉપયોગ કરી શકતો નથી. રિઝલ્ટ-કૅશ v4 મેટાડેટા મોડ અને ફિંગરપ્રિન્ટ
જાળવે છે, કાચો યુઝર ટાસ્ક ક્યારેય નહીં. ગાર્ડરેલ મેટાડેટા માગવામાં આવેલા અને
અસરકારક, બંને વિશ્લેષણ મોડ્સ રિપોર્ટ કરે છે; ઉપયોગી યુઝર ટેક્સ્ટ વિના માગવામાં આવેલ
`focused` મોડ અસરકારક રીતે `full` તરીકે રિપોર્ટ થાય છે.

ગાર્ડરેલ દરેક સપોર્ટેડ વિડિયો ભાગને એક્સ્ટ્રેક્ટ કરે છે, પરંતુ
`modalityBridgeVideoMaxVideos` કરતાં વધુનું વર્ણન કરતું નથી. જે ટાર્ગેટ માટે
`supportsVideo === false` હોવાનું સાબિત થયું હોય, તેમાં નિષ્ફળ અને મર્યાદાથી વધુ
વિડિયો સ્પષ્ટ સુરક્ષિત ટેક્સ્ટ માર્કર્સ બની જાય છે, જેથી કોઈ કાચો વિડિયો બાકી ન રહે.
જ્યારે ક્ષમતા અજ્ઞાત હોય, ત્યારે તે ભાગો તેમનો વિડિયો કૅરિયર જાળવી રાખે છે; કોઈપણ
ફૉલબૅક ટ્રાન્સક્રિપ્ટ ઉપરના સીમિત ટેક્સ્ટ રૂપાંતરણને અનુસરે છે. `supportsVideo === true`
ધરાવતા ટાર્ગેટ્સ બ્રિજને બાયપાસ કરે છે. ક્લાયન્ટ રિક્વેસ્ટનું અબોર્ટ સિગ્નલ ડાઉનલોડ,
બ્રોકર કતાર, સબપ્રોસેસ અને કૅપ્શન કૉલ્સમાં પ્રસરે છે; અબોર્ટ વિડિયો વચ્ચે પ્રક્રિયા
અટકાવે છે અને કાચા મીડિયા માટે ક્યારેય ફેલ-ઓપન થતું નથી.

રનટાઇમ સેટિંગ્સ DB-બૅક્ડ અને Zod-વૅલિડેટેડ છે:

| ----------------------------------- | ----------- | -------------------------------------------------------------------------------------------------- |

મર્યાદિત કરવામાં આવે છે; આ મર્યાદાથી ઉપરના નવા સેટિંગ્સ રાઇટ્સ નકારવામાં આવે છે.
`GET /api/modality-bridge/video/runtime` ઑથેન્ટિકેશન અથવા રનટાઇમ પ્રોબિંગ પહેલાં
વિશ્વસનીય સ્ટૅમ્પ્ડ લૂપબૅક લોકૅલિટી અને ત્યારબાદ મેનેજમેન્ટ ઑથની આવશ્યકતા રાખે છે.
રનટાઇમ અનુપલબ્ધ હોય ત્યારે તે ફક્ત `available`, સૅનિટાઇઝ કરેલા FFmpeg/ffprobe
વર્ઝન્સ અને નિશ્ચિત કારણ પરત કરે છે. આંતરિક એક્સ્ટ્રેક્શન એન્ડપૉઇન્ટ જાહેર અપલોડ
API નથી: કતાર સૅચ્યુરેશન `503` ઉપરાંત `Retry-After` પરત કરે છે, કૉલર ડિસ્કનેક્ટ
`499` પરત કરે છે અને નિશ્ચિત બ્રોકર ડેડલાઇન `504` પરત કરે છે. રૂપાંતરિત પ્રતિસાદો
Vision અથવા Audio સેગમેન્ટ્સને દૂર કર્યા વિના કેન્દ્રીય
`x-omniroute-modality-bridge` હેડરમાં
`video->text;model=<visionModel>;parts=<videos>` ઉમેરે છે.

### PII માસ્કર (`piiMasker.ts`)

**બંને** તબક્કાઓ પર ચાલે છે.

- **`preCall`** પેલોડને ક્લોન કરે છે, `system`, `messages`, `input`, અને
  `prompt` (સાદી સ્ટ્રિંગ આઇટમ્સ સહિત) માંથી પસાર થાય છે અને સ્ટ્રિંગ
  `content`/`text` ફીલ્ડ્સ પર `processPII()` (`@/shared/utils/inputSanitizer`
  માંથી) લાગુ કરે છે. જ્યારે `PII_REDACTION_ENABLED=true` હોય, ત્યારે શોધાયેલી
  PII આઉટબાઉન્ડ પેલોડમાં ઢાંકી દેવામાં આવે છે. આ `INPUT_SANITIZER_MODE` થી
  સ્વતંત્ર છે (જે ફક્ત પ્રોમ્પ્ટ-ઇન્જેક્શન નીતિને નિયંત્રિત કરે છે). જ્યારે
  રિડૅક્શન બંધ હોય, ત્યારે કૉલ કન્ટેન્ટ ફરીથી લખ્યા વિના શોધની સંખ્યાઓ
  રેકોર્ડ કરે છે.
- **`postCall`** પ્રતિસાદને ડીપ-ક્લોન કરે છે, `sanitizePIIResponse()` ઉપરાંત
  Responses-API-આકાર માસ્કર (`maskResponsesOutput` — જે
  `output_text` અને `output[].content[].text` ને આવરી લે છે) ચલાવે છે. જો કોઈ
  રિડૅક્શન થાય, તો સંશોધિત પ્રતિસાદ મૂળ પ્રતિસાદને બદલે છે.

ગાર્ડરેલ ક્યારેય બ્લૉક કરતું નથી; તે ફક્ત ઍનોટેટ (`meta.detections`,
`meta.redacted`) કરે છે અથવા ફરીથી લખે છે.

#### પ્રકાર-દીઠ પસંદગી, કસ્ટમ પેટર્ન્સ અને શોધ કાઉન્ટર્સ

**ડૅશબોર્ડ → સેટિંગ્સ → સુરક્ષા → PII માસ્કિંગ** દ્વારા _શું_ માસ્ક કરવું તે
પસંદ થાય છે. તે માસ્કિંગ ચાલુ કરતું નથી: તેના માટે હજુ પણ
`PII_REDACTION_ENABLED` (વિનંતી) અને `PII_RESPONSE_SANITIZATION` (પ્રતિસાદ +
SSE) જવાબદાર છે અને બન્ને ડિફૉલ્ટ રૂપે બંધ હોય છે.

- **પ્રકાર-દીઠ પસંદગી** — બિલ્ટ-ઇન ids
  `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`) માં સૂચિબદ્ધ છે.
  સેટ ન કરેલું હોય તો તેનો અર્થ દરેક પ્રકાર થાય છે (આ સેટિંગ અસ્તિત્વમાં આવ્યું
  તે પહેલાંનું વર્તન). વિનંતી એન્જિનનું `ssn_us` પેટર્ન `ssn` સાથે મૅપ થાય છે.
  ટેમ્પ્લેટ્સ (ન્યૂનતમ, માનક, નાણાકીય, બ્રાઝિલિયન, USA, પૂર્ણ) ફક્ત UI માં
  ચેકબૉક્સ ભરે છે.
- **કસ્ટમ પેટર્ન્સ** — વધુમાં વધુ 20 regex અથવા વાઇલ્ડકાર્ડ પેટર્ન્સ (`*` =
  વધુમાં વધુ 64 નૉન-વ્હાઇટસ્પેસ અક્ષરો, `?` = એક). મૅચ
  `[CUSTOM_REDACTED]` બને છે. દરેક પેટર્ન `compilePiiCustomPattern()`
  (`src/shared/utils/piiCustomPatterns.ts`) માંથી પસાર થાય છે: વધુમાં વધુ 500
  અક્ષરો, ફ્લૅગ્સ માત્ર `g i m s u` સુધી મર્યાદિત, કમ્પાઇલ થવું આવશ્યક,
  `safe-regex` (વિનાશકારી બૅકટ્રૅકિંગ) પાસ કરવું આવશ્યક અને ખાલી સ્ટ્રિંગ
  અથવા રિડૅક્શન પ્લેસહોલ્ડર સાથે મૅચ ન થવું જોઈએ. નિષ્ફળ જતું પેટર્ન સેવ
  કરતી વખતે અને પરીક્ષણ કરતી વખતે નકારવામાં આવે છે, અને નિષ્ફળ જતી સંગ્રહિત
  પંક્તિ કમ્પાઇલ થવાને બદલે રનટાઇમ પર છોડી દેવામાં આવે છે. કસ્ટમ પેટર્ન્સ
  ફક્ત માસ્કિંગ ચાલુ હોય ત્યારે ચાલે છે.
- **શોધ કાઉન્ટર્સ** — પ્રકાર-દીઠ સંખ્યાઓ (મૅચ થયેલા મૂલ્યો ક્યારેય નહીં),
  મેમરીમાં રાખવામાં આવે છે અને રિસ્ટાર્ટ પર રીસેટ થાય છે
  (`src/lib/pii/piiDetectionStats.ts`). તે ફક્ત માસ્કિંગ ચાલુ હોય ત્યારે જ
  વધે છે.

સેટિંગ્સ `key_value` ટેબલમાં રહે છે (નેમસ્પેસ `pii_settings`,
`src/lib/db/piiSettings.ts`) અને 1 s કૅશ મારફતે વાંચવામાં આવે છે. API:

| પદ્ધતિ | પાથ                      | હેતુ                                                                    |
| ------ | ------------------------ | ----------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | ફ્લૅગ સ્થિતિ, `enabledTypes`, `customPatterns`, શોધ કાઉન્ટર્સ           |
| `PUT`  | `/api/settings/pii`      | `enabledTypes` (`null` = બધા) અને/અથવા `customPatterns` ને બદલો         |
| `POST` | `/api/settings/pii/test` | વધુમાં વધુ 8 KB ના નમૂના સામે એક પેટર્નનું ડ્રાય-રન; કંઈ સંગ્રહાતું નથી |

ત્રણેય માટે મેનેજમેન્ટ ઑથ જરૂરી છે અને બૉડીને Zod વડે માન્ય કરે છે
(`src/shared/validation/schemas/piiSettings.ts`).

### પ્રોમ્પ્ટ ઇન્જેક્શન (`promptInjection.ts`)

વપરાશકર્તા દ્વારા આપવામાં આવેલા કન્ટેન્ટમાં વિરોધાત્મક રચનાઓ શોધે છે અને
કન્ફિગર કરેલી નીતિ લાગુ કરે છે. વર્તન એન્વાયર્નમેન્ટ વેરિએબલ્સ અને
કન્સ્ટ્રક્ટર વિકલ્પો દ્વારા સંચાલિત થાય છે:

| સેટિંગ          | એન્વાયરમેન્ટ વેરિએબલ                                                                                  | ડિફૉલ્ટ | અસર                                                                                                                                                                                                             |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| સક્ષમ           | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | જ્યારે `false` હોય, ત્યારે ગાર્ડરેલ શૉર્ટ-સર્કિટ થાય છે.                                                                                                                                                        |
| મોડ             | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | ઇન્જેક્શન નીતિ: `block`, `warn`, અથવા `log`. (`redact` બૅકવર્ડ કમ્પેટિબિલિટી માટે સ્વીકારાય છે પરંતુ ઇન્જેક્શન ટેક્સ્ટને દૂર કરતું **નથી**; વિનંતી PII રિરાઇટ `PII_REDACTION_ENABLED` દ્વારા નિયંત્રિત થાય છે.) |
| બ્લૉક થ્રેશોલ્ડ | `blockThreshold` વિકલ્પ / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ઉપનામ `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | બ્લૉક કરવા માટે જરૂરી ન્યૂનતમ ગંભીરતા. ડિફૉલ્ટ પર મધ્યમ માત્ર અવલોકન માટે છે.                                                                                                                                   |

**મોડ અગ્રતા** (`getMode`): કૉલર `options.mode` →
`INJECTION_GUARD_MODE` **DB ફીચર-ફ્લૅગ ઓવરરાઇડ** (ડૅશબોર્ડ → સેટિંગ્સ →
ફીચર ફ્લૅગ્સ) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. તેથી ડૅશબોર્ડ ઓવરરાઇડ env vars કરતાં પ્રાધાન્ય મેળવે છે, જેથી
ફીચર ફ્લૅગ્સ UI ચાલતા ગાર્ડને લાઇવ નિયંત્રિત કરે છે (રિસ્ટાર્ટ વિના). DB રીડ
ફેલ-સેફ છે: જો તેમાં ભૂલ થાય, તો ગાર્ડ env-આધારિત વર્તન પર પાછું ફરે છે, અને
જ્યારે કોઈ ઓવરરાઇડ સેટ ન હોય ત્યારે વર્તન માત્ર-env રિઝોલ્યુશન જેવું જ હોય છે.

શોધના સ્રોતો:

1. `@/shared/utils/inputSanitizer` માંથી `sanitizeRequest()` (પાઇપલાઇનમાં અન્યત્ર
   વપરાતો શેર કરેલો ડિટેક્ટર સેટ).
2. બિલ્ટ-ઇન `DEFAULT_GUARD_PATTERNS` (હાલમાં `system_override_inline` અને
   `markdown_system_block`, બન્ને `high` ગંભીરતાવાળા).
3. કન્સ્ટ્રક્ટર વિકલ્પો દ્વારા પાસ કરાયેલા વૈકલ્પિક `customPatterns` (સ્ટ્રિંગ્સ,
   regex, અથવા `{ name, pattern, severity }` રેકોર્ડ્સ).

જ્યારે `mode === "block"` **અને** ઓછામાં ઓછું એક ડિટેક્શન ગંભીરતાની
થ્રેશોલ્ડને પૂર્ણ કરે છે, ત્યારે `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` પરત કરે છે. `warn`/`log` મોડ્સમાં ગાર્ડરેલ લૉગ કરે છે પરંતુ
કૉલને મંજૂરી આપે છે. શેર કરેલ હેલ્પર `evaluatePromptInjection()` પણ એવા
કૉલર્સ માટે એક્સપોર્ટ કરવામાં આવે છે જેમને રજિસ્ટ્રીમાંથી પસાર થયા વિના પ્રોમ્પ્ટ્સનું મૂલ્યાંકન કરવાની જરૂર હોય.

**સ્કૅન મર્યાદા (v3.8.20):** ડિટેક્ટર જોડાયેલા પ્રોમ્પ્ટ ટેક્સ્ટના માત્ર **પ્રથમ 16 KB**નું
નિરીક્ષણ કરે છે — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 બાઇટ્સ)
`src/shared/utils/inputSanitizer.ts`માં. પેટર્ન લૂપ ચલાવતાં પહેલાં `detectInjection()` અને
`evaluatePromptInjection()` બંને `slice(0, MAX_INJECTION_SCAN_BYTES)` કરે છે.
ઇન્જેક્શન ડાયરેક્ટિવ્સ ઇનપુટની શરૂઆતની નજીક હોય છે, તેથી આ બહુ-સો-KB પેલોડ્સ પર
ડિટેક્શનને નબળું પાડ્યા વિના regex CPU/GCને મર્યાદિત કરે છે (જુઓ
#3932, #4041).

### ક્રેડેન્શિયલ માસ્કર (`credentialMasker.ts`)

ડિફૉલ્ટ ચેઇનમાં સૌથી છેલ્લે (પ્રાથમિકતા `95`), **બંને** તબક્કાઓ પર ચાલે છે. આઉટબાઉન્ડ પેલોડ
(મેસેજ કન્ટેન્ટ, ટૂલ-કૉલ આર્ગ્યુમેન્ટ્સ, ટૂલ પરિણામો) **અને** પ્રોવાઇડરના પ્રતિસાદમાંથી
જાણીતા API-કી / સિક્રેટ-ટોકન પેટર્ન્સને રિડેક્ટ કરે છે, જેથી પ્રોમ્પ્ટમાં પેસ્ટ કરાયેલ
ક્રેડેન્શિયલ (અથવા ટૂલ પરિણામ દ્વારા પાછું દર્શાવાયેલું) અપસ્ટ્રીમ પ્રોવાઇડર અથવા ક્લાયન્ટને
પાછું લીક ન થાય.

- **માત્ર ઑપ્ટ-ઇન**, PII રિડૅક્શન જેવો જ નિયમ (હાર્ડ રૂલ #20ની નજીક):
  `settings.credentialRedactionEnabled === true` **અથવા**
  `CREDENTIAL_REDACTION_ENABLED=true` ન હોય ત્યાં સુધી નિષ્ક્રિય. તે બંધ હોય ત્યારે, ગાર્ડરેલ
  કોઈ કાર્યવાહી કરતું નથી — તે ક્યારેય બ્લૉક કરતું નથી અને ક્યારેય ફરી લખતું નથી.
- `redactCredentials()` સમગ્ર પેલોડ/પ્રતિસાદ ટ્રીમાં ટ્રાવર્સ કરે છે (`walkValue()`,
  પ્રોટોટાઇપ-પોલ્યુશનથી સુરક્ષિત, `WeakSet` દ્વારા સાઇકલથી સુરક્ષિત) અને મેળ ખાતા ભાગોને
  `[REDACTED:<type>]` પ્લેસહોલ્ડરથી બદલે છે, માત્ર ખરેખર બદલાયેલી બ્રાન્ચિસને જ ક્લોન કરે છે.
- `CREDENTIAL_PATTERNS` LLM પ્રોવાઇડર કીઝ (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ટોકન્સ (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), પેમેન્ટ કીઝ (Stripe, Square), ક્લાઉડ
  કીઝ (AWS access key, Twilio, SendGrid, Mailgun), પ્રાઇવેટ કીઝ / JWTs,
  ક્રેડેન્શિયલ ધરાવતી કનેક્શન સ્ટ્રિંગ્સ (`mongodb://user:pass@...`, વગેરે), અને
  સામાન્ય `Authorization`/`x-api-key`/`api-key`/`apikey` હેડર-વેલ્યૂ
  પેટર્નને આવરે છે. હેડર-આકારની કીઝ (`authorization`, `x-api-key`, `api-key`,
  `apikey`)ને સામાન્ય ટેક્સ્ટ regex દ્વારા નહીં, પરંતુ રચનાત્મક રીતે રિડેક્ટ કરવામાં આવે છે
  (માત્ર વેલ્યૂ; `Bearer `/`Basic ` જેવા સ્કીમ પ્રિફિક્સ જાળવવામાં આવે છે).
- ગાર્ડરેલ ક્યારેય બ્લૉક કરતું નથી; તે માત્ર ફરી લખે છે (`modifiedPayload` /
  `modifiedResponse`) અને ઍનોટેટ કરે છે (`meta.credentialsRedacted`, `meta.count`).

રીગ્રેશન ગાર્ડ: `tests/unit/credential-masker-guardrail.test.ts`.

## આધારભૂત કરાર (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true સાંકળને તરત અટકાવે છે
  message?: string; // અવરોધિત કરતી વખતે દર્શાવવામાં આવે છે
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // વિનંતીને ફરી લખવા માટે preCall દ્વારા પરત કરવામાં આવે છે
  modifiedResponse?: TValue; // પ્રતિસાદને ફરી લખવા માટે postCall દ્વારા પરત કરવામાં આવે છે
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ગાર્ડરેલ `void`, `{}`, અથવા
`{ block: false }` પરત કરીને "કોઈ ફેરફાર નહીં" દર્શાવે છે. `modifiedPayload`/`modifiedResponse` પરત કરવાથી
ડાઉનસ્ટ્રીમ ગાર્ડરેલ્સ માટે સાંકળમાંથી પસાર થતું મૂલ્ય બદલાઈ જાય છે.
`signal?: AbortSignal` કોલ કરનારના જીવનચક્રને ગાર્ડરેલ્સ સુધી પહોંચાડે છે. વિનંતીનું નિરસ્તીકરણ ઇરાદાપૂર્વકનો fail-open અપવાદ છે: મીડિયા બ્રિજ કામ અટકાવે છે અને તેને સપોર્ટ ન કરતા હોવાનું જાણીતા લક્ષ્ય પર કાચું મીડિયા પુનઃસ્થાપિત કર્યા વિના સફાઈ કરે છે.

## રજિસ્ટ્રી (`registry.ts`)

સિંગલટન `guardrailRegistry` નીચેની સુવિધાઓ પ્રદાન કરે છે:

- `register(guardrail)` — ગાર્ડરેલ ઉમેરે છે (અથવા સામાન્યકૃત નામ દ્વારા બદલે છે) અને
  ચઢતા `priority` પ્રમાણે ફરીથી ગોઠવે છે.
- `clear()` / `list()` — વહીવટી સહાયકો.
- `runPreCallHooks(payload, context)` — સક્રિય ગાર્ડરેલ્સ પર પુનરાવર્તન કરે છે, પેલોડને
  `modifiedPayload` મારફતે આગળ ધપાવે છે અને પ્રથમ `block: true` પર અટકે છે.
- `runPostCallHooks(response, context)` — પ્રતિસાદની બાજુએ સમાન પ્રવાહ.
- `resetGuardrailsForTests({ registerDefaults })` — સ્થિતિ સાફ કરે છે અને સ્વચ્છ પરીક્ષણ અલગીકરણ માટે વૈકલ્પિક રીતે
  ડિફૉલ્ટ્સને ફરીથી નોંધે છે.

બંને રનર્સ `{ blocked, payload|response, results, guardrail?, message? }`
પરત કરે છે, જ્યાં `results` એ `GuardrailExecutionResult` રેકોર્ડ્સની ઍરે છે, જેમાં
દરેક ગાર્ડરેલ માટેના `blocked`, `skipped`, `modified`, `error`, અને `meta` ફીલ્ડ્સ સામેલ છે,
જે ટ્રેસિંગ માટે ઉપયોગી છે.

### દરેક વિનંતી માટે ગાર્ડરેલ્સ અક્ષમ કરવા

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` વર્તમાન
વિનંતી માટે અવગણવામાં આવવા જોઈએ તેવા ગાર્ડરેલ નામોની ડુપ્લિકેટ-રહિત સૂચિ એકત્રિત કરે છે.
પાંચ ચેનલો છે, જે આ ક્રમમાં વાંચવામાં આવે છે અને એક સૂચિમાં મર્જ કરવામાં આવે છે
(ડુપ્લિકેટ દૂર કરતી વખતે પ્રથમ આવૃત્તિ જાળવવામાં આવે છે):

1. `apiKeyInfo.disabledGuardrails`
2. વિનંતી બોડીનું `disabledGuardrails` (ટોચના સ્તરે)
3. વિનંતી બોડીનું `metadata.disabledGuardrails` (ફક્ત જ્યારે `metadata` ઑબ્જેક્ટ હોય)
4. હેડર `x-omniroute-disabled-guardrails`
5. લેગસી હેડર `x-disabled-guardrails`

બંને હેડર્સ સહિત તમામ પાંચ ચેનલો મર્જ કરવામાં આવે છે:
`x-omniroute-disabled-guardrails` અને `x-disabled-guardrails` બંને મોકલવાથી
તેમની સૂચિઓના યુનિયનને અવગણવામાં આવે છે, અને ખાલી આધુનિક હેડર હવે લેગસી હેડરને
છુપાવતું નથી
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), જેમાં
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805) દ્વારા સુધારો કરાયો).

મૂલ્યો સ્ટ્રિંગ્સની ઍરે અથવા અલ્પવિરામથી અલગ કરેલી સ્ટ્રિંગ હોઈ શકે છે; નામોને ટ્રિમ
કરીને લોઅરકેસ kebab-caseમાં સામાન્યકૃત કરવામાં આવે છે (`pii_masker` → `pii-masker`), અને ખાલી
એન્ટ્રીઓ દૂર કરવામાં આવે છે. પરિણામ `context.disabledGuardrails` મારફતે
રજિસ્ટ્રીને આપવામાં આવે છે, જે મેળ ખાતા ગાર્ડરેલ્સને અવગણે છે (`results`માં `skipped: true`).

અક્ષમ કરવાની સૂચિ ફક્ત **રજિસ્ટ્રી**ને અસર કરે છે. પ્રોમ્પ્ટ-ઇન્જેક્શન `block` મોડ
ફરજિયાત સીમા છે: ઇન્જેક્શન-ગાર્ડ મિડલવેર
(`src/middleware/promptInjectionGuard.ts`) કોલર દ્વારા નિયંત્રિત કરી શકાય તેવી કોઈપણ અક્ષમ સૂચિ વિના
`evaluatePromptInjection()`ને કોલ કરે છે (તે અગાઉ કરતો નિષ્ક્રિય
`resolveDisabledGuardrails({ body })` કોલ
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934)માં દૂર કરવામાં આવ્યો હતો), તેથી
`prompt-injection`ને અક્ષમ કરતી વિનંતી પણ `block` મોડમાં નકારવામાં આવે છે. આ
ઇરાદાપૂર્વક છે. અક્ષમ કરવાની ચેનલો કોલર દ્વારા નિયંત્રિત હોય છે (વિનંતી બોડી,
મેટાડેટા, હેડર્સ), અને ઑપરેટરે સેટ કરેલું સુરક્ષા નિયંત્રણ કોલર બંધ કરી શકે તેમ ન હોવું જોઈએ
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).
[#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412)નું હેડર
યુનિયન ફક્ત કયા રજિસ્ટ્રી ગાર્ડરેલ્સ અવગણવામાં આવે છે તે બદલે છે; તે ક્લાયન્ટને
મિડલવેર બાયપાસ કરવાની મંજૂરી આપતું નથી. ફરજિયાત પ્રતિ-કી અને પ્રતિ-ગ્રૂપ ગાર્ડરેલ નીતિઓ
v4 RFC [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417)માં ટ્રૅક કરવામાં આવે છે.
[કવરેજ અને મર્યાદાઓ](#coverage-and-limits) જુઓ.

## અમલીકરણ ક્રમ

`src/sse/handlers/chat.ts` અને
`open-sse/handlers/chatCore.ts`માંથી પસાર થતી દરેક વિનંતી માટે ([કવરેજ અને મર્યાદાઓ](#coverage-and-limits) હેઠળ સૂચિબદ્ધ ચેટ-ફેમિલી રૂટ્સ):

1. `resolveDisabledGuardrails(...)` API કી, બોડી અને હેડર્સમાંથી સ્કિપ સૂચિ બનાવે છે.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` વધતા પ્રાથમિકતા ક્રમમાં ગાર્ડરેલ્સ ચલાવે છે:
   - અક્ષમ કરેલા ગાર્ડરેલ્સ `skipped` તરીકે નોંધાય છે.
   - દરેક ગાર્ડરેલનું `preCall`, `modifiedPayload` મારફતે પેલોડ ફરીથી લખી શકે છે.
   - પ્રથમ `block: true` ચેઇનને તરત જ અટકાવે છે અને હેન્ડલર ગાર્ડરેલ અસ્વીકાર પ્રતિસાદ પરત કરે છે.
3. (સંભવિત રીતે ફરીથી લખાયેલું) પેલોડ કોમ્બો રાઉટિંગ અને અપસ્ટ્રીમ ડિસ્પેચમાં જાય છે.
4. **માત્ર નોન-સ્ટ્રીમિંગ:** પ્રતિસાદ તૈયાર થયા પછી,
   `guardrailRegistry.runPostCallHooks(...)` પ્રતિસાદ પર એ જ ચેઇન ચલાવે છે. અહીં `block: true` અપસ્ટ્રીમ પ્રતિસાદને કાઢી નાખે છે અને HTTP 400 પરત કરે છે. સ્ટ્રીમ કરાયેલા પ્રતિસાદો આ પગલું સંપૂર્ણપણે છોડી દે છે.

અપવાદ ફેંકતા ગાર્ડરેલ્સ `error: <message>` સાથે નોંધાય છે અને
`logger.warn` મારફતે લૉગ થાય છે, પરંતુ ચેઇન ચાલુ રહે છે — આ ડિઝાઇન મુજબ ફેઇલ-ઓપન વર્તન છે.

## કવરેજ અને મર્યાદાઓ

ગાર્ડરેલ રજિસ્ટ્રી માત્ર ચેટ પાઇપલાઇનમાં જોડાયેલી છે. આ મર્યાદાઓ
`tests/unit/guardrail-pipeline-wiring-characterization.test.ts` અને
`tests/unit/guardrail-pipeline-characterization.test.ts` દ્વારા નિશ્ચિત કરવામાં આવી છે; વર્તન બદલાય ત્યારે તે ટેસ્ટ્સને વિચારપૂર્વક અપડેટ કરો.

### હુક્સ ક્યાં ચાલે છે

| હુક / નિયંત્રણ                  | ક્યાં ચાલે છે                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `runPreCallHooks`               | `handleChat` (`src/sse/handlers/chat.ts`) દ્વારા હેન્ડલ થતી વિનંતીઓ: `/v1/chat/completions`, `/v1/completions`, `/v1/messages`, `/v1/responses` (અને `/v1/responses/*`), `/v1/relay/chat/completions`, `/v1/providers/{provider}/chat/completions`, `/v1/api/chat`, `/v1/antigravity`, `/v1beta/models/*` અને Telegram ચેટ પ્રોક્સી. ઉપરાંત, ડૅશબોર્ડ ટેસ્ટ એન્ડપોઇન્ટ `/api/guardrails/test`. પ્રી-કૉલ બ્લોક HTTP 400 પરત કરે છે. |
| `runPostCallHooks`              | માત્ર **નોન-સ્ટ્રીમિંગ** ચેટ પ્રતિસાદો (`open-sse/handlers/chatCore/nonStreamingResponse.ts`). સ્ટ્રીમ કરાયેલા પ્રતિસાદો ક્યારેય ત્યાં પહોંચતા નથી.                                                                                                                                                                                                                                                                                |
| સ્ટ્રીમિંગ PII                  | `createPiiSseTransform` (`src/lib/streamingPiiTransform.ts`), જેને `PII_RESPONSE_SANITIZATION` ચાલુ હોય ત્યારે `streamingPipeline.ts`માં પાઇપ કરવામાં આવે છે. તે ગાર્ડરેલ નથી, તેથી અક્ષમ કરવાની ચેનલો તેને અસર કરતી નથી.                                                                                                                                                                                                          |
| ઇન્જેક્શન-ગાર્ડ મિડલવેર (લેગસી) | પ્રોમ્પ્ટ ધરાવતો દરેક `/v1` રૂટ, જેમાં ચેટ-ફેમિલી પણ સામેલ છે ([રૂટ કવરેજ](#injection-guard-route-coverage--red-team-phase-8--block-d) જુઓ). માત્ર પ્રોમ્પ્ટ ઇન્જેક્શન.                                                                                                                                                                                                                                                            |

### શું આવરી લેવાયું નથી

- **મીડિયા, એમ્બેડિંગ્સ અને ડેટા રૂટ્સ** (`/v1/images/*`, `/v1/embeddings`,
  `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`,
  `/v1/rerank`, `/v1/search`, `/v1/moderations`) ક્યારેય રજિસ્ટ્રી સુધી પહોંચતા નથી. ત્યાં કોઈ
  PII માસ્કિંગ, ક્રેડેન્શિયલ માસ્કિંગ અથવા મોડાલિટી બ્રિજ ચાલતું નથી. તેમની એકમાત્ર
  તપાસ લેગસી ઇન્જેક્શન-ગાર્ડ મિડલવેર છે.
- **સ્ટ્રીમ કરાયેલા પ્રતિસાદો** પર કોઈ પોસ્ટ-કૉલ ગાર્ડરેલ લાગુ પડતા નથી: કોઈ `pii-masker` અથવા
  `credential-masker` પોસ્ટ-કૉલ નથી અને કોઈ પોસ્ટ-કૉલ બ્લોક પણ નથી. માત્ર સ્ટ્રીમિંગ PII
  ટ્રાન્સફોર્મ લાગુ પડે છે (`PII_RESPONSE_SANITIZATION` ચાલુ હોય ત્યારે). સ્ટ્રીમ કરાયેલા પ્રતિસાદમાં
  પાછું મોકલાયેલું ક્રેડેન્શિયલ રિડેક્ટ થતું નથી.
- **અક્ષમ કરવાની ચેનલો વિરુદ્ધ મિડલવેર (ડિઝાઇન મુજબ):** મિડલવેર
  કૉલર દ્વારા નિયંત્રિત કોઈપણ અક્ષમ સૂચિ પાસ કર્યા વિના, `evaluatePromptInjection()`ને પોતાના કૉલ વડે
  પ્રોમ્પ્ટ ઇન્જેક્શનનું મૂલ્યાંકન કરે છે. `block` મોડ ફરજિયાત
  સીમા છે, જેને કૉલર દ્વારા નિયંત્રિત અક્ષમતાઓ બાયપાસ કરી શકતી નથી, જેમાં ચેટ-ફેમિલી રૂટ્સ પણ સામેલ છે
  ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). `prompt-injection`ને અક્ષમ કરવાથી
  માત્ર રજિસ્ટ્રી ગાર્ડરેલ સ્કિપ થાય છે.

### પોસ્ટ-કૉલ પહેલાં પ્રતિસાદને શું જુએ છે

નોન-સ્ટ્રીમિંગ પાથ પર ક્રમ આ છે: મેમરી એક્સટ્રેક્શન → બિલ્ટ-ઇન ટૂલ
એક્ઝિક્યુશન → પોસ્ટ-કૉલ ગાર્ડરેલ્સ → પોસ્ટ-કૉલ બ્લોક એક્ઝિટ → સિમેન્ટિક-કૅશ સ્ટોર.

- **મેમરી એક્સટ્રેક્શન** અને **ટૂલ એક્ઝિક્યુશન** પ્રતિસાદને પોસ્ટ-કૉલ
  ગાર્ડરેલ્સ દ્વારા ફરી લખવામાં કે બ્લૉક કરવામાં આવે તે પહેલાં જુએ છે.
  [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401) પછીથી, જ્યારે
  `PII_RESPONSE_SANITIZATION` ચાલુ હોય ત્યારે મેમરી એક્ઝટ્રેક્શન કાઢવામાં આવેલા
  ટેક્સ્ટને `sanitizePII` મારફતે પસાર કરે છે (સ્ટ્રીમિંગ અને નૉન-સ્ટ્રીમિંગ
  બંનેમાં), પરંતુ પોસ્ટ-કૉલ દ્વારા પછીથી બ્લૉક કરવામાં આવેલ પ્રતિસાદ હજુ પણ
  મેમરી અને ટૂલ્સને આપવામાં આવ્યો હોય છે.
- **સિમેન્ટિક કૅશ** પ્રતિસાદને પોસ્ટ-કૉલ પછી સંગ્રહિત કરે છે, તેથી તે ફરી લખાયેલો
  પ્રતિસાદ સંગ્રહિત કરે છે અને બ્લૉક કરાયેલ પ્રતિસાદ ક્યારેય કૅશ થતો નથી. કૅશ
  એન્ટ્રીઓ દરેક API કી પ્રમાણે કી કરવામાં આવે છે.

| વેરિએબલ                               | આના દ્વારા વપરાય છે        | અસર                                                                                                     |
| ------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | શોધ સંપૂર્ણપણે અક્ષમ કરવા માટે `false` સેટ કરો.                                                         |

સ્ટોર (`getSettings()`)માંથી રનટાઇમ રૂપરેખાંકન વાંચે છે. Visionની પ્રાથમિક કીઝ
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, અને
`modalityBridgeCacheMaxEntries` છે. લેગસી
`visionBridge*` કીઝ માત્ર દસ્તાવેજીકૃત એક-ચક્ર રીડ
ફૉલબૅક તરીકે સ્વીકારવામાં આવે છે; ડૅશબોર્ડ રાઇટ્સ પ્રાથમિક કીઝનો ઉપયોગ કરે છે. ડિફૉલ્ટ્સ અને ફૉલબૅક
રિઝૉલ્વર `src/shared/constants/modalityBridgeDefaults.ts`માં છે, જ્યારે લેગસી
કોન્સ્ટન્ટ્સ `src/shared/constants/visionBridgeDefaults.ts`માં જાળવી રાખવામાં આવ્યા છે.

Audio, `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,

કીઝ Modality Bridge સ્કીમા સાથે રજૂ કરવામાં આવી હતી.

Video, `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos`, અને
`modalityBridgeVideoTimeout` ઉપરાંત શેર કરેલા `modalityBridgeCache*` સેટિંગ્સનો ઉપયોગ કરે છે.
તે ડિફૉલ્ટ રૂપે અક્ષમ છે, કારણ કે FFmpeg/ffprobe વૈકલ્પિક ઑપરેશનલ
ડિપેન્ડન્સીઝ છે અને ફ્રેમ કૅપ્શનિંગ લેટન્સી તથા મોડેલ ખર્ચ વધારે છે.

## કસ્ટમ ગાર્ડરેલ્સ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

પગલાં:

1. `BaseGuardrail`ને વિસ્તૃત કરતી `src/lib/guardrails/myGuardrail.ts` બનાવો.
2. `preCall` અને/અથવા `postCall` અમલમાં મૂકો.
3. કાં તો ઇમ્પોર્ટ સમયે નોંધણી કરો (`registerDefaultGuardrails`માંથી પુશ કરો) અથવા
   રનટાઇમ પર `guardrailRegistry.register(...)` કૉલ કરો — રજિસ્ટ્રી સમાન નોર્મલાઇઝ્ડ નામ ધરાવતી
   કોઈપણ અગાઉની ગાર્ડરેલને બદલી નાખે છે.
4. `tests/unit/` હેઠળ ટેસ્ટ ઉમેરો (હાલનાં ઉદાહરણો:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## ટેસ્ટિંગ

જાણીતી સ્થિતિથી પ્રારંભ કરવા માટે ટેસ્ટ્સની વચ્ચે `resetGuardrailsForTests()`નો ઉપયોગ કરો.
ખાલી રજિસ્ટ્રીથી પ્રારંભ કરવા માટે `{ registerDefaults: false }` પાસ કરો અને
ફક્ત ટેસ્ટ હેઠળની ગાર્ડરેલ્સ નોંધાવો. Vision Bridge ડિપેન્ડન્સી
ઇન્જેક્શન (`deps.getSettings`, `deps.callVisionModel`) સ્વીકારે છે; Audio Bridge સેટિંગ્સ,
ક્ષમતાઓ, STT મોડલ પસંદગી, ક્રેડેન્શિયલ તપાસ અને ટ્રાન્સક્રિપ્શન માટે સમકક્ષ
સીમ્સ ઉપલબ્ધ કરાવે છે. તેથી ટેસ્ટ્સ DB અથવા નેટવર્ક ઍક્સેસ વિના બંને ફ્લોનું પરીક્ષણ કરી શકે છે.

## ઇન્જેક્શન-ગાર્ડ રૂટ કવરેજ અને રેડ-ટીમ (તબક્કો 8 · બ્લૉક D)

ઇન્જેક્શન-ગાર્ડ (`createInjectionGuard` / `withInjectionGuard`) વપરાશકર્તા પ્રોમ્પ્ટ સ્વીકારતા
તમામ રૂટ્સને આવરી લે છે. તે `INJECTION_GUARD_MODE`નું પાલન કરે છે (ડિફૉલ્ટ `warn` = ફક્ત લૉગ;
`block` = HTTP 400 `SECURITY_001` પરત કરે છે).

| પ્રકાર           | રૂટ્સ                                                                                                                                                | ડિફૉલ્ટ મોડ |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| ટેક્સ્ટ (હાલનું) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn        |
| જનરેટિવ          | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn        |
| ડેટા             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn        |

ટેક્સ્ટ એક્સ્ટ્રેક્શન (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`ને આવરી લે છે.

**રેડ-ટીમ (રાત્રિ દરમિયાન, `nightly-llm-security.yml`):** promptfoo ચકાસે છે કે દરેક રૂટ
`INJECTION_GUARD_MODE=block`માં OWASP-LLM કૉર્પસને બ્લૉક કરે છે; garak પ્રોબ્સ ચલાવે છે (સિક્રેટ વિના સ્કિપ કરે છે).
સુસંગતતા માટે `moderations`નો સમાવેશ કરવામાં આવ્યો છે. બ્લૉક મોડ ફરજિયાત સીમા છે: `evaluatePromptInjection()`
મિડલવેર દ્વારા તેને પાસ કરાયેલી પ્રતિ-રિક્વેસ્ટ ડિસેબલ સૂચિને અવગણે છે, તેથી `disabledGuardrails` કોઈ
રૂટને તેમાંથી મુક્તિ આપતું **નથી** ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

રાત્રિ દરમિયાન ચાલતા વર્કફ્લો (`.github/workflows/nightly-llm-security.yml`, cron + મેન્યુઅલ
ડિસ્પૅચ)માં બે જૉબ છે:

- **`promptfoo-guard` (બ્લૉકિંગ)** — `INJECTION_GUARD_MODE=block` સાથે
  `promptfoo eval -c promptfooconfig.yaml` ચલાવે છે. દરેક પ્રતિકૂળ કેસ (દા.ત. "અગાઉની તમામ
  સૂચનાઓ અવગણો…", DAN-શૈલીના જેલબ્રેક્સ) ખાતરી કરે છે કે રિસ્પોન્સમાં
  `error.code === "SECURITY_001"` છે, એટલે કે ગાર્ડે ખરેખર રિક્વેસ્ટને નકારી હતી.
- **`garak` (સલાહાત્મક)** — સ્થાનિક OmniRoute ઇન્સ્ટન્સ (`http://localhost:20128/v1`) સામે
  garak `--probes promptinject,dan,leakreplay` ચલાવે છે. તેને પ્રોવાઇડર સિક્રેટ
  (`PROMPTFOO_PROVIDER_KEY`) પર ગેટ કરવામાં આવ્યું છે; તે સરળતાથી સ્કિપ થાય છે અને તેની પાછળ
  `|| true` ઉમેરાયેલું છે, તેથી તે CIને નિષ્ફળ કર્યા વિના રિપોર્ટ કરે છે.

ગાર્ડ હેલ્પર (`createInjectionGuard` / `withInjectionGuard`)નું કવરેજ પ્રોમ્પ્ટ ધરાવતા
દરેક `/v1` રૂટ સુધી વિસ્તરે છે; પ્રોમ્પ્ટ ટેક્સ્ટને
`src/shared/utils/inputSanitizer.ts`માં રહેલા `extractMessageContents()` દ્વારા
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`માંથી લેવામાં આવે છે.
