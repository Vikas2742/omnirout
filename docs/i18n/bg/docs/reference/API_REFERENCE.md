## Завършване на чат

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Персонализирани заглавки

| Заглавка                 | Посока  | Описание                                                                                                                                                                                                                                  |
| ------------------------ | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Заявка  | Задайте на `true`, за да заобиколите кеша                                                                                                                                                                                                 |
| `x-omniroute-no-memory`  | Заявка  | Задайте на `true`, за да пропуснете вмъкването на памет и умения за тази заявка (аналогично на липсата на кеш; избягва допълнителните разходи за токени/цена при всяко извикване)                                                         |
| `X-OmniRoute-Progress`   | Заявка  | Задайте на `true` за събития за напредъка                                                                                                                                                                                                 |
| `X-Session-Id`           | Заявка  | Ключ за постоянна сесия за външен афинитет на сесията                                                                                                                                                                                     |
| `x_session_id`           | Заявка  | Приема се и вариантът с долна черта (директен HTTP)                                                                                                                                                                                       |
| `X-OmniRoute-Session-Id` | Заявка  | Предоставен от извикващата страна етикет за сесия/разговор (използва се и от паметта). Когато присъства, се записва дословно в `call_logs.session_tag` за приписване на разходите по сесии (#8249) — никога не се генерира, когато липсва |
| `Idempotency-Key`        | Заявка  | Ключ за премахване на дублирания (прозорец от 5 секунди)                                                                                                                                                                                  |
| `X-Request-Id`           | Заявка  | Алтернативен ключ за премахване на дублирания                                                                                                                                                                                             |
| `x-omniroute-connection` | Заявка  | Обвързва заявка към единичен модел с една връзка към доставчик (акаунт) чрез нейния идентификатор — вижте [Обвързване към акаунт за всяка заявка](#account-pinning-per-request)                                                           |
| `X-OmniRoute-Cache`      | Отговор | `HIT` или `MISS` (без поточно предаване)                                                                                                                                                                                                  |
| `X-OmniRoute-Idempotent` | Отговор | `true`, ако е премахнато дублиране                                                                                                                                                                                                        |
| `X-OmniRoute-Progress`   | Отговор | `enabled`, ако проследяването на напредъка е включено                                                                                                                                                                                     |
| `X-OmniRoute-Session-Id` | Отговор | Действителният идентификатор на сесията, използван от OmniRoute                                                                                                                                                                           |
| `X-OmniRoute-Request-Id` | Отговор | Идентификатор за корелация на заявката (когато е известен)                                                                                                                                                                                |
| `X-OmniRoute-Version`    | Отговор | Версия на компилацията на OmniRoute (присъства винаги)                                                                                                                                                                                    |
| `X-OmniRoute-Cost-Saved` | Отговор | Сумата в USD, спестена от кеша при `HIT` (само при попадения в кеша)                                                                                                                                                                      |
| `X-OmniRoute-Decision`   | Отговор | Трасировка на маршрутизирането: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` е стратегията на комбинацията или `single` за заявка без комбинация) — присъства винаги в отговорите при завършване                         |

#### Фиксиране на акаунт за всяка заявка

Когато даден доставчик има няколко връзки (акаунти или ключове), OmniRoute обикновено избира една
чрез своята стратегия за избор на акаунт. Вместо това заявката може да бъде фиксирана към конкретна връзка
чрез заглавката `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Къде да намерите идентификатора.** Отворете страницата на доставчика в таблото за управление
  (**Табло за управление → Доставчици → <доставчик>**) и щракнете върху чипа с идентификатор `xxxxxxxx…` в реда на дадена връзка
  — това копира пълния идентификатор на връзката.
- **Кои заявки го зачитат.** Заявките с един модел (`provider/model`) към
  `/v1/chat/completions`, `/v1/messages` и `/v1/responses`. Комбинациите игнорират заглавката: вместо това
  фиксирайте акаунт за всяка стъпка от комбинацията чрез собствената връзка на стъпката.
- **Фиксирането е строго, а не предпочитание.** Фиксираната връзка се използва изключително. Неуспех
  в рамките на заявката регистрира периода на изчакване за акаунта, но **не** превключва към
  друг акаунт на същия доставчик.
- **Периодът на изчакване и квотата освобождават фиксирането.** Докато фиксираната връзка е в период на изчакване,
  квотата ѝ е изчерпана или е блокирана от политика за квоти, следващите заявки се пренасочват към другите връзки
  на доставчика, точно както при нефиксиран трафик.
- **Неизвестните или деактивираните идентификатори водят до грешка.** Идентификатор, който не е в активния набор на доставчика (изтрит,
  деактивиран или принадлежащ на друг доставчик), не оставя допустим акаунт, така че заявката
  завършва с неуспех, вместо без предупреждение да бъде насочена другаде.

Claude Code изпраща персонализирани заглавки чрез `ANTHROPIC_CUSTOM_HEADERS`. Поставете го в блока `env`
на `~/.claude/settings.json` или в `.claude/settings.json` на ниво проект, за да фиксирате различен
акаунт за всеки проект:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Източник: `src/sse/handlers/chat.ts` (прочитане на заглавката), `src/sse/services/auth.ts` и
`src/sse/services/sessionAffinityPin.ts` (освобождаване на фиксирането и проверка за липса в набора).

> **Заглавки за телеметрия на разходите:** успешните отговори без поточно предаване съдържат и набора за телеметрия на разходите `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, фиксирани 10 знака след десетичната запетая; `0.0000000000` за безплатни услуги или такива без зададена цена), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` и `X-OmniRoute-Fallback-Attempts` (само когато > 0), както и `X-OmniRoute-Request-Id` и `X-OmniRoute-Version`. Те се изпращат от завършванията на чат, `/v1/responses`, `/v1/messages`, **както и от крайните точки за мултимедия** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` и `/v1/moderations` (разходът винаги е `0`). Разходът за мултимедия се изчислява според модалността (на изображение, на секунда, на знак, на единица за търсене), когато има налични цени; в противен случай е `0` (продължаване без грешка).

> **Семантика на разходите при попадение в кеша:** при ПОПАДЕНИЕ в семантичния кеш (`X-OmniRoute-Cache-Hit: true`) не се извършва заявка към услуга нагоре по веригата, така че `X-OmniRoute-Response-Cost` е `0.0000000000` (**допълнителният** разход за обслужване на попадението). Първоначалният/потенциалният разход се отчита отделно в `X-OmniRoute-Cost-Saved`. Системите за фактуриране трябва да сумират `X-OmniRoute-Response-Cost` (попаденията не струват нищо); анализите на кеша могат да агрегират `X-OmniRoute-Cost-Saved`.

## Ексклузивни управлявани наеми на сесии

Ексклузивното управлявано наемане на сесии е незадължителен, независим от клиента договор за маршрутизиране: един активен собственик
държи една отговаряща на условията връзка на OmniRoute. То не наема модел, не изисква OAuth, не идентифицира
конкретен клиент и не изисква конкретен доставчик.

Удостоверяващият API ключ трябва да има обхват `lease:exclusive` и изрично зададен непразен
списък `allowedConnections`. Границата за промени в базата данни налага двете полета заедно при
създаване на ключ и частични актуализации.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Успешните отговори за придобиване, подновяване и освобождаване предоставят времеви маркери, `state` и точната положителна
`generation`, но никога избраната връзка или идентификационни данни. При подновяване и освобождаване
поколението се подава в JSON тялото:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Собственикът на активен наем може изрично да поиска безопасни за поверителността метаданни за показване за текущото си обвързване:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Това незадължително действие за състояние е защитено чрез непрозрачния идентификатор на собственика, удостоверения управляван API ключ и точното
активно поколение в рамките на една транзакция в базата данни. `displayName` съдържа само конфигурираното име
на връзката с премахнати водещи и завършващи интервали; стойността му е `null`, когато не съществува безопасно конфигурирано име. OmniRoute никога не го заменя с
имейл адрес или генерирана идентичност на акаунт. Стойността за доставчика е нечувствителен етикет за показване и никога
не е генериран идентификатор на съвместим доставчик. Идентификационни данни, токени, бисквитки, необработени идентификатори на връзки или API
ключове, хешове на собственици, тайни за изолиране и вътрешни данни за маршрутизиране не се включват.

Заявките с грешен ключ, грешен собственик, остаряло поколение, липсващ, изтекъл, освободен или анулиран наем
връщат една и съща грешка `409 LEASE_FENCE_STALE` без метаданни за връзката. Клиент, получил отговора за изчакване на капацитет, няма активно обвързване, което да провери. Когато маршрутизирането прехвърли активен наем,
същото поколение остава валидно и състоянието атомарно връща новото обвързване, а никога старото.
Съществуващите клиенти остават непроменени, тъй като отговорите за придобиване, подновяване, освобождаване и изчакване запазват
предишните си структури.

Този сървърен договор не променя стандартния `/status` на OpenAI Codex. В момента стандартният Codex отчита своя
доставчик на модела и вграденото състояние на удостоверяването/акаунта, но не визуализира произволни персонализирани
метаданни за акаунти на доставчици; бъдеща клиентска интеграция трябва да извика това действие и да реши как да
покаже `connection.displayName`.

След това всяка управлявана заявка за инференция подава и двете контролни заглавки:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Точният собственик, поколение, активна връзка и удостоверен API ключ се проверяват и изолират непосредствено
преди всеки поддържан опит към услуга нагоре по веригата. Повторното използване на собственик и поколение с друг ключ е неуспешно дори
когато този ключ разрешава същата връзка. Необработените идентификатори на собственици не се съхраняват постоянно, не се записват в регистрационните файлове, не се запазват в
моментната снимка на заявката и не се препращат нагоре по веригата.

Временната конкуренция за ресурс връща HTTP `429` с `Retry-After` и:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Този отговор означава единствено, че обичайният набор от отговарящи на условията връзки не е бил празен и всеки свободен кандидат е бил
зает от чужд активен наем. Неподдържаните модели/доставчици, несъответствията с правилата, периодите за изчакване, квотите,
изправността и други обичайни причини за недопустимост запазват съществуващите си отговори на OmniRoute.

### `x-omniroute-compression`

Замяна на плана за компресиране за конкретна заявка. Има най-висок приоритет — пред замяната от комбинацията за маршрутизиране,
активния профил, автоматичното задействане и настройката „По подразбиране“ от панела. Стойности:

| Стойност      | Ефект                                                                                                                 |
| ------------- | --------------------------------------------------------------------------------------------------------------------- |
| `off`         | Без компресиране за тази заявка.                                                                                      |
| `default`     | Изведеният от панела профил „По подразбиране“ (игнорира активния профил). Компресирането със загуби остава изключено. |
| `safe`        | Само премахване на дублирано съдържание и обединяване на празното пространство.                                       |
| `allow-lossy` | Запазва плана на оператора за тази заявка, включително обобщения и пренаписване на стила.                             |
| `engine:<id>` | Една машина, когато е активирана, напр. `engine:rtk`. Изрично включване на тази машина за конкретната заявка.         |
| `<combo>`     | Именувана комбинация, съпоставена първо по име (без отчитане на регистъра), а след това по идентификатор.             |

Бележки:

- Неизвестните стойности се игнорират (заявката никога не се отхвърля); определянето продължава според обичайния приоритет на оператора.
- Ако няколко комбинации имат едно и също име, подайте **идентификатора** на комбинацията за детерминирано съвпадение.
- Комбинация, чието име е `off` или `default`, не може да бъде избрана по име (тези ключови думи се интерпретират първо); посочете такава комбинация чрез нейния идентификатор.
- Главният превключвател за компресиране е безусловна преграда: когато компресирането е глобално деактивирано, тази заглавка не може да го активира.

Приложеният план се връща обратно в заглавката на отговора:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

където `<source>` е една от стойностите `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` или `off`.

## Векторни представяния

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Налични доставчици: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Идентификаторите в каталога са във формат `provider/model` (пример: `jina-ai/jina-embeddings-v5-omni-small`). Самостоятелните идентификатори на модели на Jina, които присъстват в регистъра (например `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`), също се разпознават. Операциите embed/rerank/classify/segment на Jina първо използват идентификационните данни за `jina-ai` от таблото за управление; `JINA_AI_API_KEY` се използва като резервен вариант само когато в таблото няма ключ. Картата `jina-reader` е предназначена само за Reader / `r.jina.ai` (`POST /v1/web/fetch`) и никога не обслужва заявки за векторни представяния или преранжиране.

Моделите от регистъра, които обявяват мултимодална поддръжка, приемат и до 32 структурирани
елемента, независими от доставчика. Типовете медийни елементи са `text`, `image`, `audio`, `video` и `document`. Техният медиен `source`
е или `{"type":"url","url":"https://..."}`, или
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
и псевдонимът на семейството `jina-ai/jina-embeddings-v5-omni` → omni-small) приема и собствените за Jina
документи EmbeddingsV5Request и **ги препраща непроменени** към `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Собствените стойности `{ image | audio | video | pdf }` могат да бъдат публичен HTTPS URL, `data:` URI или необработени
base64 данни. OmniRoute не преобразува тези обекти в низове и не извлича собствените URL адреси на изображения — Jina извлича
публичните медийни ресурси самостоятелно. Допълнителните полета на Jina (`task`, `normalized`, `truncate`, `embedding_type`) се
препращат. Артикулите на Jina, предназначени само за текст, продължават да отхвърлят нетекстови документи.

Ограничения за сигурността и транспорта:

- URL адресите на отдалечени медийни ресурси трябва да бъдат публични и да използват HTTPS. Каноничните елементи `{type,source:url}` се извличат
  от страна на сървъра (повторна проверка при пренасочване, изчакване, ограничения за размера, публичен DNS, фиксиране на връзката) и
  се вграждат преди извикването на доставчика. Собствените за Jina елементи `{image:"https://..."}` се препращат без промяна
  след същата проверка за публичен HTTPS адрес; Jina извлича URL адреса.
- Вградените base64 медийни данни са ограничени до 8 MiB декодирани данни на елемент и 16 MiB декодирани данни за цялата заявка.

Преобразуване за доставчика (каноничните елементи никога не се препращат непроменени):

- Мултимодални модели на Jina: всеки елемент от най-горно ниво се превръща в един обект с ключ за съответната модалност
  (`text` / `image` / `audio` / `video` / `pdf`), като за вградените медийни данни се използват data URI адреси; по един вектор за
  всеки елемент от най-горно ниво.
- Семейство Gemini Embedding 2: един масив от най-горно ниво се превръща в една собствена
  заявка `models/{model}:embedContent` с `content.parts` (`text` или `inline_data`).
- llama.cpp (`llama-cpp/<model>`, всеки модел, зареден от локалния сървър): каноничните елементи `text`
  се превръщат в обикновени низове, а `image` / `audio` / `video` се превръщат в по един
  обект `{"content": [part]}`, използвайки частите за съдържание на чат на llama-server (`image_url`,
  `input_audio` с формат `wav` / `mp3` / `flac`, `input_video`) с вградени данни; по един вектор
  за всеки елемент от най-горно ниво. Сървърът трябва да работи с `--embedding --mmproj …`; без проектор той
  сам отхвърля медийните данни. `document` не се поддържа.
- Неизвестни/динамични модели без изрични метаданни за модалност отхвърлят структурирания вход с HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Неподдържаните комбинации от модел и модалност връщат HTTP 400, вместо да преобразуват принудително елемента. Разширителните
полета извън входните данни в наследените заявки с низове/токени продължават да се предават без промяна.

```bash
# Извеждане на всички модели за векторни представяния
GET /v1/embeddings
```

## Генериране на изображения

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Наличните доставчици включват OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (локално), ComfyUI (локално).

`n` връща `n` изображения в `data[]`. За доставчиците, чийто upstream API връща по едно изображение на извикване
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), се извършват `n` отделни upstream извиквания, като най-много 4 се изпълняват едновременно. Фиксираната стойност
`seed` се измества с индекса на извикването (`seed`, `seed + 1`, …), така че изображенията да се различават, но да остават
възпроизводими. `n` е ограничено до 10. Заявката е неуспешна като цяло, ако някое извикване е неуспешно. Списъкът
с форматите за разпаралеляване е `SINGLE_IMAGE_FANOUT_FORMATS` в
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux използва повторно съществуващата връзка с API ключ и приема префиксите `zenmux/` или `zm/`:

- `zenmux/openai/gpt-image-2` използва OpenAI Images API на ZenMux. Опциите включват `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` и `response_format`.
- Други издатели, като `zm/meta/muse-image-1.0`, използват крайната точка `:predict`
  на Vertex AI в ZenMux. `n` съответства на `sampleCount`, `aspect_ratio` — на `aspectRatio`, а `image_size`
  (`1K`, `2K`, `4K`) — на `sampleImageSize`. Стойност на `size` в пиксели задава само съотношение на страните,
  без гарантирани размери в пиксели. Поддържаните съотношения, разделителни способности и брой изображения се различават според модела.
- `zm/inclusionai/ming-image-0.1-design` избира собствени размери. Пропуснете `size`,
  `aspect_ratio` и `image_size`; изрично зададени стойности връщат HTTP 400. PNG, JPEG и WebP
  могат да бъдат заявени чрез `output_format`.

Тази интеграция поддържа генериране на изображения от текст, но не и редактиране чрез референтно изображение. Изходът от Vertex
се нормализира до `data[].b64_json`; `response_format: "url"` връща upstream
HTTPS URL или URL с base64 данни, когато са налични само байтовете на изображението. Празните/филтрираните резултати
връщат грешка вместо празен успешен отговор. Достъпът до моделите зависи от акаунта в ZenMux.
Вижте [Vertex API на ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) и
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Извеждане на всички модели за изображения
GET /v1/images/generations
```

## OCR на документи

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` избира доставчика на OCR чрез префикс `provider/model`; идентификатор на модел без префикс (напр.
`mistral-ocr-latest`) се съпоставя с регистрирания му доставчик, а при пропуснат `model` по подразбиране се използва
Mistral (`mistral-ocr-latest`). Регистрирани доставчици (`open-sse/config/ocrRegistry.ts`):

| Идентификатор на доставчика   | Идентификатор на модела | Стойност на `model`                                          | Бележки                                                                                                                            |
| ----------------------------- | ----------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest`    | `mistral/mistral-ocr-latest` (или само `mistral-ocr-latest`) | Синхронно — отговорът се връща директно от единственото upstream извикване.                                                        |
| `azure-document-intelligence` | `prebuilt-read`         | `azure-document-intelligence/prebuilt-read`                  | Асинхронно upstream изпълнение (`analyze` + периодична проверка) — вижте по-долу.                                                  |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`     | `vertex-deepseek-ocr/deepseek-ocr-maas`                      | Синхронно, чрез партньорската крайна точка `openapi/chat/completions` на Vertex AI — вижте по-долу за удостоверяването/URL адреса. |

И трите доставчика връщат тяло в един и същ формат като този на Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Процес на периодична проверка в Azure Document Intelligence

API `analyze` на Azure Document Intelligence е асинхронен: първоначалната заявка връща
заглавка `Operation-Location` вместо тяло, след което резултатът трябва да бъде проверяван периодично. Манипулаторът
(`open-sse/handlers/ocr.ts`) проверява този URL всяка секунда до 30 опита, прекратява незабавно (без
да продължава проверките) при отговор от проверката, който не е `ok`, или при състояние `"failed"`, и връща `504`, ако
операцията все още се изпълнява след изчерпване на допустимия брой опити. Окончателният отговор от Azure се
нормализира до същата структура `pages`/`markdown`, използвана от Mistral, преди да бъде върнат на
извикващата страна, така че клиентският код не трябва да обработва доставчика като специален случай.

### Удостоверяване и определяне на крайната точка за Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` използва повторно същото удостоверяване във Vertex AI, което OmniRoute вече поддържа за
трафик за чат/изображения (`open-sse/executors/vertex.ts`): API ключът на връзката е или
JSON идентификационни данни за Service Account (обменяни за краткотраен OAuth токен за достъп чрез процеса JWT-bearer),
или вече издаден OAuth токен за достъп, използван без промяна. Upstream URL адресът на крайната точка е общата
партньорска крайна точка `openapi/chat/completions` на Vertex, съставена от проекта и
региона на връзката — изрично зададените `providerSpecificData.project`/`providerSpecificData.region` винаги са с предимство;
в противен случай проектът се извлича от `project_id` в JSON данните на Service Account, а регионът
по подразбиране е `us-central1`. И двете стойности се определят в `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) и се използват от
`src/app/api/v1/ocr/route.ts` преди предаването към `handleOcr`.

### Префикси на идентификаторите на модели (`?prefix=`)

Повечето модели се публикуват с **префикс на доставчика**. Получаваният префикс се управлява от
флага за функционалност `MODELS_CATALOG_PREFIX_MODE` и може да бъде заменен **за всяка отделна заявка** чрез
параметър на заявката — полезно за клиент, който иска изчистен списък, без да променя общата за
сървъра настройка за всички останали:

```bash
GET /v1/models?prefix=alias        # по един идентификатор за модел — краткият префикс на псевдонима
GET /v1/models?prefix=dual         # и двете форми (настройка по подразбиране на сървъра)
GET /v1/models?prefix=canonical    # само пълният префикс с идентификатора на доставчика
```

| Режим       | Извежда                                                 | Бележки                                                                                                                                                                                                                   |
| ----------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **и** `claude/claude-sonnet-4-6` | **По подразбиране.** И двата идентификатора насочват към един и същ модел; запазени са, за да продължат да работят клиентските конфигурации, в които едната от формите е твърдо зададена. Приблизително удвоява каталога. |
| `alias`     | `cc/claude-sonnet-4-6`                                  | По един запис за модел. Доставчиците без отделен псевдоним все пак извеждат своя запис, така че нищо не се губи.                                                                                                          |
| `canonical` | `claude/claude-sonnet-4-6`                              | По един запис за модел с пълния префикс с идентификатора на доставчика. Доставчиците без отделен псевдоним (напр. `antigravity/…`, `agy/…`) също извеждат тук единствения си идентификатор, така че нищо не се губи.      |

Огледален запис в режим `dual` може да бъде разпознат и без параметъра на заявката: той съдържа поле `parent`,
което сочи към основния идентификатор.

Клиентите, които визуализират инструмент за избор на модел, трябва да заявяват `?prefix=alias` — това прави
[разширението OmniCopilot за VS Code](../guides/VSCODE-COPILOT.md).

### Филтри за откриване (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` приема незадължителни филтри за откриване. Без тях отговорът остава
непроменен. Те стесняват каталога, който заявителят вече вижда (първо се прилагат разрешенията на API ключа),
и се изпълняват преди странирането чрез `limit` / `after` в стила на OpenAI:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # всяка посочена възможност трябва да е налична
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` в каталога; редовете без такава стойност са `chat`
GET /v1/models?q=sonnet&limit=10                           # съвпадение без значение на регистъра в идентификатора или името
```

| Параметър     | Стойности                                                                                           |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | неотрицателно цяло число, сравнявано с `context_length`                                             |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 знака                                                                                         |

Непозната стойност или стойност на `min_context`, която не е неотрицателно цяло число (например `1.5`),
връща HTTP `400`, а съобщението изброява валидните стойности. Реализация:
`src/app/api/v1/models/catalogFilters.ts`.

### Кратък списък с модели (`POST /v1/models/query`)

`POST /v1/models/query` връща кратък, детерминистичен списък от същия каталог, със същото
удостоверяване и видимост за отделния ключ като `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Всички полета са незадължителни. `capabilities` и `exclude` приемат масив или низ със стойности, разделени със запетаи;
`max_output` се сравнява с `max_output_tokens`. Резултатите се сортират по `owned_by`, а след това по `id`.
Стойността по подразбиране на `limit` е `20`, а стойностите над `100` се ограничават до `100`. Невалиден JSON, непознато
поле или невалидна стойност връща HTTP `400`.

### Индивидуално скрити модели за чат

Модел, отбелязан като **Скрит** на страницата на своя доставчик, се изключва от каталога и заявката се отхвърля
с HTTP `404` / `model_not_found`, когато моделът бъде заявен изрично. Проверката използва определения
доставчик и модел, включително псевдонимите на доставчика, префиксите на възлите на съвместими доставчици и
стойностите по подразбиране на връзката. Комбинацията пропуска скритите цели и може да използва видима алтернатива; когато не
остане изпълнима цел, тя връща същия код за грешка. Премахването на скриването влиза в сила при следващата
заявка. Настройките за видимост само за изображения не скриват модела за чат със същия идентификатор.

Тази индивидуална настройка за модел е отделна от
[списъците за разрешаване/забраняване на видимостта на модели](../routing/MODEL_EXPOSURE_LIST.md), които филтрират публикуването
в каталога и кандидатите за автоматично маршрутизиране, като същевременно запазват изричното изпращане. Разрешенията за модели
на API ключа продължават да се прилагат независимо. Режимът по подразбиране за префиксите в каталога остава `dual`.

### Варианти на модели без мислене

За моделите Claude с възможност за мислене `/v1/models` публикува и вариант **без мислене**, чийто идентификатор започва с `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Избирането на този идентификатор (напр. в конфигурация на Claude Code, която винаги добавя блок `thinking`) се преобразува обратно към действителния `<provider>/<model>` с потиснато разсъждение — `thinking:{type:"disabled"}` по пътя `/v1/messages` или с премахнати полета `reasoning`/`reasoning_effort` по пътя `/v1/chat/completions`. Вариантът се показва само за модели от семейството Claude, които поддържат разсъждение **и** зачитат `disabled` (така например моделите само с адаптивен режим, които отхвърлят `disabled`, са изключени). Операторите могат принудително да включват или изключват варианта за всеки модел чрез `ModelSpec.noThinkingAlias`.

## Генериране на аудио с ElevenLabs

Конфигурирайте връзка с доставчика `elevenlabs` в OmniRoute чрез вашия ElevenLabs API ключ.
Клиентите се удостоверяват със своя **OmniRoute** ключ (`Authorization: Bearer $OMNIROUTE_API_KEY`);
шлюзът предоставя съхранения ключ на доставчика като `xi-api-key`. Никога не изпращайте ElevenLabs ключ
като bearer токен към шлюза.

| Метод | Път                         | Отговор                                      | Категория на крайната точка за API ключ |
| ----- | --------------------------- | -------------------------------------------- | --------------------------------------- |
| POST  | `/v1/sound-generation`      | Нативни аудио байтове                        | `elevenlabs`                            |
| POST  | `/v1/music`                 | Нативни аудио байтове                        | `music`                                 |
| POST  | `/v1/music/stream`          | Поточно предавани аудио байтове              | `music`                                 |
| POST  | `/v1/music/detailed`        | Нативно multipart аудио и план за композиция | `music`                                 |
| POST  | `/v1/music/detailed/stream` | Нативни SSE метаданни и аудио фрагменти      | `music`                                 |
| POST  | `/v1/music/plan`            | JSON план за композиция                      | `music`                                 |

Тези крайни точки допълват съществуващите маршрути `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` и `/v1/speech-to-text`. Нативните JSON полета
и параметрите на заявката, като `output_format` и `enable_logging`, се запазват.
Отговорите от `/v1/music/detailed` запазват своите multipart граници; обработвайте ги като multipart.
`/v1/music/detailed/stream` връща `text/event-stream` с метаданни за композицията и
base64 аудио фрагменти в SSE събития. И шестте маршрута поддържат CORS предварителни заявки.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Кратък звуков ефект. Продължителност: от 0,5 до 30 секунди.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Продължителността на музиката се задава в милисекунди: от 3000 до 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Използвайте `/v1/music/stream` със същото JSON тяло за постепенно доставяне на аудио. Композицията
приема точно едно от `prompt` или `composition_plan`; `/v1/music/plan` изисква `prompt`
и по избор приема `source_composition_plan`. Нативните схеми запазват допълнителните
полета на доставчика, така че версиите на плановете за композиция и опциите за фина настройка да достигнат до ElevenLabs.

Унифицираната крайна точка `/v1/music/generations` също приема `elevenlabs/music_v1`,
`elevenlabs/music_v2` и `elevenlabs/music_v2_5`. При активна връзка с ElevenLabs
тези модели се показват в музикалния каталог. Тази крайна точка връща
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Нейното поле `duration` е в
секунди и се съпоставя с `music_length_ms`; изрично зададено `music_length_ms` е с предимство.
`instrumental` се съпоставя с `force_instrumental`, като нативното поле е с предимство.
Използвайте нативните крайни точки за поточно предаване и нативната крайна точка за композиция
за заявки, управлявани единствено от план за композиция.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Ограниченията за крайни точки, модели, бюджет и връзки се прилагат преди извикване към външната услуга. Нативните
маршрути връщат без промяна кодовете за състояние и телата на грешките от външната услуга, включително `402` при ограничение
на плана и `429` при достигане на квотата. Заглавките `character-cost`, `song-id`, `request-id` и `retry-after`
се запазват, когато присъстват. Наличието на безплатен кредитен баланс не гарантира достъп до всеки
музикален модел, изходен формат или API функционалност: ElevenLabs определя правата за всяка заявка.
Унифицираната крайна точка запазва кодовете за състояние на грешките в нормализирания формат за грешки на OmniRoute.

Договори на външната услуга: [звукови ефекти](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[музикална композиция](https://elevenlabs.io/docs/api-reference/music/compose) и
[подробности за поточно предавана музика](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

```bash
# Редактиране на изображение (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# Генериране на видео/музика (идентификатор на модел с префикс на доставчика)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **Възли на доставчици за преранжиране:** `POST /v1/rerank` също насочва към съвместими с OpenAI възли на доставчици
> (oMLX, vLLM, Infinity, TEI зад шлюз, …), адресирани като `<node-prefix>/<model>`. Възлите с обратна връзка
> (`localhost`, `127.0.0.1`, `172.16.0.0/12`) винаги са допустими, както и имената на хостове, които
> операторът посочва в `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (напр. име на услуга в Docker/Compose като
> `http://reranker:8080/v1`; те се извикват директно, никога чрез `HTTP(S)_PROXY` или фиксираното прокси
> на дадена връзка). Възлите на всеки друг
> хост — машина в LAN или Tailscale партньор — са допустими само когато операторът активира
> флага за функционалност `RERANK_REMOTE_PROVIDER_NODES` **и** базовият URL адрес на възела отговаря на правилата
> за изходящи URL адреси на доставчика (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Стъпката за преранжиране на механизма за памет извиква този маршрут чрез
> обратна връзка, така че същото правило управлява `rerankProviderModel` в настройките за памет.
>
> **Формати на локалния сървър:** възелът се извиква на `<base>/v1/rerank`, а при 404 — на `<base>/rerank`
> (Infinity, TEI). Тялото на заявката към сървъра нагоре по веригата съдържа както изписването на Cohere/OpenAI (`documents`,
> `return_documents`), така и изписването на TEI (`texts`, `return_text`), а отговорът от сървъра нагоре по веригата се
> нормализира до обвивката на Cohere: директният масив на TEI `[{index, score, text}]`, `{results: [{index, score}]}`
> от олекотени шлюзове и форматът на Voyage `{data: [...]}` се връщат на клиента като
> `{results: [{index, relevance_score, document?}]}`, сортирани по оценка и ограничени до `top_n`.
>
> **Откриване на възли на доставчици:** моделите на съвместим с OpenAI възел на доставчик се показват в `GET /v1/models`
> под префикса на възела. Редовете без метаданни за крайна точка (типично за локални списъци от `/v1/models`)
> наследяват `apiType` на възела, така че моделите на възел за `embeddings` са с `type: "embedding"`, а моделите
> на възел за `rerank` са с `type: "rerank"`, вместо по подразбиране да бъдат за чат; изрично зададеното
> `supportedEndpoints` в синхронизиран или ръчно добавен ред продължава да има предимство.

### `provider_options` за Exa и Tavily

Exa и Tavily четат специфичните за доставчика полета от контейнер с пространство от имена:
`provider_options.exa` (или `provider_options["exa-search"]`) и `provider_options.tavily`
(или `provider_options["tavily-search"]`). Препращат се само ключовете по-долу. Всеки от тях се
проверява спрямо собствената му Zod схема в `open-sse/handlers/search/providerOptionsPassthrough.ts`,
а ключ с грешен тип се премахва. Всеки друг ключ се игнорира, включително удостоверяване, базов URL,
`stream` и `outputSchema`. Плоските ключове, използвани от други доставчици (`cx`, `depth`, ...), работят
както преди.

| Доставчик | Полета от най-горно ниво                                                                                                                                                                                                                                                                                                                                                  | Вложени                                                                                                                                                                               |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa       | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (плоски примитивни стойности), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                  | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}`, обединено върху стойността по подразбиране `{ text: true, highlights: true }` |
| Tavily    | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                                     |

Общите полета винаги имат предимство: `query`, `max_results`, `filters` (домейни), `country` и
темата, извлечена от `search_type`. При Exa `search_type: "news"` запазва `category: "news"`.
Tavily приема също `search_type: "finance"` (`topic: "finance"`).

Общото поле `time_range` вече достига и до двата доставчика: Exa получава `startPublishedDate` (ISO
времеви печат), а Tavily получава `start_date` (`YYYY-MM-DD`). Изрично зададена дата в `provider_options`
замества съпоставената стойност.

Резултатите от Exa запазват `id`, `highlight_scores`, `summary`, `subpages`, `entities` и `extras` в
`provider_raw`. Резултатите от Tavily запазват `images` и `favicon`.

Отчитането на разходите продължава да използва плоския регистър `costPerQuery`. Tavily таксува
`search_depth: "advanced"` с повече кредити на заявка и тази разлика не е отразена в
`usage.search_cost_usd`.

## API за извличане на уеб съдържание

Извлича съдържание от URL чрез конфигуриран доставчик за извличане на уеб съдържание (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, същият API ключ като за Parallel Search) връща само
Markdown — всяка друга стойност на `format` води до `400` — и ограничава съдържанието до 100 000 знака. Когато
самата целева страница не може да бъде извлечена, услугата нагоре по веригата съобщава това в HTTP 200;
OmniRoute го представя като `422` с фиксирано съобщение.

| Метод | Път             | Описание                                                       |
| ----- | --------------- | -------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | Извлича/обхожда URL — тялото се валидира от `v1WebFetchSchema` |

**Удостоверяване:** Bearer API ключ (`extractApiKey` + `isValidApiKey`). Правилата се прилагат чрез `enforceApiKeyPolicy`.

**Резервен избор с отчитане на квотите (#8297):** когато не е зададен изрично `provider`, наборът
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) се
обхожда във фиксиран
ред на приоритет (първо се запълва първият) — конфигуриран доставчик с достигнато ограничение на заявките се пропуска,
вместо заявката да бъде прекратена незабавно, а повторим срив/изчерпване на квотата при услуга нагоре по веригата
(HTTP 429 винаги; 402/403 за безплатни планове на Firecrawl/Tavily/TinyFish с ограничения на квотата —
не и за Jina Reader и никога за обикновена невалидна заявка 400) води до преминаване към
следващия неизпробван доставчик с налични идентификационни данни по време на заявката. Когато всички доставчици в
набора са изчерпани, крайната точка връща един `429` (със заглавка `Retry-After`)
вместо предишния общ `400`. Когато изрично е заявен `provider`,
**няма** неявен резервен избор — изрично избран доставчик с достигнато ограничение или грешка
връща собствената си грешка (`429`, ако е достигнато ограничението на заявките, иначе състоянието
на услугата нагоре по веригата).

То слуша на същия порт като API/таблото за управление по пътищата `/v1/responses`,

За маршрутизиране със споделяне на квоти използвайте `model: "qtSd/<group>/codex/<model>"`. Реализирано е в
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Удостоверяване:** Bearer API ключ по време на установяването на връзката. Включеният HTTP сървър (`server-ws.mjs`)
трябва да бъде активната входна точка (както е по подразбиране, когато съществува `app/server-ws.mjs`).

#### Идентификатор на модела: използвайте базовия ChatGPT идентификатор (без префикс `codex/`)

OpenAI **Codex CLI** валидира името на модела от страната на клиента, когато
`supports_websockets = true`, и **отхвърля идентификатори с префикс на доставчика**, като
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Изпращайте **базовия** идентификатор (например `gpt-5.5`). Мостът на OmniRoute е
само за codex, затова преди тунелирането към услугата нагоре по веригата той отново определя базовия идентификатор като codex модел
(`resolveCodexWsModelInfo`) — въпреки че базовият
`gpt-5.5` иначе би бил насочен към друг доставчик чрез HTTP.

#### Конфигуриране на OpenAI Codex CLI

Насочете Codex CLI към OmniRoute, като добавите персонализиран доставчик с поддръжка на WebSocket

```toml

supports_websockets = true                # активира транспорта Responses чрез WS
env_key = "OMNIROUTE_API_KEY"             # съдържа API ключа на OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # API ключ на OmniRoute (произволен ключ, ако REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI надстройва `base_url + /responses` до WebSocket, а OmniRoute го тунелира
към избраната codex OAuth връзка. Валидирано от край до край спрямо локалния
сървър: ChatGPT връща `codex.rate_limits` + `response.created` и предава поточно
завършения отговор.

## Самостоятелна проверка на потреблението (`/api/usage/om-usage`)

Всеки API ключ може да прочете **собственото си** потребление и квоти — без удостоверяване за управление. Това е крайната точка, която
клиентът (CLI, панелът OmniCopilot) използва, за да показва разходите на притежателя на ключа.

```bash
# Текстов формат (историческият договор — обикновен текст за терминал)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Структуриран формат — използван от потребителския интерфейс
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

За ключа трябва да е активирано **`allowUsageCommand`** (изключено е по подразбиране — мениджърът на API ключове
в таблото го превключва за всеки ключ). Без него крайната точка отговаря с `403`.

`?format=json` връща разграничима структура, така че извикващата страна никога да не чете поле с данни от
отказ. При успех:

```jsonc
{
  "allowed": true,
  // присъства само когато за ключа са активирани индивидуални лимити за потребление (дневни/седмични в USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // моментната снимка на квотата за избрания доставчик или null, когато все още няма нищо кеширано:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // моментните снимки за всички връзки, така че потребителският интерфейс да може да визуализира няколко доставчика един до друг:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

При отказ (`401` невалиден ключ / `403` няма разрешение) същият маршрут връща
`{ "allowed": false, "error": { "message": "…" } }` — налично, но празно `personal`/`provider`
(ключът е разрешен, но все още няма получени данни) е различно състояние от отказ и само JSON форматът
ги разграничава.

**Удостоверяване:** собственият Bearer API ключ на извикващата страна, валидиран чрез `isValidApiKey` — това _не е_
интерфейсът за управление (`/api/keys/…`), който остава защитен чрез `requireManagementAuth`.

### Необработени спрямо коригирани според прага проценти на квотата

При използване на `/api/usage/om-usage` извикващите страни трябва да имат предвид разликата между
процентите, представени в **обикновения текстов изход**, и тези в структурирания **JSON изход**:

| Аспект                  | Формат с обикновен текст (`/api/usage/om-usage` / `@@om-usage`)                                        | JSON формат (`?format=json`)                                                             |
| :---------------------- | :----------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------- |
| **Изходно поле**        | `NN% left` (напр. `20% left`)                                                                          | `provider.quotas` / `providers[].quotas`                                                 |
| **Измерване**           | **Използваем лимит, коригиран според прага**: оставащ капацитет над граничния праг                     | **Необработена квота от доставчика**: некоригирано измерване от доставчика               |
| **Мащабиране по прага** | Мащабира се чрез `effectiveRemainingPercent()`, така че защитеният резерв да се показва като `0% left` | Няма (необработени стойности от моментната снимка, докладвани от доставчика)             |
| **Данни за прага**      | Включени са в показвания процент                                                                       | Съхраняват се в `quotaWindowThresholds` за всяка връзка (или по подразбиране от сървъра) |
| **Основен потребител**  | Интерактивни CLI инструменти, терминални подкани, оператори                                            | Програмни интеграции, табла, анализи, системи за проследяване на таксуването             |

#### Формула за коригиране според прага

OmniRoute поддържа проактивни гранични прагове за квотите, за да предотврати изчерпването им при доставчика (конфигурирани чрез
`quotaWindowThresholds` на връзката, настройките по подразбиране на доставчика или глобалните настройки за устойчивост). Когато за прозорец на квотата
е активен граничен праг (напр. `cutoff = 25%`), текстовият визуализатор изчислява оставащия лимит по следния начин:

- Ако `remaining <= cutoff`: връща `0%`.
- Ако `remaining > cutoff`: връща `((remaining - cutoff) / (100 - cutoff)) * 100`.

Форматираният текстов изход закръгля резултата до най-близкото цяло число (`Math.round(...)`).

#### Илюстративен пример

Да разгледаме прозорец на доставчик с **60% необработено потребление** (следователно **40% необработена оставаща квота**) и конфигуриран
**25% граничен праг за оставащата квота**:

| Представяне                           | Изчисление                                         | Оставащи |            Подразбиращо се използване             |
| :------------------------------------ | :------------------------------------------------- | :------: | :-----------------------------------------------: |
| **Необработен JSON (`?format=json`)** | Моментна снимка от доставчика (`quotas[window]`)   | **40%**  |                      **60%**                      |
| **Текстов формат (`NN% left`)**       | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%**  | **80%** (ако се изчислява като `100 - remaining`) |

- **Защо текстът показва 20% оставащи:** От физическата квота от 40%, оставаща за акаунта, 25% са запазени от
  политиката за граничния праг. Извикващата страна разполага само с 15% от общо 75% използваем свободен капацитет, преди маршрутизаторът да спре
  да насочва заявки към тази връзка. Мащабирането гарантира, че връзката сигнализира изчерпване (`0% left`) точно когато
  маршрутизирането бъде прекратено.
- **Защо JSON запазва необработените стойности:** JSON полезният товар връща точната моментна снимка от доставчика (`UsageSnapshot`),
  така че външните инструменти да имат достъп до действителното потребление при доставчика и до
  `quotaWindowThresholds` на ниво връзка без водещо до загуба мащабиране от страна на сървъра.

#### Насоки за миграция на потребителите

Ако външна интеграция (например плъгин за редактор или разширение за агент) преди е извличала данни от текстовата
крайна точка (`NN% left`) и е изчислявала използвания процент като `100 - NN`, преминаването към `?format=json` означава:

- Прочитането на необработените JSON стойности ще отразява **действителното потребление нагоре по веригата** (60% използвани в примера по-горе).
- Ако интеграцията иска да запази семантиката за използваемия оставащ лимит на текстовата крайна точка, тя може да изчислява
  ефективния остатък от страна на клиента, като използва `quotaWindowThresholds` за замествания на ниво връзка.

## Семантичен кеш

```bash
# Получаване на статистика за кеша
GET /api/cache/stats

# Изчистване на всички кешове
DELETE /api/cache/stats
```

Примерен отговор:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Въздействие върху латентността

При ПОПАДЕНИЕ в семантичния кеш отговорът се предоставя от кеша **без извикване
към доставчика**, така че отчетената стойност на `X-OmniRoute-Response-Latency` е близка до нула
(независимо от първоначалната латентност на доставчика). Клиентите, чувствителни към латентността
(бенчмаркинг, наблюдение на p50/p99), трябва да проверяват
HTTP заглавката на отговора `X-OmniRoute-Cache-Latency`:

| Стойност    | Значение                                                                      |
| ----------- | ----------------------------------------------------------------------------- |
| `synthetic` | Отговорът е предоставен от кеша; латентността не е реално време на доставчика |
| _(липсва)_  | Отговор от реално извикване към доставчика                                    |

### Заобикаляне на кеша за отделен ключ

API ключовете могат да се откажат от четенето на семантичния кеш чрез `cacheDefaultMode`:

| Стойност | Поведение                                                    |
| -------- | ------------------------------------------------------------ |
| `legacy` | Нормално поведение на кеша (по подразбиране)                 |
| `bypass` | Напълно пропуска търсенето в кеша; винаги извиква доставчика |

Задайте при създаването на ключ (`POST /api/keys`) или при актуализиране (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Заобикаляне за отделна заявка

Всяка заявка може да заобиколи кеша независимо от настройките на ключа:

```
X-OmniRoute-No-Cache: true
```

За синхронизирани/импортирани модели `PUT /api/provider-models` приема `provider`, `modelId` и
`maxOutputTokenOverride`: положително цяло число задава ръчно ограничение за изходните токени, а `null`
го премахва, за да възстанови стойността по подразбиране. `GET /api/provider-models?provider=<provider>` връща тези
стойности в `modelOutputOverrides`, включително моделите без запис за персонализиран модел. Замяната
използва възможността `max_output_tokens` по време на изпълнение и се запазва след повторно синхронизиране на модела. Страницата на
съвместимия с OpenAI доставчик предлага същите контроли за редактиране/премахване и обозначава моделите с изрична поддръжка на зрение.

Персонализираните възли за Chat Completions адаптират изричните откази от разсъждение към бекенда нагоре по веригата. При
успешен тест на връзката автоматично се избират контроли за шаблона за чат за всеки точен идентификатор на модел,
чийто запис в `/models` доказва разпозната стойност на `owned_by`: `vllm`, `sglang` или `llamacpp`.
Прозрачните обвивки, съвместими с OpenAI, може да запазят оригиналния запис на модела във вложен
обект `openai`; откриването проследява до три такива обвивки. Моделите с липсваща, неизвестна или
противоречива собственост запазват обичайното поведение на OpenAI. Откриването използва повторно съществуващата заявка към каталога,
не генерира токени за завършване и се анулира при промяна на крайната точка на връзката.

За да фиксирате поведението за бекенд, който не предоставя тези метаданни, използвайте съществуващия API за частично
актуализиране на доставчика:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Изпратете това тяло чрез `PUT /api/providers/<connection-id>`. За тази връзка изрично
усилие за разсъждение със стойност `none` се изпраща като `chat_template_kwargs.thinking=false` и
`chat_template_kwargs.enable_thinking=false`. Изричните вградени стойности на шаблона остават с приоритет,
освен ако правило за разсъждение от страна на сървъра не наложи определено усилие. Настройката се прилага само когато персонализирана
връзка, съвместима с OpenAI, изпраща тяло на Chat Completions; заявките към Responses и обикновените
доставчици запазват вградената си структура на заявката. Задайте `reasoningControl` на `openai`, за да наложите обичайното за OpenAI
предаване на `reasoning_effort`, или го пропуснете/задайте на `null`, за да използвате автоматично откриване.

Заявките на класификатора за автоматичен режим на Claude Code по подразбиране изключват вграденото мислене, когато
не съдържат изрични контроли за разсъждение. Откриването използва системния маркер на класификатора в заявки във формат Claude,
а не имена на модели или ограничения за завършване. Изричните контроли в тялото, поддържаните заглавки за усилие/мислене,
правилата за маршрутизиране и определеното усилие на модела запазват съществуващия си приоритет. И двата етапа на класификатора
запазват своите подкани, ограничения за завършване, последователности за спиране и реалните решения на системата нагоре по веригата
относно разрешенията; вторият етап все още може да създаде заявеното видимо разсъждение като обикновен текст.

### Версия и канал за издания

```bash
GET /api/system/version
```

Маршрут за управление, достъпен само през loopback интерфейса (с администраторско удостоверяване). Връща изпълняваната версия, най-новата
публикувана версия и състоянието на автоматичното обновяване. `releaseChannel` и `channels` са допълнителни
полета (линия 3.8.54); `channel` запазва значението си — режимът на внедряване, който програмата за обновяване на таблото
използва (`npm`, `source` или `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — npm каналът на изпълняваната компилация: `nightly` за версии `-nightly.*`,
  `next` за други предварителни издания (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` за стабилна версия от
  по-стара основна версия спрямо `channels.latest`, а във всички останали случаи — `latest`. Прилагат се същите правила като в
  `scripts/release/dist-tag.mjs`, който избира npm dist-tag при публикуване.
- `channels` — последната публикувана версия за всеки dist-tag, получена от `npm view omniroute dist-tags` (с резервно
  извличане чрез HTTP от регистъра), кеширана със същия 10-минутен TTL като `latest`. `latest` присъства винаги
  (като резервно се използва полето `latest`, а след това `"unavailable"`); `next`, `nightly` и `lts` се показват
  само когато съответният dist-tag съществува. Заявка с `Cache-Control: no-cache` опреснява и двете извличания.

Моделът на каналите (`latest` = v3 до общата наличност на 4.0, `next` = rc, `nightly` = компилации от `develop`,
`lts` = корекции за v3 след общата наличност на 4.0) е описан в `docs/ops/RELEASE_STRATEGY.md`.

## Транскрипция на аудио

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Транскрибирайте аудиофайлове чрез всеки конфигуриран STT доставчик. Първият сегмент от пътя избира нативния доставчик (`openai/…`, `deepgram/…`). Шлюзовете, които повторно експортират модел на друг доставчик, използват квалифициран идентификатор
(`openrouter/deepgram/nova-3`).

**Заявка:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Отговор:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Примерни идентификатори на модели:** `openai/whisper-1` (изисква ключ за OpenAI),
`openrouter/deepgram/nova-3` (изисква ключ за OpenRouter),
`deepgram/nova-3` (изисква нативен ключ за Deepgram). Заявка само с
`deepgram/nova-3` **не** използва OpenRouter.

**Поддържани формати:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

## Токенизирани псевдоними за VS Code / псевдоними без заглавка

Използвайте тези псевдоними, когато дадена интеграция не може да добави заглавка `Authorization` и се налага API ключът да бъде вграден в базовия URL адрес.

```bash
# Псевдоним на каталог в стил OpenAI
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# Псевдоними за чат в стил OpenAI
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Псевдоними в стил Ollama
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

Пример:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

Бележки:

- Токенизираните псевдоними използват повторно същите обработчици като `/v1/*` и `/api/tags`; форматите на отговорите остават идентични.
- Предпочитайте `Authorization: Bearer ...`, когато клиентът поддържа персонализирани заглавки.
- Токените в URL адреси може да се появят в регистрационните файлове на обратния прокси сървър, историята на браузъра и телеметрията извън OmniRoute. Разглеждайте ги като опция за съвместимост, а не като режим за удостоверяване по подразбиране.

```bash
# Получаване на състоянието на бюджета за всички API ключове
GET /api/usage/budget

# Задаване или актуализиране на бюджет
POST /api/usage/budget
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "dailyLimitUsd": 5.00,
  "weeklyLimitUsd": 30.00,
  "monthlyLimitUsd": 100.00,
  "warningThreshold": 0.8,
  "resetInterval": "monthly"
}
```

> **Бележки за схемата** (`setBudgetSchema`): `apiKeyId` е задължително; поне едно от `dailyLimitUsd`, `weeklyLimitUsd` или `monthlyLimitUsd` трябва да бъде по-голямо от нула. Незадължителни полета: `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`). Остарелият формат `{keyId, limit, period}` връща `400 Bad Request`.

## Ограничения на токените

Бюджети за **токени** за всеки API ключ (различни от базирания на USD бюджет по-горе). Прилагат се директно по пътя на заявката: когато използването на ключа в текущия прозорец достигне ограничението си, заявките се отхвърлят с `429 Too Many Requests`. Ограниченията могат да бъдат обвързани с конкретен `model`, `provider` или да бъдат приложени `global`но за целия ключ; когато няколко ограничения съответстват на дадена заявка, се прилага най-строгото.

```bash
# Извеждане на ограниченията за токени на ключ (включително текущото използване в прозореца)
GET /api/usage/token-limits?apiKeyId=key-123

# Създаване или актуализиране на ограничение за токени
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Изтриване на ограничение за токени по идентификатор
DELETE /api/usage/token-limits?id=tl-abc
```

> **Бележки за схемата** (`setTokenLimitSchema`): `apiKeyId` и `scopeType` (`model` | `provider` | `global`) са задължителни. `scopeValue` е задължително, освен ако `scopeType` е `global` (напр. идентификатор на модел за обхват `model` или идентификатор на доставчик за обхват `provider`). `tokenLimit` трябва да бъде положително цяло число (преобразувано от низ). Незадължителни: `id` (пропуснете за създаване, подайте за актуализиране), `resetInterval` (`daily` | `weekly` | `monthly`, по подразбиране `monthly`), `resetTime` (`HH:MM`), `enabled` (по подразбиране `true`). Отговорите на `GET` допълват всяко ограничение с `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` и `nextResetAt`. Това е крайна точка от управленски клас (удостоверяването се налага централизирано от конвейера за оторизация).

## Обработка на заявки

1. Клиентът изпраща заявка към `/v1/*`
2. Обработчикът на маршрута извиква `handleChat`, `handleEmbedding`, `handleAudioTranscription` или `handleImageGeneration`
3. Моделът се определя (директен доставчик/модел или псевдоним/комбинация)
4. Идентификационните данни се избират от локалната база данни с филтриране според наличността на акаунта
5. За чат: `handleChatCore` проверява семантичния кеш/кеша за подписи и определя настройките за компресиране на комбинацията
6. Проактивното компресиране се изпълнява преди преобразуването за доставчика, когато е активирано (`lite`, Caveman, RTK или наслагване)
7. Изпълнителят за доставчика изпраща заявката към услугата нагоре по веригата
8. Отговорът се преобразува обратно във формата на клиента (за чат) или се връща непроменен (за вграждания/изображения/аудио)
9. Записват се използването, анализите за компресиране и регистрационните файлове на заявките
10. При грешки се прилага резервен вариант съгласно правилата на комбинацията

Пълна справка за архитектурата: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Устойчивост (разширено)

OmniRoute предоставя три независими механизма за временни откази; крайните точки за управление по-долу позволяват на операторите да преглеждат и презаписват настройките им:

| Обхват                        | Съхранение на състоянието                      | Преглед                                   | Нулиране / изчистване                                           |
| ----------------------------- | ---------------------------------------------- | ----------------------------------------- | --------------------------------------------------------------- |
| Прекъсвач за доставчик        | `domain_circuit_breakers` + в паметта          | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                    |
| Период на изчакване за връзка | `rateLimitedUntil` във връзките към доставчици | `/api/rate-limits`, `/api/providers/[id]` | (активира се отново отложено; изчистете чрез PUT за доставчика) |
| Блокиране на модел            | Регистър в паметта за наличност на моделите    | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                        |

`PATCH /api/resilience` приема презаписвания за прекъсвачите на доставчици в `providerBreaker.oauth` и `providerBreaker.apikey`. Всеки профил поддържа `degradationThreshold`, `failureThreshold` и `resetTimeoutMs`; същите полета са достъпни в Табло → Настройки → Устойчивост.

```bash
# Изчистване на блокирането за един модел
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Изчистване на всички блокирания
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

За пълна концептуална справка и стойностите по подразбиране на прекъсвачите вижте [`CLAUDE.md`](../../CLAUDE.md) → „Състояние на устойчивостта по време на изпълнение“ и [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Опашка при ограничение на честотата и защитен механизъм за автоматично активиране

- **Поддържан начин за запис**: `POST /api/rate-limits` с тяло `{"connectionId": "<id>", "enabled": true|false}` е поддържаната крайна точка за управление за включване или изключване на защитата от ограничение на честотата за дадена връзка. `PUT /api/providers/[id]` умишлено не променя и не превключва `rateLimitProtection` (#11278).
- **Семантика на `enabled: false`**: Задаването на `enabled: false` премахва изричната защита за връзката, но **не** изключва активна връзка с API ключ от глобалния защитен механизъм за автоматично активиране (`autoEnableApiKeyProviders = true`). В `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) `false` и `undefined` са еквивалентни; активните връзки с API ключ без изрично зададена защита остават защитени от механизма за автоматично активиране.
- **Глобално деактивиране**: За да използвате връзки с API ключ без опашки за ограничение на честотата, деактивирайте защитния механизъм глобално чрез `RATE_LIMIT_AUTO_ENABLE=false` (променлива на средата) или `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Настройки → Устойчивост / `PATCH /api/resilience`).

## MCP сървър

OmniRoute включва вграден сървър за Model Context Protocol с 3 транспорта (stdio, SSE, streamable-http) и инструменти с ограничен обхват. Крайните точки на таблото по-долу четат данни за състоянието/одита и препредават заявките към HTTP транспортите.

| Метод | Път | Описание |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | Пулс, транспорт, онлайн състояние, последно извикване, най-използвани инструменти, процент на успеваемост за 24 ч. |
| GET | `/api/mcp/tools` | Списък с MCP инструменти с `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` |
| GET | `/api/mcp/sse` | Отваряне на SSE поток за SSE транспорта (връща `503`, ако MCP е деактивиран или транспортът не съвпада) |
| POST | `/api/mcp/sse` | Изпращане на JSON-RPC кадър чрез SSE транспорта |
| GET | `/api/mcp/stream` | Отваряне на SSE страната на Streamable HTTP транспорта (съобщения, инициирани от сървъра) |
| POST | `/api/mcp/stream` | Изпращане на JSON-RPC кадър чрез Streamable HTTP транспорта |
| DELETE | `/api/mcp/stream` | Прекратяване на Streamable HTTP сесия |
| GET | `/api/mcp/audit` | Заявка към одитния журнал — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | Обобщена одитна статистика (общи стойности, процент на успеваемост, средна продължителност, най-използвани инструменти) |

**Удостоверяване:** транспортите `sse`/`stream` използват специфичния за MCP механизъм за удостоверяване (Bearer API ключ с обхват `mcp`); маршрутите `status`/`tools`/`audit*` са достъпни за четене от таблото (не се изисква допълнително удостоверяване освен достъп до хоста на таблото).

> И двата HTTP транспорта се управляват от `settings.mcpEnabled` и `settings.mcpTransport` — несъответствие на транспорта връща `400`, а деактивирано състояние на MCP връща `503`.

## A2A сървър

OmniRoute предоставя A2A (Agent-to-Agent) крайна точка за JSON-RPC 2.0, както и REST обвивка за преглед и използване в таблото за управление.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # незадължително, освен ако OMNIROUTE_API_KEY не е зададен
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Поддържани методи (всички се управляват от `settings.a2aEnabled`):

| Метод            | Описание                                                            |
| ---------------- | ------------------------------------------------------------------- |
| `message/send`   | Синхронно изпълнение на умение; връща `{task, artifacts, metadata}` |
| `message/stream` | Поточно SSE изпълнение на същия набор от умения                     |
| `tasks/get`      | Извлича задача по `taskId`                                          |
| `tasks/cancel`   | Отменя задача по `taskId`                                           |

Вградени умения: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Карта на агента

```bash
GET /.well-known/agent.json
```

Връща публичната A2A карта на агента (име, описание, възможности, каталог с умения, схема за удостоверяване) — кешира се публично за 1 ч. Не се изисква удостоверяване.

### REST помощни крайни точки

| Метод | Път                          | Описание                                                                                                               |
| ----- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/a2a/status`            | Състояние на A2A + статистика за задачите + обобщение на кешираната карта на агента                                    |
| GET   | `/api/a2a/tasks`             | Изброява задачите — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST  | `/api/a2a/tasks`             | (Не е реализирано като REST помощна крайна точка — създавайте чрез JSON-RPC `message/send`)                            |
| GET   | `/api/a2a/tasks/[id]`        | Извлича една задача                                                                                                    |
| POST  | `/api/a2a/tasks/[id]/cancel` | Отменя задача                                                                                                          |

**Удостоверяване:** REST помощните крайни точки работят без удостоверяване за управление (могат да се четат от таблото за управление); JSON-RPC маршрутът `/a2a` използва Bearer `OMNIROUTE_API_KEY`, ако е конфигуриран.

## Удостоверяване

Вижте [Удостоверяване за управление](../guides/MANAGEMENT-AUTH.md) за четирите
групи идентификационни данни (сесия на таблото, локален CLI токен, `oma_live_…` токен за
достъп, API ключ с обхват за управление) и по какво се различават от ключовете за инференция.

- Маршрутите на таблото (`/dashboard/*`) използват бисквитката `auth_token`
- При влизане се използва запазеният хеш на паролата; като резервен вариант се използва `INITIAL_PASSWORD`
- `requireLogin` може да се превключва чрез `/api/settings/require-login`
- Маршрутите `/v1/*` могат да изискват Bearer API ключ, когато `REQUIRE_API_KEY=true`
- „токен за управление“ / „API ключ с обхват за управление“ в тази справка означава една от групите в това ръководство — не допълнителен недефиниран тип тайна

> **Несъвместима промяна (v3.8.0)** — `/api/v1/agents/tasks/*` и крайните точки за управление на периода на изчакване вече изискват **удостоверяване за управление** (бисквитка `auth_token` на таблото или API ключ с обхват за управление). Клиентите, които преди са извиквали тези маршрути без удостоверяване, ще получат `401 Unauthorized`. Вижте комит `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
