## Chatvoltooiingen

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Aangepaste headers

| Header                   | Richting | Beschrijving                                                                                                                                                                                                                                                      |
| ------------------------ | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Aanvraag | Stel in op `true` om de cache te omzeilen                                                                                                                                                                                                                         |
| `x-omniroute-no-memory`  | Aanvraag | Stel in op `true` om geheugen- en vaardigheidsinjectie voor deze aanvraag over te slaan (werkt zoals no-cache en voorkomt de token-/kostenoverhead per aanroep)                                                                                                   |
| `X-OmniRoute-Progress`   | Aanvraag | Stel in op `true` voor voortgangsgebeurtenissen                                                                                                                                                                                                                   |
| `X-Session-Id`           | Aanvraag | Sticky sessiesleutel voor externe sessieaffiniteit                                                                                                                                                                                                                |
| `x_session_id`           | Aanvraag | Variant met underscores wordt ook geaccepteerd (directe HTTP)                                                                                                                                                                                                     |
| `X-OmniRoute-Session-Id` | Aanvraag | Door de aanroeper opgegeven sessie-/conversatietag (wordt ook aan het geheugen doorgegeven). Indien aanwezig, wordt deze ongewijzigd opgeslagen in `call_logs.session_tag` voor kostentoerekening per sessie (#8249) — wordt nooit gegenereerd als deze ontbreekt |
| `Idempotency-Key`        | Aanvraag | Sleutel voor deduplicatie (venster van 5 seconden)                                                                                                                                                                                                                |
| `X-Request-Id`           | Aanvraag | Alternatieve deduplicatiesleutel                                                                                                                                                                                                                                  |
| `x-omniroute-connection` | Aanvraag | Koppel een aanvraag voor één model aan één providerverbinding (account) via de id ervan — zie [Account vastzetten per aanvraag](#account-pinning-per-request)                                                                                                     |
| `X-OmniRoute-Cache`      | Antwoord | `HIT` of `MISS` (zonder streaming)                                                                                                                                                                                                                                |
| `X-OmniRoute-Idempotent` | Antwoord | `true` indien gededupliceerd                                                                                                                                                                                                                                      |
| `X-OmniRoute-Progress`   | Antwoord | `enabled` als voortgangsregistratie is ingeschakeld                                                                                                                                                                                                               |
| `X-OmniRoute-Session-Id` | Antwoord | Effectieve sessie-ID die door OmniRoute wordt gebruikt                                                                                                                                                                                                            |
| `X-OmniRoute-Request-Id` | Antwoord | Correlatie-ID van de aanvraag (indien bekend)                                                                                                                                                                                                                     |
| `X-OmniRoute-Version`    | Antwoord | Buildversie van OmniRoute (altijd aanwezig)                                                                                                                                                                                                                       |
| `X-OmniRoute-Cost-Saved` | Antwoord | Het bedrag in USD dat dankzij de cache is bespaard bij een HIT (alleen bij cachetreffers)                                                                                                                                                                         |
| `X-OmniRoute-Decision`   | Antwoord | Routeringstracering: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` is de combostrategie, of `single` voor een aanvraag zonder combo) — altijd aanwezig in voltooiingsantwoorden                                                                   |

> Nginx-opmerking: als u afhankelijk bent van headers met underscores (bijvoorbeeld `x_session_id`), schakel dan `underscores_in_headers on;` in.

#### Account per request vastzetten

Wanneer een provider meerdere verbindingen (accounts of sleutels) heeft, kiest OmniRoute er normaal gesproken één
via zijn strategie voor accountselectie. Een request kan in plaats daarvan één specifieke verbinding vastzetten
met de header `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Waar u de id kunt vinden.** Open de providerpagina in het dashboard
  (**Dashboard → Providers → <provider>**) en klik op de id-chip `xxxxxxxx…` in een verbindingsrij
  — hierdoor wordt de volledige verbindings-id gekopieerd.
- **Welke requests deze respecteren.** Requests voor één model (`provider/model`) op
  `/v1/chat/completions`, `/v1/messages` en `/v1/responses`. Combo's negeren de header: zet
  in plaats daarvan per combostap een account vast via de eigen verbinding van die stap.
- **Het vastzetten is strikt, geen voorkeur.** De vastgezette verbinding wordt exclusief gebruikt. Een
  fout binnen het request registreert de cooldown van het account, maar schakelt **niet** over naar een
  ander account van dezelfde provider.
- **Cooldown en quotum heffen de vastzetting op.** Zolang de vastgezette verbinding in een cooldown zit,
  het quotum is uitgeput of de verbinding door een quotumbeleid wordt geblokkeerd, vallen latere requests terug op de
  andere verbindingen van de provider, precies zoals niet-vastgezet verkeer.
- **Onbekende of uitgeschakelde id's mislukken.** Een id die zich niet in de actieve pool van de provider bevindt (verwijderd,
  gedeactiveerd of behorend tot een andere provider), laat geen geschikt account over, waardoor het request
  mislukt in plaats van ongemerkt elders te worden gerouteerd.

Claude Code verzendt aangepaste headers via `ANTHROPIC_CUSTOM_HEADERS`. Plaats deze in het `env`-blok
van `~/.claude/settings.json`, of in een `.claude/settings.json` op projectniveau om per project een ander
account vast te zetten:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Bron: `src/sse/handlers/chat.ts` (header uitlezen), `src/sse/services/auth.ts` en
`src/sse/services/sessionAffinityPin.ts` (vrijgave van de vastzetting en de controle op ontbreken in de pool).

> **Headers voor kostentelemetrie:** succesvolle niet-streaming-responses bevatten ook de set `X-OmniRoute-*` voor kostentelemetrie — `X-OmniRoute-Response-Cost` (USD, vast aantal van 10 decimalen; `0.0000000000` voor gratis/niet-geprijsd), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` en `X-OmniRoute-Fallback-Attempts` (alleen wanneer > 0), plus `X-OmniRoute-Request-Id` en `X-OmniRoute-Version`. Deze worden gegenereerd door chat-completions, `/v1/responses`, `/v1/messages` **en de media-endpoints** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` en `/v1/moderations` (altijd kosten van `0`). Mediakosten worden per modaliteit berekend (per afbeelding, per seconde, per teken, per zoekeenheid) wanneer prijsinformatie beschikbaar is; anders zijn ze `0` (fail-open).

> **Kostensemantiek bij cachetreffers:** bij een HIT in de semantische cache (`X-OmniRoute-Cache-Hit: true`) wordt geen upstream-aanroep uitgevoerd, dus is `X-OmniRoute-Response-Cost` gelijk aan `0.0000000000` (de **incrementele** kosten voor het leveren van de treffer). De oorspronkelijke kosten/de kosten die anders zouden zijn gemaakt, worden afzonderlijk gerapporteerd in `X-OmniRoute-Cost-Saved`. Facturatieprocessen moeten `X-OmniRoute-Response-Cost` optellen (treffers kosten niets); voor cacheanalyses kan `X-OmniRoute-Cost-Saved` worden geaggregeerd.

## Exclusieve beheerde sessieleases

Exclusieve leasing van beheerde sessies is een optioneel, clientneutraal routeringscontract: één actieve eigenaar
houdt één in aanmerking komende OmniRoute-verbinding vast. Hiermee wordt geen model geleaset, OAuth is niet
vereist, er wordt geen specifieke client geïdentificeerd en er is geen specifieke provider vereist.

De API-sleutel waarmee wordt geauthenticeerd, moet het bereik `lease:exclusive` en een expliciete, niet-lege
lijst `allowedConnections` hebben. De grens van de databasemutatie dwingt beide velden gezamenlijk af bij het
maken van sleutels en gedeeltelijke updates.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Geslaagde antwoorden voor verkrijgen, verlengen en vrijgeven bevatten tijdstempels, `state` en de exacte positieve
`generation`, maar nooit de geselecteerde verbinding of referenties. Bij verlengen en vrijgeven wordt de
generatie in de JSON-body opgegeven:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Een eigenaar van een actieve lease kan expliciet privacyveilige weergavemetadata voor de huidige koppeling opvragen:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Deze optionele statusactie wordt binnen één databasetransactie afgeschermd door de ondoorzichtige eigenaar,
de geauthenticeerde beheerde API-sleutel en de exacte actieve generatie. `displayName` is uitsluitend de
bijgesneden geconfigureerde verbindingsnaam; de waarde is `null` wanneer er geen veilige geconfigureerde naam
bestaat. OmniRoute gebruikt nooit een e-mailadres of gegenereerde accountidentiteit als vervanging. De
providerwaarde is een niet-gevoelig weergavelabel en nooit een gegenereerde compatibele-provider-ID.
Referenties, tokens, cookies, onbewerkte verbindings- of API-sleutel-ID's, eigenaarshashes,
afschermingsgeheimen en interne routeringsgegevens worden uitgesloten.

Opzoekacties met een verkeerde sleutel, verkeerde eigenaar, verouderde generatie of een ontbrekende, verlopen,
vrijgegeven of ongeldig gemaakte lease retourneren allemaal dezelfde fout `409 LEASE_FENCE_STALE`, zonder
verbindingsmetadata. Een client die het antwoord voor wachten op capaciteit heeft ontvangen, heeft geen actieve
koppeling die kan worden geïnspecteerd. Wanneer de routering een actieve lease naar een andere verbinding
overzet, blijft dezelfde generatie geldig en retourneert de status atomair de nieuwe koppeling, nooit de oude.
Bestaande clients blijven ongewijzigd, omdat antwoorden voor verkrijgen, verlengen, vrijgeven en wachten hun
eerdere vorm behouden.

Dit servercontract wijzigt de standaard-`/status` van OpenAI Codex niet. De standaardversie van Codex rapporteert
momenteel de modelprovider en de ingebouwde authenticatie-/accountstatus, maar geeft geen willekeurige aangepaste
provideraccountmetadata weer; een latere clientintegratie moet deze actie aanroepen en bepalen hoe
`connection.displayName` wordt weergegeven.

Elk beheerd inferentieverzoek levert vervolgens beide besturingsheaders:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

De exacte eigenaar, generatie, actieve verbinding en geauthenticeerde API-sleutel worden direct vóór elke
ondersteunde upstream-poging afgeschermd. Het opnieuw gebruiken van de eigenaar en generatie met een andere
sleutel mislukt, zelfs wanneer die sleutel dezelfde verbinding toestaat. Onbewerkte eigenaarswaarden worden
niet opgeslagen, gelogd, bewaard in de momentopname van het verzoek of upstream doorgestuurd.

Tijdelijke capaciteitsconcurrentie retourneert HTTP `429` met `Retry-After` en:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Dit antwoord betekent uitsluitend dat de normale set met in aanmerking komende verbindingen niet leeg was en
dat elke vrije kandidaat door een buitenlandse actieve lease werd vastgehouden. Niet-ondersteunde
modellen/providers, niet-overeenkomend beleid, afkoelperioden, quota, statusproblemen en andere normale
geschiktheidsfouten behouden hun bestaande OmniRoute-antwoorden.

### `x-omniroute-compression`

Overschrijving van het compressieplan per verzoek. Heeft de hoogste prioriteit — hoger dan de
routeringscombo-overschrijving, het actieve profiel, de automatische trigger en de standaardinstelling van het
paneel. Waarden:

| Waarde        | Effect                                                                                                        |
| ------------- | ------------------------------------------------------------------------------------------------------------- |
| `off`         | Geen compressie voor dit verzoek.                                                                             |
| `default`     | Het van het paneel afgeleide standaardprofiel (negeert het actieve profiel). Lossy-engines blijven uit.       |
| `safe`        | Alleen deduplicatie en het samenvouwen van witruimte.                                                         |
| `allow-lossy` | Behoud het operatorplan voor dit verzoek, inclusief samenvattingen en stijlherschrijvingen.                   |
| `engine:<id>` | Eén engine, indien ingeschakeld, bijvoorbeeld `engine:rtk`. Optionele activering per verzoek voor die engine. |
| `<combo>`     | Een benoemde combo, eerst vergeleken op naam (hoofdletterongevoelig) en daarna op ID.                         |

Opmerkingen:

- Onbekende waarden worden genegeerd (het verzoek wordt nooit afgewezen); de oplossing valt terug op de normale operatorprioriteit.
- Als meerdere combo's dezelfde naam hebben, geeft u de combo-**id** door voor een deterministische overeenkomst.
- Een combo met de naam `off` of `default` kan niet op naam worden geselecteerd (deze trefwoorden worden eerst geïnterpreteerd); verwijs naar zo'n combo via de ID ervan.
- De hoofdschakelaar voor compressie is een harde begrenzing: wanneer compressie globaal is uitgeschakeld, kan deze header compressie niet inschakelen.

Het toegepaste plan wordt teruggegeven in de antwoordheader:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

waarbij `<source>` een van `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` of `off` is.

## Embeddings

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Beschikbare providers: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Catalogus-id's hebben de indeling `provider/model` (voorbeeld: `jina-ai/jina-embeddings-v5-omni-small`). Losse Jina-model-id's die in het register voorkomen (bijvoorbeeld `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`), worden ook herkend. Voor embed/rerank/classify/segment van Jina worden eerst de `jina-ai`-referenties uit het dashboard gebruikt; `JINA_AI_API_KEY` dient alleen als terugvaloptie wanneer er geen dashboardsleutel bestaat. De kaart `jina-reader` is uitsluitend bedoeld voor Reader / `r.jina.ai` (`POST /v1/web/fetch`) en levert nooit embeddings of reranking.

Registermodellen die multimodale ondersteuning vermelden, accepteren ook maximaal 32 providerneutrale gestructureerde
items. De mediatypen voor items zijn `text`, `image`, `audio`, `video` en `document`. Hun media-`source`
is `{"type":"url","url":"https://..."}` of
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
en de familie-alias `jina-ai/jina-embeddings-v5-omni` → omni-small) accepteert ook de native
EmbeddingsV5Request-documenten van Jina en **stuurt deze ongewijzigd door** naar `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Native `{ image | audio | video | pdf }`-waarden kunnen een openbare HTTPS-URL, een `data:`-URI of onbewerkte
base64 zijn. OmniRoute zet deze objecten niet om in tekenreeksen en haalt native afbeeldings-URL's niet op — Jina haalt
openbare media zelf op. Extra Jina-velden (`task`, `normalized`, `truncate`, `embedding_type`) worden
doorgestuurd. Jina-SKU's die alleen tekst ondersteunen, blijven niet-tekstdocumenten weigeren.

Beveiligings- en transportlimieten:

- Externe media-URL's moeten openbare HTTPS-URL's zijn. Canonieke `{type,source:url}`-items worden
  aan de serverzijde opgehaald (hervalidatie van omleidingen, time-out, groottelimieten, openbare DNS, vastzetten van verbindingen) en
  inline opgenomen vóór de provideraanroep. Jina-native `{image:"https://..."}`-items worden ongewijzigd doorgestuurd
  na dezelfde controle op openbare HTTPS; Jina haalt de URL op.
- Inline base64-media zijn beperkt tot 8 MiB gedecodeerd per item en 16 MiB gedecodeerd voor de hele aanvraag.

Providervertaling (canonieke items worden nooit ongewijzigd doorgestuurd):

- Multimodale Jina-modellen: elk item op het hoogste niveau wordt één object met een modaliteitssleutel
  (`text` / `image` / `audio` / `video` / `pdf`), waarbij data-URI's voor inline media worden gebruikt; één vector per
  item op het hoogste niveau.
- Gemini Embedding 2-familie: één array op het hoogste niveau wordt één native
  `models/{model}:embedContent`-aanvraag met `content.parts` (`text` of `inline_data`).
- llama.cpp (`llama-cpp/<model>`, elk model dat door de lokale server is geladen): canonieke `text`-items
  worden gewone tekenreeksen en `image` / `audio` / `video` worden elk één
  `{"content": [part]}`-object, waarbij de chatcontentonderdelen van llama-server (`image_url`,
  `input_audio` met indeling `wav` / `mp3` / `flac`, `input_video`) met inline gegevens worden gebruikt; één vector
  per item op het hoogste niveau. De server moet worden uitgevoerd met `--embedding --mmproj …`; zonder een projector
  weigert de server zelf media. `document` wordt niet ondersteund.
- Onbekende/dynamische modellen zonder expliciete modaliteitsmetadata weigeren gestructureerde invoer met HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Niet-ondersteunde combinaties van model en modaliteit retourneren HTTP 400 in plaats van het item te converteren. Uitbreidingsvelden buiten
de invoer voor verouderde tekenreeks-/tokenaanvragen worden nog steeds ongewijzigd doorgegeven.

```bash
# Alle embeddingmodellen weergeven
GET /v1/embeddings
```

## Afbeeldingen genereren

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Beschikbare providers zijn onder andere OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (lokaal), ComfyUI (lokaal).

`n` retourneert `n` afbeeldingen in `data[]`. Voor providers waarvan de upstream-API één afbeelding per aanroep retourneert
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), worden `n` afzonderlijke upstream-aanroepen uitgevoerd, met maximaal 4 gelijktijdige aanroepen. Een
vaste `seed` wordt met de aanroepindex verhoogd (`seed`, `seed + 1`, …), zodat de afbeeldingen verschillen maar
reproduceerbaar blijven. `n` is begrensd op 10. De aanvraag mislukt in haar geheel als een van de aanroepen mislukt. De lijst
met fan-out-indelingen is `SINGLE_IMAGE_FANOUT_FORMATS` in
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux hergebruikt de bestaande API-sleutelverbinding en accepteert de prefix `zenmux/` of `zm/`:

- `zenmux/openai/gpt-image-2` gebruikt de OpenAI Images API van ZenMux. Opties zijn onder andere `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` en `response_format`.
- Andere uitgevers, zoals `zm/meta/muse-image-1.0`, gebruiken het Vertex AI-`:predict`-
  eindpunt van ZenMux. `n` wordt toegewezen aan `sampleCount`, `aspect_ratio` aan `aspectRatio` en `image_size`
  (`1K`, `2K`, `4K`) aan `sampleImageSize`. Een `size` in pixels levert alleen een beeldverhouding op,
  geen gegarandeerde pixelafmetingen. Ondersteunde verhoudingen, resoluties en aantallen verschillen per model.
- `zm/inclusionai/ming-image-0.1-design` kiest zijn eigen afmetingen. Laat `size`,
  `aspect_ratio` en `image_size` weg; expliciete waarden retourneren HTTP 400. PNG, JPEG en WebP
  kunnen worden aangevraagd met `output_format`.

Deze integratie ondersteunt het genereren van afbeeldingen uit tekst, niet het bewerken van referentieafbeeldingen. Vertex-
uitvoer wordt genormaliseerd naar `data[].b64_json`; `response_format: "url"` retourneert een upstream-
HTTPS-URL of een base64-data-URL wanneer alleen afbeeldingsbytes beschikbaar zijn. Lege/gefilterde uitvoer
retourneert een fout in plaats van een leeg geslaagd resultaat. Modeltoegang is afhankelijk van het ZenMux-account.
Zie [de Vertex API van ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) en
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Alle afbeeldingsmodellen weergeven
GET /v1/images/generations
```

## OCR voor documenten

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` selecteert de OCR-provider via een prefix in de vorm `provider/model`; een model-id zonder prefix (bijv.
`mistral-ocr-latest`) wordt aan de geregistreerde provider gekoppeld, en wanneer `model` wordt weggelaten, wordt standaard
Mistral (`mistral-ocr-latest`) gebruikt. Geregistreerde providers (`open-sse/config/ocrRegistry.ts`):

| Provider-id                   | Model-id             | Waarde van `model`                                            | Opmerkingen                                                                                                          |
| ----------------------------- | -------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (of alleen `mistral-ocr-latest`) | Synchroon — het antwoord wordt rechtstreeks vanuit de enige upstream-aanroep geretourneerd.                          |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                   | Asynchroon upstream (`analyze` + polling) — zie hieronder.                                                           |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                       | Synchroon, via het partner-eindpunt `openapi/chat/completions` van Vertex AI — zie hieronder voor authenticatie/URL. |

Alle drie de providers antwoorden met dezelfde, op Mistral gebaseerde hoofdtekst:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Pollingproces van Azure Document Intelligence

De `analyze`-API van Azure Document Intelligence is asynchroon: de initiële aanvraag retourneert een
`Operation-Location`-header in plaats van een hoofdtekst, waarna het resultaat via polling moet worden opgevraagd. De handler
(`open-sse/handlers/ocr.ts`) vraagt die URL gedurende maximaal 30 pogingen elke seconde op, stopt onmiddellijk (en
blijft dus niet pollen) bij een pollantwoord dat niet `ok` is of een status `"failed"`, en retourneert `504` als de
bewerking na het verstrijken van het maximale aantal pogingen nog steeds wordt uitgevoerd. Het uiteindelijke Azure-antwoord wordt
genormaliseerd naar dezelfde `pages`/`markdown`-structuur die door Mistral wordt gebruikt voordat het aan de
aanroeper wordt geretourneerd, zodat clientcode geen speciale verwerking per provider nodig heeft.

### Authenticatie en eindpuntbepaling voor Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` hergebruikt dezelfde Vertex AI-authenticatie die OmniRoute al ondersteunt voor
chat-/afbeeldingsverkeer (`open-sse/executors/vertex.ts`): de API-sleutel van de verbinding is een
Service Account-JSON-referentie (die via de JWT-bearer-
flow wordt ingewisseld voor een kortlevend OAuth-toegangstoken) of een reeds uitgegeven OAuth-toegangstoken dat ongewijzigd wordt gebruikt. De URL van het upstream-eindpunt is het algemene
partner-eindpunt `openapi/chat/completions` van Vertex, opgebouwd uit het project en
de regio van de verbinding — een expliciete `providerSpecificData.project`/`providerSpecificData.region` heeft altijd voorrang;
anders wordt het project afgeleid van `project_id` in de Service Account-JSON en wordt voor de regio
standaard `us-central1` gebruikt. Beide waarden worden bepaald in `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) en gebruikt door
`src/app/api/v1/ocr/route.ts` voordat de aanvraag naar `handleOcr` wordt doorgestuurd.

## Modellen weergeven

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ Retourneert alle chat-, embedding- en afbeeldingsmodellen + combo's in OpenAI-indeling
```

### Model-id-prefixen (`?prefix=`)

De meeste modellen worden aangeboden onder een **providerprefix**. Welke prefix u krijgt, wordt bepaald door
de featureflag `MODELS_CATALOG_PREFIX_MODE` en kan **per aanvraag** worden overschreven met een
queryparameter — handig voor een client die een overzichtelijke lijst wil zonder de serverbrede
instelling voor alle anderen te wijzigen:

```bash
GET /v1/models?prefix=alias        # één id per model — de korte aliasprefix
GET /v1/models?prefix=dual         # beide vormen (serverstandaard)
GET /v1/models?prefix=canonical    # alleen de volledige provider-id-prefix
```

| Modus       | Genereert                                                | Opmerkingen                                                                                                                                                                                    |
| ----------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **en** `claude/claude-sonnet-4-6` | **Standaard.** Beide id's routeren naar hetzelfde model; behouden zodat clientconfiguraties waarin een van beide vormen hardgecodeerd is, blijven werken. Verdubbelt de catalogus ongeveer.    |
| `alias`     | `cc/claude-sonnet-4-6`                                   | Eén item per model. Providers zonder afzonderlijke alias genereren nog steeds hun item, zodat er niets verloren gaat.                                                                          |
| `canonical` | `claude/claude-sonnet-4-6`                               | Eén item per model onder de volledige provider-id-prefix. Providers zonder afzonderlijke alias (bijv. `antigravity/…`, `agy/…`) genereren hier ook hun enige id, zodat er niets verloren gaat. |

Een mirror in de modus `dual` kan ook zonder de queryparameter worden herkend: deze bevat een `parent`-veld
dat naar het primaire id verwijst.

Clients die een modelkiezer weergeven, moeten `?prefix=alias` aanvragen — dit is wat de
[OmniCopilot VS Code-extensie](../guides/VSCODE-COPILOT.md) doet.

### Detectiefilters (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` accepteert optionele detectiefilters. Zonder deze filters blijft het antwoord
ongewijzigd. Ze beperken de catalogus die de aanroeper al kan zien (API-sleutelmachtigingen worden eerst toegepast)
en worden uitgevoerd vóór de paginering in OpenAI-stijl met `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # elke vermelde mogelijkheid moet waar zijn
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # catalogus-`type`; rijen zonder type zijn `chat`
GET /v1/models?q=sonnet&limit=10                           # hoofdletterongevoelige overeenkomst op id of naam
```

| Parameter     | Waarden                                                                                             |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | niet-negatief geheel getal, vergeleken met `context_length`                                         |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 tekens                                                                                        |

Een onbekende waarde, of een `min_context` die geen niet-negatief geheel getal is (bijvoorbeeld `1.5`),
retourneert HTTP `400` en het bericht vermeldt de geldige waarden. Implementatie:
`src/app/api/v1/models/catalogFilters.ts`.

### Modellenvoorselectie (`POST /v1/models/query`)

`POST /v1/models/query` retourneert een korte, deterministische lijst uit dezelfde catalogus, met dezelfde
authenticatie en zichtbaarheid per sleutel als `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Elk veld is optioneel. `capabilities` en `exclude` accepteren een array of een door komma's gescheiden tekenreeks;
`max_output` wordt vergeleken met `max_output_tokens`. Resultaten worden eerst op `owned_by` en vervolgens op `id` gesorteerd.
`limit` is standaard `20` en waarden boven `100` worden begrensd op `100`. Ongeldige JSON, een onbekend
veld of een ongeldige waarde retourneert HTTP `400`.

### Afzonderlijk verborgen chatmodellen

Een model dat op de providerpagina als **Verborgen** is gemarkeerd, wordt uitgesloten van de catalogus en afgewezen
met HTTP `404` / `model_not_found` wanneer het expliciet wordt aangevraagd. De controle gebruikt de herleide
provider en het herleide model, met inbegrip van provideraliases, nodeprefixen van compatibele providers en
standaardwaarden van verbindingen. Een combo slaat verborgen doelen over en kan een zichtbaar zustermodel gebruiken; wanneer er geen
uitvoerbaar doel overblijft, wordt dezelfde foutcode geretourneerd. Het zichtbaar maken wordt bij de volgende
aanvraag van kracht. Zichtbaarheidsoverschrijvingen die uitsluitend voor afbeeldingen gelden, verbergen het chatmodel met hetzelfde id niet.

Deze individuele modelinstelling staat los van de
[toestaan/weigeren-lijsten voor modelblootstelling](../routing/MODEL_EXPOSURE_LIST.md), die catalogusvermeldingen
en kandidaten voor automatische routering filteren, terwijl expliciete dispatch behouden blijft. Modelmachtigingen voor API-sleutels
blijven onafhankelijk van toepassing. De standaardmodus voor catalogusprefixen blijft `dual`.

### Modelvarianten zonder denken

Voor Claude-modellen die denken ondersteunen, biedt `/v1/models` ook een **variant zonder denken** aan waarvan het id wordt voorafgegaan door `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Als deze id wordt geselecteerd (bijvoorbeeld in een Claude Code-configuratie die altijd een `thinking`-blok toevoegt), wordt deze terugvertaald naar het echte `<provider>/<model>`, waarbij reasoning wordt onderdrukt — `thinking:{type:"disabled"}` op het `/v1/messages`-pad, of waarbij de velden `reasoning`/`reasoning_effort` worden weggelaten op het `/v1/chat/completions`-pad. De variant wordt alleen vermeld voor modellen uit de Claude-familie die thinking ondersteunen **en** `disabled` respecteren (dus bijvoorbeeld modellen die uitsluitend adaptive ondersteunen en `disabled` afwijzen, worden uitgesloten). Operators kunnen de variant per model geforceerd in- of uitschakelen via `ModelSpec.noThinkingAlias`.

| POST    | `/v1/sound-generation`      | Systeemeigen audiobytes                        | `elevenlabs`                       |

Deze endpoints vormen een aanvulling op de bestaande routes `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` en `/v1/speech-to-text`. Systeemeigen JSON-velden
en queryparameters zoals `output_format` en `enable_logging` blijven behouden.
Antwoorden van `/v1/music/detailed` behouden hun multipart-grenzen; verwerk ze als multipart.
`/v1/music/detailed/stream` retourneert `text/event-stream` met compositiemetadata en
base64-audiofragmenten in SSE-events. Alle zes routes ondersteunen CORS-preflight.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Een kort geluidseffect. Duur: 0,5 tot 30 seconden.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# De muziekduur wordt uitgedrukt in milliseconden: 3000 tot 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Gebruik `/v1/music/stream` met dezelfde JSON-body voor incrementele audiobezorging. Compositie
accepteert precies één van `prompt` of `composition_plan`; `/v1/music/plan` vereist `prompt`
en accepteert optioneel `source_composition_plan`. De systeemeigen schema's behouden aanvullende
providervelden, zodat versies van compositieplannen en opties voor fine-tuning ElevenLabs bereiken.

Het geïntegreerde endpoint `/v1/music/generations` accepteert ook `elevenlabs/music_v1`,
`elevenlabs/music_v2` en `elevenlabs/music_v2_5`. Met een actieve ElevenLabs-verbinding
worden deze modellen beschikbaar gesteld via de muziekcatalogus. Dit endpoint retourneert
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Het veld `duration` wordt uitgedrukt in
seconden en wordt toegewezen aan `music_length_ms`; een expliciete `music_length_ms` heeft voorrang.
`instrumental` wordt toegewezen aan `force_instrumental`, waarbij het systeemeigen veld voorrang heeft.
Gebruik de systeemeigen streaming-endpoints voor streaming en het systeemeigen compositie-endpoint
voor aanvragen die uitsluitend door een compositieplan worden aangestuurd.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Beperkingen voor endpoints, modellen, budgetten en verbindingen worden toegepast voordat een upstream-aanroep plaatsvindt. Systeemeigen
routes retourneren upstream-statuscodes en foutbody's ongewijzigd, waaronder `402` voor een
abonnementsbeperking en `429` voor een quotalimiet. De headers `character-cost`, `song-id`, `request-id` en `retry-after`
blijven behouden wanneer ze aanwezig zijn. Een gratis creditsaldo garandeert geen toegang tot elk
muziekmodel, uitvoerformaat of elke API-functie: ElevenLabs bepaalt de rechten voor elke aanvraag.
Het geïntegreerde endpoint behoudt foutstatuscodes in de genormaliseerde foutenvelop van OmniRoute.

Upstream-contracten: [geluidseffecten](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[muziekcompositie](https://elevenlabs.io/docs/api-reference/music/compose) en
[details van gestreamde muziek](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

> **Rerank-providernodes:** `POST /v1/rerank` routeert ook naar OpenAI-compatibele providernodes
> (oMLX, vLLM, Infinity, TEI achter een gateway, …) die worden geadresseerd als `<node-prefix>/<model>`. Loopback-
> nodes (`localhost`, `127.0.0.1`, `172.16.0.0/12`) komen altijd in aanmerking, evenals hostnamen die de
> operator vermeldt in `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (bijvoorbeeld een Docker/Compose-servicenaam zoals
> `http://reranker:8080/v1`; deze worden rechtstreeks aangeroepen, nooit via `HTTP(S)_PROXY` of de
> vastgezette proxy van een verbinding). Nodes op elke andere
> host — een machine op het LAN of een Tailscale-peer — komen alleen in aanmerking wanneer de operator de
> featureflag `RERANK_REMOTE_PROVIDER_NODES` inschakelt **en** de basis-URL van de node voldoet aan het beleid voor
> uitgaande provider-URL's (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> De rerankstap van de geheugenengine roept deze route aan via
> loopback, dus dezelfde regel is van toepassing op `rerankProviderModel` in de geheugeninstellingen.
>
> **Vormen van lokale servers:** de node wordt aangeroepen via `<base>/v1/rerank` en, bij een 404, via `<base>/rerank`
> (Infinity, TEI). De upstream-body bevat zowel de Cohere/OpenAI-spelling (`documents`,
> `return_documents`) als de TEI-spelling (`texts`, `return_text`), en de upstream-respons wordt
> genormaliseerd naar de Cohere-envelope: TEI's kale `[{index, score, text}]`, `{results: [{index, score}]}`
> van eenvoudige gateways en Voyage-achtige `{data: [...]}` worden allemaal naar de client teruggestuurd als
> `{results: [{index, relevance_score, document?}]}`, gesorteerd op score en beperkt tot `top_n`.

> **Detectie van providernodes:** modellen op een OpenAI-compatibele providernode verschijnen in `GET /v1/models`
> onder de nodeprefix. Rijen zonder endpointmetadata (typisch voor lokale `/v1/models`-lijsten)
> nemen de `apiType` van de node over, zodat de modellen van een `embeddings`-node `type: "embedding"` hebben en de
> modellen van een `rerank`-node `type: "rerank"` in plaats van standaard chat te gebruiken; een expliciete
> `supportedEndpoints` in een gesynchroniseerde of handmatig toegevoegde rij heeft nog steeds voorrang.

### Exa- en Tavily-`provider_options`

Exa en Tavily lezen providerspecifieke velden uit een geneste verzameling:
`provider_options.exa` (of `provider_options["exa-search"]`) en `provider_options.tavily`
(of `provider_options["tavily-search"]`). Alleen de onderstaande sleutels worden doorgestuurd. Elke sleutel wordt
gecontroleerd aan de hand van het eigen Zod-schema in `open-sse/handlers/search/providerOptionsPassthrough.ts`,
en een sleutel met het verkeerde type wordt verwijderd. Elke andere sleutel wordt genegeerd, waaronder authenticatie, basis-URL,
`stream` en `outputSchema`. De platte sleutels die door andere providers worden gebruikt (`cx`, `depth`, ...) werken
zoals voorheen.

| Provider | Velden op het hoogste niveau                                                                                                                                                                                                                                                                                                                                              | Genest                                                                                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Exa      | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (platte primitieve waarden), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                    | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` samengevoegd over de standaardwaarde `{ text: true, highlights: true }` |
| Tavily   | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                              |

De generieke velden hebben altijd voorrang: `query`, `max_results`, `filters` (domeinen), `country` en het
onderwerp dat is afgeleid van `search_type`. Bij Exa behoudt `search_type: "news"` de waarde `category: "news"`.
Tavily accepteert ook `search_type: "finance"` (`topic: "finance"`).

De generieke `time_range` wordt nu aan beide providers doorgegeven: Exa ontvangt `startPublishedDate` (ISO-

`usage.search_cost_usd`.

## Web Fetch-API

Extraheer inhoud uit een URL via een geconfigureerde web-fetch-provider (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, dezelfde API-sleutel als Parallel Search) retourneert uitsluitend
Markdown — elke andere `format` resulteert in een `400` — en beperkt de inhoud tot 100.000 tekens. Wanneer
de doelpagina zelf niet kan worden geëxtraheerd, rapporteert de upstream dit binnen een HTTP 200;
OmniRoute geeft dit door als een `422` met een vaste melding.

| Methode | Pad             | Beschrijving                                                       |
| ------- | --------------- | ------------------------------------------------------------------ |
| POST    | `/v1/web/fetch` | Een URL ophalen/scrapen — body gevalideerd door `v1WebFetchSchema` |

**Authenticatie:** Bearer-API-sleutel (`extractApiKey` + `isValidApiKey`). Beleid wordt afgedwongen via `enforceApiKeyPolicy`.

**Quotabewuste fallback (#8297):** wanneer geen expliciete `provider` is opgegeven, wordt de pool
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) in een vaste
prioriteitsvolgorde doorlopen (fill-first) — een provider die wegens een snelheidslimiet niet beschikbaar maar wel geconfigureerd is, wordt overgeslagen
in plaats van het verzoek direct af te breken, en een opnieuw te proberen/quota-upstreamfout
(altijd HTTP 429; 402/403 voor quota-achtige gratis niveaus van Firecrawl/Tavily/TinyFish —
niet voor Jina Reader, en nooit voor een gewone 400-fout wegens een ongeldig verzoek) valt tijdens het verzoek terug op de
volgende nog niet geprobeerde provider met geconfigureerde referenties. Wanneer alle providers in de
pool zijn uitgeput, retourneert het endpoint één `429` (met een `Retry-After`-
header) in plaats van de eerdere generieke `400`. Wanneer expliciet om een `provider` wordt
gevraagd, is er **geen** stille fallback — een expliciete provider die wegens een snelheidslimiet niet beschikbaar is of faalt,
geeft zijn eigen fout door (`429` bij een snelheidslimiet, anders de upstream-
status).

## WebSocket-streaming

```bash
GET /v1/ws?handshake=1
```

Valideert een WebSocket-upgradehandshake en retourneert de voorbeeldberichten van het wire-protocol (`request`, `cancel`). Werkelijke WS-frames worden verwerkt door de meegeleverde WS-server buiten de routetabel van Next.js.

**Authenticatie:** Bearer-API-sleutel tijdens de handshake.

### Responses-API via WebSocket (alleen codex)

```bash
# Dezelfde host:poort als de HTTP-API (standaard 20128); upgrade de verbinding:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (of: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Het eerste frame MOET response.create zijn:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Een Responses-API-over-WebSocket-proxy is **uitsluitend met `codex`** verbonden (ChatGPT-
backend). Deze luistert op dezelfde poort als de API/het dashboard via de paden `/v1/responses`,
`/responses` en `/api/v1/responses`. Bij het eerste `response.create`-frame
authenticeert en initialiseert deze via de interne `codex-responses-ws`-bridge, selecteert deze een
codex-OAuth-verbinding en tunnelt deze naar `wss://chatgpt.com/backend-api/codex/responses`
via het `wreq-js`-transport. **Niet-codex-modellen worden geweigerd** (`codex_ws_provider_required`).
Gebruik voor quota-share-routering `model: "qtSd/<group>/codex/<model>"`. Geïmplementeerd in
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Authenticatie:** Bearer-API-sleutel tijdens de handshake. De meegeleverde HTTP-server (`server-ws.mjs`)
moet het actieve entrypoint zijn (dat is standaard het geval wanneer `app/server-ws.mjs` bestaat).

#### Model-id: gebruik de kale ChatGPT-id (zonder het voorvoegsel `codex/`)

De OpenAI **Codex CLI** valideert de modelnaam aan de clientzijde wanneer
`supports_websockets = true` en **weigert ids met een providervoorvoegsel**, zoals
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Verzend de **kale** id (bijvoorbeeld `gpt-5.5`). De bridge van OmniRoute is
uitsluitend voor codex, waardoor deze een kale id opnieuw als codex-model resolveert
(`resolveCodexWsModelInfo`) voordat er upstream wordt getunneld — hoewel een kale
`gpt-5.5` via HTTP anders naar een andere provider zou worden gerouteerd.

#### De OpenAI Codex CLI configureren

Laat de Codex CLI naar OmniRoute verwijzen door een aangepaste provider met WebSocket-
ondersteuning toe te voegen aan `~/.codex/config.toml` (gebruik een afzonderlijke `CODEX_HOME` om te voorkomen dat
een bestaande configuratie wordt gewijzigd):

```toml
model = "gpt-5.5"                 # kale id — NIET "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # geen afsluitende slash; de WS-URL wordt afgeleid (gebruik https/wss in productie)
wire_api = "responses"                    # de enige ondersteunde waarde sinds februari 2026
supports_websockets = true                # schakelt het Responses-over-WS-transport in
env_key = "OMNIROUTE_API_KEY"             # bevat de OmniRoute-API-sleutel (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # een OmniRoute-API-sleutel (elke sleutel als REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

De CLI upgradet `base_url + /responses` naar een WebSocket en OmniRoute tunnelt deze
naar de geselecteerde codex-OAuth-verbinding. End-to-end gevalideerd tegen de lokale
server: ChatGPT retourneert `codex.rate_limits` + `response.created` en streamt de

## Zelfbedieningsgebruik (`/api/usage/om-usage`)

Elke API-sleutel kan **zijn eigen** gebruik en quota's bekijken — zonder beheerdersauthenticatie. Dit is het endpoint dat een
client (CLI, het OmniCopilot-paneel) gebruikt om een sleutelhouder diens uitgaven te tonen.

```bash
# Tekstvorm (het historische contract — platte tekst voor een terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Gestructureerde vorm — wat een UI gebruikt
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Voor de sleutel moet **`allowUsageCommand`** zijn ingeschakeld (standaard uitgeschakeld — de API-sleutelbeheerder
van het dashboard schakelt dit per sleutel in of uit). Zonder deze instelling antwoordt het endpoint met `403`.

`?format=json` retourneert een gediscrimineerde structuur, zodat een aanroeper nooit een gegevensveld van een
weigering leest. Bij succes:

```jsonc
{
  "allowed": true,
  // alleen aanwezig wanneer voor de sleutel gebruikslimieten per sleutel zijn ingesteld (dagelijks/wekelijks in USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // de momentopname van het geselecteerde providerquotum, of null wanneer er nog niets in de cache staat:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // de momentopname van elke verbinding, zodat een UI meerdere providers naast elkaar kan weergeven:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Bij weigering (`401` ongeldige sleutel / `403` niet toegestaan) retourneert dezelfde route
`{ "allowed": false, "error": { "message": "…" } }` — een aanwezige maar lege `personal`/`provider`
(sleutel toegestaan, nog niets bekend) is een andere toestand dan een weigering, en alleen de JSON-vorm
maakt daartussen onderscheid.

**Authenticatie:** de eigen Bearer-API-sleutel van de aanroeper, gevalideerd met `isValidApiKey` — dit is _niet_ het
beheeroppervlak (`/api/keys/…`), dat beschermd blijft door `requireManagementAuth`.

### Ruwe versus voor de grenswaarde gecorrigeerde quotumpercentages

Bij het gebruik van `/api/usage/om-usage` moeten aanroepers rekening houden met het verschil tussen de
percentages in de uitvoer als **platte tekst** en de gestructureerde **JSON-uitvoer**:

| Aspect                  | Platte-tekstindeling (`/api/usage/om-usage` / `@@om-usage`)                                              | JSON-indeling (`?format=json`)                                              |
| :---------------------- | :------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------- |
| **Uitvoerveld**         | `NN% left` (bijv. `20% left`)                                                                            | `provider.quotas` / `providers[].quotas`                                    |
| **Meting**              | **Voor de grenswaarde gecorrigeerde bruikbare ruimte**: resterende capaciteit boven de grens             | **Ruw upstreamquotum**: niet-gecorrigeerde meting van de provider           |
| **Grenswaardeschaling** | Geschaald via `effectiveRemainingPercent()`, zodat de beschermde reserve als `0% left` wordt weergegeven | Geen (ruwe momentopnamewaarden zoals gerapporteerd door de provider)        |
| **Grenswaardegegevens** | Verwerkt in het weergegeven percentage                                                                   | Opgeslagen in `quotaWindowThresholds` per verbinding (of serverstandaarden) |
| **Primaire gebruiker**  | Interactieve CLI's, terminalprompts, menselijke operators                                                | Programmatische integraties, dashboards, analyses, factureringstrackers     |

#### De formule voor grenswaardecorrectie

OmniRoute ondersteunt proactieve quotumgrenzen om uitputting bij upstreamproviders te voorkomen (geconfigureerd via
`quotaWindowThresholds` voor de verbinding, standaardinstellingen van de provider of globale weerbaarheidsinstellingen). Wanneer een grenswaarde
(bijv. `cutoff = 25%`) actief is voor een quotumvenster, berekent de tekst-renderer de resterende ruimte als volgt:

- Als `remaining <= cutoff`: retourneert `0%`.
- Als `remaining > cutoff`: retourneert `((remaining - cutoff) / (100 - cutoff)) * 100`.

De opgemaakte tekstuitvoer rondt dit af op het dichtstbijzijnde gehele getal (`Math.round(...)`).

#### Illustratief voorbeeld

Neem een providervenster met **60% ruw gebruik** (dus **40% ruw resterend quotum**) en een geconfigureerde
grenswaarde van **25% resterend quotum**:

| Weergave                       | Berekening                                         | Resterend |               Impliciet gebruikt               |
| :----------------------------- | :------------------------------------------------- | :-------: | :--------------------------------------------: |
| **Ruwe JSON (`?format=json`)** | Upstreammomentopname (`quotas[window]`)            |  **40%**  |                    **60%**                     |
| **Tekstindeling (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20%**  | **80%** (bij berekening van `100 - remaining`) |

- **Waarom tekst 20% resterend toont:** Van het fysieke quotum van 40% dat nog op het account beschikbaar is, wordt 25% gereserveerd door het
  grenswaardebeleid. De aanroeper heeft slechts 15% van de 75% bruikbare ruimte over voordat de router stopt met
  routeren naar deze verbinding. De schaling zorgt ervoor dat de verbinding uitputting signaleert (`0% left`) precies wanneer
  het routeren stopt.
- **Waarom JSON ruwe waarden behoudt:** De JSON-payload retourneert de exacte providermomentopname (`UsageSnapshot`),
  zodat externe tools toegang hebben tot het werkelijke upstreamgebruik en de `quotaWindowThresholds`
  op verbindingsniveau, zonder verliesgevende schaling aan serverzijde.

#### Richtlijnen voor migratie van gebruikers

Als een externe integratie (zoals een editorplugin of agentextensie) voorheen het tekstendpoint
(`NN% left`) scrapete en het gebruikte percentage berekende als `100 - NN`, betekent migratie naar `?format=json` het volgende:

- Het uitlezen van onbewerkte JSON-waarden geeft het **daadwerkelijke upstreamverbruik** weer (60% gebruikt in het bovenstaande voorbeeld).
- Als de integratie de semantiek van de bruikbare resterende hoeveelheid van het tekstendpoint wil behouden, kan deze
  de formule voor de effectief resterende hoeveelheid aan de clientzijde evalueren met behulp van `quotaWindowThresholds` voor overschrijvingen op verbindingsniveau.

## Semantische cache

```bash
# Cachestatistieken ophalen
GET /api/cache/stats

# Alle caches wissen
DELETE /api/cache/stats
```

Voorbeeld van een respons:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Invloed op latentie

Bij een HIT in de semantische cache wordt de respons vanuit de cache geleverd
**zonder een upstream-aanroep**, waardoor de gerapporteerde
`X-OmniRoute-Response-Latency` vrijwel nul is (ongeacht de oorspronkelijke
upstream-latentie). Clients waarvoor latentie belangrijk is (benchmarking,
p50/p99-monitoring), moeten de responseheader
`X-OmniRoute-Cache-Latency` controleren:

| Waarde      | Betekenis                                                                   |
| ----------- | --------------------------------------------------------------------------- |
| `synthetic` | Respons geleverd vanuit de cache; latentie is geen werkelijke upstream-tijd |
| _(afwezig)_ | Respons van een werkelijke upstream-aanroep                                 |

### Cache per sleutel omzeilen

API-sleutels kunnen via `cacheDefaultMode` aangeven dat ze de semantische cache
niet willen uitlezen:

| Waarde   | Gedrag                                                       |
| -------- | ------------------------------------------------------------ |
| `legacy` | Normaal cachegedrag (standaard)                              |
| `bypass` | Cacheopzoeking volledig overslaan; altijd upstream aanroepen |

Stel dit in bij het aanmaken van een sleutel (`POST /api/keys`) of bij het
bijwerken ervan (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Cache per verzoek omzeilen

Elk verzoek kan de cache omzeilen, ongeacht de sleutelinstellingen:

```
X-OmniRoute-No-Cache: true
```

Voor gesynchroniseerde/geïmporteerde modellen accepteert `PUT /api/provider-models` `provider`, `modelId` en
`maxOutputTokenOverride`: een positief geheel getal stelt de handmatige limiet voor uitvoertokens in, en `null`

OpenAI-compatibele aanbieders biedt dezelfde besturingselementen voor bewerken/wissen en markeert modellen met expliciete ondersteuning voor beeldinvoer.

Aangepaste Chat Completions-knooppunten passen expliciete afmeldingen voor redeneren aan de upstreambackend aan. Een
geslaagde verbindingstest selecteert automatisch besturingselementen voor chatsjablonen voor elke exacte model-ID
waarvan het `/models`-item een herkende `owned_by`-waarde aantoont: `vllm`, `sglang` of `llamacpp`.
Transparante OpenAI-compatibele wrappers kunnen het oorspronkelijke modelitem in een genest
`openai`-object behouden; detectie volgt maximaal drie van zulke enveloppen. Modellen met ontbrekend, onbekend of
conflicterend eigenaarschap behouden het gebruikelijke OpenAI-gedrag. Detectie hergebruikt het bestaande catalogusverzoek,
genereert geen voltooiingstokens en wordt ongeldig gemaakt wanneer het verbindingseindpunt verandert.

Gebruik de bestaande API voor gedeeltelijke updates van aanbieders om dit gedrag vast te zetten voor een backend
die deze metadata niet beschikbaar stelt:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Verzend die body met `PUT /api/providers/<connection-id>`. Bij die verbinding wordt een expliciete
redeneerintensiteit van `none` verzonden als `chat_template_kwargs.thinking=false` en
`chat_template_kwargs.enable_thinking=false`. Expliciete systeemeigen sjabloonwaarden blijven leidend,
tenzij een redeneerregel aan de serverzijde een intensiteit afdwingt. De instelling is alleen van toepassing wanneer een aangepaste
OpenAI-compatibele verbinding een Chat Completions-body verzendt; Responses-verzoeken en reguliere
aanbieders behouden hun systeemeigen verzoekstructuur. Stel `reasoningControl` in op `openai` om de gebruikelijke OpenAI-
doorgifte van `reasoning_effort` af te dwingen, of laat deze weg/stel deze in op `null` om automatische detectie te gebruiken.

Classificatieverzoeken in de automatische modus van Claude Code schakelen systeemeigen denkfunctionaliteit standaard uit wanneer ze
geen expliciete besturingselementen voor redeneren bevatten. De detectie gebruikt de systeemmarkering van de classifier in verzoeken
in Claude-indeling, niet modelnamen of voltooiingslimieten. Expliciete besturingselementen in de body, ondersteunde headers voor intensiteit/denkfunctionaliteit,
routeringsregels en opgeloste modelintensiteit behouden hun bestaande prioriteit. Beide classifier-
fasen behouden hun prompts, voltooiingslimieten, stopreeksen en echte upstreambeslissingen over
toestemming; de tweede fase kan de gevraagde zichtbare redenering nog steeds als gewone tekst produceren.

### Versie en releasekanaal

```bash
GET /api/system/version
```

Beheerroute die alleen via loopback toegankelijk is (beheerdersauthenticatie). Retourneert de actieve versie, de nieuwste
gepubliceerde versie en de status van automatische updates. `releaseChannel` en `channels` zijn aanvullende
velden (rail 3.8.54); `channel` behoudt zijn betekenis — de implementatiemodus die de dashboard-updater
gebruikt (`npm`, `source` of `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — npm-kanaal van de actieve build: `nightly` voor `-nightly.*`-versies,
  `next` voor andere prereleases (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` voor een stabiele versie met een
  oudere hoofdversie dan `channels.latest`, en anders `latest`. Dezelfde regels als in
  `scripts/release/dist-tag.mjs`, dat tijdens het publiceren de npm-dist-tag kiest.
- `channels` — de laatst gepubliceerde versie van elke dist-tag, afkomstig van `npm view omniroute dist-tags` (met het register
  via HTTP als fallback), gecachet met dezelfde TTL van 10 minuten als `latest`. `latest` is altijd aanwezig
  (valt terug op het veld `latest` en daarna op `"unavailable"`); `next`, `nightly` en `lts` worden
  alleen weergegeven wanneer die dist-tag bestaat. Een verzoek met `Cache-Control: no-cache` vernieuwt beide opzoekacties.

Het kanaalmodel (`latest` = v3 tot de algemene beschikbaarheid van 4.0, `next` = rc, `nightly` = builds van `develop`,
`lts` = v3-patches na de algemene beschikbaarheid van 4.0) wordt beschreven in `docs/ops/RELEASE_STRATEGY.md`.

## Tokenlimieten

**Tokenbudgetten** per API-sleutel (los van het hierboven beschreven budget op basis van USD). Deze worden direct in het aanvraagpad afgedwongen: wanneer het gebruik van een sleutel binnen het huidige tijdvenster de limiet bereikt, worden aanvragen geweigerd met `429 Too Many Requests`. Limieten kunnen worden beperkt tot een specifiek `model` of een specifieke `provider`, of `global` worden toegepast op de hele sleutel. Wanneer meerdere limieten overeenkomen met een aanvraag, geldt de meest beperkende limiet.

```bash
# De tokenlimieten van een sleutel weergeven (inclusief actueel gebruik binnen het tijdvenster)
GET /api/usage/token-limits?apiKeyId=key-123

# Een tokenlimiet aanmaken of bijwerken
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Een tokenlimiet verwijderen op basis van id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Schemaopmerkingen** (`setTokenLimitSchema`): `apiKeyId` en `scopeType` (`model` | `provider` | `global`) zijn verplicht. `scopeValue` is verplicht, tenzij `scopeType` gelijk is aan `global` (bijvoorbeeld een model-id voor het bereik `model` of een provider-id voor het bereik `provider`). `tokenLimit` moet een positief geheel getal zijn (geconverteerd vanuit een tekenreeks). Optioneel: `id` (weglaten om aan te maken, opgeven om bij te werken), `resetInterval` (`daily` | `weekly` | `monthly`, standaard `monthly`), `resetTime` (`HH:MM`), `enabled` (standaard `true`). `GET`-antwoorden vullen elke limiet aan met `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` en `nextResetAt`. Dit is een endpoint van de beheerklasse (authenticatie wordt centraal afgedwongen door de autorisatiepipeline).

## Aanvraagverwerking

1. De client verzendt een aanvraag naar `/v1/*`
2. De routehandler roept `handleChat`, `handleEmbedding`, `handleAudioTranscription` of `handleImageGeneration` aan
3. Het model wordt bepaald (rechtstreekse provider/model-combinatie of alias/combo)
4. Referenties worden geselecteerd uit de lokale database, met filtering op accountbeschikbaarheid
5. Voor chat controleert `handleChatCore` de semantische/ondertekeningscache en bepaalt het de compressie-instellingen van de combo
6. Proactieve compressie wordt vóór de providervertaling uitgevoerd wanneer deze is ingeschakeld (`lite`, Caveman, RTK of gestapeld)
7. De providerexecutor verzendt de upstreamaanvraag
8. Het antwoord wordt terugvertaald naar de clientindeling (chat) of ongewijzigd geretourneerd (embeddings/afbeeldingen/audio)
9. Gebruik, compressieanalyses en aanvraaglogboeken worden vastgelegd
10. Bij fouten wordt fallback toegepast volgens de comboregels

Volledige architectuurreferentie: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Veerkracht (uitgebreid)

OmniRoute biedt drie onafhankelijke mechanismen voor tijdelijke fouten; met de onderstaande beheerendpoints kunnen operators deze uitlezen en overschrijven:

| Bereik                 | Statusopslag                                  | Uitlezen                                  | Resetten / wissen                                                 |
| ---------------------- | --------------------------------------------- | ----------------------------------------- | ----------------------------------------------------------------- |
| Providercircuitbreaker | `domain_circuit_breakers` + in het geheugen   | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                      |
| Verbindingscooldown    | `rateLimitedUntil` op providerverbindingen    | `/api/rate-limits`, `/api/providers/[id]` | (wordt geleidelijk opnieuw ingeschakeld; wissen via provider-PUT) |
| Modelblokkering        | Modelbeschikbaarheidsregister in het geheugen | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                          |

`PATCH /api/resilience` accepteert overschrijvingen voor providercircuitbreakers onder `providerBreaker.oauth` en `providerBreaker.apikey`. Elk profiel ondersteunt `degradationThreshold`, `failureThreshold` en `resetTimeoutMs`; dezelfde velden zijn beschikbaar in Dashboard → Instellingen → Veerkracht.

```bash
# Eén modelblokkering wissen
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Alle blokkeringen wissen
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Volledige conceptuele referentie en standaardwaarden voor circuitbreakers: zie [`CLAUDE.md`](../../CLAUDE.md) → "Runtime-status voor veerkracht" en [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Wachtrij voor snelheidslimieten en automatisch ingeschakeld vangnet

- **Ondersteund schrijfpad**: `POST /api/rate-limits` met body `{"connectionId": "<id>", "enabled": true|false}` is het ondersteunde beheerendpoint om bescherming tegen snelheidslimieten voor een verbinding in of uit te schakelen. `PUT /api/providers/[id]` wijzigt `rateLimitProtection` bewust niet en schakelt deze waarde ook niet om (#11278).
- **Semantiek van `enabled: false`**: Het instellen van `enabled: false` verwijdert expliciete bescherming voor de verbinding, maar sluit een actieve API-sleutelverbinding **niet** uit van het algemene vangnet voor automatisch inschakelen (`autoEnableApiKeyProviders = true`). In `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) zijn `false` en `undefined` gelijkwaardig; actieve API-sleutelverbindingen zonder expliciete bescherming blijven beschermd door het vangnet voor automatisch inschakelen.
- **Globaal uitschakelen**: Als u API-sleutelverbindingen zonder wachtrijen voor snelheidslimieten wilt gebruiken, schakelt u het vangnet globaal uit via `RATE_LIMIT_AUTO_ENABLE=false` (omgevingsvariabele) of `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Instellingen → Veerkracht / `PATCH /api/resilience`).

```bash

{
  "jsonrpc": "2.0",
  "id": 1,
```

Ingebouwde skills: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

## Authenticatie

Zie [Beheerauthenticatie](../guides/MANAGEMENT-AUTH.md) voor de vier
referentietypen (dashboardsessie, lokaal CLI-token, `oma_live_…`-toegangstoken,
API-sleutel met beheerbereik) en hoe deze verschillen van inferentiesleutels.

- Dashboardroutes (`/dashboard/*`) gebruiken de cookie `auth_token`
- Aanmelden gebruikt de opgeslagen wachtwoordhash, met terugval op `INITIAL_PASSWORD`
- `requireLogin` kan worden in- en uitgeschakeld via `/api/settings/require-login`
- Routes onder `/v1/*` vereisen optioneel een Bearer-API-sleutel wanneer `REQUIRE_API_KEY=true`
- Met "beheertoken" / "API-sleutel met beheerbereik" wordt in deze referentie een van de typen uit die handleiding bedoeld — niet een ongedefinieerd extra type geheim

> **Incompatibele wijziging (v3.8.0)** — `/api/v1/agents/tasks/*` en de endpoints voor cooldownbeheer vereisen nu **beheerauthenticatie** (de dashboardcookie `auth_token` of een API-sleutel met beheerbereik). Clients die deze routes eerder zonder authenticatie aanriepen, ontvangen `401 Unauthorized`. Zie commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
