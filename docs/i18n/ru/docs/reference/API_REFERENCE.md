## Завершения чата

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Пользовательские заголовки

| Заголовок                | Направление | Описание                                                                                                                                                                                                                                                  |
| ------------------------ | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Запрос      | Установите значение `true`, чтобы обойти кеш                                                                                                                                                                                                              |
| `x-omniroute-no-memory`  | Запрос      | Установите значение `true`, чтобы пропустить внедрение памяти и навыков для этого запроса (аналогично отключению кеша; позволяет избежать дополнительных затрат токенов и средств на каждый вызов)                                                        |
| `X-OmniRoute-Progress`   | Запрос      | Установите значение `true`, чтобы получать события о ходе выполнения                                                                                                                                                                                      |
| `X-Session-Id`           | Запрос      | Ключ закреплённого сеанса для внешней привязки сеанса                                                                                                                                                                                                     |
| `x_session_id`           | Запрос      | Также принимается вариант с символами подчёркивания (при прямом HTTP-запросе)                                                                                                                                                                             |
| `X-OmniRoute-Session-Id` | Запрос      | Заданный вызывающей стороной тег сеанса/диалога (также передаётся в память). Если он присутствует, то сохраняется без изменений в `call_logs.session_tag` для атрибуции затрат по сеансам (#8249) — если он отсутствует, значение никогда не генерируется |
| `Idempotency-Key`        | Запрос      | Ключ дедупликации (окно 5 с)                                                                                                                                                                                                                              |
| `X-Request-Id`           | Запрос      | Альтернативный ключ дедупликации                                                                                                                                                                                                                          |
| `x-omniroute-connection` | Запрос      | Закрепляет запрос к одной модели за одним подключением провайдера (учётной записью) по его идентификатору — см. [Закрепление учётной записи для каждого запроса](#account-pinning-per-request)                                                            |
| `X-OmniRoute-Cache`      | Ответ       | `HIT` или `MISS` (без потоковой передачи)                                                                                                                                                                                                                 |
| `X-OmniRoute-Idempotent` | Ответ       | `true`, если выполнена дедупликация                                                                                                                                                                                                                       |
| `X-OmniRoute-Progress`   | Ответ       | `enabled`, если включено отслеживание хода выполнения                                                                                                                                                                                                     |
| `X-OmniRoute-Session-Id` | Ответ       | Фактический идентификатор сеанса, используемый OmniRoute                                                                                                                                                                                                  |
| `X-OmniRoute-Request-Id` | Ответ       | Идентификатор корреляции запроса (если известен)                                                                                                                                                                                                          |
| `X-OmniRoute-Version`    | Ответ       | Версия сборки OmniRoute (присутствует всегда)                                                                                                                                                                                                             |
| `X-OmniRoute-Cost-Saved` | Ответ       | Сумма в USD, сэкономленная благодаря кешу при `HIT` (только для попаданий в кеш)                                                                                                                                                                          |
| `X-OmniRoute-Decision`   | Ответ       | Трассировка маршрутизации: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` — стратегия комбинации или `single` для запроса без комбинации) — всегда присутствует в ответах о завершении                                                     |

> Примечание по Nginx: если вы используете заголовки с символами подчёркивания (например, `x_session_id`), включите `underscores_in_headers on;`.

#### Закрепление аккаунта для отдельного запроса

Когда у провайдера есть несколько подключений (аккаунтов или ключей), OmniRoute обычно выбирает одно
из них с помощью своей стратегии выбора аккаунта. Вместо этого в запросе можно закрепить конкретное подключение
с помощью заголовка `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Где найти идентификатор.** Откройте страницу провайдера на панели управления
  (**Панель управления → Провайдеры → <провайдер>**) и нажмите на плашку идентификатора `xxxxxxxx…` в строке подключения
  — полный идентификатор подключения будет скопирован.
- **Какие запросы его учитывают.** Запросы к одной модели (`provider/model`) через
  `/v1/chat/completions`, `/v1/messages` и `/v1/responses`. Комбинации игнорируют этот заголовок: вместо этого
  закрепляйте аккаунт для каждого шага комбинации через собственное подключение этого шага.
- **Закрепление является строгим, а не предпочтительным.** Закреплённое подключение используется исключительно. Сбой
  во время запроса переводит аккаунт в режим ожидания, но **не** приводит к переключению на
  другой аккаунт того же провайдера.
- **Режим ожидания и квота снимают закрепление.** Пока закреплённое подключение находится в режиме ожидания,
  исчерпало квоту или заблокировано политикой квот, последующие запросы переключаются на другие
  подключения провайдера — точно так же, как незакреплённый трафик.
- **Неизвестные или отключённые идентификаторы приводят к ошибке.** Если идентификатор отсутствует в активном пуле провайдера (удалён,
  деактивирован или принадлежит другому провайдеру), доступных аккаунтов не остаётся, поэтому запрос
  завершается ошибкой вместо неявной маршрутизации в другое место.

Claude Code передаёт пользовательские заголовки через `ANTHROPIC_CUSTOM_HEADERS`. Добавьте эту переменную в блок `env`
файла `~/.claude/settings.json` или в файл `.claude/settings.json` на уровне проекта, чтобы закреплять разные
аккаунты для разных проектов:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Источник: `src/sse/handlers/chat.ts` (чтение заголовка), `src/sse/services/auth.ts` и
`src/sse/services/sessionAffinityPin.ts` (снятие закрепления и проверка отсутствия в пуле).

> **Заголовки телеметрии стоимости:** успешные ответы без потоковой передачи также содержат набор телеметрии стоимости `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, фиксированные 10 знаков после запятой; `0.0000000000` для бесплатных запросов или запросов без заданной цены), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` и `X-OmniRoute-Fallback-Attempts` (только если > 0), а также `X-OmniRoute-Request-Id` и `X-OmniRoute-Version`. Они добавляются в ответы на запросы завершения чата, `/v1/responses`, `/v1/messages`, **а также к конечным точкам для медиа** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` и `/v1/moderations` (стоимость всегда равна `0`). Стоимость медиа рассчитывается отдельно для каждой модальности (за изображение, секунду, символ или единицу поиска), когда информация о ценах доступна; в противном случае используется `0` (отказ не блокирует обработку).

> **Семантика стоимости при попадании в кэш:** при попадании в семантический кэш (`X-OmniRoute-Cache-Hit: true`) запрос к вышестоящему сервису не выполняется, поэтому значение `X-OmniRoute-Response-Cost` равно `0.0000000000` (**инкрементальная** стоимость обслуживания попадания). Исходная или потенциальная стоимость указывается отдельно в `X-OmniRoute-Cost-Saved`. Системам учёта оплаты следует суммировать `X-OmniRoute-Response-Cost` (попадания ничего не стоят), а системы аналитики кэша могут агрегировать `X-OmniRoute-Cost-Saved`.

## Эксклюзивные управляемые аренды сеансов

Эксклюзивная управляемая аренда сеансов — это опциональный, нейтральный к клиенту контракт маршрутизации: один активный владелец
удерживает одно подходящее подключение OmniRoute. Она не арендует модель, не требует OAuth, не идентифицирует
конкретный клиент и не требует конкретного провайдера.

API-ключ, используемый для аутентификации, должен иметь область действия `lease:exclusive` и явно заданный непустой
список `allowedConnections`. Граница мутаций базы данных обеспечивает совместное соблюдение обоих требований при
создании ключа и частичных обновлениях.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Успешные ответы на получение, продление и освобождение содержат временные метки, `state` и точное положительное
значение `generation`, но никогда не раскрывают выбранное подключение или учётные данные. При продлении и освобождении
поколение передаётся в теле JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Владелец активной аренды может явно запросить безопасные с точки зрения конфиденциальности отображаемые метаданные текущей привязки:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Это опциональное действие получения статуса защищается непрозрачным идентификатором владельца, аутентифицированным управляемым API-ключом и точным
активным поколением в рамках одной транзакции базы данных. `displayName` содержит только обрезанное настроенное
имя подключения; оно равно `null`, если безопасное настроенное имя отсутствует. OmniRoute никогда не подставляет
адрес электронной почты или сгенерированный идентификатор учётной записи. Значение провайдера является нечувствительной отображаемой меткой и никогда
не представляет собой сгенерированный идентификатор совместимого провайдера. Учётные данные, токены, файлы cookie, необработанные идентификаторы подключения или
API-ключа, хеши владельцев, секреты изоляции и внутренние данные маршрутизации исключаются.

Запросы с неверным ключом, неверным владельцем, устаревшим поколением, отсутствующей, истёкшей, освобождённой или аннулированной арендой
возвращают одну и ту же ошибку `409 LEASE_FENCE_STALE` без метаданных подключения. У клиента, получившего ответ об ожидании доступной ёмкости, нет активной привязки для проверки. Когда маршрутизация переключает активную аренду,
то же поколение остаётся действительным, а статус атомарно возвращает новую привязку, но никогда не старую.
Существующие клиенты не затрагиваются, поскольку ответы на получение, продление, освобождение и ожидание сохраняют
прежнюю структуру.

Этот серверный контракт не изменяет штатный `/status` OpenAI Codex. В настоящее время штатный Codex сообщает
о провайдере модели и встроенном состоянии аутентификации/учётной записи, но не отображает произвольные пользовательские
метаданные учётной записи провайдера; последующая клиентская интеграция должна вызывать это действие и решать, как
отображать `connection.displayName`.

Затем каждый управляемый запрос на инференс передаёт оба управляющих заголовка:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Точное соответствие владельца, поколения, активного подключения и аутентифицированного API-ключа проверяется непосредственно
перед каждой поддерживаемой попыткой обращения к вышестоящему сервису. Повторное использование владельца и поколения с другим ключом завершается ошибкой, даже
если этот ключ разрешает то же подключение. Необработанные идентификаторы владельцев не сохраняются, не записываются в журналы, не включаются в
снимок запроса и не пересылаются вышестоящему сервису.

При временной конкуренции возвращается HTTP `429` с `Retry-After` и:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Этот ответ означает только то, что обычный набор подходящих подключений был непустым, а каждый свободный кандидат
удерживался чужой активной арендой. Неподдерживаемые модели/провайдеры, несоответствие политике, период восстановления, квота,
состояние работоспособности и другие обычные причины несоответствия сохраняют существующие ответы OmniRoute.

### `x-omniroute-compression`

Переопределение плана сжатия для отдельного запроса. Имеет наивысший приоритет — превосходит переопределение комбинации маршрутизации,
активный профиль, автоматический триггер и значение по умолчанию панели. Значения:

| Значение      | Эффект                                                                                                              |
| ------------- | ------------------------------------------------------------------------------------------------------------------- |
| `off`         | Без сжатия для этого запроса.                                                                                       |
| `default`     | Профиль по умолчанию, определённый панелью (активный профиль игнорируется). Сжатие с потерями остаётся отключённым. |
| `safe`        | Только дедупликация и сворачивание пробельных символов.                                                             |
| `allow-lossy` | Сохраняет операторский план для этого запроса, включая резюмирование и перезапись стиля.                            |
| `engine:<id>` | Один включённый движок, например `engine:rtk`. Опциональное включение этого движка для отдельного запроса.          |
| `<combo>`     | Именованная комбинация: сначала сопоставляется по имени без учёта регистра, затем по идентификатору.                |

Примечания:

- Неизвестные значения игнорируются (запрос никогда не отклоняется); разрешение продолжается в соответствии с обычным порядком приоритетов оператора.
- Если несколько комбинаций имеют одинаковое имя, передайте **идентификатор** комбинации для детерминированного сопоставления.
- Комбинацию с именем `off` или `default` нельзя выбрать по имени (сначала интерпретируются эти ключевые слова); обращайтесь к такой комбинации по её идентификатору.
- Главный переключатель сжатия является жёстким ограничителем: если сжатие отключено глобально, этот заголовок не может его включить.

Применённый план возвращается в заголовке ответа:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

где `<source>` — одно из значений `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` или `off`.

## Эмбеддинги

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Доступные провайдеры: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Идентификаторы каталога имеют формат `provider/model` (пример: `jina-ai/jina-embeddings-v5-omni-small`). Также разрешаются идентификаторы моделей Jina без указания провайдера, если они присутствуют в реестре (например, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`). Для операций Jina embed/rerank/classify/segment в первую очередь используются учетные данные `jina-ai` из панели управления; `JINA_AI_API_KEY` применяется как резервный вариант, только если ключ в панели управления отсутствует. Карточка `jina-reader` предназначена только для Reader / `r.jina.ai` (`POST /v1/web/fetch`) и никогда не обслуживает эмбеддинги или переранжирование.

Модели реестра, для которых заявлена поддержка мультимодальности, также принимают до 32 структурированных
элементов в независимом от провайдера формате. Типы медиаэлементов: `text`, `image`, `audio`, `video` и `document`. Их поле `source`
имеет вид `{"type":"url","url":"https://..."}` или
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
и псевдоним семейства `jina-ai/jina-embeddings-v5-omni` → omni-small) также принимает документы в нативном формате
EmbeddingsV5Request от Jina и **пересылает их без изменений** на `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Нативные значения `{ image | audio | video | pdf }` могут быть общедоступным HTTPS URL, URI `data:` или необработанными
данными base64. OmniRoute не преобразует эти объекты в строки и не загружает нативные URL изображений — Jina самостоятельно получает
общедоступные медиафайлы. Дополнительные поля Jina (`task`, `normalized`, `truncate`, `embedding_type`)
пересылаются. SKU Jina, поддерживающие только текст, по-прежнему отклоняют нетекстовые документы.

Ограничения безопасности и передачи данных:

- URL удаленных медиафайлов должны быть общедоступными и использовать HTTPS. Канонические элементы `{type,source:url}` загружаются
  на стороне сервера (повторная проверка перенаправлений, тайм-аут, ограничения размера, общедоступный DNS, фиксация соединения) и
  встраиваются перед вызовом провайдера. Нативные элементы Jina `{image:"https://..."}` пересылаются без изменений
  после такой же проверки общедоступного HTTPS; URL загружает Jina.
- Размер встроенных медиафайлов base64 ограничен 8 МиБ декодированных данных на элемент и 16 МиБ декодированных данных на весь запрос.

Преобразование для провайдеров (канонические элементы никогда не пересылаются без изменений):

- Мультимодальные модели Jina: каждый элемент верхнего уровня становится одним объектом с ключом модальности
  (`text` / `image` / `audio` / `video` / `pdf`), при этом для встроенных медиафайлов используются URI данных; один вектор на
  каждый элемент верхнего уровня.
- Семейство Gemini Embedding 2: один массив верхнего уровня становится единым нативным запросом
  `models/{model}:embedContent` с `content.parts` (`text` или `inline_data`).
- llama.cpp (`llama-cpp/<model>`, любая модель, загруженная локальным сервером): канонические элементы `text`
  становятся обычными строками, а `image` / `audio` / `video` — отдельными объектами
  `{"content": [part]}`, использующими части содержимого чата llama-server (`image_url`,
  `input_audio` с форматом `wav` / `mp3` / `flac`, `input_video`) со встроенными данными; один вектор
  на каждый элемент верхнего уровня. Сервер должен быть запущен с `--embedding --mmproj …`; без проектора он
  самостоятельно отклоняет медиафайлы. `document` не поддерживается.
- Неизвестные/динамические модели без явных метаданных о модальностях отклоняют структурированный ввод с HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Неподдерживаемые сочетания модели и модальности возвращают HTTP 400 вместо принудительного преобразования элемента. Поля расширений,
не относящиеся к входным данным, в устаревших запросах со строками/токенами по-прежнему передаются без изменений.

```bash
# Получить список всех моделей эмбеддингов
GET /v1/embeddings
```

## Генерация изображений

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Доступные провайдеры: OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (локально), ComfyUI (локально).

`n` возвращает `n` изображений в `data[]`. Для провайдеров, вышестоящий API которых возвращает одно изображение за вызов
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), выполняется `n` отдельных вышестоящих вызовов, не более 4 одновременно. Фиксированное
значение `seed` смещается на индекс вызова (`seed`, `seed + 1`, …), поэтому изображения различаются, но остаются
воспроизводимыми. Максимальное значение `n` — 10. Если любой вызов завершается ошибкой, весь запрос считается неуспешным. Список
форматов с разветвлением запросов находится в `SINGLE_IMAGE_FANOUT_FORMATS` в
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux повторно использует существующее подключение с API-ключом и принимает префиксы `zenmux/` или `zm/`:

- `zenmux/openai/gpt-image-2` использует OpenAI Images API от ZenMux. Доступные параметры включают `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` и `response_format`.
- Другие издатели, например `zm/meta/muse-image-1.0`, используют конечную точку Vertex AI `:predict`
  от ZenMux. `n` сопоставляется с `sampleCount`, `aspect_ratio` — с `aspectRatio`, а `image_size`
  (`1K`, `2K`, `4K`) — с `sampleImageSize`. Значение `size` в пикселях задаёт только соотношение сторон,
  но не гарантированные размеры в пикселях. Поддерживаемые соотношения сторон, разрешения и количества зависят от модели.
- `zm/inclusionai/ming-image-0.1-design` самостоятельно выбирает размеры. Не указывайте `size`,
  `aspect_ratio` и `image_size`; при явном указании этих значений возвращается HTTP 400. С помощью
  `output_format` можно запросить PNG, JPEG и WebP.

Эта интеграция поддерживает генерацию изображений по тексту, но не редактирование на основе эталонного изображения. Выходные данные Vertex
нормализуются в `data[].b64_json`; `response_format: "url"` возвращает вышестоящий
HTTPS-URL или URL с данными в base64, если доступны только байты изображения. Для пустых или отфильтрованных выходных данных
возвращается ошибка, а не успешный ответ без данных. Доступ к моделям зависит от учётной записи ZenMux.
См. [Vertex API от ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) и
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Вывести список всех моделей изображений
GET /v1/images/generations
```

## Распознавание текста в документах

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` выбирает OCR-провайдера с помощью префикса `provider/model`; идентификатор модели без префикса (например,
`mistral-ocr-latest`) сопоставляется с зарегистрированным провайдером, а если `model` не указан, по умолчанию
используется Mistral (`mistral-ocr-latest`). Зарегистрированные провайдеры (`open-sse/config/ocrRegistry.ts`):

| Идентификатор провайдера      | Идентификатор модели | Значение `model`                                                     | Примечания                                                                                                                          |
| ----------------------------- | -------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (или `mistral-ocr-latest` без префикса) | Синхронный режим — ответ возвращается непосредственно из единственного вышестоящего вызова.                                         |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                          | Асинхронный вышестоящий API (`analyze` + опрос) — см. ниже.                                                                         |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                              | Синхронный режим через партнёрскую конечную точку Vertex AI `openapi/chat/completions` — сведения об аутентификации и URL см. ниже. |

Все три провайдера возвращают тело ответа одного и того же формата Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Процесс опроса Azure Document Intelligence

API `analyze` в Azure Document Intelligence работает асинхронно: первоначальный запрос возвращает заголовок
`Operation-Location` вместо тела ответа, после чего результат необходимо получать посредством опроса. Обработчик
(`open-sse/handlers/ocr.ts`) опрашивает этот URL каждую секунду, выполняя до 30 попыток, немедленно завершает работу с ошибкой (не
продолжая опрос) при ответе опроса без статуса `ok` или при статусе `"failed"` и возвращает `504`, если
операция всё ещё выполняется после исчерпания доступного количества попыток. Итоговый ответ Azure
перед возвратом вызывающей стороне нормализуется в тот же формат `pages`/`markdown`, который используется Mistral,
поэтому клиентскому коду не требуется отдельно обрабатывать этого провайдера.

### Аутентификация и разрешение конечной точки Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` повторно использует тот же механизм аутентификации Vertex AI, который OmniRoute уже поддерживает для
трафика чатов и изображений (`open-sse/executors/vertex.ts`): API-ключ подключения представляет собой либо
учётные данные Service Account в формате JSON (обмениваемые на краткосрочный токен доступа OAuth посредством
процесса JWT-bearer), либо уже выпущенный токен доступа OAuth, используемый без изменений. URL вышестоящей конечной точки — это
универсальная партнёрская конечная точка Vertex `openapi/chat/completions`, формируемая на основе проекта и
региона подключения: явно заданные `providerSpecificData.project`/`providerSpecificData.region` всегда имеют приоритет;
в противном случае проект определяется из `project_id` в JSON-файле Service Account, а регионом
по умолчанию является `us-central1`. Оба значения разрешаются в `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) и используются в
`src/app/api/v1/ocr/route.ts` перед передачей запроса в `handleOcr`.

### Префиксы идентификаторов моделей (`?prefix=`)

Большинство моделей публикуются с **префиксом провайдера**. Выбор префикса определяется
флагом функции `MODELS_CATALOG_PREFIX_MODE` и может быть переопределён **для каждого запроса**
с помощью параметра запроса — это полезно для клиента, которому нужен чистый список без изменения
общесерверной настройки для всех остальных:

```bash
GET /v1/models?prefix=alias        # один идентификатор на модель — короткий префикс псевдонима
GET /v1/models?prefix=dual         # обе формы (настройка сервера по умолчанию)
GET /v1/models?prefix=canonical    # только полный префикс идентификатора провайдера
```

| Режим       | Возвращает                                              | Примечания                                                                                                                                                                                                                        |
| ----------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **и** `claude/claude-sonnet-4-6` | **По умолчанию.** Оба идентификатора направляются к одной модели; это сохранено, чтобы конфигурации клиентов с жёстко заданной любой из форм продолжали работать. Размер каталога увеличивается примерно вдвое.                   |
| `alias`     | `cc/claude-sonnet-4-6`                                  | Одна запись на модель. Провайдеры без отдельного псевдонима по-прежнему возвращают свою запись, поэтому ничего не теряется.                                                                                                       |
| `canonical` | `claude/claude-sonnet-4-6`                              | Одна запись на модель с полным префиксом идентификатора провайдера. Провайдеры без отдельного псевдонима (например, `antigravity/…`, `agy/…`) также возвращают здесь свой единственный идентификатор, поэтому ничего не теряется. |

Зеркальную запись в режиме `dual` также можно распознать без параметра запроса: она содержит поле `parent`,
указывающее на основной идентификатор.

Клиентам, отображающим средство выбора модели, следует запрашивать `?prefix=alias` — так делает
[расширение OmniCopilot для VS Code](../guides/VSCODE-COPILOT.md).

### Фильтры обнаружения (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` поддерживает необязательные фильтры обнаружения. Если ни один из них не указан,
ответ не изменяется. Они сужают уже доступный вызывающей стороне каталог (сначала применяются разрешения
API-ключа) и выполняются до пагинации в стиле OpenAI с параметрами `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # каждая указанная возможность должна быть доступна
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # поле `type` каталога; строки без него считаются `chat`
GET /v1/models?q=sonnet&limit=10                           # поиск по идентификатору или имени без учёта регистра
```

| Параметр      | Значения                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | неотрицательное целое число, сравниваемое с `context_length`                                        |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 символов                                                                                      |

Неизвестное значение или значение `min_context`, не являющееся неотрицательным целым числом (например, `1.5`),
приводит к ответу HTTP `400`, а в сообщении перечисляются допустимые значения. Реализация:
`src/app/api/v1/models/catalogFilters.ts`.

### Краткий список моделей (`POST /v1/models/query`)

`POST /v1/models/query` возвращает короткий детерминированный список из того же каталога с теми же
правилами аутентификации и видимости для каждого ключа, что и `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Все поля необязательны. `capabilities` и `exclude` принимают массив или строку со значениями,
разделёнными запятыми; `max_output` сравнивается с `max_output_tokens`. Результаты сортируются сначала
по `owned_by`, затем по `id`. Значение `limit` по умолчанию равно `20`, а значения выше `100`
ограничиваются до `100`. Недопустимый JSON, неизвестное поле или недопустимое значение приводят к ответу HTTP `400`.

### Индивидуально скрытые модели чатов

Модель, отмеченная как **скрытая** на странице её провайдера, исключается из каталога и отклоняется
с HTTP `404` / `model_not_found` при явном запросе. Проверка использует определённые
провайдер и модель, включая псевдонимы провайдеров, префиксы узлов совместимых провайдеров и
настройки подключения по умолчанию. Комбинация пропускает скрытые целевые модели и может использовать
видимую альтернативу; если исполняемых целевых моделей не осталось, возвращается тот же код ошибки.
Снятие статуса скрытой модели вступает в силу при следующем запросе. Переопределения видимости,
относящиеся только к изображениям, не скрывают модель чата с тем же идентификатором.

Эта индивидуальная настройка модели не связана со
[списками разрешения и запрета публикации моделей](../routing/MODEL_EXPOSURE_LIST.md), которые фильтруют
публикацию в каталоге и кандидатов для автоматической маршрутизации, сохраняя при этом явную диспетчеризацию.
Разрешения моделей для API-ключей продолжают применяться независимо. Режим префиксов каталога по умолчанию остаётся `dual`.

### Варианты моделей без мышления

Для моделей Claude, поддерживающих мышление, `/v1/models` также публикует вариант **без мышления**, идентификатор которого имеет префикс `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Выбор этого идентификатора (например, в конфигурации Claude Code, которая всегда добавляет блок `thinking`) приводит к разрешению в фактический `<provider>/<model>` с отключёнными рассуждениями — `thinking:{type:"disabled"}` для маршрута `/v1/messages` либо с удалением полей `reasoning`/`reasoning_effort` для маршрута `/v1/chat/completions`. Этот вариант отображается только для моделей семейства Claude, которые поддерживают рассуждения **и** учитывают значение `disabled` (поэтому, например, модели, поддерживающие только адаптивный режим и отклоняющие `disabled`, исключаются). Операторы могут принудительно включить или отключить этот вариант для каждой модели с помощью `ModelSpec.noThinkingAlias`.

## Генерация аудио ElevenLabs

Настройте подключение к провайдеру `elevenlabs` в OmniRoute, используя свой API-ключ ElevenLabs.
Клиенты проходят аутентификацию с помощью своего ключа **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
шлюз передаёт сохранённый ключ провайдера в качестве `xi-api-key`. Никогда не отправляйте ключ ElevenLabs
в качестве bearer-токена шлюза.

| Метод | Путь                        | Ответ                                      | Категория конечной точки API-ключа |
| ----- | --------------------------- | ------------------------------------------ | ---------------------------------- |
| POST  | `/v1/sound-generation`      | Нативные аудиоданные                       | `elevenlabs`                       |
| POST  | `/v1/music`                 | Нативные аудиоданные                       | `music`                            |
| POST  | `/v1/music/stream`          | Потоковые аудиоданные                      | `music`                            |
| POST  | `/v1/music/detailed`        | Нативные multipart-аудио и план композиции | `music`                            |
| POST  | `/v1/music/detailed/stream` | Нативные SSE-метаданные и фрагменты аудио  | `music`                            |
| POST  | `/v1/music/plan`            | План композиции в формате JSON             | `music`                            |

Эти конечные точки дополняют существующие маршруты `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` и `/v1/speech-to-text`. Нативные поля JSON
и параметры запроса, такие как `output_format` и `enable_logging`, сохраняются.
Ответы `/v1/music/detailed` сохраняют свои multipart-границы; обрабатывайте их как multipart.
`/v1/music/detailed/stream` возвращает `text/event-stream` с метаданными композиции и
фрагментами аудио в формате base64 в событиях SSE. Все шесть маршрутов поддерживают предварительные запросы CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Короткий звуковой эффект. Продолжительность: от 0,5 до 30 секунд.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Продолжительность музыки указывается в миллисекундах: от 3000 до 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Используйте `/v1/music/stream` с тем же телом JSON для последовательной доставки аудио. Для композиции
принимается ровно одно из значений `prompt` или `composition_plan`; `/v1/music/plan` требует `prompt`
и дополнительно принимает `source_composition_plan`. Нативные схемы сохраняют дополнительные
поля провайдера, поэтому версии планов композиции и параметры тонкой настройки передаются в ElevenLabs.

Унифицированная конечная точка `/v1/music/generations` также принимает `elevenlabs/music_v1`,
`elevenlabs/music_v2` и `elevenlabs/music_v2_5`. При наличии активного подключения ElevenLabs
эти модели отображаются в каталоге музыки. Эта конечная точка возвращает
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Её поле `duration` указывается в
секундах и сопоставляется с `music_length_ms`; явно заданное значение `music_length_ms` имеет приоритет.
`instrumental` сопоставляется с `force_instrumental`, причём нативное поле имеет приоритет.
Используйте нативные потоковые конечные точки для потоковой передачи, а нативную конечную точку композиции —
для запросов, основанных исключительно на плане композиции.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Ограничения конечной точки, модели, бюджета и подключения применяются до вызова вышестоящего сервиса. Нативные
маршруты возвращают коды состояния и тела ошибок вышестоящего сервиса без изменений, включая `402` при ограничении
тарифного плана и `429` при превышении квоты. Заголовки `character-cost`, `song-id`, `request-id` и `retry-after`
сохраняются при их наличии. Наличие бесплатного кредитного баланса не гарантирует доступ ко всем
музыкальным моделям, форматам вывода или функциям API: ElevenLabs определяет права доступа для каждого запроса.
Унифицированная конечная точка сохраняет коды состояния ошибок в нормализованной оболочке ошибок OmniRoute.

Контракты вышестоящего сервиса: [звуковые эффекты](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[музыкальная композиция](https://elevenlabs.io/docs/api-reference/music/compose) и
[сведения о потоковой передаче музыки](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

Все маршруты POST используют одну и ту же структуру: `Bearer your-api-key` + проверенное с помощью Zod тело JSON (`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema` и т. д.; см. `src/shared/validation/schemas.ts`). При ошибке проверки схемы возвращается ответ 4xx.

```bash
# Переранжирование (провайдер облачного реестра или узел OpenAI-совместимого провайдера в виде "<prefix>/<model>")
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Классификация Jina (учётные данные Foundation API)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Сегментатор Jina
POST /v1/segment     { "content": "...", "return_chunks": true }

# Поиск Jina (s.jina.ai; псевдонимы провайдера: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# Модерация
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — возвращает тело ответа в формате audio/mpeg (или в запрошенном формате)
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Для Soniox TTS требуются язык и голос: `language` по умолчанию имеет значение "en"; отсутствующий
# голос или имя стандартного голоса OpenAI (alloy, nova, …) заменяется на "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# Редактирование изображения (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# Генерация видео/музыки (идентификатор модели с префиксом провайдера)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **Узлы провайдеров для переранжирования:** `POST /v1/rerank` также направляет запросы к OpenAI-совместимым узлам провайдеров
> (oMLX, vLLM, Infinity, TEI за шлюзом, …), адресуемым как `<node-prefix>/<model>`. Узлы обратной связи
> (`localhost`, `127.0.0.1`, `172.16.0.0/12`) разрешены всегда, как и имена хостов, указанные оператором
> в `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (например, имя сервиса Docker/Compose, такое
> как `http://reranker:8080/v1`; обращения к ним выполняются напрямую, без использования `HTTP(S)_PROXY` или
> закреплённого за подключением прокси). Узлы на любых других
> хостах — компьютере в локальной сети или пире Tailscale — разрешены только в том случае, если оператор включает
> флаг функции `RERANK_REMOTE_PROVIDER_NODES` **и** базовый URL узла соответствует политике
> исходящих URL провайдера (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> На этапе переранжирования движок памяти вызывает этот маршрут через
> интерфейс обратной связи, поэтому то же правило применяется к `rerankProviderModel` в настройках памяти.
>
> **Форматы локальных серверов:** узел вызывается по адресу `<base>/v1/rerank`, а при ответе 404 — по адресу `<base>/rerank`
> (Infinity, TEI). Тело запроса к вышестоящему сервису содержит как вариант написания Cohere/OpenAI (`documents`,
> `return_documents`), так и вариант TEI (`texts`, `return_text`), а ответ вышестоящего сервиса
> нормализуется в оболочку Cohere: простой массив TEI `[{index, score, text}]`, объект `{results: [{index, score}]}`
> от минималистичных шлюзов и объект Voyage-формата `{data: [...]}` возвращаются клиенту в виде
> `{results: [{index, relevance_score, document?}]}`, отсортированного по оценке и ограниченного значением `top_n`.

> **Обнаружение узлов провайдеров:** модели на OpenAI-совместимом узле провайдера отображаются в `GET /v1/models`
> с префиксом узла. Строки без метаданных конечной точки (что типично для локальных списков `/v1/models`)
> наследуют `apiType` узла, поэтому модели узла `embeddings` имеют `type: "embedding"`, а модели
> узла `rerank` — `type: "rerank"` вместо типа чата по умолчанию; явно заданное
> значение `supportedEndpoints` в синхронизированной или добавленной вручную строке по-прежнему имеет приоритет.

### `provider_options` для Exa и Tavily

Exa и Tavily считывают специфичные для провайдера поля из объекта с пространством имён:
`provider_options.exa` (или `provider_options["exa-search"]`) и `provider_options.tavily`
(или `provider_options["tavily-search"]`). Передаются только перечисленные ниже ключи. Каждый из них
проверяется по собственной схеме Zod в `open-sse/handlers/search/providerOptionsPassthrough.ts`,
а ключ с неверным типом отбрасывается. Все остальные ключи игнорируются, включая данные аутентификации, базовый URL,
`stream` и `outputSchema`. Плоские ключи, используемые другими провайдерами (`cx`, `depth`, ...), работают
как и раньше.

| Провайдер | Поля верхнего уровня                                                                                                                                                                                                                                                                                                                                                      | Вложенные                                                                                                                                                                        |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa       | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (плоские примитивы), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                            | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` объединяется со значением по умолчанию `{ text: true, highlights: true }` |
| Tavily    | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                                |

Общие поля всегда имеют приоритет: `query`, `max_results`, `filters` (домены), `country` и
тема, полученная из `search_type`. Для Exa значение `search_type: "news"` сохраняет `category: "news"`.
Tavily также принимает `search_type: "finance"` (`topic: "finance"`).

Общее поле `time_range` теперь передаётся обоим провайдерам: Exa получает `startPublishedDate` (временную
метку ISO), а Tavily — `start_date` (`YYYY-MM-DD`). Явно заданная дата в `provider_options`
переопределяет сопоставленное значение.

В результатах Exa поля `id`, `highlight_scores`, `summary`, `subpages`, `entities` и `extras` сохраняются в
`provider_raw`. В результатах Tavily сохраняются `images` и `favicon`.

Для учёта стоимости по-прежнему используется плоский реестр `costPerQuery`. Tavily списывает
больше кредитов за вызов при `search_depth: "advanced"`, и эта разница не отражается в
`usage.search_cost_usd`.

## API веб-загрузки

Извлекает содержимое по URL через настроенного поставщика веб-загрузки (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, тот же ключ API, что и для Parallel Search) возвращает только
Markdown — любой другой `format` приводит к `400` — и ограничивает содержимое 100 000 символами. Если
саму целевую страницу извлечь невозможно, вышестоящий сервис сообщает об этом в ответе HTTP 200;
OmniRoute преобразует такой ответ в `422` с фиксированным сообщением.

| Метод | Путь            | Описание                                                               |
| ----- | --------------- | ---------------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | Загрузка/скрейпинг URL — тело проверяется с помощью `v1WebFetchSchema` |

**Аутентификация:** Bearer-ключ API (`extractApiKey` + `isValidApiKey`). Политика применяется через `enforceApiKeyPolicy`.

**Резервирование с учётом квот (#8297):** если явный `provider` не указан, пул
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) обходится
в фиксированном
порядке приоритета (сначала заполняется первый) — настроенный поставщик с исчерпанным лимитом запросов пропускается
вместо немедленного завершения запроса, а повторяемая ошибка вышестоящего сервиса или ошибка квоты
(HTTP 429 всегда; 402/403 для бесплатных тарифов Firecrawl/Tavily/TinyFish с ограничениями квоты —
но не для Jina Reader и никогда для обычного некорректного запроса 400) приводит к переходу
к следующему ещё не опробованному поставщику с учётными данными во время выполнения запроса. Когда все поставщики
в пуле исчерпаны, конечная точка возвращает единый `429` (с заголовком `Retry-After`)
вместо прежнего универсального `400`. Если явно запрошен `provider`,
**скрытого** резервирования нет — поставщик, явно указанный и достигший лимита либо завершившийся ошибкой,
возвращает собственную ошибку (`429` при достижении лимита, иначе статус вышестоящего
сервиса).

## Потоковая передача через WebSocket

```bash
GET /v1/ws?handshake=1
```

Проверяет рукопожатие для обновления соединения до WebSocket и возвращает примеры сообщений протокола обмена (`request`, `cancel`). Фактические кадры WS обрабатываются встроенным WS-сервером за пределами таблицы маршрутов Next.js.

**Аутентификация:** Bearer-ключ API во время рукопожатия.

### Responses API через WebSocket (только codex)

```bash
# Тот же хост и порт, что и у HTTP API (по умолчанию 20128); обновите соединение:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (или: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Первым кадром ОБЯЗАТЕЛЬНО должен быть response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Прокси Responses API через WebSocket подключён **исключительно к `codex`** (серверная часть ChatGPT).
Он прослушивает тот же порт, что и API/панель управления, по путям `/v1/responses`,
`/responses` и `/api/v1/responses`. При получении первого кадра `response.create` он
выполняет аутентификацию и подготовку через внутренний мост `codex-responses-ws`, выбирает
OAuth-подключение codex и создаёт туннель к `wss://chatgpt.com/backend-api/codex/responses`
через транспорт `wreq-js`. **Модели, отличные от codex, отклоняются** (`codex_ws_provider_required`).
Для маршрутизации с разделением квот используйте `model: "qtSd/<group>/codex/<model>"`. Реализация находится в
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Аутентификация:** Bearer-ключ API во время рукопожатия. Встроенный HTTP-сервер (`server-ws.mjs`)
должен быть активной точкой входа (по умолчанию так и есть, если существует `app/server-ws.mjs`).

#### Идентификатор модели: используйте простой идентификатор ChatGPT (без префикса `codex/`)

OpenAI **Codex CLI** проверяет имя модели на стороне клиента, когда
`supports_websockets = true`, и **отклоняет идентификаторы с префиксом поставщика**, такие как
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Передавайте **простой** идентификатор (например, `gpt-5.5`). Мост OmniRoute
работает только с codex, поэтому перед созданием туннеля к вышестоящему сервису он повторно определяет простой идентификатор как модель codex
(`resolveCodexWsModelInfo`) — даже несмотря на то, что простой
`gpt-5.5` при использовании HTTP в ином случае был бы направлен другому поставщику.

#### Настройка OpenAI Codex CLI

Направьте Codex CLI на OmniRoute, добавив пользовательского поставщика с поддержкой WebSocket
в `~/.codex/config.toml` (используйте отдельный `CODEX_HOME`, чтобы не затрагивать
существующую конфигурацию):

```toml
model = "gpt-5.5"                 # простой идентификатор — НЕ "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # без завершающей косой черты; URL-адрес WS формируется автоматически (в рабочей среде используйте https/wss)
wire_api = "responses"                    # единственное поддерживаемое значение с февраля 2026 года
supports_websockets = true                # включает транспорт Responses через WS
env_key = "OMNIROUTE_API_KEY"             # содержит ключ API OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # ключ API OmniRoute (любой ключ, если REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI обновляет соединение по адресу `base_url + /responses` до WebSocket, а OmniRoute создаёт для него туннель
к выбранному OAuth-подключению codex. Работа проверена сквозным тестированием на локальном
сервере: ChatGPT возвращает `codex.rate_limits` + `response.created` и передаёт
завершение в потоковом режиме.

## Самостоятельный просмотр использования (`/api/usage/om-usage`)

Любой API-ключ может просматривать **собственные** данные об использовании и квотах — аутентификация управления не требуется. Это конечная точка, которую
клиент (CLI, панель OmniCopilot) использует, чтобы показать владельцу ключа его расходы.

```bash
# Текстовый формат (исторический контракт — обычный текст для терминала)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Структурированный формат — используется пользовательским интерфейсом
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Для ключа должна быть включена настройка **`allowUsageCommand`** (по умолчанию она отключена — диспетчер API-ключей
на панели управления переключает её отдельно для каждого ключа). Если она не включена, конечная точка отвечает кодом `403`.

`?format=json` возвращает различимую структуру, поэтому вызывающая сторона никогда не пытается прочитать поле данных
из ответа с отказом. В случае успеха:

```jsonc
{
  "allowed": true,
  // присутствует, только если для ключа включены индивидуальные лимиты использования (дневные/недельные, в USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // снимок квоты выбранного провайдера или null, если в кэше пока ничего нет:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // снимки всех подключений, чтобы пользовательский интерфейс мог отображать несколько провайдеров рядом:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

При отказе (`401` — неверный ключ / `403` — доступ не разрешён) тот же маршрут возвращает
`{ "allowed": false, "error": { "message": "…" } }` — присутствующее, но пустое значение `personal`/`provider`
(ключ разрешён, но данные ещё не получены) отличается от отказа, и различить эти состояния позволяет только формат JSON.

**Аутентификация:** собственный API-ключ Bearer вызывающей стороны, проверяемый с помощью `isValidApiKey` — это _не_
интерфейс управления (`/api/keys/…`), который по-прежнему защищён `requireManagementAuth`.

### Исходные и скорректированные с учётом порогового значения проценты квоты

При использовании `/api/usage/om-usage` вызывающим сторонам следует учитывать различие между
процентами, представленными в **текстовом выводе**, и структурированным **выводом JSON**:

| Аспект                     | Текстовый формат (`/api/usage/om-usage` / `@@om-usage`)                                                  | Формат JSON (`?format=json`)                                                                                   |
| :------------------------- | :------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------- |
| **Поле вывода**            | `NN% left` (например, `20% left`)                                                                        | `provider.quotas` / `providers[].quotas`                                                                       |
| **Измерение**              | **Доступный объём с учётом порога**: оставшаяся ёмкость сверх порогового значения                        | **Исходная квота вышестоящего провайдера**: нескорректированное измерение                                      |
| **Масштабирование порога** | Масштабируется через `effectiveRemainingPercent()`, поэтому защищённый резерв отображается как `0% left` | Отсутствует (исходные значения снимка в том виде, в котором их сообщил провайдер)                              |
| **Данные о пороге**        | Учитываются в отображаемом проценте                                                                      | Хранятся в `quotaWindowThresholds` для каждого подключения (либо используются серверные значения по умолчанию) |
| **Основной потребитель**   | Интерактивные CLI, терминальные подсказки, операторы                                                     | Программные интеграции, панели мониторинга, аналитика, средства учёта расходов                                 |

#### Формула корректировки с учётом порога

OmniRoute поддерживает упреждающие пороги отключения по квоте для предотвращения исчерпания ресурсов вышестоящего провайдера (они настраиваются через
`quotaWindowThresholds` подключения, значения провайдера по умолчанию или глобальные настройки устойчивости). Когда для окна квоты
действует порог отключения (например, `cutoff = 25%`), средство текстового отображения рассчитывает оставшийся доступный объём следующим образом:

- Если `remaining <= cutoff`: возвращает `0%`.
- Если `remaining > cutoff`: возвращает `((remaining - cutoff) / (100 - cutoff)) * 100`.

В форматированном текстовом выводе результат округляется до ближайшего целого числа (`Math.round(...)`).

#### Наглядный пример

Рассмотрим окно провайдера с **60% исходного использования** (то есть остаётся **40% исходной квоты**) и настроенным
порогом отключения на уровне **25% оставшейся квоты**:

| Представление                      | Расчёт                                             | Осталось |           Подразумеваемое использование           |
| :--------------------------------- | :------------------------------------------------- | :------: | :-----------------------------------------------: |
| **Исходный JSON (`?format=json`)** | Снимок вышестоящего провайдера (`quotas[window]`)  | **40%**  |                      **60%**                      |
| **Текстовый формат (`NN% left`)**  | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%**  | **80%** (если рассчитывать как `100 - remaining`) |

- **Почему в тексте отображается 20% оставшегося объёма:** из 40% физической квоты, оставшейся в учётной записи, 25% зарезервировано
  политикой порогового отключения. Вызывающей стороне доступно только 15% из 75% используемого запаса до того, как маршрутизатор прекратит
  направлять запросы этому подключению. Масштабирование гарантирует, что подключение сообщит об исчерпании (`0% left`) именно тогда,
  когда маршрутизация будет прекращена.
- **Почему JSON сохраняет исходные значения:** полезная нагрузка JSON возвращает точный снимок провайдера (`UsageSnapshot`),
  чтобы внешние инструменты имели доступ к достоверным данным об использовании ресурсов вышестоящего провайдера и параметрам
  `quotaWindowThresholds` на уровне подключения без необратимого масштабирования на стороне сервера.

#### Рекомендации по миграции потребителей

Если внешняя интеграция (например, плагин редактора или расширение агента) ранее извлекала данные из текстовой
конечной точки (`NN% left`) и вычисляла использованный процент как `100 - NN`, то переход на `?format=json` означает следующее:

- Чтение необработанных значений JSON будет отражать **фактическое потребление на вышестоящем уровне** (в приведённом выше примере использовано 60%).
- Если интеграции необходимо сохранить семантику доступного остатка текстовой конечной точки, она может вычислять
  формулу эффективного остатка на стороне клиента, используя `quotaWindowThresholds` для переопределений на уровне подключения.

## Семантический кеш

```bash
# Получить статистику кеша
GET /api/cache/stats

# Очистить все кеши
DELETE /api/cache/stats
```

Пример ответа:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Влияние на задержку

При ПОПАДАНИИ в семантический кеш ответ возвращается из кеша **без обращения к вышестоящему
сервису**, поэтому указанное значение `X-OmniRoute-Response-Latency` близко к нулю
(независимо от исходной задержки вышестоящего сервиса). Клиентам, чувствительным к задержке
(тестирование производительности, мониторинг p50/p99), следует проверять заголовок ответа
`X-OmniRoute-Cache-Latency`:

| Значение        | Описание                                                              |
| --------------- | --------------------------------------------------------------------- |
| `synthetic`     | Ответ получен из кеша; задержка не отражает реальное время сервиса    |
| _(отсутствует)_ | Ответ получен в результате реального обращения к вышестоящему сервису |

### Обход кеша для отдельного ключа

Ключи API могут отключить чтение из семантического кеша с помощью `cacheDefaultMode`:

| Значение | Поведение                                                                   |
| -------- | --------------------------------------------------------------------------- |
| `legacy` | Обычное поведение кеша (по умолчанию)                                       |
| `bypass` | Полностью пропустить поиск в кеше; всегда обращаться к вышестоящему сервису |

Задайте при создании ключа (`POST /api/keys`) или обновлении (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Обход кеша для отдельного запроса

Любой запрос может обойти кеш независимо от настроек ключа:

```
X-OmniRoute-No-Cache: true
```

Для синхронизированных или импортированных моделей `PUT /api/provider-models` принимает `provider`, `modelId` и
`maxOutputTokenOverride`: положительное целое число задаёт установленное вручную ограничение выходных токенов, а `null`
сбрасывает его и восстанавливает значение по умолчанию. `GET /api/provider-models?provider=<provider>` возвращает эти
значения в `modelOutputOverrides`, включая модели без записи пользовательской модели. Переопределение
использует возможность среды выполнения `max_output_tokens` и сохраняется после повторной синхронизации модели. Страница
OpenAI-совместимого провайдера предоставляет те же элементы управления для изменения и сброса, а также отмечает модели с явно заявленной поддержкой изображений.

Пользовательские узлы Chat Completions адаптируют явный отказ от рассуждений к вышестоящему бэкенду. При
успешной проверке подключения автоматически выбираются элементы управления шаблоном чата для каждого точного идентификатора модели,
в записи `/models` которого подтверждено распознанное значение `owned_by`: `vllm`, `sglang` или `llamacpp`.
Прозрачные OpenAI-совместимые обёртки могут сохранять исходную запись модели во вложенном
объекте `openai`; обнаружение проверяет до трёх таких уровней вложенности. Для моделей с отсутствующими, неизвестными или
конфликтующими данными о владельце сохраняется обычное поведение OpenAI. При обнаружении повторно используется существующий запрос каталога,
не генерируются токены завершения, а его результат аннулируется при изменении эндпоинта подключения.

Чтобы зафиксировать это поведение для бэкенда, который не предоставляет такие метаданные, используйте существующий API
частичного обновления провайдера:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Отправьте это тело с помощью `PUT /api/providers/<connection-id>`. Для этого подключения явный
уровень рассуждения `none` передаётся как `chat_template_kwargs.thinking=false` и
`chat_template_kwargs.enable_thinking=false`. Явно заданные нативные значения шаблона сохраняют приоритет,
если серверное правило рассуждения не задаёт уровень принудительно. Настройка применяется только тогда, когда пользовательское
OpenAI-совместимое подключение отправляет тело Chat Completions; запросы Responses и обычные
провайдеры сохраняют нативную структуру запросов. Установите для `reasoningControl` значение `openai`, чтобы принудительно включить обычную
сквозную передачу OpenAI-параметра `reasoning_effort`, либо не указывайте его или задайте `null`, чтобы использовать автоматическое обнаружение.

Для запросов классификатора Claude Code в автоматическом режиме нативное рассуждение по умолчанию отключено, если они
не содержат явных элементов управления рассуждением. Обнаружение использует системный маркер классификатора в запросах
формата Claude, а не имена моделей или ограничения завершения. Явные параметры тела, поддерживаемые заголовки уровня рассуждения/мышления,
правила маршрутизации и определённый уровень рассуждения модели сохраняют существующий приоритет. На обоих этапах работы классификатора
сохраняются промпты, ограничения завершения, последовательности остановки и фактические решения вышестоящего сервера
о разрешении; второй этап по-прежнему может выводить запрошенные видимые рассуждения как обычный текст.

### Версия и канал выпуска

```bash
GET /api/system/version
```

Маршрут управления, доступный только через loopback-интерфейс (требуется аутентификация администратора). Возвращает запущенную версию, последнюю опубликованную версию и состояние автоматического обновления. `releaseChannel` и `channels` — дополнительные поля (ветка 3.8.54); `channel` сохраняет своё значение — режим развёртывания, используемый средством обновления панели управления (`npm`, `source` или `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — npm-канал запущенной сборки: `nightly` для версий `-nightly.*`,
  `next` для других предварительных выпусков (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` для стабильной версии,
  основной номер которой меньше, чем у `channels.latest`, и `latest` во всех остальных случаях. Используются те же правила, что и в
  `scripts/release/dist-tag.mjs`, который выбирает dist-tag npm при публикации.
- `channels` — последняя опубликованная версия для каждого dist-tag, полученная из `npm view omniroute dist-tags` (с резервным
  обращением к реестру по HTTP) и кэшируемая с тем же TTL в 10 минут, что и `latest`. `latest` присутствует всегда
  (при отсутствии используется поле `latest`, а затем `"unavailable"`); `next`, `nightly` и `lts` отображаются
  только при наличии соответствующего dist-tag. Запрос с `Cache-Control: no-cache` обновляет результаты обоих обращений.

Модель каналов (`latest` = v3 до общедоступного выпуска 4.0, `next` = rc, `nightly` = сборки `develop`,
`lts` = исправления v3 после общедоступного выпуска 4.0) описана в `docs/ops/RELEASE_STRATEGY.md`.

## Транскрибирование аудио

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

Транскрибируйте аудиофайлы с помощью любого настроенного поставщика STT. Первый сегмент пути
выбирает нативного поставщика (`openai/…`, `deepgram/…`). Для шлюзов, которые
повторно экспортируют модель другого поставщика, используется составной идентификатор
(`openrouter/deepgram/nova-3`).

**Запрос:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**Ответ:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**Примеры идентификаторов моделей:** `openai/whisper-1` (требуется ключ OpenAI),
`openrouter/deepgram/nova-3` (требуется ключ OpenRouter),
`deepgram/nova-3` (требуется нативный ключ Deepgram). Запрос с простым идентификатором
`deepgram/nova-3` **не** использует OpenRouter.

**Поддерживаемые форматы:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

## Токенизированные псевдонимы для VS Code / без заголовков

Используйте эти псевдонимы, если интеграция не может добавить заголовок `Authorization` и необходимо встроить ключ API в базовый URL.

```bash
# Псевдоним каталога в стиле OpenAI
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# Псевдонимы чата в стиле OpenAI
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Псевдонимы в стиле Ollama
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

Пример:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

Примечания:

- Токенизированные псевдонимы используют те же обработчики, что и `/v1/*` и `/api/tags`; структуры ответов остаются идентичными.
- По возможности используйте `Authorization: Bearer ...`, если клиент поддерживает пользовательские заголовки.
- Токены в URL могут попадать в журналы обратного прокси, историю браузера и телеметрию за пределами OmniRoute. Рассматривайте их как вариант для обеспечения совместимости, а не как режим аутентификации по умолчанию.

Необязательные поля: `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`). Устаревшая структура `{keyId, limit, period}` возвращает `400 Bad Request`.

## Лимиты токенов

Бюджеты **токенов** для каждого API-ключа (отдельные от указанного выше бюджета в долларах США). Применяются непосредственно при обработке запроса: когда использование ключа в текущем временном окне достигает установленного лимита, запросы отклоняются с ошибкой `429 Too Many Requests`. Лимиты могут быть ограничены конкретной `model`, конкретным `provider` или применяться глобально (`global`) для всего ключа; если запросу соответствуют несколько лимитов, применяется наиболее строгий из них.

```bash
# Вывести лимиты токенов ключа (включая текущее использование в рамках окна)
GET /api/usage/token-limits?apiKeyId=key-123

# Создать или обновить лимит токенов
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Удалить лимит токенов по идентификатору
DELETE /api/usage/token-limits?id=tl-abc
```

> **Примечания к схеме** (`setTokenLimitSchema`): `apiKeyId` и `scopeType` (`model` | `provider` | `global`) обязательны. `scopeValue` обязателен, если только `scopeType` не равен `global` (например, идентификатор модели для области действия `model` или идентификатор провайдера для области действия `provider`). `tokenLimit` должен быть положительным целым числом (строка преобразуется в число). Необязательные поля: `id` (не указывайте для создания, укажите для обновления), `resetInterval` (`daily` | `weekly` | `monthly`, по умолчанию `monthly`), `resetTime` (`HH:MM`), `enabled` (по умолчанию `true`). Ответы `GET` дополняют каждый лимит полями `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` и `nextResetAt`. Это конечная точка класса управления (аутентификация централизованно обеспечивается конвейером авторизации).

## Обработка запросов

1. Клиент отправляет запрос в `/v1/*`
2. Обработчик маршрута вызывает `handleChat`, `handleEmbedding`, `handleAudioTranscription` или `handleImageGeneration`
3. Определяется модель (напрямую через провайдера/модель либо через псевдоним/комбинацию)
4. Учетные данные выбираются из локальной БД с фильтрацией по доступности учетной записи
5. Для чата: `handleChatCore` проверяет семантический кэш/кэш сигнатур и определяет настройки сжатия комбинации
6. Если включено проактивное сжатие, оно выполняется до преобразования запроса для провайдера (`lite`, Caveman, RTK или их сочетание)
7. Исполнитель провайдера отправляет запрос во внешний сервис
8. Ответ преобразуется обратно в клиентский формат (для чата) или возвращается без изменений (для векторных представлений, изображений и аудио)
9. Регистрируются использование, аналитика сжатия и журналы запросов
10. При ошибках применяется резервный вариант в соответствии с правилами комбинации

Полное описание архитектуры: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Отказоустойчивость (расширенная)

OmniRoute предоставляет три независимых механизма обработки временных сбоев; указанные ниже конечные точки управления позволяют операторам просматривать и переопределять их состояние:

| Область действия                | Хранилище состояния                          | Просмотр                                  | Сброс / очистка                                               |
| ------------------------------- | -------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------- |
| Предохранитель провайдера       | `domain_circuit_breakers` + в памяти         | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                  |
| Период ожидания для подключения | `rateLimitedUntil` в подключениях провайдера | `/api/rate-limits`, `/api/providers/[id]` | (повторно включается отложенно; очистка через PUT провайдера) |
| Блокировка модели               | Реестр доступности моделей в памяти          | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                      |

`PATCH /api/resilience` принимает переопределения предохранителей провайдеров в `providerBreaker.oauth` и `providerBreaker.apikey`. Каждый профиль поддерживает `degradationThreshold`, `failureThreshold` и `resetTimeoutMs`; те же поля доступны в Панель управления → Настройки → Отказоустойчивость.

```bash
# Очистить блокировку одной модели
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Удалить все блокировки
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Полное концептуальное описание и значения предохранителей по умолчанию: см. [`CLAUDE.md`](../../CLAUDE.md) → «Состояние среды выполнения отказоустойчивости» и [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Очередь ограничения частоты запросов и механизм автоматического включения

- **Поддерживаемый способ записи**: `POST /api/rate-limits` с телом `{"connectionId": "<id>", "enabled": true|false}` — это поддерживаемая конечная точка управления для включения или отключения защиты подключения от превышения частоты запросов. `PUT /api/providers/[id]` намеренно не изменяет и не переключает `rateLimitProtection` (#11278).
- **Семантика `enabled: false`**: Установка `enabled: false` удаляет явную защиту подключения, но **не** исключает активное подключение с API-ключом из глобального механизма автоматического включения (`autoEnableApiKeyProviders = true`). В `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) значения `false` и `undefined` эквивалентны; активные подключения с API-ключами без явно заданной защиты остаются защищёнными глобальным механизмом автоматического включения.
- **Глобальное отключение**: Чтобы подключения с API-ключами работали без очередей ограничения частоты запросов, глобально отключите этот механизм с помощью `RATE_LIMIT_AUTO_ENABLE=false` (переменная окружения) или `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Настройки → Отказоустойчивость / `PATCH /api/resilience`).

```bash
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Поддерживаемые методы (все зависят от `settings.a2aEnabled`):

| Метод            | Описание                                                               |
| ---------------- | ---------------------------------------------------------------------- |
| `message/send`   | Синхронное выполнение навыка; возвращает `{task, artifacts, metadata}` |
| `message/stream` | Потоковое выполнение того же набора навыков через SSE                  |
| `tasks/get`      | Получение задачи по `taskId`                                           |
| `tasks/cancel`   | Отмена задачи по `taskId`                                              |

Встроенные навыки: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

## Аутентификация

Описание четырёх семейств учётных данных (сессия панели управления, локальный токен CLI, токен доступа `oma_live_…`, API-ключ с областью управления) и их отличий от ключей инференса см. в разделе [Аутентификация управления](../guides/MANAGEMENT-AUTH.md).

- Маршруты панели управления (`/dashboard/*`) используют cookie `auth_token`
- Для входа используется сохранённый хеш пароля; резервный вариант — `INITIAL_PASSWORD`
- Параметр `requireLogin` переключается через `/api/settings/require-login`
- Маршруты `/v1/*` могут требовать Bearer API-ключ, если `REQUIRE_API_KEY=true`
- «Токен управления» / «API-ключ с областью управления» в этом справочнике означает одно из семейств, описанных в указанном руководстве, а не дополнительный неопределённый тип секрета

> **Критическое изменение (v3.8.0)** — `/api/v1/agents/tasks/*` и конечные точки управления периодом ожидания теперь требуют **аутентификацию управления** (cookie панели управления `auth_token` или API-ключ с областью управления). Клиенты, которые ранее вызывали эти маршруты без аутентификации, получат `401 Unauthorized`. См. коммит `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
