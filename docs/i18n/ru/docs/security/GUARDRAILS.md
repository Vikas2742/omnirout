> какие маршруты и пути ответов охватывают хуки, объединённые заголовки отключения (#16412), режим
> блокировки инъекций как обязательная граница (#16413) и что видит ответ до этапа post-call)

Защитные механизмы обеспечивают безопасность, соблюдение политик и преобразования контента на границе
между OmniRoute и вышестоящими провайдерами. Каждый защитный механизм может проверять (и
при необходимости отклонять, преобразовывать или аннотировать) полезную нагрузку запросов (`preCall`) и
ответы вышестоящих провайдеров (`postCall`).

Система работает по принципу **fail-open**: если при выполнении защитный механизм выбрасывает исключение, реестр
записывает ошибку и переходит к следующему защитному механизму, вместо того чтобы завершать запрос с ошибкой. Блокировка — это явное решение (`block: true`), а не случайность.
Единственное исключение — прерванный запрос: когда `signal` вызывающей стороны прерван,
защитный механизм, выбросивший исключение, отклоняет выполнение хука, вместо того чтобы быть пропущенным.

Хуки **не** запускаются на каждом маршруте и не выполняются для каждого ответа. Прочитайте
[Покрытие и ограничения](#coverage-and-limits), прежде чем полагаться на защитный механизм как на
средство обеспечения безопасности.

## Встроенные защитные механизмы

Реестр автоматически загружает шесть защитных механизмов в порядке приоритета при импорте
(см. `registry.ts` → `registerDefaultGuardrails()`):

| Приоритет | Название            | Этап(ы)        | Файл                  |
| --------- | ------------------- | -------------- | --------------------- |
| `5`       | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`       | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`       | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`      | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`      | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`      | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

Механизмы с меньшим числом приоритета запускаются **первыми**.

### Vision Bridge (`visionBridge.ts`) — модальный мост PR-1

Базовая модель GLM 5.3 и `glm-5.3-{low,high,max}` имеют явные
метаданные реестра/спецификации `supportsVision:false`. Варианты GLM 5.3 Flash
остаются моделями с нативной поддержкой зрения. Маршрут `/v1/messages` в Claude Code входит в
общую цепочку защитных механизмов `handleChat`, выполняемых перед вызовом, **до** преобразования Claude-to-OpenAI
; вложенные изображения из результатов инструмента `Read` должны быть описаны или обработаны
до того, как это преобразование перенесёт их в контент `image_url` OpenAI (#17069).

Перехватывает запросы с изображениями, адресованные **моделям без поддержки зрения**, и либо
перенаправляет весь запрос модели, поддерживающей зрение, либо заменяет части-изображения
текстовыми описаниями, созданными настраиваемой моделью зрения, перед
вызовом вышестоящего провайдера. Это позволяет провайдерам, работающим только с текстом, прозрачно обрабатывать
мультимодальные полезные нагрузки.

Поток:

1. Пропустить, если целевая модель уже поддерживает зрение (если только она не присутствует в
   списке принудительного использования моста `isVisionBridgeForcedModel`).
2. Извлечь части-изображения через `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), который делегирует **унифицированному детектору медиа**
   `detectMediaParts()` в `open-sse/utils/mediaParts.ts` — единому
   источнику истины, общему с фильтром совместимости комбо.
   Извлечение разрешено только для форм, которые `replaceImageParts` может вставить
   обратно (контракт «извлечение↔замена»): OpenAI `image_url`, Anthropic base64
   `source.type:"base64"`, Anthropic URL `source.type:"url"` и Responses
   API `input_image`. Совпадающие изображения, вложенные в Claude Code
   `tool_result.content` и в выходные данные инструментов Responses, также извлекаются и
   заменяются по исходным путям; формы, содержащие только индикатор, относятся к материалам фильтра комбо и не извлекаются.
   Пропустить, если ничего не найдено.
3. Определить конфигурацию времени выполнения через `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): новые ключи настроек `modalityBridge*`
   имеют приоритет; устаревшие ключи `visionBridge*` остаются **резервным вариантом на один цикл**
   (окно отката). Пропустить до любого обхода медиа, если
   мост отключён.
4. Селектор режима (`modalityBridgeVisionMode`, см. таблицу ниже) определяет,
   перенаправлять запрос или описывать изображения. При перенаправлении возвращается `modifiedPayload`, в котором заменён только `model`,
   плюс метаданные `{ rerouted, fromModel, toModel, imagesKept }`.
5. Путь описания: ограничить число изображений значением `maxImages`, составить промпт с учётом задачи,
   обратиться к кешу описаний, вызвать модель зрения **параллельно**
   (`Promise.allSettled`) и внедрить текстовые части `[Image N]: <description>` на
   их место. Неудачное описание возвращает `null`: исходное изображение сохраняется для
   неизвестных целей или целей с поддержкой зрения (#4012), но **подтверждённая прямая цель только с текстом**
   или комбо без поддержки зрения получает явную
   текстовую заглушку `(unavailable — no vision-capable provider connected)` для
   каждого неописанного изображения, включая частичные сбои и изображения сверх
   лимита изображений на вызов описания (#17069). Существующий резервный механизм описания для комбо, где все вызовы завершились неудачно,
   остаётся на месте (#8430).
6. Вернуть `modifiedPayload` + метаданные (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### Селектор режима (`modalityBridgeVisionMode`)

| Режим      | По умолчанию | Поведение                                                                                                                                                                                                                                                                                                                                                                                              |
| ---------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `auto`     | ✔            | Прежняя эвристика без изменений (#6640/#7204): модели, не являющиеся combo/`auto/`, перенаправляются на лучшую модель с поддержкой изображений, если у исходной модели уже нет пригодных учётных данных (в таком случае выполняется описание); целевые combo-модели всегда выполняют описание.                                                                                                         |
| `describe` |              | Всегда выполнять описание — блок перенаправления полностью пропускается; всегда отвечает выбранная пользователем модель.                                                                                                                                                                                                                                                                               |
| `reroute`  |              | Принудительное перенаправление: проверка, сохраняющая модель с учётными данными, обходится. Проверка учётных данных **целевой** модели перенаправления по-прежнему применяется — если подходящей целевой модели с поддержкой изображений нет, мост блокирует запрос с понятной ошибкой, а не выполняет описание или отправляет необработанные изображения целевой модели, поддерживающей только текст. |

Принудительные режимы завершают обработку **до** запуска автоматической эвристики; поведение `auto`
побайтово идентично защитному механизму до PR-1.

#### Область действия API-ключа (`visionBridgeKeyScope.ts`)

Когда API-ключ вызывающей стороны ограничивает `allowedConnections`, пулы квот
(`allowedQuotas`) или модели (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), мост выбирает для
перенаправления и описания только те модели, которые разрешено использовать
этому ключу, через разрешённые для него подключения. Затем вызов описания всегда
проходит через внутреннюю петлю OmniRoute с заголовком
`x-omniroute-self-loop-key-id`, чтобы принимающий запрос чата повторно применил
политику подключений и моделей этого ключа. `enforceApiKeyPolicy()`
учитывает этот заголовок только вместе с bearer-токеном внутренней петли, поэтому
он может лишь сужать доступ, а идентификатор, который не удаётся разрешить,
отклоняется.

Если для ключа не разрешена ни одна модель с поддержкой изображений, то
**подтверждённая целевая модель, поддерживающая только текст**, локально отклоняет
запрос с изображением, возвращая понятный HTTP 400, вместо пересылки байтов
изображения неспособному их обработать вышестоящему сервису (#17069). Для целевых
моделей с неизвестной или встроенной поддержкой изображений путь описания
сохраняет прежнее поведение fail-open (метаданные
`{ skipped: true, reason: "no_permitted_vision_model" }`). Запросы без ключа и
ключи без этих ограничений ведут себя точно так же, как и раньше.

#### Промпт описания с учётом задачи (`modalityBridgeVisionTaskAware`)

По умолчанию — **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`)
добавляет текст **последнего сообщения пользователя** (обрезанный до 500 символов)
к базовому промпту описания, направляя описание на то, о чём фактически спросил
пользователь (паттерн codex-vision-proxy), и запрашивая у модели с поддержкой
изображений расшифровку видимого текста. Если флаг отключён или пользовательский
текст отсутствует, базовый промпт используется без изменений.

Собственный OpenAI-совместимый запрос внутренней петли описания
(`callVisionModelSingle()` в `visionBridgeHelpers.ts`) всегда запрашивает
`image_url.detail: "high"` — безусловно, для любой вызывающей стороны и любого
провайдера, независимо от каких-либо клиентских сигналов. Выборка с низкой
детализацией ухудшает точность OCR именно для той задачи расшифровки текста,
которую задаёт этот промпт, поэтому сам вызов описания всегда запрашивает высокую
детализацию независимо от уровня детализации исходного входящего запроса. Это
влияет только на тело внутреннего запроса описания; это не изменяет способ, которым
OmniRoute передаёт собственное значение `image_url.detail` вызывающей стороны в
основном запросе — это значение по умолчанию применяется отдельно и только для
обнаруженных клиентов OpenCode в `defaultImageDetail()`
(`open-sse/handlers/chatCore/upstreamBody.ts`). Ветвь внутренней петли описания
с форматом передачи Anthropic не содержит поля `detail`, поэтому ни одно из этих
значений по умолчанию на неё не влияет.

#### Ограничение размера результата описания (`modalityBridgeVisionMaxChars`)

| Ключ                           | По умолчанию | Диапазон          |
| ------------------------------ | ------------ | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`          | `0` или 100–50000 |

`0` (значение по умолчанию) означает **отсутствие ограничения** — описание,
возвращённое `callVisionModel()`, передаётся без изменений, сохраняя существующее
поведение. Любое значение в диапазоне 100–50000 обрезает описание с добавлением
суффикса `…` до его вставки обратно в виде `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` в `src/lib/guardrails/visionBridge.ts`).
Увеличьте это значение для задач OCR с большим количеством деталей, где
последующей модели нужна полная расшифровка; уменьшите его, чтобы ограничить
расход токенов многословными моделями с поддержкой изображений. Поле панели
управления находится в разделе Advanced вкладки Vision
(`modality-bridge-max-chars` в `ModalityBridgeVisionTab.tsx`) и повышает любое
значение от 1 до 99 до минимального значения 100, оставляя явно указанное `0`
без изменений — `0` само по себе является допустимым значением Zod
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не просто
значением по умолчанию «не задано».

#### Кэш описаний (`modalityBridge/bridgeCache.ts`)

Общий для всего процесса кэш LRU + TTL в памяти для результатов описания.
Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` с
кадрированием по префиксам длины (без коллизий на границах полей). Компонент
модели — это **настроенная** модель моста, а не модель, которая фактически
ответила: `callVisionModel` может внутренне переключиться на резервную модель,
а формирование ключа для каждой попытки фрагментировало бы кэш. Неудачные
описания никогда не кэшируются. Настройки:

| Ключ                            | По умолчанию | Диапазон |
| ------------------------------- | ------------ | -------- |
| `modalityBridgeCacheEnabled`    | `true`       | —        |
| `modalityBridgeCacheTtlMinutes` | `60`         | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`        | 10–5000  |

#### Нормализация удалённых изображений (self-loop: describe и получение base64)

Когда мост сам загружает **удалённое** изображение — при самовызове describe для Anthropic и при преобразовании base64 в формат claude-wire (`ensureBase64ImagesForClaudeWire`), оба через `fetchRemoteImageAsDataUri()` в `visionBridgeHelpers.ts` — полученный data URI проходит через `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) перед встраиванием в запрос к vision-модели. Слишком большие изображения уменьшаются до **2048px по длинной стороне** (в соответствии с ограничением изменения размера, которое OpenAI/Anthropic уже применяют на стороне сервера), что сокращает объём загружаемых байтов и задержку, не меняя того, что видит vision-модель. Изменение размера использует `sharp`, загружаемый через динамический импорт: на платформе, где его нативный бинарный файл не загружается, `normalizeDataUri()` **никогда не выбрасывает исключение** — он переходит к сквозной передаче исходных байтов, поэтому путь describe/преобразования base64 всегда продолжает работать. Байты, не являющиеся изображением (случай fetch, который не вернул декодируемое изображение), также передаются без изменений. Эта нормализация ограничена изображениями, которые мост загружает для собственного самовызова — она никогда не применяется к исходной сквозной полезной нагрузке вызывающей стороны, в соответствии с принципом изменения только при явном согласии (Hard Rule #20).

#### Схема настроек и миграция

Новые ключи `modalityBridge*` проходят Zod-валидацию в `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, трио `modalityBridgeCache*` и группа `modalityBridgeAudio*`, используемая Audio Bridge. Миграция `141_modality_bridge_settings.sql` копирует существующие устаревшие значения `visionBridge*` в соответствующие новые ключи (идемпотентно, никогда не перезаписывает значение `modalityBridge*`, заданное оператором); устаревшие ключи остаются принимаемыми как резервный вариант чтения на один цикл релиза.

#### Заголовок прозрачности и статистика

Ответы, преобразованные describe, несут `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` (формируется `buildModalityBridgeHeader()` в `modalityBridge/bridgeStats.ts`, проставляется `withModalityBridgeHeader()` в `src/sse/handlers/chatHelpers.ts`). Перемаршрутизированные запросы **не** получают заголовок — полезная нагрузка осталась нетронутой, а смена модели уже видна в поле `model` тела ответа.

`GET /api/modality-bridge/stats` (аутентификация уровня управления, тот же уровень, что и `GET /api/settings`) возвращает хранящиеся в памяти счётчики по модальностям `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` и `video`. `averageLatencyMs` использует `latencySamples`, а не все попытки, в качестве знаменателя; операция без замера времени не создаёт фиктивный образец в ноль миллисекунд. `bridged` остаётся обратно совместимым псевдонимом для успешных преобразований; неудачные попытки его не увеличивают. Счётчики сбрасываются при перезапуске процесса по замыслу (это телеметрия, а не бухгалтерский учёт).

#### Настройка дашборда

Выделенная страница дашборда — `/dashboard/settings/modality-bridge`. Её вкладки `Vision`, `Audio` и `Video`, адресуемые через URL, сохраняют параметры запроса при переключении значения `tab`. Вкладка Vision предоставляет включение, режим, выбор модели (включая автоматический вариант по умолчанию), task-aware-подсказки, расширенные лимиты тайм-аута/изображений/длины описания/кэша, счётчики времени выполнения и защищённый пример запроса. Вкладка Audio также активна: она предоставляет включение, выбор модели только для STT с Auto, лимиты тайм-аута/максимальной длины клипа, аудиосчётчики и пробный тест `input_audio`. Вкладка Video функциональна: она сообщает состояние среды выполнения FFmpeg/ffprobe — одно из четырёх явных состояний UI (`unknown`, пока проверка выполняется или не смогла завершиться; `restricted` на хосте дашборда, не являющемся loopback, где проверка пропускается на стороне клиента; `unavailable`, если после проверки подтверждено отсутствие; или `available` с версиями FFmpeg/ffprobe) — сохраняет лимиты включения/модели/кадров/видео/тайм-аута, фильтрует выбор модели до моделей, поддерживающих vision, и предоставляет видеосчётчики.

Бывшая карточка Vision Bridge в настройках AI теперь является ссылкой для совместимости на новую страницу; она больше не содержит второй копии формы. Media Providers также связывает сценарии Image-to-Text и Speech-to-Text с соответствующими вкладками Modality Bridge, не удаляя существующую песочницу Speech-to-Text.

**Обход допуска при self-loop:** когда вызов describe маршрутизируется через собственный self-loop OmniRoute `/v1` (нестандартная модель провайдера), подзапрос отправляет `x-omniroute-admission-bypass: internal` и аутентифицируется с использованием разрешённых учётных данных self-loop — локального sentinel-значения `sk_omniroute` в локальном режиме или настроенного оператором ключа окружения `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350), чтобы развёртывания с `REQUIRE_API_KEY=true` всё ещё могли выполнять вызов describe. Обход учитывается только для этих конкретных учётных данных, поэтому внешние клиенты не могут использовать заголовок для пропуска допуска.

Устаревшие значения по умолчанию находятся в `src/shared/constants/visionBridgeDefaults.ts`; новые значения по умолчанию для режима/task-aware/кэша и резолвер настроек находятся в `src/shared/constants/modalityBridgeDefaults.ts`. Guardrail предоставляет опцию конструктора `deps`, чтобы тесты могли внедрять фиктивные реализации `getSettings` и `callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехватывает чат-запросы с аудио, прежде чем они достигнут цели, о которой не известно, что она принимает аудиовход. Он никогда не перенаправляет чат-запрос: аудиочасти транскрибируются через существующий multipart-эндпоинт, совместимый с OpenAI, а выбранная чат-модель продолжает работу с текстовыми транскриптами.

Поток:

1. `supportsAudio` разрешается через `getResolvedModelCapabilities()`. Приоритет имеют
   явные метаданные реестра провайдеров, затем статические метаданные модели, затем
   синхронизированное `modalities_input`. Объявленный список входных данных без
   `audio` даёт `false`; при отсутствии свидетельств о возможности остаётся `null`.
   И `false`, и `null` активируют консервативный мост, а `true` обходит его.
2. Разрешите настройки `modalityBridgeAudio*` и извлеките вставляемые аудиочасти
   верхнего уровня из каждого сообщения с помощью общего детектора
   `detectMediaParts()`. Поддерживаемые форматы передачи — OpenAI `input_audio`,
   `audio_url` и `source.media_type: "audio/*"`. Вложенное аудио обнаруживается для
   маршрутизации, но не удаляется путём вставки. Объём работы ограничен
   `modalityBridgeAudioMaxClips`; последующие части остаются нетронутыми.
3. Используйте настроенный `provider/model` либо позвольте `selectAudioBridgeModel()`
   пройти по `AUDIO_TRANSCRIPTION_PROVIDERS` в стабильном порядке каталога и выбрать
   первую модель с пригодными действующими учётными данными провайдера.
4. `callAudioTranscription()` преобразует аудио в base64/data-URI в multipart-`file`
   либо скачивает удалённый `audio_url` через публичный исходящий шлюз только для
   публичных адресов с привязкой DNS и ограничением в 25 МБ. Затем он отправляет
   POST с файлом и выбранной моделью на локальный self-loop `/v1/audio/transcriptions`,
   аутентифицируясь через `resolveSelfLoopBearer()`. Существующий маршрут
   транскрипции выполняет обычный поиск учётных данных, обработку cooldown/rate-limit
   и диспетчеризацию к провайдеру.
5. Успешные вызовы заменяют свои части на `[Audio N]: <transcript>`. Вызовы
   выполняются через `Promise.allSettled`: отдельный сбой сохраняет исходную
   аудиочасть (контракт #4012). Если все вызовы завершились неудачей и для цели
   доказано `supportsAudio === false`, части становятся
   `[Audio N]: (unavailable — no STT provider connected)` (контракт #8430). Для
   неизвестной цели (`null`) результат полного отказа остаётся нетронутым.
   Доказанная цель только с текстом без пригодных учётных данных STT получает ту же
   явную заглушку без выполнения сетевого вызова.

Успешные транскрипты используют общий для процесса LRU/TTL-кэш Modality Bridge.
Ключ объединяет аудиоссылку, стабильную метку операции `audio-transcription` и
выбранную модель STT; сбои никогда не кэшируются. Попытки работы с аудио обновляют
общие счётчики `bridged`, `cacheHits`, `failures` и `lastUsedAt`. Преобразованные
ответы несут
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; нетронутые
запросы не получают сегмент Audio Bridge.

Параметры времени выполнения хранятся в БД и валидируются Zod:

| Ключ                          | По умолчанию | Диапазон        |
| ----------------------------- | ------------ | --------------- |
| `modalityBridgeAudioEnabled`  | `true`       | —               |
| `modalityBridgeAudioModel`    | `""`         | Auto или STT ID |
| `modalityBridgeAudioTimeout`  | `60000`      | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`          | 1–10            |

Общий кэш по-прежнему управляется `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` и `modalityBridgeCacheMaxEntries`.

### Video Bridge (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехватывает видеочасти верхнего уровня в `messages` Chat Completions и `input`
Responses API до вызова цели без известной нативной поддержки видео.
Поддерживаемые форматы — `input_video`, `video_url`, `video_source`, HTTPS-URL
и data-URI вида `data:video/*;base64,...`. Простые имена файлов в тексте не
рассматриваются как видео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) отвечает за обход запроса,
проверку возможностей/политики, агрегацию в рамках запроса и полезную нагрузку
ответа. Работа по каждому видео — получение, кэш по всему результату, описание
последовательности кадров (которое объединяет любой объявленный вызывающей стороной
аудиотранскрипт) и метрики/прерывание/очистка на каждую попытку — скрыта за
`processVideoPart` в `videoBridgePipeline.ts`, вызываемой один раз на каждую
видеочасть внутри цикла `preCall`. Этот модуль также определяет явные границы
портов `VideoMediaBrokerPort` (получение байтов и извлечение выборочных кадров),
`VideoAudioTranscriptionPort` (объединение объявленного вызывающей стороной
аудиотранскрипта с выборочными субтитрами) и `VideoDrilldownPort` (граница
сохранения детализации по кадрам; пока не подключена в `processVideoPart` — на
сегодня записи детализации записывает только отдельный маршрут
`/api/modality-bridge/video/drilldown`).

Публичный путь запросов `/v1` никогда не импортирует и не вызывает подпроцесс.
Удалённые видео скачиваются с ограничением 50 MiB; для встроенных base64-видео
действует консервативное ограничение 36 MiB в декодированном виде на каждое видео,
чтобы модель/messages/кадрирование могли уложиться в лимит допуска публичных
JSON-запросов в 50 MiB. Оценки длины встроенных данных и декодированного размера
проверяются до выделения памяти. HTTPS требуется для исходного удалённого URL и
каждого перенаправления, с использованием существующего исходящего шлюза только для
публичных адресов с привязкой DNS. Затем байты пересекают точную границу внутреннего
брокера `POST /api/modality-bridge/video/extract`. Этот маршрут одновременно
`LOCAL_ONLY` и `SPAWN_CAPABLE`, принимает только аутентифицированный запрос с
доверенного loopback в рамках процесса и никогда не принимает URL, путь в
файловой системе, исполняемый файл или список аргументов. Конвейер размера тела API
и инкрементальный читатель тела в обработчике независимо друг от друга обеспечивают
ограничение входных данных брокера в 50 MiB. Его ограниченная очередь выполняет
одно извлечение за раз, допускает четыре ожидающих задания и ограничивает ожидающие
входные данные 100 MiB.

Внутри брокера `ffprobe` читает приватный локальный файл; фиксированный список разрешённых форматов исключает форматы плейлистов и манифестов. Для разрешённых контейнеров семейства MOV внешние ссылки на данные MOV по умолчанию остаются отключёнными, и фиксированная команда не включает их. И `ffprobe`, и `ffmpeg` используют белый список протоколов, допускающий только `file`, один поток, фиксированные массивы аргументов, без оболочки, а исполняемые файлы разрешаются через `PATH`. Потоки обложек в виде прикреплённых изображений не являются кандидатами для воспроизведения. Все воспроизводимые потоки должны удовлетворять ограничениям, и явно заданный поток по умолчанию имеет приоритет перед детерминированным откатом к потоку с наименьшим индексом. Видео ограничены 600 секундами, 8 192 пикселями на измерение и 33 554 432 исходными пикселями. FFmpeg выбирает от 1 до 16 JPEG-кадров из серединных точек, уменьшает длинную сторону максимум до 1 024 пикселей, не увеличивая меньшие входные данные, и никогда не получает URL. По умолчанию используется выборка `uniform`. Необязательные политики `scene_aware` и экспериментальная `segment_aware` выполняют один дополнительный фиксированный проход FFmpeg по уже проверенному локальному потоку, выбирают ограниченные временные метки сцен `showinfo` и детерминированно откатываются к тем же серединным точкам `uniform` при сбое детектора, тайм-ауте, некорректном выводе или пустом наборе кандидатов. Режим `segment_aware` распределяет серединные образцы пропорционально проверенным интервалам сцен; свидетельства и поведение отката для `segment_aware` подробно описаны ниже. Жёсткое ограничение в 16 кадров применяется после выбора в каждой политике. Когда запрос `scene_aware` имеет бюджет только в один кадр, он использует серединную точку `uniform` активного окна полного видео или окна фокуса и сообщает `policyEffective: uniform`: один выбранный кадр сцены не может сохранить оба временных конца. Вызывающая сторона может дополнительно предоставить конечное окно фокуса (секунды `start`/`end`); границы ограничиваются длительностью медиа, перевёрнутые или неконечные окна отклоняются, а все политики выборки применяются только внутри нормализованного интервала. Итоговое окно включается в метаданные выборки и в префикс недоверенного описания, чтобы нижестоящие модели могли отличить фокусированный фрагмент от полной временной шкалы.

Семантический фокус подписи — это отдельная явная настройка. Режим анализа по умолчанию `full` сохраняет существующий промпт кадра и никогда не передаёт текст запроса модели подписей. В режиме `focused` мост читает только последний непустой `text`/`input_text`, созданный пользователем, из того же контейнера Chat или Responses, нормализует его в NFC, сжимает последовательности управляющих символов и пробелов и ограничивает его 500 кодовыми точками Unicode. Пустой результат откатывается к точному промпту `full`. Пригодная подсказка сериализуется как JSON в выделенный блок недоверенного пользовательского контекста и может только расставлять приоритеты для наблюдаемых деталей; она не может переопределить отдельное предупреждение против следования инструкциям, видимым или слышимым в медиа. Текстовый фокус никогда не выводит `start`/`end` и не изменяет временной сэмплер.

#### FU-07 Структурные свидетельства сегментов

`segment_aware` использует один ограниченный проход предварительного анализа по уже проверенному локальному видеопотоку. Фиксированная цепочка фильтров сначала масштабирует изображение до ширины не более 320 пикселей, обнаруживает смены сцен и замороженные интервалы, затем с частотой 1 кадр в секунду выбирает данные о размытии, средней яркости и пространственной/временной информации. Проход ограничен 600 структурными образцами, одним потоком FFmpeg/фильтра, теми же белыми списками протоколов (только `file`) и контейнеров, ограничением вывода процесса в 1 MiB и не более чем 30 секундами в пределах общего механизма прерывания/дедлайна брокера. Он никогда не принимает команду, фильтр, путь или URL из запроса.

Структурные значения — это детерминированные свидетельства выборки, а не семантическое понимание видео. Они не выводят субъекты, действия, подписи, речь или намерения пользователя. Границы сцен и заморозки образуют сегменты; покрытие заморозки, размытие, экспозиция, пространственная детализация и временные изменения влияют только на то, как распределяется существующий бюджет в 1–16 кадров. Полностью замороженный сегмент ограничен одним кадром, а незамороженные сегменты конкурируют за оставшийся бюджет. Когда границ больше, чем кадров, сохраняется равномерное покрытие временной шкалы, чтобы быстрые ранние склейки не могли скрыть длинный конечный сегмент. Границы сцен, находящиеся в пределах 1-секундного разрешения анализа от границы заморозки, объединяются.

Отсутствующие фильтры, некорректные/пустые свидетельства, ошибка детектора или ограниченный тайм-аут предварительного анализа приводят к отказу в открытое состояние и применению точной политики серединных точек `uniform`. Прерывание вызывающей стороной или дедлайн брокера не приводят к отказу в открытое состояние: они завершают выполняющийся подпроцесс, предотвращают последующее извлечение кадров, а приватное временное дерево удаляется в `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` генерирует детерминированные реальные фикстуры FFmpeg для экономии вызовов модели подписей после дедупликации, распределения бюджета при плотном движении, свидетельств размытия/экспозиции/SI-TI, быстрых склеек с длинным хвостом и ложноположительных срабатываний при постепенном затухании. Он записывает реальное время предварительного анализа и, где доступен `/usr/bin/time`, процессорное время дочернего процесса и пиковый RSS. Его проверки качества — только структурные оракулы. Реальное качество модели подписей остаётся `HOLD`, потому что у этого стенда нет авторизованной конечной точки или замороженного судьи. Денежная экономия также остаётся `HOLD`, если только `--caption-cost-per-call-usd` не задаёт явную положительную оценку стоимости за вызов; скрипт никогда не выдумывает ни один из результатов.

Размер каждого кадра ограничен 4 MiB, всех необработанных кадров вместе — 23 MiB, а сериализованного ответа брокера — 32 MiB. Приватный временный каталог удаляется в блоке `finally`. OmniRoute не включает FFmpeg в комплект и не принимает пользовательский путь к исполняемому файлу. Перед формированием подписей мост выполняет консервативный проход визуальной дедупликации: каждый JPEG уменьшается до буфера в градациях серого размером 16×16 и сравнивается только с последним сохранённым кадром. Если запрошенный бюджет подписей превышает один кадр, извлечение предоставляет ограниченный пул кандидатов размером до удвоенного бюджета и не более 16 кадров. Запрошенное ограничение применяется только после дедупликации, при этом первый и последний выбранные кандидаты сохраняются при финальном прореживании, если бюджет составляет не менее двух. Версионированная политика `grayscale-16x16-mean-cells-v2` использует большее из двух значений: дельты средней яркости и доли ячеек миниатюры, нормализованная дельта которых не меньше 0.05. Порог дубликатов — константа 0.04, выбранная ради предсказуемости, а не вынесенная в настройку времени выполнения. Этот вторичный сигнал высокого контраста сохраняет небольшие движения и изменения видимого текста, которые может скрыть сравнение только по среднему значению. Ошибки компаратора или декодера обрабатываются по принципу fail-open и сохраняют охват. В выходных метаданных раздельно указываются извлечённые кандидаты, успешно использованные кадры и отброшенные визуальные дубликаты.

Явно помеченная часть видео может запросить контактный лист с временными метками. Мост строит JPEG-сетку не более чем из 4 столбцов и 16 кадров. Каждая ячейка размером 512 пикселей впечатывает временную метку источника в высококонтрастную нижнюю полосу, при этом те же временные метки остаются в текстовых метаданных для последующего сопоставления и аудита. Размер итогового JPEG по-прежнему ограничен 32 MiB. Если `sharp` не может декодировать или собрать сетку, мост переходит к отдельным JPEG-кадрам; прерывание клиентом по-прежнему распространяется через операцию создания контактного листа.

Доказательства для продвижения намеренно отделены от синтетического микробенчмарка композиции. `scripts/perf/video-bridge-contact-sheet-eval.ts` определяет A/B-стенд с версионированной схемой для реальных моделей зрения, совместимых с OpenAI. Он измеряет токены, сообщаемые провайдером, сквозную задержку выполнения (включая компоновку листа), количество вызовов модели и сохранение фактов, определённых манифестом. Необработанные ответы модели не записываются в отчёт; сохраняются только дайджесты SHA-256 и идентификаторы совпавших фактов. Стенд не выполняет ни сетевых вызовов, ни вызовов платных моделей, если не передан `--execute-real` и не настроены `--model`, `OMNIROUTE_BASE_URL` и `OMNIROUTE_API_KEY`. Без этого явного реального запуска его машиночитаемый вердикт остаётся `HOLD`; одни лишь синтетические измерения полезной нагрузки и количества вызовов не являются доказательствами для продвижения.

Вызывающие стороны могут прикрепить необязательный массив `transcript.cues` к поддерживаемой части видео, если у них уже есть синхронизированный текст. Каждый элемент cue должен содержать `text`, конечный интервал `start`/`end` в пределах проверенной длительности и `source` из белого списка (`client`, `embedded` или `audio-bridge`); `confidence` по умолчанию равен `1` и должен оставаться в диапазоне от `0` до `1`. Точные дубликаты cue схлопываются. OmniRoute никогда не запускает транскрипцию на основе этих метаданных: прошедшие проверку cue копируются в описанный результат с указанием источника, уверенности и интервала и отображаются как недоверенные наблюдения рядом с подписями к кадрам. Недействительный текст, текст вне диапазона или без указания происхождения отклоняется, а не примешивается к потоку подписей. Оба канала транскрипции в теле запроса нормализуют переданное происхождение до `client`, включая самостоятельно заявленные метки `embedded` или `audio-bridge`. Только принадлежащий серверу адаптер может назначить эти доверенные метки через аргумент `trustedSource`, доступный только из кода; поле JSON запроса не может достичь этого аргумента. Текст транскрипции остаётся недоверенным содержимым, производным от медиа, независимо от его происхождения, и никогда не должен определять авторизацию.

Опытный вызывающий код может предоставить дорожку `audioTranscript` для того же видео; она рассматривается как предоставленный клиентом текст, а не как доказательство серверной транскрипции. Шов слияния выполняет визуальные и аудионаблюдения в рамках одного дедлайна и сигнала прерывания, упорядочивает их на общей временной шкале, схлопывает точные дубликаты и сообщает частичный результат, когда успешна только одна сторона. Недействительный `audioTranscript` деградирует до этого частичного результата — визуальное описание сохраняется, а аудиоветвь записывает санитизированный код ошибки — вместо отказа всего видео. Доступность каждой ветви, флаг частичного результата и санитизированные коды ошибок сохраняются в описанном результате, в метаданных защитных ограничений (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), в метаданных кэша результатов и в счётчиках слияния моста. Путь Video Bridge по умолчанию не вызывает распознавание речи и не загружает вторую копию медиа; без этой явной дорожки он остаётся в режиме только видео.

**Хранение расшифровок (#12150 P1).** Это применяется автоматически всякий раз, когда
Video Bridge (который сам активируется явно) визуализирует реплику расшифровки — отдельного
флага хранения нет. Когда запрос визуализирует любую реплику расшифровки (объявленную вызывающей стороной
`transcript` или объединённую `audioTranscript`), защитный механизм помечает её как
`videoBridgeObserved` и создаёт отредактированную теневую копию описания видео —
идентичную визуализацию, в которой произвольный текст каждой реплики заменён на
`[redacted-video-transcript]`; она создаётся путём подстановки в структурированное поле реплики
до сборки строки (а не посредством анализа плоского текста, поэтому никакое содержимое
реплики — вредоносное или обычное, включая текст с `]`, такой как
`[inaudible]`/`[music]`, — сохраниться не может). В сохраняемом теле запроса журнала вызовов
каждая полученная из видео текстовая часть заменяется соответствующей отредактированной теневой копией,
сопоставленной по равенству содержимого; привязка `fullText` повторно считывается из готовой
полезной нагрузки защитного механизма перед вызовом, поэтому сопоставление по-прежнему выполняется после того,
как последующие защитные механизмы цепочки (маскировщики персональных данных и
учётных данных с приоритетами 10/95) изменят текст описания на месте, а также
после того, как внедрение системного промпта, передачи контекста и памяти преобразует массив сообщений. Тело,
отправляемое модели, не изменяется. Наблюдаемый запрос также не записывает
никаких долговременных данных в Memory (извлечение как из запроса, так и из ответа пропускается),
поэтому собственный ответ модели не может повторно записать текст расшифровки в Memory.

**Необработанные поля видео (#12430).** Когда мост включён, а наличие встроенной поддержки видео неизвестно или она отсутствует, определённые поля `transcript`/`audioTranscript` также активируют `videoBridgeObserved`, даже после сбоя описания или достижения ограничения `maxVideos`. Значения `null` и пустые строки учитываются; отсутствующие поля и метаданные, не относящиеся к видео, не учитываются. В сохраняемых копиях эти поля редактируются либо запрос не сохраняется, а кеши/Memory обходятся.

На этих резервных путях допустимые реплики, предоставленные вызывающей стороной, преобразуются в поддерживаемые
части `text`/`input_text`, а не в нестандартные поля провайдера. Обе переданные в запросе дорожки
остаются недоверенными наблюдениями `client` с явным предупреждением о том, что видео
не было описано, а временные метки не были сверены с медиаданными. Существующие
ограничения в 256 реплик/64 КиБ суммарно и на каждую реплику применяются к обеим дорожкам вместе;
временные метки должны укладываться в установленный брокером предел в 600 секунд и в любое заданное
окно фокуса. Недопустимые дорожки отбрасываются, а не пересылаются как произвольный текст; допустимая
соседняя дорожка всё ещё может использоваться, если не превышен их общий лимит. Поля со значением `null` или пустой строкой
не добавляют текст. Этот резервный механизм не добавляет получение медиаданных или транскрибирование.
Поля расширения расшифровки удаляются из резервного контейнера видео и его
объектов `video_url`/`source`. Список разрешённых полей OpenAI остаётся строгим; контейнеры
видео с неизвестной встроенной поддержкой остаются доступными, а известные цели только с текстом сохраняют безопасные маркеры.
Структурированные отредактированные теневые копии защищают добавленный текст расшифровки, при этом
исходный запрос, принадлежащий вызывающей стороне, остаётся неизменным. Цели со встроенной поддержкой
и отключённые мосты сохраняют существующее поведение обхода.

Дополнительные сохраняемые копии используют тот же сигнал наблюдаемого запроса. В необработанном
снимке клиентского запроса до применения защитных механизмов, ожидающем запросе в памяти и журнале
рано отклонённого запроса поля расшифровки в видеочастях заменяются структурно;
строковые промпты, синтезированные этапами конвейера и передачей контекста, редактируются
в точке сохранения тела запроса. Сохраняемый маркер `video_content_removed`
приводит к безопасному отказу продолжения по `previous_response_id`, а не к восстановлению
текста, который был намеренно отброшен. Если наблюдаемый запрос теряет
свою теневую копию редактирования для отдельной части до журналирования или хотя бы одна из нескольких теневых копий видео
не проходит сопоставление после последующих изменений запроса, сохраняемое тело запроса
полностью исключается вместо сохранения частично отредактированной расшифровки.

Для наблюдаемого запроса ответ модели может цитировать любую часть
расшифровки без структурированной границы реплики. Поэтому его сохраняемое в журнале вызовов
`responseBody` заменяется маркером исключения; подробный
артефакт конвейера (который может включать тела запросов и ответов вышестоящего сервиса/клиента, а также фрагменты потока)
не сохраняется. Семантический кеш, кеш идемпотентности и кеш воспроизведения рассуждений обходят
операции чтения и записи для такого запроса. Запрос к провайдеру и видимый клиенту
ответ остаются неизменными. Ранние байты поддержания соединения удаляются из временного
буфера, когда подробный артефакт исключается. Предупреждение Kiro о некорректном EventStream
сообщает только количество байтов полезной нагрузки, но никогда не её содержимое и не необработанную ошибку
JSON-парсера.
Это не означает, что были проверены все несвязанные диагностические сообщения провайдеров/плагинов;
более широкий аудит точек сохранения отслеживается в #11658.

Жизненный цикл внутреннего `/api/modality-bridge/video/drilldown` представляет собой отдельную,
аутентифицируемую по loopback/token кеширующую инфраструктуру. Для каждой операции также требуется
канонический непрозрачный идентификатор субъекта. Прежде чем разрешить доступ рабочему вызывающему компоненту, он должен
получить этот идентификатор из аутентифицированного арендатора и ни при каких условиях не передавать
значение, выбранное клиентом. Ключи кеша связывают этого субъекта с каноническими идентификаторами сеанса и
ссылки на видео, хранят только производные от них ключи SHA-256 и ограничивают как чтение,
так и удаление тем же субъектом. Кеш хранит не более 16 производных JPEG-кадров
на запись, удаляет их через десять минут и поддерживает ограниченное чтение
`start`/`end` либо явное удаление сеанса.

Для каждого субъекта установлено ограничение в 16 записей и 64 МиБ канонических данных JPEG. Эти
ограничения не зависят от глобального предела в 64 записи/256 МиБ: при исчерпании квоты
субъекта сначала вытесняются только наименее недавно использовавшиеся записи этого субъекта, и лишь затем
рассматривается глобальное вытеснение по LRU. Истёкшие записи удаляются как из учёта субъекта,
так и из глобального учёта при активности кеша, тогда как отмена и ошибка валидации не
фиксируют частичную замену.

Кэш отклоняет неканонический Base64, избыточное дополнение, не-JPEG медиа, повреждённые или
усечённые JPEG, а также JPEG, которые вызывают предупреждение во время ограниченного полнокадрового декодирования `sharp`.
Он перекодирует каждое принятое изображение в канонический JPEG, вычисляет ширину и высоту
из декодированных байтов вместо доверия полям вызывающей стороны и отбрасывает любые завершающие
полиглотные байты, а не сохраняет их. Только ограниченный канонический сжатый буфер
учитывается в обеих квотах. Лимит JSON-передачи включает накладные расходы Base64 для потолка
декодированного ввода в 32 МиБ. Каждое
сохранённое производное изображение записывает свой проверенный формат/разрешение JPEG, политику сэмплирования,
версию производной, время создания, вычисленный сервером хеш содержимого и хешированную родительскую
ссылку, а также хеш родительского содержимого от доверенной вызывающей стороны. Отмена проверяется
между асинхронными фазами декодирования/хеширования перед атомарной фиксацией в кэше.

Этот этап пока не подключает продакшн-продюсера к маршруту и не
предоставляет выбор вариантов с несколькими разрешениями. Таким образом, путь запроса прозрачного Video Bridge
не влечёт дополнительной работы, в то время как вывод субъекта, привязанного к арендатору, и
полный жизненный цикл FU-08 с несколькими разрешениями остаются явной последующей работой, а не
документированным завершённым поведением.

Кадры подписываются последовательно с использованием настроенной модели Video. Пустое
переопределение Video наследует настройку Vision; если оба пусты, авто-маршрутизатор Vision
выбирает эффективную модель, поддерживающую зрение. Успешные подписи
заменяют исходную часть стабильным префиксом `[Video description:`, который также
помечает текст как недоверенное наблюдение, полученное из медиа, и указывает нижестоящим
моделям не следовать инструкциям, найденным в медиа. Ключи кэша подписей кадров
включают байты JPEG, промпт, временную метку и эффективную модель; кэшируются только успешные
подписи. Записи кэша сохраняют фактическую успешную модель-производителя,
включая резервную модель; мост сообщает `mixed`, когда разные кадры
были созданы разными моделями. Попадание в кэш повторно использует эту идентичность производителя
вместо перемаркировки её как запрошенного плана маршрутизации. Кэш результатов всего видео
ключуется по каждому входу, который изменяет вывод — промпт, эффективная
модель, политика сэмплирования, количество кадров, режим семантического анализа, SHA-256
отпечаток нормализованной подсказки фокуса, окно фокуса, `transcript`,
`audioTranscript` и флаг контактного листа — поэтому изменение любого из этих
измерений является промахом кэша, а не устаревшим повторным использованием. Версия политики визуальной дедупликации,
порог и ограниченное количество кадров-кандидатов также явно указаны в
ключе и метаданных кэша результатов; таким образом, изменение политики не может повторно использовать устаревшее
описание всего видео. Метаданные кэша результатов v4 сохраняют режим и
отпечаток, но никогда не исходную пользовательскую задачу. Метаданные Guardrail сообщают как
запрошенный, так и эффективный режимы анализа; запрошенный режим `focused` без
пригодного для использования пользовательского текста сообщается как эффективно `full`.

Guardrail извлекает каждую поддерживаемую видечасть, но описывает не более
`modalityBridgeVideoMaxVideos`. Для цели, доказанно имеющей
`supportsVideo === false`, неудачные и превышающие лимит видео становятся явными безопасными
текстовыми маркерами, чтобы никакое сырое видео не сохранилось. Когда возможность неизвестна, эти части
сохраняют свой видеоноситель; любой резервный транскрипт следует приведённому выше ограниченному текстовому
преобразованию. Цели с `supportsVideo === true` обходят мост.
Сигнал прерывания клиентского запроса распространяется через загрузку, очередь брокера,
подпроцессы и вызовы подписей; прерывания останавливаются между видео и никогда не приводят к откату
к сырому медиа.

Настройки времени выполнения хранятся в БД и валидируются Zod:

| Ключ                                | По умолчанию | Диапазон / поведение                                                                                            |
| ----------------------------------- | ------------ | --------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`      | Опциональная среда выполнения, включается по желанию                                                            |
| `modalityBridgeVideoAnalysisMode`   | `"full"`     | `full` сохраняет общие подписи; `focused` использует ограниченный недоверенный контекст последнего пользователя |
| `modalityBridgeVideoModel`          | `""`         | Наследовать модель Vision Bridge                                                                                |
| `modalityBridgeVideoFrameCount`     | `8`          | 1–16                                                                                                            |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`  | `uniform`, `scene_aware` или пропорциональный `segment_aware`; при сбое детектора происходит откат к `uniform`  |
| `modalityBridgeVideoMaxVideos`      | `1`          | 1–4                                                                                                             |
| `modalityBridgeVideoTimeout`        | `120000`     | 1000–120000 ms                                                                                                  |

Устаревшие сохранённые значения тайм-аута Video выше 120 секунд ограничиваются
дедлайном брокера; новые записи настроек выше этого лимита отклоняются.
`GET /api/modality-bridge/video/runtime` требует доверенной отмеченной локальности loopback
перед аутентификацией или проверкой среды выполнения, затем требует аутентификацию управления.
Он возвращает только `available`, очищенные версии FFmpeg/ffprobe и фиксированную
причину, когда среда выполнения недоступна. Внутренняя конечная точка извлечения не
является публичным API загрузки: переполнение очереди возвращает `503` плюс `Retry-After`, отключение вызывающей стороны
возвращает `499`, а фиксированный дедлайн брокера возвращает `504`. Преобразованные ответы добавляют
`video->text;model=<visionModel>;parts=<videos>` к центральному
заголовку `x-omniroute-modality-bridge`, не удаляя сегменты Vision или Audio.

### Маскировщик PII (`piiMasker.ts`)

Работает на **обоих** этапах.

- **`preCall`** клонирует полезную нагрузку, проходит по `system`, `messages`, `input` и
  `prompt` (включая элементы в виде простых строк) и применяет `processPII()` (из
  `@/shared/utils/inputSanitizer`) к строковым полям `content`/`text`. Когда
  `PII_REDACTION_ENABLED=true`, обнаруженные PII маскируются в исходящей
  полезной нагрузке. Это не зависит от `INPUT_SANITIZER_MODE` (который управляет
  только политикой защиты от внедрения промптов). Когда маскирование отключено, вызов записывает счётчики
  обнаружений без перезаписи содержимого.
- **`postCall`** выполняет глубокое клонирование ответа, запускает `sanitizePIIResponse()` и
  маскировщик структуры Responses API (`maskResponsesOutput` — охватывает
  `output_text` и `output[].content[].text`). Если происходит какое-либо маскирование,
  изменённый ответ заменяет оригинал.

Защитный механизм никогда не блокирует; он только аннотирует (`meta.detections`,
`meta.redacted`) или перезаписывает.

#### Выбор по типам, пользовательские шаблоны и счётчики обнаружений

**Панель управления → Настройки → Безопасность → Маскирование PII** выбирает, _что_ маскируется. Это
не включает маскирование: за это по-прежнему отвечают `PII_REDACTION_ENABLED` (запрос) и
`PII_RESPONSE_SANITIZATION` (ответ + SSE), оба по умолчанию отключены.

- **Выбор по типам** — встроенные идентификаторы перечислены в
  `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`). Если значение не задано, используются все
  типы (поведение до появления этой настройки). Шаблон `ssn_us` движка запросов
  сопоставляется с `ssn`. Шаблоны (Minimal, Standard, Financial,
  Brazilian, USA, Full) только заполняют флажки в интерфейсе.
- **Пользовательские шаблоны** — до 20 шаблонов regex или с подстановочными знаками (`*` = до 64
  символов, не являющихся пробельными, `?` = один символ). Совпадения становятся `[CUSTOM_REDACTED]`.
  Каждый шаблон проходит через `compilePiiCustomPattern()`
  (`src/shared/utils/piiCustomPatterns.ts`): не более 500 символов, флаги ограничены
  `g i m s u`, должен компилироваться, должен проходить `safe-regex` (катастрофический
  бэктрекинг), и не должен совпадать с пустой строкой или заполнителем маскирования.
  Шаблон, который не проходит проверку, отклоняется при сохранении и при тестировании, а сохранённая строка,
  которая не проходит проверку, пропускается во время выполнения вместо компиляции. Пользовательские шаблоны
  работают только при включённом маскировании.
- **Счётчики обнаружений** — счётчики по типам (без самих совпавших значений), хранятся в
  памяти и сбрасываются при перезапуске (`src/lib/pii/piiDetectionStats.ts`). Они только
  увеличиваются при включённом маскировании.

Настройки хранятся в таблице `key_value` (пространство имён `pii_settings`,
`src/lib/db/piiSettings.ts`) и читаются через кэш на 1 с. API:

| Метод  | Путь                     | Назначение                                                                             |
| ------ | ------------------------ | -------------------------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | Состояние флага, `enabledTypes`, `customPatterns`, счётчики обнаружений                |
| `PUT`  | `/api/settings/pii`      | Заменить `enabledTypes` (`null` = все) и/или `customPatterns`                          |
| `POST` | `/api/settings/pii/test` | Пробный запуск одного шаблона на образце размером не более 8 КБ; ничего не сохраняется |

Все три требуют аутентификацию с правами управления и валидируют тело с помощью Zod
(`src/shared/validation/schemas/piiSettings.ts`).

### Внедрение промптов (`promptInjection.ts`)

Обнаруживает состязательные структуры в предоставленном пользователем контенте и применяет
настроенную политику. Поведение определяется переменными окружения и параметрами
конструктора:

| Параметр         | Переменная окружения                                                                                 | По умолчанию | Эффект                                                                                                                                                                                                       |
| ---------------- | ---------------------------------------------------------------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Включено         | `INPUT_SANITIZER_ENABLED`                                                                            | `true`       | Если `false`, защитный механизм досрочно завершается.                                                                                                                                                        |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                      | `warn`       | Политика обработки внедрений: `block`, `warn` или `log`. (`redact` принимается для обратной совместимости, но **не** удаляет текст внедрения; перезапись PII в запросе управляется `PII_REDACTION_ENABLED`.) |
| Порог блокировки | опция `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (алиас `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`       | Минимальная серьёзность, необходимая для блокировки. Medium по умолчанию используется только для наблюдения.                                                                                                 |

**Приоритет режимов** (`getMode`): `options.mode` вызывающего кода →
`INJECTION_GUARD_MODE` — **переопределение флага функции в БД** (Панель управления → Настройки →
Флаги функций) → переменная окружения `INJECTION_GUARD_MODE` → переменная окружения `INPUT_SANITIZER_MODE` →
`warn`. Таким образом, переопределение из панели управления имеет приоритет над переменными окружения, поэтому
интерфейс флагов функций управляет работающим защитным механизмом в реальном времени (без перезапуска). Чтение из БД является отказоустойчивым:
при ошибке защитный механизм возвращается к поведению на основе переменных окружения, а когда
переопределение не задано, поведение идентично разрешению только через переменные окружения.

Источники обнаружения:

1. `sanitizeRequest()` из `@/shared/utils/inputSanitizer` (общий набор детекторов,
   используемый в других частях конвейера).
2. Встроенные `DEFAULT_GUARD_PATTERNS` (сейчас `system_override_inline` и
   `markdown_system_block`, оба имеют серьёзность `high`).
3. Необязательные `customPatterns`, переданные через параметры конструктора (строки, regex
   или записи `{ name, pattern, severity }`).

Когда `mode === "block"` **и** хотя бы одно обнаружение достигает порога серьёзности, `preCall` возвращает `{ block: true, message: "Request rejected:
suspicious content detected" }`. В режимах `warn`/`log` защитное ограничение пишет в лог, но разрешает вызов. Общая вспомогательная функция `evaluatePromptInjection()` также экспортируется для вызывающего кода, которому нужно оценивать промпты без обращения к реестру.

**Граница сканирования (v3.8.20):** детектор проверяет только **первые 16 КБ** объединённого текста промпта — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байта) в `src/shared/utils/inputSanitizer.ts`. И `detectInjection()`, и `evaluatePromptInjection()` выполняют `slice(0, MAX_INJECTION_SCAN_BYTES)` перед запуском цикла по шаблонам. Директивы инъекций располагаются ближе к началу входных данных, поэтому это ограничивает нагрузку на CPU/GC от регулярных выражений при полезных нагрузках размером в сотни килобайт, не ослабляя обнаружение (ср. #3932, #4041).

### Маскировщик учётных данных (`credentialMasker.ts`)

Запускается на **обоих** этапах, последним в цепочке по умолчанию (приоритет `95`). Маскирует известные шаблоны API-ключей / секретных токенов в исходящей полезной нагрузке (содержимое сообщений, аргументы вызовов инструментов, результаты инструментов) **и** в ответе провайдера, чтобы учётные данные, вставленные в промпт (или возвращённые обратно в результате инструмента), не утекали к вышестоящему провайдеру или обратно клиенту.

- **Только по явному включению (opt-in)**, та же конвенция, что и для редактирования PII (рядом с Жёстким правилом #20):
  отключено, если только `settings.credentialRedactionEnabled === true` **или**
  `CREDENTIAL_REDACTION_ENABLED=true`. Если оно выключено, защитное ограничение работает как no-op —
  оно никогда не блокирует и не перезаписывает.
- `redactCredentials()` обходит всё дерево полезной нагрузки/ответа (`walkValue()`,
  безопасно в отношении загрязнения прототипа и циклов благодаря `WeakSet`) и заменяет совпадения на
  плейсхолдер `[REDACTED:<type>]`, клонируя только ветви, которые действительно
  изменились.
- `CREDENTIAL_PATTERNS` охватывает ключи провайдеров LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), токены VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), платёжные ключи (Stripe, Square), облачные
  ключи (ключ доступа AWS, Twilio, SendGrid, Mailgun), приватные ключи / JWT,
  строки подключения с учётными данными (`mongodb://user:pass@...` и т. д.) и
  общий шаблон значений заголовков `Authorization`/`x-api-key`/`api-key`/`apikey`.
  Ключи в форме заголовков (`authorization`, `x-api-key`, `api-key`,
  `apikey`) маскируются структурно (только значение; префикс схемы вроде
  `Bearer `/`Basic ` сохраняется), а не через общее регулярное выражение для текста.
- Защитное ограничение никогда не блокирует; оно только перезаписывает (`modifiedPayload` /
  `modifiedResponse`) и аннотирует (`meta.credentialsRedacted`, `meta.count`).

Защита от регрессий: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовый контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true прерывает цепочку
  message?: string; // отображается при блокировке
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // возвращается preCall для изменения запроса
  modifiedResponse?: TValue; // возвращается postCall для изменения ответа
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Защитный механизм сообщает об отсутствии изменений, возвращая `void`, `{}` или
`{ block: false }`. Возврат `modifiedPayload`/`modifiedResponse` заменяет
значение, передаваемое по цепочке последующим защитным механизмам.
`signal?: AbortSignal` передаёт жизненный цикл вызывающей стороны защитным механизмам. Прерывание запроса — это преднамеренное исключение с разрешением продолжить работу: медиамосты прекращают работу и выполняют очистку, не восстанавливая необработанные медиаданные для целевой стороны, которая, как известно, их не поддерживает.

## Реестр (`registry.ts`)

Одиночка `guardrailRegistry` предоставляет:

- `register(guardrail)` — добавляет защитный механизм (или заменяет его по нормализованному имени) и
  повторно сортирует механизмы по возрастанию `priority`.
- `clear()` / `list()` — административные вспомогательные функции.
- `runPreCallHooks(payload, context)` — перебирает активные защитные механизмы, последовательно передаёт
  полезную нагрузку через `modifiedPayload` и останавливается при первом `block: true`.
- `runPostCallHooks(response, context)` — выполняет тот же процесс для ответа.
- `resetGuardrailsForTests({ registerDefaults })` — очищает состояние и при необходимости
  повторно регистрирует защитные механизмы по умолчанию для полной изоляции тестов.

Оба обработчика возвращают `{ blocked, payload|response, results, guardrail?, message? }`,
где `results` — массив записей `GuardrailExecutionResult`, содержащих
для каждого защитного механизма поля `blocked`, `skipped`, `modified`, `error` и `meta`,
полезные для трассировки.

### Отключение защитных механизмов для отдельных запросов

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` формирует
список без дубликатов с именами защитных механизмов, которые следует пропустить для текущего
запроса. Данные поступают по пяти каналам, считываются в следующем порядке и объединяются в один список
(при устранении дубликатов сохраняется первое вхождение):

1. `apiKeyInfo.disabledGuardrails`
2. `disabledGuardrails` в теле запроса (на верхнем уровне)
3. `metadata.disabledGuardrails` в теле запроса (только если `metadata` является объектом)
4. Заголовок `x-omniroute-disabled-guardrails`
5. Устаревший заголовок `x-disabled-guardrails`

Все пять каналов объединяются, включая оба заголовка: отправка одновременно
`x-omniroute-disabled-guardrails` и `x-disabled-guardrails` приводит к пропуску объединения
их списков, а пустой современный заголовок больше не скрывает устаревший
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), исправлено в
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805)).

Значения могут быть массивами строк или строкой с элементами, разделёнными запятыми; имена очищаются от окружающих пробелов
и нормализуются в нижний регистр с дефисами (`pii_masker` → `pii-masker`), а пустые
элементы удаляются. Результат передаётся реестру через `context.disabledGuardrails`,
и реестр пропускает соответствующие защитные механизмы (`skipped: true` в `results`).

Список отключения влияет только на **реестр**. Режим `block` для защиты от внедрения в промпт
является обязательной границей безопасности: middleware защиты от внедрения
(`src/middleware/promptInjectionGuard.ts`) вызывает `evaluatePromptInjection()`
без какого-либо управляемого вызывающей стороной списка отключения (неиспользуемый вызов
`resolveDisabledGuardrails({ body })`, который выполнялся ранее, был удалён в
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934)), поэтому запрос,
отключающий `prompt-injection`, всё равно отклоняется в режиме `block`. Это сделано
намеренно. Каналы отключения контролируются вызывающей стороной (тело запроса,
метаданные, заголовки), и вызывающая сторона не должна иметь возможности отключить средство
безопасности, настроенное оператором
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). Объединение заголовков
из [#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412)
изменяет только то, какие защитные механизмы реестра пропускаются; оно не позволяет клиенту
обойти middleware. Обязательные политики защитных механизмов для отдельных ключей и групп
отслеживаются в RFC v4 [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417).
См. [Охват и ограничения](#coverage-and-limits).

## Порядок выполнения

Для каждого запроса, проходящего через `src/sse/handlers/chat.ts` и
`open-sse/handlers/chatCore.ts` (маршруты семейства чатов, перечисленные в разделе
[Охват и ограничения](#coverage-and-limits)):

1. `resolveDisabledGuardrails(...)` формирует список пропускаемых защитных механизмов на основе API-ключа, тела запроса
   и заголовков.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` запускает защитные механизмы в порядке возрастания
   приоритета:
   - Отключённые защитные механизмы отмечаются как `skipped`.
   - `preCall` каждого защитного механизма может перезаписать полезную нагрузку через `modifiedPayload`.
   - Первый результат `block: true` прерывает цепочку, и обработчик возвращает
     ответ об отклонении запроса защитным механизмом.
3. Полезная нагрузка (возможно, перезаписанная) передаётся в комбинированную маршрутизацию и отправку
   вышестоящему сервису.
4. **Только без потоковой передачи:** после формирования ответа
   `guardrailRegistry.runPostCallHooks(...)` запускает ту же цепочку для
   ответа. В этом случае `block: true` отбрасывает ответ вышестоящего сервиса и возвращает HTTP 400. Для потоковых ответов этот шаг полностью пропускается.

Защитные механизмы, выбрасывающие исключения, регистрируются с `error: <message>` и записываются в журнал через
`logger.warn`, но цепочка продолжает выполнение — это преднамеренное поведение по принципу fail-open.

## Охват и ограничения

Реестр защитных механизмов подключён только к конвейеру чатов. Эти ограничения
зафиксированы тестами `tests/unit/guardrail-pipeline-wiring-characterization.test.ts` и
`tests/unit/guardrail-pipeline-characterization.test.ts`; при изменении поведения
обновляйте эти тесты осознанно.

### Где выполняются хуки

| Хук / механизм управления                        | Где выполняется                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `runPreCallHooks`                                | Запросы, обрабатываемые `handleChat` (`src/sse/handlers/chat.ts`): `/v1/chat/completions`, `/v1/completions`, `/v1/messages`, `/v1/responses` (и `/v1/responses/*`), `/v1/relay/chat/completions`, `/v1/providers/{provider}/chat/completions`, `/v1/api/chat`, `/v1/antigravity`, `/v1beta/models/*`, а также прокси чата Telegram. Кроме того, тестовая конечная точка панели управления `/api/guardrails/test`. Блокировка перед вызовом возвращает HTTP 400. |
| `runPostCallHooks`                               | Только ответы чата **без потоковой передачи** (`open-sse/handlers/chatCore/nonStreamingResponse.ts`). Потоковые ответы никогда до него не доходят.                                                                                                                                                                                                                                                                                                               |
| Потоковая обработка PII                          | `createPiiSseTransform` (`src/lib/streamingPiiTransform.ts`), подключаемый через канал в `streamingPipeline.ts`, когда включён `PII_RESPONSE_SANITIZATION`. Это не защитный механизм, поэтому каналы отключения на него не влияют.                                                                                                                                                                                                                               |
| Промежуточное ПО защиты от инъекций (устаревшее) | Каждый маршрут `/v1`, содержащий запрос, включая семейство чатов (см. [охват маршрутов](#injection-guard-route-coverage--red-team-phase-8--block-d)). Только инъекция в запрос.                                                                                                                                                                                                                                                                                  |

### Что не охвачено

- **Маршруты мультимедиа, эмбеддингов и данных** (`/v1/images/*`, `/v1/embeddings`,
  `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`,
  `/v1/rerank`, `/v1/search`, `/v1/moderations`) никогда не достигают реестра. Там не выполняются
  маскирование PII, маскирование учётных данных или преобразование модальностей. Их единственная
  проверка — устаревшее промежуточное ПО защиты от инъекций.
- **Потоковые ответы** не проходят защитные механизмы после вызова: отсутствуют
  обработка после вызова с помощью `pii-masker` или `credential-masker` и блокировка после вызова. Применяется только потоковое преобразование PII
  (когда включён `PII_RESPONSE_SANITIZATION`). Учётные данные,
  возвращённые в потоковом ответе, не редактируются.
- **Каналы отключения и промежуточное ПО (по замыслу):** промежуточное ПО оценивает
  инъекцию в запрос с помощью собственного вызова `evaluatePromptInjection()`, не
  передавая какой-либо управляемый вызывающей стороной список отключений. Режим `block` является обязательной
  границей, которую нельзя обойти с помощью управляемых вызывающей стороной отключений, в том числе на маршрутах семейства чатов
  ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). Отключение
  `prompt-injection` приводит только к пропуску соответствующего защитного механизма в реестре.

### Что обрабатывает ответ до этапа после вызова

На пути без потоковой передачи порядок следующий: извлечение памяти → выполнение встроенных инструментов → защитные механизмы после вызова → выход при блокировке после вызова → сохранение в семантическом кеше.

- **Извлечение памяти** и **выполнение инструментов** видят ответ до того, как пост-вызовные guardrails смогут его переписать или заблокировать. Начиная с
  [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401), извлечение памяти пропускает извлечённый текст через `sanitizePII`, когда
  включён `PII_RESPONSE_SANITIZATION` (как в потоковом, так и в непотоковом режиме), но ответ,
  который пост-вызовные guardrails позже блокируют, всё равно уже был передан памяти и
  инструментам.
- **Семантический кэш** сохраняет ответ после пост-вызовной обработки, поэтому он сохраняет
  переписанный ответ, а заблокированный ответ никогда не кэшируется. Записи кэша
  привязаны к ключу API.

## Конфигурация

Переменные окружения, которые читают встроенные guardrails:

| Переменная                            | Используется в                       | Эффект                                                                                                             |
| ------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`                   | Установите `false`, чтобы полностью отключить обнаружение.                                                         |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`                   | Политика инъекций: `warn`, `block` или `log`. Устаревшее значение `redact` не перезаписывает текст инъекции.       |
| `INJECTION_GUARD_MODE`                | `prompt-injection`                   | Режим guardrail для инъекций; также флаг функции в БД, который **переопределяет** переменные окружения (БД > ENV). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`                   | Минимальная критичность, при которой `MODE=block` отклоняет: `high` (по умолчанию), `medium` или `low`.            |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`                   | Устаревший псевдоним для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                        |
| `PII_REDACTION_ENABLED`               | `pii-masker`                         | Если `true`, PII в запросе маскируются (независимо от режима инъекций).                                            |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (нижележащий компонент) | Управляет поведением маскировщика на стороне ответа.                                                               |

Guardrails Modality Bridge читают конфигурацию времени выполнения из хранилища настроек на основе БД (`getSettings()`), а не из переменных окружения. Основные ключи Vision:
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` и
`modalityBridgeCacheMaxEntries`. Устаревшие ключи
`visionBridge*` принимаются только как документированный резервный вариант чтения на один цикл; записи из панели управления используют основные ключи. Значения по умолчанию и резолвер резервных значений находятся в `src/shared/constants/modalityBridgeDefaults.ts`, а устаревшие константы сохранены в `src/shared/constants/visionBridgeDefaults.ts`.

Аудио использует `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` и `modalityBridgeAudioMaxClips`, а также общие
настройки `modalityBridgeCache*`. Для аудио нет fallback на устаревшие ключи, поскольку эти
ключи были введены вместе со схемой Modality Bridge.

Видео использует `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` и
`modalityBridgeVideoTimeout`, а также общие настройки `modalityBridgeCache*`.
По умолчанию оно отключено, поскольку FFmpeg/ffprobe являются необязательными операционными
зависимостями, а формирование подписей к кадрам увеличивает задержку и стоимость модели.

## Пользовательские Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Шаги:

1. Создайте `src/lib/guardrails/myGuardrail.ts`, расширяющий `BaseGuardrail`.
2. Реализуйте `preCall` и/или `postCall`.
3. Зарегистрируйте либо во время импорта (через вызов из `registerDefaultGuardrails`), либо
   вызовите `guardrailRegistry.register(...)` во время выполнения — реестр заменяет
   любой предыдущий guardrail с тем же нормализованным именем.
4. Добавьте тесты в `tests/unit/` (существующие примеры:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## Тестирование

Используйте `resetGuardrailsForTests()` между тестами, чтобы начать с известного состояния.
Передайте `{ registerDefaults: false }`, чтобы начать с пустого реестра и
зарегистрировать только те guardrails, которые тестируются. Vision Bridge поддерживает внедрение
зависимостей (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge предоставляет
эквивалентные точки расширения для настроек, возможностей, выбора модели STT, проверок
учётных данных и транскрипции. Поэтому тесты могут задействовать оба потока без доступа к БД
или сети.

## Покрытие маршрутов injection-guard и red-team (Фаза 8 · Блок D)

Injection-guard (`createInjectionGuard` / `withInjectionGuard`) покрывает все маршруты,
принимающие пользовательские промпты. Он учитывает `INJECTION_GUARD_MODE` (по умолчанию `warn` = только логирование;
`block` = возвращает HTTP 400 `SECURITY_001`).

| Тип                  | Маршруты                                                                                                                                             | Режим по умолчанию |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| Текст (существующие) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn               |
| Генеративные         | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn               |
| Данные               | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn               |

Извлечение текста (`extractMessageContents`) покрывает `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Red-team (ночной запуск, `nightly-llm-security.yml`):** promptfoo проверяет, что каждый маршрут блокирует
корпус OWASP-LLM в режиме `INJECTION_GUARD_MODE=block`; garak запускает пробы (пропускается без секрета).
`moderations` включён для единообразия. Блочный режим — обязательная граница: `evaluatePromptInjection()`
игнорирует переданный ему промежуточным ПО список отключённых для каждого запроса guardrails, поэтому `disabledGuardrails`
**не** освобождает маршрут от него ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

Ночной workflow (`.github/workflows/nightly-llm-security.yml`, cron + ручной
запуск) содержит две задачи:

- **`promptfoo-guard` (блокирующая)** — запускает `promptfoo eval -c promptfooconfig.yaml`
  с `INJECTION_GUARD_MODE=block`. Для каждого состязательного случая (например, «ignore all
  previous instructions…», джейлбрейки в стиле DAN) проверяется, что ответ содержит
  `error.code === "SECURITY_001"`, то есть guard действительно отклонил запрос.
- **`garak` (рекомендательная)** — запускает garak `--probes promptinject,dan,leakreplay`
  против локального экземпляра OmniRoute (`http://localhost:20128/v1`). Условие запуска — секрет
  провайдера (`PROMPTFOO_PROVIDER_KEY`); при отсутствии корректно пропускается и завершается суффиксом
  `|| true`, поэтому сообщает о результатах, не прерывая CI.

Покрытие вспомогательного guard-а (`createInjectionGuard` / `withInjectionGuard`)
охватывает каждый маршрут `/v1`, несущий промпт; текст промпта извлекается из
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` с помощью
`extractMessageContents()` в `src/shared/utils/inputSanitizer.ts`.
