## ჩატის დასრულებები

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### მორგებული სათაურები

| სათაური                  | მიმართულება | აღწერა                                                                                                                                                                                                                      |
| ------------------------ | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | მოთხოვნა    | კეშის გვერდის ავლისთვის დააყენეთ `true`                                                                                                                                                                                     |
| `x-omniroute-no-memory`  | მოთხოვნა    | ამ მოთხოვნისთვის მეხსიერებისა და უნარების ჩასმის გამოსატოვებლად დააყენეთ `true` (იმეორებს კეშის გამორთვის ქცევას; თავიდან აგაცილებთ თითოეული გამოძახების ტოკენებისა და ღირებულების დამატებით დანახარჯს)                     |
| `X-OmniRoute-Progress`   | მოთხოვნა    | პროგრესის მოვლენების მისაღებად დააყენეთ `true`                                                                                                                                                                              |
| `X-Session-Id`           | მოთხოვნა    | მდგრადი სესიის გასაღები გარე სესიის მიჯაჭვულობისთვის                                                                                                                                                                        |
| `x_session_id`           | მოთხოვნა    | ასევე მიიღება ქვედატირიანი ვარიანტი (პირდაპირი HTTP)                                                                                                                                                                        |
| `X-OmniRoute-Session-Id` | მოთხოვნა    | გამომძახებლის მიერ მოწოდებული სესიის/საუბრის ტეგი (ასევე მიეწოდება მეხსიერებას). არსებობისას უცვლელად ინახება `call_logs.session_tag`-ში თითოეული სესიის ხარჯის მისაკუთვნებლად (#8249) — არარსებობისას არასოდეს გენერირდება |
| `Idempotency-Key`        | მოთხოვნა    | დუბლიკატების აღმოფხვრის გასაღები (5-წამიანი ფანჯარა)                                                                                                                                                                        |
| `X-Request-Id`           | მოთხოვნა    | დუბლიკატების აღმოფხვრის ალტერნატიული გასაღები                                                                                                                                                                               |
| `x-omniroute-connection` | მოთხოვნა    | ერთი მოდელის მოთხოვნის მიბმა პროვაიდერის ერთ კავშირზე (ანგარიშზე) მისი იდენტიფიკატორის მიხედვით — იხილეთ [ანგარიშზე მიბმა თითოეული მოთხოვნისთვის](#account-pinning-per-request)                                             |
| `X-OmniRoute-Cache`      | პასუხი      | `HIT` ან `MISS` (არასტრიმინგული)                                                                                                                                                                                            |
| `X-OmniRoute-Idempotent` | პასუხი      | `true`, თუ დუბლიკატი აღმოიფხვრა                                                                                                                                                                                             |
| `X-OmniRoute-Progress`   | პასუხი      | `enabled`, თუ პროგრესის თვალყურის დევნება ჩართულია                                                                                                                                                                          |
| `X-OmniRoute-Session-Id` | პასუხი      | OmniRoute-ის მიერ გამოყენებული ეფექტური სესიის ID                                                                                                                                                                           |
| `X-OmniRoute-Request-Id` | პასუხი      | მოთხოვნის კორელაციის იდენტიფიკატორი (როდესაც ცნობილია)                                                                                                                                                                      |
| `X-OmniRoute-Version`    | პასუხი      | OmniRoute-ის ბილდის ვერსია (ყოველთვის წარმოდგენილია)                                                                                                                                                                        |
| `X-OmniRoute-Cost-Saved` | პასუხი      | USD-ში თანხა, რომლის ხარჯვასაც კეშმა აგარიდათ `HIT`-ისას (მხოლოდ კეშში დამთხვევის შემთხვევაში)                                                                                                                              |
| `X-OmniRoute-Decision`   | პასუხი      | მარშრუტიზაციის ტრასა: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` არის კომბინაციის სტრატეგია, ხოლო არაკომბინირებული მოთხოვნისთვის — `single`) — დასრულების პასუხებში ყოველთვის წარმოდგენილია              |

> Nginx-ის შენიშვნა: თუ ქვედატირიან სათაურებს იყენებთ (მაგალითად, `x_session_id`), ჩართეთ `underscores_in_headers on;`.

#### ანგარიშის მიბმა თითოეული მოთხოვნისთვის

როდესაც პროვაიდერს რამდენიმე კავშირი (ანგარიში ან გასაღები) აქვს, OmniRoute ჩვეულებრივ ერთ-ერთ მათგანს
ანგარიშის არჩევის სტრატეგიის მეშვეობით ირჩევს. ამის ნაცვლად, მოთხოვნას შეუძლია კონკრეტული კავშირის მიბმა
`x-omniroute-connection` სათაურის მეშვეობით:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **სად ვიპოვოთ id.** გახსენით პროვაიდერის გვერდი მართვის პანელში
  (**მართვის პანელი → პროვაიდერები → <provider>**) და კავშირის სტრიქონში დააწკაპუნეთ `xxxxxxxx…` id-ის ნიშნულზე
  — შედეგად, კავშირის სრული id დაკოპირდება.
- **რომელი მოთხოვნები ითვალისწინებს მას.** ერთმოდელიანი მოთხოვნები (`provider/model`)
  `/v1/chat/completions`, `/v1/messages` და `/v1/responses` მისამართებზე. კომბინაციები სათაურს უგულებელყოფს:
  ამის ნაცვლად, თითოეული კომბინაციის ეტაპზე ანგარიში ამ ეტაპის საკუთარი კავშირის მეშვეობით მიაბით.
- **მიბმა მკაცრია და არა უბრალოდ უპირატესობა.** გამოიყენება მხოლოდ მიბმული კავშირი.
  მოთხოვნის ფარგლებში წარმოქმნილი შეცდომა ანგარიშის დაყოვნების პერიოდს აფიქსირებს, მაგრამ იმავე
  პროვაიდერის სხვა ანგარიშზე **არ** გადაერთვება.
- **დაყოვნების პერიოდი და კვოტა მიბმას აუქმებს.** სანამ მიბმული კავშირი დაყოვნების პერიოდშია,
  კვოტა ამოწურული აქვს ან კვოტის პოლიტიკითაა დაბლოკილი, შემდგომი მოთხოვნები პროვაიდერის
  სხვა კავშირებზე გადაერთვება, ზუსტად ისე, როგორც მიუბმელი ტრაფიკი.
- **უცნობი ან გამორთული id-ები შეცდომას იწვევს.** id, რომელიც პროვაიდერის აქტიურ პულში არ შედის (წაშლილია,
  დეაქტივირებულია ან სხვა პროვაიდერს ეკუთვნის), არცერთ გამოსადეგ ანგარიშს არ ტოვებს, ამიტომ მოთხოვნა
  შეცდომით სრულდება და სხვა მარშრუტზე შეუმჩნევლად არ გადადის.

Claude Code მორგებულ სათაურებს `ANTHROPIC_CUSTOM_HEADERS`-ის მეშვეობით აგზავნის. ჩასვით ის `env` ბლოკში
`~/.claude/settings.json` ფაილში, ან პროექტის დონის `.claude/settings.json` ფაილში, რათა თითოეულ პროექტს
განსხვავებული ანგარიში მიაბათ:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

წყარო: `src/sse/handlers/chat.ts` (სათაურის წაკითხვა), `src/sse/services/auth.ts` და
`src/sse/services/sessionAffinityPin.ts` (მიბმის გაუქმება და პულში არარსებობის შემოწმება).

> **ღირებულების ტელემეტრიის სათაურები:** წარმატებული არანაკადური პასუხები ასევე შეიცავს ღირებულების ტელემეტრიის `X-OmniRoute-*` ნაკრებს — `X-OmniRoute-Response-Cost` (USD, ფიქსირებული 10 ათწილადი ნიშნით; `0.0000000000` უფასო/დაუფასებელი შემთხვევებისთვის), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` და `X-OmniRoute-Fallback-Attempts` (მხოლოდ მაშინ, როდესაც > 0), ასევე `X-OmniRoute-Request-Id` და `X-OmniRoute-Version`. მათ გასცემს ჩატის დასრულებები, `/v1/responses`, `/v1/messages` **და მედიის საბოლოო წერტილებიც** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` და `/v1/moderations` (ღირებულება ყოველთვის `0`). მედიის ღირებულება გამოითვლება მოდალობის მიხედვით (თითო სურათზე, წამზე, სიმბოლოზე ან ძიების ერთეულზე), როდესაც ფასები ხელმისაწვდომია; წინააღმდეგ შემთხვევაში — `0` (ღია წარუმატებლობის რეჟიმი).

> **ქეშში მოხვედრის ღირებულების სემანტიკა:** სემანტიკურ ქეშში მოხვედრისას (`X-OmniRoute-Cache-Hit: true`) ზედა დონის სერვისთან გამოძახება არ სრულდება, ამიტომ `X-OmniRoute-Response-Cost` არის `0.0000000000` (ქეშიდან პასუხის გაცემის **დამატებითი** ღირებულება). თავდაპირველი/სავარაუდო ღირებულება ცალკე, `X-OmniRoute-Cost-Saved`-ში აისახება. ბილინგის მომხმარებლებმა უნდა შეაჯამონ `X-OmniRoute-Response-Cost` (ქეშში მოხვედრა არაფერს ღირს); ქეშის ანალიტიკას კი შეუძლია `X-OmniRoute-Cost-Saved`-ის აგრეგირება.

## ექსკლუზიური მართული სესიის იჯარები

ექსკლუზიური მართული სესიის იჯარა არის სურვილისამებრ გასააქტიურებელი, კლიენტისგან დამოუკიდებელი მარშრუტიზაციის კონტრაქტი: ერთი აქტიური მფლობელი
ფლობს ერთ შესაბამის OmniRoute კავშირს. ის არ გასცემს მოდელს იჯარით, არ მოითხოვს OAuth-ს, არ განსაზღვრავს
კონკრეტულ კლიენტს და არ მოითხოვს კონკრეტულ პროვაიდერს.

ავთენტიფიკაციისთვის გამოყენებულ API გასაღებს უნდა ჰქონდეს `lease:exclusive` ფარგლები და ცალსახად მითითებული, არაცარიელი
`allowedConnections` სია. მონაცემთა ბაზაში ცვლილების საზღვარი გასაღების შექმნისა და ნაწილობრივი
განახლებებისას ორივე ველს ერთობლივად ამოწმებს.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

წარმატებული მიღების, განახლებისა და გათავისუფლების პასუხები შეიცავს დროის ნიშნულებს, `state`-ს და ზუსტ დადებით
`generation`-ს, თუმცა არასოდეს შეიცავს არჩეულ კავშირს ან ავტორიზაციის მონაცემებს. განახლებისა და გათავისუფლებისას
თაობა JSON სხეულში გადაიცემა:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

აქტიური იჯარის მფლობელს შეუძლია ცალსახად მოითხოვოს კონფიდენციალურობისთვის უსაფრთხო საჩვენებელი მეტამონაცემები თავისი მიმდინარე მიბმისთვის:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

ეს სურვილისამებრ სტატუსის მოქმედება ერთ მონაცემთა ბაზის ტრანზაქციაში დაცულია გაუმჭვირვალე მფლობელით, ავთენტიფიცირებული მართული API გასაღებითა და ზუსტი
აქტიური თაობით. `displayName` არის მხოლოდ კონფიგურირებული კავშირის შეკვეცილი
სახელი; თუ უსაფრთხო კონფიგურირებული სახელი არ არსებობს, მისი მნიშვნელობაა `null`. OmniRoute არასოდეს ანაცვლებს მას
ელფოსტის მისამართით ან გენერირებული ანგარიშის იდენტობით. პროვაიდერის მნიშვნელობა არაკონფიდენციალური საჩვენებელი იარლიყია და არასოდეს
არის გენერირებული თავსებადი პროვაიდერის იდენტიფიკატორი. ავტორიზაციის მონაცემები, ტოკენები, cookie-ები, კავშირის ან API
გასაღების დაუმუშავებელი ID-ები, მფლობელის ჰეშები, შემზღუდავი საიდუმლოებები და მარშრუტიზაციის შიდა მონაცემები გამორიცხულია.

არასწორი გასაღებით, არასწორი მფლობელით, მოძველებული თაობით, არარსებული, ვადაგასული, გათავისუფლებული და გაუქმებული იჯარის მოძიების ყველა შემთხვევა
აბრუნებს ერთსა და იმავე `409 LEASE_FENCE_STALE` შეცდომას, კავშირის მეტამონაცემების გარეშე. კლიენტს, რომელმაც სიმძლავრის ლოდინის პასუხი მიიღო, შესამოწმებელი აქტიური მიბმა არ აქვს. როდესაც მარშრუტიზაცია აქტიურ იჯარას სხვა კავშირზე გადაიყვანს,
იგივე თაობა ძალაში რჩება და სტატუსი ატომურად აბრუნებს ახალ მიბმას — არასოდეს ძველს.
არსებული კლიენტები უცვლელი რჩება, რადგან მიღების, განახლების, გათავისუფლებისა და ლოდინის პასუხები
წინა ფორმატს ინარჩუნებს.

სერვერის ეს კონტრაქტი არ ცვლის სტანდარტული OpenAI Codex-ის `/status`-ს. სტანდარტული Codex ამჟამად აჩვენებს თავის
მოდელის პროვაიდერსა და ჩაშენებულ ავთენტიფიკაციის/ანგარიშის მდგომარეობას, მაგრამ არ ასახავს მორგებული
პროვაიდერის ანგარიშის თვითნებურ მეტამონაცემებს; კლიენტის მომავალმა ინტეგრაციამ ეს მოქმედება უნდა გამოიძახოს და გადაწყვიტოს, როგორ
აჩვენოს `connection.displayName`.

ამის შემდეგ, მართული ინფერენსის ყოველი მოთხოვნა ორივე საკონტროლო სათაურს გადასცემს:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

ზუსტი მფლობელი, თაობა, აქტიური კავშირი და ავთენტიფიცირებული API გასაღები ყოველი მხარდაჭერილი
ზედა დონის სერვისთან მიმართვის მცდელობის უშუალოდ წინ მოწმდება. მფლობელისა და თაობის სხვა გასაღებით განმეორებით გამოყენება წარუმატებელია მაშინაც კი,
როდესაც ის გასაღები იმავე კავშირს უშვებს. დაუმუშავებელი მფლობელები არ ინახება მუდმივად, არ იწერება ჟურნალში, არ რჩება
მოთხოვნის სურათში და არ გადაიგზავნება ზედა დონის სერვისთან.

დროებითი კონკურენცია აბრუნებს HTTP `429`-ს `Retry-After`-თან და შემდეგ მონაცემებთან ერთად:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

ეს პასუხი მხოლოდ იმას ნიშნავს, რომ ჩვეულებრივი შესაბამისი კავშირების სიმრავლე ცარიელი არ იყო და ყოველი თავისუფალი კანდიდატი
სხვა აქტიურ იჯარას ეკავა. მხარდაუჭერელი მოდელები/პროვაიდერები, წესებთან შეუსაბამობა, მოლოდინის პერიოდი, კვოტა,
მდგომარეობა და შესაბამისობის სხვა ჩვეულებრივი შემოწმებების წარუმატებლობა OmniRoute-ის არსებულ პასუხებს ინარჩუნებს.

### `x-omniroute-compression`

შეკუმშვის გეგმის თითოეული მოთხოვნისთვის განსაზღვრული გადაფარვა. აქვს უმაღლესი პრიორიტეტი — აღემატება მარშრუტიზაციის კომბინაციის
გადაფარვას, აქტიურ პროფილს, ავტომატურ ტრიგერსა და პანელის ნაგულისხმევ პარამეტრს. მნიშვნელობები:

| მნიშვნელობა   | ეფექტი                                                                                                                             |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `off`         | ამ მოთხოვნისთვის შეკუმშვა არ გამოიყენება.                                                                                          |
| `default`     | პანელიდან მიღებული ნაგულისხმევი პროფილი (აქტიურ პროფილს უგულებელყოფს). დანაკარგიანი ძრავები გამორთული რჩება.                       |
| `safe`        | მხოლოდ დუბლიკატების მოცილება და ჰარეების შეკუმშვა.                                                                                 |
| `allow-lossy` | ამ მოთხოვნისთვის ინარჩუნებს ოპერატორის გეგმას, შეჯამებებისა და სტილის გადაწერის ჩათვლით.                                           |
| `engine:<id>` | ერთი ძრავა, როდესაც ის ჩართულია, მაგალითად `engine:rtk`. ამ ძრავის გამოყენებაზე თანხმობა თითოეული მოთხოვნისთვის ცალ-ცალკე გაიცემა. |
| `<combo>`     | სახელდებული კომბინაცია, რომელიც ჯერ სახელით (რეგისტრის გაუთვალისწინებლად), შემდეგ კი ID-ით ემთხვევა.                               |

შენიშვნები:

- უცნობი მნიშვნელობები იგნორირდება (მოთხოვნა არასოდეს უარყოფილა); განსაზღვრა ოპერატორის პრიორიტეტების ჩვეულებრივ წესზე გადადის.
- თუ რამდენიმე კომბინაციას ერთი და იგივე სახელი აქვს, დეტერმინისტული დამთხვევისთვის გადაეცით კომბინაციის **ID**.
- კომბინაცია, რომლის სახელია `off` ან `default`, სახელით ვერ შეირჩევა (ეს საკვანძო სიტყვები პირველად ინტერპრეტირდება); ასეთ კომბინაციას მისი ID-ით მიმართეთ.
- შეკუმშვის მთავარი გადამრთველი მკაცრი შემზღუდავია: როდესაც შეკუმშვა გლობალურად გამორთულია, ამ სათაურს მისი ჩართვა არ შეუძლია.

გამოყენებული გეგმა პასუხის სათაურში ბრუნდება:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

სადაც `<source>` არის ერთ-ერთი შემდეგიდან: `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` ან `off`.

## ემბედინგები

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

ხელმისაწვდომი პროვაიდერები: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

კატალოგის იდენტიფიკატორების ფორმატია `provider/model` (მაგალითად: `jina-ai/jina-embeddings-v5-omni-small`). რეესტრში არსებული Jina-ს მოდელების იდენტიფიკატორები პროვაიდერის პრეფიქსის გარეშე (მაგალითად, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) ასევე მუშავდება. Jina-ს embed/rerank/classify/segment ოპერაციები პირველ რიგში დაფის `jina-ai` ავტორიზაციის მონაცემებს იყენებს; `JINA_AI_API_KEY` სარეზერვო ვარიანტია მხოლოდ მაშინ, როცა დაფაზე გასაღები არ არსებობს. `jina-reader` ბარათი განკუთვნილია მხოლოდ Reader-ისთვის / `r.jina.ai`-სთვის (`POST /v1/web/fetch`) და არასოდეს ემსახურება ემბედინგებს ან ხელახალ რანჟირებას.

რეესტრის მოდელები, რომლებიც მულტიმოდალურ მხარდაჭერას აცხადებენ, ასევე იღებენ პროვაიდერისგან დამოუკიდებელ მაქსიმუმ 32 სტრუქტურირებულ
ელემენტს. მედია-ელემენტების ტიპებია `text`, `image`, `audio`, `video` და `document`. მათი მედიის `source`
არის ან `{"type":"url","url":"https://..."}`, ან
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
და ოჯახის ფსევდონიმი `jina-ai/jina-embeddings-v5-omni` → omni-small) ასევე იღებს Jina-ს ნატიურ
EmbeddingsV5Request დოკუმენტებს და **უცვლელად გადააგზავნის მათ** მისამართზე `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

ნატიური `{ image | audio | video | pdf }` მნიშვნელობები შეიძლება იყოს საჯარო HTTPS URL, `data:` URI ან დაუმუშავებელი
base64. OmniRoute არ გარდაქმნის ამ ობიექტებს სტრიქონებად და არ ჩამოტვირთავს ნატიურ გამოსახულებათა URL-ებს — საჯარო
მედიას თავად Jina იღებს. Jina-ს დამატებითი ველები (`task`, `normalized`, `truncate`, `embedding_type`)
გადაიგზავნება. მხოლოდ ტექსტზე გათვლილი Jina SKU-ები კვლავ უარყოფს არატექსტურ დოკუმენტებს.

უსაფრთხოებისა და გადაცემის შეზღუდვები:

- დისტანციური მედიის URL-ები უნდა იყოს საჯარო HTTPS. კანონიკური `{type,source:url}` ელემენტები
  სერვერის მხარეს ჩამოიტვირთება (გადამისამართებების ხელახალი ვალიდაციით, დროის ლიმიტით, ზომის შეზღუდვებით, საჯარო DNS-ითა და კავშირის ფიქსირებით) და
  პროვაიდერის გამოძახებამდე ჩაშენდება. Jina-ს ნატიური `{image:"https://..."}` ელემენტები უცვლელად
  გადაიგზავნება იმავე საჯარო HTTPS შემოწმების შემდეგ; URL-ს Jina ჩამოტვირთავს.
- ჩაშენებული base64 მედია შეზღუდულია 8 MiB-მდე დეკოდირებული მონაცემით თითოეულ ელემენტზე და 16 MiB-მდე დეკოდირებული მონაცემით მთლიან მოთხოვნაში.

პროვაიდერისთვის გარდაქმნა (კანონიკური ელემენტები არასოდეს გადაიგზავნება უცვლელად):

- Jina-ს მულტიმოდალური მოდელები: თითოეული ზედა დონის ელემენტი გარდაიქმნება მოდალობის გასაღებიან ერთ ობიექტად
  (`text` / `image` / `audio` / `video` / `pdf`), ჩაშენებული მედიისთვის data URI-ების გამოყენებით; თითო
  ზედა დონის ელემენტზე ერთი ვექტორი.
- Gemini Embedding 2 ოჯახი: ზედა დონის ერთი მასივი გარდაიქმნება ერთ ნატიურ
  `models/{model}:embedContent` მოთხოვნად `content.parts`-ით (`text` ან `inline_data`).
- llama.cpp (`llama-cpp/<model>`, ლოკალური სერვერის მიერ ჩატვირთული ნებისმიერი მოდელი): კანონიკური `text` ელემენტები
  გარდაიქმნება ჩვეულებრივ სტრიქონებად, ხოლო `image` / `audio` / `video` — თითო
  `{"content": [part]}` ობიექტად, llama-server-ის ჩატის კონტენტის ნაწილების გამოყენებით (`image_url`,
  `input_audio` ფორმატით `wav` / `mp3` / `flac`, `input_video`) და ჩაშენებული მონაცემებით; თითო
  ზედა დონის ელემენტზე ერთი ვექტორი. სერვერი უნდა გაეშვას `--embedding --mmproj …` პარამეტრებით; პროექტორის გარეშე ის
  თავად უარყოფს მედიას. `document` მხარდაჭერილი არ არის.
- უცნობი/დინამიკური მოდელები, რომლებსაც მოდალობის მკაფიო მეტამონაცემები არ გააჩნია, სტრუქტურირებულ შეყვანას HTTP 400 პასუხით უარყოფს.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

მოდელისა და მოდალობის მხარდაუჭერელი კომბინაციები ელემენტის იძულებითი გარდაქმნის ნაცვლად აბრუნებს HTTP 400 პასუხს. შეყვანის გარდა არსებული
გაფართოების ველები ძველი ფორმატის სტრიქონულ/ტოკენურ მოთხოვნებში კვლავ უცვლელად გადაიცემა.

## სურათების გენერაცია

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

ხელმისაწვდომ პროვაიდერებს შორისაა OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (ლოკალური), ComfyUI (ლოკალური).

`n` აბრუნებს `n` სურათს `data[]`-ში. პროვაიდერებისთვის, რომელთა ზედა დონის API თითო გამოძახებაზე ერთ სურათს აბრუნებს
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), სრულდება `n` ცალკეული ზედა დონის გამოძახება, ერთდროულად მაქსიმუმ 4. ფიქსირებულ
`seed`-ს ემატება გამოძახების ინდექსი (`seed`, `seed + 1`, …), ამიტომ სურათები განსხვავდება, თუმცა
კვლავწარმოებადობა შენარჩუნებულია. `n`-ის მაქსიმალური მნიშვნელობაა 10. თუ რომელიმე გამოძახება ვერ შესრულდება, მთელი მოთხოვნა
შეცდომით სრულდება. fan-out ფორმატების სია არის `SINGLE_IMAGE_FANOUT_FORMATS` ფაილში
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux ხელახლა იყენებს არსებულ API-გასაღების კავშირს და იღებს `zenmux/` ან `zm/` პრეფიქსებს:

- `zenmux/openai/gpt-image-2` იყენებს ZenMux-ის OpenAI Images API-ს. პარამეტრებს შორისაა `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` და `response_format`.
- სხვა გამომცემლები, მაგალითად `zm/meta/muse-image-1.0`, იყენებენ ZenMux-ის Vertex AI `:predict`
  საბოლოო წერტილს. `n` შეესაბამება `sampleCount`-ს, `aspect_ratio` — `aspectRatio`-ს, ხოლო `image_size`
  (`1K`, `2K`, `4K`) — `sampleImageSize`-ს. პიქსელებში მითითებული `size` განსაზღვრავს მხოლოდ გვერდების თანაფარდობას
  და არა გარანტირებულ პიქსელურ ზომებს. მხარდაჭერილი თანაფარდობები, გარჩევადობები და რაოდენობები მოდელის მიხედვით განსხვავდება.
- `zm/inclusionai/ming-image-0.1-design` ზომებს თავად ირჩევს. გამოტოვეთ `size`,
  `aspect_ratio` და `image_size`; აშკარად მითითებული მნიშვნელობები აბრუნებს HTTP 400-ს. PNG, JPEG და WebP
  ფორმატების მოთხოვნა შესაძლებელია `output_format`-ის საშუალებით.

### მოდელის id-ის პრეფიქსები (`?prefix=`)

მოდელების უმეტესობა წარმოდგენილია **პროვაიდერის პრეფიქსით**. თუ რომელ პრეფიქსს მიიღებთ, ამას
`MODELS_CATALOG_PREFIX_MODE` ფუნქციური ალამი განსაზღვრავს; მისი გადაფარვა ასევე შესაძლებელია **თითოეული მოთხოვნისთვის**
query-პარამეტრით — ეს სასარგებლოა კლიენტისთვის, რომელსაც სუფთა სია სურს ისე, რომ სერვერის მასშტაბით
პარამეტრი ყველა დანარჩენისთვის არ შეიცვალოს:

```bash
GET /v1/models?prefix=alias        # თითო მოდელზე ერთი id — მოკლე alias-პრეფიქსი
GET /v1/models?prefix=dual         # ორივე ფორმა (სერვერის ნაგულისხმევი ვარიანტი)
GET /v1/models?prefix=canonical    # მხოლოდ სრული provider-id პრეფიქსი
```

| რეჟიმი      | აბრუნებს                                                 | შენიშვნები                                                                                                                                                                                                    |
| ----------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **და** `claude/claude-sonnet-4-6` | **ნაგულისხმევი.** ორივე id იმავე მოდელზე მარშრუტდება; ეს შენარჩუნებულია, რათა კლიენტის კონფიგურაციებმა, რომლებშიც რომელიმე ფორმა მკაცრადაა გაწერილი, მუშაობა განაგრძოს. კატალოგის ზომას დაახლოებით აორმაგებს. |
| `alias`     | `cc/claude-sonnet-4-6`                                   | თითო მოდელზე ერთი ჩანაწერი. განსხვავებული alias-ის არმქონე პროვაიდერებიც მაინც აბრუნებენ თავიანთ ჩანაწერს, ამიტომ არაფერი იკარგება.                                                                           |
| `canonical` | `claude/claude-sonnet-4-6`                               | თითო მოდელზე ერთი ჩანაწერი სრული provider-id პრეფიქსით. განსხვავებული alias-ის არმქონე პროვაიდერებიც (მაგ., `antigravity/…`, `agy/…`) აქაც აბრუნებენ თავიანთ ერთადერთ id-ს, ამიტომ არაფერი იკარგება.          |

`dual` რეჟიმის სარკისებრი ჩანაწერის ამოცნობა query-პარამეტრის გარეშეც შეიძლება: ის შეიცავს `parent`
ველს, რომელიც ძირითად id-ზე მიუთითებს.

კლიენტებმა, რომლებიც მოდელის ამრჩევს აჩვენებენ, უნდა მოითხოვონ `?prefix=alias` — სწორედ ასე იქცევა
[OmniCopilot VS Code გაფართოება](../guides/VSCODE-COPILOT.md).

### აღმოჩენის ფილტრები (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` იღებს არჩევით აღმოჩენის ფილტრებს. თუ არცერთი მათგანი არ არის მითითებული, პასუხი
უცვლელი რჩება. ისინი ავიწროებენ კატალოგს, რომელსაც გამომძახებელი უკვე ხედავს (ჯერ API-გასაღების ნებართვები გამოიყენება),
და სრულდება OpenAI-ის სტილის `limit` / `after` გვერდებად დაყოფამდე:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # სიაში მითითებული ყველა შესაძლებლობა true უნდა იყოს
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # კატალოგის `type`; მის გარეშე სტრიქონები არის `chat`
GET /v1/models?q=sonnet&limit=10                           # რეგისტრისგან დამოუკიდებელი დამთხვევა id-ში ან სახელში
```

| პარამეტრი     | მნიშვნელობები                                                                                       |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | არაუარყოფითი მთელი რიცხვი, რომელიც შედარებულია `context_length`-თან                                 |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 სიმბოლო                                                                                       |

უცნობი მნიშვნელობა ან `min_context`, რომელიც არაუარყოფითი მთელი რიცხვი არ არის (მაგალითად, `1.5`),
აბრუნებს HTTP `400`-ს, ხოლო შეტყობინებაში ჩამოთვლილია დასაშვები მნიშვნელობები. იმპლემენტაცია:
`src/app/api/v1/models/catalogFilters.ts`.

### მოდელების მოკლე სია (`POST /v1/models/query`)

`POST /v1/models/query` იმავე კატალოგიდან აბრუნებს მოკლე, დეტერმინისტულ სიას, იგივე
ავტორიზაციითა და თითოეული გასაღებისთვის იგივე ხილვადობით, როგორც `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...მოდელები ] }
```

ყველა ველი არასავალდებულოა. `capabilities` და `exclude` იღებს მასივს ან მძიმეებით გამოყოფილ სტრიქონს;
`max_output` შედარებულია `max_output_tokens`-თან. შედეგები ჯერ `owned_by`-ის, შემდეგ კი `id`-ის მიხედვით ლაგდება.
`limit`-ის ნაგულისხმევი მნიშვნელობაა `20`, ხოლო `100`-ზე მეტი მნიშვნელობა `100`-მდე იზღუდება. არასწორი JSON, უცნობი
ველი ან არასწორი მნიშვნელობა აბრუნებს HTTP `400`-ს.

### ინდივიდუალურად დამალული ჩატის მოდელები

პროვაიდერის გვერდზე **დამალულად** მონიშნული მოდელი კატალოგიდან გამორიცხულია და მისი ცალსახად
მოთხოვნისას ბრუნდება HTTP `404` / `model_not_found`. შემოწმება იყენებს განსაზღვრულ
პროვაიდერსა და მოდელს, მათ შორის პროვაიდერის alias-ებს, თავსებადი პროვაიდერის კვანძის პრეფიქსებსა და
კავშირის ნაგულისხმევ მნიშვნელობებს. კომბინაცია გამოტოვებს დამალულ სამიზნეებს და შეუძლია ხილული თანამოდელის გამოყენება; როდესაც არცერთი
შესრულებადი სამიზნე არ რჩება, ის იმავე შეცდომის კოდს აბრუნებს. დამალვის გაუქმება მომდევნო
მოთხოვნიდან ამოქმედდება. მხოლოდ გამოსახულებისთვის განკუთვნილი ხილვადობის გადაფარვები იმავე ID-ის მქონე ჩატის მოდელს არ მალავს.

ინდივიდუალური მოდელის ეს პარამეტრი განცალკევებულია
[მოდელის გამოჩენის დაშვების/აკრძალვის სიებისგან](../routing/MODEL_EXPOSURE_LIST.md), რომლებიც ფილტრავს კატალოგში
გამოქვეყნებულ მოდელებსა და ავტომატური მარშრუტიზაციის კანდიდატებს, თუმცა პირდაპირ გაგზავნას ინარჩუნებს. API-გასაღების მოდელის
ნებართვები კვლავ დამოუკიდებლად მოქმედებს. კატალოგის პრეფიქსის ნაგულისხმევ რეჟიმად რჩება `dual`.

### აზროვნების გარეშე მოდელების ვარიანტები

აზროვნების შესაძლებლობის მქონე Claude მოდელებისთვის `/v1/models` ასევე აქვეყნებს **აზროვნების გარეშე** ვარიანტს, რომლის id-ს წინ ერთვის `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

ამ id-ის არჩევისას (მაგ., Claude Code-ის კონფიგურაციაში, რომელიც ყოველთვის ურთავს `thinking` ბლოკს), ის კვლავ რეალურ `<provider>/<model>`-ზე გადაიყვანება, თუმცა მსჯელობა გამორთული იქნება — `/v1/messages` გზაზე `thinking:{type:"disabled"}`-ის გამოყენებით, ხოლო `/v1/chat/completions` გზაზე `reasoning`/`reasoning_effort` ველების გამოტოვებით. ვარიანტი ჩამონათვალში მხოლოდ Claude-ის ოჯახის იმ მოდელებისთვის გამოჩნდება, რომლებიც აზროვნებას უჭერენ მხარს **და** `disabled` მნიშვნელობას ითვალისწინებენ (ამიტომ, მაგ., მხოლოდ ადაპტიური რეჟიმის მქონე მოდელები, რომლებიც `disabled` მნიშვნელობას უარყოფენ, გამორიცხულია). ოპერატორებს შეუძლიათ თითოეული მოდელისთვის ვარიანტი იძულებით ჩართონ ან გამორთონ `ModelSpec.noThinkingAlias`-ის მეშვეობით.

## აუდიოს გენერაცია ElevenLabs-ის მეშვეობით

OmniRoute-ში დააკონფიგურირეთ `elevenlabs` პროვაიდერთან კავშირი თქვენი ElevenLabs API-გასაღებით.
კლიენტები ავთენტიფიკაციას გადიან საკუთარი **OmniRoute** გასაღებით (`Authorization: Bearer $OMNIROUTE_API_KEY`);
gateway შენახულ პროვაიდერის გასაღებს გადასცემს, როგორც `xi-api-key`. არასოდეს გაგზავნოთ ElevenLabs-ის გასაღები
gateway-ის bearer-ტოკენად.

| მეთოდი | გზა                         | პასუხი                                         | API-გასაღების endpoint-ის კატეგორია |
| ------ | --------------------------- | ---------------------------------------------- | ----------------------------------- |
| POST   | `/v1/sound-generation`      | აუდიოს ნატიური ბაიტები                         | `elevenlabs`                        |
| POST   | `/v1/music`                 | აუდიოს ნატიური ბაიტები                         | `music`                             |
| POST   | `/v1/music/stream`          | აუდიოს ნაკადური ბაიტები                        | `music`                             |
| POST   | `/v1/music/detailed`        | ნატიური multipart-აუდიო და კომპოზიციის გეგმა   | `music`                             |
| POST   | `/v1/music/detailed/stream` | ნატიური SSE-მეტამონაცემები და აუდიოფრაგმენტები | `music`                             |
| POST   | `/v1/music/plan`            | კომპოზიციის გეგმა JSON-ფორმატში                | `music`                             |

ეს endpoint-ები ავსებს არსებულ `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` და `/v1/speech-to-text` მარშრუტებს. ნატიური JSON-ველები
და მოთხოვნის პარამეტრები, როგორიცაა `output_format` და `enable_logging`, უცვლელად ნარჩუნდება.
`/v1/music/detailed`-ის პასუხები ინარჩუნებს საკუთარ multipart-საზღვრებს; დაამუშავეთ ისინი, როგორც multipart.
`/v1/music/detailed/stream` აბრუნებს `text/event-stream`-ს კომპოზიციის მეტამონაცემებითა და
base64-ფორმატის აუდიოფრაგმენტებით SSE-მოვლენებში. ექვსივე მარშრუტი მხარს უჭერს CORS-ის წინასწარ მოთხოვნას.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# მოკლე ხმოვანი ეფექტი. ხანგრძლივობა: 0.5-დან 30 წამამდე.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# მუსიკის ხანგრძლივობა მილიწამებში გამოისახება: 3000-დან 600000-მდე.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

აუდიოს ნაწილ-ნაწილ მისაღებად გამოიყენეთ `/v1/music/stream` იმავე JSON-ტანით. კომპოზიცია
იღებს ზუსტად ერთ-ერთს — `prompt` ან `composition_plan`; `/v1/music/plan` მოითხოვს `prompt`-ს
და სურვილისამებრ იღებს `source_composition_plan`-ს. ნატიური სქემები ინარჩუნებს პროვაიდერის დამატებით
ველებს, რათა კომპოზიციის გეგმის ვერსიებმა და ზუსტი კონფიგურაციის პარამეტრებმა ElevenLabs-მდე მიაღწიოს.

გაერთიანებული `/v1/music/generations` endpoint ასევე იღებს `elevenlabs/music_v1`,
`elevenlabs/music_v2` და `elevenlabs/music_v2_5` მოდელებს. ElevenLabs-თან აქტიური კავშირის არსებობისას
ეს მოდელები ხელმისაწვდომია მუსიკის კატალოგში. ეს endpoint აბრუნებს
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`-ს. მისი `duration` ველი იზომება
წამებში და შეესაბამება `music_length_ms`-ს; აშკარად მითითებულ `music_length_ms`-ს უპირატესობა ენიჭება.
`instrumental` შეესაბამება `force_instrumental`-ს, ხოლო ნატიურ ველს უპირატესობა ენიჭება.
ნაკადური გადაცემისთვის გამოიყენეთ ნატიური ნაკადური endpoint-ები, ხოლო მხოლოდ კომპოზიციის გეგმით
განსაზღვრული მოთხოვნებისთვის — ნატიური კომპოზიციის endpoint.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

endpoint-ის, მოდელის, ბიუჯეტისა და კავშირის შეზღუდვები გამოიყენება upstream-გამოძახებამდე. ნატიური
მარშრუტები უცვლელად აბრუნებს upstream-ის სტატუსის კოდებსა და შეცდომის სხეულებს, მათ შორის `402`-ს გეგმის
შეზღუდვისთვის და `429`-ს კვოტის ლიმიტისთვის. არსებობის შემთხვევაში ნარჩუნდება `character-cost`, `song-id`, `request-id` და `retry-after`
სათაურები. უფასო კრედიტის ბალანსი არ უზრუნველყოფს წვდომას მუსიკის ყველა
მოდელზე, გამომავალ ფორმატსა თუ API-ფუნქციაზე: თითოეული მოთხოვნისთვის უფლებამოსილებას ElevenLabs განსაზღვრავს.
გაერთიანებული endpoint ინარჩუნებს შეცდომის სტატუსის კოდებს OmniRoute-ის ნორმალიზებულ შეცდომის კონვერტში.

Upstream-კონტრაქტები: [ხმოვანი ეფექტები](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[მუსიკის კომპოზიცია](https://elevenlabs.io/docs/api-reference/music/compose) და
[ნაკადური მუსიკის დეტალები](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

```bash
# მოდერაცია
```

> როგორიცაა `http://reranker:8080/v1`; მათთან დაკავშირება ხდება პირდაპირ და არასოდეს — `HTTP(S)_PROXY`-ის ან
> კავშირის ფიქსირებული პროქსის გავლით). ნებისმიერ სხვა
> ჰოსტზე არსებული კვანძები — LAN-ის კომპიუტერი ან Tailscale-ის პირი — დაშვებულია მხოლოდ მაშინ, როდესაც ოპერატორი ჩართავს
> `RERANK_REMOTE_PROVIDER_NODES` ფუნქციის დროშას **და** კვანძის საბაზისო URL აკმაყოფილებს პროვაიდერის
> გამავალი URL-ების პოლიტიკას (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> მეხსიერების ძრავის ხელახალი რანჟირების ეტაპი ამ მარშრუტს
> უკუმარყუჟის მეშვეობით იძახებს, ამიტომ იგივე წესი ვრცელდება მეხსიერების პარამეტრებში `rerankProviderModel`-ზეც.
>
> **ლოკალური სერვერის ფორმატები:** კვანძი გამოიძახება მისამართზე `<base>/v1/rerank`, ხოლო 404-ის შემთხვევაში — მისამართზე `<base>/rerank`
> (Infinity, TEI). ზემდგომი მოთხოვნის სხეული შეიცავს როგორც Cohere/OpenAI-ის ვარიანტებს (`documents`,
> `return_documents`), ისე TEI-ის ვარიანტებს (`texts`, `return_text`), ხოლო ზემდგომი პასუხი
> ნორმალიზდება Cohere-ის კონვერტის ფორმატში: TEI-ის უშუალო `[{index, score, text}]`, მსუბუქი კარიბჭეებიდან მიღებული `{results: [{index, score}]}`
> და Voyage-ის სტილის `{data: [...]}` კლიენტს ყველა შემთხვევაში უბრუნდება ფორმატით
> `{results: [{index, relevance_score, document?}]}`, ქულის მიხედვით დალაგებული და `top_n`-მდე შეზღუდული.

> **პროვაიდერის კვანძების აღმოჩენა:** OpenAI-თან თავსებადი პროვაიდერის კვანძის მოდელები `GET /v1/models`-ში
> კვანძის პრეფიქსით გამოჩნდება. ჩანაწერები, რომლებიც საბოლოო წერტილის მეტამონაცემებს არ შეიცავს (რაც ტიპურია ლოკალური `/v1/models` ჩამონათვალებისთვის),
> მემკვიდრეობით იღებს კვანძის `apiType`-ს, ამიტომ `embeddings` კვანძის მოდელებს აქვთ `type: "embedding"`, ხოლო
> `rerank` კვანძის მოდელებს — `type: "rerank"`, ჩატის ნაგულისხმევად გამოყენების ნაცვლად; სინქრონიზებულ ან ხელით დამატებულ ჩანაწერში ცხადად მითითებულ
> `supportedEndpoints`-ს კვლავ უპირატესობა ენიჭება.

## Files API

OpenAI-თან თავსებადი ფაილების endpoint პაკეტური შეყვანა/გამოტანისა და დანიშნულების მიხედვით ფაილების ატვირთვისთვის.

| მეთოდი | გზა                      | აღწერა                                                                                                               |
| ------ | ------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/files`              | ფაილის ატვირთვა (multipart: `file`, `purpose`, `expires_after[anchor]`, `expires_after[seconds]`) — მაქსიმუმ 512 MiB |
| GET    | `/v1/files`              | ავთენტიფიცირებული API გასაღების ფაილების სიის მიღება                                                                 |
| GET    | `/v1/files/[id]`         | ფაილის მეტამონაცემების მიღება                                                                                        |
| DELETE | `/v1/files/[id]`         | ფაილის წაშლა                                                                                                         |
| GET    | `/v1/files/[id]/content` | ფაილის დაუმუშავებელი შიგთავსის ნაკადის სახით დაბრუნება                                                               |

**ავთენტიფიკაცია:** Bearer API გასაღები — `getApiKeyRequestScope`-ის მეშვეობით ფაილები თითოეული API გასაღების მიხედვით არის იზოლირებული. გასაღები
ხედავს, ჩამოტვირთავს და შლის მხოლოდ საკუთარ ფაილებს; მართვის პანელის სესია გასაღების გარეშე კითხულობს
მთელი ინსტანციის მონაცემებს; მფლობელის არმქონე ფაილზე (ანონიმური ან მართვის პანელის სესიიდან ატვირთული) წვდომა აკრძალულია ყველა
არასესიური გამომძახებლისთვის. `GET /v1/files` ანონიმურ გამომძახებელს — ასევე წარმოდგენილი გასაღების შემთხვევაში, რომლის
ამოცნობაც ვერ ხერხდება — პასუხობს `401`-ით მაშინაც კი, როცა `REQUIRE_API_KEY=false`, ნაცვლად ყველა tenant-ის
ფაილების ჩამოთვლისა (GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523).

| GET    | `/v1/batches`             | პაკეტების სიის მიღება                                                                                                  |

| DELETE | `/v1/batches/[id]`        | დასრულებული/წარუმატებელი პაკეტის წაშლა                                                                                 |

არასესიური გამომძახებლისთვის (მიღება, წაშლა, გაუქმება და შექმნისას `input_file_id`-ის შემოწმება).
`GET /v1/batches` ანონიმურ გამომძახებელს პასუხობს `401`-ით მაშინაც კი, როცა `REQUIRE_API_KEY=false`.

## ძიების API

ვებ/ძიების პროვაიდერების აბსტრაქცია (Tavily, Brave, Exa, Serper და სხვ.).

| მეთოდი | გზა                    | აღწერა                                                                                                       |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| GET    | `/v1/search`           | კონფიგურირებული ძიების პროვაიდერებისა და მათი შესაძლებლობების სიის მიღება                                    |
| POST   | `/v1/search`           | ძიების მოთხოვნის გაშვება — მოთხოვნის სხეული მოწმდება `v1SearchSchema`-ით; მხარდაჭერილია კეშირება/გაერთიანება |
| GET    | `/v1/search/analytics` | თითოეული პროვაიდერის შედეგების/შეყოვნების/კეშის სტატისტიკა                                                   |

**ავტორიზაცია:** Bearer API გასაღები (`extractApiKey` + `isValidApiKey`). ძიების პოლიტიკა აღსრულდება `enforceApiKeyPolicy`-ის მეშვეობით.

### Exa-სა და Tavily-ს `provider_options`

Exa და Tavily პროვაიდერისთვის სპეციფიკურ ველებს სახელთა სივრცით გამოყოფილი ობიექტიდან კითხულობენ:
`provider_options.exa` (ან `provider_options["exa-search"]`) და `provider_options.tavily`
(ან `provider_options["tavily-search"]`). გადაიცემა მხოლოდ ქვემოთ ჩამოთვლილი გასაღებები. თითოეული მათგანი
მოწმდება საკუთარი Zod სქემის მიხედვით `open-sse/handlers/search/providerOptionsPassthrough.ts`-ში,
ხოლო არასწორი ტიპის მქონე გასაღები გამოირიცხება. ყველა სხვა გასაღები უგულებელყოფილია, მათ შორის ავტორიზაცია, საბაზისო URL,
`stream` და `outputSchema`. სხვა პროვაიდერების მიერ გამოყენებული ბრტყელი გასაღებები (`cx`, `depth`, ...) კვლავ
ძველებურად მუშაობს.

| პროვაიდერი | ზედა დონის ველები                                                                                                                                                                                                                                                                                                                                                         | ჩადგმული                                                                                                                                                                 |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Exa        | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (ბრტყელი პრიმიტივები), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                          | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` გაერთიანებულია ნაგულისხმევ `{ text: true, highlights: true }`-თან |
| Tavily     | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                        |

ზოგად ველებს ყოველთვის ენიჭებათ უპირატესობა: `query`, `max_results`, `filters` (დომენები), `country` და
`search_type`-დან მიღებული თემა. Exa-ში `search_type: "news"` ინარჩუნებს `category: "news"`-ს.
Tavily ასევე იღებს `search_type: "finance"`-ს (`topic: "finance"`).

ზოგადი `time_range` ახლა ორივე პროვაიდერს გადაეცემა: Exa იღებს `startPublishedDate`-ს (ISO
დროის ნიშნული), ხოლო Tavily — `start_date`-ს (`YYYY-MM-DD`). `provider_options`-ში ცხადად მითითებული თარიღი
გადაფარულად ანაცვლებს გარდაქმნილ მნიშვნელობას.

Exa-ს შედეგები `provider_raw`-ში ინარჩუნებს `id`, `highlight_scores`, `summary`, `subpages`, `entities` და `extras` ველებს.
Tavily-ს შედეგები ინარჩუნებს `images` და `favicon` ველებს.

ღირებულების აღრიცხვა კვლავ ბრტყელი რეესტრის, `costPerQuery`-ის, მეშვეობით ხორციელდება. Tavily
`search_depth: "advanced"`-ისთვის თითო გამოძახებაზე მეტ კრედიტს აკისრებს, თუმცა ეს განსხვავება
`usage.search_cost_usd`-ში არ აისახება.

## Web Fetch API

ამოიღეთ კონტენტი URL-დან კონფიგურირებული ვებ-ამოღების პროვაიდერის მეშვეობით (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, იგივე API გასაღები, რასაც Parallel Search იყენებს) მხოლოდ Markdown-ს
აბრუნებს — ნებისმიერი სხვა `format` იწვევს `400`-ს — და კონტენტის მოცულობას 100,000 სიმბოლომდე ზღუდავს. როდესაც
სამიზნე გვერდის ამოღება შეუძლებელია, ზემდგომი სერვისი ამის შესახებ HTTP 200 პასუხში იტყობინება;
OmniRoute ამას ფიქსირებული შეტყობინების მქონე `422` პასუხად გარდაქმნის.

| მეთოდი | მისამართი       | აღწერა                                                        |
| ------ | --------------- | ------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | URL-ის მიღება/ამოღება — სხეული მოწმდება `v1WebFetchSchema`-ით |

**ავთენტიფიკაცია:** Bearer API გასაღები (`extractApiKey` + `isValidApiKey`). პოლიტიკა აღსრულდება `enforceApiKeyPolicy`-ის მეშვეობით.

**კვოტის გათვალისწინებით სარეზერვო გადართვა (#8297):** როდესაც აშკარა `provider` მითითებული არ არის, პულში
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`)
გადაადგილება ხდება ფიქსირებული
პრიორიტეტული თანმიმდევრობით (პირველის სრულად შევსება) — სიხშირით შეზღუდული, მაგრამ კონფიგურირებული პროვაიდერი
გამოტოვებულია მოთხოვნის დაუყოვნებლივ შეწყვეტის ნაცვლად, ხოლო განმეორებით საცდელი/კვოტასთან დაკავშირებული ზემდგომი შეცდომისას
(HTTP 429 ყოველთვის; 402/403 Firecrawl/Tavily/TinyFish-ის კვოტაზე დაფუძნებული უფასო დონეებისთვის —
არა Jina Reader-ისთვის და არასოდეს ჩვეულებრივი 400 არასწორი მოთხოვნისთვის) მოთხოვნის შესრულებისას სისტემა გადადის
შემდეგ ჯერ კიდევ გამოუყენებელ, ავტორიზაციის მონაცემებით აღჭურვილ პროვაიდერზე. როდესაც პულის ყველა პროვაიდერი
ამოწურულია, ბოლო წერტილი წინა ზოგადი `400`-ის ნაცვლად აბრუნებს ერთიან `429` პასუხს (`Retry-After`
სათაურით). როდესაც მოთხოვნილია კონკრეტული `provider`, ფარული სარეზერვო გადართვა **არ** ხდება — სიხშირით
შეზღუდული ან შეცდომიანი კონკრეტული პროვაიდერი აბრუნებს საკუთარ შეცდომას (`429`, თუ სიხშირითაა შეზღუდული,
წინააღმდეგ შემთხვევაში — ზემდგომი სერვისის სტატუსს).

### Responses API WebSocket-ის მეშვეობით (მხოლოდ codex)

```bash
# იგივე ჰოსტი:პორტი, რასაც HTTP API იყენებს (ნაგულისხმევად 20128); განაახლეთ კავშირი:
```

Responses-API-over-WebSocket პროქსი დაკავშირებულია **ექსკლუზიურად `codex`-თან** (ChatGPT-ის
ბეკენდი). ის API-ის/მართვის პანელის იმავე პორტზე უსმენს მისამართებს `/v1/responses`,
`/responses` და `/api/v1/responses`. პირველი `response.create` ფრეიმის მიღებისას ის
ასრულებს ავთენტიფიკაციასა და მომზადებას შიდა `codex-responses-ws` ხიდის მეშვეობით, ირჩევს
codex OAuth კავშირს და `wreq-js` ტრანსპორტის მეშვეობით გვირაბს ქმნის `wss://chatgpt.com/backend-api/codex/responses`-მდე.
**არა-codex მოდელები უარყოფილია** (`codex_ws_provider_required`).
კვოტის განაწილებით მარშრუტიზაციისთვის გამოიყენეთ `model: "qtSd/<group>/codex/<model>"`. რეალიზებულია
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` ფაილებში.

**ავთენტიფიკაცია:** Bearer API გასაღები ხელის ჩამორთმევისას. ჩაშენებული HTTP სერვერი (`server-ws.mjs`)
აქტიური შესვლის წერტილი უნდა იყოს (ნაგულისხმევად ასეცაა, როდესაც `app/server-ws.mjs` არსებობს).

#### მოდელის ID: გამოიყენეთ ChatGPT-ის შიშველი ID (`codex/` პრეფიქსის გარეშე)

OpenAI **Codex CLI** ამოწმებს მოდელის სახელს კლიენტის მხარეს, როდესაც
`supports_websockets = true`, და **უარყოფს პროვაიდერის პრეფიქსის მქონე ID-ებს**, როგორიცაა
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). გაგზავნეთ **შიშველი** ID (მაგალითად, `gpt-5.5`). OmniRoute-ის ხიდი
მხოლოდ codex-ისთვისაა განკუთვნილი, ამიტომ ზემდგომ სერვისამდე გვირაბის შექმნამდე ის შიშველ ID-ს
ხელახლა განსაზღვრავს, როგორც codex მოდელს (`resolveCodexWsModelInfo`) — მიუხედავად იმისა, რომ შიშველი

## თვითმომსახურების გამოყენება (`/api/usage/om-usage`)

ნებისმიერ API გასაღებს შეუძლია ნახოს **საკუთარი** მოხმარება და კვოტები — მართვის ავთენტიფიკაცია საჭირო არ არის. ეს არის საბოლოო წერტილი, რომელსაც
კლიენტი (CLI, OmniCopilot-ის პანელი) იყენებს, რათა გასაღების მფლობელს აჩვენოს მისი დანახარჯი.

```bash
# ტექსტური ფორმა (ისტორიული კონტრაქტი — ჩვეულებრივი ტექსტი ტერმინალისთვის)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# სტრუქტურირებული ფორმა — რომელსაც UI მოიხმარს
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

გასაღებისთვის **`allowUsageCommand`** ჩართული უნდა იყოს (ნაგულისხმევად გამორთულია — დაფის API-გასაღებების
მენეჯერი მას თითოეული გასაღებისთვის ცალ-ცალკე გადართავს). მის გარეშე საბოლოო წერტილი პასუხობს `403`-ით.

`?format=json` აბრუნებს განმასხვავებელ სტრუქტურას, რათა გამომძახებელმა უარყოფის შემთხვევაში მონაცემთა ველი არასოდეს წაიკითხოს.
წარმატების შემთხვევაში:

```jsonc
{
  "allowed": true,
  // წარმოდგენილია მხოლოდ მაშინ, როდესაც გასაღებისთვის ჩართულია ინდივიდუალური მოხმარების ლიმიტები (დღიური/კვირეული USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // არჩეული პროვაიდერის კვოტის სურათი, ან null, თუ ჯერ არაფერია დაკეშილი:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // თითოეული კავშირის სურათი, რათა UI-მ რამდენიმე პროვაიდერი გვერდიგვერდ გამოსახოს:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

უარყოფის შემთხვევაში (`401` არასწორი გასაღები / `403` დაშვება არ არის) იგივე მარშრუტი აბრუნებს
`{ "allowed": false, "error": { "message": "…" } }`-ს — არსებული, მაგრამ ცარიელი `personal`/`provider`
(გასაღები დაშვებულია, თუმცა ჯერ არაფერია მიღებული) უარყოფისგან განსხვავებული მდგომარეობაა და მათ მხოლოდ JSON ფორმა
განასხვავებს.

**ავთენტიფიკაცია:** გამომძახებლის საკუთარი Bearer API გასაღები, რომელიც მოწმდება `isValidApiKey`-ით — ეს _არ არის_
მართვის ინტერფეისი (`/api/keys/…`), რომელიც კვლავ `requireManagementAuth`-ითაა დაცული.

`/api/usage/om-usage`-ის გამოყენებისას გამომძახებლებმა უნდა გაითვალისწინონ განსხვავება
**ჩვეულებრივ ტექსტურ გამომავალში** და სტრუქტურირებულ **JSON გამომავალში** წარმოდგენილ პროცენტებს შორის:

| ასპექტი                   | ჩვეულებრივი ტექსტის ფორმატი (`/api/usage/om-usage` / `@@om-usage`)                             | JSON ფორმატი (`?format=json`)                                                                 |

| **ძირითადი მომხმარებელი** | ინტერაქტიული CLI-ები, ტერმინალის მოთხოვნები, ოპერატორები                                       | პროგრამული ინტეგრაციები, დაფები, ანალიტიკა, ბილინგის ტრეკერები                                |

#### ზღვრულ მნიშვნელობაზე მორგების ფორმულა

OmniRoute-ს აქვს კვოტის პროაქტიული ზღვრული მნიშვნელობების მხარდაჭერა upstream-რესურსის ამოწურვის თავიდან ასაცილებლად (კონფიგურირდება კავშირის
`quotaWindowThresholds`-ის, პროვაიდერის ნაგულისხმევი მნიშვნელობების ან მდგრადობის გლობალური პარამეტრების მეშვეობით). როდესაც კვოტის ფანჯარაში
აქტიურია ზღვრული მნიშვნელობა (მაგ., `cutoff = 25%`), ტექსტის რენდერერი დარჩენილ მოცულობას შემდეგნაირად ითვლის:

- თუ `remaining <= cutoff`: აბრუნებს `0%`-ს.
- თუ `remaining > cutoff`: აბრუნებს `((remaining - cutoff) / (100 - cutoff)) * 100`-ს.

ფორმატირებული ტექსტური გამომავალი ამ მნიშვნელობას უახლოეს მთელ რიცხვამდე ამრგვალებს (`Math.round(...)`).

#### საილუსტრაციო მაგალითი

განვიხილოთ პროვაიდერის ფანჯარა **60% დაუმუშავებელი მოხმარებით** (შესაბამისად, **40% დაუმუშავებელი დარჩენილი კვოტით**) და კონფიგურირებული
**დარჩენილი კვოტის 25%-იანი ზღვრული მნიშვნელობით**:

| წარმოდგენა                              | გამოთვლა                                           | დარჩენილი |           ნაგულისხმევი მოხმარებული            |
| :-------------------------------------- | :------------------------------------------------- | :-------: | :-------------------------------------------: |
| **დაუმუშავებელი JSON (`?format=json`)** | Upstream-სურათი (`quotas[window]`)                 |  **40%**  |                    **60%**                    |
| **ტექსტური ფორმატი (`NN% left`)**       | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20%**  | **80%** (თუ ითვლება როგორც `100 - remaining`) |

- **რატომ აჩვენებს ტექსტი, რომ დარჩენილია 20%:** ანგარიშზე დარჩენილი ფიზიკური კვოტის 40%-დან 25% დაცულია
  ზღვრული მნიშვნელობის პოლიტიკით. გამომძახებელს როუტერის მიერ ამ კავშირისკენ მარშრუტიზაციის შეწყვეტამდე გამოსაყენებელი 75%-იანი მარაგიდან
  მხოლოდ 15% დარჩა. მასშტაბირება უზრუნველყოფს, რომ კავშირი ამოწურვას (`0% left`) ზუსტად მაშინ დააფიქსირებს, როდესაც
  მარშრუტიზაცია შეწყდება.
- **რატომ ინარჩუნებს JSON დაუმუშავებელ მნიშვნელობებს:** JSON-ის დატვირთვა აბრუნებს პროვაიდერის ზუსტ სურათს (`UsageSnapshot`),
  რათა გარე ხელსაწყოებს ჰქონდეთ წვდომა upstream-ის გამოყენების ფაქტობრივ მონაცემებსა და კავშირის დონის
  `quotaWindowThresholds`-ზე, სერვერის მხარეს ინფორმაციის დამკარგავი მასშტაბირების გარეშე.

#### მომხმარებლების მიგრაციის სახელმძღვანელო

თუ გარე ინტეგრაცია (მაგალითად, რედაქტორის დანამატი ან აგენტის გაფართოება) ადრე ტექსტური
endpoint-იდან (`NN% left`) იღებდა მონაცემებს და გამოყენებულ პროცენტს ითვლიდა როგორც `100 - NN`, `?format=json`-ზე გადასვლა ნიშნავს:

- დაუმუშავებელი JSON მნიშვნელობების წაკითხვა ასახავს **ზედა დონის წყაროს რეალურ მოხმარებას** (ზემოთ მოცემულ მაგალითში გამოყენებულია 60%).
- თუ ინტეგრაციას სურს შეინარჩუნოს ტექსტური endpoint-ის გამოსაყენებელი ლიმიტის სემანტიკა, მას შეუძლია
  დარჩენილი ეფექტური ოდენობის ფორმულა კლიენტის მხარეს გამოთვალოს, კავშირის დონის გადაფარვებისთვის `quotaWindowThresholds`-ის გამოყენებით.

```json
  }
}
```

გაგზავნეთ ეს სხეული `PUT /api/providers/<connection-id>`-ით. ამ კავშირზე `none` მნიშვნელობის მქონე
მსჯელობის აშკარად მითითებული ძალისხმევა იგზავნება როგორც `chat_template_kwargs.thinking=false` და
`chat_template_kwargs.enable_thinking=false`. შაბლონის აშკარად მითითებული ნატიური მნიშვნელობები კვლავ პრიორიტეტულია,
თუ სერვერის მხარეს არსებული მსჯელობის წესი ძალისხმევას იძულებით არ განსაზღვრავს. პარამეტრი გამოიყენება მხოლოდ მაშინ, როდესაც მორგებული,
OpenAI-თან თავსებადი კავშირი Chat Completions-ის სხეულს აგზავნის; Responses მოთხოვნები და ჩვეულებრივი
პროვაიდერები ინარჩუნებენ მოთხოვნის ნატიურ სტრუქტურას. OpenAI-ის ჩვეულებრივი `reasoning_effort` მნიშვნელობის
უცვლელად გადასაცემად `reasoningControl` დააყენეთ `openai`-ზე, ხოლო ავტომატური აღმოჩენის გამოსაყენებლად გამოტოვეთ იგი ან მიანიჭეთ `null`.

მსჯელობის აშკარად მითითებულ მართვის ელემენტებს არ შეიცავენ. აღმოჩენა იყენებს კლასიფიკატორის სისტემურ მარკერს Claude-ის ფორმატის

მხოლოდ loopback-იდან ხელმისაწვდომი მართვის მარშრუტი (ადმინისტრატორის ავტორიზაცია). აბრუნებს გაშვებულ ვერსიას, უახლეს გამოქვეყნებულ ვერსიასა და ავტომატური განახლების სტატუსს. `releaseChannel` და `channels` დამატებითი ველებია (rail 3.8.54); `channel` ინარჩუნებს თავის მნიშვნელობას — გაშვების რეჟიმს, რომელსაც მართვის პანელის განახლების კომპონენტი იყენებს (`npm`, `source` ან `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — გაშვებული build-ის npm არხი: `nightly` — `-nightly.*` ვერსიებისთვის, `next` — სხვა წინასწარი გამოშვებებისთვის (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` — `channels.latest`-ზე უფრო ძველი ძირითადი ვერსიის სტაბილური ვერსიისთვის, ყველა სხვა შემთხვევაში — `latest`. იგივე წესებს იყენებს `scripts/release/dist-tag.mjs`, რომელიც გამოქვეყნების დროს npm dist-tag-ს ირჩევს.
- `channels` — თითოეული dist-tag-ის უახლესი გამოქვეყნებული ვერსია, მიღებული `npm view omniroute dist-tags`-იდან (registry HTTP-ის სარეზერვო ვარიანტით), რომელიც `latest`-ის მსგავსად იგივე 10-წუთიანი TTL-ით კეშირდება. `latest` ყოველთვის არსებობს (სარეზერვოდ იყენებს `latest` ველს, შემდეგ კი `"unavailable"`-ს); `next`, `nightly` და `lts` მხოლოდ მაშინ ჩნდება, როდესაც შესაბამისი dist-tag არსებობს. `Cache-Control: no-cache` მოთხოვნა ორივე მოძიების შედეგს განაახლებს.

არხების მოდელი (`latest` = v3 4.0 GA-მდე, `next` = rc, `nightly` = `develop` build-ები, `lts` = v3-ის პატჩები 4.0 GA-ის შემდეგ) აღწერილია `docs/ops/RELEASE_STRATEGY.md`-ში.

```bash
# ყველა API გასაღების ბიუჯეტის სტატუსის მიღება
```

## ტოკენების ლიმიტები

თითოეული API გასაღებისთვის განსაზღვრული **ტოკენების** ბიუჯეტები (განსხვავდება ზემოთ მოცემული USD-ზე დაფუძნებული ბიუჯეტისგან). ისინი უშუალოდ მოთხოვნის დამუშავების გზაზე კონტროლდება: როდესაც გასაღების მიმდინარე დროის ფანჯარაში გამოყენებული ტოკენების რაოდენობა ლიმიტს მიაღწევს, მოთხოვნები უარყოფილი იქნება პასუხით `429 Too Many Requests`. ლიმიტები შეიძლება ვრცელდებოდეს კონკრეტულ `model`-ზე, `provider`-ზე ან გასაღების მასშტაბით `global`ურად მოქმედებდეს; თუ მოთხოვნას რამდენიმე ლიმიტი შეესაბამება, უპირატესობა ყველაზე მკაცრ ლიმიტს ენიჭება.

```bash
# გასაღების ტოკენების ლიმიტების სიის მიღება (მოიცავს მიმდინარე დროის ფანჯარაში გამოყენებას)
GET /api/usage/token-limits?apiKeyId=key-123

# ტოკენების ლიმიტის შექმნა ან განახლება
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# ტოკენების ლიმიტის წაშლა id-ის მიხედვით
DELETE /api/usage/token-limits?id=tl-abc
```

> **სქემის შენიშვნები** (`setTokenLimitSchema`): `apiKeyId` და `scopeType` (`model` | `provider` | `global`) სავალდებულოა. `scopeValue` სავალდებულოა, გარდა იმ შემთხვევისა, როდესაც `scopeType` არის `global` (მაგ., მოდელის id `model` მოქმედების არეალისთვის, პროვაიდერის id კი `provider` მოქმედების არეალისთვის). `tokenLimit` უნდა იყოს დადებითი მთელი რიცხვი (სტრიქონიდან გარდაიქმნება). არასავალდებულო ველები: `id` (შექმნისას გამოტოვეთ, განახლებისას მიუთითეთ), `resetInterval` (`daily` | `weekly` | `monthly`, ნაგულისხმევი მნიშვნელობაა `monthly`), `resetTime` (`HH:MM`), `enabled` (ნაგულისხმევი მნიშვნელობაა `true`). `GET` პასუხებში თითოეულ ლიმიტს ემატება `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` და `nextResetAt`. ეს არის მართვის კლასის endpoint (ავთენტიფიკაცია ცენტრალიზებულად კონტროლდება ავტორიზაციის pipeline-ის მიერ).

## მოთხოვნის დამუშავება

1. კლიენტი მოთხოვნას აგზავნის `/v1/*`-ზე
2. მარშრუტის დამმუშავებელი იძახებს `handleChat`, `handleEmbedding`, `handleAudioTranscription` ან `handleImageGeneration` ფუნქციას
3. განისაზღვრება მოდელი (პირდაპირი provider/model ან alias/combo)
4. ავტორიზაციის მონაცემები ირჩევა ლოკალური DB-დან ანგარიშის ხელმისაწვდომობის გაფილტვრით
5. ჩატისთვის: `handleChatCore` ამოწმებს სემანტიკურ/ხელმოწერის ქეშს და განსაზღვრავს combo-ს შეკუმშვის პარამეტრებს
6. ჩართული ფუნქციის შემთხვევაში, პროვაიდერის ფორმატში გარდაქმნამდე პროაქტიული შეკუმშვა სრულდება (`lite`, Caveman, RTK ან კომბინირებული)
7. პროვაიდერის შემსრულებელი upstream მოთხოვნას აგზავნის
8. პასუხი გარდაიქმნება კლიენტის ფორმატში (ჩატი) ან უცვლელად ბრუნდება (embeddings/images/audio)
9. გამოყენება, შეკუმშვის ანალიტიკა და მოთხოვნების ჟურნალები აღირიცხება
10. შეცდომების შემთხვევაში combo-ს წესების შესაბამისად გამოიყენება სარეზერვო ვარიანტი

არქიტექტურის სრული აღწერა: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## მდგრადობა (გაფართოებული)

OmniRoute უზრუნველყოფს დროებითი შეფერხებების მართვის სამ დამოუკიდებელ მექანიზმს; ქვემოთ მოცემული მართვის საბოლოო წერტილები ოპერატორებს მათი მდგომარეობის წაკითხვისა და პარამეტრების გადაწერის საშუალებას აძლევს:

| მოქმედების არეალი       | მდგომარეობის საცავი                                       | წაკითხვა                                  | ჩამოყრა / გასუფთავება                                             |
| ----------------------- | --------------------------------------------------------- | ----------------------------------------- | ----------------------------------------------------------------- |
| პროვაიდერის ამომრთველი  | `domain_circuit_breakers` + ოპერატიულ მეხსიერებაში        | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                      |
| კავშირის მოცდის პერიოდი | `rateLimitedUntil` პროვაიდერის კავშირებზე                 | `/api/rate-limits`, `/api/providers/[id]` | (ხელახლა აქტიურდება საჭიროებისას; გაასუფთავეთ პროვაიდერის PUT-ით) |

`PATCH /api/resilience` იღებს პროვაიდერის ამომრთველის გადამწერ პარამეტრებს `providerBreaker.oauth`-ისა და `providerBreaker.apikey`-ის ქვეშ. თითოეულ პროფილს აქვს `degradationThreshold`, `failureThreshold` და `resetTimeoutMs` პარამეტრების მხარდაჭერა; იგივე ველები ხელმისაწვდომია Dashboard → Settings → Resilience-ში.

```bash
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# ყველა დაბლოკვის წაშლა
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \

  -d '{"all":true}'
```

სრული კონცეპტუალური ცნობარისა და ამომრთველის ნაგულისხმევი პარამეტრებისთვის იხილეთ [`CLAUDE.md`](../../CLAUDE.md) → „მდგრადობის შესრულების დროის მდგომარეობა“ და [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### სიჩქარის შეზღუდვის რიგი და ავტომატური ჩართვის დამცავი მექანიზმი

- **მხარდაჭერილი ჩაწერის გზა**: `POST /api/rate-limits`, სხეულით `{"connectionId": "<id>", "enabled": true|false}`, არის მხარდაჭერილი მართვის საბოლოო წერტილი კავშირისთვის სიჩქარის შეზღუდვის დაცვის ჩასართავად ან გამოსართავად. `PUT /api/providers/[id]` განზრახ არ ცვლის და არ გადართავს `rateLimitProtection`-ს (#11278).
- **`enabled: false`-ის სემანტიკა**: `enabled: false`-ის დაყენება კავშირისთვის ცალსახად მითითებულ დაცვას შლის, თუმცა **არ** გამორიცხავს აქტიურ API-გასაღების კავშირს გლობალური ავტომატური ჩართვის დამცავი მექანიზმიდან (`autoEnableApiKeyProviders = true`). `reconcileEnabledConnections`-ში (`open-sse/services/rateLimitManager.ts`) `false` და `undefined` ეკვივალენტურია; აქტიური API-გასაღების კავშირები, რომლებსაც ცალსახად მითითებული დაცვა არ აქვთ, ავტომატური ჩართვის დამცავი მექანიზმით კვლავ დაცული რჩება.
- **გლობალური გამორთვა**: API-გასაღების კავშირების სიჩქარის შეზღუდვის რიგების გარეშე გამოსაყენებლად დამცავი მექანიზმი გლობალურად გამორთეთ `RATE_LIMIT_AUTO_ENABLE=false`-ის (გარემოს ცვლადი) ან `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false`-ის მეშვეობით (Settings → Resilience / `PATCH /api/resilience`).

## MCP სერვერი

OmniRoute მოიცავს ჩაშენებულ Model Context Protocol სერვერს 3 ტრანსპორტით (stdio, SSE, streamable-http) და მოქმედების არეებით შეზღუდული ხელსაწყოებით. ქვემოთ მოცემული დაფის ენდფოინთები კითხულობს სტატუსის/აუდიტის მონაცემებს და HTTP ტრანსპორტებს პროქსირებს.

| მეთოდი | გზა | აღწერა |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | პულსი, ტრანსპორტი, ონლაინ-მდგომარეობა, ბოლო გამოძახება, ყველაზე ხშირად გამოყენებული ხელსაწყოები, წარმატების მაჩვენებელი ბოლო 24 საათში |
| GET | `/api/mcp/tools` | MCP ხელსაწყოების სია ველებით `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` |
| GET | `/api/mcp/sse` | SSE ტრანსპორტისთვის SSE ნაკადის გახსნა (აბრუნებს `503`-ს, თუ MCP გამორთულია ან ტრანსპორტი არ ემთხვევა) |
| POST | `/api/mcp/sse` | JSON-RPC ჩარჩოს გაგზავნა SSE ტრანსპორტზე |

| POST | `/api/mcp/stream` | JSON-RPC ჩარჩოს გაგზავნა Streamable HTTP ტრანსპორტზე |
| DELETE | `/api/mcp/stream` | Streamable HTTP სესიის დასრულება |

| GET | `/api/mcp/audit/stats` | აუდიტის აგრეგირებული სტატისტიკა (ჯამური მაჩვენებლები, წარმატების მაჩვენებელი, საშუალო ხანგრძლივობა, ყველაზე ხშირად გამოყენებული ხელსაწყოები) |

## A2A სერვერი

OmniRoute ხელმისაწვდომს ხდის A2A (Agent-to-Agent) JSON-RPC 2.0 საბოლოო წერტილს და ასევე REST გარსს ინსპექტირებისა და მართვის პანელში გამოყენებისთვის.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # არასავალდებულოა, თუ OMNIROUTE_API_KEY არ არის დაყენებული
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

მხარდაჭერილი მეთოდები (ყველა დამოკიდებულია `settings.a2aEnabled`-ზე):

| მეთოდი           | აღწერა                                                                |
| ---------------- | --------------------------------------------------------------------- |
| `message/send`   | უნარის სინქრონული შესრულება; აბრუნებს `{task, artifacts, metadata}`-ს |
| `message/stream` | იმავე უნარების ნაკრების ნაკადური SSE შესრულება                        |
| `tasks/get`      | დავალების მიღება `taskId`-ის მიხედვით                                 |
| `tasks/cancel`   | დავალების გაუქმება `taskId`-ის მიხედვით                               |

ჩაშენებული უნარები: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### აგენტის ბარათი

```bash
GET /.well-known/agent.json
```

აბრუნებს საჯარო A2A აგენტის ბარათს (სახელი, აღწერა, შესაძლებლობები, უნარების კატალოგი, ავტორიზაციის სქემა) — საჯაროდ კეშირდება 1 საათით. ავტორიზაცია საჭირო არ არის.

### REST დამხმარე მარშრუტები

| მეთოდი | გზა                          | აღწერა                                                                                                               |
| ------ | ---------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/a2a/status`            | A2A-ს ჩართულობის სტატუსი + დავალებების სტატისტიკა + კეშირებული აგენტის ბარათის შეჯამება                              |
| GET    | `/api/a2a/tasks`             | დავალებების სია — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (არ არის იმპლემენტირებული REST დამხმარე მარშრუტის სახით — შექმენით JSON-RPC `message/send`-ის მეშვეობით)             |
| GET    | `/api/a2a/tasks/[id]`        | ერთი დავალების მიღება                                                                                                |
| POST   | `/api/a2a/tasks/[id]/cancel` | დავალების გაუქმება                                                                                                   |

**ავტორიზაცია:** REST დამხმარე მარშრუტები მუშაობს მართვის ავტორიზაციის გარეშე (მართვის პანელიდან წაკითხვადია); JSON-RPC `/a2a` მარშრუტი, კონფიგურაციის შემთხვევაში, იყენებს Bearer `OMNIROUTE_API_KEY`-ს.

## ავთენტიფიკაცია

ავტორიზაციის მონაცემების ოთხი ტიპის (მართვის პანელის სესია, ლოკალური CLI ტოკენი, `oma_live_…` წვდომის ტოკენი, მართვის უფლებების მქონე API გასაღები) და დასკვნის გამოტანის გასაღებებისგან მათი განსხვავებების შესახებ იხილეთ [მართვის ავთენტიფიკაცია](../guides/MANAGEMENT-AUTH.md).

- მართვის პანელის მარშრუტები (`/dashboard/*`) იყენებს `auth_token` cookie-ს
- შესვლისას გამოიყენება შენახული პაროლის ჰეში; სარეზერვო ვარიანტია `INITIAL_PASSWORD`
- `requireLogin`-ის გადართვა შესაძლებელია `/api/settings/require-login`-ის მეშვეობით
- `/v1/*` მარშრუტებმა შეიძლება მოითხოვოს Bearer API გასაღები, როდესაც `REQUIRE_API_KEY=true`
- ამ ცნობარში „მართვის ტოკენი“ / „მართვის უფლებების მქონე API გასაღები“ ნიშნავს აღნიშნულ სახელმძღვანელოში აღწერილ ერთ-ერთ ტიპს და არა დამატებითი საიდუმლოს განუსაზღვრელ ტიპს

> **უკუთავსებადობის დამრღვევი ცვლილება (v3.8.0)** — `/api/v1/agents/tasks/*` და დაყოვნების პერიოდის მართვის საბოლოო წერტილები ახლა მოითხოვს **მართვის ავთენტიფიკაციას** (მართვის პანელის `auth_token` cookie ან მართვის უფლებების მქონე API გასაღები). კლიენტები, რომლებიც ადრე ამ მარშრუტებს ავთენტიფიკაციის გარეშე იძახებდნენ, მიიღებენ პასუხს `401 Unauthorized`. იხილეთ კომიტი `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
