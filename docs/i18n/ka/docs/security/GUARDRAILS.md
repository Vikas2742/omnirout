დამცავი მექანიზმები უზრუნველყოფენ უსაფრთხოებას, პოლიტიკების დაცვასა და შიგთავსის გარდაქმნას OmniRoute-სა
და ზედა დონის პროვაიდერებს შორის საზღვარზე. თითოეულ დამცავ მექანიზმს შეუძლია შეამოწმოს (და
სურვილისამებრ უარყოს, გარდაქმნას ან ანოტაცია დაურთოს) მოთხოვნის სასარგებლო დატვირთვას (`preCall`) და
ზედა დონის პასუხებს (`postCall`).

სისტემა **შეცდომისას ღიაა**: თუ დამცავი მექანიზმი შესრულებისას გამონაკლისს გამოიწვევს, რეესტრი
აღრიცხავს შეცდომას და მოთხოვნის წარუმატებლად დასრულების ნაცვლად შემდეგ დამცავ მექანიზმზე
გადადის. ბლოკირება ყოველთვის მკაფიო გადაწყვეტილებაა (`block: true`) და არასოდეს — შემთხვევითობა.
ერთადერთი გამონაკლისია გაუქმებული მოთხოვნა: როდესაც გამომძახებლის `signal` გაუქმებულია,
გამონაკლისის გამომწვევი დამცავი მექანიზმი ჰუკის შესრულებას უარყოფს და არ გამოიტოვება.

ჰუკები **არ** სრულდება ყველა მარშრუტზე ან ყველა პასუხისთვის. სანამ დამცავ მექანიზმს
უსაფრთხოების კონტროლის საშუალებად დაეყრდნობით, წაიკითხეთ
[დაფარვა და შეზღუდვები](#coverage-and-limits).

### გამოსახულების ხიდი (`visionBridge.ts`) — მოდალობის ხიდი PR-1

GLM 5.3-ის საბაზისო მოდელსა და `glm-5.3-{low,high,max}`-ს რეესტრის/სპეციფიკაციის მკაფიო
`supportsVision:false` მეტამონაცემები აქვს. GLM 5.3 Flash-ის ვარიანტები
კვლავ გამოსახულების მხარდაჭერის მქონე ნატიური მოდელებია. Claude Code-ის `/v1/messages` მარშრუტი
საერთო `handleChat`-ის გამოძახებამდელი დამცავი მექანიზმების ჯაჭვში შედის **მანამდე**, სანამ Claude-დან OpenAI-ზე
გარდაქმნა მოხდება; `Read` ხელსაწყოს შედეგებში ჩადგმული გამოსახულებები უნდა აღიწეროს ან დამუშავდეს
მანამდე, სანამ ეს გარდაქმნა მათ OpenAI-ის `image_url` შიგთავსად გადაიტანს (#17069).

გამოავლენს **გამოსახულების მხარდაჭერის არმქონე მოდელებისკენ** მიმართულ, გამოსახულების შემცველ მოთხოვნებს და ან
მთელ მოთხოვნას გადაამისამართებს გამოსახულების მხარდაჭერის მქონე მოდელზე, ან ზედა დონის გამოძახებამდე
გამოსახულების ნაწილებს ჩაანაცვლებს კონფიგურირებადი გამოსახულების მოდელის მიერ შექმნილი ტექსტური
აღწერებით. ეს მხოლოდ ტექსტზე მომუშავე პროვაიდერებს მულტიმოდალური სასარგებლო დატვირთვების გამჭვირვალედ
დამუშავების საშუალებას აძლევს.

პროცესი:

1. გამოტოვება, თუ სამიზნე მოდელს უკვე აქვს გამოსახულების მხარდაჭერა (გარდა იმ შემთხვევისა, როდესაც ის
   იძულებითი ხიდის სიაში `isVisionBridgeForcedModel` გვხვდება).
2. გამოსახულების ნაწილების ამოღება `extractImageParts(messages)`-ის მეშვეობით
   (`visionBridgeHelpers.ts`), რომელიც დელეგირებას ახდენს **მედიის ერთიან
   დეტექტორზე** `detectMediaParts()` ფაილში `open-sse/utils/mediaParts.ts` — ეს არის
   ჭეშმარიტების ერთადერთი წყარო, რომელიც კომბინირებული თავსებადობის ფილტრთან საზიაროა.
   ამოღება დაშვებული ფორმების სიით შემოიფარგლება, რომელთა უკან ჩასმაც `replaceImageParts`-ს შეუძლია
   (ამოღება↔ჩანაცვლების კონტრაქტი): OpenAI `image_url`, Anthropic base64
   `source.type:"base64"`, Anthropic URL `source.type:"url"` და Responses
   API `input_image`. Claude Code-ის `tool_result.content`-ში და Responses-ის ხელსაწყოების
   შედეგებში ჩადგმული შესატყვისი გამოსახულებებიც ამოიღება და თავდაპირველ ბილიკებზე
   ჩანაცვლდება; მხოლოდ ინდიკატორის შემცველი ფორმები კომბინირებული ფილტრის მასალაა
   და არ ამოიღება.
   გამოტოვება, თუ არცერთი არ მოიძებნა.
3. შესრულების დროის კონფიგურაციის განსაზღვრა `resolveVisionBridgeRuntimeSettings()`-ის მეშვეობით
   (`src/shared/constants/modalityBridgeDefaults.ts`): ახალ `modalityBridge*`
   პარამეტრების გასაღებებს უპირატესობა ენიჭება; ძველი `visionBridge*` გასაღებები რჩება **ერთი ციკლის
   სარეზერვო ვარიანტად** (უკან დაბრუნების ფანჯარა). თუ ხიდი გამორთულია, გამოტოვება ხდება მედიის ნებისმიერ
   დამუშავებამდე.
4. რეჟიმის ამრჩევი (`modalityBridgeVisionMode`, იხილეთ ქვემოთ მოცემული ცხრილი) გადაწყვეტს,
   მოხდეს გადამისამართება თუ აღწერა. გადამისამართება აბრუნებს `modifiedPayload`-ს, რომელშიც მხოლოდ `model`
   არის შეცვლილი, ასევე მეტამონაცემებს `{ rerouted, fromModel, toModel, imagesKept }`.
5. აღწერის გზა: გამოსახულებების რაოდენობის შეზღუდვა `maxImages`-ით, ამოცანის შესაბამისი მოთხოვნის შედგენა,
   აღწერების კეშის შემოწმება, გამოსახულების მოდელის **პარალელურად** გამოძახება
   (`Promise.allSettled`) და მათ ადგილას `[Image N]: <description>` ტექსტური ნაწილების
   ჩასმა. წარუმატებელი აღწერა იძლევა `null`-ს: უცნობი/გამოსახულების მხარდაჭერის მქონე
   სამიზნეებისთვის დაუმუშავებელი გამოსახულება შენარჩუნდება (#4012), თუმცა **დადასტურებული მხოლოდ ტექსტზე მომუშავე პირდაპირი
   სამიზნე** ან გამოსახულების ნულოვანი მხარდაჭერის მქონე კომბინაცია მიიღებს მკაფიო
   `(unavailable — no vision-capable provider connected)` ტექსტურ ჩამნაცვლებელს
   ყველა აღუწერელი გამოსახულებისთვის, მათ შორის ნაწილობრივი წარუმატებლობებისა და აღწერის გამოძახებების
   ლიმიტს მიღმა დარჩენილი გამოსახულებებისთვის (#17069). არსებული, კომბინაციის ყველა აღწერის წარუმატებლობის
   სარეზერვო მექანიზმი კვლავ შენარჩუნებულია (#8430).
6. `modifiedPayload`-ისა და მეტამონაცემების (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) დაბრუნება.

#### API გასაღების ფარგლები (`visionBridgeKeyScope.ts`)

როდესაც გამომძახებლის API გასაღები ზღუდავს `allowedConnections`-ს, კვოტების ჯგუფებს
(`allowedQuotas`) ან მოდელებს (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), ხიდი გადამისამართებისა და
აღწერისთვის ირჩევს მხოლოდ იმ მოდელებს, რომელთა გამოყენებაც გასაღებს შეუძლია, და მხოლოდ იმ კავშირებზე,
რომელთა გამოყენებაც გასაღებს შეუძლია. შემდეგ აღწერის გამოძახება ყოველთვის გადის OmniRoute-ის საკუთარ მარყუჟში
`x-omniroute-self-loop-key-id` სათაურით, რათა მიმღებმა ჩატის მოთხოვნამ
კვლავ აღასრულოს ამ გასაღების კავშირებისა და მოდელების პოლიტიკა. `enforceApiKeyPolicy()`
ამ სათაურს ითვალისწინებს მხოლოდ საკუთარი მარყუჟის bearer-თან ერთად, ამიტომ მას მხოლოდ
წვდომის შეზღუდვა შეუძლია, ხოლო იდენტიფიკატორი, რომლის ამოცნობაც ვერ ხერხდება, უარყოფილია.

თუ გასაღებისთვის არცერთი ხედვის მოდელი არ არის ნებადართული, **დადასტურებული მხოლოდ ტექსტის
სამიზნე** სურათის მოთხოვნას ადგილობრივად უარყოფს მკაფიო HTTP 400 პასუხით, ნაცვლად იმისა,
რომ სურათის ბაიტები მათი დამუშავების არშემძლე upstream-ს გადაუგზავნოს (#17069). უცნობი ან
ნატიური ხედვის შესაძლებლობის მქონე სამიზნეებისთვის აღწერის გზა ინარჩუნებს წინა
fail-open ქცევას (მეტამონაცემები `{ skipped: true, reason: "no_permitted_vision_model" }`).
მოთხოვნები გასაღების გარეშე და გასაღებები ამ შეზღუდვების გარეშე ზუსტად ისე იქცევა, როგორც
ადრე.

#### დავალების გათვალისწინებით შედგენილი აღწერის მოთხოვნა (`modalityBridgeVisionTaskAware`)

ნაგულისხმევად **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) საბაზისო
აღწერის მოთხოვნას ამატებს **მომხმარებლის ბოლო შეტყობინების** ტექსტს (შემოკლებულს 500 სიმბოლომდე),
რათა აღწერა მიმართული იყოს იმისკენ, რაც მომხმარებელმა რეალურად მოითხოვა
(codex-vision-proxy-ის ნიმუში), და ხედვის მოდელს ხილული ტექსტის ტრანსკრიფციას სთხოვს.
როდესაც ალამი გამორთულია — ან მომხმარებლის ტექსტი არ არსებობს — საბაზისო მოთხოვნა
უცვლელად გამოიყენება.

აღწერის საკუთარი მარყუჟის OpenAI-სთან თავსებადი მოთხოვნა (`callVisionModelSingle()`
ფაილში `visionBridgeHelpers.ts`) ყოველთვის ითხოვს `image_url.detail: "high"`-ს —
უპირობოდ, ყველა გამომძახებლისა და პროვაიდერისთვის, კლიენტის არცერთ სიგნალზე დამოკიდებულების
გარეშე. დაბალი დეტალიზაციის სემპლინგი OCR-ის სიზუსტეს აუარესებს ზუსტად იმ ტექსტის
ტრანსკრიფციის დავალებისთვის, რომელსაც ეს მოთხოვნა ითხოვს, ამიტომ თავად აღწერის გამოძახება
ყოველთვის ითხოვს მაღალ დეტალიზაციას, მიუხედავად იმისა, თუ დეტალიზაციის რომელი დონე გამოიყენა
თავდაპირველმა შემომავალმა მოთხოვნამ. ეს გავლენას ახდენს მხოლოდ აღწერის შიდა მოთხოვნის სხეულზე;
ის არ ცვლის იმას, თუ როგორ გადაამისამართებს OmniRoute გამომძახებლის საკუთარ
`image_url.detail`-ს ძირითად მოთხოვნაში — ეს ნაგულისხმევი მნიშვნელობა ცალკე გამოიყენება და
მხოლოდ აღმოჩენილი OpenCode კლიენტებისთვის, `defaultImageDetail()`-ში
(`open-sse/handlers/chatCore/upstreamBody.ts`). აღწერის საკუთარი მარყუჟის Anthropic-ის
wire-format განშტოებას `detail` ველი არ აქვს და მასზე არცერთი ნაგულისხმევი მნიშვნელობა არ
მოქმედებს.

#### აღწერის გამომავალი მონაცემების ზღვარი (`modalityBridgeVisionMaxChars`)

| გასაღები                       | ნაგულისხმევი | დიაპაზონი        |
| ------------------------------ | ------------ | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`          | `0` ან 100–50000 |

`0` (ნაგულისხმევი) ნიშნავს, რომ **ზღვარი არ არსებობს** — `callVisionModel()`-ის მიერ
დაბრუნებული აღწერა უცვლელად გადაიცემა, რაც არსებულ ქცევას ინარჩუნებს.
100–50000 დიაპაზონის ნებისმიერი მნიშვნელობა აღწერას ამოკლებს და ბოლოში `…`-ს
ამატებს, სანამ ის უკან ჩაისმება ფორმატით `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` ფაილში `src/lib/guardrails/visionBridge.ts`).
გაზარდეთ ეს მნიშვნელობა დეტალებით დატვირთული OCR დავალებებისთვის, სადაც ქვედა დონის
მოდელს სრული ტრანსკრიფცია სჭირდება; შეამცირეთ ის მრავალსიტყვიანი ხედვის მოდელების მიერ
ტოკენების გამოყენების შესაზღუდად. საინფორმაციო პანელის ველი მდებარეობს Vision ჩანართის
Advanced პანელზე (`modality-bridge-max-chars` ფაილში `ModalityBridgeVisionTab.tsx`) და
1-დან 99-მდე ნებისმიერ მნიშვნელობას მინიმალურ ზღვრამდე, 100-მდე, ზრდის, ხოლო აშკარად
მითითებულ `0`-ს უცვლელად ტოვებს — `0` თავისთავად დასაშვები Zod მნიშვნელობაა
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`) და არა მხოლოდ
„მიუთითებელი“ ნაგულისხმევი მნიშვნელობა.

#### აღწერის ქეში (`modalityBridge/bridgeCache.ts`)

მეხსიერებაში შენახული LRU + TTL ქეში აღწერის შედეგებისთვის, რომელიც საერთო პროცესის
მასშტაბით არის გაზიარებული. გასაღები = `sha256(imageRef + composedPrompt + configuredBridgeModel)`
სიგრძის პრეფიქსით ჩარჩოების შექმნით (ველების საზღვრების შეჯახებების გარეშე). მოდელის კომპონენტია
**კონფიგურირებული** ხიდის მოდელი და არა მოდელი, რომელმაც რეალურად უპასუხა —
`callVisionModel`-მა შეიძლება შიდა fallback გამოიყენოს, ხოლო თითოეული მცდელობის მიხედვით
გასაღების შექმნა ქეშს დაანაწევრებდა. წარუმატებელი აღწერები არასოდეს ქეშირდება. პარამეტრები:

| გასაღები                        | ნაგულისხმევი | დიაპაზონი |
| ------------------------------- | ------------ | --------- |
| `modalityBridgeCacheEnabled`    | `true`       | —         |
| `modalityBridgeCacheTtlMinutes` | `60`         | 1–1440    |
| `modalityBridgeCacheMaxEntries` | `200`        | 10–5000   |

#### დისტანციური სურათების ნორმალიზაცია (self-loop აღწერა/base64 მიღება)

როდესაც ხიდი **დისტანციურ** სურათს თავად იღებს — Anthropic-ის აღწერის
self-call და claude-wire-format-ის base64 კონვერტაცია
(`ensureBase64ImagesForClaudeWire`), ორივე
`visionBridgeHelpers.ts`-ში არსებული `fetchRemoteImageAsDataUri()`-ის მეშვეობით — მიღებული მონაცემების
URI გადის `normalizeDataUri()`-ში
(`open-sse/utils/imageNormalize.ts`), სანამ vision-მოდელის მოთხოვნაში ჩაშენდება.
ზედმეტად დიდი სურათების ზომა მცირდება **2048px სიგრძის კიდემდე** (რაც
ემთხვევა ზომის შეზღუდვას, რომელსაც OpenAI/Anthropic უკვე იყენებენ სერვერის მხარეს), რითაც
მცირდება ატვირთული ბაიტების რაოდენობა/დაყოვნება ისე, რომ არ იცვლება ის, რასაც vision-მოდელი ხედავს. ზომის შეცვლა
იყენებს `sharp`-ს, რომელიც დინამიკური იმპორტით იტვირთება: პლატფორმაზე, სადაც მისი ნატიური
ბინარული ფაილის ჩატვირთვა ვერ ხერხდება, `normalizeDataUri()` **არასოდეს აგდებს გამონაკლისს** — ის
უბრუნდება თავდაპირველი ბაიტების უცვლელად გატარებას, რათა აღწერის/base64-კონვერტაციის
გზამ ყოველთვის განაგრძოს მუშაობა. არასაიმიჯო ბაიტებიც (მიღებული მონაცემები, რომლებიც
დეკოდირებად სურათს არ შეიცავს) უცვლელად გადაიცემა. ეს ნორმალიზაცია
ვრცელდება მხოლოდ იმ სურათებზე, რომლებსაც ხიდი საკუთარი self-call-ისთვის იღებს — ის არასოდეს
გამოიყენება გამომძახებლის დაუმუშავებელ, უცვლელად გადასაცემ payload-ზე, რაც შეესაბამება
მხოლოდ მკაფიო თანხმობით ცვლილების პრინციპს (მკაცრი წესი #20).

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

აუდიოს შემცველ ჩატის მოთხოვნებს იჭერს მანამდე, სანამ ისინი ისეთ სამიზნემდე მიაღწევს, რომლის
მიერ აუდიოშეყვანის მიღება დადასტურებული არ არის. ის ჩატის მოთხოვნას არასოდეს გადაამისამართებს: აუდიონაწილები
ტრანსკრიბირდება არსებული OpenAI-თავსებადი multipart endpoint-ის მეშვეობით, ხოლო
არჩეული ჩატის მოდელი მუშაობას ტექსტური ტრანსკრიპტებით აგრძელებს.

ნაკადი:

1. `supportsAudio` განსაზღვრეთ `getResolvedModelCapabilities()`-ის მეშვეობით. უპირატესობა ენიჭება provider-registry-ის ცალსახად მითითებულ მეტამონაცემებს, შემდეგ — მოდელის სტატიკურ მეტამონაცემებს, ბოლოს კი — სინქრონიზებულ `modalities_input`-ს. თუ გამოცხადებული შეყვანის სია `audio`-ს არ შეიცავს, მნიშვნელობაა `false`; თუ შესაძლებლობის დამადასტურებელი მონაცემები არ არსებობს, მნიშვნელობაა `null`. როგორც `false`, ისე `null` ააქტიურებს კონსერვატიულ ხიდს, ხოლო `true` მას გვერდს უვლის.
2. განსაზღვრეთ `modalityBridgeAudio*` პარამეტრები და საერთო `detectMediaParts()` დეტექტორის მეშვეობით თითოეული შეტყობინებიდან ამოიღეთ ზედა დონის აუდიონაწილები, რომელთა ჩანაცვლებაც შესაძლებელია. მხარდაჭერილი გადაცემის ფორმატებია OpenAI-ის `input_audio`, `audio_url` და `source.media_type: "audio/*"`. ჩადგმული აუდიო მარშრუტიზაციისთვის აღმოჩენილია, თუმცა ჩანაცვლების გზით არ იშლება. სამუშაოს ზღვარი განისაზღვრება `modalityBridgeAudioMaxClips`-ით; შემდგომი ნაწილები უცვლელი რჩება.
3. გამოიყენეთ კონფიგურირებული `provider/model`, ან მიეცით `selectAudioBridgeModel()`-ს საშუალება, სტაბილური კატალოგის თანმიმდევრობით გაიაროს `AUDIO_TRANSCRIPTION_PROVIDERS` და აირჩიოს პირველი მოდელი, რომლისთვისაც ხელმისაწვდომია აქტიური პროვაიდერის გამოსაყენებელი ავტორიზაციის მონაცემები.
4. `callAudioTranscription()` base64/data-URI აუდიოს გარდაქმნის multipart `file`-ად, ან ჩამოტვირთავს დისტანციურ `audio_url`-ს მხოლოდ საჯარო მისამართებისთვის განკუთვნილი გამავალი მოთხოვნების დამცავი მექანიზმის მეშვეობით, DNS-ის ფიქსაციითა და 25 MB-იანი შეზღუდვით. შემდეგ ის ფაილსა და არჩეულ მოდელს POST-მოთხოვნით აგზავნის ლოკალურ `/v1/audio/transcriptions` თვითმარყუჟში, `resolveSelfLoopBearer()`-ით ავტორიზაციის გამოყენებით. ტრანსკრიფციის არსებული მარშრუტი ასრულებს ავტორიზაციის მონაცემების ჩვეულებრივ მოძიებას, დაყოვნების/სიხშირის შეზღუდვის დამუშავებასა და პროვაიდერთან გადამისამართებას.
5. წარმატებული გამოძახებები შესაბამის ნაწილებს ანაცვლებს `[Audio N]: <transcript>`-ით. გამოძახებები სრულდება `Promise.allSettled`-ის გამოყენებით: ცალკეული წარუმატებლობის შემთხვევაში თავდაპირველი აუდიონაწილი შენარჩუნდება (#4012 კონტრაქტი). თუ ყველა გამოძახება წარუმატებელია და დადასტურებულია, რომ სამიზნისთვის `supportsAudio === false`, ნაწილები გარდაიქმნება
   `[Audio N]: (unavailable — no STT provider connected)`-ად (#8430 კონტრაქტი). უცნობი სამიზნისთვის (`null`) ყველა გამოძახების წარუმატებლობის შემთხვევაში ნაწილები უცვლელი რჩება. დადასტურებულად მხოლოდ ტექსტის მხარდამჭერი სამიზნე, რომლისთვისაც გამოსაყენებელი STT ავტორიზაციის მონაცემები არ არსებობს, იმავე ცალსახა ჩამნაცვლებელს იღებს ქსელური გამოძახების გარეშე.

წარმატებული ტრანსკრიპტები იყენებს პროცესის მასშტაბით მოქმედ Modality Bridge-ის LRU/TTL კეშს. გასაღები აერთიანებს აუდიოზე მითითებას, სტაბილურ `audio-transcription` ოპერაციის ჭდესა და არჩეულ STT მოდელს; წარუმატებლობები არასოდეს კეშირდება. აუდიოს დამუშავების მცდელობები აახლებს საერთო `bridged`, `cacheHits`, `failures` და `lastUsedAt` მთვლელებს. გარდაქმნილი პასუხები შეიცავს
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`-ს; უცვლელ მოთხოვნებს Audio Bridge-ის სეგმენტი არ ემატება.

გაშვების დროის პარამეტრები ინახება მონაცემთა ბაზაში და მოწმდება Zod-ით:

| გასაღები                      | ნაგულისხმევი | დიაპაზონი            |
| ----------------------------- | ------------ | -------------------- |
| `modalityBridgeAudioEnabled`  | `true`       | —                    |
| `modalityBridgeAudioModel`    | `""`         | ავტომატური ან STT ID |
| `modalityBridgeAudioTimeout`  | `60000`      | 1000–300000          |
| `modalityBridgeAudioMaxClips` | `3`          | 1–10                 |

საერთო კეშის მართვა კვლავ ხდება `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` და `modalityBridgeCacheMaxEntries` პარამეტრებით.

### ვიდეოხიდი (`videoBridge.ts`, `videoBridgePipeline.ts`)

Chat Completions-ის `messages`-ში და Responses API-ის `input`-ში არსებული ზედა დონის ვიდეონაწილების ჩაჭერა ხდება მანამდე, სანამ გამოძახებული იქნება სამიზნე, რომლისთვისაც ვიდეოს ნატიური მხარდაჭერა ცნობილი არ არის. მხარდაჭერილი ფორმატებია `input_video`, `video_url`, `video_source`, HTTPS URL-ები და `data:video/*;base64,...` data URI-ები. ტექსტში არსებული უბრალო ფაილის სახელები ვიდეოდ არ მიიჩნევა.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) მართავს მოთხოვნის შემოვლას, შესაძლებლობის/პოლიტიკის შემოწმებას, თითოეული მოთხოვნის აგრეგაციასა და საპასუხო დატვირთვას. თითოეული ვიდეოს დამუშავება — მიღება, სრული შედეგის კეში, კადრების თანმიმდევრობის აღწერა (რომელიც აერთიანებს გამომძახებლის მიერ გამოცხადებულ აუდიოტრანსკრიპტს) და თითოეული მცდელობის მეტრიკები/შეწყვეტა/გასუფთავება — დამალულია `videoBridgePipeline.ts`-ში არსებული `processVideoPart`-ის მიღმა, რომელიც `preCall`-ის ციკლში თითოეული ვიდეონაწილისთვის ერთხელ გამოიძახება. ეს მოდული ასევე განსაზღვრავს ცალსახა პორტების საზღვრებს: `VideoMediaBrokerPort` (ბაიტების მიღება და შერჩეული კადრების ამოღება), `VideoAudioTranscriptionPort` (გამომძახებლის მიერ გამოცხადებული აუდიოტრანსკრიპტის შერწყმა შერჩეული კადრების აღწერებთან) და `VideoDrilldownPort` (კადრების დეტალიზაციის მუდმივად შენახვის საზღვარი; ჯერ არ არის დაკავშირებული `processVideoPart`-თან — დღეს დეტალიზაციის ჩანაწერებს მხოლოდ ცალკე `/api/modality-bridge/video/drilldown` მარშრუტი წერს).

საჯარო `/v1` მოთხოვნის გზა არასოდეს ახდენს ქვეპროცესის იმპორტირებას ან გამოძახებას. დისტანციური ვიდეოები იტვირთება 50 MiB-იანი შეზღუდვით; ჩასმული base64 ვიდეოებისთვის მოქმედებს კონსერვატიული 36 MiB-იანი ლიმიტი თითოეული ვიდეოს დეკოდირებულ ზომაზე, რათა მოდელის/შეტყობინებების/ჩარჩოების გარსი დარჩეს საჯარო JSON მოთხოვნის მიღების 50 MiB-იანი ლიმიტის ფარგლებში. ჩასმული მონაცემების სიგრძე და დეკოდირებული ზომის შეფასებები მეხსიერების გამოყოფამდე მოწმდება. HTTPS სავალდებულოა როგორც საწყისი დისტანციური URL-ისთვის, ისე თითოეული გადამისამართებისთვის, არსებული მხოლოდ საჯარო მისამართებისთვის განკუთვნილი გამავალი მოთხოვნების დამცავი მექანიზმისა და DNS-ის ფიქსაციის გამოყენებით. შემდეგ ბაიტები გადადის ზუსტად განსაზღვრულ შიდა
`POST /api/modality-bridge/video/extract` ბროკერის საზღვარზე. ეს მარშრუტი არის როგორც
`LOCAL_ONLY`, ისე `SPAWN_CAPABLE`, იღებს მხოლოდ პროცესისთვის სპეციფიკური ავტორიზაციით აღჭურვილ, სანდო loopback-მოთხოვნას და არასოდეს იღებს URL-ს, ფაილური სისტემის ბილიკს, შესრულებად ფაილს ან არგუმენტების სიას. API-ის მოთხოვნის სხეულის ზომის დამუშავების ჯაჭვი და დამმუშავებლის ინკრემენტული სხეულის წამკითხველი ერთმანეთისგან დამოუკიდებლად უზრუნველყოფს ბროკერის შეყვანის 50 MiB-იან ლიმიტს. მისი შეზღუდული რიგი ერთ ჯერზე ერთ ამოღებას ასრულებს, ოთხ მომლოდინე დავალებას უშვებს და მომლოდინე შეყვანის მოცულობას 100 MiB-მდე ზღუდავს.

ბროკერის შიგნით `ffprobe` კითხულობს კერძო ლოკალურ ფაილს; ფორმატების ფიქსირებული ნებადართული სია გამორიცხავს დასაკრავი სიებისა და მანიფესტების ფორმატებს. ნებადართული MOV-ოჯახის კონტეინერებისთვის MOV-ის გარე მონაცემთა მითითებები ნაგულისხმევად კვლავ გამორთულია და ფიქსირებული ბრძანება მათ გამოყენებას არ რთავს. `ffprobe` და `ffmpeg` იყენებენ მხოლოდ `file` პროტოკოლის ნებადართულ სიას, ერთ ნაკადს, არგუმენტების ფიქსირებულ მასივებს, გარსის გარეშე, ხოლო შესრულებადი ფაილები მოიძებნება `PATH`-იდან. გარეკანის მიმაგრებული სურათის ნაკადები დასაკრავ კანდიდატებად არ ითვლება. ყველა დასაკრავი ნაკადი უნდა აკმაყოფილებდეს შეზღუდვებს, ხოლო აშკარად მითითებულ ნაგულისხმევ ნაკადს უპირატესობა ენიჭება დეტერმინისტულ, ყველაზე დაბალი ინდექსის მქონე სათადარიგო ვარიანტამდე. ვიდეოები შეზღუდულია 600 წამით, თითო განზომილებაში 8,192 პიქსელითა და წყაროს 33,554,432 პიქსელით. FFmpeg იღებს შუა წერტილებში განთავსებულ 1–16 JPEG კადრს, გრძელი კიდის ზომას მასშტაბირებით ამცირებს მაქსიმუმ 1,024 პიქსელამდე ისე, რომ მცირე შემავალ მონაცემებს არ ადიდებს, და არასოდეს იღებს URL-ს. შერჩევის ნაგულისხმევი პოლიტიკაა `uniform`. არასავალდებულო `scene_aware` და ექსპერიმენტული `segment_aware` პოლიტიკები უკვე ვალიდირებულ ლოკალურ ნაკადზე ასრულებენ FFmpeg-ის ერთ დამატებით ფიქსირებულ გავლას, ირჩევენ შეზღუდული რაოდენობის `showinfo` სცენის დროის ნიშნულებს და დეტექტორის შეცდომის, დროის ამოწურვის, არასწორად ფორმირებული გამომავალი მონაცემების ან კანდიდატთა ცარიელი ნაკრების შემთხვევაში დეტერმინისტულად უბრუნდებიან იმავე თანაბრად განაწილებულ შუა წერტილებს. სეგმენტების გათვალისწინების რეჟიმი შუა წერტილების ნიმუშებს ვალიდირებული სცენის ინტერვალების პროპორციულად ანაწილებს; სეგმენტების გათვალისწინების მტკიცებულებები და სათადარიგო ქცევა ქვემოთაა აღწერილი. 16-კადრიანი მკაცრი ზღვარი ყველა პოლიტიკაში შერჩევის შემდეგ გამოიყენება. როდესაც სცენების გათვალისწინების მოთხოვნას მხოლოდ ერთკადრიანი ბიუჯეტი აქვს, ის იყენებს აქტიური სრული ვიდეოს ან ფოკუსის ფანჯრის თანაბარი განაწილების შუა წერტილს და აბრუნებს `policyEffective: uniform`-ს: შერჩეული ერთი სცენის კადრი ორივე დროით ბოლოს ვერ შეინარჩუნებს. გამომძახებელს შეუძლია არასავალდებულოდ მიუთითოს სასრული ფოკუსის ფანჯარა (`start`/`end` წამებში); საზღვრები მედიაფაილის ხანგრძლივობის ფარგლებში იზღუდება, შებრუნებული ან არასასრული ფანჯრები უარყოფილია და შერჩევის ყველა პოლიტიკა მხოლოდ ნორმალიზებული ინტერვალის შიგნით სრულდება. მიღებული ფანჯარა ჩართულია შერჩევის მეტამონაცემებსა და არასანდო აღწერის პრეფიქსში, რათა შემდგომმა მოდელებმა შეძლონ ფოკუსირებული ამონარიდის სრული ქრონოლოგიისგან გარჩევა.

სემანტიკური სუბტიტრის ფოკუსი ცალკე, აშკარად განსაზღვრული პარამეტრია. ნაგულისხმევი `full` ანალიზის რეჟიმი ინარჩუნებს კადრების არსებულ მოთხოვნას და მოთხოვნის ტექსტს სუბტიტრების მოდელს არასოდეს გადასცემს. `focused` რეჟიმში ხიდი იმავე Chat ან Responses კონტეინერიდან კითხულობს მხოლოდ მომხმარებლის მიერ შექმნილ უახლეს არაცარიელ `text`/`input_text`-ს, ახდენს მის NFC ფორმაში ნორმალიზებას, საკონტროლო სიმბოლოებსა და ჰარეებს აერთიანებს და ზღუდავს 500 Unicode კოდური წერტილით. ცარიელი შედეგის შემთხვევაში სისტემა ზუსტად `full` მოთხოვნას უბრუნდება. გამოსადეგი მინიშნება სერიალიზდება JSON-ის სახით არასანდო მომხმარებლის კონტექსტის ცალკე ბლოკში და მას მხოლოდ დაკვირვებადი დეტალების პრიორიტეტიზაცია შეუძლია; ის ვერ გადაწონის ცალკე გაფრთხილებას, რომლის თანახმადაც მედიაში ხილული ან მოსმენადი ინსტრუქციები არ უნდა შესრულდეს. ტექსტური ფოკუსი არასოდეს ადგენს `start`/`end`-ს და არ ცვლის დროით შემრჩევს.

#### FU-07 სტრუქტურული სეგმენტის მტკიცებულებები

`segment_aware` უკვე ვალიდირებულ ლოკალურ ვიდეონაკადზე ასრულებს ერთ შეზღუდულ წინასწარ ანალიზს. ფიქსირებული ფილტრების ჯაჭვი თავდაპირველად მასშტაბს მაქსიმუმ 320 პიქსელის სიგანემდე ამცირებს, აღმოაჩენს სცენის ცვლილებებსა და გაყინულ ინტერვალებს, შემდეგ კი ბუნდოვანების, საშუალო სიკაშკაშისა და სივრცითი/დროითი ინფორმაციისთვის წამში 1 კადრს იღებს. გავლა შეზღუდულია 600 სტრუქტურული ნიმუშით, FFmpeg-ის/ფილტრის ერთი ნაკადით, იმავე მხოლოდ `file` პროტოკოლისა და კონტეინერების ნებადართული სიებით, პროცესის გამომავალი მონაცემების 1 MiB-იანი ზღვრითა და მაქსიმუმ 30 წამით ბროკერის საერთო გაუქმების/საბოლოო ვადის ფარგლებში. ის მოთხოვნიდან არასოდეს იღებს ბრძანებას, ფილტრს, ბილიკს ან URL-ს.

სტრუქტურული მნიშვნელობები შერჩევის დეტერმინისტული მტკიცებულებებია და არა ვიდეოს სემანტიკური გაგება. ისინი არ ადგენენ სუბიექტებს, მოქმედებებს, სუბტიტრებს, მეტყველებას ან მომხმარებლის განზრახვას. სცენისა და გაყინვის საზღვრები ქმნის სეგმენტებს; გაყინვის დაფარვა, ბუნდოვანება, ექსპოზიცია, სივრცითი დეტალიზაცია და დროითი ცვლილება მხოლოდ იმაზე მოქმედებს, თუ როგორ განაწილდება არსებული 1–16 კადრის ბიუჯეტი. სრულად გაყინული სეგმენტი მაქსიმუმ ერთი კადრით შემოიფარგლება, ხოლო გაუყინავი სეგმენტები დარჩენილი ბიუჯეტისთვის კონკურირებენ. როდესაც საზღვრების რაოდენობა კადრების რაოდენობას აჭარბებს, ქრონოლოგიის თანაბარი დაფარვა შენარჩუნებულია, რათა დასაწყისში სწრაფმა ჭრებმა გრძელი ბოლო სეგმენტი ვერ დამალოს. სცენის საზღვრები, რომლებიც გაყინვის საზღვრიდან 1-წამიანი ანალიზის გარჩევადობის ფარგლებშია, ერთიანდება.

ფილტრების არარსებობა, არასწორად ფორმირებული ან ცარიელი მტკიცებულებები, დეტექტორის შეცდომა ან შეზღუდული წინასწარი ანალიზის დროის ამოწურვა სისტემას ზუსტად თანაბრად განაწილებული შუა წერტილების პოლიტიკაზე ღიად დაბრუნებას აიძულებს. გამომძახებლის მიერ გაუქმება ან ბროკერის საბოლოო ვადის ამოწურვა ღიად დაბრუნებას არ იწვევს: ის ასრულებს მიმდინარე ქვეპროცესს, ხელს უშლის კადრების შემდგომ ამოღებას და კერძო დროებითი ხე იშლება `finally`-ში.

`scripts/perf/video-bridge-fu07-eval.ts` ქმნის დეტერმინისტულ, რეალურ FFmpeg-ის სატესტო მონაცემებს დუბლიკატების მოცილების შემდგომ სუბტიტრების გამოძახებების ეკონომიისთვის, ინტენსიური მოძრაობის ბიუჯეტის განაწილებისთვის, ბუნდოვანების/ექსპოზიციის/SI-TI მტკიცებულებებისთვის, გრძელი დაბოლოების მქონე სწრაფი ჭრებისთვის და თანდათანობითი გადასვლის ცრუ დადებითი შედეგებისთვის. ის აღრიცხავს წინასწარი ანალიზის რეალურ გასულ დროს და, როდესაც `/usr/bin/time` ხელმისაწვდომია, შვილობილი პროცესის CPU-სა და RSS-ის პიკურ მოხმარებას. მისი ხარისხის შემოწმებები მხოლოდ სტრუქტურული ორაკულებია. სუბტიტრების რეალური მოდელის ხარისხი რჩება `HOLD` მდგომარეობაში, რადგან ამ სატესტო გარემოს არც ავტორიზებული საბოლოო წერტილი აქვს და არც ფიქსირებული შემფასებელი. ფულადი ეკონომიაც რჩება `HOLD` მდგომარეობაში, თუ `--caption-cost-per-call-usd` თითო გამოძახების აშკარად განსაზღვრულ დადებით ღირებულებას არ მიაწვდის; სკრიპტი არცერთ შედეგს არ აყალბებს.

თითოეული კადრის ზომა შეზღუდულია 4 MiB-ით, ყველა დაუმუშავებელი კადრის ჯამური ზომა — 23 MiB-ით, ხოლო სერიალიზებული ბროკერის პასუხი — 32 MiB-ით. პირადი დროებითი დირექტორია იშლება `finally` ბლოკში. OmniRoute არ შეიცავს FFmpeg-ს და არ იღებს შესრულებადი ფაილის მორგებულ მისამართს. სუბტიტრების შექმნამდე bridge იყენებს კონსერვატიულ ვიზუალურ დედუპლიკაციას: თითოეული JPEG მცირდება 16×16 ნაცრისფერი ტონების ბუფერამდე და შედარება ხდება მხოლოდ ბოლოს შენარჩუნებულ კადრთან. ერთ კადრზე მეტი მოთხოვნილი სუბტიტრების ბიუჯეტისთვის ამოღება უზრუნველყოფს შეზღუდულ კანდიდატთა ნაკრებს, რომლის ზომა ამ ბიუჯეტის მაქსიმუმ ორმაგია და არასდროს აღემატება 16 კადრს. მოთხოვნილი ზღვარი გამოიყენება მხოლოდ დედუპლიკაციის შემდეგ, ხოლო საბოლოო შეთხელებისას პირველი და ბოლო არჩეული კანდიდატები შენარჩუნდება, თუ ბიუჯეტი სულ მცირე ორია. ვერსიონირებული
`grayscale-16x16-mean-cells-v2` პოლიტიკა იყენებს საშუალო სიკაშკაშის დელტასა და იმ მინიატურული გამოსახულების უჯრედების თანაფარდობას შორის უდიდეს მნიშვნელობას, რომელთა ნორმალიზებული დელტა სულ მცირე 0.05-ია. დუბლიკატის ზღვარი მუდმივი 0.04-ია, რომელიც პროგნოზირებადობისთვისაა შერჩეული და არ არის წარმოდგენილი გაშვების დროის პარამეტრად. ეს მეორეული
მაღალი კონტრასტის სიგნალი ინარჩუნებს მცირე მოძრაობასა და ხილული ტექსტის ცვლილებებს, რომლებიც მხოლოდ საშუალო მნიშვნელობაზე დაფუძნებულმა შედარებამ შეიძლება დამალოს. კომპარატორის ან დეკოდერის შეცდომების შემთხვევაში პროცესი ღიად გრძელდება და დაფარვა ნარჩუნდება. გამომავალი მეტამონაცემები ერთმანეთისგან გამოყოფს ამოღებულ კანდიდატებს, წარმატებით გამოყენებულ კადრებსა და გამოტოვებულ ვიზუალურ დუბლიკატებს.

ცალსახად მონიშნულ ვიდეონაწილს შეუძლია დროის ნიშნებიანი საკონტაქტო ფურცლის მოთხოვნა. bridge ქმნის მაქსიმუმ 4-სვეტიან, 16-კადრიან JPEG ბადეს. თითოეული 512-პიქსელიანი უჯრედი წყაროს დროის ნიშანს მაღალი კონტრასტის მქონე ქვედა ზოლში ათავსებს, ხოლო იგივე დროის ნიშნები ტექსტურ მეტამონაცემებშიც რჩება შემდგომი დაკავშირებისა და აუდიტისთვის. სრული JPEG კვლავ შეზღუდულია 32 MiB-ით. თუ `sharp` ვერ შეძლებს ბადის დეკოდირებას ან კომპოზიციას, bridge დაუბრუნდება ცალკეულ JPEG კადრებს; კლიენტის მიერ გაუქმება კვლავ გავრცელდება ფურცლის ოპერაციაზე.

ტექსტურ ნიშნულებად, რათა დაუმუშავებელი ვიდეო არ შენარჩუნდეს. როდესაც შესაძლებლობა უცნობია, ეს ნაწილები
ინარჩუნებს ვიდეოს მატარებელს; ნებისმიერი სარეზერვო ტრანსკრიპტი ექვემდებარება ზემოთ აღწერილ შეზღუდულ ტექსტურ
კონვერტაციას. სამიზნეები, რომლებსაც აქვთ `supportsVideo === true`, ხიდს გვერდს უვლის.
კლიენტის მოთხოვნის შეწყვეტის სიგნალი ვრცელდება ჩამოტვირთვაზე, ბროკერის რიგზე,
ქვეპროცესებსა და წარწერის გამოძახებებზე; შეწყვეტები ვიდეოებს შორის აჩერებს პროცესს და არასოდეს
იძლევა შეცდომისას დაუმუშავებელ მედიაზე ღია წვდომას.

გაშვების გარემოს პარამეტრები ინახება DB-ში და ვალიდირდება Zod-ით:

| გასაღები                            | ნაგულისხმევი | დიაპაზონი / ქცევა                                                                                      |
| ----------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------ |
| `modalityBridgeVideoEnabled`        | `false`      | არასავალდებულო გაშვების გარემო, თანხმობით ჩასართავი                                                    |
| `modalityBridgeVideoAnalysisMode`   | `"full"`     | `full` ინარჩუნებს ზოგად წარწერებს; `focused` იყენებს შეზღუდულ, არასანდო უახლეს სამომხმარებლო კონტექსტს |
| `modalityBridgeVideoModel`          | `""`         | მემკვიდრეობით იღებს Vision Bridge-ის მოდელს                                                            |
| `modalityBridgeVideoFrameCount`     | `8`          | 1–16                                                                                                   |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`  | `uniform`, `scene_aware` ან პროპორციული `segment_aware`; დეტექტორის მარცხისას გამოიყენება `uniform`    |
| `modalityBridgeVideoMaxVideos`      | `1`          | 1–4                                                                                                    |
| `modalityBridgeVideoTimeout`        | `120000`     | 1000–120000 ms                                                                                         |

Video-ის ძველი, შენახული ტაიმაუტის მნიშვნელობები, რომლებიც 120 წამს აღემატება,
იზღუდება ბროკერის საბოლოო ვადით; ამ ზღვარზე მეტი მნიშვნელობის მქონე ახალი პარამეტრების ჩაწერა უარყოფილია.
`GET /api/modality-bridge/video/runtime` ავთენტიფიკაციამდე ან გაშვების გარემოს შემოწმებამდე
მოითხოვს სანდო, შტამპიან უკუმარყუჟის ლოკალურობას, შემდეგ კი მართვის
ავთენტიფიკაციას. ის აბრუნებს მხოლოდ `available`-ს, გასუფთავებულ FFmpeg/ffprobe ვერსიებსა და ფიქსირებულ
მიზეზს, როდესაც გაშვების გარემო მიუწვდომელია. შიდა ამოღების საბოლოო წერტილი არ არის
საჯარო ატვირთვის API: რიგის გადავსება აბრუნებს `503`-ს და `Retry-After`-ს, გამომძახებლის
გათიშვა აბრუნებს `499`-ს, ხოლო ბროკერის ფიქსირებული საბოლოო ვადა — `504`-ს. კონვერტირებული პასუხები
ამატებს `video->text;model=<visionModel>;parts=<videos>`-ს ცენტრალურ
`x-omniroute-modality-bridge` სათაურში Vision ან Audio სეგმენტების წაშლის გარეშე.

### PII Masker (`piiMasker.ts`)

მუშაობს **ორივე** ეტაპზე.

- **`preCall`** ახდენს payload-ის კლონირებას, გადის `system`, `messages`, `input` და
  `prompt` ველებზე (მათ შორის უბრალო სტრიქონულ ელემენტებზე) და სტრიქონულ
  `content`/`text` ველებზე იყენებს `processPII()`-ს (`@/shared/utils/inputSanitizer`-დან).
  როდესაც `PII_REDACTION_ENABLED=true`, აღმოჩენილი PII გამავალ payload-ში
  რედაქტირდება. ეს არ არის დამოკიდებული `INPUT_SANITIZER_MODE`-ზე (რომელიც
  მხოლოდ prompt-ის ინექციის პოლიტიკას მართავს). როდესაც რედაქტირება გამორთულია,
  გამოძახება აფიქსირებს აღმოჩენების რაოდენობას შიგთავსის გადაწერის გარეშე.
- **`postCall`** ახდენს პასუხის ღრმა კლონირებას და უშვებს `sanitizePIIResponse()`-ს,
  ასევე Responses API-ის ფორმის შემნიღბავს (`maskResponsesOutput` — მოიცავს
  `output_text`-სა და `output[].content[].text`-ს). თუ რაიმე რედაქტირება მოხდა,
  შეცვლილი პასუხი ანაცვლებს თავდაპირველს.

დამცავი მექანიზმი არასოდეს ბლოკავს; ის მხოლოდ ამატებს ანოტაციებს
(`meta.detections`, `meta.redacted`) ან გადაწერს.

#### ტიპების მიხედვით არჩევა, მორგებული შაბლონები და აღმოჩენების მრიცხველები

**Dashboard → Settings → Security → PII masking** განსაზღვრავს, _რა_ უნდა
შეინიღბოს. ის შენიღბვას არ რთავს: ამას კვლავ `PII_REDACTION_ENABLED`
(მოთხოვნა) და `PII_RESPONSE_SANITIZATION` (პასუხი + SSE) მართავს; ორივე
ნაგულისხმევად გამორთულია.

- **ტიპების მიხედვით არჩევა** — ჩაშენებული id-ები ჩამოთვლილია
  `src/shared/constants/piiTypes.ts`-ში (`PII_BUILTIN_TYPES`). მნიშვნელობის
  არქონა ნიშნავს ყველა ტიპს (ქცევა, რომელიც ამ პარამეტრის დამატებამდე
  არსებობდა). მოთხოვნების ძრავის `ssn_us` შაბლონი შეესაბამება `ssn`-ს.
  შაბლონები (Minimal, Standard, Financial, Brazilian, USA, Full) მხოლოდ
  UI-ში ნიშნავენ მოსანიშნ ველებს.
- **მორგებული შაბლონები** — მაქსიმუმ 20 რეგულარული გამოსახულების ან wildcard
  შაბლონი (`*` = მაქსიმუმ 64 არა-ჰარეს სიმბოლო, `?` = ერთი). დამთხვევები
  გარდაიქმნება `[CUSTOM_REDACTED]`-ად. თითოეული შაბლონი გადის
  `compilePiiCustomPattern()`-ს (`src/shared/utils/piiCustomPatterns.ts`):
  მაქსიმუმ 500 სიმბოლო, ალმები შეზღუდულია `g i m s u`-ით, უნდა
  კომპილირდებოდეს, უნდა გაიაროს `safe-regex`-ის შემოწმება (კატასტროფული
  უკანდახევა) და არ უნდა ემთხვეოდეს ცარიელ სტრიქონს ან რედაქტირების
  ჩანაცვლების ნიშნულს. წარუმატებელი შაბლონი უარყოფილია როგორც შენახვისას,
  ისე ტესტირებისას, ხოლო შენახული ჩანაწერი, რომელიც შემოწმებას ვერ გაივლის,
  შესრულების დროს გამოტოვებულია და არ კომპილირდება. მორგებული შაბლონები
  მხოლოდ მაშინ სრულდება, როდესაც შენიღბვა ჩართულია.
- **აღმოჩენების მრიცხველები** — ტიპების მიხედვით რაოდენობები (არასოდეს
  დამთხვევების მნიშვნელობები), რომლებიც ინახება მეხსიერებაში და ნულდება
  ხელახლა გაშვებისას (`src/lib/pii/piiDetectionStats.ts`). ისინი მხოლოდ მაშინ

### Prompt-ის ინექცია (`promptInjection.ts`)

აღმოაჩენს მომხმარებლის მიერ მოწოდებულ შიგთავსში მტრულ სტრუქტურებს და
აღასრულებს კონფიგურირებულ პოლიტიკას. ქცევა იმართება გარემოს ცვლადებითა და
კონსტრუქტორის პარამეტრებით:

| პარამეტრი         | გარემოს ცვლადი                                                                                                | ნაგულისხმევი | ეფექტი                                                                                                                                                                                  |
| ----------------- | ------------------------------------------------------------------------------------------------------------- | ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ჩართულია          | `INPUT_SANITIZER_ENABLED`                                                                                     | `true`       | როდესაც `false`-ია, დამცავი მექანიზმი დამუშავებას დაუყოვნებლივ ასრულებს.                                                                                                                |
| რეჟიმი            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                               | `warn`       | ინექციის პოლიტიკა: `block`, `warn` ან `log`. (`redact` მიღებულია უკუთავსებადობისთვის, მაგრამ ინექციის ტექსტს **არ** შლის; მოთხოვნაში PII-ის გადაწერას `PII_REDACTION_ENABLED` მართავს.) |
| ბლოკირების ზღვარი | `blockThreshold` პარამეტრი / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ფსევდონიმი `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`       | ბლოკირებისთვის საჭირო მინიმალური სიმძიმე. ნაგულისხმევად საშუალო დონე მხოლოდ დაკვირვებისთვისაა.                                                                                          |

**რეჟიმის პრიორიტეტულობა** (`getMode`): გამომძახებლის `options.mode` →
`INJECTION_GUARD_MODE`-ის **DB feature-flag-ის გადაფარვა** (Dashboard →
Settings → Feature Flags) → `INJECTION_GUARD_MODE` გარემოს ცვლადი →
`INPUT_SANITIZER_MODE` გარემოს ცვლადი → `warn`. შესაბამისად, dashboard-ის
გადაფარვას გარემოს ცვლადებზე უპირატესობა აქვს, ამიტომ Feature Flags UI
მოქმედ დამცავ მექანიზმს რეალურ დროში მართავს (ხელახლა გაშვების გარეშე). DB-დან
წაკითხვა უსაფრთხო უკუსვლის პრინციპით მუშაობს: შეცდომის შემთხვევაში დამცავი
მექანიზმი გარემოს ცვლადებზე დაფუძნებულ ქცევას უბრუნდება, ხოლო როდესაც
გადაფარვა დაყენებული არ არის, ქცევა გარემოს ცვლადებზე დაფუძნებული
განსაზღვრის იდენტურია.

აღმოჩენის წყაროები:

1. `sanitizeRequest()` `@/shared/utils/inputSanitizer`-დან (საერთო
   დეტექტორების ნაკრები, რომელიც pipeline-ის სხვა ნაწილებშიც გამოიყენება).
2. ჩაშენებული `DEFAULT_GUARD_PATTERNS` (ამჟამად `system_override_inline` და
   `markdown_system_block`, ორივე `high` სიმძიმის).
3. არასავალდებულო `customPatterns`, რომლებიც კონსტრუქტორის პარამეტრების
   მეშვეობით გადაეცემა (სტრიქონები, რეგულარული გამოსახულებები ან
   `{ name, pattern, severity }` ჩანაწერები).

როდესაც `mode === "block"` **და** მინიმუმ ერთი აღმოჩენა აკმაყოფილებს სიმკაცრის
ზღვარს, `preCall` აბრუნებს `{ block: true, message: "Request rejected:
suspicious content detected" }`-ს. `warn`/`log` რეჟიმებში დამცავი მექანიზმი ჩანაწერს ქმნის, მაგრამ
გამოძახებას უშვებს. საერთო დამხმარე `evaluatePromptInjection()` ასევე ექსპორტირებულია
იმ გამომძახებლებისთვის, რომლებსაც მოთხოვნების შეფასება რეესტრის გვერდის ავლით სჭირდებათ.

**პირველ 16 KB-ს** — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ბაიტი)
`src/shared/utils/inputSanitizer.ts`-ში. როგორც `detectInjection()`, ისე
`evaluatePromptInjection()` შაბლონების ციკლის გაშვებამდე იყენებს
`slice(0, MAX_INJECTION_SCAN_BYTES)`-ს. ინექციის დირექტივები შეყვანის დასაწყისთან ახლოსაა, ამიტომ ეს
ზღუდავს რეგულარული გამოსახულებების მიერ CPU-ის/GC-ის გამოყენებას ასეულობით KB-ის მოცულობის მონაცემებში, აღმოჩენის ეფექტიანობის შემცირების გარეშე (იხ.
#3932, #4041).

### ავტორიზაციის მონაცემების შემნიღბავი (`credentialMasker.ts`)

მუშაობს **ორივე** ეტაპზე და ნაგულისხმევ ჯაჭვში ბოლოა (პრიორიტეტი `95`). გამავალ მონაცემებში (შეტყობინების
შიგთავსში, ხელსაწყოს გამოძახების არგუმენტებში, ხელსაწყოს შედეგებში) **და** პროვაიდერის პასუხში
ფარავს კარგად ცნობილ API-გასაღებების / საიდუმლო ტოკენების შაბლონებს, რათა მოთხოვნაში ჩასმული
ავტორიზაციის მონაცემები (ან ხელსაწყოს შედეგის მიერ დაბრუნებული მათი ასლი) არ გაჟონოს
ზედა დონის პროვაიდერთან ან უკან, კლიენტთან.

- **მხოლოდ ხელით ჩართვა**, იგივე წესი, რაც პერსონალური მონაცემების დაფარვისას (მკაცრ წეს #20-თან დაკავშირებული):
  გამორთულია, თუ `settings.credentialRedactionEnabled === true` **ან**
  `CREDENTIAL_REDACTION_ENABLED=true` არ არის. გამორთულ მდგომარეობაში დამცავი მექანიზმი არაფერს აკეთებს —
  არასოდეს ბლოკავს და არასოდეს გადაწერს.
- `redactCredentials()` გადის მონაცემების/პასუხის მთელ ხეზე (`walkValue()`,
  დაცულია პროტოტიპის დაბინძურებისგან, ციკლების მიმართ უსაფრთხოა `WeakSet`-ის მეშვეობით) და დამთხვევებს
  `[REDACTED:<type>]` ჩანაცვლებით ცვლის; ამასთან, კლონირდება მხოლოდ რეალურად
  შეცვლილი განშტოებები.
- `CREDENTIAL_PATTERNS` მოიცავს LLM-პროვაიდერების გასაღებებს (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ტოკენებს (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), გადახდის გასაღებებს (Stripe, Square), ღრუბლოვანი
  სერვისების გასაღებებს (AWS-ის წვდომის გასაღები, Twilio, SendGrid, Mailgun), პირად გასაღებებს / JWT-ებს,
  ავტორიზაციის მონაცემების შემცველ კავშირის სტრიქონებს (`mongodb://user:pass@...` და სხვ.) და
  ზოგად `Authorization`/`x-api-key`/`api-key`/`apikey` სათაურის მნიშვნელობის
  შაბლონს. სათაურის ფორმის გასაღებები (`authorization`, `x-api-key`, `api-key`,
  `apikey`) იფარება სტრუქტურულად (მხოლოდ მნიშვნელობა, ხოლო სქემის პრეფიქსი, როგორიცაა
  `Bearer `/`Basic `, შენარჩუნებულია) და არა ზოგადი ტექსტური რეგულარული გამოსახულებით.
- დამცავი მექანიზმი არასოდეს ბლოკავს; ის მხოლოდ გადაწერს (`modifiedPayload` /
  `modifiedResponse`) და ანოტაციებს ამატებს (`meta.credentialsRedacted`, `meta.count`).

რეგრესიისგან დაცვა: `tests/unit/credential-masker-guardrail.test.ts`.

## საბაზისო კონტრაქტი (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ჯაჭვის შესრულებას დაუყოვნებლივ წყვეტს
  message?: string; // ნაჩვენებია დაბლოკვისას
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // მოთხოვნის გადასაწერად აბრუნებს preCall
  modifiedResponse?: TValue; // პასუხის გადასაწერად აბრუნებს postCall
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

დამცავი მექანიზმი „ცვლილების არარსებობაზე“ მიუთითებს `void`, `{}` ან
`{ block: false }` მნიშვნელობის დაბრუნებით. `modifiedPayload`/`modifiedResponse`-ის დაბრუნება
ანაცვლებს ჯაჭვში ქვემოთ მდებარე დამცავ მექანიზმებზე გადაცემულ მნიშვნელობას.
`signal?: AbortSignal` გამომძახებლის სასიცოცხლო ციკლს დამცავ მექანიზმებს გადასცემს. მოთხოვნის შეწყვეტა არის მიზანმიმართული fail-open გამონაკლისი: მედიის ხიდები აჩერებენ მუშაობას და ასუფთავებენ რესურსებს ისე, რომ დაუმუშავებელი მედია არ აღადგინონ სამიზნისთვის, რომელიც, როგორც ცნობილია, მას მხარს არ უჭერს.

## რეესტრი (`registry.ts`)

ერთეული `guardrailRegistry` ხელმისაწვდომს ხდის:

- `register(guardrail)` — ამატებს დამცავ მექანიზმს (ან ანაცვლებს მას ნორმალიზებული სახელის მიხედვით) და
  ხელახლა ახარისხებს `priority`-ის ზრდადი თანმიმდევრობით.
- `clear()` / `list()` — ადმინისტრაციული დამხმარე ფუნქციები.
- `runPreCallHooks(payload, context)` — თანმიმდევრობით ამუშავებს აქტიურ დამცავ მექანიზმებს, გადასცემს
  payload-ს `modifiedPayload`-ის გავლით და ჩერდება პირველივე `block: true`-ზე.
- `runPostCallHooks(response, context)` — იგივე ნაკადი პასუხის მხარეს.
- `resetGuardrailsForTests({ registerDefaults })` — ასუფთავებს მდგომარეობას და, სურვილისამებრ,
  ხელახლა არეგისტრირებს ნაგულისხმევ მნიშვნელობებს ტესტების სუფთა იზოლაციისთვის.

ორივე გამშვები აბრუნებს `{ blocked, payload|response, results, guardrail?, message? }`-ს,
სადაც `results` არის `GuardrailExecutionResult` ჩანაწერების მასივი, რომელიც თითოეული
დამცავი მექანიზმისთვის შეიცავს `blocked`, `skipped`, `modified`, `error` და `meta` ველებს,
რაც სასარგებლოა თვალყურის სადევნებლად.

### დამცავი მექანიზმების გამორთვა ცალკეული მოთხოვნისთვის

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` აგროვებს
დუბლიკატებისგან გაწმენდილ დამცავი მექანიზმების სახელების სიას, რომლებიც მიმდინარე
მოთხოვნისთვის უნდა გამოტოვდეს. არსებობს ხუთი არხი, რომლებიც ამ თანმიმდევრობით იკითხება და ერთ სიაში
ერთიანდება (დუბლიკატების მოცილებისას უპირატესობა პირველ გამოჩენას ენიჭება):

1. `apiKeyInfo.disabledGuardrails`
2. მოთხოვნის სხეულის `disabledGuardrails` (ზედა დონეზე)
3. მოთხოვნის სხეულის `metadata.disabledGuardrails` (მხოლოდ მაშინ, როდესაც `metadata` ობიექტია)
4. სათაური `x-omniroute-disabled-guardrails`
5. მოძველებული სათაური `x-disabled-guardrails`

ხუთივე არხი ერთიანდება, მათ შორის ორივე სათაური: როგორც
`x-omniroute-disabled-guardrails`-ის, ისე `x-disabled-guardrails`-ის გაგზავნისას გამოტოვებული იქნება
მათი სიების გაერთიანება, ხოლო ცარიელი თანამედროვე სათაური მოძველებულ სათაურს აღარ ფარავს
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), გამოსწორდა
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805)-ში).

მნიშვნელობები შეიძლება იყოს სტრიქონების მასივები ან მძიმეებით გამოყოფილი სტრიქონი; სახელებს
მოშორდება გარე ჰარიები და ისინი ნორმალიზდება ქვედა რეგისტრის kebab-case ფორმატში (`pii_masker` → `pii-masker`), ხოლო ცარიელი
ჩანაწერები იშლება. შედეგი რეესტრს `context.disabledGuardrails`-ის გავლით გადაეცემა,
რომელიც შესაბამის დამცავ მექანიზმებს გამოტოვებს (`skipped: true` `results`-ში).

გამორთვის სია გავლენას ახდენს მხოლოდ **რეესტრზე**. Prompt-injection-ის `block` რეჟიმი
სავალდებულო საზღვარია: injection-guard middleware
(`src/middleware/promptInjectionGuard.ts`) `evaluatePromptInjection()`-ს იძახებს
გამომძახებლის მიერ კონტროლირებადი გამორთვის სიის გარეშე (მკვდარი
`resolveDisabledGuardrails({ body })` გამოძახება, რომელსაც ის ადრე ასრულებდა, წაიშალა
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934)-ში), ამიტომ მოთხოვნა,
რომელიც `prompt-injection`-ს თიშავს, `block` რეჟიმში მაინც უარყოფილი იქნება. ეს
განზრახაა. გამორთვის არხებს გამომძახებელი აკონტროლებს (მოთხოვნის სხეული,
მეტამონაცემები, სათაურები) და გამომძახებელს არ უნდა შეეძლოს ოპერატორის მიერ დაყენებული უსაფრთხოების
კონტროლის გამორთვა
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). სათაურების
გაერთიანება [#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412)-დან
ცვლის მხოლოდ იმას, თუ რეესტრის რომელი დამცავი მექანიზმები გამოტოვდება; ის კლიენტს
middleware-ის გვერდის ავლის საშუალებას არ აძლევს. სავალდებულო თითოეული გასაღებისა და თითოეული ჯგუფის დამცავი მექანიზმების პოლიტიკები
აღრიცხულია v4 RFC-ში [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417).
იხილეთ [დაფარვა და შეზღუდვები](#coverage-and-limits).

## შესრულების თანმიმდევრობა

თითოეული მოთხოვნისთვის, რომელიც გადის `src/sse/handlers/chat.ts`-სა და
`open-sse/handlers/chatCore.ts`-ში (`chat`-ის ოჯახის მარშრუტები ჩამოთვლილია
[დაფარვასა და შეზღუდვებში](#coverage-and-limits)):

1. `resolveDisabledGuardrails(...)` ქმნის გამოტოვების სიას API გასაღების, მოთხოვნის სხეულისა
   და სათაურების საფუძველზე.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` დამცავ მექანიზმებს პრიორიტეტის ზრდის
   თანმიმდევრობით უშვებს:
   - გამორთული დამცავი მექანიზმები აღირიცხება როგორც `skipped`.
   - თითოეული დამცავი მექანიზმის `preCall`-ს შეუძლია `modifiedPayload`-ის მეშვეობით სასარგებლო დატვირთვის გადაწერა.
   - პირველი `block: true` წყვეტს ჯაჭვის შესრულებას და დამმუშავებელი აბრუნებს
     დამცავი მექანიზმის მიერ უარყოფის პასუხს.
3. (შესაძლოა გადაწერილი) სასარგებლო დატვირთვა გადადის კომბინირებულ მარშრუტიზაციასა და ზემდგომ
   სერვისში გაგზავნაზე.
4. **მხოლოდ არანაკადური რეჟიმი:** პასუხის აწყობის შემდეგ,
   `guardrailRegistry.runPostCallHooks(...)` პასუხზე იმავე ჯაჭვს უშვებს.
   აქ `block: true` აუქმებს ზემდგომი სერვისის პასუხს და აბრუნებს HTTP 400-ს. ნაკადური პასუხები ამ ეტაპს მთლიანად გამოტოვებს.

დამცავი მექანიზმები, რომლებიც გამონაკლისს აგდებს, აღირიცხება `error: <message>`-ით და
ლოგირდება `logger.warn`-ის მეშვეობით, თუმცა ჯაჭვის შესრულება გრძელდება — დიზაინის მიხედვით, შეცდომისას მოთხოვნა დაშვებულია.

### რა არ არის დაფარული

- **მედიის, ჩაშენებებისა და მონაცემების მარშრუტები** (`/v1/images/*`, `/v1/embeddings`,
  `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`,
  `/v1/rerank`, `/v1/search`, `/v1/moderations`) რეესტრამდე არასოდეს აღწევს. იქ არ
  სრულდება PII-ის შენიღბვა, ავტორიზაციის მონაცემების შენიღბვა ან მოდალობებს შორის ხიდის გამოყენება. მათი ერთადერთი
  შემოწმება მემკვიდრეობითი ინექციისგან დამცავი შუალედური პროგრამაა.
- **ნაკადურ პასუხებზე** გამოძახების შემდგომი დამცავი მექანიზმები არ გამოიყენება: არც `pii-masker` ან
  `credential-masker` სრულდება გამოძახების შემდეგ და არც გამოძახების შემდგომი ბლოკირება. გამოიყენება მხოლოდ ნაკადური PII-ის
  გარდაქმნა (როდესაც `PII_RESPONSE_SANITIZATION` ჩართულია). ნაკადურ პასუხში
  უკან დაბრუნებული ავტორიზაციის მონაცემები არ რედაქტირდება.
- **გამორთვის არხები შუალედური პროგრამის წინააღმდეგ (დიზაინის მიხედვით):** შუალედური პროგრამა
  მოთხოვნის ტექსტის ინექციას აფასებს `evaluatePromptInjection()`-ის საკუთარი გამოძახებით და
  გამომძახებლის მიერ მართული გამორთვის სიის გადაცემის გარეშე.
  `block` რეჟიმი სავალდებულო საზღვარია, რომლის გვერდის ავლაც გამომძახებლის მიერ მართული გამორთვებით შეუძლებელია, მათ შორის `chat`-ის ოჯახის მარშრუტებზე
  ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). `prompt-injection`-ის გამორთვა მხოლოდ რეესტრის დამცავ მექანიზმს გამოტოვებს.

### რა ხედავს პასუხს გამოძახების შემდგომ დამუშავებამდე

არანაკადურ გზაზე თანმიმდევრობა ასეთია: მეხსიერების ამოღება → ჩაშენებული ხელსაწყოს
შესრულება → გამოძახების შემდგომი დამცავი მექანიზმები → გამოძახების შემდგომი ბლოკირების გამო გასვლა → სემანტიკურ კეშში შენახვა.

- **მეხსიერებიდან ამოღება** და **ინსტრუმენტების შესრულება** პასუხს ხედავს მანამდე, სანამ post-call
  დამცავი მექანიზმები შეძლებს მის გადაწერას ან დაბლოკვას.
  [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401)-ის შემდეგ, როდესაც
  `PII_RESPONSE_SANITIZATION` ჩართულია, მეხსიერებიდან ამოღების პროცესი ამოღებულ
  ტექსტს `sanitizePII`-ის მეშვეობით ამუშავებს (როგორც ნაკადურ, ისე არანაკადურ
  რეჟიმში), თუმცა პასუხი, რომელსაც post-call მოგვიანებით ბლოკავს, მანამდე მაინც
  გადაეცემა მეხსიერებასა და ინსტრუმენტებს.
- **სემანტიკური კეში** პასუხს post-call-ის შემდეგ ინახავს, ამიტომ მასში
  გადაწერილი პასუხი ინახება, ხოლო დაბლოკილი პასუხი კეშში არასოდეს ხვდება. კეშის
  ჩანაწერების გასაღებები თითოეული API გასაღებისთვის ცალ-ცალკე იქმნება.

## მორგებული დამცავი მექანიზმები

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ნაბიჯები:

1. შექმენით `src/lib/guardrails/myGuardrail.ts`, რომელიც აფართოებს `BaseGuardrail`-ს.
2. განახორციელეთ `preCall` და/ან `postCall`.
3. ან დაარეგისტრირეთ იმპორტის დროს (`registerDefaultGuardrails`-იდან დამატებით), ან
   შესრულების დროს გამოიძახეთ `guardrailRegistry.register(...)` — რეესტრი ჩაანაცვლებს
   ყველა წინა დამცავ მექანიზმს, რომელსაც იგივე ნორმალიზებული სახელი აქვს.
4. დაამატეთ ტესტები `tests/unit/`-ში (არსებული მაგალითები:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## ინექციისგან დაცვის მარშრუტების დაფარვა და red-team ტესტირება (ფაზა 8 · ბლოკი D)

ინექციისგან დაცვის მექანიზმი (`createInjectionGuard` / `withInjectionGuard`) მოიცავს ყველა მარშრუტს,
რომელიც მომხმარებლის მოთხოვნებს იღებს. ის ითვალისწინებს `INJECTION_GUARD_MODE`-ს (ნაგულისხმევი `warn` = მხოლოდ ჟურნალში ჩაწერა;
`block` = აბრუნებს HTTP 400 `SECURITY_001`-ს).

| ტიპი              | მარშრუტები                                                                                                                                           | ნაგულისხმევი რეჟიმი |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| ტექსტი (არსებული) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | გაფრთხილება         |
| გენერაციული       | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | გაფრთხილება         |
| მონაცემები        | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | გაფრთხილება         |

ტექსტის ამოღება (`extractMessageContents`) მოიცავს `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ველებს.

**Red-team (ყოველღამიური, `nightly-llm-security.yml`):** promptfoo ამოწმებს, რომ თითოეული მარშრუტი ბლოკავს
OWASP-LLM კორპუსს `INJECTION_GUARD_MODE=block` რეჟიმში; garak უშვებს საცდელ შეტევებს (საიდუმლო გასაღების გარეშე გამოტოვებს).
`moderations` თანმიმდევრულობისთვის არის დამატებული. ბლოკირების რეჟიმი სავალდებულო საზღვარია: `evaluatePromptInjection()`
უგულებელყოფს თითოეული მოთხოვნისთვის გამორთულთა სიას, რომელსაც შუამავალი ფენა გადასცემს, ამიტომ `disabledGuardrails`
მარშრუტს მისგან **არ** ათავისუფლებს ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

ყოველღამიური სამუშაო პროცესი (`.github/workflows/nightly-llm-security.yml`, cron + ხელით
გაშვება) ორ დავალებას შეიცავს:

- **`promptfoo-guard` (მაბლოკირებელი)** — ასრულებს `promptfoo eval -c promptfooconfig.yaml`-ს
  `INJECTION_GUARD_MODE=block` რეჟიმით. თითოეული მოწინააღმდეგეობრივი შემთხვევა (მაგ., "უგულებელყავი ყველა
  წინა ინსტრუქცია…", DAN-ის სტილის jailbreak-ები) ამოწმებს, რომ პასუხი შეიცავს
  `error.code === "SECURITY_001"`-ს, ანუ დამცავმა მექანიზმმა მოთხოვნა რეალურად უარყო.
- **`garak` (სარეკომენდაციო)** — ასრულებს garak-ს `--probes promptinject,dan,leakreplay` პარამეტრით
  ლოკალური OmniRoute ინსტანციის მიმართ (`http://localhost:20128/v1`). მისი გაშვება დამოკიდებულია
  პროვაიდერის საიდუმლო გასაღებზე (`PROMPTFOO_PROVIDER_KEY`); გასაღების არარსებობისას უპრობლემოდ გამოიტოვება და ბოლოში
  ერთვის `|| true`, ამიტომ შედეგს აცნობებს CI-ის ჩავარდნის გარეშე.

დაცვის დამხმარე ფუნქციის (`createInjectionGuard` / `withInjectionGuard`) დაფარვა
ვრცელდება მოთხოვნის შემცველ ყველა `/v1` მარშრუტზე; მოთხოვნის ტექსტი ამოიღება
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ველებიდან
`extractMessageContents()`-ის საშუალებით, რომელიც მდებარეობს `src/shared/utils/inputSanitizer.ts`-ში.
