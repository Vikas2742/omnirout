ส่งออกบันทึกการเรียก OmniRoute ไปยังแหล่งจัดเก็บข้อมูลวิเคราะห์ภายนอกอย่างต่อเนื่อง โดยส่งออกเฉพาะรายการที่เพิ่มขึ้น

แท็บ Logs ในแดชบอร์ดเก็บประวัติคำขอไว้ใน SQLite (`call_logs`) ซึ่งมีขอบเขตจำกัดตาม
การหมุนเวียนและระยะเวลาเก็บรักษา การส่งออกบันทึกจะส่งชุดระเบียนเดียวกันออกไปตามกำหนดเวลา เพื่อให้เก็บไว้ได้นานกว่า
ฐานข้อมูลภายในเครื่องและนำไปเชื่อมกับข้อมูลอื่นได้ BigQuery เป็นปลายทางแรก โดย
ไปป์ไลน์ใช้รูปแบบรีจิสทรี จึงสามารถเพิ่มปลายทางอื่นได้โดยไม่ต้องเปลี่ยนโครงสร้างเดิม

## 1. วิธีการทำงาน

```
server (decrypt + validate config, reconcile cursor)
  → start IPC → isolated exportChild OS process
    → read-only storage.sqlite → shared call-log query/mapping
      → async artifact hydration → destination prepare()/send()
        → batch IPC → server persists cursor → ack IPC
          → next batch; done IPC → server records success
```

- **กำหนดเวลา** — งาน cron ของ `JobRegistry` หนึ่งงานชื่อ `log_export` มีค่าเริ่มต้นเป็น `0 * * * *` (ทุกชั่วโมง,
  UTC) ลงทะเบียนไว้ใน `src/lib/initCloudSync.ts` และสามารถกำหนดทับด้วย `OMNIROUTE_LOG_EXPORT_CRON`
  การทำงานแต่ละรอบจะส่งข้อมูลที่ค้างอยู่ไปยังทุกปลายทางที่**เปิดใช้งาน**ตามลำดับ
- **เคอร์เซอร์** — ใช้ `call_logs.rowid` โดยนัยของ SQLite และบันทึกแยกตามปลายทางไว้ใน
  `log_export_destinations.cursor_row_id` โดยตั้งใจไม่ใช้ `timestamp` เป็นเคอร์เซอร์: ผู้เรียก
  อาจระบุค่าเองได้ ดังนั้นคำขอที่ช้าอาจถูกเขียนหลังคำขอที่เร็วกว่าแต่เริ่มทีหลัง
  และเคอร์เซอร์ที่ใช้เวลาประทับจะข้ามระเบียนนั้นไป
- **การแบ่งชุด** — ส่ง `batch_size` แถวต่อคำขอ (ค่าเริ่มต้น 500) และ `max_rows_per_run` แถวต่อการทำงานหนึ่งครั้ง
  (ค่าเริ่มต้น 10000) เพื่อให้ทยอยส่งข้อมูลค้างจำนวนมากในหลายรอบ แทนที่จะกีดขวางการทำงานรอบเดียว
- **การส่งมอบ** — เคอร์เซอร์จะเลื่อนไปข้างหน้าหลังจาก `send()` สำเร็จแล้วเท่านั้น หากชุดข้อมูลล้มเหลว
  เคอร์เซอร์จะคงอยู่ที่เดิม จึงมีการลองส่งแถวเดิมอีกครั้งในการทำงานรอบถัดไป การรับประกันคือ
  ส่งอย่างน้อยหนึ่งครั้งร่วมกับการกำจัดข้อมูลซ้ำฝั่งปลายทาง ไม่ใช่ส่งครั้งเดียวอย่างแท้จริง: BigQuery ใช้
  ID ของบันทึกการเรียกเป็นคีย์ของแต่ละแถว โดยพยายามกำจัดข้อมูลซ้ำตามคีย์นี้ภายในช่วงเวลาการกำจัดข้อมูลซ้ำของตนเอง
- **การป้องกันการทำงานซ้อนกัน** — รอบ cron และ `POST .../run` อาจเริ่มทำงานพร้อมกันได้ ปลายทาง
  ที่กำลังส่งข้อมูลค้างอยู่จะถูกข้ามแทนการส่งซ้ำสองรอบ (`skipped: true` ในผลการทำงาน)
  ดังนั้นการทำงานพร้อมกันจึงไม่สามารถส่งชุดข้อมูลซ้ำหรือเขียนเคอร์เซอร์ย้อนกลับได้
- **การกู้คืนหลังล้างข้อมูล** — หาก `cursor_row_id` มีค่าสูงกว่า `MAX(rowid)` (มีการล้างทั้งตาราง
  และเริ่ม rowid ใหม่) ตัวรันจะย้อนกลับไปที่ 0 แทนที่จะมองไม่เห็นข้อมูลใหม่อย่างถาวร

### ตัวรันแบบแยกและขีดจำกัด

การทำงานของแต่ละปลายทางบน Node จะเริ่มโพรเซสลูกของระบบปฏิบัติการที่แยกต่างหากและมีอายุสั้น (`child_process`
ที่ใช้ IPC ไม่ใช่ `worker_threads`) การอ่านเนื้อหา การแยกวิเคราะห์/ซีเรียลไลซ์ JSON ของเพย์โหลด
`prepare()` ของปลายทาง และ I/O เครือข่ายของปลายทางทั้งหมดทำงานในโพรเซสนั้น ไม่ใช่บน event loop ของเซิร์ฟเวอร์
มีเพียงการกำหนดค่าและข้อความรายงานความคืบหน้าขนาดเล็กเท่านั้นที่ส่งผ่าน IPC ระเบียนที่ส่งออกจะไม่ถูกส่งกลับไปยัง
เซิร์ฟเวอร์ งาน cron และเส้นทาง Run now ยังคงผลลัพธ์สาธารณะและการป้องกันการทำงานซ้อนกันไว้เหมือนเดิม

โพรเซสลูกเปิด `DATA_DIR/storage.sqlite` ตามพาธที่เซิร์ฟเวอร์ระบุไว้ในโหมดอ่านอย่างเดียวโดยใช้ `node:sqlite`
พร้อม `busy_timeout=5000` และ `query_only=ON` โดยไม่อิมพอร์ต DB singleton และไม่ทำ
การย้ายโครงสร้างข้อมูล การสำรองข้อมูล หรือการอัปเดต SQLite การจัดการข้อมูลกำกับอาร์ติแฟกต์ที่หายไป/เสียหาย (รวมถึง
คำสั่ง UPDATE สำหรับอาร์ติแฟกต์ที่เสียหาย) ยังคงอยู่เฉพาะในเส้นทางรายละเอียดของแดชบอร์ด ทั้งสองเส้นทางใช้
ตัวแก้ไขรายละเอียดแบบ pure ร่วมกัน การส่งออกใช้การอ่านระบบไฟล์แบบอะซิงโครนัสและลำดับการค้นหาเดียวกันคือ อาร์ติแฟกต์ → ข้อมูลแบบเก่า
ที่ฝังในระเบียน → ข้อมูลแบบเก่าบนดิสก์ → ไม่มีข้อมูล การทำงานแต่ละครั้งจะบันทึกค่าสูงสุดของ rowid สำหรับการแทรก
เมื่อโพรเซสลูกเปิดตัวอ่าน ข้อมูลที่แทรกภายหลังจะรอการทำงานรอบถัดไป นี่คือขอบเขต
การแทรกข้อมูล ไม่ใช่ธุรกรรม SQLite ที่เปิดค้างไว้นาน: ตัวเขียน WAL และเช็กพอยต์ยังทำงานได้ตามปกติระหว่าง
รอเครือข่าย ขอบเขตนี้ไม่ได้ตรึงการอัปเดต/การลบแถวที่มีอยู่แล้ว

หลังจากแต่ละชุดข้อมูลได้รับการยอมรับ โพรเซสลูกจะรอการตอบรับ เซิร์ฟเวอร์จะบันทึก
เคอร์เซอร์ด้วย `advanceLogExportCursor` ก่อน จากนั้นจึงส่ง `ack` โดยจะไม่เริ่มชุดถัดไปก่อนขั้นตอนนี้
การส่งล้มเหลว การขัดข้อง หรือการหมดเวลาจะบันทึกความล้มเหลวโดยไม่เลื่อนเคอร์เซอร์ของชุดนั้น ชุดข้อมูลที่
ได้รับการตอบรับแล้วจะยังคงถูกบันทึกไว้ มีเพียงชุดเดียวที่ยังไม่ได้รับการตอบรับเท่านั้นที่อาจถูกส่งซ้ำ
ระบบจะบันทึกความสำเร็จหลังจากได้รับ `done` และโพรเซสลูกจบการทำงานตามปกติเท่านั้น เมื่อเกิดความล้มเหลวจะยุติโพรเซสลูก
ด้วย SIGTERM และเพิ่มระดับเป็น SIGKILL หลังจาก 500 ms โดยตัวรันจะรอจนโพรเซสปิด

| ตัวแปรสภาพแวดล้อม                             | ค่าเริ่มต้น | วัตถุประสงค์                                   |
| --------------------------------------------- | ----------- | ---------------------------------------------- |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000      | ขีดจำกัดเวลาจริงต่อปลายทาง                     |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024        | ขีดจำกัด old-space ของ V8 ในโพรเซสลูก หน่วย MB |

ค่าที่ไม่ถูกต้อง/ไม่เป็นบวก/ไม่ใช่จำนวนเต็มจะใช้ค่าเริ่มต้น การตั้งค่าฮีปไม่ใช่ขีดจำกัด
RSS ทั้งหมด ชุดข้อมูลที่ใหญ่มากยังอาจใช้หน่วยความจำของโพรเซสลูกจนหมดและทำให้การทำงานล้มเหลวอย่างปลอดภัยได้
ค่าเริ่มต้น 1024 MB เผื่อพื้นที่ไว้สำหรับชุดข้อมูลเริ่มต้น 500 แถวที่มีอาร์ติแฟกต์ขนาด 512 KiB และ
เปิดใช้งานเนื้อหา รวมถึงการซีเรียลไลซ์ JSON แบบแบ่งตามจำนวนไบต์ของ BigQuery แต่ไม่ได้ทำให้
ชุดข้อมูล 10000 แถวที่มีเนื้อหาปลอดภัยต่อการใช้งาน เมื่อฮีป V8 หมด ระบบจะบันทึกความล้มเหลวพร้อมแนวทางแก้ไข: ลดขนาด
ชุดข้อมูลหรือเพิ่ม `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` โดยเคอร์เซอร์จะคงอยู่ที่ชุดล่าสุด
ที่ได้รับการตอบรับ เนื้อหาเก่าที่ฝังในระเบียน/อยู่บนดิสก์ไม่ได้อยู่ภายใต้ขีดจำกัดอาร์ติแฟกต์แบบใหม่
ผู้ดูแลระบบต้องจัดสรรงบประมาณ RSS แยกต่างหาก โดยเฉพาะภายในคอนเทนเนอร์ที่จำกัดหน่วยความจำ

โปรเซสลูกจะรับสืบทอดเฉพาะ `DATA_DIR` ที่ระบุค่าแล้ว, `NODE_ENV`, `TZ` ที่กำหนดไว้อย่างชัดเจน (การตีความเวลาท้องถิ่น
จากชื่อไฟล์แบบเดิม), `ELECTRON_RUN_AS_NODE` หากมี และค่าอินพุตสำหรับการเชื่อมต่อขาออกต่อไปนี้:
`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (รวมถึงรูปแบบตัวพิมพ์เล็ก),
`OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`
ตัวกระจายคำขอ Undici ส่วนกลางใช้กลไกการกำหนดพร็อกซีจากสภาพแวดล้อมเพียงอย่างเดียวและกฎการข้ามพร็อกซีสำหรับโฮสต์ภายใน
ร่วมกับเซิร์ฟเวอร์ รวมถึง `NO_PROXY`; โดยไม่ได้นำเข้า `proxyFetch.ts` หรือแฟล็ก DB/ฟีเจอร์ของไฟล์ดังกล่าว
ข้อมูลรับรองพร็อกซีจะถูกปกปิดจากเอาต์พุตที่ส่งต่อและข้อผิดพลาดที่บันทึกไว้ ข้อมูลรับรองของปลายทาง
จะถูกส่งผ่านข้อความ IPC สำหรับเริ่มต้นเพียงข้อความเดียวเท่านั้น ไม่ผ่าน argv หรือสภาพแวดล้อม; เอาต์พุต/ข้อผิดพลาดที่ส่งต่อจะ
มีคำนำหน้าและผ่านการกรองข้อมูลที่ละเอียดอ่อน อาร์กิวเมนต์ exec ของโปรเซสลูกจะปิดใช้เฉพาะ `ExperimentalWarning` เพื่อหลีกเลี่ยง
การแสดงคำเตือน SQLite ของ Node ซ้ำทุกครั้งที่ cron ทำงาน; คำเตือนประเภทอื่นยังคงแสดงตามปกติ

โมดูลปลายทางต้องนำเข้าได้โดยไม่พึ่งพา Next.js/ส่วนที่ใช้ได้เฉพาะเซิร์ฟเวอร์ การใช้งาน
BigQuery ที่มีอยู่เป็นไปตามข้อกำหนดนี้แล้ว แคชโทเค็นการเข้าถึงจะคงอยู่เฉพาะช่วงที่โปรเซสลูก
ทำงานเท่านั้น ไม่คงอยู่ข้ามการทำงานแต่ละครั้ง Node คือรันไทม์ที่รองรับ (engines ใน `package.json`) แต่ส่วนการติดตั้ง Bun ใน README
และ `Dockerfile.bun` ยังระบุแนวทางที่เข้ากันได้สำหรับใช้งานจริงผ่าน
`bun:sqlite` (`src/lib/db/core.ts` / อะแดปเตอร์) ด้วย ดังนั้นเมื่อใช้ Bun การส่งออกจะยังคงใช้
แนวทางเดิมที่ทำงานภายในโปรเซส และแสดงคำเตือนครั้งเดียวว่า: ไม่สามารถแยกฮีป/การหมดเวลาของโปรเซสลูกได้ ให้ใช้
Node เพื่อแยกผลกระทบต่อ event loop และภาวะหน่วยความจำไม่เพียงพอ (OOM); ในที่นี้ไม่ได้ถือว่า Bun ใช้สำหรับการพัฒนาเท่านั้น

เมื่อเปิดใช้ `includeBodies` ควรกำหนดรอบการทำงานในระดับนาที เช่น
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` แทนการสะสมเพย์โหลดค้างไว้รายชั่วโมง
ขีดจำกัดแบตช์และจำนวนแถวยังคงจำกัดปริมาณงานแต่ละครั้ง การเริ่มโปรเซสมีต้นทุนต่อปลายทางต่อการทำงานแต่ละครั้ง;
นี่คือการแลกต้นทุนการเริ่มต้นเล็กน้อยกับการแยกผลกระทบต่อ event loop ของเซิร์ฟเวอร์ ไม่ใช่การลดการใช้ CPU โดยรวม

### เพย์โหลด (พรอมป์ต์และคำตอบ)

โดยค่าเริ่มต้น การส่งออกจะมีเฉพาะฟิลด์สรุปที่แสดงใน**รายการ**บันทึก การเปิด
**ส่งออกพรอมป์ต์และคำตอบ** (`includeBodies`) จะส่งข้อมูลที่แสดงในบานหน้าต่าง**รายละเอียด**
ของบันทึกสำหรับแต่ละการเรียกเพิ่มด้วย:

| ฟิลด์                            | ข้อมูลที่เก็บ                                               |
| -------------------------------- | ----------------------------------------------------------- |
| `request_body` / `response_body` | เพย์โหลดของการเรียกตามที่แดชบอร์ดแสดง                       |
| `pipeline_route_decision`        | เป้าหมายและโมเดลที่เราเตอร์เลือก                            |
| `pipeline_client_request`        | คำขอดิบตรงตามที่ไคลเอนต์ส่งมา                               |
| `pipeline_openai_request`        | ข้อมูลหลังแปลงเป็นรูปแบบ OpenAI ภายใน                       |
| `pipeline_provider_request`      | ข้อมูลที่ส่งไปยังระบบต้นทางจริงในรูปแบบเฉพาะของผู้ให้บริการ |
| `pipeline_provider_response`     | คำตอบดิบจากระบบต้นทาง                                       |
| `pipeline_client_response`       | ข้อมูลที่ส่งกลับให้ผู้เรียก                                 |
| `pipeline_error`                 | รายละเอียดข้อผิดพลาดระดับไปป์ไลน์สำหรับการเรียกที่ล้มเหลว   |
| `bodies_truncated`               | เป็นจริงเมื่อฟิลด์ใดก็ตามข้างต้นถึงขีดจำกัด `maxBodyBytes`  |

ข้อมูลนี้เป็นเนื้อหาพรอมป์ต์ จึง**ปิดไว้โดยค่าเริ่มต้น** และตั้งใจให้เลือกเปิดแยกตามปลายทาง
ข้อมูลที่ส่งออกคือข้อมูลเดียวกับที่แดชบอร์ดแสดง เนื่องจากการส่งออกและ `getCallLogById` ใช้กลไก
การดึงรายละเอียดร่วมกัน: เพย์โหลด
ผ่านการกรองข้อมูลส่วนบุคคลที่ระบุตัวตนได้ (PII) และปกปิดข้อมูลลับแล้วเมื่อบันทึก และการเรียกที่ใช้
คีย์ API แบบ `noLog` จะไม่เก็บเพย์โหลดใด ๆ จึงไม่มีข้อมูลให้ส่งออก

เพย์โหลดจะถูกอ่านทีละแถวจากอาร์ติแฟกต์ในระบบไฟล์ ดังนั้นการโหลดข้อมูลประกอบจึงทำเฉพาะกับปลายทาง
ที่ร้องขอเท่านั้น หากอาร์ติแฟกต์หายไปหรือเสียหาย ระบบจะส่งออกข้อมูลสรุปพร้อมเพย์โหลดเป็น null แทน
การทำให้ทั้งแบตช์ล้มเหลวและเคอร์เซอร์ค้างอยู่

`maxBodyBytes` (ค่าเริ่มต้น 262144) จำกัดขนาดของแต่ละฟิลด์ เพย์โหลดที่ยาวกว่าจะถูก**ตัดให้สั้นลงแทนที่จะ
ทิ้งไป** — พรอมป์ต์ที่ถูกตัดยังคงบอกได้ว่า "ถามอะไรไป" — และแถวนั้นจะถูกทำเครื่องหมายด้วย
`bodies_truncated` จะไม่ส่งออกข้อมูลส่วนต่างที่สตรีมมาทีละชังก์; คำตอบที่ประกอบเสร็จแล้ว
อยู่ใน `pipeline_provider_response` และ `pipeline_client_response` อยู่แล้ว

## 3. REST API

ทุกเส้นทางต้องผ่านการยืนยันตัวตนสำหรับการจัดการ (`requireManagementAuth`) ข้อมูลลับจะไม่ถูกส่งกลับ:
ข้อมูลลับที่จัดเก็บไว้จะถูกส่งกลับเป็นค่าตามตัวอักษร `__stored__` และการส่งค่านั้นกลับมาเมื่ออัปเดต
จะคงข้อมูลรับรองที่จัดเก็บไว้

การสร้างหรืออัปเดตปลายทางที่ประเภทของปลายทางระบุว่ามีข้อมูลลับ **จำเป็นต้องมี
`STORAGE_ENCRYPTION_KEY`** หากไม่มีค่านี้ `encrypt()` จะส่งข้อมูลผ่านโดยไม่เข้ารหัสและไม่แจ้งเตือน ดังนั้นการเขียนข้อมูลจึง
ถูกปฏิเสธด้วยสถานะ 400 แทนที่จะบันทึกข้อมูลรับรองลงใน SQLite เป็นข้อความธรรมดา (เป็นมาตรการป้องกันเดียวกับที่
webhook ของ Telegram ใช้)

| เมธอด    | เส้นทาง                                  | วัตถุประสงค์                                                              |
| -------- | ---------------------------------------- | ------------------------------------------------------------------------- |
| `GET`    | `/api/log-export/types`                  | ประเภทปลายทาง + รายการฟิลด์การกำหนดค่าของแต่ละประเภท                      |
| `GET`    | `/api/log-export/destinations`           | แสดงรายการปลายทาง (ปกปิดข้อมูลลับ)                                        |
| `POST`   | `/api/log-export/destinations`           | สร้างปลายทาง                                                              |
| `GET`    | `/api/log-export/destinations/{id}`      | อ่านข้อมูลปลายทางหนึ่งรายการ                                              |
| `PUT`    | `/api/log-export/destinations/{id}`      | อัปเดตชื่อ / สถานะเปิดใช้งาน / การกำหนดค่า / การแบ่งเป็นชุด               |
| `DELETE` | `/api/log-export/destinations/{id}`      | ลบ                                                                        |
| `POST`   | `/api/log-export/destinations/{id}/test` | ทดสอบข้อมูลรับรองโดยไม่เขียนข้อมูลใด ๆ                                    |
| `POST`   | `/api/log-export/destinations/{id}/run`  | ส่งข้อมูลค้างทั้งหมดทันที โดยใช้เส้นทางการทำงานเดียวกับการรันตามกำหนดเวลา |
| `GET`    | `/api/log-export/status`                 | สถานะ Cron, การรันล่าสุด, ข้อมูลค้างของแต่ละปลายทาง                       |

`GET /api/log-export/types` ทำให้ UI รองรับปลายทางได้ทุกประเภท: ฟอร์มบนแดชบอร์ดถูกสร้างจาก
คำอธิบายฟิลด์ที่ส่งกลับมา จึงไม่จำเป็นต้องเปลี่ยน UI เมื่อเพิ่มปลายทางใหม่

## 4. ปลายทาง BigQuery

คีย์การกำหนดค่า (`type: "bigquery"`):

| คีย์                 | หมายเหตุ                                                             |
| -------------------- | -------------------------------------------------------------------- |
| `projectId`          | โปรเจ็กต์ GCP ที่เก็บชุดข้อมูล                                       |
| `datasetId`          | `[A-Za-z0-9_]+`                                                      |
| `tableId`            | `[A-Za-z0-9_]+`                                                      |
| `location`           | ใช้เฉพาะเมื่อต้องสร้างชุดข้อมูล (ค่าเริ่มต้น `EU`)                   |
| `serviceAccountJson` | คีย์บัญชีบริการ เป็นข้อมูลลับ: เข้ารหัสขณะจัดเก็บและไม่ส่งคืนเด็ดขาด |
| `autoCreate`         | สร้างชุดข้อมูลและตารางเมื่อส่งออกครั้งแรก (ค่าเริ่มต้น `true`)       |

บัญชีบริการต้องมีสิทธิ์ `bigquery.tables.updateData` ในตารางเป้าหมาย รวมถึง
`bigquery.datasets.create` / `bigquery.tables.create` เมื่อเปิดใช้ `autoCreate`

แบตช์ที่กำหนดค่าไว้เป็นหน่วยของ **เคอร์เซอร์** ไม่ใช่หน่วยของ HTTP: `send()` จะแบ่งแบตช์ออกเป็นการเรียก insertAll
ครั้งละไม่เกิน 500 แถว ดังนั้น `batch_size` ที่มีขนาดใหญ่จึงไม่ทำให้คำขอเกินขีดจำกัด 10 MB ของ BigQuery
สถานะข้อผิดพลาดชั่วคราว (408/429/500/502/503/504) จะได้รับการลองใหม่สูงสุดสามครั้ง โดยเพิ่มระยะเวลารอแบบทวีคูณ
และใช้ insertIds เดิมซ้ำ ส่วนข้อผิดพลาดด้านการยืนยันตัวตนและสคีมาจะโยนข้อผิดพลาดตั้งแต่ความพยายามครั้งแรก แทนที่จะ
ปล่อยให้การทำงานรอบนั้นเสียเวลาโดยเปล่าประโยชน์

ตารางที่เพิ่งสร้างจะยังไม่ปรากฏต่อเอนด์พอยต์สตรีมมิง ซึ่งจะตอบกลับด้วย
404 เป็นเวลาสองสามวินาที ระบบจะลองใหม่เมื่อพบ 404 นี้ แต่**เฉพาะเมื่อการทำงานรอบนี้เป็นผู้สร้างตารางเท่านั้น** —
หากตารางไม่มีอยู่จริง ระบบจะยังคงล้มเหลวทันที โปรดทราบว่าการสร้างตารางขึ้นใหม่ด้วยชื่อที่
เพิ่งถูกลบไปจะทำให้ BigQuery ปฏิเสธการแทรกข้อมูลแบบสตรีมมิงเป็นเวลาหลายนาที นี่เป็น
พฤติกรรมของการลบแล้วสร้างใหม่ ดังนั้นควรใช้ชื่อตารางใหม่แทนการลบแล้วเพิ่มตารางเดิมอีกครั้ง

**ความล้มเหลวบางส่วนจะส่งกลับมาเป็น HTTP 200 พร้อม `insertErrors[]` ที่ไม่ว่าง** ระบบจะถือว่าเป็น
ความล้มเหลวและโยนข้อผิดพลาด ซึ่งจะหยุดเคอร์เซอร์ไม่ให้เลื่อนผ่านแถวที่ BigQuery
ยังไม่ได้รับไว้ โดย `tests/unit/log-export-bigquery.test.ts` จะตรวจสอบให้พฤติกรรมนี้คงเดิม

การรับส่งข้อมูลใช้ REST โดยตรง — โดยนำ assertion แบบ RS256 ที่ลงลายมือชื่อด้วยตนเองไปแลกเป็นโทเค็นการเข้าถึงที่
`https://oauth2.googleapis.com/token` จากนั้นส่งแถวไปยัง `tabledata.insertAll` โดยไม่มีการนำ Google SDK
เข้ามาใช้ โทเค็นการเข้าถึงจะถูกแคชไว้ภายในโปรเซส แยกตามคู่ (บัญชีบริการ, ขอบเขตสิทธิ์)

ตารางที่สร้างขึ้นจะมีหนึ่งคอลัมน์ต่อฟิลด์ในแท็บ Logs พร้อมด้วย `exported_at` และจัดโครงสร้างให้เหมาะกับ
วิธีที่ใช้ค้นหาบันทึกการเรียกใช้งานจริง:

- **แบ่งพาร์ทิชันรายวันตาม `timestamp`** เพื่อให้การค้นหาที่จำกัดช่วงวันที่สแกนเฉพาะวันเหล่านั้น
- **จัดคลัสเตอร์ตาม `api_key_name`, `provider`, `model`, `status`** (ตามลำดับนี้) เพื่อให้การกรองตาม
  ผู้เรียกใช้งาน ปลายทางที่ส่งไป หรือการทำงานล้มเหลวหรือไม่ ช่วยตัดบล็อกที่ไม่เกี่ยวข้องภายในแต่ละพาร์ทิชันออก BigQuery
  อนุญาตให้มีคอลัมน์คลัสเตอร์ได้สูงสุดสี่คอลัมน์ และลำดับมีความสำคัญ: การกรองเฉพาะ `api_key_name`
  ช่วยตัดบล็อกที่ไม่เกี่ยวข้องได้ แต่การกรองเฉพาะ `status` ทำไม่ได้
- **เลือกกำหนดระยะเวลาเก็บรักษาพาร์ทิชันได้** ผ่าน `partitionExpirationDays` (0 หมายถึงเก็บทุกอย่างไว้) โดยจะนำไปใช้
  เมื่อสร้างตาราง

การตั้งค่าทั้งสองจะมีผลในขณะสร้างตาราง ตารางที่มีอยู่แล้วจะคงโครงสร้างเดิมไว้ ดังนั้น

## 5. ปลายทางสำหรับ traces แบบ OTLP/HTTP

การกำหนดค่าใช้ `type: "otlp-http"` นี่คือการส่งออกบันทึกการเรียกใช้ที่จัดเก็บไว้ถาวรตามกำหนดเวลา
โดยใช้เคอร์เซอร์ ไม่ใช่ตัวรับเหตุการณ์ routing แบบสดที่ทำงานแบบ best-effort ใน
`open-sse/services/routing/otel.ts` โดยจะไม่อ่านหรือเปลี่ยนแปลงตัวแปรสภาพแวดล้อม
ตัวจับเวลา หรือบัฟเฟอร์ของตัวรับนั้น การเปิดใช้งานทั้งสองอย่างอาจสร้าง span สองประเภทที่เป็นอิสระจากกัน;
ให้ใช้ instrumentation scope `omniroute.log-export` เพื่อแยกแยะ span จากบันทึกการเรียกใช้เหล่านี้

| คีย์              | ค่าเริ่มต้น / วัตถุประสงค์                                                          |
| ----------------- | ----------------------------------------------------------------------------------- |
| `endpoint`        | ต้องระบุ URL ของ traces แบบ HTTP(S) ที่สมบูรณ์; ไม่มีการต่อท้ายด้วย `/v1/traces`    |
| `headers`         | บรรทัด `Name: value` หรือออบเจ็กต์ JSON ของสตริงที่ระบุได้ตามต้องการ; มีการเข้ารหัส |
| `serviceName`     | `omniroute`; แอตทริบิวต์ทรัพยากร `service.name`                                     |
| `langfuseMapping` | `false`; เพิ่มแอตทริบิวต์ generation/session/user ของ Langfuse                      |
| `identity`        | `pseudonymous`, `keyName` หรือ `none`                                               |
| `paths`           | `/v1/chat/completions`, `/v1/responses`, `/v1/messages`                             |
| `timeoutMs`       | `30000` ต่อการพยายามส่ง HTTP แต่ละครั้ง                                             |
| `environment`     | ไม่ได้ตั้งค่า; `langfuse.environment` ที่ระบุได้ตามต้องการ                          |

แดชบอร์ดทั่วไปแสดงฟิลด์เหล่านี้ `paths` รับอาร์เรย์ผ่าน API หรือ textarea
ที่มีพาธตรงตามจริงคั่นด้วยการขึ้นบรรทัดใหม่/จุลภาค โดยจะข้ามพาธของ embeddings, rerank และพาธอื่น ๆ
เว้นแต่จะอนุญาตไว้อย่างชัดเจน แถวที่ถูกข้ามยังคงเลื่อนเคอร์เซอร์ไปข้างหน้า; ตัวนับ
`exported`/`exportedTotal` ของตัวรันที่มีอยู่จะนับแถวต้นทางที่ประมวลผลแล้ว รวมถึงแถวที่ถูกกรองออก
ไม่ใช่ span ที่ได้รับการยอมรับ การกรองดำเนินการในโปรเซสลูก โดยไม่เปลี่ยนแปลง
ข้อกำหนด IPC/เคอร์เซอร์ของโปรเซสนั้น

การตรวจสอบ URL ใช้ฟังก์ชันช่วย `parseAndValidateNonMetadataUrl` ที่ไม่ต้องใช้ DB จาก
`src/shared/network/outboundUrlGuard.ts`: นโยบาย `block-metadata` โดยมีการตรวจสอบ
metadata/โปรโตคอล/ข้อมูลรับรองที่ฝังอยู่แบบไม่มีเงื่อนไขเช่นเดียวกับตัวตรวจสอบ webhook ที่เปิดให้ใช้
URL ส่วนตัว แต่จงใจอนุญาตปลายทาง localhost/LAN โดยไม่ต้องใช้
feature flag ส่วนกลางเพื่อแทนที่ข้อจำกัด ซึ่งช่วยให้ใช้ปลายทาง Langfuse, Phoenix, Tempo และ Collector
ที่โฮสต์เองได้ รวมถึงปลายทาง HTTP ส่วนตัว โฮสต์ cloud-metadata จะถูกบล็อกเสมอ
ไม่มีการติดตามการเปลี่ยนเส้นทาง ดังนั้น collector จึงไม่สามารถเปลี่ยนเส้นทางข้อมูลรับรองไปยังโฮสต์อื่นได้
เช่นเดียวกับตัวป้องกัน URL แบบตรวจสอบข้อความที่มีอยู่ วิธีนี้ไม่ได้ตรึงผลการ resolve DNS; ให้กำหนดค่า
เฉพาะโฮสต์ที่ผู้ดูแลระบบควบคุมเท่านั้น ควรใช้ HTTPS เมื่อปลายทางไม่ได้อยู่บนเครือข่ายที่เชื่อถือได้

### เพย์โหลดและการส่ง

OTLP/HTTP JSON (`ExportTraceServiceRequest`, `Content-Type: application/json`) บรรจุ
span ชนิด CLIENT หนึ่งรายการต่อแถวที่อนุญาต โดยตั้งชื่อตามพาธคำขอที่ตรงตามจริง การตั้งชื่อตามพาธช่วยแยกแยะ
Chat Completions, Responses และ Messages โดยไม่ฝังข้อมูลโมเดลหรืออัตลักษณ์ไว้ใน
ชื่อ span แอตทริบิวต์ทรัพยากรประกอบด้วย `service.name` และ `service.version` ของแพ็กเกจ

ตัวบันทึกความพยายามแชทตามปกติ (`open-sse/handlers/chatCore/attemptLogging.ts`) เขียนค่า
`duration = Date.now() - startTime` เมื่อเสร็จสิ้น และไม่ได้ระบุประทับเวลา;
`saveCallLogOperation` ใน `src/lib/usage/callLogs.ts` จะกำหนดประทับเวลาเริ่มต้นเป็นเวลา
ที่เขียนข้อมูล (เมื่อเสร็จสิ้น) ดังนั้นการส่งออกจึงตั้งเวลาสิ้นสุด = ประทับเวลาของแถว และเวลาเริ่มต้น = เวลาสิ้นสุด − ระยะเวลา
(หน่วยมิลลิวินาที แปลงเป็นนาโนวินาทีในรูปเลขฐานสิบ) ประทับเวลาในอดีตที่ผู้เรียกใช้ระบุ
จะยังคงถูกใช้เป็นเวลาสิ้นสุดเช่นกัน; ไม่มีตัวบ่งชี้รายแถวเพื่อแยกว่าเป็นเวลาเริ่มต้นหรือเวลาเสร็จสิ้น
ระยะเวลาที่เป็น null จะกลายเป็นศูนย์ ประทับเวลาที่ไม่ถูกต้องหรือขาดหายไปจะทำให้แบตช์ล้มเหลว แทนที่จะสร้าง
span ที่ให้ผลไม่แน่นอน `ttftMs` สามารถเป็น null ได้ และแมปไปยัง `omniroute.ttft_ms`

แอตทริบิวต์ประกอบด้วย `gen_ai.operation.name="chat"`, ผู้ให้บริการ, โมเดลที่ร้องขอ/โมเดลที่ตอบกลับ,
โทเคนขาเข้า/ขาออก, โทเคนการอ่านแคช/การสร้างแคช/การให้เหตุผลที่ระบุได้ตามต้องการ, สถานะ HTTP,
combo, แหล่งที่มาของแคช, แท็กเซสชัน และรหัสสหสัมพันธ์ ค่า OTLP แบบจำนวนเต็มและประทับเวลา
เป็นสตริงเลขฐานสิบ; สตริง บูลีน และตัวเลขที่มีส่วนทศนิยมใช้ชนิดค่า OTLP
ตามชนิดข้อมูลของตนเอง span ที่มีข้อผิดพลาดจะมีสถานะ ERROR และข้อความสถานะที่ผ่านการกรองข้อมูลแล้ว ระเบียนมาตรฐาน
ไม่มี URL ของโฮสต์ต้นทาง จึงละ `server.address` ไว้ แทนที่จะระบุ
collector เป็นเซิร์ฟเวอร์โมเดลอย่างไม่ถูกต้อง ไม่มีการส่งออกค่าใช้จ่าย

เฉพาะ `includeBodies=true` เท่านั้นที่จะดึงเนื้อหามาเติม เมื่อ `langfuseMapping=false`,
`gen_ai.input.messages` / `gen_ai.output.messages` จะบรรจุ JSON ของเนื้อหาคำขอ/การตอบกลับ
ที่ผ่านการกรองข้อมูลตามที่ OmniRoute จัดเก็บไว้ (ปรับให้อยู่ในรูปแบบมาตรฐานเมื่อแยกวิเคราะห์ได้) ไม่ใช่อาร์เรย์
messages ตาม semconv ที่ปรับโครงสร้างใหม่ เนื้อหาที่ถูกตัดทอน/ไม่ใช่ JSON จะยังคงเป็นข้อความดิบ เมื่อ `langfuseMapping=true`,
เนื้อหาจะถูกส่งออกเป็น `langfuse.observation.input` / `langfuse.observation.output` เท่านั้น;
แอตทริบิวต์ `gen_ai.*.messages` จะถูกละไว้ เพื่อให้ส่งเนื้อหาแต่ละรายการเพียงครั้งเดียว ทั้งสองโหมด
สืบทอดค่า `maxBodyBytes` จากกระบวนการดึงเนื้อหามาเติมที่มีอยู่;
`omniroute.bodies_truncated=true` ใช้ระบุว่ามีการตัดทอน
ปลายทางนี้ไม่ได้เพิ่มสแนปช็อตของ pipeline หรือการอ่านอาร์ติแฟกต์ที่ยังไม่ผ่านการกรองข้อมูลเพิ่มเติม
เมื่อส่งออกเนื้อหา ให้ใช้ความถี่ระดับนาที เช่น `OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"`
แทนการสะสมงานค้างเป็นรายชั่วโมง

คำขอถูกจำกัดไว้ที่ 500 span และ JSON แบบ UTF-8 ขนาด 4 MiB รวมโครงสร้างห่อหุ้ม
ระบบจะตรวจสอบขนาดของ span ที่อนุญาตทุกรายการก่อนส่งคำขอแรกของชุดข้อมูลเคอร์เซอร์ หาก span ใด
มีขนาดเกินขีดจำกัด ระบบจะไม่ส่งส่วนใดของชุดข้อมูลนั้นและจะล้มเหลวพร้อมคำแนะนำให้ลด
`maxBodyBytes` โดยจะไม่ทิ้ง span นั้นอย่างเงียบ ๆ การตรวจสอบล่วงหน้าเก็บไว้เฉพาะการอ้างอิงระเบียนและ
จำนวนไบต์ โดยทิ้ง span/JSON ชั่วคราวแต่ละรายการ แล้วสร้าง span ขึ้นใหม่สำหรับส่วนย่อยที่จำกัดขนาด
แทนการเก็บสำเนาที่แปลงเป็นข้อมูลอนุกรมชุดที่สองของชุดข้อมูลไว้ HTTP 408/429/5xx ความล้มเหลวของเครือข่าย และการหมดเวลาจะได้รับการลองส่งสูงสุด
สามครั้ง โดยเว้นระยะแบบเอ็กซ์โพเนนเชียลที่ 250/500 ms ค่า `Retry-After` ที่เป็นวินาทีหรือวันที่แบบ HTTP
สามารถขยายเวลารอได้สูงสุด 5 วินาที สถานะอื่นจะล้มเหลวทันที การปฏิเสธบางส่วนของ OTLP ที่มีสถานะ 2xx จะทำให้เกิดข้อผิดพลาดเช่นกัน แทนที่จะ
ยืนยันการรับ span ที่สูญหาย โดยยอมรับการตอบรับที่ว่างเปล่าหรือเป็น JSON ที่ถูกต้อง และ
จำกัดการอ่านการตอบกลับไว้ที่ 64 KiB

ข้อผิดพลาดมีเฉพาะข้อเท็จจริงที่อยู่ในการควบคุมของตัวส่งออก ได้แก่ สถานะ HTTP ประเภทการลองใหม่ จำนวนครั้งที่ลอง และจำนวน span
ที่ส่ง หรือข้อความตายตัวเกี่ยวกับการตอบรับ/ความล้มเหลวของเครือข่าย เนื้อหาการตอบกลับจาก collector
จำนวนรายการที่สำเร็จบางส่วน และส่วนหัวการตอบกลับจะไม่ถูกคัดลอกลงในข้อผิดพลาด บันทึก หรือ
แดชบอร์ด ชุดข้อมูลที่ล้มเหลวหรือได้รับการยอมรับเพียงบางส่วนจะไม่ได้รับการยืนยันการรับ โดยปลายทางจะแสดง
สถานะล้มเหลวพร้อมสถานะดังกล่าว เคอร์เซอร์จะคงอยู่ที่ชุดข้อมูลล่าสุดที่ได้รับการยืนยันการรับ และการทำงานครั้งถัดไป
จะส่งแถวเดิมซ้ำ สถานะถาวรจะทำให้ล้มเหลวต่อไปจนกว่าจะมีการแก้ไข collector หรือการกำหนดค่า
ให้ใช้บันทึกของ collector เองเพื่อดูรายละเอียดการตอบกลับ สรุปข้อผิดพลาดในบันทึกการเรียกใช้ยังคง
ใช้การปกปิดข้อมูลที่แยกต่างหาก
`prepare()` ไม่จัดเตรียมสิ่งใด ปุ่มทดสอบจะส่ง POST ที่มีเนื้อหาเป็น `{"resourceSpans":[]}` เท่านั้น และรายงาน
สถานะ HTTP โดยไม่เขียน span ของบันทึกการเรียกใช้

Trace id และ span id คือเลขฐานสิบหก 32/16 หลักแรกของ SHA-256 ที่คำนวณจาก
`"omniroute.trace\\0" + callLogId` และ `"omniroute.span\\0" + callLogId` การส่งซ้ำจะใช้
id เดิม ทั้งนี้ไม่ได้รับประกันว่าจะมีการขจัดข้อมูลซ้ำ เพราะแบ็กเอนด์บางตัว รวมถึงการรับข้อมูลของ Langfuse
v4 ไม่ขจัด span ที่มี id เดียวกันออก เหตุขัดข้องหรือความล้มเหลวของส่วนย่อยบางส่วนอาจ
ทำให้ส่งซ้ำได้สูงสุดหนึ่งชุดข้อมูลเคอร์เซอร์ที่ยังไม่ได้รับการยืนยันการรับ โดยทั้งชุดข้อมูลนั้นอาจซ้ำกัน
ไม่ใช่เพียงส่วนย่อย HTTP สุดท้ายเท่านั้น ให้เลือกขนาดชุดข้อมูลเคอร์เซอร์โดยคำนึงถึงข้อแลกเปลี่ยนนี้

### ตัวอย่าง Langfuse

กำหนดค่าฟิลด์เหล่านี้สำหรับอินสแตนซ์ Langfuse ที่โฮสต์เอง:

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

สร้างค่า Authorization ในเครื่องโดยเข้ารหัสสตริงตามตัวอักษร `public-key:secret-key`
เป็น Base64 (เช่น ใช้ `Buffer.from(publicKey + ":" + secretKey).toString("base64")`)
อย่าวางข้อมูลรับรองจริงลงในบันทึก ภาพหน้าจอ หรือรายงานปัญหา การแมปจะ
ตั้งค่า `x-langfuse-ingestion-version: 4` โดยอัตโนมัติ ส่วน Authorization ยังคงต้องระบุใน `headers`
ทั้งส่วนหัวและค่า salt สำหรับข้อมูลระบุตัวตนที่สร้างขึ้นจะใช้กลไกฟิลด์ข้อมูลลับที่เข้ารหัส
และค่าตัวยึดใน API ที่มีอยู่ โดยจำเป็นต้องมี `STORAGE_ENCRYPTION_KEY`

การแมปจะเพิ่มประเภท/โมเดลของการสร้าง รายละเอียดการใช้งานแบบ JSON (อินพุต/เอาต์พุต/รวม และคีย์แคช
ที่มีให้ใช้) สแนปช็อตอินพุต/เอาต์พุตแบบ JSON ระดับ ERROR/DEFAULT ข้อความสถานะที่ผ่านการล้างข้อมูล
ชื่อ trace, session id, สภาพแวดล้อมที่ระบุหรือไม่ก็ได้ และ
`langfuse.observation.metadata.<key>` ที่กรองได้สำหรับผู้ให้บริการ โมเดลที่ร้องขอ เส้นทาง combo แหล่งที่มาของแคช
และสถานะ `langfuse.observation.completion_start_time` เป็นค่า ISO 8601 ที่
เวลาเริ่มต้น + TTFT เฉพาะเมื่อทราบ TTFT และค่านั้นอยู่ภายในระยะเวลาเท่านั้น ไม่มีการส่งแอตทริบิวต์ค่าใช้จ่าย

โหมดข้อมูลระบุตัวตนมีผลกับ `langfuse.user.id`:

- `pseudonymous` (ค่าเริ่มต้น): HMAC-SHA256 ของ id ภายในของ API key โดยใช้ salt แบบสุ่ม
  ขนาด 32 ไบต์แยกตามปลายทาง หากยังไม่มี salt ระบบจะสร้างขึ้นเมื่อสร้างปลายทาง เข้ารหัส
  เป็น `identitySalt` ไม่ส่งกลับมา และเก็บไว้ระหว่างการแก้ไข id ของคีย์แบบดิบจะไม่ถูก
  ใส่ลงในแอตทริบิวต์ของ span การสร้างใหม่/หมุนเวียน salt ของปลายทางจะเปลี่ยนข้อมูลระบุตัวตน
- `keyName`: ชื่อ API key ที่กำหนดค่าไว้ ซึ่งจงใจเปิดเผยป้ายกำกับที่ผู้ดูแลตั้งไว้
- `none`: ไม่มี user id แท็กเซสชันยังคงถูกส่งออกหากมีอยู่ โหมดเหล่านี้ไม่ได้
  ทำให้เนื้อหาพรอมป์ต์ใด ๆ หรือป้ายกำกับเซสชัน/ความสัมพันธ์ที่ผู้ดูแลระบุเป็นข้อมูลนิรนาม

### การเริ่มต้นโดยไม่เติมข้อมูลย้อนหลัง

เฉพาะตอนสร้าง ให้เปิดใช้งาน **เริ่มจากตำแหน่งปัจจุบัน (ข้ามบันทึกที่มีอยู่)** หรือส่ง
`startFromCurrentPosition: true` ที่ระดับบนสุดของเพย์โหลด API สำหรับการสร้าง การตั้งค่านี้จะกำหนดค่าเริ่มต้นของ
`cursor_row_id` เป็น rowid สูงสุดปัจจุบันของบันทึกการเรียกใช้ที่ยังเก็บอยู่ โดยใช้ฟังก์ชันช่วยจัดการเคอร์เซอร์
ที่มีอยู่ โดยไม่ต้องย้ายข้อมูล ค่าเริ่มต้นคือ false (เคอร์เซอร์เป็น 0 และเติมข้อมูลย้อนหลังจากประวัติที่ยังเก็บอยู่)
นี่ไม่ใช่การตั้งค่าสำหรับรีเซ็ตเคอร์เซอร์ขณะอัปเดต

การเพิ่ม `ttftMs` ที่ใช้ร่วมกันยังเพิ่มคอลัมน์ `ttft_ms` ที่อนุญาตให้เป็น null ลงในตัวแมป BigQuery
และสคีมาสำหรับตารางใหม่ด้วย โดยการทดสอบสคีมากำหนดให้ทุกฟิลด์ของระเบียนมาตรฐานต้องมี
คอลัมน์ ตารางที่มีอยู่ยังคงส่งออกโดยไม่เปลี่ยนแปลง: `prepare()` จะอ่านสคีมาของตารางและ
ละเว้นเฉพาะ `ttft_ms` เมื่อไม่มีคอลัมน์ดังกล่าว เพิ่มคอลัมน์ INT64 ที่อนุญาตให้เป็น null เพื่อรับ TTFT
ในการทำงานครั้งถัดไป หรือใช้ตารางใหม่ ไม่จำเป็นต้องใช้ PATCH การปรับสคีมาอัตโนมัติ หรือ
สิทธิ์เพิ่มเติม ฟิลด์อื่นทั้งหมดของแถวยังคงได้รับการตรวจสอบสคีมาอย่างเข้มงวด

## 6. การเพิ่มปลายทาง

1. สร้าง `src/lib/logExport/destinations/<name>.ts` ที่ส่งออก `LogExportDestinationType`:
   โดยมี Zod `configSchema`, อาร์เรย์ตัวอธิบาย `fields` สำหรับ UI, `secretFields` และ
   `createClient(config)` ที่คืนค่า `test()` / `prepare()` / `send(records)`
2. เพิ่มลงในอาร์เรย์ `DESTINATIONS` ใน `src/lib/logExport/registry.ts`
3. เขียนการทดสอบไว้ใน `tests/unit/`

การเปลี่ยนแปลงทั้งหมดมีเพียงเท่านี้: การจัดเก็บข้อมูลถาวร, งาน cron, ชั้น REST, การเข้ารหัสข้อมูลลับ และ
แบบฟอร์มบนแดชบอร์ดล้วนอ่านข้อมูลจากรีจิสทรี

กฎสองข้อสำหรับปลายทางใหม่:

- `send()` **ต้องโยนข้อผิดพลาด** เมื่อเกิดความล้มเหลวบางส่วน การทำงานสำเร็จหมายถึง "ปลายทางมีแถวเหล่านี้แล้ว"
  และเคอร์เซอร์จะเลื่อนผ่านแถวเหล่านั้นไปอย่างถาวร
- ปลายทางที่รับ URL จากผู้ใช้ต้องตรวจสอบความถูกต้องผ่าน
  `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`) ก่อนดึงข้อมูล
  เช่นเดียวกับเว็บฮุก BigQuery ไม่จำเป็นต้องทำเช่นนี้ เพราะโฮสต์ของ BigQuery เป็นค่าคงที่

## 7. การใช้งาน

- **แดชบอร์ด**: การผสานรวม → ส่งออกบันทึก เพิ่มปลายทาง แล้วเรียกใช้ **ทดสอบ** เพื่อตรวจสอบข้อมูลรับรอง
  โดยไม่เขียนแถวข้อมูล จากนั้นจึงเปิดใช้งาน
- **ข้อมูลค้างส่ง**: การ์ดของแต่ละปลายทางแสดงแถวที่รอส่งและเคอร์เซอร์; `GET
/api/log-export/status` คืนค่าตัวเลขเดียวกันพร้อมประวัติการรันงาน 20 ครั้งล่าสุด
- **ปลายทางที่ล้มเหลวจะไม่ทำให้ปลายทางอื่นล้มเหลวตาม** — สรุปการรันจะบันทึกสถานะของแต่ละปลายทาง
  ไว้ใน `last_status` / `last_error` และประวัติการรันงานจะเก็บผลรวมไว้
- **การลบปลายทางจะลบเคอร์เซอร์ของปลายทางนั้นด้วย** การเพิ่มกลับเข้าไปจะเริ่มจากบันทึกการเรียกใช้ที่เก่าที่สุดที่ยังเก็บไว้
  ซึ่งจะส่งแถวที่ปลายทางอาจมีอยู่แล้วซ้ำอีกครั้ง สำหรับ BigQuery ค่า
  `insertId` ของแต่ละแถวจะช่วยจัดการข้อมูลซ้ำได้เฉพาะภายในช่วงเวลาขจัดข้อมูลซ้ำของ BigQuery เองเท่านั้น ดังนั้นควรปิดใช้งาน
  ปลายทางแทนการลบ
