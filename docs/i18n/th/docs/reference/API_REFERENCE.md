## การเติมเต็มแชต

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### ส่วนหัวแบบกำหนดเอง

| ส่วนหัว                  | ทิศทาง     | คำอธิบาย                                                                                                                                                                                                                       |
| ------------------------ | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `X-OmniRoute-No-Cache`   | คำขอ       | ตั้งค่าเป็น `true` เพื่อข้ามแคช                                                                                                                                                                                                |
| `x-omniroute-no-memory`  | คำขอ       | ตั้งค่าเป็น `true` เพื่อข้ามการแทรกหน่วยความจำและทักษะสำหรับคำขอนี้ (ทำงานสอดคล้องกับการไม่ใช้แคช และหลีกเลี่ยงค่าใช้จ่ายด้านโทเค็น/ต้นทุนต่อการเรียก)                                                                         |
| `X-OmniRoute-Progress`   | คำขอ       | ตั้งค่าเป็น `true` เพื่อรับเหตุการณ์ความคืบหน้า                                                                                                                                                                                |
| `X-Session-Id`           | คำขอ       | คีย์เซสชันแบบยึดติดสำหรับการรักษาความสัมพันธ์กับเซสชันภายนอก                                                                                                                                                                   |
| `x_session_id`           | คำขอ       | รองรับรูปแบบที่ใช้ขีดล่างด้วยเช่นกัน (HTTP โดยตรง)                                                                                                                                                                             |
| `X-OmniRoute-Session-Id` | คำขอ       | แท็กเซสชัน/การสนทนาที่ผู้เรียกกำหนด (และส่งข้อมูลให้หน่วยความจำด้วย) เมื่อระบุไว้ ระบบจะบันทึกตามที่ได้รับโดยไม่เปลี่ยนแปลงลงใน `call_logs.session_tag` เพื่อระบุต้นทุนต่อเซสชัน (#8249) — และจะไม่สร้างขึ้นเองเมื่อไม่ได้ระบุ |
| `Idempotency-Key`        | คำขอ       | คีย์สำหรับขจัดรายการซ้ำ (กรอบเวลา 5 วินาที)                                                                                                                                                                                    |
| `X-Request-Id`           | คำขอ       | คีย์ทางเลือกสำหรับขจัดรายการซ้ำ                                                                                                                                                                                                |
| `x-omniroute-connection` | คำขอ       | ตรึงคำขอแบบโมเดลเดียวไว้กับการเชื่อมต่อของผู้ให้บริการหนึ่งรายการ (บัญชี) ตาม id — ดู [การตรึงบัญชีต่อคำขอ](#account-pinning-per-request)                                                                                      |
| `X-OmniRoute-Cache`      | การตอบกลับ | `HIT` หรือ `MISS` (แบบไม่สตรีม)                                                                                                                                                                                                |
| `X-OmniRoute-Idempotent` | การตอบกลับ | เป็น `true` หากมีการขจัดรายการซ้ำ                                                                                                                                                                                              |
| `X-OmniRoute-Progress`   | การตอบกลับ | เป็น `enabled` หากเปิดการติดตามความคืบหน้า                                                                                                                                                                                     |
| `X-OmniRoute-Session-Id` | การตอบกลับ | ID เซสชันที่ OmniRoute ใช้งานจริง                                                                                                                                                                                              |
| `X-OmniRoute-Request-Id` | การตอบกลับ | id สำหรับเชื่อมโยงคำขอ (เมื่อทราบ)                                                                                                                                                                                             |
| `X-OmniRoute-Version`    | การตอบกลับ | เวอร์ชันบิลด์ของ OmniRoute (มีอยู่เสมอ)                                                                                                                                                                                        |
| `X-OmniRoute-Cost-Saved` | การตอบกลับ | จำนวนเงิน USD ที่ประหยัดได้จากแคชเมื่อเกิด HIT (เฉพาะแคชฮิต)                                                                                                                                                                   |
| `X-OmniRoute-Decision`   | การตอบกลับ | ร่องรอยการกำหนดเส้นทาง: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` คือกลยุทธ์คอมโบ หรือ `single` สำหรับคำขอที่ไม่ใช่คอมโบ) — มีอยู่เสมอในการตอบกลับเมื่อดำเนินการเสร็จสิ้น                                  |

> หมายเหตุเกี่ยวกับ Nginx: หากคุณใช้ส่วนหัวที่มีขีดล่าง (ตัวอย่างเช่น `x_session_id`) ให้เปิดใช้งาน `underscores_in_headers on;`

#### การตรึงบัญชีต่อคำขอ

เมื่อผู้ให้บริการมีการเชื่อมต่อหลายรายการ (บัญชีหรือคีย์) โดยปกติ OmniRoute จะเลือกหนึ่งรายการ
ผ่านกลยุทธ์การเลือกบัญชี แต่คำขอสามารถตรึงการเชื่อมต่อที่เฉพาะเจาะจงหนึ่งรายการได้
ด้วยส่วนหัว `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **ตำแหน่งที่ใช้ค้นหา ID** เปิดหน้าผู้ให้บริการในแดชบอร์ด
  (**แดชบอร์ด → ผู้ให้บริการ → <provider>**) แล้วคลิกชิป ID `xxxxxxxx…` บนแถวการเชื่อมต่อ
  ระบบจะคัดลอก ID การเชื่อมต่อแบบเต็ม
- **คำขอที่รองรับ** คำขอแบบโมเดลเดียว (`provider/model`) บน
  `/v1/chat/completions`, `/v1/messages` และ `/v1/responses` ส่วนคอมโบจะไม่สนใจส่วนหัวนี้ โดยให้ตรึง
  บัญชีสำหรับแต่ละขั้นตอนของคอมโบผ่านการเชื่อมต่อของขั้นตอนนั้นแทน
- **การตรึงเป็นข้อกำหนดที่เคร่งครัด ไม่ใช่เพียงค่ากำหนดที่ต้องการ** ระบบจะใช้การเชื่อมต่อที่ตรึงไว้แต่เพียงผู้เดียว
  ความล้มเหลวภายในคำขอจะบันทึกคูลดาวน์ของบัญชี แต่จะ **ไม่** สลับไปยัง
  บัญชีอื่นของผู้ให้บริการรายเดียวกัน
- **คูลดาวน์และโควตาจะปลดการตรึง** ขณะที่การเชื่อมต่อที่ตรึงไว้อยู่ในช่วงคูลดาวน์
  ใช้โควตาหมด หรือถูกบล็อกโดยนโยบายโควตา คำขอหลังจากนั้นจะย้อนกลับไปใช้การเชื่อมต่ออื่น
  ของผู้ให้บริการ เช่นเดียวกับทราฟฟิกที่ไม่ได้ตรึง
- **ID ที่ไม่รู้จักหรือถูกปิดใช้งานจะทำให้ล้มเหลว** ID ที่ไม่ได้อยู่ในพูลที่ใช้งานอยู่ของผู้ให้บริการ (ถูกลบ
  ถูกปิดใช้งาน หรือเป็นของผู้ให้บริการรายอื่น) จะทำให้ไม่มีบัญชีที่มีสิทธิ์ใช้งาน ดังนั้นคำขอ
  จะล้มเหลวแทนที่จะถูกกำหนดเส้นทางไปยังที่อื่นโดยไม่มีการแจ้งเตือน

Claude Code ส่งส่วนหัวแบบกำหนดเองผ่าน `ANTHROPIC_CUSTOM_HEADERS` ให้วางตัวแปรนี้ไว้ในบล็อก `env`
ของ `~/.claude/settings.json` หรือใน `.claude/settings.json` ระดับโปรเจกต์เพื่อตรึงบัญชีที่แตกต่างกัน
สำหรับแต่ละโปรเจกต์:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

ที่มา: `src/sse/handlers/chat.ts` (การอ่านส่วนหัว), `src/sse/services/auth.ts` และ
`src/sse/services/sessionAffinityPin.ts` (การปลดการตรึงและการตรวจสอบว่าไม่พบในพูล)

> **ส่วนหัวเทเลเมทรีต้นทุน:** การตอบกลับที่สำเร็จแบบไม่สตรีมจะมีชุดเทเลเมทรีต้นทุน `X-OmniRoute-*` ด้วย — `X-OmniRoute-Response-Cost` (USD, ทศนิยมคงที่ 10 ตำแหน่ง; `0.0000000000` สำหรับรายการที่ไม่มีค่าใช้จ่าย/ไม่มีการกำหนดราคา), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` และ `X-OmniRoute-Fallback-Attempts` (เฉพาะเมื่อ > 0) รวมถึง `X-OmniRoute-Request-Id` และ `X-OmniRoute-Version` ส่วนหัวเหล่านี้ถูกส่งจากการเติมข้อความแชต, `/v1/responses`, `/v1/messages` **และเอ็นด์พอยต์สื่อ** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` และ `/v1/moderations` (มีต้นทุน `0` เสมอ) ต้นทุนสื่อจะคำนวณตามแต่ละโมดาลิตี (ต่อรูปภาพ ต่อวินาที ต่ออักขระ หรือต่อหน่วยการค้นหา) เมื่อมีข้อมูลราคา มิฉะนั้นจะเป็น `0` (ดำเนินการต่อได้เมื่อเกิดข้อผิดพลาด)

> **ความหมายของต้นทุนเมื่อพบแคช:** เมื่อพบข้อมูลในแคชเชิงความหมาย (`X-OmniRoute-Cache-Hit: true`) จะไม่มีการเรียกไปยังระบบต้นทาง ดังนั้น `X-OmniRoute-Response-Cost` จึงเป็น `0.0000000000` (ต้นทุน **ส่วนเพิ่ม** สำหรับการให้บริการจากแคช) ต้นทุนเดิม/ต้นทุนที่ควรจะเกิดขึ้นจะถูกรายงานแยกต่างหากใน `X-OmniRoute-Cost-Saved` ระบบที่ใช้ข้อมูลเพื่อการเรียกเก็บเงินควรรวมค่า `X-OmniRoute-Response-Cost` (การพบแคชไม่มีต้นทุน) ส่วนการวิเคราะห์แคชสามารถรวมค่า `X-OmniRoute-Cost-Saved` ได้

## การเช่าเซสชันแบบมีการจัดการชนิดเอกสิทธิ์

การเช่าเซสชันแบบมีการจัดการชนิดเอกสิทธิ์เป็นสัญญาการกำหนดเส้นทางที่เลือกใช้ได้และไม่ขึ้นกับไคลเอนต์ โดยเจ้าของที่ทำงานอยู่หนึ่งรายจะถือครองการเชื่อมต่อ OmniRoute ที่มีสิทธิ์หนึ่งรายการ สัญญานี้ไม่ได้เป็นการเช่าโมเดล ไม่จำเป็นต้องใช้ OAuth ไม่ได้ระบุไคลเอนต์ใดโดยเฉพาะ และไม่ได้บังคับให้ใช้ผู้ให้บริการรายใดโดยเฉพาะ

คีย์ API ที่ใช้ยืนยันตัวตนต้องมีขอบเขต `lease:exclusive` และมีรายการ `allowedConnections` ที่ระบุไว้อย่างชัดเจนและไม่ว่างเปล่า ขอบเขตการเปลี่ยนแปลงฐานข้อมูลจะบังคับใช้ทั้งสองฟิลด์ร่วมกัน ทั้งเมื่อสร้างคีย์และเมื่ออัปเดตบางส่วน

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

การตอบกลับเมื่อขอครอบครอง ต่ออายุ และปล่อยสำเร็จจะแสดงการประทับเวลา `state` และค่า `generation` ที่เป็นจำนวนบวกและตรงตามจริง แต่จะไม่เปิดเผยการเชื่อมต่อหรือข้อมูลประจำตัวที่เลือกไว้ การต่ออายุและการปล่อยจะส่ง generation ในเนื้อหา JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

เจ้าของสัญญาเช่าที่ทำงานอยู่สามารถร้องขอข้อมูลเมตาสำหรับแสดงผลที่รักษาความเป็นส่วนตัวของการผูกปัจจุบันได้อย่างชัดเจน:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

การดำเนินการสถานะแบบเลือกใช้นี้ถูกกั้นด้วยเจ้าของแบบทึบ คีย์ API แบบมีการจัดการที่ผ่านการยืนยันตัวตน และ generation ที่ทำงานอยู่ซึ่งต้องตรงกัน ภายในธุรกรรมฐานข้อมูลรายการเดียว `displayName` เป็นเพียงชื่อการเชื่อมต่อที่กำหนดค่าไว้และตัดช่องว่างแล้วเท่านั้น โดยจะเป็น `null` เมื่อไม่มีชื่อที่กำหนดค่าไว้อย่างปลอดภัย OmniRoute จะไม่นำอีเมลหรือข้อมูลระบุตัวตนของบัญชีที่สร้างขึ้นมาใช้แทน ค่าผู้ให้บริการเป็นป้ายกำกับสำหรับแสดงผลที่ไม่ละเอียดอ่อน และจะไม่ใช่ตัวระบุผู้ให้บริการที่เข้ากันได้ซึ่งสร้างขึ้น ระบบจะไม่รวมข้อมูลประจำตัว โทเค็น คุกกี้ ID ดิบของการเชื่อมต่อหรือคีย์ API แฮชของเจ้าของ ข้อมูลลับสำหรับการกั้น และข้อมูลการกำหนดเส้นทางภายใน

การค้นหาด้วยคีย์ผิด เจ้าของผิด generation เก่า รายการที่หายไป หมดอายุ ถูกปล่อย หรือถูกทำให้ใช้ไม่ได้ ล้วนส่งคืนข้อผิดพลาด `409 LEASE_FENCE_STALE` แบบเดียวกันโดยไม่มีข้อมูลเมตาของการเชื่อมต่อ ไคลเอนต์ที่ได้รับการตอบกลับให้รอความจุจะไม่มีการผูกที่ทำงานอยู่ให้ตรวจสอบ เมื่อการกำหนดเส้นทางเปลี่ยนสัญญาเช่าที่ทำงานอยู่ generation เดิมจะยังคงใช้ได้ และสถานะจะส่งคืนการผูกใหม่แบบอะตอมมิก โดยจะไม่ส่งคืนการผูกเดิม ไคลเอนต์ที่มีอยู่จะไม่ได้รับผลกระทบ เนื่องจากการตอบกลับสำหรับการขอครอบครอง การต่ออายุ การปล่อย และการรอ ยังคงมีโครงสร้างเดิม

สัญญาฝั่งเซิร์ฟเวอร์นี้ไม่เปลี่ยนแปลง `/status` ของ OpenAI Codex มาตรฐาน ปัจจุบัน Codex มาตรฐานรายงานผู้ให้บริการโมเดลและสถานะการยืนยันตัวตน/บัญชีที่มีมาให้ในตัว แต่ไม่แสดงข้อมูลเมตาของบัญชีผู้ให้บริการแบบกำหนดเองตามอำเภอใจ การผสานรวมกับไคลเอนต์ในภายหลังจะต้องเรียกการดำเนินการนี้และตัดสินใจว่าจะแสดง `connection.displayName` อย่างไร

จากนั้นคำขออนุมานแบบมีการจัดการทุกคำขอจะส่งส่วนหัวควบคุมทั้งสองรายการ:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

เจ้าของ generation การเชื่อมต่อที่ทำงานอยู่ และคีย์ API ที่ผ่านการยืนยันตัวตนซึ่งต้องตรงกันทุกประการ จะถูกตรวจสอบด้วยการกั้นทันทีก่อนความพยายามส่งคำขอไปยังต้นทางแต่ละครั้งที่รองรับ การเล่นซ้ำเจ้าของและ generation ด้วยคีย์อื่นจะล้มเหลว แม้ว่าคีย์นั้นจะอนุญาตการเชื่อมต่อเดียวกันก็ตาม เจ้าของแบบดิบจะไม่ถูกจัดเก็บแบบถาวร บันทึกในล็อก เก็บไว้ในสแนปช็อตของคำขอ หรือส่งต่อไปยังต้นทาง

ข้อขัดแย้งชั่วคราวจะส่งคืน HTTP `429` พร้อม `Retry-After` และ:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

การตอบกลับนี้หมายความเพียงว่าชุดการเชื่อมต่อที่มีสิทธิ์ตามปกติไม่ได้ว่างเปล่า และตัวเลือกที่ว่างทั้งหมดถูกถือครองโดยสัญญาเช่าที่ทำงานอยู่ของเจ้าของรายอื่น โมเดล/ผู้ให้บริการที่ไม่รองรับ ความไม่ตรงกันของนโยบาย ระยะพัก โควตา สถานะสุขภาพ และความล้มเหลวด้านสิทธิ์ตามปกติอื่น ๆ จะยังคงใช้การตอบกลับเดิมของ OmniRoute

### `x-omniroute-compression`

การแทนที่แผนการบีบอัดในระดับคำขอ มีลำดับความสำคัญสูงสุด — เหนือกว่าการแทนที่ด้วยชุดค่าการกำหนดเส้นทาง โปรไฟล์ที่ทำงานอยู่ การทริกเกอร์อัตโนมัติ และค่าเริ่มต้นของแผงควบคุม ค่าที่รองรับ:

| ค่า           | ผลลัพธ์                                                                                                |
| ------------- | ------------------------------------------------------------------------------------------------------ |
| `off`         | ไม่มีการบีบอัดสำหรับคำขอนี้                                                                            |
| `default`     | โปรไฟล์ค่าเริ่มต้นที่ได้จากแผงควบคุม (ไม่สนใจโปรไฟล์ที่ทำงานอยู่) เอนจินแบบสูญเสียข้อมูลจะยังคงปิดอยู่ |
| `safe`        | เฉพาะการลบข้อมูลซ้ำและการยุบช่องว่าง                                                                   |
| `allow-lossy` | คงแผนของผู้ดำเนินการไว้สำหรับคำขอนี้ รวมถึงการสรุปและการเขียนรูปแบบใหม่                                |
| `engine:<id>` | เอนจินเดียวเมื่อเปิดใช้งาน เช่น `engine:rtk` เป็นการเลือกใช้เอนจินนั้นในระดับคำขอ                      |
| `<combo>`     | ชุดค่าที่มีชื่อ โดยจับคู่จากชื่อก่อน (ไม่คำนึงถึงตัวพิมพ์เล็ก-ใหญ่) แล้วจึงจับคู่จาก ID                |

หมายเหตุ:

- ค่าที่ไม่รู้จักจะถูกเพิกเฉย (คำขอจะไม่ถูกปฏิเสธ) และการกำหนดค่าจะย้อนกลับไปใช้ลำดับความสำคัญปกติของผู้ดำเนินการ
- หากมีหลายชุดค่าที่ใช้ชื่อเดียวกัน ให้ส่ง **ID** ของชุดค่าเพื่อให้ได้ผลการจับคู่ที่แน่นอน
- ชุดค่าที่มีชื่อเป็น `off` หรือ `default` จะไม่สามารถเลือกด้วยชื่อได้ (ระบบจะตีความคำสำคัญเหล่านั้นก่อน) ให้อ้างอิงชุดค่าดังกล่าวด้วย ID
- สวิตช์หลักของการบีบอัดเป็นด่านบังคับ เมื่อปิดใช้งานการบีบอัดทั้งระบบ ส่วนหัวนี้จะไม่สามารถเปิดใช้งานได้

แผนที่นำไปใช้จะถูกส่งกลับในส่วนหัวการตอบกลับ:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

โดย `<source>` เป็นหนึ่งใน `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` หรือ `off`

รหัสแค็ตตาล็อกอยู่ในรูปแบบ `provider/model` (ตัวอย่าง: `jina-ai/jina-embeddings-v5-omni-small`) รหัสโมเดล Jina แบบไม่มีคำนำหน้าที่ปรากฏในรีจิสทรี (ตัวอย่างเช่น `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) ก็สามารถถูก resolve ได้เช่นกัน การ embed/rerank/classify/segment ของ Jina จะใช้ข้อมูลประจำตัว `jina-ai` จากแดชบอร์ดก่อน โดย `JINA_AI_API_KEY` จะถูกใช้เป็นทางเลือกสำรองเฉพาะเมื่อไม่มีคีย์จากแดชบอร์ดเท่านั้น การ์ด `jina-reader` ใช้สำหรับ Reader / `r.jina.ai` เท่านั้น (`POST /v1/web/fetch`) และไม่ให้บริการ embeddings หรือ rerank

โมเดลในรีจิสทรีที่ระบุว่ารองรับมัลติโหมดจะยอมรับรายการแบบมีโครงสร้างที่เป็นกลางต่อผู้ให้บริการได้สูงสุด 32
รายการด้วย ประเภทของรายการสื่อคือ `text`, `image`, `audio`, `video` และ `document` โดย `source`
ของสื่อจะเป็น `{"type":"url","url":"https://..."}` หรือ
`{"type":"base64","data":"...","media_type":"..."}`

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
และนามแฝงระดับตระกูล `jina-ai/jina-embeddings-v5-omni` → omni-small) ยังยอมรับเอกสารคำขอ EmbeddingsV5Request แบบเนทีฟของ Jina
และ **ส่งต่อโดยคงไว้ทั้งหมด** ไปยัง `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

ค่า `{ image | audio | video | pdf }` แบบเนทีฟอาจเป็น URL HTTPS สาธารณะ, URI `data:` หรือ
base64 ดิบ OmniRoute จะไม่แปลงออบเจ็กต์เหล่านั้นเป็นสตริงหรือดึง URL รูปภาพแบบเนทีฟ — Jina จะดึง
สื่อสาธารณะด้วยตัวเอง ฟิลด์เพิ่มเติมของ Jina (`task`, `normalized`, `truncate`, `embedding_type`) จะถูก
ส่งต่อ ส่วน SKU ของ Jina ที่รองรับเฉพาะข้อความจะยังคงปฏิเสธเอกสารที่ไม่ใช่ข้อความ

ข้อจำกัดด้านความปลอดภัยและการรับส่งข้อมูล:

- URL สื่อระยะไกลต้องเป็น HTTPS สาธารณะ รายการรูปแบบมาตรฐาน `{type,source:url}` จะถูกดึง
  ที่ฝั่งเซิร์ฟเวอร์ (ตรวจสอบการเปลี่ยนเส้นทางซ้ำ, กำหนดเวลาหมดอายุ, จำกัดขนาด, ใช้ DNS สาธารณะ และ
  ตรึงการเชื่อมต่อ) และแทรกข้อมูลก่อนเรียกผู้ให้บริการ รายการแบบเนทีฟของ Jina `{image:"https://..."}` จะถูกส่งต่อตามเดิม
  หลังผ่านการตรวจสอบ HTTPS สาธารณะแบบเดียวกัน โดย Jina จะเป็นผู้ดึง URL
- สื่อ base64 แบบอินไลน์ถูกจำกัดขนาดหลังถอดรหัสไว้ที่ 8 MiB ต่อรายการ และ 16 MiB หลังถอดรหัสสำหรับคำขอทั้งหมด

การแปลงรูปแบบสำหรับผู้ให้บริการ (รายการรูปแบบมาตรฐานจะไม่ถูกส่งต่อโดยไม่มีการเปลี่ยนแปลง):

- โมเดลมัลติโหมดของ Jina: รายการระดับบนสุดแต่ละรายการจะกลายเป็นออบเจ็กต์หนึ่งรายการที่มีคีย์ตามโมดาลิตี
  (`text` / `image` / `audio` / `video` / `pdf`) โดยใช้ URI ข้อมูลสำหรับสื่อแบบอินไลน์ และมีหนึ่งเวกเตอร์ต่อ
  รายการระดับบนสุด
- ตระกูล Gemini Embedding 2: อาร์เรย์ระดับบนสุดหนึ่งชุดจะกลายเป็นคำขอแบบเนทีฟ
  `models/{model}:embedContent` รายการเดียวที่มี `content.parts` (`text` หรือ `inline_data`)
- llama.cpp (`llama-cpp/<model>` หรือโมเดลใดก็ตามที่เซิร์ฟเวอร์ภายในโหลดไว้): รายการมาตรฐาน `text`
  จะกลายเป็นสตริงธรรมดา ส่วน `image` / `audio` / `video` แต่ละรายการจะกลายเป็นออบเจ็กต์
  `{"content": [part]}` หนึ่งรายการ โดยใช้ส่วนเนื้อหาแชตของ llama-server (`image_url`,
  `input_audio` ที่มีรูปแบบ `wav` / `mp3` / `flac`, `input_video`) พร้อมข้อมูลแบบอินไลน์ และมีหนึ่งเวกเตอร์
  ต่อรายการระดับบนสุด เซิร์ฟเวอร์ต้องทำงานด้วย `--embedding --mmproj …`; หากไม่มีโปรเจ็กเตอร์
  เซิร์ฟเวอร์จะปฏิเสธสื่อด้วยตัวเอง ไม่รองรับ `document`
- โมเดลที่ไม่รู้จัก/ไดนามิกซึ่งไม่มีเมทาดาทาโมดาลิตีอย่างชัดเจนจะปฏิเสธอินพุตแบบมีโครงสร้างด้วย HTTP 400

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

การจับคู่โมเดล/โมดาลิตีที่ไม่รองรับจะส่งคืน HTTP 400 แทนการบังคับแปลงรายการ ฟิลด์ส่วนขยายที่ไม่ใช่อินพุต
ในคำขอสตริง/โทเค็นแบบเดิมจะยังคงถูกส่งผ่านโดยไม่มีการเปลี่ยนแปลง

```bash
# แสดงรายการโมเดล embedding ทั้งหมด
GET /v1/embeddings
```

## การสร้างรูปภาพ

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

ผู้ให้บริการที่รองรับ ได้แก่ OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (ภายในเครื่อง) และ ComfyUI (ภายในเครื่อง)

`n` จะส่งคืนรูปภาพจำนวน `n` รูปใน `data[]` สำหรับผู้ให้บริการที่ API ต้นทางส่งคืนรูปภาพหนึ่งรูปต่อการเรียกหนึ่งครั้ง
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI) ระบบจะเรียกต้นทางแยกกันจำนวน `n` ครั้ง โดยทำพร้อมกันได้สูงสุด 4 ครั้ง
ค่า `seed` แบบคงที่จะถูกเพิ่มตามดัชนีของการเรียก (`seed`, `seed + 1`, …) เพื่อให้รูปภาพแตกต่างกันแต่ยังคง
สร้างซ้ำได้ ค่า `n` ถูกจำกัดไว้สูงสุดที่ 10 คำขอทั้งหมดจะล้มเหลวหากมีการเรียกใดล้มเหลว รายการ
รูปแบบที่ใช้การกระจายคำขออยู่ใน `SINGLE_IMAGE_FANOUT_FORMATS` ภายใน
`open-sse/handlers/imageGeneration/fanOut.ts`

ZenMux ใช้การเชื่อมต่อ API key ที่มีอยู่เดิมซ้ำ และรองรับคำนำหน้า `zenmux/` หรือ `zm/`:

- `zenmux/openai/gpt-image-2` ใช้ OpenAI Images API ของ ZenMux ตัวเลือกประกอบด้วย `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` และ `response_format`
- ผู้เผยแพร่รายอื่น เช่น `zm/meta/muse-image-1.0` จะใช้ endpoint `:predict` ของ Vertex AI ผ่าน ZenMux
  โดย `n` จะแมปกับ `sampleCount`, `aspect_ratio` จะแมปกับ `aspectRatio` และ `image_size`
  (`1K`, `2K`, `4K`) จะแมปกับ `sampleImageSize` ค่า `size` แบบพิกเซลจะระบุเฉพาะอัตราส่วนภาพ
  โดยไม่รับประกันขนาดพิกเซล อัตราส่วน ความละเอียด และจำนวนที่รองรับจะแตกต่างกันไปในแต่ละโมเดล
- `zm/inclusionai/ming-image-0.1-design` จะเลือกขนาดด้วยตนเอง ให้ละเว้น `size`,
  `aspect_ratio` และ `image_size`; การระบุค่าอย่างชัดเจนจะทำให้ได้รับ HTTP 400 สามารถขอรูปแบบ
  PNG, JPEG และ WebP ได้ด้วย `output_format`

การผสานรวมนี้รองรับการสร้างรูปภาพจากข้อความ แต่ไม่รองรับการแก้ไขรูปภาพอ้างอิง เอาต์พุตจาก Vertex
จะถูกปรับให้อยู่ในรูปแบบ `data[].b64_json`; `response_format: "url"` จะส่งคืน URL แบบ HTTPS
จากต้นทาง หรือ URL ข้อมูลแบบ base64 เมื่อมีเฉพาะไบต์ของรูปภาพ เอาต์พุตที่ว่างเปล่าหรือถูกกรอง
จะส่งคืนข้อผิดพลาดแทนการตอบกลับว่าสำเร็จแบบว่างเปล่า การเข้าถึงโมเดลขึ้นอยู่กับบัญชี ZenMux
โปรดดู [Vertex API ของ ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) และ
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image)

## OCR เอกสาร

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` ใช้เลือกผู้ให้บริการ OCR ผ่านคำนำหน้า `provider/model`; รหัสโมเดลที่ไม่มีคำนำหน้า (เช่น
`mistral-ocr-latest`) จะถูกจับคู่กับผู้ให้บริการที่ลงทะเบียนไว้ และหากละเว้น `model` ระบบจะใช้
Mistral (`mistral-ocr-latest`) เป็นค่าเริ่มต้น ผู้ให้บริการที่ลงทะเบียนไว้ (`open-sse/config/ocrRegistry.ts`):

| รหัสผู้ให้บริการ              | รหัสโมเดล            | ค่า `model`                                                               | หมายเหตุ                                                                                                       |
| ----------------------------- | -------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (หรือ `mistral-ocr-latest` โดยไม่มีคำนำหน้า) | แบบซิงโครนัส — ระบบส่งคืนการตอบกลับโดยตรงจากการเรียกต้นทางครั้งเดียว                                           |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                               | ต้นทางแบบอะซิงโครนัส (`analyze` + การโพล) — ดูรายละเอียดด้านล่าง                                               |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                                   | แบบซิงโครนัส ผ่าน endpoint พาร์ทเนอร์ `openapi/chat/completions` ของ Vertex AI — ดูการยืนยันตัวตน/URL ด้านล่าง |

ผู้ให้บริการทั้งสามรายตอบกลับด้วยเนื้อหาในรูปแบบเดียวกับ Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### ขั้นตอนการโพลของ Azure Document Intelligence

API `analyze` ของ Azure Document Intelligence ทำงานแบบอะซิงโครนัส: คำขอเริ่มต้นจะส่งคืน
ส่วนหัว `Operation-Location` แทนเนื้อหาการตอบกลับ และต้องโพลเพื่อรับผลลัพธ์ ตัวจัดการ
(`open-sse/handlers/ocr.ts`) จะโพล URL ดังกล่าวทุกหนึ่งวินาที สูงสุด 30 ครั้ง และหยุดทันที
(ไม่โพลต่อ) เมื่อการตอบกลับจากการโพลไม่ใช่ `ok` หรือมีสถานะ `"failed"` และจะส่งคืน `504` หาก
การดำเนินการยังคงทำงานอยู่หลังจากใช้จำนวนครั้งที่อนุญาตจนหมด การตอบกลับสุดท้ายจาก Azure จะถูก
ปรับให้อยู่ในรูปแบบ `pages`/`markdown` เดียวกับที่ Mistral ใช้ก่อนส่งคืนให้ผู้เรียก ดังนั้นโค้ดฝั่งไคลเอนต์
จึงไม่จำเป็นต้องจัดการผู้ให้บริการแต่ละรายเป็นกรณีพิเศษ

### การยืนยันตัวตนและการกำหนด endpoint สำหรับ Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` ใช้การยืนยันตัวตนของ Vertex AI แบบเดียวกับที่ OmniRoute รองรับอยู่แล้วสำหรับ
ทราฟฟิกแชต/รูปภาพ (`open-sse/executors/vertex.ts`): API key ของการเชื่อมต่ออาจเป็นข้อมูลประจำตัว
Service Account JSON (ซึ่งจะถูกแลกเป็นโทเค็นการเข้าถึง OAuth แบบอายุสั้นผ่านขั้นตอน JWT-bearer)
หรือเป็นโทเค็นการเข้าถึง OAuth ที่ออกไว้แล้วและนำมาใช้ได้โดยตรง URL ของ endpoint ต้นทางคือ endpoint
พาร์ทเนอร์ทั่วไป `openapi/chat/completions` ของ Vertex ซึ่งสร้างขึ้นจากโปรเจกต์และภูมิภาคของการเชื่อมต่อ
— ค่า `providerSpecificData.project`/`providerSpecificData.region` ที่ระบุอย่างชัดเจนจะมีลำดับความสำคัญ
สูงกว่าเสมอ มิฉะนั้น โปรเจกต์จะถูกดึงมาจาก `project_id` ใน Service Account JSON และภูมิภาคจะมีค่าเริ่มต้น
เป็น `us-central1` การกำหนดค่าทั้งสองส่วนเกิดขึ้นใน `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) และถูกใช้โดย
`src/app/api/v1/ocr/route.ts` ก่อนส่งต่อไปยัง `handleOcr`

### คำนำหน้า id ของโมเดล (`?prefix=`)

โมเดลส่วนใหญ่จะแสดงภายใต้ **คำนำหน้าของผู้ให้บริการ** คำนำหน้าที่คุณได้รับจะถูกควบคุมโดย
feature flag `MODELS_CATALOG_PREFIX_MODE` และสามารถเขียนทับได้ **สำหรับแต่ละคำขอ** ด้วย
พารามิเตอร์ query ซึ่งมีประโยชน์สำหรับไคลเอนต์ที่ต้องการรายการที่กระชับโดยไม่ต้องเปลี่ยนการตั้งค่า
ทั่วทั้งเซิร์ฟเวอร์สำหรับผู้ใช้อื่น:

```bash
GET /v1/models?prefix=alias        # หนึ่ง id ต่อโมเดล — คำนำหน้า alias แบบสั้น
GET /v1/models?prefix=dual         # ทั้งสองรูปแบบ (ค่าเริ่มต้นของเซิร์ฟเวอร์)
GET /v1/models?prefix=canonical    # เฉพาะคำนำหน้า provider-id แบบเต็ม
```

| โหมด        | ผลลัพธ์ที่ส่งออก                                          | หมายเหตุ                                                                                                                                                                                 |
| ----------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **และ** `claude/claude-sonnet-4-6` | **ค่าเริ่มต้น** id ทั้งสองจะกำหนดเส้นทางไปยังโมเดลเดียวกัน โดยคงไว้เพื่อให้การกำหนดค่าไคลเอนต์ที่เขียนรูปแบบใดรูปแบบหนึ่งแบบตายตัวยังคงทำงานต่อไป ขนาดแค็ตตาล็อกจะเพิ่มขึ้นประมาณสองเท่า |
| `alias`     | `cc/claude-sonnet-4-6`                                    | หนึ่งรายการต่อโมเดล ผู้ให้บริการที่ไม่มี alias แยกต่างหากจะยังคงส่งออกรายการของตน จึงไม่มีข้อมูลใดสูญหาย                                                                                 |
| `canonical` | `claude/claude-sonnet-4-6`                                | หนึ่งรายการต่อโมเดลภายใต้คำนำหน้า provider-id แบบเต็ม ผู้ให้บริการที่ไม่มี alias แยกต่างหาก (เช่น `antigravity/…`, `agy/…`) จะส่งออก id เดียวของตนที่นี่ด้วย จึงไม่มีข้อมูลใดสูญหาย      |

นอกจากนี้ ยังสามารถตรวจพบ mirror ในโหมด `dual` ได้โดยไม่ต้องใช้พารามิเตอร์ query เนื่องจากมีฟิลด์ `parent`
ที่ชี้ไปยัง id หลัก

ไคลเอนต์ที่แสดงตัวเลือกโมเดลควรร้องขอ `?prefix=alias` ซึ่งเป็นแนวทางที่
[ส่วนขยาย OmniCopilot สำหรับ VS Code](../guides/VSCODE-COPILOT.md) ใช้

### ตัวกรองสำหรับการค้นหา (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` รองรับตัวกรองสำหรับการค้นหาที่เลือกใช้ได้ หากไม่ใช้ตัวกรองใดเลย การตอบกลับจะ
ไม่เปลี่ยนแปลง ตัวกรองเหล่านี้จะจำกัดแค็ตตาล็อกที่ผู้เรียกมองเห็นอยู่แล้วให้แคบลง (ระบบจะใช้สิทธิ์ของ API key ก่อน)
และจะทำงานก่อนการแบ่งหน้าแบบ OpenAI ด้วย `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # ความสามารถทุกรายการที่ระบุต้องเป็นจริง
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` ของแค็ตตาล็อก ส่วนแถวที่ไม่มีค่าจะเป็น `chat`
GET /v1/models?q=sonnet&limit=10                           # จับคู่ id หรือ name โดยไม่คำนึงถึงตัวพิมพ์เล็ก-ใหญ่
```

| พารามิเตอร์   | ค่า                                                                                                 |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | จำนวนเต็มที่ไม่เป็นลบ ซึ่งนำไปเปรียบเทียบกับ `context_length`                                       |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 อักขระ                                                                                        |

ค่าที่ไม่รู้จัก หรือ `min_context` ที่ไม่ใช่จำนวนเต็มที่ไม่เป็นลบ (ตัวอย่างเช่น `1.5`)
จะส่งคืน HTTP `400` และข้อความจะแสดงรายการค่าที่ใช้ได้ การนำไปใช้:
`src/app/api/v1/models/catalogFilters.ts`

### รายการโมเดลที่คัดสรร (`POST /v1/models/query`)

`POST /v1/models/query` ส่งคืนรายการแบบสั้นและกำหนดผลลัพธ์แน่นอนจากแค็ตตาล็อกเดียวกัน โดยใช้
การตรวจสอบสิทธิ์และการมองเห็นต่อคีย์แบบเดียวกับ `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

ทุกฟิลด์เป็นฟิลด์ที่ไม่บังคับ `capabilities` และ `exclude` รับได้ทั้งอาร์เรย์หรือสตริงที่คั่นด้วยจุลภาค
`max_output` จะเปรียบเทียบกับ `max_output_tokens` ผลลัพธ์จะเรียงตาม `owned_by` แล้วจึงตาม `id`
ค่าเริ่มต้นของ `limit` คือ `20` และค่าที่มากกว่า `100` จะถูกจำกัดไว้ที่ `100` JSON ที่ไม่ถูกต้อง ฟิลด์ที่ไม่รู้จัก
หรือค่าที่ไม่ถูกต้องจะส่งคืน HTTP `400`

### โมเดลแชตที่ซ่อนเป็นรายโมเดล

โมเดลที่ทำเครื่องหมายเป็น **ซ่อนอยู่** ในหน้าผู้ให้บริการจะถูกแยกออกจากแค็ตตาล็อกและถูกปฏิเสธ
ด้วย HTTP `404` / `model_not_found` เมื่อมีการร้องขออย่างชัดเจน การตรวจสอบจะใช้ผู้ให้บริการ
และโมเดลที่ผ่านการ resolve แล้ว รวมถึง alias ของผู้ให้บริการ คำนำหน้าโหนดของผู้ให้บริการที่เข้ากันได้ และ
ค่าเริ่มต้นของการเชื่อมต่อ combo จะข้ามเป้าหมายที่ซ่อนอยู่และสามารถใช้โมเดลที่มองเห็นได้ในกลุ่มเดียวกัน เมื่อไม่มี
เป้าหมายที่ดำเนินการได้เหลืออยู่ ระบบจะส่งคืนรหัสข้อผิดพลาดเดียวกัน การยกเลิกการซ่อนจะมีผลในคำขอถัดไป
การเขียนทับการมองเห็นสำหรับรูปภาพเท่านั้นจะไม่ซ่อนโมเดลแชตที่มี ID เดียวกัน

การตั้งค่าโมเดลแต่ละรายการนี้แยกจาก
[รายการอนุญาต/ปฏิเสธการเปิดเผยโมเดล](../routing/MODEL_EXPOSURE_LIST.md) ซึ่งกรองการแสดงในแค็ตตาล็อก
และตัวเลือกสำหรับการกำหนดเส้นทางอัตโนมัติ แต่ยังคงอนุญาตการส่งคำขอแบบระบุชัดเจน สิทธิ์โมเดลของ API key
ยังคงมีผลแยกกัน โหมดคำนำหน้าเริ่มต้นของแค็ตตาล็อกยังคงเป็น `dual`

### ตัวแปรโมเดลแบบไม่ใช้การคิด

สำหรับโมเดล Claude ที่รองรับการคิด `/v1/models` จะแสดงตัวแปรแบบ **ไม่ใช้การคิด** เพิ่มเติมด้วย โดย id จะขึ้นต้นด้วย `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

การเลือก id นี้ (เช่น ในการกำหนดค่า Claude Code ที่แนบบล็อก `thinking` เสมอ) จะถูกแมปกลับไปยัง `<provider>/<model>` จริงโดยปิดการใช้เหตุผล — ใช้ `thinking:{type:"disabled"}` บนพาธ `/v1/messages` หรือตัดฟิลด์ `reasoning`/`reasoning_effort` ออกบนพาธ `/v1/chat/completions` ตัวแปรนี้จะแสดงเฉพาะสำหรับโมเดลตระกูล Claude ที่รองรับการคิด **และ** ยอมรับ `disabled` (ดังนั้น เช่น โมเดลแบบ adaptive-only ที่ปฏิเสธ `disabled` จะไม่รวมอยู่ด้วย) ผู้ดูแลระบบสามารถบังคับเปิดหรือปิดตัวแปรนี้แยกตามโมเดลได้ผ่าน `ModelSpec.noThinkingAlias`

## การสร้างเสียงด้วย ElevenLabs

กำหนดค่าการเชื่อมต่อผู้ให้บริการ `elevenlabs` ใน OmniRoute ด้วย API key ของ ElevenLabs
ไคลเอนต์จะยืนยันตัวตนด้วยคีย์ **OmniRoute** ของตน (`Authorization: Bearer $OMNIROUTE_API_KEY`);
เกตเวย์จะส่งคีย์ผู้ให้บริการที่จัดเก็บไว้ในรูปแบบ `xi-api-key` ห้ามส่งคีย์ ElevenLabs
เป็น bearer token ของเกตเวย์

| เมธอด | พาธ                         | การตอบกลับ                                | หมวดหมู่ endpoint ของ API key |
| ----- | --------------------------- | ----------------------------------------- | ----------------------------- |
| POST  | `/v1/sound-generation`      | ไบต์เสียงแบบเนทีฟ                         | `elevenlabs`                  |
| POST  | `/v1/music`                 | ไบต์เสียงแบบเนทีฟ                         | `music`                       |
| POST  | `/v1/music/stream`          | ไบต์เสียงแบบสตรีม                         | `music`                       |
| POST  | `/v1/music/detailed`        | เสียงและแผนการประพันธ์แบบ multipart เนทีฟ | `music`                       |
| POST  | `/v1/music/detailed/stream` | เมทาดาทา SSE และส่วนย่อยของเสียงแบบเนทีฟ  | `music`                       |
| POST  | `/v1/music/plan`            | แผนการประพันธ์ในรูปแบบ JSON               | `music`                       |

endpoint เหล่านี้เสริม route ที่มีอยู่แล้ว ได้แก่ `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` และ `/v1/speech-to-text` ฟิลด์ JSON
และพารามิเตอร์ query แบบเนทีฟ เช่น `output_format` และ `enable_logging` จะถูกคงไว้
การตอบกลับจาก `/v1/music/detailed` จะคงขอบเขต multipart ไว้ ให้แยกวิเคราะห์เป็น multipart
`/v1/music/detailed/stream` ส่งคืน `text/event-stream` พร้อมเมทาดาทาการประพันธ์และ
ส่วนย่อยของเสียงที่เข้ารหัสแบบ base64 ในอีเวนต์ SSE โดย route ทั้งหกรองรับ CORS preflight

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# เอฟเฟกต์เสียงสั้น ๆ ระยะเวลา: 0.5 ถึง 30 วินาที
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# ระยะเวลาของเพลงระบุเป็นมิลลิวินาที: 3000 ถึง 600000
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

ใช้ `/v1/music/stream` กับเนื้อหา JSON เดียวกันเพื่อส่งเสียงแบบต่อเนื่อง การประพันธ์
รองรับ `prompt` หรือ `composition_plan` อย่างใดอย่างหนึ่งเท่านั้น ส่วน `/v1/music/plan` จำเป็นต้องมี `prompt`
และเลือกระบุ `source_composition_plan` ได้ สคีมาแบบเนทีฟจะคงฟิลด์เพิ่มเติม
ของผู้ให้บริการไว้ เพื่อให้เวอร์ชันของแผนการประพันธ์และตัวเลือกการปรับแต่งส่งไปถึง ElevenLabs

endpoint แบบรวม `/v1/music/generations` ยังรองรับ `elevenlabs/music_v1`,
`elevenlabs/music_v2` และ `elevenlabs/music_v2_5` ด้วย เมื่อมีการเชื่อมต่อ ElevenLabs ที่ใช้งานอยู่
โมเดลเหล่านี้จะแสดงในแค็ตตาล็อกเพลง endpoint นี้ส่งคืน
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` ฟิลด์ `duration` ใช้หน่วย
วินาทีและแมปไปยัง `music_length_ms` โดย `music_length_ms` ที่ระบุไว้อย่างชัดเจนจะมีลำดับความสำคัญสูงกว่า
`instrumental` จะแมปไปยัง `force_instrumental` โดยฟิลด์แบบเนทีฟจะมีลำดับความสำคัญสูงกว่า
ใช้ endpoint การสตรีมแบบเนทีฟสำหรับการสตรีม และใช้ endpoint การประพันธ์แบบเนทีฟ
สำหรับคำขอที่ขับเคลื่อนด้วยแผนการประพันธ์เพียงอย่างเดียว

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

ข้อจำกัดของ endpoint, โมเดล, งบประมาณ และการเชื่อมต่อจะถูกนำมาใช้ก่อนเรียก upstream
route แบบเนทีฟจะส่งคืนรหัสสถานะและเนื้อหาข้อผิดพลาดจาก upstream โดยไม่เปลี่ยนแปลง รวมถึง `402` สำหรับข้อจำกัด
ของแพ็กเกจ และ `429` สำหรับขีดจำกัดโควตา ส่วนหัว `character-cost`, `song-id`, `request-id` และ `retry-after`
จะถูกคงไว้เมื่อมีอยู่ ยอดเครดิตฟรีไม่ได้รับประกันว่าจะเข้าถึงโมเดลเพลง
รูปแบบเอาต์พุต หรือคุณสมบัติ API ทุกรายการได้ โดย ElevenLabs จะเป็นผู้ตัดสินสิทธิ์สำหรับแต่ละคำขอ
endpoint แบบรวมจะคงรหัสสถานะข้อผิดพลาดไว้ในกรอบข้อผิดพลาดมาตรฐานของ OmniRoute

สัญญา upstream: [เอฟเฟกต์เสียง](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[การประพันธ์เพลง](https://elevenlabs.io/docs/api-reference/music/compose) และ
[รายละเอียดเพลงแบบสตรีม](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)

เส้นทาง POST ทั้งหมดใช้โครงสร้างเดียวกัน: `Bearer your-api-key` + เนื้อหา JSON ที่ตรวจสอบความถูกต้องด้วย Zod (`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema` ฯลฯ โปรดดู `src/shared/validation/schemas.ts`) ระบบจะส่งคืน 4xx เมื่อการตรวจสอบสคีมาล้มเหลว

สำหรับไคลเอนต์ที่ไม่สามารถแนบ `Authorization: Bearer ...` ได้ OmniRoute ยังรองรับคีย์ API ใน URL ผ่านความเข้ากันได้ด้วยสตริงการสืบค้น (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) หรือเอนด์พอยต์เฉพาะ `/api/v1/vscode/{token}/...` ที่อธิบายไว้ด้านล่าง

```bash
# จัดอันดับซ้ำ (ผู้ให้บริการจากรีจิสทรีบนคลาวด์ หรือโหนดผู้ให้บริการที่เข้ากันได้กับ OpenAI ในรูปแบบ "<prefix>/<model>")
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# ตัวแบ่งส่วนของ Jina
POST /v1/segment     { "content": "...", "return_chunks": true }

# การค้นหาของ Jina (s.jina.ai; นามแฝงผู้ให้บริการ: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# การตรวจสอบเนื้อหา
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — ส่งคืนเนื้อหา audio/mpeg (หรือรูปแบบที่ร้องขอ)
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS ต้องระบุภาษาและเสียง: `language` มีค่าเริ่มต้นเป็น "en"; หากไม่มี
# voice หรือใช้ชื่อเสียงมาตรฐานของ OpenAI (alloy, nova, …) ระบบจะเปลี่ยนเป็น "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# การแก้ไขรูปภาพ (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# การสร้างวิดีโอ / เพลง (รหัสโมเดลที่มีคำนำหน้าผู้ให้บริการ)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **โหนดผู้ให้บริการสำหรับการจัดอันดับใหม่:** `POST /v1/rerank` ยังส่งต่อคำขอไปยังโหนดผู้ให้บริการที่เข้ากันได้กับ OpenAI
> (oMLX, vLLM, Infinity, TEI ที่อยู่หลังเกตเวย์, …) ซึ่งระบุที่อยู่ในรูปแบบ `<node-prefix>/<model>` โหนดลูปแบ็ก
> (`localhost`, `127.0.0.1`, `172.16.0.0/12`) ใช้งานได้เสมอ เช่นเดียวกับชื่อโฮสต์ที่ผู้ดูแลระบบ
> ระบุไว้ใน `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (เช่น ชื่อบริการ Docker/Compose อย่าง
> `http://reranker:8080/v1`; ระบบจะเรียกโหนดเหล่านี้โดยตรงเสมอ โดยไม่ผ่าน `HTTP(S)_PROXY` หรือพร็อกซี
> ที่ตรึงไว้กับการเชื่อมต่อ) โหนดบนโฮสต์อื่น
> ไม่ว่าจะเป็นเครื่องใน LAN หรือเพียร์ Tailscale จะใช้งานได้เฉพาะเมื่อผู้ดูแลระบบเปิดใช้
> แฟล็กฟีเจอร์ `RERANK_REMOTE_PROVIDER_NODES` **และ** URL ฐานของโหนดผ่านนโยบาย URL ขาออก
> ของผู้ให้บริการ (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`)
> ขั้นตอนการจัดอันดับใหม่ของกลไกหน่วยความจำจะเรียกเส้นทางนี้ผ่าน
> ลูปแบ็ก ดังนั้นกฎเดียวกันนี้จึงใช้ควบคุม `rerankProviderModel` ในการตั้งค่าหน่วยความจำด้วย
>
> **รูปแบบเซิร์ฟเวอร์ภายในเครื่อง:** ระบบจะเรียกโหนดที่ `<base>/v1/rerank` และเมื่อได้รับ 404 จะเรียกที่ `<base>/rerank`
> (Infinity, TEI) เนื้อหาคำขอที่ส่งไปยังต้นทางจะมีทั้งการสะกดแบบ Cohere/OpenAI (`documents`,
> `return_documents`) และแบบ TEI (`texts`, `return_text`) และการตอบกลับจากต้นทางจะถูก
> ปรับให้เป็นเอนเวโลปแบบ Cohere: ทั้งอาร์เรย์เปล่าของ TEI `[{index, score, text}]`, รูปแบบ `{results: [{index, score}]}`
> จากเกตเวย์แบบบาง และรูปแบบ Voyage `{data: [...]}` จะถูกส่งกลับไปยังไคลเอนต์ในรูปแบบ
> `{results: [{index, relevance_score, document?}]}` โดยเรียงตามคะแนนและจำกัดจำนวนไว้ที่ `top_n`
>
> **การค้นหาโหนดผู้ให้บริการ:** โมเดลบนโหนดผู้ให้บริการที่เข้ากันได้กับ OpenAI จะปรากฏใน `GET /v1/models`
> ภายใต้คำนำหน้าของโหนด แถวที่ไม่มีเมทาดาทาของเอนด์พอยต์ (ซึ่งพบได้ทั่วไปในรายการ `/v1/models` ภายในเครื่อง)
> จะสืบทอด `apiType` ของโหนด ดังนั้นโมเดลของโหนด `embeddings` จะมี `type: "embedding"` และโมเดลของ
> โหนด `rerank` จะมี `type: "rerank"` แทนที่จะใช้แชตเป็นค่าเริ่มต้น ส่วน `supportedEndpoints`
> ที่ระบุไว้อย่างชัดเจนในแถวที่ซิงค์หรือเพิ่มด้วยตนเองยังคงมีลำดับความสำคัญสูงกว่า

## Files API

เอนด์พอยต์ไฟล์ที่เข้ากันได้กับ OpenAI สำหรับอินพุต/เอาต์พุตแบบแบตช์และการอัปโหลดไฟล์ตามวัตถุประสงค์

| เมธอด  | พาธ                      | คำอธิบาย                                                                                                       |
| ------ | ------------------------ | -------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/files`              | อัปโหลดไฟล์ (multipart: `file`, `purpose`, `expires_after[anchor]`, `expires_after[seconds]`) — สูงสุด 512 MiB |
| GET    | `/v1/files`              | แสดงรายการไฟล์สำหรับคีย์ API ที่ผ่านการตรวจสอบสิทธิ์                                                           |
| GET    | `/v1/files/[id]`         | ดึงข้อมูลเมตาของไฟล์                                                                                           |
| DELETE | `/v1/files/[id]`         | ลบไฟล์                                                                                                         |
| GET    | `/v1/files/[id]/content` | สตรีมเนื้อหาไฟล์ดิบกลับไป                                                                                      |

**การตรวจสอบสิทธิ์:** คีย์ API แบบ Bearer — ไฟล์จะถูกกำหนดขอบเขตแยกตามคีย์ API ผ่าน `getApiKeyRequestScope` คีย์หนึ่ง
สามารถดู ดาวน์โหลด และลบได้เฉพาะไฟล์ของตนเองเท่านั้น ส่วนเซสชันแดชบอร์ดที่ไม่มีคีย์สามารถอ่านได้ทั้ง
อินสแตนซ์ และไฟล์ที่ไม่มีเจ้าของ (อัปโหลดแบบไม่ระบุตัวตนหรือผ่านเซสชันแดชบอร์ด) จะถูกปฏิเสธสำหรับผู้เรียก
ที่ไม่ใช่เซสชันทุกราย `GET /v1/files` จะปฏิเสธผู้เรียกแบบไม่ระบุตัวตน — รวมถึงคีย์ที่ส่งมาแต่
ไม่สามารถระบุได้ — ด้วย `401` แม้ว่า `REQUIRE_API_KEY=false` แทนที่จะแสดงรายการไฟล์ของ
ผู้เช่าทุกราย (GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523)

การประมวลผลแบบแบตช์ที่เข้ากันได้กับ OpenAI

| เมธอด  | พาธ                       | คำอธิบาย                                                                                                             |
| ------ | ------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/batches`             | สร้างแบตช์ — เนื้อหาคำขอได้รับการตรวจสอบโดย `v1BatchCreateSchema` (`input_file_id`, `endpoint`, `completion_window`) |

| DELETE | `/v1/batches/[id]`        | ลบแบตช์ที่เสร็จสิ้น/ล้มเหลวแล้ว                                                                                      |

**การตรวจสอบสิทธิ์:** คีย์ API แบบ Bearer แบตช์จะถูกกำหนดขอบเขตแยกตามคีย์ API ภายใต้กฎสามทางเดียวกันกับ

## Search API

ชั้นนามธรรมสำหรับผู้ให้บริการเว็บ/การค้นหา (Tavily, Brave, Exa, Serper เป็นต้น)

| เมธอด | พาธ                    | คำอธิบาย                                                                                     |
| ----- | ---------------------- | -------------------------------------------------------------------------------------------- |
| GET   | `/v1/search`           | แสดงรายการผู้ให้บริการค้นหาที่กำหนดค่าไว้และความสามารถของแต่ละราย                            |
| POST  | `/v1/search`           | เรียกใช้คำค้นหา — เนื้อหาคำขอได้รับการตรวจสอบโดย `v1SearchSchema` และรองรับการแคช/การรวมคำขอ |
| GET   | `/v1/search/analytics` | สถิติการพบผลลัพธ์/เวลาแฝง/แคชแยกตามผู้ให้บริการ                                              |

**การยืนยันตัวตน:** คีย์ API แบบ Bearer (`extractApiKey` + `isValidApiKey`) นโยบายการค้นหาถูกบังคับใช้ผ่าน `enforceApiKeyPolicy`

### `provider_options` ของ Exa และ Tavily

Exa และ Tavily อ่านฟิลด์เฉพาะของผู้ให้บริการจากออบเจ็กต์ที่แบ่งเนมสเปซ:
`provider_options.exa` (หรือ `provider_options["exa-search"]`) และ `provider_options.tavily`
(หรือ `provider_options["tavily-search"]`) ระบบจะส่งต่อเฉพาะคีย์ด้านล่างเท่านั้น โดยแต่ละคีย์จะได้รับ
การตรวจสอบกับสคีมา Zod ของตนเองใน `open-sse/handlers/search/providerOptionsPassthrough.ts`
และคีย์ที่มีชนิดข้อมูลไม่ถูกต้องจะถูกตัดทิ้ง คีย์อื่นทั้งหมดจะถูกละเว้น รวมถึงข้อมูลยืนยันตัวตน, URL ฐาน,
`stream` และ `outputSchema` คีย์แบบแบนที่ผู้ให้บริการรายอื่นใช้ (`cx`, `depth`, ...) ยังคงทำงาน
เหมือนเดิม

| ผู้ให้บริการ | ฟิลด์ระดับบนสุด                                                                                                                                                                                                                                                                                                                                                           | ฟิลด์ซ้อน                                                                                                                                                    |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Exa          | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (ค่าพื้นฐานแบบแบน), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                             | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` ผสานทับค่าเริ่มต้น `{ text: true, highlights: true }` |
| Tavily       | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                            |

ฟิลด์ทั่วไปจะมีลำดับความสำคัญสูงกว่าเสมอ ได้แก่ `query`, `max_results`, `filters` (โดเมน), `country` และ
หัวข้อที่ได้มาจาก `search_type` สำหรับ Exa ค่า `search_type: "news"` จะคง `category: "news"` ไว้
Tavily ยังรองรับ `search_type: "finance"` (`topic: "finance"`) ด้วย

ขณะนี้ `time_range` แบบทั่วไปจะถูกส่งไปถึงผู้ให้บริการทั้งสองราย: Exa จะได้รับ `startPublishedDate` (การประทับเวลาแบบ ISO)
และ Tavily จะได้รับ `start_date` (`YYYY-MM-DD`) วันที่ที่ระบุไว้อย่างชัดเจนใน `provider_options`
จะแทนที่ค่าที่แมปมา

ผลลัพธ์ของ Exa จะเก็บ `id`, `highlight_scores`, `summary`, `subpages`, `entities` และ `extras` ไว้ใน
`provider_raw` ส่วนผลลัพธ์ของ Tavily จะเก็บ `images` และ `favicon`

การคำนวณต้นทุนยังคงใช้รีจิสทรีแบบแบน `costPerQuery` Tavily คิดค่าบริการ
`search_depth: "advanced"` ด้วยจำนวนเครดิตต่อการเรียกที่สูงกว่า และความแตกต่างนี้จะไม่แสดงอยู่ใน
`usage.search_cost_usd`

## Web Fetch API

ดึงเนื้อหาจาก URL ผ่านผู้ให้บริการ web-fetch ที่กำหนดค่าไว้ (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract)

Parallel Extract (`parallel-search` ซึ่งใช้ API key เดียวกับ Parallel Search) ส่งคืนเฉพาะ
Markdown เท่านั้น — `format` ค่าอื่นจะได้รับ `400` — และจำกัดเนื้อหาไว้ที่ 100,000 อักขระ เมื่อ
ไม่สามารถดึงข้อมูลจากหน้าเป้าหมายได้ ระบบต้นทางจะรายงานข้อผิดพลาดดังกล่าวภายใน HTTP 200;
OmniRoute จะแสดงข้อผิดพลาดนั้นเป็น `422` พร้อมข้อความแบบคงที่

| เมธอด | พาธ             | คำอธิบาย                                                           |
| ----- | --------------- | ------------------------------------------------------------------ |
| POST  | `/v1/web/fetch` | ดึง/สแครป URL — ตรวจสอบความถูกต้องของ body ด้วย `v1WebFetchSchema` |

**การยืนยันตัวตน:** Bearer API key (`extractApiKey` + `isValidApiKey`) บังคับใช้นโยบายผ่าน `enforceApiKeyPolicy`

**การสำรองโดยคำนึงถึงโควตา (#8297):** เมื่อไม่ได้ระบุ `provider` อย่างชัดเจน ระบบจะไล่ใช้พูล
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) ตาม
ลำดับความสำคัญคงที่
(เติมตัวแรกให้เต็มก่อน) — ผู้ให้บริการที่กำหนดค่าไว้แต่ถูกจำกัดอัตราจะถูกข้าม
แทนที่จะยุติคำขอทันที และความล้มเหลวจากระบบต้นทางที่ลองใหม่ได้/เกี่ยวข้องกับโควตา
(HTTP 429 เสมอ; 402/403 สำหรับแพ็กเกจฟรีแบบมีโควตาของ Firecrawl/Tavily/TinyFish —
ไม่ใช้กับ Jina Reader และไม่ใช้กับคำขอที่ไม่ถูกต้องแบบ 400 ทั่วไป) จะเปลี่ยนไปลอง
ผู้ให้บริการรายถัดไปที่ยังไม่เคยลองและมีข้อมูลประจำตัว ณ เวลาที่ส่งคำขอ เมื่อผู้ให้บริการทุก
รายในพูลใช้งานไม่ได้แล้ว endpoint จะส่งคืน `429` เพียงรายการเดียว (พร้อม header `Retry-After`)
แทน `400` แบบทั่วไปที่เคยใช้ก่อนหน้านี้ เมื่อมีการร้องขอ `provider` อย่างชัดเจน
จะ**ไม่มี**การสำรองแบบเงียบ — ผู้ให้บริการที่ระบุอย่างชัดเจนซึ่งถูกจำกัดอัตราหรือทำงานล้มเหลว
จะแสดงข้อผิดพลาดของตนเอง (`429` หากถูกจำกัดอัตรา มิฉะนั้นจะใช้สถานะจากระบบต้นทาง)

### Responses API ผ่าน WebSocket (เฉพาะ codex)

สำหรับการกำหนดเส้นทางแบบแบ่งโควตา ให้ใช้ `model: "qtSd/<group>/codex/<model>"` ระบบนี้ถูกติดตั้งไว้ใน
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`

**การยืนยันตัวตน:** Bearer API key ระหว่าง handshake เซิร์ฟเวอร์ HTTP ที่รวมมาให้ (`server-ws.mjs`)
ต้องเป็น entrypoint ที่กำลังทำงานอยู่ (และจะเป็นเช่นนั้นโดยค่าเริ่มต้นเมื่อมี `app/server-ws.mjs`)

#### ID ของโมเดล: ใช้ ID ของ ChatGPT โดยตรง (ไม่มีคำนำหน้า `codex/`)

**Codex CLI** ของ OpenAI จะตรวจสอบชื่อโมเดลที่ฝั่งไคลเอนต์เมื่อ
`supports_websockets = true` และ**ปฏิเสธ ID ที่มีคำนำหน้าผู้ให้บริการ** เช่น
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with

`gpt-5.5` แบบไม่มีคำนำหน้าจะถูกกำหนดเส้นทางไปยังผู้ให้บริการรายอื่นผ่าน HTTP ก็ตาม

#### การกำหนดค่า OpenAI Codex CLI

กำหนดให้ Codex CLI ชี้ไปยัง OmniRoute โดยเพิ่มผู้ให้บริการแบบกำหนดเองที่รองรับ WebSocket
ลงใน `~/.codex/config.toml` (ใช้ `CODEX_HOME` แยกต่างหากเพื่อหลีกเลี่ยงการแก้ไข
การกำหนดค่าที่มีอยู่):

```toml
model = "gpt-5.5"                 # ID โดยตรง — ไม่ใช่ "codex/gpt-5.5"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # ไม่มีเครื่องหมายทับต่อท้าย; URL ของ WS จะถูกสร้างขึ้นจากค่านี้ (ใช้ https/wss ในระบบที่ใช้งานจริง)
wire_api = "responses"                    # ค่าที่รองรับเพียงค่าเดียวนับตั้งแต่เดือนกุมภาพันธ์ 2026
supports_websockets = true                # เปิดใช้ transport แบบ Responses-over-WS
env_key = "OMNIROUTE_API_KEY"             # เก็บ API key ของ OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # API key ของ OmniRoute (ใช้ key ใดก็ได้หาก REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI จะอัปเกรด `base_url + /responses` เป็น WebSocket และ OmniRoute จะสร้าง tunnel ไปยัง
การเชื่อมต่อ codex OAuth ที่เลือกไว้ ผ่านการตรวจสอบแบบ end-to-end กับเซิร์ฟเวอร์ภายในแล้ว:
ChatGPT ส่งคืน `codex.rate_limits` + `response.created` และสตรีมผลลัพธ์จนเสร็จสมบูรณ์

## การใช้งานแบบบริการตนเอง (`/api/usage/om-usage`)

คีย์ API ใดๆ สามารถอ่านข้อมูลการใช้งานและโควตาของ**ตนเอง**ได้ โดยไม่ต้องมีสิทธิ์การจัดการ นี่คือเอนด์พอยต์ที่
ไคลเอนต์ (CLI, แผง OmniCopilot) ใช้เพื่อแสดงค่าใช้จ่ายให้ผู้ถือคีย์ทราบ

```bash
# รูปแบบข้อความ (สัญญาดั้งเดิม — ข้อความธรรมดาสำหรับเทอร์มินัล)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# รูปแบบมีโครงสร้าง — รูปแบบที่ UI ใช้งาน
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

คีย์ต้องเปิดใช้ **`allowUsageCommand`** (ปิดไว้ตามค่าเริ่มต้น — ตัวจัดการคีย์ API ของแดชบอร์ด
จะสลับเปิดหรือปิดให้แต่ละคีย์) หากไม่ได้เปิดใช้ เอนด์พอยต์จะตอบกลับด้วย `403`

`?format=json` ส่งคืนโครงสร้างแบบแบ่งแยกประเภท เพื่อให้ผู้เรียกไม่อ่านฟิลด์ข้อมูลจากการ
ปฏิเสธคำขอ เมื่อสำเร็จ:

```jsonc
{
  "allowed": true,
  // มีเฉพาะเมื่อคีย์เลือกใช้ขีดจำกัดการใช้งานต่อคีย์ (USD รายวัน/รายสัปดาห์):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // สแนปช็อตโควตาของผู้ให้บริการที่เลือก หรือ null เมื่อยังไม่มีข้อมูลใดถูกแคช:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // สแนปช็อตของทุกการเชื่อมต่อ เพื่อให้ UI แสดงผู้ให้บริการหลายรายเคียงข้างกันได้:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

เมื่อถูกปฏิเสธ (`401` คีย์ไม่ถูกต้อง / `403` ไม่ได้รับอนุญาต) เส้นทางเดียวกันนี้จะส่งคืน
`{ "allowed": false, "error": { "message": "…" } }` — `personal`/`provider` ที่มีอยู่แต่เป็นค่าว่าง
(คีย์ได้รับอนุญาต แต่ยังไม่ได้รับข้อมูลใดๆ) เป็นสถานะที่แตกต่างจากการถูกปฏิเสธ และมีเพียงรูปแบบ JSON
เท่านั้นที่แยกความแตกต่างระหว่างสถานะเหล่านี้ได้

**การยืนยันตัวตน:** คีย์ API แบบ Bearer ของผู้เรียกเอง ซึ่งตรวจสอบด้วย `isValidApiKey` — นี่_ไม่ใช่_
ส่วนติดต่อสำหรับการจัดการ (`/api/keys/…`) ซึ่งยังคงได้รับการป้องกันด้วย `requireManagementAuth`

### เปอร์เซ็นต์โควตาดิบเทียบกับเปอร์เซ็นต์โควตาที่ปรับตามค่าตัดแล้ว

เมื่อใช้งาน `/api/usage/om-usage` ผู้เรียกควรทราบความแตกต่างระหว่าง
เปอร์เซ็นต์ที่แสดงโดย**เอาต์พุตข้อความธรรมดา**และ**เอาต์พุต JSON** แบบมีโครงสร้าง:

| แง่มุม                   | รูปแบบข้อความธรรมดา (`/api/usage/om-usage` / `@@om-usage`)                                        | รูปแบบ JSON (`?format=json`)                                                            |
| :----------------------- | :------------------------------------------------------------------------------------------------ | :-------------------------------------------------------------------------------------- |
| **ฟิลด์เอาต์พุต**        | `NN% left` (เช่น `20% left`)                                                                      | `provider.quotas` / `providers[].quotas`                                                |
| **การวัด**               | **ปริมาณที่ใช้งานได้หลังปรับตามค่าตัด**: ความจุที่เหลือเหนือเกณฑ์ค่าตัด                           | **โควตาต้นทางดิบ**: ค่าที่วัดจากผู้ให้บริการโดยไม่มีการปรับ                             |
| **การปรับสเกลตามค่าตัด** | ปรับสเกลผ่าน `effectiveRemainingPercent()` เพื่อให้ส่วนสำรองที่ได้รับการป้องกันแสดงเป็น `0% left` | ไม่มี (ใช้ค่าสแนปช็อตดิบตามที่ผู้ให้บริการรายงาน)                                       |
| **ข้อมูลเกณฑ์**          | รวมอยู่ในเปอร์เซ็นต์ที่แสดง                                                                       | จัดเก็บไว้ใน `quotaWindowThresholds` ต่อการเชื่อมต่อ (หรือใช้ค่าเริ่มต้นของเซิร์ฟเวอร์) |
| **ผู้ใช้งานหลัก**        | CLI แบบโต้ตอบ พรอมต์เทอร์มินัล ผู้ปฏิบัติงานที่เป็นมนุษย์                                         | การผสานรวมเชิงโปรแกรม แดชบอร์ด การวิเคราะห์ ตัวติดตามการเรียกเก็บเงิน                   |

#### สูตรการปรับค่าตัด

OmniRoute รองรับค่าตัดโควตาเชิงรุกเพื่อป้องกันไม่ให้ทรัพยากรต้นทางหมดลง (กำหนดค่าผ่าน
`quotaWindowThresholds` ของการเชื่อมต่อ ค่าเริ่มต้นของผู้ให้บริการ หรือการตั้งค่าความยืดหยุ่นส่วนกลาง) เมื่อเกณฑ์ค่าตัด
(เช่น `cutoff = 25%`) ทำงานอยู่ในช่วงโควตาหนึ่ง ตัวเรนเดอร์ข้อความจะคำนวณปริมาณที่เหลือดังนี้:

- หาก `remaining <= cutoff`: ส่งคืน `0%`
- หาก `remaining > cutoff`: ส่งคืน `((remaining - cutoff) / (100 - cutoff)) * 100`

เอาต์พุตข้อความที่จัดรูปแบบแล้วจะปัดค่านี้เป็นจำนวนเต็มที่ใกล้ที่สุด (`Math.round(...)`)

#### ตัวอย่างประกอบ

พิจารณาช่วงโควตาของผู้ให้บริการที่มี**การใช้งานดิบ 60%** (จึงมี**โควตาดิบเหลืออยู่ 40%**) และกำหนด
เกณฑ์**ค่าตัดโควตาที่เหลือ 25%**:

| รูปแบบการแสดง                  | การคำนวณ                                           | คงเหลือ |     ปริมาณที่อนุมานว่าใช้ไปแล้ว      |
| :----------------------------- | :------------------------------------------------- | :-----: | :----------------------------------: |
| **JSON ดิบ (`?format=json`)**  | สแนปช็อตต้นทาง (`quotas[window]`)                  | **40%** |               **60%**                |
| **รูปแบบข้อความ (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (หากคำนวณ `100 - remaining`) |

- **เหตุผลที่ข้อความแสดงว่าเหลือ 20%:** จากโควตาจริง 40% ที่เหลืออยู่ในบัญชี นโยบาย
  ค่าตัดจะสำรองไว้ 25% ผู้เรียกจึงมีพื้นที่ใช้งานได้เหลือเพียง 15% จากทั้งหมด 75% ก่อนที่เราเตอร์จะหยุด
  กำหนดเส้นทางไปยังการเชื่อมต่อนี้ การปรับสเกลช่วยให้การเชื่อมต่อส่งสัญญาณว่าโควตาหมด (`0% left`) ณ เวลาที่
  การกำหนดเส้นทางหยุดลงพอดี
- **เหตุผลที่ JSON เก็บค่าดิบไว้:** เพย์โหลด JSON ส่งคืนสแนปช็อตจากผู้ให้บริการโดยตรง (`UsageSnapshot`)
  เพื่อให้เครื่องมือภายนอกเข้าถึงข้อมูลการใช้งานต้นทางตามความเป็นจริงและ
  `quotaWindowThresholds` ระดับการเชื่อมต่อได้ โดยไม่มีการปรับสเกลแบบสูญเสียข้อมูลที่ฝั่งเซิร์ฟเวอร์

#### แนวทางการย้ายระบบสำหรับผู้ใช้งาน

หากการผสานรวมภายนอก (เช่น ปลั๊กอินสำหรับเอดิเตอร์หรือส่วนขยายของเอเจนต์) เคยดึงข้อมูลจากเอนด์พอยต์แบบข้อความ
(`NN% left`) และคำนวณเปอร์เซ็นต์ที่ใช้ไปเป็น `100 - NN` การย้ายไปใช้ `?format=json` หมายความว่า:

- การอ่านค่า JSON ดิบจะแสดงถึง **การใช้งานจริงจากต้นทาง** (ใช้ไป 60% ในตัวอย่างข้างต้น)
- หากการผสานรวมต้องการคงความหมายของปริมาณที่ยังใช้ได้จากเอนด์พอยต์แบบข้อความไว้ ก็สามารถประเมิน
  สูตรคำนวณปริมาณคงเหลือที่มีผลจริงในฝั่งไคลเอนต์ โดยใช้ `quotaWindowThresholds` สำหรับการแทนที่ค่าระดับการเชื่อมต่อ

## แคชเชิงความหมาย

```bash
# ดูสถิติแคช
GET /api/cache/stats

# ล้างแคชทั้งหมด
DELETE /api/cache/stats
```

ตัวอย่างการตอบกลับ:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### ผลกระทบต่อเวลาแฝง

เมื่อแคชเชิงความหมาย HIT ระบบจะส่งการตอบกลับจากแคช **โดยไม่เรียกใช้บริการต้นทาง**
ดังนั้น `X-OmniRoute-Response-Latency` ที่รายงานจึงมีค่าเกือบเป็นศูนย์
(ไม่ว่าเวลาแฝงเดิมของบริการต้นทางจะเป็นเท่าใดก็ตาม) ไคลเอนต์ที่ให้ความสำคัญกับเวลาแฝง
(การทำเบนช์มาร์ก การตรวจสอบ p50/p99) ควรตรวจสอบส่วนหัวการตอบกลับ
`X-OmniRoute-Cache-Latency`:

| ค่า         | ความหมาย                                                    |
| ----------- | ----------------------------------------------------------- |
| `synthetic` | ส่งการตอบกลับจากแคช เวลาแฝงจึงไม่ใช่เวลาจริงของบริการต้นทาง |
| _(ไม่มี)_   | การตอบกลับมาจากการเรียกใช้บริการต้นทางจริง                  |

### การข้ามแคชสำหรับแต่ละคีย์

คีย์ API สามารถเลือกไม่อ่านแคชเชิงความหมายได้ผ่าน `cacheDefaultMode`:

| ค่า      | ลักษณะการทำงาน                                    |
| -------- | ------------------------------------------------- |
| `legacy` | การทำงานของแคชตามปกติ (ค่าเริ่มต้น)               |
| `bypass` | ข้ามการค้นหาในแคชทั้งหมด และเรียกบริการต้นทางเสมอ |

กำหนดค่าเมื่อสร้างคีย์ (`POST /api/keys`) หรืออัปเดต (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### การข้ามแคชสำหรับแต่ละคำขอ

คำขอใดๆ สามารถข้ามแคชได้โดยไม่คำนึงถึงการตั้งค่าของคีย์:

```
X-OmniRoute-No-Cache: true
```

สำหรับโมเดลที่ซิงค์/นำเข้า `PUT /api/provider-models` ยอมรับ `provider`, `modelId` และ
`maxOutputTokenOverride` โดยจำนวนเต็มบวกจะกำหนดขีดจำกัดโทเค็นเอาต์พุตด้วยตนเอง และ `null`
จะล้างค่านี้เพื่อคืนค่าเริ่มต้น `GET /api/provider-models?provider=<provider>` จะส่งคืนค่าเหล่านี้
ใน `modelOutputOverrides` รวมถึงโมเดลที่ไม่มีแถวโมเดลแบบกำหนดเอง การแทนที่ค่านี้
ใช้ความสามารถ `max_output_tokens` ขณะรันไทม์และยังคงอยู่หลังจากซิงค์โมเดลอีกครั้ง หน้าผู้ให้บริการที่เข้ากันได้กับ OpenAI
มีตัวควบคุมสำหรับแก้ไข/ล้างค่าแบบเดียวกัน และทำเครื่องหมายโมเดลที่รองรับการมองเห็นอย่างชัดเจน

โหนด Custom Chat Completions จะปรับคำสั่งปฏิเสธการใช้การให้เหตุผลอย่างชัดเจนให้เข้ากับแบ็กเอนด์ต้นทาง
การทดสอบการเชื่อมต่อที่สำเร็จจะเลือกตัวควบคุมเทมเพลตแชตโดยอัตโนมัติสำหรับ ID โมเดลที่ตรงกันแต่ละรายการ
ซึ่งรายการ `/models` ยืนยันว่ามีค่า `owned_by` ที่รู้จัก ได้แก่ `vllm`, `sglang` หรือ `llamacpp`
แรปเปอร์ที่เข้ากันได้กับ OpenAI แบบโปร่งใสอาจเก็บรายการโมเดลดั้งเดิมไว้ภายในออบเจ็กต์
`openai` ที่ซ้อนกัน โดยการตรวจจับจะติดตามเอนเวโลปดังกล่าวได้สูงสุดสามชั้น โมเดลที่ไม่มีข้อมูลความเป็นเจ้าของ มีค่าที่ไม่รู้จัก หรือ
มีข้อมูลความเป็นเจ้าของขัดแย้งกันจะยังคงใช้ลักษณะการทำงานตามปกติของ OpenAI การตรวจจับจะใช้คำขอแค็ตตาล็อกที่มีอยู่ซ้ำ
ไม่สร้างโทเค็นการเติมข้อความใดๆ และจะถูกทำให้ใช้ไม่ได้เมื่อเอนด์พอยต์การเชื่อมต่อเปลี่ยนแปลง

หากต้องการตรึงลักษณะการทำงานสำหรับแบ็กเอนด์ที่ไม่เปิดเผยเมตาดาต้าดังกล่าว ให้ใช้ API ที่มีอยู่
สำหรับอัปเดตผู้ให้บริการบางส่วน:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

ส่งเนื้อหานั้นด้วย `PUT /api/providers/<connection-id>` สำหรับการเชื่อมต่อนั้น เมื่อกำหนด
ระดับการให้เหตุผลเป็น `none` อย่างชัดเจน ระบบจะส่งเป็น `chat_template_kwargs.thinking=false` และ
`chat_template_kwargs.enable_thinking=false` ค่าเทมเพลตเนทีฟที่ระบุไว้อย่างชัดเจนจะมีผลเหนือกว่า
เว้นแต่ว่ากฎการให้เหตุผลฝั่งเซิร์ฟเวอร์จะบังคับระดับการให้เหตุผล การตั้งค่านี้มีผลเฉพาะเมื่อการเชื่อมต่อ
แบบกำหนดเองที่เข้ากันได้กับ OpenAI ส่งเนื้อหา Chat Completions เท่านั้น คำขอ Responses และ
ผู้ให้บริการทั่วไปจะยังคงใช้รูปแบบคำขอเนทีฟของตน ตั้งค่า `reasoningControl` เป็น `openai` เพื่อบังคับให้ส่งผ่าน
`reasoning_effort` ตามปกติของ OpenAI หรือไม่ต้องระบุ/ตั้งค่าเป็น `null` เพื่อใช้การตรวจจับอัตโนมัติ

คำขอจากตัวจำแนกประเภทในโหมดอัตโนมัติของ Claude Code จะปิดใช้งานการคิดแบบเนทีฟโดยค่าเริ่มต้น เมื่อไม่มี
ตัวควบคุมการให้เหตุผลที่ระบุอย่างชัดเจน การตรวจจับใช้เครื่องหมายระบบของตัวจำแนกประเภทในคำขอรูปแบบ Claude
ไม่ใช่ชื่อโมเดลหรือขีดจำกัดการเติมข้อความ ตัวควบคุมในเนื้อหาที่ระบุไว้อย่างชัดเจน ส่วนหัว effort/thinking ที่รองรับ
กฎการกำหนดเส้นทาง และระดับการให้เหตุผลของโมเดลที่คำนวณแล้ว จะยังคงมีลำดับความสำคัญตามเดิม ตัวจำแนกประเภท
ทั้งสองขั้นตอนจะคงพรอมต์ ขีดจำกัดการเติมข้อความ ลำดับหยุด และผลการตัดสินสิทธิ์จริงจากต้นทางไว้
โดยขั้นตอนที่สองยังคงสามารถสร้างการให้เหตุผลที่มองเห็นได้ตามที่ร้องขอในรูปแบบข้อความธรรมดา

`/api/db-backups/export`, `/api/db-backups/exportAll` และ `/api/settings/export-json` เปิดเผย
ข้อมูลประจำตัวทั้งหมดที่จัดเก็บไว้ ดังนั้นจึงต้องใช้เซสชันแดชบอร์ดหรือ CLI ภายในเครื่อง (หรือปิดใช้งาน
การล็อกอิน) คีย์ API ทุกขอบเขตและโทเค็นการเข้าถึง `oma_` จะได้รับ `403` การกู้คืนมี
ขอบเขตความปลอดภัยเดียวกัน: `POST /api/db-backups/import` (รวมถึง `dryRun=true`), `POST /api/db-backups` (กู้คืน
ตาม id) และ `POST /api/settings/import-json` จะแทนที่ฐานข้อมูลหรือการตั้งค่าที่ใช้งานอยู่ ดังนั้นข้อมูลประจำตัว
ของเครื่องจึงได้รับ `403` ที่ปลายทางเหล่านี้ด้วย `omniroute sync import` จะส่งข้อมูลประจำตัวของ CLI ภายในเครื่อง เช่นเดียวกับ
`DELETE /api/db-backups` (ล้างข้อมูลสำรองที่จัดเก็บไว้) และ `PATCH /api/db-backups` (การตั้งค่าการเก็บรักษา:
ค่าที่บันทึกไว้จะควบคุมการล้างอัตโนมัติหลังจากการสำรองข้อมูลทุกครั้ง) การแสดงรายการ (`GET`) และการสร้าง
ข้อมูลสำรองด้วยตนเอง (`PUT`) ยังคงใช้การยืนยันตัวตนสำหรับการจัดการทั่วไป

| `/api/rate-limit`                 | GET       | การกำหนดค่าขีดจำกัดอัตราทั่วระบบ (เลิกใช้งานแล้ว; เป็นนามแฝงของ `/api/rate-limits`)                                                                                                                                                                                                                                                                                                                                                   |

### เวอร์ชันและช่องทางการเผยแพร่

```bash
GET /api/system/version
```

เส้นทางการจัดการเฉพาะ loopback (ต้องมีการยืนยันตัวตนของผู้ดูแลระบบ) ส่งคืนเวอร์ชันที่กำลังทำงาน เวอร์ชันล่าสุดที่เผยแพร่ และสถานะการอัปเดตอัตโนมัติ `releaseChannel` และ `channels` เป็นฟิลด์ที่เพิ่มเข้ามา (rail 3.8.54); `channel` ยังคงมีความหมายเดิม — โหมดการปรับใช้ที่ตัวอัปเดตแดชบอร์ดใช้ (`npm`, `source` หรือ `docker-compose`)

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — ช่องทาง npm ของบิลด์ที่กำลังทำงาน: `nightly` สำหรับเวอร์ชัน `-nightly.*`,
  `next` สำหรับเวอร์ชันก่อนเผยแพร่อื่นๆ (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` สำหรับเวอร์ชันเสถียรของ
  major รุ่นเก่ากว่า `channels.latest` มิฉะนั้นจะเป็น `latest` ใช้กฎเดียวกับ
  `scripts/release/dist-tag.mjs` ซึ่งเลือก npm dist-tag ขณะเผยแพร่
- `channels` — เวอร์ชันล่าสุดที่เผยแพร่ของแต่ละ dist-tag จาก `npm view omniroute dist-tags` (ใช้
  HTTP ของ registry เป็นทางเลือกสำรอง) แคชด้วย TTL 10 นาทีเดียวกับ `latest` โดยจะมี `latest` อยู่เสมอ
  (ใช้ฟิลด์ `latest` เป็นค่าทดแทน จากนั้นจึงใช้ `"unavailable"`); ส่วน `next`, `nightly` และ `lts` จะปรากฏ
  เฉพาะเมื่อมี dist-tag นั้นอยู่ คำขอ `Cache-Control: no-cache` จะรีเฟรชการค้นหาทั้งสองรายการ

โมเดลช่องทาง (`latest` = v3 จนกว่า 4.0 จะพร้อมใช้งานทั่วไป, `next` = rc, `nightly` = บิลด์ `develop`,
`lts` = แพตช์ v3 หลังจาก 4.0 พร้อมใช้งานทั่วไป) อธิบายไว้ใน `docs/ops/RELEASE_STRATEGY.md`

## Alias แบบมีโทเค็นสำหรับ VS Code / แบบไม่มีส่วนหัว

ใช้ alias เหล่านี้เมื่อการผสานการทำงานไม่สามารถแทรกส่วนหัว `Authorization` และจำเป็นต้องฝังคีย์ API ไว้ใน URL ฐาน

```bash
# Alias แค็ตตาล็อกแบบ OpenAI
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# Alias แชตแบบ OpenAI
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Alias แบบ Ollama
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

ตัวอย่าง:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

หมายเหตุ:

- Alias แบบมีโทเค็นจะใช้ตัวจัดการเดียวกันกับ `/v1/*` และ `/api/tags` รูปแบบการตอบกลับจึงยังคงเหมือนเดิม
- ควรใช้ `Authorization: Bearer ...` หากไคลเอนต์รองรับส่วนหัวแบบกำหนดเอง
- โทเค็นที่อยู่ใน URL อาจปรากฏในบันทึกของพร็อกซีย้อนกลับ ประวัติเบราว์เซอร์ และข้อมูลเทเลเมทรีภายนอก OmniRoute ให้ใช้โทเค็นลักษณะนี้เป็นตัวเลือกเพื่อความเข้ากันได้ ไม่ใช่วิธีการยืนยันตัวตนเริ่มต้น

## งบประมาณ

```bash
# รับสถานะงบประมาณสำหรับคีย์ API ทั้งหมด
GET /api/usage/budget

# กำหนดหรืออัปเดตงบประมาณ
POST /api/usage/budget
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "dailyLimitUsd": 5.00,
  "weeklyLimitUsd": 30.00,
  "monthlyLimitUsd": 100.00,
  "warningThreshold": 0.8,
  "resetInterval": "monthly"
}
```

> **หมายเหตุเกี่ยวกับสคีมา** (`setBudgetSchema`): จำเป็นต้องระบุ `apiKeyId` โดยอย่างน้อยหนึ่งค่าจาก `dailyLimitUsd`, `weeklyLimitUsd` หรือ `monthlyLimitUsd` ต้องมากกว่าศูนย์ ฟิลด์ที่ไม่บังคับ ได้แก่ `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`) รูปแบบเดิม `{keyId, limit, period}` จะส่งคืน `400 Bad Request`

## ขีดจำกัดโทเค็น

งบประมาณ **โทเค็น** ต่อคีย์ API (แยกจากงบประมาณที่อิงตาม USD ด้านบน) มีการบังคับใช้โดยตรงในเส้นทางการประมวลผลคำขอ: เมื่อการใช้งานในกรอบเวลาปัจจุบันของคีย์ถึงขีดจำกัด คำขอจะถูกปฏิเสธด้วย `429 Too Many Requests` ขีดจำกัดสามารถกำหนดขอบเขตให้กับ `model` หรือ `provider` ที่เฉพาะเจาะจง หรือใช้แบบ `global` กับทั้งคีย์ได้ เมื่อมีขีดจำกัดหลายรายการที่ตรงกับคำขอ ระบบจะใช้รายการที่เข้มงวดที่สุด

```bash
# แสดงขีดจำกัดโทเค็นของคีย์ (รวมการใช้งานจริงในกรอบเวลาปัจจุบัน)
GET /api/usage/token-limits?apiKeyId=key-123

# สร้างหรืออัปเดตขีดจำกัดโทเค็น
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# ลบขีดจำกัดโทเค็นตาม id
DELETE /api/usage/token-limits?id=tl-abc
```

> **หมายเหตุเกี่ยวกับสคีมา** (`setTokenLimitSchema`): จำเป็นต้องระบุ `apiKeyId` และ `scopeType` (`model` | `provider` | `global`) จำเป็นต้องระบุ `scopeValue` เว้นแต่ `scopeType` จะเป็น `global` (เช่น id ของโมเดลสำหรับขอบเขต `model` หรือ id ของผู้ให้บริการสำหรับขอบเขต `provider`) `tokenLimit` ต้องเป็นจำนวนเต็มบวก (แปลงชนิดจากสตริง) ฟิลด์ที่ไม่บังคับ ได้แก่ `id` (ละไว้เพื่อสร้างใหม่ หรือระบุเพื่ออัปเดต), `resetInterval` (`daily` | `weekly` | `monthly` โดยมีค่าเริ่มต้นเป็น `monthly`), `resetTime` (`HH:MM`) และ `enabled` (ค่าเริ่มต้นเป็น `true`) การตอบกลับของ `GET` จะเพิ่มข้อมูลให้แต่ละขีดจำกัดด้วย `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` และ `nextResetAt` เอนด์พอยต์นี้เป็นประเภทการจัดการ (มีการบังคับใช้การยืนยันตัวตนจากส่วนกลางโดยไปป์ไลน์ authz)

## การประมวลผลคำขอ

1. ไคลเอนต์ส่งคำขอไปยัง `/v1/*`
2. ตัวจัดการเส้นทางเรียก `handleChat`, `handleEmbedding`, `handleAudioTranscription` หรือ `handleImageGeneration`
3. ระบบระบุโมเดล (ผู้ให้บริการ/โมเดลโดยตรง หรือชื่อแทน/คอมโบ)
4. เลือกข้อมูลรับรองจากฐานข้อมูลภายในเครื่องพร้อมกรองตามความพร้อมใช้งานของบัญชี
5. สำหรับแชต: `handleChatCore` จะตรวจสอบแคชเชิงความหมาย/ลายเซ็น และระบุการตั้งค่าการบีบอัดของคอมโบ
6. ระบบดำเนินการบีบอัดเชิงรุกก่อนการแปลงสำหรับผู้ให้บริการเมื่อเปิดใช้งาน (`lite`, Caveman, RTK หรือแบบซ้อน)
7. ตัวดำเนินการของผู้ให้บริการส่งคำขอไปยังระบบต้นทาง
8. ระบบแปลงการตอบกลับกลับเป็นรูปแบบของไคลเอนต์ (แชต) หรือส่งคืนตามที่ได้รับมา (การฝังเวกเตอร์/รูปภาพ/เสียง)
9. ระบบบันทึกการใช้งาน การวิเคราะห์การบีบอัด และบันทึกคำขอ
10. ระบบใช้ทางเลือกสำรองเมื่อเกิดข้อผิดพลาดตามกฎของคอมโบ

ข้อมูลอ้างอิงสถาปัตยกรรมฉบับเต็ม: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## พร็อกซีสำหรับการจัดการ

พร็อกซี HTTP(S)/SOCKS ขาออกที่สามารถกำหนดให้กับผู้ให้บริการ บัญชี หรือกำหนดแบบส่วนกลางได้

| เมธอด  | พาธ                                          | คำอธิบาย                                                                                                                                         |
| ------ | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| GET    | `/api/v1/management/proxies`                 | แสดงรายการพร็อกซี (เมื่อใช้ `?id=` จะส่งคืนหนึ่งรายการ และเมื่อใช้ `?id=&where_used=1` จะส่งคืนกราฟการกำหนด)                                     |
| POST   | `/api/v1/management/proxies`                 | สร้างพร็อกซี — เนื้อหา body จะได้รับการตรวจสอบโดย `createProxyRegistrySchema`                                                                    |
| PATCH  | `/api/v1/management/proxies`                 | อัปเดตพร็อกซี — เนื้อหา body จะได้รับการตรวจสอบโดย `updateProxyRegistrySchema` (ต้องระบุ `id`)                                                   |
| DELETE | `/api/v1/management/proxies?id=...&force=1`  | ลบพร็อกซี (ใช้ `force=1` เพื่อยกเลิกการเชื่อมโยงการกำหนด)                                                                                        |
| GET    | `/api/v1/management/proxies/assignments`     | แสดงรายการการกำหนด — กรองได้ด้วย `proxy_id`, `scope`, `scope_id`; ส่ง `resolve_connection_id=<id>` เพื่อหาพร็อกซีที่ใช้งานอยู่สำหรับการเชื่อมต่อ |
| PUT    | `/api/v1/management/proxies/assignments`     | กำหนด — เนื้อหา body จะได้รับการตรวจสอบโดย `proxyAssignmentSchema` (`{scope, scopeId?, proxyId?}`) และล้างแคชของ dispatcher                      |
| PUT    | `/api/v1/management/proxies/bulk-assign`     | กำหนดแบบกลุ่ม — เนื้อหา body จะได้รับการตรวจสอบโดย `bulkProxyAssignmentSchema` (`{scope, scopeIds[], proxyId?}`)                                 |
| GET    | `/api/v1/management/proxies/health?hours=24` | สรุปสถานะพร็อกซีโดยรวม (จำนวนครั้งที่สำเร็จ/ล้มเหลวและเวลาแฝง) ภายในช่วงเวลาที่กำหนด                                                             |

**การยืนยันตัวตน:** ทุก route ต้องมีเซสชัน/API key สำหรับการจัดการ (`requireManagementAuth`)

> `POST /api/v1/management/proxies/[id]/assignments` และ `POST /api/v1/management/proxies/[id]/health` ที่ระบุในคำอธิบายงาน ให้บริการผ่าน route แบบแบน `/assignments` และ `/health` ที่แสดงไว้ข้างต้น — ไม่มี subroute แยกตาม id ใน codebase

## ความยืดหยุ่นต่อความล้มเหลว (เพิ่มเติม)

OmniRoute มีกลไกจัดการความล้มเหลวชั่วคราวที่เป็นอิสระจากกันสามประเภท โดยปลายทางการจัดการด้านล่างช่วยให้ผู้ดูแลระบบอ่านและกำหนดค่าแทนกลไกเหล่านี้ได้:

| ขอบเขต                           | ที่จัดเก็บสถานะ                                  | อ่าน                                      | รีเซ็ต / ล้าง                                               |
| -------------------------------- | ------------------------------------------------ | ----------------------------------------- | ----------------------------------------------------------- |
| เซอร์กิตเบรกเกอร์ของผู้ให้บริการ | `domain_circuit_breakers` + ในหน่วยความจำ        | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                |
| คูลดาวน์การเชื่อมต่อ             | `rateLimitedUntil` ในการเชื่อมต่อของผู้ให้บริการ | `/api/rate-limits`, `/api/providers/[id]` | (เปิดใช้งานอีกครั้งแบบล่าช้า; ล้างผ่าน PUT ของผู้ให้บริการ) |
| การล็อกเอาต์โมเดล                | รีจิสทรีความพร้อมใช้งานของโมเดลในหน่วยความจำ     | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                    |

`PATCH /api/resilience` ยอมรับค่าที่กำหนดแทนเซอร์กิตเบรกเกอร์ของผู้ให้บริการภายใต้ `providerBreaker.oauth` และ `providerBreaker.apikey` แต่ละโปรไฟล์รองรับ `degradationThreshold`, `failureThreshold` และ `resetTimeoutMs`; ฟิลด์เดียวกันนี้สามารถเข้าถึงได้ใน แดชบอร์ด → การตั้งค่า → ความยืดหยุ่นต่อความล้มเหลว

```bash
# ล้างการล็อกเอาต์ของโมเดลหนึ่งรายการ
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# ล้างการล็อกเอาต์ทั้งหมด
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

สำหรับเอกสารอ้างอิงเชิงแนวคิดฉบับเต็มและค่าเริ่มต้นของเบรกเกอร์ โปรดดู [`CLAUDE.md`](../../CLAUDE.md) → "สถานะรันไทม์ของความยืดหยุ่นต่อความล้มเหลว" และ [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md)

### คิวจำกัดอัตราและกลไกป้องกันการเปิดใช้งานอัตโนมัติ

- **เส้นทางการเขียนที่รองรับ**: `POST /api/rate-limits` พร้อมเนื้อหา `{"connectionId": "<id>", "enabled": true|false}` คือปลายทางการจัดการที่รองรับสำหรับสลับการป้องกันการจำกัดอัตราของการเชื่อมต่อ `PUT /api/providers/[id]` ตั้งใจไม่แก้ไขหรือสลับ `rateLimitProtection` (#11278)
- **ความหมายของ `enabled: false`**: การตั้งค่า `enabled: false` จะนำการป้องกันที่กำหนดไว้อย่างชัดเจนสำหรับการเชื่อมต่อออก แต่ **ไม่ได้** ยกเว้นการเชื่อมต่อ API key ที่ใช้งานอยู่จากกลไกป้องกันการเปิดใช้งานอัตโนมัติส่วนกลาง (`autoEnableApiKeyProviders = true`) ใน `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) ค่า `false` และ `undefined` มีความหมายเทียบเท่ากัน การเชื่อมต่อ API key ที่ใช้งานอยู่และไม่มีการป้องกันที่กำหนดไว้อย่างชัดเจนจะยังคงได้รับการป้องกันภายใต้กลไกป้องกันการเปิดใช้งานอัตโนมัติ
- **การปิดใช้งานส่วนกลาง**: หากต้องการใช้การเชื่อมต่อ API key โดยไม่มีคิวจำกัดอัตรา ให้ปิดใช้งานกลไกป้องกันนี้สำหรับทั้งระบบผ่าน `RATE_LIMIT_AUTO_ENABLE=false` (ตัวแปรสภาพแวดล้อม) หรือ `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (การตั้งค่า → ความยืดหยุ่นต่อความล้มเหลว / `PATCH /api/resilience`)

## เซิร์ฟเวอร์ MCP

OmniRoute มาพร้อมกับเซิร์ฟเวอร์ Model Context Protocol แบบฝังในตัว ซึ่งรองรับการรับส่งข้อมูล 3 รูปแบบ (stdio, SSE, streamable-http) และเครื่องมือที่กำหนดขอบเขตไว้ Endpoint ของแดชบอร์ดด้านล่างใช้สำหรับอ่านข้อมูลสถานะ/การตรวจสอบ และทำหน้าที่เป็นพร็อกซีให้การรับส่งข้อมูลผ่าน HTTP

| เมธอด | พาธ | คำอธิบาย |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | ฮาร์ตบีต, รูปแบบการรับส่งข้อมูล, สถานะออนไลน์, การเรียกใช้ล่าสุด, เครื่องมือที่ใช้มากที่สุด, อัตราความสำเร็จใน 24 ชั่วโมง |
| GET | `/api/mcp/tools` | รายการเครื่องมือ MCP พร้อม `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` |
| GET | `/api/mcp/sse` | เปิดสตรีม SSE สำหรับการรับส่งข้อมูลแบบ SSE (ส่งคืน `503` หากปิดใช้งาน MCP หรือรูปแบบการรับส่งข้อมูลไม่ตรงกัน) |
| POST | `/api/mcp/sse` | ส่งเฟรม JSON-RPC ผ่านการรับส่งข้อมูลแบบ SSE |
| GET | `/api/mcp/stream` | เปิดฝั่ง SSE ของการรับส่งข้อมูลแบบ Streamable HTTP (ข้อความที่เริ่มส่งจากเซิร์ฟเวอร์) |
| POST | `/api/mcp/stream` | ส่งเฟรม JSON-RPC ผ่านการรับส่งข้อมูลแบบ Streamable HTTP |
| DELETE | `/api/mcp/stream` | สิ้นสุดเซสชัน Streamable HTTP |
| GET | `/api/mcp/audit` | สืบค้นบันทึกการตรวจสอบ — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | สถิติการตรวจสอบแบบรวม (ยอดรวม, อัตราความสำเร็จ, ระยะเวลาเฉลี่ย, เครื่องมือที่ใช้มากที่สุด) |

**การยืนยันตัวตน:** การรับส่งข้อมูลแบบ `sse`/`stream` ใช้การยืนยันตัวตนเฉพาะสำหรับ MCP (Bearer API key ที่มีขอบเขต `mcp`) ส่วนเส้นทาง `status`/`tools`/`audit*` สามารถอ่านได้จากแดชบอร์ด (ไม่ต้องมีการยืนยันตัวตนเพิ่มเติม นอกเหนือจากการเข้าถึงโฮสต์ของแดชบอร์ดได้)

> การรับส่งข้อมูลผ่าน HTTP ทั้งสองรูปแบบถูกควบคุมโดย `settings.mcpEnabled` และ `settings.mcpTransport` — หากรูปแบบการรับส่งข้อมูลไม่ตรงกันจะส่งคืน `400` และหาก MCP ถูกปิดใช้งานจะส่งคืน `503`

## เซิร์ฟเวอร์ A2A

OmniRoute ให้บริการตำแหน่งข้อมูลปลายทาง A2A (Agent-to-Agent) แบบ JSON-RPC 2.0 พร้อม REST wrapper สำหรับใช้ตรวจสอบและแสดงผลบนแดชบอร์ด

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # ไม่บังคับ เว้นแต่มีการตั้งค่า OMNIROUTE_API_KEY
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

เมธอดที่รองรับ (ทั้งหมดขึ้นอยู่กับการเปิดใช้ `settings.a2aEnabled`):

| เมธอด            | คำอธิบาย                                                       |
| ---------------- | -------------------------------------------------------------- |
| `message/send`   | เรียกใช้ทักษะแบบซิงโครนัส ส่งคืน `{task, artifacts, metadata}` |
| `message/stream` | เรียกใช้ทักษะชุดเดียวกันแบบสตรีมผ่าน SSE                       |
| `tasks/get`      | ดึงงานตาม `taskId`                                             |
| `tasks/cancel`   | ยกเลิกงานตาม `taskId`                                          |

ทักษะที่มีมาให้ในตัว: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`

### การ์ดเอเจนต์

```bash
GET /.well-known/agent.json
```

ส่งคืนการ์ดเอเจนต์ A2A สาธารณะ (ชื่อ คำอธิบาย ความสามารถ แค็ตตาล็อกทักษะ รูปแบบการยืนยันตัวตน) — แคชแบบสาธารณะเป็นเวลา 1 ชั่วโมง ไม่จำเป็นต้องยืนยันตัวตน

### ตัวช่วย REST

| เมธอด | พาธ                          | คำอธิบาย                                                                                                           |
| ----- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| GET   | `/api/a2a/status`            | สถานะการเปิดใช้ A2A + สถิติงาน + สรุปการ์ดเอเจนต์ที่แคชไว้                                                         |
| GET   | `/api/a2a/tasks`             | แสดงรายการงาน — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST  | `/api/a2a/tasks`             | (ยังไม่ได้ใช้งานเป็นตัวช่วย REST — สร้างผ่าน JSON-RPC `message/send`)                                              |
| GET   | `/api/a2a/tasks/[id]`        | ดึงข้อมูลงานหนึ่งรายการ                                                                                            |
| POST  | `/api/a2a/tasks/[id]/cancel` | ยกเลิกงาน                                                                                                          |

**การยืนยันตัวตน:** ตัวช่วย REST ทำงานโดยไม่ต้องใช้การยืนยันตัวตนสำหรับการจัดการ (แดชบอร์ดสามารถอ่านได้) ส่วนเส้นทาง JSON-RPC `/a2a` จะใช้ Bearer `OMNIROUTE_API_KEY` หากมีการกำหนดค่าไว้

## การจัดการ ACP (Agent Client Protocol)

ในรูปแบบโปรเซสลูก Endpoint เหล่านี้ใช้จัดการการตรวจหาเอเจนต์ ACP และการลงทะเบียน
เอเจนต์แบบกำหนดเอง

| เมธอด  | พาธ               | คำอธิบาย                                                                                                                                                  |
| ------ | ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/acp/agents` | แสดงรายการเอเจนต์ CLI ที่รู้จักทั้งหมด (ในตัว + กำหนดเอง) พร้อมสถานะการติดตั้ง เวอร์ชัน และไบนารี                                                         |
| POST   | `/api/acp/agents` | ลงทะเบียนเอเจนต์ ACP แบบกำหนดเองหรือรีเฟรชแคช — body: `{id, name, binary, versionCommand, providerAlias, spawnArgs, protocol}` หรือ `{action: "refresh"}` |
| DELETE | `/api/acp/agents` | ลบเอเจนต์ ACP แบบกำหนดเอง — พารามิเตอร์ query: `?id=<agentId>`                                                                                            |

**ตัวอย่างการตอบกลับ** (`GET /api/acp/agents`):

```json
{
  "agents": [
    {
      "id": "claude",
      "name": "Claude Code CLI",
      "binary": "claude",
      "version": "1.0.45",
      "installed": true,
      "protocol": "stdio",
      "providerAlias": "claude",
      "isCustom": false
    },
    {
      "id": "my-custom-cli",
      "name": "My Custom CLI",
      "installed": false,
      "protocol": "stdio",
      "providerAlias": "my-provider",
      "isCustom": true
    }
  ],
  "cacheTtlMs": 60000,
  "cacheAge": 1234
}
```

**การยืนยันตัวตน:** ต้องใช้เซสชันการจัดการ (คุกกี้ `auth_token` ของแดชบอร์ด) หรือ
คีย์ API ที่มีขอบเขตการจัดการ

ดูรายละเอียดทั้งหมดได้ที่ [เฟรมเวิร์ก ACP](../frameworks/ACP.md)

## การยืนยันตัวตน

ดู [การยืนยันตัวตนสำหรับการจัดการ](../guides/MANAGEMENT-AUTH.md) สำหรับข้อมูลประจำตัวทั้งสี่ตระกูล
(เซสชันแดชบอร์ด, โทเค็น CLI ภายในเครื่อง, Access Token `oma_live_…`,
คีย์ API ที่มีขอบเขตการจัดการ) และความแตกต่างจากคีย์สำหรับการอนุมาน

- เส้นทางแดชบอร์ด (`/dashboard/*`) ใช้คุกกี้ `auth_token`
- การเข้าสู่ระบบใช้แฮชรหัสผ่านที่บันทึกไว้ โดยจะใช้ `INITIAL_PASSWORD` เป็นตัวเลือกสำรอง
- สามารถสลับเปิดหรือปิด `requireLogin` ผ่าน `/api/settings/require-login`
- เส้นทาง `/v1/*` สามารถกำหนดให้ต้องใช้คีย์ API แบบ Bearer ได้เมื่อ `REQUIRE_API_KEY=true`
- "โทเค็นสำหรับการจัดการ" / "คีย์ API ที่มีขอบเขตการจัดการ" ในเอกสารอ้างอิงนี้หมายถึงหนึ่งในตระกูลที่ระบุไว้ในคู่มือดังกล่าว ไม่ใช่ข้อมูลลับประเภทเพิ่มเติมที่ไม่ได้กำหนดไว้

> **การเปลี่ยนแปลงที่ไม่เข้ากันกับเวอร์ชันก่อนหน้า (v3.8.0)** — ขณะนี้ `/api/v1/agents/tasks/*` และปลายทางสำหรับการจัดการช่วงพักจำเป็นต้องใช้ **การยืนยันตัวตนสำหรับการจัดการ** (คุกกี้ `auth_token` ของแดชบอร์ดหรือคีย์ API ที่มีขอบเขตการจัดการ) ไคลเอนต์ที่ก่อนหน้านี้เรียกเส้นทางเหล่านี้โดยไม่มีการยืนยันตัวตนจะได้รับ `401 Unauthorized` ดูคอมมิต `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`)
