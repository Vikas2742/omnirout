## Uzupełnienia czatu

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Niestandardowe nagłówki

| Nagłówek                 | Kierunek  | Opis                                                                                                                                                                                                                                                                                 |
| ------------------------ | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

| `x_session_id`           | Żądanie   | Akceptowany jest również wariant z podkreśleniami (bezpośredni HTTP)                                                                                                                                                                                                                 |

| `X-Request-Id`           | Żądanie   | Alternatywny klucz deduplikacji                                                                                                                                                                                                                                                      |
| `x-omniroute-connection` | Żądanie   | Przypina żądanie dotyczące jednego modelu do jednego połączenia dostawcy (konta) według jego identyfikatora — zobacz [Przypinanie konta dla każdego żądania](#account-pinning-per-request)                                                                                           |
| `X-OmniRoute-Cache`      | Odpowiedź | `HIT` lub `MISS` (bez strumieniowania)                                                                                                                                                                                                                                               |
| `X-OmniRoute-Idempotent` | Odpowiedź | `true`, jeśli przeprowadzono deduplikację                                                                                                                                                                                                                                            |
| `X-OmniRoute-Progress`   | Odpowiedź | `enabled`, jeśli śledzenie postępu jest włączone                                                                                                                                                                                                                                     |
| `X-OmniRoute-Session-Id` | Odpowiedź | Efektywny identyfikator sesji używany przez OmniRoute                                                                                                                                                                                                                                |

#### Przypinanie konta dla poszczególnych żądań

Gdy dostawca ma kilka połączeń (kont lub kluczy), OmniRoute zwykle wybiera jedno z nich
zgodnie ze swoją strategią wyboru konta. Zamiast tego żądanie może przypiąć jedno konkretne
połączenie za pomocą nagłówka `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Gdzie znaleźć identyfikator.** Otwórz stronę dostawcy w panelu
  (**Panel → Dostawcy → <provider>**) i kliknij znacznik identyfikatora `xxxxxxxx…` w wierszu
  połączenia — pełny identyfikator połączenia zostanie skopiowany.
- **Które żądania go uwzględniają.** Żądania dotyczące pojedynczego modelu (`provider/model`) wysyłane do
  `/v1/chat/completions`, `/v1/messages` i `/v1/responses`. Kombinacje ignorują ten nagłówek: konto
  należy przypiąć osobno dla każdego kroku kombinacji, korzystając z połączenia danego kroku.
- **Przypięcie jest ścisłe, a nie preferencyjne.** Przypięte połączenie jest używane wyłącznie. Awaria
  podczas obsługi żądania powoduje zapisanie okresu karencji konta, ale **nie** skutkuje przełączeniem
  na inne konto tego samego dostawcy.
- **Okres karencji i limit zwalniają przypięcie.** Gdy przypięte połączenie jest objęte okresem karencji,
  wyczerpało limit lub zostało zablokowane przez zasadę limitów, kolejne żądania przełączają się na inne
  połączenia dostawcy, dokładnie tak jak ruch bez przypięcia.
- **Nieznane lub wyłączone identyfikatory powodują błąd.** Identyfikator, którego nie ma w aktywnej puli dostawcy (ponieważ został usunięty,
  dezaktywowany lub należy do innego dostawcy), oznacza brak kwalifikującego się konta, dlatego żądanie
  kończy się niepowodzeniem zamiast zostać po cichu przekierowane gdzie indziej.

Claude Code wysyła niestandardowe nagłówki za pośrednictwem `ANTHROPIC_CUSTOM_HEADERS`. Umieść tę zmienną w bloku `env`
pliku `~/.claude/settings.json` albo w pliku `.claude/settings.json` na poziomie projektu, aby przypisać inne
konto do każdego projektu:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Źródło: `src/sse/handlers/chat.ts` (odczyt nagłówka), `src/sse/services/auth.ts` oraz
`src/sse/services/sessionAffinityPin.ts` (zwalnianie przypięcia i sprawdzanie braku w puli).

> **Nagłówki telemetrii kosztów:** odpowiedzi zakończone powodzeniem bez strumieniowania zawierają również zestaw telemetrii kosztów `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, stałe 10 miejsc po przecinku; `0.0000000000` dla żądań bezpłatnych lub bez określonej ceny), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` oraz `X-OmniRoute-Fallback-Attempts` (tylko gdy > 0), a także `X-OmniRoute-Request-Id` i `X-OmniRoute-Version`. Są one emitowane przez uzupełnienia czatu, `/v1/responses`, `/v1/messages` **oraz punkty końcowe multimediów** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` i `/v1/moderations` (koszt zawsze wynosi `0`). Koszt multimediów jest obliczany według modalności (za obraz, sekundę, znak lub jednostkę wyszukiwania), jeśli informacje o cenach są dostępne; w przeciwnym razie wynosi `0` (zgodnie z zasadą fail-open).

> **Semantyka kosztu trafienia w pamięci podręcznej:** w przypadku TRAFIENIA w semantycznej pamięci podręcznej (`X-OmniRoute-Cache-Hit: true`) nie jest wykonywane żadne wywołanie usługi nadrzędnej, dlatego `X-OmniRoute-Response-Cost` wynosi `0.0000000000` (**przyrostowy** koszt obsługi trafienia). Pierwotny koszt lub koszt, który zostałby poniesiony, jest raportowany osobno w `X-OmniRoute-Cost-Saved`. Systemy rozliczeniowe powinny sumować `X-OmniRoute-Response-Cost` (trafienia nic nie kosztują), natomiast narzędzia analityczne pamięci podręcznej mogą agregować `X-OmniRoute-Cost-Saved`.

## Wyłączne dzierżawy zarządzanych sesji

Wyłączne dzierżawienie zarządzanych sesji to opcjonalny, niezależny od klienta kontrakt routingu: jeden aktywny właściciel
utrzymuje jedno kwalifikujące się połączenie OmniRoute. Nie dzierżawi ono modelu, nie wymaga OAuth, nie identyfikuje
konkretnego klienta ani nie wymaga określonego dostawcy.

Uwierzytelniający klucz API musi mieć zakres `lease:exclusive` oraz jawną, niepustą
listę `allowedConnections`. Granica mutacji bazy danych wymusza obecność obu pól zarówno podczas
tworzenia klucza, jak i częściowych aktualizacji.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Pomyślne odpowiedzi dla uzyskania, odnowienia i zwolnienia udostępniają znaczniki czasu, `state` oraz dokładną dodatnią
wartość `generation`, ale nigdy wybrane połączenie ani dane uwierzytelniające. W przypadku odnowienia i zwolnienia
generacja jest przekazywana w treści JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Właściciel aktywnej dzierżawy może jawnie zażądać bezpiecznych pod względem prywatności metadanych wyświetlania dla swojego bieżącego powiązania:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Ta opcjonalna akcja sprawdzania statusu jest zabezpieczona nieprzezroczystym identyfikatorem właściciela, uwierzytelnionym zarządzanym kluczem API oraz dokładną
aktywną generacją w ramach pojedynczej transakcji bazy danych. `displayName` jest wyłącznie przyciętą skonfigurowaną
nazwą połączenia; ma wartość `null`, gdy nie istnieje bezpieczna skonfigurowana nazwa. OmniRoute nigdy nie zastępuje jej
adresem e-mail ani wygenerowaną tożsamością konta. Wartość dostawcy jest niewrażliwą etykietą wyświetlaną i nigdy
nie jest wygenerowanym identyfikatorem zgodnego dostawcy. Dane uwierzytelniające, tokeny, pliki cookie, nieprzetworzone identyfikatory połączeń lub kluczy
API, skróty właścicieli, sekrety odgradzające oraz wewnętrzne dane routingu są wykluczone.

Wyszukiwania z nieprawidłowym kluczem, nieprawidłowym właścicielem, nieaktualną generacją, a także dotyczące brakujących, wygasłych, zwolnionych lub unieważnionych dzierżaw
zwracają ten sam błąd `409 LEASE_FENCE_STALE` bez metadanych połączenia. Klient, który otrzymał odpowiedź oczekiwania na dostępność, nie ma aktywnego powiązania do sprawdzenia. Gdy routing przełącza aktywną dzierżawę,
ta sama generacja pozostaje ważna, a status niepodzielnie zwraca nowe powiązanie, nigdy stare.
Działanie istniejących klientów pozostaje bez zmian, ponieważ odpowiedzi dotyczące uzyskania, odnowienia, zwolnienia i oczekiwania zachowują
swoje dotychczasowe formaty.

Ten kontrakt serwera nie zmienia standardowego punktu `/status` OpenAI Codex. Standardowy Codex obecnie zgłasza swojego
dostawcę modelu oraz wbudowany stan uwierzytelniania/konta, ale nie wyświetla dowolnych niestandardowych
metadanych konta dostawcy; przyszła integracja klienta musi wywołać tę akcję i zdecydować, jak
wyświetlić `connection.displayName`.

Każde zarządzane żądanie inferencji przekazuje następnie oba nagłówki sterujące:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Dokładny właściciel, generacja, aktywne połączenie oraz uwierzytelniony klucz API są weryfikowane
bezpośrednio przed każdą obsługiwaną próbą wysłania żądania do usługi nadrzędnej. Ponowne użycie właściciela i generacji z innym kluczem kończy się niepowodzeniem nawet
wtedy, gdy ten klucz zezwala na to samo połączenie. Nieprzetworzone identyfikatory właścicieli nie są utrwalane, rejestrowane w dziennikach, zachowywane w
migawce żądania ani przekazywane do usługi nadrzędnej.

Tymczasowa rywalizacja o zasoby zwraca HTTP `429` z `Retry-After` oraz:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Ta odpowiedź oznacza wyłącznie, że standardowy zbiór kwalifikujących się połączeń nie był pusty, a każdy wolny kandydat był
zajęty przez obcą aktywną dzierżawę. Nieobsługiwane modele/dostawcy, niezgodność zasad, okres karencji, limit,
stan kondycji oraz inne standardowe błędy kwalifikacji zachowują swoje dotychczasowe odpowiedzi OmniRoute.

### `x-omniroute-compression`

Nadpisanie planu kompresji dla pojedynczego żądania. Najwyższy priorytet — ma pierwszeństwo przed nadpisaniem kombinacji routingu,
aktywnym profilem, automatycznym wyzwalaczem oraz ustawieniem domyślnym panelu. Wartości:

| Wartość       | Efekt                                                                                                                          |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `off`         | Brak kompresji dla tego żądania.                                                                                               |
| `default`     | Profil domyślny pochodzący z panelu (ignoruje aktywny profil). Mechanizmy stratne pozostają wyłączone.                         |
| `safe`        | Tylko deduplikacja i zwijanie białych znaków.                                                                                  |
| `allow-lossy` | Zachowuje plan operatora dla tego żądania, w tym podsumowania i przekształcenia stylu.                                         |
| `engine:<id>` | Pojedynczy mechanizm, gdy jest włączony, np. `engine:rtk`. Opcjonalne włączenie tego mechanizmu dla pojedynczego żądania.      |
| `<combo>`     | Nazwana kombinacja, dopasowywana najpierw według nazwy (bez uwzględniania wielkości liter), a następnie według identyfikatora. |

Uwagi:

- Nieznane wartości są ignorowane (żądanie nigdy nie jest odrzucane); rozstrzyganie przechodzi do standardowej kolejności priorytetów operatora.
- Jeśli wiele kombinacji ma tę samą nazwę, przekaż **identyfikator** kombinacji, aby uzyskać deterministyczne dopasowanie.
- Kombinacji o nazwie `off` lub `default` nie można wybrać według nazwy (te słowa kluczowe są interpretowane jako pierwsze); odwołuj się do takiej kombinacji za pomocą jej identyfikatora.
- Główny przełącznik kompresji stanowi bezwzględną blokadę: gdy kompresja jest globalnie wyłączona, ten nagłówek nie może jej włączyć.

Zastosowany plan jest zwracany w nagłówku odpowiedzi:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

gdzie `<source>` jest jedną z wartości `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` lub `off`.

## Osadzenia

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Dostępni dostawcy: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Identyfikatory katalogowe mają postać `provider/model` (przykład: `jina-ai/jina-embeddings-v5-omni-small`). Same identyfikatory modeli Jina występujące w rejestrze (na przykład `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) również są rozpoznawane. Operacje embed/rerank/classify/segment w Jina używają najpierw danych uwierzytelniających `jina-ai` z panelu; `JINA_AI_API_KEY` służy jako rozwiązanie rezerwowe tylko wtedy, gdy w panelu nie istnieje żaden klucz. Karta `jina-reader` jest przeznaczona wyłącznie dla Reader / `r.jina.ai` (`POST /v1/web/fetch`) i nigdy nie obsługuje osadzeń ani rerankingu.

Modele w rejestrze, które deklarują obsługę multimodalną, przyjmują również maksymalnie 32 ustrukturyzowane
elementy niezależne od dostawcy. Typy elementów multimedialnych to `text`, `image`, `audio`, `video` i `document`. Ich multimedialne `source`
ma postać `{"type":"url","url":"https://..."}` albo
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
oraz alias rodziny `jina-ai/jina-embeddings-v5-omni` → omni-small) przyjmuje również natywne dokumenty
EmbeddingsV5Request firmy Jina i **przekazuje je bez zmian** do `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Natywne wartości `{ image | audio | video | pdf }` mogą być publicznym adresem URL HTTPS, identyfikatorem URI `data:` albo surowymi
danymi base64. OmniRoute nie konwertuje tych obiektów na ciągi znaków ani nie pobiera natywnych adresów URL obrazów — Jina samodzielnie pobiera
publiczne multimedia. Dodatkowe pola Jina (`task`, `normalized`, `truncate`, `embedding_type`) są
przekazywane dalej. Jednostki SKU Jina obsługujące wyłącznie tekst nadal odrzucają dokumenty nietekstowe.

Ograniczenia bezpieczeństwa i transportu:

- Zdalne adresy URL multimediów muszą być publicznymi adresami HTTPS. Kanoniczne elementy `{type,source:url}` są pobierane
  po stronie serwera (ponowna walidacja przekierowań, limit czasu, limity rozmiaru, publiczny DNS, przypięcie połączenia) i
  osadzane bezpośrednio przed wywołaniem dostawcy. Natywne elementy Jina `{image:"https://..."}` są przekazywane bez zmian
  po przeprowadzeniu tej samej kontroli publicznego HTTPS; Jina pobiera zawartość z adresu URL.
- Multimedialne dane base64 przesyłane bezpośrednio są ograniczone do 8 MiB zdekodowanych danych na element i 16 MiB zdekodowanych danych w całym żądaniu.

Translacja dla dostawców (elementy kanoniczne nigdy nie są przekazywane bez zmian):

- Multimodalne modele Jina: każdy element najwyższego poziomu staje się jednym obiektem z kluczem odpowiadającym modalności
  (`text` / `image` / `audio` / `video` / `pdf`), używającym identyfikatorów URI danych dla multimediów przesyłanych bezpośrednio; jeden wektor na
  element najwyższego poziomu.
- Rodzina Gemini Embedding 2: jedna tablica najwyższego poziomu staje się pojedynczym natywnym
  żądaniem `models/{model}:embedContent` z `content.parts` (`text` lub `inline_data`).
- llama.cpp (`llama-cpp/<model>`, dowolny model załadowany przez lokalny serwer): kanoniczne elementy `text`
  stają się zwykłymi ciągami znaków, a elementy `image` / `audio` / `video` stają się osobnymi
  obiektami `{"content": [part]}`, używającymi części zawartości czatu llama-server (`image_url`,
  `input_audio` z formatem `wav` / `mp3` / `flac`, `input_video`) z danymi osadzonymi bezpośrednio; jeden wektor
  na element najwyższego poziomu. Serwer musi działać z opcjami `--embedding --mmproj …`; bez projektora
  samodzielnie odrzuca multimedia. `document` nie jest obsługiwany.
- Nieznane/dynamiczne modele bez jawnych metadanych modalności odrzucają ustrukturyzowane dane wejściowe z kodem HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Nieobsługiwane kombinacje modelu i modalności zwracają kod HTTP 400 zamiast przekształcać element. Pola rozszerzeń niezwiązane z danymi wejściowymi
w starszych żądaniach opartych na ciągach znaków/tokenach nadal są przekazywane bez zmian.

```bash
# Wyświetl wszystkie modele osadzeń
GET /v1/embeddings
```

## Generowanie obrazów

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Dostępni dostawcy obejmują OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (lokalnie), ComfyUI (lokalnie).

Parametr `n` zwraca `n` obrazów w `data[]`. W przypadku dostawców, których nadrzędne API zwraca jeden obraz na wywołanie
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), wykonywanych jest `n` oddzielnych wywołań nadrzędnych, przy czym jednocześnie trwają maksymalnie 4. Stała
wartość `seed` jest zwiększana o indeks wywołania (`seed`, `seed + 1`, …), dzięki czemu obrazy różnią się, ale pozostają
odtwarzalne. Wartość `n` jest ograniczona do 10. Całe żądanie kończy się niepowodzeniem, jeśli którekolwiek wywołanie się nie powiedzie. Lista
formatów korzystających z rozdzielania wywołań znajduje się w `SINGLE_IMAGE_FANOUT_FORMATS` w pliku
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux ponownie wykorzystuje istniejące połączenie z kluczem API i akceptuje prefiksy `zenmux/` lub `zm/`:

- `zenmux/openai/gpt-image-2` korzysta z interfejsu OpenAI Images API usługi ZenMux. Opcje obejmują `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` oraz `response_format`.
- Inni wydawcy, tacy jak `zm/meta/muse-image-1.0`, korzystają z punktu końcowego Vertex AI `:predict`
  usługi ZenMux. Parametr `n` jest mapowany na `sampleCount`, `aspect_ratio` na `aspectRatio`, a `image_size`
  (`1K`, `2K`, `4K`) na `sampleImageSize`. Wartość `size` podana w pikselach określa wyłącznie proporcje obrazu,
  a nie gwarantowane wymiary w pikselach. Obsługiwane proporcje, rozdzielczości i liczby różnią się zależnie od modelu.
- `zm/inclusionai/ming-image-0.1-design` samodzielnie wybiera wymiary. Należy pominąć `size`,
  `aspect_ratio` oraz `image_size`; jawne wartości powodują zwrócenie HTTP 400. Formaty PNG, JPEG i WebP
  można wskazać za pomocą `output_format`.

Ta integracja obsługuje generowanie obrazów na podstawie tekstu, ale nie edycję z użyciem obrazu referencyjnego. Dane wyjściowe Vertex
są normalizowane do `data[].b64_json`; `response_format: "url"` zwraca nadrzędny
adres URL HTTPS lub adres URL danych base64, gdy dostępne są tylko bajty obrazu. Puste lub odfiltrowane wyniki
powodują zwrócenie błędu zamiast pustej odpowiedzi o powodzeniu. Dostęp do modeli zależy od konta ZenMux.
Zobacz [Vertex API usługi ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) oraz
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Wyświetl wszystkie modele obrazów
GET /v1/images/generations
```

## OCR dokumentów

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

Parametr `model` wybiera dostawcę OCR za pomocą prefiksu `provider/model`; sam identyfikator modelu (np.
`mistral-ocr-latest`) jest rozpoznawany jako należący do zarejestrowanego dostawcy, a pominięcie `model` powoduje domyślne użycie
Mistral (`mistral-ocr-latest`). Zarejestrowani dostawcy (`open-sse/config/ocrRegistry.ts`):

| Identyfikator dostawcy        | Identyfikator modelu | Wartość `model`                                              | Uwagi                                                                                                                                                   |
| ----------------------------- | -------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (lub samo `mistral-ocr-latest`) | Synchronicznie — odpowiedź jest zwracana bezpośrednio z pojedynczego wywołania nadrzędnego.                                                             |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                  | Asynchroniczne wywołanie nadrzędne (`analyze` + odpytywanie) — szczegóły poniżej.                                                                       |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                      | Synchronicznie, przez partnerski punkt końcowy Vertex AI `openapi/chat/completions` — informacje o uwierzytelnianiu i adresie URL znajdują się poniżej. |

Wszyscy trzej dostawcy zwracają odpowiedź o tej samej strukturze zgodnej z Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Przepływ odpytywania Azure Document Intelligence

Interfejs API `analyze` usługi Azure Document Intelligence działa asynchronicznie: początkowe żądanie zwraca
nagłówek `Operation-Location` zamiast treści, a wynik musi być cyklicznie odpytywany. Procedura obsługi
(`open-sse/handlers/ocr.ts`) odpytuje ten adres URL co sekundę, wykonując maksymalnie 30 prób, natychmiast kończy się niepowodzeniem (bez
dalszego odpytywania) w przypadku odpowiedzi odpytywania innej niż `ok` lub stanu `"failed"` oraz zwraca `504`, jeśli
operacja nadal trwa po wyczerpaniu limitu prób. Końcowa odpowiedź Azure jest
normalizowana do tej samej struktury `pages`/`markdown`, której używa Mistral, zanim zostanie zwrócona
wywołującemu, dzięki czemu kod klienta nie musi osobno obsługiwać tego dostawcy.

### Uwierzytelnianie i rozpoznawanie punktu końcowego Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` ponownie wykorzystuje ten sam mechanizm uwierzytelniania Vertex AI, który OmniRoute obsługuje już dla
ruchu czatu i obrazów (`open-sse/executors/vertex.ts`): klucz API połączenia jest albo
poświadczeniem Service Account w formacie JSON (wymienianym na krótkotrwały token dostępu OAuth za pomocą przepływu JWT-bearer),
albo już wygenerowanym tokenem dostępu OAuth używanym bez zmian. Nadrzędny adres URL punktu końcowego to ogólny
partnerski punkt końcowy Vertex `openapi/chat/completions`, utworzony na podstawie projektu i
regionu połączenia — jawnie określone `providerSpecificData.project`/`providerSpecificData.region` zawsze mają pierwszeństwo;
w przeciwnym razie projekt jest ustalany na podstawie `project_id` z danych Service Account w formacie JSON, a domyślnym regionem
jest `us-central1`. Obie wartości są ustalane w `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) i używane przez
`src/app/api/v1/ocr/route.ts` przed przekazaniem żądania do `handleOcr`.

### Prefiksy identyfikatorów modeli (`?prefix=`)

Większość modeli jest udostępniana z **prefiksem dostawcy**. Używany prefiks jest kontrolowany przez
flagę funkcji `MODELS_CATALOG_PREFIX_MODE` i może zostać nadpisany **dla każdego żądania** za pomocą
parametru zapytania — jest to przydatne dla klienta, który chce uzyskać przejrzystą listę bez zmieniania
ustawienia obowiązującego na całym serwerze dla wszystkich pozostałych użytkowników:

```bash
GET /v1/models?prefix=alias        # jeden identyfikator na model — krótki prefiks aliasu
GET /v1/models?prefix=dual         # obie formy (ustawienie domyślne serwera)
GET /v1/models?prefix=canonical    # tylko pełny prefiks identyfikatora dostawcy
```

| Tryb        | Zwraca                                                     | Uwagi                                                                                                                                                                                                              |
| ----------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `dual`      | `cc/claude-sonnet-4-6` **oraz** `claude/claude-sonnet-4-6` | **Domyślny.** Oba identyfikatory kierują do tego samego modelu; zachowano je, aby konfiguracje klientów z zakodowaną na stałe dowolną z tych form nadal działały. Mniej więcej podwaja rozmiar katalogu.           |
| `alias`     | `cc/claude-sonnet-4-6`                                     | Jeden wpis na model. Dostawcy bez odrębnego aliasu nadal zwracają swój wpis, więc nic nie zostaje pominięte.                                                                                                       |
| `canonical` | `claude/claude-sonnet-4-6`                                 | Jeden wpis na model z pełnym prefiksem identyfikatora dostawcy. Dostawcy bez odrębnego aliasu (np. `antigravity/…`, `agy/…`) również zwracają tutaj swój pojedynczy identyfikator, więc nic nie zostaje pominięte. |

Lustrzany wpis w trybie `dual` można rozpoznać również bez parametru zapytania: zawiera pole `parent`
wskazujące główny identyfikator.

Klienci wyświetlający selektor modeli powinni wysyłać żądanie `?prefix=alias` — tak robi
[rozszerzenie OmniCopilot dla VS Code](../guides/VSCODE-COPILOT.md).

### Filtry wyszukiwania (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` obsługuje opcjonalne filtry wyszukiwania. Bez żadnego z nich odpowiedź pozostaje
niezmieniona. Zawężają one katalog, który wywołujący już widzi (najpierw stosowane są uprawnienia klucza API),
i są stosowane przed stronicowaniem w stylu OpenAI za pomocą `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # każda wymieniona funkcja musi mieć wartość true
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # katalogowe `type`; wiersze bez niego są typu `chat`
GET /v1/models?q=sonnet&limit=10                           # dopasowanie identyfikatora lub nazwy bez rozróżniania wielkości liter
```

| Parametr      | Wartości                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | nieujemna liczba całkowita, porównywana z `context_length`                                          |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 znaków                                                                                        |

Nieznana wartość lub `min_context`, który nie jest nieujemną liczbą całkowitą (na przykład `1.5`),
powoduje zwrócenie HTTP `400`, a komunikat zawiera listę prawidłowych wartości. Implementacja:
`src/app/api/v1/models/catalogFilters.ts`.

### Krótka lista modeli (`POST /v1/models/query`)

`POST /v1/models/query` zwraca krótką, deterministyczną listę z tego samego katalogu, z takim samym
uwierzytelnianiem i widocznością zależną od klucza jak w przypadku `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Każde pole jest opcjonalne. `capabilities` i `exclude` przyjmują tablicę lub ciąg rozdzielany przecinkami;
`max_output` jest porównywane z `max_output_tokens`. Wyniki są sortowane według `owned_by`, a następnie `id`.
Wartość domyślna `limit` to `20`, a wartości powyżej `100` są ograniczane do `100`. Nieprawidłowy JSON, nieznane
pole lub nieprawidłowa wartość powodują zwrócenie HTTP `400`.

### Indywidualnie ukryte modele czatu

Model oznaczony jako **Ukryty** na stronie jego dostawcy jest wykluczany z katalogu, a przy jawnym
żądaniu zostaje odrzucony z HTTP `404` / `model_not_found`. Sprawdzenie wykorzystuje rozpoznanego
dostawcę i model, w tym aliasy dostawców, prefiksy węzłów zgodnych dostawców oraz wartości domyślne
połączenia. Kombinacja pomija ukryte cele i może użyć widocznego modelu równorzędnego; gdy nie pozostaje
żaden możliwy do wykonania cel, zwracany jest ten sam kod błędu. Odkrycie modelu zaczyna obowiązywać przy
następnym żądaniu. Nadpisania widoczności dotyczące wyłącznie obrazów nie ukrywają modelu czatu o tym samym identyfikatorze.

To indywidualne ustawienie modelu jest niezależne od
[list dozwolonych/zabronionych modeli](../routing/MODEL_EXPOSURE_LIST.md), które filtrują
prezentowanie katalogu i kandydatów do automatycznego routingu, zachowując jednocześnie jawne kierowanie. Uprawnienia
modeli dla klucza API nadal obowiązują niezależnie. Domyślnym trybem prefiksu katalogu pozostaje `dual`.

### Warianty modeli bez myślenia

W przypadku modeli Claude obsługujących myślenie `/v1/models` udostępnia również wariant **bez myślenia**, którego identyfikator ma prefiks `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Wybranie tego identyfikatora (np. w konfiguracji Claude Code, która zawsze dołącza blok `thinking`) jest rozwiązywane z powrotem do rzeczywistego `<provider>/<model>` z wyłączonym rozumowaniem — `thinking:{type:"disabled"}` w ścieżce `/v1/messages` albo z pominięciem pól `reasoning`/`reasoning_effort` w ścieżce `/v1/chat/completions`. Wariant jest wyświetlany tylko dla modeli z rodziny Claude, które obsługują myślenie **i** respektują wartość `disabled` (dlatego np. modele obsługujące wyłącznie tryb adaptacyjny, które odrzucają `disabled`, są wykluczone). Operatorzy mogą wymusić włączenie lub wyłączenie wariantu dla poszczególnych modeli za pomocą `ModelSpec.noThinkingAlias`.

## Generowanie dźwięku za pomocą ElevenLabs

Skonfiguruj połączenie z dostawcą `elevenlabs` w OmniRoute przy użyciu klucza API ElevenLabs.
Klienci uwierzytelniają się za pomocą swojego klucza **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
brama przekazuje zapisany klucz dostawcy jako `xi-api-key`. Nigdy nie wysyłaj klucza ElevenLabs
jako tokenu bearer bramy.

| Metoda | Ścieżka                     | Odpowiedź                                      | Kategoria punktu końcowego klucza API |
| ------ | --------------------------- | ---------------------------------------------- | ------------------------------------- |
| POST   | `/v1/sound-generation`      | Natywne bajty audio                            | `elevenlabs`                          |
| POST   | `/v1/music`                 | Natywne bajty audio                            | `music`                               |
| POST   | `/v1/music/stream`          | Strumieniowe bajty audio                       | `music`                               |
| POST   | `/v1/music/detailed`        | Natywne wieloczęściowe audio i plan kompozycji | `music`                               |
| POST   | `/v1/music/detailed/stream` | Natywne metadane SSE i fragmenty audio         | `music`                               |
| POST   | `/v1/music/plan`            | Plan kompozycji w formacie JSON                | `music`                               |

Te punkty końcowe uzupełniają istniejące trasy `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` oraz `/v1/speech-to-text`. Natywne pola JSON
i parametry zapytania, takie jak `output_format` oraz `enable_logging`, są zachowywane.
Odpowiedzi `/v1/music/detailed` zachowują swoje granice multipart; należy je analizować jako multipart.
`/v1/music/detailed/stream` zwraca `text/event-stream` z metadanymi kompozycji oraz
fragmentami audio zakodowanymi w base64 w zdarzeniach SSE. Wszystkie sześć tras obsługuje żądania wstępne CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Krótki efekt dźwiękowy. Czas trwania: od 0,5 do 30 sekund.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Czas trwania muzyki jest wyrażony w milisekundach: od 3000 do 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Użyj `/v1/music/stream` z tą samą treścią JSON, aby przesyłać audio przyrostowo. Kompozycja
akceptuje dokładnie jedno z pól `prompt` lub `composition_plan`; `/v1/music/plan` wymaga `prompt`
i opcjonalnie akceptuje `source_composition_plan`. Natywne schematy zachowują dodatkowe
pola dostawcy, dzięki czemu wersje planu kompozycji i opcje dostrajania są przekazywane do ElevenLabs.

Ujednolicony punkt końcowy `/v1/music/generations` również akceptuje `elevenlabs/music_v1`,
`elevenlabs/music_v2` oraz `elevenlabs/music_v2_5`. Przy aktywnym połączeniu z ElevenLabs
modele te są udostępniane w katalogu muzyki. Ten punkt końcowy zwraca
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Jego pole `duration` jest wyrażone w
sekundach i mapowane na `music_length_ms`; jawnie określone `music_length_ms` ma pierwszeństwo.
`instrumental` jest mapowane na `force_instrumental`, przy czym pierwszeństwo ma pole natywne.
Do przesyłania strumieniowego używaj natywnych punktów końcowych przesyłania strumieniowego, a do
żądań opartych wyłącznie na planie kompozycji — natywnego punktu końcowego kompozycji.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Ograniczenia dotyczące punktu końcowego, modelu, budżetu i połączenia są stosowane przed wywołaniem usługi nadrzędnej. Natywne
trasy zwracają bez zmian kody stanu i treści błędów usługi nadrzędnej, w tym `402` w przypadku
ograniczenia planu oraz `429` w przypadku limitu przydziału. Nagłówki `character-cost`, `song-id`, `request-id` oraz `retry-after`
są zachowywane, jeśli występują. Bezpłatne saldo środków nie gwarantuje dostępu do każdego
modelu muzycznego, formatu wyjściowego ani funkcji API: ElevenLabs określa uprawnienia dla każdego żądania.
Ujednolicony punkt końcowy zachowuje kody stanu błędów w znormalizowanej otoczce błędów OmniRoute.

Kontrakty usługi nadrzędnej: [efekty dźwiękowe](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[kompozycja muzyczna](https://elevenlabs.io/docs/api-reference/music/compose) oraz
[szczegóły strumieniowania muzyki](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

Wszystkie trasy POST mają tę samą strukturę: `Bearer your-api-key` + treść JSON zweryfikowana za pomocą Zod (`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema` itd.; zobacz `src/shared/validation/schemas.ts`). W przypadku niepowodzenia walidacji schematu zwracany jest kod 4xx.

W przypadku klientów, którzy nie mogą dołączyć nagłówka `Authorization: Bearer ...`, OmniRoute akceptuje również klucze API w adresie URL — za pośrednictwem parametrów zapytania zapewniających zgodność (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) lub dedykowanych punktów końcowych `/api/v1/vscode/{token}/...` opisanych poniżej.

```bash
# Ponowne rangowanie (dostawca z rejestru chmurowego lub węzeł dostawcy zgodny z OpenAI jako "<prefix>/<model>")
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Klasyfikacja Jina (dane uwierzytelniające Foundation API)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Segmentator Jina
POST /v1/segment     { "content": "...", "return_chunks": true }

# Wyszukiwanie Jina (s.jina.ai; aliasy dostawcy: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# Moderacja
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — zwraca treść audio/mpeg (lub w żądanym formacie)
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS wymaga języka i głosu: wartość domyślna `language` to "en"; brakujący
# głos lub standardowa nazwa głosu OpenAI (alloy, nova, …) zostaje zastąpiona przez "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# Edycja obrazu (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# Generowanie wideo / muzyki (identyfikator modelu z prefiksem dostawcy)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **Węzły dostawców rerankingu:** `POST /v1/rerank` kieruje również żądania do węzłów dostawców zgodnych z OpenAI
> (oMLX, vLLM, Infinity, TEI za bramą, …), adresowanych jako `<node-prefix>/<model>`. Węzły
> pętli zwrotnej (`localhost`, `127.0.0.1`, `172.16.0.0/12`) są zawsze dozwolone, podobnie jak nazwy hostów
> wymienione przez operatora w `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (np. nazwa usługi Docker/Compose,
> taka jak `http://reranker:8080/v1`; są one wywoływane bezpośrednio, nigdy przez `HTTP(S)_PROXY` ani
> przypisany na stałe serwer proxy połączenia). Węzły na dowolnym innym
> hoście — urządzeniu w sieci LAN lub hoście równorzędnym Tailscale — są dozwolone tylko wtedy, gdy operator włączy
> flagę funkcji `RERANK_REMOTE_PROVIDER_NODES` **oraz** bazowy adres URL węzła przejdzie weryfikację zgodności z zasadami
> wychodzących adresów URL dostawcy (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Etap rerankingu silnika pamięci wywołuje tę trasę przez
> pętlę zwrotną, dlatego ta sama reguła dotyczy `rerankProviderModel` w ustawieniach pamięci.
>
> **Struktury serwerów lokalnych:** węzeł jest wywoływany pod adresem `<base>/v1/rerank`, a w przypadku odpowiedzi 404 — pod adresem `<base>/rerank`
> (Infinity, TEI). Treść żądania wysyłanego do serwera nadrzędnego zawiera zarówno nazewnictwo Cohere/OpenAI (`documents`,
> `return_documents`), jak i nazewnictwo TEI (`texts`, `return_text`), a odpowiedź serwera nadrzędnego jest
> normalizowana do formatu obwiedni Cohere: nieopakowane `[{index, score, text}]` z TEI, `{results: [{index, score}]}`
> z prostych bram oraz `{data: [...]}` w stylu Voyage są zwracane klientowi jako
> `{results: [{index, relevance_score, document?}]}`, posortowane według wyniku i ograniczone do `top_n`.

> **Wykrywanie węzłów dostawców:** modele znajdujące się w węźle dostawcy zgodnym z OpenAI pojawiają się w `GET /v1/models`
> pod prefiksem węzła. Wiersze, które nie zawierają metadanych punktu końcowego (co jest typowe dla lokalnych list `/v1/models`),
> dziedziczą `apiType` węzła, dzięki czemu modele węzła `embeddings` mają `type: "embedding"`, a modele
> węzła `rerank` mają `type: "rerank"`, zamiast domyślnie otrzymywać typ czatu; jawnie określone
> `supportedEndpoints` w zsynchronizowanym lub ręcznie dodanym wierszu nadal ma pierwszeństwo.

### Opcje `provider_options` dla Exa i Tavily

Exa i Tavily odczytują pola specyficzne dla dostawcy z przestrzeni nazw:
`provider_options.exa` (lub `provider_options["exa-search"]`) oraz `provider_options.tavily`
(lub `provider_options["tavily-search"]`). Przekazywane są wyłącznie poniższe klucze. Każdy z nich jest
sprawdzany względem własnego schematu Zod w `open-sse/handlers/search/providerOptionsPassthrough.ts`,
a klucz o nieprawidłowym typie jest odrzucany. Każdy inny klucz jest ignorowany, w tym dane uwierzytelniające, bazowy adres URL,
`stream` i `outputSchema`. Płaskie klucze używane przez innych dostawców (`cx`, `depth`, ...) działają
jak wcześniej.

| Dostawca | Pola najwyższego poziomu                                                                                                                                                                                                                                                                                                                                                  | Zagnieżdżone                                                                                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa      | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (płaskie wartości proste), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                      | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` scalone z domyślnym `{ text: true, highlights: true }` |
| Tavily   | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                             |

Pola ogólne mają zawsze pierwszeństwo: `query`, `max_results`, `filters` (domeny), `country` oraz
temat wyprowadzony z `search_type`. W Exa ustawienie `search_type: "news"` zachowuje `category: "news"`.
Tavily akceptuje również `search_type: "finance"` (`topic: "finance"`).

Ogólne pole `time_range` jest teraz przekazywane do obu dostawców: Exa otrzymuje `startPublishedDate` (znacznik czasu ISO),
a Tavily — `start_date` (`YYYY-MM-DD`). Jawnie podana data w `provider_options`
zastępuje wartość wynikającą z mapowania.

Wyniki Exa zachowują `id`, `highlight_scores`, `summary`, `subpages`, `entities` i `extras` w
`provider_raw`. Wyniki Tavily zachowują `images` i `favicon`.

Rozliczanie kosztów nadal korzysta z płaskiego rejestru `costPerQuery`. Tavily nalicza
więcej kredytów za wywołanie przy `search_depth: "advanced"`, a różnica ta nie jest uwzględniana w
`usage.search_cost_usd`.

## Interfejs Web Fetch API

Wyodrębnia zawartość z adresu URL za pośrednictwem skonfigurowanego dostawcy web-fetch (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, ten sam klucz API co w Parallel Search) zwraca wyłącznie Markdown
— każdy inny `format` powoduje odpowiedź `400` — i ogranicza zawartość do 100 000 znaków. Gdy
nie można wyodrębnić samej strony docelowej, usługa nadrzędna zgłasza to w odpowiedzi HTTP 200;
OmniRoute udostępnia ten błąd jako `422` ze stałym komunikatem.

| Metoda | Ścieżka         | Opis                                                                          |
| ------ | --------------- | ----------------------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | Pobiera/skanuje adres URL — treść żądania walidowana przez `v1WebFetchSchema` |

**Uwierzytelnianie:** klucz API Bearer (`extractApiKey` + `isValidApiKey`). Zasady są wymuszane przez `enforceApiKeyPolicy`.

**Mechanizm rezerwowy uwzględniający limity (#8297):** gdy nie podano jawnego `provider`, pula
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) jest
przechodzona w stałej
kolejności priorytetów (fill-first) — skonfigurowany dostawca objęty limitem szybkości jest pomijany
zamiast natychmiastowego przerywania żądania, a możliwy do ponowienia błąd usługi nadrzędnej lub przekroczenie limitu
(zawsze HTTP 429; 402/403 dla bezpłatnych planów Firecrawl/Tavily/TinyFish z limitami —
nie dla Jina Reader i nigdy w przypadku zwykłego błędnego żądania 400) powoduje przejście do
następnego niewypróbowanego dostawcy z poświadczeniami podczas obsługi żądania. Gdy wszyscy dostawcy w
puli zostaną wyczerpani, punkt końcowy zwraca pojedynczą odpowiedź `429` (z nagłówkiem `Retry-After`)
zamiast wcześniejszej ogólnej odpowiedzi `400`. Gdy jawnie zażądano określonego `provider`,
**nie ma** niejawnego mechanizmu rezerwowego — jawnie wskazany dostawca objęty limitem szybkości lub zgłaszający błąd
zwraca własny błąd (`429`, jeśli jest objęty limitem szybkości, w przeciwnym razie status
usługi nadrzędnej).

## Strumieniowanie WebSocket

```bash
GET /v1/ws?handshake=1
```

Waliduje uzgadnianie aktualizacji połączenia WebSocket i zwraca przykładowe komunikaty protokołu komunikacyjnego (`request`, `cancel`). Rzeczywiste ramki WS są obsługiwane przez dołączony serwer WS poza tabelą tras Next.js.

**Uwierzytelnianie:** klucz API Bearer podczas uzgadniania połączenia.

### Responses API przez WebSocket (tylko codex)

```bash
# Ten sam host:port co HTTP API (domyślnie 20128); zaktualizuj połączenie:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (lub: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Pierwszą ramką MUSI być response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Serwer proxy Responses-API-over-WebSocket jest połączony **wyłącznie z `codex`** (backend
ChatGPT). Nasłuchuje na tym samym porcie co API/panel pod ścieżkami `/v1/responses`,
`/responses` i `/api/v1/responses`. Po otrzymaniu pierwszej ramki `response.create`
uwierzytelnia i przygotowuje połączenie za pośrednictwem wewnętrznego mostu `codex-responses-ws`, wybiera
połączenie OAuth codex i tuneluje ruch do `wss://chatgpt.com/backend-api/codex/responses`
przez transport `wreq-js`. **Modele inne niż codex są odrzucane** (`codex_ws_provider_required`).
Aby korzystać z routingu współdzielonych limitów, użyj `model: "qtSd/<group>/codex/<model>"`. Zaimplementowano w
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Uwierzytelnianie:** klucz API Bearer podczas uzgadniania połączenia. Dołączony serwer HTTP (`server-ws.mjs`)
musi być aktywnym punktem wejścia (domyślnie tak jest, gdy istnieje `app/server-ws.mjs`).

#### Identyfikator modelu: użyj podstawowego identyfikatora ChatGPT (bez prefiksu `codex/`)

OpenAI **Codex CLI** waliduje nazwę modelu po stronie klienta, gdy
`supports_websockets = true`, i **odrzuca identyfikatory z prefiksem dostawcy**, takie jak
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Wyślij **podstawowy** identyfikator (np. `gpt-5.5`). Most OmniRoute
obsługuje wyłącznie codex, dlatego przed tunelowaniem do usługi nadrzędnej ponownie rozpoznaje podstawowy identyfikator jako model codex
(`resolveCodexWsModelInfo`) — mimo że podstawowy identyfikator
`gpt-5.5` byłby w przeciwnym razie kierowany przez HTTP do innego dostawcy.

#### Konfigurowanie OpenAI Codex CLI

Skieruj Codex CLI do OmniRoute, dodając niestandardowego dostawcę z obsługą WebSocket
do `~/.codex/config.toml` (użyj osobnego `CODEX_HOME`, aby uniknąć modyfikowania
istniejącej konfiguracji):

```toml
model = "gpt-5.5"                 # bare id — NOT "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # no trailing slash; the WS URL is derived (use https/wss in production)
wire_api = "responses"                    # only supported value since Feb 2026
supports_websockets = true                # enables the Responses-over-WS transport
env_key = "OMNIROUTE_API_KEY"             # holds the OmniRoute API key (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # an OmniRoute API key (any key if REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI aktualizuje `base_url + /responses` do WebSocket, a OmniRoute tuneluje je
do wybranego połączenia OAuth codex. Zweryfikowano kompleksowo względem lokalnego
serwera: ChatGPT zwraca `codex.rate_limits` + `response.created` i strumieniuje
odpowiedź.

## Samoobsługowy podgląd użycia (`/api/usage/om-usage`)

Każdy klucz API może odczytać **własne** użycie i limity — bez uwierzytelniania administracyjnego. Jest to punkt końcowy,
którego klient (CLI, panel OmniCopilot) używa do wyświetlania właścicielowi klucza jego wydatków.

```bash
# Format tekstowy (historyczny kontrakt — zwykły tekst przeznaczony dla terminala)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Format ustrukturyzowany — używany przez interfejs użytkownika
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Klucz musi mieć włączoną opcję **`allowUsageCommand`** (domyślnie jest wyłączona — menedżer kluczy API
w panelu przełącza ją osobno dla każdego klucza). Bez niej punkt końcowy odpowiada kodem `403`.

`?format=json` zwraca strukturę z polem rozróżniającym, dzięki czemu wywołujący nigdy nie odczyta pola danych
z odpowiedzi odmownej. W przypadku powodzenia:

```jsonc
{
  "allowed": true,
  // obecne tylko wtedy, gdy dla klucza włączono indywidualne limity użycia (dzienne/tygodniowe w USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // migawka limitu wybranego dostawcy lub null, jeśli nic nie zostało jeszcze zapisane w pamięci podręcznej:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // migawki wszystkich połączeń, aby interfejs użytkownika mógł wyświetlić kilku dostawców obok siebie:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

W przypadku odmowy (`401` — nieprawidłowy klucz / `403` — brak uprawnień) ta sama trasa zwraca
`{ "allowed": false, "error": { "message": "…" } }` — obecne, ale puste pole `personal`/`provider`
(klucz jest dozwolony, ale nie uzyskano jeszcze żadnych danych) oznacza inny stan niż odmowa, a rozróżnienie to
jest możliwe tylko w formacie JSON.

**Uwierzytelnianie:** własny klucz API typu Bearer wywołującego, zweryfikowany za pomocą `isValidApiKey` — _nie_ jest to
interfejs administracyjny (`/api/keys/…`), który pozostaje chroniony przez `requireManagementAuth`.

### Surowe a skorygowane o próg odcięcia wartości procentowe limitów

Podczas korzystania z `/api/usage/om-usage` wywołujący powinni zwrócić uwagę na różnicę między
wartościami procentowymi prezentowanymi w **wyniku tekstowym** a ustrukturyzowanym **wynikiem JSON**:

| Aspekt                  | Format tekstowy (`/api/usage/om-usage` / `@@om-usage`)                                                | Format JSON (`?format=json`)                                                                   |
| :---------------------- | :---------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------- |
| **Pole wyjściowe**      | `NN% left` (np. `20% left`)                                                                           | `provider.quotas` / `providers[].quotas`                                                       |
| **Pomiar**              | **Dostępny limit skorygowany o próg odcięcia**: pozostała pojemność powyżej progu odcięcia            | **Surowy limit usługi nadrzędnej**: nieskorygowany pomiar dostawcy                             |
| **Skalowanie odcięcia** | Skalowane przez `effectiveRemainingPercent()`, tak aby chroniona rezerwa była widoczna jako `0% left` | Brak (surowe wartości migawki zgłoszone przez dostawcę)                                        |
| **Dane progowe**        | Uwzględnione w wyświetlanej wartości procentowej                                                      | Przechowywane w `quotaWindowThresholds` dla każdego połączenia (lub domyślne wartości serwera) |
| **Główny odbiorca**     | Interaktywne narzędzia CLI, monity terminala, operatorzy                                              | Integracje programistyczne, panele, analityka, narzędzia do śledzenia rozliczeń                |

#### Wzór korekty o próg odcięcia

OmniRoute obsługuje proaktywne progi odcięcia limitu, aby zapobiegać wyczerpaniu zasobów usługi nadrzędnej (konfigurowane za pomocą
`quotaWindowThresholds` połączenia, wartości domyślnych dostawcy lub globalnych ustawień odporności). Gdy próg odcięcia
(np. `cutoff = 25%`) jest aktywny dla okna limitu, mechanizm renderowania tekstu oblicza pozostały limit w następujący sposób:

- Jeśli `remaining <= cutoff`: zwraca `0%`.
- Jeśli `remaining > cutoff`: zwraca `((remaining - cutoff) / (100 - cutoff)) * 100`.

Sformatowany wynik tekstowy zaokrągla tę wartość do najbliższej liczby całkowitej (`Math.round(...)`).

#### Przykład poglądowy

Rozważmy okno dostawcy z **60% surowego użycia** (czyli **40% surowego pozostałego limitu**) i skonfigurowanym
progiem odcięcia wynoszącym **25% pozostałego limitu**:

| Reprezentacja                    | Obliczenie                                         | Pozostało |               Wynikowe użycie               |
| :------------------------------- | :------------------------------------------------- | :-------: | :-----------------------------------------: |
| **Surowy JSON (`?format=json`)** | Migawka usługi nadrzędnej (`quotas[window]`)       |  **40%**  |                   **60%**                   |
| **Format tekstowy (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20%**  | **80%** (przy obliczaniu `100 - remaining`) |

- **Dlaczego tekst pokazuje 20% pozostałego limitu:** Z 40% fizycznego limitu pozostałego na koncie 25% jest zarezerwowane przez
  zasady odcięcia. Wywołującemu pozostało jedynie 15% z 75% dostępnego zapasu, zanim router przestanie
  kierować ruch do tego połączenia. Skalowanie sprawia, że połączenie sygnalizuje wyczerpanie (`0% left`) dokładnie wtedy, gdy
  kierowanie ruchu zostanie zakończone.
- **Dlaczego JSON zachowuje surowe wartości:** Ładunek JSON zwraca dokładną migawkę dostawcy (`UsageSnapshot`),
  dzięki czemu zewnętrzne narzędzia mają dostęp do rzeczywistego wykorzystania usługi nadrzędnej oraz wartości
  `quotaWindowThresholds` na poziomie połączenia bez stratnego skalowania po stronie serwera.

#### Wskazówki dotyczące migracji klientów

Jeśli zewnętrzna integracja (na przykład wtyczka edytora lub rozszerzenie agenta) wcześniej pobierała dane z tekstowego
punktu końcowego (`NN% left`) i obliczała wykorzystany procent jako `100 - NN`, migracja do `?format=json` oznacza, że:

- Odczyt surowych wartości JSON będzie odzwierciedlać **rzeczywiste wykorzystanie u dostawcy nadrzędnego** (60% wykorzystania w powyższym przykładzie).
- Jeśli integracja ma zachować semantykę dostępnego limitu z tekstowego punktu końcowego, może obliczać
  efektywną pozostałą wartość po stronie klienta przy użyciu `quotaWindowThresholds` dla nadpisań na poziomie połączenia.

### Wpływ na opóźnienie

Trafienie w pamięci podręcznej semantycznej powoduje zwrócenie odpowiedzi z pamięci podręcznej **bez wywołania usługi nadrzędnej**, dlatego zgłaszana wartość `X-OmniRoute-Response-Latency` jest bliska zeru
(niezależnie od pierwotnego opóźnienia usługi nadrzędnej). Klienci wrażliwi na opóźnienia
(testy porównawcze, monitorowanie p50/p99) powinni sprawdzać nagłówek odpowiedzi
`X-OmniRoute-Cache-Latency`:

| Wartość     | Znaczenie                                                                                          |
| ----------- | -------------------------------------------------------------------------------------------------- |
| `synthetic` | Odpowiedź zwrócona z pamięci podręcznej; opóźnienie nie jest rzeczywistym czasem usługi nadrzędnej |
| _(brak)_    | Odpowiedź z rzeczywistego wywołania usługi nadrzędnej                                              |

### Pomijanie pamięci podręcznej dla poszczególnych kluczy

Klucze API mogą zrezygnować z odczytów semantycznej pamięci podręcznej za pomocą `cacheDefaultMode`:

| Wartość  | Zachowanie                                                                                        |
| -------- | ------------------------------------------------------------------------------------------------- |
| `legacy` | Normalne działanie pamięci podręcznej (domyślne)                                                  |
| `bypass` | Całkowite pominięcie wyszukiwania w pamięci podręcznej; każde żądanie trafia do usługi nadrzędnej |

Ustaw podczas tworzenia klucza (`POST /api/keys`) lub jego aktualizacji (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Pomijanie pamięci podręcznej dla poszczególnych żądań

Każde żądanie może pominąć pamięć podręczną niezależnie od ustawień klucza:

```
X-OmniRoute-No-Cache: true
```

W przypadku zsynchronizowanych/importowanych modeli `PUT /api/provider-models` akceptuje `provider`, `modelId` oraz
`maxOutputTokenOverride`: dodatnia liczba całkowita ustawia ręczny limit tokenów wyjściowych, a `null`

wartości w `modelOutputOverrides`, w tym modele bez wiersza modelu niestandardowego. Nadpisanie
korzysta z możliwości środowiska wykonawczego `max_output_tokens` i jest zachowywane po ponownej synchronizacji modelu. Strona dostawcy
zgodnego z OpenAI oferuje te same opcje edycji/usuwania i oznacza modele z jawną obsługą przetwarzania obrazu.

Niestandardowe węzły Chat Completions dostosowują jawne wyłączenia rozumowania do nadrzędnego backendu.
Pomyślny test połączenia automatycznie wybiera kontrolki szablonu czatu dla każdego dokładnego identyfikatora modelu,
którego wpis `/models` potwierdza rozpoznawaną wartość `owned_by`: `vllm`, `sglang` lub `llamacpp`.
Przezroczyste wrappery zgodne z OpenAI mogą zachowywać oryginalny wpis modelu wewnątrz zagnieżdżonego
obiektu `openai`; wykrywanie obejmuje do trzech takich warstw. Modele z brakującą, nieznaną lub
sprzeczną informacją o właścicielu zachowują standardowe działanie OpenAI. Wykrywanie ponownie wykorzystuje istniejące żądanie katalogu,
nie generuje tokenów uzupełnienia i jest unieważniane po zmianie punktu końcowego połączenia.

Aby wymusić określone działanie dla backendu, który nie udostępnia tych metadanych, użyj istniejącego interfejsu API
częściowej aktualizacji dostawcy:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Wyślij tę treść za pomocą `PUT /api/providers/<connection-id>`. W tym połączeniu jawnie ustawiony
poziom rozumowania `none` jest wysyłany jako `chat_template_kwargs.thinking=false` oraz
`chat_template_kwargs.enable_thinking=false`. Jawne natywne wartości szablonu pozostają nadrzędne,
chyba że reguła rozumowania po stronie serwera wymusza określony poziom. Ustawienie ma zastosowanie tylko wtedy, gdy niestandardowe
połączenie zgodne z OpenAI wysyła treść Chat Completions; żądania Responses i standardowi
dostawcy zachowują swój natywny format żądania. Ustaw `reasoningControl` na `openai`, aby wymusić standardowe przekazywanie
`reasoning_effort` OpenAI, albo pomiń tę właściwość/ustaw ją na `null`, aby użyć automatycznego wykrywania.

Żądania klasyfikatora trybu automatycznego Claude Code domyślnie wyłączają natywne rozumowanie, jeśli
nie zawierają jawnych ustawień rozumowania. Wykrywanie wykorzystuje znacznik systemowy klasyfikatora w żądaniach
w formacie Claude, a nie nazwy modeli ani limity uzupełnienia. Jawne ustawienia treści, obsługiwane nagłówki poziomu rozumowania/myślenia,
reguły routingu oraz ustalony poziom rozumowania modelu zachowują swój dotychczasowy priorytet. Oba etapy klasyfikatora
zachowują swoje prompty, limity uzupełnienia, sekwencje zatrzymania oraz rzeczywiste decyzje nadrzędnego systemu
dotyczące uprawnień; drugi etap nadal może generować żądane widoczne rozumowanie jako zwykły tekst.

### Wersja i kanał wydań

```bash
GET /api/system/version
```

Trasa zarządzania dostępna wyłącznie przez interfejs loopback (uwierzytelnianie administratora). Zwraca uruchomioną wersję, najnowszą
opublikowaną wersję oraz stan automatycznych aktualizacji. `releaseChannel` i `channels` to pola
dodane w linii 3.8.54; `channel` zachowuje swoje znaczenie — jest to tryb wdrożenia używany przez
mechanizm aktualizacji panelu (`npm`, `source` lub `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — kanał npm uruchomionej kompilacji: `nightly` dla wersji `-nightly.*`,
  `next` dla innych wersji przedpremierowych (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` dla stabilnej wersji
  starszej głównej linii niż `channels.latest`, a w pozostałych przypadkach `latest`. Obowiązują te same reguły co w
  `scripts/release/dist-tag.mjs`, który wybiera znacznik dist-tag npm podczas publikacji.
- `channels` — najnowsza opublikowana wersja dla każdego znacznika dist-tag, pobierana za pomocą `npm view omniroute dist-tags` (z rezerwowym
  użyciem HTTP rejestru), buforowana z takim samym 10-minutowym TTL jak `latest`. `latest` jest zawsze obecny
  (wartość jest zastępczo pobierana z pola `latest`, a następnie ustawiana na `"unavailable"`); `next`, `nightly` i `lts` pojawiają się
  tylko wtedy, gdy dany znacznik dist-tag istnieje. Żądanie z `Cache-Control: no-cache` odświeża oba wyszukiwania.

Model kanałów (`latest` = v3 do czasu wydania 4.0 GA, `next` = rc, `nightly` = kompilacje `develop`,
`lts` = poprawki v3 po wydaniu 4.0 GA) opisano w `docs/ops/RELEASE_STRATEGY.md`.

## Limity tokenów

Budżety **tokenów** dla poszczególnych kluczy API (niezależne od powyższego budżetu opartego na USD). Są egzekwowane bezpośrednio podczas obsługi żądania: gdy wykorzystanie w bieżącym oknie dla danego klucza osiągnie limit, żądania są odrzucane z kodem `429 Too Many Requests`. Limity mogą być ograniczone do konkretnego `model`, `provider` albo stosowane `global`nie w obrębie klucza; gdy do żądania pasuje kilka limitów, obowiązuje najbardziej restrykcyjny.

```bash
# Wyświetlenie limitów tokenów klucza (obejmuje bieżące wykorzystanie w oknie)
GET /api/usage/token-limits?apiKeyId=key-123

# Utworzenie lub zaktualizowanie limitu tokenów
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Usunięcie limitu tokenów według identyfikatora
DELETE /api/usage/token-limits?id=tl-abc
```

> **Uwagi dotyczące schematu** (`setTokenLimitSchema`): `apiKeyId` oraz `scopeType` (`model` | `provider` | `global`) są wymagane. `scopeValue` jest wymagane, chyba że `scopeType` ma wartość `global` (np. identyfikator modelu dla zakresu `model` lub identyfikator dostawcy dla zakresu `provider`). `tokenLimit` musi być dodatnią liczbą całkowitą (konwertowaną z ciągu znaków). Opcjonalne: `id` (pomiń, aby utworzyć; podaj, aby zaktualizować), `resetInterval` (`daily` | `weekly` | `monthly`, domyślnie `monthly`), `resetTime` (`HH:MM`), `enabled` (domyślnie `true`). Odpowiedzi `GET` uzupełniają każdy limit o `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` oraz `nextResetAt`. Jest to punkt końcowy klasy zarządzania (uwierzytelnianie jest egzekwowane centralnie przez potok autoryzacji).

## Przetwarzanie żądań

1. Klient wysyła żądanie do `/v1/*`
2. Procedura obsługi trasy wywołuje `handleChat`, `handleEmbedding`, `handleAudioTranscription` albo `handleImageGeneration`
3. Model jest rozpoznawany (bezpośredni dostawca/model albo alias/kombinacja)
4. Dane uwierzytelniające są wybierane z lokalnej bazy danych z uwzględnieniem filtrowania dostępności kont
5. W przypadku czatu: `handleChatCore` sprawdza pamięć podręczną semantyczną/sygnatur i rozpoznaje ustawienia kompresji kombinacji
6. Kompresja proaktywna jest wykonywana przed translacją na format dostawcy, jeśli jest włączona (`lite`, Caveman, RTK albo tryb warstwowy)
7. Moduł wykonawczy dostawcy wysyła żądanie do usługi nadrzędnej
8. Odpowiedź jest tłumaczona z powrotem na format klienta (czat) albo zwracana bez zmian (osadzenia/obrazy/audio)
9. Rejestrowane są wykorzystanie, dane analityczne kompresji oraz dzienniki żądań
10. W przypadku błędów stosowany jest mechanizm rezerwowy zgodnie z regułami kombinacji

Pełna dokumentacja architektury: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Odporność (rozszerzona)

OmniRoute udostępnia trzy niezależne mechanizmy obsługi tymczasowych awarii; poniższe punkty końcowe zarządzania pozwalają operatorom odczytywać i zastępować ich ustawienia:

| Zakres                       | Przechowywanie stanu                          | Odczyt                                    | Resetowanie / czyszczenie                                   |
| ---------------------------- | --------------------------------------------- | ----------------------------------------- | ----------------------------------------------------------- |
| Wyłącznik dostawcy           | `domain_circuit_breakers` + pamięć operacyjna | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                |
| Okres oczekiwania połączenia | `rateLimitedUntil` w połączeniach dostawców   | `/api/rate-limits`, `/api/providers/[id]` | (ponowne włączenie przy użyciu; wyczyść przez PUT dostawcy) |
| Blokada modelu               | Rejestr dostępności modeli w pamięci          | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                    |

`PATCH /api/resilience` przyjmuje nadpisania wyłączników dostawców w `providerBreaker.oauth` i `providerBreaker.apikey`. Każdy profil obsługuje `degradationThreshold`, `failureThreshold` i `resetTimeoutMs`; te same pola są dostępne w Panel → Ustawienia → Odporność.

```bash
# Wyczyść blokadę pojedynczego modelu
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Wyczyść wszystkie blokady
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Pełny opis koncepcyjny i domyślne ustawienia wyłączników: zobacz [`CLAUDE.md`](../../CLAUDE.md) → „Stan środowiska wykonawczego odporności” oraz [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Kolejka limitowania żądań i zabezpieczenie automatycznego włączania

- **Obsługiwana ścieżka zapisu**: `POST /api/rate-limits` z treścią `{"connectionId": "<id>", "enabled": true|false}` jest obsługiwanym punktem końcowym zarządzania służącym do przełączania ochrony przed limitami żądań dla połączenia. `PUT /api/providers/[id]` celowo nie modyfikuje ani nie przełącza `rateLimitProtection` (#11278).
- **Semantyka `enabled: false`**: Ustawienie `enabled: false` usuwa jawną ochronę połączenia, ale **nie** wyłącza aktywnego połączenia korzystającego z klucza API z globalnego zabezpieczenia automatycznego włączania (`autoEnableApiKeyProviders = true`). W `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) wartości `false` i `undefined` są równoważne; aktywne połączenia korzystające z klucza API bez jawnie włączonej ochrony pozostają chronione przez zabezpieczenie automatycznego włączania.
- **Wyłączenie globalne**: Aby używać połączeń korzystających z klucza API bez kolejek limitowania żądań, wyłącz zabezpieczenie globalnie za pomocą `RATE_LIMIT_AUTO_ENABLE=false` (zmienna środowiskowa) lub `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Ustawienia → Odporność / `PATCH /api/resilience`).

## Serwer MCP

OmniRoute zawiera wbudowany serwer Model Context Protocol z 3 transportami (stdio, SSE, streamable-http) i narzędziami o określonych zakresach. Poniższe endpointy panelu odczytują dane o stanie/audycie i pośredniczą w obsłudze transportów HTTP.

| Metoda | Ścieżka | Opis |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | Sygnał aktywności, transport, stan online, ostatnie wywołanie, najczęściej używane narzędzia, wskaźnik powodzenia z 24 godz. |
| GET | `/api/mcp/tools` | Lista narzędzi MCP z `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` |
| GET | `/api/mcp/sse` | Otwarcie strumienia SSE dla transportu SSE (zwraca `503`, jeśli MCP jest wyłączony lub transport jest niezgodny) |
| POST | `/api/mcp/sse` | Wysłanie ramki JSON-RPC przez transport SSE |
| GET | `/api/mcp/stream` | Otwarcie strony SSE transportu Streamable HTTP (komunikaty inicjowane przez serwer) |
| POST | `/api/mcp/stream` | Wysłanie ramki JSON-RPC przez transport Streamable HTTP |
| DELETE | `/api/mcp/stream` | Zakończenie sesji Streamable HTTP |
| GET | `/api/mcp/audit` | Zapytanie do dziennika audytu — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | Zagregowane statystyki audytu (sumy, wskaźnik powodzenia, średni czas trwania, najczęściej używane narzędzia) |

> Oba transporty HTTP są kontrolowane przez `settings.mcpEnabled` i `settings.mcpTransport` — niezgodność transportu zwraca `400`, a wyłączony stan MCP zwraca `503`.

## Serwer A2A

OmniRoute udostępnia punkt końcowy A2A (Agent-to-Agent) zgodny z JSON-RPC 2.0 oraz nakładkę REST przeznaczoną do inspekcji i użycia w panelu.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # opcjonalne, chyba że ustawiono OMNIROUTE_API_KEY
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Obsługiwane metody (wszystkie zależne od `settings.a2aEnabled`):

| Metoda           | Opis                                                                       |
| ---------------- | -------------------------------------------------------------------------- |
| `message/send`   | Synchroniczne wykonanie umiejętności; zwraca `{task, artifacts, metadata}` |
| `message/stream` | Strumieniowe wykonanie SSE tego samego zestawu umiejętności                |
| `tasks/get`      | Pobiera zadanie według `taskId`                                            |
| `tasks/cancel`   | Anuluje zadanie według `taskId`                                            |

Wbudowane umiejętności: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Karta agenta

```bash
GET /.well-known/agent.json
```

Zwraca publiczną kartę agenta A2A (nazwa, opis, możliwości, katalog umiejętności, schemat uwierzytelniania) — publicznie buforowaną przez 1 godz. Uwierzytelnianie nie jest wymagane.

### Pomocnicze punkty końcowe REST

| Metoda | Ścieżka                      | Opis                                                                                                                   |
| ------ | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/a2a/status`            | Status włączenia A2A + statystyki zadań + podsumowanie zbuforowanej karty agenta                                       |
| GET    | `/api/a2a/tasks`             | Wyświetla zadania — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (Niezaimplementowane jako pomocniczy punkt końcowy REST — utwórz za pomocą JSON-RPC `message/send`)                    |
| GET    | `/api/a2a/tasks/[id]`        | Pobiera jedno zadanie                                                                                                  |
| POST   | `/api/a2a/tasks/[id]/cancel` | Anuluje zadanie                                                                                                        |

**Uwierzytelnianie:** pomocnicze punkty końcowe REST działają bez uwierzytelniania administracyjnego (są dostępne do odczytu przez panel); trasa JSON-RPC `/a2a` używa tokenu Bearer `OMNIROUTE_API_KEY`, jeśli został skonfigurowany.

## Uwierzytelnianie

Informacje o czterech rodzinach poświadczeń (sesja panelu, lokalny token CLI, token
dostępu `oma_live_…`, klucz API z uprawnieniami do zarządzania) oraz o tym, czym
różnią się one od kluczy inferencji, zawiera [Uwierzytelnianie zarządzania](../guides/MANAGEMENT-AUTH.md).

- Trasy panelu (`/dashboard/*`) używają pliku cookie `auth_token`
- Logowanie korzysta z zapisanego skrótu hasła; wartością rezerwową jest `INITIAL_PASSWORD`
- Ustawienie `requireLogin` można przełączać za pomocą `/api/settings/require-login`
- Trasy `/v1/*` mogą opcjonalnie wymagać klucza API typu Bearer, gdy `REQUIRE_API_KEY=true`
- Określenia „token zarządzania” / „klucz API z uprawnieniami do zarządzania” w tym dokumencie oznaczają jedną z rodzin opisanych w tym przewodniku — nie dodatkowy, niezdefiniowany typ klucza tajnego

> **Zmiana niekompatybilna wstecznie (v3.8.0)** — `/api/v1/agents/tasks/*` oraz punkty końcowe zarządzania okresem odnowienia wymagają teraz **uwierzytelniania zarządzania** (pliku cookie `auth_token` panelu lub klucza API z uprawnieniami do zarządzania). Klienci, którzy wcześniej wywoływali te trasy bez uwierzytelniania, otrzymają odpowiedź `401 Unauthorized`. Zobacz commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
