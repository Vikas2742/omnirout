## Dokončování chatu

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Vlastní hlavičky

| Hlavička                 | Směr      | Popis                                                                                                                                                                                                                           |
| ------------------------ | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Požadavek | Nastavením na `true` obejdete mezipaměť                                                                                                                                                                                         |
| `x-omniroute-no-memory`  | Požadavek | Nastavením na `true` přeskočíte pro tento požadavek vkládání paměti a dovedností (obdobně jako bez mezipaměti; zamezí režii tokenů a nákladů na jednotlivá volání)                                                              |
| `X-OmniRoute-Progress`   | Požadavek | Nastavením na `true` povolíte události průběhu                                                                                                                                                                                  |
| `X-Session-Id`           | Požadavek | Klíč trvalé relace pro externí spřažení relací                                                                                                                                                                                  |
| `x_session_id`           | Požadavek | Je přijímána také varianta s podtržítky (přímé HTTP)                                                                                                                                                                            |
| `X-OmniRoute-Session-Id` | Požadavek | Značka relace/konverzace poskytnutá volajícím (předává se také do paměti). Je-li přítomna, uloží se beze změny do `call_logs.session_tag` pro přiřazování nákladů jednotlivým relacím (#8249) — pokud chybí, nikdy se nevytváří |
| `Idempotency-Key`        | Požadavek | Klíč pro odstranění duplicit (okno 5 s)                                                                                                                                                                                         |
| `X-Request-Id`           | Požadavek | Alternativní klíč pro odstranění duplicit                                                                                                                                                                                       |
| `x-omniroute-connection` | Požadavek | Připne požadavek na jediný model k jednomu připojení poskytovatele (účtu) podle jeho ID — viz [Připnutí účtu pro jednotlivé požadavky](#account-pinning-per-request)                                                            |
| `X-OmniRoute-Cache`      | Odpověď   | `HIT` nebo `MISS` (bez streamování)                                                                                                                                                                                             |
| `X-OmniRoute-Idempotent` | Odpověď   | `true`, pokud byly odstraněny duplicity                                                                                                                                                                                         |
| `X-OmniRoute-Progress`   | Odpověď   | `enabled`, pokud je zapnuto sledování průběhu                                                                                                                                                                                   |
| `X-OmniRoute-Session-Id` | Odpověď   | Platné ID relace používané službou OmniRoute                                                                                                                                                                                    |
| `X-OmniRoute-Request-Id` | Odpověď   | Korelační ID požadavku (je-li známo)                                                                                                                                                                                            |
| `X-OmniRoute-Version`    | Odpověď   | Verze sestavení OmniRoute (vždy přítomna)                                                                                                                                                                                       |
| `X-OmniRoute-Cost-Saved` | Odpověď   | Částka v USD ušetřená díky mezipaměti při zásahu (pouze zásahy do mezipaměti)                                                                                                                                                   |
| `X-OmniRoute-Decision`   | Odpověď   | Trasování směrování: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` je strategie kombinace nebo `single` pro požadavek bez kombinace) — vždy přítomno v odpovědích po dokončení                                  |

#### Pevné přiřazení účtu pro jednotlivé požadavky

Pokud má poskytovatel několik připojení (účtů nebo klíčů), OmniRoute obvykle jedno z nich
vybere pomocí své strategie výběru účtu. Požadavek však může pevně určit konkrétní připojení
pomocí hlavičky `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Kde najít ID.** Otevřete stránku poskytovatele v řídicím panelu
  (**Řídicí panel → Poskytovatelé → <poskytovatel>**) a klikněte na čip ID `xxxxxxxx…` v řádku
  připojení — tím se zkopíruje úplné ID připojení.
- **Které požadavky jej respektují.** Požadavky s jedním modelem (`provider/model`) na
  `/v1/chat/completions`, `/v1/messages` a `/v1/responses`. Kombinace tuto hlavičku ignorují:
  účet pro každý krok kombinace pevně určete prostřednictvím vlastního připojení daného kroku.
- **Pevné přiřazení je striktní, nejde jen o preferenci.** Pevně určené připojení se používá výhradně.
  Selhání v rámci požadavku zaznamená dobu pozastavení účtu, ale **nepřepne** na jiný účet
  stejného poskytovatele.
- **Doba pozastavení a kvóta pevné přiřazení uvolní.** Zatímco je pevně určené připojení
  pozastavené, má vyčerpanou kvótu nebo je blokováno zásadami kvót, následující požadavky
  přejdou na ostatní připojení poskytovatele, stejně jako provoz bez pevného přiřazení.
- **Neznámá nebo zakázaná ID způsobí selhání.** ID, které není v aktivním fondu poskytovatele
  (bylo odstraněno, deaktivováno nebo patří jinému poskytovateli), nezanechá žádný způsobilý
  účet, takže požadavek selže namísto toho, aby byl bez upozornění směrován jinam.

Claude Code odesílá vlastní hlavičky prostřednictvím `ANTHROPIC_CUSTOM_HEADERS`. Vložte tuto
proměnnou do bloku `env` v souboru `~/.claude/settings.json`, případně do projektového souboru
`.claude/settings.json`, chcete-li pro každý projekt pevně určit jiný účet:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Zdroj: `src/sse/handlers/chat.ts` (čtení hlavičky), `src/sse/services/auth.ts` a
`src/sse/services/sessionAffinityPin.ts` (uvolnění pevného přiřazení a kontrola nepřítomnosti ve fondu).

> **Hlavičky telemetrie nákladů:** úspěšné odpovědi bez streamování obsahují také sadu telemetrie nákladů `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, pevně 10 desetinných míst; `0.0000000000` pro bezplatné položky nebo položky bez stanovené ceny), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` a `X-OmniRoute-Fallback-Attempts` (pouze když > 0), společně s `X-OmniRoute-Request-Id` a `X-OmniRoute-Version`. Tyto hlavičky generují dokončování chatu, `/v1/responses`, `/v1/messages` **i koncové body pro média** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` a `/v1/moderations` (náklady jsou vždy `0`). Náklady na média se počítají podle modality (za obrázek, za sekundu, za znak nebo za jednotku vyhledávání), pokud jsou dostupné informace o cenách; jinak jsou `0` (režim fail-open).

> **Sémantika nákladů při zásahu do mezipaměti:** při ZÁSAHU do sémantické mezipaměti (`X-OmniRoute-Cache-Hit: true`) se neprovádí žádné volání nadřazené služby, takže `X-OmniRoute-Response-Cost` je `0.0000000000` (**přírůstkové** náklady na obsloužení zásahu). Původní, respektive předpokládané náklady se vykazují samostatně v `X-OmniRoute-Cost-Saved`. Systémy zpracovávající fakturaci by měly sčítat `X-OmniRoute-Response-Cost` (zásahy nic nestojí); analýzy mezipaměti mohou agregovat `X-OmniRoute-Cost-Saved`.

## Výhradní pronájmy spravovaných relací

Výhradní pronájem spravovaných relací je volitelná, na klientovi nezávislá smlouva směrování: jeden aktivní vlastník drží jedno způsobilé připojení OmniRoute. Nepronajímá model, nevyžaduje OAuth, neidentifikuje konkrétního klienta ani nevyžaduje konkrétního poskytovatele.

Ověřovaný klíč API musí mít rozsah `lease:exclusive` a explicitní neprázdný seznam `allowedConnections`. Hranice databázové mutace vynucuje obě pole společně při vytvoření klíče i při částečných aktualizacích.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Úspěšné odpovědi na získání, obnovení a uvolnění zpřístupňují časová razítka, `state` a přesnou kladnou hodnotu `generation`, nikdy však vybrané připojení ani přihlašovací údaje. Při obnovení a uvolnění se generace předává v těle JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Vlastník aktivního pronájmu může explicitně požádat o zobrazovaná metadata svého aktuálního přiřazení, která neohrožují soukromí:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Tato volitelná stavová akce je v rámci jedné databázové transakce chráněna neprůhledným vlastníkem, ověřeným spravovaným klíčem API a přesnou aktivní generací. `displayName` je pouze oříznutý nakonfigurovaný název připojení; pokud žádný bezpečný nakonfigurovaný název neexistuje, má hodnotu `null`. OmniRoute jej nikdy nenahrazuje e-mailovou adresou ani vygenerovanou identitou účtu. Hodnota poskytovatele je necitlivý zobrazovaný popisek a nikdy nejde o vygenerovaný identifikátor kompatibilního poskytovatele. Přihlašovací údaje, tokeny, soubory cookie, nezpracované identifikátory připojení nebo klíčů API, otisky vlastníků, tajné údaje oddělující generace a interní směrovací data jsou vyloučeny.

Vyhledávání s nesprávným klíčem, nesprávným vlastníkem, zastaralou generací, chybějícím, vypršeným, uvolněným nebo zneplatněným pronájmem vracejí stejnou chybu `409 LEASE_FENCE_STALE` bez metadat připojení. Klient, který obdržel odpověď o čekání na kapacitu, nemá žádné aktivní přiřazení, které by mohl zkontrolovat. Když směrování převede aktivní pronájem, zůstává platná stejná generace a stav atomicky vrátí nové přiřazení, nikdy ne staré. Stávající klienti zůstávají beze změny, protože odpovědi na získání, obnovení, uvolnění a čekání si zachovávají své předchozí struktury.

Tato smlouva serveru nemění standardní `/status` OpenAI Codex. Standardní Codex v současnosti hlásí svého poskytovatele modelu a vestavěný stav ověřování/účtu, ale nevykresluje libovolná vlastní metadata účtu poskytovatele; budoucí integrace klienta musí tuto akci zavolat a rozhodnout, jak se má `connection.displayName` zobrazit.

Každý požadavek na spravovanou inferenci pak poskytuje obě řídicí hlavičky:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Přesný vlastník, generace, aktivní připojení a ověřený klíč API jsou ověřeny bezprostředně před každým podporovaným pokusem o přístup k nadřazené službě. Opětovné použití vlastníka a generace s jiným klíčem selže, i když daný klíč povoluje stejné připojení. Nezpracované hodnoty vlastníků se neukládají, nezaznamenávají do protokolů, neuchovávají ve snímku požadavku ani nepředávají nadřazené službě.

Dočasné soupeření o prostředky vrací HTTP `429` s `Retry-After` a:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Tato odpověď znamená pouze to, že běžná množina způsobilých připojení nebyla prázdná a každý volný kandidát byl držen cizím aktivním pronájmem. Nepodporované modely/poskytovatelé, nesoulad se zásadami, čekací doba, kvóta, stav funkčnosti a další běžná selhání způsobilosti si zachovávají své stávající odpovědi OmniRoute.

### `x-omniroute-compression`

Přepsání plánu komprese pro jednotlivý požadavek. Má nejvyšší prioritu — přebíjí přepsání směrovací kombinací, aktivní profil, automatický aktivační mechanismus i výchozí nastavení panelu. Hodnoty:

| Hodnota       | Účinek                                                                                                     |
| ------------- | ---------------------------------------------------------------------------------------------------------- |
| `off`         | Pro tento požadavek se nepoužije žádná komprese.                                                           |
| `default`     | Výchozí profil odvozený z panelu (ignoruje aktivní profil). Ztrátové moduly zůstávají vypnuté.             |
| `safe`        | Pouze deduplikace a slučování bílých znaků.                                                                |
| `allow-lossy` | Zachová pro tento požadavek plán operátora, včetně souhrnů a přepisů stylu.                                |
| `engine:<id>` | Jeden modul, je-li povolen, např. `engine:rtk`. Volitelné povolení daného modulu pro jednotlivý požadavek. |
| `<combo>`     | Pojmenovaná kombinace; nejprve se porovnává název (bez rozlišení velikosti písmen), poté identifikátor.    |

Poznámky:

- Neznámé hodnoty jsou ignorovány (požadavek není nikdy odmítnut); vyhodnocení pokračuje podle běžného pořadí priorit operátora.
- Pokud má více kombinací stejný název, předejte **id** kombinace, aby byl výsledek deterministický.
- Kombinaci s názvem `off` nebo `default` nelze vybrat podle názvu (tato klíčová slova se interpretují přednostně); na takovou kombinaci odkazujte pomocí jejího identifikátoru.
- Hlavní přepínač komprese je nepřekročitelná podmínka: pokud je komprese globálně zakázána, tato hlavička ji nemůže povolit.

Použitý plán se vrací v hlavičce odpovědi:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

kde `<source>` je jedna z hodnot `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` nebo `off`.

## Embeddingy

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Dostupní poskytovatelé: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Identifikátory katalogu mají tvar `provider/model` (příklad: `jina-ai/jina-embeddings-v5-omni-small`). Samostatné identifikátory modelů Jina, které se nacházejí v registru (například `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`), se také správně přeloží. Operace embed/rerank/classify/segment od Jina používají nejprve přihlašovací údaje `jina-ai` z řídicího panelu; `JINA_AI_API_KEY` slouží jako záložní možnost pouze v případě, že v řídicím panelu neexistuje žádný klíč. Karta `jina-reader` je určena pouze pro Reader / `r.jina.ai` (`POST /v1/web/fetch`) a nikdy neposkytuje embeddingy ani rerank.

Modely v registru, které deklarují multimodální podporu, přijímají také až 32 strukturovaných položek
nezávislých na poskytovateli. Typy multimediálních položek jsou `text`, `image`, `audio`, `video` a `document`. Jejich
multimediální `source` je buď `{"type":"url","url":"https://..."}`, nebo
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
a alias rodiny `jina-ai/jina-embeddings-v5-omni` → omni-small) přijímá také nativní dokumenty
EmbeddingsV5Request od Jina a **předává je beze změny** na `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Nativní hodnoty `{ image | audio | video | pdf }` mohou být veřejná adresa HTTPS URL, URI `data:` nebo nezpracovaný
base64. OmniRoute tyto objekty nepřevádí na řetězce ani nenačítá nativní adresy URL obrázků — veřejná
média načítá samotná služba Jina. Dodatečná pole Jina (`task`, `normalized`, `truncate`, `embedding_type`) se
předávají dál. SKU Jina určené pouze pro text nadále odmítají netextové dokumenty.

Bezpečnostní a přenosová omezení:

- Vzdálené adresy URL médií musí být veřejné a používat HTTPS. Kanonické položky `{type,source:url}` se načítají
  na straně serveru (opakované ověřování přesměrování, časový limit, omezení velikosti, veřejný DNS, připnutí
  spojení) a před voláním poskytovatele se vloží přímo do požadavku. Nativní položky Jina `{image:"https://..."}`
  se po stejné kontrole veřejného HTTPS předávají beze změny; adresu URL načte Jina.
- Média vložená jako base64 jsou omezena na 8 MiB dekódovaných dat na položku a 16 MiB dekódovaných dat v rámci požadavku.

Převod pro poskytovatele (kanonické položky se nikdy nepředávají beze změny):

- Multimodální modely Jina: každá položka nejvyšší úrovně se převede na jeden objekt s klíčem modality
  (`text` / `image` / `audio` / `video` / `pdf`), přičemž pro vložená média používá URI dat; jeden vektor pro
  každou položku nejvyšší úrovně.
- Rodina Gemini Embedding 2: jedno pole nejvyšší úrovně se převede na jediný nativní
  požadavek `models/{model}:embedContent` s `content.parts` (`text` nebo `inline_data`).
- llama.cpp (`llama-cpp/<model>`, libovolný model načtený místním serverem): kanonické položky `text`
  se převedou na prosté řetězce a položky `image` / `audio` / `video` se každá převede na jeden
  objekt `{"content": [part]}` s použitím částí obsahu chatu serveru llama (`image_url`,
  `input_audio` s formátem `wav` / `mp3` / `flac`, `input_video`) a vložených dat; jeden vektor
  pro každou položku nejvyšší úrovně. Server musí být spuštěn s `--embedding --mmproj …`; bez projektoru
  média sám odmítne. Typ `document` není podporován.
- Neznámé/dynamické modely bez explicitních metadat modalit odmítnou strukturovaný vstup s HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Nepodporované kombinace modelu a modality vracejí HTTP 400 namísto převodu položky. Rozšiřující pole mimo vstup
ve starších požadavcích s řetězci/tokeny se nadále předávají beze změny.

```bash
# Vypsat všechny modely embeddingů
GET /v1/embeddings
```

## Generování obrázků

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Mezi dostupné poskytovatele patří OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (lokální), ComfyUI (lokální).

Parametr `n` vrací `n` obrázků v poli `data[]`. U poskytovatelů, jejichž upstreamové API vrací jeden obrázek na jedno volání
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), se provede `n` samostatných upstreamových volání, přičemž souběžně probíhají nejvýše 4. Pevně zadaná
hodnota `seed` se navyšuje podle indexu volání (`seed`, `seed + 1`, …), takže se obrázky liší, ale zůstávají
reprodukovatelné. Hodnota `n` je omezena na 10. Pokud některé volání selže, selže celý požadavek. Seznam
formátů používajících rozvětvená volání je uveden v `SINGLE_IMAGE_FANOUT_FORMATS` v souboru
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux opakovaně používá stávající připojení s API klíčem a přijímá prefixy `zenmux/` nebo `zm/`:

- `zenmux/openai/gpt-image-2` používá OpenAI Images API služby ZenMux. Mezi možnosti patří `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` a `response_format`.
- Ostatní vydavatelé, například `zm/meta/muse-image-1.0`, používají endpoint Vertex AI `:predict`
  služby ZenMux. Parametr `n` se mapuje na `sampleCount`, `aspect_ratio` na `aspectRatio` a `image_size`
  (`1K`, `2K`, `4K`) na `sampleImageSize`. Hodnota `size` v pixelech určuje pouze poměr stran,
  nikoli zaručené rozměry v pixelech. Podporované poměry stran, rozlišení a počty se liší podle modelu.
- `zm/inclusionai/ming-image-0.1-design` volí vlastní rozměry. Vynechejte `size`,
  `aspect_ratio` a `image_size`; explicitní hodnoty způsobí vrácení HTTP 400. Pomocí `output_format`
  lze vyžádat PNG, JPEG a WebP.

Tato integrace podporuje generování obrázků z textu, nikoli úpravy podle referenčního obrázku. Výstup z Vertexu
je normalizován do `data[].b64_json`; při použití `response_format: "url"` se vrátí upstreamová
HTTPS URL nebo datová URL ve formátu base64, pokud jsou k dispozici pouze obrazová data. Prázdné nebo filtrované výstupy
vrátí chybu namísto prázdné úspěšné odpovědi. Přístup k modelům závisí na účtu ZenMux.
Viz [Vertex API služby ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) a
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Vypsat všechny obrazové modely
GET /v1/images/generations
```

## OCR dokumentů

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

Parametr `model` vybírá poskytovatele OCR pomocí prefixu `provider/model`; samotné ID modelu (např.
`mistral-ocr-latest`) se převede na jeho registrovaného poskytovatele a při vynechání parametru `model` se ve výchozím nastavení
použije Mistral (`mistral-ocr-latest`). Registrovaní poskytovatelé (`open-sse/config/ocrRegistry.ts`):

| ID poskytovatele              | ID modelu            | Hodnota `model`                                                  | Poznámky                                                                                                                        |
| ----------------------------- | -------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (nebo samotné `mistral-ocr-latest`) | Synchronní — odpověď se vrací přímo z jediného upstreamového volání.                                                            |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                      | Asynchronní upstream (`analyze` + dotazování) — viz níže.                                                                       |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                          | Synchronní, prostřednictvím partnerského endpointu Vertex AI `openapi/chat/completions` — informace o ověřování a URL viz níže. |

Všichni tři poskytovatelé odpovídají stejným tělem ve formátu Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Průběh dotazování Azure Document Intelligence

API `analyze` služby Azure Document Intelligence je asynchronní: počáteční požadavek vrátí namísto těla
hlavičku `Operation-Location` a na výsledek je nutné se opakovaně dotazovat. Obslužná rutina
(`open-sse/handlers/ocr.ts`) se na tuto URL dotazuje každou sekundu, nejvýše však 30krát. Při odpovědi dotazu, která není `ok`,
nebo při stavu `"failed"` okamžitě skončí s chybou (v dotazování nepokračuje) a vrátí `504`, pokud operace
stále probíhá i po vyčerpání povoleného počtu pokusů. Konečná odpověď Azure se před vrácením
volajícímu normalizuje do stejné struktury `pages`/`markdown`, jakou používá Mistral, takže klientský kód
nemusí obsahovat zvláštní zpracování pro jednotlivé poskytovatele.

### Ověřování a rozpoznání endpointu Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` opakovaně používá stejné ověřování Vertex AI, které OmniRoute již podporuje pro
chatový a obrazový provoz (`open-sse/executors/vertex.ts`): API klíčem připojení je buď
přihlašovací údaj Service Account ve formátu JSON (vyměněný za krátkodobý přístupový token OAuth prostřednictvím
toku JWT-bearer), nebo již vystavený přístupový token OAuth použitý beze změny. Upstreamovou URL endpointu tvoří obecný
partnerský endpoint Vertexu `openapi/chat/completions`, sestavený z projektu a oblasti daného připojení
— explicitně zadané `providerSpecificData.project`/`providerSpecificData.region` mají vždy přednost;
jinak se projekt odvodí z hodnoty `project_id` v JSON Service Account a jako výchozí oblast
se použije `us-central1`. K oběma rozpoznáním dochází v `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) a před předáním do `handleOcr` je využívá
`src/app/api/v1/ocr/route.ts`.

## Výpis modelů

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ Vrátí všechny chatovací, embeddingové a obrazové modely + kombinace ve formátu OpenAI
```

### Prefixy ID modelů (`?prefix=`)

Většina modelů je uváděna pod **prefixem poskytovatele**. To, který prefix získáte, řídí
příznak funkce `MODELS_CATALOG_PREFIX_MODE` a lze jej přepsat **pro každý požadavek** pomocí
parametru dotazu — což je užitečné pro klienta, který chce čistý seznam bez změny nastavení
pro celý server a všechny ostatní:

```bash
GET /v1/models?prefix=alias        # jedno ID pro každý model — krátký aliasový prefix
GET /v1/models?prefix=dual         # obě podoby (výchozí nastavení serveru)
GET /v1/models?prefix=canonical    # pouze úplný prefix ID poskytovatele
```

| Režim       | Vrací                                                   | Poznámky                                                                                                                                                                                          |
| ----------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **a** `claude/claude-sonnet-4-6` | **Výchozí.** Obě ID směrují na stejný model; zachováno proto, aby nadále fungovaly konfigurace klientů, které napevno používají jednu z těchto podob. Přibližně zdvojnásobuje katalog.            |
| `alias`     | `cc/claude-sonnet-4-6`                                  | Jedna položka pro každý model. Poskytovatelé bez samostatného aliasu svou položku stále vracejí, takže se nic neztratí.                                                                           |
| `canonical` | `claude/claude-sonnet-4-6`                              | Jedna položka pro každý model pod úplným prefixem ID poskytovatele. Poskytovatelé bez samostatného aliasu (např. `antigravity/…`, `agy/…`) zde také vracejí své jediné ID, takže se nic neztratí. |

Zrcadlenou položku v režimu `dual` lze rozpoznat také bez parametru dotazu: obsahuje pole `parent`
odkazující na primární ID.

Klienti zobrazující výběr modelu by měli požadovat `?prefix=alias` — takto postupuje
[rozšíření OmniCopilot pro VS Code](../guides/VSCODE-COPILOT.md).

### Filtry pro vyhledávání (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` přijímá volitelné filtry pro vyhledávání. Bez kteréhokoli z nich zůstává
odpověď nezměněná. Zužují katalog, který volající již vidí (oprávnění API klíče se uplatní jako
první), a spouštějí se před stránkováním ve stylu OpenAI pomocí `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # každá uvedená schopnost musí být nastavena na true
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # katalogový `type`; řádky bez něj jsou `chat`
GET /v1/models?q=sonnet&limit=10                           # porovnání ID nebo názvu bez rozlišení velkých a malých písmen
```

| Parametr      | Hodnoty                                                                                             |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | nezáporné celé číslo porovnávané s `context_length`                                                 |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 znaků                                                                                         |

Neznámá hodnota nebo `min_context`, který není nezáporným celým číslem (například `1.5`),
vrátí HTTP `400` a zpráva uvede platné hodnoty. Implementace:
`src/app/api/v1/models/catalogFilters.ts`.

### Užší výběr modelů (`POST /v1/models/query`)

`POST /v1/models/query` vrací krátký, deterministický seznam ze stejného katalogu se stejným
ověřováním a viditelností pro jednotlivé klíče jako `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Každé pole je volitelné. `capabilities` a `exclude` přijímají pole nebo řetězec oddělený čárkami;
`max_output` se porovnává s `max_output_tokens`. Výsledky jsou seřazeny podle `owned_by` a poté
podle `id`. Výchozí hodnota `limit` je `20` a hodnoty vyšší než `100` jsou omezeny na `100`.
Neplatný JSON, neznámé pole nebo neplatná hodnota vrátí HTTP `400`.

### Jednotlivě skryté chatovací modely

Model označený na stránce svého poskytovatele jako **Skrytý** je z katalogu vyloučen a při
výslovném požadavku odmítnut pomocí HTTP `404` / `model_not_found`. Kontrola používá přeloženého
poskytovatele a model, včetně aliasů poskytovatele, prefixů uzlů kompatibilních poskytovatelů
a výchozích hodnot připojení. Kombinace skryté cíle přeskočí a může použít viditelný příbuzný
model; pokud nezůstane žádný spustitelný cíl, vrátí stejný kód chyby. Zrušení skrytí se projeví
při následujícím požadavku. Přepsání viditelnosti určená pouze pro obrázky neskryjí chatovací
model se stejným ID.

Toto nastavení jednotlivého modelu je oddělené od
[seznamů povolených a zakázaných modelů](../routing/MODEL_EXPOSURE_LIST.md), které filtrují
zveřejnění v katalogu a kandidáty pro automatické směrování, zatímco zachovávají explicitní
odesílání. Oprávnění modelů pro API klíče se nadále uplatňují nezávisle. Výchozím režimem
prefixu katalogu zůstává `dual`.

### Varianty modelů bez přemýšlení

Pro modely Claude podporující přemýšlení uvádí `/v1/models` také variantu **bez přemýšlení**, jejíž ID má prefix `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Výběr tohoto ID (např. v konfiguraci Claude Code, která vždy připojuje blok `thinking`) se přeloží zpět na skutečný `<provider>/<model>` s potlačeným uvažováním — pomocí `thinking:{type:"disabled"}` na cestě `/v1/messages` nebo vynecháním polí `reasoning`/`reasoning_effort` na cestě `/v1/chat/completions`. Varianta je uvedena pouze pro modely z rodiny Claude, které podporují uvažování **a zároveň** respektují hodnotu `disabled` (takže jsou například vyloučeny modely pouze s adaptivním režimem, které hodnotu `disabled` odmítají). Operátoři mohou tuto variantu pro jednotlivé modely vynutit nebo zakázat pomocí `ModelSpec.noThinkingAlias`.

## Generování zvuku pomocí ElevenLabs

Nakonfigurujte v OmniRoute připojení poskytovatele `elevenlabs` pomocí svého API klíče ElevenLabs.
Klienti se ověřují pomocí svého klíče **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
brána předává uložený klíč poskytovatele jako `xi-api-key`. Nikdy neposílejte klíč ElevenLabs
jako bearer token brány.

| Metoda | Cesta                       | Odpověď                                 | Kategorie koncového bodu API klíče |
| ------ | --------------------------- | --------------------------------------- | ---------------------------------- |
| POST   | `/v1/sound-generation`      | Nativní zvuková data v bajtech          | `elevenlabs`                       |
| POST   | `/v1/music`                 | Nativní zvuková data v bajtech          | `music`                            |
| POST   | `/v1/music/stream`          | Streamovaná zvuková data v bajtech      | `music`                            |
| POST   | `/v1/music/detailed`        | Nativní multipart zvuk a plán kompozice | `music`                            |
| POST   | `/v1/music/detailed/stream` | Nativní metadata SSE a zvukové bloky    | `music`                            |
| POST   | `/v1/music/plan`            | Plán kompozice ve formátu JSON          | `music`                            |

Tyto koncové body doplňují stávající trasy `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` a `/v1/speech-to-text`. Nativní pole JSON
a parametry dotazu, jako jsou `output_format` a `enable_logging`, zůstávají zachovány.
Odpovědi `/v1/music/detailed` si zachovávají své multipart hranice; zpracujte je jako multipart.
`/v1/music/detailed/stream` vrací `text/event-stream` s metadaty kompozice a
zvukovými bloky kódovanými v base64 v událostech SSE. Všech šest tras podporuje předběžné požadavky CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Krátký zvukový efekt. Délka: 0,5 až 30 sekund.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Délka hudby se vyjadřuje v milisekundách: 3000 až 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Pro průběžné doručování zvuku použijte `/v1/music/stream` se stejným tělem JSON. Kompozice
přijímá právě jednu z možností `prompt` nebo `composition_plan`; `/v1/music/plan` vyžaduje `prompt`
a volitelně přijímá `source_composition_plan`. Nativní schémata zachovávají další pole
poskytovatele, takže se verze plánů kompozice a možnosti jemného doladění předají službě ElevenLabs.

Sjednocený koncový bod `/v1/music/generations` přijímá také `elevenlabs/music_v1`,
`elevenlabs/music_v2` a `elevenlabs/music_v2_5`. Při aktivním připojení ElevenLabs
jsou tyto modely dostupné v katalogu hudby. Tento koncový bod vrací
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Jeho pole `duration` je uvedeno
v sekundách a mapuje se na `music_length_ms`; explicitní `music_length_ms` má přednost.
`instrumental` se mapuje na `force_instrumental`, přičemž nativní pole má přednost.
Pro streamování používejte nativní streamovací koncové body a pro požadavky řízené pouze
plánem kompozice použijte nativní koncový bod pro kompozici.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Před voláním nadřazené služby se uplatňují omezení koncového bodu, modelu, rozpočtu a připojení.
Nativní trasy vracejí stavové kódy a chybová těla nadřazené služby beze změny, včetně `402` při
omezení tarifu a `429` při překročení kvóty. Hlavičky `character-cost`, `song-id`, `request-id` a `retry-after`
zůstávají zachovány, pokud jsou přítomny. Bezplatný zůstatek kreditu nezaručuje přístup ke každému
hudebnímu modelu, výstupnímu formátu ani funkci API: o oprávnění pro každý požadavek rozhoduje ElevenLabs.
Sjednocený koncový bod zachovává stavové kódy chyb v normalizované chybové obálce OmniRoute.

Kontrakty nadřazené služby: [zvukové efekty](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[kompozice hudby](https://elevenlabs.io/docs/api-reference/music/compose) a
[podrobnosti streamování hudby](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

```bash
# Přeřazení (poskytovatel z cloudového registru nebo uzel poskytovatele kompatibilního s OpenAI ve tvaru "<prefix>/<model>")
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Klasifikace Jina (přihlašovací údaje Foundation API)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Segmentátor Jina
POST /v1/segment     { "content": "...", "return_chunks": true }

# Vyhledávání Jina (s.jina.ai; aliasy poskytovatele: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# Moderování
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — vrací tělo audio/mpeg (nebo požadovaný formát)
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS vyžaduje jazyk a hlas: výchozí hodnota `language` je "en"; chybějící
# hlas nebo název standardního hlasu OpenAI (alloy, nova, …) se změní na "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# Úprava obrázku (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# Generování videa / hudby (ID modelu s předponou poskytovatele)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **Uzly poskytovatelů pro reranking:** `POST /v1/rerank` také směruje požadavky na uzly poskytovatelů kompatibilní s OpenAI
> (oMLX, vLLM, Infinity, TEI za bránou, …), adresované jako `<node-prefix>/<model>`. Uzly zpětné
> smyčky (`localhost`, `127.0.0.1`, `172.16.0.0/12`) jsou vždy způsobilé, stejně jako názvy hostitelů, které
> provozovatel uvede v `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (např. název služby Docker/Compose,
> jako je `http://reranker:8080/v1`; tyto uzly se volají přímo, nikdy přes `HTTP(S)_PROXY` ani
> připnutý proxy server připojení). Uzly na jakémkoli jiném
> hostiteli — zařízení v síti LAN nebo peer v Tailscale — jsou způsobilé pouze tehdy, když provozovatel povolí
> příznak funkce `RERANK_REMOTE_PROVIDER_NODES` **a zároveň** základní URL uzlu vyhovuje zásadám poskytovatele
> pro odchozí URL (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Krok rerankingu paměťového modulu volá tuto trasu přes
> zpětnou smyčku, takže stejné pravidlo se v nastavení paměti vztahuje na `rerankProviderModel`.
>
> **Podoby lokálního serveru:** uzel se volá na adrese `<base>/v1/rerank` a při odpovědi 404 na adrese `<base>/rerank`
> (Infinity, TEI). Tělo odesílané upstream obsahuje jak zápis Cohere/OpenAI (`documents`,
> `return_documents`), tak zápis TEI (`texts`, `return_text`), a upstream odpověď je
> normalizována do obálky Cohere: holé pole TEI `[{index, score, text}]`, `{results: [{index, score}]}`
> z jednoduchých bran i formát Voyage `{data: [...]}` se klientovi vracejí jako
> `{results: [{index, relevance_score, document?}]}`, seřazené podle skóre a omezené na `top_n`.

> **Zjišťování uzlů poskytovatelů:** modely na uzlu poskytovatele kompatibilním s OpenAI se zobrazují v `GET /v1/models`
> pod prefixem uzlu. Řádky bez metadat koncových bodů (typické pro lokální výpisy `/v1/models`)
> dědí `apiType` uzlu, takže modely uzlu `embeddings` mají `type: "embedding"` a modely
> uzlu `rerank` mají `type: "rerank"` namísto výchozího typu chatu; explicitní
> `supportedEndpoints` v synchronizovaném nebo ručně přidaném řádku má nadále přednost.

### `provider_options` pro Exa a Tavily

Exa a Tavily načítají pole specifická pro poskytovatele z jmenně odděleného objektu:
`provider_options.exa` (nebo `provider_options["exa-search"]`) a `provider_options.tavily`
(nebo `provider_options["tavily-search"]`). Předávány jsou pouze níže uvedené klíče. Každý z nich je
kontrolován podle vlastního schématu Zod v `open-sse/handlers/search/providerOptionsPassthrough.ts`
a klíč s nesprávným typem je zahozen. Všechny ostatní klíče jsou ignorovány, včetně ověřování, základní URL,
`stream` a `outputSchema`. Ploché klíče používané ostatními poskytovateli (`cx`, `depth`, ...) fungují
stejně jako dříve.

| Poskytovatel | Pole nejvyšší úrovně                                                                                                                                                                                                                                                                                                                                                      | Vnořená                                                                                                                                                               |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa          | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (ploché primitivní hodnoty), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                    | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` sloučené s výchozí hodnotou `{ text: true, highlights: true }` |
| Tavily       | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                     |

Obecná pole mají vždy přednost: `query`, `max_results`, `filters` (domény), `country` a
téma odvozené z `search_type`. U Exa zachová `search_type: "news"` hodnotu `category: "news"`.
Tavily přijímá také `search_type: "finance"` (`topic: "finance"`).

Obecné pole `time_range` se nyní předává oběma poskytovatelům: Exa obdrží `startPublishedDate` (časové
razítko ISO) a Tavily obdrží `start_date` (`YYYY-MM-DD`). Explicitní datum v `provider_options`
má přednost před namapovanou hodnotou.

Výsledky Exa zachovávají `id`, `highlight_scores`, `summary`, `subpages`, `entities` a `extras` v
`provider_raw`. Výsledky Tavily zachovávají `images` a `favicon`.

Účtování nákladů nadále používá plochý registr `costPerQuery`. Tavily účtuje
za `search_depth: "advanced"` více kreditů na jedno volání a tento rozdíl se nepromítá do
`usage.search_cost_usd`.

## API Web Fetch

Extrahuje obsah z adresy URL prostřednictvím nakonfigurovaného poskytovatele načítání webu (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, stejný API klíč jako Parallel Search) vrací pouze Markdown
— jakýkoli jiný `format` vede k chybě `400` — a omezuje obsah na 100 000 znaků. Když
nelze extrahovat samotnou cílovou stránku, upstream tuto skutečnost oznámí v odpovědi HTTP 200;
OmniRoute ji zpřístupní jako `422` s pevně danou zprávou.

| Metoda | Cesta           | Popis                                                         |
| ------ | --------------- | ------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | Načtení/extrakce adresy URL — tělo ověřuje `v1WebFetchSchema` |

**Ověření:** Bearer API klíč (`extractApiKey` + `isValidApiKey`). Zásady se vynucují prostřednictvím `enforceApiKeyPolicy`.

**Záložní mechanismus zohledňující kvóty (#8297):** pokud není výslovně zadán žádný `provider`, fond
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) se
prochází v pevném
pořadí priorit (fill-first) — nakonfigurovaný poskytovatel s omezenou rychlostí je přeskočen,
místo aby požadavek okamžitě ukončil, a opakovatelná chyba upstreamu nebo chyba kvóty
(HTTP 429 vždy; 402/403 u bezplatných tarifů Firecrawl/Tavily/TinyFish se stylem kvóty —
nikoli u Jina Reader a nikdy u běžného chybného požadavku 400) za běhu přejde
k dalšímu dosud nevyzkoušenému poskytovateli s nakonfigurovanými přihlašovacími údaji. Když jsou všichni poskytovatelé ve
fondu vyčerpáni, koncový bod vrátí jedinou odpověď `429` (s hlavičkou `Retry-After`)
namísto dřívější obecné odpovědi `400`. Pokud je výslovně požadován konkrétní `provider`,
k žádnému tichému záložnímu přepnutí **nedochází** — explicitně zvolený poskytovatel s omezenou
rychlostí nebo chybou zpřístupní svou vlastní chybu (`429` při omezení rychlosti, jinak stav
upstreamu).

## Streamování přes WebSocket

```bash
GET /v1/ws?handshake=1
```

Ověří handshake pro upgrade na WebSocket a vrátí ukázkové zprávy drátového protokolu (`request`, `cancel`). Skutečné rámce WS zpracovává přibalený server WS mimo tabulku tras Next.js.

**Ověření:** Bearer API klíč během handshake.

### Responses API přes WebSocket (pouze codex)

```bash
# Stejný hostitel a port jako HTTP API (výchozí 20128); upgradujte připojení:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (nebo: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Prvním rámcem MUSÍ být response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Proxy Responses API přes WebSocket je připojena **výhradně ke `codex`** (backend ChatGPT).
Naslouchá na stejném portu jako API/řídicí panel na cestách `/v1/responses`,
`/responses` a `/api/v1/responses`. Při prvním rámci `response.create`
provede ověření a přípravu prostřednictvím interního mostu `codex-responses-ws`, vybere
připojení OAuth pro codex a vytvoří tunel k `wss://chatgpt.com/backend-api/codex/responses`
prostřednictvím transportu `wreq-js`. **Modely jiné než codex jsou odmítnuty** (`codex_ws_provider_required`).
Pro směrování se sdílením kvóty použijte `model: "qtSd/<group>/codex/<model>"`. Implementace je v
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Ověření:** Bearer API klíč během handshake. Přibalený HTTP server (`server-ws.mjs`)
musí být aktivním vstupním bodem (ve výchozím nastavení jím je, pokud existuje `app/server-ws.mjs`).

#### ID modelu: použijte prosté ID ChatGPT (bez předpony `codex/`)

OpenAI **Codex CLI** ověřuje název modelu na straně klienta, pokud
`supports_websockets = true`, a **odmítá ID s předponou poskytovatele**, například
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Odešlete **prosté** ID (např. `gpt-5.5`). Most OmniRoute je
určen pouze pro codex, takže před vytvořením tunelu k upstreamu znovu přeloží prosté ID na model codex
(`resolveCodexWsModelInfo`) — přestože by se prosté
`gpt-5.5` jinak přes HTTP směrovalo k jinému poskytovateli.

#### Konfigurace OpenAI Codex CLI

Nasměrujte Codex CLI na OmniRoute přidáním vlastního poskytovatele s podporou WebSocket
do `~/.codex/config.toml` (použijte samostatný `CODEX_HOME`, abyste neovlivnili
stávající konfiguraci):

```toml
model = "gpt-5.5"                 # prosté ID — NE „codex/gpt-5.5“
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # bez koncového lomítka; adresa URL pro WS se odvodí automaticky (v produkci použijte https/wss)
wire_api = "responses"                    # jediná podporovaná hodnota od února 2026
supports_websockets = true                # povolí transport Responses přes WS
env_key = "OMNIROUTE_API_KEY"             # obsahuje API klíč OmniRoute (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # API klíč OmniRoute (libovolný klíč, pokud REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI upgraduje `base_url + /responses` na WebSocket a OmniRoute jej tuneluje
k vybranému připojení OAuth pro codex. Funkčnost byla kompletně ověřena vůči místnímu
serveru: ChatGPT vrací `codex.rate_limits` + `response.created` a streamuje
dokončení.

## Samoobslužné využití (`/api/usage/om-usage`)

Libovolný API klíč může zobrazit **své vlastní** využití a kvóty — bez ověření pro správu. Tento koncový bod
používá klient (CLI, panel OmniCopilot), aby držiteli klíče zobrazil jeho útratu.

```bash
# Textová podoba (historický kontrakt — prostý text pro terminál)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Strukturovaná podoba — určená pro uživatelské rozhraní
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Klíč musí mít povolenou možnost **`allowUsageCommand`** (ve výchozím nastavení je vypnutá — správce API klíčů
na řídicím panelu ji přepíná pro každý klíč zvlášť). Bez ní koncový bod odpoví stavem `403`.

`?format=json` vrací rozlišenou strukturu, takže se volající nikdy nepokusí číst datové pole
z odpovědi o zamítnutí. Při úspěchu:

```jsonc
{
  "allowed": true,
  // přítomno pouze tehdy, když má klíč nastavené vlastní limity využití (denní/týdenní v USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // snímek kvóty vybraného poskytovatele, nebo null, pokud zatím není nic v mezipaměti:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // snímky všech připojení, aby uživatelské rozhraní mohlo vykreslit několik poskytovatelů vedle sebe:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Při zamítnutí (`401` neplatný klíč / `403` přístup nepovolen) vrací stejná trasa
`{ "allowed": false, "error": { "message": "…" } }` — přítomné, ale prázdné `personal`/`provider`
(klíč je povolen, ale zatím nebyla získána žádná data) představuje jiný stav než zamítnutí a rozlišuje je
pouze podoba JSON.

**Ověření:** vlastní Bearer API klíč volajícího ověřený pomocí `isValidApiKey` — toto _není_
rozhraní pro správu (`/api/keys/…`), které zůstává chráněno pomocí `requireManagementAuth`.

### Nezpracované procentuální hodnoty kvót oproti hodnotám upraveným podle mezní hodnoty

Při používání `/api/usage/om-usage` by volající měli vzít v úvahu rozdíl mezi procentuálními hodnotami
uváděnými ve **výstupu v prostém textu** a ve strukturovaném **výstupu JSON**:

| Aspekt                      | Formát prostého textu (`/api/usage/om-usage` / `@@om-usage`)                                       | Formát JSON (`?format=json`)                                                         |
| :-------------------------- | :------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------- |
| **Výstupní pole**           | `NN% left` (např. `20% left`)                                                                      | `provider.quotas` / `providers[].quotas`                                             |
| **Měření**                  | **Použitelná kapacita upravená podle mezní hodnoty**: zbývající kapacita nad mezní hodnotou        | **Nezpracovaná kvóta poskytovatele**: neupravená hodnota od poskytovatele            |
| **Škálování mezní hodnoty** | Škálováno pomocí `effectiveRemainingPercent()`, takže se chráněná rezerva zobrazuje jako `0% left` | Žádné (nezpracované hodnoty snímku, jak je nahlásil poskytovatel)                    |
| **Data mezních hodnot**     | Zahrnuta do zobrazené procentuální hodnoty                                                         | Uložena v `quotaWindowThresholds` pro každé připojení (nebo výchozí hodnoty serveru) |
| **Primární uživatel**       | Interaktivní CLI, terminálové výzvy, lidští operátoři                                              | Programové integrace, řídicí panely, analytika, nástroje pro sledování fakturace     |

#### Vzorec pro úpravu podle mezní hodnoty

OmniRoute podporuje proaktivní mezní hodnoty kvót, aby zabránil vyčerpání prostředků poskytovatele (konfigurují
se pomocí `quotaWindowThresholds` připojení, výchozích hodnot poskytovatele nebo globálního nastavení odolnosti).
Když je v časovém okně kvóty aktivní mezní hodnota (např. `cutoff = 25%`), vykreslování textu vypočítá zbývající
kapacitu následovně:

- Pokud `remaining <= cutoff`: vrátí `0%`.
- Pokud `remaining > cutoff`: vrátí `((remaining - cutoff) / (100 - cutoff)) * 100`.

Formátovaný textový výstup zaokrouhlí tuto hodnotu na nejbližší celé číslo (`Math.round(...)`).

#### Ilustrační příklad

Představme si časové okno poskytovatele s **60% nezpracovaným využitím** (tedy **40% nezpracované zbývající
kvóty**) a nakonfigurovanou mezní hodnotou **25 % zbývající kvóty**:

| Reprezentace                           | Výpočet                                            |  Zbývá  |            Odvozené využití             |
| :------------------------------------- | :------------------------------------------------- | :-----: | :-------------------------------------: |
| **Nezpracovaný JSON (`?format=json`)** | Snímek poskytovatele (`quotas[window]`)            | **40%** |                 **60%**                 |
| **Textový formát (`NN% left`)**        | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (při výpočtu `100 - remaining`) |

- **Proč text zobrazuje 20 % zbývající kapacity:** Z 40 % fyzické kvóty zbývající na účtu je 25 % rezervováno
  zásadou mezní hodnoty. Volající má k dispozici pouze 15 % ze 75 % použitelné rezervy, než směrovač přestane
  směrovat požadavky do tohoto připojení. Škálování zajišťuje, že připojení signalizuje vyčerpání (`0% left`)
  přesně v okamžiku, kdy směrování skončí.
- **Proč JSON zachovává nezpracované hodnoty:** Datová část JSON vrací přesný snímek poskytovatele (`UsageSnapshot`),
  takže externí nástroje mají přístup ke skutečnému využití u poskytovatele a k hodnotám
  `quotaWindowThresholds` na úrovni připojení bez ztrátového škálování na straně serveru.

#### Pokyny pro migraci klientů

Pokud externí integrace (například plugin editoru nebo rozšíření agenta) dříve získávala data z textového
endpointu (`NN% left`) a počítala využité procento jako `100 - NN`, přechod na `?format=json` znamená:

- Čtení nezpracovaných hodnot JSON bude odrážet **skutečnou spotřebu na straně upstreamu** (ve výše uvedeném příkladu je využito 60 %).
- Pokud chce integrace zachovat sémantiku využitelného zbývajícího limitu textového endpointu, může
  vzorec pro efektivní zbývající limit vyhodnotit na straně klienta pomocí `quotaWindowThresholds` pro přepsání na úrovni připojení.

## Sémantická mezipaměť

```bash
# Získání statistik mezipaměti
GET /api/cache/stats

# Vymazání všech mezipamětí
DELETE /api/cache/stats
```

Příklad odpovědi:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,

  }
}
```

### Dopad na latenci

Při ZÁSAHU do sémantické mezipaměti je odpověď poskytnuta z mezipaměti **bez volání
nadřazené služby**, takže vykázaná hodnota `X-OmniRoute-Response-Latency` je téměř nulová
(bez ohledu na původní latenci nadřazené služby). Klienti citliví na latenci
(benchmarky, monitorování p50/p99) by měli kontrolovat hlavičku odpovědi
`X-OmniRoute-Cache-Latency`:

| Hodnota     | Význam                                                                         |
| ----------- | ------------------------------------------------------------------------------ |
| `synthetic` | Odpověď poskytnutá z mezipaměti; latence není skutečnou dobou nadřazené služby |
| _(chybí)_   | Odpověď ze skutečného volání nadřazené služby                                  |

### Obejití mezipaměti pro jednotlivé klíče

Klíče API mohou pomocí `cacheDefaultMode` zakázat čtení ze sémantické mezipaměti:

| Hodnota  | Chování                                                                |
| -------- | ---------------------------------------------------------------------- |
| `legacy` | Běžné chování mezipaměti (výchozí)                                     |
| `bypass` | Zcela přeskočí vyhledávání v mezipaměti; vždy zavolá nadřazenou službu |

Nastavte při vytvoření klíče (`POST /api/keys`) nebo aktualizaci (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Obejití pro jednotlivé požadavky

Libovolný požadavek může obejít mezipaměť bez ohledu na nastavení klíče:

```
X-OmniRoute-No-Cache: true
```

Transparentní obálky kompatibilní s OpenAI mohou zachovat původní položku modelu uvnitř vnořeného
objektu `openai`; detekce prochází až třemi takovými obálkami. Modely s chybějícím, neznámým nebo
konfliktním vlastnictvím si zachovají běžné chování OpenAI. Detekce znovu používá existující požadavek na katalog,
negeneruje žádné dokončovací tokeny a při změně koncového bodu připojení se zneplatní.

Chcete-li toto chování vynutit pro backend, který tato metadata neposkytuje, použijte existující API
pro částečnou aktualizaci poskytovatele:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Toto tělo odešlete pomocí `PUT /api/providers/<connection-id>`. U tohoto připojení se explicitní
míra uvažování `none` odešle jako `chat_template_kwargs.thinking=false` a
`chat_template_kwargs.enable_thinking=false`. Explicitní nativní hodnoty šablony mají i nadále přednost,
pokud pravidlo uvažování na straně serveru nevynutí určitou míru. Nastavení se použije pouze tehdy, když vlastní
připojení kompatibilní s OpenAI odesílá tělo Chat Completions; požadavky Responses a běžní
poskytovatelé si zachovají svůj nativní tvar požadavku. Nastavením `reasoningControl` na `openai` vynutíte běžné předávání
`reasoning_effort` do OpenAI; případně tuto hodnotu vynechte nebo ji nastavte na `null`, aby se použila automatická detekce.

Požadavky klasifikátoru automatického režimu Claude Code ve výchozím nastavení zakazují nativní přemýšlení, pokud
neobsahují žádné explicitní ovládací prvky uvažování. Detekce používá systémovou značku klasifikátoru v požadavcích
ve formátu Claude, nikoli názvy modelů ani limity dokončení. Explicitní ovládací prvky těla, podporované hlavičky
pro míru uvažování/přemýšlení, pravidla směrování a vyhodnocená míra uvažování modelu si zachovávají svou stávající prioritu. Obě fáze klasifikátoru
si zachovávají své prompty, limity dokončení, ukončovací sekvence i skutečná rozhodnutí nadřazené služby
o oprávnění; druhá fáze může nadále vytvářet požadované viditelné uvažování jako běžný text.

### Verze a kanál vydání

```bash
GET /api/system/version
```

Trasa pro správu dostupná pouze přes loopback (ověření správce). Vrací spuštěnou verzi, nejnovější
publikovanou verzi a stav automatických aktualizací. `releaseChannel` a `channels` jsou doplňková
pole (řada 3.8.54); `channel` si zachovává svůj význam — režim nasazení, který používá aktualizační
nástroj řídicího panelu (`npm`, `source` nebo `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — npm kanál spuštěného sestavení: `nightly` pro verze `-nightly.*`,
  `next` pro ostatní předběžná vydání (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` pro stabilní verzi
  starší hlavní řady, než je `channels.latest`, jinak `latest`. Stejná pravidla jako v
  `scripts/release/dist-tag.mjs`, který při publikování vybírá npm dist-tag.
- `channels` — nejnovější publikovaná verze každého dist-tagu z `npm view omniroute dist-tags`
  (se záložním dotazem HTTP na registr), uložená do mezipaměti se stejnou 10minutovou dobou platnosti
  jako `latest`. `latest` je vždy přítomen (použije se záložní hodnota z pole `latest`, poté
  `"unavailable"`); `next`, `nightly` a `lts` se zobrazí pouze tehdy, když daný dist-tag existuje.
  Požadavek s `Cache-Control: no-cache` obnoví obě vyhledávání.

Model kanálů (`latest` = v3 až do obecné dostupnosti verze 4.0, `next` = rc, `nightly` = sestavení
z `develop`, `lts` = opravy v3 po obecné dostupnosti verze 4.0) je popsán v `docs/ops/RELEASE_STRATEGY.md`.

## Limity tokenů

Rozpočty **tokenů** pro jednotlivé API klíče (odlišné od výše uvedeného rozpočtu založeného na USD). Vynucují se přímo při zpracování požadavku: když využití klíče v aktuálním časovém okně dosáhne stanoveného limitu, požadavky jsou odmítnuty s chybou `429 Too Many Requests`. Limity lze omezit na konkrétní `model`, poskytovatele (`provider`) nebo je použít globálně (`global`) pro celý klíč. Pokud požadavku odpovídá několik limitů, použije se ten nejpřísnější.

```bash
# Výpis limitů tokenů klíče (včetně aktuálního využití okna)
GET /api/usage/token-limits?apiKeyId=key-123

# Vytvoření nebo aktualizace limitu tokenů
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Odstranění limitu tokenů podle ID
DELETE /api/usage/token-limits?id=tl-abc
```

> **Poznámky ke schématu** (`setTokenLimitSchema`): `apiKeyId` a `scopeType` (`model` | `provider` | `global`) jsou povinné. `scopeValue` je povinné, pokud `scopeType` není `global` (např. ID modelu pro rozsah `model` nebo ID poskytovatele pro rozsah `provider`). `tokenLimit` musí být kladné celé číslo (řetězec je na něj převeden). Volitelné: `id` (vynechte při vytváření, zadejte při aktualizaci), `resetInterval` (`daily` | `weekly` | `monthly`, výchozí hodnota `monthly`), `resetTime` (`HH:MM`), `enabled` (výchozí hodnota `true`). Odpovědi `GET` rozšiřují každý limit o položky `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` a `nextResetAt`. Jde o koncový bod pro správu (ověřování je vynucováno centrálně autorizační pipeline).

## Zpracování požadavků

1. Klient odešle požadavek na `/v1/*`
2. Obslužná rutina trasy zavolá `handleChat`, `handleEmbedding`, `handleAudioTranscription` nebo `handleImageGeneration`
3. Vyřeší se model (přímý poskytovatel/model nebo alias/kombinace)
4. Z místní databáze se vyberou přihlašovací údaje s filtrováním podle dostupnosti účtu
5. Pro chat: `handleChatCore` zkontroluje sémantickou/signaturní mezipaměť a vyřeší nastavení komprese kombinace
6. Pokud je povolena, před převodem pro poskytovatele se provede proaktivní komprese (`lite`, Caveman, RTK nebo jejich kombinace)
7. Executor poskytovatele odešle požadavek nadřazené službě
8. Odpověď se převede zpět do formátu klienta (chat) nebo se vrátí beze změny (embeddingy/obrázky/audio)
9. Zaznamená se využití, analytika komprese a protokoly požadavků
10. Při chybách se podle pravidel kombinace použije záložní varianta

Úplný popis architektury: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Odolnost (rozšířené)

OmniRoute nabízí tři nezávislé mechanismy pro dočasná selhání; níže uvedené koncové body pro správu umožňují operátorům zobrazit a přepsat jejich nastavení:

| Rozsah               | Úložiště stavu                               | Čtení                                     | Resetování / vymazání                                                |
| -------------------- | -------------------------------------------- | ----------------------------------------- | -------------------------------------------------------------------- |
| Jistič poskytovatele | `domain_circuit_breakers` + v paměti         | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                         |
| Prodleva připojení   | `rateLimitedUntil` u připojení poskytovatelů | `/api/rate-limits`, `/api/providers/[id]` | (znovu se aktivuje až při potřebě; vymažte pomocí PUT poskytovatele) |
| Uzamčení modelu      | Registr dostupnosti modelů v paměti          | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                             |

`PATCH /api/resilience` přijímá přepsání jističe poskytovatele v `providerBreaker.oauth` a `providerBreaker.apikey`. Každý profil podporuje `degradationThreshold`, `failureThreshold` a `resetTimeoutMs`; stejná pole jsou dostupná v Ovládací panel → Nastavení → Odolnost.

```bash
# Vymazání uzamčení jednoho modelu
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Vymazání všech uzamčení
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Úplný koncepční přehled a výchozí nastavení jističe naleznete v [`CLAUDE.md`](../../CLAUDE.md) → „Stav běhového prostředí odolnosti“ a [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Fronta omezení četnosti a pojistka automatické aktivace

- **Podporovaná cesta zápisu**: `POST /api/rate-limits` s tělem `{"connectionId": "<id>", "enabled": true|false}` je podporovaný koncový bod pro správu, kterým lze zapnout nebo vypnout ochranu připojení před omezením četnosti. `PUT /api/providers/[id]` záměrně neupravuje ani nepřepíná `rateLimitProtection` (#11278).
- **Sémantika `enabled: false`**: Nastavení `enabled: false` odebere explicitní ochranu připojení, ale **nevyřadí** aktivní připojení s API klíčem z globální pojistky automatické aktivace (`autoEnableApiKeyProviders = true`). Ve funkci `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) jsou hodnoty `false` a `undefined` rovnocenné; aktivní připojení s API klíčem bez explicitní ochrany zůstávají chráněna globální pojistkou automatické aktivace.
- **Globální vypnutí**: Chcete-li provozovat připojení s API klíčem bez front omezení četnosti, vypněte pojistku globálně pomocí `RATE_LIMIT_AUTO_ENABLE=false` (proměnná prostředí) nebo `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Nastavení → Odolnost / `PATCH /api/resilience`).

## Server MCP

OmniRoute obsahuje vestavěný server Model Context Protocol se 3 transporty (stdio, SSE, streamable-http) a nástroji s omezeným rozsahem oprávnění. Níže uvedené endpointy dashboardu načítají stavová/auditní data a zprostředkovávají HTTP transporty.

| Metoda | Cesta | Popis |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |

| GET | `/api/mcp/tools` | Seznam nástrojů MCP s `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` |
| GET | `/api/mcp/sse` | Otevření streamu SSE pro transport SSE (vrací `503`, pokud je MCP zakázáno nebo transport neodpovídá) |
| POST | `/api/mcp/sse` | Odeslání rámce JSON-RPC prostřednictvím transportu SSE |
| GET | `/api/mcp/stream` | Otevření strany SSE transportu Streamable HTTP (zprávy iniciované serverem) |

| DELETE | `/api/mcp/stream` | Ukončení relace Streamable HTTP |

## Server A2A

OmniRoute zpřístupňuje koncový bod A2A (Agent-to-Agent) využívající JSON-RPC 2.0 a také obálku REST pro účely kontroly a řídicího panelu.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # volitelné, pokud není nastavena OMNIROUTE_API_KEY
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Podporované metody (všechny jsou podmíněny nastavením `settings.a2aEnabled`):

| Metoda           | Popis                                                               |
| ---------------- | ------------------------------------------------------------------- |
| `message/send`   | Synchronní spuštění dovednosti; vrací `{task, artifacts, metadata}` |
| `message/stream` | Streamované spuštění stejné sady dovedností prostřednictvím SSE     |
| `tasks/get`      | Načtení úlohy podle `taskId`                                        |
| `tasks/cancel`   | Zrušení úlohy podle `taskId`                                        |

Vestavěné dovednosti: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Karta agenta

```bash
GET /.well-known/agent.json
```

Vrací veřejnou kartu agenta A2A (název, popis, možnosti, katalog dovedností, schéma autentizace) — je veřejně ukládána do mezipaměti po dobu 1 h. Autentizace není vyžadována.

### Pomocné koncové body REST

| Metoda | Cesta                        | Popis                                                                                                           |
| ------ | ---------------------------- | --------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/a2a/status`            | Stav povolení A2A + statistiky úloh + souhrn karty agenta z mezipaměti                                          |
| GET    | `/api/a2a/tasks`             | Výpis úloh — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (Není implementováno jako pomocný koncový bod REST — vytvořte prostřednictvím JSON-RPC `message/send`)          |
| GET    | `/api/a2a/tasks/[id]`        | Načtení jedné úlohy                                                                                             |
| POST   | `/api/a2a/tasks/[id]/cancel` | Zrušení úlohy                                                                                                   |

**Autentizace:** pomocné koncové body REST fungují bez autentizace pro správu (jsou čitelné z řídicího panelu); trasa JSON-RPC `/a2a` používá Bearer `OMNIROUTE_API_KEY`, pokud je nakonfigurován.

## Ochranné mechanismy

## Ověřování

Informace o čtyřech skupinách přihlašovacích údajů (relace řídicího panelu, místní token CLI, přístupový token `oma_live_…`, klíč API s oprávněními pro správu) a jejich odlišnostech od inferenčních klíčů najdete v dokumentu [Ověřování pro správu](../guides/MANAGEMENT-AUTH.md).

- Trasy řídicího panelu (`/dashboard/*`) používají soubor cookie `auth_token`
- Přihlášení používá uložený hash hesla; jako záložní možnost používá `INITIAL_PASSWORD`
- Požadavek `requireLogin` lze přepínat prostřednictvím `/api/settings/require-login`
- Trasy `/v1/*` mohou volitelně vyžadovat klíč API typu Bearer, pokud je nastaveno `REQUIRE_API_KEY=true`
- „token pro správu“ / „klíč API s oprávněními pro správu“ v této referenční dokumentaci označuje jednu ze skupin popsaných v uvedeném průvodci — nikoli nedefinovaný dodatečný typ tajného údaje

> **Změna narušující zpětnou kompatibilitu (v3.8.0)** — `/api/v1/agents/tasks/*` a koncové body pro správu období cooldown nyní vyžadují **ověření pro správu** (soubor cookie `auth_token` řídicího panelu nebo klíč API s oprávněními pro správu). Klienti, kteří dříve volali tyto trasy bez ověření, obdrží odpověď `401 Unauthorized`. Viz commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
