## Զրույցի լրացումներ

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Հատուկ վերնագրեր

| Վերնագիր                 | Ուղղություն | Նկարագրություն                                                                                                                                                                                                                                |
| ------------------------ | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Հարցում     | Սահմանեք `true`՝ քեշը շրջանցելու համար                                                                                                                                                                                                        |
| `x-omniroute-no-memory`  | Հարցում     | Սահմանեք `true`՝ այս հարցման համար հիշողության և հմտությունների ներարկումը բաց թողնելու նպատակով (համարժեք է քեշը շրջանցելուն և թույլ է տալիս խուսափել յուրաքանչյուր կանչի թոքենների/ծախսի հավելյալ բեռից)                                    |
| `X-OmniRoute-Progress`   | Հարցում     | Սահմանեք `true`՝ ընթացքի իրադարձություններ ստանալու համար                                                                                                                                                                                     |
| `X-Session-Id`           | Հարցում     | Կայուն նստաշրջանի բանալի՝ արտաքին նստաշրջանային կապակցվածության համար                                                                                                                                                                         |
| `x_session_id`           | Հարցում     | Ընդունվում է նաև ընդգծման նշանով տարբերակը (ուղղակի HTTP)                                                                                                                                                                                     |
| `X-OmniRoute-Session-Id` | Հարցում     | Կանչողի տրամադրած նստաշրջանի/զրույցի պիտակ (նաև փոխանցվում է հիշողությանը)։ Առկայության դեպքում բառացիորեն պահպանվում է `call_logs.session_tag`-ում՝ ըստ նստաշրջանի ծախսերի վերագրման համար (#8249). բացակայության դեպքում երբեք չի ստեղծվում |
| `Idempotency-Key`        | Հարցում     | Կրկնությունների վերացման բանալի (5 վրկ պատուհան)                                                                                                                                                                                              |
| `X-Request-Id`           | Հարցում     | Կրկնությունների վերացման այլընտրանքային բանալի                                                                                                                                                                                                |
| `x-omniroute-connection` | Հարցում     | Մեկ մոդելով հարցումն ամրակցում է մատակարարի մեկ կապին (հաշվին)՝ ըստ դրա id-ի. տե՛ս [Հաշվի ամրակցում ըստ հարցման](#account-pinning-per-request)                                                                                                |
| `X-OmniRoute-Cache`      | Պատասխան    | `HIT` կամ `MISS` (առանց հոսքային փոխանցման)                                                                                                                                                                                                   |
| `X-OmniRoute-Idempotent` | Պատասխան    | `true`, եթե կրկնությունը վերացվել է                                                                                                                                                                                                           |
| `X-OmniRoute-Progress`   | Պատասխան    | `enabled`, եթե ընթացքի հետևումը միացված է                                                                                                                                                                                                     |
| `X-OmniRoute-Session-Id` | Պատասխան    | OmniRoute-ի օգտագործած փաստացի նստաշրջանի ID-ն                                                                                                                                                                                                |
| `X-OmniRoute-Request-Id` | Պատասխան    | Հարցումների փոխկապակցման id-ն (եթե հայտնի է)                                                                                                                                                                                                  |
| `X-OmniRoute-Version`    | Պատասխան    | OmniRoute-ի հավաքման տարբերակը (միշտ առկա է)                                                                                                                                                                                                  |
| `X-OmniRoute-Cost-Saved` | Պատասխան    | USD-ով այն գումարը, որը քեշը խնայել է `HIT`-ի դեպքում (միայն քեշի համընկնումների համար)                                                                                                                                                       |
| `X-OmniRoute-Decision`   | Պատասխան    | Ուղղորդման հետագիծ՝ `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>`-ը համակցման ռազմավարությունն է, իսկ ոչ համակցված հարցման դեպքում՝ `single`) — միշտ առկա է ավարտման պատասխաններում                                           |

> Nginx-ի նշում․ եթե օգտագործում եք ընդգծման նշան պարունակող վերնագրեր (օրինակ՝ `x_session_id`), միացրեք `underscores_in_headers on;` կարգավորումը։

#### Հաշվի ամրագրում յուրաքանչյուր հարցման համար

Երբ մատակարարն ունի մի քանի կապակցում (հաշիվներ կամ բանալիներ), OmniRoute-ը սովորաբար ընտրում է դրանցից մեկը՝
իր հաշվի ընտրության ռազմավարության միջոցով։ Փոխարենը հարցումը կարող է ամրագրել մեկ կոնկրետ կապակցում՝
օգտագործելով `x-omniroute-connection` վերնագիրը․

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Որտեղ գտնել id-ն։** Բացեք մատակարարի էջը կառավարման վահանակում
  (**Կառավարման վահանակ → Մատակարարներ → <provider>**) և սեղմեք կապակցման տողի `xxxxxxxx…` id նշիչը․
  այն պատճենում է կապակցման ամբողջական id-ն։
- **Որ հարցումներն են այն հաշվի առնում։** Մեկ մոդելով հարցումները (`provider/model`)՝
  `/v1/chat/completions`, `/v1/messages` և `/v1/responses` հասցեներում։ Համակցություններն անտեսում են վերնագիրը․
  փոխարենը յուրաքանչյուր համակցման քայլի համար հաշիվ ամրագրեք հենց այդ քայլի կապակցման միջոցով։
- **Ամրագրումը խիստ է, ոչ թե նախապատվություն։** Օգտագործվում է բացառապես ամրագրված կապակցումը։
  Հարցման ընթացքում տեղի ունեցած ձախողումը գրանցում է հաշվի սպասման ժամանակահատվածը, բայց **չի** անցնում
  նույն մատակարարի մեկ այլ հաշվին։
- **Սպասման ժամանակահատվածը և քվոտան ազատում են ամրագրումը։** Քանի դեռ ամրագրված կապակցումը սպասման ժամանակահատվածում է,
  սպառել է քվոտան կամ արգելափակված է քվոտայի քաղաքականությամբ, հետագա հարցումները հետ են անցնում մատակարարի
  մյուս կապակցումներին՝ ճիշտ այնպես, ինչպես չամրագրված տրաֆիկի դեպքում։
- **Անհայտ կամ անջատված id-ները հանգեցնում են ձախողման։** Մատակարարի ակտիվ ֆոնդում չգտնվող id-ն (ջնջված,
  ապաակտիվացված կամ մեկ այլ մատակարարին պատկանող) չի թողնում ոչ մի համապատասխան հաշիվ, ուստի հարցումը
  ձախողվում է՝ այլ ուղղությամբ աննկատ երթուղավորվելու փոխարեն։

Claude Code-ը հատուկ վերնագրերն ուղարկում է `ANTHROPIC_CUSTOM_HEADERS`-ի միջոցով։ Տեղադրեք այն
`~/.claude/settings.json`-ի `env` բլոկում կամ նախագծի մակարդակի `.claude/settings.json`-ում՝ յուրաքանչյուր
նախագծի համար տարբեր հաշիվ ամրագրելու նպատակով․

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Աղբյուր՝ `src/sse/handlers/chat.ts` (վերնագրի ընթերցում), `src/sse/services/auth.ts` և
`src/sse/services/sessionAffinityPin.ts` (ամրագրման ազատում և ֆոնդում բացակայության ստուգում)։

> **Արժեքի տելեմետրիայի վերնագրեր․** հոսքային չհանդիսացող հաջող պատասխանները նաև պարունակում են `X-OmniRoute-*` արժեքի տելեմետրիայի հավաքածուն՝ `X-OmniRoute-Response-Cost` (USD, ֆիքսված 10 տասնորդական նիշով, անվճար կամ չգնահատված հարցումների համար՝ `0.0000000000`), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` և `X-OmniRoute-Fallback-Attempts` (միայն երբ > 0 է), ինչպես նաև `X-OmniRoute-Request-Id` և `X-OmniRoute-Version`։ Դրանք տրամադրվում են զրույցի լրացումների, `/v1/responses`, `/v1/messages`, **ինչպես նաև մեդիա վերջնակետերի** կողմից՝ `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` և `/v1/moderations` (արժեքը միշտ `0` է)։ Մեդիայի արժեքը հաշվարկվում է ըստ եղանակի (յուրաքանչյուր պատկերի, վայրկյանի, նիշի կամ որոնման միավորի համար), երբ գնագոյացումը հասանելի է, հակառակ դեպքում՝ `0` (ձախողման դեպքում աշխատանքը շարունակվում է)։

> **Քեշում գտնվելու արժեքի իմաստաբանություն․** իմաստային քեշում HIT-ի դեպքում (`X-OmniRoute-Cache-Hit: true`) վերին մակարդակի ծառայությանը հարցում չի կատարվում, ուստի `X-OmniRoute-Response-Cost`-ը `0.0000000000` է (քեշից արդյունքը տրամադրելու **լրացուցիչ** արժեքը)։ Սկզբնական կամ ենթադրվող արժեքը առանձին հաղորդվում է `X-OmniRoute-Cost-Saved`-ում։ Վճարումների տվյալների սպառողները պետք է գումարեն `X-OmniRoute-Response-Cost`-ը (քեշում գտնված արդյունքները ոչինչ չեն արժենում), իսկ քեշի վերլուծական համակարգերը կարող են համախմբել `X-OmniRoute-Cost-Saved`-ը։

## Բացառիկ կառավարվող աշխատաշրջանների վարձակալումներ

Բացառիկ կառավարվող աշխատաշրջանի վարձակալումը ընտրովի, հաճախորդից անկախ երթուղավորման պայմանագիր է․ մեկ ակտիվ սեփականատեր տիրապետում է մեկ համապատասխան OmniRoute կապի։ Այն չի վարձակալում մոդել, չի պահանջում OAuth, չի նույնականացնում որևէ կոնկրետ հաճախորդ և չի պահանջում որևէ կոնկրետ մատակարար։

Նույնականացման համար օգտագործվող API բանալին պետք է ունենա `lease:exclusive` տիրույթ և հստակ սահմանված ոչ դատարկ `allowedConnections` ցանկ։ Տվյալների բազայի փոփոխությունների սահմանը բանալու ստեղծման և մասնակի թարմացումների ժամանակ ապահովում է երկու դաշտերի համատեղ առկայությունը։

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Հաջող ձեռքբերման, երկարաձգման և ազատման պատասխանները տրամադրում են ժամանակային դրոշմանիշները, `state`-ը և ճշգրիտ դրական `generation`-ը, սակայն երբեք չեն բացահայտում ընտրված կապը կամ հավատարմագրերը։ Երկարաձգման և ազատման հարցումները generation-ը փոխանցում են JSON մարմնում․

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Ակտիվ վարձակալման սեփականատերը կարող է բացահայտորեն պահանջել գաղտնիությունը պահպանող ցուցադրման մետատվյալներ իր ընթացիկ կապակցման համար․

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Այս ընտրովի կարգավիճակի գործողությունը մեկ տվյալների բազայի գործարքի շրջանակում պաշտպանվում է անթափանց սեփականատիրոջ, նույնականացված կառավարվող API բանալու և ճշգրիտ ակտիվ generation-ի միջոցով։ `displayName`-ը միայն կարգավորված կապի՝ բացատներից մաքրված անունն է․ այն `null` է, երբ անվտանգ կարգավորված անուն գոյություն չունի։ OmniRoute-ը երբեք այն չի փոխարինում էլփոստի հասցեով կամ գեներացված հաշվի ինքնությամբ։ Մատակարարի արժեքը ոչ զգայուն ցուցադրման պիտակ է և երբեք չի հանդիսանում գեներացված համատեղելի մատակարարի նույնացուցիչ։ Հավատարմագրերը, թոքենները, cookie-ները, կապի կամ API բանալու չմշակված id-ները, սեփականատերերի հեշերը, սահմանազատման գաղտնիքները և ներքին երթուղավորման տվյալները բացառվում են։

Սխալ բանալիով, սխալ սեփականատիրոջով, հնացած generation-ով, բացակայող, ժամկետանց, ազատված և անվավեր ճանաչված որոնումները կապի մետատվյալներ չպարունակող նույն `409 LEASE_FENCE_STALE` սխալն են վերադարձնում։ Հզորության սպասման պատասխան ստացած հաճախորդը չունի ստուգման ենթակա ակտիվ կապակցում։ Երբ երթուղավորումը փոխում է ակտիվ վարձակալման կապը, նույն generation-ը շարունակում է վավեր մնալ, իսկ կարգավիճակը ատոմային կերպով վերադարձնում է նոր կապակցումը՝ երբեք չվերադարձնելով հինը։ Գոյություն ունեցող հաճախորդները մնում են անփոփոխ, քանի որ ձեռքբերման, երկարաձգման, ազատման և սպասման պատասխանները պահպանում են իրենց նախկին կառուցվածքները։

Սերվերի այս պայմանագիրը չի փոխում ստանդարտ OpenAI Codex `/status`-ը։ Ստանդարտ Codex-ը ներկայում հաղորդում է իր մոդելի մատակարարի և ներկառուցված նույնականացման/հաշվի վիճակի մասին, սակայն չի ցուցադրում կամայական հատուկ մատակարարի հաշվի մետատվյալներ․ հաճախորդի հետագա ինտեգրումը պետք է կանչի այս գործողությունը և որոշի, թե ինչպես ցուցադրել `connection.displayName`-ը։

Այնուհետև յուրաքանչյուր կառավարվող inference հարցում փոխանցում է կառավարման երկու վերնագրերը․

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Ճշգրիտ սեփականատերը, generation-ը, ակտիվ կապը և նույնականացված API բանալին ստուգվում ու սահմանազատվում են յուրաքանչյուր աջակցվող upstream փորձից անմիջապես առաջ։ Սեփականատիրոջ և generation-ի վերարտադրումն այլ բանալիով ձախողվում է, նույնիսկ երբ այդ բանալին թույլատրում է նույն կապը։ Սեփականատերերի չմշակված արժեքները չեն պահպանվում, չեն գրանցվում մատյաններում, չեն պահվում հարցման պատկերի մեջ և չեն փոխանցվում upstream-ին։

Ժամանակավոր մրցակցությունը վերադարձնում է HTTP `429`՝ `Retry-After`-ի և հետևյալի հետ․

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Այս պատասխանը նշանակում է միայն, որ սովորական համապատասխան բազմությունը դատարկ չէր, և յուրաքանչյուր ազատ թեկնածու զբաղեցված էր օտար ակտիվ վարձակալմամբ։ Չաջակցվող մոդելները/մատակարարները, քաղաքականության անհամապատասխանությունը, սպասման ժամանակահատվածը, քվոտան, առողջական վիճակը և համապատասխանության այլ սովորական ձախողումները պահպանում են OmniRoute-ի իրենց առկա պատասխանները։

### `x-omniroute-compression`

Սեղմման պլանի՝ ըստ հարցման վերասահմանում։ Ունի ամենաբարձր առաջնահերթությունը՝ գերակայում է երթուղավորման համադրության վերասահմանման, ակտիվ պրոֆիլի, ավտոմատ գործարկիչի և վահանակի լռելյայն կարգավորման նկատմամբ։ Արժեքները՝

| Արժեք         | Արդյունք                                                                                                          |
| ------------- | ----------------------------------------------------------------------------------------------------------------- |
| `off`         | Այս հարցման համար սեղմում չի կիրառվում։                                                                           |
| `default`     | Վահանակից ստացված լռելյայն պրոֆիլը (անտեսում է ակտիվ պրոֆիլը)։ Կորուստներով աշխատող շարժիչները մնում են անջատված։ |
| `safe`        | Միայն կրկնօրինակների հեռացում և բացատների միավորում։                                                              |
| `allow-lossy` | Պահպանում է օպերատորի պլանն այս հարցման համար՝ ներառյալ ամփոփումները և ոճի վերաշարադրումները։                     |
| `engine:<id>` | Միայն մեկ շարժիչ, երբ այն միացված է, օրինակ՝ `engine:rtk`։ Այդ շարժիչի՝ ըստ հարցման ընտրովի միացում։              |
| `<combo>`     | Անվանված համադրություն, որը նախ համեմատվում է անունով (առանց մեծատառ/փոքրատառ տարբերակման), ապա՝ id-ով։           |

Նշումներ․

- Անհայտ արժեքներն անտեսվում են (հարցումը երբեք չի մերժվում)․ լուծումը շարունակվում է ըստ օպերատորի սովորական առաջնահերթության։
- Եթե մի քանի համադրություններ ունեն նույն անունը, որոշակի համապատասխանության համար փոխանցեք համադրության **id**-ն։
- Համադրությունը, որի անունը `off` կամ `default` է, չի կարող ընտրվել անունով (այդ հիմնաբառերը մեկնաբանվում են առաջինը)․ նման համադրությանը հղվեք իր id-ով։
- Սեղմման գլխավոր անջատիչը պարտադիր սահմանափակում է․ երբ սեղմումը գլոբալ կերպով անջատված է, այս վերնագիրը չի կարող այն միացնել։

Կիրառված պլանը կրկնվում է պատասխանի վերնագրում․

```
X-OmniRoute-Compression: <mode>; source=<source>
```

որտեղ `<source>`-ը `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` կամ `off` արժեքներից մեկն է։

## Էմբեդինգներ

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Հասանելի մատակարարներ՝ Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI։

Կատալոգի ID-ներն ունեն `provider/model` ձևաչափը (օրինակ՝ `jina-ai/jina-embeddings-v5-omni-small`)։ Ռեեստրում առկա՝ առանց մատակարարի անվան Jina մոդելների ID-ները (օրինակ՝ `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) նույնպես ճանաչվում են։ Jina-ի embed/rerank/classify/segment գործառույթները նախ օգտագործում են կառավարման վահանակի `jina-ai` հավատարմագրերը․ `JINA_AI_API_KEY`-ը պահուստային տարբերակ է միայն այն դեպքում, երբ կառավարման վահանակում բանալի չկա։ `jina-reader` քարտը նախատեսված է միայն Reader / `r.jina.ai`-ի համար (`POST /v1/web/fetch`) և երբեք չի սպասարկում էմբեդինգների կամ վերադասակարգման հարցումներ։

Ռեեստրի այն մոդելները, որոնք հայտարարում են բազմամոդալ աջակցության մասին, նաև ընդունում են մատակարարից անկախ մինչև 32 կառուցվածքավորված
տարր։ Մեդիա տարրերի տեսակներն են `text`, `image`, `audio`, `video` և `document`։ Դրանց մեդիա `source`-ը
կամ `{"type":"url","url":"https://..."}` է, կամ
`{"type":"base64","data":"...","media_type":"..."}`։

Jina v5 Omni-ն (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`,
և ընտանիքի `jina-ai/jina-embeddings-v5-omni` → omni-small կեղծանունը) նաև ընդունում է Jina-ի բնիկ
EmbeddingsV5Request փաստաթղթերը և **անփոփոխ փոխանցում է դրանք** դեպի `https://api.jina.ai/v1/embeddings`․

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Բնիկ `{ image | audio | video | pdf }` արժեքները կարող են լինել հանրային HTTPS URL, `data:` URI կամ չմշակված
base64։ OmniRoute-ը չի վերածում այդ օբյեկտները տողերի և չի ներբեռնում բնիկ պատկերների URL-ները․ Jina-ն ինքն է ստանում
հանրային մեդիան։ Jina-ի լրացուցիչ դաշտերը (`task`, `normalized`, `truncate`, `embedding_type`) փոխանցվում են։
Միայն տեքստ աջակցող Jina SKU-ները շարունակում են մերժել ոչ տեքստային փաստաթղթերը։

Անվտանգության և փոխանցման սահմանափակումներ․

- Հեռակա մեդիայի URL-ները պետք է լինեն հանրային HTTPS հասցեներ։ Կանոնական `{type,source:url}` տարրերը ներբեռնվում են
  սերվերի կողմից (վերահղումների վերավավերացում, ժամանակի սահմանափակում, չափի սահմանափակումներ, հանրային DNS, կապի ամրագրում) և
  ներկցվում են մինչև մատակարարին հարցում ուղարկելը։ Jina-ի բնիկ `{image:"https://..."}` տարրերը նույն հանրային HTTPS ստուգումից
  հետո փոխանցվում են անփոփոխ․ URL-ը ներբեռնում է Jina-ն։
- Ներկցված base64 մեդիան սահմանափակված է յուրաքանչյուր տարրի համար մինչև 8 MiB վերծանված ծավալով և ամբողջ հարցման համար՝ մինչև 16 MiB վերծանված ծավալով։

Մատակարարին համապատասխան փոխակերպում (կանոնական տարրերը երբեք անփոփոխ չեն փոխանցվում)․

- Jina-ի բազմամոդալ մոդելներ․ վերին մակարդակի յուրաքանչյուր տարր դառնում է մոդալության բանալիով մեկ օբյեկտ
  (`text` / `image` / `audio` / `video` / `pdf`)՝ ներկցված մեդիայի համար օգտագործելով տվյալների URI-ներ․ վերին մակարդակի
  յուրաքանչյուր տարրի համար՝ մեկ վեկտոր։
- Gemini Embedding 2 ընտանիք․ վերին մակարդակի մեկ զանգվածը դառնում է մեկ բնիկ
  `models/{model}:embedContent` հարցում՝ `content.parts`-ով (`text` կամ `inline_data`)։
- llama.cpp (`llama-cpp/<model>`, տեղային սերվերի բեռնած ցանկացած մոդել)․ կանոնական `text` տարրերը
  դառնում են սովորական տողեր, իսկ `image` / `audio` / `video` տարրերից յուրաքանչյուրը դառնում է մեկ
  `{"content": [part]}` օբյեկտ՝ ներկցված տվյալների հետ օգտագործելով llama-server-ի զրույցի բովանդակության մասերը (`image_url`,
  `input_audio`՝ `wav` / `mp3` / `flac` ձևաչափով, `input_video`)․ վերին մակարդակի յուրաքանչյուր տարրի համար՝ մեկ վեկտոր։
  Սերվերը պետք է գործարկվի `--embedding --mmproj …`-ով․ առանց պրոյեկտորի այն ինքն է մերժում
  մեդիան։ `document`-ը չի աջակցվում։
- Առանց մոդալությունների հստակ մետատվյալների անհայտ/դինամիկ մոդելները մերժում են կառուցվածքավորված մուտքային տվյալները՝ վերադարձնելով HTTP 400։

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Մոդելի և մոդալության չաջակցվող համակցությունները տարրը հարկադրաբար փոխակերպելու փոխարեն վերադարձնում են HTTP 400։ Մուտքային տվյալներին չվերաբերող
ընդլայնման դաշտերը հին ձևաչափի տողային/թոքենային հարցումներում շարունակում են անփոփոխ փոխանցվել։

```bash
# Ցուցադրել էմբեդինգների բոլոր մոդելները
GET /v1/embeddings
```

## Պատկերների գեներացում

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Հասանելի մատակարարների թվում են OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (տեղային), ComfyUI (տեղային)։

`n`-ը վերադարձնում է `n` պատկեր `data[]`-ում։ Այն մատակարարների համար, որոնց վերադաս API-ն յուրաքանչյուր կանչի դեպքում վերադարձնում է մեկ պատկեր
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), կատարվում են `n` առանձին վերադաս կանչեր՝ միաժամանակ առավելագույնը 4-ը։ Ֆիքսված
`seed`-ը շեղվում է կանչի ինդեքսով (`seed`, `seed + 1`, …), որպեսզի պատկերները տարբերվեն, սակայն մնան
վերարտադրելի։ `n`-ի առավելագույն արժեքը 10 է։ Եթե կանչերից որևէ մեկը ձախողվի, ամբողջ հարցումը համարվում է
ձախողված։ Զուգահեռացված ձևաչափերի ցանկը `SINGLE_IMAGE_FANOUT_FORMATS`-ն է՝
`open-sse/handlers/imageGeneration/fanOut.ts`-ում։

ZenMux-ը կրկնակի օգտագործում է API բանալիով գոյություն ունեցող կապը և ընդունում է `zenmux/` կամ `zm/` նախածանցները․

- `zenmux/openai/gpt-image-2`-ն օգտագործում է ZenMux-ի OpenAI Images API-ն։ Ընտրանքները ներառում են `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` և `response_format`։
- Այլ հրատարակիչները, օրինակ՝ `zm/meta/muse-image-1.0`, օգտագործում են ZenMux-ի Vertex AI `:predict`
  վերջնակետը։ `n`-ը համապատասխանեցվում է `sampleCount`-ին, `aspect_ratio`-ն՝ `aspectRatio`-ին, իսկ `image_size`-ը
  (`1K`, `2K`, `4K`)՝ `sampleImageSize`-ին։ Պիքսելներով տրված `size`-ը տրամադրում է միայն կողմերի հարաբերակցություն,
  այլ ոչ թե երաշխավորված պիքսելային չափեր։ Աջակցվող հարաբերակցությունները, լուծաչափերը և քանակները տարբերվում են՝ կախված մոդելից։
- `zm/inclusionai/ming-image-0.1-design`-ն ինքն է ընտրում իր չափերը։ Բաց թողեք `size`,
  `aspect_ratio` և `image_size` պարամետրերը․ բացահայտ արժեքները վերադարձնում են HTTP 400։ PNG, JPEG և WebP
  ձևաչափերը կարելի է պահանջել `output_format`-ի միջոցով։

Այս ինտեգրումն աջակցում է տեքստից պատկերի գեներացմանը, այլ ոչ թե հղումային պատկերի խմբագրմանը։ Vertex-ի
ելքը նորմալացվում է որպես `data[].b64_json`, իսկ `response_format: "url"`-ը վերադարձնում է վերադաս
HTTPS URL կամ base64 տվյալների URL, երբ հասանելի են միայն պատկերի բայթերը։ Դատարկ կամ զտված ելքերը
դատարկ հաջող պատասխանի փոխարեն վերադարձնում են սխալ։ Մոդելների հասանելիությունը կախված է ZenMux հաշվից։
Տե՛ս [ZenMux-ի Vertex API-ն](https://docs.zenmux.ai/api/vertexai/generate-images) և
[OpenAI Images API-ն](https://docs.zenmux.ai/api/openai/generate-an-image)։

```bash
# Թվարկել պատկերների բոլոր մոդելները
GET /v1/images/generations
```

## Փաստաթղթերի OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model`-ը ընտրում է OCR մատակարարին `provider/model` նախածանցի միջոցով․ առանց նախածանցի մոդելի նույնացուցիչը (օրինակ՝
`mistral-ocr-latest`) համապատասխանեցվում է իր գրանցված մատակարարին, իսկ `model`-ը բաց թողնելու դեպքում լռելյայն
օգտագործվում է Mistral-ը (`mistral-ocr-latest`)։ Գրանցված մատակարարները (`open-sse/config/ocrRegistry.ts`)․

| Մատակարարի նույնացուցիչը      | Մոդելի նույնացուցիչը | `model`-ի արժեքը                                                         | Նշումներ                                                                                                                 |
| ----------------------------- | -------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (կամ առանց նախածանցի՝ `mistral-ocr-latest`) | Սինխրոն․ պատասխանը վերադարձվում է անմիջապես մեկ վերադաս կանչից։                                                          |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                              | Ասինխրոն վերադաս ծառայություն (`analyze` + պարբերական ստուգում)․ տե՛ս ստորև։                                             |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                                  | Սինխրոն՝ Vertex AI-ի `openapi/chat/completions` գործընկերային վերջնակետի միջոցով․ նույնականացման/URL-ի համար տե՛ս ստորև։ |

Բոլոր երեք մատակարարները պատասխանում են Mistral-ի ձևաչափով նույն մարմնով․

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence-ի պարբերական ստուգման ընթացքը

Azure Document Intelligence-ի `analyze` API-ն ասինխրոն է․ սկզբնական հարցումը մարմնի փոխարեն վերադարձնում է
`Operation-Location` վերնագիր, և արդյունքը պետք է պարբերաբար ստուգվի։ Մշակիչը
(`open-sse/handlers/ocr.ts`) այդ URL-ը ստուգում է յուրաքանչյուր վայրկյանը մեկ՝ առավելագույնը 30 փորձով, անմիջապես ձախողվում է (չի
շարունակում ստուգումները) ոչ `ok` ստուգման պատասխանի կամ `"failed"` կարգավիճակի դեպքում և վերադարձնում է `504`, եթե
փորձերի թույլատրելի քանակը սպառելուց հետո գործողությունը դեռ կատարվում է։ Azure-ի վերջնական պատասխանը
կանչողին վերադարձվելուց առաջ նորմալացվում է Mistral-ի կողմից օգտագործվող նույն `pages`/`markdown` ձևաչափին,
ուստի հաճախորդի կոդում մատակարարի համար հատուկ մշակում անհրաժեշտ չէ։

### Vertex AI DeepSeek OCR-ի նույնականացում և վերջնակետի որոշում

`vertex-deepseek-ocr`-ը կրկնակի օգտագործում է Vertex AI-ի նույնականացման նույն մեխանիզմը, որն OmniRoute-ն արդեն աջակցում է
չաթի/պատկերների տրաֆիկի համար (`open-sse/executors/vertex.ts`)․ կապի API բանալին կա՛մ
Service Account JSON հավատարմագիր է (որը JWT-bearer
հոսքի միջոցով փոխանակվում է կարճաժամկետ OAuth հասանելիության տոկենի հետ), կա՛մ արդեն ստեղծված OAuth հասանելիության տոկեն, որն օգտագործվում է առանց փոփոխության։ Վերադաս վերջնակետի URL-ը Vertex-ի
ընդհանուր `openapi/chat/completions` գործընկերային վերջնակետն է, որը կառուցվում է կապի նախագծի և
տարածաշրջանի հիման վրա․ բացահայտ `providerSpecificData.project`/`providerSpecificData.region` արժեքները միշտ գերակայում են,
հակառակ դեպքում նախագիծը ստացվում է Service Account JSON-ի `project_id`-ից, իսկ տարածաշրջանի
լռելյայն արժեքը `us-central1` է։ Երկու արժեքներն էլ որոշվում են `open-sse/handlers/ocr.ts`-ում
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) և օգտագործվում են
`src/app/api/v1/ocr/route.ts`-ի կողմից՝ նախքան հարցումը `handleOcr`-ին փոխանցելը։

### Մոդելի id-ի նախածանցները (`?prefix=`)

Մոդելների մեծ մասը ներկայացվում է **մատակարարի նախածանցով**։ Օգտագործվող նախածանցը կառավարվում է
`MODELS_CATALOG_PREFIX_MODE` ֆունկցիոնալության դրոշակով և կարող է վերագրվել **յուրաքանչյուր հարցման համար**
հարցման պարամետրի միջոցով. սա օգտակար է այն հաճախորդի համար, որը ցանկանում է մաքուր ցանկ ստանալ՝ առանց բոլորի
համար սերվերի ընդհանուր կարգավորումը փոխելու.

```bash
GET /v1/models?prefix=alias        # մեկ id յուրաքանչյուր մոդելի համար՝ կարճ այլանվան նախածանցով
GET /v1/models?prefix=dual         # երկու ձևերն էլ (սերվերի լռելյայն տարբերակը)
GET /v1/models?prefix=canonical    # միայն մատակարարի ամբողջական id-ի նախածանցը
```

| Ռեժիմ       | Արտածում է                                              | Նշումներ                                                                                                                                                                                                                    |
| ----------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **և** `claude/claude-sonnet-4-6` | **Լռելյայն։** Երկու id-ներն էլ ուղղորդվում են դեպի նույն մոդելը. պահպանվել են, որպեսզի որևէ ձևը կոշտ կոդավորած հաճախորդների կազմաձևումները շարունակեն աշխատել։ Մոտավորապես կրկնապատկում է կատալոգը։                         |
| `alias`     | `cc/claude-sonnet-4-6`                                  | Մեկ գրառում յուրաքանչյուր մոդելի համար։ Առանձին այլանուն չունեցող մատակարարները նույնպես արտածում են իրենց գրառումը, ուստի ոչինչ չի կորչում։                                                                                |
| `canonical` | `claude/claude-sonnet-4-6`                              | Մեկ գրառում յուրաքանչյուր մոդելի համար՝ մատակարարի ամբողջական id-ի նախածանցով։ Առանձին այլանուն չունեցող մատակարարները (օր.՝ `antigravity/…`, `agy/…`) այստեղ նույնպես արտածում են իրենց միակ id-ն, ուստի ոչինչ չի կորչում։ |

`dual` ռեժիմով հայելին կարող է ճանաչվել նաև առանց հարցման պարամետրի. այն ունի `parent`
դաշտ, որը մատնանշում է հիմնական id-ն։

Մոդելի ընտրիչ ցուցադրող հաճախորդները պետք է հարցում ուղարկեն `?prefix=alias` պարամետրով. հենց այդպես է վարվում
[OmniCopilot VS Code ընդլայնումը](../guides/VSCODE-COPILOT.md)։

### Հայտնաբերման զտիչներ (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models`-ն ընդունում է ըստ ցանկության միացվող հայտնաբերման զտիչներ։ Առանց դրանց պատասխանը
չի փոխվում։ Դրանք նեղացնում են զանգահարողին արդեն հասանելի կատալոգը (նախ կիրառվում են API բանալու թույլտվությունները)
և գործարկվում են OpenAI ոճի `limit` / `after` էջավորման առաջ.

```bash
GET /v1/models?capability=vision&capability=tool_calling   # թվարկված յուրաքանչյուր հնարավորությունը պետք է ճիշտ լինի
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # կատալոգի `type`; այն չունեցող տողերը համարվում են `chat`
GET /v1/models?q=sonnet&limit=10                           # id-ի կամ անվան համընկնում՝ առանց տառաչափը հաշվի առնելու
```

| Պարամետր      | Արժեքներ                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | ոչ բացասական ամբողջ թիվ, որը համեմատվում է `context_length`-ի հետ                                   |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 նիշ                                                                                           |

Անհայտ արժեքը կամ ոչ բացասական ամբողջ թիվ չհանդիսացող `min_context`-ը (օրինակ՝ `1.5`)
վերադարձնում է HTTP `400`, իսկ հաղորդագրությունը թվարկում է թույլատրելի արժեքները։ Իրականացումը՝
`src/app/api/v1/models/catalogFilters.ts`։

### Մոդելների կարճ ցանկ (`POST /v1/models/query`)

`POST /v1/models/query`-ը նույն կատալոգից վերադարձնում է կարճ, կանխորոշված ցանկ՝ նույն
նույնականացմամբ և յուրաքանչյուր բանալու համար նույն տեսանելիությամբ, ինչ `GET /v1/models`-ը.

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...մոդելներ ] }
```

Յուրաքանչյուր դաշտ կամընտիր է։ `capabilities`-ը և `exclude`-ը կարող են ընդունել զանգված կամ ստորակետերով բաժանված տող.
`max_output`-ը համեմատվում է `max_output_tokens`-ի հետ։ Արդյունքները դասավորվում են նախ ըստ `owned_by`-ի, ապա՝ `id`-ի։
`limit`-ի լռելյայն արժեքը `20` է, իսկ `100`-ից մեծ արժեքները սահմանափակվում են `100`-ով։ Անվավեր JSON-ը, անհայտ
դաշտը կամ անվավեր արժեքը վերադարձնում են HTTP `400`։

### Առանձին թաքցված զրույցի մոդելներ

Մատակարարի էջում **Թաքցված** նշված մոդելը բացառվում է կատալոգից և բացահայտորեն
հարցվելիս մերժվում է HTTP `404` / `model_not_found` պատասխանով։ Ստուգումն օգտագործում է որոշված
մատակարարն ու մոդելը՝ ներառյալ մատակարարների այլանունները, համատեղելի մատակարարների հանգույցների նախածանցները և
կապի լռելյայն արժեքները։ Համակցությունը բաց է թողնում թաքցված թիրախները և կարող է օգտագործել տեսանելի հարակից տարբերակ.
եթե գործարկելի որևէ թիրախ չի մնում, այն վերադարձնում է նույն սխալի կոդը։ Թաքցումը հանելը ուժի մեջ է մտնում հաջորդ
հարցման ժամանակ։ Միայն պատկերների տեսանելիության վերագրումները չեն թաքցնում նույն ID-ն ունեցող զրույցի մոդելը։

Մոդելի այս անհատական կարգավորումն առանձին է
[մոդելների ցուցադրման թույլատրման/արգելման ցանկերից](../routing/MODEL_EXPOSURE_LIST.md), որոնք զտում են կատալոգում
ներկայացումն ու ավտոմատ ուղղորդման թեկնածուները՝ միաժամանակ պահպանելով բացահայտ ուղարկումը։ API բանալու՝ մոդելների
համար թույլտվությունները շարունակում են կիրառվել անկախ կերպով։ Կատալոգի նախածանցի լռելյայն ռեժիմը մնում է `dual`։

### Առանց մտածողության մոդելների տարբերակներ

Մտածողություն աջակցող Claude մոդելների համար `/v1/models`-ը նաև ներկայացնում է **առանց մտածողության** տարբերակ, որի id-ն սկսվում է `claude-3-omniroute-no-thinking/` նախածանցով.

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Այս id-ի ընտրությունը (օրինակ՝ Claude Code-ի կազմաձևում, որը միշտ կցում է `thinking` բլոկ) վերահասցեավորվում է իրական `<provider>/<model>`-ին՝ անջատված տրամաբանմամբ՝ `thinking:{type:"disabled"}`՝ `/v1/messages` ուղու դեպքում, կամ հեռացված `reasoning`/`reasoning_effort` դաշտերով՝ `/v1/chat/completions` ուղու դեպքում։ Տարբերակը ցուցակվում է միայն Claude ընտանիքի այն մոդելների համար, որոնք աջակցում են մտածողությանը **և** ընդունում են `disabled` արժեքը (ուստի, օրինակ, միայն հարմարվողական ռեժիմով աշխատող և `disabled` արժեքը մերժող մոդելները բացառվում են)։ Օպերատորները կարող են յուրաքանչյուր մոդելի համար հարկադրաբար միացնել կամ անջատել այս տարբերակը՝ օգտագործելով `ModelSpec.noThinkingAlias`։

## Պրովայդերի փլագինի մանիֆեստ

```bash
GET /api/v1/provider-plugin-manifest
```

Վերադարձնում է JSON-ի համար անվտանգ պրովայդերի փլագինի մանիֆեստը, որն օգտագործվում է Bifrost-ի, CLIProxyAPI-ի և
ապագա sidecar երթուղիչների կողմից։ Պատասխանը ստեղծվում է TypeScript-ի պրովայդերների
ռեեստրից և միտումնավոր չի ներառում OAuth հաճախորդի գաղտնիքները, կատարման միջավայրի
որոշումը, կատարող ֆունկցիաները, հարցման վերնագրերը և հաշվի տվյալները։

Օգտագործեք այս վերջնակետը, երբ sidecar-ը գործարկվում է գործընթացից դուրս և չի կարող անմիջապես ներմուծել
`open-sse/config/providerPluginManifestRegistry.ts`։

## ElevenLabs աուդիոյի ստեղծում

OmniRoute-ում կազմաձևեք `elevenlabs` պրովայդերի միացում՝ ձեր ElevenLabs API բանալիով։
Հաճախորդները նույնականացվում են իրենց **OmniRoute** բանալիով (`Authorization: Bearer $OMNIROUTE_API_KEY`);
դարպասը պահպանված պրովայդերի բանալին փոխանցում է որպես `xi-api-key`։ Երբեք ElevenLabs-ի բանալին
մի ուղարկեք որպես դարպասի bearer թոքեն։

| Մեթոդ | Ուղի                        | Պատասխան                                     | API բանալու վերջնակետի կատեգորիա |
| ----- | --------------------------- | -------------------------------------------- | -------------------------------- |
| POST  | `/v1/sound-generation`      | Բնօրինակ աուդիո բայթեր                       | `elevenlabs`                     |
| POST  | `/v1/music`                 | Բնօրինակ աուդիո բայթեր                       | `music`                          |
| POST  | `/v1/music/stream`          | Հոսքային աուդիո բայթեր                       | `music`                          |
| POST  | `/v1/music/detailed`        | Բնօրինակ բազմամաս աուդիո և կոմպոզիցիայի պլան | `music`                          |
| POST  | `/v1/music/detailed/stream` | Բնօրինակ SSE մետատվյալներ և աուդիո հատվածներ | `music`                          |
| POST  | `/v1/music/plan`            | JSON կոմպոզիցիայի պլան                       | `music`                          |

Այս վերջնակետերը լրացնում են գոյություն ունեցող `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` և `/v1/speech-to-text` երթուղիները։ Բնօրինակ JSON դաշտերը
և հարցման պարամետրերը, ինչպիսիք են `output_format` և `enable_logging`, պահպանվում են։
`/v1/music/detailed` պատասխանները պահպանում են իրենց բազմամաս սահմանազատիչները․ վերլուծեք դրանք որպես multipart։
`/v1/music/detailed/stream`-ը վերադարձնում է `text/event-stream`՝ կոմպոզիցիայի մետատվյալներով և
base64 աուդիո հատվածներով SSE իրադարձություններում։ Բոլոր վեց երթուղիներն աջակցում են CORS-ի նախնական հարցմանը։

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Կարճ ձայնային էֆեկտ։ Տևողությունը՝ 0.5-ից մինչև 30 վայրկյան։
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Երաժշտության տևողությունն արտահայտվում է միլիվայրկյաններով՝ 3000-ից մինչև 600000։
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Աուդիոյի աստիճանական առաքման համար օգտագործեք `/v1/music/stream`՝ նույն JSON մարմնով։ Կոմպոզիցիան
ընդունում է `prompt`-ից կամ `composition_plan`-ից ճշգրիտ մեկը․ `/v1/music/plan`-ը պահանջում է `prompt`
և ընտրովի ընդունում է `source_composition_plan`։ Բնօրինակ սխեմաները պահպանում են պրովայդերի լրացուցիչ
դաշտերը, որպեսզի կոմպոզիցիայի պլանի տարբերակները և ճշգրտման ընտրանքները հասնեն ElevenLabs-ին։

Միասնական `/v1/music/generations` վերջնակետը նույնպես ընդունում է `elevenlabs/music_v1`,
`elevenlabs/music_v2` և `elevenlabs/music_v2_5`։ ElevenLabs-ի ակտիվ միացման դեպքում
այս մոդելները հասանելի են երաժշտության կատալոգում։ Այս վերջնակետը վերադարձնում է
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`։ Դրա `duration` դաշտը չափվում է
վայրկյաններով և համապատասխանեցվում է `music_length_ms`-ին․ հստակ նշված `music_length_ms`-ն ունի գերակայություն։
`instrumental`-ը համապատասխանեցվում է `force_instrumental`-ին՝ բնօրինակ դաշտի գերակայությամբ։
Հոսքային փոխանցման համար օգտագործեք բնօրինակ հոսքային վերջնակետերը, իսկ միայն կոմպոզիցիայի պլանի վրա
հիմնված հարցումների համար՝ բնօրինակ կոմպոզիցիայի վերջնակետը։

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Վերջնակետի, մոդելի, բյուջեի և միացման սահմանափակումները կիրառվում են նախքան վերին հոսքի կանչը։ Բնօրինակ
երթուղիները վերադարձնում են վերին հոսքի կարգավիճակի կոդերն ու սխալի մարմիններն առանց փոփոխության՝ ներառյալ `402`-ը պլանի
սահմանափակման և `429`-ը քվոտայի սահմանաչափի համար։ `character-cost`, `song-id`, `request-id` և `retry-after`
վերնագրերը պահպանվում են առկայության դեպքում։ Անվճար վարկային մնացորդը չի երաշխավորում հասանելիություն յուրաքանչյուր
երաժշտական մոդելի, ելքային ձևաչափի կամ API գործառույթի նկատմամբ․ ElevenLabs-ը որոշում է յուրաքանչյուր հարցման հասանելիության իրավունքը։
Միասնական վերջնակետը պահպանում է սխալի կարգավիճակի կոդերը OmniRoute-ի նորմալացված սխալի ծրարում։

Վերին հոսքի պայմանագրեր՝ [ձայնային էֆեկտներ](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[երաժշտության կոմպոզիցիա](https://elevenlabs.io/docs/api-reference/music/compose) և
[հոսքային երաժշտության մանրամասներ](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)։

Այն հաճախորդների համար, որոնք չեն կարող կցել `Authorization: Bearer ...`, OmniRoute-ը նաև ընդունում է API բանալիներ URL-ում՝ կա՛մ հարցման տողի համատեղելիության միջոցով (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`), կա՛մ ստորև փաստաթղթավորված հատուկ `/api/v1/vscode/{token}/...` վերջնակետերի միջոցով։

```bash
# Վերադասակարգում (ամպային ռեեստրի մատակարար կամ OpenAI-ի հետ համատեղելի մատակարարի հանգույց՝ որպես "<prefix>/<model>")
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina դասակարգում (Foundation API-ի հավատարմագրեր)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina հատվածավորիչ
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina որոնում (s.jina.ai; մատակարարի այլանուններ՝ jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# Մոդերացիա
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — վերադարձնում է audio/mpeg (կամ պահանջված ձևաչափի) մարմին
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS-ը պահանջում է լեզու և ձայն․ `language`-ի լռելյայն արժեքը "en" է, իսկ բացակայող
# ձայնը կամ OpenAI-ի ստանդարտ ձայնի անունը (alloy, nova, …) փոխարինվում է "Adrian"-ով
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# Պատկերի խմբագրում (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# Տեսանյութի / երաժշտության ստեղծում (մատակարարի նախածանցով մոդելի id)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **Վերադասակարգման մատակարարի հանգույցներ․** `POST /v1/rerank` հարցումները նաև ուղղորդվում են OpenAI-ի հետ համատեղելի մատակարարի հանգույցներ
> (oMLX, vLLM, Infinity, դարպասի հետևում գտնվող TEI, …), որոնք հասցեագրվում են որպես `<node-prefix>/<model>`։ Հետադարձ կապի
> հանգույցները (`localhost`, `127.0.0.1`, `172.16.0.0/12`) միշտ թույլատրելի են, ինչպես նաև այն հոսթանունները, որոնք
> օպերատորը նշում է `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`-ում (օրինակ՝ Docker/Compose ծառայության անունը, ինչպիսին է
> `http://reranker:8080/v1`; դրանց դիմում են անմիջապես՝ երբեք չօգտագործելով `HTTP(S)_PROXY` կամ
> միացմանը ամրակցված պրոքսին)։ Ցանկացած այլ
> հոսթի հանգույցներ՝ LAN-ի համակարգիչ կամ Tailscale-ի հանգույց, թույլատրելի են միայն այն դեպքում, երբ օպերատորը միացնում է
> `RERANK_REMOTE_PROVIDER_NODES` գործառույթի դրոշակը, **և** հանգույցի բազային URL-ն անցնում է մատակարարի
> ելքային URL-ների քաղաքականության ստուգումը (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`)։
> Հիշողության շարժիչի վերադասակարգման քայլն այս երթուղին կանչում է
> հետադարձ կապի միջոցով, ուստի նույն կանոնը կարգավորում է Հիշողության կարգավորումներում առկա `rerankProviderModel`-ը։
>
> **Տեղային սերվերի ձևաչափեր․** հանգույցը կանչվում է `<base>/v1/rerank` հասցեով, իսկ 404-ի դեպքում՝ `<base>/rerank`
> հասցեով (Infinity, TEI)։ Վերին մակարդակ ուղարկվող մարմինը պարունակում է թե՛ Cohere/OpenAI-ի գրելաձևը (`documents`,
> `return_documents`), թե՛ TEI-ի գրելաձևը (`texts`, `return_text`), իսկ վերին մակարդակից ստացվող պատասխանը
> նորմալացվում է Cohere-ի փաթեթավորման ձևաչափին․ TEI-ի պարզ `[{index, score, text}]`-ը, թեթև դարպասներից ստացվող `{results: [{index, score}]}`
> ձևաչափը և Voyage-ի ոճով `{data: [...]}` ձևաչափը հաճախորդին վերադարձվում են
> `{results: [{index, relevance_score, document?}]}` տեսքով՝ դասավորված ըստ գնահատականի և սահմանափակված `top_n`-ով։

> **Մատակարարի հանգույցների հայտնաբերում․** OpenAI-ի հետ համատեղելի մատակարարի հանգույցի մոդելները հայտնվում են `GET /v1/models`-ում՝
> հանգույցի նախածանցի ներքո։ Վերջնակետի մետատվյալներ չունեցող տողերը (ինչը բնորոշ է տեղային `/v1/models` ցանկերին)
> ժառանգում են հանգույցի `apiType`-ը, ուստի `embeddings` հանգույցի մոդելներն ունեն `type: "embedding"`, իսկ
> `rerank` հանգույցի մոդելները՝ `type: "rerank"`՝ լռելյայն չդառնալով զրույցի մոդելներ․ համաժամացված կամ ձեռքով ավելացված տողում բացահայտորեն նշված
> `supportedEndpoints`-ը շարունակում է ունենալ առաջնահերթություն։

### Մատակարարին նվիրված երթուղիներ

```bash
POST /v1/providers/{provider}/chat/completions
POST /v1/providers/{provider}/embeddings
POST /v1/providers/{provider}/images/generations
```

Մատակարարի նախածանցը դրա բացակայության դեպքում ավելացվում է ինքնաբերաբար։ Չհամապատասխանող մոդելները վերադարձնում են `400`։

## Ֆայլերի API

OpenAI-ի հետ համատեղելի ֆայլերի վերջնակետ՝ փաթեթային մուտքային/ելքային տվյալների և ըստ նպատակի ֆայլերի վերբեռնումների համար։

| Մեթոդ  | Ուղի                     | Նկարագրություն                                                                                                          |
| ------ | ------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/files`              | Վերբեռնել ֆայլ (բազմամաս՝ `file`, `purpose`, `expires_after[anchor]`, `expires_after[seconds]`) — առավելագույնը 512 MiB |
| GET    | `/v1/files`              | Ցուցակել նույնականացված API բանալիին պատկանող ֆայլերը                                                                   |
| GET    | `/v1/files/[id]`         | Ստանալ ֆայլի մետատվյալները                                                                                              |
| DELETE | `/v1/files/[id]`         | Ջնջել ֆայլը                                                                                                             |
| GET    | `/v1/files/[id]/content` | Հոսքային եղանակով վերադարձնել ֆայլի չմշակված բովանդակությունը                                                           |

**Նույնականացում․** Bearer API բանալի․ ֆայլերի տեսանելիության շրջանակը սահմանվում է ըստ API բանալու՝ `getApiKeyRequestScope`-ի միջոցով։ Բանալին
տեսնում, ներբեռնում և ջնջում է միայն իրեն պատկանող ֆայլերը․ առանց բանալու կառավարման վահանակի աշխատաշրջանը կարդում է
ամբողջ օրինակը․ սեփականատեր չունեցող ֆայլի (անանուն կամ կառավարման վահանակի աշխատաշրջանից վերբեռնված) հասանելիությունը մերժվում է բոլոր
ոչ աշխատաշրջանային կանչողների համար։ `GET /v1/files`-ն անանուն կանչողին, ինչպես նաև տրամադրված, բայց
չճանաչված բանալիով կանչողին պատասխանում է `401`-ով, նույնիսկ երբ `REQUIRE_API_KEY=false`, այլ ոչ թե ցուցակում է բոլոր վարձակալների
ֆայլերը (GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523)։

## Փաթեթների API

OpenAI-ի հետ համատեղելի փաթեթային մշակում։

| Մեթոդ  | Ուղի                      | Նկարագրություն                                                                                                   |
| ------ | ------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/batches`             | Ստեղծել փաթեթ․ մարմինը վավերացվում է `v1BatchCreateSchema`-ով (`input_file_id`, `endpoint`, `completion_window`) |
| GET    | `/v1/batches`             | Ցուցակել փաթեթները                                                                                               |
| GET    | `/v1/batches/[id]`        | Ստանալ փաթեթի կարգավիճակը և `request_counts`-ը                                                                   |
| DELETE | `/v1/batches/[id]`        | Ջնջել ավարտված/ձախողված փաթեթը                                                                                   |
| POST   | `/v1/batches/[id]/cancel` | Չեղարկել ընթացքի մեջ գտնվող փաթեթը                                                                               |

**Նույնականացում․** Bearer API բանալի։ Փաթեթների տեսանելիության շրջանակը սահմանվում է ըստ API բանալու՝ նույն եռակողմ կանոնով, ինչ
ֆայլերի դեպքում․ միայն սեփական բանալի, կառավարման վահանակի աշխատաշրջանի համար՝ ամբողջ օրինակը, իսկ առանց սեփականատիրոջ գրառումների հասանելիությունը մերժվում է բոլոր
ոչ աշխատաշրջանային կանչողների համար (ստացում, ջնջում, չեղարկում և ստեղծելիս `input_file_id`-ի ստուգում)։
`GET /v1/batches`-ն անանուն կանչողին պատասխանում է `401`-ով, նույնիսկ երբ `REQUIRE_API_KEY=false`։

## Որոնման API

Վեբ/որոնման մատակարարների աբստրակցիա (Tavily, Brave, Exa, Serper և այլն)։

| Մեթոդ | Ուղի                   | Նկարագրություն                                                                                           |
| ----- | ---------------------- | -------------------------------------------------------------------------------------------------------- |
| GET   | `/v1/search`           | Կազմաձևված որոնման մատակարարների և հնարավորությունների ցանկ                                              |
| POST  | `/v1/search`           | Կատարում է որոնման հարցում․ մարմինը վավերացվում է `v1SearchSchema`-ով, աջակցում է քեշավորմանը/միավորմանը |
| GET   | `/v1/search/analytics` | Յուրաքանչյուր մատակարարի համար արդյունքների/հապաղման/քեշի վիճակագրություն                                |

**Նույնականացում․** Bearer API բանալի (`extractApiKey` + `isValidApiKey`)։ Որոնման քաղաքականությունը կիրառվում է `enforceApiKeyPolicy`-ի միջոցով։

### Exa-ի և Tavily-ի `provider_options`

Exa-ն և Tavily-ն մատակարարին հատուկ դաշտերը կարդում են անվանատարածքով փաթեթից՝
`provider_options.exa` (կամ `provider_options["exa-search"]`) և `provider_options.tavily`
(կամ `provider_options["tavily-search"]`)։ Փոխանցվում են միայն ստորև նշված բանալիները։ Յուրաքանչյուրը
ստուգվում է իր սեփական Zod սխեմայով՝ `open-sse/handlers/search/providerOptionsPassthrough.ts`-ում,
իսկ սխալ տիպով բանալին հեռացվում է։ Ցանկացած այլ բանալի անտեսվում է՝ ներառյալ նույնականացումը, բազային URL-ը,
`stream`-ը և `outputSchema`-ն։ Այլ մատակարարների կողմից օգտագործվող հարթ բանալիները (`cx`, `depth`, ...) աշխատում են
ինչպես նախկինում։

| Մատակարար | Վերին մակարդակի դաշտեր                                                                                                                                                                                                                                                                                                                                                    | Ներդրված                                                                                                                                                            |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa       | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (հարթ պարզունակ արժեքներ), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                      | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}`՝ միավորված լռելյայն `{ text: true, highlights: true }`-ի հետ |
| Tavily    | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                   |

Ընդհանուր դաշտերը միշտ գերակայում են՝ `query`, `max_results`, `filters` (տիրույթներ), `country` և
`search_type`-ից ստացված թեման։ Exa-ում `search_type: "news"`-ը պահպանում է `category: "news"`-ը։
Tavily-ն նաև ընդունում է `search_type: "finance"` (`topic: "finance"`)։

Ընդհանուր `time_range`-ն այժմ հասնում է երկու մատակարարներին էլ․ Exa-ն ստանում է `startPublishedDate` (ISO
ժամանակային դրոշմ), իսկ Tavily-ն՝ `start_date` (`YYYY-MM-DD`)։ `provider_options`-ում բացահայտորեն նշված ամսաթիվը
գերակայում է փոխակերպված արժեքի նկատմամբ։

Exa-ի արդյունքները `provider_raw`-ում պահպանում են `id`, `highlight_scores`, `summary`, `subpages`, `entities` և `extras`
դաշտերը։ Tavily-ի արդյունքները պահպանում են `images` և `favicon` դաշտերը։

Ծախսերի հաշվառումը դեռևս հարթ `costPerQuery` ռեեստրն է։ Tavily-ն
`search_depth: "advanced"`-ի դեպքում յուրաքանչյուր կանչի համար ավելի շատ կրեդիտ է գանձում, և այդ տարբերությունը չի արտացոլվում
`usage.search_cost_usd`-ում։

## Web Fetch API

Կորզեք բովանդակությունը URL-ից՝ կազմաձևված web-fetch մատակարարի միջոցով (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract)։

Parallel Extract-ը (`parallel-search`, նույն API բանալին, ինչ Parallel Search-ի համար) վերադարձնում է միայն
Markdown․ ցանկացած այլ `format` հանգեցնում է `400` պատասխանի, իսկ բովանդակությունը սահմանափակվում է 100,000 նիշով։ Երբ
թիրախային էջն ինքնին հնարավոր չէ կորզել, վերին հոսքի ծառայությունն այդ մասին հաղորդում է HTTP 200 պատասխանի ներսում․
OmniRoute-ը դա ներկայացնում է որպես `422`՝ հաստատուն հաղորդագրությամբ։

| Մեթոդ | Ուղի            | Նկարագրություն                                                  |
| ----- | --------------- | --------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | Ստանալ/քերել URL-ը․ մարմինը վավերացվում է `v1WebFetchSchema`-ով |

**Նույնականացում․** Bearer API բանալի (`extractApiKey` + `isValidApiKey`)։ Քաղաքականությունը կիրառվում է `enforceApiKeyPolicy`-ի միջոցով։

**Քվոտան հաշվի առնող պահուստային անցում (#8297)․** երբ հստակ `provider` նշված չէ, խմբում
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) անցումը կատարվում է հաստատուն
առաջնահերթության հերթականությամբ (առաջինը լրացնելու սկզբունքով)․ հաճախականության սահմանափակման հասած, բայց կազմաձևված մատակարարը բաց է թողնվում՝
հարցումը անմիջապես ընդհատելու փոխարեն, իսկ վերին հոսքի կրկնելի/քվոտային ձախողման դեպքում
(HTTP 429՝ միշտ, 402/403՝ Firecrawl/Tavily/TinyFish քվոտային տիպի անվճար մակարդակների համար,
բայց ոչ Jina Reader-ի համար և երբեք ոչ սովորական 400 սխալ հարցման դեպքում) հարցման կատարման պահին անցում է կատարվում
հաջորդ՝ դեռ չփորձված և հավատարմագրեր ունեցող մատակարարին։ Երբ խմբի բոլոր մատակարարների
հնարավորությունները սպառված են, վերջնակետը նախկին ընդհանուր `400`-ի փոխարեն վերադարձնում է մեկ `429`
(`Retry-After` վերնագրով)։ Երբ հստակ `provider` է
պահանջվում, աննկատ պահուստային անցում **չկա**․ հաճախականության սահմանափակման հասած կամ ձախողված՝ հստակ նշված
մատակարարի սեփական սխալն է վերադարձվում (`429`, եթե հաճախականությունը սահմանափակված է, այլապես՝ վերին հոսքի
կարգավիճակը)։

## WebSocket հոսքային փոխանցում

```bash
GET /v1/ws?handshake=1
```

Վավերացնում է WebSocket-ի արդիականացման ձեռքսեղմումը և վերադարձնում է լարային արձանագրության հաղորդագրությունների օրինակները (`request`, `cancel`)։ Իրական WS կադրերը մշակվում են ներկառուցված WS սերվերի կողմից՝ Next.js-ի երթուղիների աղյուսակից դուրս։

**Նույնականացում․** Bearer API բանալի՝ ձեռքսեղմման ընթացքում։

### Responses API-ն WebSocket-ի միջոցով (միայն codex)

```bash
# Նույն host:port-ը, ինչ HTTP API-ի դեպքում (լռելյայն՝ 20128)․ արդիականացրեք կապը.
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (կամ՝ -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Առաջին կադրը ՊԵՏՔ Է լինի response.create.
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses API-ի՝ WebSocket-ի միջոցով գործող միջնորդը միացված է **բացառապես `codex`-ին** (ChatGPT-ի
հետնամասային համակարգ)։ Այն լսում է API-ի/վահանակի նույն պորտում՝ `/v1/responses`,
`/responses` և `/api/v1/responses` ուղիներով։ Առաջին `response.create` կադրի դեպքում այն
իրականացնում է նույնականացում և նախապատրաստում ներքին `codex-responses-ws` կամրջի միջոցով, ընտրում է
codex OAuth կապ և `wreq-js` փոխադրամիջոցի միջոցով թունելավորում է դեպի `wss://chatgpt.com/backend-api/codex/responses`։
**Ոչ codex մոդելները մերժվում են** (`codex_ws_provider_required`)։
Քվոտայի համատեղ օգտագործմամբ երթուղավորման համար կիրառեք `model: "qtSd/<group>/codex/<model>"`։ Իրականացված է
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` ֆայլերում։

**Նույնականացում․** Bearer API բանալի՝ ձեռքսեղմման ընթացքում։ Ներկառուցված HTTP սերվերը (`server-ws.mjs`)
պետք է լինի ակտիվ մուտքի կետը (այն լռելյայն ակտիվ է, երբ `app/server-ws.mjs` գոյություն ունի)։

#### Մոդելի id․ օգտագործեք ChatGPT-ի պարզ id-ն (առանց `codex/` նախածանցի)

OpenAI **Codex CLI**-ն հաճախորդի կողմում վավերացնում է մոդելի անունը, երբ
`supports_websockets = true`, և **մերժում է մատակարարի նախածանցով id-ները**, օրինակ՝
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`)։ Ուղարկեք **պարզ** id-ն (օրինակ՝ `gpt-5.5`)։ OmniRoute-ի կամուրջը
միայն codex-ի համար է, ուստի վերին հոսք թունելավորելուց առաջ այն պարզ id-ն կրկին լուծում է որպես codex մոդել
(`resolveCodexWsModelInfo`), թեև պարզ
`gpt-5.5`-ը HTTP-ի միջոցով այլապես կուղղորդվեր մեկ այլ մատակարարի։

#### OpenAI Codex CLI-ի կազմաձևումը

Codex CLI-ն ուղղեք դեպի OmniRoute՝ WebSocket-ի
աջակցությամբ հատուկ մատակարար ավելացնելով `~/.codex/config.toml`-ում (օգտագործեք առանձին `CODEX_HOME`, որպեսզի
գոյություն ունեցող կազմաձևը չփոփոխվի)։

```toml
model = "gpt-5.5"                 # պարզ id՝ ՈՉ "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # առանց վերջնային շեղագծի․ WS URL-ը ածանցվում է (արտադրական միջավայրում օգտագործեք https/wss)
wire_api = "responses"                    # միակ աջակցվող արժեքը՝ 2026 թ. փետրվարից
supports_websockets = true                # միացնում է Responses-over-WS փոխադրամիջոցը
env_key = "OMNIROUTE_API_KEY"             # պարունակում է OmniRoute API բանալին (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API բանալի (ցանկացած բանալի, եթե REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI-ն `base_url + /responses`-ը արդիականացնում է WebSocket-ի, իսկ OmniRoute-ն այն
թունելավորում է դեպի ընտրված codex OAuth կապը։ Ամբողջական շղթայով վավերացված է տեղային
սերվերի նկատմամբ․ ChatGPT-ը վերադարձնում է `codex.rate_limits` + `response.created` և հոսքային եղանակով փոխանցում է
ավարտումը։

## Ինքնասպասարկման օգտագործում (`/api/usage/om-usage`)

Ցանկացած API բանալի կարող է կարդալ **իր սեփական** օգտագործման տվյալներն ու քվոտաները՝ առանց կառավարման նույնականացման։ Սա այն վերջնակետն է, որն
օգտագործում է հաճախորդը (CLI-ն, OmniCopilot վահանակը)՝ բանալու տիրոջը նրա ծախսերը ցուցադրելու համար։

```bash
# Տեքստային ձևաչափ (պատմական պայմանագիրը՝ պարզ տեքստ տերմինալի համար)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Կառուցվածքային ձևաչափ՝ այն, ինչ օգտագործում է UI-ն
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Բանալու համար պետք է միացված լինի **`allowUsageCommand`**-ը (լռելյայն անջատված է․ կառավարման վահանակի API բանալիների
կառավարիչը այն փոխարկում է առանձին՝ յուրաքանչյուր բանալու համար)։ Առանց դրա վերջնակետը պատասխանում է `403`։

`?format=json`-ը վերադարձնում է տարբերակված կառուցվածք, որպեսզի կանչողը երբեք մերժման
պատասխանից տվյալների դաշտ չկարդա։ Հաջողության դեպքում՝

```jsonc
{
  "allowed": true,
  // առկա է միայն այն դեպքում, երբ բանալու համար միացված են առանձին օգտագործման սահմանաչափեր (օրական/շաբաթական՝ USD-ով).
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // ընտրված մատակարարի քվոտայի ակնթարթային պատկերը կամ null, եթե դեռ ոչինչ քեշավորված չէ.
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // յուրաքանչյուր կապի ակնթարթային պատկերը, որպեսզի UI-ն կարողանա կողք կողքի արտապատկերել մի քանի մատակարարների.
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Մերժման դեպքում (`401`՝ սխալ բանալի / `403`՝ թույլատրված չէ) նույն երթուղին վերադարձնում է
`{ "allowed": false, "error": { "message": "…" } }`․ առկա, բայց դատարկ `personal`/`provider`-ը
(բանալին թույլատրված է, սակայն դեռ տվյալներ չեն ստացվել) մերժումից տարբերվող վիճակ է, և միայն JSON ձևաչափն է
տարբերակում դրանք։

**Նույնականացում․** կանչողի սեփական Bearer API բանալին՝ վավերացված `isValidApiKey`-ով․ սա
կառավարման միջերեսը (`/api/keys/…`) _չէ_, որը շարունակում է պաշտպանված մնալ `requireManagementAuth`-ով։

### Քվոտայի չմշակված և անջատման շեմին համապատասխան ճշգրտված տոկոսներ

`/api/usage/om-usage`-ն օգտագործելիս կանչողները պետք է հաշվի առնեն **պարզ տեքստային ելքում**
և կառուցվածքային **JSON ելքում** ներկայացվող տոկոսների տարբերությունը․

| Բնութագիր                        | Պարզ տեքստային ձևաչափ (`/api/usage/om-usage` / `@@om-usage`)                                                     | JSON ձևաչափ (`?format=json`)                                                                               |
| :------------------------------- | :--------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------- |
| **Ելքային դաշտ**                 | `NN% left` (օրինակ՝ `20% left`)                                                                                  | `provider.quotas` / `providers[].quotas`                                                                   |
| **Չափում**                       | **Անջատման շեմին համապատասխան ճշգրտված օգտագործելի սահմանաչափ**․ անջատման շեմից բարձր մնացած հզորությունը        | **Վերադաս մատակարարի չմշակված քվոտա**․ մատակարարի չճշգրտված չափումը                                        |
| **Անջատման շեմի մասշտաբավորում** | Մասշտաբավորվում է `effectiveRemainingPercent()`-ի միջոցով, որպեսզի պաշտպանված պահուստը ցուցադրվի որպես `0% left` | Չկա (չմշակված ակնթարթային արժեքներ՝ ինչպես հաղորդվել են մատակարարի կողմից)                                 |
| **Շեմի տվյալներ**                | Ներառված են ցուցադրվող տոկոսի մեջ                                                                                | Պահվում են յուրաքանչյուր կապի `quotaWindowThresholds`-ում (կամ օգտագործվում են սերվերի լռելյայն արժեքները) |
| **Հիմնական սպառող**              | Ինտերակտիվ CLI-ներ, տերմինալի հուշումներ, մարդկային օպերատորներ                                                  | Ծրագրային ինտեգրումներ, կառավարման վահանակներ, վերլուծություն, վճարումների հետևման գործիքներ               |

#### Անջատման շեմով ճշգրտման բանաձևը

OmniRoute-ն աջակցում է քվոտայի կանխարգելիչ անջատման շեմերին՝ վերադաս ռեսուրսի սպառումը կանխելու համար (կարգավորվում է կապի
`quotaWindowThresholds`-ի, մատակարարի լռելյայն արժեքների կամ հուսալիության գլոբալ կարգավորումների միջոցով)։ Երբ քվոտայի պատուհանի համար
ակտիվ է անջատման շեմը (օրինակ՝ `cutoff = 25%`), տեքստի ձևավորիչը մնացած սահմանաչափը հաշվարկում է հետևյալ կերպ․

- Եթե `remaining <= cutoff`՝ վերադարձնում է `0%`։
- Եթե `remaining > cutoff`՝ վերադարձնում է `((remaining - cutoff) / (100 - cutoff)) * 100`։

Ձևաչափված տեքստային ելքը սա կլորացնում է մինչև մոտակա ամբողջ թիվը (`Math.round(...)`)։

#### Պատկերավոր օրինակ

Դիտարկենք մատակարարի պատուհան՝ **60% չմշակված օգտագործմամբ** (հետևաբար՝ **40% չմշակված մնացորդային քվոտայով**) և կազմաձևված
**մնացորդային քվոտայի 25% անջատման շեմով**․

| Ներկայացում                        | Հաշվարկ                                            | Մնացորդ |              Ենթադրվող օգտագործում              |
| :--------------------------------- | :------------------------------------------------- | :-----: | :---------------------------------------------: |
| **Չմշակված JSON (`?format=json`)** | Վերադաս ակնթարթային պատկեր (`quotas[window]`)      | **40%** |                     **60%**                     |
| **Տեքստային ձևաչափ (`NN% left`)**  | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (`100 - remaining` հաշվարկելու դեպքում) |

- **Ինչու է տեքստը ցույց տալիս 20% մնացորդ․** Հաշվում մնացած 40% ֆիզիկական քվոտայից 25%-ը վերապահված է
  անջատման շեմի քաղաքականությամբ։ Կանչողին հասանելի է օգտագործելի 75%-ից ընդամենը 15% ազատ պաշար, մինչև երթուղիչը դադարեցնի
  հարցումների ուղղորդումն այս կապին։ Մասշտաբավորումն ապահովում է, որ կապը սպառվածություն (`0% left`) ազդարարի ճիշտ այն պահին,
  երբ երթուղավորումը դադարում է։
- **Ինչու է JSON-ը պահպանում չմշակված արժեքները․** JSON բեռնվածքը վերադարձնում է մատակարարի ճշգրիտ ակնթարթային պատկերը (`UsageSnapshot`),
  որպեսզի արտաքին գործիքները հասանելիություն ունենան վերադաս համակարգի օգտագործման իրական տվյալներին և կապի մակարդակի
  `quotaWindowThresholds`-ին՝ առանց սերվերի կողմից կորուստներով մասշտաբավորման։

#### Սպառողների տեղափոխման ուղեցույց

Եթե արտաքին ինտեգրումը (օրինակ՝ խմբագրիչի հավելումը կամ գործակալի ընդլայնումը) նախկինում վերլուծում էր տեքստային
վերջնակետը (`NN% left`) և օգտագործված տոկոսը հաշվարկում էր որպես `100 - NN`, ապա `?format=json`-ի անցնելը նշանակում է՝

- Չմշակված JSON արժեքների ընթերցումը կարտացոլի **վերին մակարդակի աղբյուրի փաստացի սպառումը** (վերևի օրինակում՝ օգտագործված է 60%-ը)։
- Եթե ինտեգրումը ցանկանում է պահպանել տեքստային վերջնակետի՝ օգտագործման համար հասանելի չափաքանակի իմաստաբանությունը, այն կարող է
  հաճախորդի կողմից հաշվարկել արդյունավետ մնացորդի բանաձևը՝ օգտագործելով `quotaWindowThresholds`-ը՝ կապի մակարդակի վերասահմանումների համար։

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Ազդեցությունը հապաղման վրա

Իմաստային քեշում HIT-ի դեպքում պատասխանը տրամադրվում է քեշից՝ **առանց վերադաս
կանչի**, ուստի հաղորդվող `X-OmniRoute-Response-Latency` արժեքը գրեթե զրոյական է
(անկախ սկզբնական վերադաս հապաղումից)։ Հապաղման նկատմամբ զգայուն հաճախորդները
(հենանիշային փորձարկումներ, p50/p99 մշտադիտարկում) պետք է ստուգեն
`X-OmniRoute-Cache-Latency` պատասխանի վերնագիրը՝

| Արժեք            | Նշանակություն                                                            |
| ---------------- | ------------------------------------------------------------------------ |
| `synthetic`      | Պատասխանը տրամադրվել է քեշից․ հապաղումը վերադաս կանչի իրական ժամանակը չէ |
| _(բացակայում է)_ | Պատասխանն ստացվել է իրական վերադաս կանչից                                |

### Յուրաքանչյուր բանալիով քեշի շրջանցում

API բանալիները կարող են հրաժարվել իմաստային քեշից ընթերցումներից՝ օգտագործելով `cacheDefaultMode`՝

| Արժեք    | Վարքագիծ                                                                  |
| -------- | ------------------------------------------------------------------------- |
| `legacy` | Քեշի սովորական վարքագիծ (լռելյայն)                                        |
| `bypass` | Ամբողջությամբ բաց թողնել քեշի որոնումը․ միշտ կանչել վերադաս ծառայությունը |

Սահմանեք բանալու ստեղծման (`POST /api/keys`) կամ թարմացման (`PATCH /api/keys/[id]`) ժամանակ՝

```json
{ "cacheDefaultMode": "bypass" }
```

### Յուրաքանչյուր հարցումով շրջանցում

Ցանկացած հարցում կարող է շրջանցել քեշը՝ անկախ բանալու կարգավորումներից՝

```
X-OmniRoute-No-Cache: true
```

շրջանակների և curl օրինակների համար տե՛ս՝
[Կառավարման նույնականացում](../guides/MANAGEMENT-AUTH.md)։

| --------------------------------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/api/providers`                        | GET/POST                  | Մատակարարների ցանկը / ստեղծում                                                                                                                       |

Համաժամացված/ներմուծված մոդելների համար `PUT /api/provider-models`-ն ընդունում է `provider`, `modelId` և
`maxOutputTokenOverride`․ դրական ամբողջ թիվը սահմանում է ելքային տոկենների ձեռքով նշված սահմանաչափը, իսկ `null`-ը
մաքրում է այն՝ վերականգնելով լռելյայն արժեքը։ `GET /api/provider-models?provider=<provider>`-ը վերադարձնում է այս
արժեքները `modelOutputOverrides`-ում՝ ներառյալ հատուկ մոդելի տող չունեցող մոդելները։ Վերասահմանումն
օգտագործում է կատարման ժամանակի `max_output_tokens` հնարավորությունը և պահպանվում է մոդելի կրկնակի համաժամացումից հետո։ OpenAI-ի հետ համատեղելի
մատակարարի էջն առաջարկում է խմբագրման/մաքրման նույն կառավարիչները և նշում է տեսողական հնարավորությունների բացահայտ աջակցությամբ մոդելները։

Հատուկ Chat Completions հանգույցները վերին մակարդակի բեքենդին են հարմարեցնում դատողությունից բացահայտ հրաժարումները։ Կապի
հաջող ստուգումն ինքնաշխատ կերպով ընտրում է չաթի ձևանմուշի կառավարիչները յուրաքանչյուր ճշգրիտ մոդելի ID-ի համար,
որի `/models` գրառումը հաստատում է ճանաչված `owned_by` արժեք՝ `vllm`, `sglang` կամ `llamacpp`։
OpenAI-ի հետ համատեղելի թափանցիկ փաթաթիչները կարող են պահպանել մոդելի սկզբնական գրառումը ներդրված
`openai` օբյեկտում․ հայտնաբերումը հետևում է առավելագույնը երեք նման շերտի։ Բացակայող, անհայտ կամ
հակասող սեփականության տվյալներով մոդելները պահպանում են OpenAI-ի սովորական վարքը։ Հայտնաբերումն օգտագործում է կատալոգի առկա հարցումը,
չի ստեղծում ավարտման տոկեններ և անվավեր է դառնում, երբ կապի վերջնակետը փոխվում է։

Այդ մետատվյալները չտրամադրող բեքենդի վարքն ամրագրելու համար օգտագործեք մատակարարի մասնակի
թարմացման առկա API-ն․

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Ուղարկեք այդ մարմինը `PUT /api/providers/<connection-id>`-ով։ Այդ կապում `none` արժեքով
բացահայտ դատողության ջանքը ուղարկվում է որպես `chat_template_kwargs.thinking=false` և
`chat_template_kwargs.enable_thinking=false`։ Ձևանմուշի բացահայտ տեղային արժեքները շարունակում են գերակա մնալ,
եթե սերվերային դատողության կանոնը որևէ ջանք չի պարտադրում։ Կարգավորումը կիրառվում է միայն այն դեպքում, երբ հատուկ
OpenAI-ի հետ համատեղելի կապն ուղարկում է Chat Completions մարմին․ Responses հարցումները և սովորական
մատակարարները պահպանում են հարցման իրենց տեղային կառուցվածքը։ `reasoningControl`-ը սահմանեք `openai`, որպեսզի պարտադրեք OpenAI-ի սովորական
`reasoning_effort`-ի թափանցիկ փոխանցումը, կամ բաց թողեք այն/սահմանեք `null`՝ ինքնաշխատ հայտնաբերումն օգտագործելու համար։

Claude Code-ի ինքնաշխատ ռեժիմի դասակարգչի հարցումներում տեղային մտածողությունը լռելյայն անջատված է, երբ դրանք
չեն պարունակում դատողության բացահայտ կառավարիչներ։ Հայտնաբերումն օգտագործում է դասակարգչի համակարգային նշիչը Claude ձևաչափով
հարցումներում, այլ ոչ թե մոդելների անունները կամ ավարտման սահմանաչափերը։ Մարմնի բացահայտ կառավարիչները, աջակցվող ջանքի/մտածողության
վերնագրերը, երթուղավորման կանոնները և մոդելի որոշված ջանքը պահպանում են իրենց առկա առաջնահերթությունը։ Դասակարգչի երկու
փուլերն էլ պահպանում են իրենց հուշումները, ավարտման սահմանաչափերը, կանգի հաջորդականությունները և վերին մակարդակի թույլտվության իրական
վճիռները․ երկրորդ փուլը դեռ կարող է իր պահանջված տեսանելի դատողությունն արտադրել որպես սովորական տեքստ։

### API բանալու թույլտվություններ

`PATCH /api/keys/{id}`-ը թարմացնում է գոյություն ունեցող բանալու թույլտվությունները։ Ինչպես յուրաքանչյուր `/api/keys*` երթուղու դեպքում, դրա համար պահանջվում է կառավարման թույլտվություն (տե՛ս [Կառավարման նույնականացում](../guides/MANAGEMENT-AUTH.md)), այլ ոչ թե ինֆերանսի բանալի։ Ուղարկեք միայն այն դաշտերը, որոնք ցանկանում եք փոխել. առանց դրանցից որևէ մեկի հարցումը մերժվում է՝ `No valid fields to update` հաղորդագրությամբ։ Ընդունվող դաշտերը սահմանվում են `src/shared/validation/schemas/keys.ts`-ի `updateKeyPermissionsSchema`-ով։

`/api/db-backups/export`, `/api/db-backups/exportAll` և `/api/settings/export-json` վերջնակետերը տրամադրում են
բոլոր պահված հավատարմագրերը, ուստի դրանք պահանջում են կառավարման վահանակի աշխատաշրջան կամ տեղային CLI (կամ անջատված
մուտքագրում)։ Ցանկացած տիրույթի API բանալիները և `oma_` մուտքի թոքենները ստանում են `403`։ Վերականգնումներն ունեն նույն
սահմանափակումը. `POST /api/db-backups/import` (ներառյալ `dryRun=true`), `POST /api/db-backups` (վերականգնում
ըստ id-ի) և `POST /api/settings/import-json` փոխարինում են գործող տվյալների բազան կամ կարգավորումները, ուստի մեքենայական
հավատարմագիրը նույնպես այնտեղ ստանում է `403`։ `omniroute sync import`-ը ուղարկում է տեղային CLI հավատարմագիրը։ Նույնը վերաբերում է
`DELETE /api/db-backups`-ին (պահված պահուստային պատճենների կրճատում) և `PATCH /api/db-backups`-ին (պահպանման կարգավորումներ.
պահված արժեքները կառավարում են ավտոմատ կրճատումը յուրաքանչյուր պահուստավորումից հետո)։ Ցուցակագրումը (`GET`) և ձեռքով
պահուստային պատճենի ստեղծումը (`PUT`) շարունակում են օգտագործել սովորական կառավարման նույնականացումը։

### Տարբերակը և թողարկման ալիքը

```bash
GET /api/system/version
```

Միայն loopback-ով հասանելի կառավարման երթուղի (ադմինիստրատորի նույնականացմամբ)։ Վերադարձնում է գործարկվող տարբերակը, վերջին
հրապարակված տարբերակը և ավտոմատ թարմացման կարգավիճակը։ `releaseChannel` և `channels` դաշտերն ավելացված
դաշտեր են (3.8.54 շարքից սկսած)։ `channel`-ը պահպանում է իր իմաստը՝ տեղակայման ռեժիմը, որը կառավարման վահանակի թարմացնողն
օգտագործում է (`npm`, `source` կամ `docker-compose`)։

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — գործարկվող կառուցման npm ալիքը՝ `nightly`՝ `-nightly.*` տարբերակների համար,
  `next`՝ այլ նախնական թողարկումների համար (`-rc.*`, `-beta.*`, `-alpha.*`), `lts`՝
  `channels.latest`-ից ավելի հին հիմնական տարբերակի կայուն տարբերակի համար, իսկ մնացած դեպքերում՝ `latest`։ Կիրառվում են նույն կանոնները, ինչ
  `scripts/release/dist-tag.mjs`-ում, որն ընտրում է npm dist-tag-ը հրապարակման պահին։
- `channels` — յուրաքանչյուր dist-tag-ի վերջին հրապարակված տարբերակը՝ ստացված `npm view omniroute dist-tags`-ից (ռեեստրի
  HTTP պահուստային տարբերակով), որը քեշավորվում է նույն 10 րոպեանոց TTL-ով, ինչ `latest`-ը։ `latest`-ը միշտ առկա է
  (հետադարձ կարգով օգտագործում է `latest` դաշտը, ապա՝ `"unavailable"`), իսկ `next`, `nightly` և `lts` դաշտերը հայտնվում են
  միայն այն դեպքում, երբ համապատասխան dist-tag-ը գոյություն ունի։ `Cache-Control: no-cache` հարցումը թարմացնում է երկու հարցումների արդյունքներն էլ։

Ալիքների մոդելը (`latest` = v3 մինչև 4.0 GA-ն, `next` = rc, `nightly` = `develop` կառուցումներ,
`lts` = v3 շտկումներ 4.0 GA-ից հետո) նկարագրված է `docs/ops/RELEASE_STRATEGY.md`-ում։

## Թոքեն պարունակող VS Code / առանց վերնագրի այլընտրանքային ուղիներ

Օգտագործեք այս այլընտրանքային ուղիները, երբ ինտեգրումը չի կարող ներարկել `Authorization` վերնագիր, և անհրաժեշտ է API բանալին ներդնել բազային URL-ում։

Օրինակ․

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
```

Նշումներ․

- Թոքեն պարունակող այլընտրանքային ուղիները կրկին օգտագործում են նույն մշակիչները, ինչ `/v1/*`-ը և `/api/tags`-ը․ պատասխանների կառուցվածքները մնում են նույնը։
- Նախընտրեք `Authorization: Bearer ...`, երբ հաճախորդն աջակցում է հատուկ վերնագրեր։
- URL-ի վրա հիմնված թոքենները կարող են հայտնվել հակադարձ պրոքսիի մատյաններում, դիտարկիչի պատմության մեջ և OmniRoute-ից դուրս հեռաչափական տվյալներում։ Դրանք դիտարկեք որպես համատեղելիության տարբերակ, այլ ոչ թե նույնականացման կանխադրված եղանակ։

## Բյուջե

```bash
# Ստանալ բյուջեի կարգավիճակը բոլոր API բանալիների համար
GET /api/usage/budget

# Սահմանել կամ թարմացնել բյուջեն
POST /api/usage/budget
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "dailyLimitUsd": 5.00,
  "weeklyLimitUsd": 30.00,
  "monthlyLimitUsd": 100.00,
  "warningThreshold": 0.8,
  "resetInterval": "monthly"
}
```

> **Սխեմայի նշումներ** (`setBudgetSchema`)․ `apiKeyId`-ն պարտադիր է․ `dailyLimitUsd`-ից, `weeklyLimitUsd`-ից կամ `monthlyLimitUsd`-ից առնվազն մեկը պետք է զրոյից մեծ լինի։ Ընտրովի դաշտեր՝ `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`)։ Հնացած `{keyId, limit, period}` կառուցվածքը վերադարձնում է `400 Bad Request`։

## Թոքենների սահմանաչափեր

Յուրաքանչյուր API բանալու համար նախատեսված **թոքենային** բյուջեներ (տարբերվում են վերևում նշված՝ USD-ի վրա հիմնված բյուջեից)։ Դրանք կիրառվում են անմիջապես հարցման մշակման ճանապարհին. երբ բանալու ընթացիկ պատուհանի օգտագործումը հասնում է սահմանաչափին, հարցումները մերժվում են `429 Too Many Requests` պատասխանով։ Սահմանաչափերը կարող են վերաբերել որոշակի `model`-ի, `provider`-ի կամ կիրառվել ամբողջ բանալու նկատմամբ՝ `global` ընդգրկույթով։ Երբ հարցմանը համապատասխանում են մի քանի սահմանաչափեր, կիրառվում է ամենախիստը։

```bash
# Ցուցադրել բանալու թոքենների սահմանաչափերը (ներառում է ընթացիկ պատուհանի օգտագործումը)
GET /api/usage/token-limits?apiKeyId=key-123

# Ստեղծել կամ թարմացնել թոքենների սահմանաչափը
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Ջնջել թոքենների սահմանաչափը՝ ըստ id-ի
DELETE /api/usage/token-limits?id=tl-abc
```

> **Սխեմայի նշումներ** (`setTokenLimitSchema`). `apiKeyId`-ն ու `scopeType`-ը (`model` | `provider` | `global`) պարտադիր են։ `scopeValue`-ն անհրաժեշտ է, եթե `scopeType`-ը `global` չէ (օրինակ՝ մոդելի id՝ `model` ընդգրկույթի համար, մատակարարի id՝ `provider` ընդգրկույթի համար)։ `tokenLimit`-ը պետք է լինի դրական ամբողջ թիվ (տողից փոխակերպվող)։ Ընտրովի են՝ `id` (բաց թողեք ստեղծելու համար, տրամադրեք՝ թարմացնելու համար), `resetInterval` (`daily` | `weekly` | `monthly`, լռելյայն՝ `monthly`), `resetTime` (`HH:MM`), `enabled` (լռելյայն՝ `true`)։ `GET` պատասխանները յուրաքանչյուր սահմանաչափ լրացնում են `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` և `nextResetAt` դաշտերով։ Սա կառավարման դասի վերջնակետ է (նույնականացումն իրականացվում է կենտրոնացված ձևով՝ authz խողովակաշարի միջոցով)։

## Հարցումների մշակում

1. Հաճախորդը հարցում է ուղարկում `/v1/*`
2. Երթուղու մշակիչը կանչում է `handleChat`, `handleEmbedding`, `handleAudioTranscription` կամ `handleImageGeneration`
3. Մոդելը որոշվում է (ուղղակի մատակարար/մոդել կամ կեղծանուն/կոմբինացիա)
4. Հաշվի հասանելիության զտմամբ հավատարմագրերն ընտրվում են տեղային ՏԲ-ից
5. Զրույցի դեպքում՝ `handleChatCore`-ը ստուգում է իմաստային/ստորագրային քեշը և որոշում կոմբինացիայի սեղմման կարգավորումները
6. Երբ միացված է, կանխարգելիչ սեղմումը կատարվում է նախքան մատակարարի ձևաչափի փոխակերպումը (`lite`, Caveman, RTK կամ համակցված)
7. Մատակարարի կատարիչը հարցումն ուղարկում է վերին հոսքի ծառայությանը
8. Պատասխանը փոխակերպվում է հաճախորդի ձևաչափին (զրույցի դեպքում) կամ վերադարձվում է անփոփոխ (ներդրումների/պատկերների/ձայնանյութի դեպքում)
9. Օգտագործման տվյալները, սեղմման վերլուծական տվյալները և հարցումների մատյանները գրանցվում են
10. Սխալների դեպքում պահուստային տարբերակն կիրառվում է կոմբինացիայի կանոններին համապատասխան

Ճարտարապետության ամբողջական տեղեկատու՝ [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Գրանցված բանալիներ (ինքնաշխատ կառավարում)

Օգտագործվում է բանալիների ինքնաշխատ կառավարման ենթահամակարգի կողմից՝ հիմքում ընկած մատակարարի/հաշվի համար API բանալիներ թողարկելու և ռոտացիայի ենթարկելու համար՝ օրական/ժամային քվոտաներով։

| Մեթոդ  | Ուղի                                  | Նկարագրություն                                                                                                                                                                                                                          |
| ------ | ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/registered-keys`             | Գրանցված բանալիների ցանկը (միայն քողարկված նախածանցը)                                                                                                                                                                                   |
| POST   | `/api/v1/registered-keys`             | Թողարկել նոր գրանցված բանալի — մարմին՝ `{name, provider?, accountId?, idempotencyKey?, expiresAt?, dailyBudget?, hourlyBudget?}`։ Չմշակված բանալին վերադարձնում է **մեկ անգամ**։ Քվոտայի պատճառով մերժման դեպքում վերադարձնում է `429`։ |
| GET    | `/api/v1/registered-keys/[id]`        | Ստանալ գրանցված բանալու մետատվյալները (առանց չմշակված գաղտնի տվյալների)                                                                                                                                                                 |
| DELETE | `/api/v1/registered-keys/[id]`        | Հետ կանչել գրանցված բանալին                                                                                                                                                                                                             |
| POST   | `/api/v1/registered-keys/[id]/revoke` | Հետկանչման բացահայտ վերջնակետ (նույն ազդեցությունն ունի, ինչ DELETE-ը)                                                                                                                                                                  |

**Նույնականացում՝** կառավարման աշխատաշրջան/API բանալի (`requireManagementAuth`) — նույն պաշտպանիչ ստուգումը, ինչ `/api/keys`-ի համար՝ կառավարման վահանակի աշխատաշրջան, տեղային CLI նշան կամ `manage`/`admin` հասանելիության տիրույթով API բանալի․ միայն ինֆերենցիայի համար նախատեսված API բանալիները ստանում են `403`։ Տե՛ս նաև `/v1/quotas/check` և `/v1/issues/report`։

| Մեթոդ  | Ուղի                          | Նկարագրություն                                                                                                                                                               |

| GET    | `/api/v1/agents/tasks`        | Առաջադրանքների ցանկ — ընտրովի `?provider=`, `?status=`, `?limit=` (1–500, լռելյայն՝ 50)                                                                                      |
| POST   | `/api/v1/agents/tasks`        | Ստեղծել առաջադրանք — հարցման մարմինը վավերացվում է `CreateCloudAgentTaskSchema`-ով (`providerId`, `prompt`, `source`, `options?`)։ Վերադարձնում է `201`՝ առաջադրանքի փաթեթով |
| DELETE | `/api/v1/agents/tasks?id=...` | Ջնջել առաջադրանքը                                                                                                                                                            |
| GET    | `/api/v1/agents/tasks/[id]`   | Կարդալ առաջադրանքը — համաժամանակ թարմացնում է կարգավիճակը վերին հոսքի cloud գործակալից, երբ սահմանված է `external_id`-ն                                                      |
| POST   | `/api/v1/agents/tasks/[id]`   | Տարբերակիչով գործողություն՝ `{action: "approve"}`, `{action: "message", message}` կամ `{action: "cancel"}`                                                                   |
| DELETE | `/api/v1/agents/tasks/[id]`   | Ջնջել որոշակի առաջադրանք՝ ըստ id-ի                                                                                                                                           |

## Կառավարման պրոքսիներ

Ելքային HTTP(S)/SOCKS պրոքսիներ, որոնք կարող են նշանակվել պրովայդերներին, հաշիվներին կամ գլոբալ մակարդակով։

| Մեթոդ  | Ուղի                                         | Նկարագրություն                                                                                                                                             |
| ------ | -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/management/proxies`                 | Պրոքսիների ցանկ (`?id=`-ի դեպքում վերադարձնում է մեկը, իսկ `?id=&where_used=1`-ի դեպքում՝ նշանակումների գրաֆը)                                             |
| POST   | `/api/v1/management/proxies`                 | Ստեղծել պրոքսի — հարցման մարմինը վավերացվում է `createProxyRegistrySchema`-ով                                                                              |
| PATCH  | `/api/v1/management/proxies`                 | Թարմացնել պրոքսին — հարցման մարմինը վավերացվում է `updateProxyRegistrySchema`-ով (պահանջվում է `id`)                                                       |
| DELETE | `/api/v1/management/proxies?id=...&force=1`  | Ջնջել պրոքսին (նշանակումները անջատելու համար օգտագործեք `force=1`)                                                                                         |
| GET    | `/api/v1/management/proxies/assignments`     | Նշանակումների ցանկ — հնարավոր է զտել ըստ `proxy_id`, `scope`, `scope_id` դաշտերի․ փոխանցեք `resolve_connection_id=<id>`՝ կապի ակտիվ պրոքսին որոշելու համար |
| PUT    | `/api/v1/management/proxies/assignments`     | Նշանակել — հարցման մարմինը վավերացվում է `proxyAssignmentSchema`-ով (`{scope, scopeId?, proxyId?}`)։ Մաքրում է դիսպետչերի քեշը                             |
| PUT    | `/api/v1/management/proxies/bulk-assign`     | Զանգվածային նշանակում — հարցման մարմինը վավերացվում է `bulkProxyAssignmentSchema`-ով (`{scope, scopeIds[], proxyId?}`)                                     |
| GET    | `/api/v1/management/proxies/health?hours=24` | Պրոքսիի առողջության ամփոփ տվյալները (հաջողությունների/ձախողումների քանակ, ուշացում) որոշակի ժամանակահատվածի համար                                          |

**Նույնականացում․** յուրաքանչյուր երթուղու համար պահանջվում է կառավարման նստաշրջան/API բանալի (`requireManagementAuth`)։

> Առաջադրանքի նկարագրության `POST /api/v1/management/proxies/[id]/assignments` և `POST /api/v1/management/proxies/[id]/health` երթուղիները սպասարկվում են վերևում ցուցադրված հարթ `/assignments` և `/health` երթուղիներով․ կոդային բազայում առանձին id-ի ենթաերթուղիներ չկան։

## Դիմակայունություն (ընդլայնված)

OmniRoute-ը տրամադրում է ժամանակավոր խափանումների մշակման երեք անկախ մեխանիզմ. ստորև ներկայացված կառավարման վերջնակետերը թույլ են տալիս օպերատորներին դիտել և վերասահմանել դրանք.

| Տիրույթ             | Վիճակի պահոց                                        | Դիտում                                    | Վերակայում / մաքրում                                                  |
| ------------------- | --------------------------------------------------- | ----------------------------------------- | --------------------------------------------------------------------- |
| Մատակարարի անջատիչ  | `domain_circuit_breakers` + հիշողության մեջ         | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                          |
| Կապի սպասման շրջան  | `rateLimitedUntil` մատակարարի կապերում              | `/api/rate-limits`, `/api/providers/[id]` | (վերագործարկվում է հետաձգված կերպով. մաքրեք մատակարարի PUT-ի միջոցով) |
| Մոդելի արգելափակում | Հիշողության մեջ պահվող մոդելի հասանելիության ռեեստր | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                              |

`PATCH /api/resilience`-ն ընդունում է մատակարարի անջատիչի վերասահմանումներ `providerBreaker.oauth`-ի և `providerBreaker.apikey`-ի ներքո։ Յուրաքանչյուր պրոֆիլ աջակցում է `degradationThreshold`, `failureThreshold` և `resetTimeoutMs` դաշտերը. նույն դաշտերը հասանելի են նաև Dashboard → Settings → Resilience բաժնում։

```bash
# Մաքրել մեկ մոդելի արգելափակումը
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Մաքրել բոլոր արգելափակումները
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
```

Ամբողջական հայեցակարգային տեղեկատուի և անջատիչի լռելյայն արժեքների համար տե՛ս [`CLAUDE.md`](../../CLAUDE.md) → «Դիմակայունության գործարկման վիճակ» և [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md)։

### Հաճախականության սահմանափակման հերթ և ավտոմատ միացման պաշտպանիչ մեխանիզմ

- **Աջակցվող գրանցման ուղի**. `POST /api/rate-limits`՝ `{"connectionId": "<id>", "enabled": true|false}` մարմնով, կապի հաճախականության սահմանափակման պաշտպանությունը միացնելու կամ անջատելու համար աջակցվող կառավարման վերջնակետն է։ `PUT /api/providers/[id]`-ը միտումնավոր չի փոփոխում կամ փոխարկում `rateLimitProtection`-ը (#11278)։
- **`enabled: false`-ի իմաստը**. `enabled: false` սահմանելը հեռացնում է կապի հստակ պաշտպանությունը, սակայն **չի** բացառում ակտիվ API բանալիով կապը ավտոմատ միացման համընդհանուր պաշտպանիչ մեխանիզմից (`autoEnableApiKeyProviders = true`)։ `reconcileEnabledConnections`-ում (`open-sse/services/rateLimitManager.ts`) `false`-ը և `undefined`-ը համարժեք են. առանց հստակ պաշտպանության ակտիվ API բանալիով կապերը շարունակում են պաշտպանված մնալ ավտոմատ միացման պաշտպանիչ մեխանիզմի ներքո։
- **Համընդհանուր անջատում**. API բանալիով կապերն առանց հաճախականության սահմանափակման հերթերի գործարկելու համար համընդհանուր կերպով անջատեք պաշտպանիչ մեխանիզմը՝ օգտագործելով `RATE_LIMIT_AUTO_ENABLE=false` (միջավայրի փոփոխական) կամ `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`)։

## MCP սերվեր

OmniRoute-ը տրամադրվում է ներկառուցված Model Context Protocol սերվերով՝ 3 փոխադրման եղանակով (stdio, SSE, streamable-http) և սահմանափակված գործիքներով։ Ստորև նշված կառավարման վահանակի վերջնակետերը կարդում են վիճակի/աուդիտի տվյալները և միջնորդում HTTP փոխադրումները։

| Մեթոդ | Ուղի | Նկարագրություն |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | Սրտազարկ, փոխադրում, առցանց վիճակ, վերջին կանչ, առաջատար գործիքներ, վերջին 24 ժամվա հաջողության ցուցանիշ |
| GET | `/api/mcp/tools` | MCP գործիքների ցանկ՝ `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` դաշտերով |
| GET | `/api/mcp/sse` | Բացել SSE հոսք SSE փոխադրման համար (վերադարձնում է `503`, եթե MCP-ն անջատված է կամ փոխադրումը չի համապատասխանում) |
| POST | `/api/mcp/sse` | Ուղարկել JSON-RPC շրջանակ SSE փոխադրմամբ |
| GET | `/api/mcp/stream` | Բացել Streamable HTTP փոխադրման SSE կողմը (սերվերի կողմից նախաձեռնվող հաղորդագրություններ) |
| POST | `/api/mcp/stream` | Ուղարկել JSON-RPC շրջանակ Streamable HTTP փոխադրմամբ |
| DELETE | `/api/mcp/stream` | Ավարտել Streamable HTTP աշխատաշրջանը |
| GET | `/api/mcp/audit` | Հարցում կատարել աուդիտի մատյանում — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | Աուդիտի ամփոփ վիճակագրություն (ընդհանուր թվեր, հաջողության ցուցանիշ, միջին տևողություն, առաջատար գործիքներ) |

**Նույնականացում․** `sse`/`stream` փոխադրումները հետևում են MCP-ին հատուկ նույնականացման մեխանիզմին (`mcp` շրջանակով Bearer API բանալի), իսկ `status`/`tools`/`audit*` երթուղիները հասանելի են կառավարման վահանակից կարդալու համար (կառավարման վահանակի հոսթին հասանելիությունից բացի լրացուցիչ նույնականացում չի պահանջվում)։

> Երկու HTTP փոխադրումներն էլ կառավարվում են `settings.mcpEnabled` և `settings.mcpTransport` պարամետրերով․ փոխադրման անհամապատասխանության դեպքում վերադարձվում է `400`, իսկ MCP-ի անջատված վիճակի դեպքում՝ `503`։

## A2A սերվեր

OmniRoute-ը տրամադրում է A2A (Agent-to-Agent) JSON-RPC 2.0 վերջնակետ, ինչպես նաև REST փաթաթիչ՝ զննման/վահանակում օգտագործելու համար։

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # պարտադիր չէ, եթե OMNIROUTE_API_KEY-ը սահմանված չէ
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Աջակցվող մեթոդները (բոլորը կախված են `settings.a2aEnabled`-ից)՝

| Մեթոդ            | Նկարագրություն                                                                 |
| ---------------- | ------------------------------------------------------------------------------ |
| `message/send`   | Հմտության համաժամանակյա կատարում․ վերադարձնում է `{task, artifacts, metadata}` |
| `message/stream` | Հմտությունների նույն հավաքածուի հոսքային SSE կատարում                          |
| `tasks/get`      | Ստանալ առաջադրանքն ըստ `taskId`-ի                                              |
| `tasks/cancel`   | Չեղարկել առաջադրանքն ըստ `taskId`-ի                                            |

Ներկառուցված հմտություններ՝ `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`։

### Գործակալի քարտ

```bash
GET /.well-known/agent.json
```

Վերադարձնում է հրապարակային A2A գործակալի քարտը (անուն, նկարագրություն, հնարավորություններ, հմտությունների կատալոգ, նույնականացման սխեմա), որը հրապարակայնորեն քեշավորվում է 1 ժամով։ Նույնականացում չի պահանջվում։

### REST օժանդակ մեթոդներ

| Մեթոդ | Ուղի                         | Նկարագրություն                                                                                                           |
| ----- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| GET   | `/api/a2a/status`            | A2A-ի միացված լինելու վիճակ + առաջադրանքների վիճակագրություն + քեշավորված գործակալի քարտի ամփոփում                       |
| GET   | `/api/a2a/tasks`             | Առաջադրանքների ցանկ — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST  | `/api/a2a/tasks`             | (Իրականացված չէ որպես REST օժանդակ մեթոդ․ ստեղծեք JSON-RPC `message/send`-ի միջոցով)                                     |
| GET   | `/api/a2a/tasks/[id]`        | Ստանալ մեկ առաջադրանք                                                                                                    |
| POST  | `/api/a2a/tasks/[id]/cancel` | Չեղարկել առաջադրանքը                                                                                                     |

**Նույնականացում․** REST օժանդակ մեթոդներն աշխատում են առանց կառավարման նույնականացման (ընթեռնելի են վահանակից), իսկ JSON-RPC `/a2a` ուղին օգտագործում է Bearer `OMNIROUTE_API_KEY`, եթե այն կազմաձևված է։

| GET | `/api/assess` | Կարդալ գնահատման վերջին դասակարգումները (ըստ մատակարարի/մոդելի) |
| POST | `/api/assess` | Գործարկել գնահատում — մարմին՝ `{scope: {type:"all"}                                                   | {type:"provider", providerId} | {type:"model", modelId}, trigger?}` |
| GET | `/api/evals` | Թվարկել ներկառուցված գնահատման փաթեթները + վերջին գործարկումները |
| POST | `/api/evals` | Սկսել գնահատման գործարկում |
| POST | `/api/evals/suites` | Ստեղծել հատուկ գնահատման փաթեթ․ մարմինը վավերացվում է `evalSuiteSaveSchema`-ով |
| GET | `/api/evals/suites/[id]` | Ստանալ հատուկ գնահատման փաթեթը |

**Նույնականացում․** `/api/cloud/auth`-ն ուղղակիորեն ստուգում է Bearer բանալին և վերադարձնում է յուրաքանչյուր կապի քողարկված բանալին ու `projectId`-ն միայն `manage` / `admin` թույլտվության տիրույթ ունեցող բանալու համար․ մյուս `/api/cloud/*`, `/api/evals/*` և `/api/assess` ուղիները պահանջում են կառավարման աշխատաշրջան/API բանալի։ `/api/assess` POST-ը կիրառում է `validateBody`՝ տարբերակիչ միավորմամբ սահմանված տիրույթի սխեմայով։

## ACP-ի (Agent Client Protocol) կառավարում

որպես ենթապրոցեսներ։ Այս վերջնակետերը կառավարում են ACP գործակալների հայտնաբերումը և հատուկ գործակալների գրանցումը։

| Մեթոդ  | Ուղի              | Նկարագրություն                                                                                                                                                  |
| ------ | ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/acp/agents` | Ցուցակագրում է բոլոր հայտնի CLI գործակալները (ներկառուցված + հատուկ)՝ տեղադրման կարգավիճակով, տարբերակով և երկուական ֆայլով                                     |
| POST   | `/api/acp/agents` | Գրանցում է հատուկ ACP գործակալ կամ թարմացնում քեշը — մարմին՝ `{id, name, binary, versionCommand, providerAlias, spawnArgs, protocol}` կամ `{action: "refresh"}` |
| DELETE | `/api/acp/agents` | Հեռացնում է հատուկ ACP գործակալ — հարցման պարամետր՝ `?id=<agentId>`                                                                                             |

**Պատասխանի օրինակ** (`GET /api/acp/agents`)՝

```json
{
  "agents": [
    {
      "id": "claude",
      "name": "Claude Code CLI",
      "binary": "claude",
      "version": "1.0.45",
      "installed": true,
      "protocol": "stdio",
      "providerAlias": "claude",
      "isCustom": false
    },
    {
      "id": "my-custom-cli",
      "name": "My Custom CLI",
      "installed": false,
      "protocol": "stdio",
      "providerAlias": "my-provider",
      "isCustom": true
    }
  ],
  "cacheTtlMs": 60000,
  "cacheAge": 1234
}
```

**Նույնականացում՝** պահանջվում է կառավարման աշխատաշրջան (կառավարման վահանակի `auth_token` cookie) կամ կառավարման շրջանակով API բանալի։

Ամբողջական մանրամասների համար տե՛ս [ACP Framework](../frameworks/ACP.md)։

## Պաշտպանական սահմանափակումներ

Ստուգեք գործարկման միջավայրի պաշտպանական սահմանափակումները (PII-ի հայտնաբերում, հուշման ներարկման հայտնաբերում, տեսողական կապակցում)։ Պաշտպանական սահմանափակումները գործարկվում են յուրաքանչյուր հարցման համար․ առանձին կանչի մակարդակով դրանցից հրաժարումն իրականացվում է `x-omniroute-disabled-guardrails` հարցման վերնագրի միջոցով. պահպանվող միացման/անջատման ինտերֆեյս չկա։

| Մեթոդ | Ուղի                   | Նկարագրություն                                                                                                              |
| ----- | ---------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/guardrails`      | Ցուցակագրել գրանցված պաշտպանական սահմանափակումները և դրանց կարգավիճակը (անուն / միացվածություն / առաջնահերթություն)         |
| POST  | `/api/guardrails/test` | Փորձնականորեն գործարկել նախնական կանչի մշակաշարը նմուշային մուտքային տվյալների վրա — մարմին՝ `{input, disabledGuardrails?}` |

**Նույնականացում․** Պահանջվում է կառավարման աշխատաշրջան։

Ամբողջական մանրամասների համար տե՛ս [Անվտանգություն > Պաշտպանական սահմանափակումներ](../security/GUARDRAILS.md)։

## Նույնականացում

Հավաստագրերի չորս ընտանիքների (վահանակի աշխատաշրջան, տեղային CLI թոքեն, `oma_live_…` հասանելիության թոքեն, կառավարման շրջանակով API բանալի) և դրանց՝ ինֆերենցիայի բանալիներից տարբերությունների մասին տե՛ս [Կառավարման նույնականացում](../guides/MANAGEMENT-AUTH.md)։

- Վահանակի երթուղիները (`/dashboard/*`) օգտագործում են `auth_token` cookie-ն
- Մուտքն օգտագործում է պահպանված գաղտնաբառի հեշը՝ անհրաժեշտության դեպքում անցնելով `INITIAL_PASSWORD`-ին
- `requireLogin`-ը կարելի է միացնել կամ անջատել `/api/settings/require-login`-ի միջոցով
- `/v1/*` երթուղիները կարող են պահանջել Bearer API բանալի, երբ `REQUIRE_API_KEY=true`
- Այս տեղեկատուում «կառավարման թոքեն» / «կառավարման շրջանակով API բանալի» նշանակում է այդ ուղեցույցում նշված ընտանիքներից մեկը, այլ ոչ թե չսահմանված լրացուցիչ գաղտնիքի տեսակ

> **Համատեղելիությունը խախտող փոփոխություն (v3.8.0)** — `/api/v1/agents/tasks/*`-ը և cooldown-ի կառավարման վերջնակետերն այժմ պահանջում են **կառավարման նույնականացում** (վահանակի `auth_token` cookie կամ կառավարման շրջանակով API բանալի)։ Այն հաճախորդները, որոնք նախկինում այս երթուղիները կանչում էին առանց նույնականացման, կստանան `401 Unauthorized`։ Տե՛ս `588a0333` commit-ը (`fix(auth): require management auth for agent and cooldown APIs`)։
