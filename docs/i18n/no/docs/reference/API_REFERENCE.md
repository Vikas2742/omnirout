## Fullføring av chat

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Egendefinerte headere

| Header                   | Retning     | Beskrivelse                                                                                                                                                                                               |
| ------------------------ | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Forespørsel | Sett til `true` for å omgå hurtigbufferen                                                                                                                                                                 |
| `x-omniroute-no-memory`  | Forespørsel | Sett til `true` for å hoppe over innsetting av minne og ferdigheter for denne forespørselen (tilsvarer ingen hurtigbuffer og unngår ekstra bruk av tokener/kostnader per kall)                            |
| `X-OmniRoute-Progress`   | Forespørsel | Sett til `true` for fremdriftshendelser                                                                                                                                                                   |
| `X-Session-Id`           | Forespørsel | Fast øktnøkkel for ekstern øktaffinitet                                                                                                                                                                   |
| `x_session_id`           | Forespørsel | Varianten med understrek godtas også (direkte HTTP)                                                                                                                                                       |
| `X-OmniRoute-Session-Id` | Forespørsel | Økt-/samtaleetikett angitt av kalleren (brukes også av minnet). Når den finnes, lagres den ordrett i `call_logs.session_tag` for kostnadstilordning per økt (#8249) — den genereres aldri når den mangler |
| `Idempotency-Key`        | Forespørsel | Nøkkel for deduplisering (vindu på 5 sekunder)                                                                                                                                                            |
| `X-Request-Id`           | Forespørsel | Alternativ nøkkel for deduplisering                                                                                                                                                                       |
| `x-omniroute-connection` | Forespørsel | Fest en forespørsel med én modell til én leverandørtilkobling (konto) ved hjelp av ID-en — se [Kontofesting per forespørsel](#account-pinning-per-request)                                                |
| `X-OmniRoute-Cache`      | Svar        | `HIT` eller `MISS` (ikke-strømmet)                                                                                                                                                                        |
| `X-OmniRoute-Idempotent` | Svar        | `true` hvis deduplisert                                                                                                                                                                                   |
| `X-OmniRoute-Progress`   | Svar        | `enabled` hvis fremdriftssporing er aktivert                                                                                                                                                              |
| `X-OmniRoute-Session-Id` | Svar        | Effektiv økt-ID brukt av OmniRoute                                                                                                                                                                        |
| `X-OmniRoute-Request-Id` | Svar        | Korrelasjons-ID for forespørselen (når kjent)                                                                                                                                                             |
| `X-OmniRoute-Version`    | Svar        | OmniRoute-byggversjon (alltid til stede)                                                                                                                                                                  |
| `X-OmniRoute-Cost-Saved` | Svar        | Beløpet i USD som hurtigbufferen sparte ved et treff (kun hurtigbuffertreff)                                                                                                                              |
| `X-OmniRoute-Decision`   | Svar        | Rutingsspor: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` er kombinasjonsstrategien, eller `single` for en forespørsel uten kombinasjon) — alltid til stede i fullføringssvar            |

> Nginx-merknad: Hvis du er avhengig av headere med understrek (for eksempel `x_session_id`), aktiver `underscores_in_headers on;`.

#### Kontofesting per forespørsel

Når en leverandør har flere tilkoblinger (kontoer eller nøkler), velger OmniRoute vanligvis én
gjennom sin strategi for kontovalg. En forespørsel kan i stedet festes til én bestemt tilkobling
med headeren `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Hvor finner du ID-en?** Åpne leverandørsiden i kontrollpanelet
  (**Kontrollpanel → Leverandører → <leverandør>**) og klikk på ID-brikken `xxxxxxxx…` i en
  tilkoblingsrad – da kopieres hele tilkoblings-ID-en.
- **Hvilke forespørsler respekterer den?** Forespørsler med én modell (`provider/model`) på
  `/v1/chat/completions`, `/v1/messages` og `/v1/responses`. Kombinasjoner ignorerer headeren:
  Fest en konto per kombinasjonstrinn gjennom trinnets egen tilkobling i stedet.
- **Festingen er streng, ikke en preferanse.** Den festede tilkoblingen brukes utelukkende. En
  feil i forespørselen registrerer kontoens nedkjølingsperiode, men bytter **ikke** til en
  annen konto hos samme leverandør.
- **Nedkjøling og kvote frigir festingen.** Mens den festede tilkoblingen er under nedkjøling,
  har brukt opp kvoten eller er blokkert av en kvotepolicy, faller senere forespørsler tilbake
  til leverandørens andre tilkoblinger, akkurat som trafikk uten festing.
- **Ukjente eller deaktiverte ID-er feiler.** En ID som ikke finnes i leverandørens aktive
  utvalg (slettet, deaktivert eller tilhørende en annen leverandør), gjør at ingen konto er
  kvalifisert. Forespørselen feiler derfor i stedet for å bli rutet et annet sted uten varsel.

Claude Code sender egendefinerte headere gjennom `ANTHROPIC_CUSTOM_HEADERS`. Legg den i `env`-blokken
i `~/.claude/settings.json`, eller i en `.claude/settings.json` på prosjektnivå for å feste en annen
konto per prosjekt:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Kilde: `src/sse/handlers/chat.ts` (lesing av header), `src/sse/services/auth.ts` og
`src/sse/services/sessionAffinityPin.ts` (frigivelse av festing og kontrollen for manglende oppføring i utvalget).

> **Headere for kostnadstelemetri:** Vellykkede svar uten strømming inneholder også settet med `X-OmniRoute-*`-headere for kostnadstelemetri – `X-OmniRoute-Response-Cost` (USD, fast 10 desimaler; `0.0000000000` for gratis/uten pris), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` og `X-OmniRoute-Fallback-Attempts` (bare når > 0), i tillegg til `X-OmniRoute-Request-Id` og `X-OmniRoute-Version`. Disse sendes av fullføringer av chat, `/v1/responses`, `/v1/messages` **og medieendepunktene** – `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` og `/v1/moderations` (alltid kostnad `0`). Mediekostnaden beregnes per modalitet (per bilde, per sekund, per tegn, per søkeenhet) når priser er tilgjengelige, ellers `0` (fortsett ved feil).

> **Kostnadssemantikk ved hurtigbuffertreff:** Ved et treff i den semantiske hurtigbufferen (`X-OmniRoute-Cache-Hit: true`) utføres det ikke noe oppstrømskall, så `X-OmniRoute-Response-Cost` er `0.0000000000` (den **inkrementelle** kostnaden ved å levere treffet). Den opprinnelige kostnaden, eller kostnaden som ellers ville ha påløpt, rapporteres separat i `X-OmniRoute-Cost-Saved`. Faktureringssystemer bør summere `X-OmniRoute-Response-Cost` (treff koster ingenting), mens hurtigbufferanalyse kan aggregere `X-OmniRoute-Cost-Saved`.

## Eksklusive administrerte øktleieavtaler

Eksklusiv administrert øktleie er en valgfri, klientnøytral rutingskontrakt: Én aktiv eier
innehar én kvalifisert OmniRoute-tilkobling. Den leier ikke en modell, krever ikke OAuth, identifiserer
ikke en bestemt klient og krever ikke en bestemt leverandør.

API-nøkkelen som brukes til autentisering, må ha omfanget `lease:exclusive` og en eksplisitt, ikke-tom
`allowedConnections`-liste. Grensen for databasemutasjoner håndhever begge feltene samlet ved
oppretting av nøkler og delvise oppdateringer.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Vellykkede svar på innhenting, fornyelse og frigivelse viser tidsstempler, `state` og den eksakte positive
`generation`, men aldri den valgte tilkoblingen eller legitimasjonen. Ved fornyelse og frigivelse oppgis
generasjonen i JSON-brødteksten:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

En aktiv leieeier kan eksplisitt be om personvernsikre visningsmetadata for sin gjeldende binding:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Denne valgfrie statushandlingen avgrenses av den ugjennomsiktige eieren, den autentiserte administrerte API-nøkkelen og den eksakte
aktive generasjonen i én databasetransaksjon. `displayName` er bare det konfigurerte tilkoblingsnavnet
etter at innledende og avsluttende blanktegn er fjernet. Verdien er `null` når det ikke finnes noe sikkert konfigurert navn. OmniRoute erstatter det aldri med en
e-postadresse eller en generert kontoidentitet. Leverandørverdien er en ikke-sensitiv visningsetikett og aldri
en generert identifikator for en kompatibel leverandør. Legitimasjon, tokener, informasjonskapsler, rå ID-er for tilkoblinger eller API-nøkler,
eierhasher, avgrensningshemmeligheter og interne rutingsdata er utelatt.

Oppslag med feil nøkkel, feil eier, foreldet generasjon, manglende, utløpt, frigitt eller ugyldiggjort leie
returnerer alle den samme `409 LEASE_FENCE_STALE`-feilen uten tilkoblingsmetadata. En klient som mottok svaret om venting på kapasitet, har ingen aktiv binding å inspisere. Når rutingen flytter en aktiv leie,
forblir den samme generasjonen gyldig, og status returnerer atomisk den nye bindingen, aldri den gamle.
Eksisterende klienter forblir uendret fordi svar på innhenting, fornyelse, frigivelse og venting beholder
sine tidligere formater.

Denne serverkontrakten endrer ikke standardimplementasjonen av OpenAI Codex `/status`. Standard Codex rapporterer for øyeblikket sin
modellleverandør og innebygde autentiserings-/kontostatus, men viser ikke vilkårlige egendefinerte
kontometadata for leverandører. En senere klientintegrasjon må kalle denne handlingen og avgjøre hvordan
`connection.displayName` skal vises.

Hver administrerte inferensforespørsel oppgir deretter begge kontrollhodene:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Den eksakte eieren, generasjonen, aktive tilkoblingen og autentiserte API-nøkkelen avgrenses umiddelbart
før hvert støttede oppstrømsforsøk. Gjenbruk av eier og generasjon med en annen nøkkel mislykkes selv
når denne nøkkelen tillater den samme tilkoblingen. Rå eierverdier lagres ikke permanent, loggføres ikke, beholdes ikke i
øyeblikksbildet av forespørselen og videresendes ikke oppstrøms.

Midlertidig ressurskonflikt returnerer HTTP `429` med `Retry-After` og:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Dette svaret betyr bare at det ordinære settet med kvalifiserte tilkoblinger ikke var tomt, og at alle ledige kandidater var
opptatt av en fremmed aktiv leie. Modeller/leverandører som ikke støttes, manglende samsvar med retningslinjer, nedkjøling, kvote,
helse og andre ordinære kvalifiseringsfeil beholder sine eksisterende OmniRoute-svar.

### `x-omniroute-compression`

Forespørselsspesifikk overstyring av komprimeringsplanen. Høyeste prioritet – overstyrer rutingskombinasjonens
overstyring, den aktive profilen, automatisk utløsning og panelets standardinnstilling. Verdier:

| Verdi         | Effekt                                                                                                          |
| ------------- | --------------------------------------------------------------------------------------------------------------- |
| `off`         | Ingen komprimering for denne forespørselen.                                                                     |
| `default`     | Standardprofilen som er utledet fra panelet (ignorerer den aktive profilen). Tapsmotorer forblir av.            |
| `safe`        | Bare deduplisering og sammenslåing av blanktegn.                                                                |
| `allow-lossy` | Behold operatørplanen for denne forespørselen, inkludert sammendrag og stilomskrivinger.                        |
| `engine:<id>` | Én enkelt motor når den er aktivert, f.eks. `engine:rtk`. Forespørselsspesifikt tilvalg for motoren.            |
| `<combo>`     | En navngitt kombinasjon, først samsvart etter navn (uten hensyn til store og små bokstaver), deretter etter ID. |

Merknader:

- Ukjente verdier ignoreres (forespørselen avvises aldri); løsningen går videre til den normale operatørprioriteten.
- Hvis flere kombinasjoner har samme navn, oppgir du kombinasjonens **ID** for et deterministisk samsvar.
- En kombinasjon med navnet `off` eller `default` kan ikke velges etter navn (disse nøkkelordene tolkes først); referer til en slik kombinasjon med dens ID.
- Hovedbryteren for komprimering er en absolutt sperre: Når komprimering er deaktivert globalt, kan dette hodet ikke aktivere den.

Den anvendte planen gjengis i svarhodet:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

der `<source>` er én av `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` eller `off`.

## Embeddings

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Tilgjengelige leverandører: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Katalog-ID-er er `provider/model` (eksempel: `jina-ai/jina-embeddings-v5-omni-small`). Jina-modell-ID-er uten prefiks som finnes i registeret (for eksempel `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`), blir også gjenkjent. Jina embed/rerank/classify/segment bruker først `jina-ai`-legitimasjon fra kontrollpanelet. `JINA_AI_API_KEY` brukes bare som reserve når det ikke finnes noen nøkkel i kontrollpanelet. `jina-reader`-kortet er bare for Reader / `r.jina.ai` (`POST /v1/web/fetch`) og tilbyr aldri embeddings eller rerank.

Registermodeller som oppgir støtte for flere modaliteter, godtar også opptil 32 leverandørnøytrale strukturerte
elementer. Medieelementtypene er `text`, `image`, `audio`, `video` og `document`. Medienes `source`
er enten `{"type":"url","url":"https://..."}` eller
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
og familiealiaset `jina-ai/jina-embeddings-v5-omni` → omni-small) godtar også Jinas egne
EmbeddingsV5Request-dokumenter og **videresender dem uendret** til `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Opprinnelige `{ image | audio | video | pdf }`-verdier kan være en offentlig HTTPS-URL, en `data:`-URI eller rå
base64. OmniRoute konverterer ikke disse objektene til strenger og henter heller ikke opprinnelige bilde-URL-er – Jina henter
offentlige medier selv. Ekstra Jina-felt (`task`, `normalized`, `truncate`, `embedding_type`) blir
videresendt. Jina-SKU-er som bare støtter tekst, avviser fortsatt dokumenter som ikke er tekst.

Sikkerhets- og transportgrenser:

- URL-er til eksterne medier må være offentlig HTTPS. Kanoniske `{type,source:url}`-elementer hentes
  på serversiden (ny validering av omdirigeringer, tidsavbrudd, størrelsesgrenser, offentlig DNS, tilkoblingsfesting) og
  bygges inn før leverandørkallet. Jina-opprinnelige `{image:"https://..."}`-elementer videresendes som de er
  etter den samme kontrollen av offentlig HTTPS. Jina henter URL-en.
- Innebygde base64-medier er begrenset til 8 MiB dekodet per element og 16 MiB dekodet for hele forespørselen.

Leverandøroversettelse (kanoniske elementer videresendes aldri uendret):

- Multimodale Jina-modeller: Hvert element på øverste nivå blir ett modalitetsnøklet objekt
  (`text` / `image` / `audio` / `video` / `pdf`) som bruker data-URI-er for innebygde medier, med én vektor per
  element på øverste nivå.
- Gemini Embedding 2-familien: Én matrise på øverste nivå blir én opprinnelig
  `models/{model}:embedContent`-forespørsel med `content.parts` (`text` eller `inline_data`).
- llama.cpp (`llama-cpp/<model>`, enhver modell som den lokale serveren har lastet inn): Kanoniske `text`-elementer
  blir vanlige strenger, mens `image` / `audio` / `video` blir ett
  `{"content": [part]}`-objekt hver, ved bruk av llama-servers innholdsdeler for chat (`image_url`,
  `input_audio` med formatet `wav` / `mp3` / `flac`, `input_video`) med innebygde data, med én vektor
  per element på øverste nivå. Serveren må kjøre med `--embedding --mmproj …`; uten en projektor
  avviser den medier selv. `document` støttes ikke.
- Ukjente/dynamiske modeller uten eksplisitte metadata om modalitet avviser strukturerte inndata med HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Modell-/modalitetskombinasjoner som ikke støttes, returnerer HTTP 400 i stedet for å tvinge frem konvertering av elementet. Utvidelsesfelt som ikke er inndata
i eldre streng-/tokenforespørsler, fortsetter å sendes videre uendret.

```bash
# Vis alle embedding-modeller
GET /v1/embeddings
```

## Bildegenerering

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Tilgjengelige leverandører inkluderer OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (lokal), ComfyUI (lokal).

`n` returnerer `n` bilder i `data[]`. Leverandører der det overordnede API-et returnerer ett bilde per kall
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), får `n` separate overordnede kall, med maksimalt 4 samtidige. En
fast `seed` forskyves med kallindeksen (`seed`, `seed + 1`, …), slik at bildene er forskjellige, men fortsatt
reproduserbare. `n` er begrenset til 10. Forespørselen mislykkes i sin helhet hvis et kall mislykkes. Listen
over formater med utsplitting er `SINGLE_IMAGE_FANOUT_FORMATS` i
`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux gjenbruker den eksisterende API-nøkkeltilkoblingen og godtar prefiksene `zenmux/` eller `zm/`:

- `zenmux/openai/gpt-image-2` bruker ZenMux sitt OpenAI Images API. Alternativene inkluderer `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` og `response_format`.
- Andre utgivere, som `zm/meta/muse-image-1.0`, bruker ZenMux sitt Vertex AI-`:predict`-
  endepunkt. `n` tilordnes til `sampleCount`, `aspect_ratio` til `aspectRatio` og `image_size`
  (`1K`, `2K`, `4K`) til `sampleImageSize`. En pikselbasert `size` angir bare et sideforhold,
  ikke garanterte pikseldimensjoner. Støttede sideforhold, oppløsninger og antall varierer fra modell til modell.
- `zm/inclusionai/ming-image-0.1-design` velger sine egne dimensjoner. Utelat `size`,
  `aspect_ratio` og `image_size`; eksplisitte verdier returnerer HTTP 400. PNG, JPEG og WebP
  kan forespørres med `output_format`.

Denne integrasjonen støtter tekst-til-bilde-generering, ikke redigering av referansebilder. Utdata fra Vertex
normaliseres til `data[].b64_json`; `response_format: "url"` returnerer en overordnet
HTTPS-URL eller en base64-data-URL når bare bildebyte er tilgjengelig. Tomme/filtrerte utdata
returnerer en feil i stedet for et tomt vellykket svar. Modelltilgang avhenger av ZenMux-kontoen.
Se [ZenMux sitt Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) og
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image).

```bash
# Vis alle bildemodeller
GET /v1/images/generations
```

## OCR for dokumenter

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` velger OCR-leverandøren via et `provider/model`-prefiks; en modell-ID uten prefiks (f.eks.
`mistral-ocr-latest`) slås opp til den registrerte leverandøren, og hvis `model` utelates, brukes
Mistral (`mistral-ocr-latest`) som standard. Registrerte leverandører (`open-sse/config/ocrRegistry.ts`):

| Leverandør-ID                 | Modell-ID            | `model`-verdi                                                  | Merknader                                                                                                     |
| ----------------------------- | -------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (eller bare `mistral-ocr-latest`) | Synkron — svaret returneres direkte fra det ene overordnede kallet.                                           |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                    | Asynkront overordnet kall (`analyze` + avspørring) — se nedenfor.                                             |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                        | Synkront, via Vertex AI sitt partnerendepunkt `openapi/chat/completions` — se nedenfor for autentisering/URL. |

Alle tre leverandørene svarer med samme Mistral-formede innhold:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Avspørringsflyt for Azure Document Intelligence

Azure Document Intelligence sitt `analyze`-API er asynkront: Den opprinnelige forespørselen returnerer en
`Operation-Location`-header i stedet for innhold, og resultatet må avspørres. Håndtereren
(`open-sse/handlers/ocr.ts`) avspør denne URL-en hvert sekund i opptil 30 forsøk, avbryter umiddelbart (fortsetter
ikke avspørringen) ved et avspørringssvar som ikke er `ok`, eller en `"failed"`-status, og returnerer `504` hvis
operasjonen fortsatt kjører etter at antallet tillatte forsøk er brukt opp. Det endelige Azure-svaret
normaliseres til samme `pages`/`markdown`-form som brukes av Mistral, før det returneres til
kalleren, slik at klientkoden ikke trenger å spesialbehandle leverandøren.

### Autentisering og endepunktløsing for Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` gjenbruker den samme Vertex AI-autentiseringen som OmniRoute allerede støtter for
chat-/bildetrafikk (`open-sse/executors/vertex.ts`): API-nøkkelen til tilkoblingen er enten en
Service Account JSON-legitimasjon (som veksles inn i et kortvarig OAuth-tilgangstoken via JWT bearer-
flyten) eller et allerede utstedt OAuth-tilgangstoken som brukes direkte. URL-en til det overordnede endepunktet er Vertex sitt
generiske partnerendepunkt `openapi/chat/completions`, bygd fra prosjektet og
regionen til tilkoblingen — eksplisitte `providerSpecificData.project`/`providerSpecificData.region` har alltid prioritet;
ellers utledes prosjektet fra `project_id` i Service Account JSON, og regionen
settes som standard til `us-central1`. Begge oppslagene skjer i `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) og brukes av
`src/app/api/v1/ocr/route.ts` før videresending til `handleOcr`.

## List modeller

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ Returnerer alle chat-, innebyggings- og bildemodeller + kombinasjoner i OpenAI-format
```

### Modell-ID-prefikser (`?prefix=`)

De fleste modeller annonseres under et **leverandørprefiks**. Hvilket prefiks du får, styres av
funksjonsflagget `MODELS_CATALOG_PREFIX_MODE`, og kan overstyres **per forespørsel** med en
spørringsparameter – nyttig for en klient som ønsker en ryddig liste uten å endre den globale
serverinnstillingen for alle andre:

```bash
GET /v1/models?prefix=alias        # én ID per modell – det korte aliasprefikset
GET /v1/models?prefix=dual         # begge former (serverstandard)
GET /v1/models?prefix=canonical    # bare det fullstendige leverandør-ID-prefikset
```

| Modus       | Genererer                                                | Merknader                                                                                                                                                                                       |
| ----------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **og** `claude/claude-sonnet-4-6` | **Standard.** Begge ID-ene rutes til samme modell. Dette beholdes slik at klientkonfigurasjoner som har hardkodet en av formene, fortsatt fungerer. Omtrent dobler katalogen.                   |
| `alias`     | `cc/claude-sonnet-4-6`                                   | Én oppføring per modell. Leverandører uten et eget alias genererer fortsatt oppføringen sin, så ingenting går tapt.                                                                             |
| `canonical` | `claude/claude-sonnet-4-6`                               | Én oppføring per modell under det fullstendige leverandør-ID-prefikset. Leverandører uten et eget alias (f.eks. `antigravity/…`, `agy/…`) genererer også sin ene ID her, så ingenting går tapt. |

Et speil i `dual`-modus kan også gjenkjennes uten spørringsparameteren: Det har et `parent`-felt
som peker på den primære ID-en.

Klienter som viser en modellvelger, bør be om `?prefix=alias` – dette er hva
[OmniCopilot-utvidelsen for VS Code](../guides/VSCODE-COPILOT.md) gjør.

### Oppdagelsesfiltre (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` godtar valgfrie oppdagelsesfiltre. Uten noen av dem er svaret
uendret. De avgrenser katalogen som innringeren allerede kan se (API-nøkkeltillatelser brukes først),
og de kjøres før OpenAI-lignende paginering med `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # alle oppførte egenskaper må være sanne
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # katalogens `type`; rader uten en slik er `chat`
GET /v1/models?q=sonnet&limit=10                           # treff på ID eller navn uten hensyn til store og små bokstaver
```

| Parameter     | Verdier                                                                                             |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | ikke-negativt heltall, sammenlignet med `context_length`                                            |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 tegn                                                                                          |

En ukjent verdi, eller en `min_context` som ikke er et ikke-negativt heltall (for eksempel `1.5`),
returnerer HTTP `400`, og meldingen viser de gyldige verdiene. Implementasjon:
`src/app/api/v1/models/catalogFilters.ts`.

### Kortliste over modeller (`POST /v1/models/query`)

`POST /v1/models/query` returnerer en kort, deterministisk liste fra den samme katalogen, med samme
autentisering og synlighet per nøkkel som `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Alle felter er valgfrie. `capabilities` og `exclude` tar en matrise eller en kommadelt streng.
`max_output` sammenlignes med `max_output_tokens`. Resultatene sorteres etter `owned_by`, deretter `id`.
`limit` er som standard `20`, og verdier over `100` begrenses til `100`. Ugyldig JSON, et ukjent
felt eller en ugyldig verdi returnerer HTTP `400`.

### Individuelt skjulte chatmodeller

En modell som er merket **Skjult** på leverandørsiden, utelates fra katalogen og avvises
med HTTP `404` / `model_not_found` når den forespørres eksplisitt. Kontrollen bruker den løste
leverandøren og modellen, inkludert leverandøraliaser, nodeprefikser for kompatible leverandører og
standardverdier for tilkoblinger. En kombinasjon hopper over skjulte mål og kan bruke et synlig søsken. Når
ingen kjørbare mål gjenstår, returnerer den samme feilkode. Oppheving av skjuling trer i kraft ved neste
forespørsel. Synlighetsoverstyringer kun for bilder skjuler ikke chatmodellen med samme ID.

Denne individuelle modellinnstillingen er atskilt fra
[tillatelses-/avvisningslistene for modelleksponering](../routing/MODEL_EXPOSURE_LIST.md), som filtrerer katalogannonsering
og kandidater for automatisk ruting, samtidig som eksplisitt videresending beholdes. Modelltillatelser for API-nøkler
gjelder fortsatt uavhengig. Standard prefiksmodus for katalogen er fortsatt `dual`.

### Modellvarianter uten tenkning

For Claude-modeller som støtter tenkning, annonserer `/v1/models` også en **uten-tenkning**-variant der ID-en har prefikset `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Hvis du velger denne ID-en (f.eks. i en Claude Code-konfigurasjon som alltid legger ved en `thinking`-blokk), løses den tilbake til den faktiske `<provider>/<model>` med resonnering deaktivert — `thinking:{type:"disabled"}` på `/v1/messages`-endepunktet, eller ved at feltene `reasoning`/`reasoning_effort` utelates på `/v1/chat/completions`-endepunktet. Varianten vises bare for modeller i Claude-familien som støtter tenkning **og** respekterer `disabled` (så f.eks. modeller som kun støtter adaptiv tenkning og avviser `disabled`, er utelatt). Operatører kan slå varianten på eller av eksplisitt for hver modell via `ModelSpec.noThinkingAlias`.

## ElevenLabs-lydgenerering

Konfigurer en `elevenlabs`-leverandørtilkobling i OmniRoute med ElevenLabs-API-nøkkelen din.
Klienter autentiserer seg med **OmniRoute**-nøkkelen sin (`Authorization: Bearer $OMNIROUTE_API_KEY`);
gatewayen oppgir den lagrede leverandørnøkkelen som `xi-api-key`. Send aldri en ElevenLabs-nøkkel
som gatewayens bearer-token.

| Metode | Bane                        | Respons                                       | Endepunktkategori for API-nøkkel |
| ------ | --------------------------- | --------------------------------------------- | -------------------------------- |
| POST   | `/v1/sound-generation`      | Opprinnelige lydbyte                          | `elevenlabs`                     |
| POST   | `/v1/music`                 | Opprinnelige lydbyte                          | `music`                          |
| POST   | `/v1/music/stream`          | Strømmende lydbyte                            | `music`                          |
| POST   | `/v1/music/detailed`        | Opprinnelig multipart-lyd og komposisjonsplan | `music`                          |
| POST   | `/v1/music/detailed/stream` | Opprinnelige SSE-metadata og lyddatablokker   | `music`                          |
| POST   | `/v1/music/plan`            | JSON-komposisjonsplan                         | `music`                          |

Disse endepunktene supplerer de eksisterende rutene `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` og `/v1/speech-to-text`. Opprinnelige JSON-felt
og spørringsparametere som `output_format` og `enable_logging` bevares.
Responser fra `/v1/music/detailed` beholder multipart-grensene sine; analyser dem som multipart.
`/v1/music/detailed/stream` returnerer `text/event-stream` med komposisjonsmetadata og
base64-kodede lyddatablokker i SSE-hendelser. Alle seks rutene støtter CORS-preflight.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# En kort lydeffekt. Varighet: 0,5 til 30 sekunder.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Musikkvarighet angis i millisekunder: 3000 til 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Bruk `/v1/music/stream` med samme JSON-innhold for trinnvis lydoverføring. Komposisjon
godtar nøyaktig én av `prompt` eller `composition_plan`; `/v1/music/plan` krever `prompt`
og godtar valgfritt `source_composition_plan`. De opprinnelige skjemaene bevarer ytterligere
leverandørfelt, slik at versjoner av komposisjonsplaner og finjusteringsalternativer når ElevenLabs.

Det enhetlige endepunktet `/v1/music/generations` godtar også `elevenlabs/music_v1`,
`elevenlabs/music_v2` og `elevenlabs/music_v2_5`. Med en aktiv ElevenLabs-tilkobling
eksponeres disse modellene av musikkatalogen. Dette endepunktet returnerer
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Feltet `duration` angis i
sekunder og tilordnes `music_length_ms`; en eksplisitt `music_length_ms` har forrang.
`instrumental` tilordnes `force_instrumental`, der det opprinnelige feltet har forrang.
Bruk de opprinnelige strømmeendepunktene for strømming og det opprinnelige komposisjonsendepunktet
for forespørsler som bare er basert på en komposisjonsplan.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Begrensninger for endepunkt, modell, budsjett og tilkobling gjelder før et oppstrømskall. Opprinnelige
ruter returnerer oppstrøms statuskoder og feilmeldinger uendret, inkludert `402` for en
abonnementsbegrensning og `429` for en kvotegrense. Hodene `character-cost`, `song-id`, `request-id` og `retry-after`
bevares når de finnes. En gratis kredittsaldo garanterer ikke tilgang til alle
musikkmodeller, utdataformater eller API-funksjoner: ElevenLabs avgjør tilgangsrettighetene for hver forespørsel.
Det enhetlige endepunktet bevarer feilstatuskoder i OmniRoutes normaliserte feilkonvolutt.

Oppstrømskontrakter: [lydeffekter](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[musikkkomposisjon](https://elevenlabs.io/docs/api-reference/music/compose) og
[detaljer for strømming av musikk](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

> (oMLX, vLLM, Infinity, TEI bak en gateway, …) adressert som `<node-prefix>/<model>`. Tilbakekoblingsnoder
> (`localhost`, `127.0.0.1`, `172.16.0.0/12`) er alltid kvalifiserte, og det samme gjelder vertsnavn som
> operatøren oppgir i `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (f.eks. et Docker/Compose-tjenestenavn som
> `http://reranker:8080/v1`; disse kalles direkte, aldri via `HTTP(S)_PROXY` eller en tilkoblings
> fastlåste proxy). Noder på alle andre
> verter — en maskin på lokalnettet eller en Tailscale-node — er bare kvalifiserte når operatøren aktiverer
> funksjonsflagget `RERANK_REMOTE_PROVIDER_NODES` **og** nodens basis-URL består leverandørens
> policy for utgående URL-er (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Minnefunksjonens omrangeringstrinn kaller denne ruten via
> tilbakekobling, så den samme regelen gjelder for `rerankProviderModel` i minneinnstillingene.
>
> **Lokale serverformater:** noden kalles på `<base>/v1/rerank` og, ved 404, på `<base>/rerank`
> (Infinity, TEI). Den oppstrøms forespørselskroppen inneholder både Cohere/OpenAI-skrivemåten (`documents`,
> `return_documents`) og TEI-skrivemåten (`texts`, `return_text`), og den oppstrøms responsen
> normaliseres til Cohere-konvolutten: TEIs rene `[{index, score, text}]`, `{results: [{index, score}]}`
> fra enkle gatewayer og Voyage-formatet `{data: [...]}` returneres alle til klienten som
> `{results: [{index, relevance_score, document?}]}`, sortert etter poengsum og begrenset til `top_n`.

> **Oppdagelse av leverandørnoder:** modeller på en OpenAI-kompatibel leverandørnode vises i `GET /v1/models`
> under nodeprefikset. Rader uten endepunktmetadata (typisk for lokale `/v1/models`-oppføringer)
> arver nodens `apiType`, slik at modellene til en `embeddings`-node får `type: "embedding"` og modellene til en
> `rerank`-node får `type: "rerank"` i stedet for å bruke chat som standard; et eksplisitt
> `supportedEndpoints` i en synkronisert eller manuelt lagt til rad har fortsatt forrang.

### Exa og Tavily `provider_options`

Exa og Tavily leser leverandørspesifikke felt fra en navngitt samling:
`provider_options.exa` (eller `provider_options["exa-search"]`) og `provider_options.tavily`
(eller `provider_options["tavily-search"]`). Bare nøklene nedenfor videresendes. Hver enkelt
kontrolleres mot sitt eget Zod-skjema i `open-sse/handlers/search/providerOptionsPassthrough.ts`,
og en nøkkel med feil type forkastes. Alle andre nøkler ignoreres, inkludert autentisering, basis-URL,
`stream` og `outputSchema`. De flate nøklene som brukes av andre leverandører (`cx`, `depth`, ...), fungerer
som før.

| Leverandør | Felt på toppnivå                                                                                                                                                                                                                                                                                                                                                          | Nestet                                                                                                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa        | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (flate primitive verdier), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                      | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` slås sammen over standardverdien `{ text: true, highlights: true }` |
| Tavily     | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                          |

De generiske feltene har alltid prioritet: `query`, `max_results`, `filters` (domener), `country` og
emnet som utledes fra `search_type`. For Exa beholder `search_type: "news"` verdien `category: "news"`.
Tavily godtar også `search_type: "finance"` (`topic: "finance"`).

Det generiske `time_range` når nå begge leverandørene: Exa får `startPublishedDate` (ISO-
tidsstempel), og Tavily får `start_date` (`YYYY-MM-DD`). En eksplisitt dato i `provider_options`
overstyrer den tilordnede datoen.

Exa-resultater beholder `id`, `highlight_scores`, `summary`, `subpages`, `entities` og `extras` i
`provider_raw`. Tavily-resultater beholder `images` og `favicon`.

Kostnadsberegningen bruker fortsatt det flate registeret `costPerQuery`. Tavily fakturerer
`search_depth: "advanced"` med flere kreditter per kall, og denne forskjellen gjenspeiles ikke i
`usage.search_cost_usd`.

## Web Fetch API

Hent innhold fra en URL via en konfigurert webhentingsleverandør (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, samme API-nøkkel som Parallel Search) returnerer kun
Markdown — alle andre `format` gir en `400` — og begrenser innholdet til 100 000 tegn. Når
selve målsiden ikke kan ekstraheres, rapporterer oppstrømstjenesten dette i en HTTP 200;
OmniRoute videreformidler det som en `422` med en fast melding.

| Metode | Bane            | Beskrivelse                                                     |
| ------ | --------------- | --------------------------------------------------------------- |
| POST   | `/v1/web/fetch` | Hent/skrap en URL — brødteksten valideres av `v1WebFetchSchema` |

**Autentisering:** Bearer-API-nøkkel (`extractApiKey` + `isValidApiKey`). Retningslinjene håndheves via `enforceApiKeyPolicy`.

**Kvotebevisst reserveleverandør (#8297):** Når ingen eksplisitt `provider` er angitt,
gjennomgås utvalget (`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) i
fast
prioritetsrekkefølge (fyll-først) — en hastighetsbegrenset, men konfigurert leverandør hoppes over
i stedet for å avbryte forespørselen, og en ny forsøksbar oppstrøms-/kvotefeil
(HTTP 429 alltid; 402/403 for kvotebaserte gratisnivåer hos Firecrawl/Tavily/TinyFish —
ikke for Jina Reader, og aldri for en vanlig 400-feilaktig forespørsel) går videre til den
neste uprøvde leverandøren med konfigurert legitimasjon på forespørselstidspunktet. Når alle leverandørene i
utvalget er oppbrukt, returnerer endepunktet én enkelt `429` (med en `Retry-After`-
header) i stedet for den tidligere generiske `400`. Når en eksplisitt `provider` er
forespurt, finnes det **ingen** stille reserveleverandør — en hastighetsbegrenset eller sviktende eksplisitt
leverandør videreformidler sin egen feil (`429` hvis den er hastighetsbegrenset, ellers oppstrøms-
statusen).

## WebSocket-strømming

```bash
GET /v1/ws?handshake=1
```

Validerer en WebSocket-oppgraderingshåndtrykk og returnerer eksempelmeldingene for nettprotokollen (`request`, `cancel`). Faktiske WS-rammer håndteres av den medfølgende WS-serveren utenfor Next.js-rutetabellen.

**Autentisering:** Bearer-API-nøkkel under håndtrykket.

### Responses API over WebSocket (kun codex)

```bash
# Samme vert:port som HTTP-API-et (standard 20128); oppgrader tilkoblingen:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (eller: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Første ramme MÅ være response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

En Responses-API-over-WebSocket-proxy er koblet **utelukkende til `codex`** (ChatGPT-
bakenden). Den lytter på samme port som API-et/kontrollpanelet på banene `/v1/responses`,
`/responses` og `/api/v1/responses`. Ved den første `response.create`-rammen
autentiserer og klargjør den via den interne `codex-responses-ws`-broen, velger en
codex OAuth-tilkobling og oppretter en tunnel til `wss://chatgpt.com/backend-api/codex/responses`
via `wreq-js`-transporten. **Modeller som ikke er codex, avvises** (`codex_ws_provider_required`).
For kvotedelingsruting bruker du `model: "qtSd/<group>/codex/<model>"`. Implementert i
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Autentisering:** Bearer-API-nøkkel under håndtrykket. Den medfølgende HTTP-serveren (`server-ws.mjs`)
må være det aktive startpunktet (noe den er som standard når `app/server-ws.mjs` finnes).

#### Modell-ID: bruk den rene ChatGPT-ID-en (uten `codex/`-prefiks)

OpenAI **Codex CLI** validerer modellnavnet på klientsiden når
`supports_websockets = true` og **avviser leverandørprefiksede ID-er** som
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Send den **rene** ID-en (f.eks. `gpt-5.5`). OmniRoutes bro er
kun for codex, så den løser en ren ID på nytt som en codex-modell
(`resolveCodexWsModelInfo`) før den oppretter tunnelen til oppstrømstjenesten — selv om en ren
`gpt-5.5` ellers ville blitt rutet til en annen leverandør over HTTP.

#### Konfigurere OpenAI Codex CLI

Rett Codex CLI mot OmniRoute ved å legge til en egendefinert leverandør med WebSocket-
støtte i `~/.codex/config.toml` (bruk en separat `CODEX_HOME` for å unngå å endre
en eksisterende konfigurasjon):

```toml
model = "gpt-5.5"                 # ren ID — IKKE "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # ingen avsluttende skråstrek; WS-URL-en avledes (bruk https/wss i produksjon)
wire_api = "responses"                    # eneste støttede verdi siden feb. 2026
supports_websockets = true                # aktiverer Responses-over-WS-transporten
env_key = "OMNIROUTE_API_KEY"             # inneholder OmniRoute-API-nøkkelen (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # en OmniRoute-API-nøkkel (valgfri nøkkel hvis REQUIRE_API_KEY=false)
codex exec "Responda apenas: PONG"
```

CLI-et oppgraderer `base_url + /responses` til en WebSocket, og OmniRoute oppretter en tunnel
til den valgte codex OAuth-tilkoblingen. Validert fra ende til ende mot den lokale
serveren: ChatGPT returnerer `codex.rate_limits` + `response.created` og strømmer
fullføringen.

## Selvbetjent bruksinformasjon (`/api/usage/om-usage`)

Enhver API-nøkkel kan lese **sin egen** bruk og sine egne kvoter — ingen administrasjonsautentisering kreves. Dette er endepunktet en
klient (CLI, OmniCopilot-panelet) bruker for å vise en nøkkelinnehaver vedkommendes forbruk.

```bash
# Tekstformat (den historiske kontrakten — ren tekst for en terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Strukturert format — det et brukergrensesnitt bruker
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Nøkkelen må ha **`allowUsageCommand`** aktivert (deaktivert som standard — API-nøkkelbehandlingen i
instrumentpanelet slår dette av eller på for hver nøkkel). Uten dette svarer endepunktet med `403`.

`?format=json` returnerer en diskriminert struktur, slik at en kallende part aldri leser et datafelt fra en
avvisning. Ved suksess:

```jsonc
{
  "allowed": true,
  // finnes bare når nøkkelen har aktivert bruksgrenser per nøkkel (daglig/ukentlig i USD):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // kvoteøyeblikksbildet for den valgte leverandøren, eller null når ingenting er mellomlagret ennå:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // øyeblikksbildet for hver tilkobling, slik at et brukergrensesnitt kan vise flere leverandører side om side:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Ved avvisning (`401` ugyldig nøkkel / `403` ikke tillatt) returnerer den samme ruten
`{ "allowed": false, "error": { "message": "…" } }` — et eksisterende, men tomt `personal`/`provider`
(nøkkelen er tillatt, men ingenting er registrert ennå) er en annen tilstand enn en avvisning, og bare JSON-formatet
skiller mellom dem.

**Autentisering:** den kallende partens egen Bearer-API-nøkkel, validert med `isValidApiKey` — dette er _ikke_
administrasjonsgrensesnittet (`/api/keys/…`), som fortsatt er beskyttet av `requireManagementAuth`.

### Rå kontra stoppgrensejusterte kvoteprosenter

Ved bruk av `/api/usage/om-usage` bør kallende parter merke seg forskjellen mellom prosentene som vises i
**ren tekst** og den strukturerte **JSON-utdataen**:

| Aspekt                          | Rent tekstformat (`/api/usage/om-usage` / `@@om-usage`)                                       | JSON-format (`?format=json`)                                                           |
| :------------------------------ | :-------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------- |
| **Utdatafelt**                  | `NN% left` (f.eks. `20% left`)                                                                | `provider.quotas` / `providers[].quotas`                                               |
| **Måling**                      | **Stoppgrensejustert brukbar kvote**: gjenværende kapasitet over stoppgrensen                 | **Rå oppstrømskvote**: ujustert måling fra leverandøren                                |
| **Skalering etter stoppgrense** | Skalert via `effectiveRemainingPercent()` slik at den beskyttede reserven vises som `0% left` | Ingen (rå øyeblikksbildeverdier slik de rapporteres av leverandøren)                   |
| **Terskeldata**                 | Inkludert i den viste prosenten                                                               | Lagret i `quotaWindowThresholds` per tilkobling (eller serverstandarder)               |
| **Primær forbruker**            | Interaktive CLI-er, terminalledetekster, menneskelige operatører                              | Programmatiske integrasjoner, instrumentpaneler, analyseverktøy og faktureringssporere |

#### Formelen for justering etter stoppgrense

OmniRoute støtter proaktive stoppgrenser for kvoter for å forhindre at oppstrømskvoten blir uttømt (konfigurert via tilkoblingens
`quotaWindowThresholds`, leverandørstandarder eller globale innstillinger for robusthet). Når en stoppgrense
(f.eks. `cutoff = 25%`) er aktiv for et kvotevindu, beregner tekstgjengivelsen gjenværende kvote slik:

- Hvis `remaining <= cutoff`: returneres `0%`.
- Hvis `remaining > cutoff`: returneres `((remaining - cutoff) / (100 - cutoff)) * 100`.

Den formaterte tekstutdataen avrunder dette til nærmeste heltall (`Math.round(...)`).

#### Illustrerende eksempel

Tenk deg et leverandørvindu med **60 % rå bruk** (og dermed **40 % rå gjenværende kvote**) og en konfigurert
**stoppgrense på 25 % gjenværende kvote**:

| Representasjon               | Beregning                                          | Gjenværende |              Implisitt brukt               |
| :--------------------------- | :------------------------------------------------- | :---------: | :----------------------------------------: |
| **Rå JSON (`?format=json`)** | Oppstrømsøyeblikksbilde (`quotas[window]`)         |  **40 %**   |                  **60 %**                  |
| **Tekstformat (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20 %**   | **80 %** (hvis `100 - remaining` beregnes) |

- **Hvorfor teksten viser 20 % igjen:** Av de 40 % av den fysiske kvoten som er igjen på kontoen, er 25 % reservert av
  stoppgrensepolicyen. Den kallende parten har bare 15 % av 75 % brukbar margin igjen før ruteren slutter
  å rute til denne tilkoblingen. Skaleringen sikrer at tilkoblingen signaliserer uttømming (`0% left`) nøyaktig når
  rutingen opphører.
- **Hvorfor JSON bevarer råverdiene:** JSON-nyttelasten returnerer det nøyaktige øyeblikksbildet fra leverandøren (`UsageSnapshot`),
  slik at eksterne verktøy får tilgang til den faktiske oppstrømsutnyttelsen og
  `quotaWindowThresholds` på tilkoblingsnivå uten tapsbringende skalering på serversiden.

#### Veiledning for migrering av forbrukere

Hvis en ekstern integrasjon (for eksempel en programtillegg for et redigeringsprogram eller en agentutvidelse) tidligere hentet data fra tekstendepunktet
(`NN% left`) og beregnet brukt prosentandel som `100 - NN`, innebærer migrering til `?format=json` følgende:

- Avlesning av rå JSON-verdier gjenspeiler **faktisk oppstrømsforbruk** (60 % brukt i eksemplet ovenfor).
- Hvis integrasjonen ønsker å bevare tekstendepunktets semantikk for brukbar kvote, kan den evaluere
  formelen for effektiv gjenværende kvote på klientsiden ved hjelp av `quotaWindowThresholds` for overstyringer på tilkoblingsnivå.

## Semantisk hurtigbuffer

```bash
# Hent hurtigbufferstatistikk
GET /api/cache/stats

# Tøm alle hurtigbuffere
DELETE /api/cache/stats
```

Eksempel på respons:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Innvirkning på ventetid

Et TREFF i den semantiske hurtigbufferen leverer responsen fra hurtigbufferen **uten et oppstrømskall**, så den rapporterte `X-OmniRoute-Response-Latency` er nær null
(uavhengig av den opprinnelige oppstrømsventetiden). Klienter som er følsomme for
ventetid (ytelsestesting, p50/p99-overvåking), bør kontrollere
responsheaderen `X-OmniRoute-Cache-Latency`:

| Verdi       | Betydning                                                                |
| ----------- | ------------------------------------------------------------------------ |
| `synthetic` | Respons levert fra hurtigbufferen; ventetiden er ikke reell oppstrømstid |
| _(mangler)_ | Respons fra et reelt oppstrømskall                                       |

### Omgå hurtigbuffer per nøkkel

API-nøkler kan velge bort lesing fra den semantiske hurtigbufferen via `cacheDefaultMode`:

| Verdi    | Virkemåte                                                          |
| -------- | ------------------------------------------------------------------ |
| `legacy` | Normal hurtigbufferatferd (standard)                               |
| `bypass` | Hopp over hurtigbufferoppslag helt; bruk alltid oppstrømstjenesten |

Angi ved opprettelse av nøkkel (`POST /api/keys`) eller oppdatering (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Omgå hurtigbuffer per forespørsel

Alle forespørsler kan omgå hurtigbufferen uavhengig av nøkkelinnstillingene:

```
X-OmniRoute-No-Cache: true
```

For synkroniserte/importerte modeller godtar `PUT /api/provider-models` `provider`, `modelId` og

Egendefinerte Chat Completions-noder tilpasser eksplisitte bortvalg av resonnering til oppstrømsserveren. En
vellykket tilkoblingstest velger automatisk kontroller for chatmaler for hver eksakte modell-ID
der `/models`-oppføringen dokumenterer en gjenkjent `owned_by`-verdi: `vllm`, `sglang` eller `llamacpp`.
Transparente OpenAI-kompatible innpakninger kan bevare den opprinnelige modelloppføringen i et nøstet
`openai`-objekt; deteksjonen følger opptil tre slike lag. Modeller med manglende, ukjent eller
motstridende eierskap beholder vanlig OpenAI-atferd. Deteksjonen gjenbruker den eksisterende katalogforespørselen,
genererer ingen fullføringstokener og ugyldiggjøres når endepunktet for tilkoblingen endres.

For å låse atferden for en oppstrømsserver som ikke eksponerer disse metadataene, bruker du det eksisterende API-et
for delvis oppdatering av leverandører:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Send denne forespørselskroppen med `PUT /api/providers/<connection-id>`. På denne tilkoblingen sendes en eksplisitt
resonneringsinnsats på `none` som `chat_template_kwargs.thinking=false` og
`chat_template_kwargs.enable_thinking=false`. Eksplisitte innebygde malverdier forblir autoritative,
med mindre en resonneringsregel på serversiden fremtvinger en innsats. Innstillingen gjelder bare når en egendefinert
OpenAI-kompatibel tilkobling sender en Chat Completions-forespørselskropp. Responses-forespørsler og ordinære
leverandører beholder sitt opprinnelige forespørselsformat. Sett `reasoningControl` til `openai` for å fremtvinge vanlig OpenAI-
videreformidling av `reasoning_effort`, eller utelat den / sett den til `null` for å bruke automatisk deteksjon.

Klassifiseringsforespørsler i Claude Code-automodus deaktiverer innebygd tenkning som standard når de ikke inneholder
eksplisitte resonneringskontroller. Deteksjonen bruker klassifiseringens systemmarkør i forespørsler i Claude-format,
ikke modellnavn eller fullføringsgrenser. Eksplisitte kontroller i forespørselskroppen, støttede innsats-/tenkningsheadere,
rutingsregler og modellens fastsatte innsats beholder sin eksisterende prioritet. Begge klassifiseringsstadiene
beholder sine ledetekster, fullføringsgrenser, stoppsekvenser og reelle tillatelsesavgjørelser fra oppstrømsserveren.
Det andre stadiet kan fortsatt produsere den forespurte synlige resonneringen som vanlig tekst.

### Versjon og utgivelseskanal

```bash
GET /api/system/version
```

Administrasjonsrute kun for loopback (administratorautentisering). Returnerer den kjørende versjonen, den nyeste
publiserte versjonen og statusen for automatisk oppdatering. `releaseChannel` og `channels` er additive
felt (spor 3.8.54); `channel` beholder betydningen sin — distribusjonsmodusen som kontrollpanelets oppdateringsfunksjon
bruker (`npm`, `source` eller `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — npm-kanalen for det kjørende bygget: `nightly` for `-nightly.*`-versjoner,
  `next` for andre forhåndsutgivelser (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` for en stabil versjon av en
  eldre hovedversjon enn `channels.latest`, ellers `latest`. Samme regler som
  `scripts/release/dist-tag.mjs`, som velger npm-dist-taggen ved publisering.
- `channels` — den publiserte toppversjonen for hver dist-tag, fra `npm view omniroute dist-tags` (reserve via
  registerets HTTP-grensesnitt), bufret med samme TTL på 10 minutter som `latest`. `latest` er alltid til stede
  (faller tilbake til feltet `latest`, deretter `"unavailable"`); `next`, `nightly` og `lts` vises
  bare når den aktuelle dist-taggen finnes. En forespørsel med `Cache-Control: no-cache` oppdaterer begge oppslagene.

Kanalmodellen (`latest` = v3 frem til 4.0 GA, `next` = rc, `nightly` = bygg fra `develop`,
`lts` = v3-oppdateringer etter 4.0 GA) er beskrevet i `docs/ops/RELEASE_STRATEGY.md`.

## Tokeniserte VS Code-aliaser / aliaser uten headere

Bruk disse aliasene når en integrasjon ikke kan legge til en `Authorization`-header og trenger at API-nøkkelen er innebygd i basis-URL-en.

```bash
# Katalogalias i OpenAI-stil
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# Chat-aliaser i OpenAI-stil
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Aliaser i Ollama-stil
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

Eksempel:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

Merknader:

- De tokeniserte aliasene gjenbruker de samme behandlerne som `/v1/*` og `/api/tags`; svarformatene forblir identiske.
- Foretrekk `Authorization: Bearer ...` når klienten støtter egendefinerte headere.
- URL-baserte tokener kan vises i logger fra reverse proxy-er, nettleserhistorikk og telemetri utenfor OmniRoute. Behandle dem som et kompatibilitetsalternativ, ikke som standard autentiseringsmetode.

## Tokengrenser

**Tokenbudsjetter** per API-nøkkel (atskilt fra det USD-baserte budsjettet ovenfor). Håndheves direkte i forespørselsflyten: Når bruken i nøkkelens gjeldende vindu når grensen, avvises forespørsler med `429 Too Many Requests`. Grenser kan avgrenses til en bestemt `model`, en `provider` eller gjelde `global`t for hele nøkkelen. Når flere grenser samsvarer med en forespørsel, gjelder den mest restriktive.

```bash
# Vis tokenbegrensningene for en nøkkel (inkluderer gjeldende bruk i vinduet)
GET /api/usage/token-limits?apiKeyId=key-123

# Opprett eller oppdater en tokengrense
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Slett en tokengrense etter id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Skjemamerknader** (`setTokenLimitSchema`): `apiKeyId` og `scopeType` (`model` | `provider` | `global`) er obligatoriske. `scopeValue` er obligatorisk med mindre `scopeType` er `global` (f.eks. en modell-id for `model`-omfang eller en leverandør-id for `provider`-omfang). `tokenLimit` må være et positivt heltall (konverteres fra streng). Valgfritt: `id` (utelat for å opprette, oppgi for å oppdatere), `resetInterval` (`daily` | `weekly` | `monthly`, standardverdi `monthly`), `resetTime` (`HH:MM`), `enabled` (standardverdi `true`). `GET`-svar utvider hver grense med `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` og `nextResetAt`. Dette er et endepunkt i administrasjonsklassen (autentisering håndheves sentralt av autorisasjonsflyten).

## Behandling av forespørsler

1. Klienten sender en forespørsel til `/v1/*`
2. Rutebehandleren kaller `handleChat`, `handleEmbedding`, `handleAudioTranscription` eller `handleImageGeneration`
3. Modellen slås opp (direkte leverandør/modell eller alias/kombinasjon)
4. Påloggingsopplysninger velges fra den lokale databasen med filtrering etter kontotilgjengelighet
5. For chat kontrollerer `handleChatCore` semantisk cache/signaturcache og slår opp komprimeringsinnstillingene for kombinasjonen
6. Proaktiv komprimering kjøres før leverandøroversettelse når dette er aktivert (`lite`, Caveman, RTK eller stablet)
7. Leverandørutføreren sender forespørselen oppstrøms
8. Svaret oversettes tilbake til klientformatet (chat) eller returneres som det er (innebygginger/bilder/lyd)
9. Bruk, komprimeringsanalyse og forespørselslogger registreres
10. Reservehåndtering brukes ved feil i henhold til kombinasjonsreglene

Fullstendig arkitekturreferanse: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Robusthet (utvidet)

OmniRoute tilbyr tre uavhengige mekanismer for midlertidige feil. Administrasjonsendepunktene nedenfor lar operatører lese og overstyre dem:

| Omfang               | Tilstandslagring                             | Les                                       | Tilbakestill / tøm                                     |
| -------------------- | -------------------------------------------- | ----------------------------------------- | ------------------------------------------------------ |
| Leverandørsikring    | `domain_circuit_breakers` + i minnet         | `/api/monitoring/health`                  | `POST /api/resilience/reset`                           |
| Tilkoblingskarantene | `rateLimitedUntil` på leverandørtilkoblinger | `/api/rate-limits`, `/api/providers/[id]` | (aktiveres igjen ved behov; tøm via leverandørens PUT) |
| Modellsperre         | Modelltilgjengelighetsregister i minnet      | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`               |

`PATCH /api/resilience` godtar overstyringer av leverandørsikringer under `providerBreaker.oauth` og `providerBreaker.apikey`. Hver profil støtter `degradationThreshold`, `failureThreshold` og `resetTimeoutMs`. De samme feltene er tilgjengelige under Dashboard → Settings → Resilience.

```bash
# Tøm én enkelt modellsperre
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Tøm alle sperrer
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Du finner en fullstendig konseptuell referanse og standardverdiene for sikringene i [`CLAUDE.md`](../../CLAUDE.md) → «Tilstand for robusthetskjøring» og [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Kø for hastighetsbegrensning og sikkerhetsnett for automatisk aktivering

- **Støttet skrivesti**: `POST /api/rate-limits` med innholdet `{"connectionId": "<id>", "enabled": true|false}` er det støttede administrasjonsendepunktet for å slå beskyttelse mot hastighetsbegrensning av eller på for en tilkobling. `PUT /api/providers/[id]` endrer eller veksler bevisst ikke `rateLimitProtection` (#11278).
- **Semantikken til `enabled: false`**: Hvis `enabled: false` angis, fjernes eksplisitt beskyttelse for tilkoblingen, men dette **unntar ikke** en aktiv API-nøkkeltilkobling fra det globale sikkerhetsnettet for automatisk aktivering (`autoEnableApiKeyProviders = true`). I `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) er `false` og `undefined` likeverdige. Aktive API-nøkkeltilkoblinger uten eksplisitt beskyttelse forblir beskyttet av sikkerhetsnettet for automatisk aktivering.
- **Global deaktivering**: Hvis API-nøkkeltilkoblinger skal kjøres uten køer for hastighetsbegrensning, deaktiverer du sikkerhetsnettet globalt via `RATE_LIMIT_AUTO_ENABLE=false` (miljøvariabel) eller `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`).

## A2A-server

OmniRoute eksponerer et A2A-endepunkt (agent-til-agent) for JSON-RPC 2.0 samt et REST-grensesnitt for inspeksjon og bruk i kontrollpanelet.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # valgfritt med mindre OMNIROUTE_API_KEY er angitt
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Støttede metoder (alle styres av `settings.a2aEnabled`):

| Metode           | Beskrivelse                                                         |
| ---------------- | ------------------------------------------------------------------- |
| `message/send`   | Synkron ferdighetskjøring; returnerer `{task, artifacts, metadata}` |
| `message/stream` | Strømmende SSE-kjøring av det samme ferdighetssettet                |
| `tasks/get`      | Hent en oppgave etter `taskId`                                      |
| `tasks/cancel`   | Avbryt en oppgave etter `taskId`                                    |

Innebygde ferdigheter: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Agentkort

```bash
GET /.well-known/agent.json
```

Returnerer det offentlige A2A-agentkortet (navn, beskrivelse, funksjoner, ferdighetskatalog, autentiseringsmetode) — bufres offentlig i 1 time. Ingen autentisering kreves.

### REST-hjelpere

| Metode | Bane                         | Beskrivelse                                                                                                       |
| ------ | ---------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/a2a/status`            | A2A aktivert + oppgavestatistikk + bufret sammendrag av agentkort                                                 |
| GET    | `/api/a2a/tasks`             | Vis oppgaver — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (Ikke implementert som en REST-hjelper — opprett via JSON-RPC `message/send`)                                     |
| GET    | `/api/a2a/tasks/[id]`        | Hent én oppgave                                                                                                   |
| POST   | `/api/a2a/tasks/[id]/cancel` | Avbryt en oppgave                                                                                                 |

**Autentisering:** REST-hjelperne kjører uten administrasjonsautentisering (kan leses av kontrollpanelet); JSON-RPC-ruten `/a2a` bruker Bearer `OMNIROUTE_API_KEY` hvis den er konfigurert.

## Autentisering

Se [Administrasjonsautentisering](../guides/MANAGEMENT-AUTH.md) for de fire
legitimasjonsfamiliene (instrumentbordøkt, lokalt CLI-token, `oma_live_…`-tilgangstoken,
administrasjonsavgrenset API-nøkkel) og hvordan de skiller seg fra inferensnøkler.

- Instrumentbordruter (`/dashboard/*`) bruker informasjonskapselen `auth_token`
- Innlogging bruker lagret passordhash, med `INITIAL_PASSWORD` som reserveløsning
- `requireLogin` kan slås av eller på via `/api/settings/require-login`
- `/v1/*`-ruter kan kreve en Bearer-API-nøkkel når `REQUIRE_API_KEY=true`
- «administrasjonstoken» / «administrasjonsavgrenset API-nøkkel» i denne referansen betyr én av familiene i den veiledningen – ikke en udefinert ekstra type hemmelighet

> **Inkompatibel endring (v3.8.0)** – `/api/v1/agents/tasks/*` og endepunktene for administrasjon av nedkjøling krever nå **administrasjonsautentisering** (`auth_token`-informasjonskapsel for instrumentbordet eller en administrasjonsavgrenset API-nøkkel). Klienter som tidligere kalte disse rutene uten autentisering, vil motta `401 Unauthorized`. Se commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
