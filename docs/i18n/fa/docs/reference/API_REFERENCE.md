## تکمیلهای گفتگو

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### هدرهای سفارشی

| هدر                      | جهت     | توضیحات                                                                                                                                                                                                       |
| ------------------------ | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | درخواست | برای دور زدن کش، روی `true` تنظیم کنید                                                                                                                                                                        |
| `x-omniroute-no-memory`  | درخواست | برای رد کردن تزریق حافظه و مهارتها در این درخواست، روی `true` تنظیم کنید (مشابه حالت بدون کش؛ از سربار توکن/هزینه بهازای هر فراخوانی جلوگیری میکند)                                                           |
| `X-OmniRoute-Progress`   | درخواست | برای رویدادهای پیشرفت، روی `true` تنظیم کنید                                                                                                                                                                  |
| `X-Session-Id`           | درخواست | کلید نشست چسبنده برای وابستگی نشست خارجی                                                                                                                                                                      |
| `x_session_id`           | درخواست | نوع دارای زیرخط نیز پذیرفته میشود (HTTP مستقیم)                                                                                                                                                               |
| `X-OmniRoute-Session-Id` | درخواست | برچسب نشست/گفتگو که فراخواننده ارائه میکند (همچنین حافظه را تغذیه میکند). در صورت وجود، عیناً در `call_logs.session_tag` برای تخصیص هزینه بهازای هر نشست ذخیره میشود (#8249) — در صورت نبود هرگز تولید نمیشود |
| `Idempotency-Key`        | درخواست | کلید حذف موارد تکراری (بازه ۵ ثانیهای)                                                                                                                                                                        |
| `X-Request-Id`           | درخواست | کلید جایگزین برای حذف موارد تکراری                                                                                                                                                                            |
| `x-omniroute-connection` | درخواست | یک درخواست تکمدلی را با استفاده از شناسه اتصال، به یک اتصال ارائهدهنده (حساب) پین میکند — [پین کردن حساب بهازای هر درخواست](#account-pinning-per-request) را ببینید                                           |
| `X-OmniRoute-Cache`      | پاسخ    | `HIT` یا `MISS` (بدون جریانسازی)                                                                                                                                                                              |
| `X-OmniRoute-Idempotent` | پاسخ    | اگر موارد تکراری حذف شده باشند، `true`                                                                                                                                                                        |
| `X-OmniRoute-Progress`   | پاسخ    | اگر ردیابی پیشرفت فعال باشد، `enabled`                                                                                                                                                                        |
| `X-OmniRoute-Session-Id` | پاسخ    | شناسه نشست مؤثری که OmniRoute استفاده کرده است                                                                                                                                                                |
| `X-OmniRoute-Request-Id` | پاسخ    | شناسه همبستگی درخواست (در صورت مشخص بودن)                                                                                                                                                                     |
| `X-OmniRoute-Version`    | پاسخ    | نسخه ساخت OmniRoute (همیشه موجود است)                                                                                                                                                                         |
| `X-OmniRoute-Cost-Saved` | پاسخ    | مبلغ دلاری که کش در یک HIT صرفهجویی کرده است (فقط برای اصابتهای کش)                                                                                                                                           |
| `X-OmniRoute-Decision`   | پاسخ    | ردپای مسیریابی: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` راهبرد ترکیب است، یا برای درخواست غیرترکیبی `single`) — همیشه در پاسخهای تکمیل موجود است                                        |

> نکته Nginx: اگر به هدرهای دارای زیرخط تکیه میکنید (برای مثال `x_session_id`)، گزینه `underscores_in_headers on;` را فعال کنید.

#### تثبیت حساب برای هر درخواست

وقتی یک ارائهدهنده چند اتصال (حساب یا کلید) دارد، OmniRoute معمولاً یکی از آنها را
از طریق راهبرد انتخاب حساب خود برمیگزیند. در عوض، هر درخواست میتواند با استفاده از هدر
`x-omniroute-connection` به یک اتصال مشخص مقید شود:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **شناسه را از کجا پیدا کنیم.** صفحه ارائهدهنده را در داشبورد باز کنید
  (**Dashboard → Providers → <provider>**) و روی تراشه شناسه `xxxxxxxx…` در ردیف اتصال
  کلیک کنید — با این کار شناسه کامل اتصال کپی میشود.
- **کدام درخواستها آن را رعایت میکنند.** درخواستهای تکمدلی (`provider/model`) در
  `/v1/chat/completions`، `/v1/messages` و `/v1/responses`. ترکیبها این هدر را نادیده میگیرند:
  در عوض، یک حساب را برای هر مرحله ترکیب از طریق اتصال اختصاصی همان مرحله تثبیت کنید.
- **این تثبیت قطعی است، نه صرفاً یک ترجیح.** اتصال تثبیتشده بهصورت انحصاری استفاده میشود.
  بروز خطا درون درخواست، دوره انتظار حساب را ثبت میکند، اما به حساب همرده دیگری از همان
  ارائهدهنده **تغییر مسیر نمیدهد**.
- **دوره انتظار و سهمیه، تثبیت را آزاد میکنند.** تا زمانی که اتصال تثبیتشده در دوره انتظار
  قرار دارد، سهمیهاش تمام شده یا توسط یک خطمشی سهمیه مسدود شده است، درخواستهای بعدی
  دقیقاً مانند ترافیک تثبیتنشده به سایر اتصالهای ارائهدهنده بازمیگردند.
- **شناسههای ناشناخته یا غیرفعال با شکست مواجه میشوند.** شناسهای که در مجموعه فعال
  ارائهدهنده نباشد (حذف یا غیرفعال شده باشد، یا به ارائهدهنده دیگری تعلق داشته باشد)،
  هیچ حساب واجد شرایطی باقی نمیگذارد؛ بنابراین درخواست بهجای مسیریابی بیسروصدا به
  مقصدی دیگر، شکست میخورد.

Claude Code هدرهای سفارشی را از طریق `ANTHROPIC_CUSTOM_HEADERS` ارسال میکند. آن را در بلوک
`env` فایل `~/.claude/settings.json` قرار دهید، یا برای تثبیت حسابی متفاوت در هر پروژه، آن را
در فایل `.claude/settings.json` در سطح پروژه قرار دهید:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

منبع: `src/sse/handlers/chat.ts` (خواندن هدر)، `src/sse/services/auth.ts` و
`src/sse/services/sessionAffinityPin.ts` (آزادسازی تثبیت و بررسی نبودن در مجموعه).

> **هدرهای تلهمتری هزینه:** پاسخهای موفق غیرجریانی همچنین مجموعه تلهمتری هزینه `X-OmniRoute-*` را به همراه دارند — `X-OmniRoute-Response-Cost` (دلار آمریکا، با 10 رقم اعشار ثابت؛ `0.0000000000` برای موارد رایگان یا بدون قیمتگذاری)، `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`، `X-OmniRoute-Model`، `X-OmniRoute-Provider`، `X-OmniRoute-Latency-Ms`، `X-OmniRoute-Cache-Hit` و `X-OmniRoute-Fallback-Attempts` (فقط هنگامی که > 0 باشد)، بهعلاوه `X-OmniRoute-Request-Id` و `X-OmniRoute-Version`. این هدرها توسط تکمیلهای چت، `/v1/responses`، `/v1/messages` و **نقاط پایانی رسانه** صادر میشوند — `/v1/embeddings`، `/v1/images/generations`، `/v1/audio/speech`، `/v1/audio/transcriptions`، `/v1/rerank`، `/v1/videos/generations`، `/v1/music/generations` و `/v1/moderations` (که هزینه آن همیشه `0` است). در صورت موجود بودن قیمتگذاری، هزینه رسانه بر اساس هر وجه محاسبه میشود (بهازای هر تصویر، هر ثانیه، هر نویسه یا هر واحد جستوجو)؛ در غیر این صورت مقدار آن `0` است (خرابیِ باز).

> **معنای هزینه در اصابت کش:** هنگام اصابت کش معنایی (`X-OmniRoute-Cache-Hit: true`) هیچ فراخوانی بالادستی انجام نمیشود؛ بنابراین `X-OmniRoute-Response-Cost` برابر با `0.0000000000` است (هزینه **افزایشی** ارائه نتیجه کششده). هزینه اصلی یا هزینهای که در حالت عادی ایجاد میشد، بهصورت جداگانه در `X-OmniRoute-Cost-Saved` گزارش میشود. مصرفکنندگان دادههای صورتحساب باید مجموع `X-OmniRoute-Response-Cost` را محاسبه کنند (اصابتهای کش هزینهای ندارند)؛ سامانههای تحلیل کش میتوانند `X-OmniRoute-Cost-Saved` را تجمیع کنند.

## اجارههای انحصاری نشست مدیریتشده

اجارهٔ انحصاری نشست مدیریتشده، یک قرارداد مسیریابی اختیاری و مستقل از کلاینت است: یک مالک فعال،
یک اتصال واجد شرایط OmniRoute را در اختیار میگیرد. این سازوکار یک مدل را اجاره نمیدهد، به OAuth نیاز ندارد، یک
کلاینت مشخص را شناسایی نمیکند و به ارائهدهندهٔ خاصی نیاز ندارد.

کلید API احراز هویتکننده باید دارای دامنهٔ `lease:exclusive` و یک فهرست صریح و غیرخالی
`allowedConnections` باشد. مرز تغییرات پایگاه داده، وجود همزمان هر دو فیلد را هنگام
ایجاد کلید و بهروزرسانیهای جزئی الزامی میکند.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

پاسخهای موفق عملیات acquire، renew و release، زمانها، `state` و مقدار مثبت و دقیق
`generation` را ارائه میکنند، اما هرگز اتصال انتخابشده یا اطلاعات احراز هویت را افشا نمیکنند. عملیات renew و release،
نسل را در بدنهٔ JSON ارسال میکنند:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

مالک یک اجارهٔ فعال میتواند صراحتاً فرادادهٔ نمایشی ایمن از نظر حریم خصوصی را برای اتصال فعلی خود درخواست کند:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

این عملیات اختیاری status، در یک تراکنش پایگاه داده با مالک مبهم، کلید API مدیریتشدهٔ احراز هویتشده و
نسل فعال دقیق حصاربندی میشود. `displayName` فقط نام پیکربندیشدهٔ اتصال پس از حذف فاصلههای اضافی است؛
وقتی هیچ نام پیکربندیشدهٔ امنی وجود نداشته باشد، مقدار آن `null` است. OmniRoute هرگز یک
ایمیل یا شناسهٔ حساب تولیدشده را جایگزین نمیکند. مقدار ارائهدهنده، یک برچسب نمایشی غیرحساس است و هرگز
شناسهٔ تولیدشدهٔ یک ارائهدهندهٔ سازگار نیست. اطلاعات احراز هویت، توکنها، کوکیها، شناسههای خام اتصال یا کلید
API، هشهای مالک، اسرار حصاربندی و دادههای داخلی مسیریابی حذف میشوند.

جستوجوهای دارای کلید نادرست، مالک نادرست، نسل قدیمی، دادهٔ مفقود، منقضیشده، آزادشده یا نامعتبرشده، همگی
بدون فرادادهٔ اتصال، همان خطای `409 LEASE_FENCE_STALE` را برمیگردانند. کلاینتی که پاسخ انتظار برای ظرفیت را دریافت کرده است، هیچ اتصال فعالی برای بررسی ندارد. هنگامی که مسیریابی، یک اجارهٔ فعال را منتقل میکند،
همان نسل معتبر باقی میماند و status بهصورت اتمی اتصال جدید را برمیگرداند، نه اتصال قبلی را.
کلاینتهای موجود بدون تغییر باقی میمانند، زیرا پاسخهای acquire، renew، release و انتظار،
ساختارهای قبلی خود را حفظ میکنند.

این قرارداد سرور، `/status` استاندارد OpenAI Codex را تغییر نمیدهد. Codex استاندارد در حال حاضر
ارائهدهندهٔ مدل و وضعیت داخلی احراز هویت/حساب خود را گزارش میکند، اما فرادادهٔ دلخواه حسابِ
ارائهدهندهٔ سفارشی را نمایش نمیدهد؛ یک یکپارچهسازی آتی کلاینت باید این عملیات را فراخوانی کند و دربارهٔ نحوهٔ
نمایش `connection.displayName` تصمیم بگیرد.

سپس هر درخواست استنتاج مدیریتشده، هر دو هدر کنترلی را ارسال میکند:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

مالک دقیق، نسل، اتصال فعال و کلید API احراز هویتشده، بلافاصله
پیش از هر تلاش پشتیبانیشده برای اتصال به سرویس بالادستی حصاربندی میشوند. بازپخش مالک و نسل با کلیدی دیگر،
حتی زمانی که آن کلید همان اتصال را مجاز میداند، ناموفق خواهد بود. مالکهای خام ذخیره، ثبت یا در
تصویر لحظهای درخواست نگهداری نمیشوند و به سرویس بالادستی نیز ارسال نمیشوند.

رقابت موقت بر سر ظرفیت، HTTP `429` را همراه با `Retry-After` و محتوای زیر برمیگرداند:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

این پاسخ فقط به این معناست که مجموعهٔ عادی اتصالات واجد شرایط خالی نبوده و هر گزینهٔ آزاد
در اختیار یک اجارهٔ فعال خارجی قرار داشته است. مدلها/ارائهدهندگان پشتیبانینشده، عدم تطابق خطمشی، دورهٔ انتظار،
سهمیه، سلامت و سایر خطاهای عادی احراز شرایط، پاسخهای فعلی OmniRoute خود را حفظ میکنند.

### `x-omniroute-compression`

نادیدهگیری طرح فشردهسازی برای هر درخواست. دارای بالاترین اولویت است — بر نادیدهگیری ترکیب مسیریابی،
پروفایل فعال، فعالسازی خودکار و مقدار Default پنل اولویت دارد. مقادیر:

| مقدار         | اثر                                                                                                                 |
| ------------- | ------------------------------------------------------------------------------------------------------------------- |
| `off`         | برای این درخواست هیچ فشردهسازی انجام نمیشود.                                                                        |
| `default`     | پروفایل Default استخراجشده از پنل (پروفایل فعال را نادیده میگیرد). موتورهای اتلافی خاموش باقی میمانند.              |
| `safe`        | فقط حذف موارد تکراری و ادغام فاصلههای سفید.                                                                         |
| `allow-lossy` | طرح اپراتور را برای این درخواست، شامل خلاصهسازیها و بازنویسیهای سبک، حفظ میکند.                                     |
| `engine:<id>` | هنگام فعال بودن، یک موتور منفرد؛ برای مثال `engine:rtk`. فعالسازی اختیاری آن موتور برای هر درخواست.                 |
| `<combo>`     | یک ترکیب نامگذاریشده که ابتدا بر اساس نام (بدون حساسیت به بزرگی و کوچکی حروف) و سپس بر اساس شناسه تطبیق داده میشود. |

نکات:

- مقادیر ناشناخته نادیده گرفته میشوند (درخواست هرگز رد نمیشود)؛ فرایند تعیین مقدار به اولویت عادی اپراتور بازمیگردد.
- اگر چند ترکیب نام یکسانی دارند، برای تطبیق قطعی، **شناسه** ترکیب را ارسال کنید.
- ترکیبی که نام آن `off` یا `default` است، با نام قابل انتخاب نیست (این کلمات کلیدی ابتدا تفسیر میشوند)؛ به چنین ترکیبی با شناسهٔ آن ارجاع دهید.
- کلید اصلی فشردهسازی یک مانع قطعی است: هنگامی که فشردهسازی بهصورت سراسری غیرفعال باشد، این هدر نمیتواند آن را فعال کند.

طرح اعمالشده در هدر پاسخ بازتاب داده میشود:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

که در آن `<source>` یکی از `request-header`، `routing-override`، `active-profile`، `auto-trigger`، `default` یا `off` است.

## تعبیهها

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

ارائهدهندگان در دسترس: Nebius، OpenAI، Mistral، Together AI، Fireworks، NVIDIA، **OpenRouter**، Jina AI.

شناسههای کاتالوگ بهشکل `provider/model` هستند (مثال: `jina-ai/jina-embeddings-v5-omni-small`). شناسههای سادهٔ مدل Jina که در رجیستری وجود دارند (برای مثال `jina-embeddings-v5-text-small` و `jina-reranker-v3.5`) نیز قابل استفادهاند. عملیات embed/rerank/classify/segment در Jina ابتدا از اعتبارنامههای `jina-ai` در داشبورد استفاده میکنند؛ `JINA_AI_API_KEY` تنها زمانی بهعنوان جایگزین استفاده میشود که هیچ کلیدی در داشبورد وجود نداشته باشد. کارت `jina-reader` فقط برای Reader / `r.jina.ai` است (`POST /v1/web/fetch`) و هرگز تعبیه یا رتبهبندی مجدد ارائه نمیدهد.

مدلهای رجیستری که پشتیبانی چندوجهی را اعلام میکنند، حداکثر ۳۲ آیتم ساختیافته و مستقل از ارائهدهنده را نیز میپذیرند. انواع آیتم رسانهای عبارتاند از `text`، `image`، `audio`، `video` و `document`. مقدار `source` رسانه یا `{"type":"url","url":"https://..."}` است یا
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`، `jina-ai/jina-embeddings-v5-omni-nano`
و نام مستعار خانوادهٔ `jina-ai/jina-embeddings-v5-omni` → omni-small) همچنین اسناد بومی
EmbeddingsV5Request متعلق به Jina را میپذیرد و آنها را **بدون تغییر** به `https://api.jina.ai/v1/embeddings` ارسال میکند:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

مقادیر بومی `{ image | audio | video | pdf }` میتوانند یک URL عمومی HTTPS، یک URI از نوع `data:` یا base64 خام باشند. OmniRoute این اشیا را به رشته تبدیل نمیکند و URLهای بومی تصویر را نیز واکشی نمیکند — خود Jina رسانههای عمومی را دریافت میکند. فیلدهای اضافی Jina (`task`، `normalized`، `truncate`، `embedding_type`) بدون تغییر ارسال میشوند. SKUهای صرفاً متنی Jina همچنان اسناد غیرمتنی را رد میکنند.

محدودیتهای امنیتی و انتقال:

- URLهای رسانهای راه دور باید عمومی و مبتنی بر HTTPS باشند. آیتمهای متعارف `{type,source:url}` در سمت سرور واکشی میشوند (با اعتبارسنجی مجدد تغییرمسیر، مهلت زمانی، محدودیت اندازه، DNS عمومی و تثبیت اتصال) و پیش از فراخوانی ارائهدهنده بهصورت درونخطی قرار میگیرند. آیتمهای بومی Jina از نوع `{image:"https://..."}` پس از همان بررسی عمومیبودن HTTPS، بدون تغییر ارسال میشوند؛ Jina خود URL را واکشی میکند.
- رسانههای base64 درونخطی به ۸ MiB دادهٔ رمزگشاییشده برای هر آیتم و ۱۶ MiB دادهٔ رمزگشاییشده در کل درخواست محدود هستند.

تبدیل برای ارائهدهندگان (آیتمهای متعارف هرگز بدون تغییر ارسال نمیشوند):

- مدلهای چندوجهی Jina: هر آیتم سطح بالا به یک شیء دارای کلید وجهی
  (`text` / `image` / `audio` / `video` / `pdf`) تبدیل میشود و برای رسانههای درونخطی از URIهای داده استفاده میکند؛ یک بردار برای هر آیتم سطح بالا.
- خانوادهٔ Gemini Embedding 2: یک آرایهٔ سطح بالا به یک درخواست بومی
  `models/{model}:embedContent` با `content.parts` (`text` یا `inline_data`) تبدیل میشود.
- llama.cpp (`llama-cpp/<model>`، هر مدلی که سرور محلی بارگذاری کرده باشد): آیتمهای متعارف `text`
  به رشتههای ساده تبدیل میشوند و `image` / `audio` / `video` هرکدام به یک شیء
  `{"content": [part]}` تبدیل میشوند؛ این تبدیل با استفاده از بخشهای محتوای چت llama-server (`image_url`،
  `input_audio` با قالب `wav` / `mp3` / `flac`، و `input_video`) و دادههای درونخطی انجام میشود؛ یک بردار
  برای هر آیتم سطح بالا. سرور باید با `--embedding --mmproj …` اجرا شود؛ بدون پروژکتور،
  خود سرور رسانه را رد میکند. `document` پشتیبانی نمیشود.
- مدلهای ناشناخته/پویا که فاقد فرادادهٔ صریح وجه هستند، ورودی ساختیافته را با HTTP 400 رد میکنند.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

ترکیبهای پشتیبانینشدهٔ مدل/وجه، بهجای تبدیل اجباری آیتم، HTTP 400 برمیگردانند. فیلدهای افزونهای غیر از ورودی در درخواستهای قدیمی رشتهای/توکنی، همچنان بدون تغییر عبور داده میشوند.

```bash
# فهرست همهٔ مدلهای تعبیه
GET /v1/embeddings
```

## تولید تصویر

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

ارائهدهندگان موجود شامل OpenAI (GPT Image 2)، xAI (Grok Image)، Together AI (FLUX)، Fireworks AI، Nebius (FLUX)، Hyperbolic، NanoBanana، **OpenRouter**، **ZenMux**، SD WebUI (محلی) و ComfyUI (محلی) هستند.

`n` تعداد `n` تصویر را در `data[]` برمیگرداند. برای ارائهدهندگانی که API بالادستی آنها در هر فراخوانی یک تصویر برمیگرداند
(Black Forest Labs، Stability AI، Leonardo، Ideogram، Haiper، Hyperbolic، Magnific/Freepik،
NVIDIA NIM، Cloudflare Workers AI)، تعداد `n` فراخوانی بالادستی جداگانه انجام میشود که حداکثر ۴ مورد از آنها همزمان در حال اجرا هستند. یک
`seed` ثابت بر اساس اندیس فراخوانی افزایش مییابد (`seed`، `seed + 1`، …)؛ بنابراین تصاویر متفاوت خواهند بود، اما
قابلیت بازتولید خود را حفظ میکنند. مقدار `n` حداکثر ۱۰ است. اگر هر یک از فراخوانیها ناموفق باشد، کل درخواست
ناموفق خواهد بود. فهرست قالبهای توزیعشونده در `SINGLE_IMAGE_FANOUT_FORMATS` واقع در
`open-sse/handlers/imageGeneration/fanOut.ts` قرار دارد.

ZenMux از اتصال موجود مبتنی بر کلید API استفاده مجدد میکند و پیشوندهای `zenmux/` یا `zm/` را میپذیرد:

- `zenmux/openai/gpt-image-2` از OpenAI Images API متعلق به ZenMux استفاده میکند. گزینهها شامل `size`،
  `quality`، `n`، `output_format`، `output_compression`، `background` و `response_format` هستند.
- ناشران دیگر، مانند `zm/meta/muse-image-1.0`، از نقطه پایانی `:predict` متعلق به Vertex AI در ZenMux
  استفاده میکنند. `n` به `sampleCount`، `aspect_ratio` به `aspectRatio` و `image_size`
  (`1K`، `2K`، `4K`) به `sampleImageSize` نگاشت میشود. یک `size` پیکسلی فقط نسبت ابعاد را تعیین میکند،
  نه ابعاد پیکسلی تضمینشده را. نسبتها، وضوحها و تعدادهای پشتیبانیشده بسته به مدل متفاوت هستند.
- `zm/inclusionai/ming-image-0.1-design` ابعاد خود را انتخاب میکند. `size`،
  `aspect_ratio` و `image_size` را حذف کنید؛ مقادیر صریح منجر به بازگشت HTTP 400 میشوند. میتوان PNG، JPEG و WebP
  را با `output_format` درخواست کرد.

این یکپارچهسازی از تولید متنبهتصویر پشتیبانی میکند، نه ویرایش تصویر مرجع. خروجی Vertex
به `data[].b64_json` نرمالسازی میشود؛ `response_format: "url"` یک URL بالادستی
HTTPS یا، هنگامی که فقط بایتهای تصویر در دسترس باشند، یک URL دادهای base64 را برمیگرداند. خروجیهای خالی/فیلترشده
بهجای یک پاسخ موفق خالی، خطا برمیگردانند. دسترسی به مدل به حساب ZenMux بستگی دارد.
[API مربوط به Vertex در ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) و
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image) را ببینید.

```bash
# فهرستکردن همه مدلهای تصویر
GET /v1/images/generations
```

## OCR اسناد

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` ارائهدهنده OCR را از طریق پیشوند `provider/model` انتخاب میکند؛ یک شناسه مدل بدون پیشوند (برای مثال
`mistral-ocr-latest`) به ارائهدهنده ثبتشده آن تفکیک میشود و در صورت حذف `model`، مقدار پیشفرض
Mistral (`mistral-ocr-latest`) خواهد بود. ارائهدهندگان ثبتشده (`open-sse/config/ocrRegistry.ts`):

| شناسه ارائهدهنده              | شناسه مدل            | مقدار `model`                                                      | توضیحات                                                                                                                     |
| ----------------------------- | -------------------- | ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (یا `mistral-ocr-latest` بدون پیشوند) | همزمان — پاسخ مستقیماً از تنها فراخوانی بالادستی برگردانده میشود.                                                           |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                        | بالادست ناهمزمان (`analyze` + نظرسنجی) — توضیحات زیر را ببینید.                                                             |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                            | همزمان، از طریق نقطه پایانی شریک `openapi/chat/completions` متعلق به Vertex AI — برای احراز هویت/URL توضیحات زیر را ببینید. |

هر سه ارائهدهنده با بدنهای یکسان و بهشکل Mistral پاسخ میدهند:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### جریان نظرسنجی Azure Document Intelligence

API مربوط به `analyze` در Azure Document Intelligence ناهمزمان است: درخواست اولیه بهجای بدنه، یک
هدر `Operation-Location` برمیگرداند و نتیجه باید از طریق نظرسنجی دریافت شود. هندلر
(`open-sse/handlers/ocr.ts`) آن URL را هر ثانیه و حداکثر طی ۳۰ تلاش نظرسنجی میکند، در صورت دریافت پاسخ نظرسنجی غیرـ`ok` یا وضعیت `"failed"` بلافاصله ناموفق میشود (و
نظرسنجی را ادامه نمیدهد) و اگر پس از پایان تعداد مجاز تلاشها عملیات همچنان در حال اجرا باشد، `504` برمیگرداند.
پاسخ نهایی Azure پیش از بازگشت به فراخواننده، به همان ساختار `pages`/`markdown` مورد استفاده Mistral
نرمالسازی میشود؛ بنابراین کد کلاینت نیازی به مدیریت ویژه برای هر ارائهدهنده ندارد.

### احراز هویت و تفکیک نقطه پایانی Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` از همان احراز هویت Vertex AI که OmniRoute از قبل برای
ترافیک چت/تصویر پشتیبانی میکند (`open-sse/executors/vertex.ts`) مجدداً استفاده میکند: کلید API اتصال یا یک
اعتبارنامه JSON حساب سرویس است (که از طریق جریان JWT-bearer با یک توکن دسترسی کوتاهعمر OAuth مبادله میشود)
یا یک توکن دسترسی OAuth ازپیشصادرشده است که بدون تغییر استفاده میشود. URL نقطه پایانی بالادستی،
نقطه پایانی عمومی شریک `openapi/chat/completions` متعلق به Vertex است که با استفاده از پروژه و
منطقه اتصال ساخته میشود — مقدار صریح `providerSpecificData.project`/`providerSpecificData.region` همیشه اولویت دارد؛
در غیر این صورت، پروژه از `project_id` موجود در JSON حساب سرویس استخراج میشود و منطقه
بهطور پیشفرض `us-central1` است. هر دو تفکیک در `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`، `resolveVertexOcrBaseUrl`) انجام میشوند و پیش از ارسال به `handleOcr` توسط
`src/app/api/v1/ocr/route.ts` مصرف میشوند.

```bash
GET /v1/models

→ همه مدلهای چت، تعبیهسازی و تصویر + ترکیبها را در قالب OpenAI برمیگرداند
```

### پیشوندهای شناسه مدل (`?prefix=`)

بیشتر مدلها با یک **پیشوند ارائهدهنده** معرفی میشوند. پیشوندی که دریافت میکنید توسط
پرچم قابلیت `MODELS_CATALOG_PREFIX_MODE` کنترل میشود و میتوان آن را **برای هر درخواست** با یک
پارامتر کوئری بازنویسی کرد — این قابلیت برای کلاینتی مفید است که بدون تغییر تنظیمات سراسری سرور
برای سایر کاربران، فهرستی مرتب میخواهد:

```bash
GET /v1/models?prefix=alias        # یک شناسه برای هر مدل — پیشوند کوتاه نام مستعار
GET /v1/models?prefix=dual         # هر دو شکل (پیشفرض سرور)
GET /v1/models?prefix=canonical    # فقط پیشوند کامل شناسه ارائهدهنده
```

| حالت        | خروجی                                                   | توضیحات                                                                                                                                                                                                           |
| ----------- | ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **و** `claude/claude-sonnet-4-6` | **پیشفرض.** هر دو شناسه به یک مدل هدایت میشوند؛ این حالت حفظ شده است تا پیکربندیهای کلاینتی که یکی از این دو شکل را بهصورت ثابت ثبت کردهاند همچنان کار کنند. اندازه کاتالوگ تقریباً دو برابر میشود.               |
| `alias`     | `cc/claude-sonnet-4-6`                                  | یک ورودی برای هر مدل. ارائهدهندگانی که نام مستعار متمایزی ندارند همچنان ورودی خود را منتشر میکنند، بنابراین چیزی از دست نمیرود.                                                                                   |
| `canonical` | `claude/claude-sonnet-4-6`                              | یک ورودی برای هر مدل تحت پیشوند کامل شناسه ارائهدهنده. ارائهدهندگانی که نام مستعار متمایزی ندارند (برای مثال `antigravity/…` و `agy/…`) نیز تنها شناسه خود را در اینجا منتشر میکنند، بنابراین چیزی از دست نمیرود. |

یک نمونه آینهای در حالت `dual` را میتوان بدون پارامتر کوئری نیز تشخیص داد: این نمونه دارای فیلد
`parent` است که به شناسه اصلی اشاره میکند.

کلاینتهایی که انتخابگر مدل نمایش میدهند باید `?prefix=alias` را درخواست کنند — این همان کاری است که
[افزونه OmniCopilot برای VS Code](../guides/VSCODE-COPILOT.md) انجام میدهد.

### فیلترهای کشف (`?capability=`، `?min_context=`، `?kind=`، `?q=`)

`GET /v1/models` فیلترهای اختیاری کشف را میپذیرد. بدون هیچیک از آنها، پاسخ
بدون تغییر باقی میماند. این فیلترها کاتالوگی را که فراخواننده از قبل میبیند محدود میکنند (مجوزهای کلید API ابتدا اعمال میشوند)
و پیش از صفحهبندی `limit` / `after` به سبک OpenAI اجرا میشوند:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # همه قابلیتهای فهرستشده باید true باشند
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` کاتالوگ؛ ردیفهای فاقد آن `chat` هستند
GET /v1/models?q=sonnet&limit=10                           # تطبیق بدون حساسیت به بزرگی و کوچکی حروف روی شناسه یا نام
```

| پارامتر       | مقادیر                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`، `reasoning`، `structured_output`، `temperature`، `thinking`، `tool_calling`، `vision` |
| `min_context` | عدد صحیح نامنفی که با `context_length` مقایسه میشود                                                 |
| `kind`        | `chat`، `audio`، `embedding`، `image`، `moderation`، `music`، `rerank`، `video`                     |
| `q`           | ۱ تا ۲۰۰ نویسه                                                                                      |

یک مقدار ناشناخته، یا `min_context`ای که عدد صحیح نامنفی نباشد (برای مثال `1.5`)،
HTTP `400` را برمیگرداند و پیام، مقادیر معتبر را فهرست میکند. پیادهسازی:
`src/app/api/v1/models/catalogFilters.ts`.

### فهرست کوتاه مدلها (`POST /v1/models/query`)

`POST /v1/models/query` فهرستی کوتاه و قطعی را از همان کاتالوگ، با همان
احراز هویت و سطح دسترسی مختص هر کلید مانند `GET /v1/models`، برمیگرداند:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

هر فیلد اختیاری است. `capabilities` و `exclude` یک آرایه یا رشتهای با مقادیر جداشده با ویرگول میپذیرند؛
`max_output` با `max_output_tokens` مقایسه میشود. نتایج ابتدا بر اساس `owned_by` و سپس `id` مرتب میشوند.
مقدار پیشفرض `limit` برابر `20` است و مقادیر بالاتر از `100` به `100` محدود میشوند. JSON نامعتبر، یک
فیلد ناشناخته یا یک مقدار نامعتبر، HTTP `400` را برمیگرداند.

### مدلهای چت پنهانشده بهصورت جداگانه

مدلی که در صفحه ارائهدهنده خود با علامت **پنهان** مشخص شده باشد، از کاتالوگ حذف میشود و اگر
بهطور صریح درخواست شود، با HTTP `404` / `model_not_found` رد خواهد شد. این بررسی از ارائهدهنده
و مدل نهاییشده، شامل نامهای مستعار ارائهدهنده، پیشوندهای گره ارائهدهنده سازگار و
پیشفرضهای اتصال استفاده میکند. یک ترکیب، اهداف پنهان را نادیده میگیرد و میتواند از یک مدل همخانواده قابلمشاهده استفاده کند؛ اگر هیچ
هدف قابلاجرایی باقی نماند، همان کد خطا را برمیگرداند. لغو پنهانسازی در درخواست بعدی
اعمال میشود. بازنویسیهای قابلیت مشاهده مختص تصویر، مدل چت دارای همان شناسه را پنهان نمیکنند.

این تنظیم مختص هر مدل، از
[فهرستهای مجاز/غیرمجاز نمایش مدل](../routing/MODEL_EXPOSURE_LIST.md) جدا است؛ این فهرستها، نمایش در کاتالوگ
و گزینههای مسیریابی خودکار را فیلتر میکنند، درحالیکه ارسال صریح را حفظ میکنند. مجوزهای مدل برای کلید API
همچنان بهطور مستقل اعمال میشوند. حالت پیشفرض پیشوند کاتالوگ همچنان `dual` است.

### گونههای مدل بدون تفکر

برای مدلهای Claude دارای قابلیت تفکر، `/v1/models` یک گونه **بدون تفکر** نیز معرفی میکند که شناسه آن با `claude-3-omniroute-no-thinking/` آغاز میشود:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

انتخاب این شناسه (برای مثال، در پیکربندی Claude Code که همیشه یک بلوک `thinking` را پیوست میکند) با غیرفعالبودن استدلال، دوباره به `<provider>/<model>` واقعی نگاشت میشود — از طریق `thinking:{type:"disabled"}` در مسیر `/v1/messages`، یا با حذف فیلدهای `reasoning`/`reasoning_effort` در مسیر `/v1/chat/completions`. این گونه فقط برای مدلهای خانوادهٔ Claude فهرست میشود که از تفکر پشتیبانی میکنند **و** مقدار `disabled` را میپذیرند (بنابراین، برای مثال، مدلهای صرفاً تطبیقی که `disabled` را رد میکنند کنار گذاشته میشوند). اپراتورها میتوانند با استفاده از `ModelSpec.noThinkingAlias` این گونه را برای هر مدل بهاجبار فعال یا غیرفعال کنند.

## تولید صوت ElevenLabs

یک اتصال ارائهدهنده `elevenlabs` را در OmniRoute با کلید API مربوط به ElevenLabs پیکربندی کنید.
کلاینتها با کلید **OmniRoute** خود احراز هویت میشوند (`Authorization: Bearer $OMNIROUTE_API_KEY`)؛
درگاه، کلید ذخیرهشده ارائهدهنده را بهعنوان `xi-api-key` ارسال میکند. هرگز کلید ElevenLabs را
بهعنوان توکن bearer درگاه ارسال نکنید.

| متد  | مسیر                        | پاسخ                            | دستهبندی نقطه پایانی کلید API |
| ---- | --------------------------- | ------------------------------- | ----------------------------- |
| POST | `/v1/sound-generation`      | بایتهای صوتی بومی               | `elevenlabs`                  |
| POST | `/v1/music`                 | بایتهای صوتی بومی               | `music`                       |
| POST | `/v1/music/stream`          | بایتهای صوتی جریانی             | `music`                       |
| POST | `/v1/music/detailed`        | صوت چندبخشی بومی و طرح آهنگسازی | `music`                       |
| POST | `/v1/music/detailed/stream` | فراداده بومی SSE و قطعههای صوتی | `music`                       |
| POST | `/v1/music/plan`            | طرح آهنگسازی JSON               | `music`                       |

این نقاط پایانی، مسیرهای موجود `/v1/audio/speech`، `/v1/audio/transcriptions`،
`/v1/voices`، `/v1/text-to-speech/{voiceId}` و `/v1/speech-to-text` را تکمیل میکنند. فیلدهای بومی JSON
و پارامترهای پرسوجو مانند `output_format` و `enable_logging` حفظ میشوند.
پاسخهای `/v1/music/detailed` مرزهای چندبخشی خود را حفظ میکنند؛ آنها را بهصورت multipart تجزیه کنید.
`/v1/music/detailed/stream`، نوع `text/event-stream` را همراه با فراداده آهنگسازی و
قطعههای صوتی base64 در رویدادهای SSE برمیگرداند. هر شش مسیر از پیشدرخواست CORS پشتیبانی میکنند.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# یک جلوه صوتی کوتاه. مدتزمان: ۰٫۵ تا ۳۰ ثانیه.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# مدتزمان موسیقی برحسب میلیثانیه بیان میشود: ۳۰۰۰ تا ۶۰۰۰۰۰.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

برای تحویل تدریجی صوت، از `/v1/music/stream` با همان بدنه JSON استفاده کنید. آهنگسازی
دقیقاً یکی از `prompt` یا `composition_plan` را میپذیرد؛ `/v1/music/plan` به `prompt`
نیاز دارد و بهصورت اختیاری `source_composition_plan` را میپذیرد. طرحوارههای بومی، فیلدهای اضافی
ارائهدهنده را حفظ میکنند تا نسخههای طرح آهنگسازی و گزینههای تنظیم دقیق به ElevenLabs برسند.

نقطه پایانی یکپارچه `/v1/music/generations` همچنین `elevenlabs/music_v1`،
`elevenlabs/music_v2` و `elevenlabs/music_v2_5` را میپذیرد. با یک اتصال فعال ElevenLabs،
این مدلها از طریق کاتالوگ موسیقی در دسترس قرار میگیرند. این نقطه پایانی
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` را برمیگرداند. فیلد `duration` آن برحسب
ثانیه است و به `music_length_ms` نگاشت میشود؛ یک `music_length_ms` صریح اولویت دارد.
`instrumental` به `force_instrumental` نگاشت میشود و فیلد بومی اولویت دارد.
برای استریم از نقاط پایانی بومی استریم و برای درخواستهایی که صرفاً بر اساس یک طرح آهنگسازی هستند
از نقطه پایانی بومی آهنگسازی استفاده کنید.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

محدودیتهای نقطه پایانی، مدل، بودجه و اتصال پیش از فراخوانی بالادستی اعمال میشوند. مسیرهای
بومی، کدهای وضعیت و بدنههای خطای بالادستی را بدون تغییر برمیگردانند؛ از جمله `402` برای محدودیت
طرح و `429` برای محدودیت سهمیه. هدرهای `character-cost`، `song-id`، `request-id` و `retry-after`
در صورت وجود حفظ میشوند. موجودی اعتبار رایگان، دسترسی به همه مدلهای موسیقی، قالبهای خروجی
یا قابلیتهای API را تضمین نمیکند: ElevenLabs مجوز هر درخواست را تعیین میکند.
نقطه پایانی یکپارچه، کدهای وضعیت خطا را در پوشش خطای نرمالسازیشده OmniRoute حفظ میکند.

قراردادهای بالادستی: [جلوههای صوتی](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert)،
[آهنگسازی موسیقی](https://elevenlabs.io/docs/api-reference/music/compose) و
[جزئیات موسیقی جریانی](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

همهٔ مسیرهای POST از ساختار یکسانی پیروی میکنند: `Bearer your-api-key` بههمراه بدنهٔ JSON اعتبارسنجیشده با Zod (`v1RerankSchema`، `v1ModerationSchema`، `v1AudioSpeechSchema` و غیره؛ به `src/shared/validation/schemas.ts` مراجعه کنید). در صورت شکست اعتبارسنجی طرحواره، خطای 4xx برگردانده میشود.

برای کلاینتهایی که نمیتوانند `Authorization: Bearer ...` را پیوست کنند، OmniRoute کلیدهای API را در URL نیز میپذیرد؛ یا از طریق سازگاری رشتهٔ پرسوجو (`?token=...`، `?apiKey=...`، `?api_key=...`، `?key=...`) یا با استفاده از نقاط پایانی اختصاصی `/api/v1/vscode/{token}/...` که در ادامه مستند شدهاند.

```bash
# بازرتبهبندی (ارائهدهندهٔ رجیستری ابری، یا یک گره ارائهدهندهٔ سازگار با OpenAI بهشکل "<prefix>/<model>")
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# دستهبندی Jina (اعتبارنامههای Foundation API)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# قطعهبند Jina
POST /v1/segment     { "content": "...", "return_chunks": true }

# جستوجوی Jina (s.jina.ai؛ نامهای مستعار ارائهدهنده: jina-search، jina-ai، jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# تعدیل محتوا
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# تبدیل متن به گفتار — بدنهٔ audio/mpeg (یا قالب درخواستی) را برمیگرداند
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# تبدیل متن به گفتار Soniox به زبان و صدا نیاز دارد: مقدار پیشفرض `language` برابر با "en" است؛ صدای
# مشخصنشده یا نام یکی از صداهای پیشفرض OpenAI (alloy، nova، …) به "Adrian" تبدیل میشود
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# ویرایش تصویر (چندبخشی)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# تولید ویدئو / موسیقی (شناسهٔ مدل با پیشوند ارائهدهنده)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **گرههای ارائهدهندهٔ بازرتبهبندی:** `POST /v1/rerank` درخواستها را به گرههای ارائهدهندهٔ سازگار با OpenAI نیز هدایت میکند
> (oMLX، vLLM، Infinity، ‏TEI پشت یک دروازه و غیره) که با `<node-prefix>/<model>` آدرسدهی میشوند. گرههای
> لوپبک (`localhost`، `127.0.0.1`، `172.16.0.0/12`) همیشه واجد شرایط هستند؛ همینطور نامهای میزبانی که
> اپراتور در `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` فهرست میکند (برای مثال، نام یک سرویس Docker/Compose مانند
> `http://reranker:8080/v1`؛ این گرهها مستقیماً فراخوانی میشوند و هرگز از طریق `HTTP(S)_PROXY` یا
> پراکسی ثابتشدهٔ یک اتصال فراخوانی نمیشوند). گرههای مستقر روی هر میزبان دیگری
> — مانند یک دستگاه در LAN یا یک همتای Tailscale — تنها زمانی واجد شرایط هستند که اپراتور پرچم قابلیت
> `RERANK_REMOTE_PROVIDER_NODES` را فعال کند **و** URL پایهٔ گره، سیاست URL خروجی ارائهدهنده
> (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`) را بگذراند.
> مرحلهٔ بازرتبهبندی موتور حافظه این مسیر را از طریق
> لوپبک فراخوانی میکند؛ بنابراین همین قاعده بر `rerankProviderModel` در تنظیمات Memory نیز حاکم است.
>
> **ساختارهای سرور محلی:** گره در `<base>/v1/rerank` و در صورت دریافت 404، در `<base>/rerank`
> (Infinity، ‏TEI) فراخوانی میشود. بدنهٔ بالادستی هم املای Cohere/OpenAI (`documents`،
> `return_documents`) و هم املای TEI (`texts`، `return_text`) را شامل میشود و پاسخ بالادستی
> به پوشش Cohere نرمالسازی میشود: آرایهٔ بدون پوشش TEI بهشکل `[{index, score, text}]`، ساختار `{results: [{index, score}]}`
> از دروازههای سبک، و ساختار Voyage بهشکل `{data: [...]}` همگی بهصورت
> `{results: [{index, relevance_score, document?}]}`، مرتبشده بر اساس امتیاز و محدودشده به `top_n`، به کلاینت بازگردانده میشوند.

> **کشف گره ارائهدهنده:** مدلهای یک گره ارائهدهندهٔ سازگار با OpenAI، در `GET /v1/models`
> زیر پیشوند گره ظاهر میشوند. ردیفهایی که فاقد فرادادهٔ نقطهٔ پایانی هستند (که برای فهرستهای محلی `/v1/models` معمول است)
> مقدار `apiType` گره را به ارث میبرند؛ بنابراین مدلهای یک گره `embeddings` دارای `type: "embedding"` و مدلهای یک
> گره `rerank` دارای `type: "rerank"` هستند، بهجای اینکه بهطور پیشفرض چت در نظر گرفته شوند؛ با این حال، مقدار صریح
> `supportedEndpoints` در یک ردیف همگامسازیشده یا افزودهشده بهصورت دستی همچنان اولویت دارد.

## API فایلها

نقطه پایانی سازگار با OpenAI برای ورودی/خروجی دستهای و بارگذاری فایل با هدف مشخص.

| متد    | مسیر                     | توضیحات                                                                                                        |
| ------ | ------------------------ | -------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/files`              | بارگذاری فایل (چندبخشی: `file`، `purpose`، `expires_after[anchor]`، `expires_after[seconds]`) — حداکثر 512 MiB |
| GET    | `/v1/files`              | فهرستکردن فایلهای کلید API احراز هویتشده                                                                       |
| GET    | `/v1/files/[id]`         | دریافت فراداده یک فایل                                                                                         |
| DELETE | `/v1/files/[id]`         | حذف یک فایل                                                                                                    |
| GET    | `/v1/files/[id]/content` | برگرداندن بدنه خام فایل بهصورت جریانی                                                                          |

**احراز هویت:** کلید API از نوع Bearer — فایلها از طریق `getApiKeyRequestScope` بهازای هر کلید API محدود میشوند. یک کلید
فقط فایلهای خودش را میبیند، دانلود میکند و حذف میکند؛ یک نشست داشبورد بدون کلید، کل
نمونه را میخواند؛ دسترسی به فایلی بدون مالک (بارگذاری ناشناس یا از طریق نشست داشبورد) برای هر
فراخواننده بدون نشست رد میشود. `GET /v1/files` درخواست یک فراخواننده ناشناس — و کلید ارائهشدهای که
قابل شناسایی نیست — را حتی زمانی که `REQUIRE_API_KEY=false` باشد، با `401` رد میکند و فایلهای
همه مستأجرها را فهرست نمیکند (GHSA-m3hp-hq9g-fpmv، GHSA-2jm2-mpx8-6523).

## API جستوجو

انتزاع ارائهدهنده وب/جستوجو (Tavily، Brave، Exa، Serper و غیره).

| متد  | مسیر                   | توضیحات                                                                                                        |
| ---- | ---------------------- | -------------------------------------------------------------------------------------------------------------- |
| GET  | `/v1/search`           | فهرستکردن ارائهدهندگان جستوجوی پیکربندیشده و قابلیتهای آنها                                                    |
| POST | `/v1/search`           | اجرای یک پرسوجوی جستوجو — بدنه با `v1SearchSchema` اعتبارسنجی میشود و از کشکردن/ادغام درخواستها پشتیبانی میکند |
| GET  | `/v1/search/analytics` | آمار موفقیت/تأخیر/کش بهازای هر ارائهدهنده                                                                      |

**احراز هویت:** کلید API از نوع Bearer (`extractApiKey` + `isValidApiKey`). سیاست جستوجو از طریق `enforceApiKeyPolicy` اعمال میشود.

### `provider_options` برای Exa و Tavily

Exa و Tavily فیلدهای مختص ارائهدهنده را از یک مجموعه دارای فضای نام میخوانند:
`provider_options.exa` (یا `provider_options["exa-search"]`) و `provider_options.tavily`
(یا `provider_options["tavily-search"]`). فقط کلیدهای زیر ارسال میشوند. هرکدام
در برابر طرحواره Zod مختص خود در `open-sse/handlers/search/providerOptionsPassthrough.ts`
بررسی میشوند و کلیدی با نوع نادرست حذف میشود. هر کلید دیگری، از جمله اطلاعات احراز هویت، نشانی پایه،
`stream` و `outputSchema` نادیده گرفته میشود. کلیدهای مسطحی که ارائهدهندگان دیگر استفاده میکنند (`cx`، `depth`، ...) مانند
قبل کار میکنند.

| ارائهدهنده | فیلدهای سطح بالا                                                                                                                                                                                                                                                                                                                                                          | تودرتو                                                                                                                                                                 |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa        | `type`، `category`، `userLocation`، `moderation`، `additionalQueries`، `objective`، `systemPrompt`، `compliance` (مقادیر اولیه مسطح)، `startPublishedDate`، `endPublishedDate`                                                                                                                                                                                            | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` روی مقدار پیشفرض `{ text: true, highlights: true }` ادغام میشود |
| Tavily     | `search_depth`، `chunks_per_source`، `time_range`، `start_date`، `end_date`، `include_published_date`، `filter_by_published_date`، `include_answer`، `include_raw_content`، `include_images`، `include_image_descriptions`، `include_favicon`، `include_domains_mode`، `language`، `filter_by_language`، `auto_parameters`، `exact_match`، `include_usage`، `safe_search` | —                                                                                                                                                                      |

فیلدهای عمومی همیشه اولویت دارند: `query`، `max_results`، `filters` (دامنهها)، `country` و
موضوع مشتقشده از `search_type`. در Exa، مقدار `search_type: "news"` باعث حفظ `category: "news"` میشود.
Tavily همچنین `search_type: "finance"` (`topic: "finance"`) را میپذیرد.

اکنون `time_range` عمومی به هر دو ارائهدهنده منتقل میشود: Exa مقدار `startPublishedDate` (مُهر زمانی ISO)
و Tavily مقدار `start_date` (`YYYY-MM-DD`) را دریافت میکند. تاریخی که بهصراحت در `provider_options`
تعیین شده باشد، مقدار نگاشتشده را لغو میکند.

نتایج Exa مقادیر `id`، `highlight_scores`، `summary`، `subpages`، `entities` و `extras` را در
`provider_raw` نگه میدارند. نتایج Tavily مقادیر `images` و `favicon` را نگه میدارند.

محاسبه هزینه همچنان بر اساس رجیستری مسطح `costPerQuery` انجام میشود. Tavily برای
`search_depth: "advanced"` در هر فراخوانی اعتبار بیشتری دریافت میکند و این تفاوت در
`usage.search_cost_usd` منعکس نمیشود.

## API واکشی وب

محتوا را از یک URL با استفاده از ارائهدهنده پیکربندیشده واکشی وب (Firecrawl، Jina
Reader، Tavily Extract، TinyFish Fetch، Nimble Extract، Parallel Extract) استخراج میکند.

Parallel Extract (`parallel-search`، با همان کلید API مربوط به Parallel Search) فقط Markdown
برمیگرداند — هر `format` دیگری منجر به `400` میشود — و محتوا را به ۱۰۰٬۰۰۰ نویسه محدود میکند. هنگامی که
خود صفحه مقصد قابل استخراج نباشد، سرویس بالادستی آن را درون یک HTTP 200 گزارش میکند؛
OmniRoute آن را بهصورت یک `422` با پیامی ثابت ارائه میدهد.

| متد  | مسیر            | توضیحات                                                               |
| ---- | --------------- | --------------------------------------------------------------------- |
| POST | `/v1/web/fetch` | واکشی/خراشدادن یک URL — بدنه توسط `v1WebFetchSchema` اعتبارسنجی میشود |

**احراز هویت:** کلید API از نوع Bearer ‏(`extractApiKey` + `isValidApiKey`). خطمشی از طریق `enforceApiKeyPolicy` اعمال میشود.

**بازگشت جایگزین آگاه از سهمیه (#8297):** هنگامی که هیچ `provider` صریحی ارائه نشده باشد، مجموعه
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) با ترتیب
اولویت ثابت
(ابتدا پرکردن) پیمایش میشود — ارائهدهندهای که پیکربندی شده اما با محدودیت نرخ مواجه است، بهجای
متوقفکردن درخواست نادیده گرفته میشود، و شکست قابلتلاشمجدد/مرتبط با سهمیه در سرویس بالادستی
(HTTP 429 همیشه؛ 402/403 برای سطوح رایگان مبتنی بر سهمیه Firecrawl/Tavily/TinyFish —
نه برای Jina Reader، و هرگز برای یک درخواست نامعتبر 400 معمولی) در زمان درخواست به
ارائهدهنده بعدی که هنوز امتحان نشده و دارای اعتبارنامه است منتقل میشود. هنگامی که تمام ارائهدهندگان موجود در
مجموعه به پایان برسند، نقطه پایانی بهجای `400` عمومی قبلی، یک `429` واحد
(همراه با سربرگ `Retry-After`) برمیگرداند. هنگامی که یک `provider` صریح
درخواست شود، **هیچ** بازگشت جایگزین پنهانی وجود ندارد — ارائهدهنده صریحی که با محدودیت نرخ یا خطا
مواجه شود، خطای خودش را ارائه میدهد (`429` در صورت محدودیت نرخ، در غیر این صورت وضعیت
سرویس بالادستی).

## استریم WebSocket

```bash
GET /v1/ws?handshake=1
```

دستدهی ارتقای WebSocket را اعتبارسنجی میکند و پیامهای نمونه پروتکل سیمی (`request`، `cancel`) را برمیگرداند. فریمهای واقعی WS توسط سرور WS همراه برنامه و خارج از جدول مسیرهای Next.js مدیریت میشوند.

**احراز هویت:** کلید API از نوع Bearer هنگام دستدهی.

### API پاسخها روی WebSocket (فقط codex)

```bash
# همان میزبان:درگاه API از نوع HTTP (پیشفرض 20128)؛ اتصال را ارتقا دهید:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (یا: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# فریم نخست باید response.create باشد:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

یک پراکسی Responses-API-over-WebSocket **منحصراً به `codex`** (بکاند ChatGPT)
متصل شده است. این پراکسی روی همان درگاه API/داشبورد و در مسیرهای `/v1/responses`،
`/responses` و `/api/v1/responses` گوش میدهد. در نخستین فریم `response.create`
از طریق پل داخلی `codex-responses-ws` احراز هویت و آمادهسازی را انجام میدهد، یک
اتصال OAuth مربوط به codex را انتخاب میکند و با استفاده از انتقالدهنده `wreq-js` به
`wss://chatgpt.com/backend-api/codex/responses` تونل میزند.
**مدلهای غیر codex رد میشوند** (`codex_ws_provider_required`).
برای مسیریابی اشتراک سهمیه از `model: "qtSd/<group>/codex/<model>"` استفاده کنید. پیادهسازی در
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` قرار دارد.

**احراز هویت:** کلید API از نوع Bearer هنگام دستدهی. سرور HTTP همراه برنامه (`server-ws.mjs`)
باید نقطه ورود فعال باشد (و هنگامی که `app/server-ws.mjs` وجود داشته باشد، بهطور پیشفرض همینطور است).

#### شناسه مدل: از شناسه خام ChatGPT استفاده کنید (بدون پیشوند `codex/`)

**Codex CLI** متعلق به OpenAI، هنگامی که
`supports_websockets = true` باشد نام مدل را در سمت کلاینت اعتبارسنجی میکند و **شناسههای دارای پیشوند ارائهدهنده** مانند
`codex/gpt-5.5` را رد میکند (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). شناسه **خام** را ارسال کنید (برای مثال `gpt-5.5`). پل OmniRoute
فقط مخصوص codex است، بنابراین پیش از تونلزدن به سرویس بالادستی، یک شناسه خام را دوباره بهعنوان مدل codex
(`resolveCodexWsModelInfo`) تفکیک میکند — حتی اگر یک
`gpt-5.5` خام در حالت HTTP در غیر این صورت به ارائهدهنده دیگری مسیریابی شود.

#### پیکربندی OpenAI Codex CLI

برای هدایت Codex CLI به OmniRoute، یک ارائهدهنده سفارشی دارای پشتیبانی WebSocket
به `~/.codex/config.toml` اضافه کنید (برای جلوگیری از دستکاری
پیکربندی موجود، از یک `CODEX_HOME` جداگانه استفاده کنید):

```toml
model = "gpt-5.5"                 # شناسه خام — نه "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # بدون اسلش انتهایی؛ URL مربوط به WS از آن استخراج میشود (در محیط عملیاتی از https/wss استفاده کنید)
wire_api = "responses"                    # تنها مقدار پشتیبانیشده از فوریه ۲۰۲۶
supports_websockets = true                # انتقال Responses-over-WS را فعال میکند
env_key = "OMNIROUTE_API_KEY"             # کلید API مربوط به OmniRoute را نگه میدارد (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # یک کلید API مربوط به OmniRoute (اگر REQUIRE_API_KEY=false باشد، هر کلیدی پذیرفته میشود)
codex exec "Responda apenas: PONG"
```

CLI، آدرس `base_url + /responses` را به WebSocket ارتقا میدهد و OmniRoute آن را
به اتصال OAuth انتخابشده codex تونل میکند. این فرایند بهصورت سرتاسری در برابر سرور محلی
اعتبارسنجی شده است: ChatGPT، ‏`codex.rate_limits` + `response.created` را برمیگرداند و
تکمیل را بهصورت جریانی ارسال میکند.

## استفاده سلفسرویس (`/api/usage/om-usage`)

هر کلید API میتواند میزان استفاده و سهمیههای **خودش** را مشاهده کند — بدون نیاز به احراز هویت مدیریتی. این همان endpointی است که
کلاینتها (CLI یا پنل OmniCopilot) برای نمایش میزان هزینهکرد دارنده کلید استفاده میکنند.

```bash
# قالب متنی (قرارداد قدیمی — متن ساده برای ترمینال)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# قالب ساختاریافته — آنچه یک رابط کاربری مصرف میکند
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

کلید باید گزینه **`allowUsageCommand`** را فعال داشته باشد (بهصورت پیشفرض غیرفعال است — مدیر کلیدهای API در داشبورد
آن را برای هر کلید تغییر میدهد). بدون آن، endpoint با `403` پاسخ میدهد.

`?format=json` یک ساختار تفکیکشده برمیگرداند تا فراخوان هیچگاه یک فیلد داده را از پاسخ
رد درخواست نخواند. در صورت موفقیت:

```jsonc
{
  "allowed": true,
  // فقط زمانی وجود دارد که محدودیتهای استفاده برای هر کلید (روزانه/هفتگی برحسب USD) فعال شده باشند:
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // تصویر لحظهای سهمیه ارائهدهنده انتخابشده، یا null اگر هنوز چیزی در حافظه پنهان ذخیره نشده باشد:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // تصویر لحظهای همه اتصالها، تا رابط کاربری بتواند چند ارائهدهنده را کنار یکدیگر نمایش دهد:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

در صورت رد درخواست (`401` برای کلید نامعتبر / `403` برای عدم مجوز)، همان مسیر
`{ "allowed": false, "error": { "message": "…" } }` را برمیگرداند — وجود `personal`/`provider` بهصورت خالی
(کلید مجاز است، اما هنوز اطلاعاتی دریافت نشده) وضعیتی متفاوت از رد درخواست است و فقط قالب JSON
این دو را از هم متمایز میکند.

**احراز هویت:** کلید API از نوع Bearer متعلق به خود فراخوان، که با `isValidApiKey` اعتبارسنجی میشود — این سطح
مدیریتی (`/api/keys/…`) نیست؛ سطح مدیریتی همچنان پشت `requireManagementAuth` باقی میماند.

### درصدهای خام در برابر درصدهای سهمیه تعدیلشده با حد توقف

هنگام استفاده از `/api/usage/om-usage`، فراخوانها باید به تفاوت میان
درصدهای ارائهشده در **خروجی متن ساده** و **خروجی ساختاریافته JSON** توجه کنند:

| جنبه                  | قالب متن ساده (`/api/usage/om-usage` / `@@om-usage`)                                                    | قالب JSON (`?format=json`)                                              |
| :-------------------- | :------------------------------------------------------------------------------------------------------ | :---------------------------------------------------------------------- |
| **فیلد خروجی**        | `NN% left` (برای مثال، `20% left`)                                                                      | `provider.quotas` / `providers[].quotas`                                |
| **معیار اندازهگیری**  | **مقدار قابلاستفاده تعدیلشده با حد توقف**: ظرفیت باقیمانده بالاتر از آستانه حد توقف                     | **سهمیه خام بالادستی**: مقدار تعدیلنشده ارائهدهنده                      |
| **مقیاسبندی حد توقف** | از طریق `effectiveRemainingPercent()` مقیاسبندی میشود تا ذخیره محافظتشده بهشکل `0% left` نمایش داده شود | ندارد (مقادیر خام تصویر لحظهای، همانطور که ارائهدهنده گزارش کرده است)   |
| **داده آستانه**       | در درصد نمایشدادهشده لحاظ میشود                                                                         | در `quotaWindowThresholds` هر اتصال (یا مقادیر پیشفرض سرور) ذخیره میشود |
| **مصرفکننده اصلی**    | CLIهای تعاملی، اعلانهای ترمینال، اپراتورهای انسانی                                                      | یکپارچهسازیهای برنامهای، داشبوردها، تحلیلها و ردیابهای صورتحساب         |

#### فرمول تعدیل حد توقف

OmniRoute برای جلوگیری از اتمام سهمیه بالادستی، از حدهای توقف پیشگیرانه سهمیه پشتیبانی میکند (که از طریق
`quotaWindowThresholds` اتصال، مقادیر پیشفرض ارائهدهنده یا تنظیمات تابآوری سراسری پیکربندی میشوند). هنگامی که یک آستانه حد توقف
(برای مثال، `cutoff = 25%`) در یک بازه سهمیه فعال باشد، رندرکننده متن مقدار باقیمانده را به این صورت محاسبه میکند:

- اگر `remaining <= cutoff` باشد: `0%` را برمیگرداند.
- اگر `remaining > cutoff` باشد: `((remaining - cutoff) / (100 - cutoff)) * 100` را برمیگرداند.

خروجی متنی قالببندیشده، این مقدار را به نزدیکترین عدد صحیح گرد میکند (`Math.round(...)`).

#### مثال توضیحی

یک بازه ارائهدهنده با **۶۰٪ استفاده خام** (و در نتیجه **۴۰٪ سهمیه خام باقیمانده**) و یک آستانه
**حد توقف ۲۵٪ برای سهمیه باقیمانده** را در نظر بگیرید:

| نمایش                         | محاسبه                                             | باقیمانده |                استفاده ضمنی                |
| :---------------------------- | :------------------------------------------------- | :-------: | :----------------------------------------: |
| **JSON خام (`?format=json`)** | تصویر لحظهای بالادستی (`quotas[window]`)           |  **۴۰٪**  |                  **۶۰٪**                   |
| **قالب متنی (`NN% left`)**    | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **۲۰٪**  | **۸۰٪** (در صورت محاسبه `100 - remaining`) |

- **چرا متن ۲۰٪ باقیمانده را نشان میدهد:** از ۴۰٪ سهمیه فیزیکی باقیمانده حساب، ۲۵٪ توسط
  سیاست حد توقف رزرو شده است. پیش از آنکه مسیریاب هدایت درخواستها به این اتصال را متوقف کند، فراخوان تنها ۱۵٪ از
  ۷۵٪ ظرفیت قابلاستفاده را در اختیار دارد. مقیاسبندی تضمین میکند که اتصال دقیقاً زمانی که
  مسیریابی متوقف میشود، اتمام سهمیه (`0% left`) را اعلام کند.
- **چرا JSON مقادیر خام را حفظ میکند:** محتوای JSON تصویر لحظهای دقیق ارائهدهنده (`UsageSnapshot`) را
  برمیگرداند تا ابزارهای خارجی بدون مقیاسبندی اتلافی سمت سرور، به میزان استفاده واقعی بالادستی و
  `quotaWindowThresholds` سطح اتصال دسترسی داشته باشند.

#### راهنمای مهاجرت مصرفکنندگان

اگر یک یکپارچهسازی خارجی (مانند افزونهٔ ویرایشگر یا افزونهٔ عامل) قبلاً متنِ
نقطهٔ پایانی (`NN% left`) را استخراج میکرد و درصد مصرفشده را بهصورت `100 - NN` محاسبه میکرد، مهاجرت به `?format=json` به این معناست:

- خواندن مقادیر خام JSON، **مصرف واقعی بالادستی** را نشان خواهد داد (در مثال بالا، ۶۰٪ مصرفشده).
- اگر یکپارچهسازی بخواهد معناشناسی میزان مجازِ قابلاستفاده در نقطهٔ پایانی متنی را حفظ کند، میتواند
  فرمول مؤثرِ باقیمانده را در سمت کلاینت و با استفاده از `quotaWindowThresholds` برای بازنویسیهای سطح اتصال ارزیابی کند.

```bash
# دریافت آمار کش

# پاککردن همه کشها
DELETE /api/cache/stats
```

```json
{
  "semanticCache": {

    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,

  }

```

### تأثیر بر تأخیر

در صورت اصابت به کش معنایی، پاسخ از کش ارائه میشود، **بدون فراخوانی سرویس
بالادستی**؛ بنابراین مقدار گزارششده برای `X-OmniRoute-Response-Latency` نزدیک به صفر است
(صرفنظر از تأخیر اصلی سرویس بالادستی). کلاینتهای حساس به تأخیر
(بنچمارکگیری، پایش p50/p99) باید هدر پاسخ
`X-OmniRoute-Cache-Latency` را بررسی کنند:

| مقدار          | معنا                                                            |
| -------------- | --------------------------------------------------------------- |
| `synthetic`    | پاسخ از کش ارائه شده است؛ تأخیر، زمان واقعی سرویس بالادستی نیست |
| _(وجود ندارد)_ | پاسخ از فراخوانی واقعی سرویس بالادستی دریافت شده است            |

### دور زدن کش برای هر کلید

کلیدهای API میتوانند از طریق `cacheDefaultMode` از خواندن کش معنایی صرفنظر کنند:

| مقدار    | رفتار                                                                        |
| -------- | ---------------------------------------------------------------------------- |
| `legacy` | رفتار عادی کش (پیشفرض)                                                       |
| `bypass` | جستوجو در کش را کاملاً نادیده میگیرد؛ همیشه سرویس بالادستی را فراخوانی میکند |

هنگام ایجاد کلید (`POST /api/keys`) تنظیم کنید یا آن را بهروزرسانی کنید (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### دور زدن کش برای هر درخواست

هر درخواستی، صرفنظر از تنظیمات کلید، میتواند کش را دور بزند:

```
X-OmniRoute-No-Cache: true
```

برای مدلهای همگامسازیشده/واردشده، `PUT /api/provider-models` مقادیر `provider`، `modelId` و
`maxOutputTokenOverride` را میپذیرد: یک عدد صحیح مثبت، سقف دستی توکن خروجی را تعیین میکند و `null`
آن را پاک میکند تا مقدار پیشفرض بازیابی شود. `GET /api/provider-models?provider=<provider>` این
مقادیر را در `modelOutputOverrides` بازمیگرداند، از جمله برای مدلهایی که ردیف مدل سفارشی ندارند. این بازنویسی
از قابلیت زمان اجرای `max_output_tokens` استفاده میکند و پس از همگامسازی مجدد مدل نیز باقی میماند. صفحه ارائهدهنده
سازگار با OpenAI همان کنترلهای ویرایش/پاککردن را ارائه میدهد و مدلهای دارای پشتیبانی صریح از بینایی را علامتگذاری میکند.

گرههای سفارشی Chat Completions، انصرافهای صریح از استدلال را با بکاند بالادستی تطبیق میدهند. یک
آزمایش اتصال موفق، کنترلهای قالب چت را بهطور خودکار برای هر شناسه دقیق مدل انتخاب میکند
که ورودی `/models` آن یکی از مقادیر شناختهشده `owned_by` را تأیید کند: `vllm`، `sglang` یا `llamacpp`.
پوششهای شفاف سازگار با OpenAI ممکن است ورودی اصلی مدل را درون یک شیء تودرتوی
`openai` حفظ کنند؛ تشخیص تا سه مورد از چنین پوششهایی را دنبال میکند. مدلهایی با مالکیت مفقود، ناشناخته یا
متناقض، رفتار معمول OpenAI را حفظ میکنند. تشخیص از درخواست موجود کاتالوگ مجدداً استفاده میکند،
هیچ توکن تکمیلی تولید نمیکند و با تغییر نقطه پایانی اتصال نامعتبر میشود.

برای تثبیت این رفتار در بکاندی که این فراداده را ارائه نمیکند، از API موجود برای بهروزرسانی جزئی
ارائهدهنده استفاده کنید:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

این بدنه را همراه با `PUT /api/providers/<connection-id>` ارسال کنید. در آن اتصال، تلاش استدلال صریح
`none` بهصورت `chat_template_kwargs.thinking=false` و
`chat_template_kwargs.enable_thinking=false` ارسال میشود. مقادیر صریح و بومی قالب همچنان مرجع نهایی هستند،
مگر آنکه یک قاعده استدلال سمت سرور سطحی از تلاش را اجبار کند. این تنظیم فقط زمانی اعمال میشود که یک اتصال
سفارشی سازگار با OpenAI، بدنهای از نوع Chat Completions ارسال کند؛ درخواستهای Responses و ارائهدهندگان
معمولی، ساختار بومی درخواست خود را حفظ میکنند. برای اجبار عبور عادی `reasoning_effort` در OpenAI،
`reasoningControl` را روی `openai` تنظیم کنید؛ یا برای استفاده از تشخیص خودکار، آن را حذف کنید/روی `null` قرار دهید.

درخواستهای دستهبند حالت خودکار Claude Code، وقتی فاقد کنترلهای صریح استدلال باشند، بهطور پیشفرض
تفکر بومی را غیرفعال میکنند. تشخیص از نشانگر سیستمی دستهبند در درخواستهای قالب Claude استفاده میکند،
نه از نام مدلها یا محدودیتهای تکمیل. کنترلهای صریح بدنه، سرآیندهای پشتیبانیشده تلاش/تفکر،
قواعد مسیریابی و تلاش مدلِ تعیینشده، اولویت فعلی خود را حفظ میکنند. هر دو مرحله دستهبندی
پرامپتها، محدودیتهای تکمیل، دنبالههای توقف و احکام واقعی مجوز بالادستی خود را حفظ میکنند؛
مرحله دوم همچنان میتواند استدلال قابلمشاهده درخواستی خود را بهصورت متن معمولی تولید کند.

`omniroute sync import` اعتبارنامه CLI محلی را ارسال میکند. این محدودیت درباره
`DELETE /api/db-backups` (هرسکردن پشتیبانهای ذخیرهشده) و `PATCH /api/db-backups` (تنظیمات
نگهداری: مقادیر ذخیرهشده، هرس خودکار پس از هر پشتیبانگیری را کنترل میکنند) نیز اعمال میشود.

### نسخه و کانال انتشار

```bash
GET /api/system/version
```

مسیر مدیریتی محدود به loopback (با احراز هویت مدیر). نسخهٔ در حال اجرا، آخرین
نسخهٔ منتشرشده و وضعیت بهروزرسانی خودکار را برمیگرداند. `releaseChannel` و `channels` فیلدهای
افزایشی هستند (شاخهٔ 3.8.54)؛ `channel` معنای خود را حفظ میکند — حالت استقراری که بهروزرسان داشبورد
از آن استفاده میکند (`npm`، `source` یا `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — کانال npm ساختِ در حال اجرا: برای نسخههای `-nightly.*` برابر با `nightly`،
  برای سایر پیشانتشارها (`-rc.*`، `-beta.*`، `-alpha.*`) برابر با `next`، برای نسخهٔ پایدار مربوط به
  نسخهٔ اصلی قدیمیتر از `channels.latest` برابر با `lts`، و در غیر این صورت برابر با `latest` است. همان قواعد
  `scripts/release/dist-tag.mjs` که هنگام انتشار dist-tag مربوط به npm را انتخاب میکند.
- `channels` — آخرین نسخهٔ منتشرشدهٔ هر dist-tag، از `npm view omniroute dist-tags` (با HTTP
  رجیستری بهعنوان راهکار جایگزین)، که با همان TTL دهدقیقهای `latest` کش میشود. `latest` همیشه موجود است
  (ابتدا به فیلد `latest` و سپس به `"unavailable"` بازمیگردد)؛ `next`، `nightly` و `lts` فقط
  زمانی نمایش داده میشوند که آن dist-tag وجود داشته باشد. درخواست `Cache-Control: no-cache` هر دو جستوجو را تازهسازی میکند.

مدل کانال (`latest` = v3 تا زمان انتشار عمومی 4.0، `next` = rc، `nightly` = ساختهای `develop`،
`lts` = وصلههای v3 پس از انتشار عمومی 4.0) در `docs/ops/RELEASE_STRATEGY.md` توضیح داده شده است.

## رونویسی صوتی

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

فایلهای صوتی را با استفاده از هر ارائهدهنده پیکربندیشده STT رونویسی کنید. نخستین بخش مسیر،
ارائهدهنده بومی را انتخاب میکند (`openai/…`، `deepgram/…`). درگاههایی که
مدل ارائهدهنده دیگری را بازعرضه میکنند، از یک شناسه کامل استفاده میکنند
(`openrouter/deepgram/nova-3`).

**درخواست:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**پاسخ:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**نمونه شناسههای مدل:** `openai/whisper-1` (به کلید OpenAI نیاز دارد)،
`openrouter/deepgram/nova-3` (به کلید OpenRouter نیاز دارد)،
`deepgram/nova-3` (به کلید بومی Deepgram نیاز دارد). یک درخواست ساده
`deepgram/nova-3` از OpenRouter استفاده **نمیکند**.

**قالبهای پشتیبانیشده:** `mp3`، `wav`، `m4a`، `flac`، `ogg`، `webm`.

## نامهای مستعار توکندار VS Code / بدون هدر

وقتی یک یکپارچهسازی نمیتواند هدر `Authorization` را تزریق کند و لازم است کلید API در URL پایه تعبیه شود، از این نامهای مستعار استفاده کنید.

```bash
# نام مستعار کاتالوگ به سبک OpenAI
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# نامهای مستعار چت به سبک OpenAI
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# نامهای مستعار به سبک Ollama
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

مثال:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

نکتهها:

- نامهای مستعار توکندار از همان مدیریتکنندههای `/v1/*` و `/api/tags` استفاده مجدد میکنند؛ ساختار پاسخها یکسان باقی میماند.
- هر زمان که کلاینت از هدرهای سفارشی پشتیبانی میکند، استفاده از `Authorization: Bearer ...` را ترجیح دهید.
- توکنهای مبتنی بر URL ممکن است در گزارشهای پراکسی معکوس، تاریخچه مرورگر و تلهمتری خارج از OmniRoute ظاهر شوند. آنها را یک گزینه سازگاری در نظر بگیرید، نه حالت پیشفرض احراز هویت.

## بودجه

```bash
# دریافت وضعیت بودجه برای همه کلیدهای API
GET /api/usage/budget

  "monthlyLimitUsd": 100.00,
```

> **نکتههای شِما** (`setBudgetSchema`): مقدار `apiKeyId` الزامی است؛ حداقل یکی از `dailyLimitUsd`، `weeklyLimitUsd` یا `monthlyLimitUsd` باید بزرگتر از صفر باشد. فیلدهای اختیاری: `warningThreshold` (0–1)، `resetInterval` (`daily` | `weekly` | `monthly`)، `resetTime` (`HH:MM`). ساختار قدیمی `{keyId, limit, period}` پاسخ `400 Bad Request` را برمیگرداند.

## محدودیتهای توکن

بودجههای **توکن** بهازای هر کلید API (متمایز از بودجه مبتنی بر USD در بالا). این محدودیتها بهصورت درونخطی در مسیر درخواست اعمال میشوند: هنگامی که میزان مصرف یک کلید در بازه فعلی به حد مجاز برسد، درخواستها با خطای `429 Too Many Requests` رد میشوند. محدودیتها میتوانند به یک `model` یا `provider` مشخص محدود شوند، یا بهصورت `global` در سراسر کلید اعمال شوند؛ هنگامی که چند محدودیت با یک درخواست مطابقت داشته باشند، محدودکنندهترین آنها اعمال میشود.

```bash
# فهرستکردن محدودیتهای توکن یک کلید (شامل مصرف زنده در بازه فعلی)
GET /api/usage/token-limits?apiKeyId=key-123

# ایجاد یا بهروزرسانی یک محدودیت توکن
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# حذف یک محدودیت توکن بر اساس شناسه
DELETE /api/usage/token-limits?id=tl-abc
```

> **یادداشتهای شِما** (`setTokenLimitSchema`): فیلدهای `apiKeyId` و `scopeType` (`model` | `provider` | `global`) الزامی هستند. فیلد `scopeValue` الزامی است، مگر آنکه `scopeType` برابر با `global` باشد (برای نمونه، یک شناسه مدل برای دامنه `model` یا یک شناسه ارائهدهنده برای دامنه `provider`). مقدار `tokenLimit` باید یک عدد صحیح مثبت باشد (از رشته تبدیل میشود). اختیاری: `id` (برای ایجاد حذف شود و برای بهروزرسانی ارائه شود)، `resetInterval` (`daily` | `weekly` | `monthly`، مقدار پیشفرض `monthly`)، `resetTime` (`HH:MM`)، `enabled` (مقدار پیشفرض `true`). پاسخهای `GET` هر محدودیت را با فیلدهای `tokensUsed`، `remaining`، `windowStart`، `periodStartAt` و `nextResetAt` تکمیل میکنند. این یک نقطه پایانی از نوع مدیریتی است (احراز هویت بهصورت مرکزی توسط خط لوله مجوزدهی اعمال میشود).

## پردازش درخواست

1. کلاینت درخواست را به `/v1/*` ارسال میکند
2. کنترلکننده مسیر، `handleChat`، `handleEmbedding`، `handleAudioTranscription` یا `handleImageGeneration` را فراخوانی میکند
3. مدل تعیین میشود (ارائهدهنده/مدل مستقیم یا نام مستعار/ترکیب)
4. اطلاعات احراز هویت با اعمال فیلتر دسترسپذیری حساب، از پایگاه داده محلی انتخاب میشوند
5. برای چت: `handleChatCore` کش معنایی/امضا را بررسی کرده و تنظیمات فشردهسازی ترکیب را تعیین میکند
6. در صورت فعالبودن، فشردهسازی پیشدستانه پیش از ترجمه ارائهدهنده اجرا میشود (`lite`، Caveman، RTK یا حالت انباشته)
7. اجراکننده ارائهدهنده، درخواست را به سرویس بالادستی ارسال میکند
8. پاسخ به قالب کلاینت ترجمه میشود (برای چت) یا بدون تغییر بازگردانده میشود (برای جاسازیها/تصاویر/صدا)
9. میزان مصرف، تحلیلهای فشردهسازی و گزارشهای درخواست ثبت میشوند
10. در صورت بروز خطا، سازوکار جایگزین مطابق با قوانین ترکیب اعمال میشود

مرجع کامل معماری: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## تابآوری (توسعهیافته)

OmniRoute سه سازوکار مستقل برای مدیریت خرابیهای موقت ارائه میدهد؛ نقاط پایانی مدیریتی زیر به اپراتورها اجازه میدهند وضعیت آنها را مشاهده و بازنویسی کنند:

| دامنه               | محل ذخیرهسازی وضعیت                       | مشاهده                                    | بازنشانی / پاکسازی                                               |
| ------------------- | ----------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------- |
| قطعکننده ارائهدهنده | `domain_circuit_breakers` + حافظه داخلی   | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                     |
| دوره انتظار اتصال   | `rateLimitedUntil` در اتصالهای ارائهدهنده | `/api/rate-limits`, `/api/providers/[id]` | (بهصورت تنبل دوباره فعال میشود؛ از طریق PUT ارائهدهنده پاک کنید) |
| قفل مدل             | رجیستری درونحافظهای دسترسپذیری مدل        | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                         |

`PATCH /api/resilience` بازنویسیهای قطعکننده ارائهدهنده را در `providerBreaker.oauth` و `providerBreaker.apikey` میپذیرد. هر پروفایل از `degradationThreshold`، `failureThreshold` و `resetTimeoutMs` پشتیبانی میکند؛ همین فیلدها در داشبورد ← تنظیمات ← تابآوری نیز در دسترس هستند.

```bash
# پاککردن قفل یک مدل
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# پاککردن همه قفلها
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

برای مرجع مفهومی کامل و مقادیر پیشفرض قطعکننده، به [`CLAUDE.md`](../../CLAUDE.md) ← «وضعیت زمان اجرای تابآوری» و [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) مراجعه کنید.

### صف محدودیت نرخ و شبکه ایمنی فعالسازی خودکار

- **مسیر نوشتن پشتیبانیشده**: `POST /api/rate-limits` با بدنه `{"connectionId": "<id>", "enabled": true|false}`، نقطه پایانی مدیریتی پشتیبانیشده برای فعال یا غیرفعالکردن محافظت محدودیت نرخ یک اتصال است. `PUT /api/providers/[id]` عمداً `rateLimitProtection` را تغییر نمیدهد یا معکوس نمیکند (#11278).
- **معنای `enabled: false`**: تنظیم `enabled: false` محافظت صریح اتصال را حذف میکند، اما یک اتصال فعال مبتنی بر کلید API را از شبکه ایمنی سراسری فعالسازی خودکار (`autoEnableApiKeyProviders = true`) **خارج نمیکند**. در `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`)، مقادیر `false` و `undefined` معادل هستند؛ اتصالهای فعال مبتنی بر کلید API که محافظت صریح ندارند، تحت شبکه ایمنی فعالسازی خودکار همچنان محافظت میشوند.
- **غیرفعالسازی سراسری**: برای اجرای اتصالهای مبتنی بر کلید API بدون صفهای محدودیت نرخ، شبکه ایمنی را بهصورت سراسری از طریق `RATE_LIMIT_AUTO_ENABLE=false` (متغیر محیطی) یا `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (تنظیمات ← تابآوری / `PATCH /api/resilience`) غیرفعال کنید.

## سرور MCP

OmniRoute شامل یک سرور داخلی Model Context Protocol با ۳ انتقال (stdio، SSE، streamable-http) و ابزارهای محدودهبندیشده است. نقاط پایانی داشبورد در ادامه، دادههای وضعیت/ممیزی را میخوانند و انتقالهای HTTP را پروکسی میکنند.

| متد | مسیر | توضیحات |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | ضربان قلب، انتقال، وضعیت آنلاین، آخرین فراخوانی، ابزارهای برتر، نرخ موفقیت ۲۴ساعته |

| POST | `/api/mcp/stream` | ارسال فریم JSON-RPC روی انتقال Streamable HTTP |
| DELETE | `/api/mcp/stream` | پایان دادن به یک نشست Streamable HTTP |
| GET | `/api/mcp/audit` | جستوجوی گزارش ممیزی — `?limit=`، `?offset=`، `?tool=`، `?success=true                                | false`، `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | آمار تجمیعی ممیزی (مجموعها، نرخ موفقیت، میانگین مدتزمان، ابزارهای برتر) |

**احراز هویت:** انتقالهای `sse`/`stream` از سطح احراز هویت اختصاصی MCP پیروی میکنند (کلید API از نوع Bearer با محدودهٔ `mcp`)؛ مسیرهای `status`/`tools`/`audit*` از داشبورد قابل خواندن هستند (غیر از امکان دسترسی به میزبان داشبورد، به احراز هویت اضافی نیاز نیست).

> هر دو انتقال HTTP توسط `settings.mcpEnabled` و `settings.mcpTransport` کنترل میشوند — عدم تطابق انتقال، `400` و غیرفعال بودن MCP، `503` برمیگرداند.

## سرور A2A

OmniRoute یک نقطه پایانی A2A (عاملبهعامل) مبتنی بر JSON-RPC 2.0 بههمراه یک پوشش REST برای بازرسی و استفاده در داشبورد ارائه میکند.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # اختیاری است، مگر اینکه OMNIROUTE_API_KEY تنظیم شده باشد
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

متدهای پشتیبانیشده (همگی وابسته به فعال بودن `settings.a2aEnabled` هستند):

| متد              | توضیحات                                                        |
| ---------------- | -------------------------------------------------------------- |
| `message/send`   | اجرای همگام مهارت؛ `{task, artifacts, metadata}` را برمیگرداند |
| `message/stream` | اجرای جریانی SSE برای همان مجموعه مهارتها                      |
| `tasks/get`      | دریافت یک وظیفه بر اساس `taskId`                               |
| `tasks/cancel`   | لغو یک وظیفه بر اساس `taskId`                                  |

مهارتهای داخلی: `smart-routing`، `quota-management`، `provider-discovery`، `cost-analysis`، `health-report`.

### کارت عامل

```bash
GET /.well-known/agent.json
```

کارت عمومی عامل A2A (نام، توضیحات، قابلیتها، فهرست مهارتها و طرح احراز هویت) را برمیگرداند — بهمدت 1h بهصورت عمومی کش میشود. نیازی به احراز هویت نیست.

### ابزارهای کمکی REST

| متد  | مسیر                         | توضیحات                                                                                                          |
| ---- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| GET  | `/api/a2a/status`            | وضعیت فعال بودن A2A + آمار وظایف + خلاصه کارت عامل کششده                                                         |
| GET  | `/api/a2a/tasks`             | فهرست وظایف — `?state=submitted\|working\|completed\|failed\|cancelled`، `?skill=`، `?limit=` (≤200)، `?offset=` |
| POST | `/api/a2a/tasks`             | (بهعنوان ابزار کمکی REST پیادهسازی نشده است — از طریق JSON-RPC و `message/send` ایجاد کنید)                      |
| GET  | `/api/a2a/tasks/[id]`        | بازیابی یک وظیفه                                                                                                 |
| POST | `/api/a2a/tasks/[id]/cancel` | لغو یک وظیفه                                                                                                     |

**احراز هویت:** ابزارهای کمکی REST بدون احراز هویت مدیریتی اجرا میشوند (قابل خواندن توسط داشبورد)؛ مسیر JSON-RPC یعنی `/a2a`، در صورت پیکربندی، از Bearer `OMNIROUTE_API_KEY` استفاده میکند.

## مسیریابی سایه

مقایسه سایهای / A-B ارائهدهندگان **یک سطح REST مستقل نیست** — این قابلیت از طریق مسیریابی ترکیبی پیکربندی میشود (به [ترکیب خودکار](../routing/AUTO-COMBO.md) مراجعه کنید). معیارهای مقایسه برای هر ترکیب از طریق `GET /api/combos/metrics` ارائه میشوند.

## حفاظها

حفاظهای زمان اجرا (تشخیص اطلاعات هویتی شخصی، تشخیص تزریق پرامپت، پلزنی بینایی) را بررسی کنید. حفاظها روی هر درخواست اجرا میشوند؛ انصراف برای هر فراخوانی از طریق هدر درخواست `x-omniroute-disabled-guardrails` انجام میشود — هیچ سطح پایداری برای فعال/غیرفعالکردن وجود ندارد.

| متد  | مسیر                   | توضیحات                                                                                         |
| ---- | ---------------------- | ----------------------------------------------------------------------------------------------- |
| GET  | `/api/guardrails`      | فهرستکردن حفاظهای ثبتشده و وضعیت آنها (نام / فعالبودن / اولویت)                                 |
| POST | `/api/guardrails/test` | اجرای آزمایشی خط لوله پیش از فراخوانی روی یک ورودی نمونه — بدنه: `{input, disabledGuardrails?}` |

**احراز هویت:** به نشست مدیریتی نیاز دارد.

برای جزئیات کامل، به [امنیت > حفاظها](../security/GUARDRAILS.md) مراجعه کنید.

## احراز هویت

برای آشنایی با چهار خانواده اعتبارنامه (نشست داشبورد، توکن CLI محلی، توکن دسترسی `oma_live_…` و کلید API با محدوده مدیریتی) و تفاوت آنها با کلیدهای استنتاج، به [احراز هویت مدیریتی](../guides/MANAGEMENT-AUTH.md) مراجعه کنید.

- مسیرهای داشبورد (`/dashboard/*`) از کوکی `auth_token` استفاده میکنند
- ورود از هش ذخیرهشده گذرواژه استفاده میکند؛ و در صورت عدم دسترسی، به `INITIAL_PASSWORD` بازمیگردد
- گزینه `requireLogin` از طریق `/api/settings/require-login` قابل تغییر است
- مسیرهای `/v1/*` در صورت تنظیم `REQUIRE_API_KEY=true` ممکن است به کلید API از نوع Bearer نیاز داشته باشند
- منظور از «توکن مدیریتی» / «کلید API با محدوده مدیریتی» در این مرجع، یکی از خانوادههای ذکرشده در آن راهنما است — نه یک نوع رمز محرمانه اضافی و تعریفنشده

> **تغییر ناسازگار (v3.8.0)** — مسیرهای `/api/v1/agents/tasks/*` و نقاط پایانی مدیریت دوره انتظار اکنون به **احراز هویت مدیریتی** (کوکی `auth_token` داشبورد یا یک کلید API با محدوده مدیریتی) نیاز دارند. کلاینتهایی که پیشتر این مسیرها را بدون احراز هویت فراخوانی میکردند، پاسخ `401 Unauthorized` را دریافت خواهند کرد. به کامیت `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`) مراجعه کنید.
