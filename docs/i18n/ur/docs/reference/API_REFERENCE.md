## چیٹ تکمیلات

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### حسبِ ضرورت ہیڈرز

| ہیڈر                     | سمت     | وضاحت                                                                                                                                                                                                                            |
| ------------------------ | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | درخواست | کیش کو نظر انداز کرنے کے لیے `true` پر سیٹ کریں                                                                                                                                                                                  |
| `x-omniroute-no-memory`  | درخواست | اس درخواست کے لیے میموری اور اسکلز کا اندراج چھوڑنے کی خاطر `true` پر سیٹ کریں (یہ no-cache کے طرز پر کام کرتا ہے؛ فی کال ٹوکن/لاگت کے اضافی بوجھ سے بچاتا ہے)                                                                   |
| `X-OmniRoute-Progress`   | درخواست | پیش رفت کے واقعات کے لیے `true` پر سیٹ کریں                                                                                                                                                                                      |
| `X-Session-Id`           | درخواست | بیرونی سیشن وابستگی کے لیے اسٹکی سیشن کلید                                                                                                                                                                                       |
| `x_session_id`           | درخواست | انڈراسکور والی قسم بھی قبول کی جاتی ہے (براہِ راست HTTP)                                                                                                                                                                         |
| `X-OmniRoute-Session-Id` | درخواست | کالر کی فراہم کردہ سیشن/گفتگو ٹیگ (میموری کو بھی فراہم کی جاتی ہے)۔ موجود ہونے پر فی سیشن لاگت منسوب کرنے کے لیے اسے بعینہٖ `call_logs.session_tag` میں محفوظ کیا جاتا ہے (#8249) — غیر موجود ہونے پر کبھی ازخود نہیں بنائی جاتی |
| `Idempotency-Key`        | درخواست | نقل ختم کرنے کی کلید (5 سیکنڈ کی مدت)                                                                                                                                                                                            |
| `X-Request-Id`           | درخواست | نقل ختم کرنے کی متبادل کلید                                                                                                                                                                                                      |
| `x-omniroute-connection` | درخواست | ایک واحد ماڈل کی درخواست کو اس کی id کے ذریعے ایک فراہم کنندہ کنکشن (اکاؤنٹ) کے ساتھ مقید کریں — [فی درخواست اکاؤنٹ پننگ](#account-pinning-per-request) دیکھیں                                                                   |
| `X-OmniRoute-Cache`      | جواب    | `HIT` یا `MISS` (غیر اسٹریمنگ)                                                                                                                                                                                                   |
| `X-OmniRoute-Idempotent` | جواب    | اگر نقل ختم کی گئی ہو تو `true`                                                                                                                                                                                                  |
| `X-OmniRoute-Progress`   | جواب    | اگر پیش رفت کی ٹریکنگ فعال ہو تو `enabled`                                                                                                                                                                                       |
| `X-OmniRoute-Session-Id` | جواب    | OmniRoute کے زیرِ استعمال مؤثر سیشن ID                                                                                                                                                                                           |
| `X-OmniRoute-Request-Id` | جواب    | درخواست کو باہم مربوط کرنے والی id (جب معلوم ہو)                                                                                                                                                                                 |
| `X-OmniRoute-Version`    | جواب    | OmniRoute بلڈ ورژن (ہمیشہ موجود)                                                                                                                                                                                                 |
| `X-OmniRoute-Cost-Saved` | جواب    | HIT پر کیش کے باعث بچنے والی امریکی ڈالر میں لاگت (صرف کیش ہٹس)                                                                                                                                                                  |
| `X-OmniRoute-Decision`   | جواب    | روٹنگ ٹریس: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` کومبو حکمتِ عملی ہے، یا غیر کومبو درخواست کے لیے `single`) — تکمیل کے جوابات میں ہمیشہ موجود                                                           |

> Nginx نوٹ: اگر آپ انڈر اسکور والے ہیڈرز پر انحصار کرتے ہیں (مثلاً `x_session_id`)، تو `underscores_in_headers on;` فعال کریں۔

#### فی درخواست اکاؤنٹ پننگ

جب کسی فراہم کنندہ کے متعدد کنکشنز (اکاؤنٹس یا کلیدیں) ہوں، تو OmniRoute عموماً اپنی
اکاؤنٹ انتخاب کی حکمتِ عملی کے ذریعے ان میں سے ایک منتخب کرتا ہے۔ اس کے بجائے کوئی درخواست
`x-omniroute-connection` ہیڈر کے ذریعے کسی ایک مخصوص کنکشن کو پن کر سکتی ہے:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **id کہاں تلاش کریں۔** ڈیش بورڈ میں فراہم کنندہ کا صفحہ کھولیں
  (**Dashboard → Providers → <provider>**) اور کنکشن کی قطار میں `xxxxxxxx…` id چِپ پر کلک
  کریں — اس سے مکمل کنکشن id کاپی ہو جاتی ہے۔
- **کون سی درخواستیں اسے استعمال کرتی ہیں۔** `/v1/chat/completions`، `/v1/messages` اور
  `/v1/responses` پر سنگل ماڈل درخواستیں (`provider/model`)۔ کومبوز اس ہیڈر کو نظر انداز کرتے ہیں:
  اس کے بجائے ہر کومبو مرحلے کے اپنے کنکشن کے ذریعے اس مرحلے کے لیے اکاؤنٹ پن کریں۔
- **پن سخت ہے، محض ترجیح نہیں۔** پن کیا گیا کنکشن خصوصی طور پر استعمال ہوتا ہے۔ درخواست
  کے اندر ہونے والی ناکامی اکاؤنٹ کا کول ڈاؤن ریکارڈ کرتی ہے، لیکن اسی فراہم کنندہ کے کسی
  دوسرے اکاؤنٹ پر **منتقل نہیں** ہوتی۔
- **کول ڈاؤن اور کوٹا پن کو ختم کر دیتے ہیں۔** جب پن کیا گیا کنکشن کول ڈاؤن میں ہو،
  اس کا کوٹا ختم ہو چکا ہو یا کوٹا پالیسی نے اسے مسدود کیا ہو، تو بعد کی درخواستیں فراہم کنندہ
  کے دوسرے کنکشنز پر واپس چلی جاتی ہیں، بالکل اسی طرح جیسے بغیر پن کیا ہوا ٹریفک۔
- **نامعلوم یا غیر فعال ids ناکام ہوتی ہیں۔** جو id فراہم کنندہ کے فعال پول میں موجود نہ ہو (حذف شدہ،
  غیر فعال، یا کسی دوسرے فراہم کنندہ سے متعلق)، اس کے باعث کوئی اہل اکاؤنٹ باقی نہیں رہتا، لہٰذا درخواست
  خاموشی سے کہیں اور روٹ ہونے کے بجائے ناکام ہو جاتی ہے۔

Claude Code حسبِ ضرورت ہیڈرز `ANTHROPIC_CUSTOM_HEADERS` کے ذریعے بھیجتا ہے۔ اسے
`~/.claude/settings.json` کے `env` بلاک میں رکھیں، یا ہر پروجیکٹ کے لیے مختلف
اکاؤنٹ پن کرنے کی خاطر پروجیکٹ سطح کی `.claude/settings.json` میں رکھیں:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

ماخذ: `src/sse/handlers/chat.ts` (ہیڈر پڑھنا)، `src/sse/services/auth.ts` اور
`src/sse/services/sessionAffinityPin.ts` (پن ختم کرنا اور پول میں عدم موجودگی کی جانچ)۔

> **لاگت ٹیلی میٹری ہیڈرز:** نان اسٹریمنگ کامیاب جوابات میں `X-OmniRoute-*` لاگت ٹیلی میٹری سیٹ بھی شامل ہوتا ہے — `X-OmniRoute-Response-Cost` (USD، اعشاریہ کے بعد مقررہ 10 ہندسے؛ مفت/بغیر قیمت کے لیے `0.0000000000`)، `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`، `X-OmniRoute-Model`، `X-OmniRoute-Provider`، `X-OmniRoute-Latency-Ms`، `X-OmniRoute-Cache-Hit`، اور `X-OmniRoute-Fallback-Attempts` (صرف اس وقت جب > 0)، نیز `X-OmniRoute-Request-Id` اور `X-OmniRoute-Version`۔ یہ چیٹ کمپلیشنز، `/v1/responses`، `/v1/messages`، **اور میڈیا اینڈ پوائنٹس** — `/v1/embeddings`، `/v1/images/generations`، `/v1/audio/speech`، `/v1/audio/transcriptions`، `/v1/rerank`، `/v1/videos/generations`، `/v1/music/generations`، اور `/v1/moderations` (لاگت ہمیشہ `0`) — سے جاری کیے جاتے ہیں۔ قیمت دستیاب ہونے پر میڈیا کی لاگت ہر موڈیلٹی کے لحاظ سے (فی تصویر، فی سیکنڈ، فی کریکٹر، فی سرچ یونٹ) شمار کی جاتی ہے، بصورتِ دیگر `0` (fail-open) ہوتی ہے۔

> **کیش ہٹ کی لاگت کے مفاہیم:** semantic-cache HIT (`X-OmniRoute-Cache-Hit: true`) پر کوئی اپ اسٹریم کال نہیں کی جاتی، اس لیے `X-OmniRoute-Response-Cost` کی قدر `0.0000000000` ہوتی ہے (ہٹ فراہم کرنے کی **اضافی** لاگت)۔ اصل/ممکنہ لاگت الگ سے `X-OmniRoute-Cost-Saved` میں رپورٹ کی جاتی ہے۔ بلنگ استعمال کنندگان کو `X-OmniRoute-Response-Cost` کا مجموعہ کرنا چاہیے (ہٹس کی کوئی لاگت نہیں ہوتی)؛ کیش تجزیات `X-OmniRoute-Cost-Saved` کو مجموعی طور پر شمار کر سکتے ہیں۔

## خصوصی منظم سیشن لیزز

خصوصی منظم سیشن لیزنگ ایک اختیاری، کلائنٹ سے غیر جانب دار روٹنگ معاہدہ ہے: ایک فعال مالک
ایک اہل OmniRoute کنکشن رکھتا ہے۔ یہ کسی ماڈل کو لیز نہیں کرتا، OAuth کا تقاضا نہیں کرتا، کسی
مخصوص کلائنٹ کی شناخت نہیں کرتا، اور نہ ہی کسی مخصوص فراہم کنندہ کا تقاضا کرتا ہے۔

توثیق کرنے والی API کلید کے پاس `lease:exclusive` اسکوپ اور ایک واضح غیر خالی
`allowedConnections` فہرست ہونی چاہیے۔ ڈیٹابیس میوٹیشن باؤنڈری کلید کی تخلیق اور جزوی
اپ ڈیٹس کے دوران دونوں فیلڈز کو ایک ساتھ نافذ کرتی ہے۔

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

کامیاب حصول، تجدید، اور اجرا کے جوابات ٹائم اسٹیمپس، `state`، اور عین مثبت
`generation` ظاہر کرتے ہیں، لیکن منتخب کنکشن یا اسناد کبھی ظاہر نہیں کرتے۔ تجدید اور اجرا
JSON باڈی میں جنریشن فراہم کرتے ہیں:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

ایک فعال لیز مالک اپنی موجودہ بائنڈنگ کے لیے واضح طور پر رازداری کے لیے محفوظ ڈسپلے میٹا ڈیٹا کی درخواست کر سکتا ہے:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

یہ اختیاری اسٹیٹس ایکشن مبہم مالک، توثیق شدہ منظم API کلید، اور عین
فعال جنریشن کے ذریعے ایک ہی ڈیٹابیس ٹرانزیکشن میں محفوظ کیا جاتا ہے۔ `displayName` صرف تراشا ہوا، ترتیب شدہ
کنکشن نام ہے؛ جب کوئی محفوظ ترتیب شدہ نام موجود نہ ہو تو یہ `null` ہوتا ہے۔ OmniRoute کبھی کسی
ای میل یا تیار کردہ اکاؤنٹ شناخت کو متبادل کے طور پر استعمال نہیں کرتا۔ فراہم کنندہ کی قدر ایک غیر حساس ڈسپلے لیبل ہے اور کبھی
تیار کردہ ہم آہنگ فراہم کنندہ شناخت کنندہ نہیں ہوتی۔ اسناد، ٹوکنز، کوکیز، خام کنکشن یا API
کلید IDs، مالک ہیشز، فینسنگ سیکرٹس، اور اندرونی روٹنگ ڈیٹا شامل نہیں کیے جاتے۔

غلط کلید، غلط مالک، پرانی جنریشن، غیر موجود، میعاد ختم شدہ، جاری کردہ، اور کالعدم تلاشیں سبھی
کنکشن میٹا ڈیٹا کے بغیر ایک ہی `409 LEASE_FENCE_STALE` خرابی واپس کرتی ہیں۔ صلاحیت کے انتظار کا جواب پانے والے کلائنٹ کے پاس معائنہ کرنے کے لیے کوئی فعال بائنڈنگ نہیں ہوتی۔ جب روٹنگ کسی فعال لیز کو منتقل کرتی ہے،
تو وہی جنریشن درست رہتی ہے اور اسٹیٹس ایٹمی طور پر نئی بائنڈنگ واپس کرتا ہے، پرانی کبھی نہیں۔
موجودہ کلائنٹس میں کوئی تبدیلی نہیں آتی کیونکہ حصول، تجدید، اجرا، اور انتظار کے جوابات
اپنی سابقہ ساختیں برقرار رکھتے ہیں۔

یہ سرور معاہدہ معیاری OpenAI Codex `/status` کو تبدیل نہیں کرتا۔ معیاری Codex فی الحال اپنے
ماڈل فراہم کنندہ اور بلٹ اِن توثیق/اکاؤنٹ کی حالت کی رپورٹ دیتا ہے، لیکن کسی بھی حسبِ منشا
فراہم کنندہ اکاؤنٹ میٹا ڈیٹا کو رینڈر نہیں کرتا؛ مستقبل کی کلائنٹ انٹیگریشن کو یہ ایکشن کال کرنا ہوگا اور فیصلہ کرنا ہوگا کہ
`connection.displayName` کو کیسے دکھایا جائے۔

اس کے بعد ہر منظم انفرنس درخواست دونوں کنٹرول ہیڈرز فراہم کرتی ہے:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

ہر معاونت یافتہ اپ اسٹریم کوشش سے فوراً پہلے عین مالک، جنریشن، فعال کنکشن، اور توثیق شدہ API کلید
کی فینسنگ کی جاتی ہے۔ کسی دوسری کلید کے ساتھ مالک اور جنریشن کو دوبارہ چلانا اس وقت بھی ناکام ہوتا ہے
جب وہ کلید اسی کنکشن کی اجازت دیتی ہو۔ خام مالکان کو برقرار نہیں رکھا جاتا، لاگ نہیں کیا جاتا، درخواست کے
اسنیپ شاٹ میں محفوظ نہیں کیا جاتا، اور نہ ہی اپ اسٹریم فارورڈ کیا جاتا ہے۔

عارضی تنازع HTTP `429` کو `Retry-After` اور درج ذیل کے ساتھ واپس کرتا ہے:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

اس جواب کا صرف یہ مطلب ہے کہ عام اہل سیٹ غیر خالی تھا اور ہر آزاد امیدوار
کسی غیر متعلقہ فعال لیز کے زیرِ قبضہ تھا۔ غیر معاونت یافتہ ماڈلز/فراہم کنندگان، پالیسی کا عدم تطابق، کول ڈاؤن، کوٹا،
صحت، اور اہلیت کی دیگر عام ناکامیاں اپنے موجودہ OmniRoute جوابات برقرار رکھتی ہیں۔

### `x-omniroute-compression`

کمپریشن پلان کی فی درخواست اوور رائیڈ۔ سب سے زیادہ ترجیح — روٹنگ کومبو
اوور رائیڈ، فعال پروفائل، خودکار ٹریگر، اور پینل Default پر غالب رہتی ہے۔ اقدار:

| قدر           | اثر                                                                                            |
| ------------- | ---------------------------------------------------------------------------------------------- |
| `off`         | اس درخواست کے لیے کوئی کمپریشن نہیں۔                                                           |
| `default`     | پینل سے اخذ کردہ Default پروفائل (فعال پروفائل کو نظر انداز کرتا ہے)۔ Lossy انجن بند رہتے ہیں۔ |
| `safe`        | صرف ڈی ڈپلیکیشن اور وائٹ اسپیس فولڈنگ۔                                                         |
| `allow-lossy` | اس درخواست کے لیے آپریٹر پلان برقرار رکھیں، بشمول خلاصوں اور اسلوب کی دوبارہ تحریر۔            |
| `engine:<id>` | فعال ہونے پر ایک واحد انجن، مثلاً `engine:rtk`۔ اس انجن کے لیے فی درخواست اختیاری شمولیت۔      |
| `<combo>`     | ایک نامزد کومبو، جسے پہلے نام (حروف کی بڑی چھوٹی شکل سے قطع نظر)، پھر id سے ملایا جاتا ہے۔     |

نوٹس:

- نامعلوم اقدار کو نظر انداز کیا جاتا ہے (درخواست کبھی مسترد نہیں ہوتی)؛ تعین معمول کی آپریٹر ترجیح کے مطابق آگے بڑھتا ہے۔
- اگر متعدد کومبوز کا نام ایک جیسا ہو تو یقینی مطابقت کے لیے کومبو **id** فراہم کریں۔
- جس کومبو کا نام `off` یا `default` ہو اسے نام کے ذریعے منتخب نہیں کیا جا سکتا (ان کلیدی الفاظ کی پہلے تشریح کی جاتی ہے)؛ ایسے کومبو کو اس کی id سے حوالہ دیں۔
- مرکزی کمپریشن سوئچ ایک قطعی گیٹ ہے: جب کمپریشن عالمی طور پر غیر فعال ہو، تو یہ ہیڈر اسے فعال نہیں کر سکتا۔

لاگو کردہ پلان کو جوابی ہیڈر میں واپس دہرایا جاتا ہے:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

جہاں `<source>`، `request-header`، `routing-override`، `active-profile`، `auto-trigger`، `default`، یا `off` میں سے ایک ہے۔

## ایمبیڈنگز

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

دستیاب فراہم کنندگان: Nebius، OpenAI، Mistral، Together AI، Fireworks، NVIDIA، **OpenRouter**، Jina AI۔

کیٹلاگ آئی ڈیز `provider/model` کی صورت میں ہیں (مثال: `jina-ai/jina-embeddings-v5-omni-small`)۔ رجسٹری میں موجود سادہ Jina ماڈل آئی ڈیز (مثلاً `jina-embeddings-v5-text-small`، `jina-reranker-v3.5`) بھی ریزولو ہو جاتی ہیں۔ Jina embed/rerank/classify/segment پہلے ڈیش بورڈ کی `jina-ai` اسناد استعمال کرتے ہیں؛ `JINA_AI_API_KEY` صرف اس وقت فال بیک ہے جب ڈیش بورڈ کی کوئی کلید موجود نہ ہو۔ `jina-reader` کارڈ صرف Reader / `r.jina.ai` کے لیے ہے (`POST /v1/web/fetch`) اور کبھی بھی embeddings یا rerank فراہم نہیں کرتا۔

ملٹی موڈل معاونت ظاہر کرنے والے رجسٹری ماڈلز فراہم کنندہ سے غیر جانب دار زیادہ سے زیادہ 32 ساختی
آئٹمز بھی قبول کرتے ہیں۔ میڈیا آئٹم کی اقسام `text`، `image`، `audio`، `video`، اور `document` ہیں۔ ان کا میڈیا `source`
یا تو `{"type":"url","url":"https://..."}` ہوتا ہے یا
`{"type":"base64","data":"...","media_type":"..."}`۔

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`، `jina-ai/jina-embeddings-v5-omni-nano`،
اور فیملی عرف `jina-ai/jina-embeddings-v5-omni` → omni-small) Jina کی مقامی
EmbeddingsV5Request دستاویزات بھی قبول کرتا ہے اور انہیں **بغیر کسی تبدیلی کے فارورڈ کرتا ہے** به `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

مقامی `{ image | audio | video | pdf }` اقدار ایک عوامی HTTPS URL، ایک `data:` URI، یا خام
base64 ہو سکتی ہیں۔ OmniRoute ان آبجیکٹس کو اسٹرنگ میں تبدیل نہیں کرتا اور نہ ہی مقامی تصویری URLs حاصل کرتا ہے — Jina
عوامی میڈیا خود حاصل کرتا ہے۔ اضافی Jina فیلڈز (`task`، `normalized`، `truncate`، `embedding_type`) کو
فارورڈ کیا جاتا ہے۔ صرف متن والے Jina SKUs اب بھی غیر متنی دستاویزات مسترد کرتے ہیں۔

سیکیورٹی اور ٹرانسپورٹ کی حدود:

- ریموٹ میڈیا URLs کا عوامی HTTPS ہونا ضروری ہے۔ معیاری `{type,source:url}` آئٹمز
  سرور کی جانب سے حاصل کیے جاتے ہیں (ری ڈائریکٹ کی دوبارہ توثیق، ٹائم آؤٹ، سائز کی حدود، عوامی DNS، کنکشن پننگ) اور
  فراہم کنندہ کو کال کرنے سے پہلے اِن لائن کر دیے جاتے ہیں۔ Jina کے مقامی `{image:"https://..."}` آئٹمز کو اسی
  عوامی HTTPS جانچ کے بعد جوں کا توں فارورڈ کیا جاتا ہے؛ Jina URL حاصل کرتا ہے۔
- اِن لائن base64 میڈیا کی حد فی آئٹم ڈی کوڈ شدہ 8 MiB اور پوری درخواست میں ڈی کوڈ شدہ 16 MiB ہے۔

فراہم کنندہ کے لیے تبدیلی (معیاری آئٹمز کبھی بھی بغیر تبدیلی کے فارورڈ نہیں کیے جاتے):

- Jina ملٹی موڈل ماڈلز: ہر اعلیٰ سطحی آئٹم ایک موڈیلٹی کلید والا آبجیکٹ بن جاتا ہے
  (`text` / `image` / `audio` / `video` / `pdf`) جس میں اِن لائن میڈیا کے لیے data URIs استعمال ہوتے ہیں؛ فی
  اعلیٰ سطحی آئٹم ایک ویکٹر۔
- Gemini Embedding 2 فیملی: ایک اعلیٰ سطحی ارے، `content.parts` (`text` یا `inline_data`) کے ساتھ، ایک واحد مقامی
  `models/{model}:embedContent` درخواست بن جاتا ہے۔
- llama.cpp (`llama-cpp/<model>`، مقامی سرور کے ذریعے لوڈ کیا گیا کوئی بھی ماڈل): معیاری `text` آئٹمز
  سادہ اسٹرنگز بن جاتے ہیں، اور `image` / `audio` / `video` میں سے ہر ایک ایک
  `{"content": [part]}` آبجیکٹ بن جاتا ہے، جس میں اِن لائن ڈیٹا کے ساتھ llama-server کے چیٹ مواد کے حصے (`image_url`،
  `input_audio` بہ فارمیٹ `wav` / `mp3` / `flac`، `input_video`) استعمال ہوتے ہیں؛ فی اعلیٰ سطحی آئٹم
  ایک ویکٹر۔ سرور کو `--embedding --mmproj …` کے ساتھ چلنا ضروری ہے؛ پروجیکٹر کے بغیر یہ
  میڈیا کو خود مسترد کر دیتا ہے۔ `document` معاونت یافتہ نہیں ہے۔
- واضح موڈیلٹی میٹا ڈیٹا کے بغیر نامعلوم/متحرک ماڈلز، ساختی ان پٹ کو HTTP 400 کے ساتھ مسترد کرتے ہیں۔

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

غیر معاون ماڈل/موڈیلٹی امتزاج، آئٹم کو جبراً تبدیل کرنے کے بجائے HTTP 400 واپس کرتے ہیں۔ پرانی اسٹرنگ/ٹوکن درخواستوں کے
غیر ان پٹ توسیعی فیلڈز بدستور بغیر تبدیلی کے آگے منتقل ہوتے ہیں۔

```bash
# تمام ایمبیڈنگ ماڈلز کی فہرست بنائیں
GET /v1/embeddings
```

## امیج جنریشن

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

دستیاب فراہم کنندگان میں OpenAI (GPT Image 2)، xAI (Grok Image)، Together AI (FLUX)، Fireworks AI، Nebius (FLUX)، Hyperbolic، NanoBanana، **OpenRouter**، **ZenMux**، SD WebUI (مقامی)، اور ComfyUI (مقامی) شامل ہیں۔

`n`، `data[]` میں `n` امیجز واپس کرتا ہے۔ جن فراہم کنندگان کی اپ اسٹریم API ہر کال پر ایک امیج واپس کرتی ہے
(Black Forest Labs، Stability AI، Leonardo، Ideogram، Haiper، Hyperbolic، Magnific/Freepik،
NVIDIA NIM، Cloudflare Workers AI)، ان کے لیے `n` الگ اپ اسٹریم کالز کی جاتی ہیں، جن میں زیادہ سے زیادہ 4 بیک وقت جاری رہ سکتی ہیں۔ ایک
مقررہ `seed` کو کال انڈیکس کے مطابق بڑھایا جاتا ہے (`seed`، `seed + 1`، …)، تاکہ امیجز مختلف ہوں لیکن
دوبارہ تیار کی جا سکیں۔ `n` کی زیادہ سے زیادہ حد 10 ہے۔ اگر کوئی بھی کال ناکام ہو تو پوری درخواست
ناکام ہو جاتی ہے۔ فین آؤٹ فارمیٹس کی فہرست `SINGLE_IMAGE_FANOUT_FORMATS` میں
`open-sse/handlers/imageGeneration/fanOut.ts` پر موجود ہے۔

ZenMux موجودہ API کلید کنکشن کو دوبارہ استعمال کرتا ہے اور `zenmux/` یا `zm/` سابقے قبول کرتا ہے:

- `zenmux/openai/gpt-image-2`، ZenMux کی OpenAI Images API استعمال کرتا ہے۔ اختیارات میں `size`،
  `quality`، `n`، `output_format`، `output_compression`، `background`، اور `response_format` شامل ہیں۔
- دیگر پبلشرز، جیسے `zm/meta/muse-image-1.0`، ZenMux کا Vertex AI `:predict`
  اینڈ پوائنٹ استعمال کرتے ہیں۔ `n` کو `sampleCount`، `aspect_ratio` کو `aspectRatio`، اور `image_size`
  (`1K`، `2K`، `4K`) کو `sampleImageSize` سے میپ کیا جاتا ہے۔ پکسل پر مبنی `size` صرف پہلو کا تناسب فراہم کرتا ہے،
  ضمانت شدہ پکسل ابعاد نہیں۔ معاون تناسب، ریزولیوشنز، اور تعداد ماڈل کے لحاظ سے مختلف ہوتے ہیں۔
- `zm/inclusionai/ming-image-0.1-design` اپنی ابعاد خود منتخب کرتا ہے۔ `size`،
  `aspect_ratio`، اور `image_size` شامل نہ کریں؛ واضح طور پر دی گئی اقدار HTTP 400 واپس کرتی ہیں۔ PNG، JPEG، اور WebP
  کی درخواست `output_format` کے ذریعے کی جا سکتی ہے۔

یہ انٹیگریشن متن سے امیج بنانے کی سہولت فراہم کرتا ہے، حوالہ جاتی امیج کی تدوین نہیں۔ Vertex
آؤٹ پٹ کو `data[].b64_json` میں معمول پر لایا جاتا ہے؛ `response_format: "url"` اپ اسٹریم
HTTPS URL واپس کرتا ہے، یا جب صرف امیج بائٹس دستیاب ہوں تو base64 ڈیٹا URL۔ خالی/فلٹر شدہ آؤٹ پٹس
خالی کامیاب نتیجے کے بجائے خرابی واپس کرتے ہیں۔ ماڈل تک رسائی ZenMux اکاؤنٹ پر منحصر ہے۔
[ZenMux کی Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) اور
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image) دیکھیں۔

```bash
# تمام امیج ماڈلز کی فہرست دکھائیں
GET /v1/images/generations
```

## دستاویز OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model`، `provider/model` سابقے کے ذریعے OCR فراہم کنندہ منتخب کرتا ہے؛ صرف ماڈل آئی ڈی (مثلاً
`mistral-ocr-latest`) اپنے رجسٹرڈ فراہم کنندہ سے منسلک ہو جاتی ہے، اور اگر `model` شامل نہ کیا جائے تو
ڈیفالٹ Mistral (`mistral-ocr-latest`) استعمال ہوتا ہے۔ رجسٹرڈ فراہم کنندگان (`open-sse/config/ocrRegistry.ts`):

| فراہم کنندہ آئی ڈی            | ماڈل آئی ڈی          | `model` کی قدر                                             | نوٹس                                                                                                           |
| ----------------------------- | -------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (یا صرف `mistral-ocr-latest`) | ہم وقت — جواب واحد اپ اسٹریم کال سے براہ راست واپس کیا جاتا ہے۔                                                |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                | غیر ہم وقت اپ اسٹریم (`analyze` + پول) — ذیل میں دیکھیں۔                                                       |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                    | ہم وقت، Vertex AI کے `openapi/chat/completions` پارٹنر اینڈ پوائنٹ کے ذریعے — توثیق/URL کے لیے ذیل میں دیکھیں۔ |

تینوں فراہم کنندگان یکساں Mistral طرز کی باڈی میں جواب دیتے ہیں:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence کا پول فلو

Azure Document Intelligence کی `analyze` API غیر ہم وقت ہے: ابتدائی درخواست باڈی کے بجائے
`Operation-Location` ہیڈر واپس کرتی ہے، اور نتیجے کے لیے پولنگ ضروری ہے۔ ہینڈلر
(`open-sse/handlers/ocr.ts`) اس URL کو ہر سیکنڈ، زیادہ سے زیادہ 30 کوششوں تک پول کرتا ہے، غیر `ok` پول جواب یا
`"failed"` اسٹیٹس پر فوراً ناکام ہو جاتا ہے (پولنگ جاری نہیں رکھتا)، اور اگر کوششوں کی مقررہ حد ختم ہونے کے بعد بھی
آپریشن جاری ہو تو `504` واپس کرتا ہے۔ آخری Azure جواب کو کالر کو واپس کرنے سے پہلے
اسی `pages`/`markdown` ساخت میں معمول پر لایا جاتا ہے جو Mistral استعمال کرتا ہے،
اس لیے کلائنٹ کوڈ کو فراہم کنندہ کے لیے کوئی خصوصی صورت سنبھالنے کی ضرورت نہیں ہوتی۔

### Vertex AI DeepSeek OCR کی توثیق اور اینڈ پوائنٹ ریزولیوشن

`vertex-deepseek-ocr` وہی Vertex AI توثیق دوبارہ استعمال کرتا ہے جسے OmniRoute پہلے ہی
چیٹ/امیج ٹریفک کے لیے سپورٹ کرتا ہے (`open-sse/executors/vertex.ts`): کنکشن کی API کلید یا تو
Service Account JSON کریڈینشل ہوتی ہے (جسے JWT-bearer
فلو کے ذریعے مختصر مدت کے OAuth رسائی ٹوکن میں تبدیل کیا جاتا ہے) یا پہلے سے بنایا گیا OAuth رسائی ٹوکن، جسے جوں کا توں استعمال کیا جاتا ہے۔ اپ اسٹریم اینڈ پوائنٹ URL، Vertex کا
عمومی `openapi/chat/completions` پارٹنر اینڈ پوائنٹ ہے، جو کنکشن کے پروجیکٹ اور
ریجن سے بنایا جاتا ہے — واضح `providerSpecificData.project`/`providerSpecificData.region` کو ہمیشہ ترجیح دی جاتی ہے؛
بصورت دیگر پروجیکٹ Service Account JSON کے `project_id` سے اخذ کیا جاتا ہے اور ریجن
ڈیفالٹ طور پر `us-central1` ہوتا ہے۔ دونوں ریزولیوشنز `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`، `resolveVertexOcrBaseUrl`) میں ہوتی ہیں، جنہیں
`src/app/api/v1/ocr/route.ts`، `handleOcr` کو ڈسپیچ کرنے سے پہلے استعمال کرتا ہے۔

## ماڈلز کی فہرست

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ تمام چیٹ، ایمبیڈنگ، اور امیج ماڈلز + کومبوز کو OpenAI فارمیٹ میں لوٹاتا ہے
```

### ماڈل id کے سابقے (`?prefix=`)

زیادہ تر ماڈلز کی تشہیر ایک **پرووائیڈر سابقے** کے تحت کی جاتی ہے۔ آپ کو کون سا سابقہ ملے گا، یہ
`MODELS_CATALOG_PREFIX_MODE` فیچر فلیگ کے ذریعے کنٹرول ہوتا ہے، اور اسے ایک query parameter کے ساتھ
**ہر درخواست کے لیے** اوور رائیڈ کیا جا سکتا ہے — یہ ایسے کلائنٹ کے لیے مفید ہے جو سب کے لیے سرور کی
عمومی ترتیب تبدیل کیے بغیر ایک صاف فہرست چاہتا ہو:

```bash
GET /v1/models?prefix=alias        # ہر ماڈل کے لیے ایک id — مختصر alias سابقہ
GET /v1/models?prefix=dual         # دونوں صورتیں (سرور کا ڈیفالٹ)
GET /v1/models?prefix=canonical    # صرف مکمل provider-id سابقہ
```

| موڈ         | اخراج                                                     | نوٹس                                                                                                                                                                                            |
| ----------- | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **اور** `claude/claude-sonnet-4-6` | **ڈیفالٹ۔** دونوں ids ایک ہی ماڈل کی طرف روٹ ہوتی ہیں؛ اسے برقرار رکھا گیا ہے تاکہ کسی بھی صورت کو ہارڈ کوڈ کرنے والی کلائنٹ کنفیگریشنز کام کرتی رہیں۔ اس سے کیٹلاگ تقریباً دوگنا ہو جاتا ہے۔   |
| `alias`     | `cc/claude-sonnet-4-6`                                    | ہر ماڈل کے لیے ایک اندراج۔ جن پرووائیڈرز کا الگ alias نہیں ہے وہ بھی اپنا اندراج خارج کرتے ہیں، اس لیے کچھ ضائع نہیں ہوتا۔                                                                      |
| `canonical` | `claude/claude-sonnet-4-6`                                | مکمل provider-id سابقے کے تحت ہر ماڈل کے لیے ایک اندراج۔ جن پرووائیڈرز کا الگ alias نہیں ہے (مثلاً `antigravity/…`، `agy/…`) وہ بھی یہاں اپنی واحد id خارج کرتے ہیں، اس لیے کچھ ضائع نہیں ہوتا۔ |

`dual` موڈ کے mirror کو query parameter کے بغیر بھی پہچانا جا سکتا ہے: اس میں بنیادی id کی طرف اشارہ کرنے والی
`parent` فیلڈ ہوتی ہے۔

ماڈل picker دکھانے والے کلائنٹس کو `?prefix=alias` کی درخواست کرنی چاہیے — یہی
[OmniCopilot VS Code ایکسٹینشن](../guides/VSCODE-COPILOT.md) کرتی ہے۔

### دریافت کے فلٹرز (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` اختیاری دریافت کے فلٹرز قبول کرتا ہے۔ ان میں سے کسی کے بغیر response
میں کوئی تبدیلی نہیں ہوتی۔ یہ اس کیٹلاگ کو محدود کرتے ہیں جو کالر پہلے ہی دیکھ سکتا ہے (API-key کی اجازتیں پہلے لاگو ہوتی ہیں)،
اور یہ OpenAI طرز کی `limit` / `after` پیجنگ سے پہلے چلتے ہیں:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # فہرست میں موجود ہر capability کا true ہونا ضروری ہے
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # کیٹلاگ `type`؛ جن قطاروں میں یہ نہ ہو وہ `chat` ہیں
GET /v1/models?q=sonnet&limit=10                           # id یا نام پر حروف کے کیس سے غیر حساس مماثلت
```

| پیرامیٹر      | اقدار                                                                                               |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | غیر منفی صحیح عدد، جس کا `context_length` سے موازنہ کیا جاتا ہے                                     |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 حروف                                                                                          |

کوئی نامعلوم قدر، یا ایسا `min_context` جو غیر منفی صحیح عدد نہ ہو (مثلاً `1.5`)،
HTTP `400` لوٹاتا ہے اور پیغام میں درست اقدار کی فہرست شامل ہوتی ہے۔ نفاذ:
`src/app/api/v1/models/catalogFilters.ts`۔

### ماڈلز کی مختصر فہرست (`POST /v1/models/query`)

`POST /v1/models/query` اسی کیٹلاگ سے ایک مختصر، قطعی فہرست لوٹاتا ہے، جس پر وہی
تصدیق اور فی-key visibility لاگو ہوتی ہے جو `GET /v1/models` پر ہوتی ہے:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

ہر فیلڈ اختیاری ہے۔ `capabilities` اور `exclude` ایک array یا comma-separated string قبول کرتے ہیں؛
`max_output` کا موازنہ `max_output_tokens` سے کیا جاتا ہے۔ نتائج پہلے `owned_by`، پھر `id` کے مطابق ترتیب دیے جاتے ہیں۔
`limit` کی ڈیفالٹ قدر `20` ہے اور `100` سے زیادہ اقدار کو `100` تک محدود کر دیا جاتا ہے۔ غیر درست JSON، کوئی نامعلوم
فیلڈ، یا کوئی غیر درست قدر HTTP `400` لوٹاتی ہے۔

### انفرادی طور پر مخفی چیٹ ماڈلز

اپنے پرووائیڈر صفحے پر **مخفی** کے طور پر نشان زد ماڈل کو کیٹلاگ سے خارج کر دیا جاتا ہے اور واضح طور پر
درخواست کیے جانے پر HTTP `404` / `model_not_found` کے ساتھ مسترد کر دیا جاتا ہے۔ جانچ حل شدہ
پرووائیڈر اور ماڈل کو استعمال کرتی ہے، جس میں پرووائیڈر aliases، compatible-provider node prefixes، اور
connection defaults شامل ہیں۔ کومبو مخفی اہداف کو چھوڑ دیتا ہے اور کسی مرئی sibling کو استعمال کر سکتا ہے؛ جب کوئی
قابلِ اجرا ہدف باقی نہ رہے تو یہ وہی error code لوٹاتا ہے۔ مخفی حالت ہٹانے کا اثر اگلی
درخواست پر ہوتا ہے۔ صرف امیج کی visibility overrides، اسی ID والے چیٹ ماڈل کو مخفی نہیں کرتیں۔

ماڈل کی یہ انفرادی ترتیب
[ماڈل نمائش کی allow/deny فہرستوں](../routing/MODEL_EXPOSURE_LIST.md) سے الگ ہے، جو واضح dispatch کو برقرار رکھتے ہوئے کیٹلاگ
کی تشہیر اور auto-routing امیدواروں کو فلٹر کرتی ہیں۔ API-key ماڈل کی اجازتیں آزادانہ طور پر بدستور لاگو رہتی ہیں۔
کیٹلاگ کے سابقے کا ڈیفالٹ موڈ `dual` ہی رہتا ہے۔

### بغیر thinking والے ماڈل variants

thinking کی صلاحیت رکھنے والے Claude ماڈلز کے لیے، `/v1/models` ایک **بغیر thinking** والا variant بھی مشتہر کرتا ہے جس کی id کے شروع میں `claude-3-omniroute-no-thinking/` شامل ہوتا ہے:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

اس آئی ڈی کو منتخب کرنے سے (مثلاً ایسی Claude Code کنفیگ میں جو ہمیشہ ایک `thinking` بلاک منسلک کرتی ہے) یہ ریزننگ کو غیر فعال رکھتے ہوئے اصل `<provider>/<model>` کی طرف واپس ریزولو ہو جاتی ہے — `/v1/messages` پاتھ پر `thinking:{type:"disabled"}`، یا `/v1/chat/completions` پاتھ پر `reasoning`/`reasoning_effort` فیلڈز کو حذف کر دیا جاتا ہے۔ یہ ویریئنٹ صرف Claude خاندان کے ان ماڈلز کے لیے فہرست میں شامل ہوتا ہے جو تھنکنگ کو سپورٹ کرتے ہیں **اور** `disabled` کی تعمیل کرتے ہیں (لہٰذا، مثلاً، صرف اڈاپٹیو ماڈلز جو `disabled` کو مسترد کرتے ہیں، خارج کر دیے جاتے ہیں)۔ آپریٹرز `ModelSpec.noThinkingAlias` کے ذریعے ہر ماڈل کے لیے اس ویریئنٹ کو لازماً آن یا آف کر سکتے ہیں۔

Bifrost، CLIProxyAPI، اور مستقبل کے سائڈکار راؤٹرز کے استعمال کردہ JSON سے محفوظ پرووائیڈر پلگ اِن مینی فیسٹ کو واپس کرتا ہے۔ جواب TypeScript پرووائیڈر رجسٹری سے تیار کیا جاتا ہے اور اس میں دانستہ طور پر OAuth کلائنٹ سیکرٹس، رن ٹائم ماحول کی ریزولیوشن، ایگزیکیوٹر فنکشنز، درخواست کے ہیڈرز، اور اکاؤنٹ ڈیٹا شامل نہیں ہوتے۔

## ElevenLabs آڈیو جنریشن

اپنی ElevenLabs API کلید کے ساتھ OmniRoute میں ایک `elevenlabs` پرووائیڈر کنکشن ترتیب دیں۔
کلائنٹس اپنی **OmniRoute** کلید (`Authorization: Bearer $OMNIROUTE_API_KEY`) سے توثیق کرتے ہیں؛
گیٹ وے محفوظ شدہ پرووائیڈر کلید کو `xi-api-key` کے طور پر فراہم کرتا ہے۔ ElevenLabs کلید کو کبھی بھی
گیٹ وے بیئرر ٹوکن کے طور پر نہ بھیجیں۔

| طریقہ | راستہ                       | جواب                                   | API کلید اینڈ پوائنٹ زمرہ |
| ----- | --------------------------- | -------------------------------------- | ------------------------- |
| POST  | `/v1/sound-generation`      | مقامی آڈیو بائٹس                       | `elevenlabs`              |
| POST  | `/v1/music`                 | مقامی آڈیو بائٹس                       | `music`                   |
| POST  | `/v1/music/stream`          | اسٹریمنگ آڈیو بائٹس                    | `music`                   |
| POST  | `/v1/music/detailed`        | مقامی ملٹی پارٹ آڈیو اور کمپوزیشن پلان | `music`                   |
| POST  | `/v1/music/detailed/stream` | مقامی SSE میٹا ڈیٹا اور آڈیو چنکس      | `music`                   |
| POST  | `/v1/music/plan`            | JSON کمپوزیشن پلان                     | `music`                   |

یہ اینڈ پوائنٹس موجودہ `/v1/audio/speech`، `/v1/audio/transcriptions`،
`/v1/voices`، `/v1/text-to-speech/{voiceId}` اور `/v1/speech-to-text` روٹس کی تکمیل کرتے ہیں۔ مقامی JSON فیلڈز
اور کوئری پیرامیٹرز، جیسے `output_format` اور `enable_logging`، برقرار رکھے جاتے ہیں۔
`/v1/music/detailed` کے جوابات اپنی ملٹی پارٹ باؤنڈریز برقرار رکھتے ہیں؛ انہیں ملٹی پارٹ کے طور پر پارس کریں۔
`/v1/music/detailed/stream` کمپوزیشن میٹا ڈیٹا اور SSE ایونٹس میں
base64 آڈیو چنکس کے ساتھ `text/event-stream` واپس کرتا ہے۔ تمام چھ روٹس CORS پری فلائٹ کی معاونت کرتے ہیں۔

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# ایک مختصر صوتی اثر۔ دورانیہ: 0.5 سے 30 سیکنڈ۔
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# موسیقی کا دورانیہ ملی سیکنڈز میں ظاہر کیا جاتا ہے: 3000 سے 600000۔
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

بتدریج آڈیو فراہمی کے لیے اسی JSON باڈی کے ساتھ `/v1/music/stream` استعمال کریں۔ کمپوزیشن
`prompt` یا `composition_plan` میں سے صرف ایک کو قبول کرتی ہے؛ `/v1/music/plan` کے لیے `prompt`
درکار ہے اور یہ اختیاری طور پر `source_composition_plan` قبول کرتا ہے۔ مقامی اسکیماز اضافی
پرووائیڈر فیلڈز کو برقرار رکھتے ہیں تاکہ کمپوزیشن پلان کے ورژنز اور فائن ٹیوننگ کے اختیارات ElevenLabs تک پہنچ سکیں۔

متحد `/v1/music/generations` اینڈ پوائنٹ `elevenlabs/music_v1`،
`elevenlabs/music_v2` اور `elevenlabs/music_v2_5` کو بھی قبول کرتا ہے۔ ایک فعال ElevenLabs کنکشن کے ساتھ،
یہ ماڈلز میوزک کیٹلاگ میں ظاہر کیے جاتے ہیں۔ یہ اینڈ پوائنٹ
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` واپس کرتا ہے۔ اس کا `duration` فیلڈ
سیکنڈز میں ہوتا ہے اور `music_length_ms` سے میپ ہوتا ہے؛ واضح طور پر فراہم کردہ `music_length_ms` کو ترجیح حاصل ہوتی ہے۔
`instrumental`، `force_instrumental` سے میپ ہوتا ہے، جبکہ مقامی فیلڈ کو ترجیح حاصل ہوتی ہے۔
اسٹریمنگ کے لیے مقامی اسٹریمنگ اینڈ پوائنٹس، اور صرف کمپوزیشن پلان سے چلنے والی درخواستوں کے لیے
مقامی کمپوزیشن اینڈ پوائنٹ استعمال کریں۔

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

اپ اسٹریم کال سے پہلے اینڈ پوائنٹ، ماڈل، بجٹ، اور کنکشن کی پابندیاں لاگو ہوتی ہیں۔ مقامی
روٹس اپ اسٹریم اسٹیٹس کوڈز اور ایرر باڈیز کو بغیر تبدیلی کے واپس کرتے ہیں، جن میں پلان
کی پابندی کے لیے `402` اور کوٹا حد کے لیے `429` شامل ہیں۔ موجود ہونے کی صورت میں `character-cost`، `song-id`، `request-id` اور `retry-after`
ہیڈرز برقرار رکھے جاتے ہیں۔ مفت کریڈٹ بیلنس ہر
میوزک ماڈل، آؤٹ پٹ فارمیٹ، یا API فیچر تک رسائی کی ضمانت نہیں دیتا: ElevenLabs ہر درخواست کے لیے استحقاق کا فیصلہ کرتا ہے۔
متحد اینڈ پوائنٹ OmniRoute کے معمول پر لائے گئے ایرر انویلپ میں ایرر اسٹیٹس کوڈز برقرار رکھتا ہے۔

اپ اسٹریم معاہدے: [صوتی اثرات](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert)،
[موسیقی کی کمپوزیشن](https://elevenlabs.io/docs/api-reference/music/compose) اور
[اسٹریمنگ موسیقی کی تفصیلات](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)۔

تمام POST روٹس ایک ہی ساخت کی پیروی کرتے ہیں: `Bearer your-api-key` + Zod سے توثیق شدہ JSON باڈی (`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema` وغیرہ، `src/shared/validation/schemas.ts` دیکھیں)۔ اسکیما کی ناکامی پر 4xx واپس کیا جاتا ہے۔

جو کلائنٹس `Authorization: Bearer ...` منسلک نہیں کر سکتے، ان کے لیے OmniRoute یو آر ایل میں API کلیدیں بھی قبول کرتا ہے، یا تو کوئری اسٹرنگ مطابقت (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) کے ذریعے یا ذیل میں دستاویزی مخصوص `/api/v1/vscode/{token}/...` اینڈ پوائنٹس کے ذریعے۔

```bash
# دوبارہ درجہ بندی (کلاؤڈ رجسٹری فراہم کنندہ، یا "<prefix>/<model>" کی صورت میں OpenAI سے مطابقت رکھنے والا فراہم کنندہ نوڈ)
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina درجہ بندی (Foundation API اسناد)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina سیگمینٹر
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina تلاش (s.jina.ai؛ فراہم کنندہ کے عرف: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# مواد کی نگرانی
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — audio/mpeg (یا مطلوبہ فارمیٹ) باڈی واپس کرتا ہے
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS کے لیے زبان اور آواز درکار ہیں: `language` کی طے شدہ قدر "en" ہے؛ غیر موجود
# آواز یا OpenAI کی معیاری آواز کا نام (alloy, nova, …) "Adrian" بن جاتا ہے
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# تصویر میں ترمیم (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# ویڈیو / موسیقی کی جنریشن (فراہم کنندہ کے سابقے والی ماڈل آئی ڈی)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **ری رینک فراہم کنندہ نوڈز:** `POST /v1/rerank` کی درخواستیں OpenAI سے مطابقت رکھنے والے فراہم کنندہ نوڈز
> (oMLX، vLLM، Infinity، گیٹ وے کے پیچھے TEI، …) کی طرف بھی بھیجی جاتی ہیں، جنہیں `<node-prefix>/<model>` کے طور پر
> ایڈریس کیا جاتا ہے۔ لوپ بیک نوڈز (`localhost`، `127.0.0.1`، `172.16.0.0/12`) ہمیشہ اہل ہوتے ہیں، اور وہ میزبان نام
> بھی اہل ہوتے ہیں جنہیں آپریٹر `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` میں درج کرتا ہے (مثلاً Docker/Compose سروس کا نام،
> جیسے `http://reranker:8080/v1`؛ ان سے براہِ راست رابطہ کیا جاتا ہے، کبھی بھی `HTTP(S)_PROXY` یا کسی کنکشن کے
> مقررہ پراکسی کے ذریعے نہیں)۔ کسی دوسرے
> میزبان پر موجود نوڈز — مثلاً LAN مشین یا Tailscale پیئر — صرف اس وقت اہل ہوتے ہیں جب آپریٹر
> `RERANK_REMOTE_PROVIDER_NODES` فیچر فلیگ فعال کرے **اور** نوڈ کا بنیادی URL فراہم کنندہ کی
> آؤٹ باؤنڈ URL پالیسی (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`) پر پورا اترے۔
> میموری انجن کا ری رینک مرحلہ اس روٹ کو
> لوپ بیک کے ذریعے کال کرتا ہے، اس لیے یہی اصول میموری کی ترتیبات میں `rerankProviderModel` پر بھی لاگو ہوتا ہے۔
>
> **مقامی سرور کی ساختیں:** نوڈ کو `<base>/v1/rerank` پر، اور 404 آنے پر `<base>/rerank`
> (Infinity، TEI) پر کال کیا جاتا ہے۔ اپ اسٹریم باڈی میں Cohere/OpenAI والی املا (`documents`،
> `return_documents`) اور TEI والی املا (`texts`، `return_text`) دونوں شامل ہوتی ہیں، اور اپ اسٹریم جواب کو
> Cohere ساخت میں معمول پر لایا جاتا ہے: TEI کا سادہ `[{index, score, text}]`، مختصر گیٹ ویز سے آنے والا
> `{results: [{index, score}]}`، اور Voyage طرز کا `{data: [...]}`، سبھی کلائنٹ کو
> `{results: [{index, relevance_score, document?}]}` کی صورت میں واپس ملتے ہیں، اسکور کے لحاظ سے مرتب اور `top_n` تک محدود۔
>
> **فراہم کنندہ نوڈ کی دریافت:** OpenAI سے مطابقت رکھنے والے فراہم کنندہ نوڈ پر موجود ماڈلز `GET /v1/models` میں
> نوڈ کے سابقے کے تحت ظاہر ہوتے ہیں۔ وہ اندراجات جن میں اینڈ پوائنٹ میٹا ڈیٹا موجود نہ ہو (جیسا کہ عموماً مقامی `/v1/models` فہرستوں میں ہوتا ہے)
> نوڈ کا `apiType` وراثت میں لیتے ہیں، اس لیے `embeddings` نوڈ کے ماڈلز `type: "embedding"` اور
> `rerank` نوڈ کے ماڈلز `type: "rerank"` ہوتے ہیں، بجائے اس کے کہ انہیں بطور ڈیفالٹ چیٹ سمجھا جائے؛ ہم وقت کردہ یا دستی طور پر شامل کردہ اندراج میں واضح
> `supportedEndpoints` کو پھر بھی ترجیح حاصل رہتی ہے۔

### مخصوص فراہم کنندہ روٹس

```bash
POST /v1/providers/{provider}/chat/completions
POST /v1/providers/{provider}/embeddings
POST /v1/providers/{provider}/images/generations
```

اگر فراہم کنندہ کا سابقہ موجود نہ ہو تو اسے خودکار طور پر شامل کر دیا جاتا ہے۔ غیر مطابق ماڈلز `400` واپس کرتے ہیں۔

## فائلز API

بیچ اِن پٹ/آؤٹ پٹ اور فائل کے مقصد کے مطابق اپ لوڈز کے لیے OpenAI سے مطابقت رکھنے والا فائلز اینڈ پوائنٹ۔

| طریقہ  | پاتھ                     | تفصیل                                                                                                                       |
| ------ | ------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/files`              | فائل اپ لوڈ کریں (ملٹی پارٹ: `file`، `purpose`، `expires_after[anchor]`، `expires_after[seconds]`) — زیادہ سے زیادہ 512 MiB |
| GET    | `/v1/files`              | توثیق شدہ API کلید کی فائلیں فہرست کریں                                                                                     |
| GET    | `/v1/files/[id]`         | فائل کا میٹا ڈیٹا حاصل کریں                                                                                                 |
| DELETE | `/v1/files/[id]`         | فائل حذف کریں                                                                                                               |
| GET    | `/v1/files/[id]/content` | فائل کی خام باڈی واپس اسٹریم کریں                                                                                           |

**توثیق:** بیئرر API کلید — فائلوں کا دائرہ `getApiKeyRequestScope` کے ذریعے ہر API کلید کے لحاظ سے متعین ہوتا ہے۔ کوئی کلید
صرف اپنی فائلیں دیکھ، ڈاؤن لوڈ اور حذف کر سکتی ہے؛ کلید کے بغیر ڈیش بورڈ سیشن پوری
انسٹینس کو پڑھ سکتا ہے؛ مالک کے بغیر فائل (گمنام یا ڈیش بورڈ سیشن سے اپ لوڈ کردہ) تک ہر
غیر سیشن کالر کی رسائی مسترد کر دی جاتی ہے۔ `GET /v1/files` کسی گمنام کالر — اور فراہم کردہ ایسی کلید جس کی
شناخت نہ ہو سکے — کو `401` کے ساتھ مسترد کرتا ہے، چاہے `REQUIRE_API_KEY=false` ہو، تاکہ ہر ٹیننٹ کی
فائلیں فہرست نہ ہوں (GHSA-m3hp-hq9g-fpmv، GHSA-2jm2-mpx8-6523)۔

### Exa اور Tavily کے `provider_options`

Exa اور Tavily فراہم کنندہ کے لیے مخصوص فیلڈز نام کی گنجائش رکھنے والے بیگ سے پڑھتے ہیں:
`provider_options.exa` (یا `provider_options["exa-search"]`) اور `provider_options.tavily`
(یا `provider_options["tavily-search"]`)۔ صرف ذیل کی کلیدیں آگے بھیجی جاتی ہیں۔ ہر کلید کو
`open-sse/handlers/search/providerOptionsPassthrough.ts` میں اس کے اپنے Zod اسکیما کے مطابق
جانچا جاتا ہے، اور غلط قسم والی کلید حذف کر دی جاتی ہے۔ توثیق، بنیادی URL،
`stream` اور `outputSchema` سمیت کسی بھی دوسری کلید کو نظر انداز کیا جاتا ہے۔ دوسرے فراہم کنندگان
کے زیر استعمال مسطح کلیدیں (`cx`, `depth`, ...) پہلے کی طرح کام کرتی ہیں۔

| فراہم کنندہ | اعلیٰ سطح کی فیلڈز                                                                                                                                                                                                                                                                                                                                                        | تودرتو                                                                                                                                                                     |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa         | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (مسطح ابتدائی اقدار)، `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                           | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` کو طے شدہ `{ text: true, highlights: true }` کے اوپر ضم کیا جاتا ہے |
| Tavily      | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                          |

عمومی فیلڈز ہمیشہ ترجیح رکھتی ہیں: `query`، `max_results`، `filters` (ڈومینز)، `country` اور
`search_type` سے اخذ کردہ موضوع۔ Exa پر، `search_type: "news"`، `category: "news"` کو برقرار رکھتا ہے۔
Tavily، `search_type: "finance"` (`topic: "finance"`) بھی قبول کرتا ہے۔

عمومی `time_range` اب دونوں فراہم کنندگان تک پہنچتا ہے: Exa کو `startPublishedDate` (ISO
ٹائم اسٹیمپ) اور Tavily کو `start_date` (`YYYY-MM-DD`) ملتا ہے۔ `provider_options`
میں واضح طور پر دی گئی تاریخ نقشہ شدہ تاریخ پر فوقیت رکھتی ہے۔

Exa کے نتائج `provider_raw` میں `id`، `highlight_scores`، `summary`، `subpages`، `entities` اور `extras`
کو برقرار رکھتے ہیں۔ Tavily کے نتائج `images` اور `favicon` کو برقرار رکھتے ہیں۔

لاگت کا حساب اب بھی مسطح رجسٹری `costPerQuery` کے ذریعے کیا جاتا ہے۔ Tavily ہر کال کے لیے
`search_depth: "advanced"` پر زیادہ کریڈٹس وصول کرتا ہے، اور یہ فرق
`usage.search_cost_usd` میں ظاہر نہیں ہوتا۔

## ویب فیچ API

کنفیگر کردہ ویب فیچ فراہم کنندہ (Firecrawl، Jina
Reader، Tavily Extract، TinyFish Fetch، Nimble Extract، Parallel Extract) کے ذریعے کسی URL سے مواد اخذ کریں۔

Parallel Extract (`parallel-search`، وہی API کلید جو Parallel Search کے لیے ہے) صرف Markdown
واپس کرتا ہے — کوئی بھی دوسرا `format` ایک `400` کا باعث بنتا ہے — اور مواد کو 100,000 حروف تک محدود کرتا ہے۔ جب
ہدف صفحے سے ہی مواد اخذ نہ کیا جا سکے، تو upstream اسے HTTP 200 کے اندر رپورٹ کرتا ہے؛
OmniRoute اسے ایک مقررہ پیغام کے ساتھ `422` کے طور پر ظاہر کرتا ہے۔

| طریقہ | راستہ           | وضاحت                                                             |
| ----- | --------------- | ----------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | URL فیچ/اسکریپ کریں — باڈی کی توثیق `v1WebFetchSchema` سے ہوتی ہے |

**تصدیق:** Bearer API کلید (`extractApiKey` + `isValidApiKey`)۔ پالیسی کا نفاذ `enforceApiKeyPolicy` کے ذریعے کیا جاتا ہے۔

**کوٹے سے آگاہ فال بیک (#8297):** جب کوئی واضح `provider` نہ دیا گیا ہو، تو پول
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) کو
مقررہ ترجیحی ترتیب (پہلے بھرنے) میں
آزمایا جاتا ہے — ریٹ کی حد تک پہنچا ہوا مگر کنفیگر شدہ فراہم کنندہ، درخواست کو وہیں ختم کرنے کے بجائے
نظر انداز کر دیا جاتا ہے، اور دوبارہ قابلِ کوشش/کوٹے سے متعلق upstream ناکامی
(HTTP 429 ہمیشہ؛ Firecrawl/Tavily/TinyFish کے کوٹے طرز کے مفت درجات کے لیے 402/403 —
Jina Reader کے لیے نہیں، اور سادہ 400 ناقص درخواست کے لیے کبھی نہیں) درخواست کے وقت
اگلے ایسے فراہم کنندہ کی طرف منتقل ہو جاتی ہے جسے ابھی آزمایا نہ گیا ہو اور جس کی اسناد موجود ہوں۔ جب پول کے تمام
فراہم کنندگان ختم ہو جائیں، تو endpoint سابقہ عمومی `400` کے بجائے ایک واحد `429`
(`Retry-After` ہیڈر کے ساتھ) واپس کرتا ہے۔ جب کسی واضح `provider` کی
درخواست کی جائے، تو کوئی خاموش فال بیک **نہیں** ہوتا — ریٹ کی حد تک پہنچا ہوا یا ناکام واضح
فراہم کنندہ اپنی ہی خرابی ظاہر کرتا ہے (اگر ریٹ محدود ہو تو `429`، بصورتِ دیگر upstream
اسٹیٹس)۔

## WebSocket اسٹریمنگ

```bash
GET /v1/ws?handshake=1
```

WebSocket اپ گریڈ ہینڈ شیک کی توثیق کرتا ہے اور وائر پروٹوکول کے مثالی پیغامات (`request`، `cancel`) واپس کرتا ہے۔ حقیقی WS فریمز کو Next.js روٹ ٹیبل سے باہر بنڈل شدہ WS سرور سنبھالتا ہے۔

**تصدیق:** ہینڈ شیک کے دوران Bearer API کلید۔

### WebSocket پر Responses API (صرف codex)

```bash
# HTTP API والا ہی host:port (ڈیفالٹ 20128)؛ کنکشن اپ گریڈ کریں:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (یا: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# پہلا فریم لازماً response.create ہونا چاہیے:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket پراکسی **خصوصی طور پر `codex`** (ChatGPT
backend) سے منسلک ہے۔ یہ API/dashboard والی اسی پورٹ پر راستوں `/v1/responses`،
`/responses`، اور `/api/v1/responses` پر سنتی ہے۔ پہلے `response.create` فریم پر یہ
اندرونی `codex-responses-ws` برج کے ذریعے تصدیق + تیاری کرتی ہے، ایک
codex OAuth کنکشن منتخب کرتی ہے، اور `wreq-js` ٹرانسپورٹ کے ذریعے `wss://chatgpt.com/backend-api/codex/responses`
تک ٹنل بناتی ہے۔ **غیر codex ماڈلز مسترد کر دیے جاتے ہیں** (`codex_ws_provider_required`)۔
کوٹا شیئر روٹنگ کے لیے `model: "qtSd/<group>/codex/<model>"` استعمال کریں۔ نفاذ
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` میں کیا گیا ہے۔

**تصدیق:** ہینڈ شیک کے دوران Bearer API کلید۔ بنڈل شدہ HTTP سرور (`server-ws.mjs`)
فعال entrypoint ہونا چاہیے (جب `app/server-ws.mjs` موجود ہو تو ڈیفالٹ طور پر یہی ہوتا ہے)۔

#### ماڈل id: سادہ ChatGPT id استعمال کریں (`codex/` سابقے کے بغیر)

OpenAI **Codex CLI** اس وقت ماڈل کے نام کی کلائنٹ سائیڈ پر توثیق کرتا ہے جب
`supports_websockets = true` ہو، اور `codex/gpt-5.5` جیسے
**فراہم کنندہ کے سابقے والے ids مسترد کر دیتا ہے** (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`)۔ **سادہ** id بھیجیں (مثلاً `gpt-5.5`)۔ OmniRoute کا برج
صرف codex کے لیے ہے، اس لیے upstream تک ٹنل بنانے سے پہلے یہ سادہ id کو codex ماڈل
(`resolveCodexWsModelInfo`) کے طور پر دوبارہ resolve کرتا ہے — حالاں کہ سادہ
`gpt-5.5` بصورتِ دیگر HTTP پر کسی دوسرے فراہم کنندہ کو روٹ ہو جاتا۔

#### OpenAI Codex CLI کو کنفیگر کرنا

`~/.codex/config.toml` میں WebSocket سپورٹ والا کسٹم فراہم کنندہ شامل کر کے Codex CLI
کو OmniRoute کی طرف پوائنٹ کریں (موجودہ کنفیگ کو چھیڑنے سے بچنے کے لیے علیحدہ `CODEX_HOME`
استعمال کریں):

```toml
model = "gpt-5.5"                 # سادہ id — "codex/gpt-5.5" نہیں
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # آخر میں slash نہیں؛ WS URL اخذ کیا جاتا ہے (پروڈکشن میں https/wss استعمال کریں)
wire_api = "responses"                    # فروری 2026 سے واحد معاونت یافتہ قدر
supports_websockets = true                # Responses-over-WS ٹرانسپورٹ فعال کرتا ہے
env_key = "OMNIROUTE_API_KEY"             # OmniRoute API کلید رکھتا ہے (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # ایک OmniRoute API کلید (اگر REQUIRE_API_KEY=false ہو تو کوئی بھی کلید)
codex exec "Responda apenas: PONG"
```

CLI، `base_url + /responses` کو WebSocket میں اپ گریڈ کرتا ہے اور OmniRoute اسے
منتخب کردہ codex OAuth کنکشن تک ٹنل کرتا ہے۔ مقامی
سرور کے خلاف ابتدا سے انتہا تک توثیق شدہ: ChatGPT، `codex.rate_limits` + `response.created` واپس کرتا ہے اور
تکمیل کو اسٹریم کرتا ہے۔

```bash
# ساخت یافتہ صورت — جسے UI استعمال کرتا ہے
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

کلید کے لیے **`allowUsageCommand`** فعال ہونا ضروری ہے (بطور ڈیفالٹ غیر فعال — ڈیش بورڈ کا API کلید
مینیجر اسے ہر کلید کے لیے الگ سے تبدیل کرتا ہے)۔ اس کے بغیر اینڈپوائنٹ `403` جواب دیتا ہے۔

`?format=json` ایک امتیازی ساخت واپس کرتا ہے تاکہ کالر کسی انکار کی صورت میں کبھی ڈیٹا فیلڈ نہ پڑھے۔
کامیابی کی صورت میں:

```jsonc
{
  "allowed": true,
  // صرف اس وقت موجود ہوتا ہے جب کلید نے فی کلید استعمال کی حدود (یومیہ/ہفتہ وار USD) اختیار کی ہوں:
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // منتخب فراہم کنندہ کے کوٹا کا اسنیپ شاٹ، یا اگر ابھی تک کچھ کیش نہ ہوا ہو تو null:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // ہر کنکشن کا اسنیپ شاٹ، تاکہ UI کئی فراہم کنندگان کو ساتھ ساتھ دکھا سکے:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

انکار کی صورت میں (`401` خراب کلید / `403` اجازت نہیں) یہی روٹ
`{ "allowed": false, "error": { "message": "…" } }` واپس کرتا ہے — موجود مگر خالی `personal`/`provider`
(کلید کو اجازت ہے، مگر ابھی تک کچھ معلوم نہیں ہوا) انکار سے ایک مختلف حالت ہے، اور صرف JSON صورت
ان میں امتیاز کرتی ہے۔

**توثیق:** کالر کی اپنی Bearer API کلید، جس کی `isValidApiKey` کے ذریعے توثیق کی جاتی ہے — یہ مینجمنٹ
سطح (`/api/keys/…`) _نہیں_ ہے، جو بدستور `requireManagementAuth` کے پیچھے رہتی ہے۔

### خام بمقابلہ کٹ آف کے مطابق ایڈجسٹ شدہ کوٹا فیصد

`/api/usage/om-usage` استعمال کرتے وقت، کالرز کو **سادہ متنی آؤٹ پٹ** اور ساخت یافتہ **JSON آؤٹ پٹ**
میں پیش کیے گئے فیصد کے درمیان فرق کو ملحوظ رکھنا چاہیے:

| پہلو              | سادہ متنی فارمیٹ (`/api/usage/om-usage` / `@@om-usage`)                                    | JSON فارمیٹ (`?format=json`)                                                   |
| :---------------- | :----------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------- |
| **آؤٹ پٹ فیلڈ**   | `NN% left` (مثلاً، `20% left`)                                                             | `provider.quotas` / `providers[].quotas`                                       |
| **پیمائش**        | **کٹ آف کے مطابق ایڈجسٹ شدہ قابل استعمال گنجائش**: کٹ آف حد سے اوپر باقی صلاحیت            | **خام اپ اسٹریم کوٹا**: فراہم کنندہ کی غیر ایڈجسٹ شدہ پیمائش                   |
| **کٹ آف اسکیلنگ** | `effectiveRemainingPercent()` کے ذریعے اسکیل کیا جاتا ہے تاکہ محفوظ ذخیرہ `0% left` دکھائے | کوئی نہیں (خام اسنیپ شاٹ اقدار، جیسا کہ فراہم کنندہ نے رپورٹ کیا)              |
| **حد کا ڈیٹا**    | دکھائے گئے فیصد میں شامل کیا جاتا ہے                                                       | ہر کنکشن کے لیے `quotaWindowThresholds` میں محفوظ ہوتا ہے (یا سرور کے ڈیفالٹس) |
| **بنیادی صارف**   | انٹرایکٹو CLIs، ٹرمینل پرامپٹس، انسانی آپریٹرز                                             | پروگرامی انٹیگریشنز، ڈیش بورڈز، تجزیات، بلنگ ٹریکرز                            |

#### کٹ آف ایڈجسٹمنٹ کا فارمولا

OmniRoute اپ اسٹریم کوٹا ختم ہونے سے بچانے کے لیے پیشگی کوٹا کٹ آف کی سہولت دیتا ہے (جسے کنکشن
`quotaWindowThresholds`، فراہم کنندہ کے ڈیفالٹس، یا عالمی لچک کی ترتیبات کے ذریعے کنفیگر کیا جاتا ہے)۔ جب کسی کوٹا ونڈو پر کٹ آف حد
(مثلاً، `cutoff = 25%`) فعال ہو، تو متن رینڈرر باقی گنجائش کا حساب یوں لگاتا ہے:

- اگر `remaining <= cutoff`: تو `0%` واپس کرتا ہے۔
- اگر `remaining > cutoff`: تو `((remaining - cutoff) / (100 - cutoff)) * 100` واپس کرتا ہے۔

فارمیٹ شدہ متنی آؤٹ پٹ اسے قریب ترین صحیح عدد تک راؤنڈ کرتا ہے (`Math.round(...)`)۔

#### وضاحتی مثال

ایک فراہم کنندہ ونڈو پر غور کریں جس میں **60% خام استعمال** ہو (یعنی **40% خام باقی کوٹا**) اور
**باقی کوٹا کی 25% کٹ آف** حد کنفیگر کی گئی ہو:

| نمائندگی                      | حساب                                               |  باقی   |                 مضمر استعمال شدہ                 |
| :---------------------------- | :------------------------------------------------- | :-----: | :----------------------------------------------: |
| **خام JSON (`?format=json`)** | اپ اسٹریم اسنیپ شاٹ (`quotas[window]`)             | **40%** |                     **60%**                      |
| **متنی فارمیٹ (`NN% left`)**  | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (اگر `100 - remaining` کا حساب کیا جائے) |

- **متن 20% باقی کیوں دکھاتا ہے:** اکاؤنٹ پر باقی 40% حقیقی کوٹا میں سے 25% کٹ آف
  پالیسی کے تحت محفوظ ہے۔ روٹر کے اس کنکشن پر روٹنگ روکنے سے پہلے کالر کے پاس 75% قابل استعمال گنجائش میں سے
  صرف 15% باقی ہے۔ اسکیلنگ یقینی بناتی ہے کہ کنکشن عین اس وقت مکمل استعمال (`0% left`) کا اشارہ دے
  جب روٹنگ بند ہو جائے گی۔
- **JSON خام اقدار کیوں محفوظ رکھتا ہے:** JSON پے لوڈ فراہم کنندہ کا عین اسنیپ شاٹ (`UsageSnapshot`)
  واپس کرتا ہے تاکہ بیرونی ٹولز کو اپ اسٹریم کے حقیقی استعمال اور کنکشن کی سطح کے
  `quotaWindowThresholds` تک، سرور سائیڈ کی نقصان دہ اسکیلنگ کے بغیر، رسائی حاصل ہو۔

#### صارفین کی منتقلی کے لیے رہنمائی

اگر کوئی بیرونی انضمام (جیسے ایڈیٹر پلگ اِن یا ایجنٹ ایکسٹینشن) پہلے متنی
اینڈ پوائنٹ (`NN% left`) سے متن حاصل کرتا تھا اور استعمال شدہ فیصد کا حساب `100 - NN` کے طور پر لگاتا تھا، تو `?format=json` پر منتقل ہونے کا مطلب ہے:

- خام JSON اقدار پڑھنے پر **اصل اپ اسٹریم کھپت** ظاہر ہوگی (اوپر دی گئی مثال میں 60% استعمال شدہ)۔
- اگر انضمام متنی اینڈ پوائنٹ کی قابلِ استعمال الاؤنس سے متعلق معنویت برقرار رکھنا چاہتا ہے، تو وہ کنکشن کی سطح کے اوور رائیڈز کے لیے `quotaWindowThresholds` استعمال کرتے ہوئے
  مؤثر باقی ماندہ مقدار کے فارمولے کا کلائنٹ کی جانب سے حساب لگا سکتا ہے۔

### تاخیر پر اثر

معنوی کیش HIT جواب کو **بغیر کسی اپ اسٹریم کال کے** کیش سے فراہم کرتا ہے،
لہٰذا رپورٹ کردہ `X-OmniRoute-Response-Latency` تقریباً صفر ہوتی ہے
(اصل اپ اسٹریم تاخیر سے قطع نظر)۔ تاخیر کے حوالے سے حساس کلائنٹس
(بینچ مارکنگ، p50/p99 مانیٹرنگ) کو `X-OmniRoute-Cache-Latency`
رسپانس ہیڈر چیک کرنا چاہیے:

| قدر           | مطلب                                                         |
| ------------- | ------------------------------------------------------------ |
| `synthetic`   | جواب کیش سے فراہم کیا گیا؛ تاخیر حقیقی اپ اسٹریم وقت نہیں ہے |
| _(غیر موجود)_ | حقیقی اپ اسٹریم کال سے حاصل کردہ جواب                        |

### فی کلید کیش بائی پاس

API کلیدیں `cacheDefaultMode` کے ذریعے معنوی کیش ریڈز سے خارج ہو سکتی ہیں:

| قدر      | طرزِ عمل                                                      |
| -------- | ------------------------------------------------------------- |
| `legacy` | کیش کا معمول کا طرزِ عمل (ڈیفالٹ)                             |
| `bypass` | کیش تلاش کو مکمل طور پر چھوڑ دیں؛ ہمیشہ اپ اسٹریم کو کال کریں |

کلید بناتے وقت (`POST /api/keys`) سیٹ کریں یا (`PATCH /api/keys/[id]`) کے ذریعے اپ ڈیٹ کریں:

```json
{ "cacheDefaultMode": "bypass" }
```

### فی درخواست بائی پاس

کلید کی ترتیبات سے قطع نظر کوئی بھی درخواست کیش کو بائی پاس کر سکتی ہے:

```
X-OmniRoute-No-Cache: true
```

مطابقت پذیر/درآمد شدہ ماڈلز کے لیے، `PUT /api/provider-models` میں `provider`، `modelId`، اور
`maxOutputTokenOverride` قبول کیے جاتے ہیں: ایک مثبت صحیح عدد دستی آؤٹ پٹ ٹوکن کی حد مقرر کرتا ہے، جبکہ `null`
اسے صاف کر کے ڈیفالٹ بحال کرتا ہے۔ `GET /api/provider-models?provider=<provider>` یہ
اقدار `modelOutputOverrides` میں واپس کرتا ہے، جن میں حسبِ ضرورت ماڈل قطار کے بغیر ماڈلز بھی شامل ہیں۔ یہ اوور رائیڈ
رن ٹائم `max_output_tokens` صلاحیت استعمال کرتا ہے اور ماڈل کی دوبارہ مطابقت پذیری کے بعد بھی برقرار رہتا ہے۔ OpenAI سے ہم آہنگ
فراہم کنندہ کا صفحہ اسی طرح کے ترمیم/صاف کرنے کے کنٹرولز پیش کرتا ہے اور واضح وژن سپورٹ والے ماڈلز کو نشان زد کرتا ہے۔

حسبِ ضرورت Chat Completions نوڈز استدلال سے واضح طور پر دست بردار ہونے کی ترتیبات کو اپ اسٹریم بیک اینڈ کے مطابق ڈھالتے ہیں۔ ایک
کامیاب کنکشن ٹیسٹ ہر اس عین ماڈل ID کے لیے خودکار طور پر چیٹ ٹیمپلیٹ کنٹرولز منتخب کرتا ہے
جس کی `/models` اندراج میں کوئی تسلیم شدہ `owned_by` قدر ثابت ہو: `vllm`، `sglang`، یا `llamacpp`۔
شفاف OpenAI سے ہم آہنگ ریپرز اصل ماڈل اندراج کو کسی نیسٹڈ
`openai` آبجیکٹ میں برقرار رکھ سکتے ہیں؛ شناخت زیادہ سے زیادہ تین ایسے لفافوں کی پیروی کرتی ہے۔ غائب، نامعلوم، یا
متضاد ملکیت والے ماڈلز عام OpenAI رویہ برقرار رکھتے ہیں۔ شناخت موجودہ کیٹلاگ درخواست کو دوبارہ استعمال کرتی ہے،
کوئی کمپلیشن ٹوکن پیدا نہیں کرتی، اور کنکشن اینڈ پوائنٹ تبدیل ہونے پر منسوخ ہو جاتی ہے۔

ایسے بیک اینڈ کے لیے اس رویے کو مستقل کرنے کے لیے جو یہ میٹا ڈیٹا ظاہر نہیں کرتا، موجودہ جزوی
فراہم کنندہ اپ ڈیٹ API استعمال کریں:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

یہ باڈی `PUT /api/providers/<connection-id>` کے ساتھ بھیجیں۔ اس کنکشن پر، `none` کی واضح
استدلالی کوشش `chat_template_kwargs.thinking=false` اور
`chat_template_kwargs.enable_thinking=false` کے طور پر بھیجی جاتی ہے۔ واضح مقامی ٹیمپلیٹ اقدار حتمی اختیار رکھتی ہیں،
سوائے اس صورت کے جب سرور سائیڈ استدلالی اصول کوئی کوشش مسلط کرے۔ یہ ترتیب صرف تب لاگو ہوتی ہے جب کوئی حسبِ ضرورت
OpenAI سے ہم آہنگ کنکشن Chat Completions باڈی بھیجتا ہے؛ Responses درخواستیں اور عام
فراہم کنندگان اپنی مقامی درخواست کی ساخت برقرار رکھتے ہیں۔ عام OpenAI
`reasoning_effort` پاس تھرو کو لازمی بنانے کے لیے `reasoningControl` کو `openai` پر سیٹ کریں، یا خودکار شناخت استعمال کرنے کے لیے اسے چھوڑ دیں/`null` پر سیٹ کریں۔

Claude Code آٹو موڈ کلاسیفائر کی درخواستوں میں کوئی واضح استدلالی کنٹرول نہ ہونے پر، مقامی تھنکنگ
بطور ڈیفالٹ غیر فعال ہوتی ہے۔ شناخت Claude فارمیٹ درخواستوں میں کلاسیفائر کے سسٹم مارکر کو استعمال کرتی ہے،
نہ کہ ماڈل کے ناموں یا کمپلیشن کی حدود کو۔ واضح باڈی کنٹرولز، معاونت یافتہ کوشش/تھنکنگ
ہیڈرز، روٹنگ اصول، اور طے شدہ ماڈل کوشش اپنی موجودہ ترجیح برقرار رکھتے ہیں۔ کلاسیفائر کے دونوں
مراحل اپنے پرامپٹس، کمپلیشن کی حدود، اسٹاپ سلسلوں، اور حقیقی اپ اسٹریم اجازت کے
فیصلوں کو برقرار رکھتے ہیں؛ دوسرا مرحلہ اب بھی اپنا مطلوبہ قابلِ مشاہدہ استدلال عام متن کے طور پر پیدا کر سکتا ہے۔

### API کلید کی اجازتیں

`PATCH /api/keys/{id}` کسی موجودہ کلید کی اجازتوں کو اپ ڈیٹ کرتا ہے۔ ہر `/api/keys*` روٹ کی طرح، اسے انتظامی اجازت درکار ہوتی ہے (دیکھیے [انتظامی توثیق](../guides/MANAGEMENT-AUTH.md))، نہ کہ استنباطی کلید۔ صرف وہی فیلڈز بھیجیں جنہیں آپ تبدیل کرنا چاہتے ہیں؛ ان میں سے کسی فیلڈ کے بغیر درخواست کو `No valid fields to update` کے ساتھ مسترد کر دیا جاتا ہے۔ قابل قبول فیلڈز کی وضاحت `src/shared/validation/schemas/keys.ts` میں `updateKeyPermissionsSchema` کے ذریعے کی گئی ہے۔

`/api/db-backups/export`، `/api/db-backups/exportAll` اور `/api/settings/export-json`
تمام محفوظ شدہ اسناد فراہم کرتے ہیں، اس لیے ان کے لیے ڈیش بورڈ سیشن یا مقامی CLI درکار ہے (یا لاگ اِن
غیر فعال ہو)۔ کسی بھی دائرۂ کار کی API کلیدوں اور `oma_` رسائی ٹوکنز کو `403` ملتا ہے۔ بحالی کے عمل پر بھی یہی
حد لاگو ہوتی ہے: `POST /api/db-backups/import` (`dryRun=true` سمیت)، `POST /api/db-backups` (id
کے ذریعے بحالی) اور `POST /api/settings/import-json` فعال ڈیٹابیس یا ترتیبات کو تبدیل کرتے ہیں، اس لیے کسی مشینی
سند کو وہاں بھی `403` ملتا ہے؛ `omniroute sync import` مقامی CLI سند بھیجتا ہے۔ اسی طرح
`DELETE /api/db-backups` (محفوظ شدہ بیک اپس کو کم کرنا) اور `PATCH /api/db-backups` (برقرار رکھنے کی ترتیبات:
محفوظ شدہ اقدار ہر بیک اپ کے بعد خودکار طور پر بیک اپس کم کرنے کے عمل کو چلاتی ہیں) بھی ہیں۔ فہرست سازی (`GET`) اور دستی
بیک اپ بنانا (`PUT`) معمول کی انتظامی توثیق استعمال کرتے ہیں۔

### ورژن اور ریلیز چینل

```bash
GET /api/system/version
```

صرف لوپ بیک کے لیے مینجمنٹ روٹ (ایڈمن توثیق)۔ زیرِ استعمال ورژن، تازہ ترین
شائع شدہ ورژن اور خودکار اپ ڈیٹ کی حالت واپس کرتا ہے۔ `releaseChannel` اور `channels` اضافی
فیلڈز ہیں (ریل 3.8.54)؛ `channel` کا مفہوم برقرار رہتا ہے — وہ تعیناتی موڈ جسے ڈیش بورڈ اپڈیٹر
استعمال کرتا ہے (`npm`، `source` یا `docker-compose`)۔

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — زیرِ استعمال بلڈ کا npm چینل: `-nightly.*` ورژنز کے لیے `nightly`،
  دیگر قبل از ریلیز ورژنز (`-rc.*`، `-beta.*`، `-alpha.*`) کے لیے `next`، اور
  `channels.latest` سے پرانے میجر کے مستحکم ورژن کے لیے `lts`، بصورتِ دیگر `latest`۔ وہی اصول
  جو `scripts/release/dist-tag.mjs` میں ہیں، جو اشاعت کے وقت npm dist-tag منتخب کرتا ہے۔
- `channels` — ہر dist-tag کا تازہ ترین شائع شدہ ورژن، `npm view omniroute dist-tags` سے (رجسٹری
  HTTP فال بیک)، جسے `latest` کی طرح اسی 10 منٹ کی TTL کے ساتھ کیش کیا جاتا ہے۔ `latest` ہمیشہ موجود
  ہوتا ہے (پہلے `latest` فیلڈ، پھر `"unavailable"` کو فال بیک کے طور پر استعمال کرتا ہے)؛ `next`، `nightly` اور `lts`
  صرف تب ظاہر ہوتے ہیں جب متعلقہ dist-tag موجود ہو۔ `Cache-Control: no-cache` درخواست دونوں تلاشوں کو تازہ کرتی ہے۔

چینل ماڈل (`latest` = 4.0 GA تک v3، `next` = rc، `nightly` = `develop` بلڈز،
`lts` = 4.0 GA کے بعد v3 پیچز) کی وضاحت `docs/ops/RELEASE_STRATEGY.md` میں کی گئی ہے۔

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

حصہ مقامی فراہم کنندہ (`openai/…`، `deepgram/…`) منتخب کرتا ہے۔ وہ گیٹ ویز جو
کسی دوسرے وینڈر کا ماڈل دوبارہ برآمد کرتے ہیں، ایک مکمل شناختی نام استعمال کرتے ہیں
(`openrouter/deepgram/nova-3`)۔

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**جواب:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**ماڈل آئی ڈیز کی مثالیں:** `openai/whisper-1` (ایک OpenAI کلید درکار ہے)،

## ٹوکنائزڈ VS Code / ہیڈر کے بغیر عرفی نام

جب کوئی انٹیگریشن `Authorization` ہیڈر شامل نہ کر سکے اور API کلید کو بنیادی URL میں شامل کرنے کی ضرورت ہو تو یہ عرفی نام استعمال کریں۔

```bash
# OpenAI طرز کا کیٹلاگ عرفی نام
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# OpenAI طرز کے چیٹ عرفی نام
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Ollama طرز کے عرفی نام
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

مثال:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

نوٹس:

- ٹوکنائزڈ عرفی نام `/v1/*` اور `/api/tags` والے ہی ہینڈلرز کو دوبارہ استعمال کرتے ہیں؛ جوابات کی ساخت یکساں رہتی ہے۔
- جب بھی کلائنٹ حسبِ ضرورت ہیڈرز کی معاونت کرتا ہو، `Authorization: Bearer ...` کو ترجیح دیں۔
- URL پر مبنی ٹوکنز ریورس پراکسی لاگز، براؤزر ہسٹری، اور OmniRoute سے باہر ٹیلی میٹری میں ظاہر ہو سکتے ہیں۔ انہیں ڈیفالٹ توثیقی طریقے کے بجائے مطابقت کے ایک اختیار کے طور پر استعمال کریں۔

```bash
# تمام API کلیدوں کے بجٹ کی حالت حاصل کریں
```

## ٹوکن کی حدود

فی API کلید **ٹوکن** بجٹس (اوپر دیے گئے USD پر مبنی بجٹ سے الگ)۔ درخواست کے راستے پر ہی ان کا نفاذ کیا جاتا ہے: جب کسی کلید کے موجودہ دورانیے کا استعمال اپنی حد تک پہنچ جاتا ہے تو درخواستیں `429 Too Many Requests` کے ساتھ مسترد کر دی جاتی ہیں۔ حدود کو کسی مخصوص `model`، کسی `provider` تک محدود کیا جا سکتا ہے، یا کلید پر `global` طور پر لاگو کیا جا سکتا ہے؛ جب کسی درخواست پر متعدد حدود منطبق ہوں تو سب سے زیادہ پابندی والی حد نافذ ہوتی ہے۔

```bash
# کسی کلید کی ٹوکن حدود کی فہرست دیکھیں (موجودہ دورانیے کا براہِ راست استعمال بھی شامل ہے)
GET /api/usage/token-limits?apiKeyId=key-123

# ٹوکن کی حد بنائیں یا اپ ڈیٹ کریں
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# id کے ذریعے ٹوکن کی حد حذف کریں
DELETE /api/usage/token-limits?id=tl-abc
```

> **اسکیما کے نوٹس** (`setTokenLimitSchema`): `apiKeyId` اور `scopeType` (`model` | `provider` | `global`) لازمی ہیں۔ `scopeValue` لازمی ہے، سوائے اس صورت کے جب `scopeType` کی قدر `global` ہو (مثلاً `model` اسکوپ کے لیے ماڈل id، یا `provider` اسکوپ کے لیے پرووائیڈر id)۔ `tokenLimit` ایک مثبت صحیح عدد ہونا چاہیے (اسٹرنگ سے تبدیل کیا جاتا ہے)۔ اختیاری: `id` (بنانے کے لیے شامل نہ کریں، اپ ڈیٹ کرنے کے لیے فراہم کریں)، `resetInterval` (`daily` | `weekly` | `monthly`، ڈیفالٹ `monthly`)، `resetTime` (`HH:MM`)، `enabled` (ڈیفالٹ `true`)۔ `GET` کے جوابات ہر حد میں `tokensUsed`، `remaining`، `windowStart`، `periodStartAt`، اور `nextResetAt` شامل کر کے اسے مزید معلومات سے مکمل کرتے ہیں۔ یہ مینجمنٹ درجے کا اینڈ پوائنٹ ہے (توثیق کا نفاذ مرکزی طور پر authz پائپ لائن کے ذریعے ہوتا ہے)۔

## درخواست کی پراسیسنگ

1. کلائنٹ `/v1/*` کو درخواست بھیجتا ہے
2. روٹ ہینڈلر `handleChat`، `handleEmbedding`، `handleAudioTranscription`، یا `handleImageGeneration` کو کال کرتا ہے
3. ماڈل کا تعین کیا جاتا ہے (براہِ راست پرووائیڈر/ماڈل یا عرف/کومبو)
4. اکاؤنٹ کی دستیابی کی فلٹرنگ کے ساتھ مقامی DB سے اسناد منتخب کی جاتی ہیں
5. چیٹ کے لیے: `handleChatCore` معنوی/دستخطی کیش چیک کرتا ہے اور کومبو کمپریشن کی ترتیبات کا تعین کرتا ہے
6. فعال ہونے کی صورت میں پرووائیڈر ترجمے سے پہلے پیشگی کمپریشن چلتی ہے (`lite`، Caveman، RTK، یا تہہ در تہہ)
7. پرووائیڈر ایگزیکیوٹر اپ اسٹریم درخواست بھیجتا ہے
8. جواب کو واپس کلائنٹ فارمیٹ میں ترجمہ کیا جاتا ہے (چیٹ)، یا جوں کا توں واپس کیا جاتا ہے (ایمبیڈنگز/تصاویر/آڈیو)
9. استعمال، کمپریشن اینالیٹکس، اور درخواست کے لاگز ریکارڈ کیے جاتے ہیں
10. کومبو کے قواعد کے مطابق خرابیوں پر فال بیک لاگو ہوتا ہے

مکمل آرکیٹیکچر کا حوالہ: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## رجسٹرڈ کلیدیں (خودکار انتظام)

روزانہ/فی گھنٹہ کوٹاز کے ساتھ، کسی بنیادی فراہم کنندہ/اکاؤنٹ کے ذریعے API کلیدیں جاری کرنے اور تبدیل کرنے کے لیے خودکار کلید مینجمنٹ ذیلی نظام استعمال کرتا ہے۔

| طریقہ  | پاتھ                                  | وضاحت                                                                                                                                                                                                      |
| ------ | ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/registered-keys`             | رجسٹرڈ کلیدوں کی فہرست دکھائیں (صرف مخفی سابقہ)                                                                                                                                                            |
| POST   | `/api/v1/registered-keys`             | نئی رجسٹرڈ کلید جاری کریں — باڈی: `{name, provider?, accountId?, idempotencyKey?, expiresAt?, dailyBudget?, hourlyBudget?}`۔ اصل کلید **صرف ایک بار** واپس کرتا ہے۔ کوٹا مسترد ہونے پر `429` واپس کرتا ہے۔ |
| GET    | `/api/v1/registered-keys/[id]`        | رجسٹرڈ کلید کا میٹا ڈیٹا حاصل کریں (اصل مواد کے بغیر)                                                                                                                                                      |

| POST   | `/api/v1/registered-keys/[id]/revoke` | واضح منسوخی کا اینڈ پوائنٹ (DELETE جیسا ہی اثر)                                                                                                                                                            |

**توثیق:** انتظامی سیشن/API کلید (`requireManagementAuth`) — وہی حفاظتی شرط جو `/api/keys` کے لیے ہے: ڈیش بورڈ سیشن، مقامی CLI ٹوکن، یا `manage`/`admin` اسکوپ والی API کلید؛ صرف انفرنس والی API کلیدوں کو `403` ملتا ہے۔ `/v1/quotas/check` اور `/v1/issues/report` بھی دیکھیں۔

| طریقہ  | راستہ                                        | تفصیل                                                                                                                                                                   |

## لچک پذیری (توسیعی)

OmniRoute عارضی ناکامی سے نمٹنے کے تین آزاد طریقہ کار فراہم کرتا ہے؛ ذیل کے انتظامی endpoints آپریٹرز کو انہیں پڑھنے اور اوور رائیڈ کرنے کی سہولت دیتے ہیں:

| دائرۂ کار         | حالت کا ذخیرہ                            | پڑھنا                                     | ری سیٹ / صاف کرنا                                               |
| ----------------- | ---------------------------------------- | ----------------------------------------- | --------------------------------------------------------------- |
| فراہم کنندہ بریکر | `domain_circuit_breakers` + اِن میموری   | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                    |
| کنکشن کول ڈاؤن    | فراہم کنندہ کنکشنز پر `rateLimitedUntil` | `/api/rate-limits`, `/api/providers/[id]` | (بتدریج دوبارہ فعال ہوتا ہے؛ فراہم کنندہ PUT کے ذریعے صاف کریں) |
| ماڈل لاک آؤٹ      | اِن میموری ماڈل دستیابی رجسٹری           | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                        |

`PATCH /api/resilience`، `providerBreaker.oauth` اور `providerBreaker.apikey` کے تحت فراہم کنندہ بریکر اوور رائیڈز قبول کرتا ہے۔ ہر پروفائل `degradationThreshold`، `failureThreshold`، اور `resetTimeoutMs` کی معاونت کرتا ہے؛ یہی فیلڈز Dashboard → Settings → Resilience میں بھی دستیاب ہیں۔

```bash
# کسی ایک ماڈل لاک آؤٹ کو صاف کریں
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# تمام لاک آؤٹس مٹا دیں
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

مکمل تصوراتی حوالہ اور بریکر کی طے شدہ اقدار کے لیے دیکھیں: [`CLAUDE.md`](../../CLAUDE.md) → "لچک پذیری کی رَن ٹائم حالت" اور [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md)۔

### ریٹ لمٹ قطار اور خودکار فعالیت کا حفاظتی نظام

- **معاونت یافتہ تحریری راستہ**: `POST /api/rate-limits`، جس کی body `{"connectionId": "<id>", "enabled": true|false}` ہو، کسی کنکشن کے لیے ریٹ لمٹ تحفظ کو فعال یا غیر فعال کرنے کا معاونت یافتہ انتظامی endpoint ہے۔ `PUT /api/providers/[id]` دانستہ طور پر `rateLimitProtection` میں ترمیم یا اس کی حالت تبدیل نہیں کرتا (#11278)۔
- **`enabled: false` کے معنی**: `enabled: false` مقرر کرنے سے کنکشن کا واضح تحفظ ہٹ جاتا ہے، لیکن یہ کسی فعال API کلید کنکشن کو عمومی خودکار فعالیت کے حفاظتی نظام (`autoEnableApiKeyProviders = true`) سے **خارج نہیں** کرتا۔ `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) میں، `false` اور `undefined` مساوی ہیں؛ واضح تحفظ کے بغیر فعال API کلید کنکشنز خودکار فعالیت کے حفاظتی نظام کے تحت محفوظ رہتے ہیں۔
- **عمومی طور پر غیر فعال کرنا**: API کلید کنکشنز کو ریٹ لمٹ قطاروں کے بغیر چلانے کے لیے، `RATE_LIMIT_AUTO_ENABLE=false` (env) یا `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`) کے ذریعے حفاظتی نظام کو عمومی طور پر غیر فعال کریں۔

## MCP سرور

OmniRoute میں 3 ٹرانسپورٹس (stdio، SSE، streamable-http) اور محدود دائرۂ کار والے ٹولز کے ساتھ ایک شامل شدہ Model Context Protocol سرور موجود ہے۔ ذیل کے dashboard endpoints حالت/آڈٹ ڈیٹا پڑھتے ہیں اور HTTP ٹرانسپورٹس کو پراکسی کرتے ہیں۔

| طریقہ | راستہ | وضاحت |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | ہارٹ بیٹ، ٹرانسپورٹ، آن لائن حالت، آخری کال، سرفہرست ٹولز، 24 گھنٹے کی کامیابی کی شرح |
| GET | `/api/mcp/tools` | `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` کے ساتھ MCP ٹولز کی فہرست |
| GET | `/api/mcp/sse` | SSE ٹرانسپورٹ کے لیے SSE اسٹریم کھولیں (اگر MCP غیر فعال ہو یا ٹرانسپورٹ مطابقت نہ رکھتا ہو تو `503` واپس کرتا ہے) |
| POST | `/api/mcp/sse` | SSE ٹرانسپورٹ پر JSON-RPC فریم بھیجیں |
| GET | `/api/mcp/stream` | Streamable HTTP ٹرانسپورٹ کا SSE رخ کھولیں (سرور کی جانب سے شروع کیے گئے پیغامات) |
| POST | `/api/mcp/stream` | Streamable HTTP ٹرانسپورٹ پر JSON-RPC فریم بھیجیں |
| DELETE | `/api/mcp/stream` | Streamable HTTP session ختم کریں |
| GET | `/api/mcp/audit` | آڈٹ لاگ استفسار کریں — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | مجموعی آڈٹ اعداد و شمار (کل تعداد، کامیابی کی شرح، اوسط دورانیہ، سرفہرست ٹولز) |

**توثیق:** `sse`/`stream` ٹرانسپورٹس MCP کے لیے مخصوص توثیقی سطح کی پابندی کرتے ہیں (`mcp` scope والی Bearer API key)؛ `status`/`tools`/`audit*` روٹس dashboard سے قابلِ مطالعہ ہیں (dashboard host تک رسائی کے علاوہ کسی اضافی توثیق کی ضرورت نہیں)۔

> دونوں HTTP ٹرانسپورٹس `settings.mcpEnabled` اور `settings.mcpTransport` کے ذریعے محدود ہیں — ٹرانسپورٹ کی عدم مطابقت `400` واپس کرتی ہے، جبکہ MCP کی غیر فعال حالت `503` واپس کرتی ہے۔

## A2A سرور

OmniRoute معائنے اور ڈیش بورڈ کے استعمال کے لیے ایک A2A (ایجنٹ سے ایجنٹ) JSON-RPC 2.0 اینڈ پوائنٹ کے ساتھ ایک REST ریپر فراہم کرتا ہے۔

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # اختیاری، جب تک OMNIROUTE_API_KEY سیٹ نہ ہو
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

معاونت یافتہ طریقے (سبھی `settings.a2aEnabled` کے ذریعے فعال ہوتے ہیں):

| طریقہ            | تفصیل                                                         |
| ---------------- | ------------------------------------------------------------- |
| `message/send`   | ہم وقت مہارت کا نفاذ؛ `{task, artifacts, metadata}` لوٹاتا ہے |
| `message/stream` | اسی مہارت کے مجموعے کا اسٹریمنگ SSE نفاذ                      |
| `tasks/get`      | `taskId` کے ذریعے ٹاسک حاصل کریں                              |
| `tasks/cancel`   | `taskId` کے ذریعے ٹاسک منسوخ کریں                             |

بلٹ اِن مہارتیں: `smart-routing`، `quota-management`، `provider-discovery`، `cost-analysis`، `health-report`۔

### ایجنٹ کارڈ

```bash
GET /.well-known/agent.json
```

عوامی A2A ایجنٹ کارڈ (نام، تفصیل، صلاحیتیں، مہارتوں کا کیٹلاگ، تصدیقی اسکیم) لوٹاتا ہے — عوامی طور پر 1h کے لیے کیش کیا جاتا ہے۔ تصدیق درکار نہیں۔

### REST معاونین

| طریقہ | راستہ                        | تفصیل                                                                                                               |
| ----- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/a2a/status`            | A2A کی فعالی + ٹاسک کے اعداد و شمار + کیش کردہ ایجنٹ کارڈ کا خلاصہ                                                  |
| GET   | `/api/a2a/tasks`             | ٹاسکس کی فہرست — `?state=submitted\|working\|completed\|failed\|cancelled`، `?skill=`، `?limit=` (≤200)، `?offset=` |
| POST  | `/api/a2a/tasks`             | (REST معاون کے طور پر نافذ نہیں — JSON-RPC `message/send` کے ذریعے بنائیں)                                          |
| GET   | `/api/a2a/tasks/[id]`        | ایک ٹاسک بازیافت کریں                                                                                               |
| POST  | `/api/a2a/tasks/[id]/cancel` | ایک ٹاسک منسوخ کریں                                                                                                 |

**تصدیق:** REST معاونین مینجمنٹ کی تصدیق کے بغیر چلتے ہیں (ڈیش بورڈ کے ذریعے قابلِ مطالعہ)؛ JSON-RPC کا `/a2a` روٹ، اگر کنفیگر کیا گیا ہو، تو Bearer `OMNIROUTE_API_KEY` استعمال کرتا ہے۔

| PUT    | `/api/skills/[id]`       | اسکل کو فعال یا غیر فعال کریں — باڈی: `{enabled?: boolean, mode?: "on" \| "off" \| "auto"}` |

**توثیق:** مینجمنٹ سیشن یا مینجمنٹ اسکوپ والی API کلید درکار ہے۔

## حفاظتی حدود

رن ٹائم حفاظتی حدود (PII کی شناخت، پرامپٹ انجیکشن کی شناخت، وژن برجنگ) کا معائنہ کریں۔ حفاظتی حدود ہر درخواست پر چلتی ہیں؛ ہر کال کے لیے آپٹ آؤٹ `x-omniroute-disabled-guardrails` ریکویسٹ ہیڈر کے ذریعے کیا جاتا ہے — فعال/غیر فعال حالت مستقل طور پر محفوظ کرنے کی کوئی سہولت نہیں ہے۔

| طریقہ | پاتھ                   | تفصیل                                                                                     |
| ----- | ---------------------- | ----------------------------------------------------------------------------------------- |
| GET   | `/api/guardrails`      | رجسٹرڈ حفاظتی حدود اور ان کی حالت (نام / فعال / ترجیح) کی فہرست دیکھیں                    |
| POST  | `/api/guardrails/test` | نمونہ ان پٹ پر پری کال پائپ لائن کا ڈرائی رَن کریں — باڈی: `{input, disabledGuardrails?}` |

**توثیق:** مینجمنٹ سیشن درکار ہے۔

مکمل تفصیلات کے لیے [سیکیورٹی > حفاظتی حدود](../security/GUARDRAILS.md) دیکھیں۔

## توثیق

چار اسنادی اقسام (ڈیش بورڈ سیشن، مقامی CLI ٹوکن، `oma_live_…` رسائی
ٹوکن، انتظامی دائرۂ کار والی API کلید) اور ان کے انفرنس کلیدوں سے فرق کے لیے
[انتظامی توثیق](../guides/MANAGEMENT-AUTH.md) دیکھیں۔

- ڈیش بورڈ روٹس (`/dashboard/*`) `auth_token` کوکی استعمال کرتے ہیں
- لاگ اِن محفوظ شدہ پاس ورڈ ہیش استعمال کرتا ہے؛ بصورت دیگر `INITIAL_PASSWORD` استعمال ہوتا ہے
- `requireLogin` کو `/api/settings/require-login` کے ذریعے فعال یا غیر فعال کیا جا سکتا ہے
- جب `REQUIRE_API_KEY=true` ہو تو `/v1/*` روٹس کے لیے اختیاری طور پر Bearer API کلید درکار ہوتی ہے
- اس حوالے میں "انتظامی ٹوکن" / "انتظامی دائرۂ کار والی API کلید" سے مراد اس رہنما میں بیان کردہ اقسام میں سے ایک ہے—کوئی غیر متعین اضافی خفیہ قسم نہیں

> **اہم تبدیلی (v3.8.0)** — `/api/v1/agents/tasks/*` اور کول ڈاؤن کے انتظامی اینڈ پوائنٹس کے لیے اب **انتظامی توثیق** (ڈیش بورڈ `auth_token` کوکی یا انتظامی دائرۂ کار والی API کلید) درکار ہے۔ جو کلائنٹس پہلے توثیق کے بغیر ان روٹس کو کال کرتے تھے، انہیں `401 Unauthorized` موصول ہوگا۔ کمٹ `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`) دیکھیں۔
