## 聊天補全

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### 自訂標頭

| 標頭                     | 方向 | 說明                                                                                                                                                     |
| ------------------------ | ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | 請求 | 設為 `true` 以略過快取                                                                                                                                   |
| `x-omniroute-no-memory`  | 請求 | 設為 `true`，可略過此請求的記憶體與技能注入（行為與不使用快取相同；避免每次呼叫產生權杖／成本開銷）                                                      |
| `X-OmniRoute-Progress`   | 請求 | 設為 `true` 以接收進度事件                                                                                                                               |
| `X-Session-Id`           | 請求 | 用於外部工作階段親和性的黏著工作階段金鑰                                                                                                                 |
| `x_session_id`           | 請求 | 也接受底線變體（直接 HTTP）                                                                                                                              |
| `X-OmniRoute-Session-Id` | 請求 | 呼叫者提供的工作階段／對話標籤（也會提供給記憶體）。若存在，會逐字保存至 `call_logs.session_tag`，以便按工作階段歸屬成本 (#8249)；若不存在，絕不自動產生 |
| `Idempotency-Key`        | 請求 | 去重金鑰（5 秒時間窗）                                                                                                                                   |
| `X-Request-Id`           | 請求 | 替代的去重金鑰                                                                                                                                           |
| `x-omniroute-connection` | 請求 | 依提供者連線（帳戶）的 ID，將單一模型請求固定至該連線；請參閱[依請求固定帳戶](#account-pinning-per-request)                                              |
| `X-OmniRoute-Cache`      | 回應 | `HIT` 或 `MISS`（非串流）                                                                                                                                |
| `X-OmniRoute-Idempotent` | 回應 | 若已去重，則為 `true`                                                                                                                                    |
| `X-OmniRoute-Progress`   | 回應 | 若已啟用進度追蹤，則為 `enabled`                                                                                                                         |
| `X-OmniRoute-Session-Id` | 回應 | OmniRoute 使用的有效工作階段 ID                                                                                                                          |
| `X-OmniRoute-Request-Id` | 回應 | 請求關聯 ID（若已知）                                                                                                                                    |
| `X-OmniRoute-Version`    | 回應 | OmniRoute 組建版本（永遠存在）                                                                                                                           |
| `X-OmniRoute-Cost-Saved` | 回應 | 快取命中時所節省的美元金額（僅限快取命中）                                                                                                               |
| `X-OmniRoute-Decision`   | 回應 | 路由追蹤：`strategy=<name>; provider=<alias>; latency_ms=<n>`（`<name>` 是組合策略；若為非組合請求，則為 `single`）— 完成回應中永遠存在                  |

> Nginx 注意事項：如果您依賴含底線的標頭（例如 `x_session_id`），請啟用 `underscores_in_headers on;`。

#### 針對每個請求鎖定帳戶

當提供者有多個連線（帳戶或金鑰）時，OmniRoute 通常會透過其帳戶選擇策略挑選其中一個。請求也可以改用 `x-omniroute-connection` 標頭來鎖定特定連線：

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **在哪裡尋找 ID。** 在儀表板中開啟提供者頁面
  （**儀表板 → 提供者 → <provider>**），然後點選連線資料列上的 `xxxxxxxx…` ID 標籤，
  即可複製完整的連線 ID。
- **哪些請求會遵循此設定。** `/v1/chat/completions`、`/v1/messages` 和
  `/v1/responses` 上的單一模型請求（`provider/model`）。組合會忽略此標頭：請改為透過
  各組合步驟本身的連線，為每個步驟鎖定帳戶。
- **鎖定是嚴格限制，而非偏好設定。** 系統只會使用已鎖定的連線。請求內部發生失敗時，
  會記錄該帳戶的冷卻狀態，但**不會**輪替至同一提供者的其他帳戶。
- **冷卻與配額會解除鎖定。** 當已鎖定的連線處於冷卻中、配額已用盡，或受到配額政策封鎖時，
  後續請求會改用該提供者的其他連線，行為與未鎖定的流量完全相同。
- **未知或已停用的 ID 會導致失敗。** 如果某個 ID 不在提供者的有效集區中（已刪除、
  已停用，或屬於其他提供者），就不會有符合條件的帳戶，因此請求會失敗，而不會悄悄路由至其他位置。

Claude Code 會透過 `ANTHROPIC_CUSTOM_HEADERS` 傳送自訂標頭。請將其放入
`~/.claude/settings.json` 的 `env` 區塊中，或放入專案層級的 `.claude/settings.json`，
以便為每個專案鎖定不同的帳戶：

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

來源：`src/sse/handlers/chat.ts`（讀取標頭）、`src/sse/services/auth.ts` 和
`src/sse/services/sessionAffinityPin.ts`（解除鎖定及檢查是否不在集區中）。

> **成本遙測標頭：**非串流的成功回應也會包含 `X-OmniRoute-*` 成本遙測標頭集——`X-OmniRoute-Response-Cost`（USD，固定 10 位小數；免費或未定價時為 `0.0000000000`）、`X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`、`X-OmniRoute-Model`、`X-OmniRoute-Provider`、`X-OmniRoute-Latency-Ms`、`X-OmniRoute-Cache-Hit`，以及 `X-OmniRoute-Fallback-Attempts`（僅在 > 0 時提供），另加上 `X-OmniRoute-Request-Id` 和 `X-OmniRoute-Version`。這些標頭會由聊天補全、`/v1/responses`、`/v1/messages`，**以及媒體端點**送出——`/v1/embeddings`、`/v1/images/generations`、`/v1/audio/speech`、`/v1/audio/transcriptions`、`/v1/rerank`、`/v1/videos/generations`、`/v1/music/generations` 和 `/v1/moderations`（成本一律為 `0`）。若有可用的定價資訊，媒體成本會依各模態計算（每張圖片、每秒、每個字元、每個搜尋單位）；否則為 `0`（失敗時開放通行）。

> **快取命中的成本語意：**語意快取命中時（`X-OmniRoute-Cache-Hit: true`），不會進行上游呼叫，因此 `X-OmniRoute-Response-Cost` 為 `0.0000000000`（提供該次命中結果的**增量**成本）。原始成本／若未命中原本會產生的成本會另外記錄於 `X-OmniRoute-Cost-Saved`。計費系統應加總 `X-OmniRoute-Response-Cost`（命中不會產生成本）；快取分析則可彙總 `X-OmniRoute-Cost-Saved`。

## 獨佔受管工作階段租約

獨佔受管工作階段租賃是一種選擇加入、用戶端中立的路由契約：一個作用中的擁有者持有一個符合資格的 OmniRoute 連線。它不會租用模型、不要求 OAuth、不識別特定用戶端，也不要求特定提供者。

用於驗證的 API 金鑰必須具有 `lease:exclusive` 範圍，以及明確且非空的 `allowedConnections` 清單。資料庫異動邊界會在建立金鑰和部分更新時一併強制執行這兩個欄位的要求。

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

成功的取得、續租和釋放回應會公開時間戳記、`state` 和確切的正整數 `generation`，但絕不會公開選取的連線或憑證。續租和釋放會在 JSON 主體中提供世代編號：

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

作用中的租約擁有者可以明確要求其目前繫結的隱私安全顯示中繼資料：

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

此選擇加入的狀態動作會在單一資料庫交易中，由不透明的擁有者、經驗證的受管 API 金鑰，以及確切的作用中世代編號進行隔離保護。`displayName` 僅為經過修剪的已設定連線名稱；若不存在安全的已設定名稱，則為 `null`。OmniRoute 絕不會以電子郵件或產生的帳戶身分取代它。提供者值是非敏感的顯示標籤，絕不會是產生的相容提供者識別碼。憑證、權杖、Cookie、原始連線或 API 金鑰 ID、擁有者雜湊、隔離密鑰和內部路由資料均不會包含在內。

錯誤金鑰、錯誤擁有者、過時世代、缺少、已到期、已釋放及已失效的查詢，都會傳回相同的 `409 LEASE_FENCE_STALE` 錯誤，且不含連線中繼資料。收到容量等待回應的用戶端沒有可供檢查的作用中繫結。當路由使作用中的租約發生轉換時，同一世代仍然有效，且狀態會以不可分割的方式傳回新的繫結，而絕不會傳回舊繫結。現有用戶端維持不變，因為取得、續租、釋放和等待回應會保留其先前的格式。

此伺服器契約不會變更原版 OpenAI Codex 的 `/status`。原版 Codex 目前會報告其模型提供者及內建的驗證／帳戶狀態，但不會呈現任意自訂的提供者帳戶中繼資料；後續的用戶端整合必須呼叫此動作，並決定如何顯示 `connection.displayName`。

之後，每個受管推論要求都會提供兩個控制標頭：

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

在每次受支援的上游嘗試之前，系統會立即隔離並驗證確切的擁有者、世代、作用中連線和已驗證的 API 金鑰。即使另一個金鑰允許相同連線，使用該金鑰重播擁有者和世代仍會失敗。原始擁有者資訊不會被持久化、記錄、保留在要求快照中，或轉送至上游。

暫時性競用會傳回 HTTP `429`、`Retry-After`，以及：

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

此回應只表示一般的符合資格集合並非空集合，而且每個可用的候選連線都由其他擁有者的作用中租約所持有。不受支援的模型／提供者、原則不符、冷卻期、配額、健康狀態及其他一般資格判定失敗，仍會保留其現有的 OmniRoute 回應。

### `x-omniroute-compression`

針對每個要求覆寫壓縮方案。其優先順序最高——高於路由組合覆寫、作用中設定檔、自動觸發及面板的預設值。值如下：

| 值            | 效果                                                              |
| ------------- | ----------------------------------------------------------------- |
| `off`         | 不壓縮此要求。                                                    |
| `default`     | 面板衍生的預設設定檔（忽略作用中設定檔）。有損引擎會維持關閉。    |
| `safe`        | 僅進行重複內容刪除和空白折疊。                                    |
| `allow-lossy` | 為此要求保留操作員方案，包括摘要和樣式改寫。                      |
| `engine:<id>` | 啟用時使用單一引擎，例如 `engine:rtk`。針對該引擎按要求選擇加入。 |
| `<combo>`     | 具名組合，先按名稱比對（不區分大小寫），再按 ID 比對。            |

注意事項：

- 未知值會被忽略（絕不會拒絕要求）；解析程序會繼續依照一般操作員優先順序進行。
- 如果多個組合共用同一名稱，請傳入組合的 **ID**，以獲得確定性的比對結果。
- 名稱為 `off` 或 `default` 的組合無法按名稱選取（會先解譯這些關鍵字）；請使用其 ID 參照此類組合。
- 主壓縮開關是一道硬性閘門：全域停用壓縮時，此標頭無法啟用壓縮。

套用的方案會在回應標頭中回傳：

```
X-OmniRoute-Compression: <mode>; source=<source>
```

其中 `<source>` 為 `request-header`、`routing-override`、`active-profile`、`auto-trigger`、`default` 或 `off` 之一。

## 嵌入

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

可用的提供者：Nebius、OpenAI、Mistral、Together AI、Fireworks、NVIDIA、**OpenRouter**、Jina AI。

目錄 ID 的格式為 `provider/model`（例如：`jina-ai/jina-embeddings-v5-omni-small`）。登錄檔中出現的簡短 Jina 模型 ID（例如 `jina-embeddings-v5-text-small`、`jina-reranker-v3.5`）也能解析。Jina 的嵌入／重新排序／分類／分段功能會優先使用儀表板中的 `jina-ai` 憑證；只有在不存在儀表板金鑰時，才會使用 `JINA_AI_API_KEY` 作為備用。`jina-reader` 卡片僅供 Reader／`r.jina.ai` 使用（`POST /v1/web/fetch`），絕不提供嵌入或重新排序服務。

登錄檔中宣告支援多模態的模型，也接受最多 32 個提供者中立的結構化項目。媒體項目類型為 `text`、`image`、`audio`、`video` 和 `document`。其媒體 `source` 可為 `{"type":"url","url":"https://..."}`，或
`{"type":"base64","data":"...","media_type":"..."}`。

Jina v5 Omni（`jina-ai/jina-embeddings-v5-omni-small`、`jina-ai/jina-embeddings-v5-omni-nano`，
以及系列別名 `jina-ai/jina-embeddings-v5-omni` → omni-small）也接受 Jina 原生的
EmbeddingsV5Request 文件，並將其**原封不動地轉送**至 `https://api.jina.ai/v1/embeddings`：

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

原生的 `{ image | audio | video | pdf }` 值可以是公開的 HTTPS URL、`data:` URI 或原始
base64。OmniRoute 不會將這些物件字串化，也不會擷取原生圖片 URL——Jina 會自行擷取
公開媒體。額外的 Jina 欄位（`task`、`normalized`、`truncate`、`embedding_type`）會被
轉送。僅支援文字的 Jina SKU 仍會拒絕非文字文件。

安全性與傳輸限制：

- 遠端媒體 URL 必須是公開的 HTTPS。標準 `{type,source:url}` 項目會由伺服器端擷取
  （重新驗證重新導向、逾時、大小限制、公開 DNS、連線固定），並在呼叫提供者前
  內嵌。Jina 原生的 `{image:"https://..."}` 項目會在經過相同的公開 HTTPS 檢查後
  原樣轉送；由 Jina 擷取該 URL。
- 內嵌 base64 媒體的限制為每個項目解碼後 8 MiB，整個請求解碼後合計 16 MiB。

提供者轉換方式（標準項目絕不會原樣轉送）：

- Jina 多模態模型：每個頂層項目會轉換為一個以模態為鍵的物件
  （`text`／`image`／`audio`／`video`／`pdf`），內嵌媒體使用 data URI；每個
  頂層項目產生一個向量。
- Gemini Embedding 2 系列：一個頂層陣列會轉換為單一原生
  `models/{model}:embedContent` 請求，其中包含 `content.parts`（`text` 或 `inline_data`）。
- llama.cpp（`llama-cpp/<model>`，本機伺服器載入的任何模型）：標準 `text` 項目
  會轉換為純字串，而 `image`／`audio`／`video` 各自會轉換為一個
  `{"content": [part]}` 物件，使用 llama-server 的聊天內容部分（`image_url`、
  格式為 `wav`／`mp3`／`flac` 的 `input_audio`、`input_video`），並內嵌資料；每個
  頂層項目產生一個向量。伺服器必須使用 `--embedding --mmproj …` 執行；若沒有投影器，
  伺服器本身會拒絕媒體。不支援 `document`。
- 沒有明確模態中繼資料的未知／動態模型，會以 HTTP 400 拒絕結構化輸入。

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

不支援的模型／模態組合會傳回 HTTP 400，而不是強制轉換該項目。對於舊版字串／權杖請求，
非輸入的擴充欄位仍會原樣傳遞。

```bash
# 列出所有嵌入模型
GET /v1/embeddings
```

## 圖像生成

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

可用的提供者包括 OpenAI（GPT Image 2）、xAI（Grok Image）、Together AI（FLUX）、Fireworks AI、Nebius（FLUX）、Hyperbolic、NanoBanana、**OpenRouter**、**ZenMux**、SD WebUI（本機）、ComfyUI（本機）。

`n` 會在 `data[]` 中傳回 `n` 張圖像。對於上游 API 每次呼叫僅傳回一張圖像的提供者
（Black Forest Labs、Stability AI、Leonardo、Ideogram、Haiper、Hyperbolic、Magnific/Freepik、
NVIDIA NIM、Cloudflare Workers AI），系統會進行 `n` 次獨立的上游呼叫，同時最多執行 4 次。
固定的 `seed` 會依呼叫索引遞增（`seed`、`seed + 1`、…），因此圖像彼此不同，但仍可
重現。`n` 上限為 10。若任何呼叫失敗，整個請求都會失敗。扇出格式清單是
`open-sse/handlers/imageGeneration/fanOut.ts` 中的 `SINGLE_IMAGE_FANOUT_FORMATS`。

ZenMux 會重複使用現有的 API 金鑰連線，並接受 `zenmux/` 或 `zm/` 前綴：

- `zenmux/openai/gpt-image-2` 使用 ZenMux 的 OpenAI Images API。選項包括 `size`、
  `quality`、`n`、`output_format`、`output_compression`、`background` 與 `response_format`。
- 其他發行者（例如 `zm/meta/muse-image-1.0`）會使用 ZenMux 的 Vertex AI `:predict`
  端點。`n` 對應至 `sampleCount`，`aspect_ratio` 對應至 `aspectRatio`，而 `image_size`
  （`1K`、`2K`、`4K`）則對應至 `sampleImageSize`。以像素指定的 `size` 僅提供長寬比，
  不保證像素尺寸。支援的比例、解析度與數量因模型而異。
- `zm/inclusionai/ming-image-0.1-design` 會自行選擇尺寸。請省略 `size`、
  `aspect_ratio` 與 `image_size`；明確指定這些值會傳回 HTTP 400。可以使用
  `output_format` 請求 PNG、JPEG 與 WebP。

此整合支援文字轉圖像生成，不支援參考圖像編輯。Vertex 輸出會正規化為
`data[].b64_json`；當只有圖像位元組可用時，`response_format: "url"` 會傳回上游
HTTPS URL 或 base64 資料 URL。空白或遭篩選的輸出會傳回錯誤，而非空白的成功回應。
模型存取權取決於 ZenMux 帳戶。請參閱 [ZenMux 的 Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) 與
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image)。

```bash
# 列出所有圖像模型
GET /v1/images/generations
```

## 文件 OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` 會透過 `provider/model` 前綴選擇 OCR 提供者；單獨的模型 ID（例如
`mistral-ocr-latest`）會解析至其註冊的提供者，而省略 `model` 時則預設使用
Mistral（`mistral-ocr-latest`）。已註冊的提供者（`open-sse/config/ocrRegistry.ts`）：

| 提供者 ID                     | 模型 ID              | `model` 值                                                    | 備註                                                                                         |
| ----------------------------- | -------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest`（或單獨的 `mistral-ocr-latest`） | 同步——直接從單次上游呼叫傳回回應。                                                           |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                   | 非同步上游（`analyze` + 輪詢）——請參閱下文。                                                 |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                       | 同步，透過 Vertex AI 的 `openapi/chat/completions` 合作夥伴端點——驗證與 URL 詳情請參閱下文。 |

這三個提供者都會以相同的 Mistral 格式主體回應：

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence 輪詢流程

Azure Document Intelligence 的 `analyze` API 是非同步的：初始請求會傳回
`Operation-Location` 標頭而非主體，因此必須透過輪詢取得結果。處理常式
（`open-sse/handlers/ocr.ts`）會每秒輪詢該 URL，最多嘗試 30 次；若輪詢回應不是
`ok` 或狀態為 `"failed"`，則會立即失敗（不會繼續輪詢）；若用盡嘗試次數後作業仍在
執行，則會傳回 `504`。最終的 Azure 回應會先正規化為與 Mistral 相同的
`pages`/`markdown` 格式，再傳回給呼叫端，因此用戶端程式碼不需要對提供者進行特殊處理。

### Vertex AI DeepSeek OCR 驗證與端點解析

`vertex-deepseek-ocr` 會重複使用 OmniRoute 已支援用於聊天／圖像流量的同一套 Vertex AI
驗證機制（`open-sse/executors/vertex.ts`）：連線的 API 金鑰可以是 Service Account JSON
憑證（透過 JWT bearer 流程交換成短期 OAuth 存取權杖），或是直接使用已簽發的 OAuth
存取權杖。上游端點 URL 是 Vertex 的通用 `openapi/chat/completions` 合作夥伴端點，
由連線的專案與區域建構——明確指定的 `providerSpecificData.project`/`providerSpecificData.region`
一律優先；否則，專案會從 Service Account JSON 的 `project_id` 衍生，而區域預設為
`us-central1`。這兩項解析都會在 `open-sse/handlers/ocr.ts` 中進行
（`resolveVertexOcrAccessToken`、`resolveVertexOcrBaseUrl`），並由
`src/app/api/v1/ocr/route.ts` 在分派至 `handleOcr` 前使用。

## 列出模型

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ 以 OpenAI 格式傳回所有聊天、嵌入與圖片模型及組合
```

### 模型 ID 前綴（`?prefix=`）

大多數模型都以**提供者前綴**對外提供。所使用的前綴由
`MODELS_CATALOG_PREFIX_MODE` 功能旗標控制，也可以透過查詢參數針對**每個請求**覆寫——這對希望取得簡潔清單、但不想變更所有使用者之伺服器全域設定的用戶端很有幫助：

```bash
GET /v1/models?prefix=alias        # 每個模型一個 ID——簡短的別名前綴
GET /v1/models?prefix=dual         # 兩種形式（伺服器預設值）
GET /v1/models?prefix=canonical    # 僅使用完整的提供者 ID 前綴
```

| 模式        | 輸出                                                     | 備註                                                                                                                                             |
| ----------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `dual`      | `cc/claude-sonnet-4-6` **和** `claude/claude-sonnet-4-6` | **預設值。** 兩個 ID 都會路由至同一模型；保留此模式，讓硬編碼任一形式的用戶端設定仍可正常運作。目錄大小大約會加倍。                              |
| `alias`     | `cc/claude-sonnet-4-6`                                   | 每個模型一個項目。沒有獨立別名的提供者仍會輸出其項目，因此不會遺漏任何內容。                                                                     |
| `canonical` | `claude/claude-sonnet-4-6`                               | 每個模型都以完整的提供者 ID 前綴輸出一個項目。沒有獨立別名的提供者（例如 `antigravity/…`、`agy/…`）也會在此輸出其唯一 ID，因此不會遺漏任何內容。 |

即使沒有查詢參數，也可以識別 `dual` 模式的鏡像項目：它會帶有指向主要 ID 的 `parent`
欄位。

呈現模型選擇器的用戶端應請求 `?prefix=alias`——
[OmniCopilot VS Code 擴充功能](../guides/VSCODE-COPILOT.md)就是這麼做的。

### 探索篩選器（`?capability=`、`?min_context=`、`?kind=`、`?q=`）

`GET /v1/models` 接受選用的探索篩選器。未使用任何篩選器時，回應維持不變。
這些篩選器會縮小呼叫端原本可見的目錄範圍（會先套用 API 金鑰權限），
並且會在 OpenAI 風格的 `limit` / `after` 分頁之前執行：

```bash
GET /v1/models?capability=vision&capability=tool_calling   # 列出的每項能力都必須為 true
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # 目錄 `type`；沒有此欄位的資料列視為 `chat`
GET /v1/models?q=sonnet&limit=10                           # 對 ID 或名稱進行不區分大小寫的比對
```

| 參數          | 值                                                                                                  |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`、`reasoning`、`structured_output`、`temperature`、`thinking`、`tool_calling`、`vision` |
| `min_context` | 非負整數，與 `context_length` 比較                                                                  |
| `kind`        | `chat`、`audio`、`embedding`、`image`、`moderation`、`music`、`rerank`、`video`                     |
| `q`           | 1–200 個字元                                                                                        |

未知的值，或並非非負整數的 `min_context`（例如 `1.5`），
會傳回 HTTP `400`，而訊息中會列出有效值。實作位於：
`src/app/api/v1/models/catalogFilters.ts`。

### 模型候選清單（`POST /v1/models/query`）

`POST /v1/models/query` 會從同一個目錄傳回簡短且具確定性的清單，並套用與
`GET /v1/models` 相同的驗證及每個金鑰的可見性設定：

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

每個欄位都是選用的。`capabilities` 和 `exclude` 可接受陣列或以逗號分隔的字串；
`max_output` 會與 `max_output_tokens` 比較。結果會先依 `owned_by`、再依 `id` 排序。
`limit` 預設為 `20`，超過 `100` 的值會限制為 `100`。無效的 JSON、未知欄位或無效值會傳回 HTTP `400`。

### 個別隱藏的聊天模型

在提供者頁面上標記為**隱藏**的模型會從目錄中排除，且在明確請求時會以
HTTP `404` / `model_not_found` 拒絕。此檢查會使用解析後的提供者與模型，包括提供者別名、相容提供者的節點前綴，以及連線預設值。組合會略過隱藏的目標，並可使用可見的同層項目；若沒有任何可執行的目標，則會傳回相同的錯誤代碼。取消隱藏會在下一個請求時生效。僅限圖片的可見性覆寫不會隱藏具有相同 ID 的聊天模型。

此個別模型設定獨立於
[模型公開允許/拒絕清單](../routing/MODEL_EXPOSURE_LIST.md)，後者會篩選目錄中公開的項目與自動路由候選項目，但仍保留明確分派。API 金鑰的模型權限會繼續獨立套用。預設的目錄前綴模式仍為 `dual`。

### 無思考模型變體

對於支援思考功能的 Claude 模型，`/v1/models` 也會公開一個 ID 前綴為 `claude-3-omniroute-no-thinking/` 的**無思考**變體：

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

選取此 ID（例如，在一律附加 `thinking` 區塊的 Claude Code 設定中）時，會解析回實際的 `<provider>/<model>`，並抑制推理——在 `/v1/messages` 路徑上使用 `thinking:{type:"disabled"}`，或在 `/v1/chat/completions` 路徑上移除 `reasoning`/`reasoning_effort` 欄位。此變體僅會為支援思考功能**且**接受 `disabled` 的 Claude 系列模型列出（因此，例如，拒絕 `disabled`、僅支援自適應模式的模型會被排除）。操作人員可透過 `ModelSpec.noThinkingAlias`，針對個別模型強制開啟或關閉此變體。

## ElevenLabs 音訊生成

使用您的 ElevenLabs API 金鑰，在 OmniRoute 中設定 `elevenlabs` 提供者連線。
用戶端使用其 **OmniRoute** 金鑰進行驗證（`Authorization: Bearer $OMNIROUTE_API_KEY`）；
閘道會以 `xi-api-key` 提供已儲存的提供者金鑰。切勿將 ElevenLabs 金鑰當作閘道的 bearer 權杖傳送。

| 方法 | 路徑                        | 回應                        | API 金鑰端點類別 |
| ---- | --------------------------- | --------------------------- | ---------------- |
| POST | `/v1/sound-generation`      | 原生音訊位元組              | `elevenlabs`     |
| POST | `/v1/music`                 | 原生音訊位元組              | `music`          |
| POST | `/v1/music/stream`          | 串流音訊位元組              | `music`          |
| POST | `/v1/music/detailed`        | 原生多部分音訊與作曲計畫    | `music`          |
| POST | `/v1/music/detailed/stream` | 原生 SSE 中繼資料與音訊區塊 | `music`          |
| POST | `/v1/music/plan`            | JSON 作曲計畫               | `music`          |

這些端點是既有 `/v1/audio/speech`、`/v1/audio/transcriptions`、
`/v1/voices`、`/v1/text-to-speech/{voiceId}` 與 `/v1/speech-to-text` 路由的補充。系統會保留原生 JSON 欄位
及查詢參數，例如 `output_format` 與 `enable_logging`。
`/v1/music/detailed` 回應會保留其多部分邊界；請將其解析為 multipart。
`/v1/music/detailed/stream` 會傳回 `text/event-stream`，其中包含作曲中繼資料，以及
SSE 事件中的 base64 音訊區塊。所有六個路由皆支援 CORS 預檢。

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# 短音效。持續時間：0.5 至 30 秒。
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# 音樂持續時間以毫秒表示：3000 至 600000。
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

若要漸進式傳遞音訊，請將相同的 JSON 主體用於 `/v1/music/stream`。作曲
只接受 `prompt` 或 `composition_plan` 其中之一；`/v1/music/plan` 需要 `prompt`，
並可選擇性接受 `source_composition_plan`。原生結構描述會保留其他
提供者欄位，讓作曲計畫版本與微調選項能傳遞至 ElevenLabs。

統一的 `/v1/music/generations` 端點也接受 `elevenlabs/music_v1`、
`elevenlabs/music_v2` 與 `elevenlabs/music_v2_5`。若存在有效的 ElevenLabs 連線，
這些模型會由音樂目錄公開。此端點會傳回
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`。其 `duration` 欄位以
秒為單位，並對應至 `music_length_ms`；明確指定的 `music_length_ms` 具有較高優先順序。
`instrumental` 對應至 `force_instrumental`，且原生欄位具有較高優先順序。
如需串流，請使用原生串流端點；若請求僅由作曲計畫驅動，則請使用原生作曲端點。

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

在進行上游呼叫之前，會套用端點、模型、預算與連線限制。原生
路由會原封不動地傳回上游狀態碼與錯誤主體，包括方案限制的 `402`
及配額限制的 `429`。若存在 `character-cost`、`song-id`、`request-id` 與 `retry-after`
標頭，則會予以保留。擁有免費點數餘額並不保證可存取所有
音樂模型、輸出格式或 API 功能：ElevenLabs 會決定每個請求的使用權限。
統一端點會在 OmniRoute 的正規化錯誤封套中保留錯誤狀態碼。

上游合約：[音效](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert)、
[音樂作曲](https://elevenlabs.io/docs/api-reference/music/compose)及
[串流音樂詳細資料](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)。

```bash
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **重新排序提供者節點：** `POST /v1/rerank` 也會路由至與 OpenAI 相容的提供者節點
> （oMLX、vLLM、Infinity、位於閘道後方的 TEI，……），其位址格式為 `<node-prefix>/<model>`。迴路
> 節點（`localhost`、`127.0.0.1`、`172.16.0.0/12`）一律符合使用資格，營運者列於
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` 中的主機名稱亦同（例如 Docker/Compose 服務名稱，
> 如 `http://reranker:8080/v1`；系統會直接呼叫這些節點，絕不透過 `HTTP(S)_PROXY` 或
> 連線的固定 Proxy）。位於任何其他
> 主機上的節點（例如 LAN 主機或 Tailscale 對等節點）僅在營運者啟用
> `RERANK_REMOTE_PROVIDER_NODES` 功能旗標，**且**節點的基底 URL 通過提供者
> 對外 URL 政策（`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`）時才符合使用資格。
> 記憶體引擎的重新排序步驟會透過
> 迴路呼叫此路由，因此相同規則也適用於「記憶體」設定中的 `rerankProviderModel`。
>
> **本機伺服器形式：**系統會在 `<base>/v1/rerank` 呼叫節點，若收到 404，則改呼叫 `<base>/rerank`
> （Infinity、TEI）。上游主體同時帶有 Cohere/OpenAI 的拼法（`documents`、
> `return_documents`）及 TEI 的拼法（`texts`、`return_text`），而上游回應會
> 正規化為 Cohere 封裝格式：TEI 的裸格式 `[{index, score, text}]`、精簡閘道回傳的 `{results: [{index, score}]}`
> 以及 Voyage 風格的 `{data: [...]}`，都會以
> `{results: [{index, relevance_score, document?}]}` 格式回傳給用戶端，依分數排序，並以 `top_n` 為數量上限。

> **提供者節點探索：**與 OpenAI 相容的提供者節點上的模型，會以節點前綴顯示於 `GET /v1/models`
> 中。未附帶端點中繼資料的資料列（本機 `/v1/models` 清單的典型情況）
> 會繼承節點的 `apiType`，因此 `embeddings` 節點的模型會是 `type: "embedding"`，而
> `rerank` 節點的模型會是 `type: "rerank"`，而非預設為聊天類型；同步或手動新增的資料列若明確指定
> `supportedEndpoints`，仍會具有較高優先順序。

## Files API

與 OpenAI 相容的檔案端點，用於批次輸入/輸出及依檔案用途上傳。

| 方法   | 路徑                     | 說明                                                                                                        |
| ------ | ------------------------ | ----------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/files`              | 上傳檔案（multipart：`file`、`purpose`、`expires_after[anchor]`、`expires_after[seconds]`）— 上限為 512 MiB |
| GET    | `/v1/files`              | 列出已驗證 API 金鑰的檔案                                                                                   |
| GET    | `/v1/files/[id]`         | 擷取檔案的中繼資料                                                                                          |
| DELETE | `/v1/files/[id]`         | 刪除檔案                                                                                                    |
| GET    | `/v1/files/[id]/content` | 以串流方式傳回原始檔案內容                                                                                  |

**驗證：** Bearer API 金鑰 — 檔案透過 `getApiKeyRequestScope` 依 API 金鑰劃分範圍。金鑰
只能查看、下載及刪除其本身的檔案；沒有金鑰的儀表板工作階段可讀取整個
執行個體；沒有擁有者的檔案（匿名或透過儀表板工作階段上傳）會拒絕所有
非工作階段呼叫者存取。`GET /v1/files` 會對匿名呼叫者，以及所提供但無法
解析的金鑰傳回 `401`，即使 `REQUIRE_API_KEY=false` 亦然，而不是列出所有租戶的
檔案（GHSA-m3hp-hq9g-fpmv、GHSA-2jm2-mpx8-6523）。

## Batches API

與 OpenAI 相容的批次處理。

| 方法   | 路徑                      | 說明                                                                                             |
| ------ | ------------------------- | ------------------------------------------------------------------------------------------------ |
| POST   | `/v1/batches`             | 建立批次 — 由 `v1BatchCreateSchema` 驗證本文（`input_file_id`、`endpoint`、`completion_window`） |

### Exa 與 Tavily 的 `provider_options`

Exa 與 Tavily 會從具命名空間的容器中讀取提供者專屬欄位：
`provider_options.exa`（或 `provider_options["exa-search"]`）及 `provider_options.tavily`
（或 `provider_options["tavily-search"]`）。只有下列鍵會被轉送。每個鍵都會
依據 `open-sse/handlers/search/providerOptionsPassthrough.ts` 中各自的 Zod 結構描述進行檢查，
類型錯誤的鍵會被捨棄。任何其他鍵都會被忽略，包括驗證、基底 URL、
`stream` 及 `outputSchema`。其他提供者使用的扁平鍵（`cx`、`depth` 等）則
維持原有運作方式。

| 提供者 | 頂層欄位                                                                                                                                                                                                                                                                                                                                                                  | 巢狀欄位                                                                                                                                                     |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Exa    | `type`、`category`、`userLocation`、`moderation`、`additionalQueries`、`objective`、`systemPrompt`、`compliance`（扁平基本型別）、`startPublishedDate`、`endPublishedDate`                                                                                                                                                                                                | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` 會合併並覆蓋預設值 `{ text: true, highlights: true }` |
| Tavily | `search_depth`、`chunks_per_source`、`time_range`、`start_date`、`end_date`、`include_published_date`、`filter_by_published_date`、`include_answer`、`include_raw_content`、`include_images`、`include_image_descriptions`、`include_favicon`、`include_domains_mode`、`language`、`filter_by_language`、`auto_parameters`、`exact_match`、`include_usage`、`safe_search` | —                                                                                                                                                            |

通用欄位一律具有優先權：`query`、`max_results`、`filters`（網域）、`country`，以及由
`search_type` 衍生的主題。在 Exa 中，`search_type: "news"` 會保留 `category: "news"`。
Tavily 也接受 `search_type: "finance"`（`topic: "finance"`）。

通用的 `time_range` 現在會傳遞至兩個提供者：Exa 會取得 `startPublishedDate`（ISO
時間戳記），而 Tavily 會取得 `start_date`（`YYYY-MM-DD`）。`provider_options`
中的明確日期會覆寫對應產生的日期。

Exa 結果會在 `provider_raw` 中保留 `id`、`highlight_scores`、`summary`、`subpages`、`entities` 及
`extras`。Tavily 結果則會保留 `images` 和 `favicon`。

成本計算仍使用扁平登錄檔 `costPerQuery`。Tavily 對
`search_depth: "advanced"` 的每次呼叫收取較多點數，而此差異不會反映在
`usage.search_cost_usd` 中。

## Web Fetch API

透過已設定的網頁擷取提供者（Firecrawl、Jina Reader、Tavily Extract、TinyFish Fetch、Nimble Extract、Parallel Extract），從 URL 擷取內容。

Parallel Extract（`parallel-search`，與 Parallel Search 使用相同的 API 金鑰）僅回傳 Markdown——任何其他 `format` 都會導致 `400`——且內容上限為 100,000 個字元。當目標頁面本身無法擷取時，上游會在 HTTP 200 回應內回報此情況；OmniRoute 則會將其呈現為帶有固定訊息的 `422`。

| 方法 | 路徑            | 說明                                               |
| ---- | --------------- | -------------------------------------------------- |
| POST | `/v1/web/fetch` | 擷取／抓取 URL——請求本文由 `v1WebFetchSchema` 驗證 |

**驗證：** Bearer API 金鑰（`extractApiKey` + `isValidApiKey`）。透過 `enforceApiKeyPolicy` 強制執行原則。

**配額感知後援機制（#8297）：** 當未明確指定 `provider` 時，系統會依固定優先順序（優先填滿）巡覽提供者池（`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` → `parallel-search`）——已設定但受到速率限制的提供者會被略過，而不會直接中止請求；在請求執行期間，若上游發生可重試／配額相關失敗（HTTP 429 一律適用；Firecrawl／Tavily／TinyFish 的配額型免費方案則適用 402/403——Jina Reader 不適用，且一般的 400 錯誤請求永不適用），系統會轉而嘗試下一個尚未嘗試且已設定憑證的提供者。當提供者池中的所有提供者都已耗盡時，端點會回傳單一 `429`（附帶 `Retry-After` 標頭），而非先前通用的 `400`。當明確要求某個 `provider` 時，則**不會**進行靜默後援——受到速率限制或失敗的指定提供者會直接呈現其自身錯誤（若受速率限制則為 `429`，否則為上游狀態碼）。

## WebSocket 串流

```bash
GET /v1/ws?handshake=1
```

驗證 WebSocket 升級交握，並回傳有線通訊協定範例訊息（`request`、`cancel`）。實際的 WS 訊框由 Next.js 路由表之外的內建 WS 伺服器處理。

**驗證：** 在交握期間使用 Bearer API 金鑰。

### 透過 WebSocket 使用 Responses API（僅限 codex）

```bash
# 與 HTTP API 使用相同的主機與連接埠（預設為 20128）；升級連線：
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# （或：-H "Authorization: Bearer <OMNIROUTE_API_KEY>"）

# 第一個訊框必須是 response.create：
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket Proxy **僅連接至 `codex`**（ChatGPT 後端）。它在與 API／儀表板相同的連接埠上，監聽 `/v1/responses`、`/responses` 與 `/api/v1/responses` 路徑。在第一個 `response.create` 訊框上，它會透過內部 `codex-responses-ws` 橋接執行驗證與準備、選取 codex OAuth 連線，並透過 `wreq-js` 傳輸層建立通往 `wss://chatgpt.com/backend-api/codex/responses` 的通道。**非 codex 模型會遭拒絕**（`codex_ws_provider_required`）。若要使用配額共用路由，請使用 `model: "qtSd/<group>/codex/<model>"`。實作位於 `app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`。

**驗證：** 在交握期間使用 Bearer API 金鑰。內建 HTTP 伺服器（`server-ws.mjs`）必須是作用中的進入點（當 `app/server-ws.mjs` 存在時，預設即為如此）。

#### 模型 ID：使用純 ChatGPT ID（不含 `codex/` 前綴）

當 `supports_websockets = true` 時，OpenAI **Codex CLI** 會在用戶端驗證模型名稱，並**拒絕帶有提供者前綴的 ID**，例如 `codex/gpt-5.5`（`The 'codex/gpt-5.5' model is not supported when using Codex with a ChatGPT account`）。請傳送**純** ID（例如 `gpt-5.5`）。OmniRoute 的橋接僅支援 codex，因此在建立上游通道之前，它會將純 ID 重新解析為 codex 模型（`resolveCodexWsModelInfo`）——即使純 `gpt-5.5` 原本會在 HTTP 上透過其他提供者進行路由。

#### 設定 OpenAI Codex CLI

若要讓 Codex CLI 指向 OmniRoute，請在 `~/.codex/config.toml` 中新增支援 WebSocket 的自訂提供者（使用獨立的 `CODEX_HOME`，以避免修改現有設定）：

```toml
model = "gpt-5.5"                 # 純 ID——不是 "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # 不含結尾斜線；WS URL 會由此推導（正式環境請使用 https/wss）
wire_api = "responses"                    # 自 2026 年 2 月起唯一支援的值
supports_websockets = true                # 啟用 Responses-over-WS 傳輸
env_key = "OMNIROUTE_API_KEY"             # 保存 OmniRoute API 金鑰（Bearer）
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API 金鑰（若 REQUIRE_API_KEY=false，則可使用任何金鑰）
codex exec "Responda apenas: PONG"
```

CLI 會將 `base_url + /responses` 升級為 WebSocket，而 OmniRoute 會將其通道連接至所選的 codex OAuth 連線。已針對本機伺服器完成端對端驗證：ChatGPT 會回傳 `codex.rate_limits` + `response.created`，並以串流方式傳送完成內容。

## 自助式用量查詢（`/api/usage/om-usage`）

任何 API 金鑰都可以讀取**自身的**用量與配額，不需要管理驗證。這是用戶端（CLI、OmniCopilot 面板）用來向金鑰持有者顯示其支出的端點。

```bash
# 文字形式（歷史既有介面規約——供終端機使用的純文字）
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# 結構化形式——供 UI 使用
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

金鑰必須啟用 **`allowUsageCommand`**（預設為關閉——儀表板的 API 金鑰管理器可針對每個金鑰切換此設定）。若未啟用，端點會回應 `403`。

`?format=json` 會傳回可辨識的資料結構，因此呼叫端不會在拒絕回應中讀取資料欄位。成功時：

```jsonc
{
  "allowed": true,
  // 僅當金鑰選擇啟用每金鑰用量限制（每日／每週美元）時才會出現：
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // 所選提供者的配額快照；若尚未快取任何資料，則為 null：
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // 每個連線的快照，讓 UI 能夠並排呈現多個提供者：
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

拒絕時（`401` 金鑰無效／`403` 不允許），同一路由會傳回 `{ "allowed": false, "error": { "message": "…" } }`——存在但為空的 `personal`／`provider`（金鑰獲准，但尚未取得任何資料）與遭拒絕是不同的狀態，而且只有 JSON 形式能區分兩者。

**驗證：** 呼叫端自身的 Bearer API 金鑰，使用 `isValidApiKey` 驗證——這**不是**管理介面（`/api/keys/…`）；管理介面仍受 `requireManagementAuth` 保護。

### 原始配額百分比與截止值調整後的配額百分比

使用 `/api/usage/om-usage` 時，呼叫端應注意**純文字輸出**與結構化 **JSON 輸出**所呈現百分比之間的差異：

| 面向           | 純文字格式（`/api/usage/om-usage`／`@@om-usage`）                           | JSON 格式（`?format=json`）                                     |
| :------------- | :-------------------------------------------------------------------------- | :-------------------------------------------------------------- |
| **輸出欄位**   | `NN% left`（例如 `20% left`）                                               | `provider.quotas`／`providers[].quotas`                         |
| **衡量方式**   | **截止值調整後的可用額度**：高於截止門檻的剩餘容量                          | **原始上游配額**：未經調整的提供者衡量值                        |
| **截止值縮放** | 透過 `effectiveRemainingPercent()` 縮放，使受保護的保留額度顯示為 `0% left` | 無（提供者回報的原始快照值）                                    |
| **門檻資料**   | 已納入顯示的百分比                                                          | 儲存在各連線的 `quotaWindowThresholds` 中（或使用伺服器預設值） |
| **主要使用者** | 互動式 CLI、終端機提示、人工作業人員                                        | 程式化整合、儀表板、分析、計費追蹤器                            |

#### 截止值調整公式

OmniRoute 支援主動式配額截止值，以防止上游配額耗盡（可透過連線的 `quotaWindowThresholds`、提供者預設值或全域韌性設定進行設定）。當某個配額視窗啟用了截止門檻（例如 `cutoff = 25%`）時，文字轉譯器會依下列方式計算剩餘額度：

- 若 `remaining <= cutoff`：傳回 `0%`。
- 若 `remaining > cutoff`：傳回 `((remaining - cutoff) / (100 - cutoff)) * 100`。

格式化文字輸出會將其四捨五入至最接近的整數（`Math.round(...)`）。

#### 說明範例

假設某個提供者視窗的**原始用量為 60%**（因此**原始剩餘配額為 40%**），並設定了**剩餘配額 25% 的截止**門檻：

| 表示方式                        | 計算方式                                           | 剩餘量  |               推算已用量               |
| :------------------------------ | :------------------------------------------------- | :-----: | :------------------------------------: |
| **原始 JSON（`?format=json`）** | 上游快照（`quotas[window]`）                       | **40%** |                **60%**                 |
| **文字格式（`NN% left`）**      | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%**（若以 `100 - remaining` 計算） |

- **為何文字顯示剩餘 20%：** 在帳戶實際剩餘的 40% 配額中，截止政策保留了 25%。在路由器停止將流量路由至此連線之前，呼叫端於 75% 的可用空間中僅剩 15%。縮放可確保連線恰好在路由停止時發出配額耗盡訊號（`0% left`）。
- **為何 JSON 保留原始值：** JSON 承載資料會傳回提供者的精確快照（`UsageSnapshot`），讓外部工具能夠存取真實的上游使用率及連線層級的 `quotaWindowThresholds`，而不會受到伺服器端有損縮放的影響。

#### 使用端遷移指南

如果外部整合（例如編輯器外掛程式或代理程式擴充功能）先前會抓取文字
端點（`NN% left`），並以 `100 - NN` 計算已使用百分比，則遷移至 `?format=json` 意味著：

- 讀取原始 JSON 值將反映**實際的上游用量**（以上述範例而言，已使用 60%）。
- 如果整合希望保留文字端點的可用配額語意，可以使用 `quotaWindowThresholds` 在用戶端
  評估有效剩餘量公式，以納入連線層級的覆寫設定。

## 語意快取

```bash
# 取得快取統計資料
GET /api/cache/stats

# 清除所有快取
DELETE /api/cache/stats
```

回應範例：

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### 延遲影響

語意快取命中時，會直接從快取提供回應，**不會呼叫上游服務**，因此回報的
`X-OmniRoute-Response-Latency` 接近零
（無論原始上游延遲為何）。對延遲敏感的用戶端
（基準測試、p50/p99 監控）應檢查
`X-OmniRoute-Cache-Latency` 回應標頭：

| 值          | 含義                                       |
| ----------- | ------------------------------------------ |
| `synthetic` | 回應由快取提供；延遲並非真實的上游處理時間 |
| _(不存在)_  | 回應來自實際的上游呼叫                     |

### 個別金鑰略過快取

API 金鑰可透過 `cacheDefaultMode` 選擇不讀取語意快取：

| 值       | 行為                               |
| -------- | ---------------------------------- |
| `legacy` | 一般快取行為（預設）               |
| `bypass` | 完全略過快取查詢；一律呼叫上游服務 |

可在建立金鑰（`POST /api/keys`）或更新金鑰（`PATCH /api/keys/[id]`）時設定：

```json
{ "cacheDefaultMode": "bypass" }
```

### 個別請求略過快取

無論金鑰設定為何，任何請求都可略過快取：

```
X-OmniRoute-No-Cache: true
```

會維持一般 OpenAI 行為。偵測會重複使用現有的目錄請求，不會產生任何完成權杖，

提供者更新 API：

```json
  }
}
```

請使用 `PUT /api/providers/<connection-id>` 傳送該主體。在該連線上，明確指定為
`none` 的推理強度會以 `chat_template_kwargs.thinking=false` 與
`chat_template_kwargs.enable_thinking=false` 傳送。除非伺服器端推理規則強制指定某個強度，
否則明確的原生範本值仍具有最高優先權。此設定僅在自訂 OpenAI 相容連線分派
Chat Completions 主體時套用；Responses 請求與一般提供者會維持其原生請求格式。
將 `reasoningControl` 設為 `openai` 可強制直接傳遞一般 OpenAI
`reasoning_effort`，或者省略此設定／將其設為 `null` 以使用自動偵測。

當 Claude Code 自動模式分類器請求不包含明確的推理控制項時，預設會停用原生思考。
偵測會使用 Claude 格式請求中的分類器系統標記，而非模型名稱或完成上限。
明確的主體控制項、受支援的強度／思考標頭、路由規則，以及解析後的模型推理強度，
都會維持其現有優先順序。分類器的兩個階段都會保留其提示、完成上限、停止序列，
以及真正的上游權限判定；第二階段仍可將其要求的可見推理產生為一般文字。

### API 金鑰權限

```json
  "news": null,

  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — 目前執行中建置版本的 npm 通道：版本為 `-nightly.*` 時是 `nightly`；
  其他預發布版本（`-rc.*`、`-beta.*`、`-alpha.*`）是 `next`；若穩定版本的主版本號
  早於 `channels.latest`，則是 `lts`；否則為 `latest`。規則與
  `scripts/release/dist-tag.mjs` 相同，該指令碼會在發布時選擇 npm dist-tag。
- `channels` — 每個 dist-tag 已發布的最新版本，資料來自 `npm view omniroute dist-tags`（registry
  HTTP 備援），並使用與 `latest` 相同的 10 分鐘 TTL 快取。`latest` 一定會存在
  （先回退至 `latest` 欄位，再回退至 `"unavailable"`）；`next`、`nightly` 和 `lts` 僅在
  對應的 dist-tag 存在時出現。帶有 `Cache-Control: no-cache` 的請求會重新整理這兩項查詢。

通道模型（`latest` = v3，直到 4.0 GA；`next` = rc；`nightly` = `develop` 建置；
`lts` = 4.0 GA 後的 v3 修補版本）記載於 `docs/ops/RELEASE_STRATEGY.md`。

## Token 限制

每個 API 金鑰的 **token** 預算（與上述以 USD 為基礎的預算不同）。此限制會在請求路徑中即時強制執行：當金鑰在目前時間窗口內的用量達到限制時，請求會遭到拒絕並回傳 `429 Too Many Requests`。限制可限定於特定 `model`、`provider`，或在整個金鑰範圍內以 `global` 套用；當一個請求符合多項限制時，會採用其中最嚴格的限制。

```bash
# 列出金鑰的 token 限制（包含即時窗口用量）
GET /api/usage/token-limits?apiKeyId=key-123

# 建立或更新 token 限制
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# 依 id 刪除 token 限制
DELETE /api/usage/token-limits?id=tl-abc
```

> **結構描述注意事項**（`setTokenLimitSchema`）：`apiKeyId` 與 `scopeType`（`model` | `provider` | `global`）為必填。除非 `scopeType` 為 `global`，否則 `scopeValue` 為必填（例如，`model` 範圍使用模型 id，`provider` 範圍使用提供者 id）。`tokenLimit` 必須是正整數（可由字串強制轉換）。選填：`id`（建立時省略，更新時提供）、`resetInterval`（`daily` | `weekly` | `monthly`，預設為 `monthly`）、`resetTime`（`HH:MM`）、`enabled`（預設為 `true`）。`GET` 回應會為每項限制補充 `tokensUsed`、`remaining`、`windowStart`、`periodStartAt` 與 `nextResetAt`。這是管理類端點（驗證由 authz 管線集中強制執行）。

## 請求處理流程

1. 用戶端將請求傳送至 `/v1/*`
2. 路由處理常式呼叫 `handleChat`、`handleEmbedding`、`handleAudioTranscription` 或 `handleImageGeneration`
3. 解析模型（直接指定提供者/模型，或使用別名/組合）
4. 從本機資料庫選取憑證，並依帳戶可用性進行篩選
5. 對於聊天：`handleChatCore` 會檢查語意/簽章快取，並解析組合壓縮設定
6. 啟用時，會在提供者格式轉換之前執行主動壓縮（`lite`、Caveman、RTK 或堆疊方式）
7. 提供者執行器將請求傳送至上游
8. 將回應轉換回用戶端格式（聊天），或原樣回傳（嵌入/圖片/音訊）
9. 記錄用量、壓縮分析資料與請求日誌
10. 發生錯誤時，依據組合規則套用後援機制

完整架構參考：[`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## 韌性（擴充）

OmniRoute 提供三種彼此獨立的暫時性失敗處理機制；下列管理端點可讓操作人員讀取及覆寫這些機制：

| 範圍         | 狀態儲存位置                         | 讀取                                      | 重設／清除                               |
| ------------ | ------------------------------------ | ----------------------------------------- | ---------------------------------------- |
| 提供者熔斷器 | `domain_circuit_breakers` + 記憶體內 | `/api/monitoring/health`                  | `POST /api/resilience/reset`             |
| 連線冷卻     | 提供者連線上的 `rateLimitedUntil`    | `/api/rate-limits`, `/api/providers/[id]` | （延遲重新啟用；可透過提供者 PUT 清除）  |
| 模型鎖定     | 記憶體內模型可用性登錄表             | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns` |

`PATCH /api/resilience` 接受位於 `providerBreaker.oauth` 和 `providerBreaker.apikey` 下的提供者熔斷器覆寫設定。每個設定檔皆支援 `degradationThreshold`、`failureThreshold` 和 `resetTimeoutMs`；相同欄位也會顯示於「儀表板 → 設定 → 韌性」。

```bash
# 清除單一模型鎖定
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# 清除所有鎖定
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

完整概念參考資料與熔斷器預設值：請參閱 [`CLAUDE.md`](../../CLAUDE.md) →「韌性執行階段狀態」以及 [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md)。

### 速率限制佇列與自動啟用安全網

- **支援的寫入路徑**：使用本文 `{"connectionId": "<id>", "enabled": true|false}` 呼叫 `POST /api/rate-limits`，是切換連線速率限制保護的受支援管理端點。`PUT /api/providers/[id]` 刻意不修改或切換 `rateLimitProtection`（#11278）。
- **`enabled: false` 的語意**：設定 `enabled: false` 會移除該連線的明確保護，但**不會**讓作用中的 API 金鑰連線退出全域自動啟用安全網（`autoEnableApiKeyProviders = true`）。在 `reconcileEnabledConnections`（`open-sse/services/rateLimitManager.ts`）中，`false` 和 `undefined` 等效；沒有明確保護的作用中 API 金鑰連線，仍會受到自動啟用安全網的保護。
- **全域停用**：若要讓 API 金鑰連線在沒有速率限制佇列的情況下執行，請透過 `RATE_LIMIT_AUTO_ENABLE=false`（環境變數）或 `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false`（設定 → 韌性／`PATCH /api/resilience`）在全域停用安全網。

## MCP 伺服器

OmniRoute 隨附內嵌的模型上下文協定伺服器，提供 3 種傳輸方式（stdio、SSE、streamable-http）及具範圍限制的工具。下列儀表板端點會讀取狀態／稽核資料，並代理 HTTP 傳輸。

| 方法 | 路徑 | 說明 |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | 心跳、傳輸、上線狀態、最近一次呼叫、熱門工具、24 小時成功率 |
| GET | `/api/mcp/tools` | 列出 MCP 工具及其 `name`、`description`、`scopes`、`phase`、`auditLevel`、`sourceEndpoints` |
| GET | `/api/mcp/sse` | 開啟 SSE 傳輸的 SSE 串流（若 MCP 已停用或傳輸不相符，則回傳 `503`） |
| POST | `/api/mcp/sse` | 透過 SSE 傳輸傳送 JSON-RPC 訊框 |
| GET | `/api/mcp/stream` | 開啟可串流 HTTP 傳輸的 SSE 端（由伺服器發起的訊息） |
| POST | `/api/mcp/stream` | 透過可串流 HTTP 傳輸傳送 JSON-RPC 訊框 |
| DELETE | `/api/mcp/stream` | 結束可串流 HTTP 工作階段 |
| GET | `/api/mcp/audit` | 查詢稽核記錄 — `?limit=`、`?offset=`、`?tool=`、`?success=true                                | false`、`?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | 彙總稽核統計資料（總計、成功率、平均持續時間、熱門工具） |

**驗證：** `sse`／`stream` 傳輸遵循 MCP 專用的驗證介面（具有 `mcp` 範圍的 Bearer API 金鑰）；`status`／`tools`／`audit*` 路由可從儀表板讀取（除了能夠存取儀表板主機之外，不需要額外驗證）。

## A2A 伺服器

OmniRoute 提供一個 A2A（代理程式對代理程式）JSON-RPC 2.0 端點，以及供檢查／儀表板使用的 REST 包裝介面。

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # 除非已設定 OMNIROUTE_API_KEY，否則為選用
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

支援的方法（全部受 `settings.a2aEnabled` 控制）：

| 方法             | 說明                                             |
| ---------------- | ------------------------------------------------ |
| `message/send`   | 同步執行技能；傳回 `{task, artifacts, metadata}` |
| `message/stream` | 以 SSE 串流方式執行相同的技能集                  |
| `tasks/get`      | 依 `taskId` 取得任務                             |
| `tasks/cancel`   | 依 `taskId` 取消任務                             |

內建技能：`smart-routing`、`quota-management`、`provider-discovery`、`cost-analysis`、`health-report`。

### 代理程式卡片

```bash
GET /.well-known/agent.json
```

傳回公開的 A2A 代理程式卡片（名稱、說明、功能、技能目錄、驗證配置）— 公開快取 1 小時。無須驗證。

### REST 輔助端點

| 方法 | 路徑                         | 說明                                                                                                           |
| ---- | ---------------------------- | -------------------------------------------------------------------------------------------------------------- |
| GET  | `/api/a2a/status`            | A2A 啟用狀態 + 任務統計資料 + 已快取的代理程式卡片摘要                                                         |
| GET  | `/api/a2a/tasks`             | 列出任務 — `?state=submitted\|working\|completed\|failed\|cancelled`、`?skill=`、`?limit=`（≤200）、`?offset=` |
| POST | `/api/a2a/tasks`             | （未實作為 REST 輔助端點 — 請透過 JSON-RPC `message/send` 建立）                                               |
| GET  | `/api/a2a/tasks/[id]`        | 取得單一任務                                                                                                   |
| POST | `/api/a2a/tasks/[id]/cancel` | 取消任務                                                                                                       |

**驗證：**REST 輔助端點無須管理驗證即可執行（儀表板可讀取）；若已設定 Bearer `OMNIROUTE_API_KEY`，JSON-RPC `/a2a` 路由會使用該金鑰。

## 驗證

請參閱[管理驗證](../guides/MANAGEMENT-AUTH.md)，以瞭解四種憑證類別（儀表板工作階段、本機 CLI 權杖、`oma_live_…` 存取權杖、管理範圍的 API 金鑰），以及它們與推論金鑰的差異。

- 儀表板路由（`/dashboard/*`）使用 `auth_token` Cookie
- 登入使用已儲存的密碼雜湊；若無法使用，則改用 `INITIAL_PASSWORD`
- `requireLogin` 可透過 `/api/settings/require-login` 切換
- 當 `REQUIRE_API_KEY=true` 時，`/v1/*` 路由可選擇要求 Bearer API 金鑰
- 本參考資料中的「管理權杖」／「管理範圍的 API 金鑰」是指該指南中的其中一種憑證類別，而不是未定義的額外密鑰類型

> **重大變更（v3.8.0）** — `/api/v1/agents/tasks/*` 與冷卻管理端點現在需要**管理驗證**（儀表板 `auth_token` Cookie 或管理範圍的 API 金鑰）。先前未經驗證即呼叫這些路由的用戶端將收到 `401 Unauthorized`。請參閱提交 `588a0333`（`fix(auth): require management auth for agent and cooldown APIs`）。
