OmniRoute அழைப்புப் பதிவுகளை வெளிப்புறப் பகுப்பாய்வுத் தரவகத்திற்குத் தொடர்ச்சியாகவும் படிப்படியாகவும் ஏற்றுமதி செய்தல்.

Logs டாஷ்போர்டு தாவல் கோரிக்கை வரலாற்றை SQLite (`call_logs`)-இல் வைத்திருக்கிறது; அதன் அளவு
சுழற்சி மற்றும் தக்கவைப்புக் கொள்கைகளால் வரையறுக்கப்படுகிறது. பதிவு ஏற்றுமதி அதே பதிவுத் தொகுப்பை அட்டவணைப்படி வெளியே அனுப்புகிறது; இதனால் அது
உள்ளூர் தரவுத்தளத்தைவிட நீண்ட காலம் நிலைத்திருந்து, பிற தரவுகளுடன் இணைக்கப்படலாம். BigQuery முதலாவது இலக்கு;
இந்தச் செயலாக்கத் தொடர் ஒரு பதிவகமாக இருப்பதால், கூடுதல் இலக்குகளைச் சேர்ப்பது விரிவாக்கமாக அமைகிறது.

## 1. இது எவ்வாறு செயல்படுகிறது

```
server (decrypt + validate config, reconcile cursor)
  → start IPC → isolated exportChild OS process
    → read-only storage.sqlite → shared call-log query/mapping
      → async artifact hydration → destination prepare()/send()
        → batch IPC → server persists cursor → ack IPC
          → next batch; done IPC → server records success
```

- **அட்டவணை** — ஒரு `JobRegistry` cron பணி, `log_export`, இயல்பாக `0 * * * *` (மணிநேரத்திற்கு ஒருமுறை,
  UTC). இது `src/lib/initCloudSync.ts`-இல் பதிவுசெய்யப்படுகிறது; `OMNIROUTE_LOG_EXPORT_CRON` மூலம் மாற்றியமைக்கலாம்.
  ஒவ்வொரு இயக்க நேரத்திலும் **இயக்கப்பட்டுள்ள** ஒவ்வொரு இலக்கிற்கும் பதிவுகள் வரிசையாக அனுப்பப்படுகின்றன.
- **கர்சர்** — SQLite-இன் மறைமுகமான `call_logs.rowid`, ஒவ்வொரு இலக்கிற்கும்
  `log_export_destinations.cursor_row_id`-இல் நிலையாகச் சேமிக்கப்படுகிறது. `timestamp` திட்டமிட்டே கர்சராகப் பயன்படுத்தப்படவில்லை: அழைப்பாளர்கள்
  தங்கள் சொந்த மதிப்பை வழங்கக்கூடும்; எனவே பின்னர் தொடங்கிய வேகமான கோரிக்கைக்குப் பிறகு மெதுவான கோரிக்கை எழுதப்படலாம்,
  அப்போது நேரமுத்திரை கர்சர் அதைத் தவறவிடும்.
- **தொகுப்பாக்கம்** — ஒரு கோரிக்கைக்கு `batch_size` வரிசைகள் (இயல்புநிலை 500), ஓர் இயக்கத்திற்கு `max_rows_per_run` வரிசைகள்
  (இயல்புநிலை 10000); இதனால் பெருமளவு தேங்கிய பதிவுகள் ஓர் இயக்கத்தைத் தடுக்காமல் பல இயக்க நேரங்களில் அனுப்பப்படுகின்றன.
- **வழங்கல்** — `send()` நிறைவடைந்த பிறகே கர்சர் முன்னேறும். ஒரு தொகுப்பு தோல்வியடைந்தால்
  கர்சர் இருந்த இடத்திலேயே இருக்கும்; எனவே அடுத்த இயக்கத்தில் அதே வரிசைகள் மீண்டும் முயற்சிக்கப்படும். வழங்கப்படும் உத்தரவாதம்
  குறைந்தபட்சம் ஒருமுறை வழங்கலுடன் இலக்குப் பக்க நகல் நீக்கமே அன்றி, உண்மையான துல்லியமாக ஒருமுறை வழங்கல் அல்ல: BigQuery ஒவ்வொரு
  வரிசைக்கும் அழைப்புப் பதிவு அடையாளத்தை விசையாகப் பயன்படுத்துகிறது; தனது நகல் நீக்கக் காலவரம்பிற்குள் அதை இயன்றவரை மதிக்கிறது.
- **ஒரே நேர இயக்கத் தடுப்பு** — cron இயக்கமும் `POST .../run`-உம் ஒரே நேரத்தில் தொடங்கலாம். ஏற்கெனவே
  பதிவுகளை அனுப்பிக்கொண்டிருக்கும் இலக்கு, இருமுறை அனுப்பப்படுவதற்குப் பதிலாகத் தவிர்க்கப்படும் (இயக்க முடிவில் `skipped: true`),
  எனவே ஒரே நேரத்தில் நடைபெறும் மற்றொரு இயக்கம் ஒரு தொகுப்பை மீண்டும் அனுப்பவோ கர்சரைப் பின்னோக்கி எழுதவோ முடியாது.
- **முழுநீக்கத்திலிருந்து மீட்பு** — `cursor_row_id`, `MAX(rowid)`-ஐவிட அதிகமாகிவிட்டால் (முழு அட்டவணையும்
  நீக்கப்பட்டு rowid-கள் மீண்டும் தொடங்கியிருந்தால்), இயக்கி நிரந்தரமாகப் பதிவுகளைக் காணத் தவறுவதற்குப் பதிலாக 0-க்குத் திரும்பும்.

### தனிமைப்படுத்தப்பட்ட இயக்கியும் வரம்புகளும்

Node-இல் ஒவ்வொரு இலக்கு இயக்கமும் தனித்த, குறுகிய கால OS துணைச் செயல்முறையைத் தொடங்குகிறது (IPC உடன் `child_process`,
`worker_threads` அல்ல). உள்ளடக்க வாசிப்புகள், payload JSON பகுப்பாய்வு/தொடராக்கம், இலக்கின்
`prepare()` மற்றும் இலக்கு வலைப்பின்னல் I/O அனைத்தும் அங்கேயே இயங்குகின்றன; சேவையகத்தின் நிகழ்வு வளையத்தில் அல்ல.
கட்டமைப்பும் சிறிய முன்னேற்றச் செய்திகளும் மட்டுமே IPC வழியாகக் கடக்கின்றன; ஏற்றுமதி செய்யப்பட்ட பதிவுகள் ஒருபோதும்
சேவையகத்திற்குத் திரும்புவதில்லை. cron பணியும் இப்போது இயக்கு வழியும் அதே பொது முடிவையும் ஒரே நேர இயக்கத் தடுப்பையும் தக்கவைக்கின்றன.

துணைச் செயல்முறை, சேவையகம் தீர்மானித்த `DATA_DIR/storage.sqlite`-ஐ `node:sqlite` மூலம் படிக்க மட்டும் திறக்கிறது;
`busy_timeout=5000` மற்றும் `query_only=ON` பயன்படுத்தப்படுகின்றன. அது எந்த DB singleton-ஐயும் இறக்குமதி செய்வதில்லை; எந்த
இடமாற்றங்களையோ, காப்புப்பிரதிகளையோ, SQLite புதுப்பிப்புகளையோ செய்வதில்லை. காணாமற்போன/சிதைந்த artifact-களுக்கான பதிவுப் பராமரிப்பு (சிதைந்த artifact-க்கான UPDATE உட்பட)
டாஷ்போர்டு விவரப் பாதையில் மட்டுமே தொடர்கிறது. இரு பாதைகளும் பக்கவிளைவற்ற ஒரே
விவரத் தீர்மானிப்பானைப் பகிர்கின்றன; ஏற்றுமதி ஒத்திசைவற்ற கோப்பு முறைமை வாசிப்புகளையும் அதே artifact → பழைய
உட்பொதிவு → பழைய வட்டு → எதுவுமில்லை என்ற தீர்மான வரிசையையும் பயன்படுத்துகிறது. துணைச் செயல்முறை தனது வாசிப்பானைத் திறக்கும்போது, ஓர் இயக்கம் அதிகபட்சச் செருகல் rowid-ஐ
நிலைப்படமாகப் பிடிக்கிறது; அதற்குப் பிந்தைய செருகல்கள் அடுத்த இயக்கம் வரை காத்திருக்கும். இது ஒரு செருகல்
எல்லையே அன்றி, நீண்ட கால SQLite பரிவர்த்தனை அல்ல: வலைப்பின்னல் காத்திருப்புகளின்போது WAL எழுதிகளும் சோதனைப்புள்ளிகளும் தடையின்றிச் செயல்படும்.
ஏற்கெனவே உள்ள வரிசைகளின் புதுப்பிப்புகள்/நீக்கங்கள் இந்த எல்லையால் உறையவைக்கப்படுவதில்லை.

ஏற்கப்பட்ட ஒவ்வொரு தொகுப்பிற்குப் பிறகும், துணைச் செயல்முறை ஒப்புகைக்காகக் காத்திருக்கும். சேவையகம் முதலில்
`advanceLogExportCursor` மூலம் கர்சரை நிலையாகச் சேமித்து, பின்னர் `ack` அனுப்புகிறது; அதற்கு முன் அடுத்த தொகுப்பு தொடங்காது.
அனுப்புதல் தோல்வி, செயலிழப்பு அல்லது காலக்கெடு முடிவு ஏற்பட்டால், அந்தத் தொகுப்பிற்கான கர்சரை முன்னேற்றாமல் தோல்வி பதிவுசெய்யப்படும். முன்பே
ஒப்புகை பெறப்பட்ட தொகுப்புகள் உறுதிசெய்யப்பட்டவையாகத் தொடரும்; அதிகபட்சமாக ஒப்புகை பெறாத அந்த ஒரு தொகுப்பு மட்டுமே மீண்டும் அனுப்பப்படலாம்.
`done` கிடைத்து துணைச் செயல்முறை சிக்கலின்றி வெளியேறிய பிறகே வெற்றி பதிவுசெய்யப்படும். தோல்விகள் துணைச் செயல்முறையை
SIGTERM மூலம் நிறுத்துகின்றன; 500 ms-க்குப் பிறகு SIGKILL-ஆகத் தீவிரப்படுத்துகின்றன; செயல்முறை முழுமையாக மூடப்படும் வரை இயக்கி காத்திருக்கும்.

| சூழல் மாறி                                    | இயல்புநிலை | நோக்கம்                                          |
| --------------------------------------------- | ---------- | ------------------------------------------------ |
| `OMNIROUTE_LOG_EXPORT_RUN_TIMEOUT_MS`         | 900000     | ஒவ்வொரு இலக்கிற்குமான மொத்த நேர வரம்பு           |
| `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB` | 1024       | துணைச் செயல்முறையின் V8 old-space வரம்பு, MB-இல் |

செல்லாத/நேர்மறையல்லாத/முழு எண்ணல்லாத மதிப்புகளுக்கு இயல்புநிலைகள் பயன்படுத்தப்படும். heap அமைப்பு மொத்த
RSS வரம்பல்ல; மிகப் பெரிய தொகுப்புகள் துணைச் செயல்முறையின் நினைவகத்தைத் தீர்த்துவிட்டு, இயக்கத்தைப் பாதுகாப்பாகத் தோல்வியடையச் செய்யக்கூடும்.
1024 MB இயல்புநிலை, உள்ளடக்கங்கள் இயக்கப்பட்ட நிலையில் 512 KiB artifact-களைக் கொண்ட இயல்புநிலை 500-வரிசைத் தொகுப்பிற்கு,
BigQuery-இன் பைட் துண்டுகளாகப் பிரிக்கப்பட்ட JSON தொடராக்கம் உட்பட, கூடுதல் இடத்தை வழங்குகிறது. இது
உள்ளடக்கங்களுடன் கூடிய 10000-வரிசைத் தொகுப்பைப் பாதுகாப்பானதாக்காது. V8 heap தீர்ந்துபோதல், நடவடிக்கை எடுக்கக்கூடிய தோல்வியைப் பதிவுசெய்கிறது: தொகுப்பின்
அளவைக் குறைக்கவும் அல்லது `OMNIROUTE_LOG_EXPORT_CHILD_MAX_OLD_SPACE_MB`-ஐ உயர்த்தவும்; கர்சர் கடைசியாக
ஒப்புகை பெறப்பட்ட தொகுப்பிலேயே இருக்கும். பழைய உட்பொதிந்த/வட்டில் உள்ள உள்ளடக்கங்களுக்கு நவீன artifact அளவு வரம்பு பொருந்தாது.
இயக்குநர்கள் RSS-க்குத் தனியாக வள ஒதுக்கீட்டைத் திட்டமிட வேண்டும்; குறிப்பாக நினைவக வரம்புள்ள கொள்கலன்களுக்குள்.

துணைச் செயல்முறை, தீர்மானிக்கப்பட்ட `DATA_DIR`, `NODE_ENV`, வெளிப்படையாக அமைக்கப்பட்ட `TZ` (பழைய கோப்புப்பெயர்களின்
உள்ளூர் நேரத் தீர்மானம்), இருந்தால் `ELECTRON_RUN_AS_NODE`, மற்றும் பின்வரும் வெளிச்செல்லும் உள்ளீடுகளை மட்டுமே பெறுகிறது:
`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (மற்றும் அவற்றின் சிற்றெழுத்து வடிவங்கள்),
`OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`.
உலகளாவிய Undici dispatcher, சேவையகத்தின் சூழல் மாறிகளை மட்டுமே சார்ந்த proxy தீர்மானத்தையும் உள்ளூர் ஹோஸ்ட்
விலக்கு விதிகளையும், `NO_PROXY` உட்பட, பகிர்கிறது; அது `proxyFetch.ts` அல்லது அதன் DB/அம்சக் கொடிகளை இறக்குமதி செய்வதில்லை.
அனுப்பப்படும் வெளியீட்டிலும் பதிவுசெய்யப்படும் பிழைகளிலும் proxy சான்றுத் தகவல்கள் மறைக்கப்படுகின்றன. இலக்குச் சான்றுத் தகவல்கள்
ஒரே தொடக்க IPC செய்தியில் மட்டுமே அனுப்பப்படுகின்றன; argv அல்லது சூழல் மாறிகளில் ஒருபோதும் அனுப்பப்படுவதில்லை; வெளியீடு/பிழை அனுப்புதலுக்கு
முன்னொட்டு சேர்க்கப்பட்டு, உணர்திறன் மிக்க தகவல்கள் நீக்கப்படுகின்றன. ஒவ்வொரு cron இயக்கத்திலும் Node-இன் SQLite எச்சரிக்கை
மீண்டும் வருவதைத் தவிர்க்க, துணைச் செயல்முறையின் இயக்க மதிப்புருக்களில் `ExperimentalWarning` மட்டும் முடக்கப்படுகிறது; பிற எச்சரிக்கை வகைகள் தொடர்ந்து காட்டப்படும்.

இலக்குத் தொகுதிகள் Next.js/server-only சார்புகள் இல்லாமல் இறக்குமதி செய்யக்கூடியதாக இருக்க வேண்டும். தற்போதைய
BigQuery செயலாக்கம் ஏற்கெனவே அந்த ஒப்பந்தத்தைப் பூர்த்தி செய்கிறது. அணுகல் டோக்கன் தற்காலிகச் சேமிப்புகள் துணைச் செயல்முறையின்
இயக்கத்திற்கு மட்டுமே நீடிக்கும்; இயக்கங்களுக்கு இடையே நீடிப்பதில்லை. Node தான் ஆதரிக்கப்படும் இயக்கச் சூழல் (`package.json` engines), ஆனால் README-இன் Bun
நிறுவல் பகுதியும் `Dockerfile.bun`-உம் `bun:sqlite` (`src/lib/db/core.ts` / அடாப்டர்கள்) பயன்படுத்தும்
உற்பத்திச் சூழலுக்கான இணக்கப் பாதையையும் குறிப்பிடுகின்றன. எனவே Bun-இல், ஏற்றுமதிகள் முந்தைய
அதே செயல்முறைக்குள் இயங்கும் பாதையைத் தக்கவைத்து, ஒருமுறை எச்சரிக்கையை வெளியிடுகின்றன: துணைச் செயல்முறைக்கான heap/நேரவரம்புத் தனிமைப்படுத்தல் கிடைக்காது.
நிகழ்வு வளையம் மற்றும் OOM தனிமைப்படுத்தலுக்கு Node-ஐப் பயன்படுத்தவும்; இங்கே Bun மேம்பாட்டுப் பயன்பாட்டுக்கு மட்டுமானதாகக் கருதப்படுவதில்லை.

`includeBodies` இயக்கப்பட்டிருக்கும்போது, மணிநேர அளவிலான தரவுச் சுமை நிலுவையைக் குவிப்பதற்குப் பதிலாக
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` போன்ற நிமிட அளவிலான இடைவெளியைத் தேர்ந்தெடுக்கவும்.
தொகுதி மற்றும் வரி வரம்புகள் ஒவ்வொரு இயக்கத்தையும் தொடர்ந்து கட்டுப்படுத்துகின்றன. ஒவ்வொரு இயக்கத்திலும் ஒவ்வொரு இலக்கிற்கும் செயல்முறை தொடக்கச் செலவு ஏற்படுகிறது;
இது சேவையக நிகழ்வு வளையத் தனிமைப்படுத்தலுக்காகச் சிறிய தொடக்கச் செலவை ஏற்கிறது; மொத்த CPU பயன்பாட்டைக் குறைப்பதற்காக அல்ல.

### தரவுச் சுமைகள் (தூண்டுரைகள் மற்றும் நிறைவுகள்)

இயல்பாக, பதிவுகளின் **பட்டியல்** காட்டும் சுருக்கப் புலங்களை மட்டுமே ஏற்றுமதி கொண்டிருக்கும்.
**தூண்டுரைகள் மற்றும் பதில்களை ஏற்றுமதி செய்** (`includeBodies`) என்பதை இயக்கினால், ஒவ்வொரு அழைப்பிற்கும் பதிவுகளின் **விவரப்**
பலகம் காட்டும் தகவல்களும் கூடுதலாக அனுப்பப்படும்:

| புலம்                            | அது கொண்டிருப்பது                                                    |
| -------------------------------- | -------------------------------------------------------------------- |
| `request_body` / `response_body` | கட்டுப்பாட்டுப் பலகத்தில் காட்டப்படும் அழைப்புத் தரவுச் சுமைகள்      |
| `pipeline_route_decision`        | வழிச்செலுத்தி தேர்ந்தெடுத்த இலக்கும் மாதிரியும்                      |
| `pipeline_client_request`        | கிளையன்ட் அனுப்பியபடியே உள்ள மூலக் கோரிக்கை                          |
| `pipeline_openai_request`        | உள் OpenAI வடிவத்திற்கு மாற்றிய பிறகான கோரிக்கை                      |
| `pipeline_provider_request`      | வழங்குநரின் வடிவத்தில், மேல்நிலைக்கு உண்மையில் அனுப்பப்பட்ட கோரிக்கை |
| `pipeline_provider_response`     | மூல மேல்நிலைப் பதில்                                                 |
| `pipeline_client_response`       | அழைப்பாளருக்குத் திருப்பி வழங்கப்பட்டது                              |
| `pipeline_error`                 | தோல்வியடைந்த அழைப்பிற்கான pipeline-நிலைப் பிழை விவரம்                |
| `bodies_truncated`               | மேலுள்ள ஏதேனும் புலம் `maxBodyBytes` வரம்பை எட்டும்போது True         |

இது தூண்டுரை உள்ளடக்கம் என்பதால், **இயல்பாக முடக்கப்பட்டுள்ளது**; மேலும், திட்டமிட்டே ஒவ்வொரு இலக்கிற்குமான தனித் தேர்வாக உள்ளது.
கட்டுப்பாட்டுப் பலகத்தில் காட்டப்படுவதே அனுப்பப்படுகிறது, ஏனெனில் ஏற்றுமதியும் `getCallLogById`-உம் ஒரே விவரத்
தீர்மானத்தைப் பகிர்கின்றன: தரவுச் சுமைகள்
எழுதப்படும்போதே தனிநபர் அடையாளத் தகவல்கள் நீக்கப்பட்டு, இரகசியங்கள் மறைக்கப்படுகின்றன; மேலும்,
`noLog` API விசையைக் கொண்டு செய்யப்படும் அழைப்பு எந்தத் தரவுச் சுமையையும் சேமிப்பதில்லை, எனவே ஏற்றுமதி செய்ய எதுவும் இருப்பதில்லை.

தரவுச் சுமைகள் கோப்பு முறைமைச் சேமிப்புப் பொருளிலிருந்து ஒவ்வொரு வரியாகப் படிக்கப்படுகின்றன; எனவே அவற்றைக் கோரிய
இலக்குகளுக்கு மட்டுமே முழுத் தரவு நிரப்புதல் நடைபெறும். சேமிப்புப் பொருள் இல்லாவிட்டாலோ சிதைந்திருந்தாலோ, தொகுதியைத் தோல்வியடையச் செய்து
கர்சரை முன்னேற முடியாமல் விடுவதற்குப் பதிலாக, null தரவுச் சுமைகளுடன் அதன் சுருக்கம் ஏற்றுமதி செய்யப்படும்.

`maxBodyBytes` (இயல்புநிலை 262144) ஒவ்வொரு புலத்தையும் வரம்பிடுகிறது. நீளமான தரவுச் சுமைகள் **கைவிடப்படுவதற்குப் பதிலாக
வெட்டிச் சுருக்கப்படுகின்றன** — வெட்டப்பட்ட தூண்டுரைகூட "என்ன கேட்கப்பட்டது" என்பதற்குப் பதிலளிக்கிறது — மேலும் அந்த வரி
`bodies_truncated` மூலம் குறிக்கப்படுகிறது. ஸ்ட்ரீமில் துண்டு துண்டாக வரும் மாற்றங்கள் ஏற்றுமதி செய்யப்படுவதில்லை; ஒருங்கிணைக்கப்பட்ட பதில்
ஏற்கெனவே `pipeline_provider_response` மற்றும் `pipeline_client_response` ஆகியவற்றில் உள்ளது.

## 3. REST API

அனைத்து வழித்தடங்களுக்கும் மேலாண்மை அங்கீகாரம் தேவை (`requireManagementAuth`). ரகசியங்கள் ஒருபோதும் திருப்பி அனுப்பப்படுவதில்லை:
சேமிக்கப்பட்ட ரகசியம் `__stored__` என்ற நேரடி மதிப்பாகத் திருப்பி அனுப்பப்படும்; புதுப்பிக்கும்போது அந்த மதிப்பைத் திருப்பி அனுப்பினால்
சேமிக்கப்பட்ட நற்சான்று தக்கவைக்கப்படும்.

ரகசியத்தை அறிவிக்கும் வகையைச் சேர்ந்த இலக்கை உருவாக்க அல்லது புதுப்பிக்க **`STORAGE_ENCRYPTION_KEY`
தேவை**. அது இல்லாமல் `encrypt()` எந்த மாற்றமும் செய்யாமல் உள்ளீட்டை அப்படியே அனுப்பிவிடும்; எனவே நற்சான்றை
SQLite-இல் சாதாரண உரையாகச் சேமிப்பதற்குப் பதிலாக, எழுதும் செயல் 400 பிழையுடன்
நிராகரிக்கப்படும் (Telegram webhook பயன்படுத்தும் அதே பாதுகாப்பு).

## 4. BigQuery இலக்கு

உள்ளமைவு விசைகள் (`type: "bigquery"`):

| விசை                 | குறிப்புகள்                                                                                     |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| `projectId`          | தரவுத்தொகுப்பைக் கொண்டுள்ள GCP திட்டம்                                                          |
| `datasetId`          | `[A-Za-z0-9_]+`                                                                                 |
| `tableId`            | `[A-Za-z0-9_]+`                                                                                 |
| `location`           | தரவுத்தொகுப்பை உருவாக்க வேண்டியிருக்கும்போது மட்டுமே பயன்படுத்தப்படும் (இயல்புநிலை `EU`)        |
| `serviceAccountJson` | சேவைக் கணக்கு விசை. ரகசியமானது: சேமிப்பில் மறைகுறியாக்கப்படும், ஒருபோதும் திருப்பியளிக்கப்படாது |
| `autoCreate`         | முதல் ஏற்றுமதியின்போது தரவுத்தொகுப்பையும் அட்டவணையையும் உருவாக்கும் (இயல்புநிலை `true`)         |

சேவைக் கணக்கிற்கு இலக்கு அட்டவணையில் `bigquery.tables.updateData` அனுமதியும்,
`autoCreate` இயக்கப்பட்டிருக்கும்போது `bigquery.datasets.create` / `bigquery.tables.create` அனுமதிகளும் தேவை.

உள்ளமைக்கப்பட்ட தொகுதி என்பது **கர்சர்** அலகு; HTTP அலகு அல்ல: `send()` அதை அதிகபட்சம் 500 வரிகளைக் கொண்ட insertAll
அழைப்புகளாகப் பிரிக்கிறது. எனவே பெரிய `batch_size` மதிப்பால் BigQuery-இன் 10 MB கோரிக்கை வரம்பை மீற முடியாது.
தற்காலிக நிலைக் குறியீடுகளுக்கு (408/429/500/502/503/504), அதே insertIds-ஐ மீண்டும் பயன்படுத்தி, அதிவேகமாக அதிகரிக்கும்
காத்திருப்பு இடைவெளியுடன் மூன்று முறை வரை மீண்டும் முயற்சிக்கப்படும்; அங்கீகாரம் மற்றும் தரவுக்கட்டமைப்பு தோல்விகள், செயலோட்டத்தை
வீணடிப்பதற்குப் பதிலாக முதல் முயற்சியிலேயே விதிவிலக்கை எழுப்பும்.

சற்றுமுன் உருவாக்கப்பட்ட அட்டவணை ஸ்ட்ரீமிங் முனையத்திற்கு இன்னும் புலப்படாது; அது சில வினாடிகளுக்கு
404 பதிலை வழங்கும். அந்த 404-க்கு மீண்டும் முயற்சிக்கப்படும், ஆனால் **இந்தச் செயலோட்டமே அட்டவணையை உருவாக்கியிருந்தால் மட்டுமே** —
உண்மையிலேயே இல்லாத அட்டவணை உடனடியாகத் தோல்வியடையும். சமீபத்தில் நீக்கப்பட்ட பெயரில் அட்டவணையை
மீண்டும் உருவாக்கினால், BigQuery பல நிமிடங்களுக்கு ஸ்ட்ரீமிங் செருகல்களை மறுக்கும் என்பதை நினைவில் கொள்ளவும்; இது
நீக்கிவிட்டு மீண்டும் உருவாக்குவதன் இயல்பு. எனவே அட்டவணையை நீக்கி மீண்டும் சேர்ப்பதற்குப் பதிலாகப் புதிய அட்டவணைப் பெயரைப் பயன்படுத்தவும்.

**பகுதியளவு தோல்வி, காலியாக இல்லாத `insertErrors[]` உடன் HTTP 200 ஆக வரும்.** அது
தோல்வியாகக் கருதப்பட்டு விதிவிலக்கை எழுப்பும்; இதுவே BigQuery ஏற்றுக்கொள்ளாத வரிகளைத் தாண்டி கர்சர்
முன்னேறுவதைத் தடுக்கிறது; `tests/unit/log-export-bigquery.test.ts` இந்த நடத்தையை உறுதிப்படுத்துகிறது.

பரிமாற்றம் சாதாரண REST வழியாக நடைபெறுகிறது — சுயமாகக் கையொப்பமிடப்பட்ட RS256 உறுதிச்சான்று,
`https://oauth2.googleapis.com/token` முகவரியில் அணுகல் டோக்கனாக மாற்றப்படுகிறது; பின்னர் வரிகள் `tabledata.insertAll`-க்கு அனுப்பப்படுகின்றன. Google SDK எதுவும்
சேர்க்கப்படுவதில்லை. ஒவ்வொரு (சேவைக் கணக்கு, அனுமதி வரம்பு) இணைக்கும் அணுகல் டோக்கன்கள் செயல்முறைக்குள் தற்காலிகமாகச் சேமிக்கப்படுகின்றன.

உருவாக்கப்படும் அட்டவணையில் பதிவுகள் தாவலின் ஒவ்வொரு புலத்திற்கும் ஒரு நெடுவரிசையும், கூடுதலாக `exported_at` நெடுவரிசையும் இருக்கும். அழைப்புப் பதிவுகள்
உண்மையில் எவ்வாறு வினவப்படுகின்றன என்பதற்கேற்ப அதன் அமைப்பு இருக்கும்:

- **`timestamp` அடிப்படையில் நாள் வாரியாகப் பகுக்கப்படும்**, எனவே தேதியால் வரையறுக்கப்பட்ட வினவல் அந்த நாட்களை மட்டுமே ஸ்கேன் செய்யும்.
- **`api_key_name`, `provider`, `model`, `status` அடிப்படையில் கிளஸ்டர் செய்யப்படும்** (அதே வரிசையில்), எனவே
  அதை இயக்கியவர், அது சென்ற இடம் அல்லது அது தோல்வியடைந்ததா என்பவற்றின் அடிப்படையில் வடிகட்டுவது ஒவ்வொரு பகுப்பிலும் உள்ள தொகுதிகளை ஸ்கேன் செய்வதிலிருந்து விலக்கும். BigQuery
  அதிகபட்சம் நான்கு கிளஸ்டரிங் நெடுவரிசைகளை அனுமதிக்கிறது; அவற்றின் வரிசை முக்கியமானது: `api_key_name` மட்டும் கொண்ட வடிகட்டி
  தொகுதிகளை விலக்கும்; `status` மட்டும் கொண்ட வடிகட்டி அவ்வாறு செய்யாது.
- **விருப்பத்தேர்வான பகுப்பு தக்கவைப்புக் காலம்**, `partitionExpirationDays` வழியாக (0 அனைத்தையும் தக்கவைக்கும்), அட்டவணை
  உருவாக்கப்படும்போது பயன்படுத்தப்படும்.

இரண்டு அமைப்புகளும் உருவாக்கும் நேரத்தில் பயன்படுத்தப்படும். ஏற்கெனவே உள்ள அட்டவணை அதன் தற்போதைய அமைப்பையே தக்கவைக்கும். எனவே
இவற்றைப் பயன்படுத்த விரும்பினால், இலக்கைப் புதிய அட்டவணை அடையாளத்திற்கு அமைக்கவும்.

`tests/unit/log-export-bigquery.test.ts`, மேப்பரும் அட்டவணையின் தரவுக்கட்டமைப்பும் ஒத்திசைவில் இருப்பதை
உறுதிப்படுத்துகிறது. எனவே ஏற்றுமதியின்போது புதிய அழைப்புப் பதிவு நெடுவரிசை எதுவும் கவனிக்கப்படாமல் விடுபட முடியாது.

தொகுதிகள் வரிகளின் எண்ணிக்கை மற்றும் வரிசையாக்கப்பட்ட பைட்டுகள் **இரண்டின்** அடிப்படையிலும் பிரிக்கப்படுகின்றன. பேலோடுகள் ஏற்றுமதி செய்யப்படும்போது
வரிகளின் எண்ணிக்கை மட்டும் போதாது: பிராம்ப்ட்களைக் கொண்ட 500 வரிகள் பல பத்து மெகாபைட்டுகளாக இருக்கலாம்; மேலும் insertAll,
10 MB-க்கு அதிகமான கோரிக்கையை நிராகரிக்கும். 500 வரிகள் அல்லது 9 MB ஆகியவற்றில் எது முதலில் எட்டப்படுகிறதோ, அப்போது துண்டு நிறைவு செய்யப்படும்.

## 5. OTLP/HTTP தடங்களுக்கான இலக்கு

கட்டமைப்பு `type: "otlp-http"` என்பதைப் பயன்படுத்துகிறது. இது சேமிக்கப்பட்ட அழைப்புப் பதிவுகளை
அட்டவணைப்படி, கர்சர் அடிப்படையில் ஏற்றுமதி செய்யும் அமைப்பாகும்;
`open-sse/services/routing/otel.ts` இல் உள்ள, இயன்றவரை நேரடி வழித்தட நிகழ்வுகளைப் பெறும் அமைப்பு அல்ல.
அந்த அமைப்பின் சூழல் மாறிகள், நேரக்கணிப்பான்கள் அல்லது இடையகங்களை இது படிப்பதோ மாற்றுவதோ இல்லை.
இரண்டையும் இயக்குவது தனித்தனியான இரண்டு வகை ஸ்பான்களை உருவாக்கலாம்;
இந்த அழைப்புப் பதிவு ஸ்பான்களை வேறுபடுத்திக் காண `omniroute.log-export` கருவியமைப்பு வரம்பைப் பயன்படுத்தவும்.

பொதுவான கண்காணிப்புப் பலகம் இந்தப் புலங்களைக் காட்டுகிறது. `paths` ஒரு API அணியையோ,
புதிய வரிகள்/காற்புள்ளிகளால் பிரிக்கப்பட்ட துல்லியமான பாதைகளைக் கொண்ட உரைப்பகுதியையோ ஏற்கிறது.
வெளிப்படையாக அனுமதிக்கப்படாத வரை embeddings, rerank மற்றும் பிற பாதைகள் தவிர்க்கப்படும்.
தவிர்க்கப்பட்ட வரிகளும் கர்சரை முன்னேற்றும்; ஏற்கப்பட்ட ஸ்பான்களை எண்ணுவதற்குப் பதிலாக,
தற்போதைய இயக்கியின் `exported`/`exportedTotal` எண்ணிகள், வடிகட்டப்பட்ட வரிகள் உட்பட
செயலாக்கப்பட்ட மூல வரிகளை எண்ணுகின்றன. துணைச் செயலாக்கத்தின் IPC/கர்சர் ஒப்பந்தத்தை மாற்றாமல்,
அதற்குள்ளேயே வடிகட்டல் செய்யப்படுகிறது.

URL சரிபார்ப்பு, `src/shared/network/outboundUrlGuard.ts` இல் உள்ள, தரவுத்தளத்தைச் சாராத
`parseAndValidateNonMetadataUrl` உதவிச் செயல்பாட்டைப் பயன்படுத்துகிறது: `block-metadata` கொள்கை.
தனிப்பட்ட URL-கள் அனுமதிக்கப்பட்ட webhook சரிபார்ப்பியைப் போலவே,
நிபந்தனையற்ற மீத்தரவு/நெறிமுறை/உட்பொதிக்கப்பட்ட நற்சான்று சோதனைகள் இதிலும் உள்ளன;
ஆனால் உலகளாவிய அம்சக் கொடி மீறல் இல்லாமலேயே localhost/LAN இலக்குகளை இது வேண்டுமென்றே அனுமதிக்கிறது.
இது தனிப்பட்ட HTTP முனைப்புள்ளிகள் உட்பட, சுயமாக நிறுவி இயக்கப்படும் Langfuse, Phoenix, Tempo மற்றும் Collector
முனைப்புள்ளிகளைப் பயன்படுத்த அனுமதிக்கிறது. கிளவுட் மீத்தரவு ஹோஸ்ட்கள் எப்போதும் தடுக்கப்படும்.
திசைமாற்றங்கள் பின்தொடரப்படுவதில்லை; எனவே ஒரு collector நற்சான்றுகளை வேறொரு ஹோஸ்டுக்குத் திசைமாற்ற முடியாது.
தற்போதைய சொல்வடிவ அடிப்படையிலான URL பாதுகாப்பைப் போலவே, இது DNS தீர்மானத்தை நிலைநிறுத்துவதில்லை;
இயக்குநரின் கட்டுப்பாட்டில் உள்ள ஹோஸ்ட்களை மட்டுமே கட்டமைக்கவும்.
முனைப்புள்ளி நம்பகமான பிணையத்தில் இல்லாதபோது HTTPS-ஐ முன்னுரிமையாகப் பயன்படுத்தவும்.

### தரவுத்தொகுப்பும் அனுப்புதலும்

OTLP/HTTP JSON (`ExportTraceServiceRequest`, `Content-Type: application/json`), அனுமதிக்கப்பட்ட
ஒவ்வொரு வரிக்கும் ஒரு CLIENT ஸ்பானை எடுத்துச் செல்கிறது; அதன் பெயர் அந்த வரியின் துல்லியமான கோரிக்கைப் பாதையாக இருக்கும்.
ஸ்பான் பெயரில் மாதிரி அல்லது அடையாளத் தரவை உட்பொதிக்காமல், பாதை அடிப்படையிலான பெயரிடல்
Chat Completions, Responses மற்றும் Messages ஆகியவற்றை வேறுபடுத்துகிறது.
வளப் பண்புகளில் `service.name` மற்றும் தொகுப்பின் `service.version` ஆகியவை அடங்கும்.

வழக்கமான அரட்டை முயற்சிப் பதிவி (`open-sse/handlers/chatCore/attemptLogging.ts`), நிறைவடையும் போது
`duration = Date.now() - startTime` என்பதை எழுதுகிறது; நேரமுத்திரையை வழங்குவதில்லை;
`src/lib/usage/callLogs.ts` இல் உள்ள `saveCallLogOperation`, நேரமுத்திரையின் இயல்புநிலையாக
எழுதப்படும் (நிறைவடையும்) நேரத்தை அமைக்கிறது. எனவே ஏற்றுமதி, முடிவு = வரியின் நேரமுத்திரை என்றும்
தொடக்கம் = முடிவு − காலஅளவு என்றும் அமைக்கிறது
(மில்லிவிநாடிகள், தசம நானோவிநாடிகளாக மாற்றப்படும்). அழைப்பாளர் வழங்கும் வரலாற்று நேரமுத்திரைகளும்
முடிவு நேரமாகவே தக்கவைக்கப்படுகின்றன; ஒவ்வொரு வரிக்கும் தொடக்கம்/நிறைவு என்பதை வேறுபடுத்தும் குறியீடு இல்லை.
null காலஅளவு பூஜ்ஜியமாகும். செல்லாத/விடுபட்ட நேரமுத்திரைகள், நிர்ணயிக்க முடியாத ஸ்பான்களை உருவாக்குவதற்குப்
பதிலாகத் தொகுதியைத் தோல்வியடையச் செய்யும். `ttftMs` null ஆக இருக்கலாம்; அது `omniroute.ttft_ms` உடன் பொருத்தப்படுகிறது.

பண்புகளில் `gen_ai.operation.name="chat"`, வழங்குநர், கோரப்பட்ட/பதிலளித்த மாதிரி,
உள்ளீட்டு/வெளியீட்டு டோக்கன்கள், விருப்பத்திற்குரிய தற்காலிகச் சேமிப்பு வாசிப்பு/உருவாக்கம்/பகுத்தறிவு டோக்கன்கள்,
HTTP நிலை, சேர்க்கை, தற்காலிகச் சேமிப்பின் மூலம், அமர்வுக் குறிச்சொல் மற்றும் தொடர்பு அடையாளம் ஆகியவை அடங்கும்.
முழுஎண் OTLP மதிப்புகளும் நேரமுத்திரைகளும் தசமச் சரங்களாக இருக்கும்; சரங்கள், பூலியன்கள் மற்றும் பின்ன எண்கள்
அவற்றுக்குரிய இயல்பான OTLP மதிப்பு வகைகளைப் பயன்படுத்துகின்றன. பிழை ஸ்பான்களில் ERROR நிலையும்,
உணர்திறன் தகவல்கள் நீக்கப்பட்ட நிலைச் செய்தியும் இருக்கும். நியமப் பதிவில் மேல்நிலை ஹோஸ்ட் URL இல்லை;
எனவே collector-ஐ மாதிரிச் சேவையகமாகத் தவறாக அடையாளப்படுத்துவதற்குப் பதிலாக `server.address` தவிர்க்கப்படுகிறது.
செலவு ஏற்றுமதி செய்யப்படுவதில்லை.

`includeBodies=true` மட்டுமே உள்ளடக்கத்தை நிரப்புகிறது. `langfuseMapping=false` ஆக இருக்கும்போது,
`gen_ai.input.messages` / `gen_ai.output.messages` ஆகியவை, மறுவடிவமைக்கப்பட்ட semconv
செய்திகள் அணிக்குப் பதிலாக, OmniRoute சேமித்தபடியான, உணர்திறன் தகவல்கள் நீக்கப்பட்ட கோரிக்கை/பதில்
உள்ளடக்க JSON-ஐ எடுத்துச் செல்கின்றன (பகுத்தறிய முடிந்தால் நியம வடிவமாக்கப்படும்).
வெட்டப்பட்ட/JSON அல்லாத உள்ளடக்கங்கள் மூல உரையாகவே இருக்கும். `langfuseMapping=true` ஆக இருக்கும்போது,
உள்ளடக்கங்கள் `langfuse.observation.input` / `langfuse.observation.output` ஆக மட்டுமே வெளியிடப்படும்;
ஒவ்வொரு உள்ளடக்கமும் ஒருமுறை மட்டுமே அனுப்பப்படுவதற்காக `gen_ai.*.messages` பண்புகள் தவிர்க்கப்படுகின்றன.
இரண்டு முறைகளும் தற்போதைய உள்ளடக்க நிரப்பல் பாதையிலிருந்து `maxBodyBytes` மதிப்பைப் பெறுகின்றன;
`omniroute.bodies_truncated=true` என்பது வெட்டப்பட்டதைக் குறிக்கிறது.
இந்த இலக்கு கூடுதல் செயலாக்கத் தொடர் நிலைப்படங்களையோ, உணர்திறன் தகவல்கள் நீக்கப்படாத தரவுப் பொருள் வாசிப்புகளையோ சேர்ப்பதில்லை.
உள்ளடக்கங்களை ஏற்றுமதி செய்யும்போது, மணிநேர நிலுவையைச் சேர்ப்பதற்குப் பதிலாக,
`OMNIROUTE_LOG_EXPORT_CRON="*/5 * * * *"` போன்ற நிமிட அளவிலான இடைவெளியைப் பயன்படுத்தவும்.

உறை உட்பட, கோரிக்கைகள் 500 span-கள் மற்றும் 4 MiB UTF-8 JSON அளவுக்குள் கட்டுப்படுத்தப்படுகின்றன.
ஒரு cursor தொகுதியின் முதல் கோரிக்கைக்கு முன், அனுமதிக்கப்பட்ட ஒவ்வொரு span-இன் அளவும் சரிபார்க்கப்படுகிறது. தனிப்பட்ட
span ஒன்று வரம்பைவிடப் பெரிதாக இருந்தால், அந்தத் தொகுதியின் எந்தப் பகுதியும் அனுப்பப்படாது; மேலும்
`maxBodyBytes` மதிப்பைக் குறைக்குமாறு வழிகாட்டுதலுடன் தோல்வியடையும்; அது அறிவிப்பின்றி கைவிடப்படாது. முன்சோதனை பதிவுக் குறிப்புகளையும்
பைட் எண்ணிக்கைகளையும் மட்டுமே வைத்துக்கொண்டு, ஒவ்வொரு தற்காலிக span/JSON-ஐயும் நீக்குகிறது; தொகுதியின் தொடராக்கப்பட்ட இரண்டாவது நகலை
வைத்திருப்பதற்குப் பதிலாக, வரம்புக்குட்பட்ட துண்டுகளுக்காக span-கள் மீண்டும் உருவாக்கப்படுகின்றன. HTTP 408/429/5xx, பிணையத் தோல்விகள் மற்றும் நேரமுடிவுகளுக்கு அதிகபட்சம்
மூன்று முயற்சிகள் செய்யப்படுகின்றன; 250/500 ms அடுக்குக்குறி இடைவெளி பயன்படுத்தப்படுகிறது. `Retry-After` வினாடிகள் அல்லது HTTP தேதிகள்
தாமதத்தை 5 வினாடிகள் வரை நீட்டிக்கலாம். பிற நிலைகள் உடனடியாகத் தோல்வியடைகின்றன. OTLP 2xx பகுதி நிராகரிப்பும்,
இழந்த span-ஐ ஏற்றுக்கொண்டதாக உறுதிப்படுத்துவதற்குப் பதிலாக பிழையை எழுப்புகிறது; வெற்று அல்லது செல்லுபடியான JSON ஏற்பு உறுதிப்படுத்தல்கள் ஏற்றுக்கொள்ளப்படுகின்றன;
பதிலைப் படிப்பதற்கான வரம்பு 64 KiB ஆகும்.

பிழைகளில் ஏற்றுமதியாளருக்குச் சொந்தமான தகவல்கள் மட்டுமே இருக்கும்: HTTP நிலை, மறுமுயற்சி வகை, முயற்சிகள் மற்றும் அனுப்பப்பட்ட span
எண்ணிக்கைகள், அல்லது ஏற்பு உறுதிப்படுத்தல்/பிணையத் தோல்விக்கான நிலையான வாசகங்கள். சேகரிப்பானின் பதில் உடல்கள்,
பகுதி வெற்றி எண்ணிக்கைகள் மற்றும் பதில் தலைப்புகள் ஒருபோதும் பிழைகள், பதிவுகள் அல்லது
கண்காணிப்புப் பலகையில் நகலெடுக்கப்படுவதில்லை. தோல்வியடைந்த அல்லது பகுதியாக ஏற்றுக்கொள்ளப்பட்ட தொகுதிக்கு ஏற்பு உறுதிப்படுத்தல் வழங்கப்படாது: சேருமிடம்
அந்த நிலையுடன் தோல்வியடைவதாகக் காட்டும், cursor கடைசியாக ஏற்பு உறுதிப்படுத்தப்பட்ட தொகுதியிலேயே இருக்கும், அடுத்த இயக்கம்
அதே வரிசைகளை மீண்டும் அனுப்பும். சேகரிப்பான் அல்லது உள்ளமைவு
சரிசெய்யப்படும் வரை நிரந்தர நிலைகள் தொடர்ந்து தோல்வியடையும். பதில் விவரங்களுக்கு சேகரிப்பானின் சொந்தப் பதிவுகளைப் பயன்படுத்தவும். அழைப்புப் பதிவுப் பிழைச் சுருக்கங்கள்
அவற்றுக்கான தனித்த மறைப்புச் செயல்முறையைத் தொடர்ந்து பயன்படுத்துகின்றன.
`prepare()` எதையும் உருவாக்கி வழங்காது; சோதனை துல்லியமாக `{"resourceSpans":[]}` என்பதை அனுப்பி,
அழைப்புப் பதிவு span-களை எழுதாமல் HTTP நிலையைத் தெரிவிக்கும்.

Trace id-களும் span id-களும் முறையே
`"omniroute.trace\\0" + callLogId` மற்றும் `"omniroute.span\\0" + callLogId` ஆகியவற்றின் SHA-256 மதிப்பின் முதல் 32/16 பதினாறும அக்கங்களாகும். மீண்டும் அனுப்பப்படுபவை
அதே id-களைக் கொண்டிருக்கும். இது நகல் நீக்கத்திற்கான உத்தரவாதமல்ல: Langfuse
v4 ingestion உள்ளிட்ட சில பின்தளங்கள், ஒரே id கொண்ட span-களின் நகல்களை நீக்குவதில்லை. செயலிழப்பு அல்லது பகுதி துண்டுத் தோல்வி ஏற்பட்டால்,
ஏற்பு உறுதிப்படுத்தப்படாத ஒரே ஒரு cursor தொகுதி மட்டுமே அதிகபட்சமாக மீண்டும் அனுப்பப்படலாம்; அந்த முழுத் தொகுதியும் நகலாகலாம்,
அதன் கடைசி HTTP துண்டு மட்டும் அல்ல. இந்தச் சமரசத்தைக் கருத்தில் கொண்டு cursor தொகுதியின் அளவைத் தேர்வுசெய்யவும்.

### Langfuse எடுத்துக்காட்டு

சுயமாக வழங்கப்படும் Langfuse அமைப்பிற்கு இந்தப் புலங்களை உள்ளமைக்கவும்:

```json
{
  "endpoint": "https://langfuse.example.com/api/public/otel/v1/traces",
  "headers": "Authorization: Basic <base64-of-public-key:secret-key>",
  "serviceName": "omniroute",
  "langfuseMapping": true,
  "identity": "pseudonymous",
  "environment": "production"
}
```

`public-key:secret-key` என்ற நேரடி சரத்தின் Base64 வடிவமாக Authorization மதிப்பை உள்ளூரிலேயே உருவாக்கவும்
(எடுத்துக்காட்டாக `Buffer.from(publicKey + ":" + secretKey).toString("base64")` மூலம்).
உண்மையான சான்றுகளைப் பதிவுகள், திரைப்பிடிப்புகள் அல்லது சிக்கல் அறிக்கைகளில் ஒட்ட வேண்டாம். பொருத்தமைவு தானாகவே
`x-langfuse-ingestion-version: 4` என்பதை அமைக்கிறது; Authorization தொடர்ந்து `headers` இல் வழங்கப்படுகிறது.
தலைப்புகளும் உருவாக்கப்படும் அடையாள salt-உம் ஏற்கெனவே உள்ள மறையாக்கப்பட்ட இரகசியப் புல
வழிமுறையையும் API இடநிரப்பிகளையும் பயன்படுத்துகின்றன; `STORAGE_ENCRYPTION_KEY` தேவை.

பொருத்தமைவு உருவாக்க வகை/மாதிரி, JSON பயன்பாட்டு விவரங்கள் (உள்ளீடு/வெளியீடு/மொத்தம் மற்றும் கிடைக்கும்
தற்காலிகச் சேமிப்பு விசைகள்), JSON உள்ளீடு/வெளியீட்டுப் படப்பதிவுகள், ERROR/DEFAULT நிலை, சுத்திகரிக்கப்பட்ட நிலைச் செய்தி,
trace பெயர், அமர்வு id, விருப்பச் சூழல் மற்றும் வழங்குநர், கோரப்பட்ட மாதிரி, பாதை, சேர்க்கை, தற்காலிகச் சேமிப்பு
மூலம் மற்றும் நிலை ஆகியவற்றிற்காக வடிகட்டக்கூடிய `langfuse.observation.metadata.<key>` ஆகியவற்றைச் சேர்க்கிறது.
TTFT தெரிந்திருந்து, கால அளவுக்குள் இருந்தால் மட்டுமே `langfuse.observation.completion_start_time`,
தொடக்கம் + TTFT நேரத்தை ISO 8601 வடிவில் கொண்டிருக்கும். செலவுப் பண்புகள் எதுவும் அனுப்பப்படுவதில்லை.

அடையாள முறைகள் `langfuse.user.id` க்குப் பொருந்தும்:

- `pseudonymous` (இயல்புநிலை): ஒவ்வொரு சேருமிடத்திற்குமான சீரற்ற
  32-பைட் salt-ஐப் பயன்படுத்தி API விசையின் உள் id-க்கு கணக்கிடப்படும் HMAC-SHA256. உருவாக்கும்போது salt இல்லாவிட்டால் அது உருவாக்கப்பட்டு,
  `identitySalt` ஆக மறையாக்கப்படும்; ஒருபோதும் திருப்பி வழங்கப்படாது; திருத்தங்களின்போது தக்கவைக்கப்படும். மூல விசை id-கள் ஒருபோதும்
  span பண்புகளில் சேர்க்கப்படுவதில்லை. சேருமிடத்தின் salt-ஐ மீண்டும் உருவாக்குவது/மாற்றுவது அடையாளங்களை மாற்றும்.
- `keyName`: உள்ளமைக்கப்பட்ட API விசைப் பெயர்; இது அந்த இயக்குநர் பெயரடையாளத்தை நோக்கத்துடன் வெளிப்படுத்துகிறது.
- `none`: பயனர் id இல்லை. அமர்வுக் குறிச்சொற்கள் இருந்தால் அவை தொடர்ந்து ஏற்றுமதி செய்யப்படும்; இந்த முறைகள்
  தன்னிச்சையான prompt உள்ளடக்கத்தையோ இயக்குநர் வழங்கிய அமர்வு/தொடர்புறுத்தல் பெயரடையாளங்களையோ அநாமதேயமாக்குவதில்லை.

### பழைய பதிவுகளை நிரப்பாமல் தொடங்குதல்

உருவாக்கும்போது மட்டும், **தற்போதைய நிலையிலிருந்து தொடங்கு (ஏற்கெனவே உள்ள பதிவுகளைத் தவிர்)** என்பதை இயக்கவும் அல்லது
உருவாக்கும் API தரவுச் சுமையின் மேல் நிலையில் `startFromCurrentPosition: true` என்பதை வழங்கவும். இது ஏற்கெனவே உள்ள cursor
உதவிச் செயலிகளைப் பயன்படுத்தி, இடமாற்றமின்றி, `cursor_row_id` ஐ தற்போது தக்கவைக்கப்பட்டுள்ள அழைப்புப் பதிவுகளின் அதிகபட்ச rowid ஆக
தொடக்கநிலைப்படுத்துகிறது. இயல்புநிலை false ஆகும் (cursor 0 மற்றும் தக்கவைக்கப்பட்ட வரலாற்றுப் பதிவுகளின் நிரப்புதல்).
இது புதுப்பிக்கும்போது cursor-ஐ மீட்டமைப்பதற்கான அமைப்பு அல்ல.

பகிரப்பட்ட `ttftMs` சேர்த்தல், BigQuery பொருத்தியிலும்
புதிய அட்டவணை கட்டமைப்பிலும் null மதிப்பை அனுமதிக்கும் `ttft_ms` நெடுவரிசையையும் சேர்க்கிறது: அதன் கட்டமைப்புச் சோதனை, ஒவ்வொரு நியமப் பதிவுப் புலத்திற்கும் ஒரு
நெடுவரிசை இருக்க வேண்டும் எனக் கோருகிறது. ஏற்கெனவே உள்ள அட்டவணைகள் மாற்றமின்றி தொடர்ந்து ஏற்றுமதி செய்யும்: `prepare()` அட்டவணைக் கட்டமைப்பைப் படித்து,
அந்த நெடுவரிசை இல்லாதபோது `ttft_ms` ஐ மட்டும் தவிர்க்கிறது. அடுத்த இயக்கத்தில் TTFT-ஐப் பெற null மதிப்பை அனுமதிக்கும் INT64 நெடுவரிசையைச்
சேர்க்கவும் அல்லது புதிய அட்டவணையைப் பயன்படுத்தவும். PATCH, தானியங்கிக் கட்டமைப்பு மாற்றம் அல்லது கூடுதல்
அனுமதிகள் தேவையில்லை; மற்ற எல்லா வரிசைப் புலங்களுக்கும் கடுமையான கட்டமைப்புச் சரிபார்ப்பு தொடரும்.

## 6. ஒரு இலக்கைச் சேர்த்தல்

1. `LogExportDestinationType` ஒன்றை ஏற்றுமதி செய்யும் `src/lib/logExport/destinations/<name>.ts` கோப்பை உருவாக்கவும்:
   ஒரு Zod `configSchema`, UI-க்கான `fields` விவரிப்பான் வரிசை, `secretFields`, மற்றும்
   `test()` / `prepare()` / `send(records)` ஆகியவற்றைத் திருப்பியளிக்கும் `createClient(config)`.
2. அதை `src/lib/logExport/registry.ts` கோப்பிலுள்ள `DESTINATIONS` வரிசையில் சேர்க்கவும்.
3. `tests/unit/` என்பதன் கீழ் சோதனைகளை எழுதவும்.

மாற்றம் அவ்வளவுதான்: நிலையான சேமிப்பு, cron பணி, REST அடுக்கு, ரகசியத் தகவல் குறியாக்கம் மற்றும்
கட்டுப்பாட்டுப் பலகைப் படிவம் ஆகிய அனைத்தும் பதிவகத்தைப் படிக்கின்றன.

புதிய இலக்கிற்கான இரண்டு விதிகள்:

- பகுதியளவு தோல்வி ஏற்பட்டால் `send()` **கட்டாயம் விதிவிலக்கை எழுப்ப வேண்டும்**. வெற்றிகரமாக நிறைவடைவது என்பது "இலக்கில் இந்த வரிசைகள் உள்ளன"
  என்பதைக் குறிக்கும்; சுட்டி அவற்றைக் கடந்து நிரந்தரமாக முன்னேறும்.
- பயனர் வழங்கும் URL-ஐ ஏற்கும் இலக்கு, அதிலிருந்து தரவைப் பெறுவதற்கு முன்,
  webhook-கள் செய்வதைப் போலவே `parseAndValidateWebhookUrl` (`src/shared/network/outboundUrlGuardPolicy.ts`) மூலம் அதைச் சரிபார்க்க வேண்டும்.
  BigQuery-க்கு இது தேவையில்லை: அதன் ஹோஸ்ட்கள் மாறிலிகள்.

## 7. இதை இயக்குதல்

- **கட்டுப்பாட்டுப் பலகை**: ஒருங்கிணைப்புகள் → பதிவேடு ஏற்றுமதி. ஓர் இலக்கைச் சேர்த்து, வரிசைகளை எழுதாமல்
  சான்றுகளைச் சரிபார்க்க **சோதனை** என்பதை இயக்கி, பின்னர் அதைச் செயல்படுத்தவும்.
- **நிலுவைத் தொகுப்பு**: ஒவ்வொரு இலக்கு அட்டையும் நிலுவையிலுள்ள வரிசைகளையும் சுட்டியையும் காட்டும்; `GET
/api/log-export/status` அதே எண்ணிக்கைகளுடன் கடைசி 20 பணி இயக்கங்களையும் திருப்பியளிக்கும்.
- **ஓர் இலக்கின் தோல்வி மற்றவற்றைத் தோல்வியடையச் செய்யாது** — இயக்கச் சுருக்கம் ஒவ்வொரு இலக்கின்
  நிலையையும் `last_status` / `last_error` ஆகியவற்றில் பதிவு செய்கிறது; பணி இயக்க வரலாறு ஒட்டுமொத்த நிலையை வைத்திருக்கும்.
- **ஓர் இலக்கை நீக்குவது அதன் சுட்டியையும் நீக்கும்.** அதை மீண்டும் சேர்த்தால், தக்கவைக்கப்பட்டுள்ள மிகப் பழைய
  அழைப்புப் பதிவிலிருந்து தொடங்கும்; இதனால் இலக்கில் ஏற்கெனவே இருக்கக்கூடிய வரிசைகள் மீண்டும் அனுப்பப்படும். BigQuery-இல், ஒவ்வொரு வரிசையின்
  `insertId` இதை BigQuery-இன் சொந்த நகல் நீக்க நேர வரம்பிற்குள் மட்டுமே கையாளும்; எனவே இலக்கை
  நீக்குவதற்குப் பதிலாக முடக்குவதை விரும்பத்தக்கதாகக் கொள்ளவும்.
