## च्याट कम्प्लिसन्स

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### अनुकूलन हेडरहरू

| हेडर                     | दिशा        | विवरण                                                                                                                                                                                                                                     |
| ------------------------ | ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | अनुरोध      | क्यासलाई बाइपास गर्न `true` मा सेट गर्नुहोस्                                                                                                                                                                                              |
| `x-omniroute-no-memory`  | अनुरोध      | यस अनुरोधका लागि मेमोरी + सीप इन्जेक्सन छोड्न `true` मा सेट गर्नुहोस् (नो-क्यासको व्यवहारसँग मेल खान्छ; प्रत्येक कलमा लाग्ने टोकन/लागतको अतिरिक्त भारबाट बचाउँछ)                                                                          |
| `X-OmniRoute-Progress`   | अनुरोध      | प्रगति घटनाहरूका लागि `true` मा सेट गर्नुहोस्                                                                                                                                                                                             |
| `X-Session-Id`           | अनुरोध      | बाह्य सत्र एफिनिटीका लागि स्टिकी सत्र कुञ्जी                                                                                                                                                                                              |
| `x_session_id`           | अनुरोध      | अन्डरस्कोर भेरियन्ट पनि स्वीकार गरिन्छ (प्रत्यक्ष HTTP)                                                                                                                                                                                   |
| `X-OmniRoute-Session-Id` | अनुरोध      | कलकर्ताले उपलब्ध गराएको सत्र/वार्तालाप ट्याग (मेमोरीमा पनि पठाइन्छ)। उपलब्ध हुँदा, प्रतिसत्र लागत निर्धारणका लागि `call_logs.session_tag` मा जस्ताको तस्तै स्थायी रूपमा भण्डारण गरिन्छ (#8249) — अनुपस्थित हुँदा कहिल्यै संश्लेषण गरिँदैन |
| `Idempotency-Key`        | अनुरोध      | डिडुप कुञ्जी (5s समयावधि)                                                                                                                                                                                                                 |
| `X-Request-Id`           | अनुरोध      | वैकल्पिक डिडुप कुञ्जी                                                                                                                                                                                                                     |
| `x-omniroute-connection` | अनुरोध      | एकल-मोडेल अनुरोधलाई त्यसको id प्रयोग गरी एउटा प्रदायक कनेक्सन (खाता) मा पिन गर्नुहोस् — [प्रत्येक अनुरोधका लागि खाता पिनिङ](#account-pinning-per-request) हेर्नुहोस्                                                                      |
| `X-OmniRoute-Cache`      | प्रतिक्रिया | `HIT` वा `MISS` (नन-स्ट्रिमिङ)                                                                                                                                                                                                            |
| `X-OmniRoute-Idempotent` | प्रतिक्रिया | डिडुप्लिकेट गरिएको भए `true`                                                                                                                                                                                                              |
| `X-OmniRoute-Progress`   | प्रतिक्रिया | प्रगति ट्र्याकिङ सक्रिय भए `enabled`                                                                                                                                                                                                      |
| `X-OmniRoute-Session-Id` | प्रतिक्रिया | OmniRoute ले प्रयोग गरेको प्रभावकारी सत्र ID                                                                                                                                                                                              |
| `X-OmniRoute-Request-Id` | प्रतिक्रिया | अनुरोध सहसम्बन्ध id (थाहा भएको अवस्थामा)                                                                                                                                                                                                  |
| `X-OmniRoute-Version`    | प्रतिक्रिया | OmniRoute बिल्ड संस्करण (सधैँ उपलब्ध)                                                                                                                                                                                                     |
| `X-OmniRoute-Cost-Saved` | प्रतिक्रिया | HIT हुँदा क्यासले जोगाएको USD (क्यास हिटहरूमा मात्र)                                                                                                                                                                                      |
| `X-OmniRoute-Decision`   | प्रतिक्रिया | राउटिङ ट्रेस: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` कम्बो रणनीति हो, वा नन-कम्बो अनुरोधका लागि `single`) — पूर्णता प्रतिक्रियाहरूमा सधैँ उपलब्ध हुन्छ                                                             |

> Nginx नोट: यदि तपाईं अन्डरस्कोर हेडरहरूमा निर्भर हुनुहुन्छ (उदाहरणका लागि `x_session_id`), भने `underscores_in_headers on;` सक्षम गर्नुहोस्।

#### प्रत्येक अनुरोधका लागि खाता पिनिङ

जब कुनै प्रदायकसँग धेरै कनेक्सनहरू (खाता वा कुञ्जीहरू) हुन्छन्, OmniRoute ले सामान्यतया आफ्नो खाता-चयन रणनीतिमार्फत एउटा चयन गर्छ। यसको सट्टा, अनुरोधले `x-omniroute-connection` हेडर प्रयोग गरेर कुनै एउटा विशिष्ट कनेक्सन पिन गर्न सक्छ:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **id कहाँ फेला पार्ने।** ड्यासबोर्डमा प्रदायकको पृष्ठ खोल्नुहोस्
  (**ड्यासबोर्ड → प्रदायकहरू → <प्रदायक>**) र कनेक्सनको पङ्क्तिमा रहेको `xxxxxxxx…` id चिपमा क्लिक गर्नुहोस्
  — यसले पूर्ण कनेक्सन id प्रतिलिपि गर्छ।
- **कुन अनुरोधहरूले यसलाई मान्छन्।** `/v1/chat/completions`, `/v1/messages` र
  `/v1/responses` मा एकल-मोडेल अनुरोधहरू (`provider/model`)। कम्बोहरूले हेडरलाई बेवास्ता गर्छन्: यसको सट्टा
  प्रत्येक कम्बो चरणका लागि त्यस चरणकै कनेक्सनमार्फत खाता पिन गर्नुहोस्।
- **पिन प्राथमिकता मात्र नभई कडा नियम हो।** पिन गरिएको कनेक्सन मात्र विशेष रूपमा प्रयोग गरिन्छ।
  अनुरोधभित्रको विफलताले खाताको कूलडाउन अभिलेख गर्छ, तर उही प्रदायकको अर्को
  खातामा **रोटेट गर्दैन**।
- **कूलडाउन र कोटाले पिन हटाउँछन्।** पिन गरिएको कनेक्सन कूलडाउनमा हुँदा,
  कोटा सकिएको वा कोटा नीतिद्वारा रोकिएको अवस्थामा, पछिल्ला अनुरोधहरू प्रदायकका
  अन्य कनेक्सनहरूमा फर्कन्छन्, ठ्याक्कै पिन नगरिएको ट्राफिकजस्तै।
- **अज्ञात वा असक्षम गरिएका id हरू विफल हुन्छन्।** प्रदायकको सक्रिय पूलमा नभएको id (मेटाइएको,
  निष्क्रिय पारिएको वा अर्को प्रदायकसँग सम्बन्धित) ले कुनै योग्य खाता बाँकी राख्दैन, त्यसैले अनुरोध
  चुपचाप अन्यत्र रुट हुनुको सट्टा विफल हुन्छ।

Claude Code ले `ANTHROPIC_CUSTOM_HEADERS` मार्फत अनुकूलन हेडरहरू पठाउँछ। यसलाई
`~/.claude/settings.json` को `env` ब्लकमा राख्नुहोस्, वा प्रत्येक परियोजनाका लागि फरक
खाता पिन गर्न परियोजना-स्तरीय `.claude/settings.json` मा राख्नुहोस्:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

स्रोत: `src/sse/handlers/chat.ts` (हेडर पढ्ने), `src/sse/services/auth.ts` र
`src/sse/services/sessionAffinityPin.ts` (पिन हटाउने र पूलमा नभएको जाँच)।

> **लागत टेलिमेट्री हेडरहरू:** नन-स्ट्रिमिङ सफल प्रतिक्रियाहरूमा `X-OmniRoute-*` लागत-टेलिमेट्री सेट पनि हुन्छ — `X-OmniRoute-Response-Cost` (USD, निश्चित 10 दशमलव स्थान; निःशुल्क/मूल्य निर्धारण नगरिएकाका लागि `0.0000000000`), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit`, र `X-OmniRoute-Fallback-Attempts` (> 0 हुँदा मात्र), साथै `X-OmniRoute-Request-Id` र `X-OmniRoute-Version`। यी च्याट कम्प्लिसनहरू, `/v1/responses`, `/v1/messages`, **र मिडिया एन्डपोइन्टहरूबाट पनि** उत्सर्जित हुन्छन् — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations`, र `/v1/moderations` (लागत सधैँ `0`)। मूल्य निर्धारण उपलब्ध हुँदा मिडिया लागत प्रत्येक मोडालिटीअनुसार (प्रति-छवि, प्रति-सेकेन्ड, प्रति-क्यारेक्टर, प्रति खोज-एकाइ) गणना गरिन्छ, अन्यथा `0` (फेल-ओपन)।

> **क्यास-हिट लागतको अर्थ:** सिमान्टिक-क्यास HIT (`X-OmniRoute-Cache-Hit: true`) हुँदा कुनै अपस्ट्रिम कल गरिँदैन, त्यसैले `X-OmniRoute-Response-Cost` को मान `0.0000000000` हुन्छ (हिट प्रदान गर्दाको **वृद्धिशील** लागत)। मूल/हुन सक्ने लागतलाई `X-OmniRoute-Cost-Saved` मा छुट्टै रिपोर्ट गरिन्छ। बिलिङ उपभोक्ताहरूले `X-OmniRoute-Response-Cost` को योग गर्नुपर्छ (हिटमा कुनै लागत लाग्दैन); क्यास एनालिटिक्सले `X-OmniRoute-Cost-Saved` लाई समग्रित गर्न सक्छ।

## विशेष व्यवस्थापित सत्र लिजहरू

विशेष व्यवस्थापित सत्र लिजिङ एक स्वैच्छिक, क्लाइन्ट-निरपेक्ष राउटिङ सम्झौता हो: एउटा सक्रिय मालिकले
एउटा योग्य OmniRoute जडान ओगट्छ। यसले कुनै मोडेल लिजमा दिँदैन, OAuth आवश्यक पार्दैन, कुनै
विशेष क्लाइन्ट पहिचान गर्दैन, वा कुनै विशेष प्रदायक आवश्यक पार्दैन।

प्रमाणीकरण गर्ने API कुञ्जीसँग `lease:exclusive` स्कोप र स्पष्ट रूपमा गैर-रिक्त
`allowedConnections` सूची हुनुपर्छ। डेटाबेस म्युटेसन सीमाले कुञ्जी सिर्जना र आंशिक अद्यावधिकहरूमा
दुवै फिल्डलाई सँगै लागू गर्छ।

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

सफल प्राप्ति, नवीकरण, र विमोचन प्रतिक्रियाहरूले टाइमस्ट्याम्पहरू, `state`, र ठ्याक्कै सकारात्मक
`generation` देखाउँछन्, तर चयन गरिएको जडान वा प्रमाणहरू कहिल्यै देखाउँदैनन्। नवीकरण र विमोचनले
JSON बडीमा जेनेरेसन उपलब्ध गराउँछन्:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

एक सक्रिय लिज मालिकले आफ्नो हालको बाइन्डिङका लागि गोपनीयता-सुरक्षित प्रदर्शन मेटाडेटा स्पष्ट रूपमा अनुरोध गर्न सक्छ:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

यो स्वैच्छिक स्थिति कार्य अपारदर्शी मालिक, प्रमाणीकृत व्यवस्थापित API कुञ्जी, र ठ्याक्कै
सक्रिय जेनेरेसनद्वारा एउटै डेटाबेस ट्रान्ज्याक्सनमा सुरक्षित गरिएको हुन्छ। `displayName` केवल ट्रिम गरिएको कन्फिगर गरिएको
जडान नाम हो; कुनै सुरक्षित कन्फिगर गरिएको नाम नभएमा यो `null` हुन्छ। OmniRoute ले कहिल्यै पनि
इमेल वा उत्पन्न गरिएको खाता पहिचान प्रतिस्थापन गर्दैन। प्रदायक मान गैर-संवेदनशील प्रदर्शन लेबल हो र कहिल्यै पनि
उत्पन्न गरिएको मिल्दो-प्रदायक पहिचायक हुँदैन। प्रमाणहरू, टोकनहरू, कुकीहरू, कच्चा जडान वा API
कुञ्जी आईडीहरू, मालिक ह्यासहरू, फेन्सिङ गोप्य मानहरू, र आन्तरिक राउटिङ डेटा समावेश गरिँदैनन्।

गलत-कुञ्जी, गलत-मालिक, पुरानो-जेनेरेसन, हराएको, म्याद सकिएको, विमोचित, र अमान्य बनाइएका लुकअपहरू सबैले
जडान मेटाडेटाबिना एउटै `409 LEASE_FENCE_STALE` त्रुटि फर्काउँछन्। क्षमता-प्रतीक्षा प्रतिक्रिया प्राप्त गरेको क्लाइन्टसँग निरीक्षण गर्न कुनै सक्रिय बाइन्डिङ हुँदैन। राउटिङले सक्रिय लिजलाई अर्को जडानमा सार्दा,
उही जेनेरेसन मान्य रहन्छ र स्थितिले पुरानो होइन, नयाँ बाइन्डिङलाई परमाणविक रूपमा फर्काउँछ।
प्राप्ति, नवीकरण, विमोचन, र प्रतीक्षा प्रतिक्रियाहरूले आफ्ना अघिल्ला संरचनाहरू कायम राख्ने भएकाले
विद्यमान क्लाइन्टहरू अपरिवर्तित रहन्छन्।

यो सर्भर सम्झौताले मानक OpenAI Codex `/status` परिवर्तन गर्दैन। मानक Codex ले हाल आफ्नो
मोडेल प्रदायक र अन्तर्निर्मित प्रमाणीकरण/खाता अवस्था रिपोर्ट गर्छ, तर स्वेच्छाचारी अनुकूलन
प्रदायक खाता मेटाडेटा रेन्डर गर्दैन; पछिल्लो क्लाइन्ट एकीकरणले यो कार्य कल गर्नुपर्छ र
`connection.displayName` कसरी प्रदर्शन गर्ने भन्ने निर्णय गर्नुपर्छ।

त्यसपछि प्रत्येक व्यवस्थापित इन्फरेन्स अनुरोधले दुवै नियन्त्रण हेडर उपलब्ध गराउँछ:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

ठ्याक्कै मिल्ने मालिक, जेनेरेसन, सक्रिय जडान, र प्रमाणीकृत API कुञ्जीलाई प्रत्येक समर्थित
अपस्ट्रिम प्रयासभन्दा ठीक अगाडि फेन्स गरिन्छ। अर्को कुञ्जीसँग मालिक र जेनेरेसन पुनः प्रयोग गर्दा, त्यो कुञ्जीले
उही जडानलाई अनुमति दिए पनि प्रयास असफल हुन्छ। कच्चा मालिकहरू स्थायी रूपमा भण्डारण, लग, अनुरोध
स्न्यापसटमा कायम, वा अपस्ट्रिममा फर्वार्ड गरिँदैनन्।

अस्थायी प्रतिस्पर्धाले `Retry-After` सहित HTTP `429` र निम्न प्रतिक्रिया फर्काउँछ:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

यो प्रतिक्रियाको अर्थ केवल सामान्य योग्य सेट गैर-रिक्त थियो र प्रत्येक खाली उम्मेदवार
अर्को सक्रिय लिजद्वारा ओगटिएको थियो भन्ने हो। असमर्थित मोडेल/प्रदायकहरू, नीति बेमेल, कुलडाउन, कोटा,
स्वास्थ्य, र अन्य सामान्य योग्यता विफलताहरूले आफ्ना विद्यमान OmniRoute प्रतिक्रियाहरू कायम राख्छन्।

### `x-omniroute-compression`

कम्प्रेसन योजनाको प्रति-अनुरोध ओभरराइड। सर्वोच्च प्राथमिकता — यसले राउटिङ-कम्बो
ओभरराइड, सक्रिय प्रोफाइल, स्वतः-ट्रिगर, र प्यानलको पूर्वनिर्धारित विकल्पलाई उछिन्छ। मानहरू:

| मान           | प्रभाव                                                                                                             |
| ------------- | ------------------------------------------------------------------------------------------------------------------ |
| `off`         | यो अनुरोधका लागि कम्प्रेसन हुँदैन।                                                                                 |
| `default`     | प्यानलबाट प्राप्त पूर्वनिर्धारित प्रोफाइल (सक्रिय प्रोफाइललाई बेवास्ता गर्छ)। क्षययुक्त इन्जिनहरू बन्द नै रहन्छन्। |
| `safe`        | डिडुप र ह्वाइटस्पेस फोल्डिङ मात्र।                                                                                 |
| `allow-lossy` | सारांश र शैली पुनर्लेखनसहित यो अनुरोधका लागि अपरेटर योजना कायम राख्नुहोस्।                                         |
| `engine:<id>` | सक्षम हुँदा एउटा मात्र इन्जिन, जस्तै `engine:rtk`। उक्त इन्जिनका लागि प्रति-अनुरोध स्वैच्छिक सक्रियता।             |
| `<combo>`     | नामद्वारा पहिले मिलाइने (अक्षरको केसप्रति असंवेदनशील), त्यसपछि आईडीद्वारा मिलाइने नाम दिइएको कम्बो।                |

टिप्पणीहरू:

- अज्ञात मानहरूलाई बेवास्ता गरिन्छ (अनुरोध कहिल्यै अस्वीकार गरिँदैन); रिजोल्युसन सामान्य अपरेटर प्राथमिकतामा फर्कन्छ।
- धेरै कम्बोहरूले एउटै नाम साझा गर्छन् भने, निर्धारक मिलानका लागि कम्बोको **id** पठाउनुहोस्।
- `off` वा `default` नाम भएको कम्बोलाई नामद्वारा चयन गर्न सकिँदैन (ती किवर्डहरू पहिले व्याख्या गरिन्छन्); त्यस्तो कम्बोलाई यसको आईडीद्वारा सन्दर्भ गर्नुहोस्।
- मुख्य कम्प्रेसन स्विच कडा गेट हो: कम्प्रेसन विश्वव्यापी रूपमा असक्षम हुँदा, यो हेडरले त्यसलाई सक्षम गर्न सक्दैन।

लागू गरिएको योजना प्रतिक्रिया हेडरमा प्रतिध्वनित गरिन्छ:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

जहाँ `<source>` `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default`, वा `off` मध्ये एउटा हुन्छ।

## एम्बेडिङहरू

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

उपलब्ध प्रदायकहरू: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI।

क्याटलग ID हरू `provider/model` हुन् (उदाहरण: `jina-ai/jina-embeddings-v5-omni-small`)। रेजिस्ट्रीमा देखिने प्रदायकबिनाका Jina मोडेल ID हरू (उदाहरणका लागि `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) पनि रिजल्भ हुन्छन्। Jina embed/rerank/classify/segment ले पहिले ड्यासबोर्डका `jina-ai` क्रेडेन्सियलहरू प्रयोग गर्छन्; कुनै ड्यासबोर्ड कुञ्जी नभएको अवस्थामा मात्र `JINA_AI_API_KEY` फल्ब्याक हो। `jina-reader` कार्ड Reader / `r.jina.ai` का लागि मात्र हो (`POST /v1/web/fetch`) र यसले कहिल्यै एम्बेडिङ वा rerank सेवा दिँदैन।

मल्टिमोडल समर्थन जनाउने रेजिस्ट्री मोडेलहरूले प्रदायक-निरपेक्ष संरचित वस्तुहरू पनि अधिकतम 32 वटासम्म स्वीकार गर्छन्।
मिडिया वस्तुका प्रकारहरू `text`, `image`, `audio`, `video`, र `document` हुन्। तिनको मिडिया `source`
कि त `{"type":"url","url":"https://..."}` हुन्छ वा
`{"type":"base64","data":"...","media_type":"..."}` हुन्छ।

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`,
र family alias `jina-ai/jina-embeddings-v5-omni` → omni-small) ले Jina का नेटिभ
EmbeddingsV5Request डकुमेन्टहरू पनि स्वीकार गर्छ र तिनलाई `https://api.jina.ai/v1/embeddings` मा **जस्ताको तस्तै फर्वार्ड गर्छ**:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

नेटिभ `{ image | audio | video | pdf }` मान सार्वजनिक HTTPS URL, `data:` URI, वा कच्चा
base64 हुन सक्छ। OmniRoute ले ती वस्तुहरूलाई स्ट्रिङमा रूपान्तरण गर्दैन वा नेटिभ image URL हरू फेच गर्दैन — Jina ले
सार्वजनिक मिडिया आफैँ प्राप्त गर्छ। अतिरिक्त Jina फिल्डहरू (`task`, `normalized`, `truncate`, `embedding_type`)
फर्वार्ड गरिन्छन्। टेक्स्ट-मात्र Jina SKU हरूले अझै पनि गैर-टेक्स्ट डकुमेन्टहरू अस्वीकार गर्छन्।

सुरक्षा र ट्रान्सपोर्ट सीमाहरू:

- रिमोट मिडिया URL हरू सार्वजनिक HTTPS हुनुपर्छ। क्यानोनिकल `{type,source:url}` वस्तुहरू
  सर्भर-साइडमा फेच गरिन्छन् (रिडाइरेक्ट पुनःप्रमाणीकरण, टाइमआउट, आकार सीमा, सार्वजनिक DNS, कनेक्सन पिनिङ) र
  प्रदायकलाई कल गर्नुअघि इनलाइन गरिन्छन्। Jina-नेटिभ `{image:"https://..."}` वस्तुहरू उही सार्वजनिक-HTTPS जाँचपछि
  जस्ताको तस्तै फर्वार्ड गरिन्छन्; Jina ले URL फेच गर्छ।
- इनलाइन base64 मिडियाको सीमा प्रति वस्तु डिकोड गरिएको 8 MiB र सम्पूर्ण अनुरोधभरि डिकोड गरिएको 16 MiB हो।

प्रदायक रूपान्तरण (क्यानोनिकल वस्तुहरू कहिल्यै अपरिवर्तित रूपमा फर्वार्ड गरिँदैनन्):

- Jina मल्टिमोडल मोडेलहरू: प्रत्येक शीर्ष-स्तरीय वस्तु इनलाइन मिडियाका लागि data URI प्रयोग गर्दै एउटा modality-keyed वस्तु
  (`text` / `image` / `audio` / `video` / `pdf`) बन्छ; प्रत्येक
  शीर्ष-स्तरीय वस्तुका लागि एउटा भेक्टर।
- Gemini Embedding 2 family: एउटा शीर्ष-स्तरीय array, `content.parts` (`text` वा `inline_data`) सहितको एकल नेटिभ
  `models/{model}:embedContent` अनुरोध बन्छ।
- llama.cpp (`llama-cpp/<model>`, स्थानीय सर्भरले लोड गरेको कुनै पनि मोडेल): क्यानोनिकल `text` वस्तुहरू
  साधारण स्ट्रिङ बन्छन्, र `image` / `audio` / `video` प्रत्येक एउटा
  `{"content": [part]}` वस्तु बन्छन्, जसले इनलाइन डेटा सहित llama-server का chat content parts (`image_url`,
  `input_audio` जसको format `wav` / `mp3` / `flac` हुन्छ, `input_video`) प्रयोग गर्छ; प्रत्येक शीर्ष-स्तरीय
  वस्तुका लागि एउटा भेक्टर। सर्भर `--embedding --mmproj …` सहित चल्नुपर्छ; projector बिना यसले
  मिडिया आफैँ अस्वीकार गर्छ। `document` समर्थित छैन।
- स्पष्ट modality metadata नभएका अज्ञात/डाइनामिक मोडेलहरूले संरचित इनपुटलाई HTTP 400 सहित अस्वीकार गर्छन्।

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

असमर्थित मोडेल/modality संयोजनहरूले वस्तुलाई जबरजस्ती रूपान्तरण गर्नुको सट्टा HTTP 400 फर्काउँछन्। पुराना string/token अनुरोधहरूमा भएका non-input
extension फिल्डहरू अपरिवर्तित रूपमा पास भइरहन्छन्।

```bash
# सबै एम्बेडिङ मोडेलहरू सूचीबद्ध गर्नुहोस्
GET /v1/embeddings
```

## छवि सिर्जना

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

उपलब्ध प्रदायकहरूमा OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (स्थानीय), ComfyUI (स्थानीय) समावेश छन्।

`n` ले `data[]` मा `n` वटा छवि फर्काउँछ। जसका अपस्ट्रिम API ले प्रत्येक कलमा एउटा छवि फर्काउँछन्
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), ती प्रदायकहरूका लागि अधिकतम 4 वटा एकैपटक सञ्चालनमा रहने गरी `n` वटा छुट्टाछुट्टै अपस्ट्रिम कल गरिन्छ। स्थिर
`seed` लाई कल अनुक्रमणिकाअनुसार अफसेट गरिन्छ (`seed`, `seed + 1`, …), जसले गर्दा छविहरू फरक भए पनि
पुनरुत्पादनयोग्य रहन्छन्। `n` को अधिकतम सीमा 10 हो। कुनै पनि कल असफल भएमा सम्पूर्ण अनुरोध
असफल हुन्छ। फ्यान-आउट ढाँचाहरूको सूची
`open-sse/handlers/imageGeneration/fanOut.ts` मा रहेको `SINGLE_IMAGE_FANOUT_FORMATS` हो।

ZenMux ले विद्यमान API-key जडान पुनः प्रयोग गर्छ र `zenmux/` वा `zm/` उपसर्गहरू स्वीकार गर्छ:

- `zenmux/openai/gpt-image-2` ले ZenMux को OpenAI Images API प्रयोग गर्छ। विकल्पहरूमा `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background`, र `response_format` समावेश छन्।
- `zm/meta/muse-image-1.0` जस्ता अन्य प्रकाशकहरूले ZenMux को Vertex AI `:predict`
  एन्डपोइन्ट प्रयोग गर्छन्। `n` लाई `sampleCount`, `aspect_ratio` लाई `aspectRatio`, र `image_size`
  (`1K`, `2K`, `4K`) लाई `sampleImageSize` मा म्याप गरिन्छ। पिक्सेल `size` ले पक्ष अनुपात मात्र प्रदान गर्छ,
  सुनिश्चित पिक्सेल आयामहरू होइन। समर्थित अनुपात, रिजोल्युसन र सङ्ख्याहरू मोडेलअनुसार फरक हुन्छन्।
- `zm/inclusionai/ming-image-0.1-design` ले आफ्ना आयामहरू आफैँ चयन गर्छ। `size`,
  `aspect_ratio`, र `image_size` हटाउनुहोस्; स्पष्ट मानहरू दिएमा HTTP 400 फर्किन्छ। `output_format` मार्फत
  PNG, JPEG, र WebP अनुरोध गर्न सकिन्छ।

यो एकीकरणले पाठबाट छवि सिर्जना समर्थन गर्छ, सन्दर्भ-छवि सम्पादन होइन। Vertex को
आउटपुटलाई `data[].b64_json` मा सामान्यीकरण गरिन्छ; `response_format: "url"` ले अपस्ट्रिम
HTTPS URL वा छविका बाइटहरू मात्र उपलब्ध हुँदा base64 data URL फर्काउँछ। खाली/फिल्टर गरिएका आउटपुटहरूले
खाली सफलता फर्काउनुको सट्टा त्रुटि फर्काउँछन्। मोडेल पहुँच ZenMux खातामा निर्भर हुन्छ।
[ZenMux को Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) र
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image) हेर्नुहोस्।

```bash
# सबै छवि मोडेलहरूको सूची देखाउनुहोस्
GET /v1/images/generations
```

## कागजात OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` ले `provider/model` उपसर्गमार्फत OCR प्रदायक चयन गर्छ; प्रदायक नखुलाइएको मोडेल id (जस्तै
`mistral-ocr-latest`) यसको दर्ता गरिएको प्रदायकमा रिजल्भ हुन्छ, र `model` नदिइएमा पूर्वनिर्धारित रूपमा
Mistral (`mistral-ocr-latest`) प्रयोग हुन्छ। दर्ता गरिएका प्रदायकहरू (`open-sse/config/ocrRegistry.ts`):

| प्रदायक id                    | मोडेल id             | `model` मान                                                              | टिप्पणी                                                                                                             |
| ----------------------------- | -------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (वा प्रदायक नखुलाइएको `mistral-ocr-latest`) | सिंक्रोनस — एकल अपस्ट्रिम कलबाट प्रतिक्रिया सिधै फर्काइन्छ।                                                         |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                              | एसिंक्रोनस अपस्ट्रिम (`analyze` + पोल) — तल हेर्नुहोस्।                                                             |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                                  | सिंक्रोनस, Vertex AI को `openapi/chat/completions` साझेदार एन्डपोइन्टमार्फत — प्रमाणीकरण/URL का लागि तल हेर्नुहोस्। |

तीनवटै प्रदायकले समान Mistral-आकारको बडीमा प्रतिक्रिया दिन्छन्:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence पोल प्रवाह

Azure Document Intelligence को `analyze` API एसिंक्रोनस छ: प्रारम्भिक अनुरोधले बडीको सट्टा
`Operation-Location` हेडर फर्काउँछ, र नतिजाका लागि पोल गर्नुपर्छ। ह्यान्डलर
(`open-sse/handlers/ocr.ts`) ले उक्त URL लाई प्रत्येक सेकेन्डमा बढीमा 30 प्रयाससम्म पोल गर्छ, `ok` नभएको पोल प्रतिक्रिया वा `"failed"` स्थितिमा तुरुन्तै असफल हुन्छ (पोल जारी राख्दैन), र
प्रयास सीमा समाप्त भएपछि पनि सञ्चालन चलिरहेमा `504` फर्काउँछ। अन्तिम Azure प्रतिक्रियालाई
कलरलाई फर्काउनुअघि Mistral ले प्रयोग गर्ने समान `pages`/`markdown` संरचनामा सामान्यीकरण गरिन्छ,
त्यसैले क्लाइन्ट कोडले प्रदायकका लागि छुट्टै विशेष अवस्था सम्हाल्नु पर्दैन।

### Vertex AI DeepSeek OCR प्रमाणीकरण र एन्डपोइन्ट रिजोल्युसन

`vertex-deepseek-ocr` ले च्याट/छवि ट्राफिकका लागि OmniRoute ले पहिले नै समर्थन गर्ने उही Vertex AI प्रमाणीकरण
(`open-sse/executors/vertex.ts`) पुनः प्रयोग गर्छ: जडानको API key या त
Service Account JSON क्रेडेन्सियल हुन्छ (JWT-bearer प्रवाहमार्फत छोटो अवधिको OAuth access token सँग साटिने)
वा पहिले नै जारी गरिएको OAuth access token हुन्छ, जुन जस्ताको तस्तै प्रयोग गरिन्छ। अपस्ट्रिम एन्डपोइन्ट URL Vertex को
सामान्य `openapi/chat/completions` साझेदार एन्डपोइन्ट हो, जुन जडानको project र
region बाट निर्माण गरिन्छ — स्पष्ट `providerSpecificData.project`/`providerSpecificData.region` ले सधैँ प्राथमिकता पाउँछ;
अन्यथा project लाई Service Account JSON को `project_id` बाट निकालिन्छ र region
पूर्वनिर्धारित रूपमा `us-central1` हुन्छ। दुवै रिजोल्युसन `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) मा हुन्छन्, जसलाई
`handleOcr` मा पठाउनुअघि `src/app/api/v1/ocr/route.ts` ले प्रयोग गर्छ।

## मोडेलहरूको सूची

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ OpenAI ढाँचामा सबै च्याट, इम्बेडिङ र छवि मोडेलहरू + कम्बोहरू फर्काउँछ
```

### मोडेल id उपसर्गहरू (`?prefix=`)

धेरैजसो मोडेलहरू **प्रदायक उपसर्ग** अन्तर्गत उपलब्ध गराइन्छन्। तपाईंले कुन उपसर्ग प्राप्त गर्नुहुन्छ भन्ने कुरा
`MODELS_CATALOG_PREFIX_MODE` फिचर फ्ल्यागद्वारा नियन्त्रित हुन्छ, र क्वेरी प्यारामिटरमार्फत **प्रत्येक अनुरोधका लागि** ओभरराइड गर्न सकिन्छ — सबैका लागि सर्भर-व्यापी
सेटिङ परिवर्तन नगरी सफा सूची चाहने क्लाइन्टका लागि उपयोगी:

```bash
GET /v1/models?prefix=alias        # प्रत्येक मोडेलका लागि एउटा id — छोटो alias उपसर्ग
GET /v1/models?prefix=dual         # दुवै रूप (सर्भरको पूर्वनिर्धारित)
GET /v1/models?prefix=canonical    # पूरा provider-id उपसर्ग मात्र
```

| मोड         | उत्सर्जन                                                | टिप्पणीहरू                                                                                                                                                                                                |
| ----------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **र** `claude/claude-sonnet-4-6` | **पूर्वनिर्धारित।** दुवै id एउटै मोडेलमा रुट हुन्छन्; कुनै एक रूप हार्डकोड गरेका क्लाइन्ट कन्फिगहरूले काम गरिरहून् भनेर राखिएको हो। यसले क्याटलगको आकार लगभग दोब्बर बनाउँछ।                               |
| `alias`     | `cc/claude-sonnet-4-6`                                  | प्रत्येक मोडेलका लागि एउटा प्रविष्टि। छुट्टै alias नभएका प्रदायकहरूले पनि आफ्नो प्रविष्टि उत्सर्जन गर्छन्, त्यसैले केही पनि हराउँदैन।                                                                     |
| `canonical` | `claude/claude-sonnet-4-6`                              | पूरा provider-id उपसर्गअन्तर्गत प्रत्येक मोडेलका लागि एउटा प्रविष्टि। छुट्टै alias नभएका प्रदायकहरू (जस्तै `antigravity/…`, `agy/…`) ले पनि यहाँ आफ्नो एकल id उत्सर्जन गर्छन्, त्यसैले केही पनि हराउँदैन। |

`dual`-मोडको मिररलाई क्वेरी प्यारामिटरबिनै पनि पहिचान गर्न सकिन्छ: यसमा प्राथमिक id तर्फ सङ्केत गर्ने `parent`
फिल्ड हुन्छ।

मोडेल चयनकर्ता रेन्डर गर्ने क्लाइन्टहरूले `?prefix=alias` अनुरोध गर्नुपर्छ —
[OmniCopilot VS Code एक्सटेन्सन](../guides/VSCODE-COPILOT.md) ले यही गर्छ।

### खोज फिल्टरहरू (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` ले अप्ट-इन खोज फिल्टरहरू स्वीकार गर्छ। यीमध्ये कुनै पनि नभए प्रतिक्रिया
अपरिवर्तित रहन्छ। तिनले कलरले पहिल्यै देख्ने क्याटलगलाई साँघुरो बनाउँछन् (API-key अनुमतिहरू पहिले लागू हुन्छन्),
र ती OpenAI-शैलीको `limit` / `after` पेजिङअघि चल्छन्:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # सूचीबद्ध प्रत्येक क्षमता true हुनुपर्छ
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # क्याटलग `type`; यो नभएका पङ्क्तिहरू `chat` हुन्
GET /v1/models?q=sonnet&limit=10                           # id वा नाममा केस-असंवेदनशील मिलान
```

| प्यारामिटर    | मानहरू                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | गैर-ऋणात्मक पूर्णाङ्क, `context_length` सँग तुलना गरिन्छ                                            |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 वर्ण                                                                                          |

अज्ञात मान, वा गैर-ऋणात्मक पूर्णाङ्क नभएको `min_context` (उदाहरणका लागि `1.5`) ले
HTTP `400` फर्काउँछ र सन्देशमा मान्य मानहरू सूचीबद्ध हुन्छन्। कार्यान्वयन:
`src/app/api/v1/models/catalogFilters.ts`।

### मोडेलको छोटो सूची (`POST /v1/models/query`)

`POST /v1/models/query` ले `GET /v1/models` कै समान प्रमाणीकरण र प्रत्येक key का लागि समान दृश्यतासहित,
एउटै क्याटलगबाट छोटो र निर्धारणात्मक सूची फर्काउँछ:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

प्रत्येक फिल्ड वैकल्पिक हो। `capabilities` र `exclude` ले एरे वा अल्पविरामद्वारा छुट्याइएको स्ट्रिङ स्वीकार गर्छन्;
`max_output` लाई `max_output_tokens` सँग तुलना गरिन्छ। परिणामहरू पहिले `owned_by`, त्यसपछि `id` अनुसार क्रमबद्ध हुन्छन्।
`limit` को पूर्वनिर्धारित मान `20` हो र `100` भन्दा माथिका मानहरूलाई `100` मा सीमित गरिन्छ। अमान्य JSON, अज्ञात
फिल्ड वा अमान्य मानले HTTP `400` फर्काउँछ।

### व्यक्तिगत रूपमा लुकाइएका च्याट मोडेलहरू

आफ्नो प्रदायक पृष्ठमा **लुकाइएको** भनी चिन्ह लगाइएको मोडेललाई क्याटलगबाट हटाइन्छ र स्पष्ट रूपमा
अनुरोध गर्दा HTTP `404` / `model_not_found` सहित अस्वीकार गरिन्छ। जाँचले प्रदायक alias हरू, compatible-provider node उपसर्गहरू र
जडानका पूर्वनिर्धारित मानहरूसहित समाधान गरिएको प्रदायक र मोडेल प्रयोग गर्छ।
कम्बोले लुकाइएका लक्ष्यहरूलाई छोड्छ र दृश्य sibling प्रयोग गर्न सक्छ; कार्यान्वयनयोग्य लक्ष्य बाँकी नरहेमा
यसले उही त्रुटि कोड फर्काउँछ। लुकाइएको अवस्था हटाएपछि अर्को अनुरोधबाट प्रभावकारी हुन्छ।
छवि-मात्र दृश्यता ओभरराइडहरूले उही ID भएको च्याट मोडेललाई लुकाउँदैनन्।

यो व्यक्तिगत मोडेल सेटिङ
[मोडेल एक्सपोजर अनुमति/अस्वीकृति सूचीहरू](../routing/MODEL_EXPOSURE_LIST.md) भन्दा अलग छ, जसले स्पष्ट डिस्प्याच कायम राख्दै क्याटलग
विज्ञापन र स्वतः-रुटिङ उम्मेदवारहरू फिल्टर गर्छ। API-key मोडेल अनुमतिहरू स्वतन्त्र रूपमा लागू भइरहन्छन्।
पूर्वनिर्धारित क्याटलग उपसर्ग मोड `dual` नै रहन्छ।

### thinking-विहीन मोडेल भेरियन्टहरू

thinking-सक्षम Claude मोडेलहरूका लागि, `/v1/models` ले `claude-3-omniroute-no-thinking/` उपसर्ग भएको **thinking-विहीन** भेरियन्ट पनि उपलब्ध गराउँछ:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

यो id चयन गर्दा (जस्तै, सधैँ `thinking` ब्लक संलग्न गर्ने Claude Code कन्फिगरेसनमा), यो तर्क निष्क्रिय पारिएको वास्तविक `<provider>/<model>` मा पुनः समाधान हुन्छ — `/v1/messages` पथमा `thinking:{type:"disabled"}`, वा `/v1/chat/completions` पथमा `reasoning`/`reasoning_effort` फिल्डहरू हटाइन्छन्। यो भेरियन्ट सोचाइ समर्थन गर्ने **र** `disabled` लाई पालना गर्ने Claude-परिवारका मोडेलहरूका लागि मात्र सूचीबद्ध गरिन्छ (त्यसैले, उदाहरणका लागि, `disabled` अस्वीकार गर्ने adaptive-only मोडेलहरू समावेश गरिँदैनन्)। अपरेटरहरूले `ModelSpec.noThinkingAlias` मार्फत प्रत्येक मोडेलका लागि यो भेरियन्ट जबरजस्ती अन वा अफ गर्न सक्छन्।

## ElevenLabs अडियो उत्पादन

तपाईंको ElevenLabs API कुञ्जीसहित OmniRoute मा `elevenlabs` प्रदायक जडान कन्फिगर गर्नुहोस्।
क्लाइन्टहरूले आफ्नो **OmniRoute** कुञ्जी (`Authorization: Bearer $OMNIROUTE_API_KEY`) मार्फत प्रमाणीकरण गर्छन्;
गेटवेले भण्डारण गरिएको प्रदायक कुञ्जीलाई `xi-api-key` का रूपमा पठाउँछ। ElevenLabs कुञ्जीलाई
गेटवे बियरर टोकनका रूपमा कहिल्यै नपठाउनुहोस्।

| विधि | पाथ                         | प्रतिक्रिया                              | API कुञ्जी एन्डपोइन्ट वर्ग |
| ---- | --------------------------- | ---------------------------------------- | -------------------------- |
| POST | `/v1/sound-generation`      | नेटिभ अडियो बाइटहरू                      | `elevenlabs`               |
| POST | `/v1/music`                 | नेटिभ अडियो बाइटहरू                      | `music`                    |
| POST | `/v1/music/stream`          | स्ट्रिमिङ अडियो बाइटहरू                  | `music`                    |
| POST | `/v1/music/detailed`        | नेटिभ मल्टिपार्ट अडियो र कम्पोजिसन योजना | `music`                    |
| POST | `/v1/music/detailed/stream` | नेटिभ SSE मेटाडेटा र अडियो खण्डहरू       | `music`                    |
| POST | `/v1/music/plan`            | JSON कम्पोजिसन योजना                     | `music`                    |

यी एन्डपोइन्टहरूले विद्यमान `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` र `/v1/speech-to-text` रुटहरूलाई परिपूरक बनाउँछन्। `output_format` र `enable_logging` जस्ता नेटिभ JSON फिल्डहरू
र क्वेरी प्यारामिटरहरू यथावत् राखिन्छन्।
`/v1/music/detailed` का प्रतिक्रियाहरूले आफ्ना मल्टिपार्ट सीमाहरू कायम राख्छन्; तिनलाई मल्टिपार्टका रूपमा पार्स गर्नुहोस्।
`/v1/music/detailed/stream` ले कम्पोजिसन मेटाडेटा र SSE इभेन्टहरूमा
base64 अडियो खण्डहरूसहित `text/event-stream` फिर्ता गर्छ। सबै छवटा रुटहरूले CORS प्रिफ्लाइट समर्थन गर्छन्।

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# छोटो ध्वनि प्रभाव। अवधि: ०.५ देखि ३० सेकेन्ड।
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# सङ्गीतको अवधि मिलिसेकेन्डमा व्यक्त गरिन्छ: ३००० देखि ६०००००।
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

क्रमिक अडियो डेलिभरीका लागि उही JSON बडीसँग `/v1/music/stream` प्रयोग गर्नुहोस्। कम्पोजिसनले
`prompt` वा `composition_plan` मध्ये ठ्याक्कै एउटा स्वीकार गर्छ; `/v1/music/plan` लाई `prompt`
आवश्यक पर्छ र वैकल्पिक रूपमा `source_composition_plan` स्वीकार गर्छ। नेटिभ स्किमाहरूले अतिरिक्त
प्रदायक फिल्डहरू कायम राख्छन्, जसले गर्दा कम्पोजिसन-योजना संस्करणहरू र फाइन-ट्युनिङ विकल्पहरू ElevenLabs सम्म पुग्छन्।

एकीकृत `/v1/music/generations` एन्डपोइन्टले `elevenlabs/music_v1`,
`elevenlabs/music_v2` र `elevenlabs/music_v2_5` पनि स्वीकार गर्छ। सक्रिय ElevenLabs जडान हुँदा,
यी मोडेलहरू सङ्गीत क्याटलगमा उपलब्ध गराइन्छन्। यो एन्डपोइन्टले
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` फिर्ता गर्छ। यसको `duration` फिल्ड
सेकेन्डमा हुन्छ र `music_length_ms` मा म्याप हुन्छ; स्पष्ट रूपमा दिइएको `music_length_ms` ले प्राथमिकता पाउँछ।
`instrumental` लाई `force_instrumental` मा म्याप गरिन्छ, जहाँ नेटिभ फिल्डले प्राथमिकता पाउँछ।
स्ट्रिमिङका लागि नेटिभ स्ट्रिमिङ एन्डपोइन्टहरू र केवल कम्पोजिसन योजनाद्वारा सञ्चालित अनुरोधहरूका लागि
नेटिभ कम्पोजिसन एन्डपोइन्ट प्रयोग गर्नुहोस्।

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

अपस्ट्रिम कलअघि एन्डपोइन्ट, मोडेल, बजेट र जडानसम्बन्धी प्रतिबन्धहरू लागू हुन्छन्। नेटिभ
रुटहरूले अपस्ट्रिम स्थिति कोडहरू र त्रुटि बडीहरू अपरिवर्तित रूपमा फिर्ता गर्छन्, जसमा योजना
प्रतिबन्धका लागि `402` र कोटा सीमाका लागि `429` समावेश छन्। उपलब्ध हुँदा `character-cost`, `song-id`, `request-id` र `retry-after`
हेडरहरू यथावत् राखिन्छन्। निःशुल्क क्रेडिट ब्यालेन्सले हरेक
सङ्गीत मोडेल, आउटपुट ढाँचा वा API सुविधामा पहुँच सुनिश्चित गर्दैन: ElevenLabs ले प्रत्येक अनुरोधको अधिकार निर्धारण गर्छ।
एकीकृत एन्डपोइन्टले OmniRoute को सामान्यीकृत त्रुटि आवरणमा त्रुटि स्थिति कोडहरू कायम राख्छ।

अपस्ट्रिम कन्ट्र्याक्टहरू: [ध्वनि प्रभावहरू](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[सङ्गीत कम्पोजिसन](https://elevenlabs.io/docs/api-reference/music/compose) र
[स्ट्रिमिङ सङ्गीत विवरणहरू](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)।

सबै POST रुटहरूले एउटै संरचना पछ्याउँछन्: `Bearer your-api-key` + Zod-द्वारा प्रमाणीकरण गरिएको JSON बडी (`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema`, आदि, `src/shared/validation/schemas.ts` हेर्नुहोस्)। स्किमा प्रमाणीकरण असफल हुँदा 4xx फर्काइन्छ।

`Authorization: Bearer ...` संलग्न गर्न नसक्ने क्लाइन्टहरूका लागि, OmniRoute ले क्वेरी-स्ट्रिङ अनुकूलता (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) वा तल अभिलेखीकृत समर्पित `/api/v1/vscode/{token}/...` एन्डपोइन्टहरूमार्फत URL मा API कुञ्जीहरू पनि स्वीकार गर्छ।

```bash
# पुनःक्रमाङ्कन (क्लाउड रजिस्ट्री प्रदायक, वा "<prefix>/<model>" को रूपमा OpenAI-सङ्गत प्रदायक नोड)
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina वर्गीकरण (Foundation API प्रमाणहरू)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina सेग्मेन्टर
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina खोज (s.jina.ai; प्रदायक उपनामहरू: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# मोडरेसनहरू
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — audio/mpeg (वा अनुरोध गरिएको ढाँचा) बडी फर्काउँछ
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS लाई language र voice आवश्यक पर्छ: `language` पूर्वनिर्धारित रूपमा "en" हुन्छ; छुटेको
# voice वा OpenAI को मानक voice नाम (alloy, nova, …) "Adrian" बन्छ
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# छवि सम्पादन (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# भिडियो / सङ्गीत सिर्जना (प्रदायक-उपसर्गयुक्त मोडेल id)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **पुनःश्रेणीकरण प्रदायक नोडहरू:** `POST /v1/rerank` ले OpenAI-सङ्गत प्रदायक नोडहरूमा पनि रुट गर्छ
> (oMLX, vLLM, Infinity, गेटवेपछाडि रहेको TEI, …), जसलाई `<node-prefix>/<model>` का रूपमा सम्बोधन गरिन्छ। लुपब्याक
> नोडहरू (`localhost`, `127.0.0.1`, `172.16.0.0/12`) सधैँ योग्य हुन्छन्, र सञ्चालकले
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` मा सूचीबद्ध गरेका होस्टनामहरू पनि योग्य हुन्छन् (उदाहरणका लागि,
> `http://reranker:8080/v1` जस्तो Docker/Compose सेवा नाम; यिनलाई सधैँ प्रत्यक्ष कल गरिन्छ,
> `HTTP(S)_PROXY` वा कुनै जडानको पिन गरिएको प्रोक्सीमार्फत कहिल्यै होइन)। अन्य कुनै पनि
> होस्टमा रहेका नोडहरू — LAN मेसिन वा Tailscale पियर — सञ्चालकले
> `RERANK_REMOTE_PROVIDER_NODES` सुविधा फ्ल्याग सक्षम गरेको **र** नोडको आधार URL ले प्रदायकको
> आउटबाउन्ड URL नीति (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`) पार गरेको अवस्थामा मात्र योग्य हुन्छन्।
> मेमोरी इन्जिनको पुनःश्रेणीकरण चरणले यो रुटलाई
> लुपब्याकमार्फत कल गर्छ, त्यसैले यही नियमले Memory सेटिङहरूमा रहेको `rerankProviderModel` लाई पनि नियन्त्रित गर्छ।
>
> **स्थानीय सर्भरका स्वरूपहरू:** नोडलाई `<base>/v1/rerank` मा र, 404 आएमा, `<base>/rerank`
> (Infinity, TEI) मा कल गरिन्छ। अपस्ट्रिम बडीमा Cohere/OpenAI हिज्जे (`documents`,
> `return_documents`) र TEI हिज्जे (`texts`, `return_text`) दुवै समावेश हुन्छन्, र अपस्ट्रिम प्रतिक्रियालाई
> Cohere इनभेलपमा सामान्यीकरण गरिन्छ: TEI को साधारण `[{index, score, text}]`, हलुका गेटवेहरूबाट आउने
> `{results: [{index, score}]}`, र Voyage-शैलीको `{data: [...]}` सबै क्लाइन्टमा
> `{results: [{index, relevance_score, document?}]}` का रूपमा फर्किन्छन्, स्कोरअनुसार क्रमबद्ध गरिएका र `top_n` मा सीमित गरिएका।
>
> **प्रदायक-नोड खोज:** OpenAI-सङ्गत प्रदायक नोडमा रहेका मोडेलहरू नोड प्रिफिक्सअन्तर्गत `GET /v1/models`
> मा देखिन्छन्। कुनै एन्डपोइन्ट मेटाडेटा नभएका पङ्क्तिहरू (स्थानीय `/v1/models` सूचीहरूमा सामान्य)
> ले नोडको `apiType` उत्तराधिकारमा लिन्छन्, त्यसैले `embeddings` नोडका मोडेलहरू च्याटमा पूर्वनिर्धारित हुनुको सट्टा
> `type: "embedding"` हुन्छन् र `rerank` नोडका मोडेलहरू `type: "rerank"` हुन्छन्; सिंक गरिएको वा
> म्यानुअल रूपमा थपिएको पङ्क्तिमा स्पष्ट रूपमा दिइएको `supportedEndpoints` ले अझै पनि प्राथमिकता पाउँछ।

### समर्पित प्रदायक रुटहरू

```bash
POST /v1/providers/{provider}/chat/completions
POST /v1/providers/{provider}/embeddings
POST /v1/providers/{provider}/images/generations
```

प्रदायक प्रिफिक्स छुटेको भए स्वतः थपिन्छ। नमिलेका मोडेलहरूले `400` फर्काउँछन्।

## Files API

ब्याच इनपुट/आउटपुट र फाइल-उद्देश्य अपलोडहरूका लागि OpenAI-सङ्गत फाइल्स एन्डपोइन्ट।

| विधि   | पथ                       | विवरण                                                                                                                    |
| ------ | ------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| POST   | `/v1/files`              | फाइल अपलोड गर्नुहोस् (मल्टिपार्ट: `file`, `purpose`, `expires_after[anchor]`, `expires_after[seconds]`) — अधिकतम 512 MiB |
| GET    | `/v1/files`              | प्रमाणीकरण गरिएको API कुञ्जीका फाइलहरू सूचीबद्ध गर्नुहोस्                                                                |
| GET    | `/v1/files/[id]`         | फाइलको मेटाडेटा प्राप्त गर्नुहोस्                                                                                        |
| DELETE | `/v1/files/[id]`         | फाइल मेटाउनुहोस्                                                                                                         |
| GET    | `/v1/files/[id]/content` | कच्चा फाइल बडीलाई स्ट्रिमका रूपमा फिर्ता पठाउनुहोस्                                                                      |

**प्रमाणीकरण:** Bearer API कुञ्जी — फाइलहरूलाई `getApiKeyRequestScope` मार्फत प्रत्येक API-कुञ्जीअनुसार सीमित गरिन्छ। एउटा कुञ्जीले
आफ्नै फाइलहरू मात्र हेर्न, डाउनलोड गर्न र मेटाउन सक्छ; कुञ्जीविनाको ड्यासबोर्ड सत्रले
सम्पूर्ण इन्स्ट्यान्स पढ्न सक्छ; मालिक नभएको फाइल (बेनामी वा ड्यासबोर्ड-सत्र अपलोड) मा हरेक
गैर-सत्र कलरको पहुँच अस्वीकार गरिन्छ। `GET /v1/files` ले प्रत्येक टेनन्टका
फाइलहरू सूचीबद्ध गर्नुको सट्टा, `REQUIRE_API_KEY=false` हुँदा पनि बेनामी कलरलाई — र प्रस्तुत गरिएको तर
रिजोल्भ नहुने कुञ्जीलाई — `401` सहित अस्वीकार गर्छ (GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523)।

## Batches API

OpenAI-सङ्गत ब्याच प्रशोधन।

| विधि   | पथ                        | विवरण                                                                                                                         |
| ------ | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| POST   | `/v1/batches`             | ब्याच सिर्जना गर्नुहोस् — बडीलाई `v1BatchCreateSchema` (`input_file_id`, `endpoint`, `completion_window`) द्वारा मान्य गरिन्छ |
| GET    | `/v1/batches`             | ब्याचहरू सूचीबद्ध गर्नुहोस्                                                                                                   |

| DELETE | `/v1/batches/[id]`        | समाप्त/असफल ब्याच मेटाउनुहोस्                                                                                                 |
| POST   | `/v1/batches/[id]/cancel` | प्रगतिमा रहेको ब्याच रद्द गर्नुहोस्                                                                                           |

**प्रमाणीकरण:** Bearer API कुञ्जी। ब्याचहरूलाई फाइलहरूकै समान त्रिपक्षीय नियमअन्तर्गत प्रत्येक API-कुञ्जीअनुसार सीमित गरिन्छ:
आफ्नै कुञ्जी मात्र, ड्यासबोर्ड सत्रका लागि इन्स्ट्यान्स-व्यापी पहुँच, र null-मालिक भएका रेकर्डहरूमा प्रत्येक
गैर-सत्र कलरका लागि पहुँच निषेध (प्राप्त गर्ने, मेटाउने, रद्द गर्ने, र सिर्जना गर्दा गरिने `input_file_id` जाँच)।
`GET /v1/batches` ले `REQUIRE_API_KEY=false` हुँदा पनि बेनामी कलरलाई `401` सहित अस्वीकार गर्छ।

## खोज API

वेब/खोज प्रदायक अमूर्तीकरण (Tavily, Brave, Exa, Serper, आदि)।

| विधि | पथ                     | विवरण                                                                                         |
| ---- | ---------------------- | --------------------------------------------------------------------------------------------- |
| GET  | `/v1/search`           | कन्फिगर गरिएका खोज प्रदायकहरू + क्षमताहरूको सूची बनाउँछ                                       |
| POST | `/v1/search`           | खोज क्वेरी चलाउँछ — बडी `v1SearchSchema` द्वारा प्रमाणीकरण गरिन्छ, क्यासिङ/कोएलेसिङ समर्थित छ |
| GET  | `/v1/search/analytics` | प्रत्येक प्रदायकका हिट/विलम्बता/क्यास तथ्याङ्कहरू                                             |

**प्रमाणीकरण:** Bearer API कुञ्जी (`extractApiKey` + `isValidApiKey`)। खोज नीति `enforceApiKeyPolicy` मार्फत लागू गरिन्छ।

### Exa र Tavily का `provider_options`

Exa र Tavily ले नेमस्पेस गरिएको ब्यागबाट प्रदायक-विशिष्ट फिल्डहरू पढ्छन्:
`provider_options.exa` (वा `provider_options["exa-search"]`) र `provider_options.tavily`
(वा `provider_options["tavily-search"]`)। तलका कुञ्जीहरू मात्र फर्वार्ड गरिन्छन्। प्रत्येकलाई
`open-sse/handlers/search/providerOptionsPassthrough.ts` मा रहेको आफ्नै Zod स्किमासँग
जाँच गरिन्छ, र गलत प्रकार भएको कुञ्जी हटाइन्छ। प्रमाणीकरण, आधार URL,
`stream` र `outputSchema` सहित अन्य कुनै पनि कुञ्जी बेवास्ता गरिन्छ। अन्य प्रदायकहरूले प्रयोग गर्ने समतल कुञ्जीहरू (`cx`, `depth`, ...) पहिलेझैँ
काम गर्छन्।

| प्रदायक | शीर्ष-स्तरका फिल्डहरू                                                                                                                                                                                                                                                                                                                                                     | नेस्टेड                                                                                                                                                                       |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa     | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (समतल प्रिमिटिभहरू), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                            | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` लाई पूर्वनिर्धारित `{ text: true, highlights: true }` माथि मर्ज गरिन्छ |
| Tavily  | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                             |

जेनेरिक फिल्डहरू सधैँ प्राथमिक हुन्छन्: `query`, `max_results`, `filters` (डोमेनहरू), `country` र
`search_type` बाट व्युत्पन्न गरिएको विषय। Exa मा, `search_type: "news"` ले `category: "news"` कायम राख्छ।
Tavily ले `search_type: "finance"` (`topic: "finance"`) पनि स्वीकार गर्छ।

जेनेरिक `time_range` अब दुवै प्रदायकसम्म पुग्छ: Exa ले `startPublishedDate` (ISO
टाइमस्ट्याम्प) प्राप्त गर्छ र Tavily ले `start_date` (`YYYY-MM-DD`) प्राप्त गर्छ। `provider_options`
मा स्पष्ट रूपमा दिइएको मितिले म्याप गरिएको मितिलाई ओभरराइड गर्छ।

Exa का परिणामहरूले `id`, `highlight_scores`, `summary`, `subpages`, `entities` र `extras` लाई
`provider_raw` मा कायम राख्छन्। Tavily का परिणामहरूले `images` र `favicon` कायम राख्छन्।

लागत लेखाङ्कन अझै पनि समतल रजिस्ट्री `costPerQuery` नै हो। Tavily ले
`search_depth: "advanced"` का लागि प्रति कल बढी क्रेडिट बिल गर्छ, र त्यो भिन्नता
`usage.search_cost_usd` मा प्रतिबिम्बित हुँदैन।

## वेब फेच API

कन्फिगर गरिएको वेब-फेच प्रदायक (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract) मार्फत URL बाट सामग्री निकाल्नुहोस्।

Parallel Extract (`parallel-search`, Parallel Search कै समान API कुञ्जी) ले Markdown
मात्र फर्काउँछ — अन्य कुनै पनि `format` ले `400` फर्काउँछ — र सामग्रीलाई 100,000 वर्णमा सीमित गर्छ। जब
लक्षित पृष्ठ नै निकाल्न सकिँदैन, upstream ले त्यसलाई HTTP 200 भित्र रिपोर्ट गर्छ;
OmniRoute ले त्यसलाई निश्चित सन्देशसहितको `422` का रूपमा प्रस्तुत गर्छ।

| विधि | पथ              | विवरण                                                                       |
| ---- | --------------- | --------------------------------------------------------------------------- |
| POST | `/v1/web/fetch` | URL फेच/स्क्रेप गर्छ — body लाई `v1WebFetchSchema` द्वारा प्रमाणीकरण गरिन्छ |

**प्रमाणीकरण:** Bearer API कुञ्जी (`extractApiKey` + `isValidApiKey`)। नीति `enforceApiKeyPolicy` मार्फत लागू गरिन्छ।

**कोटा-सचेत fallback (#8297):** कुनै स्पष्ट `provider` नदिइएको अवस्थामा, pool
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) लाई
निश्चित प्राथमिकता क्रम (fill-first) मा
क्रमशः प्रयोग गरिन्छ — rate-limit भएको तर कन्फिगर गरिएको प्रदायकले अनुरोधलाई तत्काल रोक्नुको
सट्टा त्यसलाई छोडिन्छ, र पुनः प्रयासयोग्य/कोटासम्बन्धी upstream विफलता
(HTTP 429 सधैँ; Firecrawl/Tavily/TinyFish का कोटा-शैलीका निःशुल्क tier का लागि 402/403 —
Jina Reader का लागि होइन, र सामान्य 400 bad request का लागि कहिल्यै होइन) हुँदा अनुरोधकै समयमा
अर्को अझै प्रयास नगरिएको credential भएको प्रदायकमा fallback गरिन्छ। pool का सबै प्रदायक
समाप्त भएपछि, endpoint ले पहिलेको सामान्य `400` को सट्टा एउटै `429` (`Retry-After`
header सहित) फर्काउँछ। स्पष्ट `provider` अनुरोध गरिएको अवस्थामा,
कुनै मौन fallback हुँदैन — rate-limit भएको वा विफल स्पष्ट
प्रदायकले आफ्नै त्रुटि प्रस्तुत गर्छ (rate-limit भएको भए `429`, अन्यथा upstream
status)।

## WebSocket स्ट्रिमिङ

```bash
GET /v1/ws?handshake=1
```

WebSocket upgrade handshake प्रमाणीकरण गर्छ र wire protocol का उदाहरण सन्देशहरू (`request`, `cancel`) फर्काउँछ। वास्तविक WS frame हरूलाई Next.js route table बाहिर रहेको bundled WS server ले सम्हाल्छ।

**प्रमाणीकरण:** handshake को समयमा Bearer API कुञ्जी।

### WebSocket माथि Responses API (codex मात्र)

```bash
# HTTP API कै समान host:port (पूर्वनिर्धारित 20128); connection upgrade गर्नुहोस्:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (वा: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# पहिलो frame response.create नै हुनुपर्छ:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket proxy लाई **विशेष रूपमा `codex`** (ChatGPT
backend) सँग जोडिएको छ। यसले API/dashboard कै समान port मा `/v1/responses`,
`/responses`, र `/api/v1/responses` पथहरूमा सुन्छ। पहिलो `response.create` frame मा यसले
आन्तरिक `codex-responses-ws` bridge मार्फत प्रमाणीकरण + तयारी गर्छ, एउटा
codex OAuth connection चयन गर्छ, र `wreq-js` transport मार्फत `wss://chatgpt.com/backend-api/codex/responses`
मा tunnel गर्छ। **गैर-codex model हरू अस्वीकार गरिन्छ** (`codex_ws_provider_required`)।
quota-share routing का लागि `model: "qtSd/<group>/codex/<model>"` प्रयोग गर्नुहोस्। यो
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` मा कार्यान्वयन गरिएको छ।

**प्रमाणीकरण:** handshake को समयमा Bearer API कुञ्जी। bundled HTTP server (`server-ws.mjs`)
सक्रिय entrypoint हुनुपर्छ (`app/server-ws.mjs` अवस्थित हुँदा पूर्वनिर्धारित रूपमा यही हुन्छ)।

#### Model id: मूल ChatGPT id प्रयोग गर्नुहोस् (`codex/` prefix बिना)

OpenAI **Codex CLI** ले `supports_websockets = true` हुँदा client-side मै model name प्रमाणीकरण गर्छ र
`codex/gpt-5.5` जस्ता **provider-prefixed id हरू अस्वीकार गर्छ**
(`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`)। **मूल** id पठाउनुहोस् (जस्तै `gpt-5.5`)। OmniRoute को bridge
codex-only भएकाले, upstream मा tunnel गर्नु अघि यसले मूल id लाई codex model का रूपमा
(`resolveCodexWsModelInfo`) पुनः resolve गर्छ — यद्यपि मूल
`gpt-5.5` अन्यथा HTTP मार्फत अर्को प्रदायकमा route हुने थियो।

#### OpenAI Codex CLI कन्फिगर गर्ने

`~/.codex/config.toml` मा WebSocket समर्थनसहितको custom provider थपेर Codex CLI लाई
OmniRoute तर्फ निर्देशित गर्नुहोस् (पहिलेदेखिको config नछुन छुट्टै `CODEX_HOME` प्रयोग गर्नुहोस्):

```toml
model = "gpt-5.5"                 # मूल id — "codex/gpt-5.5" होइन
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # अन्त्यमा slash नराख्नुहोस्; WS URL निकालिन्छ (production मा https/wss प्रयोग गर्नुहोस्)
wire_api = "responses"                    # Feb 2026 देखि समर्थित एक मात्र value
supports_websockets = true                # Responses-over-WS transport सक्षम गर्छ
env_key = "OMNIROUTE_API_KEY"             # OmniRoute API कुञ्जी (Bearer) राख्छ
```

```bash
export OMNIROUTE_API_KEY=sk-...           # एउटा OmniRoute API कुञ्जी (REQUIRE_API_KEY=false भए कुनै पनि कुञ्जी)
codex exec "Responda apenas: PONG"
```

CLI ले `base_url + /responses` लाई WebSocket मा upgrade गर्छ र OmniRoute ले यसलाई
चयन गरिएको codex OAuth connection मा tunnel गर्छ। स्थानीय
server विरुद्ध end-to-end प्रमाणीकरण गरिएको छ: ChatGPT ले `codex.rate_limits` + `response.created` फर्काउँछ र
completion stream गर्छ।

## स्व-सेवा प्रयोग (`/api/usage/om-usage`)

कुनै पनि API कुञ्जीले व्यवस्थापन प्रमाणीकरणबिना **आफ्नै** प्रयोग र कोटाहरू पढ्न सक्छ। यो त्यही endpoint हो जसलाई
client (CLI, OmniCopilot panel) ले कुञ्जी धारकलाई उनीहरूको खर्च देखाउन प्रयोग गर्छ।

```bash
# पाठ्य रूप (ऐतिहासिक अनुबन्ध — terminal का लागि सादा पाठ)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# संरचित रूप — UI ले प्रयोग गर्ने
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

कुञ्जीमा **`allowUsageCommand`** सक्षम गरिएको हुनुपर्छ (पूर्वनिर्धारित रूपमा बन्द हुन्छ—dashboard को API-कुञ्जी
manager ले यसलाई प्रत्येक कुञ्जीका लागि टगल गर्छ)। यो नभए endpoint ले `403` जवाफ दिन्छ।

`?format=json` ले छुट्याउन सकिने संरचना फर्काउँछ, जसले गर्दा caller ले अस्वीकृतिबाट कहिल्यै data field पढ्दैन।
सफल हुँदा:

```jsonc
{
  "allowed": true,
  // कुञ्जीले प्रति-कुञ्जी प्रयोग सीमाहरू (दैनिक/साप्ताहिक USD) रोजेको अवस्थामा मात्र उपस्थित हुन्छ:
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // चयन गरिएको provider कोटा snapshot, वा अहिलेसम्म केही पनि cache नभएको अवस्थामा null:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // प्रत्येक connection को snapshot, जसले गर्दा UI ले धेरै provider हरूलाई सँगसँगै render गर्न सक्छ:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

अस्वीकृति हुँदा (`401` गलत कुञ्जी / `403` अनुमति नभएको), सोही route ले
`{ "allowed": false, "error": { "message": "…" } }` फर्काउँछ—उपस्थित तर खाली `personal`/`provider`
(कुञ्जीलाई अनुमति छ, तर अहिलेसम्म केही थाहा भएको छैन) अस्वीकृतिभन्दा फरक अवस्था हो, र JSON रूपले मात्र
तिनलाई छुट्याउँछ।

**प्रमाणीकरण:** caller को आफ्नै Bearer API कुञ्जी, `isValidApiKey` द्वारा प्रमाणित—यो व्यवस्थापन
surface (`/api/keys/…`) _होइन_, जुन `requireManagementAuth` पछाडि नै रहन्छ।

### अपरिष्कृत र Cutoff-समायोजित कोटा प्रतिशतहरू

`/api/usage/om-usage` प्रयोग गर्दा, caller हरूले **सादा-पाठ output** र संरचित **JSON output** द्वारा प्रस्तुत
प्रतिशतहरूबीचको भिन्नता ध्यान दिनुपर्छ:

| पक्ष                  | सादा-पाठ ढाँचा (`/api/usage/om-usage` / `@@om-usage`)                                            | JSON ढाँचा (`?format=json`)                                                                           |
| :-------------------- | :----------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------- |
| **Output field**      | `NN% left` (जस्तै, `20% left`)                                                                   | `provider.quotas` / `providers[].quotas`                                                              |
| **मापन**              | **Cutoff-समायोजित प्रयोगयोग्य सीमा**: cutoff threshold भन्दा माथिको बाँकी क्षमता                 | **अपरिष्कृत upstream कोटा**: समायोजन नगरिएको provider मापन                                            |
| **Cutoff scaling**    | `effectiveRemainingPercent()` मार्फत scale गरिन्छ, जसले गर्दा सुरक्षित reserve `0% left` देखिन्छ | कुनै पनि छैन (provider ले रिपोर्ट गरेअनुसारका अपरिष्कृत snapshot मानहरू)                              |
| **Threshold data**    | देखाइएको प्रतिशतमा समावेश गरिएको                                                                 | प्रत्येक connection को `quotaWindowThresholds` मा भण्डारण गरिएको (वा server का पूर्वनिर्धारित मानहरू) |
| **प्राथमिक उपभोक्ता** | अन्तरक्रियात्मक CLI हरू, terminal prompt हरू, मानवीय operator हरू                                | प्रोग्रामगत integration हरू, dashboard हरू, analytics, billing tracker हरू                            |

#### Cutoff समायोजन सूत्र

OmniRoute ले upstream समाप्त हुन नदिन सक्रिय कोटा cutoff हरू समर्थन गर्छ (connection
`quotaWindowThresholds`, provider का पूर्वनिर्धारित मानहरू, वा global resilience settings मार्फत configure गरिन्छ)। कोटा window मा cutoff threshold
(जस्तै, `cutoff = 25%`) सक्रिय हुँदा, text renderer ले बाँकी सीमा यसरी गणना गर्छ:

- यदि `remaining <= cutoff` भएमा: `0%` फर्काउँछ।
- यदि `remaining > cutoff` भएमा: `((remaining - cutoff) / (100 - cutoff)) * 100` फर्काउँछ।

ढाँचाबद्ध text output ले यसलाई सबैभन्दा नजिकको पूर्णाङ्कमा round गर्छ (`Math.round(...)`)।

#### उदाहरणात्मक नमुना

**60% अपरिष्कृत प्रयोग** (अर्थात् **40% अपरिष्कृत बाँकी कोटा**) भएको provider window र configure गरिएको
**25% बाँकी-कोटा cutoff** threshold लाई विचार गर्नुहोस्:

| प्रस्तुतीकरण                        | गणना                                               |  बाँकी  |              निहित प्रयोग              |
| :---------------------------------- | :------------------------------------------------- | :-----: | :------------------------------------: |
| **अपरिष्कृत JSON (`?format=json`)** | Upstream snapshot (`quotas[window]`)               | **40%** |                **60%**                 |
| **Text ढाँचा (`NN% left`)**         | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (`100 - remaining` गणना गरेमा) |

- **Text ले 20% बाँकी किन देखाउँछ:** account मा भौतिक रूपमा बाँकी रहेको 40% कोटामध्ये, 25% लाई
  cutoff policy ले reserve गरेको हुन्छ। router ले यस connection मा routing रोक्नुअघि caller सँग प्रयोगयोग्य 75% headroom मध्ये
  15% मात्र बाँकी हुन्छ। Scaling ले routing बन्द हुने ठीक समयमा connection ले समाप्ति (`0% left`) सङ्केत गर्ने सुनिश्चित गर्छ।
- **JSON ले अपरिष्कृत मानहरू किन सुरक्षित राख्छ:** JSON payload ले provider को सटीक snapshot (`UsageSnapshot`)
  फर्काउँछ, जसले गर्दा बाह्य tool हरूले server-side lossy scaling बिना वास्तविक upstream उपयोग र connection-level
  `quotaWindowThresholds` मा पहुँच पाउँछन्।

#### उपभोक्ता Migration मार्गदर्शन

यदि कुनै बाह्य एकीकरण (जस्तै सम्पादक प्लगइन वा एजेन्ट एक्सटेन्सन) ले पहिले टेक्स्ट
एन्डपोइन्ट (`NN% left`) स्क्रेप गरेर प्रयोग भएको प्रतिशतलाई `100 - NN` का रूपमा गणना गर्थ्यो भने, `?format=json` मा माइग्रेट गर्नुको अर्थ:

- कच्चा JSON मानहरू पढ्दा **अपस्ट्रिममा भएको वास्तविक खपत** प्रतिबिम्बित हुनेछ (माथिको उदाहरणमा 60% प्रयोग भएको)।
- यदि एकीकरणले टेक्स्ट एन्डपोइन्टको प्रयोगयोग्य बाँकी परिमाणसम्बन्धी अर्थविज्ञान कायम राख्न चाहन्छ भने, यसले जडान-स्तरीय ओभरराइडहरूका लागि `quotaWindowThresholds` प्रयोग गरी
  क्लाइन्ट-साइडमा प्रभावकारी बाँकी परिमाणको सूत्र मूल्याङ्कन गर्न सक्छ।

सिङ्क वा आयात गरिएका मोडेलहरूका लागि, `PUT /api/provider-models` ले `provider`, `modelId`, र
`maxOutputTokenOverride` स्वीकार गर्छ: धनात्मक पूर्णाङ्कले म्यानुअल आउटपुट-टोकन सीमा सेट गर्छ, र `null`
ले पूर्वनिर्धारित मान पुनर्स्थापना गर्न त्यसलाई हटाउँछ। `GET /api/provider-models?provider=<provider>` ले अनुकूलन-मोडेल पङ्क्ति
नभएका मोडेलहरूसहित यी मानहरू `modelOutputOverrides` मा फर्काउँछ। ओभरराइडले
रनटाइम `max_output_tokens` क्षमता प्रयोग गर्छ र मोडेल पुनः सिङ्क गरिएपछि पनि कायम रहन्छ। OpenAI-सङ्गत
प्रदायक पृष्ठले उही सम्पादन/हटाउने नियन्त्रणहरू उपलब्ध गराउँछ र स्पष्ट vision समर्थन भएका मोडेलहरूलाई चिन्ह लगाउँछ।

अनुकूलन Chat Completions नोडहरूले स्पष्ट reasoning अप्ट-आउटहरूलाई अपस्ट्रिम ब्याकइन्डअनुसार अनुकूलित गर्छन्।
सफल जडान परीक्षणले `/models` प्रविष्टिले मान्यताप्राप्त `owned_by` मान प्रमाणित गर्ने प्रत्येक ठ्याक्कै मिल्ने मोडेल ID का लागि
chat-template नियन्त्रणहरू स्वतः चयन गर्छ: `vllm`, `sglang`, वा `llamacpp`।
पारदर्शी OpenAI-सङ्गत र्यापरहरूले मूल मोडेल प्रविष्टिलाई नेस्ट गरिएको
`openai` वस्तुभित्र सुरक्षित राख्न सक्छन्; पहिचानले त्यस्ता बढीमा तीनवटा आवरण पछ्याउँछ। स्वामित्व छुटेका, अज्ञात भएका वा
बाझिएका मोडेलहरूले सामान्य OpenAI व्यवहार कायम राख्छन्। पहिचानले विद्यमान क्याटलग अनुरोध पुनः प्रयोग गर्छ,
कुनै completion टोकन उत्पन्न गर्दैन, र जडानको अन्त्यबिन्दु परिवर्तन हुँदा अमान्य हुन्छ।

त्यो मेटाडेटा नदेखाउने ब्याकइन्डका लागि व्यवहार निश्चित गर्न, विद्यमान आंशिक
प्रदायक अद्यावधिक API प्रयोग गर्नुहोस्:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

त्यो body लाई `PUT /api/providers/<connection-id>` मार्फत पठाउनुहोस्। त्यस जडानमा, `none` को स्पष्ट
reasoning effort लाई `chat_template_kwargs.thinking=false` र
`chat_template_kwargs.enable_thinking=false` का रूपमा पठाइन्छ। सर्भर-साइड reasoning नियमले कुनै effort बाध्यकारी
नबनाएसम्म स्पष्ट नेटिभ template मानहरू नै आधिकारिक रहन्छन्। यो सेटिङ अनुकूलन
OpenAI-सङ्गत जडानले Chat Completions body पठाउँदा मात्र लागू हुन्छ; Responses अनुरोधहरू र सामान्य
प्रदायकहरूले आफ्नै नेटिभ अनुरोध संरचना कायम राख्छन्। सामान्य OpenAI
`reasoning_effort` पासथ्रु बाध्यकारी बनाउन `reasoningControl` लाई `openai` मा सेट गर्नुहोस्, वा स्वचालित पहिचान प्रयोग गर्न यसलाई नदिनुहोस्/`null` मा सेट गर्नुहोस्।

Claude Code स्वतः-मोड वर्गीकारक अनुरोधहरूमा कुनै स्पष्ट reasoning नियन्त्रणहरू नहुँदा नेटिभ thinking पूर्वनिर्धारित रूपमा
असक्षम हुन्छ। पहिचानले मोडेल नाम वा completion सीमाहरू होइन, Claude-ढाँचाका
अनुरोधहरूमा रहेको वर्गीकारकको system marker प्रयोग गर्छ। स्पष्ट body नियन्त्रणहरू, समर्थित effort/thinking
हेडरहरू, routing नियमहरू, र समाधान गरिएको मोडेल effort ले आफ्ना विद्यमान प्राथमिकता कायम राख्छन्। वर्गीकारकका दुवै
चरणहरूले आफ्ना prompts, completion सीमाहरू, stop sequences, र वास्तविक अपस्ट्रिम अनुमति
निर्णयहरू कायम राख्छन्; दोस्रो चरणले अझै पनि अनुरोध गरिएको दृश्य reasoning लाई सामान्य पाठका रूपमा उत्पादन गर्न सक्छ।

### संस्करण र रिलीज च्यानल

```bash
GET /api/system/version
```

लुपब्याकमा मात्र उपलब्ध व्यवस्थापन रुट (एडमिन प्रमाणीकरण)। यसले चलिरहेको संस्करण, नवीनतम
प्रकाशित संस्करण र स्वचालित अद्यावधिकको स्थिति फर्काउँछ। `releaseChannel` र `channels` थपिएका
फिल्डहरू हुन् (रेल 3.8.54); `channel` को अर्थ उही रहन्छ — ड्यासबोर्ड अद्यावधिककर्ताले प्रयोग गर्ने
डिप्लोयमेन्ट मोड (`npm`, `source` वा `docker-compose`)।

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — चलिरहेको बिल्डको npm च्यानल: `-nightly.*` संस्करणहरूका लागि `nightly`,
  अन्य पूर्व-रिलीजहरू (`-rc.*`, `-beta.*`, `-alpha.*`) का लागि `next`, `channels.latest` भन्दा
  पुरानो प्रमुख संस्करणको स्थिर संस्करणका लागि `lts`, अन्यथा `latest`। प्रकाशनको समयमा npm
  dist-tag चयन गर्ने `scripts/release/dist-tag.mjs` कै नियमहरू लागू हुन्छन्।
- `channels` — `npm view omniroute dist-tags` बाट प्राप्त प्रत्येक dist-tag को प्रकाशित नवीनतम
  संस्करण (रेजिस्ट्री HTTP फलब्याकसहित), जुन `latest` जस्तै १०-मिनेट TTL सँग क्यास गरिन्छ।
  `latest` सधैँ उपस्थित हुन्छ (`latest` फिल्डमा फलब्याक हुन्छ, त्यसपछि `"unavailable"` मा);
  `next`, `nightly` र `lts` सम्बन्धित dist-tag अवस्थित हुँदा मात्र देखिन्छन्।
  `Cache-Control: no-cache` अनुरोधले दुवै लुकअपलाई ताजा गर्छ।

च्यानल मोडेल (`latest` = 4.0 GA नआउँदासम्म v3, `next` = rc, `nightly` = `develop` बिल्डहरू,
`lts` = 4.0 GA पछि v3 प्याचहरू) को वर्णन `docs/ops/RELEASE_STRATEGY.md` मा गरिएको छ।

## टोकनयुक्त VS Code / हेडररहित उपनामहरू

कुनै एकीकरणले `Authorization` हेडर थप्न नसक्ने र आधार URL मै API कुञ्जी समावेश गर्नुपर्ने अवस्थामा यी उपनामहरू प्रयोग गर्नुहोस्।

```bash
# OpenAI-शैलीको क्याटलग उपनाम
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# OpenAI-शैलीका च्याट उपनामहरू
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Ollama-शैलीका उपनामहरू
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

उदाहरण:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

टिप्पणीहरू:

- टोकनयुक्त उपनामहरूले `/v1/*` र `/api/tags` कै ह्यान्डलरहरू पुनः प्रयोग गर्छन्; प्रतिक्रियाका संरचनाहरू समान रहन्छन्।
- क्लाइन्टले अनुकूलित हेडरहरू समर्थन गर्ने अवस्थामा सधैँ `Authorization: Bearer ...` लाई प्राथमिकता दिनुहोस्।
- URL-आधारित टोकनहरू रिभर्स-प्रोक्सी लगहरू, ब्राउजर इतिहास र OmniRoute बाहिरको टेलिमेट्रीमा देखिन सक्छन्। तिनलाई पूर्वनिर्धारित प्रमाणीकरण विधिका रूपमा नभई अनुकूलता विकल्पका रूपमा लिनुहोस्।

# सबै API कुञ्जीहरूको बजेट स्थिति प्राप्त गर्नुहोस्

## टोकन सीमाहरू

प्रति-API-key **टोकन** बजेटहरू (माथिको USD-आधारित बजेटभन्दा फरक)। अनुरोध मार्गमै लागू गरिन्छ: कुनै key को हालको विन्डो प्रयोग यसको सीमामा पुगेपछि, अनुरोधहरू `429 Too Many Requests` सहित अस्वीकार गरिन्छन्। सीमाहरूलाई कुनै विशिष्ट `model`, कुनै `provider` मा सीमित गर्न वा सम्पूर्ण key मा `global` रूपमा लागू गर्न सकिन्छ; एउटै अनुरोधसँग धेरै सीमाहरू मेल खाएमा, सबैभन्दा प्रतिबन्धात्मक सीमा लागू हुन्छ।

```bash
# कुनै key का टोकन सीमाहरूको सूची देखाउनुहोस् (प्रत्यक्ष विन्डो प्रयोगसहित)
GET /api/usage/token-limits?apiKeyId=key-123

# टोकन सीमा सिर्जना वा अद्यावधिक गर्नुहोस्
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# id का आधारमा टोकन सीमा मेटाउनुहोस्
DELETE /api/usage/token-limits?id=tl-abc
```

> **स्किमा टिप्पणीहरू** (`setTokenLimitSchema`): `apiKeyId` र `scopeType` (`model` | `provider` | `global`) आवश्यक छन्। `scopeType`, `global` नभएसम्म `scopeValue` आवश्यक हुन्छ (जस्तै, `model` स्कोपका लागि model id, `provider` स्कोपका लागि provider id)। `tokenLimit` धनात्मक पूर्णाङ्क हुनुपर्छ (string बाट रूपान्तरित)। वैकल्पिक: `id` (सिर्जना गर्न नदिनुहोस्, अद्यावधिक गर्न प्रदान गर्नुहोस्), `resetInterval` (`daily` | `weekly` | `monthly`, पूर्वनिर्धारित `monthly`), `resetTime` (`HH:MM`), `enabled` (पूर्वनिर्धारित `true`)। `GET` प्रतिक्रियाहरूले प्रत्येक सीमामा `tokensUsed`, `remaining`, `windowStart`, `periodStartAt`, र `nextResetAt` थप्छन्। यो व्यवस्थापन-श्रेणीको endpoint हो (authz pipeline द्वारा प्रमाणीकरण केन्द्रीय रूपमा लागू गरिन्छ)।

## अनुरोध प्रशोधन

1. क्लाइन्टले `/v1/*` मा अनुरोध पठाउँछ
2. Route handler ले `handleChat`, `handleEmbedding`, `handleAudioTranscription`, वा `handleImageGeneration` कल गर्छ
3. Model निर्धारण गरिन्छ (प्रत्यक्ष provider/model वा alias/combo)
4. Account उपलब्धता फिल्टरिङसहित स्थानीय DB बाट credentials चयन गरिन्छन्
5. Chat का लागि: `handleChatCore` ले semantic/signature cache जाँच गर्छ र combo compression settings निर्धारण गर्छ
6. सक्षम गरिएको अवस्थामा provider translation अघि proactive compression चल्छ (`lite`, Caveman, RTK, वा stacked)
7. Provider executor ले upstream अनुरोध पठाउँछ
8. प्रतिक्रिया client format मा पुनः अनुवाद गरिन्छ (chat) वा जस्ताको तस्तै फिर्ता गरिन्छ (embeddings/images/audio)
9. Usage, compression analytics, र request logs रेकर्ड गरिन्छन्
10. त्रुटि हुँदा combo नियमहरूअनुसार fallback लागू हुन्छ

पूर्ण architecture सन्दर्भ: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Combo व्यवस्थापन

उच्च-स्तरीय routing combos (`/api/combos*` अन्तर्गत पहिले नै सारांशित) लाई model id pattern बाट 1:1 रूपमा पनि म्याप गर्न सकिन्छ, जसले OpenAI-style model id लाई combo मा पारदर्शी रूपमा पुनर्निर्देशित गर्न अनुमति दिन्छ।

| विधि   | मार्ग                            | विवरण                                                                                     |
| ------ | -------------------------------- | ----------------------------------------------------------------------------------------- |
| GET    | `/api/model-combo-mappings`      | सबै model→combo mappings को सूची देखाउनुहोस्                                              |
| POST   | `/api/model-combo-mappings`      | Mapping सिर्जना गर्नुहोस् — body: `{pattern, comboId, priority?, enabled?, description?}` |
| GET    | `/api/model-combo-mappings/[id]` | एउटै mapping प्राप्त गर्नुहोस्                                                            |
| PUT    | `/api/model-combo-mappings/[id]` | अवस्थित mapping का fields अद्यावधिक गर्नुहोस्                                             |
| DELETE | `/api/model-combo-mappings/[id]` | Mapping हटाउनुहोस्                                                                        |

**प्रमाणीकरण:** management session/API key (`requireManagementAuth`)।

प्रदायक, खाताहरू वा विश्वव्यापी रूपमा तोक्न सकिने आउटबाउन्ड HTTP(S)/SOCKS प्रोक्सीहरू।

| विधि   | पथ                                           | विवरण                                                                                                                                                              |
| ------ | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GET    | `/api/v1/management/proxies`                 | प्रोक्सीहरूको सूची (`?id=` सहित एउटामात्र फर्काउँछ; `?id=&where_used=1` सहित तोकाइ ग्राफ फर्काउँछ)                                                                 |
| POST   | `/api/v1/management/proxies`                 | प्रोक्सी सिर्जना — अनुरोधको मुख्य भाग `createProxyRegistrySchema` द्वारा प्रमाणीकरण गरिन्छ                                                                         |
| PATCH  | `/api/v1/management/proxies`                 | प्रोक्सी अद्यावधिक — अनुरोधको मुख्य भाग `updateProxyRegistrySchema` द्वारा प्रमाणीकरण गरिन्छ (`id` आवश्यक)                                                         |
| DELETE | `/api/v1/management/proxies?id=...&force=1`  | प्रोक्सी मेटाउनुहोस् (तोकाइहरू हटाउन `force=1` प्रयोग गर्नुहोस्)                                                                                                   |
| GET    | `/api/v1/management/proxies/assignments`     | तोकाइहरूको सूची — `proxy_id`, `scope`, `scope_id` द्वारा फिल्टर गर्न सकिने; कुनै जडानका लागि सक्रिय प्रोक्सी निर्धारण गर्न `resolve_connection_id=<id>` पठाउनुहोस् |
| PUT    | `/api/v1/management/proxies/assignments`     | तोक्नुहोस् — अनुरोधको मुख्य भाग `proxyAssignmentSchema` (`{scope, scopeId?, proxyId?}`) द्वारा प्रमाणीकरण गरिन्छ। डिस्प्याचर क्यास खाली गर्छ                       |
| PUT    | `/api/v1/management/proxies/bulk-assign`     | सामूहिक रूपमा तोक्नुहोस् — अनुरोधको मुख्य भाग `bulkProxyAssignmentSchema` (`{scope, scopeIds[], proxyId?}`) द्वारा प्रमाणीकरण गरिन्छ                               |
| GET    | `/api/v1/management/proxies/health?hours=24` | समयावधिभरको समग्र प्रोक्सी स्वास्थ्य (सफलता/असफलता सङ्ख्या, विलम्बता)                                                                                              |

## लचिलोपन (विस्तारित)

OmniRoute ले अस्थायी विफलताका तीन स्वतन्त्र संयन्त्रहरू उपलब्ध गराउँछ; तलका व्यवस्थापन एन्डपोइन्टहरूले सञ्चालकहरूलाई तिनको अवस्था पढ्न र अधिलेखन गर्न दिन्छन्:

| क्षेत्र        | अवस्था भण्डारण                        | पढ्ने                                     | रिसेट गर्ने / हटाउने                                           |
| -------------- | ------------------------------------- | ----------------------------------------- | -------------------------------------------------------------- |
| प्रदायक ब्रेकर | `domain_circuit_breakers` + इन-मेमोरी | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                   |
| जडान कूलडाउन   | प्रदायक जडानहरूमा `rateLimitedUntil`  | `/api/rate-limits`, `/api/providers/[id]` | (आवश्यक पर्दा पुनः सक्षम हुन्छ; प्रदायक PUT मार्फत हटाउनुहोस्) |
| मोडेल लकआउट    | इन-मेमोरी मोडेल-उपलब्धता रजिस्ट्री    | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                       |

`PATCH /api/resilience` ले `providerBreaker.oauth` र `providerBreaker.apikey` अन्तर्गत प्रदायक ब्रेकर अधिलेखनहरू स्वीकार गर्छ। प्रत्येक प्रोफाइलले `degradationThreshold`, `failureThreshold`, र `resetTimeoutMs` समर्थन गर्छ; उही फिल्डहरू ड्यासबोर्ड → सेटिङ्स → लचिलोपनमा पनि उपलब्ध छन्।

```bash
# एउटा मोडेल लकआउट हटाउनुहोस्
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# सबै लकआउटहरू हटाउनुहोस्
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

पूर्ण अवधारणात्मक सन्दर्भ र ब्रेकरका पूर्वनिर्धारित मानहरूका लागि: [`CLAUDE.md`](../../CLAUDE.md) → "लचिलोपनको रनटाइम अवस्था" र [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) हेर्नुहोस्।

### दर-सीमा क्यु र स्वतः-सक्षम सुरक्षा जाल

- **समर्थित लेखन मार्ग**: `{"connectionId": "<id>", "enabled": true|false}` बडीसहितको `POST /api/rate-limits` कुनै जडानको दर-सीमा सुरक्षा टगल गर्नका लागि समर्थित व्यवस्थापन एन्डपोइन्ट हो। `PUT /api/providers/[id]` ले जानाजानी `rateLimitProtection` परिमार्जन वा उल्ट्याउँदैन (#11278)।
- **`enabled: false` को अर्थ**: `enabled: false` सेट गर्दा जडानको स्पष्ट सुरक्षा हट्छ, तर यसले सक्रिय API-key जडानलाई विश्वव्यापी स्वतः-सक्षम सुरक्षा जाल (`autoEnableApiKeyProviders = true`) बाट **बाहिर निकाल्दैन**। `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) मा `false` र `undefined` समान हुन्छन्; स्पष्ट सुरक्षा नभएका सक्रिय API-key जडानहरू स्वतः-सक्षम सुरक्षा जालअन्तर्गत सुरक्षित नै रहन्छन्।
- **विश्वव्यापी रूपमा असक्षम गर्ने**: दर-सीमा क्युहरूबिना API-key जडानहरू सञ्चालन गर्न, `RATE_LIMIT_AUTO_ENABLE=false` (env) वा `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (सेटिङ्स → लचिलोपन / `PATCH /api/resilience`) मार्फत सुरक्षा जाललाई विश्वव्यापी रूपमा असक्षम गर्नुहोस्।

## MCP सर्भर

OmniRoute मा 3 वटा ट्रान्सपोर्ट (stdio, SSE, streamable-http) र सीमित-क्षेत्रका उपकरणहरूसहित अन्तर्निर्मित Model Context Protocol सर्भर समावेश छ। तलका ड्यासबोर्ड एन्डपोइन्टहरूले स्थिति/अडिट डेटा पढ्छन् र HTTP ट्रान्सपोर्टहरूलाई प्रोक्सी गर्छन्।

| विधि | पथ | विवरण |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | हार्टबिट, ट्रान्सपोर्ट, अनलाइन स्थिति, पछिल्लो कल, शीर्ष उपकरणहरू, 24 घण्टाको सफलता दर |
| GET | `/api/mcp/tools` | `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` सहित MCP उपकरणहरूको सूची |
| GET | `/api/mcp/sse` | SSE ट्रान्सपोर्टका लागि SSE स्ट्रिम खोल्नुहोस् (MCP अक्षम भएमा वा ट्रान्सपोर्ट नमिलेमा `503` फर्काउँछ) |
| POST | `/api/mcp/sse` | SSE ट्रान्सपोर्टमा JSON-RPC फ्रेम पठाउनुहोस् |
| GET | `/api/mcp/stream` | Streamable HTTP ट्रान्सपोर्टको SSE पक्ष खोल्नुहोस् (सर्भरद्वारा आरम्भ गरिएका सन्देशहरू) |

## A2A सर्भर

OmniRoute ले निरीक्षण/ड्यासबोर्ड प्रयोगका लागि REST र्यापरसहित A2A (Agent-to-Agent) JSON-RPC 2.0 एन्डपोइन्ट उपलब्ध गराउँछ।

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # OMNIROUTE_API_KEY सेट गरिएको अवस्थामा बाहेक वैकल्पिक
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

समर्थित विधिहरू (सबै `settings.a2aEnabled` मा निर्भर छन्):

| विधि             | विवरण                                                               |
| ---------------- | ------------------------------------------------------------------- |
| `message/send`   | सिंक्रोनस स्किल कार्यान्वयन; `{task, artifacts, metadata}` फर्काउँछ |
| `message/stream` | उही स्किल सेटको स्ट्रिमिङ SSE कार्यान्वयन                           |
| `tasks/get`      | `taskId` द्वारा टास्क प्राप्त गर्छ                                  |
| `tasks/cancel`   | `taskId` द्वारा टास्क रद्द गर्छ                                     |

अन्तर्निर्मित स्किलहरू: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`।

### एजेन्ट कार्ड

```bash
GET /.well-known/agent.json
```

सार्वजनिक A2A एजेन्ट कार्ड (नाम, विवरण, क्षमताहरू, स्किल क्याटलग, प्रमाणीकरण योजना) फर्काउँछ — सार्वजनिक रूपमा 1h का लागि क्यास गरिन्छ। प्रमाणीकरण आवश्यक छैन।

### REST सहायकहरू

| विधि | पाथ                          | विवरण                                                                                                                |
| ---- | ---------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| GET  | `/api/a2a/status`            | A2A सक्षम स्थिति + टास्क तथ्याङ्क + क्यास गरिएको एजेन्ट कार्डको सारांश                                               |
| GET  | `/api/a2a/tasks`             | टास्कहरूको सूची — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST | `/api/a2a/tasks`             | (REST सहायकका रूपमा कार्यान्वयन गरिएको छैन — JSON-RPC `message/send` मार्फत सिर्जना गर्नुहोस्)                       |
| GET  | `/api/a2a/tasks/[id]`        | एउटा टास्क प्राप्त गर्छ                                                                                              |
| POST | `/api/a2a/tasks/[id]/cancel` | टास्क रद्द गर्छ                                                                                                      |

**प्रमाणीकरण:** REST सहायकहरू व्यवस्थापन प्रमाणीकरणबिना चल्छन् (ड्यासबोर्डबाट पढ्न मिल्ने); कन्फिगर गरिएको छ भने JSON-RPC `/a2a` रुटले Bearer `OMNIROUTE_API_KEY` प्रयोग गर्छ।

| GET | `/api/evals` | अन्तर्निर्मित इभ्याल सुइटहरू + सबैभन्दा पछिल्ला रनहरूको सूची देखाउँछ |

## ACP (Agent Client Protocol) व्यवस्थापन

चाइल्ड प्रोसेसहरूको रूपमा। यी एन्डपोइन्टहरूले ACP एजेन्ट पहिचान र अनुकूलन एजेन्ट
दर्ता व्यवस्थापन गर्छन्।

| विधि   | पाथ               | विवरण                                                                                                                                                        |
| ------ | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GET    | `/api/acp/agents` | स्थापना स्थिति, संस्करण र बाइनरीसहित सबै ज्ञात CLI एजेन्टहरू (अन्तर्निर्मित + अनुकूलन) सूचीबद्ध गर्छ                                                         |
| POST   | `/api/acp/agents` | अनुकूलन ACP एजेन्ट दर्ता गर्छ वा क्यास रिफ्रेस गर्छ — बडी: `{id, name, binary, versionCommand, providerAlias, spawnArgs, protocol}` वा `{action: "refresh"}` |
| DELETE | `/api/acp/agents` | अनुकूलन ACP एजेन्ट हटाउँछ — क्वेरी प्यारामिटर: `?id=<agentId>`                                                                                               |

**रेस्पोन्सको उदाहरण** (`GET /api/acp/agents`):

```json
{
  "agents": [
    {
      "id": "claude",
      "name": "Claude Code CLI",
      "binary": "claude",
      "version": "1.0.45",
      "installed": true,
      "protocol": "stdio",
      "providerAlias": "claude",
      "isCustom": false
    },
    {
      "id": "my-custom-cli",
      "name": "My Custom CLI",
      "installed": false,
      "protocol": "stdio",
      "providerAlias": "my-provider",
      "isCustom": true
    }
  ],
  "cacheTtlMs": 60000,
  "cacheAge": 1234
}
```

**प्रमाणीकरण:** व्यवस्थापन सत्र (ड्यासबोर्डको `auth_token` कुकी) वा
व्यवस्थापन-स्कोप भएको API कुञ्जी आवश्यक हुन्छ।

पूर्ण विवरणका लागि [ACP फ्रेमवर्क](../frameworks/ACP.md) हेर्नुहोस्।

## प्रमाणीकरण

चार प्रकारका प्रमाणपत्र समूहहरू (ड्यासबोर्ड सत्र, स्थानीय CLI टोकन, `oma_live_…` पहुँच
टोकन, व्यवस्थापन-स्कोप भएको API कुञ्जी) र तिनीहरू इन्फरेन्स कुञ्जीहरूभन्दा कसरी फरक छन् भन्नेबारे
[व्यवस्थापन प्रमाणीकरण](../guides/MANAGEMENT-AUTH.md) हेर्नुहोस्।

- ड्यासबोर्ड रुटहरू (`/dashboard/*`) ले `auth_token` कुकी प्रयोग गर्छन्
- लगइनले सुरक्षित गरिएको पासवर्ड ह्यास प्रयोग गर्छ; उपलब्ध नभएमा `INITIAL_PASSWORD` प्रयोग गर्छ
- `requireLogin` लाई `/api/settings/require-login` मार्फत टगल गर्न सकिन्छ
- `REQUIRE_API_KEY=true` हुँदा `/v1/*` रुटहरूले वैकल्पिक रूपमा Bearer API कुञ्जी आवश्यक पार्छन्
- यस सन्दर्भमा "व्यवस्थापन टोकन" / "व्यवस्थापन-स्कोप भएको API कुञ्जी" भन्नाले उक्त गाइडमा भएका समूहमध्ये कुनै एकलाई जनाउँछ — कुनै अपरिभाषित अतिरिक्त गोप्य प्रकारलाई होइन

> **ब्रेकिङ परिवर्तन (v3.8.0)** — `/api/v1/agents/tasks/*` र कूलडाउन व्यवस्थापन इन्डपोइन्टहरूलाई अब **व्यवस्थापन प्रमाणीकरण** (ड्यासबोर्ड `auth_token` कुकी वा व्यवस्थापन-स्कोप भएको API कुञ्जी) आवश्यक पर्छ। पहिले यी रुटहरूलाई प्रमाणीकरणबिना कल गर्ने क्लाइन्टहरूले `401 Unauthorized` प्राप्त गर्नेछन्। कमिट `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`) हेर्नुहोस्।
