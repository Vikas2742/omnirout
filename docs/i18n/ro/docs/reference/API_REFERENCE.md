## Completări de chat

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### Antete personalizate

| Antet                    | Direcție   | Descriere                                                                                                                                                                                                                                              |
| ------------------------ | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `X-OmniRoute-No-Cache`   | Solicitare | Setați la `true` pentru a evita cache-ul                                                                                                                                                                                                               |
| `x-omniroute-no-memory`  | Solicitare | Setați la `true` pentru a omite injectarea memoriei și a abilităților pentru această solicitare (reflectă comportamentul fără cache; evită costul suplimentar per apel aferent tokenurilor și costurilor)                                              |
| `X-OmniRoute-Progress`   | Solicitare | Setați la `true` pentru evenimente de progres                                                                                                                                                                                                          |
| `X-Session-Id`           | Solicitare | Cheie de sesiune persistentă pentru afinitatea externă a sesiunii                                                                                                                                                                                      |
| `x_session_id`           | Solicitare | Este acceptată și varianta cu caracter de subliniere (HTTP direct)                                                                                                                                                                                     |
| `X-OmniRoute-Session-Id` | Solicitare | Etichetă de sesiune/conversație furnizată de apelant (utilizată și de memorie). Când este prezentă, este stocată textual în `call_logs.session_tag` pentru atribuirea costurilor per sesiune (#8249) — nu este generată niciodată atunci când lipsește |
| `Idempotency-Key`        | Solicitare | Cheie de deduplicare (interval de 5 s)                                                                                                                                                                                                                 |
| `X-Request-Id`           | Solicitare | Cheie alternativă de deduplicare                                                                                                                                                                                                                       |
| `x-omniroute-connection` | Solicitare | Fixează o solicitare pentru un singur model la o conexiune a furnizorului (cont), pe baza id-ului acesteia — consultați [Fixarea contului per solicitare](#account-pinning-per-request)                                                                |
| `X-OmniRoute-Cache`      | Răspuns    | `HIT` sau `MISS` (fără streaming)                                                                                                                                                                                                                      |
| `X-OmniRoute-Idempotent` | Răspuns    | `true` dacă solicitarea a fost deduplicată                                                                                                                                                                                                             |
| `X-OmniRoute-Progress`   | Răspuns    | `enabled` dacă urmărirea progresului este activată                                                                                                                                                                                                     |
| `X-OmniRoute-Session-Id` | Răspuns    | ID-ul efectiv al sesiunii utilizat de OmniRoute                                                                                                                                                                                                        |
| `X-OmniRoute-Request-Id` | Răspuns    | ID-ul de corelare al solicitării (când este cunoscut)                                                                                                                                                                                                  |
| `X-OmniRoute-Version`    | Răspuns    | Versiunea buildului OmniRoute (prezentă întotdeauna)                                                                                                                                                                                                   |
| `X-OmniRoute-Cost-Saved` | Răspuns    | Suma în USD economisită de cache la un rezultat HIT (numai pentru accesările din cache)                                                                                                                                                                |
| `X-OmniRoute-Decision`   | Răspuns    | Urmărirea rutării: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` este strategia combinației sau `single` pentru o solicitare fără combinație) — este prezentă întotdeauna în răspunsurile de finalizare                                |

> Notă Nginx: dacă vă bazați pe antete care conțin caractere de subliniere (de exemplu, `x_session_id`), activați `underscores_in_headers on;`.

#### Fixarea contului pentru fiecare solicitare

Atunci când un furnizor are mai multe conexiuni (conturi sau chei), OmniRoute alege în mod normal una
prin strategia sa de selectare a contului. În schimb, o solicitare poate fixa o anumită conexiune
cu antetul `x-omniroute-connection`:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Unde găsiți ID-ul.** Deschideți pagina furnizorului în panoul de control
  (**Panou de control → Furnizori → <furnizor>**) și faceți clic pe eticheta de ID `xxxxxxxx…` dintr-un rând
  de conexiune — astfel se copiază ID-ul complet al conexiunii.
- **Ce solicitări îl respectă.** Solicitările cu un singur model (`provider/model`) către
  `/v1/chat/completions`, `/v1/messages` și `/v1/responses`. Combinațiile ignoră antetul: fixați
  un cont pentru fiecare pas al combinației prin conexiunea proprie a pasului.
- **Fixarea este strictă, nu o preferință.** Conexiunea fixată este utilizată exclusiv. O
  eroare apărută în cadrul solicitării înregistrează perioada de așteptare a contului, dar **nu** comută la un
  alt cont al aceluiași furnizor.
- **Perioada de așteptare și cota anulează fixarea.** Cât timp conexiunea fixată se află în perioada de așteptare,
  are cota epuizată sau este blocată de o politică privind cotele, solicitările ulterioare recurg la celelalte
  conexiuni ale furnizorului, exact ca traficul fără fixare.
- **ID-urile necunoscute sau dezactivate provoacă o eroare.** Un ID care nu se află în grupul activ al furnizorului (șters,
  dezactivat sau aparținând altui furnizor) nu lasă niciun cont eligibil, astfel încât solicitarea
  eșuează în loc să fie direcționată în mod silențios în altă parte.

Claude Code trimite antete personalizate prin `ANTHROPIC_CUSTOM_HEADERS`. Introduceți această variabilă în blocul `env`
din `~/.claude/settings.json` sau într-un fișier `.claude/settings.json` la nivel de proiect pentru a fixa un cont diferit
pentru fiecare proiect:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Sursă: `src/sse/handlers/chat.ts` (citirea antetului), `src/sse/services/auth.ts` și
`src/sse/services/sessionAffinityPin.ts` (anularea fixării și verificarea absenței din grup).

> **Antete de telemetrie a costurilor:** răspunsurile reușite fără streaming includ și setul de telemetrie a costurilor `X-OmniRoute-*` — `X-OmniRoute-Response-Cost` (USD, cu 10 zecimale fixe; `0.0000000000` pentru operațiuni gratuite/fără preț), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` și `X-OmniRoute-Fallback-Attempts` (numai când > 0), plus `X-OmniRoute-Request-Id` și `X-OmniRoute-Version`. Acestea sunt emise de completările de chat, `/v1/responses`, `/v1/messages`, **precum și de endpointurile media** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` și `/v1/moderations` (cost întotdeauna `0`). Costul media este calculat pentru fiecare modalitate (per imagine, per secundă, per caracter, per unitate de căutare) atunci când informațiile despre preț sunt disponibile; în caz contrar, este `0` (funcționare permisivă în caz de eroare).

> **Semantica costului pentru rezultatele din cache:** la un rezultat găsit în cache-ul semantic (`X-OmniRoute-Cache-Hit: true`) nu se efectuează niciun apel în amonte, astfel încât `X-OmniRoute-Response-Cost` este `0.0000000000` (costul **incremental** al furnizării rezultatului din cache). Costul inițial/care ar fi fost suportat este raportat separat în `X-OmniRoute-Cost-Saved`. Consumatorii datelor de facturare trebuie să însumeze `X-OmniRoute-Response-Cost` (rezultatele din cache nu costă nimic); instrumentele de analiză a cache-ului pot agrega `X-OmniRoute-Cost-Saved`.

## Închirieri exclusive gestionate ale sesiunilor

Închirierea exclusivă gestionată a sesiunilor este un contract de rutare opțional, independent de client: un singur deținător activ
deține o conexiune OmniRoute eligibilă. Aceasta nu închiriază un model, nu necesită OAuth, nu identifică un
anumit client și nu necesită un anumit furnizor.

Cheia API utilizată pentru autentificare trebuie să aibă domeniul `lease:exclusive` și o listă explicită nevidă
`allowedConnections`. Limita mutațiilor bazei de date impune prezența ambelor câmpuri împreună la crearea cheii
și la actualizările parțiale.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Răspunsurile reușite la achiziționare, reînnoire și eliberare expun marcajele temporale, `state` și valoarea pozitivă exactă
`generation`, dar niciodată conexiunea selectată sau acreditările. Pentru reînnoire și eliberare, generația este furnizată în
corpul JSON:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Deținătorul unei închirieri active poate solicita în mod explicit metadate de afișare care protejează confidențialitatea pentru asocierea sa curentă:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Această acțiune opțională de verificare a stării este protejată prin deținătorul opac, cheia API gestionată și autentificată și generația
activă exactă, într-o singură tranzacție a bazei de date. `displayName` reprezintă numai numele configurat al
conexiunii, fără spațiile albe de la început și sfârșit; valoarea sa este `null` atunci când nu există un nume configurat sigur. OmniRoute nu înlocuiește niciodată acest nume cu
o adresă de e-mail sau cu o identitate de cont generată. Valoarea furnizorului este o etichetă de afișare nesensibilă și niciodată
un identificator generat pentru un furnizor compatibil. Acreditările, tokenurile, cookie-urile, identificatorii bruți ai conexiunilor sau ai cheilor
API, hashurile deținătorilor, secretele de protecție și datele interne de rutare sunt excluse.

Căutările cu o cheie greșită, un deținător greșit, o generație depășită, lipsă, expirată, eliberată sau invalidată
returnează toate aceeași eroare `409 LEASE_FENCE_STALE`, fără metadate despre conexiune. Un client care a primit răspunsul de așteptare a capacității nu are nicio asociere activă pe care să o poată inspecta. Atunci când rutarea mută o închiriere activă,
aceeași generație rămâne validă, iar starea returnează atomic noua asociere, niciodată pe cea veche.
Clienții existenți rămân neschimbați, deoarece răspunsurile de achiziționare, reînnoire, eliberare și așteptare își păstrează
formatele anterioare.

Acest contract de server nu modifică endpointul `/status` din OpenAI Codex standard. În prezent, Codex standard raportează
furnizorul modelului și starea încorporată a autentificării/contului, dar nu afișează metadate arbitrare despre conturile
furnizorilor personalizați; o integrare viitoare cu un client trebuie să apeleze această acțiune și să decidă cum să
afișeze `connection.displayName`.

Fiecare cerere de inferență gestionată furnizează apoi ambele antete de control:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Deținătorul exact, generația, conexiunea activă și cheia API autentificată sunt verificate
imediat înaintea fiecărei încercări upstream acceptate. Reutilizarea deținătorului și a generației cu altă cheie eșuează chiar
și atunci când cheia respectivă permite aceeași conexiune. Valorile brute ale deținătorilor nu sunt persistate, înregistrate în jurnale, păstrate în
instantaneul cererii sau transmise upstream.

Concurența temporară returnează HTTP `429` cu `Retry-After` și:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Acest răspuns indică numai că setul obișnuit de conexiuni eligibile nu era gol și că fiecare candidat disponibil era
deținut de o închiriere activă străină. Modelele/furnizorii neacceptați, neconcordanțele cu politica, perioada de așteptare, cota,
starea de funcționare și alte erori obișnuite de eligibilitate își păstrează răspunsurile OmniRoute existente.

### `x-omniroute-compression`

Suprascrierea per cerere a planului de compresie. Are cea mai mare prioritate — prevalează asupra suprascrierii combinației de
rutare, profilului activ, declanșării automate și valorii implicite din panou. Valori:

| Valoare       | Efect                                                                                                            |
| ------------- | ---------------------------------------------------------------------------------------------------------------- |
| `off`         | Fără compresie pentru această cerere.                                                                            |
| `default`     | Profilul implicit derivat din panou (ignoră profilul activ). Motoarele cu pierderi rămân dezactivate.            |
| `safe`        | Numai deduplicare și compactarea spațiilor albe.                                                                 |
| `allow-lossy` | Păstrează planul operatorului pentru această cerere, inclusiv rezumatele și rescrierile de stil.                 |
| `engine:<id>` | Un singur motor, dacă este activat, de ex. `engine:rtk`. Activare per cerere pentru motorul respectiv.           |
| `<combo>`     | O combinație denumită, identificată mai întâi după nume (fără a ține cont de litere mari și mici), apoi după ID. |

Note:

- Valorile necunoscute sunt ignorate (cererea nu este niciodată respinsă); rezoluția continuă conform priorității normale a operatorului.
- Dacă mai multe combinații au același nume, transmiteți **id-ul** combinației pentru o potrivire deterministă.
- O combinație al cărei nume este `off` sau `default` nu poate fi selectată după nume (aceste cuvinte-cheie sunt interpretate mai întâi); referiți o astfel de combinație prin ID-ul său.
- Comutatorul principal de compresie este o limitare strictă: atunci când compresia este dezactivată global, acest antet nu o poate activa.

Planul aplicat este returnat în antetul răspunsului:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

unde `<source>` este una dintre valorile `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` sau `off`.

## Încorporări

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Furnizori disponibili: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

ID-urile din catalog sunt de forma `provider/model` (exemplu: `jina-ai/jina-embeddings-v5-omni-small`). ID-urile simple ale modelelor Jina care apar în registru (de exemplu, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) sunt, de asemenea, rezolvate. Operațiunile Jina de încorporare/rerangare/clasificare/segmentare utilizează mai întâi acreditările `jina-ai` din tabloul de bord; `JINA_AI_API_KEY` este utilizată ca alternativă numai când nu există nicio cheie în tabloul de bord. Cardul `jina-reader` este destinat exclusiv serviciului Reader / `r.jina.ai` (`POST /v1/web/fetch`) și nu furnizează niciodată încorporări sau rerangare.

Modelele din registru care declară suport multimodal acceptă, de asemenea, până la 32 de elemente structurate
independente de furnizor. Tipurile de elemente media sunt `text`, `image`, `audio`, `video` și `document`. Câmpul media `source`
este fie `{"type":"url","url":"https://..."}`, fie
`{"type":"base64","data":"...","media_type":"..."}`.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
și aliasul familiei `jina-ai/jina-embeddings-v5-omni` → omni-small) acceptă, de asemenea, documentele EmbeddingsV5Request native Jina
și **le transmite intacte** către `https://api.jina.ai/v1/embeddings`:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Valorile native `{ image | audio | video | pdf }` pot fi un URL HTTPS public, un URI `data:` sau date base64
brute. OmniRoute nu convertește acele obiecte în șiruri și nici nu preia URL-urile native ale imaginilor — Jina preia
direct conținutul media public. Câmpurile Jina suplimentare (`task`, `normalized`, `truncate`, `embedding_type`) sunt
transmise mai departe. SKU-urile Jina exclusiv text continuă să respingă documentele care nu sunt text.

Limite de securitate și transport:

- URL-urile media la distanță trebuie să fie HTTPS publice. Elementele canonice `{type,source:url}` sunt preluate
  pe server (cu revalidarea redirecționărilor, expirare, limite de dimensiune, DNS public și fixarea conexiunii) și
  încorporate înainte de apelarea furnizorului. Elementele native Jina `{image:"https://..."}` sunt transmise ca atare
  după aceeași verificare pentru HTTPS public; Jina preia URL-ul.
- Conținutul media base64 inclus este limitat la 8 MiB decodați per element și la 16 MiB decodați pentru întreaga cerere.

Conversia pentru furnizori (elementele canonice nu sunt niciodată transmise fără modificări):

- Modelele multimodale Jina: fiecare element de nivel superior devine un obiect cu cheie de modalitate
  (`text` / `image` / `audio` / `video` / `pdf`), utilizând URI-uri de date pentru conținutul media inclus; câte un vector pentru
  fiecare element de nivel superior.
- Familia Gemini Embedding 2: un tablou de nivel superior devine o singură cerere nativă
  `models/{model}:embedContent` cu `content.parts` (`text` sau `inline_data`).
- llama.cpp (`llama-cpp/<model>`, orice model încărcat de serverul local): elementele canonice `text`
  devin șiruri simple, iar `image` / `audio` / `video` devin fiecare câte un obiect
  `{"content": [part]}`, utilizând părțile de conținut pentru chat ale llama-server (`image_url`,
  `input_audio` cu formatul `wav` / `mp3` / `flac`, `input_video`) și date incluse; câte un vector
  pentru fiecare element de nivel superior. Serverul trebuie să ruleze cu `--embedding --mmproj …`; fără un proiector,
  acesta respinge direct conținutul media. `document` nu este acceptat.
- Modelele necunoscute/dinamice fără metadate explicite privind modalitatea resping datele de intrare structurate cu HTTP 400.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Combinațiile model/modalitate neacceptate returnează HTTP 400 în loc să convertească forțat elementul. Câmpurile de extensie
care nu țin de datele de intrare din cererile vechi cu șiruri/tokenuri continuă să fie transmise fără modificări.


```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
```

Furnizorii disponibili includ OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (local), ComfyUI (local).

`n` returnează `n` imagini în `data[]`. Pentru furnizorii al căror API din amonte returnează o imagine per apel
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), sunt efectuate `n` apeluri separate în amonte, cu cel mult 4 în desfășurare simultan. O valoare

reproductibile. `n` este limitat la 10. Solicitarea eșuează în întregime dacă oricare dintre apeluri eșuează. Lista

`open-sse/handlers/imageGeneration/fanOut.ts`.

ZenMux reutilizează conexiunea existentă cu cheie API și acceptă prefixele `zenmux/` sau `zm/`:

- `zenmux/openai/gpt-image-2` utilizează API-ul OpenAI Images al ZenMux. Opțiunile includ `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` și `response_format`.
- Alți editori, precum `zm/meta/muse-image-1.0`, utilizează endpointul Vertex AI `:predict`
  al ZenMux. `n` este mapat la `sampleCount`, `aspect_ratio` la `aspectRatio`, iar `image_size`
  (`1K`, `2K`, `4K`) la `sampleImageSize`. O valoare în pixeli pentru `size` furnizează doar un raport de aspect,
  nu dimensiuni garantate în pixeli. Rapoartele, rezoluțiile și numerele acceptate variază în funcție de model.
- `zm/inclusionai/ming-image-0.1-design` își alege propriile dimensiuni. Omiteți `size`,
  `aspect_ratio` și `image_size`; valorile explicite returnează HTTP 400. Formatele PNG, JPEG și WebP
  pot fi solicitate prin `output_format`.

Această integrare acceptă generarea text-imagine, nu editarea imaginilor de referință. Rezultatul Vertex
este normalizat în `data[].b64_json`; `response_format: "url"` returnează un URL HTTPS din amonte
sau un URL de date base64 atunci când sunt disponibili doar octeții imaginii. Rezultatele goale/filtrate
returnează o eroare, nu un răspuns de succes gol. Accesul la modele depinde de contul ZenMux.
Consultați [API-ul Vertex al ZenMux](https://docs.zenmux.ai/api/vertexai/generate-images) și
[API-ul OpenAI Images](https://docs.zenmux.ai/api/openai/generate-an-image).

## OCR pentru documente

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` selectează furnizorul OCR printr-un prefix `provider/model`; un identificator de model simplu (de exemplu,
`mistral-ocr-latest`) este asociat furnizorului său înregistrat, iar dacă `model` este omis, valoarea implicită este
Mistral (`mistral-ocr-latest`). Furnizori înregistrați (`open-sse/config/ocrRegistry.ts`):

| ID furnizor                   | ID model             | Valoare `model`                                                | Note                                                                                                                            |
| ----------------------------- | -------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (sau simplu `mistral-ocr-latest`) | Sincron — răspunsul este returnat direct de apelul unic din amonte.                                                             |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                    | Asincron în amonte (`analyze` + interogare) — consultați secțiunea de mai jos.                                                  |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                        | Sincron, prin endpointul partener Vertex AI `openapi/chat/completions` — consultați mai jos detaliile despre autentificare/URL. |

Toți cei trei furnizori răspund folosind același corp în format Mistral:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Fluxul de interogare Azure Document Intelligence

API-ul `analyze` al Azure Document Intelligence este asincron: solicitarea inițială returnează un antet
`Operation-Location` în locul unui corp, iar rezultatul trebuie interogat periodic. Handlerul
(`open-sse/handlers/ocr.ts`) interoghează acel URL la fiecare secundă, pentru cel mult 30 de încercări, eșuează imediat (nu
continuă interogarea) în cazul unui răspuns de interogare care nu este `ok` sau al unei stări `"failed"` și returnează `504` dacă
operațiunea încă rulează după epuizarea numărului de încercări. Răspunsul Azure final este
normalizat în aceeași structură `pages`/`markdown` utilizată de Mistral înainte de a fi returnat
apelantului, astfel încât codul clientului nu trebuie să trateze furnizorul ca pe un caz special.

### Autentificarea și rezolvarea endpointului Vertex AI DeepSeek OCR

`vertex-deepseek-ocr` reutilizează aceeași autentificare Vertex AI pe care OmniRoute o acceptă deja pentru
traficul de chat/imagini (`open-sse/executors/vertex.ts`): cheia API a conexiunii este fie o
credențială JSON de cont de serviciu (schimbată cu un token de acces OAuth cu durată scurtă prin fluxul JWT bearer),
fie un token de acces OAuth deja emis, utilizat ca atare. URL-ul endpointului din amonte este endpointul partener generic
`openapi/chat/completions` al Vertex, construit pe baza proiectului și regiunii conexiunii — valorile explicite
`providerSpecificData.project`/`providerSpecificData.region` au întotdeauna prioritate;
în caz contrar, proiectul este derivat din `project_id` din JSON-ul contului de serviciu, iar regiunea
are valoarea implicită `us-central1`. Ambele rezolvări au loc în `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) și sunt utilizate de
`src/app/api/v1/ocr/route.ts` înainte de expedierea către `handleOcr`.

## Listarea modelelor

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ Returnează toate modelele de chat, încorporare și imagine + combinațiile în format OpenAI
```

### Prefixele ID-urilor modelelor (`?prefix=`)

Majoritatea modelelor sunt prezentate sub un **prefix al furnizorului**. Prefixul obținut este controlat de
indicatorul de funcționalitate `MODELS_CATALOG_PREFIX_MODE` și poate fi suprascris **pentru fiecare solicitare** printr-un
parametru de interogare — util pentru un client care dorește o listă curată fără a modifica setarea
la nivel de server pentru toți ceilalți:

```bash
GET /v1/models?prefix=alias        # un ID per model — prefixul scurt al aliasului
GET /v1/models?prefix=dual         # ambele forme (valoarea implicită a serverului)
GET /v1/models?prefix=canonical    # numai prefixul complet al ID-ului furnizorului
```

| Mod         | Emite                                                    | Note                                                                                                                                                                                                                              |
| ----------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **și** `claude/claude-sonnet-4-6` | **Implicit.** Ambele ID-uri sunt direcționate către același model; sunt păstrate astfel încât configurațiile clienților care au codificat direct oricare dintre forme să continue să funcționeze. Aproximativ dublează catalogul. |
| `alias`     | `cc/claude-sonnet-4-6`                                   | O intrare per model. Furnizorii fără un alias distinct își emit în continuare intrarea, astfel încât nu se pierde nimic.                                                                                                          |
| `canonical` | `claude/claude-sonnet-4-6`                               | O intrare per model sub prefixul complet al ID-ului furnizorului. Furnizorii fără un alias distinct (de exemplu, `antigravity/…`, `agy/…`) își emit și aici ID-ul unic, astfel încât nu se pierde nimic.                          |

O replică în modul `dual` poate fi recunoscută și fără parametrul de interogare: conține un câmp `parent`
care indică ID-ul principal.

Clienții care afișează un selector de modele ar trebui să solicite `?prefix=alias` — aceasta este abordarea utilizată de
[extensia OmniCopilot pentru VS Code](../guides/VSCODE-COPILOT.md).

### Filtre de descoperire (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` acceptă filtre de descoperire opționale. Fără niciunul dintre acestea, răspunsul rămâne
neschimbat. Acestea restrâng catalogul pe care apelantul îl poate vedea deja (permisiunile cheii API se aplică mai întâi)
și sunt aplicate înaintea paginării în stil OpenAI prin `limit` / `after`:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # fiecare capabilitate listată trebuie să fie adevărată
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` din catalog; rândurile fără unul sunt `chat`
GET /v1/models?q=sonnet&limit=10                           # potrivire fără a ține cont de majuscule/minuscule după ID sau nume
```

| Parametru     | Valori                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | număr întreg nenegativ, comparat cu `context_length`                                                |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 de caractere                                                                                  |

O valoare necunoscută sau un `min_context` care nu este un număr întreg nenegativ (de exemplu, `1.5`)
returnează HTTP `400`, iar mesajul enumeră valorile valide. Implementare:
`src/app/api/v1/models/catalogFilters.ts`.

### Lista restrânsă de modele (`POST /v1/models/query`)

`POST /v1/models/query` returnează o listă scurtă și deterministă din același catalog, cu aceeași
autentificare și aceeași vizibilitate per cheie ca `GET /v1/models`:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Fiecare câmp este opțional. `capabilities` și `exclude` acceptă o matrice sau un șir separat prin virgule;
`max_output` este comparat cu `max_output_tokens`. Rezultatele sunt sortate după `owned_by`, apoi după `id`.
Valoarea implicită pentru `limit` este `20`, iar valorile peste `100` sunt limitate la `100`. Un JSON nevalid, un câmp
necunoscut sau o valoare nevalidă returnează HTTP `400`.

### Modele de chat ascunse individual

Un model marcat ca **Ascuns** pe pagina furnizorului său este exclus din catalog și respins
cu HTTP `404` / `model_not_found` atunci când este solicitat explicit. Verificarea utilizează furnizorul
și modelul rezolvate, inclusiv aliasurile furnizorilor, prefixele nodurilor furnizorilor compatibili și
valorile implicite ale conexiunii. O combinație omite țintele ascunse și poate utiliza o alternativă vizibilă; atunci când nu
rămâne nicio țintă executabilă, returnează același cod de eroare. Anularea ascunderii intră în vigoare la următoarea
solicitare. Suprascrierile de vizibilitate exclusiv pentru imagini nu ascund modelul de chat cu același ID.

Această setare individuală a modelului este separată de
[listele de permitere/interzicere pentru expunerea modelelor](../routing/MODEL_EXPOSURE_LIST.md), care filtrează
prezentarea catalogului și candidații pentru rutarea automată, păstrând în același timp expedierea explicită. Permisiunile
modelelor pentru cheile API continuă să se aplice independent. Modul implicit pentru prefixul catalogului rămâne `dual`.

### Variante de modele fără gândire

Pentru modelele Claude cu funcționalitate de gândire, `/v1/models` prezintă și o variantă **fără gândire**, al cărei ID are prefixul `claude-3-omniroute-no-thinking/`:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Selectarea acestui id (de ex., într-o configurație Claude Code care atașează întotdeauna un bloc `thinking`) este rezolvată înapoi la valoarea reală `<provider>/<model>`, cu raționamentul suprimat — `thinking:{type:"disabled"}` pe calea `/v1/messages` sau câmpurile `reasoning`/`reasoning_effort` eliminate pe calea `/v1/chat/completions`. Varianta este listată numai pentru modelele din familia Claude care acceptă funcționalitatea de gândire **și** respectă valoarea `disabled` (astfel, de ex., modelele exclusiv adaptive care resping valoarea `disabled` sunt excluse). Operatorii pot activa sau dezactiva forțat varianta pentru fiecare model prin `ModelSpec.noThinkingAlias`.

## Generarea audio cu ElevenLabs

Configurați în OmniRoute o conexiune la furnizorul `elevenlabs` folosind cheia API ElevenLabs.
Clienții se autentifică folosind cheia lor **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
gateway-ul furnizează cheia stocată a furnizorului drept `xi-api-key`. Nu trimiteți niciodată o cheie ElevenLabs
drept token bearer al gateway-ului.

| Metodă | Cale                        | Răspuns                                     | Categoria endpointului pentru cheia API |
| ------ | --------------------------- | ------------------------------------------- | --------------------------------------- |
| POST   | `/v1/sound-generation`      | Octeți audio nativi                         | `elevenlabs`                            |
| POST   | `/v1/music`                 | Octeți audio nativi                         | `music`                                 |
| POST   | `/v1/music/stream`          | Octeți audio transmiși în flux              | `music`                                 |
| POST   | `/v1/music/detailed`        | Audio multipart nativ și plan de compoziție | `music`                                 |
| POST   | `/v1/music/detailed/stream` | Metadate SSE native și fragmente audio      | `music`                                 |
| POST   | `/v1/music/plan`            | Plan de compoziție JSON                     | `music`                                 |

Aceste endpointuri completează rutele existente `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` și `/v1/speech-to-text`. Câmpurile JSON native
și parametrii de interogare precum `output_format` și `enable_logging` sunt păstrați.
Răspunsurile `/v1/music/detailed` își păstrează delimitatoarele multipart; procesați-le ca multipart.
`/v1/music/detailed/stream` returnează `text/event-stream` cu metadatele compoziției și
fragmente audio base64 în evenimente SSE. Toate cele șase rute acceptă solicitări preliminare CORS.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Un efect sonor scurt. Durată: între 0,5 și 30 de secunde.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Durata muzicii este exprimată în milisecunde: între 3000 și 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Utilizați `/v1/music/stream` cu același corp JSON pentru livrarea audio incrementală. Compoziția
acceptă exact unul dintre `prompt` sau `composition_plan`; `/v1/music/plan` necesită `prompt`
și acceptă opțional `source_composition_plan`. Schemele native păstrează câmpurile suplimentare
ale furnizorului, astfel încât versiunile planurilor de compoziție și opțiunile de ajustare fină să ajungă la ElevenLabs.

Endpointul unificat `/v1/music/generations` acceptă, de asemenea, `elevenlabs/music_v1`,
`elevenlabs/music_v2` și `elevenlabs/music_v2_5`. Cu o conexiune ElevenLabs activă,
aceste modele sunt expuse de catalogul muzical. Acest endpoint returnează
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`. Câmpul său `duration` este exprimat în
secunde și este mapat la `music_length_ms`; un `music_length_ms` explicit are prioritate.
`instrumental` este mapat la `force_instrumental`, câmpul nativ având prioritate.
Utilizați endpointurile native de streaming pentru transmiterea în flux și endpointul nativ de compoziție
pentru solicitările bazate exclusiv pe un plan de compoziție.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Restricțiile privind endpointul, modelul, bugetul și conexiunea se aplică înaintea unui apel către serviciul din amonte. Rutele
native returnează neschimbate codurile de stare și corpurile erorilor din amonte, inclusiv `402` pentru o restricție
de plan și `429` pentru o limită de cotă. Anteturile `character-cost`, `song-id`, `request-id` și `retry-after`
sunt păstrate atunci când sunt prezente. Un sold de credite gratuite nu garantează accesul la fiecare
model muzical, format de ieșire sau funcționalitate API: ElevenLabs decide drepturile de acces pentru fiecare solicitare.
Endpointul unificat păstrează codurile de stare ale erorilor în învelișul de eroare normalizat al OmniRoute.

Contracte din amonte: [efecte sonore](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[compoziție muzicală](https://elevenlabs.io/docs/api-reference/music/compose) și
[detalii despre muzica transmisă în flux](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

> **Noduri ale furnizorilor pentru rerank:** `POST /v1/rerank` direcționează cererile și către noduri de furnizor compatibile cu OpenAI
> (oMLX, vLLM, Infinity, TEI în spatele unui gateway, …), adresate ca `<node-prefix>/<model>`. Nodurile
> loopback (`localhost`, `127.0.0.1`, `172.16.0.0/12`) sunt întotdeauna eligibile, la fel ca numele de gazdă
> enumerate de operator în `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` (de exemplu, numele unui serviciu Docker/Compose,
> precum `http://reranker:8080/v1`; acestea sunt apelate direct, niciodată prin `HTTP(S)_PROXY` sau prin
> proxy-ul fixat al unei conexiuni). Nodurile de pe orice altă
> gazdă — un dispozitiv din LAN sau un peer Tailscale — sunt eligibile numai atunci când operatorul activează
> indicatorul de funcționalitate `RERANK_REMOTE_PROVIDER_NODES` **și** URL-ul de bază al nodului respectă politica
> privind URL-urile de ieșire ale furnizorului (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`).
> Etapa de rerank a motorului de memorie apelează această rută prin
> loopback, astfel încât aceeași regulă se aplică pentru `rerankProviderModel` în setările pentru memorie.
>
> **Structuri ale serverelor locale:** nodul este apelat la `<base>/v1/rerank` și, în cazul unui răspuns 404, la `<base>/rerank`
> (Infinity, TEI). Corpul cererii upstream include atât denumirile Cohere/OpenAI (`documents`,
> `return_documents`), cât și denumirile TEI (`texts`, `return_text`), iar răspunsul upstream este
> normalizat la structura Cohere: răspunsul TEI simplu `[{index, score, text}]`, răspunsul `{results: [{index, score}]}`
> de la gateway-uri minimale și răspunsul în stil Voyage `{data: [...]}` sunt toate returnate clientului ca
> `{results: [{index, relevance_score, document?}]}`, sortate după scor și limitate la `top_n`.

> **Descoperirea nodurilor furnizorilor:** modelele de pe un nod de furnizor compatibil cu OpenAI apar în `GET /v1/models`
> sub prefixul nodului. Rândurile care nu conțin metadate despre endpoint (situație tipică pentru listările locale `/v1/models`)
> moștenesc proprietatea `apiType` a nodului, astfel încât modelele unui nod `embeddings` au `type: "embedding"`, iar
> modelele unui nod `rerank` au `type: "rerank"` în loc să folosească implicit tipul chat; o valoare explicită
> `supportedEndpoints` dintr-un rând sincronizat sau adăugat manual are în continuare prioritate.

### `provider_options` pentru Exa și Tavily

Exa și Tavily citesc câmpurile specifice furnizorului dintr-un container cu spațiu de nume:
`provider_options.exa` (sau `provider_options["exa-search"]`) și `provider_options.tavily`
(sau `provider_options["tavily-search"]`). Sunt transmise mai departe numai cheile de mai jos. Fiecare este
verificată în raport cu propria schemă Zod din `open-sse/handlers/search/providerOptionsPassthrough.ts`,
iar o cheie cu un tip incorect este eliminată. Orice altă cheie este ignorată, inclusiv autentificarea, URL-ul de bază,
`stream` și `outputSchema`. Cheile plate utilizate de ceilalți furnizori (`cx`, `depth`, ...) funcționează
ca înainte.

| Furnizor | Câmpuri de nivel superior                                                                                                                                                                                                                                                                                                                                                 | Imbricate                                                                                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa      | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (primitive plate), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                              | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` îmbinate peste valoarea implicită `{ text: true, highlights: true }` |
| Tavily   | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                           |

Câmpurile generice au întotdeauna prioritate: `query`, `max_results`, `filters` (domenii), `country` și
subiectul derivat din `search_type`. În Exa, `search_type: "news"` păstrează `category: "news"`.
Tavily acceptă și `search_type: "finance"` (`topic: "finance"`).

Câmpul generic `time_range` ajunge acum la ambii furnizori: Exa primește `startPublishedDate` (marcă temporală ISO),
iar Tavily primește `start_date` (`YYYY-MM-DD`). O dată explicită din `provider_options`
o suprascrie pe cea mapată.

Rezultatele Exa păstrează `id`, `highlight_scores`, `summary`, `subpages`, `entities` și `extras` în
`provider_raw`. Rezultatele Tavily păstrează `images` și `favicon`.

Contabilizarea costurilor utilizează în continuare registrul plat `costPerQuery`. Tavily taxează
`search_depth: "advanced"` cu mai multe credite per apel, iar diferența respectivă nu este reflectată în
`usage.search_cost_usd`.

## API Web Fetch

Extrage conținutul dintr-un URL prin intermediul unui furnizor web-fetch configurat (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract).

Parallel Extract (`parallel-search`, aceeași cheie API ca Parallel Search) returnează numai Markdown
— orice alt `format` produce un răspuns `400` — și limitează conținutul la 100.000 de caractere. Atunci când
pagina țintă nu poate fi extrasă, serviciul din amonte raportează acest lucru într-un răspuns HTTP 200;
OmniRoute îl expune ca `422`, cu un mesaj fix.

| Metodă | Cale            | Descriere                                                 |
| ------ | --------------- | --------------------------------------------------------- |
| POST   | `/v1/web/fetch` | Preia/extrage un URL — corp validat de `v1WebFetchSchema` |

**Autentificare:** cheie API Bearer (`extractApiKey` + `isValidApiKey`). Politica este aplicată prin `enforceApiKeyPolicy`.

**Fallback care ține cont de cotă (#8297):** când nu este specificat niciun `provider` explicit, lista
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) este
parcursă într-o ordine fixă de
prioritate (fill-first) — un furnizor configurat, dar cu rata limitată, este omis
în loc să întrerupă imediat cererea, iar o eroare reîncercabilă/de cotă a serviciului din amonte
(HTTP 429 întotdeauna; 402/403 pentru nivelurile gratuite de tip cotă ale Firecrawl/Tavily/TinyFish —
nu pentru Jina Reader și niciodată pentru o simplă cerere incorectă 400) determină trecerea la
următorul furnizor neîncercat pentru care există acreditări, în timpul procesării cererii. Când toți furnizorii din
listă sunt epuizați, endpointul returnează un singur `429` (cu un antet `Retry-After`)
în locul răspunsului generic anterior `400`. Când este solicitat un `provider`
explicit, **nu** există fallback silențios — un furnizor explicit cu rata limitată sau care eșuează
își expune propria eroare (`429` dacă rata este limitată, în caz contrar starea
serviciului din amonte).

## Streaming prin WebSocket

```bash
GET /v1/ws?handshake=1
```

Validează un handshake de upgrade WebSocket și returnează mesajele exemplificative ale protocolului pe fir (`request`, `cancel`). Cadrele WS propriu-zise sunt gestionate de serverul WS inclus, în afara tabelului de rute Next.js.

**Autentificare:** cheie API Bearer în timpul handshake-ului.

### Responses API prin WebSocket (numai codex)

```bash
# Același host:port ca API-ul HTTP (implicit 20128); efectuați upgrade-ul conexiunii:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (sau: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Primul cadru TREBUIE să fie response.create:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Un proxy Responses-API-over-WebSocket este conectat **exclusiv la `codex`** (backendul ChatGPT).
Acesta ascultă pe același port ca API-ul/panoul de control, la căile `/v1/responses`,
`/responses` și `/api/v1/responses`. La primul cadru `response.create`, acesta
autentifică + pregătește prin puntea internă `codex-responses-ws`, selectează o
conexiune OAuth codex și creează un tunel către `wss://chatgpt.com/backend-api/codex/responses`
prin transportul `wreq-js`. **Modelele care nu sunt codex sunt respinse** (`codex_ws_provider_required`).
Pentru rutarea cu partajarea cotei, utilizați `model: "qtSd/<group>/codex/<model>"`. Implementat în
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts`.

**Autentificare:** cheie API Bearer în timpul handshake-ului. Serverul HTTP inclus (`server-ws.mjs`)
trebuie să fie punctul de intrare activ (ceea ce se întâmplă implicit atunci când există `app/server-ws.mjs`).

#### ID-ul modelului: utilizați ID-ul ChatGPT simplu (fără prefixul `codex/`)

**Codex CLI** de la OpenAI validează numele modelului pe partea clientului atunci când
`supports_websockets = true` și **respinge ID-urile cu prefixul furnizorului**, precum
`codex/gpt-5.5` (`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). Trimiteți ID-ul **simplu** (de exemplu, `gpt-5.5`). Puntea OmniRoute este
exclusiv pentru codex, astfel încât aceasta rezolvă din nou un ID simplu ca model codex
(`resolveCodexWsModelInfo`) înainte de tunelarea către serviciul din amonte — chiar dacă un ID simplu
`gpt-5.5` ar fi rutat în mod normal către alt furnizor prin HTTP.

#### Configurarea OpenAI Codex CLI

Direcționați Codex CLI către OmniRoute adăugând în `~/.codex/config.toml` un furnizor personalizat cu suport
WebSocket (utilizați un `CODEX_HOME` separat pentru a evita modificarea
unei configurații existente):

```toml
model = "gpt-5.5"                 # ID simplu — NU "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"

```

```bash

codex exec "Responda apenas: PONG"
```

CLI-ul face upgrade pentru `base_url + /responses` la un WebSocket, iar OmniRoute creează un tunel către
conexiunea OAuth codex selectată. Validat end-to-end pe serverul
local: ChatGPT returnează `codex.rate_limits` + `response.created` și transmite progresiv
răspunsul.

## Utilizare cu autoservire (`/api/usage/om-usage`)

Orice cheie API își poate citi **propria** utilizare și propriile cote — fără autentificare de administrare. Acesta este endpoint-ul pe care un
client (CLI, panoul OmniCopilot) îl utilizează pentru a-i afișa deținătorului unei chei cheltuielile sale.

```bash
# Format text (contractul istoric — text simplu pentru un terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Format structurat — utilizat de o interfață
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Cheia trebuie să aibă activată opțiunea **`allowUsageCommand`** (dezactivată implicit — managerul de chei API
al panoului o comută pentru fiecare cheie). Fără aceasta, endpoint-ul răspunde cu `403`.

`?format=json` returnează o structură discriminată, astfel încât un apelant să nu citească niciodată un câmp de date dintr-un
refuz. În caz de succes:

```jsonc
{
  "allowed": true,
  // prezent numai când cheia a optat pentru limite de utilizare per cheie (USD zilnic/săptămânal):
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // instantaneul cotei furnizorului selectat sau null când încă nu există nimic în cache:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // instantaneul fiecărei conexiuni, astfel încât o interfață să poată afișa alăturat mai mulți furnizori:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

În caz de refuz (`401` cheie incorectă / `403` acces nepermis), aceeași rută returnează
`{ "allowed": false, "error": { "message": "…" } }` — un câmp `personal`/`provider` prezent, dar gol
(cheia este permisă, însă încă nu s-a obținut nicio informație) reprezintă o stare diferită de un refuz, iar numai formatul JSON
face distincția între acestea.

**Autentificare:** propria cheie API Bearer a apelantului, validată cu `isValidApiKey` — aceasta _nu_ este
interfața de administrare (`/api/keys/…`), care rămâne protejată de `requireManagementAuth`.

### Procente de cotă brute comparativ cu cele ajustate în funcție de pragul de întrerupere

Când consumă `/api/usage/om-usage`, apelanții trebuie să rețină diferența dintre
procentele prezentate de **ieșirea în text simplu** și **ieșirea JSON** structurată:

| Aspect                   | Format text simplu (`/api/usage/om-usage` / `@@om-usage`)                                        | Format JSON (`?format=json`)                                                                        |
| :----------------------- | :----------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------- |
| **Câmp de ieșire**       | `NN% left` (de exemplu, `20% left`)                                                              | `provider.quotas` / `providers[].quotas`                                                            |
| **Măsurătoare**          | **Cotă utilizabilă ajustată în funcție de prag**: capacitatea rămasă peste pragul de întrerupere | **Cotă brută din amonte**: măsurătoare neajustată a furnizorului                                    |
| **Scalarea pragului**    | Scalată prin `effectiveRemainingPercent()`, astfel încât rezerva protejată să apară ca `0% left` | Niciuna (valorile brute ale instantaneului, așa cum sunt raportate de furnizor)                     |
| **Date despre prag**     | Incluse în procentul afișat                                                                      | Stocate în `quotaWindowThresholds` pentru fiecare conexiune (sau valorile implicite ale serverului) |
| **Consumator principal** | CLI-uri interactive, solicitări în terminal, operatori umani                                     | Integrări programatice, panouri de control, analize, sisteme de urmărire a facturării               |

#### Formula de ajustare în funcție de pragul de întrerupere

OmniRoute acceptă praguri proactive de întrerupere a cotei pentru a preveni epuizarea resurselor din amonte (configurate prin
`quotaWindowThresholds` ale conexiunii, valorile implicite ale furnizorului sau setările globale de reziliență). Când un prag de întrerupere
(de exemplu, `cutoff = 25%`) este activ pentru o fereastră de cotă, generatorul de text calculează cota rămasă astfel:

- Dacă `remaining <= cutoff`: returnează `0%`.
- Dacă `remaining > cutoff`: returnează `((remaining - cutoff) / (100 - cutoff)) * 100`.

Ieșirea text formatată rotunjește rezultatul la cel mai apropiat număr întreg (`Math.round(...)`).

#### Exemplu ilustrativ

Să luăm în considerare o fereastră a furnizorului cu **60% utilizare brută** (așadar, **40% cotă brută rămasă**) și un prag configurat de
**25% cotă rămasă pentru întrerupere**:

| Reprezentare                   | Calcul                                             |  Rămas  |              Utilizare implicită               |
| :----------------------------- | :------------------------------------------------- | :-----: | :--------------------------------------------: |
| **JSON brut (`?format=json`)** | Instantaneu din amonte (`quotas[window]`)          | **40%** |                    **60%**                     |
| **Format text (`NN% left`)**   | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (dacă se calculează `100 - remaining`) |

- **De ce textul afișează 20% rămas:** Din cota fizică de 40% rămasă în cont, 25% este rezervată de
  politica pragului de întrerupere. Apelantul mai are disponibil doar 15% din marja utilizabilă de 75% înainte ca routerul să oprească
  direcționarea către această conexiune. Scalarea garantează că respectiva conexiune semnalează epuizarea (`0% left`) exact atunci când
  direcționarea va înceta.
- **De ce JSON păstrează valorile brute:** Sarcina utilă JSON returnează instantaneul exact al furnizorului (`UsageSnapshot`),
  astfel încât instrumentele externe să aibă acces la gradul real de utilizare din amonte și la
  `quotaWindowThresholds` la nivel de conexiune, fără o scalare cu pierderi efectuată pe server.

#### Îndrumări pentru migrarea consumatorilor

Dacă o integrare externă (cum ar fi un plugin pentru editor sau o extensie de agent) prelua anterior datele din endpointul text
(`NN% left`) și calcula procentajul utilizat ca `100 - NN`, migrarea la `?format=json` înseamnă:

- Citirea valorilor JSON brute va reflecta **consumul real din amonte** (60% utilizat în exemplul de mai sus).
- Dacă integrarea dorește să păstreze semantica limitei utilizabile a endpointului text, aceasta poate evalua
  formula efectivă pentru cota rămasă la nivelul clientului, utilizând `quotaWindowThresholds` pentru suprascrierile la nivel de conexiune.

## Cache semantic

```bash
# Obține statisticile cache-ului
GET /api/cache/stats

# Golește toate cache-urile
DELETE /api/cache/stats
```

Exemplu de răspuns:

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Impactul asupra latenței

O potrivire în cache-ul semantic furnizează răspunsul din cache **fără un apel
către serviciul din amonte**, astfel încât valoarea raportată pentru `X-OmniRoute-Response-Latency` este aproape de zero
(indiferent de latența inițială a serviciului din amonte). Clienții sensibili la latență
(testare de performanță, monitorizare p50/p99) ar trebui să verifice antetul de răspuns
`X-OmniRoute-Cache-Latency`:

| Valoare     | Semnificație                                                             |
| ----------- | ------------------------------------------------------------------------ |
| `synthetic` | Răspuns furnizat din cache; latența nu reprezintă timpul real din amonte |
| _(absent)_  | Răspuns provenit dintr-un apel real către serviciul din amonte           |

### Ocolirea cache-ului pentru fiecare cheie

Cheile API pot renunța la citirile din cache-ul semantic prin intermediul `cacheDefaultMode`:

| Valoare  | Comportament                                                               |
| -------- | -------------------------------------------------------------------------- |
| `legacy` | Comportament normal al cache-ului (implicit)                               |
| `bypass` | Omite complet căutarea în cache; apelează întotdeauna serviciul din amonte |

Setați la crearea cheii (`POST /api/keys`) sau la actualizare (`PATCH /api/keys/[id]`):

```json
{ "cacheDefaultMode": "bypass" }
```

### Ocolirea pentru fiecare solicitare

Orice solicitare poate ocoli cache-ul, indiferent de setările cheii:

```
X-OmniRoute-No-Cache: true
```

Pentru modelele sincronizate/importate, `PUT /api/provider-models` acceptă `provider`, `modelId` și
`maxOutputTokenOverride`: un număr întreg pozitiv stabilește limita manuală a tokenurilor de ieșire, iar `null`
o elimină pentru a restabili valoarea implicită. `GET /api/provider-models?provider=<provider>` returnează aceste
valori în `modelOutputOverrides`, inclusiv pentru modelele fără un rând de model personalizat. Suprascrierea
utilizează capabilitatea `max_output_tokens` din timpul execuției și persistă după resincronizarea modelului. Pagina
furnizorului compatibil cu OpenAI oferă aceleași controale de editare/eliminare și marchează modelele cu suport explicit pentru viziune.

Nodurile personalizate Chat Completions adaptează dezactivările explicite ale raționamentului la backendul din amonte. Un
test de conexiune reușit selectează automat controalele pentru șablonul de chat pentru fiecare ID exact de model
a cărui intrare `/models` dovedește o valoare `owned_by` recunoscută: `vllm`, `sglang` sau `llamacpp`.
Wrapper-ele transparente compatibile cu OpenAI pot păstra intrarea originală a modelului într-un obiect
`openai` imbricat; detectarea urmărește până la trei astfel de învelișuri. Modelele cu proprietate absentă, necunoscută sau
conflictuală păstrează comportamentul OpenAI obișnuit. Detectarea reutilizează solicitarea existentă a catalogului,
nu generează tokenuri de completare și este invalidată atunci când endpointul conexiunii se modifică.

Pentru a fixa comportamentul în cazul unui backend care nu expune aceste metadate, utilizați API-ul existent
de actualizare parțială a furnizorului:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Trimiteți acest corp cu `PUT /api/providers/<connection-id>`. Pentru conexiunea respectivă, un
nivel explicit de efort de raționament `none` este trimis ca `chat_template_kwargs.thinking=false` și
`chat_template_kwargs.enable_thinking=false`. Valorile explicite ale șablonului nativ rămân prioritare,
cu excepția cazului în care o regulă de raționament de pe server impune un anumit efort. Setarea se aplică numai când o conexiune
personalizată compatibilă cu OpenAI expediază un corp Chat Completions; solicitările Responses și furnizorii
obișnuiți își păstrează structura nativă a solicitării. Setați `reasoningControl` la `openai` pentru a impune transmiterea
obișnuită a parametrului OpenAI `reasoning_effort` sau omiteți-l/setați-l la `null` pentru a utiliza detectarea automată.

Solicitările clasificatorului din modul automat Claude Code au în mod implicit raționamentul nativ dezactivat atunci când nu conțin
controale explicite pentru raționament. Detectarea utilizează marcajul de sistem al clasificatorului din solicitările în format Claude,
nu numele modelelor sau limitele de completare. Controalele explicite din corp, anteturile acceptate pentru efort/raționament,
regulile de rutare și efortul rezolvat al modelului își păstrează prioritatea existentă. Ambele etape ale clasificatorului
își păstrează prompturile, limitele de completare, secvențele de oprire și verdictele reale privind permisiunile din amonte;
a doua etapă poate produce în continuare raționamentul vizibil solicitat ca text obișnuit.

### Versiune și canal de lansare

```bash
GET /api/system/version
```

Rută de administrare disponibilă numai prin interfața loopback (autentificare de administrator). Returnează versiunea care rulează, cea mai recentă
versiune publicată și starea actualizării automate. `releaseChannel` și `channels` sunt câmpuri
aditive (linia 3.8.54); `channel` își păstrează semnificația — modul de implementare utilizat de
programul de actualizare al panoului de control (`npm`, `source` sau `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — canalul npm al versiunii care rulează: `nightly` pentru versiunile `-nightly.*`,
  `next` pentru alte versiuni preliminare (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` pentru o versiune stabilă
  dintr-o versiune majoră mai veche decât `channels.latest`, iar în caz contrar `latest`. Aceleași reguli ca în
  `scripts/release/dist-tag.mjs`, care selectează eticheta de distribuție npm în momentul publicării.
- `channels` — cea mai recentă versiune publicată pentru fiecare etichetă de distribuție, obținută de la `npm view omniroute dist-tags` (cu
  registrul HTTP ca variantă de rezervă), memorată în cache cu același TTL de 10 minute ca `latest`. `latest` este întotdeauna prezent
  (recurge la câmpul `latest`, apoi la `"unavailable"`); `next`, `nightly` și `lts` apar
  numai atunci când există eticheta de distribuție respectivă. O solicitare `Cache-Control: no-cache` reîmprospătează ambele interogări.

Modelul de canale (`latest` = v3 până la lansarea generală 4.0, `next` = rc, `nightly` = versiuni din `develop`,
`lts` = corecții pentru v3 după lansarea generală 4.0) este descris în `docs/ops/RELEASE_STRATEGY.md`.

## Limite de tokenuri

Bugete de **tokenuri** per cheie API (distincte de Bugetul bazat pe USD de mai sus). Sunt aplicate direct pe traseul cererii: când utilizarea din fereastra curentă a unei chei atinge limita, cererile sunt respinse cu `429 Too Many Requests`. Limitele pot viza un anumit `model`, un `provider` sau pot fi aplicate `global` pentru întreaga cheie; când mai multe limite corespund unei cereri, se aplică cea mai restrictivă.

```bash
# Listează limitele de tokenuri ale unei chei (include utilizarea curentă din fereastră)
GET /api/usage/token-limits?apiKeyId=key-123

# Creează sau actualizează o limită de tokenuri
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Șterge o limită de tokenuri după id
DELETE /api/usage/token-limits?id=tl-abc
```

> **Note privind schema** (`setTokenLimitSchema`): `apiKeyId` și `scopeType` (`model` | `provider` | `global`) sunt obligatorii. `scopeValue` este obligatoriu, cu excepția cazului în care `scopeType` este `global` (de exemplu, un id de model pentru domeniul `model` sau un id de furnizor pentru domeniul `provider`). `tokenLimit` trebuie să fie un număr întreg pozitiv (convertit din șir de caractere). Opționale: `id` (omiteți-l pentru creare, furnizați-l pentru actualizare), `resetInterval` (`daily` | `weekly` | `monthly`, valoare implicită `monthly`), `resetTime` (`HH:MM`), `enabled` (valoare implicită `true`). Răspunsurile `GET` completează fiecare limită cu `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` și `nextResetAt`. Acesta este un endpoint din clasa de administrare (autentificarea este aplicată centralizat de fluxul authz).

## Procesarea cererilor

1. Clientul trimite cererea către `/v1/*`
2. Gestionarul rutei apelează `handleChat`, `handleEmbedding`, `handleAudioTranscription` sau `handleImageGeneration`
3. Modelul este determinat (furnizor/model direct sau alias/combinație)
4. Datele de autentificare sunt selectate din baza de date locală, cu filtrare în funcție de disponibilitatea contului
5. Pentru chat: `handleChatCore` verifică memoria cache semantică/de semnături și determină setările de compresie ale combinației
6. Compresia proactivă rulează înaintea traducerii pentru furnizor atunci când este activată (`lite`, Caveman, RTK sau în stivă)
7. Executorul furnizorului trimite cererea către serviciul din amonte
8. Răspunsul este tradus înapoi în formatul clientului (chat) sau returnat ca atare (încorporări/imagini/audio)
9. Utilizarea, datele analitice privind compresia și jurnalele cererilor sunt înregistrate
10. Mecanismul de rezervă se aplică în cazul erorilor, conform regulilor combinației

Referință completă pentru arhitectură: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Reziliență (extinsă)

OmniRoute expune trei mecanisme independente pentru gestionarea defecțiunilor temporare; endpointurile de administrare de mai jos le permit operatorilor să le consulte și să le suprascrie:

| Domeniu de aplicare   | Stocarea stării                                       | Citire                                    | Resetare / golire                                               |
| --------------------- | ----------------------------------------------------- | ----------------------------------------- | --------------------------------------------------------------- |
| Întrerupător furnizor | `domain_circuit_breakers` + în memorie                | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                    |
| Pauză conexiune       | `rateLimitedUntil` pe conexiunile furnizorilor        | `/api/rate-limits`, `/api/providers/[id]` | (se reactivează la nevoie; se golește prin PUT pentru furnizor) |
| Blocare model         | Registru în memorie pentru disponibilitatea modelelor | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                        |

`PATCH /api/resilience` acceptă suprascrieri pentru întrerupătoarele furnizorilor în `providerBreaker.oauth` și `providerBreaker.apikey`. Fiecare profil acceptă `degradationThreshold`, `failureThreshold` și `resetTimeoutMs`; aceleași câmpuri sunt disponibile în Panou de control → Setări → Reziliență.

```bash
# Golește blocarea unui singur model
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Elimină toate blocările
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

Pentru referința conceptuală completă și valorile implicite ale întrerupătoarelor, consultați [`CLAUDE.md`](../../CLAUDE.md) → „Starea de execuție a rezilienței” și [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### Coada pentru limitarea ratei și mecanismul de siguranță pentru activarea automată

- **Cale de scriere acceptată**: `POST /api/rate-limits` cu corpul `{"connectionId": "<id>", "enabled": true|false}` este endpointul de administrare acceptat pentru activarea sau dezactivarea protecției împotriva limitării ratei pentru o conexiune. `PUT /api/providers/[id]` nu modifică și nu comută în mod intenționat `rateLimitProtection` (#11278).
- **Semantica valorii `enabled: false`**: Setarea `enabled: false` elimină protecția explicită pentru conexiune, dar **nu** exclude o conexiune activă cu cheie API din mecanismul global de siguranță pentru activarea automată (`autoEnableApiKeyProviders = true`). În `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`), `false` și `undefined` sunt echivalente; conexiunile active cu cheie API fără protecție explicită rămân protejate de mecanismul de siguranță pentru activarea automată.
- **Dezactivare globală**: Pentru a utiliza conexiunile cu cheie API fără cozi de limitare a ratei, dezactivați global mecanismul de siguranță prin `RATE_LIMIT_AUTO_ENABLE=false` (variabilă de mediu) sau `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Setări → Reziliență / `PATCH /api/resilience`).

## Server A2A

OmniRoute expune un endpoint A2A (Agent-to-Agent) JSON-RPC 2.0, precum și un wrapper REST pentru inspectare/utilizare în tabloul de bord.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # opțional, cu excepția cazului în care este setată OMNIROUTE_API_KEY
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Metode acceptate (toate condiționate de `settings.a2aEnabled`):

| Metodă           | Descriere                                                                 |
| ---------------- | ------------------------------------------------------------------------- |
| `message/send`   | Executare sincronă a abilității; returnează `{task, artifacts, metadata}` |
| `message/stream` | Executare SSE prin streaming pentru același set de abilități              |
| `tasks/get`      | Preia o sarcină după `taskId`                                             |
| `tasks/cancel`   | Anulează o sarcină după `taskId`                                          |

Abilități încorporate: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Fișa agentului

```bash
GET /.well-known/agent.json
```

Returnează fișa publică a agentului A2A (nume, descriere, capabilități, catalog de abilități, schemă de autentificare) — stocată public în cache timp de 1h. Nu este necesară autentificarea.

### Funcții auxiliare REST

| Metodă | Cale                         | Descriere                                                                                                               |
| ------ | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/a2a/status`            | Starea activării A2A + statistici despre sarcini + rezumatul fișei agentului stocate în cache                           |
| GET    | `/api/a2a/tasks`             | Listează sarcinile — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (Neimplementată ca funcție auxiliară REST — creați prin JSON-RPC `message/send`)                                        |
| GET    | `/api/a2a/tasks/[id]`        | Preia o sarcină                                                                                                         |
| POST   | `/api/a2a/tasks/[id]/cancel` | Anulează o sarcină                                                                                                      |

**Autentificare:** funcțiile auxiliare REST rulează fără autentificare de administrare (pot fi citite de tabloul de bord); ruta JSON-RPC `/a2a` utilizează Bearer `OMNIROUTE_API_KEY` dacă este configurată.

## Autentificare

Consultați [Autentificarea pentru administrare](../guides/MANAGEMENT-AUTH.md) pentru cele patru
familii de acreditări (sesiune de tablou de bord, token CLI local, token de acces
`oma_live_…`, cheie API cu domeniu de administrare) și modul în care acestea diferă de cheile de inferență.

- Rutele tabloului de bord (`/dashboard/*`) utilizează cookie-ul `auth_token`
- Autentificarea utilizează hashul parolei salvate; ca alternativă, `INITIAL_PASSWORD`
- `requireLogin` poate fi comutat prin `/api/settings/require-login`
- Rutele `/v1/*` necesită opțional o cheie API Bearer atunci când `REQUIRE_API_KEY=true`
- „token de administrare” / „cheie API cu domeniu de administrare” din această referință înseamnă una dintre familiile din ghidul respectiv — nu un tip suplimentar nedefinit de secret

> **Modificare incompatibilă (v3.8.0)** — `/api/v1/agents/tasks/*` și endpointurile de administrare a perioadei de așteptare necesită acum **autentificare pentru administrare** (cookie-ul `auth_token` al tabloului de bord sau o cheie API cu domeniu de administrare). Clienții care apelau anterior aceste rute fără autentificare vor primi `401 Unauthorized`. Consultați commitul `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`).
