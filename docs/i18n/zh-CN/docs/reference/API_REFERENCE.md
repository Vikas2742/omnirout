## 聊天补全

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### 自定义标头

| 标头                     | 方向 | 描述                                                                                                                                                        |
| ------------------------ | ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | 请求 | 设置为 `true` 以绕过缓存                                                                                                                                    |
| `x-omniroute-no-memory`  | 请求 | 设置为 `true`，可为此请求跳过记忆和技能注入（与不使用缓存类似；可避免每次调用产生相应的令牌/成本开销）                                                      |
| `X-OmniRoute-Progress`   | 请求 | 设置为 `true` 以启用进度事件                                                                                                                                |
| `X-Session-Id`           | 请求 | 用于外部会话亲和性的粘性会话键                                                                                                                              |
| `x_session_id`           | 请求 | 也接受带下划线的变体（直接 HTTP）                                                                                                                           |
| `X-OmniRoute-Session-Id` | 请求 | 调用方提供的会话/对话标签（也会提供给记忆功能）。如果存在，则原样持久化到 `call_logs.session_tag`，以便按会话归因成本 (#8249)；如果不存在，则绝不会自动生成 |
| `Idempotency-Key`        | 请求 | 去重键（5 秒窗口）                                                                                                                                          |
| `X-Request-Id`           | 请求 | 备用去重键                                                                                                                                                  |
| `x-omniroute-connection` | 请求 | 通过提供者连接（账户）的 ID，将单模型请求固定到一个提供者连接；请参阅[按请求固定账户](#account-pinning-per-request)                                         |
| `X-OmniRoute-Cache`      | 响应 | `HIT` 或 `MISS`（非流式）                                                                                                                                   |
| `X-OmniRoute-Idempotent` | 响应 | 如果已去重，则为 `true`                                                                                                                                     |
| `X-OmniRoute-Progress`   | 响应 | 如果已启用进度跟踪，则为 `enabled`                                                                                                                          |
| `X-OmniRoute-Session-Id` | 响应 | OmniRoute 使用的有效会话 ID                                                                                                                                 |
| `X-OmniRoute-Request-Id` | 响应 | 请求关联 ID（已知时）                                                                                                                                       |
| `X-OmniRoute-Version`    | 响应 | OmniRoute 构建版本（始终存在）                                                                                                                              |
| `X-OmniRoute-Cost-Saved` | 响应 | 缓存命中时节省的美元金额（仅限缓存命中）                                                                                                                    |
| `X-OmniRoute-Decision`   | 响应 | 路由跟踪信息：`strategy=<name>; provider=<alias>; latency_ms=<n>`（`<name>` 是组合策略；对于非组合请求则为 `single`）——始终包含在完成响应中                 |

> Nginx 注意事项：如果你依赖带下划线的请求头（例如 `x_session_id`），请启用 `underscores_in_headers on;`。

#### 为每个请求固定账户

当一个提供者存在多个连接（账户或密钥）时，OmniRoute 通常会通过其账户选择策略选择一个连接。
请求也可以改用 `x-omniroute-connection` 请求头固定到某个特定连接：

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **在哪里查找 id。** 在控制面板中打开提供者页面
  （**控制面板 → 提供者 → <提供者>**），然后点击连接行中的 `xxxxxxxx…` id 标签
  ——这会复制完整的连接 id。
- **哪些请求支持它。** `/v1/chat/completions`、`/v1/messages` 和 `/v1/responses` 上的
  单模型请求（`provider/model`）。组合会忽略该请求头：如需为组合中的每个步骤固定账户，
  请通过该步骤自身的连接进行设置。
- **固定是强制性的，而不是一种偏好。** 系统只会使用固定的连接。请求过程中发生故障时，
  会记录该账户的冷却状态，但**不会**轮换到同一提供者的其他同级账户。
- **冷却和配额限制会解除固定。** 当固定的连接正处于冷却状态、配额已用尽或被配额策略阻止时，
  后续请求会回退到该提供者的其他连接，与未固定的流量完全相同。
- **未知或已禁用的 id 会导致失败。** 如果某个 id 不在提供者的活动池中（已删除、
  已停用或属于其他提供者），则不会有符合条件的账户，因此请求会失败，而不会静默路由到其他连接。

Claude Code 通过 `ANTHROPIC_CUSTOM_HEADERS` 发送自定义请求头。将其放入
`~/.claude/settings.json` 的 `env` 块中，或者放入项目级 `.claude/settings.json`，以便为每个项目固定不同的
账户：

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

来源：`src/sse/handlers/chat.ts`（读取请求头）、`src/sse/services/auth.ts` 和
`src/sse/services/sessionAffinityPin.ts`（解除固定以及检查连接是否不在池中）。

> **成本遥测请求头：** 非流式成功响应还会携带 `X-OmniRoute-*` 成本遥测字段集——`X-OmniRoute-Response-Cost`（美元，固定保留 10 位小数；免费或未定价时为 `0.0000000000`）、`X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`、`X-OmniRoute-Model`、`X-OmniRoute-Provider`、`X-OmniRoute-Latency-Ms`、`X-OmniRoute-Cache-Hit` 和 `X-OmniRoute-Fallback-Attempts`（仅在 > 0 时提供），以及 `X-OmniRoute-Request-Id` 和 `X-OmniRoute-Version`。这些请求头由聊天补全、`/v1/responses`、`/v1/messages` **以及媒体端点**返回——包括 `/v1/embeddings`、`/v1/images/generations`、`/v1/audio/speech`、`/v1/audio/transcriptions`、`/v1/rerank`、`/v1/videos/generations`、`/v1/music/generations` 和 `/v1/moderations`（成本始终为 `0`）。如果有可用的定价信息，则会按不同模态计算媒体成本（按图像、按秒、按字符、按搜索单元）；否则为 `0`（故障时开放）。

> **缓存命中的成本语义：** 语义缓存命中时（`X-OmniRoute-Cache-Hit: true`）不会发起上游调用，因此 `X-OmniRoute-Response-Cost` 为 `0.0000000000`（处理此次缓存命中的**增量**成本）。原始成本或本应产生的成本会单独记录在 `X-OmniRoute-Cost-Saved` 中。计费使用方应对 `X-OmniRoute-Response-Cost` 求和（缓存命中不产生成本）；缓存分析则可以汇总 `X-OmniRoute-Cost-Saved`。

## 独占托管会话租约

独占托管会话租赁是一种可选择启用、与客户端无关的路由契约：一个活动所有者
持有一个符合条件的 OmniRoute 连接。它不租赁模型、不要求 OAuth、不标识
特定客户端，也不要求使用特定提供者。

用于身份验证的 API 密钥必须具有 `lease:exclusive` 作用域以及显式的非空
`allowedConnections` 列表。数据库变更边界会在创建密钥和执行部分更新时同时强制要求
这两个字段。

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

成功的获取、续租和释放响应会公开时间戳、`state` 和准确的正数
`generation`，但绝不会公开所选连接或凭据。续租和释放操作通过
JSON 正文提供 generation：

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

活动租约所有者可以显式请求其当前绑定的隐私安全显示元数据：

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

此可选择启用的状态操作会在单个数据库事务中，由不透明的所有者标识、经过身份验证的托管 API 密钥和准确的
活动 generation 共同进行围栏校验。`displayName` 仅为经过修剪的已配置
连接名称；如果不存在安全的已配置名称，则其值为 `null`。OmniRoute 绝不会用
电子邮件地址或生成的账户身份替代它。提供者值是非敏感的显示标签，绝不会是
生成的兼容提供者标识符。凭据、令牌、Cookie、原始连接或 API
密钥 ID、所有者哈希、围栏密钥以及内部路由数据均不会包含在内。

错误密钥、错误所有者、过期 generation、缺失、到期、已释放和已失效的查询都会
返回相同的 `409 LEASE_FENCE_STALE` 错误，并且不包含连接元数据。收到容量等待响应的客户端没有可供检查的活动绑定。当路由切换活动租约时，
同一个 generation 仍然有效，并且状态操作会以原子方式返回新绑定，而绝不会返回旧绑定。
现有客户端保持不变，因为获取、续租、释放和等待响应会保留
其原有结构。

此服务器契约不会更改原版 OpenAI Codex 的 `/status`。原版 Codex 当前会报告其
模型提供者和内置身份验证/账户状态，但不会呈现任意自定义
提供者账户元数据；后续客户端集成必须调用此操作，并决定如何
显示 `connection.displayName`。

之后，每个托管推理请求都要提供这两个控制标头：

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

在每次受支持的上游尝试之前，系统都会立即对准确的所有者、generation、活动连接以及经过身份验证的 API 密钥
执行围栏校验。即使另一个密钥允许使用相同连接，使用该密钥重放所有者和 generation 也会失败。
原始所有者值不会被持久化、记录到日志、保留在
请求快照中，也不会转发到上游。

临时争用会返回带有 `Retry-After` 的 HTTP `429`，以及：

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

此响应仅表示常规的合格集合非空，并且所有空闲候选项都被
其他所有者的活动租约占用。不受支持的模型/提供者、策略不匹配、冷却期、配额、
健康状况以及其他常规资格检查失败仍会保留其现有的 OmniRoute 响应。

### `x-omniroute-compression`

按请求覆盖压缩计划。优先级最高——高于路由组合
覆盖、活动配置文件、自动触发和面板默认设置。可用值：

| 值            | 效果                                                               |
| ------------- | ------------------------------------------------------------------ |
| `off`         | 不压缩此请求。                                                     |
| `default`     | 使用面板派生的默认配置文件（忽略活动配置文件）。有损引擎保持关闭。 |
| `safe`        | 仅执行去重和空白折叠。                                             |
| `allow-lossy` | 为此请求保留操作员计划，包括摘要和样式重写。                       |
| `engine:<id>` | 启用时使用单个引擎，例如 `engine:rtk`。按请求选择启用该引擎。      |
| `<combo>`     | 命名组合，先按名称匹配（不区分大小写），再按 ID 匹配。             |

注意：

- 未知值会被忽略（请求绝不会因此被拒绝）；解析过程会回退到正常的操作员优先级。
- 如果多个组合使用相同名称，请传递组合的 **id** 以确保确定性匹配。
- 名称为 `off` 或 `default` 的组合无法通过名称选择（这些关键字会被优先解释）；请通过其 ID 引用此类组合。
- 压缩总开关是硬性门控：全局禁用压缩时，此标头无法启用压缩。

应用的计划会通过响应标头回显：

```
X-OmniRoute-Compression: <mode>; source=<source>
```

其中 `<source>` 是 `request-header`、`routing-override`、`active-profile`、`auto-trigger`、`default` 或 `off` 之一。

## 嵌入

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

可用提供者：Nebius、OpenAI、Mistral、Together AI、Fireworks、NVIDIA、**OpenRouter**、Jina AI。

目录 ID 的格式为 `provider/model`（示例：`jina-ai/jina-embeddings-v5-omni-small`）。注册表中出现的、不含提供者前缀的 Jina 模型 ID（例如 `jina-embeddings-v5-text-small`、`jina-reranker-v3.5`）也可以解析。Jina 的嵌入/重排/分类/分段功能会优先使用控制面板中的 `jina-ai` 凭据；仅当控制面板中不存在密钥时，才会回退使用 `JINA_AI_API_KEY`。`jina-reader` 卡片仅用于 Reader / `r.jina.ai`（`POST /v1/web/fetch`），绝不会提供嵌入或重排服务。

注册表中声明支持多模态的模型还可接受最多 32 个提供者无关的结构化
条目。媒体条目类型包括 `text`、`image`、`audio`、`video` 和 `document`。其媒体 `source`
可以是 `{"type":"url","url":"https://..."}`，也可以是
`{"type":"base64","data":"...","media_type":"..."}`。

Jina v5 Omni（`jina-ai/jina-embeddings-v5-omni-small`、`jina-ai/jina-embeddings-v5-omni-nano`
以及系列别名 `jina-ai/jina-embeddings-v5-omni` → omni-small）还接受 Jina 原生的
EmbeddingsV5Request 文档，并将其**原样转发**至 `https://api.jina.ai/v1/embeddings`：

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

原生 `{ image | audio | video | pdf }` 值可以是公共 HTTPS URL、`data:` URI 或原始
base64。OmniRoute 不会将这些对象字符串化，也不会获取原生图像 URL——Jina 会自行获取
公共媒体。额外的 Jina 字段（`task`、`normalized`、`truncate`、`embedding_type`）会被
转发。仅支持文本的 Jina SKU 仍会拒绝非文本文档。

安全与传输限制：

- 远程媒体 URL 必须是公共 HTTPS。规范的 `{type,source:url}` 条目由
  服务端获取（重新验证重定向、设置超时和大小限制、验证公共 DNS、固定连接），并在
  调用提供者之前内联。Jina 原生的 `{image:"https://..."}` 条目经过相同的公共 HTTPS
  检查后会按原样转发；由 Jina 获取该 URL。
- 内联 base64 媒体限制为每个条目解码后不超过 8 MiB，整个请求解码后不超过 16 MiB。

提供者转换（规范条目绝不会原样转发）：

- Jina 多模态模型：每个顶层条目会转换为一个以模态为键的对象
  （`text` / `image` / `audio` / `video` / `pdf`），内联媒体使用 data URI；每个
  顶层条目生成一个向量。
- Gemini Embedding 2 系列：一个顶层数组会转换为单个原生
  `models/{model}:embedContent` 请求，其中包含 `content.parts`（`text` 或 `inline_data`）。
- llama.cpp（`llama-cpp/<model>`，即本地服务器加载的任意模型）：规范的 `text` 条目
  会转换为纯字符串，而 `image` / `audio` / `video` 各自会转换为一个
  `{"content": [part]}` 对象，使用 llama-server 的聊天内容部分（`image_url`、
  格式为 `wav` / `mp3` / `flac` 的 `input_audio`、`input_video`），并使用内联数据；每个
  顶层条目生成一个向量。服务器必须使用 `--embedding --mmproj …` 运行；如果没有投影器，
  服务器会自行拒绝媒体。`document` 不受支持。
- 没有显式模态元数据的未知/动态模型会拒绝结构化输入，并返回 HTTP 400。

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

不受支持的模型/模态组合会返回 HTTP 400，而不是强制转换条目。对于旧版字符串/令牌请求，
非输入扩展字段仍会按原样传递。

```bash
# 列出所有嵌入模型
GET /v1/embeddings
```

## 图像生成

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

可用的提供者包括 OpenAI (GPT Image 2)、xAI (Grok Image)、Together AI (FLUX)、Fireworks AI、Nebius (FLUX)、Hyperbolic、NanoBanana、**OpenRouter**、**ZenMux**、SD WebUI（本地）、ComfyUI（本地）。

`n` 会在 `data[]` 中返回 `n` 张图像。对于上游 API 每次调用仅返回一张图像的提供者
（Black Forest Labs、Stability AI、Leonardo、Ideogram、Haiper、Hyperbolic、Magnific/Freepik、
NVIDIA NIM、Cloudflare Workers AI），系统会发起 `n` 次独立的上游调用，最多同时进行 4 次。
固定的 `seed` 会根据调用索引进行偏移（`seed`、`seed + 1`、……），因此图像彼此不同，但仍然
可以复现。`n` 的上限为 10。如果任意调用失败，则整个请求都会失败。需要扇出的格式列表位于
`open-sse/handlers/imageGeneration/fanOut.ts` 中的 `SINGLE_IMAGE_FANOUT_FORMATS`。

ZenMux 会复用现有的 API 密钥连接，并接受 `zenmux/` 或 `zm/` 前缀：

- `zenmux/openai/gpt-image-2` 使用 ZenMux 的 OpenAI Images API。选项包括 `size`、
  `quality`、`n`、`output_format`、`output_compression`、`background` 和 `response_format`。
- 其他发布商（例如 `zm/meta/muse-image-1.0`）使用 ZenMux 的 Vertex AI `:predict`
  端点。`n` 映射到 `sampleCount`，`aspect_ratio` 映射到 `aspectRatio`，而 `image_size`
  （`1K`、`2K`、`4K`）映射到 `sampleImageSize`。以像素表示的 `size` 仅提供宽高比，
  不保证具体的像素尺寸。支持的宽高比、分辨率和数量因模型而异。
- `zm/inclusionai/ming-image-0.1-design` 会自行选择尺寸。请省略 `size`、
  `aspect_ratio` 和 `image_size`；显式指定这些值将返回 HTTP 400。可以通过
  `output_format` 请求 PNG、JPEG 和 WebP。

此集成支持文生图，不支持参考图像编辑。Vertex
输出会被规范化为 `data[].b64_json`；当仅有图像字节可用时，`response_format: "url"` 会返回上游
HTTPS URL 或 base64 数据 URL。空输出或被过滤的输出将返回错误，而不是返回内容为空的成功响应。
模型访问权限取决于 ZenMux 账户。请参阅 [ZenMux 的 Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) 和
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image)。

```bash
# 列出所有图像模型
GET /v1/images/generations
```

## 文档 OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` 通过 `provider/model` 前缀选择 OCR 提供者；不带前缀的模型 ID（例如
`mistral-ocr-latest`）会解析到其已注册的提供者，而省略 `model` 时则默认使用
Mistral（`mistral-ocr-latest`）。已注册的提供者（`open-sse/config/ocrRegistry.ts`）：

| 提供者 ID                     | 模型 ID              | `model` 值                                                        | 备注                                                                                         |
| ----------------------------- | -------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest`（或不带前缀的 `mistral-ocr-latest`） | 同步——响应会直接从单次上游调用返回。                                                         |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                       | 异步上游（`analyze` + 轮询）——见下文。                                                       |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                           | 同步，通过 Vertex AI 的 `openapi/chat/completions` 合作伙伴端点——身份验证和 URL 详情见下文。 |

所有三个提供者都返回相同的 Mistral 风格响应体：

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence 轮询流程

Azure Document Intelligence 的 `analyze` API 是异步的：初始请求返回
`Operation-Location` 标头而不是响应体，因此必须通过轮询获取结果。处理程序
（`open-sse/handlers/ocr.ts`）每秒轮询一次该 URL，最多尝试 30 次；如果轮询响应不是 `ok`
或状态为 `"failed"`，则会立即失败（不再继续轮询）；如果操作在用尽尝试次数后仍在运行，
则返回 `504`。最终的 Azure 响应在返回给调用方之前，会被规范化为与 Mistral 相同的
`pages`/`markdown` 格式，因此客户端代码无需对该提供者进行特殊处理。

### Vertex AI DeepSeek OCR 身份验证和端点解析

`vertex-deepseek-ocr` 会复用 OmniRoute 已为聊天/图像流量支持的相同 Vertex AI 身份验证机制
（`open-sse/executors/vertex.ts`）：连接的 API 密钥可以是 Service Account JSON 凭据
（通过 JWT-bearer 流程交换为短期 OAuth 访问令牌），也可以是已签发并直接使用的 OAuth 访问令牌。
上游端点 URL 是 Vertex 的通用 `openapi/chat/completions` 合作伙伴端点，根据连接的项目和
区域构建——显式设置的 `providerSpecificData.project`/`providerSpecificData.region` 始终优先；
否则，项目从 Service Account JSON 的 `project_id` 派生，区域默认为 `us-central1`。
这两项解析都在 `open-sse/handlers/ocr.ts` 中进行
（`resolveVertexOcrAccessToken`、`resolveVertexOcrBaseUrl`），并由
`src/app/api/v1/ocr/route.ts` 在分派给 `handleOcr` 之前使用。

## 模型列表

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ 以 OpenAI 格式返回所有聊天、嵌入和图像模型及组合
```

### 模型 ID 前缀（`?prefix=`）

大多数模型都使用**提供者前缀**公布。具体使用哪种前缀由
`MODELS_CATALOG_PREFIX_MODE` 功能标志控制，并且可以通过查询参数**按请求**覆盖——这对于希望获得简洁列表、但又不想更改面向其他所有用户的服务器全局设置的客户端非常有用：

```bash
GET /v1/models?prefix=alias        # 每个模型一个 ID——使用短别名前缀
GET /v1/models?prefix=dual         # 两种形式（服务器默认值）
GET /v1/models?prefix=canonical    # 仅使用完整的提供者 ID 前缀
```

| 模式        | 输出                                                     | 说明                                                                                                                                           |
| ----------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **和** `claude/claude-sonnet-4-6` | **默认值。** 两个 ID 都路由到同一模型；保留它们是为了让硬编码了任一形式的客户端配置继续工作。目录大小大约会翻倍。                              |
| `alias`     | `cc/claude-sonnet-4-6`                                   | 每个模型一个条目。没有独立别名的提供者仍会输出其条目，因此不会遗漏任何内容。                                                                   |
| `canonical` | `claude/claude-sonnet-4-6`                               | 每个模型使用完整提供者 ID 前缀输出一个条目。没有独立别名的提供者（例如 `antigravity/…`、`agy/…`）也会在此输出其唯一 ID，因此不会遗漏任何内容。 |

即使不使用查询参数，也可以识别出 `dual` 模式的镜像：它会带有一个指向主 ID 的 `parent`
字段。

呈现模型选择器的客户端应请求 `?prefix=alias`——
[OmniCopilot VS Code 扩展](../guides/VSCODE-COPILOT.md)正是这样做的。

### 发现筛选器（`?capability=`、`?min_context=`、`?kind=`、`?q=`）

`GET /v1/models` 接受可选的发现筛选器。如果不使用任何筛选器，响应将保持
不变。它们会缩小调用方已能看到的目录范围（首先应用 API 密钥权限），
并在 OpenAI 风格的 `limit` / `after` 分页之前执行：

```bash
GET /v1/models?capability=vision&capability=tool_calling   # 列出的每项能力都必须为 true
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # 目录 `type`；没有该值的行视为 `chat`
GET /v1/models?q=sonnet&limit=10                           # 对 ID 或名称进行不区分大小写的匹配
```

| 参数          | 值                                                                                                  |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`、`reasoning`、`structured_output`、`temperature`、`thinking`、`tool_calling`、`vision` |
| `min_context` | 非负整数，与 `context_length` 比较                                                                  |
| `kind`        | `chat`、`audio`、`embedding`、`image`、`moderation`、`music`、`rerank`、`video`                     |
| `q`           | 1–200 个字符                                                                                        |

未知值或不是非负整数的 `min_context`（例如 `1.5`）
会返回 HTTP `400`，且消息中会列出有效值。实现：
`src/app/api/v1/models/catalogFilters.ts`。

### 模型候选短名单（`POST /v1/models/query`）

`POST /v1/models/query` 从同一目录中返回一个简短且确定性的列表，其身份验证和按密钥可见性与 `GET /v1/models`
相同：

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

所有字段均为可选。`capabilities` 和 `exclude` 接受数组或以逗号分隔的字符串；
`max_output` 与 `max_output_tokens` 比较。结果先按 `owned_by` 排序，再按 `id` 排序。
`limit` 默认为 `20`，大于 `100` 的值将被限制为 `100`。无效的 JSON、未知字段或无效值会返回 HTTP `400`。

### 单独隐藏的聊天模型

在其提供者页面上标记为**隐藏**的模型会从目录中排除，并且在被显式请求时返回
HTTP `404` / `model_not_found`。此检查使用解析后的提供者和模型，包括提供者别名、兼容提供者节点前缀以及
连接默认值。组合会跳过隐藏的目标，并可使用可见的同级目标；当没有剩余可执行目标时，
它会返回相同的错误代码。取消隐藏后会在下一次请求时生效。仅限图像的可见性覆盖不会隐藏具有相同 ID 的聊天模型。

此单独模型设置与
[模型公开允许/拒绝列表](../routing/MODEL_EXPOSURE_LIST.md)相互独立；后者会筛选目录中公布的模型和自动路由候选模型，但保留显式分派能力。API 密钥模型
权限仍会独立应用。默认目录前缀模式仍为 `dual`。

### 无思考模型变体

对于支持思考功能的 Claude 模型，`/v1/models` 还会公布一个 ID 以 `claude-3-omniroute-no-thinking/` 为前缀的**无思考**变体：

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

选择此 id（例如，在始终附加 `thinking` 块的 Claude Code 配置中）会解析回真实的 `<provider>/<model>`，并抑制推理——在 `/v1/messages` 路径上使用 `thinking:{type:"disabled"}`，或在 `/v1/chat/completions` 路径上丢弃 `reasoning`/`reasoning_effort` 字段。该变体仅针对支持思考功能**且**遵循 `disabled` 的 Claude 系列模型列出（因此，例如，仅支持自适应思考且拒绝 `disabled` 的模型会被排除）。运维人员可以通过 `ModelSpec.noThinkingAlias` 为每个模型强制开启或关闭该变体。

## ElevenLabs 音频生成

在 OmniRoute 中使用您的 ElevenLabs API 密钥配置一个 `elevenlabs` 提供者连接。客户端使用其 **OmniRoute** 密钥（`Authorization: Bearer $OMNIROUTE_API_KEY`）进行身份验证；网关会将存储的提供者密钥作为 `xi-api-key` 提供。切勿将 ElevenLabs 密钥作为网关的 bearer token 发送。

| 方法 | 路径                        | 响应                          | API 密钥端点类别 |
| ---- | --------------------------- | ----------------------------- | ---------------- |
| POST | `/v1/sound-generation`      | 原生音频字节                  | `elevenlabs`     |
| POST | `/v1/music`                 | 原生音频字节                  | `music`          |
| POST | `/v1/music/stream`          | 流式音频字节                  | `music`          |
| POST | `/v1/music/detailed`        | 原生 multipart 音频和作曲方案 | `music`          |
| POST | `/v1/music/detailed/stream` | 原生 SSE 元数据和音频分块     | `music`          |
| POST | `/v1/music/plan`            | JSON 作曲方案                 | `music`          |

这些端点是对现有 `/v1/audio/speech`、`/v1/audio/transcriptions`、`/v1/voices`、`/v1/text-to-speech/{voiceId}` 和 `/v1/speech-to-text` 路由的补充。原生 JSON 字段和查询参数（例如 `output_format` 和 `enable_logging`）会被保留。`/v1/music/detailed` 响应会保留其 multipart 边界；请将其作为 multipart 解析。`/v1/music/detailed/stream` 返回 `text/event-stream`，其中包含作曲元数据和 SSE 事件中的 base64 音频分块。全部六个路由均支持 CORS 预检。

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# 一个简短的音效。时长：0.5 到 30 秒。
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# 音乐时长以毫秒表示：3000 到 600000。
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

使用具有相同 JSON 正文的 `/v1/music/stream` 以增量方式传输音频。作曲请求必须且只能接受 `prompt` 或 `composition_plan` 其中之一；`/v1/music/plan` 要求提供 `prompt`，并可选接受 `source_composition_plan`。原生 schema 会保留其他提供者字段，以便将作曲方案版本和微调选项传递给 ElevenLabs。

统一的 `/v1/music/generations` 端点也接受 `elevenlabs/music_v1`、`elevenlabs/music_v2` 和 `elevenlabs/music_v2_5`。当存在有效的 ElevenLabs 连接时，这些模型会在音乐目录中公开。此端点返回 `{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`。其 `duration` 字段以秒为单位，并映射到 `music_length_ms`；显式指定的 `music_length_ms` 优先级更高。`instrumental` 映射到 `force_instrumental`，其中原生字段优先级更高。如需流式传输，请使用原生流式端点；对于仅由作曲方案驱动的请求，请使用原生作曲端点。

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

在调用上游之前，会应用端点、模型、预算和连接限制。原生路由会原样返回上游状态码和错误正文，包括套餐限制对应的 `402` 和配额限制对应的 `429`。如果存在，`character-cost`、`song-id`、`request-id` 和 `retry-after` 标头会被保留。免费信用额度余额并不保证能够访问所有音乐模型、输出格式或 API 功能：ElevenLabs 会决定每个请求的权限。统一端点会在 OmniRoute 的标准化错误封装中保留错误状态码。

上游契约：[音效](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert)、
[音乐创作](https://elevenlabs.io/docs/api-reference/music/compose)和
[流式音乐详情](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)。

```bash
# 重排序（云注册表提供者，或模型指定为 "<prefix>/<model>" 的 OpenAI 兼容提供者节点）
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# Soniox TTS 需要语言和声音：`language` 默认为 "en"；缺少声音或使用
# OpenAI 内置声音名称（alloy、nova 等）时，将改为 "Adrian"
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# 图像编辑（multipart）
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# 视频/音乐生成（带提供者前缀的模型 ID）
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **重排序提供者节点：** `POST /v1/rerank` 也会路由到 OpenAI 兼容的提供者节点
> （oMLX、vLLM、Infinity、网关后的 TEI 等），其地址格式为 `<node-prefix>/<model>`。环回
> 节点（`localhost`、`127.0.0.1`、`172.16.0.0/12`）始终符合条件，运营方在
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` 中列出的主机名也同样符合条件（例如 Docker/Compose
> 服务名称，如 `http://reranker:8080/v1`；这些节点始终直接调用，绝不会通过 `HTTP(S)_PROXY`
> 或连接所固定的代理）。位于任何其他
> 主机上的节点（例如局域网主机或 Tailscale 对等节点）仅在运营方启用
> `RERANK_REMOTE_PROVIDER_NODES` 功能标志，**并且**节点的基础 URL 通过提供者
> 出站 URL 策略（`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`）时才符合条件。
> 内存引擎的重排序步骤通过
> 环回地址调用此路由，因此同一规则也适用于内存设置中的 `rerankProviderModel`。
>
> **本地服务器形式：**首先通过 `<base>/v1/rerank` 调用节点；如果返回 404，则改为调用 `<base>/rerank`
> （Infinity、TEI）。上游请求体同时包含 Cohere/OpenAI 拼写形式（`documents`、
> `return_documents`）和 TEI 拼写形式（`texts`、`return_text`），而上游响应会
> 统一规范为 Cohere 信封格式：TEI 的裸 `[{index, score, text}]`、精简网关返回的
> `{results: [{index, score}]}` 以及 Voyage 风格的 `{data: [...]}`，都会以
> `{results: [{index, relevance_score, document?}]}` 的形式返回给客户端，并按分数排序，且最多保留 `top_n` 项。

> **提供者节点发现：**OpenAI 兼容提供者节点上的模型会显示在 `GET /v1/models` 中，
> 并归于相应的节点前缀下。不含端点元数据的条目（本地 `/v1/models` 列表中很常见）
> 会继承节点的 `apiType`，因此 `embeddings` 节点的模型为 `type: "embedding"`，
> `rerank` 节点的模型为 `type: "rerank"`，而不会默认为聊天模型；已同步或手动添加的条目中显式指定的
> `supportedEndpoints` 仍具有更高优先级。

## 搜索 API

Web/搜索提供者抽象层（Tavily、Brave、Exa、Serper 等）。

| 方法 | 路径                   | 描述                                                        |
| ---- | ---------------------- | ----------------------------------------------------------- |
| GET  | `/v1/search`           | 列出已配置的搜索提供者及其功能                              |
| POST | `/v1/search`           | 执行搜索查询——请求体由 `v1SearchSchema` 验证，支持缓存/合并 |

### Exa 和 Tavily 的 `provider_options`

Exa 和 Tavily 从带命名空间的属性集合中读取提供者特定字段：
`provider_options.exa`（或 `provider_options["exa-search"]`）和 `provider_options.tavily`
（或 `provider_options["tavily-search"]`）。仅转发下列键。每个键都会依据
`open-sse/handlers/search/providerOptionsPassthrough.ts` 中各自的 Zod schema
进行检查，类型错误的键将被丢弃。其他任何键都会被忽略，包括身份验证、基础 URL、
`stream` 和 `outputSchema`。其他提供者使用的扁平键（`cx`、`depth` 等）仍然
像以前一样工作。

| 提供者 | 顶层字段                                                                                                                                                                                                                                                                                                                                                                  | 嵌套字段                                                                                                                                                    |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa    | `type`、`category`、`userLocation`、`moderation`、`additionalQueries`、`objective`、`systemPrompt`、`compliance`（扁平原始值）、`startPublishedDate`、`endPublishedDate`                                                                                                                                                                                                  | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` 合并到默认值 `{ text: true, highlights: true }` 之上 |
| Tavily | `search_depth`、`chunks_per_source`、`time_range`、`start_date`、`end_date`、`include_published_date`、`filter_by_published_date`、`include_answer`、`include_raw_content`、`include_images`、`include_image_descriptions`、`include_favicon`、`include_domains_mode`、`language`、`filter_by_language`、`auto_parameters`、`exact_match`、`include_usage`、`safe_search` | —                                                                                                                                                           |

通用字段始终优先：`query`、`max_results`、`filters`（域名）、`country`，以及从
`search_type` 派生的主题。在 Exa 上，`search_type: "news"` 会保留 `category: "news"`。
Tavily 也接受 `search_type: "finance"`（`topic: "finance"`）。

通用的 `time_range` 现在会传递给两个提供者：Exa 获取 `startPublishedDate`（ISO
时间戳），Tavily 获取 `start_date`（`YYYY-MM-DD`）。`provider_options`
中显式指定的日期会覆盖映射得到的日期。

Exa 结果会在 `provider_raw` 中保留 `id`、`highlight_scores`、`summary`、`subpages`、`entities` 和 `extras`。Tavily 结果会保留 `images` 和 `favicon`。

成本核算仍使用扁平注册表 `costPerQuery`。Tavily 对每次
`search_depth: "advanced"` 调用收取更多额度，而该差异不会反映在
`usage.search_cost_usd` 中。

## Web Fetch API

通过配置的网页抓取提供者（Firecrawl、Jina Reader、Tavily Extract、TinyFish Fetch、Nimble Extract、Parallel Extract）从 URL 中提取内容。

Parallel Extract（`parallel-search`，与 Parallel Search 使用相同的 API 密钥）仅返回 Markdown——任何其他 `format` 都会产生 `400`——并将内容限制在 100,000 个字符以内。当目标页面本身无法提取时，上游会在 HTTP 200 响应中报告该情况；OmniRoute 会将其呈现为带有固定消息的 `422`。

| 方法 | 路径            | 描述                                              |
| ---- | --------------- | ------------------------------------------------- |
| POST | `/v1/web/fetch` | 获取/抓取 URL——请求正文由 `v1WebFetchSchema` 验证 |

**身份验证：** Bearer API 密钥（`extractApiKey` + `isValidApiKey`）。通过 `enforceApiKeyPolicy` 强制执行策略。

**配额感知回退（#8297）：** 当未明确指定 `provider` 时，系统会按固定优先级顺序（优先填满）遍历提供者池（`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` → `parallel-search`）——已配置但受到速率限制的提供者会被跳过，而不是直接终止请求；可重试的上游故障或配额故障（HTTP 429 始终适用；对于 Firecrawl/Tavily/TinyFish 的配额型免费层，402/403 也适用——但不适用于 Jina Reader，且普通的 400 错误请求永远不适用）会在请求时回退到下一个尚未尝试且已配置凭据的提供者。当池中的每个提供者均已耗尽时，端点会返回单个 `429`（带有 `Retry-After` 标头），而不是之前通用的 `400`。当明确请求某个 `provider` 时，**不会**进行静默回退——受到速率限制或发生故障的指定提供者会直接呈现其自身错误（若受速率限制则为 `429`，否则为上游状态码）。


验证 WebSocket 升级握手，并返回线路协议示例消息（`request`、`cancel`）。实际的 WS 帧由 Next.js 路由表之外的捆绑 WS 服务器处理。

### 通过 WebSocket 使用 Responses API（仅限 codex）

```bash
# 与 HTTP API 使用相同的主机和端口（默认 20128）；升级连接：
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# （或者：-H "Authorization: Bearer <OMNIROUTE_API_KEY>"）

# 第一帧必须是 response.create：
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket 代理**仅连接到 `codex`**（ChatGPT 后端）。它与 API/仪表板监听相同的端口，路径为 `/v1/responses`、`/responses` 和 `/api/v1/responses`。收到第一个 `response.create` 帧时，它会通过内部 `codex-responses-ws` 桥接器进行身份验证和准备，选择一个 codex OAuth 连接，并通过 `wreq-js` 传输层建立到 `wss://chatgpt.com/backend-api/codex/responses` 的隧道。**非 codex 模型会被拒绝**（`codex_ws_provider_required`）。如需使用配额共享路由，请使用 `model: "qtSd/<group>/codex/<model>"`。实现在 `app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` 中。

**身份验证：** 握手期间使用 Bearer API 密钥。捆绑的 HTTP 服务器（`server-ws.mjs`）必须作为活动入口点（默认情况下，只要 `app/server-ws.mjs` 存在，它就是活动入口点）。

#### 模型 ID：使用裸 ChatGPT ID（不带 `codex/` 前缀）

当 `supports_websockets = true` 时，OpenAI **Codex CLI** 会在客户端验证模型名称，并且会**拒绝带提供者前缀的 ID**，例如 `codex/gpt-5.5`（`The 'codex/gpt-5.5' model is not supported when using Codex with a ChatGPT account`）。请发送**裸** ID（例如 `gpt-5.5`）。OmniRoute 的桥接器仅支持 codex，因此在建立上游隧道之前，它会将裸 ID 重新解析为 codex 模型（`resolveCodexWsModelInfo`）——即使裸 `gpt-5.5` 在通过 HTTP 使用时原本会路由到其他提供者。

#### 配置 OpenAI Codex CLI

要将 Codex CLI 指向 OmniRoute，请在 `~/.codex/config.toml` 中添加一个支持 WebSocket 的自定义提供者（使用单独的 `CODEX_HOME`，以免修改现有配置）：

```toml
model = "gpt-5.5"                 # 裸 ID——不是 "codex/gpt-5.5"
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # 不带末尾斜杠；WS URL 由此派生（生产环境中使用 https/wss）
wire_api = "responses"                    # 自 2026 年 2 月起唯一支持的值
supports_websockets = true                # 启用 Responses-over-WS 传输
env_key = "OMNIROUTE_API_KEY"             # 保存 OmniRoute API 密钥（Bearer）
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API 密钥（若 REQUIRE_API_KEY=false，则可使用任意密钥）
codex exec "Responda apenas: PONG"
```

CLI 会将 `base_url + /responses` 升级为 WebSocket，而 OmniRoute 会将其通过隧道连接到选定的 codex OAuth 连接。已针对本地服务器完成端到端验证：ChatGPT 会返回 `codex.rate_limits` + `response.created`，并以流式方式传输补全结果。

## 自助式用量查询（`/api/usage/om-usage`）

任何 API 密钥都可以读取**自身的**用量和配额——无需管理认证。这是客户端
（CLI、OmniCopilot 面板）用于向密钥持有者显示其支出的端点。

```bash
# 文本形式（历史约定——用于终端的纯文本）
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# 结构化形式——供 UI 使用
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

该密钥必须启用 **`allowUsageCommand`**（默认关闭——控制面板的 API 密钥
管理器可按密钥切换此设置）。如果未启用，该端点将返回 `403`。

`?format=json` 会返回可判别的结构，因此调用方绝不会从拒绝响应中读取数据字段。
成功时：

```jsonc
{
  "allowed": true,
  // 仅当该密钥选择启用按密钥计算的用量限制（每日/每周美元）时才存在：
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // 选定提供者的配额快照；尚未缓存任何内容时为 null：
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // 每个连接的快照，以便 UI 并排呈现多个提供者：
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

被拒绝时（`401` 表示密钥无效 / `403` 表示不允许访问），同一路由会返回
`{ "allowed": false, "error": { "message": "…" } }`——存在但为空的 `personal`/`provider`
（密钥已获准，但尚未获取任何数据）与拒绝状态不同，而且只有 JSON 形式
才能区分这两种状态。

**认证：** 调用方自己的 Bearer API 密钥，使用 `isValidApiKey` 验证——这_不是_
管理接口（`/api/keys/…`），后者仍受 `requireManagementAuth` 保护。

### 原始配额百分比与截止值调整后的配额百分比

使用 `/api/usage/om-usage` 时，调用方应注意**纯文本输出**与结构化 **JSON 输出**
所呈现百分比之间的区别：

| 方面           | 纯文本格式（`/api/usage/om-usage` / `@@om-usage`）                          | JSON 格式（`?format=json`）                                   |
| :------------- | :-------------------------------------------------------------------------- | :------------------------------------------------------------ |
| **输出字段**   | `NN% left`（例如 `20% left`）                                               | `provider.quotas` / `providers[].quotas`                      |
| **度量方式**   | **经截止值调整的可用额度**：高于截止阈值的剩余容量                          | **原始上游配额**：未经调整的提供者度量值                      |
| **截止值缩放** | 通过 `effectiveRemainingPercent()` 缩放，使受保护的预留额度显示为 `0% left` | 无（提供者报告的原始快照值）                                  |
| **阈值数据**   | 已计入显示的百分比                                                          | 按连接存储在 `quotaWindowThresholds` 中（或使用服务器默认值） |
| **主要使用者** | 交互式 CLI、终端提示、人类运维人员                                          | 程序化集成、控制面板、分析和账单跟踪工具                      |

#### 截止值调整公式

OmniRoute 支持主动设置配额截止值，以防上游配额耗尽（通过连接的
`quotaWindowThresholds`、提供者默认值或全局弹性设置进行配置）。当某个配额窗口启用了截止阈值
（例如 `cutoff = 25%`）时，文本渲染器会按以下方式计算剩余额度：

- 如果 `remaining <= cutoff`：返回 `0%`。
- 如果 `remaining > cutoff`：返回 `((remaining - cutoff) / (100 - cutoff)) * 100`。

格式化的文本输出会将结果四舍五入为最接近的整数（`Math.round(...)`）。

#### 示例

假设某个提供者窗口的**原始用量为 60%**（因此**原始剩余配额为 40%**），并配置了
**25% 剩余配额截止**阈值：

| 表示形式                        | 计算                                               | 剩余量  |                推算用量                |
| :------------------------------ | :------------------------------------------------- | :-----: | :------------------------------------: |
| **原始 JSON（`?format=json`）** | 上游快照（`quotas[window]`）                       | **40%** |                **60%**                 |
| **文本格式（`NN% left`）**      | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%**（若按 `100 - remaining` 计算） |

- **为什么文本显示剩余 20%：** 在账户实际剩余的 40% 配额中，25% 被截止策略预留。
  在路由器停止将请求路由到此连接之前，调用方仅剩 75% 可用余量中的 15%。缩放可确保连接恰好在
  路由停止时发出配额耗尽信号（`0% left`）。
- **为什么 JSON 保留原始值：** JSON 载荷会返回提供者的精确快照（`UsageSnapshot`），
  以便外部工具访问真实的上游利用率和连接级
  `quotaWindowThresholds`，而无需经过服务器端的有损缩放。

#### 使用方迁移指南

如果某个外部集成（例如编辑器插件或智能体扩展）之前抓取文本
端点（`NN% left`），并以 `100 - NN` 计算已用百分比，那么迁移到 `?format=json` 意味着：

- 读取原始 JSON 值将反映**实际上游消耗量**（在上述示例中已使用 60%）。
- 如果该集成希望保留文本端点的可用配额语义，可以在客户端使用 `quotaWindowThresholds`
  评估有效剩余量公式，以支持连接级别的覆盖配置。

```bash
# 获取缓存统计信息
GET /api/cache/stats

# 清除所有缓存
DELETE /api/cache/stats
```

响应示例：

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,

  }

```

### 延迟影响

语义缓存命中时，将直接从缓存提供响应，**不会调用上游**，因此报告的
`X-OmniRoute-Response-Latency` 接近于零（无论原始上游延迟是多少）。对延迟敏感的客户端
（基准测试、p50/p99 监控）应检查
`X-OmniRoute-Cache-Latency` 响应标头：

| 值          | 含义                                   |
| ----------- | -------------------------------------- |
| `synthetic` | 响应来自缓存；该延迟并非真实的上游耗时 |
| _(不存在)_  | 响应来自真实的上游调用                 |

### 按密钥绕过缓存

API 密钥可通过 `cacheDefaultMode` 选择不读取语义缓存：

| 值       | 行为                           |
| -------- | ------------------------------ |
| `legacy` | 正常缓存行为（默认）           |
| `bypass` | 完全跳过缓存查找；始终调用上游 |

可在创建密钥时（`POST /api/keys`）设置，或通过更新（`PATCH /api/keys/[id]`）设置：

```json
{ "cacheDefaultMode": "bypass" }
```

### 按请求绕过缓存

无论密钥设置如何，任何请求都可以绕过缓存：

```
X-OmniRoute-No-Cache: true
```

检测使用 Claude 格式请求中的分类器系统标记，而不是模型名称或补全限制。显式请求体控制、

### 版本和发布通道

```bash
GET /api/system/version
```

仅限环回地址访问的管理路由（需要管理员身份验证）。返回当前运行版本、最新发布版本以及自动更新状态。`releaseChannel` 和 `channels` 是新增字段（rail 3.8.54）；`channel` 保持其原有含义——即仪表板更新程序所使用的部署模式（`npm`、`source` 或 `docker-compose`）。

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — 当前运行构建的 npm 通道：对于 `-nightly.*` 版本为 `nightly`，
  对于其他预发布版本（`-rc.*`、`-beta.*`、`-alpha.*`）为 `next`，对于主版本号低于
  `channels.latest` 的旧稳定版本为 `lts`，其他情况则为 `latest`。其规则与
  `scripts/release/dist-tag.mjs` 相同，后者会在发布时选择 npm dist-tag。
- `channels` — 每个 dist-tag 的最新已发布版本，来自 `npm view omniroute dist-tags`（注册表
  HTTP 回退），并采用与 `latest` 相同的 10 分钟 TTL 进行缓存。`latest` 始终存在
  （依次回退到 `latest` 字段，然后回退到 `"unavailable"`）；`next`、`nightly` 和 `lts`
  仅在对应的 dist-tag 存在时出现。带有 `Cache-Control: no-cache` 的请求会刷新这两项查询。

通道模型（`latest` = 4.0 GA 之前的 v3，`next` = rc，`nightly` = `develop` 构建，
`lts` = 4.0 GA 之后的 v3 补丁）在 `docs/ops/RELEASE_STRATEGY.md` 中进行了说明。

## 音频转录

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

使用任意已配置的 STT 提供者转录音频文件。路径的第一个分段用于选择原生提供者（`openai/…`、`deepgram/…`）。重新导出其他供应商模型的网关使用限定 ID（`openrouter/deepgram/nova-3`）。

**请求：**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**响应：**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**模型 ID 示例：** `openai/whisper-1`（需要 OpenAI 密钥）、
`openrouter/deepgram/nova-3`（需要 OpenRouter 密钥）、
`deepgram/nova-3`（需要原生 Deepgram 密钥）。不带其他限定信息的
`deepgram/nova-3` 请求**不会**使用 OpenRouter。

**支持的格式：** `mp3`、`wav`、`m4a`、`flac`、`ogg`、`webm`。


注意：

- 带令牌的别名复用与 `/v1/*` 和 `/api/tags` 相同的处理程序；响应结构保持一致。
- 只要客户端支持自定义请求头，就应优先使用 `Authorization: Bearer ...`。
- 基于 URL 的令牌可能出现在 OmniRoute 之外的反向代理日志、浏览器历史记录和遥测数据中。应将其视为一种兼容性选项，而非默认身份验证方式。

## Token 限额

每个 API 密钥的 **token** 预算（不同于上面的基于 USD 的预算）。在请求路径中直接强制执行：当密钥在当前窗口中的使用量达到限额时，请求将被拒绝并返回 `429 Too Many Requests`。限额可以限定于特定 `model`、`provider`，也可以按 `global` 范围应用于整个密钥；当多个限额与某个请求匹配时，以最严格的限额为准。

```bash
# 列出密钥的 token 限额（包括实时窗口使用量）
GET /api/usage/token-limits?apiKeyId=key-123

# 创建或更新 token 限额
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# 按 id 删除 token 限额
DELETE /api/usage/token-limits?id=tl-abc
```

> **Schema 说明**（`setTokenLimitSchema`）：`apiKeyId` 和 `scopeType`（`model` | `provider` | `global`）为必填项。除非 `scopeType` 为 `global`，否则 `scopeValue` 为必填项（例如，`model` 范围需要模型 id，`provider` 范围需要提供者 id）。`tokenLimit` 必须是正整数（可从字符串强制转换）。可选项：`id`（创建时省略，更新时提供）、`resetInterval`（`daily` | `weekly` | `monthly`，默认为 `monthly`）、`resetTime`（`HH:MM`）、`enabled`（默认为 `true`）。`GET` 响应会为每个限额补充 `tokensUsed`、`remaining`、`windowStart`、`periodStartAt` 和 `nextResetAt`。这是一个管理类端点（由 authz 管道集中实施身份验证）。

## 请求处理

1. 客户端向 `/v1/*` 发送请求
2. 路由处理程序调用 `handleChat`、`handleEmbedding`、`handleAudioTranscription` 或 `handleImageGeneration`
3. 解析模型（直接指定 provider/model，或使用 alias/combo）
4. 从本地数据库中选择凭据，并按账户可用性进行筛选
5. 对于聊天：`handleChatCore` 检查语义/签名缓存，并解析 combo 压缩设置
6. 启用主动压缩时，会在转换为提供者格式之前运行（`lite`、Caveman、RTK 或堆叠模式）
7. 提供者执行器发送上游请求
8. 将响应转换回客户端格式（聊天），或按原样返回（嵌入/图像/音频）
9. 记录使用量、压缩分析数据和请求日志
10. 根据 combo 规则，在发生错误时应用回退机制

完整架构参考：[`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## 弹性机制（扩展）

OmniRoute 提供三种相互独立的临时故障处理机制；以下管理端点允许运维人员读取和覆盖其状态：

| 范围         | 状态存储                          | 读取                                      | 重置 / 清除                               |
| ------------ | --------------------------------- | ----------------------------------------- | ----------------------------------------- |
| 提供者断路器 | `domain_circuit_breakers` + 内存  | `/api/monitoring/health`                  | `POST /api/resilience/reset`              |
| 连接冷却     | 提供者连接上的 `rateLimitedUntil` | `/api/rate-limits`, `/api/providers/[id]` | （惰性地重新启用；可通过提供者 PUT 清除） |
| 模型锁定     | 内存中的模型可用性注册表          | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`  |

`PATCH /api/resilience` 接受位于 `providerBreaker.oauth` 和 `providerBreaker.apikey` 下的提供者断路器覆盖配置。每个配置文件均支持 `degradationThreshold`、`failureThreshold` 和 `resetTimeoutMs`；Dashboard → Settings → Resilience 中也提供了相同字段。

```bash
# 清除单个模型锁定
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# 清除所有锁定
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

完整的概念参考和断路器默认值：请参阅 [`CLAUDE.md`](../../CLAUDE.md) → “弹性运行时状态”以及 [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md)。

### 限流队列与自动启用安全网

- **受支持的写入路径**：使用请求体 `{"connectionId": "<id>", "enabled": true|false}` 调用 `POST /api/rate-limits`，这是切换连接限流保护状态的受支持管理端点。`PUT /api/providers/[id]` 有意不修改或切换 `rateLimitProtection`（#11278）。
- **`enabled: false` 的语义**：设置 `enabled: false` 会移除该连接的显式保护，但**不会**让活跃的 API 密钥连接退出全局自动启用安全网（`autoEnableApiKeyProviders = true`）。在 `reconcileEnabledConnections`（`open-sse/services/rateLimitManager.ts`）中，`false` 和 `undefined` 等效；未显式启用保护的活跃 API 密钥连接仍会受到自动启用安全网的保护。
- **全局禁用**：若要在不使用限流队列的情况下运行 API 密钥连接，请通过 `RATE_LIMIT_AUTO_ENABLE=false`（环境变量）或 `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false`（Settings → Resilience / `PATCH /api/resilience`）全局禁用该安全网。

OmniRoute 提供了一个 A2A（代理到代理）JSON-RPC 2.0 端点，以及一个用于检查和仪表板的 REST 包装器。

## 身份验证

有关四类凭据（仪表板会话、本地 CLI 令牌、`oma_live_…` 访问令牌、管理范围的 API 密钥）以及它们与推理密钥的区别，请参阅[管理身份验证](../guides/MANAGEMENT-AUTH.md)。

- 仪表板路由（`/dashboard/*`）使用 `auth_token` Cookie
- 登录使用已保存的密码哈希；回退使用 `INITIAL_PASSWORD`
- `requireLogin` 可通过 `/api/settings/require-login` 切换
- 当 `REQUIRE_API_KEY=true` 时，`/v1/*` 路由可以要求提供 Bearer API 密钥
- 本参考文档中的“管理令牌”/“管理范围的 API 密钥”是指该指南中的某类凭据，而不是某种未定义的额外机密类型

> **破坏性变更（v3.8.0）** — `/api/v1/agents/tasks/*` 和冷却时间管理端点现在需要**管理身份验证**（仪表板 `auth_token` Cookie 或管理范围的 API 密钥）。之前以未认证方式调用这些路由的客户端将收到 `401 Unauthorized`。请参阅提交 `588a0333`（`fix(auth): require management auth for agent and cooldown APIs`）。
