## ការបំពេញការជជែក

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### បឋមកថាផ្ទាល់ខ្លួន

| បឋមកថា                   | ទិសដៅ      | ការពិពណ៌នា                                                                                                                                                                                                                         |
| ------------------------ | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | សំណើ       | កំណត់ជា `true` ដើម្បីរំលងឃ្លាំងសម្ងាត់                                                                                                                                                                                             |
| `x-omniroute-no-memory`  | សំណើ       | កំណត់ជា `true` ដើម្បីរំលងការបញ្ចូលអង្គចងចាំ + ជំនាញសម្រាប់សំណើនេះ (ដំណើរការដូចជាការមិនប្រើឃ្លាំងសម្ងាត់ និងជៀសវាងចំណាយ token/ថ្លៃដើមក្នុងការហៅនីមួយៗ)                                                                              |
| `X-OmniRoute-Progress`   | សំណើ       | កំណត់ជា `true` សម្រាប់ព្រឹត្តិការណ៍វឌ្ឍនភាព                                                                                                                                                                                        |
| `X-Session-Id`           | សំណើ       | សោសម័យស្អិតសម្រាប់ភាពជាប់ទាក់ទងនៃសម័យខាងក្រៅ                                                                                                                                                                                       |
| `x_session_id`           | សំណើ       | វ៉ារ្យ៉ង់ដែលប្រើសញ្ញាគូសក្រោមក៏ត្រូវបានទទួលយកផងដែរ (HTTP ផ្ទាល់)                                                                                                                                                                   |
| `X-OmniRoute-Session-Id` | សំណើ       | ស្លាកសម័យ/ការសន្ទនាដែលអ្នកហៅផ្តល់ឱ្យ (ក៏បញ្ចូលទៅអង្គចងចាំផងដែរ)។ នៅពេលមាន វាត្រូវបានរក្សាទុកតាមសភាពដើមទៅក្នុង `call_logs.session_tag` សម្រាប់ការកំណត់ថ្លៃដើមតាមសម័យ (#8249) — មិនត្រូវបានបង្កើតឡើងដោយស្វ័យប្រវត្តិឡើយនៅពេលអវត្តមាន |
| `Idempotency-Key`        | សំណើ       | សោសម្រាប់លុបធាតុស្ទួន (ចន្លោះពេល 5 វិនាទី)                                                                                                                                                                                         |
| `X-Request-Id`           | សំណើ       | សោជំនួសសម្រាប់លុបធាតុស្ទួន                                                                                                                                                                                                         |
| `x-omniroute-connection` | សំណើ       | ភ្ជាប់សំណើម៉ូដែលតែមួយទៅនឹងការតភ្ជាប់របស់អ្នកផ្តល់សេវាមួយ (គណនី) តាម id របស់វា — មើល [ការភ្ជាប់គណនីតាមសំណើនីមួយៗ](#account-pinning-per-request)                                                                                     |
| `X-OmniRoute-Cache`      | ការឆ្លើយតប | `HIT` ឬ `MISS` (មិនមែនការស្ទ្រីម)                                                                                                                                                                                                  |
| `X-OmniRoute-Idempotent` | ការឆ្លើយតប | `true` ប្រសិនបើត្រូវបានលុបធាតុស្ទួន                                                                                                                                                                                                |
| `X-OmniRoute-Progress`   | ការឆ្លើយតប | `enabled` ប្រសិនបើការតាមដានវឌ្ឍនភាពត្រូវបានបើក                                                                                                                                                                                     |
| `X-OmniRoute-Session-Id` | ការឆ្លើយតប | ID សម័យមានប្រសិទ្ធភាពដែល OmniRoute បានប្រើ                                                                                                                                                                                         |
| `X-OmniRoute-Request-Id` | ការឆ្លើយតប | id សម្រាប់ផ្គូផ្គងសំណើ (នៅពេលស្គាល់)                                                                                                                                                                                               |
| `X-OmniRoute-Version`    | ការឆ្លើយតប | កំណែ build របស់ OmniRoute (មានជានិច្ច)                                                                                                                                                                                             |
| `X-OmniRoute-Cost-Saved` | ការឆ្លើយតប | ចំនួន USD ដែលឃ្លាំងសម្ងាត់បានជួយសន្សំនៅពេល HIT (សម្រាប់តែ cache hit ប៉ុណ្ណោះ)                                                                                                                                                      |
| `X-OmniRoute-Decision`   | ការឆ្លើយតប | ដានការកំណត់ផ្លូវ៖ `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` គឺជាយុទ្ធសាស្ត្របន្សំ ឬ `single` សម្រាប់សំណើដែលមិនមែនជាបន្សំ) — មានជានិច្ចនៅក្នុងការឆ្លើយតបពេលបញ្ចប់                                               |

> ចំណាំអំពី Nginx៖ ប្រសិនបើអ្នកពឹងផ្អែកលើ header ដែលមានសញ្ញាគូសក្រោម (ឧទាហរណ៍ `x_session_id`) សូមបើក `underscores_in_headers on;`។

#### ការកំណត់ភ្ជាប់គណនីសម្រាប់សំណើនីមួយៗ

នៅពេល provider មួយមានការតភ្ជាប់ច្រើន (គណនី ឬ key) ជាធម្មតា OmniRoute នឹងជ្រើសរើសមួយ
តាមរយៈយុទ្ធសាស្ត្រជ្រើសរើសគណនីរបស់វា។ ផ្ទុយទៅវិញ សំណើមួយអាចកំណត់ភ្ជាប់ទៅការតភ្ជាប់ជាក់លាក់មួយ
ដោយប្រើ header `x-omniroute-connection`៖

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **កន្លែងស្វែងរក id។** បើកទំព័រ provider នៅក្នុង dashboard
  (**Dashboard → Providers → <provider>**) ហើយចុច chip id `xxxxxxxx…` នៅលើជួរដេកនៃការតភ្ជាប់
  — វានឹងចម្លង connection id ពេញលេញ។
- **សំណើណាខ្លះដែលគោរពតាមវា។** សំណើម៉ូដែលតែមួយ (`provider/model`) នៅលើ
  `/v1/chat/completions`, `/v1/messages` និង `/v1/responses`។ Combo មិនអើពើនឹង header នេះទេ៖ សូមកំណត់ភ្ជាប់
  គណនីសម្រាប់ជំហាននីមួយៗនៃ combo តាមរយៈការតភ្ជាប់ផ្ទាល់របស់ជំហាននោះជំនួសវិញ។
- **ការកំណត់ភ្ជាប់មានលក្ខណៈតឹងរ៉ឹង មិនមែនជាចំណូលចិត្តទេ។** ការតភ្ជាប់ដែលបានកំណត់នឹងត្រូវបានប្រើផ្តាច់មុខ។ ការ
  បរាជ័យនៅក្នុងសំណើនឹងកត់ត្រារយៈពេល cooldown របស់គណនី ប៉ុន្តែ **មិន** ប្តូរទៅ
  គណនីផ្សេងទៀតរបស់ provider ដូចគ្នានោះទេ។
- **Cooldown និង quota នឹងបញ្ឈប់ការកំណត់ភ្ជាប់។** ខណៈពេលការតភ្ជាប់ដែលបានកំណត់កំពុងស្ថិតក្នុង cooldown,
  អស់ quota ឬត្រូវបានទប់ស្កាត់ដោយគោលការណ៍ quota សំណើបន្ទាប់ៗនឹងត្រឡប់ទៅប្រើការតភ្ជាប់
  ផ្សេងទៀតរបស់ provider ដូចគ្នាទៅនឹង traffic ដែលមិនបានកំណត់ភ្ជាប់។
- **id ដែលមិនស្គាល់ ឬត្រូវបានបិទនឹងបរាជ័យ។** id ដែលមិនស្ថិតនៅក្នុង pool សកម្មរបស់ provider (ត្រូវបានលុប,
  បិទដំណើរការ ឬជាកម្មសិទ្ធិរបស់ provider ផ្សេង) ធ្វើឱ្យគ្មានគណនីសមស្រប ដូច្នេះសំណើ
  នឹងបរាជ័យ ជំនួសឱ្យការបញ្ជូនទៅកន្លែងផ្សេងដោយស្ងៀមស្ងាត់។

Claude Code ផ្ញើ header ផ្ទាល់ខ្លួនតាមរយៈ `ANTHROPIC_CUSTOM_HEADERS`។ ដាក់វានៅក្នុង block `env`
នៃ `~/.claude/settings.json` ឬនៅក្នុង `.claude/settings.json` កម្រិត project ដើម្បីកំណត់ភ្ជាប់ទៅគណនីផ្សេងគ្នា
សម្រាប់ project នីមួយៗ៖

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },

```

ប្រភព៖ `src/sse/handlers/chat.ts` (ការអាន header), `src/sse/services/auth.ts` និង
`src/sse/services/sessionAffinityPin.ts` (ការបញ្ឈប់ការកំណត់ភ្ជាប់ និងការត្រួតពិនិត្យថាមិនមាននៅក្នុង pool)។

> **Header តេឡេមេទ្រីនៃថ្លៃចំណាយ៖** response ជោគជ័យដែលមិនមែនជា streaming ក៏មានសំណុំតេឡេមេទ្រីនៃថ្លៃចំណាយ `X-OmniRoute-*` ផងដែរ — `X-OmniRoute-Response-Cost` (USD ដែលមានទសភាគថេរ 10 ខ្ទង់; `0.0000000000` សម្រាប់អ្វីដែលឥតគិតថ្លៃ/គ្មានតម្លៃកំណត់), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` និង `X-OmniRoute-Fallback-Attempts` (មានតែនៅពេល > 0) ព្រមទាំង `X-OmniRoute-Request-Id` និង `X-OmniRoute-Version`។ ទាំងនេះត្រូវបានបញ្ចេញដោយ chat completions, `/v1/responses`, `/v1/messages` និង **media endpoints ផងដែរ** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` និង `/v1/moderations` (តែងតែមានថ្លៃចំណាយ `0`)។ ថ្លៃចំណាយ media ត្រូវបានគណនាតាម modality នីមួយៗ (ក្នុងមួយរូបភាព ក្នុងមួយវិនាទី ក្នុងមួយតួអក្សរ ក្នុងមួយ search-unit) នៅពេលមានតម្លៃ ហើយបើមិនមាន គឺ `0` (fail-open)។

> **អត្ថន័យនៃថ្លៃចំណាយពេល cache-hit៖** នៅពេល semantic-cache HIT (`X-OmniRoute-Cache-Hit: true`) គ្មានការហៅ upstream ត្រូវបានធ្វើឡើយ ដូច្នេះ `X-OmniRoute-Response-Cost` គឺ `0.0000000000` (ថ្លៃចំណាយ **បន្ថែម** សម្រាប់ការផ្តល់លទ្ធផល hit នោះ)។ ថ្លៃចំណាយដើម/ដែលនឹងកើតមាន ត្រូវបានរាយការណ៍ដោយឡែកនៅក្នុង `X-OmniRoute-Cost-Saved`។ ប្រព័ន្ធប្រើប្រាស់ទិន្នន័យសម្រាប់ billing គួរបូកសរុប `X-OmniRoute-Response-Cost` (hit មិនមានថ្លៃចំណាយទេ); ការវិភាគ cache អាចប្រមូលផ្តុំ `X-OmniRoute-Cost-Saved`។

## ការជួលសម័យដែលបានគ្រប់គ្រងផ្តាច់មុខ

ការជួលសម័យដែលបានគ្រប់គ្រងផ្តាច់មុខ គឺជាកិច្ចសន្យាកំណត់ទិសដៅដែលអាចជ្រើសរើសប្រើ និងមិនអាស្រ័យលើកម្មវិធីអតិថិជន៖ ម្ចាស់សកម្មម្នាក់
កាន់កាប់ការតភ្ជាប់ OmniRoute ដែលមានសិទ្ធិមួយ។ វាមិនជួលម៉ូដែល មិនតម្រូវឱ្យមាន OAuth មិនកំណត់អត្តសញ្ញាណ
កម្មវិធីអតិថិជនជាក់លាក់ណាមួយ និងមិនតម្រូវឱ្យមានអ្នកផ្តល់សេវាជាក់លាក់ណាមួយឡើយ។

API key ដែលប្រើសម្រាប់ការផ្ទៀងផ្ទាត់ត្រូវតែមានវិសាលភាព `lease:exclusive` និងបញ្ជី
`allowedConnections` ដែលបានកំណត់ច្បាស់លាស់ និងមិនទទេ។ ព្រំដែននៃការកែប្រែមូលដ្ឋានទិន្នន័យអនុវត្តលក្ខខណ្ឌទាំងពីរនេះរួមគ្នា នៅពេលបង្កើត key
និងធ្វើបច្ចុប្បន្នភាពដោយផ្នែក។

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

ការឆ្លើយតបដែលជោគជ័យសម្រាប់ការទទួល ការបន្តសុពលភាព និងការដោះលែង បង្ហាញត្រាពេលវេលា `state` និងតម្លៃវិជ្ជមានពិតប្រាកដនៃ
`generation` ប៉ុន្តែមិនបង្ហាញការតភ្ជាប់ដែលបានជ្រើសរើស ឬព័ត៌មានសម្ងាត់ឡើយ។ ការបន្តសុពលភាព និងការដោះលែង ផ្តល់
generation នៅក្នុងតួ JSON៖

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

```json
{ "action": "status", "generation": 1 }
```

### `x-omniroute-compression`

ការជំនួសផែនការបង្ហាប់សម្រាប់សំណើនីមួយៗ។ មានអាទិភាពខ្ពស់បំផុត — ឈ្នះលើការជំនួស routing-combo,
profile សកម្ម ការបង្កដោយស្វ័យប្រវត្តិ និងលំនាំដើមរបស់ផ្ទាំង។ តម្លៃ៖

| តម្លៃ         | ប្រសិទ្ធភាព                                                                                          |
| ------------- | ---------------------------------------------------------------------------------------------------- |
| `off`         | មិនមានការបង្ហាប់សម្រាប់សំណើនេះ។                                                                      |
| `default`     | profile លំនាំដើមដែលបានមកពីផ្ទាំង (មិនអើពើ profile សកម្ម)។ ម៉ាស៊ីនដែលបាត់បង់ព័ត៌មានត្រូវបានទុកឱ្យបិទ។ |

| `allow-lossy` | រក្សាផែនការរបស់អ្នកប្រតិបត្តិការសម្រាប់សំណើនេះ រួមទាំងសេចក្តីសង្ខេប និងការសរសេររចនាប័ទ្មឡើងវិញ។      |

ចំណាំ៖

- តម្លៃដែលមិនស្គាល់ត្រូវបានមិនអើពើ (សំណើមិនត្រូវបានបដិសេធឡើយ); ការដោះស្រាយនឹងបន្តទៅតាមលំដាប់អាទិភាពធម្មតារបស់អ្នកប្រតិបត្តិការ។
- ប្រសិនបើ combo ច្រើនមានឈ្មោះដូចគ្នា សូមបញ្ជូន **id** របស់ combo ដើម្បីឱ្យការផ្គូផ្គងមានលទ្ធផលកំណត់ច្បាស់លាស់។
- combo ដែលមានឈ្មោះជា `off` ឬ `default` មិនអាចត្រូវបានជ្រើសរើសតាមឈ្មោះទេ (ពាក្យគន្លឹះទាំងនោះត្រូវបានបកស្រាយជាមុន); សូមយោង combo បែបនេះតាម id របស់វា។
- កុងតាក់បង្ហាប់មេគឺជាច្រកត្រួតពិនិត្យដាច់ខាត៖ នៅពេលការបង្ហាប់ត្រូវបានបិទជាសកល header នេះមិនអាចបើកវាបានទេ។

ផែនការដែលបានអនុវត្តត្រូវបានបញ្ជូនត្រឡប់ក្នុង header នៃការឆ្លើយតប៖

```

```

ដែល `<source>` គឺជាតម្លៃមួយក្នុងចំណោម `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` ឬ `off`។

```json
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

តម្លៃដើម `{ image | audio | video | pdf }` អាចជា URL HTTPS សាធារណៈ, URI `data:` ឬ
base64 ឆៅ។ OmniRoute មិនបម្លែង object ទាំងនោះទៅជា string ឬទាញយក URL រូបភាពដើមទេ — Jina ទាញយក
មេឌៀសាធារណៈដោយខ្លួនឯង។ វាល Jina បន្ថែម (`task`, `normalized`, `truncate`, `embedding_type`) ត្រូវបាន
បញ្ជូនបន្ត។ SKU របស់ Jina ដែលគាំទ្រតែអត្ថបទ នៅតែបដិសេធឯកសារដែលមិនមែនជាអត្ថបទ។

ដែនកំណត់សុវត្ថិភាព និងការបញ្ជូនទិន្នន័យ៖

- URL មេឌៀពីចម្ងាយត្រូវតែជា HTTPS សាធារណៈ។ ធាតុ Canonical `{type,source:url}` ត្រូវបានទាញយក
  នៅផ្នែក server (ការផ្ទៀងផ្ទាត់ការបញ្ជូនបន្តឡើងវិញ, timeout, ដែនកំណត់ទំហំ, DNS សាធារណៈ និងការចងភ្ជាប់ការតភ្ជាប់)
  ហើយត្រូវបានបង្កប់មុនការហៅទៅអ្នកផ្តល់សេវា។ ធាតុ Jina-native `{image:"https://..."}` ត្រូវបានបញ្ជូនបន្តដូចដើម
  បន្ទាប់ពីការត្រួតពិនិត្យ HTTPS សាធារណៈដូចគ្នា ហើយ Jina ជាអ្នកទាញយក URL។
- មេឌៀ base64 ដែលបង្កប់ផ្ទាល់ត្រូវបានកំណត់ត្រឹម 8 MiB បន្ទាប់ពីឌិកូដក្នុងមួយធាតុ និង 16 MiB បន្ទាប់ពីឌិកូដសរុបសម្រាប់សំណើទាំងមូល។

ការបម្លែងតាមអ្នកផ្តល់សេវា (ធាតុ canonical មិនត្រូវបានបញ្ជូនបន្តដោយមិនកែប្រែឡើយ)៖

- ម៉ូដែលពហុមធ្យោបាយរបស់ Jina៖ ធាតុកម្រិតកំពូលនីមួយៗត្រូវបានបម្លែងទៅជា object មួយដែលមាន key តាម modality
  (`text` / `image` / `audio` / `video` / `pdf`) ដោយប្រើ data URI សម្រាប់មេឌៀដែលបង្កប់ផ្ទាល់ ហើយមាន vector មួយសម្រាប់
  ធាតុកម្រិតកំពូលនីមួយៗ។
- ក្រុម Gemini Embedding 2៖ array កម្រិតកំពូលមួយត្រូវបានបម្លែងទៅជាសំណើដើមតែមួយ
  `models/{model}:embedContent` ដែលមាន `content.parts` (`text` ឬ `inline_data`)។
- llama.cpp (`llama-cpp/<model>`, ម៉ូដែលណាមួយដែល local server បានផ្ទុក)៖ ធាតុ canonical `text`
  ត្រូវបានបម្លែងទៅជា string ធម្មតា ហើយ `image` / `audio` / `video` នីមួយៗត្រូវបានបម្លែងទៅជា
  object `{"content": [part]}` មួយ ដោយប្រើផ្នែកមាតិកា chat របស់ llama-server (`image_url`,
  `input_audio` ដែលមានទម្រង់ `wav` / `mp3` / `flac`, `input_video`) ជាមួយទិន្នន័យដែលបង្កប់ផ្ទាល់ ហើយមាន vector មួយ
  សម្រាប់ធាតុកម្រិតកំពូលនីមួយៗ។ server ត្រូវតែដំណើរការជាមួយ `--embedding --mmproj …`។ បើគ្មាន projector ទេ
  វានឹងបដិសេធមេឌៀដោយខ្លួនឯង។ `document` មិនត្រូវបានគាំទ្រទេ។
- ម៉ូដែលមិនស្គាល់/ថាមវន្តដែលគ្មាន metadata អំពី modality ជាក់លាក់ នឹងបដិសេធ input ដែលមានរចនាសម្ព័ន្ធដោយប្រើ HTTP 400។

```json
  "model": "jina-ai/jina-embeddings-v5-omni-small",

      "type": "image",
```

```bash
Authorization: Bearer your-api-key
```

### លំហូរ poll របស់ Azure Document Intelligence

API `analyze` របស់ Azure Document Intelligence ដំណើរការដោយអសមកាលកម្ម៖ សំណើដំបូងត្រឡប់ header
`Operation-Location` ជំនួសឱ្យ body ហើយលទ្ធផលត្រូវតែត្រូវបាន poll។ Handler
(`open-sse/handlers/ocr.ts`) ធ្វើការ poll URL នោះរៀងរាល់មួយវិនាទី រហូតដល់ 30 ដង ហើយបរាជ័យភ្លាមៗ (មិន
បន្ត poll ទៀតទេ) នៅពេល response នៃការ poll មិនមែនជា `ok` ឬមានស្ថានភាព `"failed"` ហើយត្រឡប់ `504` ប្រសិនបើ

### បុព្វបទ ID របស់ម៉ូដែល (`?prefix=`)

ម៉ូដែលភាគច្រើនត្រូវបានបង្ហាញក្រោម **បុព្វបទរបស់អ្នកផ្តល់សេវា**។ បុព្វបទដែលអ្នកទទួលបានត្រូវបានគ្រប់គ្រងដោយ
feature flag `MODELS_CATALOG_PREFIX_MODE` ហើយអាចបដិសេធការកំណត់នេះ **សម្រាប់សំណើនីមួយៗ** តាមរយៈ
query parameter — វាមានប្រយោជន៍សម្រាប់ client ដែលចង់បានបញ្ជីស្អាត ដោយមិនចាំបាច់ប្តូរការកំណត់ទូទាំង server
សម្រាប់អ្នកផ្សេងទៀតទាំងអស់៖

```bash
GET /v1/models?prefix=alias        # ID មួយក្នុងមួយម៉ូដែល — បុព្វបទឈ្មោះក្លែងកាត់ខ្លី
```

### តម្រងសម្រាប់ស្វែងរក (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` ទទួលយកតម្រងសម្រាប់ស្វែងរកដែលត្រូវជ្រើសរើសប្រើ។ ប្រសិនបើគ្មានតម្រងណាមួយ ការឆ្លើយតប
មិនផ្លាស់ប្តូរទេ។ តម្រងទាំងនេះបង្រួមកាតាឡុកដែលអ្នកហៅអាចមើលឃើញរួចហើយ (សិទ្ធិ API key ត្រូវបានអនុវត្តជាមុន)
ហើយវាដំណើរការមុនការបែងចែកទំព័រតាមរចនាប័ទ្ម OpenAI ដោយប្រើ `limit` / `after`៖

```bash
GET /v1/models?capability=vision&capability=tool_calling   # សមត្ថភាពទាំងអស់ដែលបានរាយត្រូវតែជា true
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # `type` របស់កាតាឡុក; ជួរដែលគ្មានវាត្រូវចាត់ទុកជា `chat`
GET /v1/models?q=sonnet&limit=10                           # ផ្គូផ្គងដោយមិនប្រកាន់អក្សរធំតូចលើ ID ឬឈ្មោះ
```

| ប៉ារ៉ាម៉ែត្រ  | តម្លៃ                                                                                               |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | ចំនួនគត់មិនអវិជ្ជមាន ដែលត្រូវបានប្រៀបធៀបជាមួយ `context_length`                                      |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 តួអក្សរ                                                                                       |

តម្លៃដែលមិនស្គាល់ ឬ `min_context` ដែលមិនមែនជាចំនួនគត់មិនអវិជ្ជមាន (ឧទាហរណ៍ `1.5`)
ត្រឡប់ HTTP `400` ហើយសារនឹងរាយតម្លៃដែលត្រឹមត្រូវ។ ការអនុវត្ត៖
`src/app/api/v1/models/catalogFilters.ts`។

### បញ្ជីសង្ខេបម៉ូដែល (`POST /v1/models/query`)

`POST /v1/models/query` ត្រឡប់បញ្ជីខ្លីដែលមានលទ្ធផលកំណត់ជាក់លាក់ពីកាតាឡុកដូចគ្នា ដោយប្រើ
ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ និងលទ្ធភាពមើលឃើញសម្រាប់ key នីមួយៗដូចគ្នានឹង `GET /v1/models`៖

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Field ទាំងអស់សុទ្ធតែជាជម្រើស។ `capabilities` និង `exclude` អាចទទួលយក array ឬ string ដែលបំបែកដោយសញ្ញាក្បៀស;
`max_output` ប្រៀបធៀបជាមួយ `max_output_tokens`។ លទ្ធផលត្រូវបានតម្រៀបតាម `owned_by` បន្ទាប់មកតាម `id`។
`limit` មានតម្លៃលំនាំដើមជា `20` ហើយតម្លៃលើស `100` ត្រូវបានកំណត់ត្រឹម `100`។ JSON មិនត្រឹមត្រូវ field ដែលមិនស្គាល់
ឬតម្លៃមិនត្រឹមត្រូវ នឹងត្រឡប់ HTTP `400`។

### ម៉ូដែលជជែកដែលបានលាក់រៀងៗខ្លួន

ម៉ូដែលដែលត្រូវបានសម្គាល់ជា **បានលាក់** នៅលើទំព័ររបស់អ្នកផ្តល់សេវា នឹងត្រូវដកចេញពីកាតាឡុក និងត្រូវបានបដិសេធ

និងម៉ូដែលដែលបានដោះស្រាយ រួមទាំងឈ្មោះក្លែងរបស់អ្នកផ្តល់សេវា បុព្វបទ node របស់អ្នកផ្តល់សេវាដែលត្រូវគ្នា និង
ការកំណត់លំនាំដើមនៃការតភ្ជាប់។ បន្សំមួយនឹងរំលងគោលដៅដែលបានលាក់ ហើយអាចប្រើម៉ូដែលរួមក្រុមដែលអាចមើលឃើញបាន។ នៅពេលគ្មាន
គោលដៅដែលអាចប្រតិបត្តិបាននៅសល់ វានឹងត្រឡប់កូដកំហុសដូចគ្នា។ ការឈប់លាក់នឹងមានប្រសិទ្ធភាពនៅសំណើបន្ទាប់។
ការបដិសេធការកំណត់លទ្ធភាពមើលឃើញសម្រាប់តែរូបភាព មិនលាក់ម៉ូដែលជជែកដែលមាន ID ដូចគ្នាទេ។

## ការបង្កើតអូឌីយ៉ូ ElevenLabs

កំណត់រចនាសម្ព័ន្ធការតភ្ជាប់អ្នកផ្តល់សេវា `elevenlabs` នៅក្នុង OmniRoute ដោយប្រើ API key របស់ ElevenLabs។
កម្មវិធីអតិថិជនផ្ទៀងផ្ទាត់អត្តសញ្ញាណដោយប្រើ key របស់ **OmniRoute** (`Authorization: Bearer $OMNIROUTE_API_KEY`);
gateway ផ្តល់ key របស់អ្នកផ្តល់សេវាដែលបានរក្សាទុកជា `xi-api-key`។ កុំផ្ញើ key របស់ ElevenLabs
ជា bearer token របស់ gateway ឡើយ។

| វិធីសាស្ត្រ | Path                        | ការឆ្លើយតប                               | ប្រភេទ endpoint របស់ API key |
| ----------- | --------------------------- | ---------------------------------------- | ---------------------------- |
| POST        | `/v1/sound-generation`      | បៃអូឌីយ៉ូដើម                             | `elevenlabs`                 |
| POST        | `/v1/music`                 | បៃអូឌីយ៉ូដើម                             | `music`                      |
| POST        | `/v1/music/stream`          | បៃអូឌីយ៉ូបែប streaming                   | `music`                      |
| POST        | `/v1/music/detailed`        | អូឌីយ៉ូ multipart ដើម និងផែនការតែងនិពន្ធ | `music`                      |
| POST        | `/v1/music/detailed/stream` | metadata SSE ដើម និងបំណែកអូឌីយ៉ូ         | `music`                      |
| POST        | `/v1/music/plan`            | ផែនការតែងនិពន្ធ JSON                     | `music`                      |

endpoint ទាំងនេះបំពេញបន្ថែមលើ route ដែលមានស្រាប់ `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` និង `/v1/speech-to-text`។ វាល JSON ដើម
និង query parameter ដូចជា `output_format` និង `enable_logging` ត្រូវបានរក្សាទុកដដែល។
ការឆ្លើយតបពី `/v1/music/detailed` រក្សា boundary multipart របស់វា ដូច្នេះត្រូវញែកវាជា multipart។
`/v1/music/detailed/stream` ត្រឡប់ `text/event-stream` ដែលមាន metadata នៃការតែងនិពន្ធ និង
បំណែកអូឌីយ៉ូ base64 នៅក្នុងព្រឹត្តិការណ៍ SSE។ route ទាំងប្រាំមួយគាំទ្រ CORS preflight។

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# បែបផែនសំឡេងខ្លីមួយ។ រយៈពេល៖ 0.5 ដល់ 30 វិនាទី។
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# រយៈពេលតន្ត្រីគិតជាមិល្លីវិនាទី៖ 3000 ដល់ 600000។
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

ប្រើ `/v1/music/stream` ជាមួយ JSON body ដូចគ្នា ដើម្បីបញ្ជូនអូឌីយ៉ូជាបន្តបន្ទាប់។ ការតែងនិពន្ធ
ទទួលយកតែមួយក្នុងចំណោម `prompt` ឬ `composition_plan`; `/v1/music/plan` តម្រូវឱ្យមាន `prompt`
ហើយអាចទទួលយក `source_composition_plan` ជាជម្រើស។ schema ដើមរក្សាទុកវាលបន្ថែមរបស់
អ្នកផ្តល់សេវា ដើម្បីឱ្យកំណែផែនការតែងនិពន្ធ និងជម្រើស fine-tuning អាចទៅដល់ ElevenLabs។

endpoint រួម `/v1/music/generations` ក៏ទទួលយក `elevenlabs/music_v1`,
`elevenlabs/music_v2` និង `elevenlabs/music_v2_5` ផងដែរ។ នៅពេលមានការតភ្ជាប់ ElevenLabs សកម្ម
ម៉ូដែលទាំងនេះនឹងត្រូវបង្ហាញក្នុងកាតាឡុកតន្ត្រី។ endpoint នេះត្រឡប់
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}`។ វាល `duration` របស់វាគិតជា
វិនាទី ហើយត្រូវបានផ្គូផ្គងទៅនឹង `music_length_ms`; `music_length_ms` ដែលបានកំណត់ជាក់លាក់មានអាទិភាព។
`instrumental` ត្រូវបានផ្គូផ្គងទៅនឹង `force_instrumental` ដោយវាលដើមមានអាទិភាព។
ប្រើ endpoint streaming ដើមសម្រាប់ streaming និង endpoint ការតែងនិពន្ធដើម
សម្រាប់សំណើដែលដំណើរការដោយផ្អែកតែលើផែនការតែងនិពន្ធប៉ុណ្ណោះ។

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

ការរឹតបន្តឹងលើ endpoint, ម៉ូដែល, ថវិកា និងការតភ្ជាប់ ត្រូវបានអនុវត្តមុនពេលហៅទៅ upstream។ route ដើម
ត្រឡប់កូដស្ថានភាព និង error body ពី upstream ដោយមិនផ្លាស់ប្តូរ រួមទាំង `402` សម្រាប់ការរឹតបន្តឹង
លើគម្រោង និង `429` សម្រាប់ដែនកំណត់កូតា។ បឋមកថា `character-cost`, `song-id`, `request-id` និង `retry-after`
ត្រូវបានរក្សាទុកនៅពេលមាន។ សមតុល្យឥណទានឥតគិតថ្លៃមិនធានាសិទ្ធិចូលប្រើគ្រប់
ម៉ូដែលតន្ត្រី, ទម្រង់លទ្ធផល ឬមុខងារ API ទាំងអស់ទេ៖ ElevenLabs ជាអ្នកសម្រេចសិទ្ធិសម្រាប់សំណើនីមួយៗ។
endpoint រួមរក្សាកូដស្ថានភាពកំហុសនៅក្នុង error envelope ដែលបានធ្វើឱ្យមានទម្រង់ស្តង់ដាររបស់ OmniRoute។

កិច្ចសន្យា upstream៖ [បែបផែនសំឡេង](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[ការតែងនិពន្ធតន្ត្រី](https://elevenlabs.io/docs/api-reference/music/compose) និង
[ព័ត៌មានលម្អិតតន្ត្រីបែប streaming](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)។

សម្រាប់ client ដែលមិនអាចភ្ជាប់ `Authorization: Bearer ...` បាន OmniRoute ក៏ទទួលយក API key នៅក្នុង URL តាមរយៈ query string ដែលត្រូវគ្នា (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) ឬតាមរយៈចំណុចបញ្ចប់ `/api/v1/vscode/{token}/...` ជាក់លាក់ដែលបានចងក្រងឯកសារខាងក្រោម។

```bash

POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# voice ឬប្រើឈ្មោះសំឡេងស្រាប់របស់ OpenAI (alloy, nova, …) វានឹងក្លាយជា "Adrian"
```

## Batches API

ការដំណើរការជាបាច់ដែលឆបគ្នាជាមួយ OpenAI។

| វិធីសាស្ត្រ | ផ្លូវ                     | សេចក្តីពិពណ៌នា                                                                                                      |

`GET /v1/batches` បដិសេធអ្នកហៅអនាមិកដោយ `401` ទោះបីជា `REQUIRE_API_KEY=false` ក៏ដោយ។

## API ទាញយកពីវេប

ស្រង់មាតិកាពី URL តាមរយៈអ្នកផ្តល់សេវាទាញយកពីវេបដែលបានកំណត់រចនាសម្ព័ន្ធ (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract)។

Parallel Extract (`parallel-search`, ប្រើ API key ដូចគ្នានឹង Parallel Search) ត្រឡប់តែ Markdown
ប៉ុណ្ណោះ — `format` ផ្សេងទៀតទាំងអស់នឹងទទួលបាន `400` — ហើយកំណត់មាតិកាអតិបរមាត្រឹម 100,000 តួអក្សរ។ នៅពេល
ទំព័រគោលដៅមិនអាចត្រូវបានស្រង់ Upstream នឹងរាយការណ៍វានៅក្នុង HTTP 200;
OmniRoute បង្ហាញករណីនោះជា `422` ជាមួយសារថេរមួយ។

| វិធីសាស្ត្រ | ផ្លូវ           | សេចក្ដីពិពណ៌នា                                                             |
| ----------- | --------------- | -------------------------------------------------------------------------- |
| POST        | `/v1/web/fetch` | ទាញយក/ស្រង់ទិន្នន័យពី URL — body ត្រូវបានផ្ទៀងផ្ទាត់ដោយ `v1WebFetchSchema` |

**ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ:** Bearer API key (`extractApiKey` + `isValidApiKey`)។ គោលការណ៍ត្រូវបានអនុវត្តតាមរយៈ `enforceApiKeyPolicy`។

**ការប្តូរទៅជម្រើសបម្រុងដោយគិតគូរពីកូតា (#8297):** នៅពេលមិនមានការបញ្ជាក់ `provider` ជាក់លាក់ pool
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) នឹងត្រូវបាន
ពិនិត្យតាមលំដាប់អាទិភាពថេរ
(fill-first) — អ្នកផ្តល់សេវាដែលបានកំណត់រចនាសម្ព័ន្ធ ប៉ុន្តែត្រូវបានកម្រិតអត្រា នឹងត្រូវបានរំលង
ជំនួសឱ្យការបញ្ឈប់សំណើភ្លាមៗ ហើយកំហុស Upstream ដែលអាចសាកល្បងឡើងវិញបាន/ទាក់ទងនឹងកូតា
(HTTP 429 ជានិច្ច; 402/403 សម្រាប់កម្រិតឥតគិតថ្លៃដែលមានលក្ខណៈជាកូតារបស់ Firecrawl/Tavily/TinyFish —
មិនអនុវត្តចំពោះ Jina Reader ហើយមិនដែលអនុវត្តចំពោះសំណើមិនត្រឹមត្រូវ 400 ធម្មតាទេ) នឹងបន្តទៅ
អ្នកផ្តល់សេវាបន្ទាប់ដែលមានព័ត៌មានសម្ងាត់ និងមិនទាន់បានសាកល្បង នៅពេលដំណើរការសំណើ។ នៅពេលអ្នកផ្តល់សេវាទាំងអស់ក្នុង
pool ត្រូវបានប្រើអស់ endpoint នឹងត្រឡប់ `429` តែមួយ (ជាមួយ header `Retry-After`)

Upstream)។

## ការស្ទ្រីមតាម WebSocket

```bash
GET /v1/ws?handshake=1
```

ផ្ទៀងផ្ទាត់ WebSocket upgrade handshake ហើយត្រឡប់សារគំរូនៃ wire protocol (`request`, `cancel`)។ WS frame ពិតប្រាកដត្រូវបានគ្រប់គ្រងដោយ WS server ដែលបានរួមបញ្ចូល នៅក្រៅតារាង route របស់ Next.js។

**ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ:** Bearer API key អំឡុងពេល handshake។

### Responses API តាមរយៈ WebSocket (សម្រាប់តែ codex)

```bash
# ម៉ាស៊ីន និងច្រកដូចគ្នានឹង HTTP API (លំនាំដើម 20128); ធ្វើ upgrade ការតភ្ជាប់៖
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (ឬ៖ -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# frame ដំបូងត្រូវតែជា response.create៖
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

ប្រូកស៊ី Responses-API-over-WebSocket ត្រូវបានភ្ជាប់**ផ្តាច់មុខទៅ `codex`** (backend របស់ ChatGPT)។

`/responses` និង `/api/v1/responses`។ នៅលើ frame `response.create` ដំបូង វា
ផ្ទៀងផ្ទាត់អត្តសញ្ញាណ + រៀបចំតាមរយៈ bridge ខាងក្នុង `codex-responses-ws` ជ្រើសរើស

## ការពិនិត្យការប្រើប្រាស់ដោយខ្លួនឯង (`/api/usage/om-usage`)

សោ API ណាមួយអាចអានទិន្នន័យការប្រើប្រាស់ និងកូតា **របស់ខ្លួនឯង** បាន — មិនត្រូវការការផ្ទៀងផ្ទាត់អត្តសញ្ញាណសម្រាប់ការគ្រប់គ្រងទេ។ នេះគឺជា endpoint ដែល
client (CLI ឬផ្ទាំង OmniCopilot) ប្រើដើម្បីបង្ហាញការចំណាយរបស់អ្នកកាន់សោ។

```bash
# ទម្រង់អត្ថបទ (កិច្ចសន្យាដែលមានតាំងពីមុន — អត្ថបទធម្មតាសម្រាប់ terminal)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# ទម្រង់មានរចនាសម្ព័ន្ធ — អ្វីដែល UI ប្រើប្រាស់
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

សោត្រូវតែបើក **`allowUsageCommand`** (បិទតាមលំនាំដើម — កម្មវិធីគ្រប់គ្រងសោ API របស់ dashboard
បិទបើកវាសម្រាប់សោនីមួយៗ)។ បើគ្មានវា endpoint នឹងឆ្លើយតបដោយ `403`។

`?format=json` ត្រឡប់រចនាសម្ព័ន្ធដែលអាចបែងចែកប្រភេទបាន ដូច្នេះអ្នកហៅមិនអានវាលទិន្នន័យពី
ការបដិសេធឡើយ។ នៅពេលជោគជ័យ៖

```jsonc
{
  "allowed": true,
  // មានតែនៅពេលសោបានជ្រើសរើសប្រើដែនកំណត់ការប្រើប្រាស់តាមសោ (USD ប្រចាំថ្ងៃ/ប្រចាំសប្ដាហ៍)៖
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // រូបថតបច្ចុប្បន្ននៃកូតារបស់អ្នកផ្តល់សេវាដែលបានជ្រើសរើស ឬ null នៅពេលមិនទាន់មានអ្វីត្រូវបានរក្សាទុកក្នុងឃ្លាំងសម្ងាត់៖
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // រូបថតបច្ចុប្បន្នរបស់ការតភ្ជាប់ទាំងអស់ ដើម្បីឱ្យ UI អាចបង្ហាញអ្នកផ្តល់សេវាច្រើននៅក្បែរគ្នា៖
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

នៅពេលបដិសេធ (`401` សោមិនត្រឹមត្រូវ / `403` មិនត្រូវបានអនុញ្ញាត) route ដដែលនឹងត្រឡប់
`{ "allowed": false, "error": { "message": "…" } }` — `personal`/`provider` ដែលមានវត្តមានប៉ុន្តែទទេ
(សោត្រូវបានអនុញ្ញាត ប៉ុន្តែមិនទាន់ទទួលបានព័ត៌មានអ្វី) គឺជាស្ថានភាពខុសពីការបដិសេធ ហើយមានតែទម្រង់ JSON ប៉ុណ្ណោះ
ដែលអាចបែងចែកស្ថានភាពទាំងនេះបាន។

**ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ:** សោ Bearer API ផ្ទាល់របស់អ្នកហៅ ដែលត្រូវបានផ្ទៀងផ្ទាត់ដោយ `isValidApiKey` — នេះ _មិនមែន_ ជា
ផ្ទៃគ្រប់គ្រង (`/api/keys/…`) ដែលនៅតែត្រូវបានការពារដោយ `requireManagementAuth` នោះទេ។

### ភាគរយកូតាដើម ធៀបនឹងភាគរយកូតាដែលបានកែតម្រូវតាមកម្រិតកាត់ផ្តាច់

នៅពេលប្រើប្រាស់ `/api/usage/om-usage` អ្នកហៅគួរកត់សម្គាល់ភាពខុសគ្នារវាង
ភាគរយដែលបង្ហាញដោយ **លទ្ធផលជាអត្ថបទធម្មតា** និងលទ្ធផល **JSON** ដែលមានរចនាសម្ព័ន្ធ៖

| ទិដ្ឋភាព                                 | ទម្រង់អត្ថបទធម្មតា (`/api/usage/om-usage` / `@@om-usage`)                                             | ទម្រង់ JSON (`?format=json`)                                                                |
| :--------------------------------------- | :---------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------ |
| **វាលលទ្ធផល**                            | `NN% left` (ឧ. `20% left`)                                                                            | `provider.quotas` / `providers[].quotas`                                                    |
| **រង្វាស់**                              | **ចំណែកប្រើប្រាស់ដែលបានកែតម្រូវតាមកម្រិតកាត់ផ្តាច់**៖ សមត្ថភាពដែលនៅសល់លើសកម្រិតកាត់ផ្តាច់             | **កូតាដើមពីប្រភពផ្តល់សេវា**៖ រង្វាស់មិនបានកែតម្រូវពីអ្នកផ្តល់សេវា                           |
| **ការធ្វើមាត្រដ្ឋានតាមកម្រិតកាត់ផ្តាច់** | ធ្វើមាត្រដ្ឋានតាមរយៈ `effectiveRemainingPercent()` ដើម្បីឱ្យចំណែកបម្រុងដែលបានការពារបង្ហាញជា `0% left` | គ្មាន (តម្លៃរូបថតបច្ចុប្បន្នដើម ដូចដែលបានរាយការណ៍ដោយអ្នកផ្តល់សេវា)                          |
| **ទិន្នន័យកម្រិតកំណត់**                  | ត្រូវបានបញ្ចូលក្នុងភាគរយដែលបង្ហាញ                                                                     | រក្សាទុកក្នុង `quotaWindowThresholds` សម្រាប់ការតភ្ជាប់នីមួយៗ (ឬតម្លៃលំនាំដើមរបស់ម៉ាស៊ីនមេ) |
| **អ្នកប្រើប្រាស់ចម្បង**                  | CLI អន្តរកម្ម សារបញ្ចូលក្នុង terminal និងប្រតិបត្តិករមនុស្ស                                           | ការរួមបញ្ចូលតាមកម្មវិធី dashboard ការវិភាគ និងឧបករណ៍តាមដានវិក្កយបត្រ                        |

#### រូបមន្តកែតម្រូវកម្រិតកាត់ផ្តាច់

OmniRoute គាំទ្រការកំណត់កម្រិតកាត់ផ្តាច់កូតាជាមុន ដើម្បីទប់ស្កាត់ការប្រើធនធានពីប្រភពផ្តល់សេវាអស់ទាំងស្រុង (កំណត់រចនាសម្ព័ន្ធតាមរយៈ
`quotaWindowThresholds` របស់ការតភ្ជាប់ តម្លៃលំនាំដើមរបស់អ្នកផ្តល់សេវា ឬការកំណត់ភាពធន់សកល)។ នៅពេលកម្រិតកាត់ផ្តាច់
(ឧ. `cutoff = 25%`) សកម្មលើចន្លោះកូតាមួយ កម្មវិធីបង្ហាញអត្ថបទគណនាចំណែកប្រើប្រាស់ដែលនៅសល់ដូចខាងក្រោម៖

- ប្រសិនបើ `remaining <= cutoff`៖ ត្រឡប់ `0%`។
- ប្រសិនបើ `remaining > cutoff`៖ ត្រឡប់ `((remaining - cutoff) / (100 - cutoff)) * 100`។

លទ្ធផលអត្ថបទដែលបានធ្វើទ្រង់ទ្រាយនឹងបង្គត់ទៅចំនួនគត់ដែលនៅជិតបំផុត (`Math.round(...)`)។

#### ឧទាហរណ៍បង្ហាញ

ពិចារណាចន្លោះរបស់អ្នកផ្តល់សេវាមួយដែលមាន **ការប្រើប្រាស់ដើម 60%** (ដូច្នេះ **កូតាដើមនៅសល់ 40%**) និងបានកំណត់
កម្រិត **កាត់ផ្តាច់កូតានៅសល់ 25%**៖

| របៀបបង្ហាញ                    | ការគណនា                                             |  នៅសល់  |          ភាគរយដែលសន្មតថាបានប្រើ          |
| :---------------------------- | :-------------------------------------------------- | :-----: | :--------------------------------------: |
| **JSON ដើម (`?format=json`)** | រូបថតបច្ចុប្បន្នពីប្រភពផ្តល់សេវា (`quotas[window]`) | **40%** |                 **60%**                  |
| **ទម្រង់អត្ថបទ (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100`  | **20%** | **80%** (ប្រសិនបើគណនា `100 - remaining`) |

- **មូលហេតុដែលអត្ថបទបង្ហាញថានៅសល់ 20%៖** ក្នុងចំណោមកូតាជាក់ស្តែង 40% ដែលនៅសល់ក្នុងគណនី 25% ត្រូវបានបម្រុងទុកដោយ
  គោលការណ៍កាត់ផ្តាច់។ អ្នកហៅមានចន្លោះប្រើប្រាស់ត្រឹមតែ 15% ក្នុងចំណោមចន្លោះដែលអាចប្រើបាន 75% មុនពេល router ឈប់
  បញ្ជូនសំណើទៅការតភ្ជាប់នេះ។ ការធ្វើមាត្រដ្ឋានធានាថាការតភ្ជាប់បង្ហាញសញ្ញាថាបានប្រើអស់ (`0% left`) ចំពេលដែល
  ការបញ្ជូននឹងឈប់។
- **មូលហេតុដែល JSON រក្សាតម្លៃដើម៖** payload JSON ត្រឡប់រូបថតបច្ចុប្បន្នពិតប្រាកដរបស់អ្នកផ្តល់សេវា (`UsageSnapshot`)
  ដើម្បីឱ្យឧបករណ៍ខាងក្រៅអាចចូលប្រើទិន្នន័យពិតប្រាកដនៃការប្រើប្រាស់ពីប្រភពផ្តល់សេវា និង
  `quotaWindowThresholds` កម្រិតការតភ្ជាប់ ដោយមិនមានការធ្វើមាត្រដ្ឋានដែលបាត់បង់ទិន្នន័យពីផ្នែកម៉ាស៊ីនមេ។

#### ការណែនាំសម្រាប់ការផ្លាស់ប្តូររបស់អ្នកប្រើប្រាស់

ប្រសិនបើការរួមបញ្ចូលខាងក្រៅ (ដូចជាកម្មវិធីជំនួយសម្រាប់កម្មវិធីកែសម្រួល ឬផ្នែកបន្ថែមរបស់ agent) ពីមុនបានទាញយកទិន្នន័យពីចំណុចចុង
អត្ថបទ (`NN% left`) ហើយគណនាភាគរយដែលបានប្រើជា `100 - NN` ការផ្លាស់ប្តូរទៅ `?format=json` មានន័យថា៖

- ការអានតម្លៃ JSON ដើមនឹងបង្ហាញពី **ការប្រើប្រាស់ជាក់ស្តែងនៅប្រភពខាងលើ** (បានប្រើ 60% ក្នុងឧទាហរណ៍ខាងលើ)។
- ប្រសិនបើការរួមបញ្ចូលចង់រក្សាន័យនៃចំនួនដែលអាចប្រើបានរបស់ចំណុចចុងអត្ថបទ វាអាចវាយតម្លៃ
  រូបមន្តចំនួនដែលនៅសល់ជាក់ស្តែងនៅផ្នែក client ដោយប្រើ `quotaWindowThresholds` សម្រាប់ការកំណត់ជំនួសនៅកម្រិតការតភ្ជាប់។

### កំណែ និងឆានែលចេញផ្សាយ

```bash
GET /api/system/version
```

ផ្លូវគ្រប់គ្រងសម្រាប់តែ loopback ប៉ុណ្ណោះ (ការផ្ទៀងផ្ទាត់អ្នកគ្រប់គ្រង)។ ត្រឡប់កំណែដែលកំពុងដំណើរការ កំណែចុងក្រោយ
ដែលបានចេញផ្សាយ និងស្ថានភាពអាប់ដេតដោយស្វ័យប្រវត្តិ។ `releaseChannel` និង `channels` ជាវាលបន្ថែម
(ខ្សែ 3.8.54); `channel` រក្សាអត្ថន័យដដែល — របៀបដាក់ពង្រាយដែលកម្មវិធីអាប់ដេតផ្ទាំងគ្រប់គ្រង
ប្រើ (`npm`, `source` ឬ `docker-compose`)។

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — ឆានែល npm នៃ build ដែលកំពុងដំណើរការ៖ `nightly` សម្រាប់កំណែ `-nightly.*`,
  `next` សម្រាប់កំណែមុនចេញផ្សាយផ្សេងទៀត (`-rc.*`, `-beta.*`, `-alpha.*`), `lts` សម្រាប់កំណែមានស្ថិរភាពនៃ
  កំណែ major ចាស់ជាង `channels.latest`, បើមិនដូច្នោះទេគឺ `latest`។ ប្រើច្បាប់ដូចគ្នានឹង
  `scripts/release/dist-tag.mjs` ដែលជ្រើស npm dist-tag នៅពេលចេញផ្សាយ។
- `channels` — កំណែកំពូលដែលបានចេញផ្សាយនៃ dist-tag នីមួយៗ ពី `npm view omniroute dist-tags` (ប្រើ registry
  HTTP ជាជម្រើសបម្រុង) ដែលត្រូវបាន cache ដោយមាន TTL 10 នាទីដូចគ្នានឹង `latest`។ `latest` តែងតែមាន
  (បើមិនមាន នឹងប្រើវាល `latest` ហើយបន្ទាប់មក `"unavailable"`); `next`, `nightly` និង `lts` បង្ហាញ
  តែនៅពេលដែលមាន dist-tag នោះប៉ុណ្ណោះ។ សំណើ `Cache-Control: no-cache` នឹងធ្វើឱ្យការស្វែងរកទាំងពីរស្រស់ឡើងវិញ។

ម៉ូដែលឆានែល (`latest` = v3 រហូតដល់ 4.0 GA, `next` = rc, `nightly` = build ពី `develop`,
`lts` = patch របស់ v3 បន្ទាប់ពី 4.0 GA) ត្រូវបានពិពណ៌នានៅក្នុង `docs/ops/RELEASE_STRATEGY.md`។

## ការចម្លងសំឡេងជាអត្ថបទ

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

ចម្លងឯកសារសំឡេងជាអត្ថបទដោយប្រើក្រុមហ៊ុនផ្ដល់សេវា STT ដែលបានកំណត់រចនាសម្ព័ន្ធណាមួយ។ ផ្នែកទីមួយនៃផ្លូវ
ជ្រើសរើសក្រុមហ៊ុនផ្ដល់សេវាដើម (`openai/…`, `deepgram/…`)។ ច្រកទ្វារដែល
នាំចេញម៉ូដែលរបស់ក្រុមហ៊ុនផ្ដល់សេវាផ្សេងឡើងវិញ ប្រើលេខសម្គាល់ដែលមានឈ្មោះកំណត់ពេញលេញ
(`openrouter/deepgram/nova-3`)។

**សំណើ:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**ការឆ្លើយតប:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**លេខសម្គាល់ម៉ូដែលឧទាហរណ៍:** `openai/whisper-1` (តម្រូវឱ្យមានសោ OpenAI),
`openrouter/deepgram/nova-3` (តម្រូវឱ្យមានសោ OpenRouter),
`deepgram/nova-3` (តម្រូវឱ្យមានសោដើមរបស់ Deepgram)។ សំណើ
`deepgram/nova-3` ដែលគ្មានឈ្មោះកំណត់បន្ថែម **មិន** ប្រើ OpenRouter ទេ។

**ទម្រង់ដែលគាំទ្រ:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`។


កំណត់សម្គាល់:

- ឈ្មោះក្លែងដែលមានថូខឹន ប្រើកម្មវិធីដោះស្រាយដូចគ្នានឹង `/v1/*` និង `/api/tags`; រចនាសម្ព័ន្ធការឆ្លើយតបនៅតែដូចគ្នា។
- គួរប្រើ `Authorization: Bearer ...` នៅពេលណាដែលកម្មវិធីអតិថិជនគាំទ្របឋមកថាផ្ទាល់ខ្លួន។
- ថូខឹនដែលមានមូលដ្ឋានលើ URL អាចលេចឡើងក្នុងកំណត់ហេតុ reverse-proxy ប្រវត្តិកម្មវិធីរុករក និងទិន្នន័យទូរមាត្រនៅក្រៅ OmniRoute។ ចាត់ទុកពួកវាជាជម្រើសសម្រាប់ភាពត្រូវគ្នា មិនមែនជារបៀបផ្ទៀងផ្ទាត់អត្តសញ្ញាណលំនាំដើមទេ។

## ថវិកា

```bash
# ទទួលយកស្ថានភាពថវិកាសម្រាប់សោ API ទាំងអស់
GET /api/usage/budget

Content-Type: application/json

{
  "apiKeyId": "key-123",
  "dailyLimitUsd": 5.00,
  "weeklyLimitUsd": 30.00,

```

> **កំណត់សម្គាល់អំពីគ្រោងការណ៍** (`setBudgetSchema`): តម្រូវឱ្យមាន `apiKeyId`; យ៉ាងហោចណាស់តម្លៃមួយក្នុងចំណោម `dailyLimitUsd`, `weeklyLimitUsd` ឬ `monthlyLimitUsd` ត្រូវតែធំជាងសូន្យ។ វាលស្រេចចិត្ត: `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`)។ រចនាសម្ព័ន្ធចាស់ `{keyId, limit, period}` ត្រឡប់ `400 Bad Request`។

## ដែនកំណត់ Token

កញ្ចប់ថវិកា **token** សម្រាប់ API key នីមួយៗ (ខុសពីកញ្ចប់ថវិកាផ្អែកលើ USD ខាងលើ)។ ដែនកំណត់ទាំងនេះត្រូវបានអនុវត្តដោយផ្ទាល់លើផ្លូវសំណើ៖ នៅពេលការប្រើប្រាស់ក្នុងចន្លោះពេលបច្ចុប្បន្នរបស់ key ឈានដល់ដែនកំណត់ សំណើនឹងត្រូវបានបដិសេធដោយ `429 Too Many Requests`។ ដែនកំណត់អាចកំណត់វិសាលភាពសម្រាប់ `model` ជាក់លាក់មួយ ឬ `provider` មួយ ឬអនុវត្តជា `global` ទូទាំង key នោះ។ នៅពេលមានដែនកំណត់ច្រើនត្រូវគ្នានឹងសំណើមួយ ដែនកំណត់ដែលតឹងរ៉ឹងបំផុតនឹងត្រូវបានអនុវត្ត។

```bash
# រាយបញ្ជីដែនកំណត់ token របស់ key មួយ (រួមទាំងការប្រើប្រាស់បច្ចុប្បន្នក្នុងចន្លោះពេល)
GET /api/usage/token-limits?apiKeyId=key-123

# បង្កើត ឬធ្វើបច្ចុប្បន្នភាពដែនកំណត់ token
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# លុបដែនកំណត់ token តាម id
DELETE /api/usage/token-limits?id=tl-abc
```

> **កំណត់សម្គាល់អំពី Schema** (`setTokenLimitSchema`): តម្រូវឱ្យមាន `apiKeyId` និង `scopeType` (`model` | `provider` | `global`)។ តម្រូវឱ្យមាន `scopeValue` លើកលែងតែ `scopeType` ជា `global` (ឧ. id របស់ model សម្រាប់វិសាលភាព `model` ឬ id របស់ provider សម្រាប់វិសាលភាព `provider`)។ `tokenLimit` ត្រូវតែជាចំនួនគត់វិជ្ជមាន (បំប្លែងពី string)។ ជាជម្រើស៖ `id` (កុំបញ្ចូលដើម្បីបង្កើត បញ្ចូលដើម្បីធ្វើបច្ចុប្បន្នភាព), `resetInterval` (`daily` | `weekly` | `monthly`, លំនាំដើម `monthly`), `resetTime` (`HH:MM`), `enabled` (លំនាំដើម `true`)។ ការឆ្លើយតបរបស់ `GET` បន្ថែមព័ត៌មានទៅដែនកំណត់នីមួយៗដោយមាន `tokensUsed`, `remaining`, `windowStart`, `periodStartAt`, និង `nextResetAt`។ នេះជា endpoint ថ្នាក់គ្រប់គ្រង (ការផ្ទៀងផ្ទាត់សិទ្ធិត្រូវបានអនុវត្តកណ្ដាលដោយ authz pipeline)។

## ដំណើរការសំណើ

1. Client ផ្ញើសំណើទៅ `/v1/*`
2. Route handler ហៅ `handleChat`, `handleEmbedding`, `handleAudioTranscription`, ឬ `handleImageGeneration`
3. Model ត្រូវបានកំណត់ (provider/model ផ្ទាល់ ឬ alias/combo)
4. Credentials ត្រូវបានជ្រើសរើសពី DB មូលដ្ឋាន ដោយមានការច្រោះតាមភាពអាចប្រើបានរបស់ account
5. សម្រាប់ chat៖ `handleChatCore` ពិនិត្យ semantic/signature cache និងកំណត់ការកំណត់ combo compression
6. Proactive compression ដំណើរការមុនការបំប្លែងសម្រាប់ provider នៅពេលបានបើកប្រើ (`lite`, Caveman, RTK, ឬការដាក់ជាជាន់ៗ)
7. Provider executor ផ្ញើសំណើទៅ upstream
8. Response ត្រូវបានបំប្លែងត្រឡប់ទៅជាទម្រង់របស់ client (សម្រាប់ chat) ឬត្រឡប់ដូចដើម (សម្រាប់ embeddings/images/audio)
9. Usage, compression analytics, និង request logs ត្រូវបានកត់ត្រា
10. Fallback ត្រូវបានអនុវត្តនៅពេលមានកំហុស ស្របតាមច្បាប់របស់ combo

ឯកសារយោងអំពីស្ថាបត្យកម្មពេញលេញ៖ [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## ភាពធន់នឹងបញ្ហា (បន្ថែម)

OmniRoute ផ្តល់យន្តការឯករាជ្យចំនួនបីសម្រាប់គ្រប់គ្រងការបរាជ័យបណ្ដោះអាសន្ន។ Endpoint គ្រប់គ្រងខាងក្រោមអនុញ្ញាតឱ្យអ្នកប្រតិបត្តិការអាន និងកែសម្រួលពួកវា៖

| វិសាលភាព                            | កន្លែងផ្ទុកស្ថានភាព                              | អាន                                       | កំណត់ឡើងវិញ / សម្អាត                                                |
| ----------------------------------- | ------------------------------------------------ | ----------------------------------------- | ------------------------------------------------------------------- |
| ឧបករណ៍ផ្តាច់សៀគ្វីរបស់អ្នកផ្តល់សេវា | `domain_circuit_breakers` + ក្នុងអង្គចងចាំ       | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                        |
| រយៈពេលរង់ចាំនៃការតភ្ជាប់            | `rateLimitedUntil` លើការតភ្ជាប់របស់អ្នកផ្តល់សេវា | `/api/rate-limits`, `/api/providers/[id]` | (បើកដំណើរការឡើងវិញនៅពេលចាំបាច់; សម្អាតតាមរយៈ PUT របស់អ្នកផ្តល់សេវា) |
| ការចាក់សោម៉ូដែល                     | បញ្ជីឈ្មោះភាពអាចប្រើបានរបស់ម៉ូដែលក្នុងអង្គចងចាំ  | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                            |

`PATCH /api/resilience` ទទួលយកការកំណត់ជំនួសសម្រាប់ឧបករណ៍ផ្តាច់សៀគ្វីរបស់អ្នកផ្តល់សេវា នៅក្រោម `providerBreaker.oauth` និង `providerBreaker.apikey`។ ទម្រង់នីមួយៗគាំទ្រ `degradationThreshold`, `failureThreshold` និង `resetTimeoutMs`។ វាលដូចគ្នាទាំងនេះក៏មាននៅក្នុង Dashboard → Settings → Resilience ផងដែរ។

```bash
# សម្អាតការចាក់សោសម្រាប់ម៉ូដែលតែមួយ
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# សម្អាតការចាក់សោទាំងអស់
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

សម្រាប់ឯកសារយោងពេញលេញអំពីគោលគំនិត និងតម្លៃលំនាំដើមរបស់ឧបករណ៍ផ្តាច់សៀគ្វី៖ សូមមើល [`CLAUDE.md`](../../CLAUDE.md) → "ស្ថានភាពពេលដំណើរការនៃភាពធន់នឹងបញ្ហា" និង [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md)។

### ជួររង់ចាំកម្រិតអត្រា និងយន្តការសុវត្ថិភាពបើកដំណើរការដោយស្វ័យប្រវត្តិ

- **ផ្លូវសរសេរដែលគាំទ្រ**៖ `POST /api/rate-limits` ជាមួយ body `{"connectionId": "<id>", "enabled": true|false}` គឺជា endpoint គ្រប់គ្រងដែលគាំទ្រសម្រាប់បិទបើកការការពារកម្រិតអត្រាសម្រាប់ការតភ្ជាប់មួយ។ `PUT /api/providers/[id]` មិនកែប្រែ ឬប្ដូរស្ថានភាព `rateLimitProtection` ដោយចេតនាទេ (#11278)។
- **អត្ថន័យរបស់ `enabled: false`**៖ ការកំណត់ `enabled: false` នឹងលុបការការពារដែលបានកំណត់ជាក់លាក់សម្រាប់ការតភ្ជាប់ ប៉ុន្តែវា **មិន** ដកការតភ្ជាប់ API-key ដែលកំពុងសកម្មចេញពីយន្តការសុវត្ថិភាពបើកដំណើរការដោយស្វ័យប្រវត្តិសកល (`autoEnableApiKeyProviders = true`) ទេ។ នៅក្នុង `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) `false` និង `undefined` មានន័យដូចគ្នា។ ការតភ្ជាប់ API-key ដែលកំពុងសកម្ម និងគ្មានការការពារដែលបានកំណត់ជាក់លាក់ នៅតែទទួលបានការការពារក្រោមយន្តការសុវត្ថិភាពបើកដំណើរការដោយស្វ័យប្រវត្តិ។
- **ការបិទជាសកល**៖ ដើម្បីដំណើរការការតភ្ជាប់ API-key ដោយគ្មានជួររង់ចាំកម្រិតអត្រា សូមបិទយន្តការសុវត្ថិភាពជាសកលតាមរយៈ `RATE_LIMIT_AUTO_ENABLE=false` (env) ឬ `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`)។

## ម៉ាស៊ីនមេ MCP

OmniRoute ភ្ជាប់មកជាមួយម៉ាស៊ីនមេ Model Context Protocol ដែលបង្កប់ក្នុងប្រព័ន្ធ ដោយមាន transport ចំនួន 3 (stdio, SSE, streamable-http) និងឧបករណ៍ដែលកំណត់វិសាលភាព។ endpoint របស់ dashboard ខាងក្រោមអានទិន្នន័យស្ថានភាព/សវនកម្ម និងធ្វើប្រូកស៊ី transport HTTP។

| វិធីសាស្ត្រ | ផ្លូវ | សេចក្ដីពិពណ៌នា |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | Heartbeat, transport, ស្ថានភាពអនឡាញ, ការហៅចុងក្រោយ, ឧបករណ៍ដែលប្រើច្រើនបំផុត, អត្រាជោគជ័យក្នុងរយៈពេល 24 ម៉ោង |
| GET | `/api/mcp/tools` | បញ្ជីឧបករណ៍ MCP ដែលមាន `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` |
| GET | `/api/mcp/sse` | បើក SSE stream សម្រាប់ SSE transport (ត្រឡប់ `503` ប្រសិនបើ MCP ត្រូវបានបិទ ឬ transport មិនត្រូវគ្នា) |
| POST | `/api/mcp/sse` | ផ្ញើ JSON-RPC frame តាម SSE transport |
| GET | `/api/mcp/stream` | បើកផ្នែក SSE នៃ Streamable HTTP transport (សារដែលផ្ដួចផ្ដើមដោយម៉ាស៊ីនមេ) |
| POST | `/api/mcp/stream` | ផ្ញើ JSON-RPC frame តាម Streamable HTTP transport |
| DELETE | `/api/mcp/stream` | បញ្ចប់ session របស់ Streamable HTTP |
| GET | `/api/mcp/audit` | សាកសួរកំណត់ហេតុសវនកម្ម — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | ស្ថិតិសវនកម្មសរុប (ចំនួនសរុប, អត្រាជោគជ័យ, រយៈពេលមធ្យម, ឧបករណ៍ដែលប្រើច្រើនបំផុត) |

**ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ៖** transport `sse`/`stream` គោរពតាមផ្ទៃការផ្ទៀងផ្ទាត់អត្តសញ្ញាណជាក់លាក់របស់ MCP (Bearer API key ដែលមានវិសាលភាព `mcp`)។ route `status`/`tools`/`audit*` អាចអានបានពី dashboard (មិនតម្រូវឱ្យមានការផ្ទៀងផ្ទាត់អត្តសញ្ញាណបន្ថែម ក្រៅពីអាចចូលដល់ dashboard host)។

## ម៉ាស៊ីនមេ A2A

OmniRoute ផ្តល់ endpoint A2A (Agent-to-Agent) JSON-RPC 2.0 ព្រមទាំង wrapper REST សម្រាប់ការត្រួតពិនិត្យ និងការប្រើប្រាស់ក្នុង dashboard។

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # ជាជម្រើស លុះត្រាតែ OMNIROUTE_API_KEY ត្រូវបានកំណត់
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

វិធីសាស្ត្រដែលគាំទ្រ (ទាំងអស់ត្រូវបានគ្រប់គ្រងដោយ `settings.a2aEnabled`)៖

| វិធីសាស្ត្រ      | សេចក្ដីពិពណ៌នា                                                        |
| ---------------- | --------------------------------------------------------------------- |
| `message/send`   | ប្រតិបត្តិ skill ដោយសមកាលកម្ម ហើយត្រឡប់ `{task, artifacts, metadata}` |
| `message/stream` | ប្រតិបត្តិ streaming SSE លើសំណុំ skill ដូចគ្នា                        |
| `tasks/get`      | ទាញយក task តាម `taskId`                                               |
| `tasks/cancel`   | បោះបង់ task តាម `taskId`                                              |

Skill ដែលមានស្រាប់៖ `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`។

### កាត Agent

```bash
GET /.well-known/agent.json
```

ត្រឡប់កាត agent A2A សាធារណៈ (ឈ្មោះ សេចក្ដីពិពណ៌នា សមត្ថភាព កាតាឡុក skill និងគ្រោងការណ៍ auth) — ត្រូវបាន cache ជាសាធារណៈរយៈពេល 1 ម៉ោង។ មិនទាមទារ auth ទេ។

### ជំនួយការ REST

| វិធីសាស្ត្រ | Path                         | សេចក្ដីពិពណ៌នា                                                                                                     |
| ----------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| GET         | `/api/a2a/status`            | ស្ថានភាពបើក A2A + ស្ថិតិ task + សេចក្ដីសង្ខេបកាត agent ដែលបាន cache                                                |
| GET         | `/api/a2a/tasks`             | រាយបញ្ជី task — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST        | `/api/a2a/tasks`             | (មិនទាន់ត្រូវបានអនុវត្តជាជំនួយការ REST ទេ — បង្កើតតាម JSON-RPC `message/send`)                                     |

## ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ

សូមមើល [ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណសម្រាប់ការគ្រប់គ្រង](../guides/MANAGEMENT-AUTH.md) សម្រាប់ព័ត៌មានអំពីក្រុមព័ត៌មានសម្គាល់អត្តសញ្ញាណទាំងបួន
(សម័យ dashboard, token របស់ CLI មូលដ្ឋាន, `oma_live_…` Access
Token និង API key ដែលមានវិសាលភាពគ្រប់គ្រង) ព្រមទាំងភាពខុសគ្នារបស់ពួកវាពី inference key។

- Route របស់ dashboard (`/dashboard/*`) ប្រើ cookie `auth_token`
- ការចូលប្រើប្រើ password hash ដែលបានរក្សាទុក ដោយប្រើ `INITIAL_PASSWORD` ជាជម្រើសបម្រុង
- `requireLogin` អាចបិទបើកបានតាមរយៈ `/api/settings/require-login`
- Route `/v1/*` អាចតម្រូវឱ្យមាន Bearer API key នៅពេល `REQUIRE_API_KEY=true`
- «management token» / «management-scoped API key» នៅក្នុងឯកសារយោងនេះ សំដៅលើក្រុមមួយក្នុងចំណោមក្រុមដែលមាននៅក្នុងមគ្គុទ្ទេសក៍នោះ — មិនមែនជាប្រភេទព័ត៌មានសម្ងាត់បន្ថែមដែលមិនបានកំណត់នោះទេ

> **ការផ្លាស់ប្តូរដែលមិនត្រូវគ្នានឹងកំណែមុន (v3.8.0)** — `/api/v1/agents/tasks/*` និង endpoint សម្រាប់ការគ្រប់គ្រង cooldown ឥឡូវនេះតម្រូវឱ្យមាន **ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណសម្រាប់ការគ្រប់គ្រង** (cookie `auth_token` របស់ dashboard ឬ API key ដែលមានវិសាលភាពគ្រប់គ្រង)។ Client ដែលពីមុនបានហៅ route ទាំងនេះដោយគ្មានការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ នឹងទទួលបាន `401 Unauthorized`។ សូមមើល commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`)។
