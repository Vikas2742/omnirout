## Chat yakunlashlari

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

#### Har bir soʻrov uchun hisobni biriktirish

Provayderda bir nechta ulanish (hisob yoki kalit) mavjud boʻlsa, OmniRoute odatda
hisob tanlash strategiyasi orqali ulardan birini tanlaydi. Buning oʻrniga soʻrov
`x-omniroute-connection` sarlavhasi yordamida muayyan ulanishni biriktirishi mumkin:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **Identifikatorni qayerdan topish mumkin.** Boshqaruv panelida provayder sahifasini oching
  (**Boshqaruv paneli → Provayderlar → <provider>**) va ulanish qatoridagi `xxxxxxxx…`
  identifikator belgisini bosing — bu toʻliq ulanish identifikatorini nusxalaydi.
- **Qaysi soʻrovlar uni hisobga oladi.** `/v1/chat/completions`, `/v1/messages` va
  `/v1/responses` manzillaridagi bitta modelli soʻrovlar (`provider/model`). Kombinatsiyalar
  sarlavhani eʼtiborsiz qoldiradi: buning oʻrniga har bir kombinatsiya bosqichi uchun hisobni
  shu bosqichning oʻz ulanishi orqali biriktiring.
- **Biriktirish qatʼiy, afzallik emas.** Faqat biriktirilgan ulanishdan foydalaniladi.
  Soʻrov ichidagi nosozlik hisobning kutish davrini qayd etadi, ammo ayni provayderning
  boshqa hisobiga **oʻtmaydi**.
- **Kutish davri va kvota biriktirishni bekor qiladi.** Biriktirilgan ulanish kutish davrida,
  kvotasi tugagan yoki kvota siyosati tomonidan bloklangan boʻlsa, keyingi soʻrovlar xuddi
  biriktirilmagan trafik kabi provayderning boshqa ulanishlariga oʻtadi.
- **Nomaʼlum yoki oʻchirilgan identifikatorlar xatoga olib keladi.** Provayderning faol
  pulida boʻlmagan identifikator (oʻchirilgan, faolsizlantirilgan yoki boshqa provayderga
  tegishli) mos hisob qoldirmaydi, shuning uchun soʻrov boshqa yoʻnalishga yashirincha
  yoʻnaltirilish oʻrniga xato bilan yakunlanadi.

Claude Code maxsus sarlavhalarni `ANTHROPIC_CUSTOM_HEADERS` orqali yuboradi. Uni
`~/.claude/settings.json` faylidagi `env` blokiga yoki har bir loyiha uchun boshqa hisobni
biriktirish maqsadida loyiha darajasidagi `.claude/settings.json` fayliga joylashtiring:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

Manba: `src/sse/handlers/chat.ts` (sarlavhani oʻqish), `src/sse/services/auth.ts` va
`src/sse/services/sessionAffinityPin.ts` (biriktirishni bekor qilish va pulda mavjud emasligini tekshirish).

> **Xarajat telemetriyasi sarlavhalari:** oqimsiz muvaffaqiyatli javoblar `X-OmniRoute-*` xarajat telemetriyasi toʻplamini ham oʻz ichiga oladi — `X-OmniRoute-Response-Cost` (USD, verguldan keyin qatʼiy 10 ta raqam; bepul/narxlanmagan holat uchun `0.0000000000`), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` va `X-OmniRoute-Fallback-Attempts` (faqat > 0 boʻlganda), shuningdek `X-OmniRoute-Request-Id` hamda `X-OmniRoute-Version`. Ular chat yakunlash soʻrovlari, `/v1/responses`, `/v1/messages` va **media soʻnggi nuqtalari** — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` hamda `/v1/moderations` (xarajat doimo `0`) tomonidan chiqariladi. Narxlar mavjud boʻlganda media xarajati modal tur boʻyicha (har bir rasm, soniya, belgi yoki qidiruv birligi uchun) hisoblanadi, aks holda `0` boʻladi (ochiq ishlash rejimi).

> **Keshga mos kelish xarajati semantikasi:** semantik keshda MOSLIK topilganda (`X-OmniRoute-Cache-Hit: true`) yuqori oqimga murojaat qilinmaydi, shu sababli `X-OmniRoute-Response-Cost` qiymati `0.0000000000` boʻladi (moslik natijasini taqdim etishning **qoʻshimcha** xarajati). Dastlabki/yuzaga kelishi mumkin boʻlgan xarajat `X-OmniRoute-Cost-Saved` da alohida koʻrsatiladi. Hisob-kitob tizimlari `X-OmniRoute-Response-Cost` qiymatlarini jamlashi kerak (keshdagi mosliklar xarajatsiz); kesh tahlili esa `X-OmniRoute-Cost-Saved` qiymatlarini jamlashi mumkin.

## Eksklyuziv boshqariladigan seans ijaralari

Eksklyuziv boshqariladigan seans ijarasi — ixtiyoriy, mijozga bogʻliq boʻlmagan marshrutlash shartnomasi: bitta faol egasi bitta mos OmniRoute ulanishini egallaydi. U modelni ijaraga bermaydi, OAuth talab qilmaydi, muayyan mijozni aniqlamaydi yoki muayyan provayderni talab qilmaydi.

Autentifikatsiya qiluvchi API kaliti `lease:exclusive` doirasiga va aniq ko‘rsatilgan bo‘sh bo‘lmagan `allowedConnections` ro‘yxatiga ega bo‘lishi kerak. Ma’lumotlar bazasidagi o‘zgartirish chegarasi kalit yaratish va qisman yangilash vaqtida ikkala maydonning birgalikda mavjud bo‘lishini ta’minlaydi.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

Muvaffaqiyatli egallash, yangilash va bo‘shatish javoblari vaqt belgilarini, `state` va aniq musbat `generation` qiymatini ko‘rsatadi, ammo tanlangan ulanish yoki hisob ma’lumotlarini hech qachon oshkor qilmaydi. Yangilash va bo‘shatish amallari generatsiyani JSON tanasida uzatadi:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

Faol ijara egasi joriy bog‘lanishi uchun maxfiylikni saqlovchi ko‘rsatish metama’lumotlarini aniq so‘rashi mumkin:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

Bu ixtiyoriy holat amali bitta ma’lumotlar bazasi tranzaksiyasida noaniq egasi, autentifikatsiya qilingan boshqariladigan API kaliti va aniq faol generatsiya bilan himoyalanadi. `displayName` faqat probellari olib tashlangan sozlangan ulanish nomidir; xavfsiz sozlangan nom mavjud bo‘lmasa, u `null` bo‘ladi. OmniRoute hech qachon uning o‘rniga e-pochta manzili yoki yaratilgan hisob identifikatorini qo‘ymaydi. Provayder qiymati maxfiy bo‘lmagan ko‘rsatish yorlig‘i bo‘lib, hech qachon yaratilgan mos provayder identifikatori bo‘lmaydi. Hisob ma’lumotlari, tokenlar, cookie fayllari, ulanish yoki API kalitlarining xom identifikatorlari, egasi xeshlari, himoyalash sirlari va ichki marshrutlash ma’lumotlari chiqarib tashlanadi.

Noto‘g‘ri kalit, noto‘g‘ri egasi, eskirgan generatsiya, mavjud bo‘lmagan, muddati tugagan, bo‘shatilgan va bekor qilingan qidiruvlarning barchasi ulanish metama’lumotlarisiz bir xil `409 LEASE_FENCE_STALE` xatosini qaytaradi. Sig‘imni kutish javobini olgan mijozda tekshirish uchun faol bog‘lanish mavjud bo‘lmaydi. Marshrutlash faol ijarani boshqa ulanishga o‘tkazganda, ayni generatsiya haqiqiyligicha qoladi va holat eski bog‘lanishni emas, yangi bog‘lanishni atomar tarzda qaytaradi. Mavjud mijozlar o‘zgarishsiz qoladi, chunki egallash, yangilash, bo‘shatish va kutish javoblari avvalgi shakllarini saqlab qoladi.

Ushbu server shartnomasi standart OpenAI Codex `/status` holatini o‘zgartirmaydi. Standart Codex hozirda o‘zining model provayderi va ichki autentifikatsiya/hisob holatini bildiradi, ammo ixtiyoriy maxsus provayder hisob metama’lumotlarini ko‘rsatmaydi; keyingi mijoz integratsiyasi ushbu amalni chaqirishi va `connection.displayName` qanday ko‘rsatilishini hal qilishi kerak.

Shundan so‘ng har bir boshqariladigan inferensiya so‘rovi ikkala boshqaruv sarlavhasini ham uzatadi:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

Aniq egasi, generatsiya, faol ulanish va autentifikatsiya qilingan API kaliti har bir qo‘llab-quvvatlanadigan yuqori oqim urinishidan darhol oldin himoyalanadi. Egasi va generatsiyani boshqa kalit bilan qayta ishlatish, hatto o‘sha kalit ayni ulanishga ruxsat bersa ham, muvaffaqiyatsiz tugaydi. Egalar haqidagi xom ma’lumotlar saqlanmaydi, jurnalga yozilmaydi, so‘rov suratida qoldirilmaydi yoki yuqori oqimga uzatilmaydi.

Vaqtinchalik raqobat HTTP `429`, `Retry-After` va quyidagini qaytaradi:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

Bu javob faqat odatiy mos to‘plam bo‘sh bo‘lmaganini va har bir bo‘sh nomzod begona faol ijara tomonidan egallanganini anglatadi. Qo‘llab-quvvatlanmaydigan modellar/provayderlar, siyosat nomuvofiqligi, sovish davri, kvota, salomatlik va boshqa odatiy muvofiqlik xatolari mavjud OmniRoute javoblarini saqlab qoladi.

### `x-omniroute-compression`

Har bir so‘rov uchun siqish rejasini qayta belgilash. Eng yuqori ustuvorlikka ega — marshrutlash kombinatsiyasi qayta belgilashidan, faol profildan, avtomatik ishga tushirishdan va paneldagi standart sozlamadan ustun turadi. Qiymatlar:

| Qiymat        | Ta’siri                                                                                                                |
| ------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `off`         | Ushbu so‘rov uchun siqish yo‘q.                                                                                        |
| `default`     | Paneldan olingan standart profil (faol profilni e’tiborsiz qoldiradi). Yo‘qotishli mexanizmlar o‘chiriladi.            |
| `safe`        | Faqat takrorlarni olib tashlash va bo‘shliqlarni ixchamlash.                                                           |
| `allow-lossy` | Ushbu so‘rov uchun operator rejasini, jumladan, xulosalar va uslubiy qayta yozishlarni saqlaydi.                       |
| `engine:<id>` | Yoqilganida bitta mexanizm, masalan, `engine:rtk`. O‘sha mexanizm uchun har bir so‘rovda ixtiyoriy yoqish.             |
| `<combo>`     | Avval nomi (katta-kichik harflarni farqlamasdan), so‘ng identifikatori bo‘yicha moslashtiriladigan nomli kombinatsiya. |

Eslatmalar:

- Noma’lum qiymatlar e’tiborsiz qoldiriladi (so‘rov hech qachon rad etilmaydi); aniqlash odatiy operator ustuvorligiga o‘tadi.
- Agar bir nechta kombinatsiya bir xil nomga ega bo‘lsa, deterministik moslik uchun kombinatsiya **id** qiymatini uzating.
- Nomi `off` yoki `default` bo‘lgan kombinatsiyani nomi orqali tanlab bo‘lmaydi (bu kalit so‘zlar avval talqin qilinadi); bunday kombinatsiyaga uning identifikatori orqali murojaat qiling.
- Asosiy siqish kaliti qat’iy cheklovdir: siqish global miqyosda o‘chirilganida, bu sarlavha uni yoqa olmaydi.

Qo‘llangan reja javob sarlavhasida qaytariladi:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

bu yerda `<source>` quyidagilardan biri: `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` yoki `off`.

## Embeddinglar

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

Mavjud provayderlar: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

Katalog identifikatorlari `provider/model` formatida (masalan: `jina-ai/jina-embeddings-v5-omni-small`). Reyestrda mavjud bo‘lgan qisqa Jina model identifikatorlari (masalan, `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) ham aniqlanadi. Jina embed/rerank/classify/segment avval boshqaruv panelidagi `jina-ai` hisob ma’lumotlaridan foydalanadi; `JINA_AI_API_KEY` faqat boshqaruv paneli kaliti mavjud bo‘lmaganda zaxira sifatida ishlatiladi. `jina-reader` kartasi faqat Reader / `r.jina.ai` uchun (`POST /v1/web/fetch`) mo‘ljallangan va hech qachon embedding yoki rerank xizmatini ko‘rsatmaydi.

Multimodal qo‘llab-quvvatlashni e’lon qilgan reyestr modellari provayderga bog‘liq bo‘lmagan 32 tagacha tuzilmali
elementni ham qabul qiladi. Media element turlari: `text`, `image`, `audio`, `video` va `document`. Ularning media `source`
qiymati `{"type":"url","url":"https://..."}` yoki
`{"type":"base64","data":"...","media_type":"..."}` bo‘ladi.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
va oilaviy taxallus `jina-ai/jina-embeddings-v5-omni` → omni-small) Jina’ning mahalliy
EmbeddingsV5Request hujjatlarini ham qabul qiladi va **ularni o‘zgartirmasdan yo‘naltiradi**: `https://api.jina.ai/v1/embeddings`

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

Mahalliy `{ image | audio | video | pdf }` qiymatlari ommaviy HTTPS URL, `data:` URI yoki xom
base64 bo‘lishi mumkin. OmniRoute bu obyektlarni satrga aylantirmaydi yoki mahalliy tasvir URL manzillarini yuklab olmaydi — Jina
ommaviy mediani o‘zi yuklab oladi. Qo‘shimcha Jina maydonlari (`task`, `normalized`, `truncate`, `embedding_type`)
yo‘naltiriladi. Faqat matnli Jina SKU’lari matn bo‘lmagan hujjatlarni hamon rad etadi.

Xavfsizlik va uzatish cheklovlari:

- Masofaviy media URL manzillari ommaviy HTTPS bo‘lishi kerak. Kanonik `{type,source:url}` elementlari
  server tomonida yuklab olinadi (qayta yo‘naltirishlarni qayta tekshirish, vaqt cheklovi, hajm cheklovlari, ommaviy DNS, ulanishni mahkamlash) va
  provayder chaqiruvidan oldin ichki ko‘rinishda joylanadi. Jina’ga xos `{image:"https://..."}` elementlari xuddi shu ommaviy HTTPS tekshiruvidan
  o‘tgach, o‘zgartirilmasdan yo‘naltiriladi; URL manzilini Jina yuklab oladi.
- Ichki base64 media hajmi har bir element uchun dekodlanganda 8 MiB va butun so‘rov bo‘yicha dekodlanganda 16 MiB bilan cheklangan.

Provayder uchun o‘zgartirish (kanonik elementlar hech qachon o‘zgartirilmasdan yo‘naltirilmaydi):

- Jina multimodal modellari: har bir yuqori darajadagi element bitta modal kalitli obyektga
  (`text` / `image` / `audio` / `video` / `pdf`) aylanadi; ichki media uchun data URI’lardan foydalaniladi; har bir
  yuqori darajadagi element uchun bitta vektor.
- Gemini Embedding 2 oilasi: bitta yuqori darajadagi massiv `content.parts` (`text` yoki `inline_data`) bilan yagona mahalliy
  `models/{model}:embedContent` so‘roviga aylanadi.
- llama.cpp (`llama-cpp/<model>`, mahalliy server yuklagan istalgan model): kanonik `text` elementlari
  oddiy satrlarga, `image` / `audio` / `video` elementlari esa har biri bitta
  `{"content": [part]}` obyektiga aylanadi; bunda llama-server’ning ichki ma’lumotli chat kontent qismlaridan (`image_url`,
  `input_audio` va `wav` / `mp3` / `flac` formati, `input_video`) foydalaniladi; har bir yuqori darajadagi
  element uchun bitta vektor. Server `--embedding --mmproj …` bilan ishlashi kerak; proyektorsiz u
  mediani o‘zi rad etadi. `document` qo‘llab-quvvatlanmaydi.
- Aniq modal metama’lumotlarsiz noma’lum/dinamik modellar tuzilmali kiritishni HTTP 400 bilan rad etadi.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

Qo‘llab-quvvatlanmaydigan model/modal kombinatsiyalari elementni majburan moslashtirish o‘rniga HTTP 400 qaytaradi. Eski satr/token so‘rovlaridagi
kiritishga aloqador bo‘lmagan kengaytma maydonlari o‘zgartirilmasdan uzatilishda davom etadi.

```bash
# Barcha embedding modellarini ro‘yxatlash
GET /v1/embeddings
```

## Tasvir yaratish

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

Mavjud provayderlar qatoriga OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (mahalliy), ComfyUI (mahalliy) kiradi.

`n` qiymati `data[]` ichida `n` ta tasvirni qaytaradi. Yuqori oqim API’si har bir chaqiruvda bitta tasvir qaytaradigan provayderlar
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI) uchun yuqori oqimga `n` ta alohida chaqiruv yuboriladi, bir vaqtda ko‘pi bilan 4 tasi bajariladi. O‘zgarmas
`seed` chaqiruv indeksi bo‘yicha siljitiladi (`seed`, `seed + 1`, …), shuning uchun tasvirlar bir-biridan farq qiladi, ammo
qayta hosil qilinishi mumkin. `n` qiymati ko‘pi bilan 10 bo‘lishi mumkin. Agar chaqiruvlardan biri muvaffaqiyatsiz tugasa, butun so‘rov
muvaffaqiyatsiz hisoblanadi. Kengaytirib yuborish formatlari ro‘yxati
`open-sse/handlers/imageGeneration/fanOut.ts` faylidagi `SINGLE_IMAGE_FANOUT_FORMATS`da joylashgan.

ZenMux mavjud API kaliti ulanishidan qayta foydalanadi va `zenmux/` yoki `zm/` prefikslarini qabul qiladi:

- `zenmux/openai/gpt-image-2` ZenMux’ning OpenAI Images API’sidan foydalanadi. Parametrlar qatoriga `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` va `response_format` kiradi.
- `zm/meta/muse-image-1.0` kabi boshqa nashriyotchilar ZenMux’ning Vertex AI `:predict`
  endpointidan foydalanadi. `n` qiymati `sampleCount`ga, `aspect_ratio` qiymati `aspectRatio`ga va `image_size`
  (`1K`, `2K`, `4K`) qiymati `sampleImageSize`ga moslanadi. Piksellardagi `size` faqat tomonlar nisbatini belgilaydi,
  aniq piksel o‘lchamlari kafolatlanmaydi. Qo‘llab-quvvatlanadigan nisbatlar, aniqliklar va miqdorlar modelga qarab farq qiladi.
- `zm/inclusionai/ming-image-0.1-design` o‘z o‘lchamlarini o‘zi tanlaydi. `size`,
  `aspect_ratio` va `image_size`ni ko‘rsatmang; aniq qiymatlar HTTP 400 javobini qaytaradi. PNG, JPEG va WebP
  formatlarini `output_format` orqali so‘rash mumkin.

Ushbu integratsiya matndan tasvir yaratishni qo‘llab-quvvatlaydi, namunaviy tasvirni tahrirlashni emas. Vertex
natijasi `data[].b64_json` ko‘rinishiga me’yorlashtiriladi; `response_format: "url"` yuqori oqimdagi
HTTPS URL’ni yoki faqat tasvir baytlari mavjud bo‘lsa, base64 ma’lumot URL’ini qaytaradi. Bo‘sh yoki filtrlangan natijalar
bo‘sh muvaffaqiyatli javob o‘rniga xatoni qaytaradi. Modellardan foydalanish imkoniyati ZenMux hisobiga bog‘liq.
[ZenMux’ning Vertex API’si](https://docs.zenmux.ai/api/vertexai/generate-images) va
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image) hujjatlariga qarang.

```bash
# Barcha tasvir modellarini ro‘yxatlash
GET /v1/images/generations
```

## Hujjat OCR’i

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
```

`model` OCR provayderini `provider/model` prefiksi orqali tanlaydi; prefikssiz model identifikatori (masalan,

Mistral (`mistral-ocr-latest`) ishlatiladi. Ro‘yxatdan o‘tgan provayderlar (`open-sse/config/ocrRegistry.ts`):

| Provayder identifikatori      | Model identifikatori | `model` qiymati                                                     | Izohlar                                                                                                                |
| ----------------------------- | -------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (yoki prefikssiz `mistral-ocr-latest`) | Sinxron — javob yuqori oqimdagi yagona chaqiruvdan bevosita qaytariladi.                                               |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                         | Asinxron yuqori oqim (`analyze` + so‘rovnoma) — quyiga qarang.                                                         |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                             | Sinxron, Vertex AI’ning `openapi/chat/completions` hamkor endpointi orqali — autentifikatsiya/URL uchun quyiga qarang. |

Uchala provayder ham bir xil Mistral shaklidagi tanada javob qaytaradi:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence so‘rovnoma jarayoni

Azure Document Intelligence’ning `analyze` API’si asinxron: dastlabki so‘rov tana o‘rniga
`Operation-Location` sarlavhasini qaytaradi va natijani so‘rovnoma orqali tekshirib turish kerak. Ishlov beruvchi
(`open-sse/handlers/ocr.ts`) ushbu URL’ni har soniyada, ko‘pi bilan 30 marta tekshiradi; `ok` bo‘lmagan so‘rovnoma javobi yoki `"failed"` holatida darhol xato bilan yakunlanadi
(tekshirishni davom ettirmaydi) va urinishlar limiti tugaganidan keyin operatsiya hali ham bajarilayotgan bo‘lsa,
`504` qaytaradi. Yakuniy Azure javobi chaqiruvchiga qaytarilishidan oldin Mistral ishlatadigan ayni
`pages`/`markdown` shakliga me’yorlashtiriladi, shuning uchun mijoz kodi provayder uchun alohida ishlov berishi shart emas.

### Vertex AI DeepSeek OCR autentifikatsiyasi va endpointni aniqlash

`vertex-deepseek-ocr` OmniRoute chat/tasvir trafigi uchun allaqachon qo‘llab-quvvatlaydigan ayni Vertex AI autentifikatsiyasidan
(`open-sse/executors/vertex.ts`) qayta foydalanadi: ulanishning API kaliti yoki Service Account JSON hisob ma’lumoti
(JWT-bearer jarayoni orqali qisqa muddatli OAuth kirish tokeniga almashtiriladi), yoki o‘z holicha ishlatiladigan
oldindan yaratilgan OAuth kirish tokenidir. Yuqori oqim endpoint URL’i ulanishning loyiha va
hudud ma’lumotlaridan tuziladigan Vertex’ning umumiy `openapi/chat/completions` hamkor endpointidir — aniq ko‘rsatilgan `providerSpecificData.project`/`providerSpecificData.region` har doim ustun turadi;
aks holda loyiha Service Account JSON’dagi `project_id`dan olinadi va hududning birlamchi qiymati
`us-central1` bo‘ladi. Har ikkala qiymat ham `open-sse/handlers/ocr.ts` ichida
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) aniqlanadi va `handleOcr`ga yuborilishidan oldin
`src/app/api/v1/ocr/route.ts` tomonidan ishlatiladi.

### Model id prefikslari (`?prefix=`)

Aksariyat modellar **provayder prefiksi** ostida taqdim etiladi. Qaysi prefiksni olishingiz
`MODELS_CATALOG_PREFIX_MODE` funksiya bayrogʻi orqali boshqariladi va soʻrov parametri yordamida
**har bir soʻrov uchun** alohida o‘zgartirilishi mumkin — bu server miqyosidagi sozlamani boshqalar
uchun oʻzgartirmasdan toza roʻyxat olishni istaydigan mijoz uchun foydali:

```bash
GET /v1/models?prefix=alias        # har bir model uchun bitta id — qisqa taxallus prefiksi
GET /v1/models?prefix=dual         # ikkala shakl (server standarti)
GET /v1/models?prefix=canonical    # faqat toʻliq provayder-id prefiksi
```

| Rejim       | Chiqaradi                                                | Izohlar                                                                                                                                                                                                                        |
| ----------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `dual`      | `cc/claude-sonnet-4-6` **va** `claude/claude-sonnet-4-6` | **Standart.** Har ikkala id bir xil modelga yoʻnaltiriladi; shakllardan birini qatʼiy belgilab qoʻygan mijoz konfiguratsiyalari ishlashda davom etishi uchun saqlangan. Katalog hajmini taxminan ikki baravar oshiradi.        |
| `alias`     | `cc/claude-sonnet-4-6`                                   | Har bir model uchun bitta yozuv. Alohida taxallusi boʻlmagan provayderlar ham oʻz yozuvini chiqaradi, shuning uchun hech narsa yoʻqolmaydi.                                                                                    |
| `canonical` | `claude/claude-sonnet-4-6`                               | Toʻliq provayder-id prefiksi ostida har bir model uchun bitta yozuv. Alohida taxallusi boʻlmagan provayderlar (masalan, `antigravity/…`, `agy/…`) ham bu yerda yagona id sini chiqaradi, shuning uchun hech narsa yoʻqolmaydi. |

`dual` rejimidagi nusxani soʻrov parametrisiz ham aniqlash mumkin: unda asosiy id ga ishora qiluvchi `parent`
maydoni mavjud.

Model tanlash interfeysini koʻrsatadigan mijozlar `?prefix=alias` soʻrashlari kerak —
[OmniCopilot VS Code kengaytmasi](../guides/VSCODE-COPILOT.md) aynan shunday qiladi.

### Topish filtrlari (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` ixtiyoriy topish filtrlarini qabul qiladi. Ulardan hech biri boʻlmasa, javob
oʻzgarmaydi. Ular chaqiruvchi allaqachon koʻra oladigan katalogni toraytiradi (avval API kaliti ruxsatlari
qoʻllanadi) va OpenAI uslubidagi `limit` / `after` sahifalashidan oldin ishga tushadi:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # roʻyxatdagi har bir imkoniyat rost boʻlishi kerak
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # katalog `type`; bunday qiymati boʻlmagan qatorlar `chat` hisoblanadi
GET /v1/models?q=sonnet&limit=10                           # id yoki nom boʻyicha katta-kichik harfga bogʻliq boʻlmagan moslik
```

| Parametr      | Qiymatlar                                                                                           |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | manfiy boʻlmagan butun son, `context_length` bilan taqqoslanadi                                     |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 ta belgi                                                                                      |

Nomaʼlum qiymat yoki manfiy boʻlmagan butun son hisoblanmaydigan `min_context` (masalan, `1.5`)
HTTP `400` qaytaradi va xabarda yaroqli qiymatlar keltiriladi. Amalga oshirilishi:
`src/app/api/v1/models/catalogFilters.ts`.

### Modellarning qisqa roʻyxati (`POST /v1/models/query`)

`POST /v1/models/query` ayni katalogdan autentifikatsiya va har bir kalit uchun koʻrinish qoidalari
`GET /v1/models` bilan bir xil boʻlgan qisqa, deterministik roʻyxatni qaytaradi:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

Har bir maydon ixtiyoriy. `capabilities` va `exclude` massiv yoki vergul bilan ajratilgan satrni qabul qiladi;
`max_output` `max_output_tokens` bilan taqqoslanadi. Natijalar avval `owned_by`, keyin `id` boʻyicha saralanadi.
`limit` standart boʻyicha `20`, `100` dan katta qiymatlar esa `100` bilan cheklanadi. Yaroqsiz JSON, nomaʼlum
maydon yoki yaroqsiz qiymat HTTP `400` qaytaradi.

### Alohida yashirilgan chat modellari

Provayder sahifasida **Yashirin** deb belgilangan model katalogdan chiqarib tashlanadi va aniq
soʻralganda HTTP `404` / `model_not_found` bilan rad etiladi. Tekshiruv aniqlangan provayder va modeldan,
jumladan provayder taxalluslari, mos provayder tuguni prefikslari va ulanishning standart qiymatlaridan
foydalanadi. Kombinatsiya yashirin nishonlarni oʻtkazib yuboradi va koʻrinadigan muqobildan foydalanishi mumkin;
bajariladigan nishon qolmasa, u ayni xato kodini qaytaradi. Yashirishni bekor qilish keyingi soʻrovdan kuchga
kiradi. Faqat tasvirga oid koʻrinish istisnolari ayni ID ga ega chat modelini yashirmaydi.

Ushbu alohida model sozlamasi katalogda koʻrsatiladigan modellar va avtomatik yoʻnaltirish nomzodlarini
filtrlab, aniq joʻnatishni saqlab qoladigan
[modelni taqdim etish ruxsat/taqiq roʻyxatlaridan](../routing/MODEL_EXPOSURE_LIST.md) alohida.
API kalitining model ruxsatlari mustaqil ravishda qoʻllanishda davom etadi. Katalog prefiksining standart rejimi `dual` boʻlib qoladi.

### Fikrlashsiz model variantlari

Fikrlash imkoniyatiga ega Claude modellari uchun `/v1/models` id si `claude-3-omniroute-no-thinking/` prefiksi bilan boshlanadigan **fikrlashsiz** variantni ham taqdim etadi:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

Ushbu IDni tanlash (masalan, har doim `thinking` blokini biriktiradigan Claude Code konfiguratsiyasida) mulohaza yuritish o‘chirilgan holda haqiqiy `<provider>/<model>`ga qayta yo‘naltiradi — `/v1/messages` yo‘lida `thinking:{type:"disabled"}` qo‘llanadi yoki `/v1/chat/completions` yo‘lida `reasoning`/`reasoning_effort` maydonlari olib tashlanadi. Variant faqat fikrlashni qo‘llab-quvvatlaydigan **va** `disabled` qiymatiga amal qiladigan Claude oilasidagi modellar uchun ko‘rsatiladi (shuning uchun, masalan, `disabled` qiymatini rad etadigan faqat adaptiv rejimdagi modellar bundan mustasno). Operatorlar `ModelSpec.noThinkingAlias` orqali har bir model uchun bu variantni majburan yoqishi yoki o‘chirishi mumkin.

## ElevenLabs orqali audio yaratish

OmniRoute ichida ElevenLabs API kalitingiz bilan `elevenlabs` provayder ulanishini sozlang.
Mijozlar oʻzlarining **OmniRoute** kaliti (`Authorization: Bearer $OMNIROUTE_API_KEY`) bilan autentifikatsiyadan oʻtadi;
shlyuz saqlangan provayder kalitini `xi-api-key` sifatida yuboradi. ElevenLabs kalitini hech qachon
shlyuzning bearer tokeni sifatida yubormang.

| Metod | Yoʻl                        | Javob                                      | API kaliti endpoint toifasi |
| ----- | --------------------------- | ------------------------------------------ | --------------------------- |
| POST  | `/v1/sound-generation`      | Asl audio baytlari                         | `elevenlabs`                |
| POST  | `/v1/music`                 | Asl audio baytlari                         | `music`                     |
| POST  | `/v1/music/stream`          | Oqimli audio baytlari                      | `music`                     |
| POST  | `/v1/music/detailed`        | Asl multipart audio va kompozitsiya rejasi | `music`                     |
| POST  | `/v1/music/detailed/stream` | Asl SSE metamaʼlumotlari va audio qismlari | `music`                     |
| POST  | `/v1/music/plan`            | JSON kompozitsiya rejasi                   | `music`                     |

Ushbu endpointlar mavjud `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` va `/v1/speech-to-text` yoʻnalishlarini toʻldiradi. `output_format` va `enable_logging` kabi asl JSON maydonlari
hamda soʻrov parametrlari saqlanadi.
`/v1/music/detailed` javoblari oʻz multipart chegaralarini saqlab qoladi; ularni multipart sifatida tahlil qiling.
`/v1/music/detailed/stream` kompozitsiya metamaʼlumotlari va SSE hodisalaridagi
base64 audio qismlari bilan `text/event-stream` qaytaradi. Oltita yoʻnalishning barchasi CORS dastlabki soʻrovini qoʻllab-quvvatlaydi.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# Qisqa tovush effekti. Davomiyligi: 0,5 dan 30 soniyagacha.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# Musiqa davomiyligi millisekundlarda ifodalanadi: 3000 dan 600000 gacha.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

Audioni qismlarga boʻlib yetkazish uchun ayni JSON tanasi bilan `/v1/music/stream` dan foydalaning. Kompozitsiya
`prompt` yoki `composition_plan` dan aynan bittasini qabul qiladi; `/v1/music/plan` uchun `prompt`
talab qilinadi va u ixtiyoriy ravishda `source_composition_plan` ni qabul qiladi. Asl sxemalar kompozitsiya rejasi versiyalari va nozik sozlash parametrlari ElevenLabs xizmatiga yetib borishi uchun provayderning qoʻshimcha maydonlarini saqlab qoladi.

Birlashtirilgan `/v1/music/generations` endpointi `elevenlabs/music_v1`,
`elevenlabs/music_v2` va `elevenlabs/music_v2_5` ni ham qabul qiladi. Faol ElevenLabs ulanishi mavjud boʻlsa,
ushbu modellar musiqa katalogida koʻrsatiladi. Bu endpoint
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` javobini qaytaradi. Undagi `duration` maydoni
soniyalarda boʻlib, `music_length_ms` ga moslashtiriladi; aniq koʻrsatilgan `music_length_ms` ustunlikka ega.
`instrumental` maydoni `force_instrumental` ga moslashtiriladi, bunda asl maydon ustunlikka ega.
Oqimli uzatish uchun asl oqimli endpointlardan, faqat kompozitsiya rejasi asosidagi soʻrovlar uchun esa asl kompozitsiya endpointidan foydalaning.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Yuqori oqimdagi chaqiruvdan oldin endpoint, model, byudjet va ulanish cheklovlari qoʻllanadi. Asl
yoʻnalishlar yuqori oqimdagi holat kodlari va xato tanalarini oʻzgartirmasdan qaytaradi, jumladan tarif
cheklovi uchun `402` va kvota chegarasi uchun `429`. Mavjud boʻlganda `character-cost`, `song-id`, `request-id` va `retry-after`
sarlavhalari saqlanadi. Bepul kredit qoldigʻi har bir musiqa modeli, chiqish formati yoki API funksiyasidan foydalanishni kafolatlamaydi: har bir soʻrov uchun ruxsatni ElevenLabs belgilaydi.
Birlashtirilgan endpoint OmniRouteʼning meʼyorlashtirilgan xato konvertida xato holati kodlarini saqlab qoladi.

Yuqori oqim shartnomalari: [tovush effektlari](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[musiqa kompozitsiyasi](https://elevenlabs.io/docs/api-reference/music/compose) va
[oqimli musiqa tafsilotlari](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).


> **Rerank provayder tugunlari:** `POST /v1/rerank` soʻrovlari `<node-prefix>/<model>` shaklida
> manzillangan OpenAI bilan mos provayder tugunlariga (oMLX, vLLM, Infinity, shlyuz ortidagi TEI, …)
> ham yoʻnaltiriladi. Loopback tugunlaridan (`localhost`, `127.0.0.1`, `172.16.0.0/12`) har doim
> foydalanish mumkin; operator `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` roʻyxatiga kiritgan xost nomlari
> ham shunday (masalan, `http://reranker:8080/v1` kabi Docker/Compose xizmat nomi; ularga
> `HTTP(S)_PROXY` yoki ulanishga biriktirilgan proksi orqali emas, har doim bevosita murojaat
> qilinadi). Boshqa har qanday xostdagi tugunlardan — LAN qurilmasi yoki Tailscale hamkor tugunidan —
> faqat operator `RERANK_REMOTE_PROVIDER_NODES` funksiya bayrogʻini yoqsa **va** tugunning asosiy
> URL manzili provayderning chiquvchi URL siyosatidan
> (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`) oʻtsa
> foydalanish mumkin. Xotira mexanizmining rerank bosqichi ushbu yoʻnalishni loopback orqali
> chaqiradi, shu sababli ayni qoida Xotira sozlamalaridagi `rerankProviderModel` uchun ham amal qiladi.
>
> **Mahalliy server formatlari:** tugun avval `<base>/v1/rerank` manzilida, 404 holatida esa
> `<base>/rerank` manzilida (Infinity, TEI) chaqiriladi. Yuqori oqim tanasi Cohere/OpenAI
> yozilishini (`documents`, `return_documents`) ham, TEI yozilishini (`texts`, `return_text`) ham
> oʻz ichiga oladi va yuqori oqim javobi Cohere konvertiga meʼyorlashtiriladi: TEI ning oddiy
> `[{index, score, text}]` formati, yupqa shlyuzlardan keluvchi `{results: [{index, score}]}` va
> Voyage uslubidagi `{data: [...]}` formatlarining barchasi mijozga
> `{results: [{index, relevance_score, document?}]}` shaklida, ball boʻyicha saralangan va `top_n`
> bilan cheklangan holda qaytariladi.

> **Provayder tugunlarini aniqlash:** OpenAI bilan mos provayder tugunidagi modellar `GET /v1/models`
> ichida tugun prefiksi ostida koʻrinadi. Endpoint metamaʼlumotlari boʻlmagan qatorlar (mahalliy
> `/v1/models` roʻyxatlari uchun odatiy holat) tugunning `apiType` qiymatini meros qilib oladi, shu
> sababli `embeddings` tugunining modellari standart chat turiga oʻtish oʻrniga `type: "embedding"`,
> `rerank` tugunining modellari esa `type: "rerank"` boʻladi; sinxronlangan yoki qoʻlda qoʻshilgan
> qatorda aniq koʻrsatilgan `supportedEndpoints` hali ham ustunlikka ega.

### Exa va Tavily `provider_options`

Exa va Tavily provayderga xos maydonlarni nomlar fazosi bilan ajratilgan to‘plamdan o‘qiydi:
`provider_options.exa` (yoki `provider_options["exa-search"]`) va `provider_options.tavily`
(yoki `provider_options["tavily-search"]`). Faqat quyidagi kalitlar uzatiladi. Ularning har biri
`open-sse/handlers/search/providerOptionsPassthrough.ts` ichidagi o‘z Zod sxemasi bilan
tekshiriladi va turi noto‘g‘ri bo‘lgan kalit olib tashlanadi. Boshqa barcha kalitlar, jumladan
autentifikatsiya, asosiy URL, `stream` va `outputSchema` e’tiborga olinmaydi. Boshqa provayderlar
ishlatadigan yassi kalitlar (`cx`, `depth`, ...) avvalgidek ishlaydi.

| Provayder | Yuqori darajadagi maydonlar                                                                                                                                                                                                                                                                                                                                               | Ichki maydonlar                                                                                                                                                           |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa       | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (yassi sodda qiymatlar), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                        | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` standart `{ text: true, highlights: true }` ustiga birlashtiriladi |
| Tavily    | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                         |

Umumiy maydonlar doimo ustun keladi: `query`, `max_results`, `filters` (domenlar), `country` va
`search_type` asosida aniqlanadigan mavzu. Exa’da `search_type: "news"` ishlatilganda
`category: "news"` saqlanadi. Tavily `search_type: "finance"` qiymatini ham qabul qiladi
(`topic: "finance"`).

Umumiy `time_range` endi har ikkala provayderga ham yetib boradi: Exa
`startPublishedDate` (ISO vaqt belgisi), Tavily esa `start_date` (`YYYY-MM-DD`) qiymatini oladi.
`provider_options` ichida aniq ko‘rsatilgan sana moslashtirilgan qiymatni bekor qiladi.

Exa natijalarida `provider_raw` ichida `id`, `highlight_scores`, `summary`, `subpages`,
`entities` va `extras` saqlanadi. Tavily natijalarida `images` va `favicon` saqlanadi.

Xarajatlarni hisobga olish hali ham yassi `costPerQuery` reyestridan foydalanadi. Tavily
`search_depth: "advanced"` uchun har bir chaqiruvga ko‘proq kredit hisoblaydi va bu farq
`usage.search_cost_usd` qiymatida aks etmaydi.

## Web Fetch API

Sozlangan web-fetch provayderi (Firecrawl, Jina Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract) orqali URL manzilidan kontentni ajratib oling.

Parallel Extract (`parallel-search`, Parallel Search bilan bir xil API kaliti) faqat Markdown qaytaradi — boshqa har qanday `format` `400` javobiga olib keladi — va kontent hajmini 100 000 ta belgi bilan cheklaydi. Maqsadli sahifaning oʻzini ajratib boʻlmaganda, yuqori oqimdagi xizmat bu holatni HTTP 200 javobi ichida bildiradi; OmniRoute esa buni qatʼiy belgilangan xabar bilan `422` sifatida taqdim etadi.

| Metod | Yoʻl            | Tavsif                                                                                 |
| ----- | --------------- | -------------------------------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | URL manzilini olish/qirib olish — soʻrov tanasi `v1WebFetchSchema` orqali tekshiriladi |

**Autentifikatsiya:** Bearer API kaliti (`extractApiKey` + `isValidApiKey`). Siyosat `enforceApiKeyPolicy` orqali qoʻllanadi.

**Kvotani hisobga oluvchi zaxira mexanizmi (#8297):** aniq `provider` berilmaganda, pul
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) qatʼiy
ustuvorlik tartibida (birinchisini toʻldirish tamoyili bilan) koʻrib chiqiladi — tezlik chekloviga uchragan, ammo sozlangan provayder soʻrovni darhol toʻxtatish oʻrniga oʻtkazib yuboriladi va qayta urinish mumkin boʻlgan yoki kvota bilan bogʻliq yuqori oqim xatosi
(HTTP 429 har doim; Firecrawl/Tavily/TinyFish xizmatlarining kvotaga asoslangan bepul tariflari uchun 402/403 —
Jina Reader uchun emas va oddiy notoʻgʻri 400 soʻrovi uchun hech qachon emas) soʻrov vaqtida hali sinab koʻrilmagan, hisob maʼlumotlari mavjud keyingi provayderga oʻtadi. Puldagi barcha provayderlar tugaganda, endpoint avvalgi umumiy `400` oʻrniga bitta `429` (`Retry-After` sarlavhasi bilan) qaytaradi. Aniq `provider` soʻralganda, **yashirin zaxira oʻtish mavjud emas** — tezlik chekloviga uchragan yoki ishlamayotgan aniq provayder oʻz xatosini qaytaradi (tezlik cheklangan boʻlsa `429`, aks holda yuqori oqimdagi status).

### WebSocket orqali Responses API (faqat codex)

```bash
# HTTP API bilan bir xil host:port (standart 20128); ulanishni yangilang:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (yoki: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# Birinchi freym response.create BOʻLISHI SHART:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket proksisi **faqat `codex` bilan ishlash uchun** ulangan (ChatGPT
bekendi). U API/boshqaruv paneli bilan bir xil portda `/v1/responses`,
`/responses` va `/api/v1/responses` yoʻllarini tinglaydi. Birinchi `response.create` freymida u ichki `codex-responses-ws` koʻprigi orqali autentifikatsiya qiladi va tayyorgarlik koʻradi, codex OAuth ulanishini tanlaydi hamda `wreq-js` transporti orqali `wss://chatgpt.com/backend-api/codex/responses` manziliga tunnel yaratadi. **Codex boʻlmagan modellar rad etiladi** (`codex_ws_provider_required`).
Kvota ulushiga asoslangan marshrutlash uchun `model: "qtSd/<group>/codex/<model>"` dan foydalaning. Bu
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` ichida amalga oshirilgan.

**Autentifikatsiya:** qoʻl siqish vaqtida Bearer API kaliti. Birga taqdim etiluvchi HTTP serveri (`server-ws.mjs`)
faol kirish nuqtasi boʻlishi kerak (`app/server-ws.mjs` mavjud boʻlsa, u standart holatda faol boʻladi).

#### Model identifikatori: oddiy ChatGPT identifikatoridan foydalaning (`codex/` prefiksisiz)

OpenAI **Codex CLI** `supports_websockets = true` boʻlganda model nomini mijoz tomonida tekshiradi va `codex/gpt-5.5` kabi **provayder prefiksli identifikatorlarni rad etadi** (`The 'codex/gpt-5.5' model is not supported when using Codex with a ChatGPT account`). **Oddiy** identifikatorni yuboring (masalan, `gpt-5.5`). OmniRoute koʻprigi faqat codex bilan ishlaydi, shu sababli yuqori oqimga tunnel yaratishdan oldin oddiy identifikatorni codex modeli sifatida qayta aniqlaydi (`resolveCodexWsModelInfo`) — garchi oddiy `gpt-5.5` HTTP orqali aks holda boshqa provayderga yoʻnaltirilgan boʻlsa ham.

#### OpenAI Codex CLIʼni sozlash

`~/.codex/config.toml` fayliga WebSocket qoʻllab-quvvatloviga ega maxsus provayder qoʻshib, Codex CLIʼni OmniRouteʼga yoʻnaltiring (mavjud konfiguratsiyaga tegmaslik uchun alohida `CODEX_HOME` dan foydalaning):

```toml
model = "gpt-5.5"                 # oddiy identifikator — "codex/gpt-5.5" EMAS
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # oxirida qiya chiziq boʻlmasin; WS URL avtomatik hosil qilinadi (ishlab chiqarish muhitida https/wss dan foydalaning)
wire_api = "responses"                    # 2026-yil fevralidan beri qoʻllab-quvvatlanadigan yagona qiymat
supports_websockets = true                # Responses-over-WS transportini yoqadi
env_key = "OMNIROUTE_API_KEY"             # OmniRoute API kalitini saqlaydi (Bearer)
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API kaliti (REQUIRE_API_KEY=false boʻlsa, istalgan kalit)
codex exec "Responda apenas: PONG"
```

CLI `base_url + /responses` manzilini WebSocket ulanishiga yangilaydi va OmniRoute uni tanlangan codex OAuth ulanishiga tunnellaydi. Mahalliy server bilan boshidan oxirigacha tekshirilgan: ChatGPT `codex.rate_limits` + `response.created` ni qaytaradi va natijani oqim tarzida uzatadi.

## Mustaqil foydalanish (`/api/usage/om-usage`)

Har qanday API kaliti **oʻzining** foydalanish maʼlumotlari va kvotalarini boshqaruv autentifikatsiyasisiz oʻqishi mumkin. Bu mijoz
(CLI, OmniCopilot paneli) kalit egasiga uning xarajatlarini koʻrsatish uchun foydalanadigan endpoint hisoblanadi.

```bash
# Matn shakli (tarixiy shartnoma — terminal uchun oddiy matn)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# Tuzilmali shakl — UI foydalanadigan format
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Kalitda **`allowUsageCommand`** yoqilgan boʻlishi kerak (sukut boʻyicha oʻchirilgan — boshqaruv panelidagi API kalitlari
menejeri uni har bir kalit uchun alohida yoqadi). U boʻlmasa, endpoint `403` javobini qaytaradi.

`?format=json` ajratib koʻrsatilgan tuzilmani qaytaradi, shuning uchun chaqiruvchi rad etish javobidan maʼlumot maydonini hech qachon
oʻqimaydi. Muvaffaqiyatli holatda:

```jsonc
{
  "allowed": true,
  // faqat kalit har bir kalit uchun foydalanish limitlarini (kunlik/haftalik USD) tanlaganida mavjud:
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // tanlangan provayder kvotasining oniy tasviri yoki hali hech narsa keshlanmagan boʻlsa null:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // UI bir nechta provayderni yonma-yon koʻrsatishi uchun har bir ulanishning oniy tasviri:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

Rad etilganda (`401` notoʻgʻri kalit / `403` ruxsat berilmagan) ayni marshrut
`{ "allowed": false, "error": { "message": "…" } }` javobini qaytaradi — mavjud, ammo boʻsh `personal`/`provider`
(kalitga ruxsat berilgan, ammo hali hech qanday maʼlumot olinmagan) rad etishdan farqli holatdir va ularni faqat JSON shakli
farqlaydi.

**Autentifikatsiya:** chaqiruvchining `isValidApiKey` orqali tekshiriladigan oʻz Bearer API kaliti — bu
`requireManagementAuth` bilan himoyalangan boshqaruv interfeysi (`/api/keys/…`) _emas_.

### Xom va chegara boʻyicha tuzatilgan kvota foizlari

`/api/usage/om-usage` dan foydalanishda chaqiruvchilar **oddiy matnli chiqish** va tuzilmali
**JSON chiqishi** taqdim etadigan foizlar oʻrtasidagi farqni hisobga olishlari kerak:

| Jihat                    | Oddiy matn formati (`/api/usage/om-usage` / `@@om-usage`)                                                     | JSON formati (`?format=json`)                                                                |
| :----------------------- | :------------------------------------------------------------------------------------------------------------ | :------------------------------------------------------------------------------------------- |
| **Chiqish maydoni**      | `NN% left` (masalan, `20% left`)                                                                              | `provider.quotas` / `providers[].quotas`                                                     |
| **Oʻlchov**              | **Chegara boʻyicha tuzatilgan foydalanish mumkin boʻlgan limit**: chegara qiymatidan yuqoridagi qolgan sigʻim | **Yuqori oqimning xom kvotasi**: provayderning tuzatilmagan oʻlchovi                         |
| **Chegara miqyosi**      | Himoyalangan zaxira `0% left` sifatida koʻrinishi uchun `effectiveRemainingPercent()` orqali masshtablanadi   | Yoʻq (provayder xabar bergan xom oniy tasvir qiymatlari)                                     |
| **Chegara maʼlumotlari** | Koʻrsatiladigan foizga kiritilgan                                                                             | Har bir ulanish uchun `quotaWindowThresholds` ichida saqlanadi (yoki server standartlari)    |
| **Asosiy isteʼmolchi**   | Interaktiv CLI’lar, terminal soʻrovlari, inson operatorlari                                                   | Dasturiy integratsiyalar, boshqaruv panellari, tahlil vositalari, hisob-kitob kuzatuvchilari |

#### Chegarani tuzatish formulasi

OmniRoute yuqori oqim resurslarining tugashini oldini olish uchun proaktiv kvota chegaralarini qoʻllab-quvvatlaydi (ulanishning
`quotaWindowThresholds`, provayder standartlari yoki global bardoshlilik sozlamalari orqali konfiguratsiya qilinadi). Kvota oynasida chegara qiymati
(masalan, `cutoff = 25%`) faol boʻlsa, matn rendereri qolgan limitni quyidagicha hisoblaydi:

- Agar `remaining <= cutoff` boʻlsa: `0%` qaytaradi.
- Agar `remaining > cutoff` boʻlsa: `((remaining - cutoff) / (100 - cutoff)) * 100` qaytaradi.

Formatlangan matn chiqishi bu qiymatni eng yaqin butun songa yaxlitlaydi (`Math.round(...)`).

#### Koʻrgazmali misol

**60% xom foydalanish** (demak, **40% xom qolgan kvota**) va konfiguratsiya qilingan
**25% qolgan kvota chegarasi** mavjud provayder oynasini koʻrib chiqamiz:

| Koʻrinish                     | Hisoblash                                          | Qolgan  |      Nazarda tutilgan foydalanish      |
| :---------------------------- | :------------------------------------------------- | :-----: | :------------------------------------: |
| **Xom JSON (`?format=json`)** | Yuqori oqim oniy tasviri (`quotas[window]`)        | **40%** |                **60%**                 |
| **Matn formati (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (`100 - remaining` hisoblansa) |

- **Nega matn 20% qolganini koʻrsatadi:** Hisobda qolgan 40% jismoniy kvotaning 25%i
  chegara siyosati tomonidan zaxiralangan. Router ushbu ulanishga yoʻnaltirishni toʻxtatishidan oldin chaqiruvchi foydalanishi mumkin boʻlgan
  75% oraliqning faqat 15%i qolgan. Masshtablash ulanish aynan yoʻnaltirish toʻxtatilgan paytda
  resurs tugaganini (`0% left`) bildirishini taʼminlaydi.
- **Nega JSON xom qiymatlarni saqlaydi:** JSON foydali yuklamasi provayderning aniq oniy tasvirini (`UsageSnapshot`)
  qaytaradi, natijada tashqi vositalar server tomonidagi yoʻqotishli masshtablashsiz yuqori oqimdan foydalanishning haqiqiy qiymatlari va ulanish darajasidagi
  `quotaWindowThresholds` maʼlumotlariga kirish imkoniga ega boʻladi.

#### Isteʼmolchilarni migratsiya qilish boʻyicha koʻrsatmalar

Agar tashqi integratsiya (masalan, muharrir plagini yoki agent kengaytmasi) ilgari matnli
endpointdan (`NN% left`) maʼlumotlarni ajratib olgan va foydalanilgan foizni `100 - NN` sifatida hisoblagan boʻlsa, `?format=json` formatiga oʻtish quyidagilarni anglatadi:

- JSON qiymatlarini bevosita oʻqish **yuqori oqimdagi haqiqiy sarfni** aks ettiradi (yuqoridagi misolda 60% ishlatilgan).
- Agar integratsiya matnli endpointning foydalanish mumkin boʻlgan limit semantikasini saqlab qolishni istasa, ulanish darajasidagi qayta belgilashlar uchun `quotaWindowThresholds`dan foydalanib,
  amaldagi qoldiq formulasini mijoz tomonida hisoblab chiqishi mumkin.

| `/api/provider-models/validate-and-add` | POST                      | Boshqaruv autentifikatsiyasidan oʻtgan, ixtiyoriy qatʼiy ulanish tekshiruvi va maxsus modelni atomar roʻyxatdan oʻtkazish; [Modelni tekshirish](../guides/MODEL-VALIDATION.md) boʻlimiga qarang |

Sinxronlangan/import qilingan modellar uchun `PUT /api/provider-models` soʻrovi `provider`, `modelId` va
`maxOutputTokenOverride` qiymatlarini qabul qiladi: musbat butun son chiqish tokenlari uchun qoʻlda belgilangan cheklovni oʻrnatadi, `null`
esa uni tozalab, standart qiymatni tiklaydi. `GET /api/provider-models?provider=<provider>` ushbu
qiymatlarni `modelOutputOverrides` ichida, jumladan maxsus model qatori boʻlmagan modellar uchun ham qaytaradi. Qayta belgilash
ishlash vaqtidagi `max_output_tokens` imkoniyatidan foydalanadi va model qayta sinxronlanganda ham saqlanib qoladi. OpenAI bilan mos
provayder sahifasi xuddi shu tahrirlash/tozalash boshqaruvlarini taklif qiladi va tasvirlarni qoʻllab-quvvatlashi aniq koʻrsatilgan modellarni belgilaydi.

Maxsus Chat Completions tugunlari fikrlashni aniq rad etish parametrlarini yuqori oqimdagi backend tizimiga moslashtiradi.
Ulanish muvaffaqiyatli sinalganda, `/models` yozuvi tan olingan `owned_by` qiymatini tasdiqlaydigan har bir aniq model IDsi
uchun chat shabloni boshqaruvlari avtomatik tanlanadi: `vllm`, `sglang` yoki `llamacpp`.
Shaffof OpenAI bilan mos oʻrovchilar asl model yozuvini ichki
`openai` obyekti ichida saqlashi mumkin; aniqlash shunday oʻramlarning uchtagachasini kuzatadi. Egalik maʼlumoti mavjud boʻlmagan, nomaʼlum yoki
ziddiyatli boʻlgan modellar odatiy OpenAI xatti-harakatini saqlab qoladi. Aniqlash mavjud katalog soʻrovidan qayta foydalanadi,
hech qanday yakunlash tokenlarini yaratmaydi va ulanishning kirish nuqtasi oʻzgarganda bekor qilinadi.

Bunday metamaʼlumotlarni taqdim etmaydigan backend uchun xatti-harakatni qatʼiy belgilash maqsadida mavjud qisman
provayderni yangilash APIsidan foydalaning:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

Ushbu tanani `PUT /api/providers/<connection-id>` orqali yuboring. Bu ulanishda `none` qiymatiga ega aniq
fikrlash darajasi `chat_template_kwargs.thinking=false` va
`chat_template_kwargs.enable_thinking=false` sifatida yuboriladi. Server tomonidagi fikrlash qoidasi muayyan darajani majburan belgilamasa,
aniq mahalliy shablon qiymatlari ustuvor boʻlib qoladi. Sozlama faqat maxsus
OpenAI bilan mos ulanish Chat Completions tanasini yuborganda qoʻllanadi; Responses soʻrovlari va odatiy
provayderlar oʻzlarining mahalliy soʻrov shaklini saqlab qoladi. Odatiy OpenAI
`reasoning_effort` qiymatini oʻzgarishsiz uzatishni majburlash uchun `reasoningControl` qiymatini `openai` qilib belgilang yoki avtomatik aniqlashdan foydalanish uchun uni kiritmang/`null` qilib belgilang.

Claude Code avtomatik rejimi tasniflagichi soʻrovlarida aniq fikrlash boshqaruvlari mavjud boʻlmasa,
mahalliy fikrlash sukut boʻyicha oʻchiriladi. Aniqlash model nomlari yoki yakunlash cheklovlaridan emas,
Claude formatidagi soʻrovlardagi tasniflagichning tizim markeridan foydalanadi. Tana ichidagi aniq boshqaruvlar, qoʻllab-quvvatlanadigan fikrlash darajasi/fikrlash
sarlavhalari, yoʻnaltirish qoidalari va model uchun aniqlangan fikrlash darajasi oʻzining mavjud ustuvorligini saqlab qoladi. Tasniflagichning har ikkala
bosqichi oʻz promptlari, yakunlash cheklovlari, toʻxtatish ketma-ketliklari va yuqori oqimdagi haqiqiy ruxsat
hukmlarini saqlab qoladi; ikkinchi bosqich ham soʻralgan koʻrinadigan fikrlashni odatiy matn sifatida yaratishi mumkin.

### Versiya va reliz kanali

```bash
GET /api/system/version
```

Faqat loopback orqali foydalaniladigan boshqaruv marshruti (administrator autentifikatsiyasi). Ishlayotgan versiya, eng soʻnggi
eʼlon qilingan versiya va avtomatik yangilanish holatini qaytaradi. `releaseChannel` va `channels` qoʻshimcha
maydonlardir (3.8.54 reliz liniyasi); `channel` oʻz maʼnosini saqlab qoladi — boshqaruv paneli yangilagichi
foydalanadigan joylashtirish rejimi (`npm`, `source` yoki `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — ishlayotgan tuzilmaning npm kanali: `-nightly.*` versiyalari uchun `nightly`,
  boshqa dastlabki relizlar (`-rc.*`, `-beta.*`, `-alpha.*`) uchun `next`, `channels.latest` dagidan
  eskiroq asosiy versiyaning barqaror relizi uchun `lts`, boshqa hollarda esa `latest`. Eʼlon qilish vaqtida
  npm dist-tagini tanlaydigan `scripts/release/dist-tag.mjs` bilan bir xil qoidalar qoʻllanadi.
- `channels` — `npm view omniroute dist-tags` orqali olinadigan har bir dist-tagning eʼlon qilingan eng soʻnggi versiyasi (reestrning
  HTTP zaxira usuli bilan), `latest` kabi bir xil 10 daqiqalik TTL bilan keshlanadi. `latest` har doim mavjud
  (avval `latest` maydoniga, soʻng `"unavailable"` qiymatiga qaytadi); `next`, `nightly` va `lts` esa
  faqat tegishli dist-tag mavjud boʻlganda koʻrsatiladi. `Cache-Control: no-cache` soʻrovi ikkala qidiruvni ham yangilaydi.

Kanal modeli (`latest` = 4.0 GA chiqishigacha v3, `next` = rc, `nightly` = `develop` tuzilmalari,
`lts` = 4.0 GA chiqishidan keyingi v3 tuzatishlari) `docs/ops/RELEASE_STRATEGY.md` hujjatida tavsiflangan.

## Token limitlari

Har bir API kaliti uchun **token** budjetlari (yuqoridagi USD asosidagi Budjetdan alohida). Soʻrov yoʻlida bevosita qoʻllanadi: kalitning joriy davrdagi sarfi limitga yetganda, soʻrovlar `429 Too Many Requests` xatosi bilan rad etiladi. Limitlar muayyan `model`, `provider` doirasida yoki butun kalit boʻylab `global` tarzda qoʻllanishi mumkin; bir nechta limit soʻrovga mos kelsa, eng qatʼiy limit ustun keladi.

```bash
# Kalitning token limitlarini roʻyxatlash (joriy davrdagi sarfni ham oʻz ichiga oladi)
GET /api/usage/token-limits?apiKeyId=key-123

# Token limitini yaratish yoki yangilash
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# Token limitini id boʻyicha oʻchirish
DELETE /api/usage/token-limits?id=tl-abc
```

> **Sxema izohlari** (`setTokenLimitSchema`): `apiKeyId` va `scopeType` (`model` | `provider` | `global`) majburiy. `scopeType` qiymati `global` boʻlmasa, `scopeValue` majburiy (masalan, `model` doirasi uchun model identifikatori, `provider` doirasi uchun provayder identifikatori). `tokenLimit` musbat butun son boʻlishi kerak (satrdan avtomatik oʻgiriladi). Ixtiyoriy: `id` (yaratish uchun kiritmang, yangilash uchun kiriting), `resetInterval` (`daily` | `weekly` | `monthly`, standart qiymat `monthly`), `resetTime` (`HH:MM`), `enabled` (standart qiymat `true`). `GET` javoblari har bir limitni `tokensUsed`, `remaining`, `windowStart`, `periodStartAt` va `nextResetAt` bilan boyitadi. Bu boshqaruv toifasidagi endpoint hisoblanadi (autentifikatsiya markaziy authz konveyeri tomonidan taʼminlanadi).

1. Mijoz soʻrovni `/v1/*` manziliga yuboradi
2. Yoʻnalish ishlov beruvchisi `handleChat`, `handleEmbedding`, `handleAudioTranscription` yoki `handleImageGeneration` funksiyasini chaqiradi

9. Foydalanish, siqish tahlili va soʻrov jurnallari qayd etiladi
10. Xatoliklarda kombinatsiya qoidalariga muvofiq zaxira variant qoʻllanadi

## Nosozliklarga chidamlilik (kengaytirilgan)

OmniRoute vaqtinchalik nosozliklarni boshqarish uchun uchta mustaqil mexanizmni taqdim etadi; quyidagi boshqaruv endpointlari operatorlarga ularning holatini ko‘rish va qayta belgilash imkonini beradi:

| Qamrov sohasi        | Holat saqlanadigan joy                       | Ko‘rish                                   | Qayta o‘rnatish / tozalash                                  |
| -------------------- | -------------------------------------------- | ----------------------------------------- | ----------------------------------------------------------- |
| Provayder uzgichi    | `domain_circuit_breakers` + xotirada         | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                |
| Ulanish kutish davri | Provayder ulanishlaridagi `rateLimitedUntil` | `/api/rate-limits`, `/api/providers/[id]` | (kechiktirib qayta yoqiladi; provayder PUT orqali tozalang) |
| Model bloklanishi    | Xotiradagi model mavjudligi reyestri         | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                    |

`PATCH /api/resilience` provayder uzgichi uchun qayta belgilashlarni `providerBreaker.oauth` va `providerBreaker.apikey` ostida qabul qiladi. Har bir profil `degradationThreshold`, `failureThreshold` va `resetTimeoutMs` parametrlarini qo‘llab-quvvatlaydi; ayni maydonlar Boshqaruv paneli → Sozlamalar → Nosozliklarga chidamlilik bo‘limida ham mavjud.

```bash
# Bitta model bloklanishini tozalash
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Barcha bloklanishlarni o‘chirish
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

To‘liq konseptual ma’lumotnoma va uzgichning standart qiymatlari uchun qarang: [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" va [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md).

### So‘rovlar tezligi chegarasi navbati va avtomatik yoqish himoya mexanizmi

- **Qo‘llab-quvvatlanadigan yozish yo‘li**: `POST /api/rate-limits`, tanasi `{"connectionId": "<id>", "enabled": true|false}` bo‘lib, ulanish uchun so‘rovlar tezligi chegarasi himoyasini yoqish yoki o‘chirishga mo‘ljallangan boshqaruv endpointidir. `PUT /api/providers/[id]` ataylab `rateLimitProtection` qiymatini o‘zgartirmaydi yoki almashtirmaydi (#11278).
- **`enabled: false` semantikasi**: `enabled: false` o‘rnatilishi ulanish uchun aniq belgilangan himoyani olib tashlaydi, ammo faol API kalitli ulanishni global avtomatik yoqish himoya mexanizmidan (`autoEnableApiKeyProviders = true`) **chiqarmaydi**. `reconcileEnabledConnections` ichida (`open-sse/services/rateLimitManager.ts`) `false` va `undefined` teng hisoblanadi; aniq belgilangan himoyasiz faol API kalitli ulanishlar avtomatik yoqish himoya mexanizmi doirasida himoyalangan holda qoladi.
- **Global o‘chirish**: API kalitli ulanishlarni so‘rovlar tezligi chegarasi navbatlarisiz ishlatish uchun himoya mexanizmini `RATE_LIMIT_AUTO_ENABLE=false` (muhit o‘zgaruvchisi) yoki `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Sozlamalar → Nosozliklarga chidamlilik / `PATCH /api/resilience`) orqali global tarzda o‘chiring.

## A2A serveri

OmniRoute A2A (Agent-to-Agent) JSON-RPC 2.0 endpointini hamda tekshirish/boshqaruv panelida foydalanish uchun REST o‘ramini taqdim etadi.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # OMNIROUTE_API_KEY o‘rnatilmagan bo‘lsa, ixtiyoriy
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

Qo‘llab-quvvatlanadigan metodlar (barchasi `settings.a2aEnabled` orqali boshqariladi):

| Metod            | Tavsif                                                                |
| ---------------- | --------------------------------------------------------------------- |
| `message/send`   | Sinxron ko‘nikma bajarilishi; `{task, artifacts, metadata}` qaytaradi |
| `message/stream` | Xuddi shu ko‘nikmalar to‘plamini SSE orqali oqimli bajarish           |
| `tasks/get`      | Vazifani `taskId` bo‘yicha olish                                      |
| `tasks/cancel`   | Vazifani `taskId` bo‘yicha bekor qilish                               |

Ichki ko‘nikmalar: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### Agent kartasi

```bash
GET /.well-known/agent.json
```

Ommaviy A2A agent kartasini (nomi, tavsifi, imkoniyatlari, ko‘nikmalar katalogi, autentifikatsiya sxemasi) qaytaradi — ommaviy tarzda 1 soatga keshlanadi. Autentifikatsiya talab qilinmaydi.

### REST yordamchilari

| Metod | Yo‘l                         | Tavsif                                                                                                                  |
| ----- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/a2a/status`            | A2A holati + vazifalar statistikasi + keshlangan agent kartasi xulosasi                                                 |
| GET   | `/api/a2a/tasks`             | Vazifalar ro‘yxati — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST  | `/api/a2a/tasks`             | (REST yordamchisi sifatida amalga oshirilmagan — JSON-RPC `message/send` orqali yarating)                               |
| GET   | `/api/a2a/tasks/[id]`        | Bitta vazifani olish                                                                                                    |
| POST  | `/api/a2a/tasks/[id]/cancel` | Vazifani bekor qilish                                                                                                   |

**Autentifikatsiya:** REST yordamchilari boshqaruv autentifikatsiyasisiz ishlaydi (boshqaruv panelidan o‘qish mumkin); JSON-RPC `/a2a` yo‘nalishi sozlangan bo‘lsa, Bearer `OMNIROUTE_API_KEY` dan foydalanadi.

| Metod  | Yoʻl               | Tavsif                                                                              |
| ------ | ------------------ | ----------------------------------------------------------------------------------- |
| GET    | `/api/memory`      | Xotira yozuvlari roʻyxati (qamrov, tur va qidiruv soʻrovi boʻyicha filtrlash)       |
| POST   | `/api/memory`      | Yangi xotira yozuvini yaratish — soʻrov tanasi: `{scope, type, content, metadata?}` |
| GET    | `/api/memory/[id]` | Muayyan xotira yozuvini olish                                                       |
| PUT    | `/api/memory/[id]` | Xotira yozuvini yangilash                                                           |
| DELETE | `/api/memory/[id]` | Xotira yozuvini oʻchirish                                                           |
| GET    | `/api/memory?q=`   | Xotirada qidirish (FTS5 + vektor) — statistika shu javobning oʻzida taqdim etiladi  |

**Autentifikatsiya:** Boshqaruv seansi yoki boshqaruv qamroviga ega API kaliti talab qilinadi.

## Himoya cheklovlari

| Metod | Yoʻl                   | Tavsif                                                                                                                    |

Batafsil maʼlumot uchun [Xavfsizlik > Himoya cheklovlari](../security/GUARDRAILS.md) sahifasiga qarang.

## Autentifikatsiya

To‘rtta hisob ma’lumotlari oilasi (boshqaruv paneli seansi, mahalliy CLI tokeni, `oma_live_…` kirish
tokeni, boshqaruv doirasidagi API kaliti) va ularning inferensiya kalitlaridan qanday farq qilishi haqida
[Boshqaruv autentifikatsiyasi](../guides/MANAGEMENT-AUTH.md) qo‘llanmasiga qarang.

- Boshqaruv paneli yo‘nalishlari (`/dashboard/*`) `auth_token` cookie faylidan foydalanadi
- Tizimga kirishda saqlangan parol xeshi ishlatiladi; zaxira sifatida `INITIAL_PASSWORD` qo‘llanadi
- `requireLogin` parametrini `/api/settings/require-login` orqali almashtirish mumkin
- `REQUIRE_API_KEY=true` bo‘lganda, `/v1/*` yo‘nalishlari ixtiyoriy ravishda Bearer API kalitini talab qiladi
- Ushbu ma’lumotnomadagi «boshqaruv tokeni» / «boshqaruv doirasidagi API kaliti» o‘sha qo‘llanmadagi oilalardan birini anglatadi — alohida, ta’riflanmagan qo‘shimcha maxfiy ma’lumot turini emas

> **Moslikni buzuvchi o‘zgarish (v3.8.0)** — `/api/v1/agents/tasks/*` va kutish davrini boshqarish endpointlari endi **boshqaruv autentifikatsiyasini** (boshqaruv panelining `auth_token` cookie fayli yoki boshqaruv doirasidagi API kaliti) talab qiladi. Ilgari bu yo‘nalishlarni autentifikatsiyasiz chaqirgan mijozlar `401 Unauthorized` javobini oladi. `588a0333` kommitiga qarang (`fix(auth): require management auth for agent and cooldown APIs`).
