## चॅट पूर्णता

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### सानुकूल हेडर्स

| हेडर                     | दिशा     | वर्णन                                                                                                                                                                                                                                   |
| ------------------------ | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | विनंती   | कॅशे वगळण्यासाठी `true` वर सेट करा                                                                                                                                                                                                      |
| `x-omniroute-no-memory`  | विनंती   | या विनंतीसाठी मेमरी + कौशल्य अंतःक्षेप वगळण्यासाठी `true` वर सेट करा (नो-कॅशेप्रमाणेच; प्रत्येक कॉलचा टोकन/खर्च ओव्हरहेड टाळते)                                                                                                         |
| `X-OmniRoute-Progress`   | विनंती   | प्रगती इव्हेंट्ससाठी `true` वर सेट करा                                                                                                                                                                                                  |
| `X-Session-Id`           | विनंती   | बाह्य सत्र अॅफिनिटीसाठी स्टिकी सत्र की                                                                                                                                                                                                  |
| `x_session_id`           | विनंती   | अंडरस्कोर प्रकारही स्वीकारला जातो (थेट HTTP)                                                                                                                                                                                            |
| `X-OmniRoute-Session-Id` | विनंती   | कॉलरने पुरवलेला सत्र/संभाषण टॅग (मेमरीलाही पुरवला जातो). उपस्थित असल्यास, प्रत्येक सत्राच्या खर्च-वाटपासाठी `call_logs.session_tag` मध्ये जसाच्या तसा कायम केला जातो (#8249) — अनुपस्थित असल्यास कधीही कृत्रिमरीत्या तयार केला जात नाही |
| `Idempotency-Key`        | विनंती   | डीडुप्लिकेशन की (5s विंडो)                                                                                                                                                                                                              |
| `X-Request-Id`           | विनंती   | पर्यायी डीडुप्लिकेशन की                                                                                                                                                                                                                 |
| `x-omniroute-connection` | विनंती   | एका मॉडेलची विनंती त्याच्या id द्वारे एका प्रदाता कनेक्शनशी (खाते) पिन करा — [प्रत्येक विनंतीसाठी खाते पिन करणे](#account-pinning-per-request) पहा                                                                                      |
| `X-OmniRoute-Cache`      | प्रतिसाद | `HIT` किंवा `MISS` (नॉन-स्ट्रीमिंग)                                                                                                                                                                                                     |
| `X-OmniRoute-Idempotent` | प्रतिसाद | डीडुप्लिकेट केले असल्यास `true`                                                                                                                                                                                                         |
| `X-OmniRoute-Progress`   | प्रतिसाद | प्रगती ट्रॅकिंग सुरू असल्यास `enabled`                                                                                                                                                                                                  |
| `X-OmniRoute-Session-Id` | प्रतिसाद | OmniRoute ने वापरलेला प्रभावी सत्र ID                                                                                                                                                                                                   |
| `X-OmniRoute-Request-Id` | प्रतिसाद | विनंती सहसंबंध id (माहित असल्यास)                                                                                                                                                                                                       |
| `X-OmniRoute-Version`    | प्रतिसाद | OmniRoute बिल्ड आवृत्ती (नेहमी उपस्थित)                                                                                                                                                                                                 |
| `X-OmniRoute-Cost-Saved` | प्रतिसाद | HIT मुळे कॅशेने वाचवलेली USD रक्कम (केवळ कॅशे हिट्स)                                                                                                                                                                                    |
| `X-OmniRoute-Decision`   | प्रतिसाद | राउटिंग ट्रेस: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` ही कॉम्बो रणनीती असते किंवा नॉन-कॉम्बो विनंतीसाठी `single` असते) — पूर्णता प्रतिसादांमध्ये नेहमी उपस्थित                                                   |

> Nginx टीप: तुम्ही अंडरस्कोअर असलेल्या हेडर्सवर अवलंबून असल्यास (उदाहरणार्थ `x_session_id`), `underscores_in_headers on;` सक्षम करा.

#### प्रत्येक विनंतीसाठी खाते पिन करणे

एखाद्या प्रदात्याकडे अनेक कनेक्शन्स (खाती किंवा कीज) असल्यास, OmniRoute सामान्यतः त्याच्या खाते-निवड धोरणाद्वारे त्यापैकी एक निवडते. त्याऐवजी, विनंती `x-omniroute-connection` हेडर वापरून एखादे विशिष्ट कनेक्शन पिन करू शकते:

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **आयडी कुठे मिळेल.** डॅशबोर्डमध्ये प्रदाता पृष्ठ उघडा
  (**डॅशबोर्ड → प्रदाते → <प्रदाता>**) आणि कनेक्शनच्या ओळीवरील `xxxxxxxx…` आयडी चिपवर क्लिक करा
  — यामुळे संपूर्ण कनेक्शन आयडी कॉपी होतो.
- **कोणत्या विनंत्या याचा आदर करतात.** `/v1/chat/completions`, `/v1/messages` आणि
  `/v1/responses` वरील एकल-मॉडेल विनंत्या (`provider/model`). कॉम्बो हेडरकडे दुर्लक्ष करतात:
  त्याऐवजी प्रत्येक कॉम्बो पायरीसाठी त्या पायरीच्या स्वतःच्या कनेक्शनद्वारे खाते पिन करा.
- **पिन कठोर आहे, केवळ प्राधान्य नाही.** पिन केलेले कनेक्शनच केवळ वापरले जाते.
  विनंतीमधील अपयशामुळे खात्याचा कूलडाउन नोंदवला जातो, परंतु त्याच प्रदात्याच्या दुसऱ्या
  खात्याकडे **रोटेट केले जात नाही**.
- **कूलडाउन आणि कोटा पिन मुक्त करतात.** पिन केलेले कनेक्शन कूलडाउनमध्ये असताना,
  त्याचा कोटा संपलेला असताना किंवा ते कोटा धोरणामुळे ब्लॉक झालेले असताना, त्यानंतरच्या
  विनंत्या पिन न केलेल्या ट्रॅफिकप्रमाणेच प्रदात्याच्या इतर कनेक्शन्सवर फॉलबॅक करतात.
- **अज्ञात किंवा अक्षम आयडी अपयशी ठरतात.** प्रदात्याच्या सक्रिय पूलमध्ये नसलेल्या आयडीमुळे
  (हटवलेला, निष्क्रिय केलेला किंवा दुसऱ्या प्रदात्याशी संबंधित असलेला) कोणतेही पात्र खाते
  उपलब्ध राहत नाही, त्यामुळे विनंती शांतपणे इतरत्र रूट होण्याऐवजी अपयशी ठरते.

Claude Code हे `ANTHROPIC_CUSTOM_HEADERS` द्वारे कस्टम हेडर्स पाठवते. ते
`~/.claude/settings.json` मधील `env` ब्लॉकमध्ये ठेवा किंवा प्रत्येक प्रकल्पासाठी वेगळे खाते
पिन करण्यासाठी प्रकल्प-स्तरीय `.claude/settings.json` मध्ये ठेवा:

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

स्रोत: `src/sse/handlers/chat.ts` (हेडर वाचन), `src/sse/services/auth.ts` आणि
`src/sse/services/sessionAffinityPin.ts` (पिन मुक्त करणे आणि पूलमध्ये नसल्याची तपासणी).

> **खर्च टेलिमेट्री हेडर्स:** नॉन-स्ट्रीमिंग यशस्वी प्रतिसादांमध्ये `X-OmniRoute-*` खर्च-टेलिमेट्री संचही असतो — `X-OmniRoute-Response-Cost` (USD, निश्चित 10 दशांश स्थाने; विनामूल्य/किंमत नसलेल्यांसाठी `0.0000000000`), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit`, आणि `X-OmniRoute-Fallback-Attempts` (केवळ > 0 असताना), तसेच `X-OmniRoute-Request-Id` आणि `X-OmniRoute-Version`. हे चॅट कम्प्लिशन्स, `/v1/responses`, `/v1/messages`, **तसेच मीडिया एंडपॉइंट्सद्वारेही** उत्सर्जित केले जातात — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations`, आणि `/v1/moderations` (खर्च नेहमी `0`). किंमत उपलब्ध असल्यास मीडिया खर्च प्रत्येक मोडॅलिटीनुसार (प्रत्येक प्रतिमा, प्रत्येक सेकंद, प्रत्येक अक्षर, प्रत्येक शोध-युनिट) मोजला जातो; अन्यथा तो `0` (फेल-ओपन) असतो.

> **कॅश-हिट खर्चाचे अर्थशास्त्र:** सिमॅंटिक-कॅश HIT (`X-OmniRoute-Cache-Hit: true`) झाल्यावर कोणताही अपस्ट्रीम कॉल केला जात नाही, त्यामुळे `X-OmniRoute-Response-Cost` हे `0.0000000000` असते (हिट सर्व्ह करण्याचा **वाढीव** खर्च). मूळ/झाला असता असा खर्च `X-OmniRoute-Cost-Saved` मध्ये स्वतंत्रपणे नोंदवला जातो. बिलिंग वापरकर्त्यांनी `X-OmniRoute-Response-Cost` ची बेरीज करावी (हिटसाठी कोणताही खर्च नाही); कॅश विश्लेषणासाठी `X-OmniRoute-Cost-Saved` एकत्रित करता येते.

## विशेष व्यवस्थापित सत्र लीझ

विशेष व्यवस्थापित सत्र लीझिंग हा ऐच्छिक, क्लायंट-निरपेक्ष राउटिंग करार आहे: एक सक्रिय मालक
एक पात्र OmniRoute कनेक्शन धारण करतो. हे मॉडेल लीझ करत नाही, OAuth ची आवश्यकता ठेवत नाही, एखादा
विशिष्ट क्लायंट ओळखत नाही किंवा विशिष्ट प्रदात्याची आवश्यकता ठेवत नाही.

प्रमाणीकरण करणाऱ्या API कीकडे `lease:exclusive` स्कोप आणि स्पष्टपणे नमूद केलेली रिकामी नसलेली
`allowedConnections` सूची असणे आवश्यक आहे. की तयार करताना आणि आंशिक अद्यतनांदरम्यान डेटाबेस म्युटेशन सीमा
दोन्ही फील्ड एकत्रितपणे लागू करते.

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

यशस्वी acquire, renew आणि release प्रतिसादांमध्ये टाइमस्टॅम्प, `state` आणि अचूक धनात्मक
`generation` उपलब्ध असतात, मात्र निवडलेले कनेक्शन किंवा क्रेडेन्शियल्स कधीही उपलब्ध नसतात. Renew आणि release
JSON बॉडीमध्ये generation पुरवतात:

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

सक्रिय लीझ मालक त्याच्या वर्तमान बाइंडिंगसाठी गोपनीयता-सुरक्षित प्रदर्शन मेटाडेटाची स्पष्टपणे विनंती करू शकतो:

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

ही ऐच्छिक status क्रिया अपारदर्शक मालक, प्रमाणीकृत व्यवस्थापित API की आणि अचूक
सक्रिय generation यांच्याद्वारे एकाच डेटाबेस ट्रान्झॅक्शनमध्ये संरक्षित केली जाते. `displayName` हे फक्त ट्रिम केलेले, कॉन्फिगर केलेले
कनेक्शन नाव असते; कोणतेही सुरक्षित कॉन्फिगर केलेले नाव उपलब्ध नसल्यास ते `null` असते. OmniRoute कधीही त्याऐवजी
ईमेल किंवा जनरेट केलेली खाते ओळख वापरत नाही. provider मूल्य हे असंवेदनशील प्रदर्शन लेबल असते आणि कधीही
जनरेट केलेला compatible-provider आयडेंटिफायर नसतो. क्रेडेन्शियल्स, टोकन्स, कुकीज, रॉ कनेक्शन किंवा API
की आयडी, मालक हॅश, फेन्सिंग सिक्रेट्स आणि अंतर्गत राउटिंग डेटा वगळला जातो.

चुकीची की, चुकीचा मालक, कालबाह्य generation, अनुपलब्ध, मुदत संपलेल्या, रिलीज केलेल्या आणि अवैध ठरवलेल्या लुकअपसाठी
कनेक्शन मेटाडेटाशिवाय समान `409 LEASE_FENCE_STALE` त्रुटी परत केली जाते. capacity-wait प्रतिसाद मिळालेल्या क्लायंटकडे तपासण्यासाठी कोणतेही सक्रिय बाइंडिंग नसते. राउटिंगमुळे सक्रिय लीझचे संक्रमण झाल्यास,
तेच generation वैध राहते आणि status अणुगतपणे नवीन बाइंडिंग परत करते, जुने बाइंडिंग कधीही परत करत नाही.
विद्यमान क्लायंटमध्ये कोणताही बदल होत नाही, कारण acquire, renew, release आणि waiting प्रतिसादांचे
पूर्वीचे स्वरूप कायम राहते.

हा सर्व्हर करार मूळ OpenAI Codex `/status` बदलत नाही. मूळ Codex सध्या त्याचा
मॉडेल प्रदाता आणि अंगभूत प्रमाणीकरण/खाते स्थिती नोंदवतो, परंतु मनमानी सानुकूल
प्रदाता खाते मेटाडेटा रेंडर करत नाही; भावी क्लायंट इंटिग्रेशनने ही क्रिया कॉल करून
`connection.displayName` कसे प्रदर्शित करायचे हे ठरवणे आवश्यक आहे.

त्यानंतर प्रत्येक व्यवस्थापित इन्फरन्स विनंती दोन्ही नियंत्रण हेडर्स पुरवते:

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

प्रत्येक समर्थित अपस्ट्रीम प्रयत्नाच्या तात्काळ आधी अचूक मालक, generation, सक्रिय कनेक्शन आणि प्रमाणीकृत API की
फेन्स केली जातात. समान कनेक्शनला परवानगी देणारी दुसरी की असली तरी तिच्यासह मालक आणि generation रीप्ले करणे
अयशस्वी होते. रॉ मालक कायमस्वरूपी साठवले जात नाहीत, लॉग केले जात नाहीत, विनंती स्नॅपशॉटमध्ये राखले जात नाहीत किंवा
अपस्ट्रीमकडे फॉरवर्ड केले जात नाहीत.

तात्पुरत्या स्पर्धेमुळे `Retry-After` सह HTTP `429` आणि पुढील प्रतिसाद परत केला जातो:

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

या प्रतिसादाचा अर्थ केवळ इतकाच आहे की सामान्य पात्र संच रिकामा नव्हता आणि प्रत्येक उपलब्ध उमेदवार
परकीय सक्रिय लीझने धरून ठेवला होता. असमर्थित मॉडेल्स/प्रदाते, धोरण विसंगती, cooldown, quota,
health आणि इतर सामान्य पात्रता अपयशांसाठी त्यांचे विद्यमान OmniRoute प्रतिसाद कायम राहतात.

### `x-omniroute-compression`

compression plan चे प्रति-विनंती ओव्हरराइड. याला सर्वोच्च प्राधान्य आहे — हे routing-combo
ओव्हरराइड, सक्रिय profile, auto-trigger आणि पॅनेल Default यांच्यापेक्षा वरचढ ठरते. मूल्ये:

| मूल्य         | परिणाम                                                                                                         |
| ------------- | -------------------------------------------------------------------------------------------------------------- |
| `off`         | या विनंतीसाठी compression नाही.                                                                                |
| `default`     | पॅनेलवरून व्युत्पन्न केलेले Default profile (सक्रिय profile कडे दुर्लक्ष करते). Lossy engines बंद ठेवले जातात. |
| `safe`        | फक्त dedup आणि whitespace folding.                                                                             |
| `allow-lossy` | summaries आणि style rewrites यांसह, या विनंतीसाठी operator plan कायम ठेवा.                                     |
| `engine:<id>` | सक्षम केलेले असताना एकच engine, उदा. `engine:rtk`. त्या engine साठी प्रति-विनंती opt-in.                       |
| `<combo>`     | नावाने जुळणारा named combo—प्रथम नावाने (case-insensitive), त्यानंतर id ने.                                    |

टीपा:

- अज्ञात मूल्यांकडे दुर्लक्ष केले जाते (विनंती कधीही नाकारली जात नाही); निराकरण सामान्य operator precedence कडे जाते.
- एकाधिक combos चे नाव समान असल्यास, निश्चित जुळणीसाठी combo **id** द्या.
- `off` किंवा `default` नाव असलेला combo नावाने निवडता येत नाही (त्या keywords चे प्रथम अर्थ लावले जातात); अशा combo चा संदर्भ त्याच्या id द्वारे द्या.
- मुख्य compression switch हा कठोर नियंत्रक आहे: compression जागतिक स्तरावर अक्षम असताना, हा header ते सक्षम करू शकत नाही.

लागू केलेला plan प्रतिसाद header मध्ये परत पाठवला जातो:

```
X-OmniRoute-Compression: <mode>; source=<source>
```

येथे `<source>` हे `request-header`, `routing-override`, `active-profile`, `auto-trigger`, `default` किंवा `off` यांपैकी एक असते.

## एम्बेडिंग्ज

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

उपलब्ध प्रदाते: Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI.

कॅटलॉग आयडी `provider/model` स्वरूपात असतात (उदाहरण: `jina-ai/jina-embeddings-v5-omni-small`). नोंदणीमध्ये दिसणारे केवळ Jina मॉडेल आयडीदेखील (उदाहरणार्थ `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) रिझॉल्व्ह होतात. Jina embed/rerank/classify/segment प्रथम डॅशबोर्डवरील `jina-ai` क्रेडेन्शियल्स वापरतात; डॅशबोर्ड की उपलब्ध नसल्यासच `JINA_AI_API_KEY` फॉलबॅक म्हणून वापरली जाते. `jina-reader` कार्ड केवळ Reader / `r.jina.ai` साठी आहे (`POST /v1/web/fetch`) आणि ते embeddings किंवा rerank कधीही पुरवत नाही.

मल्टिमोडल समर्थन घोषित करणारी नोंदणीतील मॉडेल्स, प्रदात्यापासून स्वतंत्र असे जास्तीत जास्त 32 संरचित
आयटमदेखील स्वीकारतात. मीडिया आयटमचे प्रकार `text`, `image`, `audio`, `video`, आणि `document` आहेत. त्यांचा मीडिया `source`
एकतर `{"type":"url","url":"https://..."}` किंवा
`{"type":"base64","data":"...","media_type":"..."}` असतो.

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`,
आणि फॅमिली उपनाव `jina-ai/jina-embeddings-v5-omni` → omni-small) Jina चे मूळ
EmbeddingsV5Request दस्तऐवजदेखील स्वीकारते आणि ते `https://api.jina.ai/v1/embeddings` कडे **जसेच्या तसे फॉरवर्ड करते**:

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

मूळ `{ image | audio | video | pdf }` मूल्य हे सार्वजनिक HTTPS URL, `data:` URI किंवा रॉ
base64 असू शकते. OmniRoute त्या ऑब्जेक्ट्सचे स्ट्रिंगमध्ये रूपांतर करत नाही किंवा मूळ image URLs प्राप्त करत नाही — Jina
सार्वजनिक मीडिया स्वतः प्राप्त करते. अतिरिक्त Jina फील्ड्स (`task`, `normalized`, `truncate`, `embedding_type`)
फॉरवर्ड केली जातात. केवळ मजकूरासाठी असलेले Jina SKUs मजकूराव्यतिरिक्त इतर दस्तऐवज अजूनही नाकारतात.

सुरक्षा आणि वाहतूक मर्यादा:

- रिमोट मीडिया URLs सार्वजनिक HTTPS असणे आवश्यक आहे. कॅनॉनिकल `{type,source:url}` आयटम्स
  सर्व्हरकडून प्राप्त केले जातात (रीडायरेक्टचे पुनर्प्रमाणीकरण, टाइमआउट, आकार मर्यादा, सार्वजनिक DNS, कनेक्शन पिनिंग) आणि
  प्रदाता कॉलपूर्वी इनलाइन केले जातात. Jina चे मूळ `{image:"https://..."}` आयटम्स त्याच सार्वजनिक-HTTPS तपासणीनंतर
  जसेच्या तसे फॉरवर्ड केले जातात; Jina URL प्राप्त करते.
- इनलाइन base64 मीडिया प्रत्येक आयटमसाठी डीकोड केल्यानंतर 8 MiB आणि संपूर्ण विनंतीसाठी डीकोड केल्यानंतर 16 MiB पर्यंत मर्यादित आहे.

प्रदाता रूपांतरण (कॅनॉनिकल आयटम्स कधीही बदल न करता फॉरवर्ड केले जात नाहीत):

- Jina मल्टिमोडल मॉडेल्स: प्रत्येक उच्च-स्तरीय आयटम हा एका मोडॅलिटी-की असलेल्या ऑब्जेक्टमध्ये रूपांतरित होतो
  (`text` / `image` / `audio` / `video` / `pdf`), ज्यात इनलाइन मीडियासाठी data URIs वापरले जातात; प्रत्येक
  उच्च-स्तरीय आयटमसाठी एक व्हेक्टर.
- Gemini Embedding 2 फॅमिली: एक उच्च-स्तरीय अॅरे `content.parts` (`text` किंवा `inline_data`) सह एका मूळ
  `models/{model}:embedContent` विनंतीमध्ये रूपांतरित होतो.
- llama.cpp (`llama-cpp/<model>`, स्थानिक सर्व्हरने लोड केलेले कोणतेही मॉडेल): कॅनॉनिकल `text` आयटम्स
  साध्या स्ट्रिंग्समध्ये रूपांतरित होतात आणि `image` / `audio` / `video` प्रत्येकी एका
  `{"content": [part]}` ऑब्जेक्टमध्ये रूपांतरित होतात; यामध्ये इनलाइन डेटासह llama-server चे चॅट कंटेंट पार्ट्स (`image_url`,
  `input_audio` आणि `wav` / `mp3` / `flac` फॉरमॅट, `input_video`) वापरले जातात; प्रत्येक उच्च-स्तरीय
  आयटमसाठी एक व्हेक्टर. सर्व्हर `--embedding --mmproj …` सह चालणे आवश्यक आहे; प्रोजेक्टरशिवाय तो
  स्वतःच मीडिया नाकारतो. `document` समर्थित नाही.
- स्पष्ट मोडॅलिटी मेटाडेटा नसलेली अज्ञात/डायनॅमिक मॉडेल्स HTTP 400 सह संरचित इनपुट नाकारतात.

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

असमर्थित मॉडेल/मोडॅलिटी संयोजनांमध्ये आयटमचे जबरदस्तीने रूपांतरण करण्याऐवजी HTTP 400 परत केला जातो. जुन्या स्ट्रिंग/टोकन
विनंत्यांमधील इनपुटव्यतिरिक्त इतर एक्स्टेंशन फील्ड्स पूर्वीप्रमाणेच बदल न करता पुढे पाठवली जातात.

```bash
# सर्व एम्बेडिंग मॉडेल्सची सूची दाखवा
GET /v1/embeddings
```

## प्रतिमा निर्मिती

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

उपलब्ध प्रदात्यांमध्ये OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (स्थानिक), ComfyUI (स्थानिक) यांचा समावेश आहे.

`n`, `data[]` मध्ये `n` प्रतिमा परत करते. ज्या प्रदात्यांचे अपस्ट्रीम API प्रत्येक कॉलमध्ये एक प्रतिमा परत करते
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI), त्यांच्यासाठी `n` स्वतंत्र अपस्ट्रीम कॉल केले जातात आणि एकावेळी जास्तीत जास्त 4 कॉल सुरू असतात. निश्चित
`seed` मध्ये कॉल निर्देशांकानुसार बदल केला जातो (`seed`, `seed + 1`, …), त्यामुळे प्रतिमा वेगळ्या असतात, पण त्यांची
पुनरुत्पादकता कायम राहते. `n` ची कमाल मर्यादा 10 आहे. कोणताही कॉल अयशस्वी झाल्यास संपूर्ण विनंती
अयशस्वी होते. फॅन-आउट स्वरूपांची यादी `SINGLE_IMAGE_FANOUT_FORMATS` मध्ये
`open-sse/handlers/imageGeneration/fanOut.ts` येथे आहे.

ZenMux विद्यमान API-key कनेक्शनचा पुनर्वापर करते आणि `zenmux/` किंवा `zm/` उपसर्ग स्वीकारते:

- `zenmux/openai/gpt-image-2` ZenMux चे OpenAI Images API वापरते. पर्यायांमध्ये `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background`, आणि `response_format` यांचा समावेश आहे.
- `zm/meta/muse-image-1.0` सारखे इतर प्रकाशक ZenMux चा Vertex AI `:predict`
  एंडपॉइंट वापरतात. `n` हे `sampleCount` शी, `aspect_ratio` हे `aspectRatio` शी, आणि `image_size`
  (`1K`, `2K`, `4K`) हे `sampleImageSize` शी मॅप होते. पिक्सेलमधील `size` केवळ आस्पेक्ट रेशो पुरवते,
  निश्चित पिक्सेल परिमाणांची हमी देत नाही. समर्थित गुणोत्तरे, रिझोल्यूशन्स आणि संख्या मॉडेलनुसार बदलतात.
- `zm/inclusionai/ming-image-0.1-design` स्वतःची परिमाणे निवडते. `size`,
  `aspect_ratio`, आणि `image_size` वगळा; स्पष्ट मूल्ये दिल्यास HTTP 400 परत येतो. PNG, JPEG, आणि WebP
  यांची विनंती `output_format` वापरून करता येते.

हे एकत्रीकरण मजकुरापासून-प्रतिमा निर्मितीस समर्थन देते, संदर्भ-प्रतिमा संपादनास नाही. Vertex
आउटपुट `data[].b64_json` मध्ये सामान्यीकृत केले जाते; `response_format: "url"` अपस्ट्रीम
HTTPS URL किंवा केवळ प्रतिमा बाइट्स उपलब्ध असतील तेव्हा base64 डेटा URL परत करते. रिकामे/फिल्टर केलेले आउटपुट
रिकाम्या यशस्वी प्रतिसादाऐवजी त्रुटी परत करतात. मॉडेलचा प्रवेश ZenMux खात्यावर अवलंबून असतो.
[ZenMux चे Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) आणि
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image) पहा.

```bash
# सर्व प्रतिमा मॉडेल्सची यादी
GET /v1/images/generations
```

## दस्तऐवज OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model`, `provider/model` उपसर्गाद्वारे OCR प्रदाता निवडते; प्रदाता उपसर्ग नसलेला मॉडेल आयडी (उदा.
`mistral-ocr-latest`) त्याच्या नोंदणीकृत प्रदात्याशी जुळवला जातो, आणि `model` वगळल्यास डीफॉल्ट म्हणून
Mistral (`mistral-ocr-latest`) वापरले जाते. नोंदणीकृत प्रदाते (`open-sse/config/ocrRegistry.ts`):

| प्रदाता आयडी                  | मॉडेल आयडी           | `model` मूल्य                                                  | नोंदी                                                                                                     |
| ----------------------------- | -------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (किंवा केवळ `mistral-ocr-latest`) | समकालिक — एकमेव अपस्ट्रीम कॉलचा प्रतिसाद थेट परत केला जातो.                                               |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                    | असमकालिक अपस्ट्रीम (`analyze` + पोल) — खाली पहा.                                                          |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                        | समकालिक, Vertex AI च्या `openapi/chat/completions` भागीदार एंडपॉइंटद्वारे — प्रमाणीकरण/URL साठी खाली पहा. |

तिन्ही प्रदाते समान Mistral-स्वरूपातील मुख्य भागासह प्रतिसाद देतात:

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence पोल प्रवाह

Azure Document Intelligence चे `analyze` API असमकालिक आहे: प्रारंभिक विनंती मुख्य भागाऐवजी
`Operation-Location` शीर्षलेख परत करते आणि निकालासाठी वारंवार पोल करणे आवश्यक असते. हँडलर
(`open-sse/handlers/ocr.ts`) त्या URL वर प्रत्येक सेकंदाला जास्तीत जास्त 30 प्रयत्नांपर्यंत पोल करतो, `ok` नसलेला पोल प्रतिसाद किंवा `"failed"` स्थिती मिळाल्यास त्वरित अयशस्वी होतो (पोल करणे
सुरू ठेवत नाही), आणि प्रयत्नांची मर्यादा संपल्यानंतरही ऑपरेशन सुरू असल्यास `504` परत करतो.
अंतिम Azure प्रतिसाद कॉलरला परत करण्यापूर्वी Mistral द्वारे वापरल्या जाणाऱ्या त्याच
`pages`/`markdown` स्वरूपात सामान्यीकृत केला जातो, त्यामुळे क्लायंट कोडला प्रदात्यासाठी विशेष हाताळणी करण्याची आवश्यकता नसते.

### Vertex AI DeepSeek OCR प्रमाणीकरण आणि एंडपॉइंट निर्धारण

`vertex-deepseek-ocr`, OmniRoute चॅट/प्रतिमा ट्रॅफिकसाठी आधीपासून समर्थित असलेल्या त्याच Vertex AI प्रमाणीकरणाचा
(`open-sse/executors/vertex.ts`) पुनर्वापर करते: कनेक्शनची API key एकतर
Service Account JSON क्रेडेन्शियल असते (JWT-bearer प्रवाहाद्वारे अल्पकालीन OAuth ॲक्सेस टोकनसाठी देवाणघेवाण केली जाते)
किंवा आधीच जारी केलेले OAuth ॲक्सेस टोकन जसेच्या तसे वापरले जाते. अपस्ट्रीम एंडपॉइंट URL हा Vertex चा
सामान्य `openapi/chat/completions` भागीदार एंडपॉइंट असून, तो कनेक्शनच्या प्रकल्प आणि
प्रदेशावरून तयार केला जातो — स्पष्ट `providerSpecificData.project`/`providerSpecificData.region` ला नेहमी प्राधान्य दिले जाते;
अन्यथा प्रकल्प Service Account JSON च्या `project_id` वरून मिळवला जातो आणि प्रदेशासाठी
`us-central1` हे डीफॉल्ट असते. दोन्ही निर्धारणे `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) मध्ये होतात आणि
`handleOcr` कडे पाठवण्यापूर्वी `src/app/api/v1/ocr/route.ts` द्वारे वापरली जातात.

## मॉडेल्सची सूची

```bash
GET /v1/models
Authorization: Bearer your-api-key

→ सर्व चॅट, एम्बेडिंग आणि प्रतिमा मॉडेल्स + कॉम्बो OpenAI स्वरूपात परत करते
```

### मॉडेल आयडी उपसर्ग (`?prefix=`)

बहुतेक मॉडेल्स **प्रदाता उपसर्गाअंतर्गत** दर्शवली जातात. तुम्हाला कोणता उपसर्ग मिळेल हे
`MODELS_CATALOG_PREFIX_MODE` फीचर फ्लॅगद्वारे नियंत्रित केले जाते आणि क्वेरी पॅरामीटर वापरून
**प्रत्येक विनंतीसाठी** ते ओव्हरराइड करता येते — सर्वांसाठी सर्व्हर-व्यापी सेटिंग न बदलता स्वच्छ सूची
हवी असलेल्या क्लायंटसाठी हे उपयुक्त आहे:

```bash
GET /v1/models?prefix=alias        # प्रत्येक मॉडेलसाठी एक आयडी — लघु उपनाव उपसर्ग
GET /v1/models?prefix=dual         # दोन्ही रूपे (सर्व्हरचे डीफॉल्ट)
GET /v1/models?prefix=canonical    # केवळ संपूर्ण प्रदाता-आयडी उपसर्ग
```

| मोड         | उत्सर्जित मूल्ये                                          | नोंदी                                                                                                                                                                                                     |
| ----------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **आणि** `claude/claude-sonnet-4-6` | **डीफॉल्ट.** दोन्ही आयडी एकाच मॉडेलकडे रूट होतात; दोन्हीपैकी कोणतेही रूप हार्डकोड केलेली क्लायंट कॉन्फिगरेशन कार्यरत राहावीत म्हणून ते ठेवले आहेत. यामुळे कॅटलॉगचा आकार साधारण दुप्पट होतो.               |
| `alias`     | `cc/claude-sonnet-4-6`                                    | प्रत्येक मॉडेलसाठी एक नोंद. स्वतंत्र उपनाव नसलेले प्रदाते तरीही त्यांची नोंद उत्सर्जित करतात, त्यामुळे काहीही गमावले जात नाही.                                                                            |
| `canonical` | `claude/claude-sonnet-4-6`                                | संपूर्ण प्रदाता-आयडी उपसर्गाअंतर्गत प्रत्येक मॉडेलसाठी एक नोंद. स्वतंत्र उपनाव नसलेले प्रदाते (उदा. `antigravity/…`, `agy/…`) येथेही त्यांचा एकमेव आयडी उत्सर्जित करतात, त्यामुळे काहीही गमावले जात नाही. |

`dual`-मोड मिरर क्वेरी पॅरामीटरशिवायही ओळखता येतो: त्यामध्ये प्राथमिक आयडीकडे निर्देश करणारे `parent`
फील्ड असते.

मॉडेल निवडसूची रेंडर करणाऱ्या क्लायंटने `?prefix=alias` ची विनंती करावी —
[OmniCopilot VS Code विस्तार](../guides/VSCODE-COPILOT.md) हेच करतो.

### शोध फिल्टर्स (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` स्वेच्छेने वापरता येणारे शोध फिल्टर्स स्वीकारते. त्यांपैकी कोणतेही फिल्टर नसल्यास प्रतिसाद
बदलत नाही. ते कॉलरला आधीपासून दिसणारा कॅटलॉग मर्यादित करतात (API-की परवानग्या प्रथम लागू होतात)
आणि ते OpenAI-शैलीतील `limit` / `after` पेजिंगपूर्वी चालतात:

```bash
GET /v1/models?capability=vision&capability=tool_calling   # सूचीबद्ध केलेली प्रत्येक क्षमता सत्य असणे आवश्यक आहे
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # कॅटलॉग `type`; हे मूल्य नसलेल्या पंक्ती `chat` असतात
GET /v1/models?q=sonnet&limit=10                           # आयडी किंवा नावावर केस-संवेदनारहित जुळणी
```

| पॅरामीटर      | मूल्ये                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | ऋणेतर पूर्णांक, ज्याची तुलना `context_length` शी केली जाते                                          |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | 1–200 वर्ण                                                                                          |

अज्ञात मूल्य किंवा ऋणेतर पूर्णांक नसलेले `min_context` (उदाहरणार्थ `1.5`) दिल्यास,
HTTP `400` परत केले जाते आणि संदेशामध्ये वैध मूल्ये सूचीबद्ध केली जातात. अंमलबजावणी:
`src/app/api/v1/models/catalogFilters.ts`.

### मॉडेलची संक्षिप्त सूची (`POST /v1/models/query`)

`POST /v1/models/query` त्याच कॅटलॉगमधून एक छोटी, निर्धारक सूची परत करते आणि तिचे प्रमाणीकरण
व प्रत्येक कीसाठीची दृश्यमानता `GET /v1/models` प्रमाणेच असते:

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

प्रत्येक फील्ड पर्यायी आहे. `capabilities` आणि `exclude` अॅरे किंवा स्वल्पविरामाने विभक्त केलेली स्ट्रिंग
स्वीकारतात; `max_output` ची तुलना `max_output_tokens` शी केली जाते. परिणाम प्रथम `owned_by` आणि नंतर `id`
नुसार क्रमबद्ध केले जातात. `limit` चे डीफॉल्ट मूल्य `20` आहे आणि `100` पेक्षा जास्त मूल्ये `100` पर्यंत मर्यादित केली जातात. अवैध JSON, अज्ञात
फील्ड किंवा अवैध मूल्य दिल्यास HTTP `400` परत केले जाते.

### स्वतंत्रपणे लपवलेली चॅट मॉडेल्स

एखाद्या प्रदाता पृष्ठावर **लपवलेले** म्हणून चिन्हांकित केलेले मॉडेल कॅटलॉगमधून वगळले जाते आणि त्याची स्पष्टपणे
विनंती केल्यास HTTP `404` / `model_not_found` सह ती नाकारली जाते. ही तपासणी निराकरण केलेला
प्रदाता आणि मॉडेल वापरते, ज्यामध्ये प्रदाता उपनावे, सुसंगत-प्रदाता नोड उपसर्ग आणि
कनेक्शन डीफॉल्ट्स समाविष्ट असतात. कॉम्बो लपवलेली लक्ष्ये वगळतो आणि दृश्यमान समकक्ष वापरू शकतो; जेव्हा
अंमलबजावणीयोग्य कोणतेही लक्ष्य शिल्लक राहत नाही, तेव्हा तो समान त्रुटी कोड परत करतो. मॉडेल पुन्हा दृश्यमान केल्याचा परिणाम पुढील
विनंतीपासून लागू होतो. केवळ-प्रतिमा दृश्यमानता ओव्हरराइड्स समान आयडी असलेले चॅट मॉडेल लपवत नाहीत.

ही स्वतंत्र मॉडेल सेटिंग
[मॉडेल एक्सपोजर अनुमती/नकार सूचींपासून](../routing/MODEL_EXPOSURE_LIST.md) वेगळी आहे, ज्या स्पष्ट डिस्पॅच कायम ठेवून कॅटलॉगमधील
प्रदर्शन आणि स्वयंचलित-रूटिंग उमेदवार फिल्टर करतात. API-की मॉडेल
परवानग्या स्वतंत्रपणे लागू होत राहतात. डीफॉल्ट कॅटलॉग उपसर्ग मोड `dual` हाच राहतो.

### विचार-विरहित मॉडेल प्रकार

विचार करण्यास सक्षम Claude मॉडेल्ससाठी, `/v1/models` एक **विचार-विरहित** प्रकारही दर्शवते, ज्याच्या आयडीच्या सुरुवातीला `claude-3-omniroute-no-thinking/` हा उपसर्ग असतो:

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

हा id निवडल्यास (उदा. नेहमी `thinking` ब्लॉक जोडणाऱ्या Claude Code config मध्ये), reasoning दडपून तो वास्तविक `<provider>/<model>` कडे परत resolve होतो — `/v1/messages` path वर `thinking:{type:"disabled"}`, किंवा `/v1/chat/completions` path वर `reasoning`/`reasoning_effort` fields वगळली जातात. हा variant केवळ thinking समर्थित करणाऱ्या **आणि** `disabled` चे पालन करणाऱ्या Claude-family models साठी सूचीबद्ध केला जातो (त्यामुळे, उदा. `disabled` नाकारणारे adaptive-only models वगळले जातात). Operators प्रत्येक model साठी `ModelSpec.noThinkingAlias` द्वारे हा variant सक्तीने चालू किंवा बंद करू शकतात.

## ElevenLabs ऑडिओ निर्मिती

तुमच्या ElevenLabs API कीसह OmniRoute मध्ये `elevenlabs` provider कनेक्शन कॉन्फिगर करा.
क्लायंट त्यांच्या **OmniRoute** कीने (`Authorization: Bearer $OMNIROUTE_API_KEY`) प्रमाणीकरण करतात;
gateway संग्रहित provider की `xi-api-key` म्हणून पुरवतो. gateway bearer token म्हणून ElevenLabs की कधीही पाठवू नका.

| पद्धत | पाथ                         | प्रतिसाद                          | API की endpoint श्रेणी |
| ----- | --------------------------- | --------------------------------- | ---------------------- |
| POST  | `/v1/sound-generation`      | मूळ ऑडिओ बाइट्स                   | `elevenlabs`           |
| POST  | `/v1/music`                 | मूळ ऑडिओ बाइट्स                   | `music`                |
| POST  | `/v1/music/stream`          | स्ट्रीमिंग ऑडिओ बाइट्स            | `music`                |
| POST  | `/v1/music/detailed`        | मूळ multipart ऑडिओ आणि रचना योजना | `music`                |
| POST  | `/v1/music/detailed/stream` | मूळ SSE मेटाडेटा आणि ऑडिओ चंक्स   | `music`                |
| POST  | `/v1/music/plan`            | JSON रचना योजना                   | `music`                |

हे endpoints विद्यमान `/v1/audio/speech`, `/v1/audio/transcriptions`,
`/v1/voices`, `/v1/text-to-speech/{voiceId}` आणि `/v1/speech-to-text` routes ना पूरक आहेत. `output_format` आणि `enable_logging` यांसारखी मूळ JSON फील्ड्स आणि क्वेरी पॅरामीटर्स जतन केली जातात.
`/v1/music/detailed` प्रतिसाद त्यांच्या multipart boundaries जतन करतात; त्यांचे multipart म्हणून पार्सिंग करा.
`/v1/music/detailed/stream` रचना मेटाडेटा आणि SSE events मधील
base64 ऑडिओ चंक्ससह `text/event-stream` परत करते. सर्व सहा routes CORS preflight ला समर्थन देतात.

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# एक छोटा ध्वनी प्रभाव. कालावधी: 0.5 ते 30 सेकंद.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# संगीताचा कालावधी मिलिसेकंदांमध्ये व्यक्त केला जातो: 3000 ते 600000.
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

वाढत्या क्रमाने ऑडिओ वितरणासाठी त्याच JSON body सह `/v1/music/stream` वापरा. रचना नेमक्या `prompt` किंवा `composition_plan` यांपैकी एकाचा स्वीकार करते; `/v1/music/plan` साठी `prompt` आवश्यक आहे आणि तो पर्यायाने `source_composition_plan` स्वीकारतो. मूळ schemas अतिरिक्त provider फील्ड्स जतन करतात, त्यामुळे रचना-योजना आवृत्त्या आणि fine-tuning पर्याय ElevenLabs पर्यंत पोहोचतात.

एकीकृत `/v1/music/generations` endpoint `elevenlabs/music_v1`,
`elevenlabs/music_v2` आणि `elevenlabs/music_v2_5` देखील स्वीकारतो. सक्रिय ElevenLabs कनेक्शन असल्यास, ही मॉडेल्स संगीत कॅटलॉगद्वारे उपलब्ध केली जातात. हा endpoint
`{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` परत करतो. त्याचे `duration` फील्ड सेकंदांमध्ये असते आणि `music_length_ms` शी मॅप होते; स्पष्टपणे दिलेल्या `music_length_ms` ला प्राधान्य असते.
`instrumental` हे `force_instrumental` शी मॅप होते, ज्यामध्ये मूळ फील्डला प्राधान्य असते.
स्ट्रीमिंगसाठी मूळ स्ट्रीमिंग endpoints आणि केवळ रचना योजनेद्वारे चालवल्या जाणाऱ्या विनंत्यांसाठी मूळ रचना endpoint वापरा.

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

upstream कॉलपूर्वी endpoint, मॉडेल, बजेट आणि कनेक्शन निर्बंध लागू होतात. मूळ
routes upstream स्थिती कोड आणि त्रुटी bodies कोणताही बदल न करता परत करतात, ज्यामध्ये योजना निर्बंधासाठी `402` आणि कोटा मर्यादेसाठी `429` यांचा समावेश आहे. उपलब्ध असल्यास `character-cost`, `song-id`, `request-id` आणि `retry-after`
हेडर्स जतन केले जातात. मोफत क्रेडिट शिल्लक असल्याने प्रत्येक संगीत मॉडेल, आउटपुट फॉरमॅट किंवा API वैशिष्ट्याचा अॅक्सेस मिळेलच याची खात्री नसते: प्रत्येक विनंतीसाठी पात्रता ElevenLabs ठरवते.
एकीकृत endpoint OmniRoute च्या प्रमाणित त्रुटी envelope मध्ये त्रुटी स्थिती कोड जतन करतो.

Upstream करार: [ध्वनी प्रभाव](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert),
[संगीत रचना](https://elevenlabs.io/docs/api-reference/music/compose) आणि
[स्ट्रीमिंग संगीत तपशील](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream).

जे क्लायंट `Authorization: Bearer ...` जोडू शकत नाहीत, त्यांच्यासाठी OmniRoute क्वेरी-स्ट्रिंग सुसंगततेद्वारे (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) किंवा खाली दस्तऐवजीकरण केलेल्या समर्पित `/api/v1/vscode/{token}/...` एंडपॉइंट्सद्वारे URL मधील API की देखील स्वीकारते.

```bash
# पुनःक्रमांकन (क्लाउड रजिस्ट्री प्रदाता किंवा "<prefix>/<model>" स्वरूपातील OpenAI-सुसंगत प्रदाता नोड)
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina वर्गीकरण (Foundation API क्रेडेन्शियल्स)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina सेगमेंटर
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina शोध (s.jina.ai; प्रदाता उपनाम: jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# मॉडरेशन
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — audio/mpeg (किंवा विनंती केलेल्या स्वरूपाची) बॉडी परत करते
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS साठी भाषा आणि व्हॉइस आवश्यक आहेत: `language` डीफॉल्टने "en" असते; व्हॉइस नसल्यास
# किंवा OpenAI चे स्टॉक व्हॉइस नाव (alloy, nova, …) असल्यास ते "Adrian" होते
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# प्रतिमा संपादन (मल्टिपार्ट)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# व्हिडिओ / संगीत निर्मिती (प्रदाता-उपसर्गयुक्त मॉडेल आयडी)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **रिरँक प्रदाता नोड्स:** `POST /v1/rerank` हे `<node-prefix>/<model>` या स्वरूपात संबोधित केलेल्या OpenAI-सुसंगत प्रदाता नोड्सकडेही
> (oMLX, vLLM, Infinity, गेटवेमागील TEI, …) रूट केले जाते. लूपबॅक
> नोड्स (`localhost`, `127.0.0.1`, `172.16.0.0/12`) नेहमीच पात्र असतात आणि ऑपरेटरने
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` मध्ये सूचीबद्ध केलेली होस्टनावेही पात्र असतात (उदा. `http://reranker:8080/v1`
> सारखे Docker/Compose सेवा नाव; यांना थेट कॉल केला जातो, `HTTP(S)_PROXY` किंवा कनेक्शनच्या
> पिन केलेल्या प्रॉक्सीमधून कधीही नाही). इतर कोणत्याही
> होस्टवरील नोड्स — LAN बॉक्स किंवा Tailscale पीअर — केवळ ऑपरेटरने
> `RERANK_REMOTE_PROVIDER_NODES` फीचर फ्लॅग सक्षम केला **आणि** नोडचा बेस URL प्रदात्याचे
> आउटबाउंड URL धोरण (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`) पूर्ण करत असेल, तरच पात्र ठरतात.
> मेमरी इंजिनची रिरँक पायरी या रूटला
> लूपबॅकवरून कॉल करते, त्यामुळे मेमरी सेटिंग्जमधील `rerankProviderModel` वरही हाच नियम लागू होतो.
>
> **स्थानिक सर्व्हरची स्वरूपे:** नोडला `<base>/v1/rerank` येथे आणि 404 आल्यास `<base>/rerank`
> (Infinity, TEI) येथे कॉल केला जातो. अपस्ट्रीम बॉडीमध्ये Cohere/OpenAI शब्दलेखन (`documents`,
> `return_documents`) आणि TEI शब्दलेखन (`texts`, `return_text`) ही दोन्ही असतात आणि अपस्ट्रीम प्रतिसाद
> Cohere एन्व्हलपमध्ये सामान्यीकृत केला जातो: TEI चे साधे `[{index, score, text}]`, हलक्या गेटवेमधील
> `{results: [{index, score}]}` आणि Voyage-शैलीतील `{data: [...]}` हे सर्व क्लायंटकडे
> `{results: [{index, relevance_score, document?}]}` म्हणून परत येतात, गुणांनुसार क्रमबद्ध केलेले आणि `top_n` पर्यंत मर्यादित केलेले.
>
> **प्रदाता-नोड शोध:** OpenAI-सुसंगत प्रदाता नोडवरील मॉडेल्स `GET /v1/models` मध्ये
> नोड प्रीफिक्सअंतर्गत दिसतात. एंडपॉइंट मेटाडेटा नसलेल्या पंक्ती (स्थानिक `/v1/models` सूचींसाठी सामान्य)
> नोडचा `apiType` वारशाने घेतात, त्यामुळे `embeddings` नोडची मॉडेल्स डीफॉल्टने चॅट म्हणून न धरता
> `type: "embedding"` असतात आणि `rerank` नोडची मॉडेल्स `type: "rerank"` असतात; सिंक केलेल्या किंवा
> व्यक्तिचलितपणे जोडलेल्या पंक्तीवरील स्पष्ट `supportedEndpoints` ला तरीही प्राधान्य मिळते.

### समर्पित प्रदाता रूट्स

```bash
POST /v1/providers/{provider}/chat/completions
POST /v1/providers/{provider}/embeddings
POST /v1/providers/{provider}/images/generations
```

वेब/शोध प्रदाता अमूर्तीकरण (Tavily, Brave, Exa, Serper इ.).

| पद्धत | पथ                     | वर्णन                                                                                    |
| ----- | ---------------------- | ---------------------------------------------------------------------------------------- |
| GET   | `/v1/search`           | कॉन्फिगर केलेल्या शोध प्रदात्यांची आणि क्षमतांची सूची                                    |
| POST  | `/v1/search`           | शोध क्वेरी चालवा — मुख्य भाग `v1SearchSchema` द्वारे प्रमाणित, कॅशिंग/एकत्रीकरणास समर्थन |
| GET   | `/v1/search/analytics` | प्रत्येक प्रदात्यासाठी हिट/विलंबता/कॅश आकडेवारी                                          |

**प्रमाणीकरण:** Bearer API की (`extractApiKey` + `isValidApiKey`). शोध धोरण `enforceApiKeyPolicy` द्वारे लागू केले जाते.

### Exa आणि Tavily `provider_options`

Exa आणि Tavily प्रदाता-विशिष्ट फील्ड नाम-अवकाशित संग्रहातून वाचतात:
`provider_options.exa` (किंवा `provider_options["exa-search"]`) आणि `provider_options.tavily`
(किंवा `provider_options["tavily-search"]`). फक्त खालील की अग्रेषित केल्या जातात. प्रत्येक कीची
`open-sse/handlers/search/providerOptionsPassthrough.ts` मधील तिच्या स्वतःच्या Zod स्कीमाशी
तपासणी केली जाते आणि चुकीचा प्रकार असलेली की वगळली जाते. प्रमाणीकरण, मूळ URL,
`stream` आणि `outputSchema` यांसह इतर कोणतीही की दुर्लक्षित केली जाते. इतर प्रदात्यांद्वारे
वापरल्या जाणाऱ्या सपाट की (`cx`, `depth`, ...) पूर्वीप्रमाणेच कार्य करतात.

| प्रदाता | शीर्ष-स्तरीय फील्ड                                                                                                                                                                                                                                                                                                                                                        | नेस्टेड                                                                                                                                                              |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa     | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (सपाट मूलभूत मूल्ये), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                           | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` डीफॉल्ट `{ text: true, highlights: true }` वर विलीन केले जाते |
| Tavily  | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                    |

सर्वसाधारण फील्डना नेहमी प्राधान्य असते: `query`, `max_results`, `filters` (डोमेन), `country` आणि
`search_type` मधून मिळालेला विषय. Exa वर, `search_type: "news"` हे `category: "news"` कायम ठेवते.
Tavily देखील `search_type: "finance"` (`topic: "finance"`) स्वीकारते.

सर्वसाधारण `time_range` आता दोन्ही प्रदात्यांपर्यंत पोहोचते: Exa ला `startPublishedDate` (ISO
टाइमस्टॅम्प) मिळतो आणि Tavily ला `start_date` (`YYYY-MM-DD`) मिळतो. `provider_options` मधील
स्पष्ट तारीख मॅप केलेल्या तारखेवर अधिलिखित होते.

Exa परिणाम `id`, `highlight_scores`, `summary`, `subpages`, `entities` आणि `extras` हे
`provider_raw` मध्ये कायम ठेवतात. Tavily परिणाम `images` आणि `favicon` कायम ठेवतात.

खर्चाचा हिशोब अजूनही सपाट रजिस्ट्री `costPerQuery` आहे. Tavily प्रत्येक कॉलसाठी
`search_depth: "advanced"` वर अधिक क्रेडिट आकारते आणि हा फरक
`usage.search_cost_usd` मध्ये प्रतिबिंबित होत नाही.

## Web Fetch API

कॉन्फिगर केलेल्या web-fetch प्रदात्याद्वारे (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract) URL मधून सामग्री एक्स्ट्रॅक्ट करा.

Parallel Extract (`parallel-search`, Parallel Search सारखीच API की) केवळ Markdown
परत करते — इतर कोणतेही `format` दिल्यास `400` मिळतो — आणि सामग्रीची मर्यादा 100,000 वर्ण आहे. जेव्हा
लक्ष्य पृष्ठच एक्स्ट्रॅक्ट करता येत नाही, तेव्हा upstream ते HTTP 200 प्रतिसादामध्ये नोंदवते;
OmniRoute ते एका निश्चित संदेशासह `422` म्हणून दर्शवते.

| पद्धत | पथ              | वर्णन                                                                     |
| ----- | --------------- | ------------------------------------------------------------------------- |
| POST  | `/v1/web/fetch` | URL फेच/स्क्रेप करा — body ची पडताळणी `v1WebFetchSchema` द्वारे केली जाते |

**प्रमाणीकरण:** Bearer API की (`extractApiKey` + `isValidApiKey`). धोरणाची अंमलबजावणी `enforceApiKeyPolicy` द्वारे केली जाते.

**कोटा-जागरूक fallback (#8297):** कोणताही स्पष्ट `provider` दिला नसल्यास, पूलमधून
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`)
निश्चित
प्राधान्यक्रमाने (fill-first) क्रमशः प्रयत्न केले जातात — विनंती त्वरित अयशस्वी करण्याऐवजी दर-मर्यादित पण कॉन्फिगर केलेला प्रदाता वगळला जातो,
आणि पुन्हा प्रयत्न करण्यायोग्य/कोटा-संबंधित upstream अपयश
(HTTP 429 नेहमी; Firecrawl/Tavily/TinyFish च्या कोटा-शैलीतील विनामूल्य स्तरांसाठी 402/403 —
Jina Reader साठी नाही, आणि साध्या 400 bad request साठी कधीही नाही) विनंतीच्या वेळी
पुढील, अद्याप न वापरलेल्या आणि क्रेडेन्शियल असलेल्या प्रदात्याकडे जाते. पूलमधील प्रत्येक प्रदाता
संपल्यानंतर, endpoint पूर्वीच्या सर्वसाधारण `400` ऐवजी एकच `429` (`Retry-After`
header सह) परत करतो. स्पष्ट `provider` ची विनंती केल्यास,
**कोणताही** मूक fallback होत नाही — दर-मर्यादित किंवा अयशस्वी स्पष्ट
प्रदाता स्वतःची त्रुटी दर्शवतो (दर-मर्यादित असल्यास `429`, अन्यथा upstream
status).

## WebSocket स्ट्रीमिंग

```bash
GET /v1/ws?handshake=1
```

WebSocket upgrade handshake ची पडताळणी करते आणि wire protocol चे उदाहरण संदेश (`request`, `cancel`) परत करते. प्रत्यक्ष WS frames हे Next.js route table च्या बाहेर असलेल्या बंडल केलेल्या WS server द्वारे हाताळले जातात.

**प्रमाणीकरण:** handshake दरम्यान Bearer API की.

### WebSocket वर Responses API (फक्त codex)

```bash
# HTTP API सारखाच host:port (डीफॉल्ट 20128); कनेक्शन upgrade करा:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (किंवा: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# पहिले frame response.create असणे आवश्यक आहे:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket proxy **केवळ `codex` शी** जोडलेला आहे (ChatGPT
backend). तो API/dashboard सारख्याच port वर `/v1/responses`,
`/responses`, आणि `/api/v1/responses` या paths वर ऐकतो. पहिल्या `response.create` frame वर तो
अंतर्गत `codex-responses-ws` bridge द्वारे प्रमाणीकरण + तयारी करतो, एक
codex OAuth connection निवडतो आणि `wreq-js` transport द्वारे `wss://chatgpt.com/backend-api/codex/responses`
कडे tunnel करतो. **codex नसलेली models नाकारली जातात** (`codex_ws_provider_required`).
कोटा-share routing साठी `model: "qtSd/<group>/codex/<model>"` वापरा. याची अंमलबजावणी
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` मध्ये केली आहे.

**प्रमाणीकरण:** handshake दरम्यान Bearer API की. बंडल केलेला HTTP server (`server-ws.mjs`)
हा सक्रिय entrypoint असणे आवश्यक आहे (`app/server-ws.mjs` अस्तित्वात असल्यास, डीफॉल्टनुसार तोच असतो).

#### Model id: मूळ ChatGPT id वापरा (`codex/` prefix शिवाय)

OpenAI **Codex CLI**, `supports_websockets = true` असताना model name ची client-side पडताळणी करते आणि
`codex/gpt-5.5` सारखे **provider-prefix असलेले ids नाकारते**
(`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`). **मूळ** id पाठवा (उदा. `gpt-5.5`). OmniRoute चा bridge
केवळ codex साठी आहे, त्यामुळे upstream कडे tunnel करण्यापूर्वी तो मूळ id चे codex model म्हणून
(`resolveCodexWsModelInfo`) पुन्हा resolution करतो — जरी मूळ
`gpt-5.5` अन्यथा HTTP वर दुसऱ्या प्रदात्याकडे route झाला असता.

#### OpenAI Codex CLI कॉन्फिगर करणे

`~/.codex/config.toml` मध्ये WebSocket
support असलेला सानुकूल प्रदाता जोडून Codex CLI ला OmniRoute कडे निर्देशित करा (अस्तित्वात असलेल्या config मध्ये बदल टाळण्यासाठी स्वतंत्र `CODEX_HOME` वापरा):

```toml
model = "gpt-5.5"                 # मूळ id — "codex/gpt-5.5" नाही
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # शेवटी slash नाही; WS URL यावरून तयार केला जातो (production मध्ये https/wss वापरा)
wire_api = "responses"                    # Feb 2026 पासून समर्थित असलेले एकमेव value
supports_websockets = true                # Responses-over-WS transport सक्षम करते
env_key = "OMNIROUTE_API_KEY"             # OmniRoute API की (Bearer) ठेवते
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API की (REQUIRE_API_KEY=false असल्यास कोणतीही की)
codex exec "Responda apenas: PONG"
```

CLI, `base_url + /responses` ला WebSocket मध्ये upgrade करते आणि OmniRoute त्याला
निवडलेल्या codex OAuth connection कडे tunnel करते. स्थानिक
server विरुद्ध end-to-end पडताळणी केली आहे: ChatGPT `codex.rate_limits` + `response.created` परत करते आणि
completion stream करते.

## स्वयं-सेवा वापर (`/api/usage/om-usage`)

कोणतीही API की **स्वतःचा** वापर आणि कोटे पाहू शकते — व्यवस्थापन प्रमाणीकरणाची आवश्यकता नाही. क्लायंट (CLI, OmniCopilot पॅनेल) की धारकाला त्याचा खर्च दाखवण्यासाठी हा एंडपॉइंट वापरतो.

```bash
# मजकूर स्वरूप (ऐतिहासिक करार — टर्मिनलसाठी साधा मजकूर)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# संरचित स्वरूप — UI जे वापरते
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

कीसाठी **`allowUsageCommand`** सक्षम असणे आवश्यक आहे (डीफॉल्टनुसार बंद — डॅशबोर्डचा API-की व्यवस्थापक प्रत्येक कीसाठी ते टॉगल करतो). ते नसल्यास एंडपॉइंट `403` प्रतिसाद देतो.

`?format=json` विभेदित रचना परत करते, त्यामुळे कॉलर नकाराच्या प्रतिसादातून कधीही डेटा फील्ड वाचत नाही. यशस्वी झाल्यास:

```jsonc
{
  "allowed": true,
  // कीने प्रति-की वापर मर्यादा (दैनिक/साप्ताहिक USD) स्वीकारल्या असतील तेव्हाच उपस्थित:
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // निवडलेल्या प्रदात्याच्या कोट्याचा स्नॅपशॉट किंवा अद्याप काहीही कॅश केलेले नसल्यास null:
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // प्रत्येक कनेक्शनचा स्नॅपशॉट, जेणेकरून UI अनेक प्रदाते शेजारी-शेजारी दर्शवू शकेल:
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

नकार दिल्यास (`401` अवैध की / `403` परवानगी नाही), हाच रूट
`{ "allowed": false, "error": { "message": "…" } }` परत करतो — उपस्थित-परंतु-रिक्त `personal`/`provider`
(कीला परवानगी आहे, पण अद्याप काहीही माहिती मिळालेली नाही) ही नकारापेक्षा वेगळी स्थिती आहे आणि केवळ JSON स्वरूप त्यांच्यात फरक करते.

**प्रमाणीकरण:** कॉलरची स्वतःची Bearer API की, `isValidApiKey` वापरून सत्यापित केली जाते — हे व्यवस्थापन इंटरफेस (`/api/keys/…`) _नाही_, जो `requireManagementAuth` द्वारे संरक्षित राहतो.

### मूळ विरुद्ध कटऑफ-समायोजित कोटा टक्केवारी

`/api/usage/om-usage` वापरताना, कॉलरने **साध्या-मजकूर आउटपुट** आणि संरचित **JSON आउटपुट** मध्ये सादर केलेल्या टक्केवारीतील फरक लक्षात घ्यावा:

| पैलू                   | साधे-मजकूर स्वरूप (`/api/usage/om-usage` / `@@om-usage`)                                              | JSON स्वरूप (`?format=json`)                                                                 |
| :--------------------- | :---------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------- |
| **आउटपुट फील्ड**       | `NN% left` (उदा., `20% left`)                                                                         | `provider.quotas` / `providers[].quotas`                                                     |
| **मोजमाप**             | **कटऑफ-समायोजित वापरण्यायोग्य वाटप**: कटऑफ मर्यादेपेक्षा जास्त उर्वरित क्षमता                         | **मूळ अपस्ट्रीम कोटा**: प्रदात्याचे समायोजित न केलेले मोजमाप                                 |
| **कटऑफ स्केलिंग**      | `effectiveRemainingPercent()` द्वारे स्केल केलेले, त्यामुळे संरक्षित राखीव भाग `0% left` म्हणून दिसतो | नाही (प्रदात्याने अहवाल दिल्याप्रमाणे मूळ स्नॅपशॉट मूल्ये)                                   |
| **मर्यादा डेटा**       | प्रदर्शित टक्केवारीमध्ये समाविष्ट                                                                     | प्रत्येक कनेक्शनसाठी `quotaWindowThresholds` मध्ये संग्रहित (किंवा सर्व्हरची डीफॉल्ट मूल्ये) |
| **प्राथमिक वापरकर्ता** | परस्परसंवादी CLI, टर्मिनल प्रॉम्प्ट, मानवी ऑपरेटर                                                     | प्रोग्रामॅटिक एकत्रीकरणे, डॅशबोर्ड, विश्लेषणे, बिलिंग ट्रॅकर                                 |

#### कटऑफ समायोजन सूत्र

OmniRoute अपस्ट्रीम कोटा संपुष्टात येणे टाळण्यासाठी सक्रिय कोटा कटऑफला समर्थन देते (कनेक्शनच्या `quotaWindowThresholds`, प्रदात्याची डीफॉल्ट मूल्ये किंवा जागतिक लवचिकता सेटिंग्जद्वारे कॉन्फिगर केलेले). कोटा विंडोवर कटऑफ मर्यादा (उदा., `cutoff = 25%`) सक्रिय असताना, मजकूर रेंडरर उर्वरित वाटपाची गणना अशी करतो:

- `remaining <= cutoff` असल्यास: `0%` परत करते.
- `remaining > cutoff` असल्यास: `((remaining - cutoff) / (100 - cutoff)) * 100` परत करते.

स्वरूपित मजकूर आउटपुट याला सर्वात जवळच्या पूर्णांकापर्यंत पूर्णांकित करते (`Math.round(...)`).

#### उदाहरणात्मक नमुना

**60% मूळ वापर** (म्हणजे **40% मूळ उर्वरित कोटा**) असलेली आणि **25% उर्वरित-कोटा कटऑफ** मर्यादा कॉन्फिगर केलेली प्रदाता विंडो विचारात घ्या:

| प्रतिनिधित्व                  | गणना                                               | उर्वरित |                  सूचित वापर                  |
| :---------------------------- | :------------------------------------------------- | :-----: | :------------------------------------------: |
| **मूळ JSON (`?format=json`)** | अपस्ट्रीम स्नॅपशॉट (`quotas[window]`)              | **40%** |                   **60%**                    |
| **मजकूर स्वरूप (`NN% left`)** | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` | **20%** | **80%** (`100 - remaining` अशी गणना केल्यास) |

- **मजकुरात 20% शिल्लक का दिसते:** खात्यावर प्रत्यक्ष उरलेल्या 40% कोट्यापैकी 25% कटऑफ धोरणाद्वारे राखीव ठेवला आहे. राउटर या कनेक्शनकडे रूटिंग थांबवण्यापूर्वी कॉलरकडे वापरण्यायोग्य 75% मोकळ्या क्षमतेपैकी फक्त 15% उरली आहे. स्केलिंगमुळे रूटिंग थांबेल त्याच क्षणी कनेक्शन संपुष्टात आल्याचा संकेत (`0% left`) देते.
- **JSON मूळ मूल्ये का जतन करते:** JSON पेलोड प्रदात्याचा अचूक स्नॅपशॉट (`UsageSnapshot`) परत करतो, ज्यामुळे बाह्य साधनांना सर्व्हर-साइड हानीकारक स्केलिंगशिवाय वास्तविक अपस्ट्रीम वापर आणि कनेक्शन-स्तरीय `quotaWindowThresholds` उपलब्ध होतात.

#### वापरकर्ता स्थलांतर मार्गदर्शन

एखाद्या बाह्य एकात्मिकरणाने (जसे की एडिटर प्लगइन किंवा एजंट एक्स्टेंशन) यापूर्वी मजकूर
एंडपॉइंट (`NN% left`) स्क्रॅप केला असेल आणि वापरलेली टक्केवारी `100 - NN` अशी मोजली असेल, तर `?format=json` वर स्थलांतरित करण्याचा अर्थ असा होतो:

- कच्ची JSON मूल्ये वाचल्यास **वास्तविक अपस्ट्रीम वापर** दिसून येईल (वरील उदाहरणात 60% वापर).
- एकात्मिकरणाला मजकूर एंडपॉइंटचे वापरण्यायोग्य-शिल्लक भत्त्याचे अर्थशास्त्र जतन करायचे असल्यास, ते कनेक्शन-स्तरीय ओव्हरराइडसाठी `quotaWindowThresholds` वापरून
  प्रभावी शिल्लक सूत्राचे क्लायंट-साइडवर मूल्यमापन करू शकते.

### विलंबावरील परिणाम

सिमॅंटिक कॅश HIT झाल्यास प्रतिसाद कॅशमधून **अपस्ट्रीम कॉल न करता**
दिला जातो, त्यामुळे नोंदवलेला `X-OmniRoute-Response-Latency` जवळपास शून्य
असतो (मूळ अपस्ट्रीम विलंब कितीही असला तरी). विलंबाबाबत संवेदनशील असलेल्या
क्लायंटनी (बेंचमार्किंग, p50/p99 निरीक्षण) `X-OmniRoute-Cache-Latency`
प्रतिसाद हेडर तपासावा:

| मूल्य         | अर्थ                                                            |
| ------------- | --------------------------------------------------------------- |
| `synthetic`   | प्रतिसाद कॅशमधून दिला आहे; विलंब हा वास्तविक अपस्ट्रीम वेळ नाही |
| _(अनुपस्थित)_ | वास्तविक अपस्ट्रीम कॉलमधून मिळालेला प्रतिसाद                    |

### प्रत्येक कीसाठी कॅश बायपास

API की `cacheDefaultMode` द्वारे सिमॅंटिक कॅश वाचनातून बाहेर पडण्याचा पर्याय निवडू शकतात:

| मूल्य    | वर्तन                                              |
| -------- | -------------------------------------------------- |
| `legacy` | सामान्य कॅश वर्तन (डीफॉल्ट)                        |
| `bypass` | कॅश लुकअप पूर्णपणे वगळा; नेहमी अपस्ट्रीमला कॉल करा |

की तयार करताना (`POST /api/keys`) सेट करा किंवा (`PATCH /api/keys/[id]`) अद्ययावत करा:

```json
{ "cacheDefaultMode": "bypass" }
```

की सेटिंग्ज काहीही असल्या तरी कोणतीही विनंती कॅशला बायपास करू शकते:

सिंक केलेल्या/आयात केलेल्या मॉडेल्ससाठी, `PUT /api/provider-models` हे `provider`, `modelId`, आणि
`maxOutputTokenOverride` स्वीकारते: धन पूर्णांक मॅन्युअल आउटपुट-टोकन मर्यादा निश्चित करतो आणि `null`
ही मर्यादा काढून डीफॉल्ट पुनर्स्थापित करते. `GET /api/provider-models?provider=<provider>` ही मूल्ये
`modelOutputOverrides` मध्ये परत करते, ज्यात कस्टम-मॉडेल ओळ नसलेली मॉडेल्सही समाविष्ट असतात. ओव्हरराइड
रनटाइम `max_output_tokens` क्षमता वापरते आणि मॉडेल पुन्हा सिंक केल्यानंतरही कायम राहते. OpenAI-सुसंगत
प्रोव्हायडर पृष्ठावर तीच संपादन/काढून टाकण्याची नियंत्रणे उपलब्ध असतात आणि स्पष्ट व्हिजन समर्थन असलेली मॉडेल्स चिन्हांकित केली जातात.

कस्टम Chat Completions नोड्स स्पष्ट रीझनिंग-वगळण्याचे पर्याय अपस्ट्रीम बॅकएंडशी जुळवून घेतात.
यशस्वी कनेक्शन चाचणी प्रत्येक अचूक मॉडेल ID साठी आपोआप चॅट-टेम्पलेट नियंत्रणे निवडते,
ज्याची `/models` नोंद मान्यताप्राप्त `owned_by` मूल्य सिद्ध करते: `vllm`, `sglang`, किंवा `llamacpp`.
पारदर्शक OpenAI-सुसंगत रॅपर्स मूळ मॉडेल नोंद नेस्टेड
`openai` ऑब्जेक्टमध्ये जतन करू शकतात; शोध जास्तीत जास्त अशा तीन आवरणांपर्यंत केला जातो. मालकी गहाळ, अज्ञात किंवा
परस्परविरोधी असलेली मॉडेल्स नेहमीचे OpenAI वर्तन कायम ठेवतात. शोध विद्यमान कॅटलॉग विनंतीचा पुनर्वापर करतो,
कोणतेही कम्प्लिशन टोकन निर्माण करत नाही आणि कनेक्शन एंडपॉइंट बदलल्यावर तो अवैध ठरतो.

हा मेटाडेटा उघड न करणाऱ्या बॅकएंडसाठी हे वर्तन निश्चित करण्यासाठी, विद्यमान आंशिक
प्रोव्हायडर अपडेट API वापरा:

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

तो मुख्य भाग `PUT /api/providers/<connection-id>` सह पाठवा. त्या कनेक्शनवर, `none` हा स्पष्ट
रीझनिंग प्रयत्न `chat_template_kwargs.thinking=false` आणि
`chat_template_kwargs.enable_thinking=false` म्हणून पाठवला जातो. सर्व्हर-साइड रीझनिंग नियमाने प्रयत्न सक्तीने लागू केला नसेल,
तर स्पष्ट नेटिव्ह टेम्पलेट मूल्ये अधिकृत राहतात. हे सेटिंग केवळ कस्टम
OpenAI-सुसंगत कनेक्शन Chat Completions मुख्य भाग पाठवते तेव्हाच लागू होते; Responses विनंत्या आणि सामान्य
प्रोव्हायडर्स त्यांची नेटिव्ह विनंती रचना कायम ठेवतात. सामान्य OpenAI
`reasoning_effort` पासथ्रू सक्तीने लागू करण्यासाठी `reasoningControl` हे `openai` वर सेट करा किंवा स्वयंचलित शोध वापरण्यासाठी ते वगळा/`null` वर सेट करा.

Claude Code ऑटो-मोड क्लासिफायर विनंत्यांमध्ये कोणतीही स्पष्ट रीझनिंग नियंत्रणे नसल्यास,
त्या डीफॉल्टनुसार नेटिव्ह थिंकिंग अक्षम करतात. शोधासाठी मॉडेलची नावे किंवा कम्प्लिशन मर्यादा नव्हे,
तर Claude-स्वरूपातील विनंत्यांमधील क्लासिफायरचे सिस्टीम मार्कर वापरले जाते. स्पष्ट मुख्य भाग नियंत्रणे, समर्थित प्रयत्न/थिंकिंग
हेडर्स, राउटिंग नियम आणि निर्धारित मॉडेल प्रयत्न यांचे विद्यमान प्राधान्य कायम राहते. क्लासिफायरचे दोन्ही
टप्पे त्यांचे प्रॉम्प्ट्स, कम्प्लिशन मर्यादा, स्टॉप सिक्वेन्सेस आणि वास्तविक अपस्ट्रीम परवानगीचे
निर्णय कायम ठेवतात; दुसरा टप्पा तरीही त्याने विनंती केलेले दृश्यमान रीझनिंग सामान्य मजकूर म्हणून निर्माण करू शकतो.

### आवृत्ती आणि रिलीझ चॅनेल

```bash
GET /api/system/version
```

केवळ लूपबॅकवर उपलब्ध असलेला व्यवस्थापन मार्ग (प्रशासक प्रमाणीकरण). सध्या चालू असलेली आवृत्ती, नवीनतम
प्रकाशित आवृत्ती आणि स्वयंचलित अद्यतनाची स्थिती परत करतो. `releaseChannel` आणि `channels` ही अतिरिक्त
फील्ड आहेत (रेल 3.8.54); `channel` चा अर्थ पूर्वीप्रमाणेच आहे — डॅशबोर्ड अद्यतनकर्ता वापरत असलेला
उपयोजन मोड (`npm`, `source` किंवा `docker-compose`).

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — चालू बिल्डचे npm चॅनेल: `-nightly.*` आवृत्त्यांसाठी `nightly`,
  इतर पूर्व-रिलीझसाठी (`-rc.*`, `-beta.*`, `-alpha.*`) `next`, `channels.latest` पेक्षा जुन्या प्रमुख
  आवृत्तीच्या स्थिर आवृत्तीसाठी `lts`, अन्यथा `latest`. हे नियम
  `scripts/release/dist-tag.mjs` प्रमाणेच आहेत, जे प्रकाशनाच्या वेळी npm dist-tag निवडते.
- `channels` — `npm view omniroute dist-tags` मधून प्रत्येक dist-tag ची नवीनतम प्रकाशित आवृत्ती (नोंदणी
  HTTP फॉलबॅकसह), `latest` प्रमाणेच 10-मिनिटांच्या TTL सह कॅश केली जाते. `latest` नेहमी उपलब्ध असते
  (आधी `latest` फील्ड आणि त्यानंतर `"unavailable"` हा फॉलबॅक वापरते); `next`, `nightly` आणि `lts` हे
  संबंधित dist-tag अस्तित्वात असेल तेव्हाच दिसतात. `Cache-Control: no-cache` विनंती दोन्ही शोध रीफ्रेश करते.

चॅनेल मॉडेल (`latest` = 4.0 GA पर्यंत v3, `next` = rc, `nightly` = `develop` बिल्ड,
`lts` = 4.0 GA नंतरचे v3 पॅच) `docs/ops/RELEASE_STRATEGY.md` मध्ये वर्णन केले आहे.

## ऑडिओ लिप्यंतरण

```bash
POST /v1/audio/transcriptions
Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

कॉन्फिगर केलेल्या कोणत्याही STT प्रदात्याचा वापर करून ऑडिओ फाइल्सचे लिप्यंतरण करा. पहिला पाथ
सेगमेंट मूळ प्रदाता निवडतो (`openai/…`, `deepgram/…`). दुसऱ्या विक्रेत्याचे मॉडेल
पुन्हा उपलब्ध करून देणारे गेटवे पात्र आयडी वापरतात
(`openrouter/deepgram/nova-3`).

**विनंती:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**प्रतिसाद:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**मॉडेल आयडींची उदाहरणे:** `openai/whisper-1` (OpenAI की आवश्यक आहे),
`openrouter/deepgram/nova-3` (OpenRouter की आवश्यक आहे),
`deepgram/nova-3` (मूळ Deepgram की आवश्यक आहे). साधी
`deepgram/nova-3` विनंती OpenRouter वापरत **नाही**.

**समर्थित स्वरूपे:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

जेव्हा एखादे इंटिग्रेशन `Authorization` हेडर समाविष्ट करू शकत नाही आणि API की बेस URL मध्ये एम्बेड करणे आवश्यक असते, तेव्हा ही उपनावे वापरा.

```bash
# OpenAI-शैलीतील चॅट उपनावे
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Ollama-शैलीतील उपनावे
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

```bash

curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

टीपा:

- टोकनयुक्त उपनावे `/v1/*` आणि `/api/tags` सारखेच हँडलर पुन्हा वापरतात; प्रतिसादांची रचना एकसारखी राहते.
- क्लायंट कस्टम हेडरना समर्थन देत असल्यास नेहमी `Authorization: Bearer ...` ला प्राधान्य द्या.
- URL-आधारित टोकन रिव्हर्स-प्रॉक्सी लॉग, ब्राउझर इतिहास आणि OmniRoute च्या बाहेरील टेलिमेट्रीमध्ये दिसू शकतात. त्यांना डीफॉल्ट प्रमाणीकरण पद्धत न मानता सुसंगततेचा पर्याय म्हणून वापरा.

```bash
# सर्व API कींसाठी बजेटची स्थिती मिळवा
GET /api/usage/budget

# बजेट सेट किंवा अपडेट करा
```

> **स्कीमा टीपा** (`setBudgetSchema`): `apiKeyId` आवश्यक आहे; `dailyLimitUsd`, `weeklyLimitUsd` किंवा `monthlyLimitUsd` यांपैकी किमान एकाचे मूल्य शून्यापेक्षा जास्त असणे आवश्यक आहे. पर्यायी फील्ड: `warningThreshold` (0–1), `resetInterval` (`daily` | `weekly` | `monthly`), `resetTime` (`HH:MM`). जुनी `{keyId, limit, period}` रचना `400 Bad Request` परत करते.

## टोकन मर्यादा

प्रत्येक API कीसाठी **टोकन** बजेट (वरील USD-आधारित बजेटपेक्षा वेगळे). विनंतीच्या मार्गावरच याची अंमलबजावणी केली जाते: एखाद्या कीचा सध्याच्या विंडोमधील वापर तिच्या मर्यादेपर्यंत पोहोचल्यावर, विनंत्या `429 Too Many Requests` सह नाकारल्या जातात. मर्यादा विशिष्ट `model`, `provider` यांच्यापुरत्या मर्यादित करता येतात किंवा संपूर्ण कीवर `global` पातळीवर लागू करता येतात; जेव्हा एका विनंतीशी अनेक मर्यादा जुळतात, तेव्हा सर्वांत प्रतिबंधात्मक मर्यादा लागू होते.

```bash
# कीच्या टोकन मर्यादांची सूची दाखवा (सध्याच्या विंडोचा प्रत्यक्ष वापर समाविष्ट)
GET /api/usage/token-limits?apiKeyId=key-123

# टोकन मर्यादा तयार करा किंवा अद्ययावत करा
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# id नुसार टोकन मर्यादा हटवा
DELETE /api/usage/token-limits?id=tl-abc
```

> **स्कीमा नोंदी** (`setTokenLimitSchema`): `apiKeyId` आणि `scopeType` (`model` | `provider` | `global`) आवश्यक आहेत. `scopeType` हे `global` नसल्यास `scopeValue` आवश्यक आहे (उदा. `model` व्याप्तीसाठी मॉडेल आयडी, `provider` व्याप्तीसाठी प्रदाता आयडी). `tokenLimit` हा धन पूर्णांक असणे आवश्यक आहे (स्ट्रिंगमधून रूपांतरित केला जातो). पर्यायी: `id` (तयार करण्यासाठी वगळा, अद्ययावत करण्यासाठी द्या), `resetInterval` (`daily` | `weekly` | `monthly`, डीफॉल्ट `monthly`), `resetTime` (`HH:MM`), `enabled` (डीफॉल्ट `true`). `GET` प्रतिसादांमध्ये प्रत्येक मर्यादेसोबत `tokensUsed`, `remaining`, `windowStart`, `periodStartAt`, आणि `nextResetAt` ही अतिरिक्त माहिती दिली जाते. हा व्यवस्थापन-श्रेणीतील एंडपॉइंट आहे (authz पाइपलाइनद्वारे प्रमाणीकरणाची अंमलबजावणी मध्यवर्ती पद्धतीने केली जाते).

## विनंती प्रक्रिया

1. क्लायंट `/v1/*` वर विनंती पाठवतो
2. रूट हँडलर `handleChat`, `handleEmbedding`, `handleAudioTranscription`, किंवा `handleImageGeneration` कॉल करतो
3. मॉडेलचे निराकरण केले जाते (थेट प्रदाता/मॉडेल किंवा उपनाव/कॉम्बो)
4. खात्याची उपलब्धता फिल्टर करून स्थानिक DB मधून क्रेडेन्शियल्स निवडली जातात
5. चॅटसाठी: `handleChatCore` सिमॅंटिक/सिग्नेचर कॅश तपासतो आणि कॉम्बो कॉम्प्रेशन सेटिंग्जचे निराकरण करतो
6. सक्षम केलेले असताना प्रदाता भाषांतरापूर्वी प्रोॲक्टिव्ह कॉम्प्रेशन चालते (`lite`, Caveman, RTK, किंवा स्टॅक केलेले)
7. प्रदाता एक्झिक्युटर अपस्ट्रीम विनंती पाठवतो
8. प्रतिसादाचे पुन्हा क्लायंट स्वरूपात भाषांतर केले जाते (चॅट) किंवा तो जशाचा तसा परत केला जातो (एम्बेडिंग्ज/इमेजेस/ऑडिओ)
9. वापर, कॉम्प्रेशन विश्लेषण आणि विनंती लॉग नोंदवले जातात
10. त्रुटी आल्यास कॉम्बो नियमांनुसार फॉलबॅक लागू केला जातो

संपूर्ण आर्किटेक्चर संदर्भ: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## व्यवस्थापन प्रॉक्सी

प्रोव्हायडर्स, खाती किंवा जागतिक स्तरावर नियुक्त करता येणारे आउटबाउंड HTTP(S)/SOCKS प्रॉक्सी.

| पद्धत  | पाथ                                          | वर्णन                                                                                                                                                         |
| ------ | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/management/proxies`                 | प्रॉक्सींची सूची (`?id=` सह एक प्रॉक्सी परत करते; `?id=&where_used=1` सह असाइनमेंट ग्राफ परत करते)                                                            |

| PATCH  | `/api/v1/management/proxies`                 | प्रॉक्सी अपडेट करा — बॉडीचे प्रमाणीकरण `updateProxyRegistrySchema` द्वारे केले जाते (`id` आवश्यक)                                                             |
| DELETE | `/api/v1/management/proxies?id=...&force=1`  | प्रॉक्सी हटवा (असाइनमेंट विलग करण्यासाठी `force=1` वापरा)                                                                                                     |
| GET    | `/api/v1/management/proxies/assignments`     | असाइनमेंटची सूची — `proxy_id`, `scope`, `scope_id` नुसार फिल्टर करता येते; कनेक्शनसाठी सक्रिय प्रॉक्सी रिझॉल्व्ह करण्यासाठी `resolve_connection_id=<id>` द्या |
| PUT    | `/api/v1/management/proxies/assignments`     | नियुक्त करा — बॉडीचे प्रमाणीकरण `proxyAssignmentSchema` द्वारे केले जाते (`{scope, scopeId?, proxyId?}`). डिस्पॅचर कॅशे साफ करते                              |
| PUT    | `/api/v1/management/proxies/bulk-assign`     | मोठ्या प्रमाणात नियुक्त करा — बॉडीचे प्रमाणीकरण `bulkProxyAssignmentSchema` द्वारे केले जाते (`{scope, scopeIds[], proxyId?}`)                                |
| GET    | `/api/v1/management/proxies/health?hours=24` | कालावधीतील एकत्रित प्रॉक्सी आरोग्य (यश/अपयश संख्या, विलंब)                                                                                                    |

**प्रमाणीकरण:** प्रत्येक रूटवर व्यवस्थापन सत्र/API की आवश्यक आहे (`requireManagementAuth`).

> कार्य वर्णनातील `POST /api/v1/management/proxies/[id]/assignments` आणि `POST /api/v1/management/proxies/[id]/health` वरील सपाट `/assignments` आणि `/health` रूटद्वारे हाताळले जातात — कोडबेसमध्ये प्रत्येक id साठी स्वतंत्र सबरूट नाहीत.

## लवचिकता (विस्तारित)

OmniRoute तात्पुरत्या अपयशांसाठी तीन स्वतंत्र यंत्रणा उपलब्ध करून देते; खालील व्यवस्थापन एंडपॉइंट ऑपरेटरना त्या वाचण्याची आणि अधिलिखित करण्याची सुविधा देतात:

| व्याप्ती        | स्थिती संचयन                           | वाचन                                      | रीसेट / साफ करणे                                              |
| --------------- | -------------------------------------- | ----------------------------------------- | ------------------------------------------------------------- |
| प्रदाता ब्रेकर  | `domain_circuit_breakers` + इन-मेमरी   | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                  |
| कनेक्शन कूलडाउन | प्रदाता कनेक्शनवरील `rateLimitedUntil` | `/api/rate-limits`, `/api/providers/[id]` | (आवश्यकतेनुसार पुन्हा सक्षम होते; प्रदाता PUT द्वारे साफ करा) |
| मॉडेल लॉकआउट    | इन-मेमरी मॉडेल-उपलब्धता रजिस्ट्री      | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                      |

`PATCH /api/resilience`, `providerBreaker.oauth` आणि `providerBreaker.apikey` अंतर्गत प्रदाता ब्रेकर अधिलिखने स्वीकारते. प्रत्येक प्रोफाइल `degradationThreshold`, `failureThreshold`, आणि `resetTimeoutMs` यांना समर्थन देते; हीच फील्ड Dashboard → Settings → Resilience मध्ये उपलब्ध आहेत.

```bash
# एकाच मॉडेलचा लॉकआउट साफ करा
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# सर्व लॉकआउट हटवा
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

संपूर्ण संकल्पनात्मक संदर्भ आणि ब्रेकरची डीफॉल्ट मूल्ये: [`CLAUDE.md`](../../CLAUDE.md) → "लवचिकता रनटाइम स्थिती" आणि [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) पहा.

### दर-मर्यादा रांग आणि स्वयं-सक्षम सुरक्षा जाळे

- **समर्थित लेखन मार्ग**: कनेक्शनसाठी दर-मर्यादा संरक्षण टॉगल करण्याकरिता `{"connectionId": "<id>", "enabled": true|false}` बॉडीसह `POST /api/rate-limits` हा समर्थित व्यवस्थापन एंडपॉइंट आहे. `PUT /api/providers/[id]` जाणूनबुजून `rateLimitProtection` मध्ये बदल किंवा उलटफेर करत नाही (#11278).
- **`enabled: false` चे अर्थविज्ञान**: `enabled: false` सेट केल्याने कनेक्शनसाठी स्पष्ट संरक्षण काढून टाकले जाते, परंतु त्यामुळे सक्रिय API-की कनेक्शन जागतिक स्वयं-सक्षम सुरक्षा जाळ्यातून (`autoEnableApiKeyProviders = true`) बाहेर पडत **नाही**. `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) मध्ये, `false` आणि `undefined` समतुल्य आहेत; स्पष्ट संरक्षण नसलेली सक्रिय API-की कनेक्शन स्वयं-सक्षम सुरक्षा जाळ्याअंतर्गत संरक्षित राहतात.
- **जागतिक अक्षमकरण**: दर-मर्यादा रांगांशिवाय API-की कनेक्शन चालवण्यासाठी, `RATE_LIMIT_AUTO_ENABLE=false` (env) किंवा `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`) द्वारे सुरक्षा जाळे जागतिक स्तरावर अक्षम करा.

## MCP सर्व्हर

OmniRoute मध्ये 3 ट्रान्सपोर्टसह (stdio, SSE, streamable-http) आणि व्याप्तीनुसार मर्यादित साधनांसह एक अंगभूत मॉडेल कॉन्टेक्स्ट प्रोटोकॉल सर्व्हर समाविष्ट आहे. खालील डॅशबोर्ड एंडपॉइंट्स स्थिती/ऑडिट डेटा वाचतात आणि HTTP ट्रान्सपोर्ट्सना प्रॉक्सी करतात.

| पद्धत | पथ | वर्णन |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | हार्टबीट, ट्रान्सपोर्ट, ऑनलाइन स्थिती, शेवटचा कॉल, सर्वाधिक वापरलेली साधने, 24 तासांचा यशाचा दर |
| GET | `/api/mcp/tools` | `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` यांसह MCP साधनांची सूची |
| GET | `/api/mcp/sse` | SSE ट्रान्सपोर्टसाठी SSE प्रवाह उघडा (MCP अक्षम असल्यास किंवा ट्रान्सपोर्ट जुळत नसल्यास `503` परत करतो) |
| POST | `/api/mcp/sse` | SSE ट्रान्सपोर्टवर JSON-RPC फ्रेम पाठवा |
| GET | `/api/mcp/stream` | Streamable HTTP ट्रान्सपोर्टची SSE बाजू उघडा (सर्व्हरकडून सुरू केलेले संदेश) |
| POST | `/api/mcp/stream` | Streamable HTTP ट्रान्सपोर्टवर JSON-RPC फ्रेम पाठवा |
| DELETE | `/api/mcp/stream` | Streamable HTTP सत्र समाप्त करा |
| GET | `/api/mcp/audit` | ऑडिट लॉगची क्वेरी करा — `?limit=`, `?offset=`, `?tool=`, `?success=true                                | false`, `?apiKeyId=` |
| GET | `/api/mcp/audit/stats` | एकत्रित ऑडिट आकडेवारी (एकूण संख्या, यशाचा दर, सरासरी कालावधी, सर्वाधिक वापरलेली साधने) |

**प्रमाणीकरण:** `sse`/`stream` ट्रान्सपोर्ट्स MCP-विशिष्ट प्रमाणीकरण पृष्ठभागाचा वापर करतात (`mcp` व्याप्ती असलेली Bearer API की); `status`/`tools`/`audit*` मार्ग डॅशबोर्डवरून वाचता येतात (डॅशबोर्ड होस्टपर्यंत पोहोचण्याव्यतिरिक्त कोणतेही अतिरिक्त प्रमाणीकरण आवश्यक नाही).

> दोन्ही HTTP ट्रान्सपोर्ट्स `settings.mcpEnabled` आणि `settings.mcpTransport` द्वारे नियंत्रित केले जातात — ट्रान्सपोर्ट जुळत नसल्यास `400`, तर MCP अक्षम असल्यास `503` परत केले जाते.

## A2A सर्व्हर

OmniRoute तपासणी/डॅशबोर्ड वापरासाठी REST रॅपरसह A2A (एजंट-टू-एजंट) JSON-RPC 2.0 एंडपॉइंट उपलब्ध करून देते.

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # OMNIROUTE_API_KEY सेट केलेले नसल्यास पर्यायी
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

समर्थित पद्धती (सर्व `settings.a2aEnabled` द्वारे नियंत्रित):

| पद्धत            | वर्णन                                                             |
| ---------------- | ----------------------------------------------------------------- |
| `message/send`   | समकालिक कौशल्य अंमलबजावणी; `{task, artifacts, metadata}` परत करते |
| `message/stream` | त्याच कौशल्य संचाची स्ट्रीमिंग SSE अंमलबजावणी                     |
| `tasks/get`      | `taskId` द्वारे कार्य मिळवा                                       |
| `tasks/cancel`   | `taskId` द्वारे कार्य रद्द करा                                    |

अंगभूत कौशल्ये: `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`.

### एजंट कार्ड

```bash
GET /.well-known/agent.json
```

सार्वजनिक A2A एजंट कार्ड (नाव, वर्णन, क्षमता, कौशल्य कॅटलॉग, प्रमाणीकरण योजना) परत करते — सार्वजनिकरीत्या 1 तासासाठी कॅश केले जाते. प्रमाणीकरण आवश्यक नाही.

### REST सहाय्यक

| पद्धत | पथ                           | वर्णन                                                                                                               |
| ----- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| GET   | `/api/a2a/status`            | A2A सक्षम स्थिती + कार्य आकडेवारी + कॅश केलेल्या एजंट कार्डचा सारांश                                                |
| GET   | `/api/a2a/tasks`             | कार्यांची सूची — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST  | `/api/a2a/tasks`             | (REST सहाय्यक म्हणून अंमलात आणलेले नाही — JSON-RPC `message/send` द्वारे तयार करा)                                  |
| GET   | `/api/a2a/tasks/[id]`        | एक कार्य मिळवा                                                                                                      |
| POST  | `/api/a2a/tasks/[id]/cancel` | कार्य रद्द करा                                                                                                      |

**प्रमाणीकरण:** REST सहाय्यक व्यवस्थापन प्रमाणीकरणाशिवाय चालतात (डॅशबोर्डवर वाचण्यायोग्य); कॉन्फिगर केले असल्यास JSON-RPC `/a2a` मार्ग Bearer `OMNIROUTE_API_KEY` वापरतो.

## प्रमाणीकरण

क्रेडेन्शियलच्या चार प्रकारांसाठी (डॅशबोर्ड सत्र, स्थानिक CLI टोकन, `oma_live_…` प्रवेश
टोकन, manage-व्याप्ती असलेली API की) आणि ते इन्फरन्स कींपेक्षा कसे वेगळे आहेत यासाठी
[व्यवस्थापन प्रमाणीकरण](../guides/MANAGEMENT-AUTH.md) पहा.

- डॅशबोर्ड मार्ग (`/dashboard/*`) `auth_token` कुकी वापरतात
- लॉगिन जतन केलेला पासवर्ड हॅश वापरते; पर्याय म्हणून `INITIAL_PASSWORD` वापरला जातो
- `requireLogin` हे `/api/settings/require-login` द्वारे बदलता येते
- `REQUIRE_API_KEY=true` असताना `/v1/*` मार्गांसाठी पर्यायाने Bearer API की आवश्यक असते
- या संदर्भातील "व्यवस्थापन टोकन" / "व्यवस्थापन-व्याप्ती असलेली API की" म्हणजे त्या मार्गदर्शिकेतील प्रकारांपैकी एक — अपरिभाषित अतिरिक्त गुप्त प्रकार नव्हे

> **ब्रेकिंग बदल (v3.8.0)** — `/api/v1/agents/tasks/*` आणि कूलडाउन व्यवस्थापन एंडपॉइंट्सना आता **व्यवस्थापन प्रमाणीकरण** (डॅशबोर्ड `auth_token` कुकी किंवा व्यवस्थापन-व्याप्ती असलेली API की) आवश्यक आहे. यापूर्वी प्रमाणीकरणाशिवाय या मार्गांना कॉल करणाऱ्या क्लायंट्सना `401 Unauthorized` मिळेल. कमिट `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`) पहा.
