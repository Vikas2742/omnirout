## Chat Completions

```bash
POST /v1/chat/completions
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "cc/claude-opus-4-6",
  "messages": [
    {"role": "user", "content": "Write a function to..."}
  ],
  "stream": true
}
```

### စိတ်ကြိုက် Header များ

| Header                   | ဦးတည်ချက် | ဖော်ပြချက်                                                                                                                                                                                                                                                                |
| ------------------------ | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-OmniRoute-No-Cache`   | Request   | Cache ကို ကျော်လွှားရန် `true` ဟု သတ်မှတ်ပါ                                                                                                                                                                                                                               |
| `x-omniroute-no-memory`  | Request   | ဤ request အတွက် memory + skills ထည့်သွင်းမှုကို ကျော်ရန် `true` ဟု သတ်မှတ်ပါ (no-cache ကို ထင်ဟပ်လုပ်ဆောင်ပြီး call တစ်ခုချင်းစီ၏ token/cost အပိုကုန်ကျမှုကို ရှောင်ရှားပေးသည်)                                                                                           |
| `X-OmniRoute-Progress`   | Request   | တိုးတက်မှု event များရရှိရန် `true` ဟု သတ်မှတ်ပါ                                                                                                                                                                                                                          |
| `X-Session-Id`           | Request   | ပြင်ပ session affinity အတွက် sticky session key                                                                                                                                                                                                                           |
| `x_session_id`           | Request   | Underscore မူကွဲကိုလည်း လက်ခံသည် (တိုက်ရိုက် HTTP)                                                                                                                                                                                                                        |
| `X-OmniRoute-Session-Id` | Request   | ခေါ်ဆိုသူက ပေးပို့သော session/conversation tag (memory သို့လည်း ထည့်သွင်းပေးသည်)။ ရှိနေပါက session တစ်ခုချင်းစီအလိုက် ကုန်ကျစရိတ်ခွဲဝေသတ်မှတ်ရန် `call_logs.session_tag` ထဲသို့ မူရင်းအတိုင်း သိမ်းဆည်းသည် (#8249) — မပါရှိပါက မည်သည့်အခါမျှ အလိုအလျောက်ဖန်တီးခြင်းမပြုပါ |
| `Idempotency-Key`        | Request   | ထပ်တူဖယ်ရှားရေး key (5s အချိန်ကာလ)                                                                                                                                                                                                                                        |
| `X-Request-Id`           | Request   | အခြားရွေးချယ်နိုင်သော ထပ်တူဖယ်ရှားရေး key                                                                                                                                                                                                                                 |
| `x-omniroute-connection` | Request   | Model တစ်ခုတည်းပါသော request ကို id အသုံးပြု၍ provider connection (account) တစ်ခုတွင် ချိတ်ထားပါ — [Request တစ်ခုချင်းစီအလိုက် account ချိတ်ထားခြင်း](#account-pinning-per-request) ကို ကြည့်ပါ                                                                           |
| `X-OmniRoute-Cache`      | Response  | `HIT` သို့မဟုတ် `MISS` (streaming မဟုတ်သောအခါ)                                                                                                                                                                                                                            |
| `X-OmniRoute-Idempotent` | Response  | ထပ်တူဖယ်ရှားထားပါက `true`                                                                                                                                                                                                                                                 |
| `X-OmniRoute-Progress`   | Response  | တိုးတက်မှုခြေရာခံခြင်း ဖွင့်ထားပါက `enabled`                                                                                                                                                                                                                              |
| `X-OmniRoute-Session-Id` | Response  | OmniRoute အသုံးပြုသည့် အကျိုးသက်ရောက်သော session ID                                                                                                                                                                                                                       |
| `X-OmniRoute-Request-Id` | Response  | Request ဆက်စပ်ဖော်ထုတ်ရန် id (သိရှိထားသည့်အခါ)                                                                                                                                                                                                                            |
| `X-OmniRoute-Version`    | Response  | OmniRoute build version (အမြဲပါဝင်သည်)                                                                                                                                                                                                                                    |
| `X-OmniRoute-Cost-Saved` | Response  | HIT ဖြစ်သည့်အခါ cache ကြောင့် သက်သာသွားသော USD ပမာဏ (cache hit များအတွက်သာ)                                                                                                                                                                                               |
| `X-OmniRoute-Decision`   | Response  | Routing trace: `strategy=<name>; provider=<alias>; latency_ms=<n>` (`<name>` သည် combo strategy ဖြစ်ပြီး combo မဟုတ်သော request အတွက် `single` ဖြစ်သည်) — ပြီးဆုံးမှု response များတွင် အမြဲပါဝင်သည်                                                                      |

> Nginx မှတ်ချက်- underscore ပါသော header များ (ဥပမာ `x_session_id`) ကို အသုံးပြုပါက `underscores_in_headers on;` ကို ဖွင့်ထားပါ။

#### Request တစ်ခုချင်းစီအလိုက် account ကို pin လုပ်ခြင်း

Provider တစ်ခုတွင် connection (account သို့မဟုတ် key) အများအပြားရှိသည့်အခါ OmniRoute သည် ပုံမှန်အားဖြင့် ၎င်း၏ account ရွေးချယ်မှုနည်းဗျူဟာမှတစ်ဆင့် တစ်ခုကို ရွေးချယ်သည်။ ထိုအစား request တစ်ခုသည် `x-omniroute-connection` header ဖြင့် သတ်မှတ်ထားသော connection တစ်ခုကို pin လုပ်နိုင်သည်-

```bash
curl http://localhost:20128/v1/chat/completions \
  -H "Authorization: Bearer <your OmniRoute API key>" \
  -H "Content-Type: application/json" \
  -H "x-omniroute-connection: <connection id>" \
  -d '{"model": "codex/gpt-5.5", "messages": [{"role": "user", "content": "hi"}]}'
```

- **id ကို ရှာဖွေရမည့်နေရာ။** Dashboard ရှိ provider စာမျက်နှာ
  (**Dashboard → Providers → <provider>**) ကို ဖွင့်ပြီး connection row တစ်ခုရှိ `xxxxxxxx…` id chip ကို နှိပ်ပါ
  — ၎င်းက connection id အပြည့်အစုံကို ကူးယူပေးသည်။
- **၎င်းကို လိုက်နာသည့် request များ။** `/v1/chat/completions`, `/v1/messages` နှင့်
  `/v1/responses` ရှိ single-model request များ (`provider/model`)။ Combo များသည် header ကို လျစ်လျူရှုသည်- ၎င်းအစား
  combo အဆင့်တစ်ခုချင်းစီအတွက် ထိုအဆင့်၏ကိုယ်ပိုင် connection မှတစ်ဆင့် account တစ်ခုကို pin လုပ်ပါ။
- **Pin သည် preference မဟုတ်ဘဲ တိကျစွာ လိုက်နာရမည့် သတ်မှတ်ချက်ဖြစ်သည်။** Pin လုပ်ထားသော connection တစ်ခုတည်းကိုသာ အသုံးပြုသည်။ Request အတွင်း
  ပျက်ကွက်မှုဖြစ်ပါက account ၏ cooldown ကို မှတ်တမ်းတင်သော်လည်း တူညီသော provider ရှိ
  အခြား account တစ်ခုသို့ **မ**ပြောင်းလဲပါ။
- **Cooldown နှင့် quota က pin ကို ဖြုတ်ပေးသည်။** Pin လုပ်ထားသော connection သည် cooldown ဖြစ်နေစဉ်၊
  quota ကုန်ဆုံးနေစဉ် သို့မဟုတ် quota policy ကြောင့် ပိတ်ဆို့ခံထားရစဉ် နောက်ပိုင်း request များသည် pin မလုပ်ထားသော traffic ကဲ့သို့ပင်
  provider ၏ အခြား connection များကို fallback လုပ်သည်။
- **မသိသော သို့မဟုတ် ပိတ်ထားသော id များသည် ပျက်ကွက်စေသည်။** Provider ၏ active pool ထဲတွင် မရှိသော id တစ်ခု (ဖျက်ထားသော၊
  ပိတ်ထားသော သို့မဟုတ် အခြား provider တစ်ခုနှင့် သက်ဆိုင်သော id) ကြောင့် အသုံးပြုနိုင်သည့် account မရှိတော့သဖြင့် request သည်
  အခြားနေရာသို့ တိတ်တဆိတ် route လုပ်မည့်အစား ပျက်ကွက်သည်။

Claude Code သည် custom header များကို `ANTHROPIC_CUSTOM_HEADERS` မှတစ်ဆင့် ပေးပို့သည်။ Project တစ်ခုချင်းစီအလိုက် မတူညီသော
account ကို pin လုပ်ရန် ၎င်းကို `~/.claude/settings.json` ၏ `env` block ထဲတွင် သို့မဟုတ် project-level `.claude/settings.json` ထဲတွင်
ထည့်ပါ-

```jsonc
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<your OmniRoute>:20128",
    "ANTHROPIC_AUTH_TOKEN": "<your OmniRoute API key>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-omniroute-connection: <connection id>",
  },
}
```

ရင်းမြစ်- `src/sse/handlers/chat.ts` (header ဖတ်ရှုမှု), `src/sse/services/auth.ts` နှင့်
`src/sse/services/sessionAffinityPin.ts` (pin ဖြုတ်မှုနှင့် pool ထဲတွင် မရှိကြောင်း စစ်ဆေးမှု)။

> **ကုန်ကျစရိတ် telemetry header များ:** streaming မဟုတ်သော အောင်မြင်သည့် response များတွင် `X-OmniRoute-*` ကုန်ကျစရိတ် telemetry အစုလည်း ပါဝင်သည် — `X-OmniRoute-Response-Cost` (USD၊ ဒဿမ 10 နေရာ ပုံသေဖြစ်ပြီး အခမဲ့/ဈေးနှုန်းမသတ်မှတ်ထားပါက `0.0000000000`), `X-OmniRoute-Tokens-In` / `X-OmniRoute-Tokens-Out`, `X-OmniRoute-Model`, `X-OmniRoute-Provider`, `X-OmniRoute-Latency-Ms`, `X-OmniRoute-Cache-Hit` နှင့် `X-OmniRoute-Fallback-Attempts` (> 0 ဖြစ်မှသာ) အပြင် `X-OmniRoute-Request-Id` နှင့် `X-OmniRoute-Version` တို့ဖြစ်သည်။ ၎င်းတို့ကို chat completion များ၊ `/v1/responses`, `/v1/messages` နှင့် **media endpoint များတွင်လည်း** ထုတ်ပေးသည် — `/v1/embeddings`, `/v1/images/generations`, `/v1/audio/speech`, `/v1/audio/transcriptions`, `/v1/rerank`, `/v1/videos/generations`, `/v1/music/generations` နှင့် `/v1/moderations` (ကုန်ကျစရိတ် အမြဲတမ်း `0`)။ ဈေးနှုန်းအချက်အလက် ရရှိနိုင်သည့်အခါ media ကုန်ကျစရိတ်ကို modality တစ်ခုချင်းစီအလိုက် (ပုံတစ်ပုံလျှင်၊ တစ်စက္ကန့်လျှင်၊ စာလုံးတစ်လုံးလျှင်၊ search-unit တစ်ခုလျှင်) တွက်ချက်ပြီး၊ မရရှိနိုင်ပါက `0` (fail-open) ဖြစ်သည်။

> **Cache-hit ကုန်ကျစရိတ်ဆိုင်ရာ သတ်မှတ်ချက်:** semantic-cache HIT (`X-OmniRoute-Cache-Hit: true`) ဖြစ်ပါက upstream call မပြုလုပ်သဖြင့် `X-OmniRoute-Response-Cost` သည် `0.0000000000` (hit ကို ဖြည့်ဆည်းပေးခြင်းအတွက် **ထပ်တိုး** ကုန်ကျစရိတ်) ဖြစ်သည်။ မူလ/ဖြစ်လာနိုင်ခဲ့သည့် ကုန်ကျစရိတ်ကို `X-OmniRoute-Cost-Saved` တွင် သီးခြားဖော်ပြသည်။ Billing အသုံးပြုသူများသည် `X-OmniRoute-Response-Cost` ကို စုစုပေါင်းတွက်ချက်သင့်သည် (hit များသည် ကုန်ကျစရိတ်မရှိပါ)။ Cache analytics များသည် `X-OmniRoute-Cost-Saved` ကို စုစည်းတွက်ချက်နိုင်သည်။

## သီးသန့် စီမံခန့်ခွဲထားသော Session Lease များ

သီးသန့် စီမံခန့်ခွဲထားသော session leasing သည် မိမိဆန္ဒအလျောက် အသုံးပြုနိုင်ပြီး client အမျိုးအစားနှင့် မသက်ဆိုင်သော routing သဘောတူညီချက်တစ်ခုဖြစ်သည်။ လက်ရှိအသက်ဝင်နေသော owner တစ်ဦးက သတ်မှတ်ချက်ပြည့်မီသော OmniRoute connection တစ်ခုကို ပိုင်ဆိုင်ထားသည်။ ၎င်းသည် model တစ်ခုကို lease မလုပ်သကဲ့သို့ OAuth မလိုအပ်ပါ၊ သီးခြား client တစ်ခုကိုလည်း ခွဲခြားသတ်မှတ်ခြင်းမပြုသကဲ့သို့ သီးခြား provider တစ်ခုကိုလည်း မလိုအပ်ပါ။

စစ်မှန်ကြောင်းအတည်ပြုရာတွင် အသုံးပြုသည့် API key တွင် `lease:exclusive` scope နှင့် တန်ဖိုးပါဝင်ကြောင်း အတိအလင်း သတ်မှတ်ထားသော `allowedConnections` list တစ်ခု ရှိရမည်။ Key ဖန်တီးခြင်းနှင့် တစ်စိတ်တစ်ပိုင်း update လုပ်ခြင်းများတွင် database mutation boundary က field နှစ်ခုစလုံးကို တွဲဖက်၍ မဖြစ်မနေ လိုက်နာစေသည်။

```http
POST /api/v1/session-leases
Authorization: Bearer <managed-api-key>
Content-Type: application/json
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>

{"action":"acquire","model":"glm/glm-4.6"}
```

အောင်မြင်သော acquire၊ renew နှင့် release response များတွင် timestamp များ၊ `state` နှင့် အတိအကျ အပေါင်းတန်ဖိုးဖြစ်သော `generation` ကို ဖော်ပြသော်လည်း ရွေးချယ်ထားသော connection သို့မဟုတ် credential များကို မည်သည့်အခါမျှ မဖော်ပြပါ။ Renew နှင့် release အတွက် generation ကို JSON body ထဲတွင် ထည့်သွင်းပေးရသည်။

```json
{ "action": "renew", "generation": 1 }
```

```json
{ "action": "release", "generation": 1, "reason": "OWNER_EXIT" }
```

အသက်ဝင်နေသော lease owner သည် ၎င်း၏ လက်ရှိ binding အတွက် privacy-safe display metadata ကို အတိအလင်း တောင်းဆိုနိုင်သည်။

```json
{ "action": "status", "generation": 1 }
```

```json
{
  "state": "ACTIVE",
  "generation": 1,
  "acquiredAt": "2026-08-28T12:00:00.000Z",
  "renewedAt": "2026-08-28T12:00:30.000Z",
  "expiresAt": "2026-08-28T12:02:30.000Z",
  "connection": {
    "displayName": "Primary Codex",
    "provider": "codex"
  }
}
```

ဤမိမိဆန္ဒအလျောက် status action ကို database transaction တစ်ခုတည်းအတွင်း opaque owner၊ စစ်မှန်ကြောင်းအတည်ပြုထားသော managed API key နှင့် အတိအကျ အသက်ဝင်နေသည့် generation တို့ဖြင့် ကန့်သတ်ကာကွယ်ထားသည်။ `displayName` သည် အစနှင့်အဆုံး whitespace များကို ဖယ်ရှားထားသော configured connection name သာဖြစ်ပြီး လုံခြုံစွာအသုံးပြုနိုင်သော configured name မရှိသည့်အခါ `null` ဖြစ်သည်။ OmniRoute သည် email သို့မဟုတ် အလိုအလျောက်ဖန်တီးထားသော account identity ကို မည်သည့်အခါမျှ အစားထိုးအသုံးမပြုပါ။ Provider တန်ဖိုးသည် အရေးမကြီးသော display label တစ်ခုဖြစ်ပြီး အလိုအလျောက်ဖန်တီးထားသော compatible-provider identifier မဟုတ်ပါ။ Credential များ၊ token များ၊ cookie များ၊ ပြုပြင်မွမ်းမံခြင်းမပြုထားသော connection သို့မဟုတ် API key id များ၊ owner hash များ၊ fencing secret များနှင့် အတွင်းပိုင်း routing data များကို ချန်လှပ်ထားသည်။

Key မှားခြင်း၊ owner မှားခြင်း၊ generation ဟောင်းနေခြင်း၊ မရှိခြင်း၊ သက်တမ်းကုန်ခြင်း၊ release လုပ်ထားခြင်းနှင့် invalidate လုပ်ထားခြင်းဆိုင်ရာ lookup များအားလုံးသည် connection metadata မပါဘဲ တူညီသော `409 LEASE_FENCE_STALE` error ကို ပြန်ပေးသည်။ Capacity-wait response ကို လက်ခံရရှိထားသော client တွင် စစ်ဆေးကြည့်ရှုနိုင်သည့် အသက်ဝင်နေသော binding မရှိပါ။ Routing က အသက်ဝင်နေသော lease တစ်ခုကို ပြောင်းလဲသည့်အခါ တူညီသော generation သည် ဆက်လက်အသုံးပြုနိုင်ပြီး status သည် binding အသစ်ကို atomically ပြန်ပေးကာ အဟောင်းကို မည်သည့်အခါမျှ ပြန်မပေးပါ။ Acquire၊ renew၊ release နှင့် waiting response များသည် ၎င်းတို့၏ ယခင်ပုံစံများကို ဆက်လက်ထိန်းသိမ်းထားသောကြောင့် ရှိပြီးသား client များမှာ ပြောင်းလဲမှုမရှိပါ။

ဤ server သဘောတူညီချက်သည် မူလ OpenAI Codex `/status` ကို မပြောင်းလဲပါ။ လက်ရှိ မူလ Codex သည် ၎င်း၏ model provider နှင့် built-in authentication/account state ကို ဖော်ပြသော်လည်း စိတ်ကြိုက် custom provider account metadata ကို မဖော်ပြပါ။ အနာဂတ် client integration တစ်ခုက ဤ action ကို ခေါ်ပြီး `connection.displayName` ကို မည်သို့ဖော်ပြရမည်ကို ဆုံးဖြတ်ရပါမည်။

ထို့နောက် managed inference request တစ်ခုစီသည် control header နှစ်ခုစလုံးကို ထည့်သွင်းပေးရသည်။

```http
X-OmniRoute-Lease-Owner: vlo_<43-base64url-characters>
X-OmniRoute-Lease-Generation: 1
```

အတိအကျ owner၊ generation၊ အသက်ဝင်နေသော connection နှင့် စစ်မှန်ကြောင်းအတည်ပြုထားသော API key တို့ကို ပံ့ပိုးထားသည့် upstream attempt တစ်ခုစီမတိုင်မီ ချက်ချင်း fencing လုပ်သည်။ တူညီသော connection ကို အခြား key က ခွင့်ပြုထားသည့်တိုင် owner နှင့် generation ကို ထို key ဖြင့် ပြန်လည်အသုံးပြုပါက မအောင်မြင်ပါ။ ပြုပြင်မွမ်းမံခြင်းမပြုထားသော owner များကို persist မလုပ်ပါ၊ log မမှတ်တမ်းတင်ပါ၊ request snapshot ထဲတွင် မထိန်းသိမ်းပါ၊ သို့မဟုတ် upstream သို့ မပို့ပါ။

ယာယီအရင်းအမြစ်ယှဉ်ပြိုင်မှုဖြစ်ပါက `Retry-After` နှင့်အတူ HTTP `429` ကို ပြန်ပေးပြီး အောက်ပါအတိုင်း ဖြစ်သည်။

```json
{
  "state": "WAITING_FOR_CAPACITY",
  "error": { "type": "lease_error", "code": "LEASE_CAPACITY_UNAVAILABLE" },
  "reason": "NO_FREE_ELIGIBLE_CONNECTION",
  "retryAfter": 30
}
```

ဤ response သည် ပုံမှန်သတ်မှတ်ချက်ပြည့်မီသော set တွင် အနည်းဆုံးတစ်ခု ပါဝင်ပြီး လွတ်နေသည့် candidate တိုင်းကို အခြားသူပိုင် အသက်ဝင်နေသော lease တစ်ခုက ထိန်းထားသည်ဟုသာ ဆိုလိုသည်။ ပံ့ပိုးမထားသော model/provider များ၊ policy မကိုက်ညီမှု၊ cooldown၊ quota၊ health နှင့် အခြားပုံမှန် eligibility failure များသည် ၎င်းတို့၏ ရှိပြီးသား OmniRoute response များကို ဆက်လက်ထိန်းသိမ်းထားသည်။

### `x-omniroute-compression`

Request တစ်ခုချင်းအလိုက် compression plan ကို override လုပ်ခြင်းဖြစ်သည်။ ဦးစားပေးမှု အမြင့်ဆုံးဖြစ်ပြီး routing-combo override၊ အသက်ဝင်နေသော profile၊ auto-trigger နှင့် panel Default တို့ထက် ဦးစားပေးသည်။ တန်ဖိုးများမှာ-

| တန်ဖိုး       | သက်ရောက်မှု                                                                                                                         |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `off`         | ဤ request အတွက် compression မပြုလုပ်ပါ။                                                                                             |
| `default`     | Panel မှ ဆင်းသက်လာသော Default profile ဖြစ်သည်၊ အသက်ဝင်နေသော profile ကို လျစ်လျူရှုသည်။ Lossy engine များကို ပိတ်ထားသည်။             |
| `safe`        | Dedup နှင့် whitespace folding ကိုသာ လုပ်ဆောင်သည်။                                                                                  |
| `allow-lossy` | Summary နှင့် style rewrite များအပါအဝင် ဤ request အတွက် operator plan ကို ဆက်လက်အသုံးပြုသည်။                                        |
| `engine:<id>` | Enable လုပ်ထားသည့်အခါ engine တစ်ခုတည်းကို အသုံးပြုသည်၊ ဥပမာ `engine:rtk`။ ထို engine အတွက် request တစ်ခုချင်းအလိုက် opt-in ဖြစ်သည်။ |
| `<combo>`     | အမည်ပေးထားသော combo တစ်ခုဖြစ်ပြီး ပထမဦးစွာ အမည်ဖြင့် စာလုံးအကြီးအသေးမခွဲဘဲ ကိုက်ညီစေကာ၊ ထို့နောက် id ဖြင့် ကိုက်ညီစေသည်။            |

မှတ်ချက်များ-

- မသိသောတန်ဖိုးများကို လျစ်လျူရှုသည်၊ request ကို မည်သည့်အခါမျှ ပယ်ချမည်မဟုတ်ပါ။ ဖြေရှင်းမှုသည် ပုံမှန် operator precedence သို့ ဆက်လက်ကျရောက်သွားသည်။
- Combo များစွာသည် အမည်တူနေပါက တစ်သမတ်တည်း ကိုက်ညီမှုရရှိရန် combo **id** ကို ပေးပို့ပါ။
- အမည်မှာ `off` သို့မဟုတ် `default` ဖြစ်သော combo ကို အမည်ဖြင့် ရွေးချယ်၍မရပါ။ အဆိုပါ keyword များကို ဦးစွာ အဓိပ္ပာယ်ဖော်သည်။ ထိုကဲ့သို့သော combo ကို ၎င်း၏ id ဖြင့် ရည်ညွှန်းပါ။
- Master compression switch သည် အပြီးသတ်ကန့်သတ်ချက်ဖြစ်သည်။ Compression ကို globally disable လုပ်ထားပါက ဤ header ဖြင့် enable လုပ်၍မရပါ။

အသုံးချထားသော plan ကို response header တွင် ပြန်လည်ဖော်ပြသည်။

```
X-OmniRoute-Compression: <mode>; source=<source>
```

ဤနေရာတွင် `<source>` သည် `request-header`၊ `routing-override`၊ `active-profile`၊ `auto-trigger`၊ `default` သို့မဟုတ် `off` တစ်ခုခုဖြစ်သည်။

## Embeddings

```bash
POST /v1/embeddings
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "nebius/Qwen/Qwen3-Embedding-8B",
  "input": "The food was delicious"
}
```

ရရှိနိုင်သော provider များ- Nebius, OpenAI, Mistral, Together AI, Fireworks, NVIDIA, **OpenRouter**, Jina AI။

Catalog id များသည် `provider/model` ပုံစံဖြစ်သည် (ဥပမာ- `jina-ai/jina-embeddings-v5-omni-small`)။ Registry တွင် ပါရှိသော prefix မပါသည့် Jina model id များ (ဥပမာ `jina-embeddings-v5-text-small`, `jina-reranker-v3.5`) ကိုလည်း ရှာဖွေဖြေရှင်းနိုင်သည်။ Jina embed/rerank/classify/segment သည် dashboard ရှိ `jina-ai` အထောက်အထားများကို ဦးစွာအသုံးပြုသည်။ Dashboard key မရှိမှသာ `JINA_AI_API_KEY` ကို အရန်အဖြစ် အသုံးပြုသည်။ `jina-reader` card သည် Reader / `r.jina.ai` အတွက်သာဖြစ်ပြီး (`POST /v1/web/fetch`) embeddings သို့မဟုတ် rerank ကို မည်သည့်အခါမျှ မပံ့ပိုးပါ။

Multimodal ပံ့ပိုးမှုရှိကြောင်း ဖော်ပြထားသည့် registry model များသည် provider နှင့်မသက်ဆိုင်သည့် structured
item ၃၂ ခုအထိကိုလည်း လက်ခံသည်။ Media item အမျိုးအစားများမှာ `text`, `image`, `audio`, `video` နှင့် `document` တို့ဖြစ်သည်။ ၎င်းတို့၏ media `source`
သည် `{"type":"url","url":"https://..."}` သို့မဟုတ်
`{"type":"base64","data":"...","media_type":"..."}` ဖြစ်သည်။

Jina v5 Omni (`jina-ai/jina-embeddings-v5-omni-small`, `jina-ai/jina-embeddings-v5-omni-nano`
နှင့် family alias ဖြစ်သော `jina-ai/jina-embeddings-v5-omni` → omni-small) သည် Jina ၏ မူရင်း
EmbeddingsV5Request doc များကိုလည်း လက်ခံပြီး ၎င်းတို့ကို `https://api.jina.ai/v1/embeddings` သို့ **မပြောင်းလဲဘဲ တိုက်ရိုက်ပို့ပေးသည်**-

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "task": "retrieval.query",
  "normalized": true,
  "input": [
    { "text": "a red bicycle" },
    { "image": "https://example.com/bike.png" },
    { "content": [{ "text": "caption" }, { "image": "data:image/png;base64,..." }] }
  ]
}
```

မူရင်း `{ image | audio | video | pdf }` value များသည် အများပြည်သူဝင်ရောက်နိုင်သော HTTPS URL၊ `data:` URI သို့မဟုတ် raw
base64 ဖြစ်နိုင်သည်။ OmniRoute သည် ထို object များကို string အဖြစ် မပြောင်းလဲသကဲ့သို့ မူရင်း image URL များကိုလည်း fetch မလုပ်ပါ — Jina က
အများပြည်သူဝင်ရောက်နိုင်သော media ကို ကိုယ်တိုင်ရယူသည်။ ထပ်ဆောင်း Jina field များ (`task`, `normalized`, `truncate`, `embedding_type`) ကို
တိုက်ရိုက်ပို့ပေးသည်။ Text-only Jina SKU များသည် text မဟုတ်သော doc များကို ဆက်လက်ငြင်းပယ်သည်။

လုံခြုံရေးနှင့် ပို့ဆောင်မှုဆိုင်ရာ ကန့်သတ်ချက်များ-

- Remote media URL များသည် အများပြည်သူဝင်ရောက်နိုင်သော HTTPS ဖြစ်ရမည်။ Canonical `{type,source:url}` item များကို
  server ဘက်တွင် fetch လုပ်ပြီး (redirect ကို ပြန်လည်စစ်ဆေးခြင်း၊ timeout၊ အရွယ်အစားကန့်သတ်ချက်များ၊ public DNS၊ connection pinning)
  provider ကို မခေါ်ဆိုမီ inline အဖြစ် ထည့်သွင်းသည်။ Jina မူရင်း `{image:"https://..."}` item များကို တူညီသော public-HTTPS စစ်ဆေးမှု ပြုလုပ်ပြီးနောက် မပြောင်းလဲဘဲ
  တိုက်ရိုက်ပို့သည်။ Jina က URL ကို fetch လုပ်သည်။
- Inline base64 media ကို item တစ်ခုလျှင် decode လုပ်ပြီး အရွယ်အစား 8 MiB နှင့် request တစ်ခုလုံးအတွက် decode လုပ်ပြီး အရွယ်အစား 16 MiB အထိ ကန့်သတ်ထားသည်။

Provider အလိုက် ပြောင်းလဲမှု (canonical item များကို မပြောင်းလဲဘဲ မည်သည့်အခါမျှ တိုက်ရိုက်မပို့ပါ)-

- Jina multimodal model များ- ထိပ်ဆုံးအဆင့် item တစ်ခုစီသည် modality-key ပါသော object တစ်ခု
  (`text` / `image` / `audio` / `video` / `pdf`) ဖြစ်လာပြီး inline media အတွက် data URI များကို အသုံးပြုသည်။ ထိပ်ဆုံးအဆင့် item
  တစ်ခုလျှင် vector တစ်ခု ထုတ်ပေးသည်။
- Gemini Embedding 2 family- ထိပ်ဆုံးအဆင့် array တစ်ခုကို `content.parts` (`text` သို့မဟုတ် `inline_data`) ပါဝင်သည့် မူရင်း
  `models/{model}:embedContent` request တစ်ခုအဖြစ် ပြောင်းလဲသည်။
- llama.cpp (`llama-cpp/<model>`၊ local server က load လုပ်ထားသော မည်သည့် model မဆို)- canonical `text` item များသည်
  ရိုးရိုး string များဖြစ်လာပြီး `image` / `audio` / `video` တစ်ခုစီသည်
  `{"content": [part]}` object တစ်ခု ဖြစ်လာသည်။ ၎င်းတွင် llama-server ၏ chat content part များ (`image_url`,
  format `wav` / `mp3` / `flac` ပါသော `input_audio`၊ `input_video`) ကို inline data နှင့်အတူ အသုံးပြုသည်။ ထိပ်ဆုံးအဆင့် item
  တစ်ခုလျှင် vector တစ်ခု ထုတ်ပေးသည်။ Server ကို `--embedding --mmproj …` ဖြင့် run ရမည်။ Projector မရှိပါက
  server ကိုယ်တိုင်က media ကို ငြင်းပယ်သည်။ `document` ကို မပံ့ပိုးပါ။
- တိကျသော modality metadata မရှိသည့် အမည်မသိ/dynamic model များသည် structured input ကို HTTP 400 ဖြင့် ငြင်းပယ်သည်။

```json
{
  "model": "jina-ai/jina-embeddings-v5-omni-small",
  "input": [
    { "type": "text", "text": "A red bicycle" },
    {
      "type": "image",
      "source": { "type": "url", "url": "https://example.com/bicycle.png" }
    }
  ],
  "dimensions": 512,
  "encoding_format": "float"
}
```

မပံ့ပိုးသော model/modality ပေါင်းစပ်မှုများသည် item ကို အတင်းအကျပ်ပြောင်းလဲမည့်အစား HTTP 400 ကို ပြန်ပေးသည်။ အစဉ်အလာ string/token request များရှိ input မဟုတ်သော
extension field များကို မပြောင်းလဲဘဲ ဆက်လက်ပို့ပေးသည်။

```bash
# Embedding model အားလုံးကို စာရင်းပြုစုရန်
GET /v1/embeddings
```

## ပုံထုတ်လုပ်ခြင်း

```bash
POST /v1/images/generations
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "openai/gpt-image-2",
  "prompt": "A beautiful sunset over mountains",
  "size": "1024x1024"
}
```

ရရှိနိုင်သော provider များတွင် OpenAI (GPT Image 2), xAI (Grok Image), Together AI (FLUX), Fireworks AI, Nebius (FLUX), Hyperbolic, NanoBanana, **OpenRouter**, **ZenMux**, SD WebUI (local), ComfyUI (local) တို့ ပါဝင်သည်။

`n` သည် `data[]` အတွင်း ပုံ `n` ပုံကို ပြန်ပေးသည်။ upstream API က call တစ်ကြိမ်လျှင် ပုံတစ်ပုံ ပြန်ပေးသည့် provider များ
(Black Forest Labs, Stability AI, Leonardo, Ideogram, Haiper, Hyperbolic, Magnific/Freepik,
NVIDIA NIM, Cloudflare Workers AI) အတွက် သီးခြား upstream call `n` ကြိမ် ပြုလုပ်ပြီး တစ်ပြိုင်နက် အများဆုံး 4 ကြိမ် လုပ်ဆောင်သည်။
ပုံသေ `seed` ကို call အညွှန်းအလိုက် (`seed`, `seed + 1`, …) တိုးပေးသဖြင့် ပုံများ ကွဲပြားသော်လည်း
ထပ်မံဖန်တီး၍ တူညီသောရလဒ် ရရှိနိုင်သည်။ `n` ကို အများဆုံး 10 အထိ ကန့်သတ်ထားသည်။ call တစ်ခုခု မအောင်မြင်ပါက request
တစ်ခုလုံး မအောင်မြင်ပါ။ fan-out format များ၏ စာရင်းမှာ
`open-sse/handlers/imageGeneration/fanOut.ts` ရှိ `SINGLE_IMAGE_FANOUT_FORMATS` ဖြစ်သည်။

ZenMux သည် ရှိပြီးသား API key connection ကို ပြန်လည်အသုံးပြုပြီး `zenmux/` သို့မဟုတ် `zm/` prefix များကို လက်ခံသည်-

- `zenmux/openai/gpt-image-2` သည် ZenMux ၏ OpenAI Images API ကို အသုံးပြုသည်။ Option များတွင် `size`,
  `quality`, `n`, `output_format`, `output_compression`, `background` နှင့် `response_format` တို့ ပါဝင်သည်။
- `zm/meta/muse-image-1.0` ကဲ့သို့သော အခြား publisher များသည် ZenMux ၏ Vertex AI `:predict`
  endpoint ကို အသုံးပြုသည်။ `n` ကို `sampleCount` သို့၊ `aspect_ratio` ကို `aspectRatio` သို့၊ `image_size`
  (`1K`, `2K`, `4K`) ကို `sampleImageSize` သို့ ချိတ်ဆက်ပေးသည်။ Pixel `size` သည် aspect ratio ကိုသာ သတ်မှတ်ပေးပြီး
  pixel အတိုင်းအတာများကို အာမခံမပေးပါ။ ပံ့ပိုးထားသော ratio များ၊ resolution များနှင့် အရေအတွက်များသည် model အလိုက် ကွဲပြားသည်။
- `zm/inclusionai/ming-image-0.1-design` သည် ၎င်း၏ အတိုင်းအတာများကို ကိုယ်တိုင်ရွေးချယ်သည်။ `size`,
  `aspect_ratio` နှင့် `image_size` တို့ကို ချန်လှပ်ပါ။ တန်ဖိုးများကို အတိအကျ ထည့်သွင်းပါက HTTP 400 ပြန်ပေးသည်။ PNG, JPEG နှင့် WebP
  တို့ကို `output_format` ဖြင့် တောင်းဆိုနိုင်သည်။

ဤ integration သည် စာသားမှပုံ ထုတ်လုပ်ခြင်းကို ပံ့ပိုးပြီး အကိုးအကားပုံ တည်းဖြတ်ခြင်းကို မပံ့ပိုးပါ။ Vertex
output ကို `data[].b64_json` အဖြစ် စံသတ်မှတ်ပြောင်းလဲပေးသည်။ `response_format: "url"` သည် upstream
HTTPS URL သို့မဟုတ် ပုံ byte များသာ ရရှိနိုင်သည့်အခါ base64 data URL ကို ပြန်ပေးသည်။ ဗလာဖြစ်သော သို့မဟုတ် စစ်ထုတ်ခံထားရသော output များအတွက်
အောင်မြင်သည့် ဗလာရလဒ်အစား error တစ်ခု ပြန်ပေးသည်။ Model အသုံးပြုခွင့်သည် ZenMux account ပေါ်တွင် မူတည်သည်။
[ZenMux ၏ Vertex API](https://docs.zenmux.ai/api/vertexai/generate-images) နှင့်
[OpenAI Images API](https://docs.zenmux.ai/api/openai/generate-an-image) တို့ကို ကြည့်ပါ။

```bash
# ပုံ model အားလုံးကို စာရင်းပြုစုရန်
GET /v1/images/generations
```

## စာရွက်စာတမ်း OCR

```bash
POST /v1/ocr
Authorization: Bearer your-api-key
Content-Type: application/json

{
  "model": "mistral/mistral-ocr-latest",
  "document": {
    "type": "document_url",
    "document_url": "https://example.com/invoice.pdf"
  }
}
```

`model` သည် `provider/model` prefix မှတစ်ဆင့် OCR provider ကို ရွေးချယ်သည်။ provider prefix မပါသော model id (ဥပမာ
`mistral-ocr-latest`) သည် ၎င်း၏ မှတ်ပုံတင်ထားသော provider သို့ ဖြေရှင်းသတ်မှတ်ပြီး `model` ကို ချန်လှပ်ထားပါက
မူလတန်ဖိုးအဖြစ် Mistral (`mistral-ocr-latest`) ကို အသုံးပြုသည်။ မှတ်ပုံတင်ထားသော provider များ (`open-sse/config/ocrRegistry.ts`)-

| Provider id                   | Model id             | `model` တန်ဖိုး                                                                      | မှတ်ချက်များ                                                                                                                             |
| ----------------------------- | -------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `mistral`                     | `mistral-ocr-latest` | `mistral/mistral-ocr-latest` (သို့မဟုတ် provider prefix မပါသော `mistral-ocr-latest`) | Synchronous — upstream call တစ်ကြိမ်တည်းမှ response ကို တိုက်ရိုက် ပြန်ပေးသည်။                                                           |
| `azure-document-intelligence` | `prebuilt-read`      | `azure-document-intelligence/prebuilt-read`                                          | Asynchronous upstream (`analyze` + poll) — အောက်တွင် ကြည့်ပါ။                                                                            |
| `vertex-deepseek-ocr`         | `deepseek-ocr-maas`  | `vertex-deepseek-ocr/deepseek-ocr-maas`                                              | Vertex AI ၏ `openapi/chat/completions` partner endpoint မှတစ်ဆင့် synchronous လုပ်ဆောင်သည် — authentication/URL အတွက် အောက်တွင် ကြည့်ပါ။ |

Provider သုံးခုလုံးသည် တူညီသော Mistral ပုံစံ body ဖြင့် တုံ့ပြန်သည်-

```json
{
  "pages": [{ "index": 0, "markdown": "# Extracted text..." }],
  "model": "mistral-ocr-latest",
  "usage_info": { "pages_processed": 1 }
}
```

### Azure Document Intelligence poll စီးဆင်းမှု

Azure Document Intelligence ၏ `analyze` API သည် asynchronous ဖြစ်သည်။ ကနဦး request သည် body အစား
`Operation-Location` header ကို ပြန်ပေးပြီး ရလဒ်ရရှိရန် poll ပြုလုပ်ရမည်။ Handler
(`open-sse/handlers/ocr.ts`) သည် ထို URL ကို တစ်စက္ကန့်လျှင်တစ်ကြိမ် အများဆုံး အကြိမ် 30 အထိ poll ပြုလုပ်သည်။ `ok` မဟုတ်သော poll response သို့မဟုတ် `"failed"` status ရရှိပါက ချက်ချင်း ရပ်တန့်ပြီး မအောင်မြင်ကြောင်း ပြန်ပေးကာ (ဆက်လက်
poll မပြုလုပ်ပါ) သတ်မှတ်ထားသော ကြိုးပမ်းမှုအရေအတွက် ကုန်ဆုံးပြီးနောက် operation က ဆက်လက်လုပ်ဆောင်နေသေးပါက `504` ကို ပြန်ပေးသည်။ နောက်ဆုံး Azure response ကို
ခေါ်ယူသူထံ ပြန်မပေးမီ Mistral အသုံးပြုသည့် တူညီသော `pages`/`markdown` ပုံစံသို့ စံသတ်မှတ်ပြောင်းလဲပေးသောကြောင့်
client code တွင် provider အလိုက် သီးခြားကိုင်တွယ်ရန် မလိုအပ်ပါ။

### Vertex AI DeepSeek OCR authentication နှင့် endpoint ဖြေရှင်းသတ်မှတ်ခြင်း

`vertex-deepseek-ocr` သည် chat/image traffic အတွက် OmniRoute က ပံ့ပိုးထားပြီးသား တူညီသော Vertex AI authentication
(`open-sse/executors/vertex.ts`) ကို ပြန်လည်အသုံးပြုသည်။ Connection ၏ API key သည် Service Account JSON credential
(JWT-bearer flow မှတစ်ဆင့် သက်တမ်းတို OAuth access token အဖြစ် လဲလှယ်သည်) သို့မဟုတ် ထုတ်ပေးပြီးသား OAuth access token
တစ်ခုဖြစ်ကာ မပြောင်းလဲဘဲ တိုက်ရိုက်အသုံးပြုသည်။ Upstream endpoint URL သည် connection ၏ project နှင့် region မှ
တည်ဆောက်ထားသော Vertex ၏ ယေဘုယျ `openapi/chat/completions` partner endpoint ဖြစ်သည်။ အတိအကျ သတ်မှတ်ထားသော
`providerSpecificData.project`/`providerSpecificData.region` ကို အမြဲ ဦးစားပေးသည်။
သို့မဟုတ်ပါက project ကို Service Account JSON ၏ `project_id` မှ ရယူပြီး region ၏
မူလတန်ဖိုးကို `us-central1` အဖြစ် သတ်မှတ်သည်။ ဖြေရှင်းသတ်မှတ်မှုနှစ်ခုလုံးကို `open-sse/handlers/ocr.ts`
(`resolveVertexOcrAccessToken`, `resolveVertexOcrBaseUrl`) တွင် လုပ်ဆောင်ပြီး
`handleOcr` သို့ ပေးပို့မလုပ်ဆောင်မီ `src/app/api/v1/ocr/route.ts` က အသုံးပြုသည်။

```bash
→ chat၊ embedding နှင့် image မော်ဒယ်များအားလုံး + combo များကို OpenAI ဖော်မတ်ဖြင့် ပြန်ပေးသည်
```

### မော်ဒယ် id ရှေ့ဆက်များ (`?prefix=`)

မော်ဒယ်အများစုကို **ပံ့ပိုးသူ ရှေ့ဆက်** အောက်တွင် ဖော်ပြထားသည်။ မည်သည့်ရှေ့ဆက်ကို ရရှိမည်ကို
`MODELS_CATALOG_PREFIX_MODE` feature flag က ထိန်းချုပ်ပြီး query parameter တစ်ခုဖြင့်
**request တစ်ခုချင်းစီအလိုက်** ပြန်လည်သတ်မှတ်နိုင်သည် — အခြားသူများအားလုံးအတွက် server-wide
ဆက်တင်ကို မပြောင်းလဲဘဲ ရှင်းလင်းသောစာရင်းကို လိုချင်သည့် client အတွက် အသုံးဝင်သည်-

```bash
GET /v1/models?prefix=alias        # မော်ဒယ်တစ်ခုလျှင် id တစ်ခု — alias ရှေ့ဆက်အတို
GET /v1/models?prefix=dual         # ပုံစံနှစ်မျိုးလုံး (server မူလသတ်မှတ်ချက်)
GET /v1/models?prefix=canonical    # provider-id ရှေ့ဆက်အပြည့်အစုံသာ
```

| မုဒ်        | ထုတ်ပေးသည့်အရာ                                              | မှတ်ချက်များ                                                                                                                                                                                                                              |
| ----------- | ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dual`      | `cc/claude-sonnet-4-6` **နှင့်** `claude/claude-sonnet-4-6` | **မူလသတ်မှတ်ချက်။** id နှစ်ခုစလုံးသည် မော်ဒယ်တစ်ခုတည်းသို့ route လုပ်သည်။ ပုံစံတစ်မျိုးမျိုးကို hardcode လုပ်ထားသည့် client config များ ဆက်လက်အလုပ်လုပ်စေရန် ထိန်းသိမ်းထားခြင်းဖြစ်သည်။ ကတ်တလောက်အရွယ်အစားကို အကြမ်းဖျင်း နှစ်ဆတိုးစေသည်။ |
| `alias`     | `cc/claude-sonnet-4-6`                                      | မော်ဒယ်တစ်ခုလျှင် entry တစ်ခု။ သီးခြား alias မရှိသည့် ပံ့ပိုးသူများသည်လည်း ၎င်းတို့၏ entry ကို ထုတ်ပေးသဖြင့် မည်သည့်အရာမျှ မဆုံးရှုံးပါ။                                                                                                  |
| `canonical` | `claude/claude-sonnet-4-6`                                  | provider-id ရှေ့ဆက်အပြည့်အစုံအောက်တွင် မော်ဒယ်တစ်ခုလျှင် entry တစ်ခု။ သီးခြား alias မရှိသည့် ပံ့ပိုးသူများ (ဥပမာ `antigravity/…`, `agy/…`) သည်လည်း ၎င်းတို့၏ တစ်ခုတည်းသော id ကို ဤနေရာတွင် ထုတ်ပေးသဖြင့် မည်သည့်အရာမျှ မဆုံးရှုံးပါ။      |

`dual` မုဒ် mirror တစ်ခုကို query parameter မပါဘဲလည်း ခွဲခြားသိရှိနိုင်သည်။ ၎င်းတွင် အဓိက id ကို
ညွှန်ပြနေသည့် `parent` field ပါရှိသည်။

မော်ဒယ်ရွေးချယ်ကိရိယာကို render လုပ်သော client များသည် `?prefix=alias` ကို request လုပ်သင့်သည် —
[OmniCopilot VS Code extension](../guides/VSCODE-COPILOT.md) ကလည်း ဤနည်းအတိုင်း လုပ်ဆောင်သည်။

### ရှာဖွေဖော်ထုတ်မှု filter များ (`?capability=`, `?min_context=`, `?kind=`, `?q=`)

`GET /v1/models` သည် ရွေးချယ်အသုံးပြုနိုင်သော ရှာဖွေဖော်ထုတ်မှု filter များကို လက်ခံသည်။ ၎င်းတို့တစ်ခုမျှ
မပါဝင်ပါက response သည် မပြောင်းလဲပါ။ ၎င်းတို့သည် ခေါ်ယူသူ မြင်တွေ့ပြီးဖြစ်သည့် ကတ်တလောက်ကို
ကျဉ်းမြောင်းစေသည် (API key ခွင့်ပြုချက်များကို ဦးစွာ သက်ရောက်စေသည်)။ ထို့ပြင် OpenAI ပုံစံ
`limit` / `after` paging မတိုင်မီ လုပ်ဆောင်သည်-

```bash
GET /v1/models?capability=vision&capability=tool_calling   # စာရင်းဝင် capability တိုင်းသည် true ဖြစ်ရမည်
GET /v1/models?capability=vision,reasoning&min_context=200000
GET /v1/models?kind=embedding                              # ကတ်တလောက် `type`; မပါဝင်သော row များသည် `chat` ဖြစ်သည်
GET /v1/models?q=sonnet&limit=10                           # id သို့မဟုတ် name တွင် စာလုံးအကြီးအသေးမခွဲခြားဘဲ ကိုက်ညီမှုရှာသည်
```

| Parameter     | တန်ဖိုးများ                                                                                         |
| ------------- | --------------------------------------------------------------------------------------------------- |
| `capability`  | `attachment`, `reasoning`, `structured_output`, `temperature`, `thinking`, `tool_calling`, `vision` |
| `min_context` | သုည သို့မဟုတ် အပေါင်းကိန်းပြည့်၊ `context_length` နှင့် နှိုင်းယှဉ်သည်                              |
| `kind`        | `chat`, `audio`, `embedding`, `image`, `moderation`, `music`, `rerank`, `video`                     |
| `q`           | စာလုံး 1–200 လုံး                                                                                   |

မသိသောတန်ဖိုးတစ်ခု သို့မဟုတ် သုည သို့မဟုတ် အပေါင်းကိန်းပြည့်မဟုတ်သည့် `min_context` တစ်ခု
(ဥပမာ `1.5`) သည် HTTP `400` ကို ပြန်ပေးပြီး message တွင် မှန်ကန်သောတန်ဖိုးများကို စာရင်းပြုစုထားသည်။
အကောင်အထည်ဖော်မှု- `src/app/api/v1/models/catalogFilters.ts`။

### မော်ဒယ်ဆန်ခါတင်စာရင်း (`POST /v1/models/query`)

`POST /v1/models/query` သည် `GET /v1/models` နှင့် တူညီသော ကတ်တလောက်မှ အတိုချုံးပြီး
ရလဒ်အမြဲတူညီသော စာရင်းတစ်ခုကို ပြန်ပေးသည်။ authentication နှင့် key တစ်ခုချင်းစီအလိုက်
မြင်နိုင်မှုလည်း တူညီသည်-

```bash
POST /v1/models/query
Authorization: Bearer your-api-key
Content-Type: application/json

{ "capabilities": ["vision", "tool_calling"], "min_context": 128000, "max_output": 16000,
  "kind": "chat", "q": "gpt", "owned_by": "openai", "exclude": ["openai/gpt-4o"], "limit": 5 }

→ { "object": "list", "data": [ ...models ] }
```

field တိုင်းသည် မဖြစ်မနေမဟုတ်ဘဲ ချန်လှပ်ထားနိုင်သည်။ `capabilities` နှင့် `exclude` သည် array
သို့မဟုတ် ကော်မာဖြင့် ခွဲထားသော string တစ်ခုကို လက်ခံသည်။ `max_output` ကို
`max_output_tokens` နှင့် နှိုင်းယှဉ်သည်။ ရလဒ်များကို ဦးစွာ `owned_by`၊ ထို့နောက် `id` အလိုက်
စီထားသည်။ `limit` ၏ မူလတန်ဖိုးမှာ `20` ဖြစ်ပြီး `100` ထက်ကျော်သော တန်ဖိုးများကို `100`
အထိ ကန့်သတ်သည်။ မမှန်ကန်သော JSON၊ မသိသော field သို့မဟုတ် မမှန်ကန်သောတန်ဖိုးသည် HTTP
`400` ကို ပြန်ပေးသည်။

### တစ်ခုချင်းစီ သီးခြားဖျောက်ထားသော chat မော်ဒယ်များ

၎င်း၏ ပံ့ပိုးသူစာမျက်နှာတွင် **ဖျောက်ထားသည်** ဟု သတ်မှတ်ထားသော မော်ဒယ်တစ်ခုကို ကတ်တလောက်မှ
ဖယ်ထုတ်ပြီး တိတိကျကျ request လုပ်သောအခါ HTTP `404` / `model_not_found` ဖြင့် ငြင်းပယ်သည်။
စစ်ဆေးမှုသည် ဖြေရှင်းသတ်မှတ်ပြီးသော ပံ့ပိုးသူနှင့် မော်ဒယ်ကို အသုံးပြုပြီး provider alias များ၊
compatible-provider node ရှေ့ဆက်များနှင့် connection မူလသတ်မှတ်ချက်များလည်း ပါဝင်သည်။
combo တစ်ခုသည် ဖျောက်ထားသော target များကို ကျော်ပြီး မြင်နိုင်သော sibling ကို အသုံးပြုနိုင်သည်။
လုပ်ဆောင်နိုင်သည့် target တစ်ခုမျှ မကျန်ရှိသောအခါ တူညီသည့် error code ကို ပြန်ပေးသည်။
ဖျောက်ထားမှုကို ပယ်ဖျက်ခြင်းသည် နောက် request မှစတင်၍ အကျိုးသက်ရောက်သည်။ image အတွက်သာ
သီးသန့်ဖြစ်သော မြင်နိုင်မှု override များသည် ID တူညီသော chat မော်ဒယ်ကို မဖျောက်ပါ။

ဤတစ်ဦးချင်း မော်ဒယ်ဆက်တင်သည် ကတ်တလောက်တွင် ဖော်ပြမှုနှင့် auto-routing candidate များကို
စစ်ထုတ်သော်လည်း တိတိကျကျ dispatch လုပ်ခြင်းကို ဆက်လက်ထိန်းသိမ်းထားသည့်
[မော်ဒယ်ဖော်ပြမှု allow/deny စာရင်းများ](../routing/MODEL_EXPOSURE_LIST.md) နှင့် သီးခြားဖြစ်သည်။
API key မော်ဒယ်ခွင့်ပြုချက်များသည်လည်း သီးခြားလွတ်လပ်စွာ ဆက်လက်သက်ရောက်သည်။ ကတ်တလောက်
ရှေ့ဆက်၏ မူလမုဒ်သည် `dual` အဖြစ် ဆက်လက်တည်ရှိသည်။

### Thinking မပါသော မော်ဒယ် variant များ

Thinking လုပ်နိုင်သည့် Claude မော်ဒယ်များအတွက် `/v1/models` သည် id ကို
`claude-3-omniroute-no-thinking/` ဖြင့် ရှေ့ဆက်ထားသော **thinking မပါသည့်** variant တစ်ခုကိုလည်း
ဖော်ပြသည်-

```
claude-3-omniroute-no-thinking/<provider>/<model>
```

ဤ id ကို ရွေးချယ်ခြင်းသည် (ဥပမာ `thinking` block ကို အမြဲတမ်း ထည့်သွင်းပေးသည့် Claude Code config တစ်ခုတွင်) reasoning ကို ပိတ်ထားပြီး မူရင်း `<provider>/<model>` သို့ ပြန်လည်ဖြေရှင်းပေးသည် — `/v1/messages` path တွင် `thinking:{type:"disabled"}` ကို အသုံးပြုခြင်း၊ သို့မဟုတ် `/v1/chat/completions` path တွင် `reasoning`/`reasoning_effort` fields များကို ဖယ်ရှားခြင်းဖြစ်သည်။ ဤ variant ကို thinking ပံ့ပိုးပေးပြီး `disabled` ကိုလည်း လက်ခံသည့် Claude-family models များအတွက်သာ စာရင်းပြုစုထားသည် (**ထို့ကြောင့်** ဥပမာ `disabled` ကို ငြင်းပယ်သည့် adaptive-only models များကို ချန်လှပ်ထားသည်)။ Operators များသည် model တစ်ခုချင်းစီအလိုက် `ModelSpec.noThinkingAlias` မှတစ်ဆင့် ဤ variant ကို မဖြစ်မနေ ဖွင့်ရန် သို့မဟုတ် ပိတ်ရန် သတ်မှတ်နိုင်သည်။

## Provider Plugin Manifest

```bash
GET /api/v1/provider-plugin-manifest
```

Bifrost၊ CLIProxyAPI နှင့် အနာဂတ် sidecar router များက အသုံးပြုသည့် JSON-safe provider plugin manifest ကို ပြန်ပေးသည်။ တုံ့ပြန်ချက်ကို TypeScript provider registry မှ ထုတ်လုပ်ထားပြီး OAuth client secret များ၊ runtime environment resolution၊ executor function များ၊ request header များနှင့် account data များကို ရည်ရွယ်ချက်ရှိရှိ ချန်လှပ်ထားသည်။

sidecar တစ်ခုသည် သီးခြား process အဖြစ် အလုပ်လုပ်ပြီး `open-sse/config/providerPluginManifestRegistry.ts` ကို တိုက်ရိုက် import မလုပ်နိုင်သည့်အခါ ဤ endpoint ကို အသုံးပြုပါ။

## ElevenLabs အသံထုတ်လုပ်ခြင်း

သင်၏ ElevenLabs API key ဖြင့် OmniRoute တွင် `elevenlabs` provider connection တစ်ခုကို ပြင်ဆင်သတ်မှတ်ပါ။ Client များသည် ၎င်းတို့၏ **OmniRoute** key (`Authorization: Bearer $OMNIROUTE_API_KEY`) ဖြင့် authenticate လုပ်ကြပြီး gateway က သိမ်းဆည်းထားသည့် provider key ကို `xi-api-key` အဖြစ် ထည့်သွင်းပေးသည်။ ElevenLabs key ကို gateway bearer token အဖြစ် လုံးဝ မပို့ပါနှင့်။

| နည်းလမ်း | လမ်းကြောင်း                 | တုံ့ပြန်ချက်                                  | API key endpoint အမျိုးအစား |
| -------- | --------------------------- | --------------------------------------------- | --------------------------- |
| POST     | `/v1/sound-generation`      | မူရင်း audio byte များ                        | `elevenlabs`                |
| POST     | `/v1/music`                 | မူရင်း audio byte များ                        | `music`                     |
| POST     | `/v1/music/stream`          | Streaming audio byte များ                     | `music`                     |
| POST     | `/v1/music/detailed`        | မူရင်း multipart audio နှင့် composition plan | `music`                     |
| POST     | `/v1/music/detailed/stream` | မူရင်း SSE metadata နှင့် audio chunk များ    | `music`                     |
| POST     | `/v1/music/plan`            | JSON composition plan                         | `music`                     |

ဤ endpoint များသည် လက်ရှိ `/v1/audio/speech`၊ `/v1/audio/transcriptions`၊
`/v1/voices`၊ `/v1/text-to-speech/{voiceId}` နှင့် `/v1/speech-to-text` route များကို ဖြည့်စွက်ပေးသည်။ `output_format` နှင့် `enable_logging` ကဲ့သို့သော မူရင်း JSON field များနှင့် query parameter များကို မပြောင်းလဲဘဲ ထိန်းသိမ်းထားသည်။
`/v1/music/detailed` တုံ့ပြန်ချက်များတွင် ၎င်းတို့၏ multipart boundary များကို ဆက်လက်ထိန်းသိမ်းထားသည်၊ ထို့ကြောင့် ၎င်းတို့ကို multipart အဖြစ် parse လုပ်ပါ။
`/v1/music/detailed/stream` သည် composition metadata နှင့် SSE event များအတွင်းရှိ base64 audio chunk များပါဝင်သော `text/event-stream` ကို ပြန်ပေးသည်။ Route ခြောက်ခုစလုံးသည် CORS preflight ကို ပံ့ပိုးသည်။

```bash
export OMNIROUTE_BASE_URL="http://localhost:20128"
export OMNIROUTE_API_KEY="your-omniroute-api-key"

# အသံအကျိုးသက်ရောက်မှုတိုတစ်ခု။ ကြာချိန်- 0.5 မှ 30 စက္ကန့်။
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/sound-generation?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"text":"A single soft bell chime","duration_seconds":1,"model_id":"eleven_text_to_sound_v2"}' \
  --output effect.mp3

# ဂီတကြာချိန်ကို millisecond ဖြင့် ဖော်ပြသည်- 3000 မှ 600000။
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music?output_format=mp3_44100_128" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"Gentle instrumental piano","music_length_ms":10000,"force_instrumental":true,"model_id":"music_v1"}' \
  --output music.mp3
```

audio ကို အပိုင်းလိုက် ပေးပို့ရန် တူညီသော JSON body ဖြင့် `/v1/music/stream` ကို အသုံးပြုပါ။ Composition သည် `prompt` သို့မဟုတ် `composition_plan` နှစ်ခုအနက် တစ်ခုတည်းကိုသာ လက်ခံသည်။ `/v1/music/plan` တွင် `prompt` လိုအပ်ပြီး `source_composition_plan` ကို ရွေးချယ်အသုံးပြုနိုင်သည်။ Composition-plan version များနှင့် fine-tuning option များ ElevenLabs သို့ ရောက်ရှိစေရန် မူရင်း schema များက ထပ်ဆောင်း provider field များကို ထိန်းသိမ်းထားသည်။

ပေါင်းစည်းထားသော `/v1/music/generations` endpoint သည် `elevenlabs/music_v1`၊
`elevenlabs/music_v2` နှင့် `elevenlabs/music_v2_5` တို့ကိုလည်း လက်ခံသည်။ အလုပ်လုပ်နေသော ElevenLabs connection တစ်ခုရှိပါက ဤ model များကို music catalog မှ ဖော်ပြပေးသည်။ ဤ endpoint သည် `{"created":...,"data":[{"b64_json":"...","format":"mp3"}]}` ကို ပြန်ပေးသည်။ ၎င်း၏ `duration` field သည် စက္ကန့်ယူနစ်ဖြစ်ပြီး `music_length_ms` သို့ ချိတ်ဆက်သတ်မှတ်သည်။ `music_length_ms` ကို အတိအလင်း သတ်မှတ်ထားပါက ၎င်းကို ဦးစားပေးသည်။
`instrumental` ကို `force_instrumental` သို့ ချိတ်ဆက်သတ်မှတ်ပြီး မူရင်း field ရှိပါက ၎င်းကို ဦးစားပေးသည်။
Streaming အတွက် မူရင်း streaming endpoint များကို အသုံးပြုပြီး composition plan တစ်ခုတည်းဖြင့် မောင်းနှင်သည့် request များအတွက် မူရင်း composition endpoint ကို အသုံးပြုပါ။

```bash
curl --fail-with-body "$OMNIROUTE_BASE_URL/v1/music/generations" \
  -H "Authorization: Bearer $OMNIROUTE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"elevenlabs/music_v1","prompt":"Gentle instrumental piano","duration":10,"instrumental":true}'
```

Upstream call မပြုလုပ်မီ endpoint၊ model၊ budget နှင့် connection ဆိုင်ရာ ကန့်သတ်ချက်များကို သက်ရောက်စေသည်။ မူရင်း route များသည် plan ကန့်သတ်ချက်အတွက် `402` နှင့် quota ကန့်သတ်ချက်အတွက် `429` အပါအဝင် upstream status code များနှင့် error body များကို မပြောင်းလဲဘဲ ပြန်ပေးသည်။ `character-cost`၊ `song-id`၊ `request-id` နှင့် `retry-after` header များရှိပါက ထိန်းသိမ်းထားသည်။ အခမဲ့ credit balance ရှိခြင်းသည် music model၊ output format သို့မဟုတ် API feature တိုင်းကို အသုံးပြုခွင့်ရမည်ဟု အာမမခံပါ။ Request တစ်ခုစီအတွက် အသုံးပြုခွင့်ကို ElevenLabs က ဆုံးဖြတ်သည်။
ပေါင်းစည်းထားသော endpoint သည် OmniRoute ၏ စံပြုပြင်ထားသည့် error envelope အတွင်း error status code များကို ထိန်းသိမ်းထားသည်။

Upstream contract များ- [အသံအကျိုးသက်ရောက်မှုများ](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert)၊
[ဂီတဖွဲ့စည်းခြင်း](https://elevenlabs.io/docs/api-reference/music/compose) နှင့်
[streaming ဂီတအသေးစိတ်များ](https://elevenlabs.io/docs/api-reference/music/compose-detailed-stream)။

| POST     | `/api/v1/vscode/{token}/chat/completions` | OpenAI token ပါသော alias                     |
| POST     | `/api/v1/vscode/{token}/responses`        | OpenAI Responses token ပါသော alias           |
| POST     | `/api/v1/vscode/{token}/api/chat`         | Ollama token ပါသော alias                     |
| GET      | `/api/v1/vscode/{token}/api/tags`         | Ollama tags token ပါသော alias                |

POST route အားလုံးသည် တူညီသောပုံစံကို လိုက်နာသည်- `Bearer your-api-key` + Zod ဖြင့် အတည်ပြုထားသော JSON body (`v1RerankSchema`, `v1ModerationSchema`, `v1AudioSpeechSchema` စသည်တို့၊ `src/shared/validation/schemas.ts` ကို ကြည့်ပါ)။ Schema အတည်ပြုမှု မအောင်မြင်ပါက 4xx ကို ပြန်ပေးသည်။

`Authorization: Bearer ...` ကို ပူးတွဲမပေးပို့နိုင်သော client များအတွက် OmniRoute သည် query-string လိုက်ဖက်ညီမှု (`?token=...`, `?apiKey=...`, `?api_key=...`, `?key=...`) သို့မဟုတ် အောက်တွင် မှတ်တမ်းတင်ထားသော သီးသန့် `/api/v1/vscode/{token}/...` endpoint များမှတစ်ဆင့် URL ထဲရှိ API key များကိုလည်း လက်ခံသည်။

```bash
# ပြန်လည်အဆင့်သတ်မှတ်ခြင်း (cloud registry provider သို့မဟုတ် "<prefix>/<model>" အဖြစ် OpenAI နှင့် လိုက်ဖက်ညီသော provider node)
POST /v1/rerank      { "model": "jina-ai/jina-reranker-v3.5", "query": "...", "documents": ["..."] }

# Jina အမျိုးအစားခွဲခြားခြင်း (Foundation API အထောက်အထားများ)
POST /v1/classify    { "model": "jina-embeddings-v5-text-small", "input": ["..."], "labels": ["a", "b"] }

# Jina segmenter
POST /v1/segment     { "content": "...", "return_chunks": true }

# Jina ရှာဖွေမှု (s.jina.ai; provider alias များ- jina-search, jina-ai, jina)
POST /v1/search      { "query": "...", "provider": "jina-search" }

# အကြောင်းအရာ စိစစ်ထိန်းချုပ်မှုများ
POST /v1/moderations { "model": "omni-moderation-latest", "input": "..." }

# TTS — audio/mpeg (သို့မဟုတ် တောင်းဆိုထားသော ဖော်မတ်) body ကို ပြန်ပေးသည်
POST /v1/audio/speech { "model": "openai/tts-1", "input": "Hello", "voice": "alloy" }

# Soniox TTS အတွက် ဘာသာစကားနှင့် အသံတစ်ခု လိုအပ်သည်- `language` သည် မူလအားဖြင့် "en" ဖြစ်သည်၊ မပါရှိသော
# အသံ သို့မဟုတ် OpenAI ၏ မူရင်းအသံအမည် (alloy, nova, …) သည် "Adrian" ဖြစ်လာမည်
POST /v1/audio/speech { "model": "soniox/tts-rt-v1", "input": "Xin chào", "voice": "Adrian", "language": "vi" }

# ပုံတည်းဖြတ်ခြင်း (multipart)
POST /v1/images/edits  -F image=@input.png -F prompt="..." -F mask=@mask.png

# ဗီဒီယို / တေးဂီတ ဖန်တီးခြင်း (provider prefix ပါသော model id)
POST /v1/videos/generations { "model": "runway/gen-3", "prompt": "..." }
POST /v1/music/generations  { "model": "kie/suno-v4.0",   "prompt": "..." }
```

> **Rerank provider node များ:** `POST /v1/rerank` သည် `<node-prefix>/<model>` အဖြစ် လိပ်စာသတ်မှတ်ထားသော OpenAI နှင့် တွဲဖက်အသုံးပြုနိုင်သည့် provider node များ
> (oMLX, vLLM, Infinity, gateway နောက်ကွယ်ရှိ TEI၊ …) သို့လည်း route လုပ်ပေးသည်။ Loopback
> node များ (`localhost`, `127.0.0.1`, `172.16.0.0/12`) ကို အမြဲအသုံးပြုနိုင်ပြီး၊ operator က
> `OMNIROUTE_LOCAL_PROVIDER_NODE_HOSTS` တွင် စာရင်းထည့်ထားသည့် hostname များလည်း အသုံးပြုနိုင်သည် (ဥပမာ
> `http://reranker:8080/v1` ကဲ့သို့ Docker/Compose service အမည်တစ်ခု၊ ၎င်းတို့ကို `HTTP(S)_PROXY` သို့မဟုတ်
> connection တစ်ခု၏ pinned proxy မှတစ်ဆင့် ဘယ်တော့မှမခေါ်ဘဲ တိုက်ရိုက်ခေါ်သည်)။ အခြား
> host ပေါ်ရှိ node များ — LAN စက်တစ်လုံး သို့မဟုတ် Tailscale peer တစ်ခု — ကို operator က
> `RERANK_REMOTE_PROVIDER_NODES` feature flag ကို ဖွင့်ထားပြီး node ၏ base URL သည် provider
> outbound URL policy (`OMNIROUTE_ALLOW_LOCAL_PROVIDER_URLS` / `OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS`) ကို ဖြတ်သန်းနိုင်မှသာ အသုံးပြုနိုင်သည်။
> memory engine ၏ rerank အဆင့်သည် ဤ route ကို
> loopback မှတစ်ဆင့် ခေါ်သောကြောင့် Memory settings ရှိ `rerankProviderModel` ကိုလည်း တူညီသောစည်းမျဉ်းဖြင့် ထိန်းချုပ်သည်။
>
> **Local server ပုံစံများ:** node ကို `<base>/v1/rerank` တွင် ခေါ်ပြီး 404 ဖြစ်ပါက `<base>/rerank`
> (Infinity, TEI) တွင် ခေါ်သည်။ Upstream body တွင် Cohere/OpenAI စာလုံးပေါင်း (`documents`,
> `return_documents`) နှင့် TEI စာလုံးပေါင်း (`texts`, `return_text`) နှစ်မျိုးလုံး ပါဝင်ပြီး upstream response ကို
> Cohere envelope ပုံစံသို့ စံကိုက်ပြောင်းပေးသည်။ TEI ၏ တိုက်ရိုက် `[{index, score, text}]`၊ ပါးလွှာသော gateway များမှ `{results: [{index, score}]}` နှင့်
> Voyage ပုံစံ `{data: [...]}` တို့အားလုံးကို client ထံ
> `{results: [{index, relevance_score, document?}]}` အဖြစ် ပြန်ပို့ပြီး၊ score အလိုက် စီကာ `top_n` အရေအတွက်အထိ ကန့်သတ်ထားသည်။

> **Provider-node ရှာဖွေဖော်ထုတ်မှု:** OpenAI နှင့် တွဲဖက်အသုံးပြုနိုင်သည့် provider node ပေါ်ရှိ model များသည် `GET /v1/models` တွင်
> node prefix အောက်၌ ပေါ်လာသည်။ Endpoint metadata မပါရှိသော row များ (local `/v1/models` စာရင်းများတွင် တွေ့ရလေ့ရှိသည်) သည်
> node ၏ `apiType` ကို ဆက်ခံသောကြောင့် `embeddings` node ၏ model များသည် `type: "embedding"` ဖြစ်ပြီး
> `rerank` node ၏ model များသည် chat အဖြစ် ပုံသေသတ်မှတ်ခံရမည့်အစား `type: "rerank"` ဖြစ်သည်။ Sync လုပ်ထားသော သို့မဟုတ် ကိုယ်တိုင်ထည့်ထားသော row တစ်ခုရှိ
> အတိအလင်းဖော်ပြထားသည့် `supportedEndpoints` သည် ဦးစားပေးအဖြစ် ဆက်လက်သက်ရောက်သည်။

### သီးသန့် Provider Route များ


## Files API

Batch အဝင်/အထွက်နှင့် ဖိုင်ရည်ရွယ်ချက်အလိုက် အပ်လုဒ်များအတွက် OpenAI နှင့် ကိုက်ညီသော ဖိုင် endpoint ဖြစ်သည်။

| နည်းလမ်း | လမ်းကြောင်း              | ဖော်ပြချက်                                                                                                                      |
| -------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| POST     | `/v1/files`              | ဖိုင်တစ်ခု အပ်လုဒ်လုပ်ရန် (multipart: `file`, `purpose`, `expires_after[anchor]`, `expires_after[seconds]`) — အများဆုံး 512 MiB |
| GET      | `/v1/files`              | အတည်ပြုထားသော API key အတွက် ဖိုင်များကို စာရင်းပြုစုရန်                                                                         |
| GET      | `/v1/files/[id]`         | ဖိုင်၏ metadata ကို ရယူရန်                                                                                                      |
| DELETE   | `/v1/files/[id]`         | ဖိုင်တစ်ခုကို ဖျက်ရန်                                                                                                           |
| GET      | `/v1/files/[id]/content` | မူရင်းဖိုင်အကြောင်းအရာကို stream လုပ်၍ ပြန်ပို့ရန်                                                                              |

**အထောက်အထားစိစစ်ခြင်း:** Bearer API key — ဖိုင်များကို `getApiKeyRequestScope` မှတစ်ဆင့် API key တစ်ခုချင်းစီအလိုက် နယ်ပယ်သတ်မှတ်ထားသည်။ Key တစ်ခုသည် ၎င်းကိုယ်ပိုင်ဖိုင်များကိုသာ ကြည့်ရှု၊ ဒေါင်းလုဒ်လုပ်ပြီး ဖျက်နိုင်သည်။ Key မပါသော dashboard session သည် instance တစ်ခုလုံးကို ဖတ်ရှုနိုင်သည်။ ပိုင်ရှင်မရှိသော ဖိုင် (အမည်မသိ သို့မဟုတ် dashboard-session အပ်လုဒ်) ကို session မဟုတ်သော ခေါ်ဆိုသူအားလုံးအတွက် ဝင်ရောက်ခွင့် ငြင်းပယ်သည်။ `GET /v1/files` သည် `REQUIRE_API_KEY=false` ဖြစ်နေသည့်တိုင် အမည်မသိခေါ်ဆိုသူနှင့် စိစစ်အတည်ပြု၍မရသော key ကို တင်ပြသည့် ခေါ်ဆိုသူကို tenant အားလုံး၏ဖိုင်များ စာရင်းပြုစုပေးမည့်အစား `401` ဖြင့် ငြင်းပယ်သည် (GHSA-m3hp-hq9g-fpmv, GHSA-2jm2-mpx8-6523)။

## Batches API

OpenAI နှင့် ကိုက်ညီသော batch လုပ်ဆောင်မှု ဖြစ်သည်။

| နည်းလမ်း | လမ်းကြောင်း               | ဖော်ပြချက်                                                                                                                   |
| -------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| POST     | `/v1/batches`             | Batch ဖန်တီးရန် — request body ကို `v1BatchCreateSchema` ဖြင့် အတည်ပြုသည် (`input_file_id`, `endpoint`, `completion_window`) |
| GET      | `/v1/batches`             | Batch များကို စာရင်းပြုစုရန်                                                                                                 |
| GET      | `/v1/batches/[id]`        | Batch အခြေအနေ + `request_counts` ကို ရယူရန်                                                                                  |
| DELETE   | `/v1/batches/[id]`        | ပြီးဆုံးသော/မအောင်မြင်သော batch ကို ဖျက်ရန်                                                                                  |
| POST     | `/v1/batches/[id]/cancel` | လုပ်ဆောင်ဆဲ batch ကို ပယ်ဖျက်ရန်                                                                                             |

**အထောက်အထားစိစစ်ခြင်း:** Bearer API key။ Batch များကို ဖိုင်များနှင့် တူညီသော သုံးမျိုးခွဲစည်းမျဉ်းအရ API key တစ်ခုချင်းစီအလိုက် နယ်ပယ်သတ်မှတ်ထားသည်။ ကိုယ်ပိုင် key ကိုသာ အသုံးပြုနိုင်ခြင်း၊ dashboard session ဖြင့် instance တစ်ခုလုံးကို အသုံးပြုနိုင်ခြင်းနှင့် ပိုင်ရှင်မရှိသော record များကို session မဟုတ်သည့် ခေါ်ဆိုသူအားလုံးအတွက် ငြင်းပယ်ခြင်းတို့ဖြစ်သည် (ရယူခြင်း၊ ဖျက်ခြင်း၊ ပယ်ဖျက်ခြင်းနှင့် ဖန်တီးရာတွင် `input_file_id` စစ်ဆေးခြင်း)။ `GET /v1/batches` သည် `REQUIRE_API_KEY=false` ဖြစ်နေသည့်တိုင် အမည်မသိခေါ်ဆိုသူကို `401` ဖြင့် ငြင်းပယ်သည်။

## ရှာဖွေရေး API

ဝဘ်/ရှာဖွေရေး ပံ့ပိုးသူများအတွက် abstraction (Tavily, Brave, Exa, Serper စသည်)။

| Method | Path                   | ဖော်ပြချက်                                                                                                           |
| ------ | ---------------------- | -------------------------------------------------------------------------------------------------------------------- |
| GET    | `/v1/search`           | ပြင်ဆင်သတ်မှတ်ထားသော ရှာဖွေရေးပံ့ပိုးသူများနှင့် လုပ်ဆောင်နိုင်စွမ်းများကို စာရင်းပြုစုရန်                           |
| POST   | `/v1/search`           | ရှာဖွေမှု query တစ်ခုကို လုပ်ဆောင်ရန် — body ကို `v1SearchSchema` ဖြင့် စစ်ဆေးပြီး caching/coalescing ကို ပံ့ပိုးသည် |
| GET    | `/v1/search/analytics` | ပံ့ပိုးသူတစ်ဦးချင်းစီအလိုက် hit/latency/cache ကိန်းဂဏန်းများ                                                         |

**အထောက်အထားစိစစ်ခြင်း:** Bearer API key (`extractApiKey` + `isValidApiKey`)။ ရှာဖွေမှုမူဝါဒကို `enforceApiKeyPolicy` မှတစ်ဆင့် ကျင့်သုံးသည်။

### Exa နှင့် Tavily `provider_options`

Exa နှင့် Tavily သည် ပံ့ပိုးသူအလိုက် သီးခြားသတ်မှတ်ထားသော field များကို namespace ပါဝင်သည့် bag မှ ဖတ်ရှုသည်-
`provider_options.exa` (သို့မဟုတ် `provider_options["exa-search"]`) နှင့် `provider_options.tavily`
(သို့မဟုတ် `provider_options["tavily-search"]`)။ အောက်ပါ key များကိုသာ ဆက်လက်ပေးပို့သည်။ တစ်ခုချင်းစီကို
`open-sse/handlers/search/providerOptionsPassthrough.ts` ရှိ သက်ဆိုင်ရာ Zod schema ဖြင့်
စစ်ဆေးပြီး type မှားယွင်းသည့် key ကို ဖယ်ရှားသည်။ auth၊ base URL၊
`stream` နှင့် `outputSchema` အပါအဝင် အခြားမည်သည့် key ကိုမဆို လျစ်လျူရှုသည်။ အခြားပံ့ပိုးသူများ အသုံးပြုသည့် flat key များ (`cx`, `depth`, ...) သည်
ယခင်အတိုင်း ဆက်လက်အလုပ်လုပ်သည်။

| ပံ့ပိုးသူ | ထိပ်တန်းအဆင့် field များ                                                                                                                                                                                                                                                                                                                                                  | အဆင့်ဆင့်ထည့်သွင်းထားသော field များ                                                                                                                                                 |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exa       | `type`, `category`, `userLocation`, `moderation`, `additionalQueries`, `objective`, `systemPrompt`, `compliance` (flat primitive များ), `startPublishedDate`, `endPublishedDate`                                                                                                                                                                                          | `contents.{text, highlights, summary, extras, subpages, subpageTarget, livecrawlTimeout, maxAgeHours}` ကို မူလသတ်မှတ်ချက် `{ text: true, highlights: true }` ပေါ်တွင် ပေါင်းစည်းသည် |
| Tavily    | `search_depth`, `chunks_per_source`, `time_range`, `start_date`, `end_date`, `include_published_date`, `filter_by_published_date`, `include_answer`, `include_raw_content`, `include_images`, `include_image_descriptions`, `include_favicon`, `include_domains_mode`, `language`, `filter_by_language`, `auto_parameters`, `exact_match`, `include_usage`, `safe_search` | —                                                                                                                                                                                   |

ယေဘုယျ field များဖြစ်သည့် `query`, `max_results`, `filters` (domain များ), `country` နှင့်
`search_type` မှ ဆင်းသက်လာသော topic တို့ကို အမြဲတမ်း ဦးစားပေးသည်။ Exa တွင် `search_type: "news"` သည် `category: "news"` ကို ဆက်လက်ထိန်းသိမ်းထားသည်။
Tavily သည် `search_type: "finance"` (`topic: "finance"`) ကိုလည်း လက်ခံသည်။

ယေဘုယျ `time_range` သည် ယခုအခါ ပံ့ပိုးသူနှစ်ခုလုံးသို့ ရောက်ရှိသည်- Exa သည် `startPublishedDate` (ISO
timestamp) ကို ရရှိပြီး Tavily သည် `start_date` (`YYYY-MM-DD`) ကို ရရှိသည်။ `provider_options` ထဲတွင် အတိအလင်းသတ်မှတ်ထားသော ရက်စွဲသည်
mapping လုပ်ထားသော ရက်စွဲကို အစားထိုးသည်။

Exa ရလဒ်များသည် `id`, `highlight_scores`, `summary`, `subpages`, `entities` နှင့် `extras` ကို
`provider_raw` ထဲတွင် ဆက်လက်ထိန်းသိမ်းထားသည်။ Tavily ရလဒ်များသည် `images` နှင့် `favicon` ကို ဆက်လက်ထိန်းသိမ်းထားသည်။

ကုန်ကျစရိတ်တွက်ချက်မှုသည် flat registry `costPerQuery` ကို ဆက်လက်အသုံးပြုသည်။ Tavily သည်
`search_depth: "advanced"` အတွက် ခေါ်ဆိုမှုတစ်ကြိမ်လျှင် credit ပိုမိုကောက်ခံပြီး ထိုကွာခြားချက်ကို
`usage.search_cost_usd` တွင် ထည့်သွင်းဖော်ပြထားခြင်းမရှိပါ။

## Web Fetch API

ပြင်ဆင်သတ်မှတ်ထားသော web-fetch provider (Firecrawl, Jina
Reader, Tavily Extract, TinyFish Fetch, Nimble Extract, Parallel Extract) မှတစ်ဆင့် URL တစ်ခုမှ အကြောင်းအရာကို ထုတ်ယူပါ။

Parallel Extract (`parallel-search`၊ Parallel Search နှင့် API key တူညီသည်) သည် Markdown
ကိုသာ ပြန်ပေးသည် — အခြားမည်သည့် `format` မဆို `400` ဖြစ်မည် — ထို့အပြင် အကြောင်းအရာကို စာလုံးရေ 100,000 အထိ ကန့်သတ်ထားသည်။ ပစ်မှတ်စာမျက်နှာကိုယ်တိုင်ကို
ထုတ်ယူ၍မရသောအခါ upstream သည် ၎င်းကို HTTP 200 အတွင်း သတင်းပို့ပြီး၊
OmniRoute က ၎င်းကို သတ်မှတ်ထားသော မက်ဆေ့ချ်နှင့်အတူ `422` အဖြစ် ဖော်ပြသည်။

| နည်းလမ်း | လမ်းကြောင်း     | ဖော်ပြချက်                                                               |
| -------- | --------------- | ------------------------------------------------------------------------ |
| POST     | `/v1/web/fetch` | URL တစ်ခုကို ရယူ/ခြစ်ယူသည် — body ကို `v1WebFetchSchema` ဖြင့် စစ်ဆေးသည် |

**အထောက်အထားစစ်ဆေးခြင်း:** Bearer API key (`extractApiKey` + `isValidApiKey`)။ မူဝါဒကို `enforceApiKeyPolicy` မှတစ်ဆင့် အတည်ပြုကျင့်သုံးသည်။

**Quota ကို ထည့်သွင်းစဉ်းစားသော fallback (#8297):** `provider` ကို တိတိကျကျ မပေးထားသည့်အခါ pool
(`firecrawl` → `jina-reader` → `tavily-search` → `tinyfish` → `nimble-search` →
`parallel-search`) ကို ပုံသေ
ဦးစားပေးအစီအစဉ် (fill-first) အတိုင်း
အစဉ်လိုက် စမ်းသပ်သည် — ပြင်ဆင်သတ်မှတ်ထားသော်လည်း rate limit ထိနေသော provider ကို request ကို ချက်ချင်းရပ်တန့်မည့်အစား ကျော်သွားပြီး၊ ပြန်လည်စမ်းသပ်နိုင်သော/quota ဆိုင်ရာ upstream ချို့ယွင်းမှု
(HTTP 429 သည် အမြဲတမ်း၊ Firecrawl/Tavily/TinyFish ၏ quota ပုံစံ free tier များအတွက် 402/403 —
Jina Reader အတွက် မဟုတ်သကဲ့သို့ သာမန် 400 bad request အတွက်လည်း လုံးဝမဟုတ်) ဖြစ်ပါက request လုပ်နေချိန်တွင်
အထောက်အထားပါရှိပြီး မစမ်းသပ်ရသေးသော နောက် provider သို့ ဆက်သွားသည်။ Pool အတွင်းရှိ provider အားလုံး
ကုန်ဆုံးသွားပါက endpoint သည် ယခင် ယေဘုယျ `400` အစား `429` တစ်ခုတည်းကို
(`Retry-After` header နှင့်အတူ) ပြန်ပေးသည်။ `provider` ကို တိတိကျကျ
တောင်းဆိုထားပါက အသံတိတ် fallback **မရှိပါ** — rate limit ထိနေသော သို့မဟုတ် ချို့ယွင်းနေသော တိတိကျကျသတ်မှတ်ထားသည့်
provider သည် ၎င်း၏ကိုယ်ပိုင် error ကို ဖော်ပြသည် (rate limit ထိနေပါက `429`၊ မဟုတ်ပါက upstream
status)။

## WebSocket Streaming

```bash
GET /v1/ws?handshake=1
```

WebSocket upgrade handshake တစ်ခုကို စစ်ဆေးပြီး wire protocol နမူနာမက်ဆေ့ချ်များ (`request`, `cancel`) ကို ပြန်ပေးသည်။ အမှန်တကယ် WS frame များကို Next.js route table ပြင်ပရှိ ပူးတွဲပါ WS server က ကိုင်တွယ်သည်။

**အထောက်အထားစစ်ဆေးခြင်း:** Handshake ပြုလုပ်စဉ် Bearer API key။

### WebSocket ပေါ်ရှိ Responses API (codex သီးသန့်)

```bash
# HTTP API နှင့် host:port တူညီသည် (မူလသတ်မှတ်ချက် 20128)၊ ချိတ်ဆက်မှုကို upgrade လုပ်ပါ:
wscat -c "ws://localhost:20128/v1/responses?api_key=<OMNIROUTE_API_KEY>"
# (သို့မဟုတ်: -H "Authorization: Bearer <OMNIROUTE_API_KEY>")

# ပထမ frame သည် response.create ဖြစ်ကိုဖြစ်ရမည်:
{ "type": "response.create", "model": "gpt-5.5", "input": [ { "role": "user", "content": "hi" } ] }
```

Responses-API-over-WebSocket proxy ကို **`codex` နှင့်သာ သီးသန့်ချိတ်ဆက်ထားသည်** (ChatGPT
backend)။ ၎င်းသည် API/dashboard နှင့် port တူညီသော `/v1/responses`,
`/responses` နှင့် `/api/v1/responses` လမ်းကြောင်းများတွင် နားထောင်သည်။ ပထမဆုံး `response.create` frame တွင်
၎င်းသည် အတွင်းပိုင်း `codex-responses-ws` bridge မှတစ်ဆင့် အထောက်အထားစစ်ဆေးခြင်း + ပြင်ဆင်ခြင်းကို လုပ်ဆောင်ပြီး၊
codex OAuth connection တစ်ခုကို ရွေးချယ်ကာ `wreq-js` transport မှတစ်ဆင့် `wss://chatgpt.com/backend-api/codex/responses`
သို့ tunnel လုပ်ပေးသည်။ **codex မဟုတ်သော model များကို ငြင်းပယ်သည်** (`codex_ws_provider_required`)။
Quota-share routing အတွက် `model: "qtSd/<group>/codex/<model>"` ကို အသုံးပြုပါ။ အကောင်အထည်ဖော်ထားသည့်နေရာများမှာ
`app/server-ws.mjs` + `scripts/dev/responses-ws-proxy.mjs` + `src/app/api/internal/codex-responses-ws/route.ts` ဖြစ်သည်။

**အထောက်အထားစစ်ဆေးခြင်း:** Handshake ပြုလုပ်စဉ် Bearer API key။ ပူးတွဲပါ HTTP server (`server-ws.mjs`)
သည် အသုံးပြုနေသော entrypoint ဖြစ်ရမည် (`app/server-ws.mjs` ရှိသည့်အခါ မူလသတ်မှတ်ချက်အရ ၎င်းပင်ဖြစ်သည်)။

#### Model id: ChatGPT id အစစ်ကို အသုံးပြုပါ (`codex/` prefix မပါရ)

OpenAI **Codex CLI** သည်
`supports_websockets = true` ဖြစ်သည့်အခါ client ဘက်တွင် model အမည်ကို စစ်ဆေးပြီး
`codex/gpt-5.5` ကဲ့သို့သော provider-prefix ပါသည့် id များကို **ငြင်းပယ်သည်**
(`The 'codex/gpt-5.5' model is not supported when using Codex with
a ChatGPT account`)။ **Prefix မပါသော** id ကို ပို့ပါ (ဥပမာ `gpt-5.5`)။ OmniRoute ၏ bridge သည်
codex သီးသန့်ဖြစ်သောကြောင့် upstream သို့ tunnel မလုပ်မီ prefix မပါသော id ကို codex model အဖြစ်
(`resolveCodexWsModelInfo`) ပြန်လည်သတ်မှတ်သည် — prefix မပါသော
`gpt-5.5` သည် ပုံမှန်အားဖြင့် HTTP မှတစ်ဆင့် အခြား provider တစ်ခုသို့ route လုပ်မည်ဖြစ်သော်လည်း ထိုသို့ ပြုလုပ်ခြင်းဖြစ်သည်။

#### OpenAI Codex CLI ကို ပြင်ဆင်သတ်မှတ်ခြင်း

WebSocket ပံ့ပိုးမှုပါသော custom provider တစ်ခုကို `~/.codex/config.toml` တွင် ထည့်ခြင်းဖြင့်
Codex CLI ကို OmniRoute သို့ ညွှန်ပါ (ရှိပြီးသား config ကို မထိခိုက်စေရန် သီးခြား `CODEX_HOME` ကို အသုံးပြုပါ)။

```toml
model = "gpt-5.5"                 # prefix မပါသော id — "codex/gpt-5.5" မဟုတ်ပါ
model_provider = "omniroute"

[model_providers.omniroute]
name = "OmniRoute (WS)"
base_url = "http://localhost:20128/v1"   # နောက်ဆုံး slash မပါရ၊ WS URL ကို ဆင်းသက်သတ်မှတ်သည် (production တွင် https/wss ကို အသုံးပြုပါ)
wire_api = "responses"                    # Feb 2026 မှစ၍ ပံ့ပိုးသည့် တစ်ခုတည်းသော value
supports_websockets = true                # Responses-over-WS transport ကို ဖွင့်ပေးသည်
env_key = "OMNIROUTE_API_KEY"             # OmniRoute API key (Bearer) ကို သိမ်းထားသည်
```

```bash
export OMNIROUTE_API_KEY=sk-...           # OmniRoute API key တစ်ခု (REQUIRE_API_KEY=false ဖြစ်ပါက မည်သည့် key မဆို)
codex exec "Responda apenas: PONG"
```

CLI သည် `base_url + /responses` ကို WebSocket သို့ upgrade လုပ်ပြီး OmniRoute က ၎င်းကို
ရွေးချယ်ထားသော codex OAuth connection သို့ tunnel လုပ်ပေးသည်။ Local
server နှင့် end-to-end စစ်ဆေးအတည်ပြုပြီးဖြစ်သည်။ ChatGPT က `codex.rate_limits` + `response.created` ကို ပြန်ပေးပြီး
completion ကို stream လုပ်သည်။

## ကိုယ်တိုင်ဝန်ဆောင်မှုရယူသုံးစွဲမှု (`/api/usage/om-usage`)

မည်သည့် API key မဆို **၎င်းကိုယ်တိုင်၏** အသုံးပြုမှုနှင့် quota များကို ဖတ်ရှုနိုင်ပြီး စီမံခန့်ခွဲမှုဆိုင်ရာ စစ်မှန်ကြောင်းအတည်ပြုမှု မလိုအပ်ပါ။ ဤ endpoint ကို
client (CLI၊ OmniCopilot panel) က key ကိုင်ဆောင်သူအား ၎င်း၏ ကုန်ကျစရိတ်ကို ပြသရန် အသုံးပြုသည်။

```bash
# စာသားပုံစံ (မူလကတည်းကရှိသော သဘောတူညီချက် — terminal အတွက် ရိုးရိုးစာသား)
curl -H "Authorization: Bearer <your-api-key>" \
  http://localhost:20128/api/usage/om-usage

# ဖွဲ့စည်းပုံကျသောပုံစံ — UI တစ်ခုက အသုံးပြုသည့်ပုံစံ
curl -H "Authorization: Bearer <your-api-key>" \
  "http://localhost:20128/api/usage/om-usage?format=json"
```

Key တွင် **`allowUsageCommand`** ကို ဖွင့်ထားရမည် (ပုံသေအားဖြင့် ပိတ်ထားပြီး dashboard ၏ API-key
manager က key တစ်ခုချင်းစီအလိုက် အဖွင့်အပိတ် ပြောင်းလဲပေးသည်)။ ယင်းကို မဖွင့်ထားပါက endpoint က `403` ဖြင့် တုံ့ပြန်သည်။

`?format=json` သည် ငြင်းပယ်ခံရသည့် တုံ့ပြန်မှုမှ data field တစ်ခုကို ခေါ်ယူသူက မည်သည့်အခါမျှ မဖတ်မိစေရန် ခွဲခြားသတ်မှတ်ထားသော ဖွဲ့စည်းပုံတစ်ခုကို ပြန်ပေးသည်။
အောင်မြင်သည့်အခါ-

```jsonc
{
  "allowed": true,
  // key က key တစ်ခုချင်းအလိုက် အသုံးပြုမှုကန့်သတ်ချက်များ (နေ့စဉ်/အပတ်စဉ် USD) ကို ရွေးချယ်ထားမှသာ ပါဝင်သည်-
  "personal": {
    "dailySpentUsd": 1.25,
    "dailyLimitUsd": 5,
    "dailyResetAtIso": "…",
    "weeklySpentUsd": 8,
    "weeklyLimitUsd": 20,
    "weeklyResetAtIso": "…" /* … */,
  },
  // ရွေးချယ်ထားသော provider quota snapshot သို့မဟုတ် cache မလုပ်ရသေးပါက null-
  "provider": { "connectionId": "…", "provider": "claude", "plan": "…", "quotas": {/* … */} },
  // UI က provider အများအပြားကို ဘေးချင်းယှဉ်၍ ဖော်ပြနိုင်ရန် connection တစ်ခုချင်းစီ၏ snapshot-
  "providers": [
    { "connectionId": "…", "provider": "claude" /* … */ },
    { "provider": "codex" /* … */ },
  ],
}
```

ငြင်းပယ်သည့်အခါ (`401` မမှန်ကန်သော key / `403` ခွင့်မပြုထားခြင်း) တူညီသော route က
`{ "allowed": false, "error": { "message": "…" } }` ကို ပြန်ပေးသည်။ `personal`/`provider` ရှိနေသော်လည်း အလွတ်ဖြစ်နေခြင်း
(key ကို ခွင့်ပြုထားသော်လည်း မည်သည့်အချက်အလက်မျှ မရရှိသေးခြင်း) သည် ငြင်းပယ်ခံရခြင်းနှင့် မတူညီသော အခြေအနေဖြစ်ပြီး JSON ပုံစံကသာ
ယင်းတို့ကို ခွဲခြားဖော်ပြနိုင်သည်။

**စစ်မှန်ကြောင်းအတည်ပြုခြင်း:** ခေါ်ယူသူ၏ ကိုယ်ပိုင် Bearer API key ကို `isValidApiKey` ဖြင့် စစ်ဆေးအတည်ပြုသည်။ ဤအရာသည်
`requireManagementAuth` နောက်တွင် ဆက်လက်ကာကွယ်ထားသည့် စီမံခန့်ခွဲမှုဆိုင်ရာ မျက်နှာပြင် (`/api/keys/…`) _မဟုတ်ပါ_။

### မူရင်းနှင့် Cutoff ချိန်ညှိထားသော Quota ရာခိုင်နှုန်းများ

`/api/usage/om-usage` ကို အသုံးပြုသည့်အခါ ခေါ်ယူသူများသည် **ရိုးရိုးစာသား output** နှင့် ဖွဲ့စည်းပုံကျသော **JSON output** တို့တွင်
ဖော်ပြထားသော ရာခိုင်နှုန်းများ၏ ကွာခြားချက်ကို သတိပြုသင့်သည်-

| အချက်              | ရိုးရိုးစာသားပုံစံ (`/api/usage/om-usage` / `@@om-usage`)                                                    | JSON ပုံစံ (`?format=json`)                                                                                  |
| :----------------- | :----------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------- |
| **Output field**   | `NN% left` (ဥပမာ၊ `20% left`)                                                                                | `provider.quotas` / `providers[].quotas`                                                                     |
| **တိုင်းတာမှု**    | **Cutoff ချိန်ညှိထားသော အသုံးပြုနိုင်သည့် ခွင့်ပြုချက်**- cutoff threshold အထက်တွင် ကျန်ရှိသော ပမာဏ          | **မူရင်း upstream quota**- ချိန်ညှိမထားသော provider တိုင်းတာမှု                                              |
| **Cutoff scaling** | ကာကွယ်ထားသော အရန်ပမာဏကို `0% left` အဖြစ် ဖတ်ရှုနိုင်စေရန် `effectiveRemainingPercent()` ဖြင့် အချိုးချိန်သည် | မရှိပါ (provider က အစီရင်ခံသည့်အတိုင်း မူရင်း snapshot တန်ဖိုးများ)                                          |
| **Threshold data** | ပြသထားသော ရာခိုင်နှုန်းထဲတွင် ထည့်သွင်းထားသည်                                                                | Connection တစ်ခုချင်းအလိုက် `quotaWindowThresholds` တွင် သိမ်းဆည်းထားသည် (သို့မဟုတ် server ပုံသေတန်ဖိုးများ) |
| **အဓိကအသုံးပြုသူ** | အပြန်အလှန်တုံ့ပြန်နိုင်သော CLI များ၊ terminal prompt များ၊ လူသား operator များ                               | ပရိုဂရမ်ဖြင့် ချိတ်ဆက်အသုံးပြုမှုများ၊ dashboard များ၊ analytics၊ billing tracker များ                       |

#### Cutoff ချိန်ညှိမှု ဖော်မြူလာ

OmniRoute သည် upstream quota ကုန်ဆုံးခြင်းကို ကာကွယ်ရန် ကြိုတင်လုပ်ဆောင်သည့် quota cutoff များကို ပံ့ပိုးသည် (connection
`quotaWindowThresholds`၊ provider ပုံသေတန်ဖိုးများ သို့မဟုတ် global resilience setting များမှတစ်ဆင့် စီစဉ်သတ်မှတ်သည်)။ Quota window တစ်ခုတွင် cutoff threshold
(ဥပမာ၊ `cutoff = 25%`) အသက်ဝင်နေသည့်အခါ စာသား renderer က ကျန်ရှိသော ခွင့်ပြုချက်ကို အောက်ပါအတိုင်း တွက်ချက်သည်-

- `remaining <= cutoff` ဖြစ်ပါက `0%` ကို ပြန်ပေးသည်။
- `remaining > cutoff` ဖြစ်ပါက `((remaining - cutoff) / (100 - cutoff)) * 100` ကို ပြန်ပေးသည်။

Format ချထားသော စာသား output သည် ယင်းကို အနီးဆုံး ကိန်းပြည့်သို့ လုံးပေးသည် (`Math.round(...)`)။

#### နမူနာဥပမာ

**မူရင်းအသုံးပြုမှု 60%** (ထို့ကြောင့် **မူရင်းကျန်ရှိ quota 40%**) ရှိပြီး **ကျန်ရှိ quota အတွက် 25% cutoff**
threshold သတ်မှတ်ထားသော provider window တစ်ခုကို စဉ်းစားကြည့်ပါ-

| ဖော်ပြမှုပုံစံ                   | တွက်ချက်မှု                                        | ကျန်ရှိမှု |       သွယ်ဝိုက်ဖော်ပြသော အသုံးပြုမှု       |
| :------------------------------- | :------------------------------------------------- | :--------: | :----------------------------------------: |
| **မူရင်း JSON (`?format=json`)** | Upstream snapshot (`quotas[window]`)               |  **40%**   |                  **60%**                   |
| **စာသားပုံစံ (`NN% left`)**      | `((40 - 25) / (100 - 25)) * 100 = (15 / 75) * 100` |  **20%**   | **80%** (`100 - remaining` ဟု တွက်ချက်ပါက) |

- **စာသားတွင် 20% ကျန်သည်ဟု ပြသရသည့်အကြောင်းရင်း:** Account တွင် အမှန်တကယ် ကျန်ရှိသော quota 40% အနက် 25% ကို
  cutoff policy က အရန်ထားသည်။ Router က ဤ connection သို့ routing ပြုလုပ်ခြင်းကို မရပ်မီ ခေါ်ယူသူအတွက် အသုံးပြုနိုင်သော headroom 75% အနက်
  15% သာ ကျန်ရှိသည်။ အချိုးချိန်ခြင်းကြောင့် routing ရပ်ဆိုင်းမည့်အချိန်အတိအကျတွင် connection က quota ကုန်ဆုံးမှု (`0% left`) ကို
  ဖော်ပြနိုင်သည်။
- **JSON က မူရင်းတန်ဖိုးများကို ထိန်းသိမ်းထားရသည့်အကြောင်းရင်း:** JSON payload သည် provider snapshot (`UsageSnapshot`) အတိအကျကို ပြန်ပေးသဖြင့်
  ပြင်ပ tool များသည် server ဘက်မှ အချက်အလက်ဆုံးရှုံးစေသော scaling မလုပ်ဘဲ အမှန်တကယ် upstream အသုံးချမှုနှင့် connection အဆင့်
  `quotaWindowThresholds` တို့ကို ရယူအသုံးပြုနိုင်သည်။

#### အသုံးပြုသူများအတွက် ရွှေ့ပြောင်းအသုံးပြုမှု လမ်းညွှန်ချက်

ပြင်ပပေါင်းစည်းမှုတစ်ခု (ဥပမာ တည်းဖြတ်ကိရိယာ ပလပ်အင် သို့မဟုတ် အေးဂျင့် တိုးချဲ့မှု) သည် ယခင်က စာသား
အဆုံးမှတ် (`NN% left`) ကို ရယူပြီး အသုံးပြုပြီး ရာခိုင်နှုန်းကို `100 - NN` အဖြစ် တွက်ချက်ခဲ့ပါက `?format=json` သို့ ပြောင်းရွှေ့ခြင်းသည် အောက်ပါအတိုင်း အဓိပ္ပာယ်ရသည်-

- JSON တန်ဖိုးအကြမ်းများကို ဖတ်ရှုခြင်းသည် **မူလရင်းမြစ်ဘက်ရှိ အမှန်တကယ် သုံးစွဲမှု** ကို ဖော်ပြမည် (အထက်ပါ ဥပမာတွင် 60% အသုံးပြုပြီး)။
- ပေါင်းစည်းမှုက စာသားအဆုံးမှတ်၏ အသုံးပြုနိုင်သော ခွင့်ပြုပမာဏဆိုင်ရာ အဓိပ္ပာယ်ဖွင့်ဆိုချက်ကို ဆက်လက်ထိန်းသိမ်းလိုပါက ချိတ်ဆက်မှုအဆင့် အစားထိုးသတ်မှတ်ချက်များအတွက် `quotaWindowThresholds` ကို အသုံးပြုပြီး
  ထိရောက်သော လက်ကျန်ပမာဏ ဖော်မြူလာကို ကလိုင်းယင့်ဘက်တွင် တွက်ချက်နိုင်သည်။

## Semantic Cache

```bash
# Cache စာရင်းအင်းများကို ရယူရန်
GET /api/cache/stats

# Cache အားလုံးကို ရှင်းလင်းရန်
DELETE /api/cache/stats
```

တုံ့ပြန်မှု နမူနာ-

```json
{
  "semanticCache": {
    "memorySize": 42,
    "memoryMaxSize": 500,
    "dbSize": 128,
    "hitRate": 0.65
  },
  "idempotency": {
    "activeKeys": 3,
    "windowMs": 5000
  }
}
```

### Latency အပေါ် သက်ရောက်မှု

Semantic cache HIT ဖြစ်ပါက တုံ့ပြန်မှုကို cache မှ **upstream
ခေါ်ဆိုမှုမရှိဘဲ** ပေးပို့သောကြောင့် ဖော်ပြထားသည့် `X-OmniRoute-Response-Latency` သည် သုညနီးပါး
ဖြစ်သည် (မူလ upstream latency မည်မျှရှိသည်ဖြစ်စေ)။ Latency ကို အလေးထားသည့် client များ
(benchmarking၊ p50/p99 monitoring) သည်
`X-OmniRoute-Cache-Latency` တုံ့ပြန်မှု header ကို စစ်ဆေးသင့်သည်-

| တန်ဖိုး     | အဓိပ္ပာယ်                                                                        |
| ----------- | -------------------------------------------------------------------------------- |
| `synthetic` | တုံ့ပြန်မှုကို cache မှ ပေးပို့ထားသည်၊ latency သည် တကယ့် upstream အချိန် မဟုတ်ပါ |
| _(မရှိပါ)_  | တကယ့် upstream ခေါ်ဆိုမှုမှ တုံ့ပြန်မှု                                          |

### Key တစ်ခုချင်းအလိုက် cache ကို ကျော်ခြင်း

API key များသည် `cacheDefaultMode` မှတစ်ဆင့် semantic cache ဖတ်ရှုမှုကို မသုံးရန် ရွေးချယ်နိုင်သည်-

| တန်ဖိုး  | လုပ်ဆောင်ပုံ                                                  |
| -------- | ------------------------------------------------------------- |
| `legacy` | ပုံမှန် cache လုပ်ဆောင်ပုံ (မူလသတ်မှတ်ချက်)                   |
| `bypass` | Cache ရှာဖွေမှုကို လုံးဝကျော်ပြီး upstream ကို အမြဲခေါ်ဆိုသည် |

Key ဖန်တီးချိန်တွင် (`POST /api/keys`) သတ်မှတ်ပါ သို့မဟုတ် (`PATCH /api/keys/[id]`) ဖြင့် အပ်ဒိတ်လုပ်ပါ-

```json
{ "cacheDefaultMode": "bypass" }
```

### Request တစ်ခုချင်းအလိုက် ကျော်ခြင်း

မည်သည့် request မဆို key ဆက်တင်များနှင့် မသက်ဆိုင်ဘဲ cache ကို ကျော်နိုင်သည်-

```
X-OmniRoute-No-Cache: true
```

တစ်ပြိုင်တည်းလုပ်ထားသော/တင်သွင်းထားသော မော်ဒယ်များအတွက် `PUT /api/provider-models` သည် `provider`, `modelId` နှင့်
`maxOutputTokenOverride` ကို လက်ခံသည်။ အပေါင်းကိန်းတစ်ခုက ကိုယ်တိုင်သတ်မှတ်သော output-token အများဆုံးကန့်သတ်ချက်ကို သတ်မှတ်ပြီး `null`
က ၎င်းကို ရှင်းလင်းကာ မူလတန်ဖိုးကို ပြန်လည်အသုံးပြုစေသည်။ `GET /api/provider-models?provider=<provider>` သည် စိတ်ကြိုက်မော်ဒယ် row မရှိသည့်
မော်ဒယ်များအပါအဝင် ဤတန်ဖိုးများကို `modelOutputOverrides` အတွင်း ပြန်ပေးသည်။ ဤအစားထိုးသတ်မှတ်ချက်သည် runtime `max_output_tokens`
လုပ်ဆောင်နိုင်စွမ်းကို အသုံးပြုပြီး မော်ဒယ်ကို ပြန်လည်တစ်ပြိုင်တည်းလုပ်ပြီးနောက်တွင်လည်း ဆက်လက်တည်ရှိသည်။ OpenAI နှင့် ကိုက်ညီသော
ပံ့ပိုးသူစာမျက်နှာတွင် အလားတူ ပြင်ဆင်/ရှင်းလင်း ထိန်းချုပ်မှုများ ပါရှိပြီး vision ပံ့ပိုးမှုကို တိကျစွာ သတ်မှတ်ထားသော မော်ဒယ်များကို အမှတ်အသားပြုသည်။

စိတ်ကြိုက် Chat Completions node များသည် တိကျစွာ သတ်မှတ်ထားသော reasoning ပိတ်ထားမှုများကို upstream backend နှင့် ကိုက်ညီအောင် ပြောင်းလဲပေးသည်။
အောင်မြင်သော ချိတ်ဆက်မှုစမ်းသပ်ချက်သည် `/models` entry က အသိအမှတ်ပြုထားသော `owned_by` တန်ဖိုးဖြစ်သည့် `vllm`, `sglang`, သို့မဟုတ် `llamacpp`
ကို သက်သေပြသည့် တိကျသော မော်ဒယ် ID တစ်ခုချင်းစီအတွက် chat-template ထိန်းချုပ်မှုများကို အလိုအလျောက် ရွေးချယ်ပေးသည်။
ကြားခံဖြစ်ကြောင်း မသိသာသော OpenAI နှင့် ကိုက်ညီသည့် wrapper များသည် မူရင်းမော်ဒယ် entry ကို အဆင့်ဆင့်ထည့်သွင်းထားသော
`openai` object တစ်ခုအတွင်း ထိန်းသိမ်းထားနိုင်သည်။ စစ်ဆေးဖော်ထုတ်မှုသည် ထိုကဲ့သို့သော envelope သုံးဆင့်အထိ လိုက်လံစစ်ဆေးသည်။ ပိုင်ဆိုင်မှုအချက်အလက်
ပျောက်နေသော၊ မသိရှိသော သို့မဟုတ် ပဋိပက္ခဖြစ်နေသော မော်ဒယ်များသည် ပုံမှန် OpenAI လုပ်ဆောင်ပုံကို ဆက်လက်ထိန်းသိမ်းထားသည်။ စစ်ဆေးဖော်ထုတ်မှုသည် ရှိပြီးသား catalog request ကို
ပြန်လည်အသုံးပြုကာ completion token များ ထုတ်လုပ်ခြင်းမရှိဘဲ ချိတ်ဆက်မှု endpoint ပြောင်းလဲသည့်အခါ ပျက်ပြယ်သွားသည်။

ထို metadata ကို မဖော်ပြသော backend တစ်ခုအတွက် အပြုအမူကို ပုံသေသတ်မှတ်ရန် ရှိပြီးသား တစ်စိတ်တစ်ပိုင်း
ပံ့ပိုးသူ အပ်ဒိတ် API ကို အသုံးပြုပါ။

```json
{
  "providerSpecificData": {
    "reasoningControl": "chat-template"
  }
}
```

ထို body ကို `PUT /api/providers/<connection-id>` ဖြင့် ပို့ပါ။ ထိုချိတ်ဆက်မှုတွင် `none` ဟု တိကျစွာသတ်မှတ်ထားသော
reasoning effort ကို `chat_template_kwargs.thinking=false` နှင့်
`chat_template_kwargs.enable_thinking=false` အဖြစ် ပို့သည်။ server-side reasoning စည်းမျဉ်းတစ်ခုက effort တစ်ခုကို အတင်းသတ်မှတ်ခြင်းမရှိပါက
တိကျစွာသတ်မှတ်ထားသော native template တန်ဖိုးများကိုသာ ဦးစားပေးအသုံးပြုသည်။ ဤဆက်တင်သည် စိတ်ကြိုက်
OpenAI နှင့် ကိုက်ညီသော ချိတ်ဆက်မှုတစ်ခုက Chat Completions body တစ်ခုကို ပေးပို့သည့်အခါတွင်သာ သက်ရောက်သည်။ Responses request များနှင့် ပုံမှန်
ပံ့ပိုးသူများသည် ၎င်းတို့၏ မူရင်း request ပုံစံကို ဆက်လက်အသုံးပြုသည်။ ပုံမှန် OpenAI
`reasoning_effort` passthrough ကို အတင်းအသုံးပြုရန် `reasoningControl` ကို `openai` ဟု သတ်မှတ်ပါ၊ သို့မဟုတ် အလိုအလျောက် စစ်ဆေးဖော်ထုတ်မှုကို အသုံးပြုရန် ၎င်းကို ချန်လှပ်ထားပါ/`null` ဟု သတ်မှတ်ပါ။

Claude Code auto-mode classifier request များတွင် တိကျစွာသတ်မှတ်ထားသော reasoning ထိန်းချုပ်မှုများ မပါဝင်ပါက native thinking ကို မူလအားဖြင့်
ပိတ်ထားသည်။ စစ်ဆေးဖော်ထုတ်မှုသည် မော်ဒယ်အမည်များ သို့မဟုတ် completion ကန့်သတ်ချက်များကို မဟုတ်ဘဲ Claude-format
request များရှိ classifier ၏ system marker ကို အသုံးပြုသည်။ တိကျစွာသတ်မှတ်ထားသော body ထိန်းချုပ်မှုများ၊ ပံ့ပိုးထားသော effort/thinking
header များ၊ routing စည်းမျဉ်းများနှင့် ဖြေရှင်းသတ်မှတ်ပြီးသော မော်ဒယ် effort တို့သည် ၎င်းတို့၏ ရှိပြီးသား ဦးစားပေးအဆင့်ကို ဆက်လက်ထိန်းသိမ်းထားသည်။ Classifier
အဆင့်နှစ်ခုစလုံးသည် ၎င်းတို့၏ prompt များ၊ completion ကန့်သတ်ချက်များ၊ stop sequence များနှင့် အမှန်တကယ် upstream ခွင့်ပြုချက်
ဆုံးဖြတ်ချက်များကို ဆက်လက်ထိန်းသိမ်းထားသည်။ ဒုတိယအဆင့်သည် တောင်းဆိုထားသော မြင်နိုင်သည့် reasoning ကို ပုံမှန်စာသားအဖြစ် ဆက်လက်ထုတ်လုပ်နိုင်သည်။

`PATCH /api/keys/{id}` သည် ရှိပြီးသား key တစ်ခု၏ ခွင့်ပြုချက်များကို အပ်ဒိတ်လုပ်သည်။ `/api/keys*` route အားလုံးကဲ့သို့ပင် ၎င်းသည် inference key မဟုတ်ဘဲ စီမံခန့်ခွဲမှုဆိုင်ရာ authorization လိုအပ်သည် ([စီမံခန့်ခွဲမှုဆိုင်ရာ အထောက်အထားစစ်ဆေးခြင်း](../guides/MANAGEMENT-AUTH.md) ကို ကြည့်ပါ)။ သင်ပြောင်းလဲလိုသည့် field များကိုသာ ပေးပို့ပါ။ ယင်း field များ တစ်ခုမျှမပါဝင်သော request ကို `No valid fields to update` ဖြင့် ပယ်ချမည်ဖြစ်သည်။ လက်ခံသော field များကို `src/shared/validation/schemas/keys.ts` ရှိ `updateKeyPermissionsSchema` က သတ်မှတ်ထားသည်။

| `/api/db-backups`           | PATCH  | အရန်သိမ်းဆည်းမှု ထိန်းသိမ်းထားရှိရေး ဆက်တင်များကို သိမ်းရန် (operator သာ)                                     |

`/api/db-backups/export`၊ `/api/db-backups/exportAll` နှင့် `/api/settings/export-json` တို့သည်
သိမ်းဆည်းထားသော credential အားလုံးကို ထုတ်ပေးသဖြင့် dashboard session သို့မဟုတ် local CLI
(သို့မဟုတ် login ပိတ်ထားခြင်း) လိုအပ်သည်။ မည်သည့် scope မဆိုရှိသော API key များနှင့် `oma_`
access token များသည် `403` ကို ရရှိမည်။ ပြန်လည်ရယူခြင်းများတွင်လည်း တူညီသော ကန့်သတ်ချက်ရှိသည်-
`POST /api/db-backups/import` (`dryRun=true` ပါဝင်သည်)၊ `POST /api/db-backups` (id ဖြင့် ပြန်လည်ရယူခြင်း)
နှင့် `POST /api/settings/import-json` တို့သည် လက်ရှိအသုံးပြုနေသော ဒေတာဘေ့စ် သို့မဟုတ် ဆက်တင်များကို
အစားထိုးသဖြင့် machine credential တစ်ခုသည်လည်း ထိုနေရာတွင် `403` ကို ရရှိမည်ဖြစ်သည်။ `omniroute sync import`
သည် local CLI credential ကို ပေးပို့သည်။ `DELETE /api/db-backups` (သိမ်းထားသော အရန်သိမ်းဆည်းမှုများကို ရှင်းလင်းခြင်း)
နှင့် `PATCH /api/db-backups` (ထိန်းသိမ်းထားရှိရေး ဆက်တင်များ- သိမ်းဆည်းထားသော တန်ဖိုးများက အရန်သိမ်းဆည်းမှုတစ်ခုစီ
ပြီးတိုင်း အလိုအလျောက်ရှင်းလင်းမှုကို ထိန်းချုပ်သည်) တို့လည်း ထိုနည်းတူဖြစ်သည်။ စာရင်းပြုစုခြင်း (`GET`) နှင့်
ကိုယ်တိုင် အရန်သိမ်းဆည်းမှု ဖန်တီးခြင်း (`PUT`) တို့တွင် ပုံမှန် management auth ကို ဆက်လက်အသုံးပြုသည်။

### ခံနိုင်ရည်ရှိမှုနှင့် Rate Limits

| Endpoint                          | Method    | ဖော်ပြချက်                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `/api/resilience`                 | GET/PATCH | တောင်းဆိုမှုတန်းစီစနစ်၊ ချိတ်ဆက်မှု cooldown၊ provider breaker နှင့် စောင့်ဆိုင်းမှုဆိုင်ရာ ဆက်တင်များကို ရယူ/အပ်ဒိတ်လုပ်ရန်                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `/api/resilience/reset`           | POST      | provider circuit breaker များကို ပြန်လည်သတ်မှတ်ရန်                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `/api/resilience/model-cooldowns` | GET       | လက်ရှိအသုံးပြုနေသော (provider၊ connection၊ model) တစ်ခုချင်းစီအလိုက် lockout များကို ကျန်ရှိသည့်အချိန်အလိုက် စီပြီး စာရင်းပြုစုရန်                                                                                                                                                                                                                                                                                                                                                                                                               |
| `/api/resilience/model-cooldowns` | DELETE    | model lockout တစ်ခုကို ရှင်းလင်းရန် — body အနေဖြင့် `{provider, model}` သို့မဟုတ် အားလုံးကို ဖယ်ရှားရန် `{all: true}` ကို အသုံးပြုရန်                                                                                                                                                                                                                                                                                                                                                                                                            |

| `/api/rate-limit`                 | GET       | ကမ္ဘာလုံးဆိုင်ရာ rate limit ဖွဲ့စည်းသတ်မှတ်ချက် (အသုံးမပြုတော့ပါ၊ `/api/rate-limits` အတွက် alias ဖြစ်သည်)                                                                                                                                                                                                                                                                                                                                                                                                                                        |

> `/api/resilience/*` route လေးခုစလုံးတွင် **စီမံခန့်ခွဲမှုဆိုင်ရာ အထောက်အထားစစ်ဆေးခြင်း** (`requireManagementAuth`) လိုအပ်သည်။ provider breaker၊ connection cooldown နှင့် model lockout တို့၏ ကွာခြားချက်အပြည့်အစုံကို [ခံနိုင်ရည်ရှိမှု (အသေးစိတ်)](#resilience-extended) တွင် ကြည့်ပါ။

### OAuth Environment ပြုပြင်ခြင်း _(v3.6.1+)_

```bash
POST /api/system/env/repair
Content-Type: application/json

{
  "provider": "claude-code"
}
```

သတ်မှတ်ထားသော provider တစ်ခုအတွက် ပျောက်ဆုံးနေသော သို့မဟုတ် ပျက်စီးနေသော OAuth environment variable များကို ပြုပြင်ပေးသည်။ အောက်ပါတို့ကို ပြန်ပေးသည်-

```json
{
  "success": true,
  "repaired": ["CLAUDE_CODE_OAUTH_CLIENT_ID", "CLAUDE_CODE_OAUTH_CLIENT_SECRET"],
  "backupPath": "/home/user/.omniroute/backups/env-repair-2026-04-11.bak"
}
```

### ဗားရှင်းနှင့် ဖြန့်ချိရေး Channel

```bash
GET /api/system/version
```

Loopback မှသာ ဝင်ရောက်နိုင်သော စီမံခန့်ခွဲရေး route (admin auth) ဖြစ်သည်။ လက်ရှိအသုံးပြုနေသော ဗားရှင်း၊ နောက်ဆုံးထုတ်ပြန်ထားသော ဗားရှင်းနှင့် အလိုအလျောက် update လုပ်သည့် အခြေအနေတို့ကို ပြန်ပေးသည်။ `releaseChannel` နှင့် `channels` တို့သည် ထပ်ဖြည့်ထားသော field များ (rail 3.8.54) ဖြစ်သည်။ `channel` သည် မူလအဓိပ္ပာယ်ကို ဆက်လက်ထိန်းသိမ်းထားပြီး dashboard updater က အသုံးပြုသည့် deployment mode (`npm`, `source` သို့မဟုတ် `docker-compose`) ကို ဆိုလိုသည်။

```json
{
  "current": "3.8.52",
  "latest": "3.8.52",
  "updateAvailable": false,
  "channel": "npm",
  "autoUpdateSupported": true,
  "autoUpdateError": null,
  "news": null,
  "releaseChannel": "latest",
  "channels": { "latest": "3.8.52", "next": "3.8.53-rc.1" }
}
```

- `releaseChannel` — လက်ရှိအသုံးပြုနေသော build ၏ npm channel ဖြစ်သည်။ `-nightly.*` ဗားရှင်းများအတွက် `nightly`၊ အခြား pre-release များ (`-rc.*`, `-beta.*`, `-alpha.*`) အတွက် `next`၊ `channels.latest` ထက် major version အဟောင်းဖြစ်သော stable version အတွက် `lts` ဖြစ်ပြီး၊ ထိုသို့မဟုတ်ပါက `latest` ဖြစ်သည်။ ထုတ်ပြန်ချိန်တွင် npm dist-tag ကို ရွေးချယ်ပေးသော `scripts/release/dist-tag.mjs` နှင့် တူညီသည့် စည်းမျဉ်းများကို အသုံးပြုသည်။
- `channels` — `npm view omniroute dist-tags` မှရရှိသော dist-tag တစ်ခုစီ၏ နောက်ဆုံးထုတ်ပြန်ထားသည့် ဗားရှင်းဖြစ်ပြီး (registry HTTP fallback ပါဝင်သည်)၊ `latest` ကဲ့သို့ပင် 10 မိနစ် TTL ဖြင့် cache လုပ်ထားသည်။ `latest` သည် အမြဲတမ်း ပါဝင်သည် (`latest` field ကို fallback အဖြစ် အသုံးပြုပြီး၊ ထို့နောက် `"unavailable"` ကို အသုံးပြုသည်)။ `next`, `nightly` နှင့် `lts` တို့သည် သက်ဆိုင်ရာ dist-tag ရှိမှသာ ပေါ်လာသည်။ `Cache-Control: no-cache` request သည် lookup နှစ်ခုစလုံးကို refresh လုပ်ပေးသည်။

Channel model (`latest` = 4.0 GA မတိုင်မီအထိ v3၊ `next` = rc၊ `nightly` = `develop` build များ၊ `lts` = 4.0 GA နောက်ပိုင်း v3 patch များ) ကို `docs/ops/RELEASE_STRATEGY.md` တွင် ဖော်ပြထားသည်။

## အသံမှ စာသားကူးပြောင်းခြင်း

```bash

Authorization: Bearer your-api-key
Content-Type: multipart/form-data
```

စီစဉ်သတ်မှတ်ထားသော မည်သည့် STT ပံ့ပိုးသူကိုမဆို အသုံးပြုပြီး အသံဖိုင်များကို စာသားအဖြစ် ကူးပြောင်းပါ။ ပထမဆုံး path
segment သည် မူရင်းပံ့ပိုးသူ (`openai/…`, `deepgram/…`) ကို ရွေးချယ်သည်။ အခြား vendor ၏ model ကို
ပြန်လည်ထုတ်ပေးသည့် gateway များသည် qualified id
(`openrouter/deepgram/nova-3`) ကို အသုံးပြုသည်။

**တောင်းဆိုချက်:**

```bash
curl -X POST http://localhost:20128/v1/audio/transcriptions \
  -H "Authorization: Bearer your-api-key" \
  -F "file=@recording.mp3" \
  -F "model=openai/whisper-1"
```

**တုံ့ပြန်ချက်:**

```json
{
  "text": "Hello, this is the transcribed audio content.",
  "task": "transcribe",
  "language": "en",
  "duration": 12.5
}
```

**နမူနာ model id များ:** `openai/whisper-1` (OpenAI key လိုအပ်သည်),
`openrouter/deepgram/nova-3` (OpenRouter key လိုအပ်သည်),
`deepgram/nova-3` (မူရင်း Deepgram key လိုအပ်သည်)။ ရိုးရိုး
`deepgram/nova-3` တောင်းဆိုချက်သည် OpenRouter ကို အသုံးပြုခြင်း **မရှိပါ**။

**ပံ့ပိုးထားသော format များ:** `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`.

## Token ပါသော VS Code / Header မပါသော Alias များ

Integration တစ်ခုက `Authorization` header ကို ထည့်သွင်းမပေးနိုင်ဘဲ API key ကို base URL ထဲတွင် ထည့်သွင်းရန် လိုအပ်သည့်အခါ ဤ alias များကို အသုံးပြုပါ။

```bash
# OpenAI ပုံစံ catalog alias
GET /api/v1/vscode/{token}/
GET /api/v1/vscode/{token}/models

# OpenAI ပုံစံ chat alias များ
POST /api/v1/vscode/{token}/chat/completions
POST /api/v1/vscode/{token}/responses

# Ollama ပုံစံ alias များ
POST /api/v1/vscode/{token}/api/chat
GET /api/v1/vscode/{token}/api/tags
```

ဥပမာ:

```bash
curl https://your-host.example/api/v1/vscode/YOUR_API_KEY/models
curl -X POST https://your-host.example/api/v1/vscode/YOUR_API_KEY/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"hello"}]}'
```

မှတ်ချက်များ:

- Token ပါသော alias များသည် `/v1/*` နှင့် `/api/tags` တို့၏ handler များကိုပင် ပြန်လည်အသုံးပြုသောကြောင့် တုံ့ပြန်ချက်ပုံစံများ တူညီစွာရှိနေမည်။
- Client က custom header များကို ပံ့ပိုးသည့်အခါတိုင်း `Authorization: Bearer ...` ကို ဦးစားပေးအသုံးပြုပါ။
- URL အခြေပြု token များသည် reverse-proxy log များ၊ browser history နှင့် OmniRoute ပြင်ပရှိ telemetry တို့တွင် ပေါ်လာနိုင်သည်။ ၎င်းတို့ကို မူလ authentication mode အဖြစ်မဟုတ်ဘဲ လိုက်ဖက်ညီမှုအတွက် ရွေးချယ်စရာအဖြစ် သတ်မှတ်ပါ။

```bash
# API key အားလုံးအတွက် ဘတ်ဂျက်အခြေအနေကို ရယူရန်
GET /api/usage/budget
```

## တိုကင် ကန့်သတ်ချက်များ

API ကီးတစ်ခုချင်းစီအလိုက် **တိုကင်** သုံးစွဲခွင့်ပမာဏများ (အထက်ပါ USD အခြေပြု ဘတ်ဂျက်နှင့် သီးခြားဖြစ်သည်)။ တောင်းဆိုမှု လမ်းကြောင်းပေါ်တွင် တိုက်ရိုက် အတည်ပြုကန့်သတ်ထားသည်။ ကီးတစ်ခု၏ လက်ရှိအချိန်ကာလအတွင်း အသုံးပြုမှုပမာဏသည် ၎င်း၏ ကန့်သတ်ချက်သို့ ရောက်ရှိသောအခါ တောင်းဆိုမှုများကို `429 Too Many Requests` ဖြင့် ငြင်းပယ်မည်။ ကန့်သတ်ချက်များကို သီးခြား `model` တစ်ခု၊ `provider` တစ်ခုအတွက် သတ်မှတ်နိုင်သကဲ့သို့ ကီးတစ်ခုလုံးတွင် `global` အဖြစ်လည်း သက်ရောက်စေနိုင်သည်။ တောင်းဆိုမှုတစ်ခုနှင့် ကန့်သတ်ချက်များစွာ ကိုက်ညီပါက အတင်းကျပ်ဆုံး ကန့်သတ်ချက်ကို အသုံးပြုမည်။

```bash
# ကီးတစ်ခု၏ တိုကင်ကန့်သတ်ချက်များကို စာရင်းပြုစုခြင်း (လက်ရှိအချိန်ကာလအတွင်း အသုံးပြုမှု ပါဝင်သည်)
GET /api/usage/token-limits?apiKeyId=key-123

# တိုကင်ကန့်သတ်ချက်တစ်ခုကို ဖန်တီးခြင်း သို့မဟုတ် အပ်ဒိတ်လုပ်ခြင်း
POST /api/usage/token-limits
Content-Type: application/json

{
  "apiKeyId": "key-123",
  "scopeType": "model",
  "scopeValue": "openai/gpt-4o",
  "tokenLimit": 1000000,
  "resetInterval": "monthly",
  "enabled": true
}

# id ဖြင့် တိုကင်ကန့်သတ်ချက်တစ်ခုကို ဖျက်ခြင်း
DELETE /api/usage/token-limits?id=tl-abc
```

> **Schema မှတ်ချက်များ** (`setTokenLimitSchema`): `apiKeyId` နှင့် `scopeType` (`model` | `provider` | `global`) တို့သည် မဖြစ်မနေ လိုအပ်သည်။ `scopeType` သည် `global` မဟုတ်ပါက `scopeValue` လိုအပ်သည် (ဥပမာ၊ `model` နယ်ပယ်အတွက် model id၊ `provider` နယ်ပယ်အတွက် provider id)။ `tokenLimit` သည် အပေါင်းကိန်းပြည့် ဖြစ်ရမည် (string မှ အလိုအလျောက် ပြောင်းလဲပေးသည်)။ ရွေးချယ်နိုင်သော အရာများမှာ `id` (အသစ်ဖန်တီးရန် မထည့်ပါနှင့်၊ အပ်ဒိတ်လုပ်ရန် ထည့်ပေးပါ)၊ `resetInterval` (`daily` | `weekly` | `monthly`၊ မူလသတ်မှတ်ချက် `monthly`)၊ `resetTime` (`HH:MM`) နှင့် `enabled` (မူလသတ်မှတ်ချက် `true`) တို့ဖြစ်သည်။ `GET` တုံ့ပြန်ချက်များတွင် ကန့်သတ်ချက်တစ်ခုစီအတွက် `tokensUsed`၊ `remaining`၊ `windowStart`၊ `periodStartAt` နှင့် `nextResetAt` တို့ကို ထပ်မံဖြည့်စွက်ပေးသည်။ ဤသည်မှာ စီမံခန့်ခွဲမှုအဆင့် endpoint တစ်ခုဖြစ်သည် (စစ်မှန်ကြောင်း အတည်ပြုမှုကို authz pipeline က ဗဟိုမှ ထိန်းချုပ်အတည်ပြုသည်)။

## တောင်းဆိုမှု လုပ်ဆောင်ပုံ

1. Client က တောင်းဆိုမှုကို `/v1/*` သို့ ပေးပို့သည်
2. Route handler က `handleChat`၊ `handleEmbedding`၊ `handleAudioTranscription` သို့မဟုတ် `handleImageGeneration` ကို ခေါ်ယူသည်
3. Model ကို သတ်မှတ်ဖြေရှင်းသည် (တိုက်ရိုက် provider/model သို့မဟုတ် alias/combo)
4. Account အသုံးပြုနိုင်မှုကို စစ်ထုတ်ပြီး local DB မှ အထောက်အထားများကို ရွေးချယ်သည်
5. Chat အတွက် `handleChatCore` က semantic/signature cache ကို စစ်ဆေးပြီး combo compression ဆက်တင်များကို သတ်မှတ်ဖြေရှင်းသည်
6. ဖွင့်ထားပါက provider ဘာသာပြန်ပြောင်းလဲမှုမတိုင်မီ ကြိုတင် compression ကို လုပ်ဆောင်သည် (`lite`၊ Caveman၊ RTK သို့မဟုတ် အဆင့်ဆင့်ပေါင်းစပ်ထားသည့် နည်းလမ်း)
7. Provider executor က upstream တောင်းဆိုမှုကို ပေးပို့သည်
8. တုံ့ပြန်ချက်ကို client format သို့ ပြန်လည်ဘာသာပြန်ပြောင်းလဲပေးသည် (chat) သို့မဟုတ် မူလအတိုင်း ပြန်ပေးသည် (embeddings/images/audio)
9. အသုံးပြုမှု၊ compression analytics နှင့် တောင်းဆိုမှုမှတ်တမ်းများကို မှတ်တမ်းတင်သည်
10. အမှားများ ဖြစ်ပေါ်ပါက combo စည်းမျဉ်းများအတိုင်း fallback ကို အသုံးပြုသည်

ဗိသုကာဖွဲ့စည်းပုံ အပြည့်အစုံကို ကိုးကားရန်: [`ARCHITECTURE.md`](../architecture/ARCHITECTURE.md)

## Combo စီမံခန့်ခွဲမှု

အဆင့်မြင့် routing combo များ (`/api/combos*` အောက်တွင် အကျဉ်းချုပ်ဖော်ပြထားပြီးဖြစ်သည်) ကို model id pattern တစ်ခုမှ 1:1 အဖြစ်လည်း mapping ပြုလုပ်နိုင်သည်။ ထို့ကြောင့် OpenAI ပုံစံ model id တစ်ခုကို combo တစ်ခုသို့ အလိုအလျောက် ပွင့်လင်းမြင်သာစွာ လမ်းကြောင်းပြောင်းပေးနိုင်သည်။

| Method | Path                             | ဖော်ပြချက်                                                                          |
| ------ | -------------------------------- | ----------------------------------------------------------------------------------- |
| GET    | `/api/model-combo-mappings`      | model→combo mapping အားလုံးကို စာရင်းပြုစုခြင်း                                     |
| POST   | `/api/model-combo-mappings`      | mapping ဖန်တီးခြင်း — body: `{pattern, comboId, priority?, enabled?, description?}` |
| GET    | `/api/model-combo-mappings/[id]` | mapping တစ်ခုတည်းကို ရယူခြင်း                                                       |
| PUT    | `/api/model-combo-mappings/[id]` | ရှိပြီးသား mapping တစ်ခု၏ field များကို အပ်ဒိတ်လုပ်ခြင်း                            |

## မှတ်ပုံတင်ထားသော Key များ (အလိုအလျောက်စီမံခန့်ခွဲမှု)

နေ့စဉ်/နာရီအလိုက် quota များဖြင့် နောက်ခံ provider/account တစ်ခုကို အသုံးပြု၍ API key များ ထုတ်ပေးခြင်းနှင့် လဲလှယ်ခြင်းအတွက် အလိုအလျောက် key စီမံခန့်ခွဲမှု subsystem က အသုံးပြုသည်။

| Method | Path                                  | ဖော်ပြချက်                                                                                                                                                                                                                             |
| ------ | ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/v1/registered-keys`             | မှတ်ပုံတင်ထားသော key များကို စာရင်းပြုစုသည် (ဖုံးကွယ်ထားသော prefix သာလျှင်)                                                                                                                                                            |
| POST   | `/api/v1/registered-keys`             | မှတ်ပုံတင်ထားသော key အသစ်တစ်ခု ထုတ်ပေးသည် — body: `{name, provider?, accountId?, idempotencyKey?, expiresAt?, dailyBudget?, hourlyBudget?}`။ မူရင်း key ကို **တစ်ကြိမ်သာ** ပြန်ပေးသည်။ Quota ကြောင့် ငြင်းပယ်ပါက `429` ကို ပြန်ပေးသည်။ |
| GET    | `/api/v1/registered-keys/[id]`        | မှတ်ပုံတင်ထားသော key တစ်ခု၏ metadata ကို ရယူသည် (မူရင်း key အချက်အလက် မပါဝင်ပါ)                                                                                                                                                        |
| DELETE | `/api/v1/registered-keys/[id]`        | မှတ်ပုံတင်ထားသော key တစ်ခုကို ရုပ်သိမ်းသည်                                                                                                                                                                                             |
| POST   | `/api/v1/registered-keys/[id]/revoke` | သီးခြားရုပ်သိမ်းရေး endpoint (DELETE နှင့် သက်ရောက်မှုတူညီသည်)                                                                                                                                                                         |

**စစ်မှန်ကြောင်းအတည်ပြုခြင်း:** စီမံခန့်ခွဲမှု session/API key (`requireManagementAuth`) — `/api/keys` နှင့် တူညီသော guard ဖြစ်သည်။ dashboard session၊ local CLI token သို့မဟုတ် `manage`/`admin` scope ပါသော API key ကို အသုံးပြုနိုင်သည်။ inference သီးသန့် API key များသည် `403` ကို ရရှိမည်။ `/v1/quotas/check` နှင့် `/v1/issues/report` တို့ကိုလည်း ကြည့်ပါ။

## အေးဂျင့်များဆိုင်ရာ ပရိုတိုကော

OmniRoute အသုံးပြုသူများကိုယ်စား အဝေးမှ လုပ်ဆောင်သည့် cloud agent အလုပ်များ (Claude Code, Codex Cloud, OpenHands စသည်တို့)။

| နည်းလမ်း | လမ်းကြောင်း                   | ဖော်ပြချက်                                                                                                                                                                  |
| -------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET      | `/api/v1/agents/tasks`        | အလုပ်များကို စာရင်းပြုစုခြင်း — `?provider=`, `?status=`, `?limit=` (1–500၊ မူလတန်ဖိုး 50) တို့ကို ရွေးချယ်အသုံးပြုနိုင်သည်                                                 |
| POST     | `/api/v1/agents/tasks`        | အလုပ်ဖန်တီးခြင်း — body ကို `CreateCloudAgentTaskSchema` (`providerId`, `prompt`, `source`, `options?`) ဖြင့် အတည်ပြုစစ်ဆေးသည်။ task envelope နှင့်အတူ `201` ကို ပြန်ပေးသည် |
| DELETE   | `/api/v1/agents/tasks?id=...` | အလုပ်တစ်ခုကို ဖျက်ခြင်း                                                                                                                                                     |
| GET      | `/api/v1/agents/tasks/[id]`   | အလုပ်ကို ဖတ်ရှုခြင်း — `external_id` သတ်မှတ်ထားပါက upstream cloud agent မှ အခြေအနေကို synchronous ပုံစံဖြင့် ပြန်လည်မွမ်းမံသည်                                              |
| POST     | `/api/v1/agents/tasks/[id]`   | ခွဲခြားသတ်မှတ်ထားသော လုပ်ဆောင်ချက်- `{action: "approve"}`, `{action: "message", message}` သို့မဟုတ် `{action: "cancel"}`                                                    |
| DELETE   | `/api/v1/agents/tasks/[id]`   | သတ်မှတ်ထားသော id ဖြင့် အလုပ်တစ်ခုကို ဖျက်ခြင်း                                                                                                                              |


## စီမံခန့်ခွဲမှု Proxy များ

Provider များ၊ account များ သို့မဟုတ် ကမ္ဘာလုံးဆိုင်ရာအဖြစ် သတ်မှတ်ပေးနိုင်သည့် အပြင်သို့ထွက်သော HTTP(S)/SOCKS proxy များ။

| နည်းလမ်း | လမ်းကြောင်း                                  | ဖော်ပြချက်                                                                                                                                                                                                               |
| -------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GET      | `/api/v1/management/proxies`                 | Proxy များကို စာရင်းပြုစုခြင်း (`?id=` ဖြင့် တစ်ခုကို ပြန်ပေးပြီး `?id=&where_used=1` ဖြင့် assignment graph ကို ပြန်ပေးသည်)                                                                                             |
| POST     | `/api/v1/management/proxies`                 | Proxy ဖန်တီးခြင်း — body ကို `createProxyRegistrySchema` ဖြင့် အတည်ပြုစစ်ဆေးသည်                                                                                                                                          |
| PATCH    | `/api/v1/management/proxies`                 | Proxy ကို အပ်ဒိတ်လုပ်ခြင်း — body ကို `updateProxyRegistrySchema` ဖြင့် အတည်ပြုစစ်ဆေးသည် (`id` လိုအပ်သည်)                                                                                                                |
| DELETE   | `/api/v1/management/proxies?id=...&force=1`  | Proxy ကို ဖျက်ခြင်း (ချိတ်ဆက်သတ်မှတ်မှုများကို ဖြုတ်ရန် `force=1` ကို အသုံးပြုပါ)                                                                                                                                        |
| GET      | `/api/v1/management/proxies/assignments`     | ချိတ်ဆက်သတ်မှတ်မှုများကို စာရင်းပြုစုခြင်း — `proxy_id`, `scope`, `scope_id` တို့ဖြင့် စစ်ထုတ်နိုင်သည်။ connection တစ်ခုအတွက် လက်ရှိအသုံးပြုနေသော proxy ကို ရှာဖွေဆုံးဖြတ်ရန် `resolve_connection_id=<id>` ကို ပေးပို့ပါ |
| PUT      | `/api/v1/management/proxies/assignments`     | ချိတ်ဆက်သတ်မှတ်ခြင်း — body ကို `proxyAssignmentSchema` (`{scope, scopeId?, proxyId?}`) ဖြင့် အတည်ပြုစစ်ဆေးသည်။ dispatcher cache ကို ရှင်းလင်းသည်                                                                        |
| PUT      | `/api/v1/management/proxies/bulk-assign`     | အစုလိုက် ချိတ်ဆက်သတ်မှတ်ခြင်း — body ကို `bulkProxyAssignmentSchema` (`{scope, scopeIds[], proxyId?}`) ဖြင့် အတည်ပြုစစ်ဆေးသည်                                                                                            |
| GET      | `/api/v1/management/proxies/health?hours=24` | သတ်မှတ်ကာလအတွင်း proxy ကျန်းမာရေးအခြေအနေကို စုစည်းဖော်ပြခြင်း (အောင်မြင်/မအောင်မြင် အရေအတွက်များ၊ latency)                                                                                                               |

**အထောက်အထားစစ်ဆေးမှု-** route တိုင်းတွင် management session/API key လိုအပ်သည် (`requireManagementAuth`)။

> အလုပ်ဖော်ပြချက်ရှိ `POST /api/v1/management/proxies/[id]/assignments` နှင့် `POST /api/v1/management/proxies/[id]/health` တို့ကို အထက်တွင်ပြထားသော flat `/assignments` နှင့် `/health` route များက ပံ့ပိုးပေးသည် — codebase တွင် id တစ်ခုချင်းအလိုက် subroute များ မရှိပါ။

## ခံနိုင်ရည် (တိုးချဲ့ဖော်ပြချက်)

OmniRoute သည် ယာယီချို့ယွင်းမှုကို ကိုင်တွယ်သည့် သီးခြားယန္တရားသုံးခုကို ဖော်ထုတ်ပေးထားသည်။ အောက်ပါ စီမံခန့်ခွဲမှု endpoint များမှတစ်ဆင့် အော်ပရေတာများသည် ၎င်းတို့ကို ဖတ်ရှုနိုင်ပြီး သတ်မှတ်ချက်များကို အစားထိုးပြင်ဆင်နိုင်သည်-

| အကျုံးဝင်မှု         | အခြေအနေသိမ်းဆည်းမှု                            | ဖတ်ရှုရန်                                 | ပြန်လည်သတ်မှတ်ရန် / ရှင်းလင်းရန်                                         |
| -------------------- | ---------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------ |
| Provider breaker     | `domain_circuit_breakers` + မမ်မိုရီအတွင်း     | `/api/monitoring/health`                  | `POST /api/resilience/reset`                                             |
| ချိတ်ဆက်မှု cooldown | provider ချိတ်ဆက်မှုများရှိ `rateLimitedUntil` | `/api/rate-limits`, `/api/providers/[id]` | (လိုအပ်ချိန်တွင် ပြန်လည်ဖွင့်ပေးသည်၊ provider PUT မှတစ်ဆင့် ရှင်းလင်းပါ) |
| မော်ဒယ် lockout      | မမ်မိုရီအတွင်းရှိ မော်ဒယ်ရရှိနိုင်မှု registry | `GET /api/resilience/model-cooldowns`     | `DELETE /api/resilience/model-cooldowns`                                 |

`PATCH /api/resilience` သည် `providerBreaker.oauth` နှင့် `providerBreaker.apikey` အောက်ရှိ provider breaker override များကို လက်ခံသည်။ Profile တစ်ခုစီသည် `degradationThreshold`, `failureThreshold` နှင့် `resetTimeoutMs` တို့ကို ပံ့ပိုးပြီး တူညီသော field များကို Dashboard → Settings → Resilience တွင်လည်း အသုံးပြုနိုင်သည်။

```bash
# မော်ဒယ် lockout တစ်ခုတည်းကို ရှင်းလင်းရန်
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -H "Content-Type: application/json" \
  -d '{"provider":"openai","model":"gpt-4o-mini"}'

# Lockout အားလုံးကို ရှင်းလင်းရန်
curl -X DELETE http://localhost:20128/api/resilience/model-cooldowns \
  -H "Cookie: auth_token=..." \
  -d '{"all":true}'
```

အယူအဆဆိုင်ရာ အကိုးအကားအပြည့်အစုံနှင့် breaker မူလတန်ဖိုးများအတွက် [`CLAUDE.md`](../../CLAUDE.md) → "Resilience Runtime State" နှင့် [`docs/architecture/RESILIENCE_GUIDE.md`](../architecture/RESILIENCE_GUIDE.md) ကို ကြည့်ပါ။

### Rate-Limit Queue နှင့် Auto-Enable လုံခြုံရေးအကာအကွယ်

- **ပံ့ပိုးထားသည့် ရေးသားမှုလမ်းကြောင်း**- body `{"connectionId": "<id>", "enabled": true|false}` ပါသော `POST /api/rate-limits` သည် ချိတ်ဆက်မှုတစ်ခု၏ rate-limit ကာကွယ်မှုကို အဖွင့်အပိတ်လုပ်ရန် ပံ့ပိုးထားသည့် စီမံခန့်ခွဲမှု endpoint ဖြစ်သည်။ `PUT /api/providers/[id]` သည် `rateLimitProtection` ကို ရည်ရွယ်ချက်ရှိရှိ ပြင်ဆင်ခြင်း သို့မဟုတ် အဖွင့်အပိတ်ပြောင်းခြင်း မပြုပါ (#11278)။
- **`enabled: false` ၏ အဓိပ္ပာယ်**- `enabled: false` ဟု သတ်မှတ်ခြင်းသည် ချိတ်ဆက်မှုအတွက် အတိအလင်းသတ်မှတ်ထားသော ကာကွယ်မှုကို ဖယ်ရှားပေးသော်လည်း လက်ရှိအသုံးပြုနေသည့် API-key ချိတ်ဆက်မှုကို ကမ္ဘာလုံးဆိုင်ရာ auto-enable လုံခြုံရေးအကာအကွယ် (`autoEnableApiKeyProviders = true`) မှ **ဖယ်ထုတ်မပေးပါ**။ `reconcileEnabledConnections` (`open-sse/services/rateLimitManager.ts`) တွင် `false` နှင့် `undefined` တို့သည် တူညီပြီး အတိအလင်းသတ်မှတ်ထားသော ကာကွယ်မှုမရှိသည့် လက်ရှိအသုံးပြုနေသော API-key ချိတ်ဆက်မှုများကို auto-enable လုံခြုံရေးအကာအကွယ်အောက်တွင် ဆက်လက်ကာကွယ်ထားသည်။
- **ကမ္ဘာလုံးဆိုင်ရာ ပိတ်ခြင်း**- Rate-limit queue များမပါဘဲ API-key ချိတ်ဆက်မှုများကို အသုံးပြုရန် `RATE_LIMIT_AUTO_ENABLE=false` (env) သို့မဟုတ် `resilienceSettings.requestQueue.autoEnableApiKeyProviders = false` (Settings → Resilience / `PATCH /api/resilience`) မှတစ်ဆင့် လုံခြုံရေးအကာအကွယ်ကို ကမ္ဘာလုံးဆိုင်ရာအဖြစ် ပိတ်ပါ။

## MCP ဆာဗာ

OmniRoute တွင် transport ၃ မျိုး (stdio, SSE, streamable-http) နှင့် နယ်ပယ်သတ်မှတ်ထားသော tools များပါဝင်သည့် embedded Model Context Protocol ဆာဗာတစ်ခု ပါရှိသည်။ အောက်ပါ dashboard endpoints များသည် အခြေအနေ/စာရင်းစစ်ဒေတာကို ဖတ်ရှုပြီး HTTP transports များကို proxy လုပ်ပေးသည်။

| နည်းလမ်း | လမ်းကြောင်း | ဖော်ပြချက် |
| ------ | ---------------------- | ------------------------------------------------------------------------------------------------ | -------------------- |
| GET | `/api/mcp/status` | Heartbeat၊ transport၊ online အခြေအနေ၊ နောက်ဆုံးခေါ်ဆိုမှု၊ ထိပ်တန်း tools နှင့် 24 နာရီအတွင်း အောင်မြင်မှုနှုန်း |
| GET | `/api/mcp/tools` | `name`, `description`, `scopes`, `phase`, `auditLevel`, `sourceEndpoints` တို့ပါဝင်သော MCP tools စာရင်း |
| GET | `/api/mcp/sse` | SSE transport အတွက် SSE stream ကို ဖွင့်ခြင်း (MCP ကို ပိတ်ထားပါက သို့မဟုတ် transport မကိုက်ညီပါက `503` ပြန်ပေးသည်) |

| GET | `/api/mcp/audit/stats` | စုစည်းထားသော စာရင်းစစ်ကိန်းဂဏန်းများ (စုစုပေါင်းများ၊ အောင်မြင်မှုနှုန်း၊ ပျမ်းမျှကြာချိန်၊ ထိပ်တန်း tools) |

## A2A ဆာဗာ

OmniRoute သည် A2A (Agent-to-Agent) JSON-RPC 2.0 endpoint တစ်ခုနှင့် စစ်ဆေးခြင်း/dashboard အသုံးပြုမှုအတွက် REST wrapper တစ်ခုကို ပံ့ပိုးပေးသည်။

### JSON-RPC

```bash
POST /a2a
Authorization: Bearer your-api-key   # optional unless OMNIROUTE_API_KEY is set
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "skill": "smart-routing",
    "messages": [{"role": "user", "content": "Route this coding task"}]
  }
}
```

ပံ့ပိုးထားသော method များ (အားလုံးသည် `settings.a2aEnabled` ကို ဖွင့်ထားမှ အသုံးပြုနိုင်သည်)-

| Method           | ဖော်ပြချက်                                                                       |
| ---------------- | -------------------------------------------------------------------------------- |
| `message/send`   | တစ်ပြိုင်တည်း skill လုပ်ဆောင်ခြင်း၊ `{task, artifacts, metadata}` ကို ပြန်ပေးသည် |
| `message/stream` | တူညီသော skill အစုကို Streaming SSE ဖြင့် လုပ်ဆောင်ခြင်း                          |
| `tasks/get`      | `taskId` ဖြင့် task တစ်ခုကို ရယူခြင်း                                            |
| `tasks/cancel`   | `taskId` ဖြင့် task တစ်ခုကို ပယ်ဖျက်ခြင်း                                        |

အသင့်ပါရှိသော skill များ- `smart-routing`, `quota-management`, `provider-discovery`, `cost-analysis`, `health-report`။

### Agent Card

```bash
GET /.well-known/agent.json
```

အများပြည်သူကြည့်ရှုနိုင်သော A2A agent card (အမည်၊ ဖော်ပြချက်၊ စွမ်းဆောင်ရည်များ၊ skill catalog၊ auth scheme) ကို ပြန်ပေးသည် — အများပြည်သူအတွက် 1h ကြာ cache သိမ်းထားသည်။ Auth မလိုအပ်ပါ။

### REST အကူများ

| Method | Path                         | ဖော်ပြချက်                                                                                                                         |
| ------ | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/api/a2a/status`            | A2A ဖွင့်ထားမှု + task စာရင်းအင်း + cache သိမ်းထားသော agent card အကျဉ်းချုပ်                                                       |
| GET    | `/api/a2a/tasks`             | Task များကို စာရင်းပြုစုခြင်း — `?state=submitted\|working\|completed\|failed\|cancelled`, `?skill=`, `?limit=` (≤200), `?offset=` |
| POST   | `/api/a2a/tasks`             | (REST အကူအဖြစ် မတည်ဆောက်ရသေးပါ — JSON-RPC `message/send` မှတစ်ဆင့် ဖန်တီးပါ)                                                       |
| GET    | `/api/a2a/tasks/[id]`        | Task တစ်ခုကို ရယူခြင်း                                                                                                             |
| POST   | `/api/a2a/tasks/[id]/cancel` | Task တစ်ခုကို ပယ်ဖျက်ခြင်း                                                                                                         |

**Auth:** REST အကူများသည် management auth မလိုဘဲ အလုပ်လုပ်သည် (dashboard မှ ဖတ်ရှုနိုင်သည်)။ JSON-RPC `/a2a` route သည် သတ်မှတ်ပြင်ဆင်ထားပါက Bearer `OMNIROUTE_API_KEY` ကို အသုံးပြုသည်။

| GET | `/api/evals/suites/[id]` | စိတ်ကြိုက် eval suite တစ်ခုကို ရယူခြင်း |

**Auth:** `/api/cloud/auth` သည် Bearer key တစ်ခုကို တိုက်ရိုက်အတည်ပြုပြီး `manage` / `admin` scope ပါရှိသော key အတွက်သာ connection တစ်ခုချင်းစီ၏ ဖုံးကွယ်ထားသော key နှင့် `projectId` ကို ပြန်ပေးသည်။ အခြား `/api/cloud/*`, `/api/evals/*` နှင့် `/api/assess` route များသည် management session/API key လိုအပ်သည်။ `/api/assess` POST သည် discriminated-union scope schema ပါသော `validateBody` ကို အသုံးပြုသည်။

## ACP (Agent Client Protocol) စီမံခန့်ခွဲမှု

child process များအဖြစ်။ ဤ endpoint များသည် ACP agent ရှာဖွေသတ်မှတ်ခြင်းနှင့် စိတ်ကြိုက် agent မှတ်ပုံတင်ခြင်းကို စီမံခန့်ခွဲသည်။

| နည်းလမ်း | လမ်းကြောင်း       | ဖော်ပြချက်                                                                                                                                                                                         |
| -------- | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET      | `/api/acp/agents` | ထည့်သွင်းထားမှုအခြေအနေ၊ version နှင့် binary တို့ပါဝင်သည့် သိရှိထားသော CLI agent များအားလုံး (အသင့်ပါရှိသော + စိတ်ကြိုက်) ကို စာရင်းပြုစုသည်                                                       |
| POST     | `/api/acp/agents` | စိတ်ကြိုက် ACP agent တစ်ခုကို မှတ်ပုံတင်သည် သို့မဟုတ် cache ကို ပြန်လည်ဆန်းသစ်သည် — body: `{id, name, binary, versionCommand, providerAlias, spawnArgs, protocol}` သို့မဟုတ် `{action: "refresh"}` |
| DELETE   | `/api/acp/agents` | စိတ်ကြိုက် ACP agent တစ်ခုကို ဖယ်ရှားသည် — query parameter: `?id=<agentId>`                                                                                                                        |

**တုံ့ပြန်ချက် နမူနာ** (`GET /api/acp/agents`):

```json
{
  "agents": [
    {
      "id": "claude",
      "name": "Claude Code CLI",
      "binary": "claude",
      "version": "1.0.45",
      "installed": true,
      "protocol": "stdio",
      "providerAlias": "claude",
      "isCustom": false
    },
    {
      "id": "my-custom-cli",
      "name": "My Custom CLI",
      "installed": false,
      "protocol": "stdio",
      "providerAlias": "my-provider",
      "isCustom": true
    }
  ],
  "cacheTtlMs": 60000,
  "cacheAge": 1234
}
```

**အထောက်အထားစိစစ်မှု:** စီမံခန့်ခွဲမှု session (dashboard `auth_token` cookie) သို့မဟုတ်
စီမံခန့်ခွဲမှုနယ်ပယ်သတ်မှတ်ထားသော API key တစ်ခု လိုအပ်သည်။

အသေးစိတ်အပြည့်အစုံအတွက် [ACP Framework](../frameworks/ACP.md) ကို ကြည့်ပါ။

## စစ်မှန်ကြောင်းအတည်ပြုခြင်း

အထောက်အထားအမျိုးအစား လေးမျိုး (ဒက်ရှ်ဘုတ် session၊ local CLI token၊ `oma_live_…` Access Token နှင့် စီမံခန့်ခွဲမှုဆိုင်ရာ အတိုင်းအတာသတ်မှတ်ထားသော API key) နှင့် ၎င်းတို့က inference key များနှင့် မည်သို့ကွာခြားသည်ကို သိရှိရန် [စီမံခန့်ခွဲမှုဆိုင်ရာ စစ်မှန်ကြောင်းအတည်ပြုခြင်း](../guides/MANAGEMENT-AUTH.md) ကို ကြည့်ပါ။

- ဒက်ရှ်ဘုတ် route များ (`/dashboard/*`) သည် `auth_token` cookie ကို အသုံးပြုသည်
- Login ဝင်ရာတွင် သိမ်းဆည်းထားသော password hash ကို အသုံးပြုပြီး၊ မရရှိပါက `INITIAL_PASSWORD` ကို အစားထိုးအသုံးပြုသည်
- `requireLogin` ကို `/api/settings/require-login` မှတစ်ဆင့် ဖွင့်/ပိတ်နိုင်သည်
- `REQUIRE_API_KEY=true` ဖြစ်သည့်အခါ `/v1/*` route များသည် Bearer API key ကို လိုအပ်နိုင်သည်
- ဤကိုးကားချက်တွင် "စီမံခန့်ခွဲမှု token" / "စီမံခန့်ခွဲမှုဆိုင်ရာ အတိုင်းအတာသတ်မှတ်ထားသော API key" ဆိုသည်မှာ အထက်ပါလမ်းညွှန်တွင် ဖော်ပြထားသည့် အမျိုးအစားများထဲမှ တစ်ခုကို ဆိုလိုခြင်းဖြစ်ပြီး သီးခြားသတ်မှတ်မထားသော လျှို့ဝှက်ချက်အမျိုးအစားတစ်ခုကို ဆိုလိုခြင်းမဟုတ်ပါ

> **နောက်ပြန်သဟဇာတမဖြစ်စေသော ပြောင်းလဲမှု (v3.8.0)** — `/api/v1/agents/tasks/*` နှင့် cooldown စီမံခန့်ခွဲမှု endpoint များသည် ယခုအခါ **စီမံခန့်ခွဲမှုဆိုင်ရာ စစ်မှန်ကြောင်းအတည်ပြုခြင်း** (ဒက်ရှ်ဘုတ် `auth_token` cookie သို့မဟုတ် စီမံခန့်ခွဲမှုဆိုင်ရာ အတိုင်းအတာသတ်မှတ်ထားသော API key) ကို လိုအပ်သည်။ ယခင်က စစ်မှန်ကြောင်းအတည်ပြုခြင်းမရှိဘဲ ဤ route များကို ခေါ်ဆိုခဲ့သော client များသည် `401 Unauthorized` ကို လက်ခံရရှိမည်ဖြစ်သည်။ commit `588a0333` (`fix(auth): require management auth for agent and cooldown APIs`) ကို ကြည့်ပါ။
